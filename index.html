Fun with uv and PEP 723

作者: deepakjois | 评分: 139 | 评论数: 17 | 发布时间: 2025-06-24 18:41
文章摘要

文章介绍了使用 **uv** 和 **PEP 723** 元数据简化 Python 脚本运行的新方法。 **uv** 是一个用 Rust 编写的高速 Python 包和项目管理工具，带有 **uvx** 命令，可自动处理虚拟环境、Python 版本和依赖包。 **PEP 723** 提出了一种在单文件脚本中嵌入元数据的方法，帮助启动器和 IDE 识别所需的 Python 版本和依赖。 结合 **uv** 和 **PEP 723**，可以轻松运行包含依赖的 Python 脚本，例如提取 YouTube 视频字幕的脚本。通过在脚本中加入 shebang 行 `#!/usr/bin/env -S uv run --script`，脚本可直接作为可执行文件运行，无需手动配置环境。这使得 Python 在处理一次性脚本时更加便捷和高效。

评论摘要
主要讨论点：Python 项目中使用 `uv` 工具进行依赖管理和脚本执行的可行性及优缺点 不同观点： • **支持观点**： - **易用性和速度**：[sambaumann]、[ACAVJW4H] 和 [jkingsman] 都提到 `uv` 的速度快，管理依赖简单，且不需要手动创建虚拟环境，极大地简化了工作流程。 - **实用性**：[satvikpendem] 和 [gigatexal] 认为 `uv` 使得 Python 脚本变得更易操作，尤其是在传递脚本和编写小工具时非常有用，类似于 Rust 中的单文件脚本管理。 - **比较优势**：[babuloseo] 表示 `uv` 比 Pipenv 更强大，简化了项目管理。 • **质疑和担忧**： - **文档和过渡支持**：[sambaumann] 指出 `uv` 的文档有待改进，尤其是从 `requirements.txt` 过渡到 `uv` 的路径不明确。 - **锁定文件和依赖固定**：[korijn] 担心没有锁定文件会导致未来的脚本因未固定的依赖版本而失效。 - **环境膨胀**：[kristianp] 质疑 `uv` 是否会为每个脚本创建单独的环境，从而导致系统臃肿。 • **中立和观望**： - **长期价值**：[kzrdude] 认为 PEP 723 可能只是一个噱头，而非真正有长期价值的工具。 - **工具的持久性**：[doctoboggan] 对 `uv` 是否只是一时潮流表示怀疑，倾向于使用内建工具。 • **与其他语言的对比**： - **Ruby 的内建支持**：[ali1ism] 提到 Ruby 的默认包管理器已经内建了类似功能，表明其他语言在这方面可能更为成熟。 - **Node.js 的生态优势**：[k__] 指出 Python 开发者曾羡慕 Node.js 的包管理生态，而 `uv` 似乎弥补了这一不足。 补充讨论： • **PEP 723 和 `uv` 的关系**：[Noumenon72] 和 [kzrdude] 对 PEP 723 的实际作用存在疑问，认为 `uv` 的功能可能依赖于第三方的支持，而非 Python 官方的实现。 • **对 shell 脚本的支持**：[ACAVJW4H] 提到 shell 脚本在依赖管理和可重复性方面仍然落后，希望有类似工具来改进。 争议焦点：`uv` 是否能作为一个持久且可靠的工具，还是仅仅是一个暂时的技术潮流。此外，对 PEP 723 和 `uv` 实现细节的理解也存在分歧。

The German automotive industry wants to develop open-source software together

作者: smartmic | 评分: 35 | 评论数: 6 | 发布时间: 2025-06-24 20:07
文章摘要

2025年6月23日，在第29届国际汽车电子大会（AEK）上，在德国汽车工业协会（VDA）的支持下，11家汽车行业公司签署了一份关于基于开源软件联合开发的谅解备忘录（MoU）。该合作旨在提高软件开发的速度和效率，同时确保高质量和安全性，以应对汽车软件日益复杂的需求。合作将专注于非用户直接接触且不具差异化的软件模块，通过开放和协作的生态系统进行开发。开发过程将遵循一种全新的开源开发流程，以确保功能安全并符合相关标准。软件开发将在Eclipse基金会的无厂商依赖环境中进行，作为S-CORE项目的一部分。该生态系统对欧洲和国际公司开放合作，预计2026年将提供用于自动驾驶平台的软件，供行业定制和系列开发使用。这一举措将帮助制造商专注于差异化功能，同时共同维护核心组件。VDA董事总经理Bollig博士表示，这一开放、透明和安全的软件生态系统将为行业创新奠定坚实基础。多家公司高管也对该计划表示支持和承诺。

评论摘要
主要讨论点：汽车行业在软件和用户界面（UI）开发中的技术选择和企业策略 不同观点： • [mathverse] 认为大多数公司使用 QT Auto 创建外观糟糕的界面，且使用廉价电子设备无法支持复杂的UI效果。同时指出中国公司在这方面做得更好，能够创建好看且实用的UI，并深入技术栈。 • [hengheng] 指出在企业内部，合理的技术选择往往与公司结构和决策不一致，并以Cariad项目（与Audi合作）的失败为例，质疑这种技术选择能否在公司内部政治中胜出。 • [ognarb] 认为使用开源组件（如KWin和Wayland compositor）是一个明智的选择，可以避免像转向Android Auto那样失去对关键体验组件的控制。 • [AlotOfReading] 认为当前的做法类似于重新发明AUTOSAR，虽然这是一个更好的技术基础选择，但并没有解决汽车行业在软件理解上的核心问题。 • [cadamsdotcom] 以幽默的方式表达了对Linux在汽车领域应用的乐观态度，称之为“Linux汽车之年”。 • [okokwhatever] 认为汽车公司（如VW、Audi、Mercedes-Benz）因过去多年高价销售不必要的汽车而失去市场份额，现在看到中国厂商在蚕食他们的市场，才开始反思技术选择。 补充讨论： • 讨论中涉及了企业内部技术选择与政治决策之间的矛盾，尤其是以Audi和Cariad项目为例。 • 对开源组件使用的支持与反对意见并存，部分观点认为使用开源可以保持控制权，而另一些观点则认为汽车行业整体在软件开发上存在理解不足的问题。 • 中国厂商的技术能力被认为是值得借鉴的，特别是在UI设计和硬件选择方面。

评论摘要
主要讨论点：Wayland与X11在处理DPI缩放和分辨率方面的差异与技术挑战 不同观点： • Pedrocr认为Wayland直接以目标分辨率渲染比现有的通过"先2倍渲染再缩小"的方法（受OSX启发并在Linux中被采用）更好。直接渲染避免了性能损失和模糊输出，只需要告诉应用渲染到某个像素缓冲区及输出缩放比例即可。这种方法更符合Wayland将任务委托给客户端的理念。 • Wmf指出缩放的难点在于UI元素如栅格图标或1px细线的非模糊绘制，而不仅仅是像圆形这种简单图形的绘制。 • Kragen提到GLX在网络上的表现问题，暗示X11在网络环境下的缩放和显示可能存在更多复杂性。 • Creatonez强调在古老GUI库的整个生态系统中处理缩放问题非常困难，尤其是在处理不同图标、文本和绘图方式时会遇到很多麻烦。 • Kunzhi对X11转发 over SSH 的功能表示赞赏，认为这是一种很酷且有用的功能，尽管现代已不太使用。 • Lelandbatey指出，当人们说“X11不支持DPI缩放”时，实际上是指大多数基于Xlib的程序不理解缩放。X11本身通过Xlib暴露的函数大多是像素坐标的，而缩放信息通常由RandR扩展提供。 • DonHopkins通过详细描述X11在设备独立性和图形绘制方面的诸多复杂性和历史问题，强调了X Window System在处理缩放和其他图形任务时的固有困难。 补充讨论： • 讨论中涉及了X11和Wayland在处理缩放时的哲学差异，X11的扩展和API复杂性，以及Wayland的潜在优势和当前实现中的挑战。 • 提到了一些历史和技术背景，比如Mac多显示器设置的趣闻和X11颜色处理的复杂性，进一步展示了图形系统演进中的问题和趣味。
