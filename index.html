How to Secure Existing C and C++ Software Without Memory Safety [pdf]

作者: aw1621107 | 评分: 24 | 评论数: 3 | 发布时间: 2025-03-31 07:36
文章摘要

该文章讨论了如何在不实现内存安全的情况下，提高现有C和C++软件的安全性。作者Úlfar Erlingsson指出，虽然内存安全能防止许多漏洞被利用，但对于未修改的C/C++软件，可以通过消除软件内存损坏时的执行交错来实现类似的安全效果。文章介绍了几种实用的编译器和运行时机制，这些机制无需特殊硬件支持，且开销较小，已经在一些平台上投入使用。通过在开发工具链中整合这些机制，可以显著增强C和C++软件对抗远程代码执行攻击的能力。

Taming the UB Monsters in C++

作者: ingve | 评分: 31 | 评论数: 3 | 发布时间: 2025-03-31 06:45
文章摘要

Herb Sutter的这篇文章讨论了C++在安全性和防护方面的进展，特别是针对未定义行为（UB）的改进。文章提到，C++社区正在努力解决UB问题，以增强软件的安全性。自C++11以来，越来越多的C++代码变得无UB。在即将发布的C++26中，编译时执行的代码已无UB，且标准库的常见越界错误也不再是UB。文章还提到，正在系统性地解决运行时UB问题，包括引入"错误行为（EB）"和"合约断言"等工具。Bjarne Stroustrup的配置文件框架也在开发中，旨在通过默认全安全选项并允许在必要时选择退出。此外，Úlfar Erlingsson提议通过一个配置文件来消除用于远程代码执行的UB。这些改进旨在解决C++中常见的内存安全和安全漏洞问题。

评论摘要
主要讨论点：C++语言中与生命周期相关的未定义行为（UB）问题的现有动态缓解措施及其局限性，以及这些措施在实际应用和未来发展的前景。 不同观点： • [roca] 认为当前并没有新的方法来防御与生命周期相关的UB问题。文章引用的研究只是对现有动态缓解措施的总结，而这些措施并不能在语言层面解决UB问题，且伴随着性能权衡。例如，指针完整性需要硬件支持，而像x86这样的架构并不支持。此外，即便像Chrome这样的成熟产品已经在尽可能地实施这些措施，但它们仍然担心C++ UB问题，表明这些缓解措施并不足够。 • [pjslp] 对C++语言缓解UB的努力表示欢迎，但认为现在才开始着手解决这个问题可能为时已晚。标准工作组和实际从事C/C++编译器开发的人员之间的交集很少，因此这些改进能否以及如何在编译器中实现还有待观察。不过，对于许多用C++编写的工具而言，它们很可能不会被重写成其他语言，因此任何改进都是受欢迎的。 补充讨论： • [techbrovanguard] 引用了对C++中UB问题的情绪阶段模型，从否认、愤怒、讨价还价、抑郁到接受，暗示技术评论家对C++能否有效解决UB问题存在不同情绪阶段的反应，并带有一些讽刺意味。 争议焦点：当前的动态缓解措施是否足够解决C++中的UB问题，以及这些措施在实际应用和未来编译器开发中的可行性和有效性。

Public secrets exposure leads to supply chain attack on GitHub CodeQL

作者: cyberbender | 评分: 250 | 评论数: 9 | 发布时间: 2025-03-30 19:54
文章摘要

本文介绍了GitHub CodeQL潜在供应链攻击的发现过程。攻击始于一个公开暴露的秘密，有效时间仅1.022秒。利用这一秒，攻击者可以在使用CodeQL的GitHub Actions工作流中执行代码，影响GitHub云平台和GitHub Enterprise。攻击者可能借此窃取私有代码库的源代码、盗取GitHub Actions中的凭证、在内网基础设施上执行代码，并进一步发动供应链攻击。 研究人员通过自建的Actions Artifacts Secret Scanner工具发现了这一漏洞（CVE-2025-24362）。GitHub Actions工作流会生成GITHUB_TOKEN，用于与代码库交互，若权限过高，令牌泄露将导致严重后果。尽管发现了潜在风险，GitHub表示尚未发现其平台或系统受到实际攻击的证据。

评论摘要
主要讨论点：GitHub Actions的安全性、临时令牌权限、CI/CD环境的分离以及自建CI系统的建议 不同观点： • [Sytten] 认为GitHub应推出不可变动作（immutable actions）以减少当前约70%的攻击风险。他提到这是解决GitHub Actions安全问题的关键，并暗示GitHub在这方面的进展缓慢。 • [nyrikki] 质疑临时令牌为何拥有创建新部署和生成工件证明的权限，指出GitHub的修复措施（禁用调试日志）未能解决临时令牌权限过大的问题。 • [ashishb] 主张将CI和CD环境完全分离，以防止CI的妥协导致CD相关令牌泄露，强调了两者分离的重要性。 • [udev4096] 建议不要使用公共GitHub Actions，认为分析工作流程序是必要的，并推荐使用自建CI系统（如Woodpecker、Circle、Travis、GitLab等）以提高安全性。 补充讨论： • [junto] 对GitHub的响应速度表示赞赏，认为其反应时间非常快。 • [helsinki] 提及个人对域名的兴趣，与主要讨论点无关。 • [ryao] 分享其在OpenZFS项目中使用CodeQL的经验，指出由于代码非保密，因此不存在相关问题。 • [atxtechbro] 直接询问问题是否已修复，未提供具体论据。 • [bloqs] 抱怨GitHub页面性能差，影响用户体验，但未涉及安全和技术细节。 争议焦点： - 临时令牌权限的适当性及其安全风险是讨论中的一个争议点，nyrikki指出GitHub的修复未完全解决问题。 - 使用公共GitHub Actions的安全性以及是否应使用自建CI系统是另一个争议点，udev4096强烈建议自建系统以提高安全性。 总结：讨论主要围绕GitHub Actions的安全性、临时令牌权限管理、CI/CD环境分离的必要性以及自建CI系统的优劣展开，各方对GitHub当前的解决方案和安全性措施存在不同看法。
