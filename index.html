HorizonDB, a geocoding engine in Rust that replaces Elasticsearch

作者: j_kao | 评分: 67 | 评论数: 10 | 发布时间: 2025-08-08 12:57
文章摘要

本文介绍了Radar公司如何使用Rust和RocksDB构建高性能的地理空间数据库HorizonDB，以替代原有的Elasticsearch和MongoDB架构。HorizonDB能够处理每日超过10亿次API调用，支持地理编码、搜索、路由和地理位置合规等多种功能，且在单核上能处理1000 QPS，前向地理编码中位延迟为50毫秒，反向地理编码中位延迟小于1毫秒。HorizonDB通过RocksDB进行高效数据存储，利用S2进行空间索引，并使用FSTs实现高效字符串压缩和前缀查询。该架构提升了性能，简化了操作，并降低了硬件成本，实现了地理空间服务的高效整合。

Getting Good Results from Claude Code

文章摘要

本文总结了作者使用LLM编程代理（尤其是Claude Code）进行编程实验的经验。作者在短时间内完成了约12个编程项目，认为没有Claude Code无法在相同时间内完成这些工作。尽管AI生成的代码常有错误或低效，作者强调自己对代码质量负责，并在专业环境中手动审查所有AI生成的代码和测试用例。 作者分享了获得良好结果的关键方法： 1. 提前编写清晰的规格说明，为代理提供上下文。 2. 创建项目结构文档，指导如何运行构建和代码检查。 3. 让代理进行代码审查。 4. 使用个人“全局”代理指南，概述最佳实践，如增量进展、学习现有代码、务实方法、简洁意图等。 指南还包括开发哲学、过程、技术标准和决策框架，强调测试驱动开发、代码质量和错误处理。作者建议在遇到问题时，记录失败尝试、研究替代方案、质疑基本原理，并尝试不同方法。最终，手动审查是验证代码行为和测试正确性的必要步骤。

评论摘要
主要讨论点：Claude Code在软件开发中的使用体验和技巧 不同观点： • **time0ut** 认为Claude Code相比其他工具（如Cursor和Q）更优秀。他分享了自己的使用流程：首先在web控制台与Claude进行头脑风暴，设定项目目标并分解里程碑，随后在Claude Code中开始项目并不断更新项目文档。他还提到，尽管有明确的指导，Claude有时会超前行动，因此需要保持专注，逐步构建项目。 • **aosaigh** 首次成功使用Claude Code后表示，明确的规范是成功的关键。他花了两个小时写下12步实施文档，Claude按步骤生成代码，节省了大量时间。他认为，中级和高级开发人员仍然不可或缺，因为成功的关键在于明确的指导和设计。 • **softwaredoug** 强调在代码中先手动实现模式和初步想法，然后让Claude按模式逐步实现功能。他发现，功能实现步骤过于庞大时，往往会出现意外的错误和不合理的重构。 • **bgirard** 在使用Claude Code开发ASCII版Factorio时遇到了一些问题。起初未严格监督代码，导致后续修复时引发新的问题。他还发现Claude在使用React和游戏引擎方面存在不足，需要手动干预和代码审查，最终项目进展变慢但质量提高。 • **iambateman** 分享了自己为Laravel开发的工具speedrun，帮助用户更好地利用Claude Code。该工具帮助用户先构建规范，然后通过子代理实现功能，并进行代码审查和最佳实践检查。 • **delichon** 发现让Claude对自己的代码进行审查非常有效。Claude往往能发现之前输出的问题并提供合理的理由，他希望这种双重检查能自动化。 • **berlinismycity** 认为将Claude Code纳入常规订阅是明智之举，相比从聊天窗口复制粘贴代码要高效得多，但如果需要通过API付费使用，则难以判断其价值。 补充讨论： • 多个用户提到Claude Code在生成代码时需要明确的规范和指导，且在项目规模较大时容易出现问题，因此建议逐步、增量式地进行开发。 • 一些用户分享了自己的使用技巧和工具，如iambateman的speedrun工具和delichon的代码审查方法，这些技巧能提高Claude Code的使用效率和代码质量。 • bgirard的经历表明，Claude Code在处理复杂项目和特定技术（如游戏引擎）时可能存在不足，需要开发者的手动干预和监督。

文章摘要

本文讨论了在Wayland环境下，应用程序如何通过XDG Activation协议请求窗口激活，而不能强制获取焦点。与X不同，Wayland要求应用通过获取XDG Activation token来请求激活，避免未经用户同意的窗口弹出。该token可以通过环境变量或DBus传递，且由 compositor 控制是否允许激活。KDE和Qt等工具包已适配这一流程，但仍有一些场景未正确实现，比如Dolphin和KRunner等应用在特定情况下未能正确请求激活。为确保应用行为正确，建议使用KWin的“Extreme”Focus Stealing Prevention模式进行测试和修复相关问题。

评论摘要
主要讨论点：窗口激活和焦点管理机制，特别是在Linux和Wayland环境下的行为 不同观点： • **支持焦点管理机制**： - dmart：赞赏Linux和Wayland的机制，认为macOS让自动更新程序随意夺取焦点的行为很糟糕。 - nh2：支持新的焦点管理机制，认为X11下经常误点弹窗很烦人，曾自行修补i3代码解决此问题，但非完美方案。 - nottorp：认为窗口管理器应决定焦点切换，而不是应用程序随意夺取焦点。 • **当前机制的不足**： - treve：虽然认为新的焦点管理机制是个好主意，但目前由于尚未全面应用，有时密码弹窗会隐藏在其他窗口后，体验仍待改进。 • **对话题的误解**： - rs186：最初误以为文章讨论的是Windows激活，导致阅读时产生困惑，直到重新理解标题。 - rekabis：认为标题有点击诱饵之嫌，因为通常“激活”一词更多用于Windows注册，容易引起误解。 • **比较不同系统的焦点管理**： - jovial_cavalier：指出X11下夺取焦点是可能的，但需要窗口管理器实现，比如其使用的dwm不会随意重新聚焦。 - webdevver：主张让自由市场决定焦点管理方式，认为Windows的机制相对无摩擦，用户可以通过选择不用某些应用来规避不良体验，建议Linux借鉴这种做法，而非增加权限和协议的复杂性。 • **技术实现的个人经验**： - burnt-resistor：提到维护Linux下的UI自动化测试非常痛苦，暗示对焦点管理问题有深刻体会。 - zb3：由于焦点管理逻辑，不得不写一个扩展以实现通过快捷键打开Firefox并使其获得焦点。 补充讨论： - andrewmcwatters：提到不仅讨厌窗口弹出夺取焦点，还特别提到带有自动聚焦元素的窗口，会双重夺取注意力，且缺乏防止误操作的机制。 - 链接分享：sho_hn提到之前在另一个讨论中开发者们的评论，提供了一个讨论线索。 争议焦点：窗口焦点管理机制的最佳实践，特别是在不同操作系统（Linux、Windows、macOS）之间的差异和取舍。用户体验和系统安全性、自由度的平衡是讨论的核心。

What Does Consulting Do?

作者: surprisetalk | 评分: 15 | 评论数: 5 | 发布时间: 2025-08-08 13:52
文章摘要

这篇文章通过分析比利时2002-2023年间的增值税相关数据，首次系统性地研究了管理与战略咨询行业。研究显示，咨询服务主要由大型、高劳动生产率的公司使用，且公司在雇佣咨询顾问时呈现出“U型”模式，即高绩效和低绩效公司都会聘用。新客户通常在不到一年的短期内花费约3%的工资总额在咨询服务上。研究发现，咨询对劳动生产率有3.6%的正面影响，主要通过轻微减少雇员并保持收入稳定实现。平均工资上升2.7%，且劳动价值占比未下降，表明生产率提升并非通过剥削工人实现。组织重组导致了解雇率的小幅上升和外包的减少。研究还表明，初始生产率较低的公司在咨询后生产率提升更大，支持了咨询提高生产效率的观点。

评论摘要
主要讨论点：咨询顾问的作用和价值 不同观点： • **mykarakus**：在一些风险规避的环境中，咨询顾问的部分职责是在关键决策需要做出时承担责任，以便在事情出现问题时成为被指责的一方。这表明顾问有时充当“背锅者”的角色。 • **binarymax**：咨询顾问的核心作用是推动决策的做出。公司雇佣顾问是因为他们自己不确定该如何决策或下一步该往哪里走。决策是否正确取决于顾问公司的能力和经验，以及一些运气因素。 • **calvinmorrison**：咨询顾问为缺乏专业知识的公司提供专业技能，他们只是专家。当公司雇佣大量顾问（如300名）时显得奇怪，但雇佣一个锅炉专家则是合理的。这强调了顾问在特定领域的专业性。 • **ausbah**：用学术论文来回答“你们到底在这里做什么”这个古老问题本身就带有自我解答的讽刺意味。这暗示了对咨询行业实际价值的质疑。 补充讨论： • **mgh2**：引用了外部文章讨论顾问的可替代性（Dispense costs, shift/take blame）以及咨询行业的 subjective value（主观价值）。提到的文章进一步探讨了咨询行业的价值和是否只是“充斥着废话”。 争议焦点： • 咨询顾问的核心价值和作用存在争议。一部分人认为顾问只是为了转移责任或填补公司内部的知识空白，而另一部分人则强调他们在决策过程中的重要性和专业性。 总结： 评论中对咨询顾问的作用和价值存在不同看法，有人认为他们主要负责决策和承担责任，有人则强调他们的专业技能和在特定领域的贡献，同时也有人质疑其整体价值和必要性。

Linear sent me down a local-first rabbit hole

作者: jcusch | 评分: 301 | 评论数: 29 | 发布时间: 2025-08-08 05:45
文章摘要

文章讲述了作者使用项目管理工具Linear后，对其快速响应的特性产生兴趣，进而研究"本地优先"（local-first）技术架构的经历。这种架构将数据存储在客户端本地数据库优先处理，再异步同步到服务器和其他客户端，从而消除网络延迟，实现即时响应。作者发现构建此类同步引擎涉及离线处理、冲突解决等复杂问题，并介绍了2025年可用的几种成熟解决方案，如Electric SQL、Jazz等，其中Jazz通过"协作值"等创新设计让开发者能轻松构建实时协作应用。文章展现了local-first技术如何颠覆传统Web应用架构，提升用户体验。

评论摘要
主要讨论点：本地优先（Local-First）软件开发及其相关技术与工具的优劣分析 不同观点： • **对低延迟交互的质疑**：incorrecthorse 认为 Linear 这样的工具因为其极快的响应速度而受到赞誉，反映出当前 web 开发中对低延迟的过度理想化，认为这是一种不合理的标准。 • **本地优先的技术挑战**：nicoritschel 指出，尽管本地优先和同步项目在技术上令人印象深刻，但在实际应用中可能过于理想化。例如，在浏览器中运行真实数据库（如 sqlite 或 pglite）时，存在数据持久性问题，特别是 Safari 对 OPFS 的激进清理策略。他认为，将缓存存储在用户目录中可能是一个解决方案。 • **同步与实时协作的处理**：thruflo 和 jeremy_k 强调了本地优先工具在处理同步和协作方面的能力。thruflo 提到 Electric 现在支持本地写入和事务性乐观突变。jeremy_k 分享了使用 Zero 工具实现类似 Google Sheets 的实时协作体验，指出这种方法极大地简化了数据同步和 UI 更新。 • **本地优先架构的优势与限制**：Cassandra99 开发了一个基于 CRDT 的开源任务管理软件，强调了本地优先架构的优势，如数据本地存储带来的快速响应，简化的功能开发，以及轻量级的服务器端逻辑。但也指出了其局限性，包括对大文件存储的支持不足和同步代码的复杂性。 • **本地优先在不同平台的适用性**：sergioisidoro 和 petralithic 讨论了本地优先技术在不同平台上的适用性。sergioisidoro 认为本地优先工具在复杂项目中可能难以维持，而 petralithic 则指出这些工具更适合移动端，因为移动设备可能经常没有网络连接。 • **本地优先工具的实际应用**：CafeRacer 和 rylan-talerico 分享了他们在实际项目中使用本地优先工具的经验。CafeRacer 使用 Dexie 和 RxJS 组合，认为这种方法减少了复杂性。rylan-talerico 推荐了 InstantDB，认为它是实现本地优先的良好选择。 补充讨论： • **本地优先的未来与工具选择**：mentalgear 认为本地优先和同步引擎是未来趋势，并提供了一个本地优先框架的概览。他还提到了 Triplit.dev、PowerSync 和 NextGraph 等工具。 • **本地优先与静态托管的结合**：antgiant 正在开发一个需要在没有互联网连接情况下使用的浏览器应用，尝试将本地优先与静态托管结合，但发现当前的工具仍以服务器为中心。 • **历史技术的比较**：mkarliner 提到 Meteor 是一个类似于本地优先的旧技术，曾用于一些重大项目。 争议焦点： • **本地优先工具是否过于理想化**：一些开发者认为本地优先工具在技术上令人印象深刻，但在实际应用中可能过于理想化，特别是在复杂的实时协作和同步场景中。 • **本地优先技术在不同平台上的适用性**：讨论中对本地优先工具在 web 和移动平台上的适用性存在不同看法，一些人认为移动端更适合，而 web 端通常有网络连接。 • **本地优先架构的复杂性与收益**：一些开发者强调了本地优先架构带来的技术挑战和复杂性，如数据同步和冲突解决，而另一些人则强调了其带来的用户体验优势和开发简化。
