Tree Borrows

作者: zdw | 评分: 41 | 评论数: 2 | 发布时间: 2025-07-09 14:40
文章摘要

本文介绍了Rust编程语言中用于处理不安全代码的新模型——Tree Borrows。Rust以其基于所有权的类型系统著称，提供内存安全和数据竞争自由等强保证，但“不安全”代码块需手动维护安全。为确保编译器优化正确性，需明确定义何为“不良”不安全代码。先前模型Stacked Borrows设定了相关规则，但排除了现实中常见的一些模式，且未考虑Rust借用检查器的最新高级功能。Tree Borrows通过将Stacked Borrows的栈结构替换为树结构，解决了这些问题，减少了被拒绝的测试案例数量，并证明能保留大部分优化，还支持新的优化如读-读重排。该研究获得了PLDI'25的杰出论文奖。

Why LLMs Can't Write Q/Kdb+: Writing Code Right-to-Left

作者: gabiteodoru | 评分: 88 | 评论数: 16 | 发布时间: 2025-07-08 10:40
文章摘要

文章讨论了大型语言模型（LLMs）在编写q/kdb+代码时遇到的困难，主要问题在于评估顺序的不同。q/kdb+及其祖先语言如APL、J、k采用从右到左且无运算符优先级（RL-NOP）的评估方式，而LLMs在这种方式下表现不佳。例如，在处理表达式时，LLMs常混用Python和q的语法，导致错误。文章还指出，尽管右到左书写在代码中是必要的，但LLMs不擅长这种模式，因为它们的训练数据中q代码相对稀缺，且这种训练可能需要对模型架构进行重大修改。由于经济激励不足和训练数据的匮乏，行业不太可能为这些小众语言重新训练大型模型。文章最后提出了一种实用解决方案，即引入Qython作为桥梁，以帮助LLMs更好地处理RL-NOP语言的代码编写。

评论摘要
主要讨论点：LLM（语言模型）在编写代码时的思维方式、方向性（从左到右或从右到左的评估）以及在不同编程范式中的表现。 不同观点： • FeepingCreature认为，LLM（如Claude）在编写Python代码时会放入不必要的import，因为它会预先猜测可能需要的模块，这是一种对未来需求的预防性措施。 • clord指出，编写代码的过程可能是非线性的，人类程序员有时从数据或最终返回值开始编写，再逐步回推到输入。当前的LLM可能缺乏这种非线性思考的能力，只能按照线性顺序输出，未来可能会有改进。 • trjordan认为，问题可能与训练数据集的大小有关，并建议对q/kdb+等语言的错误进行量化分析，以探讨语言方向性对LLM表现的影响。 • leprechaun1066反驳方向性是问题核心的观点，认为q语言难以掌握是因为其编程思维方式与常见的命令式语言不同，LLM若过度训练于命令式风格，可能会在q等语言中遇到困难。 • briandw提到扩散模型可能具备处理非线性生成能力，例如扩散编码模型，但目前尚未在右至左评估上进行尝试。 • electroly认为APL语言的书写顺序（类似堆叠函数调用）不符合现代编程习惯，NumPy通过点状函数调用修正了这一问题，并推测若APL在现代开发，可能会更倾向于左至右的评估。 • grej对新兴的扩散模型表示兴趣，认为这些模型可能提供更好的解决方案。 • vessenes认为，右至左评估需要从末端开始或在工作记忆中保持表达式，这对LLM来说较为困难，并推测扩散模型可能在这方面表现更好。 • cess11质疑LLM是否真的能遵循规则引擎，并指出本地模型在处理不同编程语言时容易混淆，认为LLM SaaS在软件开发中的应用有限。 • ape4提到新Apple AI可能具备乱序输出的能力，或许能解决此问题。 • roschdal表示，自己可以选择但不习惯从右至左编写代码。 • yujzgzc反问，如果从右至左的编程方式更实用，人类应该早已采用。 • rob_c认为，LLM不理解所有语言的根本原因是训练不足，并预计未来多语言模型会表现更好。 补充讨论： • 讨论中涉及LLM在不同编程语言和范式中的局限性，尤其是命令式与非命令式语言之间的差异。 • 对未来模型改进的期望，包括非线性生成和多语言处理能力的提升。 • 争议焦点在于方向性是否是LLM编写代码时的主要障碍，部分参与者认为问题更复杂，涉及训练数据和编程范式。

Ruby 3.4 frozen string literals: What Rails developers need to know

作者: thomas_witt | 评分: 119 | 评论数: 13 | 发布时间: 2025-07-06 09:58
文章摘要

Ruby 3.4开始逐步引入冻结字符串字面量，默认情况下现有代码不受影响，但可以通过启用弃用警告来提前准备未来的变化。变化分为三个阶段：3.4版本引入可选警告，3.7版本默认启用警告，4.0版本默认冻结字符串字面量。冻结字符串可以带来性能提升，如减少垃圾回收和内存使用。开发者需要关注依赖的gem可能出现的警告。要查找问题，可以在开发环境中启用警告，并使用测试套件进行检查。常见需要修改的模式包括字符串构建和就地修改等。对于新代码，建议直接编写适应冻结字符串的代码，而对于现有应用则无需急于移除魔法注释。

评论摘要
主要讨论点：Ruby字符串默认冻结的改变及其影响 不同观点： • **支持并理解该改变**： - maximegarcia 指出，默认冻结字符串能优化垃圾回收（GC），减少每次声明字符串时的内存分配。尽管会促使开发者倾向于不可变操作（可能导致更多字符串分配），但通过手动处理（如使用 `+"My String"`）可以绕过这一问题。 - skywhopper 认为，Ruby团队经过多年逐步引导开发者适应这一改变，方法得当，尽量减少了对用户的干扰。 • **对该改变的质疑与担忧**： - ttoinou 提出疑问，动态类型和解释型语言是否应该像静态类型语言一样进行大量优化？并质疑如果Ruby一开始就具备这些复杂特性，是否还能取得成功。 - llamataboot 提到Python 2到3的过渡教训，担心这次改变也会带来类似的“依赖地狱”问题，尽管性能提升明显，但过渡过程可能依然痛苦。 • **技术实现的讨论**： - meisel 对Ruby如何在底层实现字符串冻结和去重机制表示好奇，询问是否通过维护一个全局字符串映射或引用计数来实现。 - _flux 提到OCaml也经历了从可变字符串到只读字符串的过渡，虽然初期有些波折，但静态类型检查帮助解决了问题。此外，OCaml提供了一个开关让旧代码可以继续运行。 • **对社区反应的评论**： - jbverschoor 表示对线程中关于可变字符串的误解感到无奈。 - ksec 认为，如果Shopify和GitHub这样的大公司都已经测试并接受这一改变，那么Rails社区应该也能很好地适应。 • **对版本过渡的疑问**： - baggy_trough 对Ruby 3.7/4版本的过渡计划表示不确定，提到除了这篇博客外，没有看到其他地方描述该计划。 • **对历史经验的反思**： - samgranieri 希望这次改变能比关键字参数的过渡更加顺利。 补充讨论： - bitbckt 提到Twitter早在15年前就进行了类似的优化，暗示这一改变是迟早要发生的。 - 整个讨论还涉及不同编程语言（如Python和OCaml）在类似改变上的经验，以及社区和工具（如Rubocop）对这种改变的支持。

文章描述了Helm中的一个高危安全漏洞（CVE-2025-53547），影响版本<= 3.18.3。当存在恶意构造的`Chart.yaml`和`Chart.lock`文件时，更新依赖项可能导致本地代码执行。如果`Chart.lock`文件被symlink到可执行文件（如`bash.rc`），更新依赖时会将恶意内容写入该文件，导致 unwanted 执行。该问题已在Helm v3.18.4中修复。临时解决方案是确保`Chart.lock`不是symlink。CVSS评分8.5，表示高严重性，需要用户交互但无需特殊权限。

Most RESTful APIs aren't really RESTful

作者: BerislavLopac | 评分: 86 | 评论数: 33 | 发布时间: 2025-07-09 07:04
文章摘要

这篇文章主要讨论了Roy Thomas Fielding的论文《架构风格与基于网络的软件架构设计》，该论文介绍了代表性状态转移（REST）架构风格，旨在设计可扩展、高性能和可维护的网络系统，特别是Web服务。Fielding分析了多种网络架构风格的优缺点，强调REST专注于可扩展性、简洁性和适应性。他指出，REST是一种提供原则和约束的架构风格，而非具体的技术实现，如HTTP动词或CRUD风格API。 文章澄清了关于REST的常见误解，例如REST不等于CRUD，资源也不仅仅是持久化实体。Fielding特别强调了超媒体作为应用状态引擎（HATEOAS）的重要性，认为没有超媒体控制的API不能称为RESTful。HATEOAS通过动态发现链接减少客户端与服务器的耦合，提高系统的可演化性。 此外，文章解释了REST中的“资源”概念，指出资源是信息的抽象映射，而非具体的服务器实体，URI的语义由创建者定义，而非客户端或服务器需要理解的内容。

评论摘要
主要讨论点：REST和RESTful API的实际应用及其与理论定义的差距 不同观点： • cjpearson认为，REST API这个术语已经发生了语义扩散，实际使用中与Fielding论文中的原始定义不符。他指出，现代所谓的"REST API"通常返回JSON，使用CRUD操作映射到HTTP方法，并且在状态码使用上常常存在争议。他主张要么坚持原定义，要么接受现实，按常用理解使用该术语。 • mixedbit分享了自己的经验，指出他在深入研究Fielding的论文后发现，真正的REST在实际应用中并不总是有用。他认为Fielding的论文没有提供完整的自发现API构建方案，最终实现的自发现API往往缺乏客户端代码重用，且与特定应用的API无异。他还提到，REST的目标与良好的用户体验可能不兼容。 • _heimdall认为，REST和HATEOS在第三方作为API消费者时更有意义，而对于特定前端应用的后端API，REST的成本往往超过其收益。 • salmonellaeater指出，REST API设计适用于用户通过代理（如浏览器）导航和交互的场景，而不是针对特定Web应用的API设计。这类API更适合公开信息和交互的政府门户或开放数据项目。 • dwaltrip质疑HATEOAS的实用性，认为没有真正的客户端能够利用自动发现的API，并质疑这种客户端的必要性。 • Scarblac强调，UI设计师需要对页面外观进行详细控制，而RESTful API的自发现特性与此需求不符。 • nchmy建议通过更易懂的资源学习REST相关概念，并提供了一些参考链接。 • sublinear认为，通过引用schema定义（如JSON Schema）实现API动态导航在现实中存在问题，并质疑是否有必要在JSON响应中包含复杂的链接信息。 • osigurdson幽默地指出，集体忽视了Fielding的论文，只是喜欢使用"REST"这个词来描述HTTP/JSON的任意应用。 • makeitdouble支持实用主义，建议避免使用"RESTful"这个术语，而改用"HTTP based APIs"。 • pradn理解了Fielding的REST原则，认为其核心在于动态发现和抽象实体，允许API以更动态和通用的方式使用。 • bravesoul2反对REST和GQL，认为RPC风格更实用，强调应根据实际需求选择API风格，而非强制适应某种风格。 • 0x445442认为，REST在实践中只是通过JSON通信的分布式功能调用，开发和维护 nightmare。 • layer8认为，文章没有提供有力论据支持Fielding的REST定义应被视为标准，并指出该定义对非交互式客户端不适用，这也是其未被广泛采用的原因。 补充讨论： • cowsandmilk提到其所在公司将实际操作称为HTTP绑定，反映了业界对REST定义的实际应用差异。 争议焦点：REST的理论定义与实际应用的差距，以及HATEOAS的实用性和必要性。
