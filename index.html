I write type-safe generic data structures in C

作者: todsacerdoti | 评分: 150 | 评论数: 19 | 发布时间: 2025-06-30 16:55
文章摘要

本文介绍了在C语言中实现类型安全的通用数据结构的方法。作者展示了一种利用联合（unions）来关联类型信息的技术，通过实现一个简单的链表来说明。文章比较了三种不同的通用性实现方式： 1. **通用头文件**：使用宏定义来实现，但会导致代码可读性和维护性差，二进制体积增大，且需要使用类型前缀函数。 2. **使用void***：通过void指针实现通用性，但不类型安全，且存在内存和性能问题。 3. **内联存储**：使用柔性数组成员存储数据，解决内存和性能问题，但需要传递数据大小。 最后，作者提出了**类型检查**级别，通过使用带有payload成员的联合来实现类型安全的通用数据结构，确保编译时捕获类型错误。这种方法结合了类型安全和高效内存管理。

评论摘要
主要讨论点：C语言中泛型编程的实现及其相关问题 不同观点： • **o11c**：认为在C中实现泛型时，使用`uint64_t data[]`对于对齐要求大于`uint64_t`的类型是不正确的，而对于对齐要求小于`uint64_t`的类型则是浪费内存。此外，指出了在没有`typeof`的情况下，无法安全地返回值，并且现有的解决方法可能会导致`const`相关的错误。同时提到，无法省略`payload`，因为需要它来确定正确的数据大小。 • **layer8**：指出函数类型的强制转换假设了项目指针类型（如`Foo*`）与`void*`具有相同的表示形式，但C标准并不保证这一点，这会导致未定义行为，并影响编译器的别名分析。 • **gritzko**：反对上述观点，认为通过一些技巧可以创建一个完整的C方言，并提供了一个通用二叉堆的示例，认为这种方式可以得到非常普通、可预测和可优化的C结构体。 • **cherryteastain**：质疑为何不直接使用C++来实现“带有泛型的C”，而非要通过各种复杂方法在C中实现泛型。 • **mfuzzey**：提到Linux内核中使用的嵌入`list_head`的方法，也是一种实现泛型的思路。 • **eqvinox**：分享了他们使用大型宏定义包装器的方法，认为这是实现侵入式数据结构的必要手段，并提供了一个哈希表包装器的示例。 补充讨论： • **uecker**：提到已经在实验库中使用了类似的技巧。 • **HexDecOctBin**：指出C23标准中引入的新特性可以解决部分类型安全问题，并提供了相关文档链接。 • **hgs3**：好奇这种方法如何应用于哈希表，特别是如何对键进行哈希计算和比较。 • **monkeyelite**：提出另一种思路，即不尝试编写泛型数据结构，而是根据具体使用情况简化数据结构，认为数组是最重要的数据结构。 • **ape4**：建议使用CFront翻译成C代码的方式。 • **asplake**：分享了正在开发的基于ML风格标记变体的C语言生成器的教育项目，并计划未来进行兼容性测试。 • **b0a04gl**：质疑如果两个类型具有相同的大小和对齐方式但语义不同（如`int` vs `float`），类型标签系统是否能防止意外的重用，即如何防御结构碰撞。 争议焦点： • 对于C中实现泛型的最佳方法存在分歧，一部分人支持使用特定的技巧和宏定义，另一部分人则认为直接使用C++是更优的选择。 • 关于函数指针类型强制转换是否会导致未定义行为及其对编译器别名分析的影响存在争议。 • 对于类型标签系统能否有效防御结构碰撞存在疑问。

文章摘要

评论摘要
主要讨论点：Qualcomm芯片调试功能的实现及其安全性 不同观点： • **mmastrac的观点**： - 认为新的调试体验比以前的Qualcomm调试体验要好得多，以前的调试接口是通过USB暴露的读/写/执行原语，安全性极差，可以让用户轻松获得root权限。 - 指出大多数移动芯片组的调试端口严重不足，MediaTek的设备仍然使用旧的方法，需要通过一些特殊的操作来暴露串行接口。 - 认为Qualcomm开始让调试功能变得更易用，但大多数OEM厂商会禁用该功能，尤其是Google不支持在终端用户设备中启用调试功能。 • **tripdout的观点**： - 关注生产设备上该调试功能的实现，提到OnePlus 6虽然禁用了该功能但仍然可以访问。 - 提出如何在生产版的OnePlus 6上读取eFuse的问题，并提到Qualcomm签名的EDL加载器。 - 提到在SM4350设备的设备树中有eud_enable_reg，并计划通过重新编译内核来访问/dev/mem。 • **dazhbog的观点**： - 对Qualcomm的定制芯片设计表示惊讶，描述了其通过寄存器控制的自定义硅片，当启用时，会重定向ARM的USB引脚，添加一个USB集线器，并在集线器上添加SWD编程器和串行端口，连接回ARM核心的I/O。 补充讨论： - 调试功能的实现细节及其在不同设备上的访问方式是讨论的焦点，尤其是如何绕过OEM厂商的限制。 - 安全性是另一个重要话题，特别是以前调试接口的严重安全性问题，以及未来可能如何被厂商限制或禁用。 - 技术细节如eFuse的读取、设备树中的特定寄存器、以及内核编译方法是技术爱好者和开发者关注的重点。 争议焦点： - 调试功能的易用性与安全性之间的平衡，尤其是OEM厂商和Google出于安全考虑可能会禁用该功能，而技术爱好者则希望能够保持访问调试功能的能力。

文章摘要

《Donkey Kong Country 2》在旧SNES模拟器ZSNES中存在一个知名bug：某些关卡的旋转桶无法正常控制。具体表现为，当角色跳入桶中后，按方向键本应控制桶的旋转，但在ZSNES中，轻触方向键会导致桶无限旋转，直到按反方向键才会停止。这个bug使游戏难度增加，因为旋转桶常出现在尖刺等危险上方。 该问题源于ZSNES未正确模拟"开放总线"行为。这种行为发生在读取无效内存地址时，CPU会重新读取上次在数据总线上的值。SNES的CPU是65816，其复杂的内存分页和地址处理进一步增加了模拟难度。 这个问题曾在ZSNES论坛上讨论，但论坛已下线，而另一个模拟器Snes9x通过硬编码修复了此问题。ZSNES由于长期未更新（最后版本于2007年发布），该bug一直未被修复。
