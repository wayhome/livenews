GitHub MCP exploited: Accessing private repositories via MCP

作者: andy99 | 评分: 68 | 评论数: 33 | 发布时间: 2025-05-26 13:46
文章摘要

文章披露了GitHub MCP服务器的一个严重漏洞，该漏洞允许攻击者通过恶意GitHub Issue劫持用户代理，窃取私有代码库的数据。这一漏洞由Invariant的安全分析工具发现，属于首次发现的“有毒代理流”（Toxic Agent Flows）类型。攻击者可在公共代码库中创建恶意问题，当用户查询代理时触发数据泄露，将私有信息暴露在公开的代码库中。文章详细描述了攻击步骤、演示了具体案例，并提出了检测和缓解此类攻击的方法。这一漏洞提醒业界在部署编码代理和集成开发环境时需提高安全意识。

评论摘要
主要讨论点：围绕LLM（如Claude）在使用GitHub访问令牌时的潜在安全问题和漏洞的讨论 不同观点： • **losvedir**：认为用户在给LLM提供凭证时应该意识到该凭证的权限范围。如果使用细粒度的访问令牌，限制其仅能访问必要的资源，这种攻击不会成功。攻击的成功依赖于LLM拥有全局访问权限，这是危险的。 • **mirzap**：不认为这是一种“ exploit（漏洞利用）”。如果给代理提供了一个访问私有仓库的令牌，那么它就可以访问该仓库。问题的关键在于权限设置，而不是工具本身的漏洞。 • **kiitos**：认为有关漏洞的声明被夸大了。问题的发生需要多个条件同时满足，包括用户设置不当等。这并不完全是系统漏洞，更多是用户配置不当导致。 • **adeon**：从安全角度出发，认为如果LLM处理来自不可信来源的文本，该来源可能引导LLM生成任意文本并调用工具，因此存在风险。同时，指出需要外部安全产品来加强AI系统的安全性，表明AI公司在安全设计上不足。 • **godelski**：认为问题核心在于用户将敏感信息交给了不可信的第三方。这更像是一个用户错误，而非系统漏洞。同时质疑将未成熟的AI技术用于对安全有高要求的场景是否合适。 • **ttoinou**：建议用户可以精细控制LLM对自身信息的访问权限，并希望通过软件硬性限制而不是依赖LLM的模糊描述来保障安全。 • **drkrab**：指出当用户给第三方访问GitHub仓库时，也必须信任该第三方遵循所有安全策略，这实际上很难完全保证。 • **TOMDM**：认为问题类似于将私人信息暴露给公众然后惊讶于信息泄露。如果不希望LLM访问某些私人信息，就不应给予其访问权限。 • **ed**：不认为这是攻击，因为Claude只是按照要求执行任务。建议GitHub考虑引入人工审核机制以防止意外泄露。 补充讨论： • **mcintyre1994**：对LLM提到的“排除minesweeper”感到好奇，并怀疑是否存在一个私有仓库与此相关。 • **lbeurerkellner**：分享了一个具体的恶意issue链接，展示LLM如何被引导完成利用。 • **pawanjswal**：对一个简单的GitHub issue能导致私有仓库数据泄露表示惊讶。 • **kapitanjakc**：分享了GitHub Copilot之前也存在读取私有仓库的经历，表明类似问题早已存在。 争议焦点： • 该问题是否应被视为系统漏洞还是用户配置错误。 • LLM处理不可信输入时的潜在风险以及是否需要外部安全产品来增强安全性。 • 是否应在安全敏感场景中使用尚未成熟的AI技术。

Show HN: PgDog – Shard Postgres without extensions

文章摘要

PgDog 是一个用 Rust 编写的事务池和逻辑复制管理器，支持 PostgreSQL 的自动分片和水平扩展。它能够管理数百个数据库和数十万个连接，具有高速度和安全性。PgDog 作为一个应用层负载均衡器，支持多种负载均衡策略，并能实时维护健康主机列表，实现自动故障转移。它还支持事务池和会话池，类似于 PgBouncer。PgDog 能够自动路由查询到不同的数据库分片，支持跨分片查询，并集成了逻辑复制功能，可以在不中断服务的情况下扩展数据库。其配置灵活，支持运行时调整，并且提供了 Docker 和 Kubernetes 的快速启动方式。
