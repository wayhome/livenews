Don't animate height

作者: birdculture | 评分: 63 | 评论数: 13 | 发布时间: 2025-07-19 20:44
文章摘要

本文讲述了作者在开发笔记应用Granola时，发现应用在MacBook上占用60% CPU和25% GPU，最终发现问题源自一个CSS高度动画。作者解释了如何通过Chrome开发工具找到昂贵的动画，以及为何某些动画会如此消耗资源。浏览器渲染CSS动画时，涉及布局、绘制和合成三个步骤，而动画高度会触发布局重算和重绘，是开销最高的属性。相比之下，使用transform和opacity等合成属性开销最小。作者通过将高度动画替换为transform动画，成功解决了性能问题，CPU和GPU使用率大幅下降。文章最后提到下一步将介绍使用Chrome的about://tracing工具进一步优化性能。

评论摘要
主要讨论点：网页动画性能与资源消耗问题 不同观点： • Eric_WVGG和alterom认为高度动画的性能开销令人震惊，尤其是与几十年前的游戏相比，现代网页动画的资源消耗显得不成比例。Eric_WVGG提到自己早已不再使用高度动画，而采用类似的变换技术。 • bob1029和andrewstuart提供了技术建议，提到可以使用CSS的`contain`和`will-change`属性来优化性能，以及Chrome可能正在进行高度过渡的优化。 • HWR_14和Liftyee关注硬件性能，HWR_14特别提到即使使用M2芯片的Mac在渲染网页时也会消耗大量资源，而几十年前的游戏却能更快速地渲染图形。Liftyee则表示理解了为何简单的网页会消耗大量资源。 • jtangelder和jasonjmcghee提出了替代方案，jtangelder建议使用简单的GIF动画，而jasonjmcghee认为可以使用小型的canvas来实现动画。 • h1fra提出一个简单的问题，询问将父div设置为绝对定位是否能解决合成问题。 • JakeSc关注未来的开发环境，建议在开发时加入内置验证机制以提高性能，并提到LLM（大型语言模型）在编码中的应用。 • dvt对整个讨论持批评态度，认为现代初创公司忽视了核心功能，过度关注无关紧要的动画性能问题，并指出文中对布局/绘制/合成的描述存在误解。 • zahlman提出一个具体问题，质疑一个笔记应用为何需要音频可视化功能。 补充讨论： • 讨论中多次提到Electron应用的性能问题，dylan604和dvt都认为Electron应用普遍存在资源浪费的问题。 • 争议的焦点在于现代网页技术在处理简单动画时的性能开销是否合理，以及开发者是否应更关注核心功能而非动画性能优化。

Go allocation probe

作者: blenderob | 评分: 57 | 评论数: 4 | 发布时间: 2025-07-22 14:45
文章摘要

本文介绍了作者通过编写一个名为`go_allocation_probe`的工具，分析Go程序中堆分配的具体类型。Go的性能分析工具可以显示分配发生的位置，但不会记录分配的类型。为了解决这个问题，作者利用`bpftrace`和`uprobe`钩取Go运行时中的`mallocgc`函数，捕获每次分配的类型和大小。 Go的每个堆分配都会经过`mallocgc`，通过钩取该函数，作者能够记录分配的类型指针（`TypePtr`）和名称偏移（`NameOff`），以及分配的次数和总大小。然而，`NameOff`只是类型名称的偏移量，需要进一步解析。 作者通过解析Go可执行文件的符号和节区，从`.noptrdata`和`.rodata`节中提取类型名称，最终将偏移量转换为可读的类型名称，从而帮助识别出哪些类型导致了大量内存分配。

评论摘要
主要讨论点：Go 语言中的内存分配问题，特别是字符串在堆上的分配以及 escape analysis 相关的话题。 不同观点： • fsmv 认为在 Go 中避免将字符串分配到堆上非常困难。他提到即使在确保循环中只使用固定内存量的情况下，传递给 fmt 函数的字符串仍然会被移到堆上，因为 interface{} 类型的参数会被视为逃逸，导致堆分配。他还引用了相关的 GitHub 问题单（#8618）来支持自己的观点。 • jasonthorsness 对 fsmv 使用的 bpftrace 工具表示兴趣，认为通过函数的分配行为通常可以猜测出内存分配的来源，并赞赏了 fsmv 使用 bpftrace 获取所需信息的方法。不过，jasonthorsness 并没有直接讨论 Go 的 escape analysis 问题，而是对工具的使用表示关注。 • 90s_dev 提出了一个与主讨论点不直接相关的问题，询问在 Go 团队的一次问答活动中，人工智能是否对选择 Go 语言而非其他解决方案产生了影响或提供了建议。这表明他对 Go 语言的选择背景有兴趣，但并没有参与到内存分配技术细节的讨论中。 补充讨论： • 争议的焦点主要集中在 Go 语言的 escape analysis 和字符串分配行为上。fsmv 认为字符串容易逃逸到堆上，这与 Go 的设计机制有关，而 jasonthorsness 则关注如何通过工具分析和追踪这些分配问题。 • fsmv 引用的 GitHub 问题单（#8618）可能提供了一个更广泛的社区讨论背景，显示这个问题在 Go 开发者中是已知的并且曾被讨论过。 • 90s_dev 的提问引出了一个不同的讨论方向，即 Go 语言在选择和使用过程中是否受到人工智能的影响，但这在当前评论中并没有得到解答或进一步讨论。

AI Market Clarity

文章摘要
