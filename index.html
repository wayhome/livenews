For the love of god stop using CPU limits in Kubernetes

作者: iljanevo · 评分: 35 · 评论: 13 · 2026-08-14 10:41

文章摘要

文章分析 Kubernetes CPU 限制的负面影响：CPU limit 通过 CFS 配额周期性冻结容器，即使节点有空闲资源，也会造成延迟升高、启动变慢，且平均 CPU 指标可能掩盖节流。建议保留 CPU requests 以保障公平份额，移除 CPU limits；内存 limits 仍应保留。合理调整 requests 可提升性能、减少节点并降低成本，并需分阶段实施、监控节流指标。

展开评论摘要
主要讨论点：Kubernetes 中是否应取消或减少 CPU limits，以及 CPU requests、调度公平性、运行时配置和多租户隔离之间的权衡。 不同观点： • **反对普遍使用 CPU limits**：认为 limits 会导致性能下降、CPU throttling 和调度开销；CPU 密集型工作负载可单独安排到节点组。有人指出这一观点早在2018年就已提出，并非新鲜内容。 • **支持保留 CPU limits**：limits 能限制单个 Pod 的资源占用，避免一次错误变更耗尽节点 CPU，保护多租户环境中的其他服务，控制故障影响范围。 • **强调取消 limits 的运维风险**：许多语言和运行时（如 Go、Java、.NET）会根据可见 CPU 数量自动配置线程池。取消 limits 后，程序可能误启动256个线程而非4个，导致边界场景性能恶化；这要求团队主动配置、沟通并强制执行。 • **质疑 requests 是否足够公平**：讨论 CPU request 的“保证”如何落实：Linux 调度器是否会按 1 CPU 与16 CPU 的请求分配时间，还是仍需依赖 cgroups。 • **强调系统整体责任**：无论是否设置 limits，都必须考虑同节点其他 Pod；资源限制和健康检查本身也常成为生产事故来源。 补充讨论：评论普遍认为原文论证不充分、带有明显 AI 生成痕迹，且忽略维护成本与调度器开销。争议焦点是性能优化与资源隔离、稳定性之间应如何取舍。
