We should all be using dependency cooldowns

文章摘要

这篇文章主要讨论了依赖冷却期（dependency cooldowns）在开源供应链安全中的重要作用。作者指出大多数开源供应链攻击的有效期很短（通常不到一周），而设置依赖冷却期（如7-14天）可以显著减少这类攻击的影响。文章强调了依赖冷却期的三个优点：实证有效、易于实现（可通过Dependabot等工具免费设置）以及能促使安全供应商更快报告问题。尽管不是万能解决方案，但作者认为广泛采用依赖冷却期是缓解大多数供应链攻击的简单有效方法。

评论摘要
主要讨论点：[是否应该立即更新依赖项，还是采用“冷却期”策略] 不同观点： • **支持冷却期策略**：认为立即更新依赖项会增加供应链攻击的风险，建议监控依赖项的漏洞并根据实际需要更新。例如，[layer8]提到大多数漏洞只有在特定情况下才可被利用，不必急于更新。[compumike]进一步分析了更新可能引入新漏洞的风险，建议根据SemVer版本号调整冷却期长度。 • **反对冷却期策略**：认为延迟更新会积累技术债务，并可能错过重要的安全补丁或功能更新。[gbin]指出等待他人解决问题是“公地悲剧”，可能导致更痛苦的升级过程。[jayd16]和[abalone]质疑冷却期期间会暴露于已知漏洞。 • **折中观点**：认为应根据项目具体情况和依赖项的特性灵活选择策略。[cmckn]强调安全需要具体情况具体分析，而非盲目遵循“最佳实践”。[OhMeadhbh]提出可以通过“测试期”的概念来平衡冷却期和更新压力。 补充讨论： • **生态系统差异**：[gr4vityWall]提到Debian的稳定版模型在某些快速发展的生态系统中不适用，如Node.js缺乏类似apt的包管理支持。 • **依赖项管理**：[cosmic_cheese]和[programmertote]建议减少依赖项的数量和复杂性，以降低安全风险。 • **更新文化争议**：[DrScientist]和[BrenBarn]批评了盲目更新的文化，认为新版本未必更安全或更好。 • **攻击者策略**：[xg15]警告攻击者可能利用冷却期策略，通过制造紧急更新请求来植入恶意代码。
