Supabase MCP can leak your entire SQL database

作者: rexpository | 评分: 296 | 评论数: 29 | 发布时间: 2025-07-08 17:46
文章摘要

文章指出Supabase MCP（Model Context Protocol）存在安全漏洞，可能导致整个SQL数据库泄露。具体而言，攻击者可以利用LLM系统中的"致命三要素"攻击——访问私有数据、执行恶意指令和外传数据。在Supabase场景中，Cursor助手使用高权限的`service_role`访问数据库，若攻击者提交包含恶意指令的 support ticket，可能诱导系统读取私有数据并外泄。虽然Supabase文档建议使用只读模式来降低风险，但作者认为应更明确警示此类攻击的潜在威胁。

评论摘要
主要讨论点：Supabase MCP中的提示注入问题及其解决方案和争议 不同观点： • gregnr（Supabase工程师）： - 已经采取了多项缓解措施，如默认设置为只读、在SQL响应外包裹提示以防止LLM执行注入指令，以及编写E2E测试以验证LLM不会受到攻击影响。 - 目前正在研究更多细粒度的权限控制和更多文档说明，以帮助用户了解攻击风险。 - 强调这些只是缓解措施，提示注入问题尚未完全解决。 • tptacek： - 认为提示注入问题类似于XSS攻击，是由于管理应用程序处理未经过滤的用户生成内容引起的。 - 将经典的XSS问题与LLM提示注入进行了类比，指出两者都是内部管理应用的常见问题。 • simonw： - 建议将数据库访问MCP配置为只读，以防止攻击直接损害数据。 - 强调要小心组合其他MCP，尤其是那些可以对外通信的MCP，以防止数据泄露。 • consumer451： - 引用了具体的攻击技术和提示示例，展示了攻击者如何通过精心设计的消息进行攻击。 • joshwarwick15： - 认为这些攻击本质上都是未受信任的输入、秘密和工具调用问题，MCP只是加速了影响的显现，但并非根本原因。 - 讨论了模型提供者和应用程序开发者在缓解此类攻击中的角色。 • pests： - 指出支持站点通常是许多攻击的载体，回顾了过去类似的攻击案例。 • sshh12： - 惊讶于这些类型的攻击在实际生产中并不常见，指出尽管这些攻击广为人知，但官方文档中并未明确提及。 • coderinsan： - 分享了在Neon DB MCP中发现的类似漏洞，表明这些问题并非Supabase独有。 • TeMPOraL： - 认为将LLM拟人化有助于理解其问题，指出LLM作为通用系统，其问题和不足是根本性的。 • yard2010： - 对cursor助手通过service_role操作Supabase数据库并绕过行级安全保护表示担忧。 • qualeed： - 质疑为何允许用户生成支持工单指令AI代理操作数据，认为这不应成为可能。 • akdom： - 指出MCP应用中缺乏更好的授权控制是关键问题，建议更细粒度的权限控制和动态调整以减少攻击面。 • borromakot： - 对LLM持乐观态度，但困惑于为何使用Supabase MCP时没有类似“开发沙盒”的凭据，仅访问开发/暂存数据。 - 对提示工程作为缓解措施感到困惑和不解。 • imilk： - 对Supabase的安全性表示担忧，基于过去一年未修复的开放认证问题。 • losvedir： - 对“致命三重奏”的框架表示不安，认为第三点不应仅限于数据泄露，恶意写入操作同样严重。 补充讨论： - 讨论的焦点在于如何有效缓解提示注入攻击，包括技术解决方案（如权限控制和文档说明）和概念性理解（如拟人化和问题本质）。 - 争议点包括MCP在加速攻击中的角色以及提示工程作为缓解措施的有效性。 - 多个评论提到了对官方文档和实际生产环境中安全措施的担忧。

Breaking Git with a carriage return and cloning RCE

作者: dgl | 评分: 276 | 评论数: 18 | 发布时间: 2025-07-08 17:48
文章摘要

这篇文章讨论了CVE-2025-48384漏洞，该漏洞影响Unix类平台上的Git。当用户使用`git clone --recursive`克隆不受信任的代码库时，可能导致远程代码执行。漏洞源于Git处理配置文件时对回车符（CR）和换行符（LF）的处理不当。Git的配置格式支持DOS换行符（CR+LF），但在特定情况下，Git会错误地处理以回车符结尾的值，可能导致控制字符被引入文件路径中。攻击者可以利用此漏洞，在子模块路径中插入恶意控制字符，从而在克隆过程中执行任意代码。为避免此问题，用户应更新到Git的修复版本，并谨慎处理不受信任的代码库。

评论摘要
主要讨论点：Git子模块漏洞及远程代码执行的可能性，配置文件解析问题，以及不同系统对文件名中控制字符的处理问题。 不同观点： • [armchairhacker] 对文章中提到的“远程代码执行”表示质疑，认为文章夸大了漏洞的严重性。他提到该漏洞类似于CVE-2024-32002，但未提供具体证明（PoC）。他指出该漏洞可以让恶意仓库通过Git钩子在clone操作时执行代码，而正常情况下git clone不会安装这些钩子。 • [10000truths] 认为使用自定义DSL（领域特定语言）进行配置是问题根源之一，因为缺乏正式的语法规范，导致解析和序列化实现可能不同步，从而引发漏洞。他建议应保持唯一的数据源以生成相关配置。 • [acheong08] 成功复现了该问题并提供了示例，指出尽管已更新Git版本，但Arch Linux等平台尚未及时推送更新，可能导致大多数用户无法及时修复该问题。 • [Lockal] 质疑Git为何不使用Landlock进行权限控制，建议`git clone`操作应限制为只读访问配置目录和读写克隆目录，且不应允许子进程。他批评当前每个漏洞演示都展示了通过git执行任意代码的可能性。 • [deanc] 担心Homebrew可能因为递归克隆而受到该漏洞影响，并提供了相关代码链接以供验证。 • [mrheosuper] 幽默地指出在2025年仍然存在换行符不统一的问题，暗示这是技术债务。 • [dwheeler] 认为该漏洞的根本原因是Linux和Unix系统允许文件名中包含控制字符，从而增加了编写正确代码的难度。他提到POSIX最近的一些改进（如xargs -0和find -print0）有助于解决此问题，并计划继续开发其"safename" Linux模块以增强系统安全性。 补充讨论： • 关于漏洞的紧急性和修复状态：[acheong08]、[therealmarv] 和 [lossolo] 都提到Git版本更新滞后问题，尤其是Homebrew和Debian Bookworm等平台仍提供易受攻击的版本。 • 历史背景和技术反思：[JdeBP] 通过引用历史文献和相关技术分析，指出该问题早在20世纪末就被研究过，但至今仍未彻底解决。 • 非技术性讨论：[smaudet] 提到博客字体阅读体验不佳，属于非核心但值得注意的用户体验问题。 • 对Git设计决策的批评：[b0a04gl] 强烈反对Git在clone时运行子模块钩子的设计，认为这是不安全的，即便没有CRLF bug，这种行为也极具风险。 争议焦点：该漏洞是否真的能实现“远程代码执行”，以及Git设计上是否应允许在clone时执行子模块钩子。

Xenharmlib: A music theory library that supports non-western harmonic systems

作者: retooth | 评分: 46 | 评论数: 1 | 发布时间: 2025-07-08 22:37
文章摘要

Xenharmlib 0.3.0 是一个支持传统和非传统音乐理论的Python库，特别适用于非十二平均律系统的微音程和宏音程调音。它易于使用且可扩展，支持西方和非西方音阶系统、非标准记谱法以及音程、音阶的分析与调制建议。该库还提供对波尔-皮尔斯调音的群论分析等功能。Xenharmlib 并非用于乐谱编写或合成，而是专注于和声关系的科学探索，采用函数式编程原则，对象为不可变类型。未来计划包括支持更多记谱法、高级后调性分析和Just Intonation等。该库基于GNU Public License v3发布，源代码托管于Gitlab，并有Discord社区支持。

评论摘要
主要讨论点：音乐国际化（music-i18n）的实现，特别是对非西方音乐元素的支持以及与现有音乐格式（如MusicXML和MIDI）的兼容性。 不同观点： • ksr认为音乐国际化类似于软件领域中对世界语言和地区的支持，提出整个项目名为"music-i18n"。他强调了支持全球不同音乐传统和元素的重要性，并列举了一些关键的技术需求。 • 支持非十二平均律（non-ET tunings）的必要性。ksr指出，许多非西方音乐使用不同于西方十二平均律的调音系统，因此在音乐国际化过程中需要特别关注这些调音系统的支持。 • 支持四音音列（tetrachords）和其他音阶构件（如阿拉伯音阶ajnas）。ksr认为，不同文化的音乐往往基于不同的音阶结构，软件需要能够处理这些基本构件，以实现对全球音乐的全面支持。 • 关于MusicXML的导入/导出。ksr关心如何在现有音乐格式（如MusicXML）中整合这些国际化音乐元素，以便在不同音乐软件之间进行无缝的数据交换。 • 关于导出到MIDI。ksr还提到了MIDI导出的重要性，因为MIDI是广泛使用的音乐数据格式，确保国际化音乐元素能够正确导出到MIDI格式中是一个关键的技术挑战。 补充讨论： • ksr对音乐国际化的整体规划和具体技术需求表现出浓厚的兴趣，并希望了解更多关于这些方面的计划和想法。这表明在音乐软件开发中，国际化和对非西方音乐元素的支持是一个复杂而多方面的问题，涉及调音系统、音阶结构、以及与现有音乐格式的兼容性。 • 值得注意的是，ksr的评论中并没有直接的争议或反对意见，更多的是提出了一系列技术问题和需求，以推动音乐国际化项目的发展。
