文章摘要

SearXNG是一个开源的元搜索引擎项目,在GitHub上拥有3.3万星标。它聚合来自Google、Bing、DuckDuckGo、Yahoo等多个搜索服务的结果,核心特点是注重用户隐私保护——既不追踪用户也不建立用户画像。 该项目主要使用Python开发(占81.7%),采用AGPL-3.0开源许可证。提供完整的安装和配置指南,支持自主部署。社区活跃,拥有3.1千个分支和160名关注者。 这是一个"去Google化"(degoogle)的隐私友好型搜索解决方案,适合重视搜索隐私的用户和组织使用。

评论摘要
主要讨论点：SearXNG 元搜索引擎的使用体验、可靠性问题及替代方案 不同观点： • **长期满意用户**：部分用户自托管 SearXNG 多年，体验优秀并强烈推荐。有用户将其集成到 Kubernetes 部署方案中，认为表现出色。 • **遇到问题用户**：有用户反映 SearXNG 存在引擎频繁失败、速度慢的问题。尝试 Degoog 替代后发现结果更差，陷入"速度与质量"的两难选择。 • **技术方案探讨**：有用户推荐 TinySearch 作为封装方案，特别适合 AI agent 使用，能优化上下文节省 tokens。另有用户指出使用 Brave Search API 效果好，但爬虫模式不可靠，Google 引擎近期失效。 • **替代方案支持者**：部分用户使用公共托管实例（如 searx.be）或转向 Brave search，也有人偏好 4get 等其他替代工具。 补充讨论：核心争议在于 SearXNG 的可靠性——自托管用户体验良好，而使用公共实例或特定配置的用户遇到稳定性问题。讨论还涉及自托管 vs 托管实例的选择，以及在不同场景（个人搜索、AI 集成）下的最佳实践。

FreeBSD ate my RAM

作者: theanonymousone | 评分: 51 | 评论数: 9 | 发布时间: 2026-07-03 19:08
文章摘要

这篇文章探讨了为什么在现代操作系统中准确报告内存使用情况比看起来复杂。 **核心观点**：操作系统会将磁盘数据缓存到RAM中以提升性能，但这些缓存是可回收的，因此"未使用的RAM就是浪费的RAM"。 **技术细节**：FreeBSD的虚拟内存系统将物理内存划分为不同的页面队列： - **active**：正在被进程使用 - **inactive**：暂时未访问的页面 - **laundry**：准备写入swap的页面 - **wired**：内核使用的不可交换内存（包含磁盘缓存） - **free**：完全未使用的内存 **关键结论**：判断"空闲"内存很困难，因为inactive队列和部分wired内存（如ZFS的ARC缓存）实际上都是可回收的，在需要时会被释放。这就是为什么不同工具显示的内存使用情况会有差异。

评论摘要
主要讨论点：FreeBSD内存管理行为及其与Linux的比较，特别是关于ZFS文件系统的缓存机制 不同观点： • **技术解释派（naturalmovement）**：认为这是ZFS缓存的正常行为，用户安装企业级文件系统后就应该预期其工作方式不同，批评原帖缺乏"可学习的时刻" • **Linux支持派（shevy-java）**：以此为例说明选择Linux的理由，暗示FreeBSD作为替代操作系统面临更大挑战，竞争力下降 • **技术比较派（jmclnx）**：关注技术细节，询问FreeBSD的swap使用逻辑是否仍保持优于Linux的优势 • **积极反馈派（duendefm）**：单纯表达对原帖质量的认可 补充讨论： 评论中存在明显的操作系统立场分歧。争议焦点在于：这是FreeBSD/ZFS的设计特性还是用户体验问题？naturalmovement认为用户理应了解企业级文件系统的特性，而shevy-java的评论暗示这种"不同行为"恰恰是FreeBSD的劣势。另有评论者关注教育话题（教科书保留）和推荐相关技术文章。
