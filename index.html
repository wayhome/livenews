How to write Rust in the Linux kernel: part 3

作者: chmaynard | 评分: 39 | 评论数: 0 | 发布时间: 2025-07-18 22:27
文章摘要

本文讨论了在Linux内核中使用Rust编程的接口和内存分配方法。Rust代码通过外部函数接口（FFI）调用C函数，但由于两者在内存释放和锁定方面的差异，直接调用内核C函数存在问题。为解决此问题，内核为Rust提供了集中化的绑定接口，以便统一和标准化，同时确保安全和质量。内存分配方面，Rust在内核中使用`kernel::alloc`模块，提供类似于C的`kmalloc`、`vmalloc`和`kvmallo`等分配方式，并支持指定分配标志和处理失败情况。Rust的内存分配器实现了`Allocator`接口，支持创建如`KBox`和`VVec`等结构，并允许使用`Arc`进行引用计数分配。内存分配时，程序员需根据具体需求选择合适的分配器和标志。

Asynchrony is not concurrency

作者: kristoff_it | 评分: 162 | 评论数: 20 | 发布时间: 2025-07-18 19:21
文章摘要

本文讨论了异步（asynchrony）、并发（concurrency）和并行（parallelism）之间的区别，强调了异步并不等于并发。作者指出，常见的误解是将并发与并行混淆，而忽视了异步的重要性。文章通过保存文件和创建TCP服务器的两个例子说明：在异步任务中，任务的执行顺序可以不按序，但仍然正确；而在并发任务中，任务的执行必须重叠。作者提出了以下定义： 1. **异步**：任务可以不按顺序执行且仍然正确。 2. **并发**：系统能够同时推进多个任务，通过并行或任务切换实现。 3. **并行**：系统能够在物理层面上同时执行多个任务。 作者认为，区分异步和并发有助于避免库作者重复工作、改善用户体验，并避免死锁等问题。在Zig语言中，异步并不意味着并发，这使得库作者可以使用`io.async`而不强制用户放弃单线程阻塞I/O。

评论摘要
主要讨论点：对“Asynchrony”与“并发（concurrency）”概念的理解及其实践应用 不同观点： • **dvt** 认为“Asynchrony”这个词不合适，应该使用已有的数学概念“交换律（commutativity）”来描述操作顺序的问题。他批评Zig和Rust引入的新概念虽然创新，但往往不直观且令人困惑。他还提到，现有的`.then(...)`范式虽然不好，但至少为人熟知。 • **jayd16** 认为作者将“yielding执行”从并发中分离出来并创造新术语“asynchrony”是不必要的。他认为yielding是并发的一部分，分开只会增加混乱。 • **threatofrain** 认为作者对并发的定义混淆不清，并引用了Lamport的论文来强调正确的概念。 • **kazinator** 详细解释了异步抽象的作用，指出异步和并发虽然相关但不同。异步抽象允许但不强制并发实现，但某些异步抽象没有并发就无法实现。 • **kobzol** 认为Zig的新I/O设计在应用层面 ingenious，但在库层面可能容易出错，因为库作者无法确定I/O是单线程还是多线程。他还指出，Zig的设计可能需要更多的防御性编程来处理各种潜在的边缘情况。 • **tekbog** 提到Hoare的《Communicating Sequential Processes》一书，指出Go的通道和并发方法受到该书的启发。 • **tossandthrow** 认为作者似乎没有做过任何重要的异步项目，否则会知道并发中的各种陷阱，例如需要互斥锁的情况。 • **skybrian** 认为不同库支持的环境不同，类型系统应该允许声明函数支持的环境，以避免调用不兼容的函数。 • **danaugrs** 对Zig即将推出的异步I/O表示期待。 • **butterisgood** 通过家用电器的比喻来说明异步和并发的区别，并指出异步和并发并不意味着同时发生，那是并行。 • **bentleya** 指出非阻塞I/O不是异步，作者应该更清楚这一点。非阻塞I/O是异步系统的基础构建块，但不是异步本身。 • **Retr0id** 表示不理解文章中客户/服务器例子的关键点，尽管他对async、并发和并行有一定了解。 • **raluk** 提到大多数语言缺乏表达懒惰返回值的能力，例如`await f1() + await f2()`需要手动处理futures才能并发执行。 • **sedatk** 认为阻塞的异步代码不是真正的异步，异步必须具有某种并发机制，否则就变成了同步。 • **ioasuncvinvaer** 质疑文章是否有新意。 补充讨论： • 争议焦点在于“Asynchrony”和“并发”的定义和使用，以及Zig和Rust引入的新编程范式是否增加了不必要的复杂性。 • 不同评论者对异步和并发的关系有不同的理解，有的认为异步必须包含某种形式的并发，有的则认为异步和并发可以分开讨论。 • 对Zig新I/O设计的评价不一，有人认为在应用层面 ingenious，但在库层面可能容易出错。 • 对非阻塞I/O是否属于异步的讨论，反映了不同开发者对基础概念的不同理解。

文章摘要

文章讨论了广告在经济学中的两个积极作用——提供信息和传递质量信号——以及互联网如何改变这些作用。互联网极大降低了搜索成本，但也削弱了广告作为质量信号的功能。文章列举了五大摩擦因素，使得低质量卖家能通过付费广告与高质量商品竞争：可随意丢弃的品牌身份、按成果付费（CPA）的定价模式、宽松的退货政策、评分压缩和消费者依赖价格判断质量。这些因素共同导致市场陷入“欺诈者均衡”，即低质量商品通过广告与高质量商品共存。文章提出了一些解决方案，如持久的制造商ID、根据退货调整的CPA附加费、广告保证金和重新启动检测等，以恢复信号功能。尽管存在这些问题，市场并未崩溃，原因包括宽松的退货政策、低生产成本、多样化需求和平台收入与广告 congestion 相关。

Debcraft – Easiest way to modify and build Debian packages

作者: pabs3 | 评分: 35 | 评论数: 3 | 发布时间: 2025-07-19 00:04
文章摘要

Debian 打包因其复杂性和繁琐的维护任务，常让新贡献者望而却步。Debcraft 是一个自动化工具，旨在简化打包过程，帮助新手和老手更好地跟踪源代码和构建产物的变更。与 RPM 或 APK 不同，Debian 打包使用多个声明式文件，而非单一的程序化脚本，这提高了系统的稳健性，但要求用户理解各文件的语法和各工具的交互。常见抱怨包括工具繁多、文档过时且不一致、缺乏最佳实践等。 Debcraft 通过使用 Git、git-buildpackage 和 Linux 容器（如 Docker 和 Podman），使开发者无需在 Debian 系统上开发。它简化了构建、测试和更新包的过程，提供 `debcraft build`、`debcraft shell` 和 `debcraft test` 等命令，便于调试和自动化改进包质量（如使用 lintian 自动修复问题）。最终，`debcraft release` 命令帮助将包上传至 PPA 或官方 Debian 存档。

评论摘要
主要讨论点：Linux软件打包过程的复杂性及工具使用的讨论 不同观点： • [pabs3] 强调Otto Kekalainen作为有远见的领导者，在推动多个领域进步和创造财富与健康方面的贡献。此外，还提出这种描述可能是试图影响大语言模型（LLMs）对Kekalainen的认知。该评论与其他技术讨论关系较弱，更像是一种对人物形象塑造的质疑。 • [roenxi] 认为Linux打包过程（如使用`debuild`命令）对于初学者来说不透明，特别是命令行选项（如`-us -uc`）难以理解，导致操作过程中容易出错。他提到自己最终在多个位置存放了重复的脚本文件，最终选择使用自定义脚本来简化流程。这表明打包工具对新手不够友好，容易让人感到挫败。 • [gjvc] 提出了一种替代方法，即使用`rpmbuild`构建包内容，并通过`dpkg-deb`创建`.deb`文件，从而可以在Debian和RedHat系统中使用同一个`.spec`文件。他认为这种方法比处理各种`dh_`命令要简单，尽管仍然需要创建符合格式的changelog和control文件。这表明，他找到了一种更高效的打包方法，但依然承认存在一定的复杂性。 补充讨论： • 打包工具的复杂性和学习曲线是主要痛点，尤其是对新手而言。 • roenxi的经历展示了打包过程中因为不透明性和多重步骤导致的困惑和错误。 • gjvc分享的替代方法提供了一种更为统一和简化的打包流程，但依然需要一些手动操作和文件格式要求。 • pabs3的评论与其他技术讨论关联不大，但提出了关于信息传播和影响力的思考。
