How a 20 year old bug in GTA San Andreas surfaced in Windows 11 24H2

作者: yett | 评分: 539 | 评论数: 21 | 发布时间: 2025-04-23 14:00
文章摘要

文章描述了在Windows 11 24H2版本更新后，《GTA: San Andreas》游戏中的Skimmer飞机无法生成的问题。最初有用户报告该问题，并怀疑与SilentPatch有关。然而，经过多方测试，发现无论是否安装该补丁，问题都存在于Windows 11 24H2中。通过进一步调试，发现问题根源在于游戏代码中处理螺旋桨叶片角度的循环出现错误，导致游戏冻结。具体原因是叶片速度值异常高，导致浮点运算溢出。该问题仅在Windows 11 24H2中出现，更新前版本则无此问题。最终确认是操作系统更新引入的API问题，而非游戏或模组本身所致。

CubeCL: GPU Kernels in Rust for CUDA, ROCm, and WGPU

作者: ashvardanian | 评分: 22 | 评论数: 2 | 发布时间: 2025-04-23 23:19
文章摘要

CubeCL 是一个用于 Rust 的高性能多平台计算语言扩展，旨在简化高效可移植计算内核的编写。通过利用零成本抽象，开发者可以编写可维护、灵活且高效的计算内核。CubeCL 支持函数、泛型和结构体，并部分支持特征、方法和类型推断，未来计划扩展对 Rust 语言基本类型的支持。用户可以通过 `cube` 属性标记函数使其在 GPU 上运行，例如 `gelu_array` 和 `gelu_scalar` 函数。CubeCL 支持多种 GPU 运行时，包括跨平台的 WGPU、NVIDIA 的 CUDA 和 AMD 的 ROCm（开发中），并计划开发支持 SIMD 指令的 JIT CPU 运行时。其核心功能包括自动向量化、编译时计算和自动调优，旨在提升代码的可组合性、可重用性、可测试性和可维护性，同时保持最佳性能。CubeCL 还专注于通过重用缓冲区来优化内存管理，并致力于构建 Rust 高性能科学计算生态系统。

评论摘要
主要讨论点：CUbeCL与OpenCL等其他类似项目的对比，特别是在跨平台代码执行和性能优化方面的差异。 不同观点： • [zekrioca的观点]：对CUbeCL项目表示兴趣，并提出其与OpenCL的比较。他认为OpenCL的核心思想是"write once, run everywhere"（一次编写，到处运行），并询问CUbeCL是否因为在Rust中进行的内部优化（尤其是在编译时优化）而有所不同。他关注的是CUbeCL在Rust中的编译时优化如何提升性能。 • [LegNeato的观点]：提供了Rust和GPU生态系统中其他项目的比较链接，暗示CUbeCL可能与其他Rust项目存在功能或性能上的差异，并建议通过该链接了解CUbeCL与其他项目的具体对比情况。他关注的是CUbeCL在整个Rust和GPU生态系统中的定位和区别。 补充讨论： • 争议的焦点：目前没有直接的争议，但隐含的讨论焦点可能是CUbeCL相对于OpenCL等成熟技术的优势，特别是在跨平台执行和编译时优化方面的具体差异和实际效果。 • 重要论据和例子： - OpenCL作为"write once, run everywhere"的典型例子，被用作比较CUbeCL的基准。 - 提供了Rust和GPU生态系统中其他项目的比较链接，帮助进一步理解CUbeCL的独特之处。 • 讨论关系：zekrioca提出了关于CUbeCL和OpenCL对比的具体问题，LegNeato则通过提供更多资源来扩展讨论，帮助更全面地理解CUbeCL在更广泛的生态系统中的位置。

Yagri: You are gonna read it

作者: escot | 评分: 70 | 评论数: 14 | 发布时间: 2025-04-23 21:47
文章摘要

文章提出了一个名为YAGRI（You Are Gonna Read It）的概念，作为YAGNI（You Aren't Gonna Need It）的补充。YAGRI建议在开发中不仅要存储当前产品需求所需的最小数据，还应预先存储可能需要读取的数据，如时间戳和元数据，以支持调试和分析。文章特别提到，在实现如删除功能时，应记录谁、何时、如何以及为何删除，而不仅仅是执行删除操作。推荐存储的字段包括创建时间、更新时间、删除时间、创建者、权限等。虽然不是所有存储的数据都有用，但某些关键时刻可能非常关键。文章强调，作为工程师，妥善管理和维护数据是重要职责，但也要避免过度记录。

评论摘要
主要讨论点：关于数据库设计中的软删除及相关实践的讨论 不同观点： • **对软删除的实用性存在争议**： - [hoipaloi] 提出反面观点，引用文章《软删除可能不值得》来质疑软删除的实用性。 - [evanmoran] 也提到软删除的复杂性让他质疑是否值得使用deleted_at字段，并提出其他替代方案如将删除行移到单独的表中。 - [seveibar] 支持硬删除与归档表的模式，认为比软删除更好。 • **软删除与数据存储的权衡**： - [al_borland] 认为应该有一定的前瞻性来规划数据库的增长和需求，但也指出过度捕捉用户数据可能带来风险。 - [mkhalil] 提到事件溯源（event-sourcing）可以解决数据存储问题，但由于缺乏便捷的框架，该方法未广泛使用。 - [sgarland] 指出时间戳字段在大量数据下会占用较多存储资源，尤其是在内存中，因此需要谨慎使用。 • **软删除的实现方式与索引问题**： - [reillyse] 分享了在Rails中使用时间戳代替布尔值的经验，如用is_deleted字段存储删除时间，以获取更多信息。 - [seveibar] 提醒不要过度索引，认为文章中的建议可能导致过度索引问题。 • **对YAGNI和YAGRI原则的讨论**： - [im_anon_on_hn] 提到YAGNI（You Aren't Gonna Need It）和YAGRI（You ARE Gonna Read It）的对立观点，指出错误解读可能带来相反的效果。 - [ffitch] 指出YAGNI和YAGRI可能同时适用于相同字段，具体取决于团队成员的观点权衡。 补充讨论： • **审计日志的重要性**： - [zie] 认为一个良好的审计日志可以解决大部分问题，并自动提供所需信息。 • **UI设计与产品需求的关系**： - [shaunofthedev] 指出UI设计不应主导数据库设计，产品需求应明确指出需要哪些字段和信息，以避免数据库管理员频繁介入。 • **数据丢失的考虑**： - [nailer] 强调删除数据可能导致数据丢失，应考虑是否可以接受，通常不建议丢失删除记录。 争议焦点： • 软删除的复杂性与实用性之间的权衡，以及是否有更好的替代方案（如归档表或事件溯源）。

C++26: more constexpr in the core language

作者: jandeboevrie | 评分: 65 | 评论数: 6 | 发布时间: 2025-04-23 19:13
文章摘要

C++26将进一步扩展`constexpr`的功能，使其更适用于常量表达式。具体变化包括：通过P2738R1提案，允许在常量表达式中从`void*`进行类型转换，从而支持如`std::format`、`std::function`等标准库函数在编译时使用；通过P2747R2提案，使placement new可在常量表达式中使用，解决只能进行值初始化的问题；通过P2686R5提案，允许`constexpr`声明中的结构化绑定和引用，放宽了对`constexpr`引用的限制，但仍不允许lambda中的`constexpr`引用绑定到外部函数的变量。C++26将使更多标准库功能在编译时计算成为可能。

评论摘要
主要讨论点：C++标准的快速发展与编译器实现速度之间的矛盾，以及是否应继续不断增强C++语言。 不同观点： • **[mcdeltat] 对C++标准发展速度与编译器实现滞后的担忧**：该用户担心C++标准的快速发展（如C++20尚未完全在主流编译器中实现，C++23的实现更少）会带来问题，并质疑C++标准委员会是否会减少未来新功能的添加。 • **[veilrap] 支持编译时功能和期待C++26的新特性**：该用户对C++的新编译时功能表示欢迎，并特别期待C++26中的反射特性（reflection），认为这些功能可以减少目前使用宏和运行时技巧的必要，提升代码质量。 • **[Quitschquat] 希望C++像Lisp一样在编译时提供完整语言支持**：该用户表达了对C++在编译时提供更强大功能的期望，希望C++能像Lisp一样在编译时提供完整的语言和运行时支持。 • **[psyclobe] 对C++现有功能的小缺憾**：该用户总体上对C++持积极态度，但提到一个小问题，即在constexpr表达式中仍无法将char类型转换为uint8_t，暗示了某些细节功能尚不完备。 • **[worik] 质疑C++持续增强的必要性**：该用户认为C++已经是一个重要语言，拥有庞大的用户基础，类似于COBOL，因此质疑是否有必要持续对C++进行增强，并认为资源可以投入到更有价值的地方。 补充讨论： • **对C++未来发展的不同态度**：一些用户（如[mcdeltat]和[worik]）对C++持续增加新功能的必要性表示怀疑，担心发展速度过快；而另一些用户（如[veilrap]和[Quitschquat]）则对新功能充满期待，认为这些功能能带来实际的好处和编程体验的提升。 • **具体功能需求**：[veilrap]和[psyclobe]提到了对具体功能（如反射和constexpr中的类型转换）的需求，反映出部分开发者对C++新功能的实际应用场景充满期待。 • **争议焦点**：C++标准的发展速度与编译器实现滞后之间的矛盾是主要争议点，部分用户担心这种不平衡会影响C++的实际使用，而另一部分用户则关注新功能带来的潜在好处，不太在意实现滞后的问题。
