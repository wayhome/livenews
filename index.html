文章摘要

文章讨论了WebAssembly (Wasm) 是否能直接支持DOM操作，并指出Wasm可能永远不会直接访问DOM，但通过JavaScript间接调用DOM API已经足够成熟，适用于各种Web应用。Wasm与JavaScript严格分离，但通过“粘合代码”可以实现与JavaScript API的无缝集成。文章通过示例展示了如何利用JavaScript作为中介，让Wasm调用如`console.log`这样的Web API。Wasm模块通过导入和导出功能与JavaScript交互，且使用数组和整数索引来处理JavaScript对象引用。尽管未来可能引入直接调用Web API的机制，但目前的方案已能有效减少代码量并提升性能。Wasm与JavaScript的集成仍在不断发展中。

主要讨论点：WebAssembly (Wasm) 的应用、局限性以及与JavaScript生态系统的交互 不同观点： • Havoc 认为 Wasm 的一个吸引力在于可以摆脱 JavaScript 生态系统中杂乱无章的发展，但 Wasm 包含的各种 JavaScript API 又引入了编译器生成的粘合代码，这似乎与他原本的期望相悖。 • sfvisser 分享了在将大量 Rust 代码嵌入到 Web 前端时使用 Wasm 的经验。他们指出 Wasm 和 TypeScript 之间的交互层非常痛苦，需要大量缓慢且不安全的粘合代码。此外，Wasm 似乎更适合长时间运行的后台计算，而不是频繁跨越边界进行交互，这限制了它的使用场景。 • CaptainFever 担心 Wasm 的广泛使用会减少网站的可扩展性，因为当前很多网站由于使用 JavaScript 而实际上是源码可见的。Wasm 的普及可能导致这种情况发生变化。 • jauntywundrkind 表达了对 Wasm 发展的不确定性和进展缓慢的沮丧。尽管有一些技术进展（如 ref types），但整体上 Wasm 的整合和应用仍然让人困惑。他们希望能有更多官方的状态更新和指导。 • theSherwood 希望 Wasm 能访问 DOM，但不愿意 Wasm 依赖 UTF-16 编码。他们建议引入一个 8-bit 编码的 DOMString8 接口，以避免进一步与 16-bit 字符串编码纠缠。 • criticalfault 质疑为什么 Wasm 添加 DOM 访问如此困难，并提出是否可以有除 JavaScript/TypeScript 以外的其他选项（如 Dart），以解决当前 Wasm 的一些问题。 • edg5000 询问是否有人为 C++/Rust 编写了一个良好的 DOM 包装器，以便能够从 C++/Rust 应用中方便地访问 DOM API。 补充讨论： • 争议焦点之一是 Wasm 与 JavaScript 生态系统的交互复杂性和 DOM 访问的困难。一些人认为 Wasm 的设计限制了其在 Web 开发中的广泛应用，而另一些人则希望能有更多官方指导和工具来解决这些问题。 • 对 Wasm 的期望和现实之间的差距也是一个重要讨论点。尽管 Wasm 有潜力，但其当前的状态和整合进展让人感到困惑和失望。 • 不同开发者对 Wasm 的需求和期望各不相同，从 DOM 访问到字符串编码，再到对其他编程语言支持的渴望，这些都反映了 Wasm 生态系统的多样性和复杂性。
