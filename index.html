Excalidraw+ Is Now SoC 2 Certified

作者: gmays | 评分: 47 | 评论数: 6 | 发布时间: 2025-06-24 01:54
文章摘要

Excalidraw+ 获得了 SOC 2 认证，以简化安全合规流程。他们使用 Vanta 来连接服务并修复合规差距，编写了大量政策，实施了零信任生产访问，升级了技术栈，进行了渗透测试，并评估了所有供应商。最终，他们通过了 SOC 2 Type I 认证，正在进行 Type II 认证。SOC 2 是一种安全和合规框架，分为 Type I（检查系统和政策是否存在）和 Type II（检查政策是否长期有效）。尽管政策编写是最繁琐的部分，但大多数安全措施他们早已实施，只是需要正式记录。未来可能还会追求 GDPR 或 ISO 27001 认证。这一过程帮助他们建立了更安全的运营基础。

评论摘要
主要讨论点：SOC 2认证过程及其相关细节 不同观点： • [tptacek的观点] Type 1 只是记录某个时间点的基线，重点在于Type 2，它检验你是否持续可靠地执行了Type 1中的承诺。因此，应尽量减少在Type 1中投入的工作量，只专注于一小部分你确定会长期遵守的最佳实践。许多供应商利用Type 1让团队提升技能并部署各种内容，这是一个容易避免的错误。此外，Type 1的通过是必然的，所以不必对此感到过度兴奋。 • [Vic-Bhatia的观点] 强调了正确的术语使用，公司只能获得SOC 2 Type 1的“证明”而非“认证”。此外，没有人会“失败”于SOC 2审计，只会获得四种审计意见之一。他还指出了技术领域的严格审查部分和报告中需要注意的区域，并建议不要盲目接受安全政策模板。SOC 2的复杂性和费用往往被过度夸大。 • [quicklime的观点] 质疑为何一个由会计师创立的框架（SOC 2）会在科技行业广泛采用，并成为评估软件安全实践的标准。对为何科技公司不选择由科技行业人士制定的框架表示不解。 • [blackbirdsr71的观点] 关注文章中图表的美观，对其制作方式表示好奇。 • [9283409232的观点] 询问是否存在Excalidraw的自托管替代方案，因为其团队所有服务都是自托管的。 • [ranger_danger的观点] 询问文章中所提到的“安全问卷”的具体含义，包括问卷的来源和目的。 补充讨论： • SOC 2 Type 1和Type 2的区别以及各自的重点 • 审计过程中需要特别注意的技术领域和报告部分 • 使用如Vanta/Drata等工具时的注意事项 • SOC 2认证的实际复杂性和费用问题 • 对SOC 2框架在科技行业广泛应用的疑惑 • 对自托管解决方案的需求 争议焦点： • SOC 2认证过程的实际必要性和复杂性，特别是对Type 1和Type 2的不同看法。 • 由会计师主导的SOC 2框架为何在科技行业如此广泛应用，以及其合理性。

A Deep Dive into Solid Queue for Ruby on Rails

作者: fbuilesv | 评分: 70 | 评论数: 4 | 发布时间: 2025-06-20 10:31
文章摘要

本文是Ruby on Rails的Solid Queue系列的第二篇，深入探讨了Solid Queue的调度功能。与传统依赖外部服务（如Redis）的队列系统不同，Solid Queue将所有任务数据存储在数据库中，且性能出色。它不仅支持简单的后台任务执行，还支持任务调度、定时执行以及并发限制等功能。 Solid Queue通过`solid_queue_scheduled_executions`表存储调度任务，该表与`solid_queue_ready_executions`表结构相似，但增加了`scheduled_at`列，用于指定任务的执行时间。调度任务时，系统会将任务数据插入`solid_queue_scheduled_executions`表。 Dispatcher进程负责定时检查并执行已到期的任务。它通过一个循环调用`poll`方法，持续从数据库中查询到期的任务并将其转移到`solid_queue_ready_executions`表，供工作进程执行。Supervisor则负责监督Dispatcher和工作进程的运行状态。 总体而言，Solid Queue提供了强大的任务调度功能，且无需外部依赖，配置简单，功能全面。

评论摘要
主要讨论点：Rails应用中如何实现周期性任务以及使用队列处理任务的复杂性 不同观点： • [pqdbr] 认为在Rails应用中使用Puma的插件系统进行周期性任务处理的文档不足，最终选择了sidekiq-cron来解决周期性任务的需求。他还提到通常希望Rails/Puma自动处理进程/线程的分配，而不是手动管理。 • [nkraft11] 分享了一个在Ruby公司工作时的负面经验，指出该公司对所有性能问题都依赖队列解决方案，导致系统复杂且难以维护。特别提到多区域队列管理不当的问题，使得问题追踪变得几乎不可能。 补充讨论： • [pqdbr] 对如何在Puma中实现Supervisor的功能有兴趣，特别是如何为每个工作进程/调度器分叉单独的进程，并对Puma插件支持的文档不足表示失望。 • [nkraft11] 通过个人经历揭示了过度依赖队列可能导致系统架构复杂化的问题，特别是在多区域部署的情况下，这不仅没有解决问题，反而增加了系统的复杂性和维护难度。 争议焦点： • 在Rails应用中处理周期性任务的最佳实践：是依赖像sidekiq-cron这样的外部工具，还是深入理解和利用像Puma插件这样的内建机制。 • 队列系统在处理性能问题时的适用性和可能导致的系统复杂性。
