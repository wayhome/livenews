The "S" in MCP Stands for Security

作者: skilldeliver | 评分: 207 | 评论数: 20 | 发布时间: 2025-04-06 09:42
文章摘要

文章讨论了MCP（Model Context Protocol）在促进大型语言模型（LLM）与工具和数据集成方面的作用，但也指出了其默认不安全的问题。MCP允许AI代理连接工具、维持会话并共享上下文，但存在多种安全风险，包括命令注入漏洞、工具中毒攻击、静默重新定义以及跨服务器工具阴影等。当前MCP缺乏认证标准、上下文加密和工具完整性验证机制，容易导致远程代码执行和数据泄露。为应对这些问题，文章建议开发者进行输入验证、固定服务器和工具版本、清理工具描述，而平台构建者应显示完整工具元数据并实施会话安全措施。文章最后提出构建像ScanMCP.com这样的工具，以提供对MCP工具的安全审计和风险监控。简而言之，MCP虽强大，但其安全性亟待提升。

评论摘要
主要讨论点：MCP（Multi-Component Processor）工具调用中的安全问题，尤其是与间接提示注入、工具阴影、工具中毒等相关的攻击场景。 不同观点： • **lbeurerkellner**（作者）：强调MCP工具调用中的安全问题，特别是间接提示注入和工具阴影。他指出，当MCP服务器在代理系统中使用时，可能会发生一个不受信任的MCP服务器操纵代理的行为，进而影响其他服务器。此外，MCP的动态特性使其可以在任何时候变恶意，而当前的MCP客户端不会通知用户这些变化，导致用户易受攻击。 • **anaisbetts**：认为这些攻击只是“处在不利位置”的例子，并没有跨越权限边界。她将MCP服务器的安全问题与NPM或VS Code扩展等其他开发工具生态系统的问题相比较，认为这些攻击并没有特别的创新性，只是对现有问题的另一种表现。 • **TeMPOraL**：质疑是否可以设计出一个既安全又实用的MCP系统，同时不引入过多的手动确认步骤或依赖于封闭的市场和企业守门人。他认为安全性和实用性是相互对立的，设计这样的系统并不容易。 • **neomantra**：指出MCP服务器在可观察性和安全性方面存在文化和技术上的问题。许多用户没有安全意识，只是盲目运行下载的程序，缺乏审计和指标。他预计随着MCP的发展，相关的安全和可观察性工具会逐渐完善。 • **metalrain**：关注如何确保MCP服务器在用户期望的范围内使用，特别是在有多个选项时，如何防止出错。他认为需要在灵活性和安全性之间找到平衡。 • **tuananh**：分享了他选择OCI格式和WebAssembly来增强MCP项目安全性的经验，通过OCI的图像签名和验证以及Wasm的沙盒化来提高安全性。 补充讨论： • **争议焦点**：MCP工具调用的安全性和实用性之间的平衡。一些评论者认为这些安全问题并不是MCP独有的，而是与其他开发工具生态系统类似，而另一些评论者则认为设计一个既安全又实用的MCP系统非常困难。 • **其他值得注意的讨论点**： - **billyp-rva**：提到Medium是否会自动在文章标题中添加表情符号，这是一个与主要讨论无关的 tangential 问题。 - **chrisweekly**：指出访问Medium文章时遇到的问题，无法在登录状态下访问链接。 - **owenthejumper**和**867-5309**：用幽默的方式将当前MCP的安全问题与过去的互联网安全问题（如2003年的OWASP和IoT）相比较。

Show HN: I built a Rust crate for running unsafe code safely

作者: braxxox | 评分: 25 | 评论数: 5 | 发布时间: 2025-04-06 13:28
文章摘要

`mem-isolate` 是一个 Rust crate，旨在通过使用 `fork()` 系统调用安全地运行不安全代码。它会在子进程中执行用户提供的函数，确保该函数不会影响父进程的内存状态，实现内存隔离。主要特点包括： 1. **内存纯净性**：即使函数存在内存泄漏或堆碎片化问题，也不会影响主进程。 2. **跨进程通信**：通过管道在父子进程间传递结果，使用序列化（如 `serde`）处理数据。 3. **性能开销**：每次调用引入约 1ms 延迟，适合对内存安全要求高的场景。 4. **系统支持**：仅支持 POSIX 系统（如 Linux, macOS），不支持 Windows 和 WebAssembly。 该工具适用于运行可能导致内存问题的代码，如 FFI 调用或不安全代码，通过隔离确保主程序的稳定性。

评论摘要
主要讨论点：在应用程序中使用多进程、进程间通信（IPC）和操作系统沙箱API的优缺点，以及具体技术实现中的挑战，特别是在Rust和Windows环境下的问题。 不同观点： • [pjmlp] 认为应该从一开始就设计多进程应用，使用操作系统的IPC和沙箱API，而不是依赖即时伪沙箱技术。他提到传统的UNIX守护进程启动方式证明了伪沙箱存在问题。 • [djha-skin] 同意多进程设计的理论价值，但指出`fork()`在性能关键路径上可能非常昂贵，建议谨慎使用这种方法。 • [null_investor] 提到，虽然`fork()`和相关工具包在处理不安全代码时有用，但其使用应有限。他认为，在Rust中过度依赖`fork()`可能导致失去Rust相对于Python或Ruby的性能优势。 • [dijit] 关注在Windows环境下用Rust调用Win32 API时遇到的实际问题，尤其是内存调试工具的缺乏，导致对内存损坏或泄漏的担忧。他请求推荐在Windows上有效的调试工具。 • [teknopaul] 对整个讨论持简短的调侃态度，认为这种技巧在紧急情况下是个聪明的解决办法，但并没有深入讨论具体技术问题。 补充讨论： • 争议的焦点之一是`fork()`在多进程应用中的实际性能开销，以及是否应在现代应用设计中广泛使用。 • 另一个值得注意的讨论点是Rust在处理不安全代码（尤其是与操作系统API交互时）时的实际开发挑战，特别是在调试和内存管理方面。 • 对Windows环境下有效调试工具的需求反映了跨平台开发中的实际困难，以及开发者在不同操作系统中面临的工具差距。

SeedLM: Compressing LLM Weights into Seeds of Pseudo-Random Generators

文章摘要

《SeedLM: Compressing LLM Weights into Seeds of Pseudo-Random Generators》一文介绍了一种新型的压缩方法，称为SeedLM，用于减少大型语言模型（LLM）在推理过程中的内存访问和计算成本。该方法通过使用伪随机生成器（LFSR）的种子来编码和压缩模型权重。在推理时，种子生成随机矩阵，并与压缩系数结合以重建权重块。该方法无需校准数据，能在多种任务中有效应用，并在Llama3 70B模型上展示了与FP16基准相当的性能，同时在FPGA测试中实现了近4倍的速度提升。这种方法显著提升了内存密集型任务的效率。

评论摘要
主要讨论点：LLM权重量化与压缩技术及其应用 不同观点： • [visarga] 认为该压缩技巧通过使用快速计算的基础向量词典，无需存储，具有创新性。不过，量化结果仅有3或4比特，改进有限。由于瓦片（tile）较小（8或12个权重），压缩效果不显著。他提出如果能够实现小于1比特/权重的量化，可能需要更大的瓦片。他还讨论了在神经网络架构中使用更大熵池的可能性，特别是在训练中，并赞扬了Apple和Meta的研究，认为这将有助于在手机上高效运行LLM。 • [jlcases] 将此压缩方法与人类知识传递相比较，认为两者都在寻找能够重建复杂信息的紧凑表示。他提到在技术文档中应用类似概念，即通过定义一组最小的原则和架构决策来“再生”完整理解，而不是详尽记录每个实现细节。他还提出当前LLM在扩展压缩概念方面表现出色，但仍在寻找显性知识和隐性知识之间的最佳平衡。 • [elashri] 简单地建议直接链接到相关论文，并提供了论文的链接，强调这是Apple和Meta研究人员的成果。 • [gblargg] 解释该技术类似于找到最接近目标数据的伪随机序列部分，然后存储随机种子和较小的修正项。 • [torginus] 质疑该技术是否特别适用于LLM权重而非通用数据，认为这听起来像是“多此一举”的压缩。 • [anshumankmr] 则对Apple的AI项目未按期发布表示失望，偏离了主要技术讨论。 补充讨论： • 该技术是否能进一步降低量化比特数以及在更大范围内的应用潜力。 • 该压缩方法与人类知识传递的类比及其在技术知识管理中的潜在应用。 • 对具体研究论文的引用及认可Apple和Meta的贡献。 • 对该技术是否具有特殊性及其在LLM权重压缩中的独特应用的质疑。
