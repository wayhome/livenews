文章摘要

文章主要介绍了作者受Bartosz Ciechanowski博客启发，计划制作一个真实机械表的“爆炸图”模型。这种模型可以让各个零件悬浮在一个透明树脂中，从不同角度观察。作者提到，目前市场上没有这样的产品，即便有机械表零件的树脂模型，也多作为“蒸汽朋克艺术品”出售，缺乏实际组装结构。作者打算使用简单的老式怀表机芯来进行此项目，因为其结构相对简单，没有日期功能和自动上弦装置。制作过程中，作者尝试了分层树脂浇铸，但遇到树脂发黄、固化时间长以及层间缝隙明显等问题。尽管如此，作者仍决心继续这个项目，并寻找解决方案。

Git Notes: Git's coolest, most unloved­ feature (2022)

作者: Delgan | 评分: 241 | 评论数: 21 | 发布时间: 2025-06-22 09:14
文章摘要

Git notes 是一种向 Git 提交添加元数据的方式，用于在不变更提交本身的情况下，为旧提交附加新信息，如代码审查和测试结果。它们可以存储关于任何 Git 对象（提交、blob、树）的元数据，并通过命令行操作。尽管功能强大，Git notes 使用起来较为复杂，界面不直观，导致其使用率低，且 GitHub 等平台未广泛支持。然而，一些工具和插件（如 Gerrit 的 reviewnotes 插件和 Google 的 git-appraise）展示了 Git notes 在分布式代码审查中的潜力。总体而言，Git notes 提供了强大的功能，但受限于可用性和用户体验。

评论摘要
主要讨论点：Git Notes 功能的用途、优缺点及其实际应用 不同观点： • [oftenwrong] 介绍 Git trailers 作为一种提交时的元数据附加方式，并提到 Gerrit 使用 Change-Id 的例子。 • [homebrewer] 补充 Forgejo 也从今年初开始支持该功能，提供了相关版本发布说明和代码合并请求链接。 • [kccqzy] 认为 Git notes 只在特定情况下有用，例如在提交后添加文本，并质疑 Acked-By 和邮件列表链接的实际需求，提出可以在提交信息中包含讨论内容。此外，认为在提交被回滚的情况下使用 Git notes 更有意义。 • [b0a04gl] 分享了在工作中大量使用 Git notes 的经验，用来记录内部代码审查、工单映射和事件线程链接，避免依赖平台 UI，强调了其在规模化使用中的价值。 • [noelwelsh] 认为 Git notes 使用率低是因为用户界面问题，而非用户知识不足，指出如果 GitHub 的 UI 支持显示 notes，其使用率会大幅提升。 • [lars512] 提供了在公共数据管道项目中使用 Git notes 的实例，记录构建输出哈希，但实际使用频率不高，且 notes 默认隐藏影响 awareness。 • [lucasoshiro] 提到许多 Git 的强大但被忽视的功能，如 bisect、reflog 等，认为很多人只把 Git 当作简单的文件存储工具，忽视了其高级功能。 • [cesarb] 分享了 LibreOffice 项目中使用 Git notes 跟踪提交的案例，用于记录提交的相关性等信息，但该用法已停止，因为 Apache OpenOffice 的变更速度减慢。 • [legends2k] 提到从手册中发现了 Git notes，但由于是本地功能且默认不推送或获取，团队未采用该功能。 • [mtillman] 认为 Git notes 的使用并不复杂，可以将文本笔记直接通过管道添加到 Git notes 中，质疑关于接口不便的批评。 • [paffdragon] 开发了一个基于 Git notes 的版本控制工具，用于版本覆盖，认为这在迁移功能到新仓库时非常有用。 • [Shank] 质疑 GitHub 为何取消了对 Git notes 的支持，并询问如何逆转该决定。 • [olejorgenb] 关心在 rebase 时带有 notes 的提交会发生什么。 • [pettereriksson] 提出将提示或其摘要作为每个提交的 note 添加，以便 LLM 后续推理代码变更的需求。 补充讨论： • Git notes 的实际应用场景讨论较多，包括代码审查、提交回滚、构建输出记录等，但其实际使用率受到 UI 支持不足和默认隐藏设置的限制。 • 争议焦点在于 Git notes 的使用复杂性与 UI 支持不足，部分用户认为其强大且有用，而另一些用户则认为其使用不便或不必要。 • 关于 GitHub 取消支持 Git notes 的决定引发了不满，用户希望逆转该决定以提升 Git notes 的可用性。

2048 with only 64 bits of state

作者: todsacerdoti | 评分: 65 | 评论数: 7 | 发布时间: 2025-06-19 16:43
文章摘要

《Bitwise Challenge: 2048》是一个在终端运行的经典2048游戏实现。该项目将整个游戏板状态压缩到仅64位，允许通过一个数字分享游戏状态。若环境变量`$STATE`未设置，则游戏会生成一个随机种子，开始新的游戏；若设置了`$STATE`，则游戏状态和后续生成单元都是确定的。项目主要使用Shell语言编写，目前获得60个星标和1个分支。

评论摘要
主要讨论点：2048游戏的64位状态实现及其高效编码方式 不同观点： • [eurleif] 认为实现的亮点在于用不到200行的bash脚本实现游戏，而不是使用64位状态。他解释了如何通过每个格子12种可能的状态（包括空格），每个状态用4位表示，从而总共只需64位（4*4*4）。 • [lotyrin] 认同64位状态的实现并不复杂，因为每个格子只能有特定的幂次方块。他还提到了一种将复杂状态空间映射为简单线性序列的方法，并给出了用有限字符集编码文本的例子。 • [carra] 指出原版2048游戏可以在达到2048后继续进行，而这个64位实现为了达到64位状态限制，去掉了这一选项，但仍认为这是一个聪明的实现。 • [enriquto] 通过计算指出，如果不达到2048，总状态数为11^16，取对数后需要56位，因此64位是足够的，但很紧凑。 • [nneonneo] 分享了自己在2048 AI中使用类似技巧的经历，并提到其实现中允许块达到32768，每个块用半个字节表示，从而将整个游戏板打包进一个机器寄存器，非常高效。 补充讨论： • [meta-level] 提到自己有一个类似的bash脚本，用于启动docker容器，代码行数也差不多，暗示实现这样的功能在不同场景下都可以相对简短。 • [kinduff] 简单表达了对代码行数和实现的赞赏。 争议焦点： • 讨论中并没有明显的争议，但不同用户对实现亮点的看法有所不同。Eurleif和部分其他用户更关注脚本的简洁性，而其他用户如lotyrin和nneonneo则更关注64位状态的编码技巧和效率。

TPU Deep Dive

文章摘要

本文简要介绍了谷歌TPU（Tensor Processing Units）的设计理念和内部结构，强调其可扩展性、高吞吐量和能效。TPU是谷歌为满足人工智能计算需求而开发的专用集成电路（ASIC），特别擅长处理大规模矩阵乘法和神经网络计算。TPU的强大性能得益于硬件（如能量效率和模块化设计）和软件（如XLA编译器）的协同设计。 TPU的单芯片包含两个TensorCore，每个TensorCore具有共享内存和专门的计算单元，如矩阵乘法单元（MXU）、向量单元（VPU）等。TPU采用脉动阵列设计，通过流水线技术实现高吞吐量，特别适合矩阵乘法和卷积操作。然而，脉动阵列对稀疏矩阵的处理效率较低。 相较于GPU，TPU拥有更大的片上内存和更少的计算核心，但通过优化设计实现了极高的计算效率。例如，TPUv5p单芯片可达500 TFLOPs/秒，而TPUv7整个计算单元可达42.5 ExaFLOPs/秒。 总体而言，TPU通过独特的设计选择，在处理AI任务上展现了出色的性能和能效。
