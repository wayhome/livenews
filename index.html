I Write Type Safe Generic Data Structures in C

作者: todsacerdoti | 评分: 39 | 评论数: 9 | 发布时间: 2025-06-30 16:55
文章摘要

本文介绍了在C语言中实现类型安全的通用数据结构的方法。作者展示了一种利用联合（unions）来关联类型信息的技术，通过实现一个简单的链表来说明。文章比较了三种不同的通用性实现方式： 1. **通用头文件**：使用宏定义来实现，但会导致代码可读性和维护性差，二进制体积增大，且需要使用类型前缀函数。 2. **使用void***：通过void指针实现通用性，但不类型安全，且存在内存和性能问题。 3. **内联存储**：使用柔性数组成员存储数据，解决内存和性能问题，但需要传递数据大小。 最后，作者提出了**类型检查**级别，通过使用带有payload成员的联合来实现类型安全的通用数据结构，确保编译时捕获类型错误。这种方法结合了类型安全和高效内存管理。

主要讨论点：C语言中的泛型数据结构实现及其类型安全 不同观点： • **gritzko**：认为使用C语言可以创建整个 dialect，并提供了一个基于C的通用二进制堆实现作为例子。他指出这种方法的缺点是语法不如C++模板优雅，但优势在于产生的是扁平的C结构体。同时，他批评了基于void*和运行时内存调整的实现方式，认为这是很大的缺点。 • **eqvinox**：提出了一种使用联合（union）和typeof()来实现类型安全的思路，但也表示他们使用了定义包装器的大宏来实现侵入式数据结构。他认为使用联合和typeof可能可行，但不确定如何具体实现。 • **HexDecOctBin**：强调了使用函数指针的类型来实现类型安全，而不是使用类似Sean Barrett的stretchy_buffers的"handle"类型。他还提到了C23标准解决了C语言类型比较的问题，并提供了相关文档链接，指出GCC和Clang已经支持但MSVC尚未支持。 • **asplake**：表示正在开发一个类似ML风格的C语言变体和相关函数的生成器，并计划在完成后检查是否能兼容当前讨论的技巧。 • **uecker**：表示已经在实验性库中使用了类似的技巧，并提供了一个链表实现的链接作为例子。 补充讨论： • **notnmeyer**：幽默地表示C语言可能正在成为新的Go语言，暗示C语言在某些方面正重新焕发活力或受到关注。 争议焦点： • 不同实现方式的优劣比较，如基于宏的方法与联合和typeof()方法的对比。 • C语言在类型安全和泛型实现上的局限性以及C23标准是否能有效解决这些问题。 总结：评论围绕C语言中实现泛型数据结构的不同方法展开，讨论了各自的优缺点以及可能的改进方向，涉及语法优雅性、类型安全和编译器支持等方面。

文章摘要

TokenDagger是一个OpenAI TikToken的高性能实现，专为大规模文本处理设计，具有2倍吞吐量和4倍代码样本分词速度。它采用优化的PCRE2正则引擎进行快速分词，并与TikToken完全兼容，可直接替换。通过简化的BPE算法，减少了大词汇量对性能的影响。在AMD EPYC 4584PX处理器上进行的基准测试显示，TokenDagger在代码分词上速度提升4.02倍。安装可通过PyPI进行，依赖PCRE2库。项目遵循MIT许可证。

Donkey Kong Country 2 and Open Bus

作者: colejohnson66 | 评分: 124 | 评论数: 8 | 发布时间: 2025-06-30 15:01
文章摘要

《Donkey Kong Country 2》在旧SNES模拟器ZSNES中存在一个知名bug：某些关卡的旋转桶无法正常控制。具体表现为，当角色跳入桶中后，按方向键本应控制桶的旋转，但在ZSNES中，轻触方向键会导致桶无限旋转，直到按反方向键才会停止。这个bug使游戏难度增加，因为旋转桶常出现在尖刺等危险上方。 该问题源于ZSNES未正确模拟"开放总线"行为。这种行为发生在读取无效内存地址时，CPU会重新读取上次在数据总线上的值。SNES的CPU是65816，其复杂的内存分页和地址处理进一步增加了模拟难度。 这个问题曾在ZSNES论坛上讨论，但论坛已下线，而另一个模拟器Snes9x通过硬编码修复了此问题。ZSNES由于长期未更新（最后版本于2007年发布），该bug一直未被修复。

评论摘要
主要讨论点：围绕6502汇编编程中的内存访问与立即数问题、开放总线行为及其在游戏和模拟器中的影响展开的讨论。 不同观点： • **deater和nicetryguy**：作为6502汇编程序员，他们都提到忘记在立即数前加#符号是一个常见且容易犯的错误。这会导致意外的内存访问而不是使用立即数，且问题可能在不同机器上表现不同（如不同DRAM芯片导致的不同行为）。nicetryguy进一步提到，即使是有经验的程序员也会犯这种错误，并分享了通过在IDE中高亮#符号来减少错误的个人方法。 • **anonymousiam**：认为原文标题中的"Open Bus"可能会被误解为某种旧的总线协议或标准，而实际上它指的是未连接任何设备的总线状态。此外，他指出修正后的代码因为不需要从内存读取数据，可能会执行得更快（快约2微秒），但这种优化可能仅对裸机环境有意义，而模拟器通常不精确模拟时间。 • **NobodyNada**：详细解释了开放总线的硬件行为，指出未映射或未驱动的地址会导致未定义行为，数据总线上的残余电压可能会导致读取到之前传输的数据。他提到有些游戏会无意中依赖这种开放总线效应，且在速度跑酷中也有利用这种行为的策略。此外，他还讨论了在SNES中HDMA与开放总线读取的复杂交互，以及这种交互对速度跑酷策略的影响，引发了社区内的争议。 补充讨论： • **pipes**：提到在使用模拟器玩游戏时，遇到问题常常会怀疑是模拟器的bug，而不是游戏设计本身的问题。他还分享了自己为了解决类似问题而使用FPGA设备（Mister FPGA）的经历。 • **jihadjihad**：虽然与主要讨论点不直接相关，但他表达了对DK Country 2这款老游戏的高度赞赏，认为其在现代仍然表现出色。 • **helf**：简单表达了对这类技术内容的喜爱。 争议焦点： • **开放总线行为在不同硬件和模拟器中的表现差异**，特别是在HDMA交互的复杂情况下，是否应在模拟器中精确模拟这些边缘情况以保持与真实硬件一致，还是可以有所妥协。这在速度跑酷社区中引发了一定争议，因为某些策略在模拟器中有效，而在真实硬件上可能导致崩溃。

The provenance memory model for C

作者: HexDecOctBin | 评分: 166 | 评论数: 12 | 发布时间: 2025-06-30 09:25
文章摘要

Auth for B2B SaaS: it's not like auth for consumer software

作者: noleary | 评分: 29 | 评论数: 6 | 发布时间: 2025-06-30 15:06
文章摘要

本文讨论了B2B软件与B2C软件在身份认证（auth）方面的关键区别，指出B2B认证不能简单照搬B2C模式。主要从三个方面进行比较： 1. **逻辑隔离与租户模型**：在B2C中，用户是直接客户，拥有独立账户和数据控制权。而在B2B中，企业客户需要控制其用户访问权限，用户权限不同，租户模型以公司为核心，如Slack的“工作区”。 2. **优先级与权衡**：B2B软件需要考虑企业控制、合规性等，而B2C更注重用户体验和快速增长。 3. **协议与功能**：B2B需要支持复杂的权限管理和跨公司协作功能，而B2C通常只需简单用户管理。 作者建议在设计初期就考虑这些区别，以避免后续复杂重构。B2B认证需要适应企业的多租户和权限管理需求。

评论摘要
主要讨论点：身份验证与授权系统的复杂性及其解决方案 不同观点： • weitendorf 认为身份验证（Auth）的复杂性源于过度复杂化的设计，实际上只需要关注身份（Identity）和授权模型（Authorization model）两个核心概念。消费者和B2B的Auth差异主要体现在身份管理和授权模型的不同。消费者通常依赖第三方（如Gmail、Facebook）来管理身份，而企业则通过域名和邮箱控制员工身份。此外，消费者默认只能访问自己的数据，而企业中管理员可以访问企业的全部数据，因此需要通过角色和权限来限制访问。最终问题归结为互联网缺乏良好的身份管理系统，导致依赖基于电子邮件和域名的账户体系，这种集中化信息管理模式存在权限升级的漏洞。 • nijave 同意weitendorf的观点，但补充提到OpenIDC作为SAML的前身，具有无需处理证书到期的优点，并且被广泛支持。 • skeptrune 指出处理类似"让所有人使用Yubikey"这种超级烦人的要求是一个痛点，表示愿意购买解决方案来解决这一问题。 • funerr 提问，想了解该方案与better-auth的比较。 • nylonstrung 提问，想了解该方案与zitadel的比较。 补充讨论： • koakuma-chan 提供了一个链接，但链接似乎出现了客户端异常，无法访问。 争议焦点： • 对于身份验证和授权系统的简化方案存在不同实现方式的讨论，例如OpenIDC、better-auth和zitadel等，各有其支持者与应用场景。用户对于如何选择适合的解决方案存在疑问，特别是比较不同工具之间的优劣。 总体来看，讨论的核心在于如何简化身份验证和授权系统，同时有效解决实际应用中的复杂性与安全问题。不同用户对具体工具和实现方式有各自的偏好和疑问。
