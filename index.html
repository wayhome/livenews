pg_durable: Microsoft open sources in-database durable execution

作者: coffeemug | 评分: 181 | 评论数: 12 | 发布时间: 2026-06-05 15:59
文章摘要

pg_durable 是微软开源的 PostgreSQL 扩展，在数据库内实现持久化执行（Durable Execution）。它让长时间运行的 SQL 函数具备容错能力，通过检查点机制在每步执行后保存状态，崩溃或重启后可从断点恢复，无需重新执行已完成的工作。 适用场景包括：向量嵌入管道、数据摄取、定时维护、并行聚合、外部 API 调用等。可替代 pg_cron + 状态表、外部编排器（Airflow/Temporal）、队列+工作者等传统方案，将工作流逻辑统一在 SQL 中管理，减少架构复杂度。 核心优势是消除部分失败后的手动恢复、避免长事务锁定、将重试和进度跟踪集中到 Postgres。不适合单条 SQL 语句、毫秒级同步请求，或需要复杂应用逻辑的场景。

评论摘要
主要讨论点：微软开源的 pg_durable（PostgreSQL 持久化工作流引擎）是否是合适的技术选择 不同观点： • **支持派**：认为 2026 年是 Postgres 队列之年，社区贡献值得肯定；可用于为长时间 cron 任务添加持久化和可恢复性；Azure 用户希望能获得更多现代化功能支持 • **质疑派**：不理解为什么要把控制流存储在数据库而不是代码中；认为这是用错误方案解决老问题（Apache Airflow 等 DAG 调度器已解决）；担心数据库本身难扩展，为何还要增加长时间运行任务的负载 • **困惑派**：不明白相比外部编排工具（如 Temporal）有何优势，特别是当工作流跨越多个异构系统时；文档和示例不够清晰（如 wait_for_schedule() 的幂等性、错误处理机制） 补充讨论：有开发者更倾向将队列逻辑放在 Git 代码中便于管理；有人提到 Absurd 等替代方案最小化纯数据库方法；也有人询问是否基于 pgmq 构建或与其他工具（pgflow）的兼容性；有建议将其用于导出 pg_dump 到 S3 等维护任务

Stop Using Conventional Commits

作者: jsve | 评分: 104 | 评论数: 31 | 发布时间: 2026-06-05 15:39
文章摘要

这篇文章批评了 Conventional Commits 标准，认为它存在严重缺陷： **主要问题：** 1. **优先级错误** - 将 `type`（类型）置于 `scope`（范围）之前，而实际上范围才是最重要的信息。对于代码贡献者、调试人员和事故响应者来说，他们更关心"哪个部分被修改了"而非"是什么类型的修改"。 2. **类型信息冗余且限制性强** - 提交描述通常已经表明了变更类型，单独标注类型浪费空间。而且很多变更同时包含多种类型（bugfix、重构、新功能），强制分类反而不准确。 3. **scope 竟然是可选的** - 这导致提交信息缺少最关键的"主语"，降低了实用价值。 作者认为 Conventional Commits 专注于错误的东西，未能兑现其承诺。

评论摘要
**主要讨论点：** Conventional Commits（约定式提交）规范的实用价值和适用场景 **不同观点：** • **支持派 - 自动化价值**：Conventional Commits 最大价值在于 CI/CD 自动化，可自动处理语义化版本号（fix→patch，feat→minor，feat!→major）和生成 changelog，适合 99% 的项目改善发布流程（Benjamin_Dobell, RVuRnvbM2e） • **反对派 - 信息冗余**：类型前缀（fix/feat）占用空间却信息量少，不如用自然英语动词写成完整句子。真正重要的是"为什么改"而非"改了什么"，应该在 footer 中添加 issue 编号获取上下文（ralferoo, chrishill89, mh-cx） • **质疑派 - 缺失关键信息**：Conventional Commits 标准甚至不包含 issue 编号，这才是最重要的信息。过去 15 年工作中经常需要通过旧提交引用的 issue 来理解完整上下文（mh-cx） • **中立派 - 因项目而异**：不同项目需求不同。大型项目（如 Linux kernel）不适合此规范，但对小项目有价值。关键是写好提交信息本身，而非拘泥于格式（ralferoo, osigurdson） **补充讨论：** 有人指出 AI 编程工具（如 Claude）的系统提示词正在潜移默化地影响开发规范的传播（flakiness）。也有观点认为至少有个规范能迫使团队写出有意义的提交信息，胜过毫无章法（estetlinus）。

英国政府数字服务(GDS)将其GOV.UK Pay支付服务的处理商从Stripe更换为荷兰供应商Adyen。这份为期三年、价值最高2530万英镑的合同涵盖地方政府、警察部门和武装部队的支付服务，约占GOV.UK Pay交易量的17%但覆盖超过70%的机构。新合作将引入"银行直付"功能，用户无需输入银行卡信息即可通过开放银行服务直接转账。约1000项服务将迁移至新供应商，对用户体验不会有明显影响。GOV.UK Pay自2016年推出以来已处理1.375亿笔交易，总额约92亿英镑。

主要讨论点：英国政府与Adyen签订支付服务合同的影响与意义 不同观点： • **合同规模观点**：arjie认为政府合同金额出乎意料地小，仅为美国中型企业云账单的一小部分，反映出政府采购与商业支出的巨大差异 • **Adyen准入门槛**：maelito指出Adyen拒绝百万以下的小客户，暗示其高端市场定位 • **品牌营销对比**：siren2026认为Stripe在营销和炒作方面远超Adyen，使自己看起来比实际更重要 • **支付方式扩展**：telesilla强调Stripe也支持类似功能（如Wero），可能带来比美国信用卡更好的转化率和处理费率 • **成本转嫁方案**：m101提出让用户承担交易成本，促使人们使用银行转账来降低整体费用 • **实际效益质疑**：oakinnagbe好奇此举是实质性降低地方政府成本，还是仅为扩展支付选项 补充讨论：thomashabets2提到英国税务局（HMRC）数字服务总体不错，但退税流程繁琐，希望新系统能改善这一问题。多位评论者分享了相关政府公告和性能数据链接。
