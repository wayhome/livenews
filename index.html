Show HN: New world record – verified Goldbach Conjecture up to 4*10^18+7*10^13

作者: jay_gridbach | 评分: 82 | 评论数: 10 | 发布时间: 2025-04-19 06:11
文章摘要

Hiroaki Jay Nakata开发了一个名为Gridbach的网格计算系统，成功将哥德巴赫猜想的验证范围从4×10¹⁸扩展到了4×10¹⁸ + 70×10¹²，打破了此前由T. Oliveira e Silva在2013年创下的记录。哥德巴赫猜想由数学家Christian Goldbach于1742年提出，声称所有大于2的偶数都可以表示为两个质数之和，但至今未被证明。Gridbach系统利用分布式云计算，用户可以通过网页或移动端参与计算，无需登录或安装应用。该系统使用了高性能WASM和JAMStack架构，计算核心算法已作为开源工具发布。Nakata计划继续扩大验证范围，并希望就此成果发表论文以获得官方认可。

15,000 lines of verified cryptography now in Python

作者: todsacerdoti | 评分: 352 | 评论数: 12 | 发布时间: 2025-04-18 19:28
文章摘要

2022年11月，有人在Python的GitHub仓库中提交了issue 99108，建议在SHA3实现中出现CVE后，Python应为其所有哈希相关基础设施采用经过验证的代码。截至最近，该问题已解决，Python默认暴露的所有哈希和HMAC算法现在都由经过验证的加密库HACL*提供。这次过渡对Python用户完全透明，没有功能损失。Python现在包含来自HACL*的15,000行经过验证的C代码。从上游HACL*仓库拉取新版本已实现自动化。HACL*成功实现了新功能，如Blake2算法的附加模式、覆盖所有Keccak变体的SHA3新API、严格的抽象模式以处理构建系统困难、适当的错误管理（特别是分配失败），以及利用HMAC算法实例化HACL的通用“流”功能，包括需要同时保持两个哈希状态的优化。 这一成果历时2.5年，Aymeric Fromherz贡献巨大，他承担了大量实施工作。Son Ho早期贡献关键，将HACL的“流”功能泛化以处理需要“预输入”的块算法，这对实现优化的HMAC至关重要。在Python方面，Gregory P. Smith、Bénédikt Tran和Chris Eibl提供了大量帮助。HACS系列研讨会建立了联系并提供了动力。 流式API复杂且难以实现，因为它们处理具有复杂不变性的长期状态。参考实现中的SHA3在2022年受到CVE影响，Python也因此受到牵连。流式API允许输入任意长度数据，并处理缓冲和中间哈希计算。完全通用的验证通过依赖类型捕捉块算法的定义，并一次验证通用流构造，然后应用于具体算法以生成流API。 实现完全泛型需要处理许多细节，如最终摘要长度是否固定、块算法是否需要预输入等。

主要讨论点：Python 3.14 新特性中加密库的引入及其影响 不同观点： • chrisrodrigue 认为文章没有明确提及该特性适用于哪个 Python 版本，经过查证后发现是 Python 3.14，这意味着该特性在10月前不会发布。他还提出争议，认为这是一个安全修复，应向后兼容到 Python 3.9 以上的所有版本。 • bgwalter 质疑这个更新的实际意义，认为这只是一个包装好的 C 库，Python 本身并没有太大的创新，只是将微软的 F* 语言生成的 C 库代码引入到了 CPython 中。 • Retr0id 关注 SHAKE 算法中的“流式输出”支持问题，提到在 pyca/cryptography 库中有相关讨论，但在 Python 标准库中没有找到对应的讨论。 • IlikeKitties 从社会角度出发，提到现代加密技术已经无处不在且几乎无法破解，回顾了90年代的“加密战争”，并提出了加密技术对现代社会的影响问题。 • badmonster 关心新引入的通用流式验证框架在加密哈希之外的可复用性。 • pluto_modadic 对引入加密模块是否需要依赖 G++ 或其他不常见的编译工具提出疑问，或者这些库会被直接编译进 CPython。 • hall0ween 表示自己对加密技术不了解，询问这个更新对 Python 的具体意义。 • tsecurity 关注此更新的验证过程，尤其是“验证困难”的说法让他有些担忧。 • thebeardisred 认为代码行数作为衡量标准很差，特别是在加密代码中吹嘘大量代码行数是不合适的。 • Tarucho 提到虽然这个更新有用，但 Python 的加密库现在依赖于微软的技术，并给出了相关链接。 补充讨论： • 争议焦点之一是该特性是否应被视为安全修复并向后移植到旧版本。 • 另一个焦点是 Python 是否只是简单地包装了微软的 C 库，而非在加密技术上的创新。 • 关于流式输出支持的问题在社区中已有讨论，但在标准库中未有明确计划。 • Python 加密库依赖微软技术引发了对技术依赖性的讨论。
