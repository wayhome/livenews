What went wrong with wireless USB

作者: goldenskye | 评分: 61 | 评论数: 3 | 发布时间: 2025-05-04 02:03
文章摘要

本文简要探讨了无线USB技术的历史和其消亡原因，以及与Wi-Fi和蓝牙的比较。作者最初尝试通过Palm OS智能手表进行移动网络连接，但设备缺乏内置网络功能。作者设想通过无线USB解决这一问题，回顾了无线USB曾短暂存在的平行技术世界。无线USB基于超宽带（UWB）技术，旨在提供短距离高带宽通信。然而，由于竞争标准和Wi-Fi的普及，无线USB很快在市场上消失。文章还解释了窄带和宽带无线电传输的区别，以及UWB与雷达脉冲技术的渊源。最终，Wi-Fi和蓝牙的普及使得无线USB未能广泛应用。

评论摘要
主要讨论点：无线USB标准的发展、竞争及其与现代无线技术（如WiFi、Bluetooth、802.11ad/ay等）的比较 不同观点： • Kensai认为无线USB标准发展缓慢，且相比WiFi和Bluetooth等竞争标准没有太多优势。他质疑当前是否更适合使用WiFi和Bluetooth，并询问是否有关于能耗的实际对比数据。 • Jauntywundrkind补充了关于802.11ad (2011) 和 802.11ay (2021) 以及Wigig（主要用于视频和VR头显）的相关信息，并提到Intel的tri-band 17265（2015）作为当时较受欢迎的WiFi+Wigig+Bluetooth适配器。他还讨论了使用这些技术来减少办公室和户外线缆的可能性，但指出当时价格较高且没有Linux支持。此外，他提到对USB-IP系统的兴趣，以及802.15.4组在UWB（超宽带）方面的进展，比如Spark Microsystems的低功耗SR1120收发器，认为这可能用于通用外设互联。 补充讨论： • Liftyee表示对带宽限制和数据速率的关系有了更好的理解，并提到之前对“为什么不能更快地开关波形”之类的问题缺乏全面的认识。 争议焦点： • 无线USB标准是否因发展缓慢和竞争劣势而被WiFi和Bluetooth取代。 • 关于不同无线技术在实际应用中的能耗对比，目前缺乏具体数据。 总结：讨论主要围绕无线USB标准的发展历程及其与现代无线技术的竞争，参与者分享了关于802.11ad/ay和Wigig的实际应用经验，并对未来USB-IP系统和UWB技术在通用外设互联方面的潜力表示期待。能耗对比是争议点之一，尚缺乏具体数据支持。

DuckDB is probably the most important geospatial software of the last decade

作者: dbreunig | 评分: 143 | 评论数: 17 | 发布时间: 2025-05-03 19:30
文章摘要

文章主要讨论了DuckDB在地理空间数据处理方面的重要性，尤其是在其发布空间扩展后，显著降低了处理地理空间数据的难度。过去，处理这些数据需要安装多个开源软件包、配置路径以及搭建专用数据库，而现在通过DuckDB，只需一两行代码即可实现。这大大简化了操作，吸引了更多非专业人士参与地理空间数据工作，扩大了该领域的影响力。文章还提到，在Cloud-Native Geospatial会议上，DuckDB的空间扩展被视为扩大地理空间数据受众的关键工具，可能推动了Overture Maps Foundation等项目的使用增长。作者对DuckDB在这一领域的未来发展表示期待。

评论摘要
主要讨论点：DuckDB在地理空间分析中的作用和独特性 不同观点： • Demiurge认为，DuckDB并没有在安装和使用简便性上带来实质性的改变。他指出，PostGIS等地理空间扩展已经存在多年，因此DuckDB并不是一个冷启动环境下的唯一或最佳选择。 • wenc赞赏DuckDB在处理大规模地理空间数据时的性能优势，尤其是在处理parquet/geoparquet文件时，比geopandas更高效。此外，DuckDB支持一些高级地理空间特性，如Hilbert曲线和Uber H3。 • larsiusprime质疑DuckDB的独特性，认为像geopandas这样的工具已经提供了类似的功能，并希望看到更实际的例子来证明DuckDB的声称。 • jparishy对Felt.com的潜力感到兴奋，认为它有可能颠覆地理空间技术在消费者应用中的集成方式。他指出，培训人员掌握地理空间技术需要大量时间和精力，并认为DuckDB和PostGIS在功能上相似。 • wodenokoto不认为DuckDB在安装简便性上比"pip install geopandas"有明显优势，两者都是一行命令。 • WD-42质疑DuckDB是否比'load extension postgis'更简单，并提到Docker已经简化了许多安装过程。 • jandrewrogers认为地理空间软件长期以来停滞不前，新工具只是旧工具的变种。他指出，许多地理空间分析并不涉及地图制作，但工具往往强制用户通过地图视角进行分析。 • patja提到SQL Server多年前就已经具备地理空间数据类型，无需额外扩展。 • twelvechairs认为DuckDB虽然是地理空间分析的重要工具，但并不是过去十年中最重要或唯一的工具，其他工具如QGIS、PostGIS、ArcGIS在线、JS地图工具等也同样重要。 • badmonster提出，将地理空间能力直接嵌入通用数据工具如DuckDB，可能会改变参与地理空间分析的人群及其解决问题的方式。 • WD-42对DuckDB的许可证表示担忧，预测可能会出现类似Redis的许可证争议。 • fidotron提到Uber的H3系统可能更具影响力。 • cyanydeez认为QGIS才是最重要的地理空间工具。 • bingaweek对夸张的标题表示不满。 • jeffbee表示尝试使用地理空间工具时遇到困难，认为SQL并不是降低用户门槛的最佳选择。 补充讨论： • 评论中多次提到PostGIS、geopandas等传统工具，显示出DuckDB在功能和简便性上的优势尚有争议。 • 对DuckDB许可证的担忧表明，用户对其长期可持续性和法律问题存在疑虑。 • 对Felt.com等新兴工具的讨论显示出对地理空间技术集成和开发者工具的未来期望。

A PostgreSQL planner semi-join gotcha with CTE, LIMIT, and RETURNING

作者: namanyayg | 评分: 12 | 评论数: 3 | 发布时间: 2025-05-04 01:24
文章摘要

文章描述了在PostgreSQL中使用CTE（Common Table Expression）结合`DELETE ... RETURNING`和`LIMIT`处理队列表任务时遇到的意外行为。尽管查询中明确使用了`LIMIT 1`，但有时会返回多条记录。这是因为PostgreSQL的查询规划器将查询优化为一个嵌套循环半连接（Nested Loop Semi Join），导致子查询（包括`LIMIT 1`）针对每个候选行执行多次，从而可能删除并返回多行。 问题的根源在于CTE没有被当作一个优化屏障，规划器自由地将其内联或转换。为解决此问题，作者建议避免在`DELETE`条件中使用CTE，改为直接在`WHERE`子句中使用子查询： ```sql DELETE FROM task_queue WHERE id = ( SELECT id FROM task_queue WHERE queue_group_id = 15 LIMIT 1 FOR UPDATE SKIP LOCKED ) RETURNING item_id; ``` 这样可以确保`LIMIT`在全局范围内应用，从而实现预期行为。

评论摘要
主要讨论点：关于Postgres查询中未定义行为和多行删除的讨论，以及如何防范查询优化带来的意外结果。 不同观点： • [swid] 认为未定义行为（如删除多行）是不应该发生的，并对Postgres查询计划的处理方式提出质疑。他指出博客文章没有给出明确答案，且查询计划可能存在歧义，导致意外删除多行。虽然他理解查询计划的复杂性，但期望Postgres对查询有更明确的单一解释。 • [wordofx] 对博客文章中使用CTE（Common Table Expression）选择所有数据的做法提出质疑，认为没有必要使用CTE来返回所有数据，可能存在过度复杂化的问题。 • [abhisek] 关注如何防范查询优化导致意外结果的潜在风险，指出这可能引发严重bug。他提出是否可以通过linter工具或在CI阶段进行检测，以避免这些问题在生产环境中出现。 补充讨论： • [swid] 提到了查询计划的歧义性以及Postgres在处理此类查询时的潜在问题，可能存在bug。 • [abhisek] 提出了实际应用中的风险管理问题，建议通过技术手段（如linter工具和CI检测）来提前发现和防止这些问题。 争议焦点：Postgres查询计划的处理是否应该更明确、单一，以避免多行删除等未定义行为的发生，以及如何在开发过程中有效检测和防范这些风险。
