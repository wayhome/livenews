PSA: SQLite WAL checksums fail silently and may lose data

作者: avinassh | 评分: 147 | 评论数: 9 | 发布时间: 2025-07-24 14:48
文章摘要

本文讨论了SQLite数据库在WAL模式下的校验和（checksum）处理机制。尽管SQLite在WAL模式中引入了校验和，但它不会在检测到校验和错误时抛出错误，而是直接丢弃出错帧及其后的所有帧，即使它们未损坏。这种行为是设计使然，不是bug。SQLite在校验和验证过程中，通过单次扫描WAL文件来检查每个帧的校验和，并在发现第一个无效校验和时停止。如果缺少伴随的`.db-shm`文件或在WAL写入时发生不洁关机，就可能触发此问题，导致数据丢失。作者认为，默认行为不应直接截断WAL文件并丢失数据，而应抛出错误让代码处理，并建议提供选项让用户选择是否忽略损坏数据。SQLite的这种设计可能是为了在嵌入式环境或移动设备上更好地运行，而非像企业级数据库那样处理数据损坏。

评论摘要
主要讨论点：SQLite的WAL（Write-Ahead Log）中的校验和（checksum）功能的目的和效果，尤其是在数据损坏检测和恢复中的作用。 不同观点： • **teraflop**：认为WAL中的校验和主要用于检测部分写入（partial writes），而不是任意数据损坏。部分写入的检测对于崩溃恢复至关重要，而全面的数据库校验和并非WAL的初衷。SQLite的journal（无论是回滚journal还是WAL）始终使用校验和。 • **lxgr**：支持SQLite依赖底层系统处理数据损坏，WAL中的校验和设计是有意为之，并符合SQLite文档中的假设和设计理念。SQLite期望由底层存储系统处理数据损坏问题。 • **kburman**：认为SQLite的WAL校验和实际上是一种安全特性，而不是缺陷。WAL的设计防止了数据库损坏，而不是导致损坏。 • **cwillu**：强调SQLite的WAL机制确保数据库最终处于一个实际存在过的状态，即便这意味着可能丢失部分提交的事务。相较于数据库处于不可用状态，丢失部分数据是更好的结果。 • **slashdev**：指出如果校验和失败，数据库应停止在第一个错误点，以恢复到最后一个良好的状态，而不是尝试继续应用后续的WAL页，因为这会导致数据库损坏。 • **ryanjshaw**：认为SQLite的设计（在检测到损坏时自动恢复到之前状态）是有道理的。在应用程序中，如果WAL损坏，应用逻辑应自行处理数据恢复，例如从云端重新同步。 • **dathinab**：提到SQLite有一个官方的校验和VFS shim，但它的使用需要手动检查和处理。同时，SQLite的校验和并不是为数据备份或恢复设计的，更多高级数据恢复方法可能需要额外的实现。 • **adzm**：建议SQLite应该提供一种机制，将校验和错误通知应用层，以便应用自行处理。 • **westurner**：探讨了使用Merkle树哈希代替当前的WAL校验和的可能性，认为这样可以提供更强的数据一致性保障，尤其是在分布式系统中。 补充讨论： • SQLite的WAL校验和是否足够用于防止数据损坏存在争议。部分观点认为WAL的校验和设计目的明确，足够应对崩溃恢复，而另一些人则认为可以增强错误处理和通知机制。 • 关于如何改进SQLite的校验和功能，提出了诸如Merkle树等更复杂的校验机制，以实现更强的数据一致性和错误恢复能力。 • 讨论中也提到了SQLite的各种扩展和替代方案，例如使用RAFT、CRDT等技术的分布式SQLite版本，以应对不同场景下的需求。 争议焦点： • SQLite的WAL校验和是否应该用于检测任意数据损坏，还是仅限于部分写入检测。 • 在检测到损坏后，SQLite是否应提供更明确的错误通知机制，让应用层处理数据恢复。 • 是否需要增强SQLite的数据一致性保障机制，如引入Merkle树等更复杂的校验方法。

There is no memory safety without thread safety

作者: tavianator | 评分: 167 | 评论数: 18 | 发布时间: 2025-07-24 15:35
文章摘要

本文讨论了“内存安全”的定义及其局限性，指出通常所指的内存安全语言能防止使用已释放内存或越界访问内存。然而，作者认为这种细分（如内存安全与线程安全）并不实用，程序真正需要的是“无未定义行为”。文章通过Go语言的例子展示了数据竞争如何导致内存安全问题，例如Go程序中因接口类型和并发操作不当引发的崩溃。相比之下，Java通过严密的并发内存模型避免了类似问题，确保即使在数据竞争情况下也不会出现解引用无效指针的错误。作者提出，确保并发程序安全有两种方法：一是限制编译器优化以保证多字值的一致性（如Java、C#），二是通过强类型系统排除数据竞争（如Rust、Swift）。Go未能完全实现这两种方法，因此并非严格意义上的内存安全语言。

评论摘要
主要讨论点：Go 语言的内存安全性和并发处理问题 不同观点： • **chadaustin 的观点**：Go 语言并非内存安全，特别是在并发访问数据结构时，可能出现段错误。他提到在新工程师不注意同步数据结构时，这样的问题在 Dropbox 的 Go 服务器中很常见，并指出 Swift 也有类似问题。 • **crawshaw 的观点**：内存安全是一个重要问题，尤其对于 C 程序而言，但线程安全对于 Go 程序并非主要问题。他认为理论上的讨论在实践中并不成立。 • **FiloSottile 的观点**：在实际的 Go 代码中，数据竞争导致的可利用漏洞很少见。相比之下，C/C++ 中的内存安全问题更常见。他认为内存安全是一个光谱，收益会逐渐减少。 • **norir 的观点**：大多数支持线程的语言默认使用全局变量和无限制的内存共享，这是数据损坏和竞争的主要来源。虽然进程模型能避免这些问题，但其开销较大。他建议通过消息传递来减少线程间的数据共享问题。 • **Thaxll 的观点**：Go 语言在常见定义下是内存安全的，实际中很少见到因数据竞争导致的漏洞。他质疑讨论此问题的实际意义。 • **jchw 的观点**：虽然 Go 的数据竞争问题确实存在，但在实际生产环境中很少遇到。Uber 的文章总结了 Go 开发者实际面临的问题，数据竞争并不常见。他认为即便存在问题，也可以通过修复来解决，并不会对现有 Go 代码造成重大影响。 • **loeg 的观点**：质疑为何仍在争论内存安全的定义。 • **chc4 的观点**：Zig 语言声称内存安全，但在并发处理上缺乏类似于 Rust 的 Send/Sync 类型支持，可能在引入 async 支持后会出现问题。 • **advisedwang 的观点**：Go 强调使用通信原语而非直接内存共享，以此避免并发问题。 • **Mawr 的观点**：用极端例子讽刺讨论中的某些观点。 • **nromiun 的观点**：大多数程序并非多线程或并发，内存安全问题更普遍。 • **munificent 的观点**：同意需要线程安全来保证内存安全，但认为未定义行为和内存安全是不同的问题，Go 缺乏内存模型保证，实践中很少成为问题。 • **tptacek 的观点**：认为 Go 不存在内存损坏漏洞，实际中几乎没有针对 Go 程序的内存安全漏洞。他批评了过度定义“内存安全”的讨论。 • **qcnguy 的观点**：指出编程语言理论中的并发讨论忽视了数据库中的并发问题，如缺少锁定或事务处理，这可能比语言层面的并发问题更重要。 • **danbruc 的观点**：没有未定义行为并不意味着线程安全，例如 .NET 中对宽变量的写入不保证原子性，这可能导致线程安全问题。 补充讨论： • 争议焦点在于 Go 语言是否应被视为内存安全，特别是在并发访问数据结构时的问题。 • 讨论还涉及内存安全与线程安全的区别，以及不同语言在处理这些问题上的优劣。 • 实际开发中并发问题的发生频率和严重性也是讨论的重要方面。

Use Your Type System

作者: ingve | 评分: 103 | 评论数: 28 | 发布时间: 2025-07-24 14:57
文章摘要

文章讨论了一种简单但有效的技术，通过定义不同的类型来避免在编程中因使用基本类型（如整数、字符串、UUID）而导致的错误。例如，用不同的ID类型（如AccountID和UserID）代替通用UUID，以防止传递错误参数。作者在Golang的天气计算库*libwx*中应用了这种方法，为每个测量值定义专属类型，并提供转换方法，避免直接使用*float64*带来的潜在错误。编译器能帮助捕获这些错误，避免运行时问题。文章强调充分利用类型系统可显著减少类似错误，并建议广泛采用这种技术。代码示例可在GitHub上找到。

评论摘要
主要讨论点：类型系统及其在软件开发中的应用与优缺点 不同观点： • pclowes：支持使用类型系统来避免不良状态，但指出如果开发者仅停留在第一层级的类型实现，可能会导致类型繁杂、难以协同工作。如果能进一步将逻辑推入类型控制流，如使用联合类型和模式匹配，体验会变得更好。 • abraxas：支持使用检查异常（checked exceptions）来处理不同类型的异常，并分享了实际项目中的成功经验。尽管初期团队成员有抵触，但最终项目变得非常健壮。 • taeric：认同类型系统的总体理念，但指出在处理字节移动和特定领域计算混合的代码时，类型系统可能会失败。 • tyleo：分享了在C#中使用带有标记类型（marker types）的结构来创建唯一标识符的实践，并提到在TypeScript和Rust中的类似应用。 • bbkane：提到在Go语言中由于自动转换特性，类型安全的好处不明显，最终放弃了这种做法。 • recursivedoubts：认为复杂的类型系统可能导致不必要的负担，尤其是对于已经熟悉基本类型（如UUID、String）的开发者来说。 • tonymet：认为从Python、Perl或PHP转向Go时，早期强制考虑类型在中等复杂度项目中会带来好处。 • mcflubbins：分享了个人经验，认识到类型系统在防止错误和提高代码可读性方面的价值。 • jjice：询问这种方法的专业术语，并表示这种概念超越了普通的强类型。 • peterldowns：引用了朋友Lukas的术语“Safety Through Incompatibility”来描述这种技术，并提供了相关文章链接。 • jerf：认为这种技术是使用类型系统防止错误的基础方法，但在实际推广中遇到很多阻力，常常需要解释和争取。 • hiddew：提到在具有内联类型的语言（如Kotlin）中可以避免构造/析构的开销。 • jshxr：指出在TypeScript等结构化类型语言中实现这种方法可能会有些尴尬，常常需要使用hack方式。 • mk_chan：分享了在C++中使用hack方法的长期经验，并表达了对C++语法和默认设置的不满。 • fellowniusmonk：持哲学性观点，认为复杂类型不存在，只有模式存在，应避免滥用类型。 补充讨论： • 争议的焦点在于类型系统的复杂性和实用性。一些开发者认为复杂的类型系统可以提高代码健壮性和可维护性，而另一些开发者则认为这可能导致不必要的复杂性和负担。 • 实际应用中的类型系统和检查异常的成功案例和挑战也被广泛讨论，尤其是在团队接受度和项目实施中的实际效果。 • 不同语言对类型系统的支持程度和实现方式也有所讨论，如Go的自动转换特性、TypeScript的结构化类型等。 • 术语和命名问题也被提及，显示出在类型系统应用中对统一术语的需求。

I wasted weeks hand optimizing assembly because I benchmarked on random data

作者: thunderbong | 评分: 37 | 评论数: 2 | 发布时间: 2025-07-21 07:40
文章摘要
