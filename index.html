Deciphering language processing in the human brain through LLM representations

作者: Korling | 评分: 53 | 评论数: 3 | 发布时间: 2025-03-21 18:44
文章摘要

这篇文章探讨了人类大脑在日常对话中如何处理自然语言，并与大型语言模型（LLMs）的处理方式进行比较。研究表明，LLMs通过自监督学习目标（如下一词预测）和强化学习生成上下文相关的语言输出，其内部表示（嵌入）与人类大脑处理语言时的神经活动呈现线性对应关系。研究使用侵入性电极记录人脑神经活动，并与Whisper语音转文本模型的嵌入进行比较，发现模型中的语音嵌入与大脑语音区（如颞上回，STG）活动对应，语言嵌入与语言区（如布罗卡区，Broca's area）活动对应。在语言理解和生成过程中，模型嵌入能准确预测神经响应的时序，揭示了LLMs在理解人脑语言处理机制方面的潜力。研究发表在《Nature Human Behaviour》上。

评论摘要
主要讨论点：当前模型是否仅仅是“随机鹦鹉”以及研究对未来科技发展的潜在影响 不同观点： • [cs702] 认为当前的模型不仅仅是“随机鹦鹉”（即只是机械地重复数据）。他引用了原作者的研究结果，指出这些模型通过学习可以对世界进行类似于人脑的表征。具体论据包括：语音编码器的嵌入通过线性变换后，与大脑处理语音区域的神经活动模式高度吻合；同样，语言解码器的嵌入通过线性变换后，与大脑语言处理区域的神经活动模式相吻合。 • [ogogmad] 从这个研究引申到了是否可能将人脑上传到计算机，以实现“杀死死亡”的梦想。虽然这一观点较为科幻且未深入讨论技术可行性，但表达了对该研究可能带来永生技术的期待。 • [taosx] 对谷歌的研究表示赞赏，并期待这项研究能进一步推动对大脑的理解和“破解”大脑的潜力。他的观点侧重于希望通过这类研究，人类能更深入理解大脑并带来更多科学发现。 补充讨论： • 争议焦点：[cs702] 主要关注当前模型的能力和人脑表征之间的关系，反驳“随机鹦鹉”的观点；而[ogogmad] 和 [taosx] 则更关注这项研究在未来科技（如脑机接口和大脑上传）方面的潜在应用。 • 讨论的延伸：[ogogmad] 提出的“上传大脑”概念虽然在科学上尚属科幻，但引发了对这项研究长远影响的思考；[taosx] 则希望通过这类研究破解大脑，带来更实用的科学进步。

Whose code am I running in GitHub Actions?

作者: ingve | 评分: 56 | 评论数: 10 | 发布时间: 2025-03-25 17:17
文章摘要

这篇文章讨论了GitHub Actions中使用可变引用（如标签）可能带来的安全风险。具体来说，有人在一周前向`tj-actions/changed-files` Action添加了恶意代码，导致秘密信息可能泄露。问题源于常用标签引用实际上是可变的，如果标签指向的提交被更改，Action将运行不同的代码。 为解决此问题，作者提供了一个shell脚本，用于检查本地仓库中所有使用的GitHub Actions，列出并统计每个Action的使用次数。作者建议使用不可变的提交ID来确保代码不变，并建议评估所使用Action的来源和必要性，优先使用来自大组织或自己编写的Action。 脚本通过Unix管道和一系列文本处理工具实现，具体步骤包括查找工作流文件、提取使用Action的行、清理和统计结果。作者最后对自己的项目进行了检查，发现大多数Action来自大组织，风险较小。

评论摘要
主要讨论点：GitHub Actions 的安全性和使用可变引用（mutable reference）的风险 不同观点： • [donatj] 认为使用可变 Git 标签作为版本控制机制存在设计缺陷。即使标签如 "v2" 看似指向某个固定版本，但实际上可能被更改为指向不同的提交（commit），从而导致下次运行时执行不同的代码。这种设计让维护者需要删除并重新标记主要版本，以确保标签指向最新的次要版本。 • [dgl] 指出，使用短提交 ID（short commit ID）作为引用仍然存在风险，因为如果有人能找到冲突或推送同名标签，可能会导致引用变得可变。即使 GitHub 禁止推送某些特定长度的标签，其他服务可能没有类似限制。 • [mmmaantu] 认为即使固定 SHA 也可能无法完全解决问题，因为如果依赖的资源本身没有固定其依赖，则仍然可能通过易受攻击的标签拉取不安全的资源。作者期待 GitHub 的一个未来功能（GitHub 路线图问题 #592）能解决这一问题。 • [dietrichepp] 分享了个人经验，提到在使用 GitHub Actions 时，参考了一些公开的步骤，但最终选择自己编写代码来减少对公开 Actions 的依赖。虽然这样做更耗时，但可以减少对 GitHub Actions 的依赖，使得 CI 构建更具灵活性。 • [password4321] 提到该文章可能是在回应最近一个被超过 23K 仓库使用的 GitHub Action 被入侵的事件，并指出这个讨论并不是重复的，而是讨论一种检测工具。 • [Jenk] 表示 GitHub 文档中早就提到了安全加固的方法，并提到有些工具和 linter 可以警告未使用固定 SHA 的情况，但具体工具名称记不清楚。 • [bdcravens] 提到 GitHub Actions 确实可能被滥用，例如用于网络爬虫以绕过某些限制，因为 GitHub Actions 使用的是住宅 IP 地址空间。 • [ohgr] 认为当前软件生态系统普遍存在从互联网下载任意内容并运行的现象，相对于整个生态系统的问题，GitHub Actions 的风险只是一个小问题。 补充讨论： • 争议的焦点在于 GitHub Actions 使用可变标签的设计是否合理，以及如何有效避免因引用可变性导致的安全风险。部分用户认为通过固定 SHA 可以解决问题，但也有用户指出这种方法的局限性。 • 讨论中还涉及 GitHub Actions 可能被滥用的场景，例如用于网络爬虫等活动，这引发了对平台安全性和使用规范的进一步思考。
