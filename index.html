文章摘要

这是一个将1991年Microsoft Word 1.1a（代号Opus）移植到64位Windows的开源项目。项目保留了原始C源代码和资源文件，通过以下方式实现现代化： - 将16位x86汇编代码翻译为C/C++ - 适配分段内存模型到x64架构 - 将Win16 API调用转换为Win32 API - 使用现代工具重新构建原始资源 构建环境需要Visual Studio 2022和CMake 3.25+。项目包含完整的测试套件，覆盖运行时、数据结构和UI自动化测试。 这不是模拟器或重新实现，而是让原始Word应用以64位可执行文件的形式运行，保持了原汁原味的用户体验。项目提供了详细的构建说明和测试流程，适合研究早期文字处理软件的架构和实现。

Improving Heuristics for A* Pathfinding

文章摘要

这篇文章介绍了一种通过改进启发式函数来优化A*寻路算法的技术。 文章指出，传统的距离启发式不了解地图中的墙体障碍，常常指向错误方向。虽然"完美启发式"能准确反映真实路径，但为每个目标计算代价太高。 核心方法是使用"地标"(landmark)技术：预先计算到特定地标点的距离，然后利用三角不等式 cost(B, X) ≥ cost(B, L) - cost(X, L) 来估算到其他目标的距离。当目标点在起点到地标的路径上或附近时，这个估算特别有效。 由于单个地标只对特定方向有效，文章建议使用多个地标，并取它们提供的最大下界值作为改进的启发式函数，从而减少A*需要探索的节点数量，提升算法性能。

这篇文章介绍了如何制作带抖动图像的二维码。核心方法是： 1. **基本原理**：二维码分为功能模块（定位图案）和数据模块。通过缩小数据模块，可在剩余空间嵌入低分辨率图像。 2. **抖动技术**：使用Floyd-Steinberg误差扩散算法，从左上角开始阈值化像素，并将误差分散到相邻未处理的像素，使整体亮度更接近原图。 3. **关键改进**：进行两次误差扩散处理。第一次专门处理数据模块产生的随机噪点，第二次进行常规抖动，大幅提升图像清晰度。 4. **实际应用**：这种二维码适合用于大屏幕或海报，但在易损坏的材料（如可能被揉皱的传单）上扫描效果会受影响。二维码的纠错能力允许修改少量像素而不影响扫描。

Shopify replaced Redis with MySQL for inventory reservations–and it scaled

文章摘要

Shopify在结账库存预留系统中用MySQL替换了Redis,以解决超卖问题。原Redis方案将预留和库存账本分离在两个系统中,无法保证原子性,可能导致超卖或少卖。新方案利用MySQL 8的SKIP LOCKED特性,采用"一行一个库存单位"而非"一行一个商品"的设计,将预留和账本放在同一数据库中,通过ACID事务保证一致性。系统为每个商品/地点组合维护最多1000行的可用行池,预留操作从池中消费行,补充流程从账本补充。该方案成功支撑了2025年黑色星期五每分钟510万美元的销售峰值。

评论摘要
主要讨论点：Shopify库存系统从Redis迁移到MySQL的技术方案，特别是"每个item/location维护1000行池"的设计选择 不同观点： • **质疑派**：manbash对1000行池方案感到不适，认为这是为避免同步问题的权宜之计；bijowo1676认为设计不佳，建议用cart*SKU而非shop*SKU的1000行方案；jdw64质疑从高并发的Redis退回到线程模型的MySQL是倒退 • **替代方案派**：isigal提出更简单方案——预留时直接扣除库存，超时后用后台GC进程归还；codedokode建议按shop_id分片并用UPDATE状态替代删除行；nurettin激进地建议自建数据库系统 • **理解派**：firasd认为reserved_quantities本质是临时表，两种方案差异不大；srcreigh关注到实现该方案需要移除50%读操作和33%事务的代价 • **文章质量批评**：REPLicated2批评文章表名不一致、质量马虎；culi不满结尾的AI生成图片显得廉价 补充讨论：mrloopex和shay_ker持积极态度，欣赏真实案例分享；zhivota引用文章核心教训——真正瓶颈往往不是表面观察到的问题
