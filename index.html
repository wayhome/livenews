RFC 10008: The new HTTP Query Method

作者: schappim | 评分: 62 | 评论数: 8 | 发布时间: 2026-06-17 10:51
文章摘要

这篇RFC 10008规范定义了HTTP的QUERY方法。QUERY方法用于发送安全且幂等的请求，将查询参数放在请求体中而非URI中。它解决了GET方法URI长度限制和POST方法语义不明确的问题。与GET类似，QUERY是安全幂等的，支持缓存和自动重试；与POST类似，可在请求体中传输大量复杂数据。这为需要传输大量查询参数的场景提供了标准化解决方案，避免了URI过长、编码低效和日志泄露等问题。

评论摘要
主要讨论点：HTTP QUERY 方法提案的可行性和实用价值 不同观点： • 支持派：认为 QUERY 能解决实际问题，如避免 POST 表单刷新重复提交警告（CodesInChaos），突破查询字符串的长度限制（lanycrost），以及为复杂 API 提供更语义化的搜索端点替代方案（toybeaver） • 质疑派：认为提案动机不足，示例过于简单且可用 GET 替代（100ms）；将请求体作为缓存键存在语义问题，用户可控的无界缓存键易被恶意利用；复杂场景下的缓存应在应用层而非 HTTP 层实现 • 务实派：指出历史教训——WebDAV SEARCH 方法存在近 20 年但因中间件兼容性问题未被广泛采用（haeseong）；大量代理、WAF 和负载均衡器会剥离或拒绝不认识的方法的请求体，实际部署中 POST + 缓存头更可行 补充讨论：有人提出用 POST 配合新缓存头（如 "Vary: request-body"）实现相同语义，向后兼容性更好（100ms）；也有人关注浏览器书签是否支持保存请求参数（andltsemi3）；还有人提议用 ETag 配合 POST 实现幂等性（brookst）。核心争议在于是否值得为小众场景引入新方法及其基础设施成熟度。

文章摘要

这篇文章介绍了如何在漏洞赏金活动中攻击IIS服务器的实战技巧。 **主要内容包括：** **发现IIS服务器的方法：**使用Shodan搜索、Google Dork查询、以及通过响应头进行技术指纹识别。 **攻击技术：** - 利用HTTP/1.0请求泄露内部IP - 使用Nuclei模板自动化扫描 - 绕过HTTPAPI 2.0错误页面 - IIS波浪号枚举漏洞 - 利用LLM和GitHub/BigQuery解析短文件名 - 针对IIS的目录爆破 - 利用web.config配置文件获取敏感信息 - 通过路径遍历、DLL暴露、反向代理混淆等方式进行攻击 - NTFS特性绕过认证 - 文件上传技巧 - HTTP参数污染绕过WAF 文章强调IIS服务器常被错误配置，蕴含大量安全隐患，值得深入挖掘。

评论摘要
主要讨论点：关于IIS（Internet信息服务）Web服务器的技术特性、安全漏洞及其在当代的使用情况 不同观点： • **安全用途观点**（naturalmovement）：主动利用IIS作为蜜罐诱饵，吸引黑客攻击以浪费他们的时间，将IIS的"臭名昭著"转化为防御优势 • **技术分析观点**（Lammy）：深入探讨IIS漏洞的技术根源，指出8.3文件名机制是Windows C盘默认启用、其他盘默认禁用的底层OS行为，与IIS默认安装在C:\Inetpub有关 • **历史回顾观点**（xmcp123）：回忆过去IIS扫描器泛滥的时代，目录遍历漏洞（仅通过URL编码"../"）曾让整个互联网服务器日志几乎无法使用，持续数月 • **质疑相关性观点**（t1234s）：直接质疑IIS是否还有人使用，暗示该技术可能已过时 补充讨论： 多位评论者关注文章本身的呈现质量——有人称赞桌面端设计精美、内容优秀（sytelus），有人指出网页格式问题如左侧边栏遮挡正文（NooneAtAll3）和移动端显示故障（AuthAuth），还有人希望看到nginx的类似分析（Group_B）。整体而言，这是一篇引发技术怀旧和安全讨论的文章。
