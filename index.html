Rust running on every GPU

作者: littlestymaar | 评分: 277 | 评论数: 16 | 发布时间: 2025-07-26 10:08
文章摘要

本文介绍了一个使用Rust编写的跨平台GPU计算演示，能够在多个主要GPU平台上运行，包括CUDA（NVIDIA GPU）、SPIR-V（Vulkan兼容GPU）、Metal（Apple设备）、DirectX 12（Windows）和WebGPU（浏览器），并为非GPU系统提供CPU后备。该项目通过结合Rust GPU、Rust CUDA和Naga等项目，实现了用标准Rust代码直接编译到多个GPU目标，避免了传统的专用着色器语言。 演示实现了一个简单的bitonic排序算法，计算逻辑在CPU和GPU上运行相同的代码。通过Rust特性标志和编译目标选择不同的后端和驱动API，如wgpu、Vulkan、CUDA等。尽管演示使用了单一计算内核，但底层工具支持多个内核和入口点。该项目展示了Rust在跨平台GPU计算方面的潜力，尽管仍有诸多待改进之处，但已是一个重要的里程碑。

评论摘要
主要讨论点：Rust与GPU编程中的抽象层次及其优缺点 不同观点： • Voultapher指出，在Rust代码和硬件之间存在多层抽象（如wgpu、Vulkan等），这些层次隐藏了复杂性，但可能影响性能。他认为，如果需要深入了解或优化，这些抽象可能成为障碍。 • vouwfietsman对GPU API的抽象持怀疑态度，认为不同硬件目标之间存在显著差异，抽象可能导致错误和性能损失。他建议由厂商提供类似的系统，但指出由于厂商之间的争议，这种方案可能不易实现。 • Archit3ch关注音频应用的性能，对通过多层翻译阶段的 pipeline（如Rust到WebGPU到Metal）表示担忧，认为这可能导致脆弱的性能表现。相比之下，直接使用Metal的Julia表现更好。 • slashdev对打破GPU软件的厂商锁定表示兴奋，认为即使需要针对不同厂商编写特定代码，这种抽象仍能提供跨平台的内核。 • chrisldgk提出疑问，WebGPU是否已经解决了跨GPU后端兼容性的问题，并认为WebGPU本身已经是对原生GPU API的抽象。 • piker对现有no_std和no alloc crates在GPU上运行的潜力表示惊讶，认为这开启了许多有趣的可能性。 • hardwaresofton认为Rust GPU项目的多样性令人振奋，但指出不同项目基于不同基础，建议添加使用Naga的后端。 • bobajeff赞赏GPU Working Group的努力，强调在异构计算和GPU编程中改善开发者体验的重要性。 • gedw99对跨平台开发的简化表示高兴，认为这使得开发者可以专注于构建功能而非平台战争。 • ivanjermakov质疑这是否真的是“Rust”在GPU上运行，认为GPU编程需要特别关注，过度抽象可能导致某些优化无法实现。 • max-privatevoid认为Rust社区需要先学会如何正确加载GPU库。 • rbanffy认为目标应是编写通用代码，并在任何平台上运行。 • omnicognate提到Zig也可以编译成SPIR-V，对其他语言的SPIR-V编译能力不太确定。 • jdbohrman对讨论的动机表示不解。 补充讨论： • 讨论中涉及的具体技术包括WebGPU、Vulkan、Metal、SPIR-V、MoltenVk等，以及Rust的特性如newtype、traits和macros在GPU编程中的应用。 • 争议的焦点在于抽象层次的复杂性与性能之间的平衡，以及是否需要针对不同硬件编写特定代码以实现最佳性能。 • 一些评论者对跨平台抽象的潜力表示兴奋，而另一些则担心性能损失和优化限制。

Font-size-adjust Is Useful

作者: Bogdanp | 评分: 52 | 评论数: 5 | 发布时间: 2025-07-23 11:34
文章摘要

本文介绍了CSS中的`font-size-adjust`属性，并声称包括Google、MDN和CSS规范在内的所有人都误解了其用途。通常认为，`font-size`定义的是字体周围框的高度，而不是字符本身的大小，因此不同字体的实际显示尺寸可能差异很大。`font-size-adjust`可以调整字体，使得字符（如"x"）在不同字体中保持相对一致的显示比例。 主流观点认为，该属性主要用于处理字体回退时的尺寸不一致问题。但作者认为，更有价值的用法是将其应用于网页中使用多种字体的情况，以确保字体尺寸的一致性。作者建议在CSS重置中加入`font-size-adjust: ex-height 0.53`，以统一字体显示比例。

评论摘要
主要讨论点：网页字体和样式在加载过程中的处理方式，包括字体调整、页面闪烁（FOUC）、性能优化等问题。 不同观点： • [adregan] 认为 `font-size-adjust` 和文本框修剪（text-box-trim）在使用场景上最终是相同的，因为它们都关注字体变化对页面质感的影响。 • [alberth] 对 `font-size-adjust` 和 `text-box-trim` 的区别感到困惑，并提供了一个 GitHub 链接以查看具体示例，表明他希望了解两者在实际应用中的不同之处。 • [lelandfe] 反对为了避免瞬间的闪烁（FOUC）而将整个字体内嵌，认为这样会损害页面加载性能。他提供了一个关于高性能网页设计的文章链接，认为那仍然是处理此类问题的权威参考。 • [mananaysiempre] 质疑将页面首次可用渲染置于约1MB资源之后的做法，认为这种为了避免FOUC而牺牲加载速度的策略不合理，特别是在低速或高延迟网络环境下。他提到过去网页设计中对div和内联样式的批评，并怀念早期浏览器提供的“仅缓存图片”选项。 补充讨论： • [Waterluvian] 表示对讨论中的解决方案非常喜爱，并提到自己在游戏开发中遇到字体和图标不一致的问题，认为这正是他所需要的解决方案。 争议焦点： • 是否应该为了避免FOUC而牺牲页面加载性能，特别是在低速网络环境下。 • `font-size-adjust` 和 `text-box-trim` 的具体区别和应用场景，以及它们在实际使用中的效果。 这些观点展示了在网页设计和开发中，如何平衡视觉效果和性能之间的不同看法和实践方法。

Breaking the WASM/JS communication performance barrier

作者: weinzierl | 评分: 65 | 评论数: 5 | 发布时间: 2025-07-23 07:11
文章摘要

Sledgehammer Bindgen 是一个用于加速 Rust 与 JavaScript 之间 WASM 通信的工具，特别为需要快速访问 DOM 的 web 框架设计。与通用的 wasm-bindgen 相比，Sledgehammer 通过批量处理字符串解码、缓存字符串以及将操作编码为字节序列等方法来提升性能。它通过减少每次调用 TextDecoder 的开销，并利用 u32 数组批量读取操作数据，以提高效率。用户可以将 Sledgehammer 与 wasm-bindgen 结合使用，以优化性能。项目提供了文档和示例以供参考。

评论摘要
主要讨论点：Rust社区在改进WASM到JS字符串解码性能的过程中遇到的性能问题及解决方案讨论 不同观点： • **samwillis的观点**：认为Rust社区在解决WASM到JS字符串解码性能问题上取得了进展，但核心问题在于JavaScript引擎需要复制缓冲区以将其作为字符串使用，即使使用TextDecoder API也只能做到单次复制，仍存在开销。他建议引入一种"String View"来包装数组缓冲区，将确保UTF-16的责任交给WASM代码，从而避免复制，但这种方式也带来了复杂性，因为JS中的字符串需要是不可变的，而底层缓冲区可能会被更改。 • **andyferris的观点**：指出UTF-8和UTF-16之间的转换使得问题更加复杂。他希望JavaScript和DOM能够原生支持UTF-8处理，认为即使有TextEncoder/TextDecoder也不够。他建议为整个页面选择一种模式，这对于将原生语言编译到WASM并应用于网页是一个巨大的进步。 • **nhatcher的观点**：提到他以前写过一篇相关的文章，讨论了链接浏览器实现的原则，虽然代码有些过时，但原则仍然适用。他提供了文章链接以供参考。 • **CyanLite2的观点**：对浏览器尚未原生支持此类功能表示遗憾。 • **bcardarella的观点**：关注性能问题，询问与Wasmtime等项目的性能比较。 补充讨论： • 字符串解码性能问题的核心在于缓冲区的复制开销以及UTF-8和UTF-16转换的复杂性。 • 有人提出希望JavaScript和DOM能够提供更原生的UTF-8支持，以简化问题。 • 不同解决方案的性能比较也被提出，如与Wasmtime项目的比较，显示出对实际应用中性能优化的关注。 • 链接外部资源（如nhatcher的文章）提供了进一步的背景信息，有助于理解讨论的背景和相关原则。

It's time for modern CSS to kill the SPA

作者: tambourine_man | 评分: 227 | 评论数: 53 | 发布时间: 2025-07-25 21:08
文章摘要

文章主要讨论了现代CSS技术（如View Transitions API）如何使单页应用（SPA）的优势变得不再必要。过去，SPA通过避免页面重载和滚动位置重置，提供了更流畅的用户体验，但这种方法往往带来了复杂的架构和性能问题，如延迟导航和布局偏移。现代浏览器已经支持原生的页面过渡和交互处理，无需借助JavaScript和客户端路由。通过CSS，开发者可以轻松实现页面淡入淡出、共享元素动画等效果，同时保持真实的URL和页面加载，避免了过度依赖JavaScript带来的性能负担。文章呼吁回归浏览器原生功能，以构建更快、更稳定的网站。

评论摘要
