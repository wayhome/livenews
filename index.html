Error handling in Rust

作者: emschwartz | 评分: 22 | 评论数: 4 | 发布时间: 2025-06-29 20:28
文章摘要

本文讨论了Rust中处理错误的现状和替代方法。目前标准做法是为每个模块或整个包定义一个错误枚举，涵盖所有可能的错误情况。这种方法导致函数返回包含其不会产生的错误变体的枚举，需要手动区分。作者认为这种大错误枚举不理想，提出了一种更细化的方法，即用结构体而非枚举来表示错误，并介绍了一个名为`error_set`的包，它通过宏简化错误枚举的定义和转换。虽然这种方法稍显繁琐，但作者认为在处理复杂错误时更为优雅。文中还提到其他探索类似范式的库，如`SmartErr`，并寻找一种能自动生成错误枚举的宏。

评论摘要
主要讨论点：Rust中错误处理的设计和实现方式 不同观点： • [slau] 认为应为每个函数或动作创建单独的错误类型，这样每个函数只关注自己的错误并生成相应的错误，而不依赖宏，仅使用 thiserror。这种方法强调错误处理的精细化和局部化。 • [burnt-resistor] 建议使用 anyhow 库来避免在 Rust 中重新创建类似面向对象编程（OOP）的错误处理机制。Anyany 提供了一种简化的错误处理方式，避免了复杂的错误类型定义。 • [jgilias] 不赞成使用过多的宏，认为错误枚举（error enums）已经足够，并且可以根据代码库的需要进行细粒度调整，形成类似错误树的结构。他强调代码的可读性和减少“魔法”的必要性，以避免增加额外的认知负担。 • [fwip] 认为为成熟的或核心的库创建精细和特定的错误类型是有价值的，特别是在 API 映射到正交错误集或在积极开发和迭代时。这种方法有助于开发者理解“可能出什么问题”，并且在多层抽象中效果更显著。不过，对于尚在快速发展的 API，可能不会带来太多价值。 补充讨论： • 争议的焦点在于错误处理的复杂性和可维护性之间的平衡。一些开发者（如 [slau] 和 [fwip]）认为更细粒度的错误类型有助于代码的理解和文档化，而另一些开发者（如 [jgilias]）则倾向于简单的错误枚举以保持代码的可读性和降低认知负担。 • 对于是否使用宏和 anyhow 这样的库也存在不同看法，部分开发者（如 [burnt-resistor]）认为这些工具可以简化错误处理，而其他人（如 [jgilias]）则担心这些工具引入了过多的“魔法”，使得代码更难理解。

Most ints are not floats

作者: zdw | 评分: 26 | 评论数: 8 | 发布时间: 2025-06-27 15:57
文章摘要

本文讨论了计算机中整数和浮点数表示的差异。整数（如int32和int64）和浮点数（如float32和float64）在计算机中的表示方式不同，导致大多数整数无法精确表示为浮点数。具体而言，int32类型的整数中，只有约3.5%能精确表示为float32类型；而对于int64和float64，只有约0.5%的int64整数能精确表示为float64。这是因为浮点数用固定位数表示小数部分和指数部分，无法精确表示所有整数。Python中的整数范围不受限，但浮点数对应于float64，因此大整数或高精度数可能无法精确表示为浮点数。

评论摘要
主要讨论点：数据类型转换，特别是整型与浮点型之间的转换及其相关问题 不同观点： • dmurray认为，32位整型和32位浮点型的数量相同，但由于大多数浮点数无法表示为整型，因此反之亦然，即大多数整型也无法表示为浮点型。他批评了一些系统不允许隐式转换浮点型到整型，但却允许整型到浮点型的转换，认为这是不合理的。 • derriz同意dmurray的观点，并补充了自己在长整型到双精度浮点型转换中的类似经历。他指出，C风格语言中从float到double的自动转换可能会导致一些意想不到的问题，尤其是结合方法重载和用户输入解析时。他还提到，这种转换问题在浮点数中比在长整型转换中更不明显。 • tikhonj提到在Avro规范中，整型/长整型和浮点型/双精度浮点型之间的自动转换被用于向后兼容系统，他认为这是一个不必要的错误，并质疑该规范是否在新版本中有所改变。 • deckar01提供了一个关于float32密度的可视化，讨论了float32的结构以及为何需要尾数（mantissa）。他提出了一个设想，即如果将所有31位都用于指数，并将结果标准化为±2^7，就可以得到一个连续的函数版本。 • taeric认为，将浮点数作为实数的计算机表示方式来教学是有问题的，建议将它们视为“科学计数”来帮助理解。 • furyofantares简要重申了dmurray的观点，即在N位的情况下，大多数浮点数不是整型，且由于两者数量相同，因此大多数整型也不是浮点数。 • PaulHoule提到，人们习惯使用双精度浮点型，并且在许多语言（如Javascript）中，只有双精度浮点型和32位整型。他还分享了一些关于幻想计算机的构思，涉及24位和48位字长以及与地址空间相关的复杂设计。 补充讨论： • 评论中涉及了自动类型转换的安全性问题，尤其是在C风格语言中，这种转换可能会导致意外行为。 • 讨论中还涉及到历史和技术发展的假设性话题，如24位计算架构的未实现可能性以及与现代计算系统的比较。 • 对浮点数结构及其表示能力的深入探讨，包括指数和尾数的使用，以及对精度和表示范围的影响。

Bloom Filters by Example

作者: ibobev | 评分: 151 | 评论数: 11 | 发布时间: 2025-06-29 11:56
文章摘要

Bloom Filter是一种快速且节省内存的数据结构，用于判断元素是否存在于集合中。它是一个概率数据结构，可能出现误报，即错误地判断一个元素可能存在于集合中。其核心是一个位向量，通过多个哈希函数将元素映射到位向量的索引位置，并将这些位置标记为1。测试元素是否在集合中时，再次使用相同的哈希函数，检查对应位是否全为1；若不全为1，则元素一定不在集合中；若全为1，则可能存在。 选择合适的哈希函数和参数（如位向量大小m和哈希函数个数k）可以调整误报率。哈希函数应独立且均匀分布，常用Murmur、FNV等。Bloom Filter的插入和查询时间复杂度为O(k)，空间效率高但存在误报可能。设计时需根据预期元素数量n调整m和k以优化性能。

评论摘要
