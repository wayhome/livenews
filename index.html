PNG Is Back

作者: tbillington | 评分: 140 | 评论数: 8 | 发布时间: 2025-06-25 03:54
文章摘要

PNG图像格式在停滞二十年后迎来复兴，获得多家机构推荐，并进行了多项重要更新。首先，新版PNG增加了对HDR的支持，使用4字节实现未来验证的HDR图像显示。其次，正式支持动画PNG（APNG），现已广泛兼容。此外，新版还支持Exif数据，包含版权、拍摄地点等信息。其他更新包括修正错误、 clarification和规范整理。技术巨头如Adobe、Apple、Google等已参与新规范的开发，许多软件如Chrome、Safari、Photoshop等已支持新版PNG。未来更新将专注于提升压缩效率和并行编解码。PNG工作组正推动格式持续进步。

评论摘要
主要讨论点：PNG文件格式的新变化及其相关技术比较 不同观点： • LeoPanthera担心改变压缩算法会破坏向后兼容性，导致出现实际并非PNG格式的新"PNG"文件，类似于USB-C接口的兼容性问题。 • ggm提出需要一种统一的方式来处理人类时间/日期的近似值，特别是在处理历史照片时，例如“照片扫描于2025年，内容关于1920至1940年间的复活节”。 • LegionMammal978指出，新的cICP chunk类型提供了简化的色彩空间信息，适合小图像文件，但其实ICC配置文件已经可以实现类似功能。 • qwertox对PNG正式支持Exif数据表示欢迎，并询问Exif是否包含磁力计（旋转）和加速度（重力）字段，认为这些信息对后期处理很有帮助。 • adgjlsfhk1对PNG与无损JPEG XL的比较表示好奇，希望看到两者的最终对比结果。 • albert_e提到动画PNG（APNG）可以替代动画GIF，具有透明背景和无损压缩的优势，并询问是否存在标准框架的动画SVG。 • kumarvvr表示作为核心技术爱好者，之前未听说过动画PNG，对此感到惊喜。 • Joel_Mckay认为PNG在某些商业应用中虽然流行，但在色彩和曝光处理上存在问题，建议更多使用OpenEXR格式，并选择一致的色彩标准，不支持PNG再增加新的编码选项。 补充讨论： • PNG格式的压缩算法变化及其兼容性问题引发了一些担忧，特别是对旧格式向后兼容的影响。 • 对Exif数据支持的增强被认为是积极的进展，但用户对Exif包含的传感器数据字段有更多期望。 • 动画PNG和动画SVG的技术和怀旧价值引起了一些讨论，特别是关于其应用和标准框架。 • 不同图像格式（如PNG、JPEG XL、OpenEXR）之间的比较也是讨论的重点，特别是在实际应用中的表现和适用性。

How renewables are saving Texans billions

作者: adrianN | 评分: 88 | 评论数: 8 | 发布时间: 2025-06-25 03:59
文章摘要

文章主要讨论了可再生能源，尤其是太阳能，如何为德州居民节省了数十亿美元的电费。作者分析了德州电力可靠性委员会（ERCOT）的数据，比较了2018年和2024年8月的电力成本。结果显示，由于太阳能的迅速扩展，2024年的净负荷（总负荷减去可再生能源发电量）显著降低，从而减少了对化石燃料发电的需求。由于德州的电价由边际发电机（通常是化石燃料发电厂）决定，净负荷的降低直接导致了电价下降。数据显示，2024年8月的电价较2018年同期更低，估计2024年平均电价为39美元/MWh，若没有大量建设太阳能，电价可能会更高。文章得出结论，可再生能源不仅环保，还为德州居民节省了大量电费。

Fun with uv and PEP 723

作者: deepakjois | 评分: 306 | 评论数: 30 | 发布时间: 2025-06-24 18:41
文章摘要

文章介绍了使用 **uv** 和 **PEP 723** 元数据简化 Python 脚本运行的新方法。 **uv** 是一个用 Rust 编写的高速 Python 包和项目管理工具，带有 **uvx** 命令，可自动处理虚拟环境、Python 版本和依赖包。 **PEP 723** 提出了一种在单文件脚本中嵌入元数据的方法，帮助启动器和 IDE 识别所需的 Python 版本和依赖。 结合 **uv** 和 **PEP 723**，可以轻松运行包含依赖的 Python 脚本，例如提取 YouTube 视频字幕的脚本。通过在脚本中加入 shebang 行 `#!/usr/bin/env -S uv run --script`，脚本可直接作为可执行文件运行，无需手动配置环境。这使得 Python 在处理一次性脚本时更加便捷和高效。

文章摘要

这篇文章讨论了哈希碰撞的概率问题。哈希函数将复杂输入映射为一个数字，用于数据存储和加密等领域。当两个不同的输入被哈希函数映射到同一值时，就会发生哈希碰撞，这可能导致问题。文章通过生日问题来解释哈希碰撞的概率。例如，在一个房间里有30个人，他们中有两人同一天生日的概率约为70.6%。类似地，计算哈希碰撞概率时，我们首先计算没有碰撞的概率，然后用1减去这个值。 具体来说，如果有N个盒子（如生日问题中的365天）和k个物品（如房间中的人），没有碰撞的概率是N/N × (N-1)/N × ... × (N-(k-1))/N。因此，至少有一个碰撞的概率是1减去上述结果。文章还提到，随着物品数量增加，碰撞概率逐渐增大，即使有大量盒子，碰撞也难以完全避免。

评论摘要
主要讨论点：UUID v4 的取值范围及其发生碰撞的可能性 不同观点： • UUID v4 具有非常大的取值空间：UUID v4 使用 122 位随机数，这意味着它可以有 2^122 种可能的取值。具体数值为 5.31 x 10^36 种可能的组合。 • 发生碰撞的可能性极低：根据 "生日悖论" 的计算方法，要使得 UUID v4 发生碰撞的概率达到一个微小的值（例如 0.0000000000001%），需要生成约 2.71 x 10^18 个 UUID。这意味着在极大规模的使用情况下，碰撞依然是一个极其遥远的可能性。 • 实际使用中几乎不可能遇到碰撞：由于生成如此大量的 UUID 在实际应用场景中非常罕见，UUID v4 被认为在绝大多数情况下是唯一且安全的，碰撞风险可以忽略不计。 补充讨论： • UUID v4 的优势：UUID v4 依赖于随机生成，不依赖于时间戳或硬件标识，因此在分布式系统中非常有用，可以有效避免集中式管理的问题。 • 数学依据：通过 "生日悖论" 的计算，虽然 2^122 看起来不像是一个天文数字，但实际需要生成的数量（2.71 x 10^18）远远超出了大多数应用场景中可能生成的数量，这使得 UUID v4 非常适合用于需要唯一标识符的场景。 • 潜在争议焦点：尽管理论上碰撞概率极低，但在超大规模数据系统或全球级分布式系统中，仍然存在极小的碰撞概率，因此在某些特殊情况下，可能需要考虑其他更严格的唯一标识方案。
