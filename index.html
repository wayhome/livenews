文章摘要

Kioxia与Dell合作，将40块245.76TB LC9 QLC NVMe SSD装入2RU PowerEdge R7725xd服务器，容量达9.8PB，支持5个400Gbps网卡，面向AI、数据湖和备份等高密度存储场景；满机柜可达196PB。

评论摘要

Windows 9x Subsystem for Linux

作者: ibobev | 评分: 161 | 评论数: 16 | 发布时间: 2026-05-13 10:37
文章摘要

WSL9x 是一个让现代 Linux 6.19 内核协同运行在 Windows 9x 内核中的实验项目。它由补丁版 Linux、VxD 驱动和 16 位 wsl.com 客户端组成，支持加载内核、处理系统调用/缺页、利用 DOS 窗口作终端，并需交叉工具链与 Open Watcom 构建。

评论摘要
主要讨论点：围绕一个面向 Windows 9x/i386 的兼容/移植项目，讨论其怀旧价值、实际用途和技术可行性。 不同观点： • 支持与惊叹：有人对“128MB RAM 的 Pentium 跑 Win95/98”表示“富得流油”，也有人称“无 AI 编写”很赞，认为这个项目很酷。 • 怀旧与历史反思：有人感叹若 90 年代就有这种东西，很多事会不同；也有人觉得它像“完美 OS”的某种补丁。 • 实用怀疑：不少人质疑为什么会有人想继续用 Win9x，甚至觉得做这么复杂的东西“难以想象”，并追问它到底实不实际、能否作为“老爸老妈客户端”的低维护方案。 • 技术类联想：有人把它类比为 colinux，另有人问能否运行 Linux subsystem；也有人提到 2026 年 Linux 内核仍支持 i386，感慨老平台未被完全抛弃。 补充讨论： • 夹杂了对界面/平台的玩笑（如“以为是 GitHub，结果是 Codeberg/Forgejo”）以及对 Windows 粉丝的嘲讽；还有人认为这类帖子在刷屏。

Δ-Mem: Efficient Online Memory for Large Language Models

作者: 44za12 | 评分: 175 | 评论数: 14 | 发布时间: 2026-05-16 09:30
文章摘要

论文提出 δ-mem：一种面向大语言模型的轻量在线记忆机制。它在冻结的全注意力模型上加入固定大小关联记忆状态，用 delta-rule 更新，并通过低秩修正影响注意力。仅 8×8 状态即可提升多项记忆任务表现，同时基本保留通用能力，无需扩展上下文或全量微调。

评论摘要
主要讨论点：围绕 δ-mem/Δ-Mem 论文的“LLM记忆”能力、实际价值、评估方式，以及 HN 标题自动改写问题展开。 不同观点： • 标题与符号问题：有人指出 HN 将论文标题中的小写 δ 改成大写 Δ，改变了含义；认为 HN 不应自动修改非 ASCII 字符大小写。另有人也注意到标题与论文不一致，怀疑是大小写转换导致。 • 对论文技术价值的怀疑：有评论认为 δ-mem 只是把 DeltaNet/hypernetwork 加到现有 LLM 上，并不算特别新颖或突破；也有人担心固定大小记忆可能只是过拟合或测试集泄漏，需要细读验证。 • “记忆”能力的根本限制：有人认为固定大小状态矩阵并未真正解决记忆容量问题。即使能压缩更多上下文，也仍要把查询和记忆正确关联；输入细微变化会造成激活差异，影响缓存效果。真正需要的是基于语义抽象的上下文搜索，让相似事件/对象触发相同响应。 • 实用需求导向：有人希望看到经过实践验证、对编码代理真正有用的记忆机制，而不仅是论文或插件；例如让 agent 记住代码库规范，而不是每次会话都重新喂入多份 Markdown 并消耗 token。 • 模型评估指标建议：有评论主张所有模型都应明确报告运行所需 RAM 字节数，并附带首 token 时间、吞吐、延迟等指标。仅用参数量会掩盖 FP16、INT4、MoE 等差异，无法反映真实部署成本。 • 能耗与复用：有人提出应复用他人已完成的相似搜索/任务，避免每次从零开始，节省能源；更进一步应先判断任务是否有必要执行。 补充讨论： • 有人认为 HN 上高票论文与实际重要性相关性不强，更像抽奖，Twitter 上常有更有价值的论文传播。 • 另有评论调侃论文是否也是 AI 生成的。

Frontier AI has broken the open CTF format

文章摘要

作者以资深CTF选手经历指出：前沿AI已能自动解决大量中高难题，开放CTF逐渐变成比拼模型、算力和编排能力的“付费赢”游戏，削弱了排行榜、招募参考和新人学习阶梯的意义，也打击出题者热情。

评论摘要
主要讨论点：AI/LLM 对开放式 CTF（网络安全 Capture The Flag）竞赛与学习路径的冲击，以及标题表述是否清晰。 不同观点： • 标题/术语不清：有人认为原题“The CTF scene is dead”更直观，新标题“Frontier AI...”容易误解；多位评论者指出文章开头应解释 CTF，否则会被误认为文件格式、加密标准等。 • AI 正在破坏 CTF 的学习价值：评论认为新手会过早依赖 AI，跳过“主动挣扎”与直觉养成；这不仅影响 CTF，也类似教育领域中学生用 LLM“代做”的问题。 • CTF 并非死亡，而需适应新工具：有人认为变化不等于终结，比赛仍可存在，只是要承认 AI 工具成为技能展示的一部分，类似游戏中区分普通竞赛与 TAS（工具辅助速通）。 • 线下/受控环境可能是出路：有人建议借鉴竞赛编程，转向现场赛、断网、统一新装系统、限定本机工具等方式，但也承认组织成本更高。 • AI 已显著增强攻防能力：有评论举例用模型反混淆代码，反而得到强大的反混淆器；也有人回忆早期 ChatGPT 已能在安全 workshop 中拿高名次，认为如今 agent 更可能全面碾压。 • 争议焦点：CTF 的核心到底是“人类竞技/学习”还是“使用最强工具解决问题”；AI 优势是否意味着开放赛失去意义，还是只是规则需要重构。 补充讨论： • 有人提出可设计更难题目或“AI 才能找到的 flag”，但也质疑难度上升是否会让 CTF 失去可学性。另有人关心 AI 在黑盒攻击、真实互联网目标上的能力是否同样超过人类。
