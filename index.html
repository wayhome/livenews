文章摘要

WebAssembly（Wasm）3.0标准正式发布，这是继2.0版本后的重大更新。主要新增功能包括：支持64位地址空间（理论上可达16EB）；允许单个模块使用多个内存空间，提升灵活性和安全性；引入垃圾回收机制，提供基本内存管理功能；扩展类型系统，支持更丰富的引用类型；新增尾调用指令，优化函数调用效率；添加原生异常处理机制，提高跨平台兼容性；以及放宽向量指令限制，增强SIMD操作的硬件适应性。这些改进显著提升了Wasm在非Web环境中的应用能力，支持更大规模应用和更复杂的语言特性编译。

评论摘要
主要讨论点：[WebAssembly 3.0 的新特性及其影响] 不同观点： • **64位支持**：jjcm 对默认支持64位表示兴奋，认为这将解除Web应用（如在线视频编辑器和Figma）的32位限制，但对移动设备的内存上限表示担忧。 • **垃圾回收（GC）**：j0e1 对Wasm GC的低级特性表示惊叹，而preommr 则担心人们会误解GC的能力，认为C++和Rust仍是主要选择。jasonthorsness 指出当前GC功能尚不足以支持C#运行时。 • **版本化发布模型**：re 对Wasm转向版本化发布模型表示疑惑，并询问其与“evergreen”模型的关系。 • **开发者体验**：alabhyajindal 批评Wasm的开发者体验较差，认为Binaryen.js的文档和设计不够友好。 • **多内存支持**：flohofwoe 探讨多内存特性是否有助于避免WebGPU资源映射时的额外拷贝问题。 • **DOM支持**：hinkley 调侃Wasm仍未提及DOM支持，预计需等待Wasm 4.0。 • **微控制器应用**：boricj 询问Wasm是否仍使用64 KiB页面，认为这在微控制器（如图形计算器）上可能不适用。 补充讨论： • **组件模型**：pbiswal 询问组件模型工作是否与3.0版本相关。 • **内存限制**：modeless 探讨16 GB内存限制的技术原因及JS堆大小的限制是否同步放宽。 • **语言支持**：spankalee 希望AssemblyScript能转向Wasm GC，认为GC支持已足够广泛。

One Token to rule them all – Obtaining Global Admin in every Entra ID tenant

文章摘要

研究人员在准备今年7月的Black Hat和DEF CON演讲时，发现了微软Entra ID（原Azure AD）的重大安全漏洞。该漏洞由两个部分组成：微软后端使用的未公开"Actor tokens"（演员令牌）以及Azure AD Graph API中未正确验证源租户的关键缺陷，使得攻击者可以跨租户访问任何用户（包括全局管理员）的数据。该漏洞允许攻击者完全控制任何Entra ID租户，绕过条件访问等安全策略，且不会留下日志记录。 研究人员当天向微软安全响应中心报告了该漏洞（CVE-2025-55241），微软在几天内修复了问题并实施了额外防护措施。微软内部遥测显示该漏洞未被滥用。该漏洞影响范围极广，可访问用户信息、组和角色、租户设置、应用程序权限、设备信息等所有Entra ID数据。若冒充全局管理员，还可修改所有设置，完全控制整个租户。 文章末尾提供了用于检测潜在滥用行为的KQL查询语句。

评论摘要
主要讨论点：[CVE漏洞评级的合理性及微软Entra ID的安全性问题] 不同观点： • **CVE评级不合理** - [Freak_NL]认为CVE将攻击复杂度标记为“高”不准确，因为攻击者仅需基础管理员权限和目标用户的netId（可通过暴力枚举获取），其他均为公开信息，不符合“需不可控条件”的定义。 - 争议焦点：CVE评级是否刻意淡化漏洞严重性。 • **微软Entra ID的设计缺陷** - [userbinator]指出系统未正确验证令牌来源租户，质疑设计初衷；[darkamaul]认为长期支持策略导致遗留API与新功能交互漏洞频发（类似Windows注册表问题）。 - [Sytten]批评Entra ID用户体验混乱，涉及租户创建、订阅层级和文档过时等问题。 - [pcj-github]甚至怀疑是“故意后门”。 • **替代方案与历史对比** - [gfody]质疑Entra ID的必要性，认为Kerberos经过36年已稳定可靠。 - [buster]引用类似漏洞案例（荷兰黑客攻破Microsoft 365租户）佐证系统性风险。 补充讨论： - **漏洞影响与响应** - [malnourish]和[jwpapi]关注漏洞赏金金额，暗示该漏洞危害极大。 - [rootsudo]提到曾接近发现此漏洞，说明攻击路径可能较明显。 - **用户情绪** - [TavsiE9s]和[cr125rider]的讽刺评论反映对微软安全性的普遍不信任。

Boring is good

作者: zdw | 评分: 170 | 评论数: 13 | 发布时间: 2025-09-15 20:51
文章摘要

文章指出，大型语言模型（LLM）的狂热正在消退。95%的企业尚未从中获益，人们常误将语言流畅性等同于真实智能。作者提出两个关键观点：1.技术发展遵循"从大到小、从集中到分散"的规律，开源社区推动的小型语言模型（SLM）更适合完成具体任务，成本更低且不易产生幻觉；2.新技术应用初期常走弯路，如同80年代数据库和互联网泡沫的教训。未来LLM将转向更小型化、专业化且"无聊"的实际应用，这才是其真正价值所在。

评论摘要
主要讨论点：[LLM的应用场景和可靠性，"无聊技术"的价值，以及技术选择的合理性] 不同观点： • LLM在模糊和准确性要求不高的场景下更有价值（如开发者的试验性解决方案），而在需要高准确性的场景（如审计日志）则不适用。部分企业未能正确区分这些场景，但预计未来会有所改善。 • LLM解决复杂问题时即使成功率较低（如50%）仍有价值，但在处理小型任务时，即使是1%的错误率也会导致系统不可靠。小型任务更适合手工编写的代码，以确保更高的可靠性和可预测性。 • LLM并非真正的智能，也不会超越人类在认知或机器人任务中的表现。这一观点引发了关于LLM能力和未来发展潜力的争议。 • LLM已经能在某些方面（如代码编写）超越大多数人类，但问题在于我们期望LLM一次性完成人类可能需要长时间完成的任务。缺乏长期LLM工作的协调机制是主要障碍。 • "无聊技术"（如HTTPS、S3）的价值在于它们可靠、经过充分测试且能高效完成任务。然而，"无聊"一词可能引起误解，因为某些技术（如C++）虽然历史悠久但仍充满意外。 补充讨论： • 技术选择不应仅仅为了提升估值或迎合趋势（如云和AI），而应根据实际需求选择合适工具。盲目追求新技术可能导致成本增加、功能延迟和系统复杂性提高。 • 对于"无聊技术"的讨论中，作者提到"无聊"一词可能不够准确，因为某些技术虽然表面无聊，但实际上非常高效和可靠。 • 关于LLM的争论主要集中在它们的能力和未来发展潜力上，尤其是它们是否能真正实现智能或超越人类。
