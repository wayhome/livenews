LinkedIn Feed Blocker 是一个轻量级 Chrome 扩展程序,用于屏蔽 LinkedIn 首页动态流,同时保留其他功能正常使用。 **功能特点:** - 隐藏 /feed 页面的全部动态内容 - 阻止无限滚动加载更多帖子 - 保留个人资料、求职、搜索、消息等其他 LinkedIn 功能 **开发动机:** 作者认为 LinkedIn 的求职和招聘沟通功能很有价值,但不喜欢充满噪音的社交动态流。 **技术实现:** 通过 CSS 规则隐藏主动态流组件,通过拦截规则阻止动态流分页请求。 **安装方式:** 下载仓库后在 Chrome 扩展管理页面以开发者模式加载即可使用。

评论摘要
主要讨论点：如何应对 LinkedIn 信息流充斥无关内容（连接点赞陌生人帖子、AI生成内容等）的问题 不同观点： • **技术过滤派**：提供多种解决方案，包括 uBlock Origin 规则、浏览器扩展（News Feed Eradicator、Scrolless）、自定义样式表、用户脚本等，认为可以通过技术手段屏蔽信息流同时保留平台其他功能 • **风险警告派**：指出 LinkedIn 有强大的 DOM 检测机制，使用修改页面的扩展可能导致账号被 shadowban（搜索不可见、帖子受限、失去招聘者关注），认为风险大于收益 • **极简主义派**：通过取消关注所有连接（但保持连接关系）让信息流"崩溃"显示错误，或直接删除账号，认为 LinkedIn 已无价值 • **内容质量批评派**：认为平台已被 AI 生成内容（"AI slop"、"Claudeslop"）占据，算法失效，与 Twitter 类似都沦为无意义的参与度农场，符合"死亡互联网理论" 补充讨论：争议焦点在于是否值得为优化体验而冒账号受限风险，以及 LinkedIn 本身是否还有存在价值。多数人倾向技术解决方案或彻底放弃，反映出对平台内容质量的普遍失望。

A domain can now say it is for sale, in DNS

作者: shaunpud | 评分: 215 | 评论数: 29 | 发布时间: 2026-08-08 13:26
文章摘要

`_for-sale` 是 RFC 10023 定义的保留 DNS 节点名称,用于标识域名可供出售。它通过在 DNS 中发布 TXT 记录(如 `_for-sale.example.com`)来传递出售信号,而不影响网站正常运营。 记录格式为 `v=FORSALE1;` 加一个标签值对,可包含联系方式(furi)、价格(fval)或说明文本(ftxt)。多个信息需分别发布为独立记录。 该机制专为经纪人和自动化服务设计,与域名停放不同——网站继续运行,记录可随时添加删除。实施要点包括:强制版本标签、每记录一个标签值对、TTL不超过3600秒、使用DNSSEC签名、不再出售时立即移除。 这为域名交易提供了标准化的可发现渠道,避免了冷邮件和隐私保护带来的沟通障碍。

评论摘要
主要讨论点：围绕DNS域名销售标记新标准（RFC 10023）及域名投机问题的多角度讨论 不同观点： • **支持新标准派**：认为标准化的"域名待售"标记能提高透明度，方便买家找到愿意出售的域名（如temp0826分享成功获得心仪域名的经历） • **反对域名投机派**：Anoian直接表示应该禁止域名投机而非改善投机者体验；anigbrowl批评域名系统在30年间过度金融化，认为这对整体生态无益 • **提出替代方案派**：asdfman123建议采用Georgism税收模式——域名持有者自定价格但需按价格的2-5%缴纳年费，以激励投机者将域名卖给真正使用者 • **技术实现质疑派**：Tiberium和kmoser指出标准存在逻辑矛盾（既说不打算卖别加记录，又说记录不构成义务）；Bender担心允许在任意DNS层级添加标记会造成混淆 补充讨论：comrade1234的Sony案例引发关于商标仲裁的讨论——公开表示域名待售可能被视为不实际需要该域名的证据；1970-01-01和gguncth提出对标准被恶意利用的担忧（AI操纵交易、借机没收投机域名）

评论摘要
主要讨论点：Intel新芯片能否在性能和能效上与Apple芯片竞争 不同观点： • **怀疑派**：Intel只是勉强追平Apple已过时的芯片（如A18），而非最新的M系列，不值得兴奋；单一HPL FP64指标的胜利不能代表整体性能，A18在几乎所有其他测试中都以一半功耗击败Intel • **Apple优势派**：Apple Neo图形性能仍快2倍、单核快1.4倍，且使用的还是比M系列慢的iPhone CPU；软件生态方面，Linux在非Apple硬件上的浏览器性能表现糟糕，工作效率差距明显 • **技术中立派**：标准化对比显示，在相同制程和频率下，AMD和Apple能效相当，AMD Zen 5c在性能/面积上还有12%优势；Intel在制程工艺上确实击败了TSMC • **实用主义派**：关注实际功能如耳机接口缺失；期待1.5倍电池续航提升；希望Intel能在保持可维修性的同时达到Mac性能 补充讨论：核心分歧在于如何评价Intel的进步——是"终于追上"还是"仍然落后"，以及单项测试胜利是否有实际意义。

这篇文章讨论了Python字符串字面量的有趣特性。主要内容包括： 1. **原始字符串的悖论**：尽管r''前缀使反斜杠不被转义，但原始字符串仍不能以单个反斜杠结尾（如`r'asdf\'`是语法错误），因为词法分析器仍会将后续引号视为字符串的一部分。 2. **f-string的复杂性**：f-string中的花括号表达式需要完整的Python解析器处理，可以包含引号、多行代码甚至注释。表达式由未括号化的`}`、`!`或`:`终止，这导致lambda和赋值表达式必须加括号才能在f-string中使用。 文章揭示了Python为简化早期实现而做的设计选择，与后来引入的复杂f-string特性形成有趣对比。

评论摘要
主要讨论点：Python 的字符串特性（特别是 f-strings）的实用性与复杂性之争 不同观点： • **支持 f-strings**：phyzome 认为除了边缘情况外，f-strings 很好用；vova_hn2 虽然讨论其他语言，但表达了对原始字符串设计的认可 • **反对新特性**：dwdz 认为过去10年 Python 新特性只增加复杂性无实际益处；TZubiri 使用 Python 近10年从不用这些"花哨"特性，坚持用简单的 + 操作符；smitty1e 构建 JSON 时更喜欢旧的 %s 语法 • **技术细节讨论**：xg15 深入探讨 f-strings 中嵌套引号的词法分析规则，质疑某些语法行为是否有变化 • **可访问性问题**：ethin 从无障碍角度批评博文缺少大写影响屏幕阅读器体验 补充讨论：PyWoody 的元评论反映出 HN 技术讨论与实际使用体验的脱节；cocodill 和 madprops 的简短评论则代表了困惑和赞赏两种边缘反应。核心争议在于语言特性的复杂性是否值得——实用主义者倾向简单方案，而另一派认为新特性带来便利。
