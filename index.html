Prolog Coding Horror

作者: RohanAdwankar | 评分: 58 | 评论数: 5 | 发布时间: 2026-05-17 21:15
文章摘要

文章指出 Prolog 编程应避免几类“恐怖”做法：使用剪切、条件、var 等非纯构造会丢失解；用 assert/retract 修改全局状态会产生隐式依赖；直接打印结果会破坏关系式编程和测试性；依赖 is、>/2 等低级算术会增加理解和教学难度。作者主张保持纯 Prolog：用清晰数据结构、约束（如 dif/2、CLP(FD)）、元谓词和参数传递状态，让顶层输出结果，从而写出正确、可推理、可测试的程序。

评论摘要
主要讨论点：围绕如何理解 Prolog、其“可接受错误答案/需验证答案”的思维方式，以及现实用途展开。 不同观点： • 理解 Prolog 的关键在于“四端口模型”：原帖认为若想真正理解 Prolog，需要掌握其执行/回溯的四端口模型，并给出文章作为学习材料。 • 对 Prolog“可能产生错误答案但可检查”的看法：rtpg 认为文章中提到的“horror”很有启发性；虽然通常不能接受程序返回真假混杂的结果，但在相信 P≠NP、面对难解问题时，这种“生成候选解再验证”的思路可能合理。 • 质疑 Prolog 的现实用途：appil 表示在大学课程中接触过 Prolog，但觉得它相比其他内容很冷门、偏学术，像是为计算机科学家自娱自乐而发明的语言，并询问实际应用场景。 • 反对夸大其特殊性：crustycoder 简短回应“Mostly overblown”，暗示对 Prolog 神秘性、恐怖感或争议性的描述被夸大了。 补充讨论：争议焦点在于 Prolog 的非传统编程模型是否实用，以及“先产生答案再验证”的逻辑编程方式是有价值的搜索策略，还是令人不安/不可靠的程序行为。

Show HN: Semble – Code search for agents that uses 98% fewer tokens than grep

文章摘要

Semble 是面向 AI 代理的快速代码搜索库，可用自然语言查询并返回精准代码片段，较 grep+read 节省约 98% token。它纯 CPU 运行、无需外部服务，支持 MCP、Bash、CLI/Python，本地或 Git 仓库，具备毫秒级索引与查询性能。

评论摘要
主要讨论点：围绕“语义/结构化代码搜索工具替代 grep”在真实编码 Agent 场景中的有效性、成本、可信度与对比基准展开。 不同观点： • 需要真实 Agent 基准：有人希望看到在 Claude Code、Copilot CLI 等环境中移除 grep、改用该工具后的结果；核心不是单次检索省 token，而是 Agent 是否能更快、更低成本完成同等质量任务。 • 对现有基准存疑：有用户测试 RTK/headroom 后发现，虽然上下文有时减少，但完成任务轮次增加，总成本更高；认为很多工具只证明“比 grep 少 token”，却没有证明“让 Agent 工作更好”。 • Agent 信任问题：多位评论提到模型长期被训练习惯使用 grep，可能不信任新工具结果，反复重试或重读，抵消 token 节省；让 Agent 主动偏好使用该工具是实际难点。 • 与现有工具比较：多人询问与 LSP、colgrep、context-mode、serina、codebase-memory-mcp、maki.sh 索引、fff 等工具的差异或是否可结合使用。 • 检索可靠性争议：有人认为相比 grep，语义搜索是概率性的，担心小模型漏掉重要结果；争议焦点在于“召回率/确定性”是否足以替代 grep。 • 结构化代码理解的支持观点：有人认为源码有结构，使用解析器、索引或 LSP 类方法比纯 grep 更节省 token，也可能更适合人类和 Agent。 • 应用范围扩展：有人询问是否适用于非代码文档，如 API 文档、AI memory 文件等。 补充讨论：也有人认为语义代码搜索不仅适合 Agent，对人类开发者也有价值。

Mercurial, 20 years and counting: how are we still alive and kicking? [video]

作者: ibobev | 评分: 162 | 评论数: 28 | 发布时间: 2026-05-15 11:39
文章摘要

这是一场 FOSDEM 2026 主会场演讲，题为“Mercurial，20年仍在前行”。演讲回顾分布式版本控制系统 Mercurial 自2005年以来的发展，探讨其虽在流行度上输给 Git、却仍保持活跃和竞争力的原因。内容涵盖项目历史、技术与社区演变、大公司参与影响、Mercurial 对现代工具的贡献，以及版本控制和社区开源的未来。

评论摘要
主要讨论点：围绕 Mercurial（hg）与 Git 的技术体验、生态胜负及替代工具展开，核心是“技术上更好用”与“生态上输给 Git/GitHub”的落差。 不同观点： • Mercurial 技术体验更好：多人认为 hg 更安全、更清晰、命令面更小、对普通团队足够，TortoiseHg、Windows Explorer 集成等让使用更顺手；相比 Git，遇到复杂问题时更怀念 hg。 • Git 胜在生态而非纯技术：原帖和 reddit 旧员工都认为当年选择 hg 技术上合理，但 Git 因成为主流、GitHub/开源贡献流程普及而胜出。reddit 开源时即使偏好 hg，也为获得贡献和“显得严肃”改用 Git。 • 托管平台影响关键：Bitbucket 停止支持 Mercurial 被多位评论者视为促使放弃 hg 的转折点；缺少 GitHub 式平台、Heptapod 使用不顺，也削弱了 hg 的生存空间。 • Mercurial 仍有现实用途：有人继续自托管或在家用 Raspberry Pi 部署 hg，认为如今家庭光纤让自托管更可行。 • 新工具可能取代 hg：有人认为 Jujutsu（jj）出现后，Mercurial 复兴希望更小；也有人期待 jj 获得更多认可。 • 争议焦点：Git 的“更强大”是否真是大多数团队所需；Mercurial 是否因生态失败而非技术失败被淘汰。 补充讨论：有人怀念 Mercurial 作者 Matt Mackall 的工程文化；也顺带表达了对 Perforce 的反感、对 Hginit 回归的关注。
