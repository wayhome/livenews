Span.SequenceEquals is faster than memcmp

作者: xnorswap | 评分: 50 | 评论数: 10 | 发布时间: 2025-03-30 14:53
文章摘要

本文讨论了在.NET中提升性能的方法，特别是从.NET Framework 4.8.1迁移到.NET 8时如何优化字节数组比较。作者发现使用`msvcrt.dll`中的`memcmp`是常见的加速方法，但现代.NET中的`Span`类型提供了更好的性能。 作者比较了多种方法，包括`memcmp`、`for`循环、`Enumerable.SequenceEqual`以及`Span.SequenceEqual`，在不同数组大小（10字节、1KB、1MB、1GB）下进行基准测试。结果显示，`Span.SequenceEqual`在多数情况下性能最佳，明显优于`memcmp`和传统循环方法。特别是在大数组比较中，`Span`方法表现出显著的性能优势。 总结来说，使用`Span`进行字节数组比较是比`memcmp`更快、更现代的解决方案，特别是在.NET 8及以上版本中。

评论摘要
主要讨论点：C# 中数组比较的性能和实现细节，特别是与 `memcmp` 的对比，以及对 `Span` 等新抽象的使用和理解。 不同观点： • [Dwedit] 认为 `memcmp` 的调用存在开销，因为它是一个无法内联的导入函数，并且在数组传递给原生代码时，marshaler 会自动创建固定的 GC 句柄。他建议尝试直接传递指针给 `memcmp`，而不是经过 marshal 的数组，以减少开销。 • [bob1029] 赞赏 `Span` 的新抽象，表示在构建图灵机解释器时大量使用，并倾向于在大多数场景下使用它而不是数组。 • [merb] 纠正关于 `Span` 的描述，指出它并不一定是堆栈分配，而是可以指向不同类型的内存，只有使用 `stackalloc` 时内存才在堆栈上分配。 • [xnorswap] 讨论了不再需要通过 P/Invoke 调用 `memcmp` 来进行数组比较，并指出过时的 StackOverflow 回答可能会误导开发者，强调了保持最新知识的重要性。 • [junto] 惊叹于现代 .NET 的高性能，并对 .NET 在 Linux 容器中的性能表现感到好奇。 • [loeg] 认为调用 C 中的 `memcmp` 带来的开销是不可避免的，但指出两个实现本质上应该在做相同的事情。 • [neonsunset] 提到 LINQ 的 `SequenceEqual` 和其他 CoreLib 方法在可能的情况下都会转发到相同的底层比较例程，并指出这些都基于强大的可移植 SIMD 原语和平台内在函数。 • [npalli] 比较了 .NET 的 `Span` 和 C++ 中的 `std::span`，认为 .NET 自 6 版本以来已经变得相当快。 • [DeathArrow] 简短地表示 .NET 已经变得非常快。 补充讨论： • 讨论中多次提到 .NET 性能的显著提升，特别是在与 C++ 等其他语言的对比中。 • 提到了过时的编程信息可能带来的问题，强调了保持知识更新和验证的重要性。 • 涉及了 `Span` 的特性和适用场景，包括其在不同内存分配方式中的表现。 • 最后，提到了跨平台性能表现的潜在问题，例如在 Linux 容器中的表现。 争议焦点： • 主要集中在 `memcmp` 的调用开销以及是否应该直接使用指针来避免 marshal 开销。

Rust Any part 3: we have upcasts

作者: jmillikin | 评分: 135 | 评论数: 7 | 发布时间: 2025-03-30 11:15
文章摘要

Armin Ronacher在2025年3月27日的博客文章中讨论了Rust 1.86版本如何解决了"upcasting"问题。三年前，他分享了一个名为"As-Any Hack"的技巧，以在稳定版的Rust中实现向上转型（upcasting）到超traits。具体问题是在使用如`DebugAny`这种继承自`Any`的trait时，无法在`dyn DebugAny`上调用`Any`的方法，如`downcast_ref`，导致编译错误。随着Rust 1.86的发布，这个问题得到了修复，现在可以正常进行转型和方法调用。这一更新意味着许多旧的技巧可以被淘汰，但需要根据最低支持的Rust版本来调整。Ronacher对参与修复这一问题的开发者表示感谢。

评论摘要
主要讨论点：Rust语言中的trait继承与多trait实现的机制及其与传统面向对象编程（OO）语言的区别。 不同观点： • **kibwen的观点**：Rust中的trait不是传统面向对象语言中的“继承”关系，而是“依赖”关系。一个trait可以“要求”另一个trait，但这不意味着方法的继承，而是实现上的前提条件。因此，不能用传统OO语言中的继承概念来理解Rust的trait关系。 • **trashface的观点**：提出在Rust中如果一个类型可能实现多个trait（如A, B, C），是否必须全部实现这些trait的问题。他希望有一个基础trait对象，可以查询是否支持其他trait，而不必为不支持的trait实现stub。这类似于C++中的dynamic_cast功能，但由于Rust没有继承，目前可能无法实现。 • **mmastrac的观点**：提到Rust的vtable布局变化，现在可以保证supertrait的布局在方法前缀中是可预测的，或者提供指向合适vtable的指针。他认为这可能与菱形trait继承有关。 • **the__alchemist的观点**：表达了对文章内容的不解，尽管使用Rust多年，仍不清楚文章描述的内容。 • **fcantournet的观点**：简单提问，带有调侃性质，询问某个类型是否是Debug或DebugAny。 • **aerzen的观点**：喜欢Rust的原因是Any类型使用起来不方便，这促使开发者使用静态类型实现，从而推动更合理的代码设计。 • **jtrueb的观点**：认为Rust正在逐渐接近面向对象编程（OOP），暗示Rust可能在某些方面变得更像传统OO语言。 补充讨论： • 争议焦点在于Rust的trait机制与传统OO语言继承机制的区别，以及在多trait实现和查询支持的其他trait时的实现难度。 • 不同用户对Rust的复杂性、类型系统及其与传统OO语言的差异有不同的理解和期待，部分用户对文章内容和技术细节感到困惑。 • 部分用户关注Rust的演变，尤其是其与OOP的接近程度，反映了Rust在语言设计上可能正在经历的变化。

评论摘要

Functors, Applicatives, and Monads

作者: abhi9u | 评分: 28 | 评论数: 6 | 发布时间: 2025-03-28 11:46
文章摘要

本文简要介绍了函数式编程中的函子（Functors）、 applicative（Applicatives）和单子（Monads）概念，主要使用Haskell作为示例，但不要求读者必须懂Haskell。 ### 函子（Functors） 函子是一种抽象概念，允许在不改变上下文的情况下对容器内的值应用函数。例如，Haskell中的`Maybe`类型代表一个可能包含值的盒子（box），可以使用`fmap`对盒子内的值应用函数，而无需手动打开盒子。如果对空盒子应用函数，结果仍然是空盒子。函子不仅限于`Maybe`，还可应用于列表、`Either`等数据结构。 ### Applicative 函子虽然能对容器内的值应用函数，但有一定局限性。Applicative则更进一步，允许对容器内的函数应用容器内的值，从而实现更复杂的操作。例如，在Haskell中可以使用`<*>`操作符对多个`Maybe`值应用函数。 本文还提到后续将讨论更复杂的单子（Monads），它们能处理更加复杂的链式操作。

评论摘要
主要讨论点：关于Monads与其他抽象（如Applicatives）的比较及应用，以及对Monads的误解和教学方式的讨论 不同观点： • lihaoyi认为Monads被过度关注，Applicatives在某些场景下更有优势，例如静态分析、优化和并行化。他以Haxl和Mill build tool为例，说明Applicatives在这些领域的应用和优势。 • rthnbgrredf提到近年来支持函数式编程的类型语言（如TypeScript和Rust）的兴起，并猜测这种趋势是否会在AI助理编程中继续。 • jerf批评了对Monads的常见误解，如Monads作用于"容器"以及Monad有"一个"值的误解。他认为这些误解在初学者中很普遍，并强调需要更准确的解释。 • randomstate分享了自己作为非Haskell背景的开发者理解`Just`作为`Maybe`类型的构造函数的过程，并提供了一个Stack Overflow链接以帮助理解。 • personperson69认为虽然Haskell社区的人回应时有些无礼，但他们的观点大体正确。他指出，通过“盒子”类比来解释Monads对学习者帮助有限，建议通过使用不同的Monads来学习。 • behnamoh调侃Monads像是功能编程中的神秘存在，认为虽然没人真正了解Monads，但大家都喜欢写文章用类比解释，而这些类比在实践中往往不成立。 补充讨论： • Monads和其他抽象（如Applicatives）的实际应用场景和各自的优势是讨论的核心。 • 对Monads的误解，特别是其在函数和多值情况下的应用，是另一个值得注意的讨论点。 • 社区对如何有效教学Monads存在争议，特别是对使用类比和教程的效果存在不同看法。 • 不同背景的开发者对Monads理解的难易程度和学习曲线的讨论。
