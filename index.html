How We Rooted Copilot

作者: uponasmile | 评分: 100 | 评论数: 9 | 发布时间: 2025-07-26 16:06
文章摘要

本文描述了微软Copilot Enterprise的一次更新，该更新引入了一个运行Jupyter Notebook的Python沙盒，可执行后端代码。作者发现可以通过Jupyter Notebook的`%command`语法让系统执行指定代码。该沙盒在一个以`ubuntu`用户运行的miniconda环境中执行Linux命令，而该用户属于`sudo`组，但没有`sudo`命令。 作者进一步分析了沙盒的文件系统和网络接口，发现其使用OverlayFS文件系统和一个Tika服务器。通过执行一系列命令后，可以下载文件或打包文件夹。然而，二进制数据会被损坏，需用base64编码下载。 关键漏洞在于`entrypoint.sh`脚本中，`pgrep`命令未使用完整路径，且`$PATH`变量可被篡改。利用这一漏洞，作者能在`/app/miniconda/bin`目录下创建恶意脚本，从而在系统上执行任意代码。

Rust running on every GPU

作者: littlestymaar | 评分: 367 | 评论数: 17 | 发布时间: 2025-07-26 10:08
文章摘要

本文介绍了一个使用Rust编写的跨平台GPU计算演示，能够在多个主要GPU平台上运行，包括CUDA（NVIDIA GPU）、SPIR-V（Vulkan兼容GPU）、Metal（Apple设备）、DirectX 12（Windows）和WebGPU（浏览器），并为非GPU系统提供CPU后备。该项目通过结合Rust GPU、Rust CUDA和Naga等项目，实现了用标准Rust代码直接编译到多个GPU目标，避免了传统的专用着色器语言。 演示实现了一个简单的bitonic排序算法，计算逻辑在CPU和GPU上运行相同的代码。通过Rust特性标志和编译目标选择不同的后端和驱动API，如wgpu、Vulkan、CUDA等。尽管演示使用了单一计算内核，但底层工具支持多个内核和入口点。该项目展示了Rust在跨平台GPU计算方面的潜力，尽管仍有诸多待改进之处，但已是一个重要的里程碑。

评论摘要
主要讨论点：Rust和GPU编程中的抽象层次及其优缺点 不同观点： • Voultapher指出，在Rust中使用多层抽象（如通过不同的GPU库和API）隐藏了大量复杂性，可能影响性能优化。每一层抽象都可能导致性能损失，特别是在需要访问硬件特定细节时。 • vouwfietsman认为，抽象层对于需要在不同客户硬件上运行的应用并不理想，因为每个目标硬件都有显著差异。直接处理GPU的底层细节是必要的，以避免错误和性能损失。不过，条件编译是一个有用的特性。 • Archit3ch关注性能问题，特别是对于音频应用和计算API的需求。他对通过多层转换（如Rust到WebGPU到SPIR-V等）的性能表示怀疑，并与直接使用原生API（如Julia到Metal）进行对比。 • slashdev对打破厂商锁定和实现跨平台的潜力感到兴奋，认为即使需要针对特定硬件编写优化代码，基本的可移植内核仍然非常有价值。 补充讨论： • chrisldgk提出疑问，WebGPU是否已经通过单个API解决了跨GPU后端兼容性的问题，并质疑在已有抽象之上再加一层抽象的必要性。 • piker对使用no_std和no alloc的crate在GPU上运行的潜力表示惊讶，认为这 unlock了很多有趣的想法。 • hardwaresofton讨论了Rust GPU项目的低层次抽象和现有项目之间的差异，并提到naga项目的新进展。 • ivanjermakov质疑在GPU上使用Rust是否真正可行，认为GPU编程需要特别关注，过多的抽象可能导致某些优化无法实现。 • reactordev对未来能够编写与用户程序语义相同的GPU程序表示期待，认为这对推理（inference）有重大影响。 • omnicognate提到Zig也可以编译成SPIR-V，并指出其他语言的可能性。 • bobajeff对简化异构计算开发体验的努力表示赞赏，认为这是减少碎片化和提升开发者体验的重要工作。 • rbanffy认为，编写能够在任何平台上运行的通用代码是目标，这与多后端编译的讨论相关。 • gedw99对这项工作表示欣喜，认为这解决了开发者在平台战争中的困扰，并提到具体项目（如webgpu）的实用性。 • max-privatevoid认为Rust社区需要先学会如何正确加载GPU库。 • jdbohrman对max-privatevoid的观点表示不解，提出“为什么要先学会加载GPU库”的疑问。 争议焦点： • 多层抽象对性能的影响：部分开发者担心多层抽象可能导致性能损失，而另一些开发者认为这是实现跨平台和简化开发的必要代价。 • Rust在GPU编程中的实际可行性：有开发者质疑Rust在GPU编程中的实际应用效果，认为GPU编程需要特别处理，而过多抽象可能不利于性能优化。

Purple Earth Hypothesis

作者: colinprince | 评分: 26 | 评论数: 0 | 发布时间: 2025-07-24 00:43
文章摘要

**紫色地球假说**（Purple Earth Hypothesis）是由分子生物学家Shiladitya DasSarma于2007年提出的天体生物学假说。该假说认为，早期地球上的首批光合生物使用的是简单的视黄醛分子，而非复杂的卟啉基叶绿素，这使得地球表面生物圈呈现紫色而非现在的绿色。这一现象估计发生在35亿至24亿年前的太古宙，早于大氧化事件和休伦冰河时期。视黄醛吸收绿黄光，反射红蓝光，导致生物体呈现洋红色。相比叶绿素，视黄醛的结构更简单，与细胞膜中的类异戊二烯脂质相关。现代例子如卤古菌（Haloarchaea）利用视黄醛进行无氧光合作用。随着基于卟啉的生物体进化并释放氧气，大氧化事件改变了地球的大气成分，最终使紫色生物被绿色光合生物取代。

Font-size-adjust Is Useful

作者: Bogdanp | 评分: 100 | 评论数: 10 | 发布时间: 2025-07-23 11:34
文章摘要

本文介绍了CSS中的`font-size-adjust`属性，并声称包括Google、MDN和CSS规范在内的所有人都误解了其用途。通常认为，`font-size`定义的是字体周围框的高度，而不是字符本身的大小，因此不同字体的实际显示尺寸可能差异很大。`font-size-adjust`可以调整字体，使得字符（如"x"）在不同字体中保持相对一致的显示比例。 主流观点认为，该属性主要用于处理字体回退时的尺寸不一致问题。但作者认为，更有价值的用法是将其应用于网页中使用多种字体的情况，以确保字体尺寸的一致性。作者建议在CSS重置中加入`font-size-adjust: ex-height 0.53`，以统一字体显示比例。

评论摘要
主要讨论点：网页字体渲染、FOUC（未样式化内容闪烁）、页面加载性能与用户体验之间的权衡 不同观点： • [mananaysiempre] 认为，为了避免短暂的FOC（未样式化内容闪烁）而加载大约1MB的字体资源是不值得的，特别是在慢速或高延迟的网络连接下，这种做法会导致用户长时间面对空白页面。他怀念以前更简单的网页设计时代，当时对div和内联样式的使用是被广泛反对的。 • [lelandfe] 支持mananaysiempre的观点，认为不应该通过内联整个字体来避免短暂的闪烁，因为这会导致每个页面的加载性能变差。他引用了外部资源，强调高性能网页设计的原则。 • [Waterluvian] 表达了对使用字体和表情符号作为游戏图标的兴趣，认为这解决了不一致性的问题。 • [alberth] 对“font-size-adjust”和“text-box-trim”的区别感到困惑，提出了技术细节上的疑问。 • [adregan] 认为“font-size-adjust”和“text-box-trim”在使用场景上是一致的，都是关于字体变化对页面纹理的影响。 • [bee_rider] 推测字体设计师有意根据字体框的大小而不是字母x的高度来定义字体尺寸，认为这背后有其理由。 • [mcculley] 询问是否有自动调整字体大小的方法，类似于iOS中的“adjustsFontSizeToFitWidth”功能。 • [hiccuphippo] 想知道如何让文本在一行内填满盒子，根据文本长度自动调整字体大小，并指出目前需要通过JavaScript实现。 • [bawolff] 认为大多数人觉得“font-adjust”不实用的原因是，如果特意选择了字体，通常会选择具有兼容性指标的字体。 • [kbelder] 提出一个激进的观点，认为浏览器不应该允许指定确切的字体，认为如果接受服务器只能建议内容的显示方式而不是控制它，网络会更好。 补充讨论： • 讨论中涉及多个技术细节，如“font-size-adjust”和“text-box-trim”的区别与应用、自动调整字体大小的方法等。 • 争议的焦点在于是否值得为了避免FOC而牺牲页面加载性能，特别是在网络条件不佳的情况下。 • 另一个值得注意的点是对网页设计历史的回顾以及对现代网页设计复杂性的反思。

Breaking the WASM/JS communication performance barrier

文章摘要

Sledgehammer Bindgen 是一个用于加速 Rust 与 JavaScript 之间 WASM 通信的工具，特别为需要快速访问 DOM 的 web 框架设计。与通用的 wasm-bindgen 相比，Sledgehammer 通过批量处理字符串解码、缓存字符串以及将操作编码为字节序列等方法来提升性能。它通过减少每次调用 TextDecoder 的开销，并利用 u32 数组批量读取操作数据，以提高效率。用户可以将 Sledgehammer 与 wasm-bindgen 结合使用，以优化性能。项目提供了文档和示例以供参考。

评论摘要
主要讨论点：WASM与JavaScript之间字符串解码的性能优化及相关技术挑战 不同观点： • [vanderZwan] 提出 Wasm-bindgen 和 Sledgehammer 在字符串解码上的不同处理方式。Wasm-bindgen 对每个字符串调用 TextDecoder.decode，而 Sledgehammer 对每一批数据只调用一次 TextEncoder.decode。质疑这种批量处理和在JS端分割字符串的操作是否会影响JS的垃圾回收（GC）。 • [samwillis] 赞同 Rust 社区在提升WASM到JS字符串解码性能方面的努力，指出这是使用WASM时常见的性能瓶颈。解释了当前通过 TextDecoder API 处理UTF16缓冲区的效率问题，认为理想的方案是创建一种“String View”来避免复制操作，但同时指出这种方案在JS中的复杂性，因为JS中的字符串需要不可变，而底层缓冲区可能会被修改。 • [andyferris] 认为UTF-8和UTF-16的转换使得问题变得复杂，期望JavaScript和DOM原生支持处理UTF-8的方式，认为这是推进将原生语言编译到WASM和Web应用的重要一步，不认为 TextEncoder/TextDecoder 是理想的解决方案。 • [nhatcher] 提到自己曾写过相关问题的文章，虽然代码有些过时，但原则上支持通过浏览器实现来解决链接问题，提供了一个链接供参考。 • [CyanLite2] 对浏览器没有原生支持这类优化表示遗憾。 • [bcardarella] 关心性能问题，询问与 Wasmtime 等项目的性能对比。 补充讨论： • 讨论中涉及的关键技术点包括 TextDecoder/TextEncoder 的使用效率、UTF-8 和 UTF-16 编码之间的转换、以及避免数据复制以提升性能的可能性。 • 争议的焦点之一在于是否可以通过某种“String View”方式避免数据复制，以及JavaScript对字符串不可变性的要求带来的复杂性。 • 另一个焦点是对于UTF-8在JavaScript和DOM中的原生支持的缺乏，认为这是性能提升的一大障碍。 • 不同工具和实现方式（如 Wasm-bindgen、Sledgehammer、Wasmtime）之间的性能比较也是讨论中的一个重要方面。
