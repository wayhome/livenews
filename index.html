评论摘要
主要讨论点：如何定义和理解“回收”以及将废物转化为燃料颗粒是否属于回收行为 不同观点： • **观点一（biofox）**：将废物转化为燃料颗粒应被视为回收。biofox认为，将废物转化为燃料颗粒为废物提供了“第二次生命”，而不是让它们直接进入垃圾填埋场。这种观点强调了废物再利用的重要性，认为只要废物被重新利用而不是丢弃，就属于回收的一部分。 • **观点二（隐含反对观点）**：该观点未直接呈现，但可以推测出存在一种相反意见，即认为将废物转化为燃料颗粒不能算作真正的回收。这种观点可能认为回收应仅限于将材料重新加工成新的可用产品，而不是简单地将废物转化为能源。这种观点可能更强调物质的再利用，而不是能量的回收。 补充讨论： • 争议的焦点在于对“回收”定义的理解。一方认为任何形式的再利用，包括转化为燃料，都是回收；另一方可能认为只有将材料重新加工成新的产品才算回收。 • biofox的论据集中在废物再利用和避免垃圾填埋场的环境影响上，强调了废物转化为能源的积极意义。 • 反对观点可能基于对传统回收（如塑料、纸张等材料的再加工）和能量回收（如燃烧废物发电）的区分，认为这两者有本质不同。

Ten years of JSON Web Token and preparing for the future

作者: mooreds | 评分: 180 | 评论数: 17 | 发布时间: 2025-05-25 23:05
文章摘要

本文回顾了JSON Web Token (JWT) 自2015年成为RFC 7519以来的十年发展，并介绍了与其相关的系列RFC标准（如JWS、JWE、JWK等）。JWT及其配套标准在OpenID Connect和OAuth等技术中广泛应用，已成为在线安全的重要组成部分。作者Mike Jones及其团队正在更新JWT的最佳实践文档，以应对过去五年中出现的新威胁和漏洞，并修订与OAuth 2.0相关的JWT规范以解决令牌中的模糊性问题。展望未来，团队将继续致力于确保JWT在未来十年的安全性与实用性。

评论摘要
主要讨论点：JWT（JSON Web Token）的实际应用价值和优缺点 不同观点： • **支持观点**： - **[genghisjahn]**：认为JWT在服务器间通信中非常有用，但在客户端和服务器间通信时，JWT实际上是在重新实现cookies/sessions的功能。 - **[90s_dev]**：认为JWT的广泛使用证明了它的实用性和多功能性，尽管它的应用场景可能超出了发明者的初衷。 • **反对观点**： - **[martinald]**：指出JWT中除了用户ID，其他信息很难长期有效。例如，如果账户被盗，需要立即撤销授权，而JWT的无状态特性使得这种实时控制变得困难。此外，角色变更也无法及时生效。 - **[hdjrudni]**：认为JWT在实际应用中往往是次优选择，尤其是在实现2FA（双因素认证）时，使用JWT存在安全风险，比如无限尝试攻击。他认为使用一次性挑战密钥的方式更为安全且易于追踪。 - **[TheChaplain]**：认为在有SameSite和CSP头可用的情况下，JWT的优势不再明显。后端框架通常已经内置了session跟踪功能，而JWT需要重新实现这一整套机制。 - **[pjmlp]**：对JWT和OAuth的设置感到痛苦，认为这增加了开发的复杂性。 - **[rvz]**：直接批评JWT，认为它是“有史以来最糟糕的标准之一”。 - **[pelagicAustral]**：认为JWT是JavaScript社区的“虚荣项目”，并质疑其在传统密钥交换无法满足需求时的必要性。 • **技术替代方案**： - **[francislavoie]**：推荐Paseto（https://paseto.io/）作为JWT的替代方案，但指出OAuth强制使用JWT。 - **[jrvarela56]**：引用了HN讨论中关于API tokens的调查，暗示可能有更好的选择。 • **安全性与隐私问题**： - **[methou]**：指出JWT被滥用的问题，比如在URL或头中传递JWT以进行第三方追踪，甚至违反隐私政策。此外，很多开发者混淆了编码和加密。 • **复杂授权需求**： - **[marifjeren]**：认为JWT在处理复杂授权规则时表现不佳，尤其是在权限信息快速增长和角色信息集中化问题上。 补充讨论： - **争议焦点**：JWT在现代应用中的实际价值和应用场景，尤其是在处理安全性和授权时的有效性。 - **技术选择**：讨论了Paseto等替代方案，以及在不同架构（如微服务架构）中的适用性。 - **实际问题**：包括无限尝试攻击、权限信息膨胀、角色变更延迟等问题，显示了JWT在实际应用中的一些局限性。

文章摘要

Jujutsu UI (jjui) 是一个为 Jujutsu 版本控制系统设计的终端用户界面（TUI）。它支持通过自动补全更改 revset、 rebase 操作、修订版本的压缩（squash）、查看修订详情、移动书签、操作日志查看等功能。用户可以通过快捷键进行多种操作，如分割、恢复、编辑文件或修订，查看 diff，以及进行 Git 推送/获取等。安装方式包括通过 Homebrew、Archlinux、Nix、go install 或从源码构建。最低支持的 Jujutsu 版本为 v0.21，项目采用 MIT 许可证，并欢迎贡献。

评论摘要
主要讨论点：用户对版本控制工具 **jj（Jujutsu）** 的评价和其与 **git** 的对比 不同观点： • **endtime** 对 jj 总体满意，认为它比 git 更符合其需求，尤其是在本地管理堆叠差异（stacked diffs）方面表现出色。然而，他提出了一些痛点： 1. **没有 GitHub PR 同步功能**：jj 缺乏像 Sapling 那样的 PR 同步功能，这使得在团队内部推广 jj 时遇到阻力。 2. **不支持推送/拉取更改**：无法在不同设备间通过推送/拉取来同步更改，手动复制 `.jj` 目录显得脆弱且容易出错。 3. **忘记创建新版本时处理麻烦**：如果在操作前忘记创建新版本，后续分割更改会比较麻烦。 4. **兼容性问题**：某些旧项目中的工具和脚本依赖 `.git` 目录，虽然可以通过 `--colocate` 解决，但依然是个麻烦。 • **silvanocerza** 对 jj 持积极态度，认为它在自己尝试的新项目中会很有用，特别是在理解溢出问题时可能带来帮助。 • **skeptrune** 对 jj 的出现表示欢迎，认为它是构建让用户满意的工具的一种体现。尽管自己对 git 感到满意，但乐见有人愿意尝试新工具并构建新的生态系统。 补充讨论： • **工具的生态兼容性**：endtime 提到了 jj 在某些项目中的兼容性问题，尤其是依赖 `.git` 目录的工具和脚本，这显示了 jj 与 git 之间仍存在的实际兼容性差距。 • **社区反馈与推广**：endtime 在推广 jj 时遇到了功能差距的质疑，这表明 jj 在功能完整性上还需要进一步完善，特别是在与 GitHub PR 同步等关键功能上。 • **不同用户需求**：skeptrune 代表了一类对现有工具（如 git）感到满意的用户，而 endtime 则代表了愿意尝试新工具并对其提出改进建议的用户。 争议焦点： • jj 的 **GitHub PR 同步功能** 缺失是 endtime 认为的主要痛点，也是其在团队内部推广 jj 时遇到的主要障碍。这显示了在现代开发工作流中，PR 同步功能对部分用户的重要性。

Lottie is an open format for animated vector graphics

作者: marcodiego | 评分: 245 | 评论数: 24 | 发布时间: 2025-05-25 14:45
文章摘要

Lottie是一种开放的矢量图形动画文件格式，由Hernan Torrisi于2015年创建，最初用于从Adobe After Effects导出和播放动画。Lottie动画通常包含复杂的动画、运动图形和交互元素，并可以导出为JSON文件，该文件包含 recreate 动画所需的所有信息。Lottie基于JSON格式，具有跨平台、可操作性强的特点，并有一个成熟的生态系统支持，包括播放器、创作工具和免费资源。Lottie动画社区（LAC）是一个由Linux基金会主持的非营利开源项目，致力于推动Lottie格式成为高效、可扩展、跨平台的动画技术标准。LAC通过开放协作的方式促进该格式的规范制定和广泛采用。
