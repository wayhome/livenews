文章摘要

RCE Vulnerability in React and Next.js

作者: rayhaanj | 评分: 248 | 评论数: 19 | 发布时间: 2025-12-03 16:00
文章摘要

这篇文章报告了一个Next.js和React框架中的关键安全漏洞（CVE-2025-66478），影响版本包括Next.js 15.x和16.x（使用App Router时）以及React 19.0.0至19.2.0。漏洞严重性评分为10.0（最高级别），允许远程攻击者无需权限即可获取系统高权限，可能导致数据泄露和系统崩溃。受影响用户应立即升级到已修复版本：Next.js应升级至15.0.5+或16.0.7+，React应升级至19.0.1+、19.1.2+或19.2.1+。漏洞由lachlan2k发现并报告。

评论摘要
主要讨论点：[React Server Components (RSC) 的安全漏洞及其设计问题] 不同观点： • **安全问题与设计缺陷** - 漏洞的根本原因是 RSC 直接将不受信任的客户端输入反序列化为模块+导出名称查找，并直接调用客户端请求的内容（未验证 `metadata.name` 是否为自身属性）。 - React 从未承认它在构建 RPC 层，而传统的 RPC 框架（如 gRPC 或 SOAP）都从模式定义和显式服务开始，而 React 的设计恰恰相反，导致安全风险。 - 修复补丁通过限制暴露的函数（白名单）来解决问题，但原型链中的危险函数可能仍然存在风险。 • **对 React 团队的批评** - RSC 功能被认为是“重新发明轮子”，不仅没有显著优于 SSR 或客户端渲染，反而增加了复杂性。 - 开发者体验在引入 Hooks 后下降，React 团队应专注于改进原生 JS 控制流支持，而不是继续开发 RSC。 - Next.js/RSC 被比作“新的 PHP”，可能成为攻击者的新目标（如扫描 `/_next` 路径）。 • **对 RSC 价值的质疑** - 许多开发者认为 RSC 的优势不明确，相比传统的 HTML 渲染 + HTMX 或其他轻量级方案，RSC 增加了不必要的复杂性。 - 有人将 RSC 比作“动态生成 API”（类似 Java 反射），认为这种做法存在安全隐患。 • **平台保护与缓解措施** - Vercel 和 Cloudflare 等平台已提供针对此漏洞的保护措施。 - 静态构建（static builds）被认为是避免此类问题的解决方案。 补充讨论： - **争议焦点**：React 团队是否忽视了设计中的安全隐患？RSC 是否真的解决了实际问题，还是增加了不必要的复杂性？ - **开发者态度**：部分开发者因 RSC 的复杂性而放弃使用 React，转而选择更简单的技术栈（如 HTMX）。 - **行业影响**：此次漏洞可能影响 React 和 Next.js 在 JavaScript 生态中的领导地位。
