Tree Borrows

作者: zdw | 评分: 213 | 评论数: 7 | 发布时间: 2025-07-09 14:40
文章摘要

本文介绍了Rust编程语言中用于处理不安全代码的新模型——Tree Borrows。Rust以其基于所有权的类型系统著称，提供内存安全和数据竞争自由等强保证，但“不安全”代码块需手动维护安全。为确保编译器优化正确性，需明确定义何为“不良”不安全代码。先前模型Stacked Borrows设定了相关规则，但排除了现实中常见的一些模式，且未考虑Rust借用检查器的最新高级功能。Tree Borrows通过将Stacked Borrows的栈结构替换为树结构，解决了这些问题，减少了被拒绝的测试案例数量，并证明能保留大部分优化，还支持新的优化如读-读重排。该研究获得了PLDI'25的杰出论文奖。

评论摘要
主要讨论点：Rust语言中的Stacked Borrows和Tree Borrows模型，及其在编译器中的实现和应用。 不同观点： • [kibwen] 分享了Ralf Jung的博客文章和演讲，提供了关于Rust操作语义精确定义的背景，特别是Tree Borrows模型及其可执行形式的工作。 • [pvg] 提到了Stacked Borrows在2018年和2020年已有讨论，提供了相关链接，表明这一话题并不是全新的。 • [Voultapher] 赞赏Tree Borrows模型的优雅解决方法，并通过个人项目经验[1][2]说明Tree Borrows允许一些在Stacked Borrows下不合法的代码。 • [vollbrecht] 对博客文章中提到的某些代码应被拒绝的说法进行了实验，发现当前稳定版编译器并未拒绝该代码，对理论与实际的差异提出质疑。 • [fuhsnn] 提出未来编程语言是否可能允许多种借用检查器实现，以便在编译速度、运行速度和算法灵活性等方面进行选择。 • [wavemode] 对论文中关于不安全代码的示例提出质疑，认为使用指针共存多个可变引用是未定义行为，不理解论文试图表达的观点。 补充讨论： • [pil0u] 提到作者Neven Villani是数学家Cédric Villani的儿子，暗示优秀的学术基因传承。 争议焦点： • 不同模型（Stacked Borrows与Tree Borrows）在处理Rust中的借用和可变引用时的有效性和实际应用差异。 • 理论上应被拒绝的代码在实际稳定版编译器中未被拒绝，显示出理论与实现之间的差距。 • 不安全代码示例的理解与实际行为之间的争议。 这些讨论反映了Rust社区对内存模型和借用检查器实现细节的关注，以及在理论与实践结合中的挑战。

Why LLMs Can't Write Q/Kdb+: Writing Code Right-to-Left

作者: gabiteodoru | 评分: 130 | 评论数: 23 | 发布时间: 2025-07-08 10:40
文章摘要

文章讨论了大型语言模型（LLMs）在编写q/kdb+代码时遇到的困难，主要问题在于评估顺序的不同。q/kdb+及其祖先语言如APL、J、k采用从右到左且无运算符优先级（RL-NOP）的评估方式，而LLMs在这种方式下表现不佳。例如，在处理表达式时，LLMs常混用Python和q的语法，导致错误。文章还指出，尽管右到左书写在代码中是必要的，但LLMs不擅长这种模式，因为它们的训练数据中q代码相对稀缺，且这种训练可能需要对模型架构进行重大修改。由于经济激励不足和训练数据的匮乏，行业不太可能为这些小众语言重新训练大型模型。文章最后提出了一种实用解决方案，即引入Qython作为桥梁，以帮助LLMs更好地处理RL-NOP语言的代码编写。

评论摘要
主要讨论点：LLM（大型语言模型）在处理非线性、不同语言评估顺序以及代码生成方面的能力和局限性。 不同观点： • clord认为当前的LLM在处理非线性思维（如从数据或返回值反向推导代码）时存在困难，并提出未来LLM是否能够处理非线性结构，或在非线性空间中工作再映射回线性输出。 • FeepingCreature指出，LLM在生成Python代码时，有时会插入不必要的导入语句，这是因为模型对可能需要的模块进行了对冲导入。 • am17an提到，LLM在生成代码时会插入随机的空白字符，似乎存在不同长度的空白标记。 • trjordan认为，训练数据集的大小也可能影响LLM的表现，并建议对不同语言的错误进行量化分析。 • briandw提到，扩散模型有可能解决非线性问题，例如扩散编码模型可以训练为从右到左生成代码。 • electroly对比了APL和NumPy的语法顺序，认为如果APL在今天开发，可能会更倾向于从左到右的评估顺序。 • i000指出，R语言的右赋值语法（`1 -> x`）似乎被LLM过度使用。 • sitkack建议，可以通过允许模型在一个方向上思考并反转输出结果来克服顺序问题。 • vessenes认为，从右到左的评估需要从末尾开始或在工作记忆中保持表达式，而这正是LLM不擅长的。 • aghilmort讨论了主流模型缺乏可逆因果推理能力，并提出了一些技巧和方法来改进模型在这方面的表现。 • knome提到，LLM在解析和生成某些自定义语言代码时，经历了从糟糕到逐渐改善的过程。 • tantalor认为，难以被LLM处理的语言也对普通大众不友好，建议语言设计者使语言更LLM友好，这也有助于提高语言的人类友好性。 • cess11指出，LLM在处理不同编程语言时存在混淆和不稳定的情况，并质疑使用LLM进行软件开发的实用性。 • leprechaun1066认为，LLM在处理如q语言等不同范式语言时的困难，不仅仅是因为评估顺序，而是因为训练数据和思维方式的局限。 补充讨论： • 讨论中提到了多种改进LLM处理非线性和不同评估顺序语言的方法，包括训练扩散模型、使用因果标记、优化输入输出格式等。 • 有争议的焦点在于LLM是否能够有效地处理非线性结构和不同评估顺序的语言，以及如何改进模型的表现。 • 语言设计者是否应该使语言更LLM友好，以同时提高语言的人类友好性，也是一个值得注意的讨论点。

文章摘要

考古学家在秘鲁北部巴兰卡省发现了一座距今3500年的古城佩尼科（Peñico），该城建于公元前1800至1500年之间，位于海拔600米的山坡上，距利马北部约200公里。佩尼科被认为是连接太平洋沿岸社区与安第斯山脉和亚马逊盆地居民的重要贸易枢纽。研究显示，该城有18座建筑，包括仪式庙宇和住宅建筑，出土文物包括仪式物品、陶土雕塑和贝壳项链。佩尼科靠近公元前3000年建立的卡拉尔文明，这一发现有助于理解卡拉尔文明在气候变化影响后的发展。考古学家Ruth Shady指出，佩尼科在贸易和文化交流中占据战略位置，是卡拉尔社会的延续。

评论摘要
主要讨论点：关于Peñico古城是否为美洲最古老文明的讨论，以及对该发现的新颖性和重要性的不同看法。 不同观点： • [tree_enjoyer]认为将Peñico称为最古老文明有些夸张。他们指出，虽然Peñico拥有早期幸存的建筑结构，但越来越多的证据表明，在更早的时间里美洲已经有人类活动。他们提到，在人类开始建造如奥尔梅克文明那样的大型石制建筑之前，可能已经存在其他文明和城市。此外，他们强调南美丛林中仍有许多未解之谜。 • [adolph]对该发现的新颖性提出质疑。他们提到，研究人员Shady和Machacuay在Google Scholar上没有新的关于Peñico的出版物，并指出该遗址经过八年的研究，出土了18个结构，包括仪式庙宇和住宅建筑。这暗示可能没有新的重大发现，或者媒体报道夸大了发现的独特性。 补充讨论： • [tree_enjoyer]的观点强调了对文明定义的讨论，以及对南美历史中未知部分的探索兴趣。他们认为Peñico可能不是唯一或最早的文明，只是目前已知的最早之一。 • [adolph]则关注于研究成果的学术发布和媒体报道之间的差异，质疑新发现的实际新颖性，并指出已有较长时间的研究历史。 争议焦点：Peñico是否能被称为美洲最古老文明，以及该发现是否具有真正的新颖性。

Most RESTful APIs aren't really RESTful

作者: BerislavLopac | 评分: 86 | 评论数: 33 | 发布时间: 2025-07-09 07:04
文章摘要

这篇文章主要讨论了Roy Thomas Fielding的论文《架构风格与基于网络的软件架构设计》，该论文介绍了代表性状态转移（REST）架构风格，旨在设计可扩展、高性能和可维护的网络系统，特别是Web服务。Fielding分析了多种网络架构风格的优缺点，强调REST专注于可扩展性、简洁性和适应性。他指出，REST是一种提供原则和约束的架构风格，而非具体的技术实现，如HTTP动词或CRUD风格API。 文章澄清了关于REST的常见误解，例如REST不等于CRUD，资源也不仅仅是持久化实体。Fielding特别强调了超媒体作为应用状态引擎（HATEOAS）的重要性，认为没有超媒体控制的API不能称为RESTful。HATEOAS通过动态发现链接减少客户端与服务器的耦合，提高系统的可演化性。 此外，文章解释了REST中的“资源”概念，指出资源是信息的抽象映射，而非具体的服务器实体，URI的语义由创建者定义，而非客户端或服务器需要理解的内容。

评论摘要
主要讨论点：REST和RESTful API的实际应用及其与理论定义的差距 不同观点： • cjpearson认为，REST API这个术语已经发生了语义扩散，实际使用中与Fielding论文中的原始定义不符。他指出，现代所谓的"REST API"通常返回JSON，使用CRUD操作映射到HTTP方法，并且在状态码使用上常常存在争议。他主张要么坚持原定义，要么接受现实，按常用理解使用该术语。 • mixedbit分享了自己的经验，指出他在深入研究Fielding的论文后发现，真正的REST在实际应用中并不总是有用。他认为Fielding的论文没有提供完整的自发现API构建方案，最终实现的自发现API往往缺乏客户端代码重用，且与特定应用的API无异。他还提到，REST的目标与良好的用户体验可能不兼容。 • _heimdall认为，REST和HATEOS在第三方作为API消费者时更有意义，而对于特定前端应用的后端API，REST的成本往往超过其收益。 • salmonellaeater指出，REST API设计适用于用户通过代理（如浏览器）导航和交互的场景，而不是针对特定Web应用的API设计。这类API更适合公开信息和交互的政府门户或开放数据项目。 • dwaltrip质疑HATEOAS的实用性，认为没有真正的客户端能够利用自动发现的API，并质疑这种客户端的必要性。 • Scarblac强调，UI设计师需要对页面外观进行详细控制，而RESTful API的自发现特性与此需求不符。 • nchmy建议通过更易懂的资源学习REST相关概念，并提供了一些参考链接。 • sublinear认为，通过引用schema定义（如JSON Schema）实现API动态导航在现实中存在问题，并质疑是否有必要在JSON响应中包含复杂的链接信息。 • osigurdson幽默地指出，集体忽视了Fielding的论文，只是喜欢使用"REST"这个词来描述HTTP/JSON的任意应用。 • makeitdouble支持实用主义，建议避免使用"RESTful"这个术语，而改用"HTTP based APIs"。 • pradn理解了Fielding的REST原则，认为其核心在于动态发现和抽象实体，允许API以更动态和通用的方式使用。 • bravesoul2反对REST和GQL，认为RPC风格更实用，强调应根据实际需求选择API风格，而非强制适应某种风格。 • 0x445442认为，REST在实践中只是通过JSON通信的分布式功能调用，开发和维护 nightmare。 • layer8认为，文章没有提供有力论据支持Fielding的REST定义应被视为标准，并指出该定义对非交互式客户端不适用，这也是其未被广泛采用的原因。 补充讨论： • cowsandmilk提到其所在公司将实际操作称为HTTP绑定，反映了业界对REST定义的实际应用差异。 争议焦点：REST的理论定义与实际应用的差距，以及HATEOAS的实用性和必要性。
