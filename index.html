Mechanical Watch: Exploded View

作者: fellerts | 评分: 281 | 评论数: 20 | 发布时间: 2025-06-22 14:56
文章摘要

文章主要介绍了作者受Bartosz Ciechanowski博客启发，计划制作一个真实机械表的“爆炸图”模型。这种模型可以让各个零件悬浮在一个透明树脂中，从不同角度观察。作者提到，目前市场上没有这样的产品，即便有机械表零件的树脂模型，也多作为“蒸汽朋克艺术品”出售，缺乏实际组装结构。作者打算使用简单的老式怀表机芯来进行此项目，因为其结构相对简单，没有日期功能和自动上弦装置。制作过程中，作者尝试了分层树脂浇铸，但遇到树脂发黄、固化时间长以及层间缝隙明显等问题。尽管如此，作者仍决心继续这个项目，并寻找解决方案。

评论摘要
主要讨论点：对将手机或手表零件悬浮在树脂中并进行展示的项目进行讨论，涉及项目技术、艺术价值以及实际操作的可行性。 不同观点： • **Jameshart**：提到Adam Savage曾做过类似项目，将手机拆解并悬浮在树脂中，虽然项目有赞助且部分工作较为仓促，最终效果更像是一个原型，但解决问题的技巧和方法值得一看。 • **Thom**：一方面认为拆解并展示这些精密设备可能有些“亵渎”，因为这些设备的魅力在于其长时间可靠运作，且修复过程也充满魅力；但另一方面，认为这种树脂雕塑非常酷，并回忆了自己尝试类似手工的经历。 • **Modeless**：提出是否存在一种透明凝胶物质，能在固化前保持胶状一段时间，以便手动调整零件位置，最终通过UV光固化。这一想法类似于悬浮3D打印技术。 • **Retr0id**：分享了自己使用砂纸逐步打磨树脂铸件的经验，指出可以通过这种方法达到较好的表面效果，并提到可能需要使用抛光剂。 • **WillAdams**：建议使用激光打印或建模的方式在玻璃或亚克力块内打印出零件模型，认为这样更容易实现类似效果，并提供了相关公司和资源的链接。 • **J_bum**：简单表达了对项目的赞赏，认为其非常了不起。 • **Petermcneeley**：指出如果悬浮介质与零件具有相同的折射率，支撑结构将不可见。 • **Jasonjmcghee**：认为这些作品非常出色，建议可以放在博物馆展示，并提供了相关灵感网站链接。 • **Yapyap**：提到TK Jewelers的负面经历，认为其是骗局，可能与项目本身无直接关系。 • **Cybertim**：好奇项目创作者是否会联系专业手表制作人进行最终铸造，并表示自己会喜欢拥有这样的作品。 • **Amelius**：建议可以逐层添加零件和环氧树脂，以避免使用支撑结构，但承认这可能需要为每层创建新的真空环境。 • **Nativeit**：认为如果作品能被打磨至完美状态，将会更加惊艳。 • **Jv22222**：表示如果在商店看到这样的作品，会非常想购买。 • **Kiru_io**：认为这是一个很酷的创意，建议可以联系手表制造商进行销售或合作。 • **Peterpanzeri**：简单表达了对实现类似项目的希望。 补充讨论： • 项目是否应保持零件的完整性和功能性（Thom, Yapyap）。 • 不同材料和技术（如砂纸打磨、凝胶物质、激光打印）在项目中的应用可行性（Retr0id, Modeless, WillAdams）。 • 作品的商业潜力及可能的手表制造商合作机会（Cybertim, Kiru_io）。 争议焦点：项目是否应尊重设备的原始功能和完整性（Thom）。

I wrote my PhD Thesis in Typst

作者: todsacerdoti | 评分: 126 | 评论数: 14 | 发布时间: 2025-06-22 21:12
文章摘要

这篇文章介绍了作者使用Typst而不是LaTeX撰写博士论文的经历。Typst是一种现代排版语言，语法类似Markdown，并具有类似Rust的动态类型脚本语言，易于学习和使用。作者赞赏Typst的编译速度快，即使是大型文档也能在数秒内完成编译，显著提高工作效率。此外，Typst的脚本功能强大，支持TOML文件解析和自定义数据处理，使得文档内容更具灵活性。在布局调整和语法高亮方面，Typst也表现优异，允许用户轻松定制模板和实现高质量的代码语法高亮显示。总体而言，作者认为Typst在很多方面优于LaTeX，是撰写学术论文的一个出色选择。

主要讨论点：LaTeX与Typst两种排版工具的优缺点及使用体验 不同观点： • [对LaTeX的批评] shermantanktop认为LaTeX使人沉迷于宏和排版细节，导致拖延，并将其比作“坑害学生的陷阱”。WhyNotHugo也指出LaTeX的工具链复杂，调试困难，有时需要多次运行命令或进行复杂的操作如`git clean`才能解决问题。 • [支持Typst] TimorousBestie和octernion认为Typst在编译速度和使用体验上优于LaTeX，特别是编译速度快，使用起来更加轻松。irundebian则提到在Typst中处理带有状态的宏较为困难。 • [LLM与排版] vessenes指出，尽管Typst在某些方面有优势，但由于LLM（大型语言模型）目前对LaTeX的支持更好，因此在处理长文档布局时LaTeX仍具优势。shrinks99也提到在处理多重参考文献时遇到问题，并考虑使用Alexandria等解决方案。 • [工具对比与解决方案] commandersaki分享了使用Typst制作的文档示例，展示了其在实际应用中的潜力。dkga则建议使用quarto来解决一些Typst存在的问题，尤其是参考文献问题。tiagod提到使用Typst生成多语言报告的经验，通过传递JSON数据实现。 • [使用LLM辅助排版] BiteCode_dev提供了一个使用LLM辅助排版的技巧，即先编写无格式或简单格式的内容，然后让LLM自动添加标记和格式，最后再手动调整错误。 • [对技术怀旧的看法] Svoka认为LaTeX像是一种“80年代的技术”，虽然功能强大，但需要更多现代的替代方案。他强调不同工具适合不同人群，不必强求所有人都使用LaTeX。 补充讨论： • [视觉展示] rossant建议添加截图以便更直观地展示Typst的效果。 • [个人经历] pityJuke分享了自己从LaTeX转向Typst的经历，并对Typst的稳定性和一致性表示赞赏。 争议焦点： • LaTeX的复杂性与Typst的易用性成为讨论的焦点。部分用户认为LaTeX工具链复杂且容易导致拖延，而Typst则提供了更现代、更高效的选择。 • LLM对不同排版工具的支持差异也是争议之一，目前LLM在LaTeX上的表现优于Typst。 总结： 讨论围绕LaTeX和Typst两种排版工具的优缺点展开，涉及工具链复杂性、编译速度、LLM支持、实际应用案例以及对技术怀旧的看法。用户普遍认为Typst作为新兴工具在某些方面优于LaTeX，但也存在一些需要改进的地方，如LLM支持和宏处理等。

Cross-Account and Cross-Region Backups with AWS Backup (and Friends)

文章摘要

文章主要讨论了在使用AWS Backup时遇到的一个问题：尽管AI可能声称AWS Backup支持跨账户和跨区域备份，但实际上AWS Backup并不支持同时进行跨账户和跨区域的备份。文章指出，AWS Backup可以支持跨账户复制和跨区域复制，但无法同时实现两者，特别是在处理RDS、Aurora、DocumentDB和Neptune等数据库服务时。 作者强调，为了满足数据保护和灾难恢复的需求，同时实现跨账户和跨区域备份是必要的。跨区域备份可以防止未经授权的访问，而跨账户备份则可以在区域性灾难（如火山爆发）时保护数据。 尽管AWS Backup支持集中式备份计划，但目前仍无法同时实现跨账户和跨区域的备份。作者建议了一种临时解决方案，即使用AWS Lambda脚本在完成第一次复制后触发第二次复制，并删除第一次复制。最终，作者期望AWS未来能支持同时进行跨账户和跨区域的备份，以简化实施过程。

评论摘要

Git Notes: Git's coolest, most unloved­ feature (2022)

作者: Delgan | 评分: 241 | 评论数: 21 | 发布时间: 2025-06-22 09:14
文章摘要

Git notes 是一种向 Git 提交添加元数据的方式，用于在不变更提交本身的情况下，为旧提交附加新信息，如代码审查和测试结果。它们可以存储关于任何 Git 对象（提交、blob、树）的元数据，并通过命令行操作。尽管功能强大，Git notes 使用起来较为复杂，界面不直观，导致其使用率低，且 GitHub 等平台未广泛支持。然而，一些工具和插件（如 Gerrit 的 reviewnotes 插件和 Google 的 git-appraise）展示了 Git notes 在分布式代码审查中的潜力。总体而言，Git notes 提供了强大的功能，但受限于可用性和用户体验。

评论摘要
主要讨论点：Git Notes 功能的用途、优缺点及其实际应用 不同观点： • [oftenwrong] 介绍 Git trailers 作为一种提交时的元数据附加方式，并提到 Gerrit 使用 Change-Id 的例子。 • [homebrewer] 补充 Forgejo 也从今年初开始支持该功能，提供了相关版本发布说明和代码合并请求链接。 • [kccqzy] 认为 Git notes 只在特定情况下有用，例如在提交后添加文本，并质疑 Acked-By 和邮件列表链接的实际需求，提出可以在提交信息中包含讨论内容。此外，认为在提交被回滚的情况下使用 Git notes 更有意义。 • [b0a04gl] 分享了在工作中大量使用 Git notes 的经验，用来记录内部代码审查、工单映射和事件线程链接，避免依赖平台 UI，强调了其在规模化使用中的价值。 • [noelwelsh] 认为 Git notes 使用率低是因为用户界面问题，而非用户知识不足，指出如果 GitHub 的 UI 支持显示 notes，其使用率会大幅提升。 • [lars512] 提供了在公共数据管道项目中使用 Git notes 的实例，记录构建输出哈希，但实际使用频率不高，且 notes 默认隐藏影响 awareness。 • [lucasoshiro] 提到许多 Git 的强大但被忽视的功能，如 bisect、reflog 等，认为很多人只把 Git 当作简单的文件存储工具，忽视了其高级功能。 • [cesarb] 分享了 LibreOffice 项目中使用 Git notes 跟踪提交的案例，用于记录提交的相关性等信息，但该用法已停止，因为 Apache OpenOffice 的变更速度减慢。 • [legends2k] 提到从手册中发现了 Git notes，但由于是本地功能且默认不推送或获取，团队未采用该功能。 • [mtillman] 认为 Git notes 的使用并不复杂，可以将文本笔记直接通过管道添加到 Git notes 中，质疑关于接口不便的批评。 • [paffdragon] 开发了一个基于 Git notes 的版本控制工具，用于版本覆盖，认为这在迁移功能到新仓库时非常有用。 • [Shank] 质疑 GitHub 为何取消了对 Git notes 的支持，并询问如何逆转该决定。 • [olejorgenb] 关心在 rebase 时带有 notes 的提交会发生什么。 • [pettereriksson] 提出将提示或其摘要作为每个提交的 note 添加，以便 LLM 后续推理代码变更的需求。 补充讨论： • Git notes 的实际应用场景讨论较多，包括代码审查、提交回滚、构建输出记录等，但其实际使用率受到 UI 支持不足和默认隐藏设置的限制。 • 争议焦点在于 Git notes 的使用复杂性与 UI 支持不足，部分用户认为其强大且有用，而另一些用户则认为其使用不便或不必要。 • 关于 GitHub 取消支持 Git notes 的决定引发了不满，用户希望逆转该决定以提升 Git notes 的可用性。
