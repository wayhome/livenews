pg_durable: Microsoft open sources in-database durable execution

作者: coffeemug | 评分: 324 | 评论数: 17 | 发布时间: 2026-06-05 15:59
文章摘要

pg_durable 是微软开源的 PostgreSQL 扩展，在数据库内实现持久化执行（Durable Execution）。它让长时间运行的 SQL 函数具备容错能力，通过检查点机制在每步执行后保存状态，崩溃或重启后可从断点恢复，无需重新执行已完成的工作。 适用场景包括：向量嵌入管道、数据摄取、定时维护、并行聚合、外部 API 调用等。可替代 pg_cron + 状态表、外部编排器（Airflow/Temporal）、队列+工作者等传统方案，将工作流逻辑统一在 SQL 中管理，减少架构复杂度。 核心优势是消除部分失败后的手动恢复、避免长事务锁定、将重试和进度跟踪集中到 Postgres。不适合单条 SQL 语句、毫秒级同步请求，或需要复杂应用逻辑的场景。

评论摘要
主要讨论点：微软开源的 pg_durable 项目——在 Postgres 中实现持久化工作流队列的可行性与价值 不同观点： • **支持者立场**：认为 2026 是 Postgres 队列年，社区贡献值得肯定；对本地数据库任务和需要持久化的长时间 cron 作业有价值；结合 PostgREST 可以构建功能强大的作业队列 • **质疑者立场**：将业务逻辑放入数据库类似存储过程的老问题——无法单元测试、版本控制困难、缺乏可观测性、扩展压力全落在 Postgres 上、隔离工作负载困难、缺少 IO 能力（尤其是 API 调用） • **困惑者立场**：不理解为何不用成熟的编排工具（如 Temporal、Apache Airflow 等 DAG 调度器）——控制流应该在代码中而非数据库中；文档中的限制条件（跨异构系统的工作流）让人质疑其与 Temporal 的可比性 • **架构层面担忧**：数据库本身已是最难扩展的基础设施，为何要给它增加长时间运行的作业负担？这可能是编程语言/虚拟机缺乏确定性执行和状态挂起恢复能力导致的"内部平台效应" 补充讨论：有用户关注实现细节（wait_for_schedule 的幂等性、错误处理机制、超时常量）；Azure Postgres 用户抱怨功能滞后；有人希望用于 S3 导出等维护任务；也有人期待微软赞助 PGRX 项目

评论摘要
主要讨论点：关于太阳能海水淡化新技术的可行性、效率和影响 不同观点： • **技术效率质疑派**：认为传统反渗透(RO)已接近理论最优能效，该热能方法应与同面积太阳能板驱动传统设备对比效率。指出海水淡化存在基本能量需求下限(ajb) • **实用性怀疑派**：技术仍处于实验室玻璃容器阶段，关键防堵塞机制和盐分清除系统尚未验证，需证明可长年运行(Animats)。成本高昂且需要飞秒激光等专利技术，难以规模化推广(shevy-java) • **潜在价值派**：直接产出晶体盐比盐水更易处理且可能有商业价值，尤其是镁、锂等矿物提取可能抵消部分淡化成本。海水中镁含量可观，固体副产品提取效率更高(scythe, photochemsyn) • **生态担忧派**：海洋矿物提取一旦盈利可能导致过度开采，威胁生态系统，希望技术无法规模化(noripcord) • **应用场景派**：设备复杂且对温度敏感，更适合应急响应或游艇等小规模场景，而非大规模部署(photochemsyn) 补充讨论：有人提议低技术方案(如除湿机+太阳能板用于灌溉)，也有人对沙漠海岸蒸发通道结合红树林的构想表示兴趣。论文数据显示日产水10.33升/平方米，盐0.38公斤/平方米。

评论摘要
主要讨论点：AI代理开发中是否应该使用TDD（测试驱动开发） 不同观点： • **支持TDD派**：认为测试是保持AI开发在正轨的最重要手段，能提升代码质量、减少bug。建议通过多轮子代理审查来提高质量，虽然消耗更多token但长期更节省时间。有人通过简单指令"用pytest做红绿TDD"就获得良好效果。 • **反对TDD派**：认为TDD在AI开发中是"虚荣指标"，会导致token成本暴增、开发速度变慢。AI可能在测试失败时修改测试而非代码，因为规格变化而非代码问题。更推荐瀑布式方法和工单/PR作为AI记忆，而非测试。 • **实践问题派**：指出TDD存在具体隐患：1) AI过度使用fallback导致静默错误（如地理计算用了不准确方法）；2) 测试可能是表面的"幻觉"，触发误报导致不必要的重构；3) 需要注入bug验证测试有效性，否则只是确认"能通过"而非"真有用"。 补充讨论： 关于实现方式有分歧：有人认为应通过直接指令而非技能配置来实现TDD，因为LLM已懂TDD概念。还有批评指出这类讨论缺乏实际对比数据，如果TDD真的更好应该已被纳入系统提示词。

英国政府数字服务(GDS)将其GOV.UK Pay支付服务的处理商从Stripe更换为荷兰供应商Adyen。这份为期三年、价值最高2530万英镑的合同涵盖地方政府、警察部门和武装部队的支付服务，约占GOV.UK Pay交易量的17%但覆盖超过70%的机构。新合作将引入"银行直付"功能，用户无需输入银行卡信息即可通过开放银行服务直接转账。约1000项服务将迁移至新供应商，对用户体验不会有明显影响。GOV.UK Pay自2016年推出以来已处理1.375亿笔交易，总额约92亿英镑。

评论摘要
主要讨论点：英国政府选择Adyen作为支付服务提供商，替代美国技术方案 不同观点： • **合同规模出乎意料**：政府全面支付合同金额竟小于美国中型企业的云账单，显示政府采购规模并非想象中庞大 • **Stripe营销vs实力**：认为Stripe擅长营销造势，让自己看起来比实际更重要；但也有人指出Stripe同样支持欧洲支付方式如Wero • **Adyen门槛问题**：批评Adyen拒绝年交易额低于百万的小客户，服务定位偏高端 • **去美国化趋势**：观察到各方尽可能放弃美国技术的趋势 • **成本转嫁方案**：建议让用户承担交易成本，促使大家使用银行转账 • **欧美科技竞争的双标**：批评HN社区对欧洲科技持贬低态度，但当美国公司被欧洲公司替代时又找不出好话，揭示潜在偏见 补充讨论：有人关注此举能否实质性降低地方政府成本，还是仅扩展支付选项；也有人吐槽英国税务局(HMRC)退税流程繁琐，希望数字服务改善。
