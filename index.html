主要讨论点：F-Droid 构建服务器因不支持 SSE4.1 指令集而无法运行新版 aapt2 的问题，以及解决方案和背景争议。 不同观点： • **重新编译 aapt2** - [ivanjermakov] 和 [userbinator] 建议直接重新编译 aapt2 以适配旧硬件，并指出其源代码是开放的。 - [karteum] 类比 buildroot/openwrt 的做法，主张从源码编译整个工具链（包括 gradle/aapt2）以确保结果可预测。 • **Google 已修复问题** - [jchw] 提到上游（Google）可能已修复此问题，并引用 F-Droid 的 issue 讨论作为依据。 • **硬件过时的争议** - [micw] 和 [trenchpilgrim] 认为 SSE4.1 是 2008-2011 年的技术，质疑为何仍在使用如此陈旧的服务器。 - [wtallis] 提出可能是虚拟机配置问题（未暴露指令集支持），而非硬件本身不支持。 • **F-Droid 的构建策略批评** - [yjftsjthsd-h] 对 F-Droid 直接使用上游二进制文件（而非从源码构建）表示惊讶，认为与其强调隔离构建环境的理念矛盾。 - [edgan] 借此批评 F-Droid 的构建流程复杂性，并推广自己的替代项目 Discoverium。 • **其他案例类比** - [roywashere] 引用 MySQL Docker 容器类似问题（突然要求 x86-64-v2 指令集），说明此类问题并非孤立事件。 补充讨论： - 争议焦点：是否应强制升级硬件（或配置）以支持现代指令集，还是通过修改工具链兼容旧系统。 - [exabrial] 和 [benrutter] 的评论偏离技术讨论，前者吐槽 Android 的虚拟机设计，后者表达对 F-Droid 生态重要性的担忧。 - [nativforks] 整理了相关 issue 链接，提供具体案例（如 Catima、MBCompass）佐证问题的广泛性。
