Can your terminal do emojis? How big?

作者: dgl | 评分: 42 | 评论数: 7 | 发布时间: 2025-06-24 02:13
文章摘要

文章介绍了如何在终端中使用大号emoji和文本。通过利用VT100终端的**DEC Double-Height Line (DECDHL)**转义序列，可以实现双倍高度的文本显示，从而使emoji看起来更大。具体方法是使用特定的转义字符组合，将文本或emoji分成上下两部分显示，如示例中使用`printf '\e#3😑\n\e#4😶\n'`。这种方法不仅可以在老式VT100终端上实现，某些现代终端如Apple Terminal和Windows Terminal也支持。此外，文章还提到可以结合Unicode字符创造出常规不存在的emoji组合，如大脑和外星人图案。虽然并非所有终端都支持这种功能，但它为脚本输出增加了趣味性，且在不支持的终端上会降级为普通文本显示。最后，文章还提到Kitty终端有一种更现代的方法来实现不同大小的文本显示。

评论摘要
主要讨论点：终端中 emoji 宽度问题的技术原因及其影响 不同观点： • [b0a04gl] 认为 emoji 宽度问题主要源于终端如何解析 Unicode 的 "grapheme clusters"（字素簇）、"codepoints"（码位）和 "display cells"（显示单元）。由于 emoji 通常由零宽连接符、变化选择符和肤色修饰符等多个码位组成，导致终端在计算宽度时容易出错。除非使用支持字素感知的渲染器并与字体引擎同步，否则终端在处理 emoji 宽度时总会出现猜测错误。Wezterm 和 Kitty 终端在这方面表现较好。 • [phito] 表示其终端甚至连文本缩放功能都没有，暗示其终端在处理 emoji 宽度问题上可能更加基础或不完善。 • [liamkearney] 对该技术细节的讨论表示赞赏，认为这是一个有趣的互动，并表示感谢。 • [LtWorf] 指出 konsole 终端中因此出现了许多 bug，暗示该问题在 konsole 中的表现尤为明显。 • [mmastrac] 认为目前终端对警告三角 emoji 的宽度处理不一致，给脚本编写带来了困难。他希望有一个标准机构能够规范 emoji 在终端中的显示方式，以便开发者更容易处理相关问题。 补充讨论： • 争议的焦点在于终端对 emoji 宽度的处理缺乏统一标准，导致实际显示效果不一致，影响了用户体验和脚本编写。 • 提到了 wezterm 和 kitty 终端在处理 emoji 宽度问题上相对较好，可能是因为它们采用了更先进的渲染技术。 • 有用户对该技术问题的讨论表示兴趣和赞赏，也有用户直接受到该问题的影响并表达不满。

Excalidraw+ Is Now SoC 2 Certified

作者: gmays | 评分: 134 | 评论数: 13 | 发布时间: 2025-06-24 01:54
文章摘要

Excalidraw+ 获得了 SOC 2 认证，以简化安全合规流程。他们使用 Vanta 来连接服务并修复合规差距，编写了大量政策，实施了零信任生产访问，升级了技术栈，进行了渗透测试，并评估了所有供应商。最终，他们通过了 SOC 2 Type I 认证，正在进行 Type II 认证。SOC 2 是一种安全和合规框架，分为 Type I（检查系统和政策是否存在）和 Type II（检查政策是否长期有效）。尽管政策编写是最繁琐的部分，但大多数安全措施他们早已实施，只是需要正式记录。未来可能还会追求 GDPR 或 ISO 27001 认证。这一过程帮助他们建立了更安全的运营基础。

评论摘要
主要讨论点：SOC 2认证的过程、重要性、实际效果以及其在科技行业中的角色。 不同观点： • **[tptacek]** 认为，SOC 2 Type 1几乎不可能不通过，因为它只是记录某个时间点的基线状态，真正的考验在于Type 2。他建议在Type 1阶段尽量减少安全工作量，只关注那些长期能够遵守的最佳实践，以避免日后移除不必要的控制措施带来的麻烦。同时，他批评了一些供应商利用Type 1让客户过度升级安全措施，这是一种误导。 • **[Vic-Bhatia]** 指出，SOC 2并没有“认证”这一说法，只有“证明”（attestation）。他强调了用词的准确性，并解释了四种审计意见（Unmodified, Qualified, Adverse, Disclaimer），建议在准备SOC 2证明时要特别注意访问管理、变更管理以及威胁和漏洞管理等技术领域。此外，他还提醒要谨慎定义系统范围和审计测试矩阵。 • **[quicklime]** 质疑为什么一个由会计师（AICPA）创建的安全框架会在科技行业中被广泛接受，并成为评估SaaS供应商安全实践的标准。他认为这有些不可思议，因为通常应该由科技行业的人来评估IT安全实践。 • **[b0a04gl]** 分享了他们的实际经验，指出获取SOC 2 Type 1并不容易，尤其是当基础设施存在多年积累的问题时。这迫使他们清理了大量历史问题，并建立了完善的日志和访问记录系统。对于开放核心（open core）的设置，还需明确哪些部分公开，哪些部分需要登录和跟踪。 • **[hsbauauvhabzb]** 提到，尽管一些产品拥有SOC 2证明，但实际安全状况很差，质疑是否可以通过造假或玩弄系统来获得SOC 2证明，或者是否是审计师 incompetent。 补充讨论： • **[rajeshrajappan]** 表示，他们正在进行SOC 2和ISO 27001的过程，认为虽然合规平台帮助很大，但仍需大量工作，建议早期引入有审计经验的人参与。 • **[danjc]** 指出，即使拥有SOC 2证明，仍需面对供应商问卷和特殊安全要求，但过程会更容易。 • **[ivolimmen]** 提到，在荷兰的大型市政机构中，也有类似的严格记录和审计要求，认为一旦适应了这些框架，ISO等其他框架也会变得简单。 • **[shrubble]** 认为，电信行业因为高度监管，也需要处理类似的安全官僚程序。 • **[blackbirdsr71]** 和 **[9283409232]** 则关注了文章中的图表和Excalidraw的自托管替代方案问题，偏离了主要讨论点。 • **[doctorpangloss]** 和 **[ranger_danger]** 对SOC 2认证的必要性和实际效果提出了质疑，前者希望这种“疯狂”能结束，后者则询问了安全问卷的具体情况和目的。 争议焦点： • SOC 2认证的实际难度和价值：一些人认为很容易通过，尤其是Type 1，而另一些人则认为需要大量工作和清理历史问题。 • SOC 2认证的权威性和可靠性：有人质疑是否可以通过造假或玩弄系统来获得证明，或者审计师的资质和能力是否足够。

A Deep Dive into Solid Queue for Ruby on Rails

文章摘要

本文是Ruby on Rails的Solid Queue系列的第二篇，深入探讨了Solid Queue的调度功能。与传统依赖外部服务（如Redis）的队列系统不同，Solid Queue将所有任务数据存储在数据库中，且性能出色。它不仅支持简单的后台任务执行，还支持任务调度、定时执行以及并发限制等功能。 Solid Queue通过`solid_queue_scheduled_executions`表存储调度任务，该表与`solid_queue_ready_executions`表结构相似，但增加了`scheduled_at`列，用于指定任务的执行时间。调度任务时，系统会将任务数据插入`solid_queue_scheduled_executions`表。 Dispatcher进程负责定时检查并执行已到期的任务。它通过一个循环调用`poll`方法，持续从数据库中查询到期的任务并将其转移到`solid_queue_ready_executions`表，供工作进程执行。Supervisor则负责监督Dispatcher和工作进程的运行状态。 总体而言，Solid Queue提供了强大的任务调度功能，且无需外部依赖，配置简单，功能全面。
