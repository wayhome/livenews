Can we have the day off?

作者: mlsu | 评分: 180 | 评论数: 33 | 发布时间: 2026-05-28 00:40
文章摘要

作者以讽刺口吻质疑“AI将让白领生产力暴增”的说法：如果AI真能把效率提高10倍，人们理应更快完成工作、每周少上一天班，比如周五休息。文章借此追问，技术进步为何总被用来要求员工产出更多，而不是换来更少工时、更好生活与育儿空间。

评论摘要
主要讨论点：AI带来生产率提升后，收益应如何在员工、公司与股东之间分配；这是否能转化为更短工时、更高薪酬或更差的劳动处境。 不同观点： • 员工应主动争取把AI红利转化为自身收益。cattown认为，大家一边炫耀AI提升效率，一边接受更低安全感和不涨薪，很吃亏；应在公司会议中直接追问：能否减少工时、增加休假或提高薪酬。 • 历史经验显示，技术进步未必减少劳动时间。alexpotato引用其父亲在证券业电脑化后的经历：当年也承诺“会有更多空闲”，但之后30年工时并未减少。terminalgravity进一步类比卢德运动，认为技术红利往往流向股东，工人则面临工资受压和技能贬值。 • 支持更短工作周，认为现实可行。NDlurker分享3天/4天轮班、连续休9天的正面体验；nemomarx称四天工作制已多次试验且生产率不降，若AI agent成熟甚至可考虑三天；erelong主张创业公司应直接实践推广；jdougan讨论“周三变第二个周末”的具体安排。 • 反对或质疑缩短工时的落地逻辑。madrox认为四天工作制像“囚徒困境”：若有人继续更长工时就更易职场领先，导致集体无法降工时。kingforaday则担心缩短工时会引发薪资、AI使用成本、办公租约等连锁争论，现实上可能变成员工吃亏。 • 生产率提升未必对应真正“少干活”。bruce511指出，程序员的“真实工作”大量是开会，AI主要减少编码时间，却可能让员工参加更多会议，因此管理层高兴，但员工未必能换来周五休息。 补充讨论： • distantprovince指出，现实中不少人会以“少干一点、慢一点”私下保留部分效率收益。 • 也有人把话题延伸到更广泛福利，如全民医保（ZitchDog）或后稀缺社会想象（tantalor）。 • 争议焦点在于：AI红利究竟应归员工、企业还是股东，以及“高效率”能否真正换来更少劳动而非更高要求。

评论摘要
主要讨论点：YouTube等平台是否应识别/标注AI生成内容，以及这在视频、音乐、评论、广告和搜索中的实际效果与风险。 不同观点： • 支持标注/过滤AI内容：不少人认为平台应提供AI内容标签，并允许用户在推荐、首页和搜索中屏蔽这类内容；有人希望扩展到音乐、网页文章、Reddit/Twitter评论甚至广告，核心诉求是减少“AI灌水”与误导。 • 质疑自动检测可靠性：多位评论者担心AI检测会有大量误判，引用文本检测工具把《独立宣言》判成AI的例子；他们认为漏判不好，但错杀更严重，可能伤及创作者收入与声誉。 • 对AI视频内容“有条件接受”：有人不反感生成式视频素材本身，认为可替代b-roll、节省成本；但强烈反感AI配音/AI脚本，称其是“立即拉黑”的信号。也有人表示只要内容有信息量就能忍受，但很快会因套话、文风机械而厌倦。 • 认为用户可主动规避：有人建议直接关闭推荐页，只看订阅内容，以避免平台推送大量随机或疑似AI内容。 补充讨论： • 争议焦点在于“是否该标”和“能否准确认出AI内容”之间的矛盾。 • 有人指出Google立场尴尬：一边推广自家AI视频工具，一边若给AI内容打标签，可能反而打击其使用。

What Apple and Google are doing to push notifications

作者: iamacyborg | 评分: 168 | 评论数: 28 | 发布时间: 2026-05-27 19:24
文章摘要

文章指出，推送通知正重演邮箱的路径：苹果和谷歌从“传输管道”变成“主动中介”。出于电量、体验和注意力管理，平台通过通知分级、频道、权限、专注模式和设备端模型，对推送进行过滤、降权、汇总甚至改写。结果是品牌对触达用户的控制持续减弱，推送越来越由平台算法而非发送方决定。

评论摘要
主要讨论点：手机推送通知应服务于用户而非营销；平台（Apple/Google）是否应限制通知，以及用户应拥有多大控制权。 不同观点： • 用户注意力优先派：多数人认为通知只应限于电话、消息、银行、健康、停车等真正紧急或事务性信息；促销、连击、推荐、配送更新不值得打扰。有人用长期勿扰、删App、关通知、过滤邮件等方式自保。 • 支持平台强管控派：认为Apple/Google压制营销推送是好事，推送应主要用于transactional notifications；广播和促销被削弱“完全没问题”。 • 强调更细粒度控制派：希望系统提供“关闭所有营销通知”“更好的摘要/digest”“按通知类型单独管理”。有人称Android在通知内直接细分控制优于iOS。 • 担忧平台中心化派：虽认可平台替用户挡垃圾，但担心APNS/FCM宕机、审查或过度控制；主张自托管或替代推送方案，如Unified Push、Home Assistant直连通知。 • 开发者/发送者视角受质疑：评论者指出作者把发送者与接收者利益对立化；也有人不关心开发者困境，认为营销团队滥用推送才是根源。 补充讨论： • 争议焦点在于：平台限制通知究竟是保护用户，还是过度掌控基础通信渠道。 • 有业内例子称推送延迟、抑制、合并自2011年前后就存在，说明平台干预并非新鲜事。

Rust (and Slint) on a Jailbroken Kindle

作者: homarp | 评分: 99 | 评论数: 8 | 发布时间: 2026-05-27 19:51
文章摘要

文章讲述作者在越狱后的 Kindle Paperwhite 上运行 Rust 与 Slint 的过程：先用 cargo-zigbuild 交叉编译到 ARMv7 musl 目标，再通过 USBNetwork 获得 SSH 访问并部署程序。随后作者把 Slint 的软件渲染输出写入 /dev/fb0 帧缓冲，并用 ioctl 刷新电子墨水屏；同时从 /dev/input/event1 读取触摸事件并转换给 Slint。最终成功让 Rust GUI 在 Kindle 上运行。

评论摘要
主要讨论点：围绕在 Kindle 等低功耗设备上运行/开发 Slint、Rust、Zig 等软件的可行性，以及越狱、供电和生态成熟度等实际问题展开。 不同观点： • 支持与赞赏的观点：多位评论者认为这个项目“很酷”“很想试试”，肯定了在旧 Kindle 上折腾软件的趣味性，尤其喜欢墨水屏带来的复古体验。FlyingSnake 还以自己在旧 Kindle 上交叉编译 Zig 的经历作为呼应，说明这类尝试有实际可行性。 • 偏技术交流的观点：sandreas 分享了自己在 LicheeRV Nano（RISC-V 64-bit musl）上编译 Rust/Slint 的经验，用自定义 Cross Docker 镜像完成构建，并提到便携音频播放器项目中的供电问题：TP4057 模块不够稳定，难以可靠驱动 USB-C 转 3.5mm 适配器，正在改用 Battery Pal 评估。 • 对框架比较的关注：KolmogorovComp 将话题延伸到 Slint 与 Druid/egui 的对比，反映出讨论不仅限于 Kindle 改造，也涉及 Rust GUI 框架选型，但评论中未给出进一步回答。 • 持谨慎观望态度的观点：hardwaresofton 关注 Kindle 越狱是否稳定、如何避免自动更新，以及“后改装”生态是否过小，因此暂时选择 xteink 或未来考虑 Boox。其核心诉求是：若 Kindle 能可靠越狱并运行自定义软件，才是更有吸引力的方案。 • 使用条件疑问：IshKebab 提出是否必须一直插电使用，说明大家也关心这类改造设备的独立续航和实际部署方式。 补充讨论： • homarp 补充了项目代码仓库，方便他人复现与深入研究。 • 争议/焦点主要在两点：一是 Kindle 越狱与绕过更新是否足够可靠；二是硬件供电与续航是否稳定到能支持实际使用。

文章摘要

作者虽自建ISP，仍感互联网高度依赖少数中心化服务商，难抗审查且缺乏真正“所有权”。他主张以LoRa等免授权无线电发展网状网络，作为互联网的低成本、抗审查、具韧性的补充，适合消息、社交与信息共享。文中以Meshtastic为例，肯定其易用和先发优势，但批评其设计更适合小型私有群组，不适合大规模公共网状网络。

主要讨论点：对 Meshtastic、MeshCore、Reticulum 等网状/去中心化通信方案的实用性、应用场景与技术路线的讨论。 不同观点： • 质疑实用性：有人认为这类技术常见问题是“距离短、速率低”，在复杂地形和高密度地区效果更差，像“90年代无绳电话”或不如摩尔斯电码，更多是可玩但不够实用的设备。 • 看好低速“平行互联网”：有人被 MeshCore 吸引，认为只够文本传播反而是优点；既有复古情怀，也觉得这种天然不适合图片音视频的网络，能在设计上减少垃圾信息和色情内容。 • 强调已有成果：有人分享已部署太阳能节点，实现约200英里覆盖，显示在特定条件和折腾投入下，这类网络能做到相当远距离。 • 认为 Mesh* 偏“玩具/技术演示”：有评论明确觉得 Meshtastic、MeshCore 相比 Reticulum“不严肃”，适合小型专用私网或爱好者交流，但存在明显且致命的扩展问题，难发展成可持续的大网络。 • 倾向 IP 化路线：有人更希望发展基于 IP 的自组网通信，认为 802.11ah/HaLow 这类长距离 Wi‑Fi 方案更通用、更灵活，应让现有 Wi‑Fi 具备更强的 ad-hoc 能力。 补充讨论：评论间的争议焦点主要在“低速低带宽是缺点还是优点”以及“应继续发展专用 Mesh 协议，还是转向更通用的 IP/Wi‑Fi 自组网”。另有人联想到 Gemini/Gopher/Finger 这类轻量文本协议，认为可能与 Reticulum 形成配合。
