Using AI to write better code more slowly

作者: signa11 | 评分: 137 | 评论数: 18 | 发布时间: 2026-05-25 23:16
文章摘要

作者认为，AI写代码不该追求“又快又烂”，而应帮助开发者更慢但更高质量地开发。核心做法是让多个模型反复审查PR、发现并交叉验证问题，再优先修复高风险缺陷，必要时放弃错误方案。这样虽不一定提升表面效率，却能改善代码库健康、加深对系统失败模式的理解。

评论摘要
主要讨论点：AI 在编程中的合适角色，尤其是“写代码”与“做代码审查/辅助实现”之间的边界，以及效率、质量、控制感和能力退化的争议。 不同观点： • 支持“多模型迭代审查”流程：`bottlepalm`认为让 Claude 实现、Codex 审查、反复修正与补测试，虽来回成本高，但首版质量接近“v3”。`justinlivi`也说审查循环更慢，却常换来更高质量代码。 • 支持“AI做辅助/审查，不主导编码”：`crabmusket`认可 AI review 价值，认为这比直接代写代码更不易让人失去思考；`EFLKumo`、`slopinthebag`主张人定架构/接口、AI补中等难度或重复实现，以保持上下文和控制权。 • 质疑“代理式写代码”：`TACIXAT`认为编程中大量微观架构决策无法预先写成完整规格，Claude/Codex过于急于达成目标，导致边界情况和架构契合度信心低，还削弱编程乐趣。 • 强烈反对 AI 编码：`ai_fry_ur_brain`、`ptlan_asnh`认为 AI 不能替代人的能力，长期依赖会削弱思维，讽刺舆论已从“AI 无 bug”转向“慢慢享受 AI”。 • 将 AI 视为学习和低风险助手：`kiba`把 LLM 当 tutor，用于陌生领域纠错；`syntaxing`偏好“较笨模型”，因为更会主动验证结果，避免放手让它大改代码库。 • 关注文章本身不足：`smusamashah`批评原文缺少代码示例，只有经验和提示词，像常见观点文，缺乏可学习的具体过程。 补充讨论：争议焦点主要在三点：1. AI 是否真的节省时间，还是把时间转移到审查与返工；2. AI 应做主导编码还是局部增强；3. 长期使用是提升质量，还是削弱理解力与工程判断。

Norway's 2 petabytes of Huawei flash storage and LLM training

作者: rbanffy | 评分: 158 | 评论数: 18 | 发布时间: 2026-05-25 19:37
文章摘要

挪威国家图书馆受文化部委托，依托本国最大数字文化馆藏，建设挪威语主权大模型。其数据管道采用2PB华为全闪存储，先完成数据清洗、去重和标准化，再送往国家超算训练。项目难点不在算力，而在海量档案向AI流水线迁移、评测标准、治理及多系统协同。

评论摘要
主要讨论点：挪威建设“主权LLM”是否必要、可行，以及相比自训模型是否应更侧重数据开放与文化语料建设。 不同观点： • 支持“本地语言/文化AI需被照顾”的立场：原说法认为若没有本国语言主权LLM，全球英语模型可能不了解只存在于本地语言中的历史、新闻和文化；这背后强调AI需要“文化托管者”而不只是技术建设者。 • 怀疑“语言劣势论”的立场：多位评论者质疑这一前提，认为大型模型早已尽可能抓取多语种公开数据，未必真会忽视小语种；也有人直言这类说法更像争取 funding 的叙事，而非技术判断。 • 反对“从零训练主权LLM”的立场：不少人认为现有硬件规模不足以训练真正有竞争力的大模型，做 LoRA 或基于开源模型微调更现实；因此担心项目成本高、效果差，甚至质疑是否在浪费公共资金。 • 倾向“建设数据而非模型”的立场：有人建议挪威更应整理、授权并免费共享高质量挪威语与本国文化数据，让各家前沿模型都能学会挪威语和本地知识；也有挪威用户提到国家图书馆检索系统已很好，说明基础数据服务本身就很有价值。 • 现实政治悲观看法：即便理念成立，小语种国家也未必有足够政治意愿和持续投入去做，因为支持本地代表性的人往往也接受直接用 ChatGPT 之类外国产品，或干脆反对AI。 补充讨论：争议焦点主要在两点，一是“全球模型是否真的不懂本地文化”，二是“应投钱训练主权模型，还是投向数据整理、开放和检索基础设施”。另有一些评论在争论文中硬件与存储数字是否夸张、表述是否失真。

Taking a walk may lead to more creativity than sitting, study finds (2014)

作者: bilsbie | 评分: 49 | 评论数: 17 | 发布时间: 2026-05-25 22:30
文章摘要

美国心理学会2014年研究称，步行比静坐更能激发创造力。针对176名参与者的多项实验发现，走路时在“发散性思维”任务中更容易提出新颖、合适的想法，室内跑步机和户外步行都有类似效果，且步行后的创造力提升有一定持续性；但在只有单一答案的聚合性问题上，步行者略逊于静坐者。

评论摘要
主要讨论点：离开电脑、通过步行等低干扰活动来促进编程调试、问题解决和思考，是否确实有效，以及这种方法为何有效。 不同观点： • 多数观点支持“离开电脑有助于解题”。散步、洗澡、睡觉、骑车、割草、上厕所路上等场景，都被认为能触发灵感；有人提到晨走时能“修好”棘手 bug，也有人说复杂问题和人生决策常在步行或割草时想通。 • 一类观点强调关键不只是运动，而是“无干扰”。主帖和后续评论都认为，去掉播客、音乐、手机等刺激后，大脑才能持续“后台运转”，类似“shower thoughts”让潜在想法浮现。 • 还有观点把这上升为普遍方法甚至管理建议。有人引用拉丁语“solvitur ambulando”，有人举康德定时散步、乔布斯靠散步促成商业谈判的例子，也有人建议强制安排步行/活动休息。 • 少数评论提出现实限制或反差体验。比如有人说快走时会被路人干扰，反而更饿更烦；也有人指出最难的是“强迫自己离开电脑”。 补充讨论：争议焦点不在“是否完全有用”，而在“有效因素是什么”及“是否人人适用”。整体共识偏向：步行等活动通过放松、专注和减少外界刺激来提升思考质量。

How Shamir's Secret Sharing Works

作者: subract | 评分: 35 | 评论数: 5 | 发布时间: 2026-05-25 22:37
文章摘要

文章介绍了Shamir秘密分享方案：把一个秘密拆成多份，只有达到门槛数量的份额才能恢复，少于门槛则完全得不到任何信息。其原理是把秘密藏在多项式在0处的取值中，每份额是曲线上的一个点；2份定直线，3份定抛物线，更高门槛对应更高阶多项式。文中还提到Ente将其用于Legacy Kit恢复流程。

评论摘要
主要讨论点：围绕“如何分割并恢复秘密/数据”的技术选择，比较 Shamir 秘密分享、Reed-Solomon/Par2 类纠删码方案，以及它们在教学和实际实现中的应用。 不同观点： • 一种观点强调 Shamir 秘密分享很适合教学。`_jackdk_`认为这是很酷的技巧，甚至适合在中学阶段作为“多项式在计算机科学中的应用”来讲授，重点在其直观性和教育价值。 • 一种观点提供了实际落地案例。`Cider9986`直接给出 Ente 的实现链接，说明这类方案已有可用实现，讨论从理论延伸到工程实践。 • 一种观点区分了 Shamir 与 Reed-Solomon 的安全性质。`teravor`指出：大秘密通常先加密，再分发密钥份额；若直接用 Reed-Solomon 切分载荷，也能做恢复，但会失去 Shamir 的信息论安全性。其论据是：一旦依赖加密，这种“绝对安全”本就部分让位于计算安全；而 Reed-Solomon 还需配合 AONT，避免某些分片在病态情况下泄露信息。 • 另一种观点从直觉上质疑“为何不能直接用 Par2 类系统替代”。`compsciphd`表示自己最初就想过用恢复块方案：把数据切成恢复块分给不同用户，任意 N 人即可恢复密钥并解密，核心是在功能上类比门限恢复。 补充讨论：争议焦点在于“功能可替代”不等于“安全性质等价”。`compsciphd`提出的是可恢复性思路，`teravor`则回应其隐含问题：纠删码能解决恢复，但若没有 AONT 等处理，可能泄露部分信息，因此与 Shamir 的门限保密目标并不完全相同。

Show HN: Write your BPF programs in Go, not C

作者: boratanrikulu | 评分: 58 | 评论数: 8 | 发布时间: 2026-05-21 16:25
文章摘要

`gobee` 是一个把受限 Go 代码转译为 eBPF C 的工具，让开发者用 Go 而不是 C 编写内核侧 BPF 程序。它会同时生成可读的 BPF C、源码映射和类型安全的 Go 用户态绑定，并复用 `clang` 实现 CO-RE、装载前内核版本检查等能力。项目目标不是替代传统 `libbpf` 工作流，而是为希望把内核态、用户态和构建流程统一在一个 Go 模块中的场景提供方案。

评论摘要
主要讨论点：是否有必要用 Go 转译来编写 eBPF，以及这相比直接用 C/Rust 的实际价值与工程可行性。 不同观点： • 质疑使用 Go 的必要性。`badc0ffee`指出 eBPF 本质上仍在面对内核 C 接口和 C 数据结构，且受限很多：循环会被展开、不能用可变参数，也用不上 goroutine、select、context 等 Go 特性，因此“既然写 eBPF 还得会读内核 C 源码，为何不用原生语言”。`shirleyquirk`也直接追问为何不写“原生语言”。 • 支持“转译到 C”是现实折中。`hnlmorg`转述项目理由：Go 官方编译器没有 LLVM 的 BPF 后端，直接支持是多年工程；因此先生成 C，再复用 clang 的成熟 BPF 后端，可顺带获得 BTF 和 CO-RE。并提出 `TinyGo` 或许因基于 LLVM 更适合，这是一个延伸讨论点。 • 认为 Rust 更适合 eBPF。`sparrc`虽偏爱 Go，但认为 BPF 是 Rust 的优势场景，和上面对 Go 适配性的怀疑形成呼应。 • 主张 C 依然最佳。`razighter777`认为在内核 eBPF 中，Go/Rust 常见的内存安全优势被 verifier 对边界、访问和正确性的校验部分替代，因此多数场景下直接写 C 仍最好。 补充讨论： • 争议焦点在于：Go 在 eBPF 场景中是否真的带来收益，还是只增加一层转译复杂度。 • `hbwang2076`关注工程质量，强调异常情况下的退化和错误处理。 • `i2km`批评 README 暴露出“草率”，偏向项目成熟度而非语言路线。 • `a1o`提出“BPF 是什么”，说明讨论门槛较高。
