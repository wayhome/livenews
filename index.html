I found 10k GitHub repositories distributing Trojan malware

文章摘要

作者在GitHub上发现了大规模恶意软件传播活动。起因是他发现有人复制了他的项目仓库，并在README中添加了指向恶意zip压缩包的链接。这些仓库每隔几小时就删除旧提交并推送新提交，仅更新README文件中的压缩包链接。压缩包内含木马病毒，但VirusTotal无法检测链接本身。 作者向GitHub举报后等待一个月才得到处理。后来他编写脚本分析GitHub事件数据，从1600万次提交中筛选出符合特定模式的仓库（频繁更新、仅修改README、包含压缩包链接等）。最终发现了约10,000个类似的恶意仓库，它们来自不同贡献者，使用不同名称，但遵循相同的恶意传播模式。

评论摘要
主要讨论点：GitHub上出现大规模恶意代码仓库克隆攻击，通过伪装成合法开源项目传播木马病毒，窃取用户账号和加密货币。 不同观点： • **攻击目标争议**：有人认为主要针对AI代理程序（自动添加依赖时被感染），并可能服务于选举操纵（窃取社交媒体账号用于机器人传播）；另有人通过技术分析认为目标是窃取加密货币（病毒向Polygon RPC节点发送请求） • **GitHub责任问题**：部分用户批评GitHub响应缓慢且不一致（盗版软件举报2年未处理，恶意仓库有的24小时删除有的1个月无回应）；有人建议GitHub应与杀毒公司合作扫描发布文件 • **开源安全神话破灭**：指出"开源即安全"的原则已失效，因为无人有时间审计代码，且GitHub已成为大量无审计能力用户的软件分发中心 • **检测系统缺陷**：VirusTotal等工具存在盲区（提交链接显示安全，提交文件本身才检测出木马；未扫描压缩包内的下游恶意文件） • **搜索引擎差异**：Bing比Google更容易返回钓鱼网站和恶意结果，用户因此放弃使用 补充讨论：攻击者使用频繁删除/推送commit来提升"最近更新"排名；需要持续扫描开源软件的自动化工具；受害者发现恶意方案后感到无力处理。

BOMwiki是一个免费的物料清单百科全书，将每个产品拆解至最小零部件（如螺丝、轴承）。目前已收录4,879个产品、30,390,912个零件、192,471个独立项目，涵盖51个领域。网站展示了从商用客机（约60万个零件）到智能手机的详细物料清单，追溯至原材料层级。最大的物料清单是波音747级别的巨型喷气式飞机，包含564万个零件。网站还统计了最常用的零部件（如紧固件组、连接器）和跨产品的共享组件，构建了一个完整的产品零部件知识图谱。

American Express: Cell-Based Architecture for Resilient Payment Systems

作者: birdculture | 评分: 47 | 评论数: 8 | 发布时间: 2026-06-15 22:36
文章摘要

美国运通核心支付系统采用**基于单元的架构**（Cell-Based Architecture）来确保全球支付平台的高可用性和低延迟。每个单元是独立的部署单元，包含自己的微服务、数据库和组件，可独立处理支付交易。 **核心设计原则**： - **故障隔离**：单元之间相互独立，一个单元故障不会影响其他单元 - **数据本地化**：静态数据预先复制到各单元，避免处理时的远程调用 - **无跨单元同步依赖**：关键交易路径中不存在单元间的同步依赖 - **区域边界**：单元不跨多个区域，所有组件保持本地 这种架构虽增加了管理复杂度，但显著降低了故障影响范围，提升了系统韧性、降低了延迟，并支持通过增加独立单元来扩展处理能力。对于任务关键型支付系统，收益远超成本。

评论摘要
主要讨论点：美国运通(Amex)的分布式支付系统架构设计 不同观点： • **技术认可派(physix)**：设计理念不错，通过事后对账和追回流程换取更高可用性是合理取舍。但指出全局路由器状态同步存在潜在问题，可能因路由信息过时导致请求被发送到错误的cell，且文章未说明路由器自身的高可用方案。 • **用户体验批评派(badlibrarian, llmslave)**：质疑Amex实际技术能力，列举糟糕用户体验(过度的欺诈检测导致卡被封、繁琐的身份验证)。认为公司价值主要在品牌而非技术，系统表面光鲜实则落后。 • **技术怀疑派(neerajsi, jeremycarter, kev009)**：对架构细节提出质疑——cell故障时如何保证持久性、是否会回滚已完成的支付。有人认为这类分布式方案相比大型机部署更混乱，也有人直接表示设计并无新意。 • **调侃派(rekttrader, toast0)**：用加密货币和PS3 Cell处理器等类比进行讽刺性评论。 补充讨论：核心争议在于该架构是否真正先进可靠，以及理论设计与实际用户体验之间的巨大差距。

文章摘要

作者从GNU stow迁移到chezmoi来管理dotfiles配置文件。Stow使用符号链接方式，在多台设备上维护时容易出现冲突和同步问题。Chezmoi采用复制而非符号链接的方式，将配置文件存储在`~/.local/share/chezmoi`源目录中，通过`chezmoi add`添加文件、`chezmoi apply`应用更改。这种方式让配置变更更可控，避免了意外修改。作者用它管理三台Mac（工作MacBook Pro、个人MacBook Air和Mac Mini服务器）的shell配置、git配置、终端配置和AI代理技能文件等，通过模板和脚本实现跨设备的差异化配置。

评论摘要
主要讨论点：dotfiles（配置文件）管理工具的选择和使用体验 不同观点： • **GNU Stow 阵营**：认为 Stow 简单够用，但也承认其符号链接的双向特性存在问题——每次编辑都会直接写入 git 仓库。有用户通过精心设计文件结构（如将本地配置分离到不被追踪的文件）来规避这个问题，将双向特性视为功能而非缺陷。 • **Chezmoi 支持者**：认为 Chezmoi 是社区宠儿，功能强大（支持模板、按机器配置、秘密管理）。配合 mise 工具可以用 2-3 条命令快速配置新机器。但也有人觉得其模板和文件命名规范不够直观，工作流需要适应（常忘记先调用 `chezmoi edit`）。 • **Nix/Home Manager 进阶派**：认为 Chezmoi 只是过渡方案，最终应该升级到 Nix——"既然都爬到山顶附近了，为什么不登顶？"可以声明式管理跨平台（macOS/Linux）配置。 • **极简主义者**： - 自己手写 POSIX shell 脚本（6 年未变），追求完全理解和掌控 - 直接用 Git 仓库 + 符号链接 + Fossil，"低技术、低戏剧性" - 用 rsync 同步整个家目录，视笔记本文件为临时性 • **其他工具倡导者**：yadm（轻量简洁）、Syncthing（自动实时同步 git 目录）、Ansible（重建整个桌面环境） 补充讨论：社区对工具复杂度有分歧——有人认为 Git 仓库就够了（可能是对 git 不够熟悉），有人则认为需要更强大的功能；Atuin 也被提及但未详细讨论。
