cppyy: Automatic Python-C++ Bindings

作者: gjvc | 评分: 33 | 评论数: 4 | 发布时间: 2025-07-16 12:39
文章摘要

cppyy 是一个自动的 Python-C++ 绑定生成工具，能够在运行时实现 Python 与 C++ 的互调，支持跨语言调用、延迟加载、模板实例化、异常映射等功能。它基于 C++ 解释器 Cling，无需语言扩展或手写代码，支持大型 C++ 项目，并能无缝集成如 Boost 等复杂 C++ 库。cppyy 适用于 CPython 和 PyPy，具备高性能，支持 STL、回调和跨继承等特性，简化了 C++ 库在 Python 中的使用。通过预编译头文件和动态加载等技术，cppyy 可以处理包含大量类和代码的 C++ 项目。

评论摘要
主要讨论点：Cppyy工具的适用性、性能及其在项目分发中的影响 不同观点： • [rich_sasha] 认为 cppyy 可能是一个 scipy.weave 的替代品，但对其能否真正取代 scipy.weave 持怀疑态度。他指出，cppyy 通过 Cling 解释 C++ 代码，而不是生成真正的二进制文件。他还提到文档中缺乏与 CPython3 对比的性能基准测试，且现有的基准测试主要关注 C++ 包装的开销，而非与 Python 实现的直接比较。虽然某些情况下速度接近，但这些测试较为陈旧（2018年），可能不再适用。 • [actinium226] 关注 cppyy 在项目分发中的实际问题，特别是如果使用 cppyy 的项目打包成 pip 包，是否需要用户安装 C++ 编译器。他质疑 cppyy 是否自带编译器，或者是否会给终端用户带来额外的安装负担。 • [ashvardanian] 提供了一个实际应用案例，展示了如何通过 cppyy 使用 C++ 内核实现某些实验性功能（如相似性度量和 kNN 数据结构），并与 Numba（Python）和 PeachPy（x86 汇编）进行对比。他提供了一个 GitHub 链接，展示了一个具体项目的实现方式，为 cppyy 的实际应用提供了参考。 • [bogeholm] 的评论较为随意，没有深入讨论技术细节，只是提到了项目名称让他联想到 BBBQ 和 BYOBB，可能是在调侃项目名称的趣味性。 补充讨论： • rich_sasha 强调了对 cppyy 和 CPython3 性能进行对比的必要性，尤其是基准测试中 I/O 操作的影响以及缺乏 Python 原生实现对比的问题。 • actinium226 提出的分发问题引出了 cppyy 是否依赖外部编译器的重要问题，这对于实际项目应用有很大影响。 • ashvardanian 提供的实际案例为 cppyy 的应用场景提供了具体参考，展示了其在处理复杂计算任务中的潜在优势。 争议焦点： • cppyy 是否能完全替代 scipy.weave，特别是在性能和易用性方面。 • 使用 cppyy 项目的分发问题，尤其是对终端用户的环境要求。 • 现有性能基准测试的有效性和全面性。

AWS open-sourced Postgres active-active replication extension

作者: ForHackernews | 评分: 88 | 评论数: 2 | 发布时间: 2025-07-16 09:15
文章摘要

**pgactive** 是一个 PostgreSQL 扩展，用于实现 **active-active（双活）数据库复制。这种复制方式允许多个数据库实例同时接受写入操作，并相互复制数据，适用于多区域高可用性、减少写入延迟、蓝绿部署等场景。与传统的 active-standby 模式不同，active-active 没有单一的数据来源，因此需要处理数据冲突和复制延迟等问题。该项目利用 PostgreSQL 的逻辑复制功能，并通过扩展增强其对双活复制的支持。项目基于 Apache-2.0 许可证，目前有 426 个星标和 19 个分支。

评论摘要
主要讨论点：AWS推出的pgactive项目及其用途和实现机制 不同观点： • [zknill的观点] - 认为pgactive项目使用了Postgres逻辑复制（Postgres Logical Replication）在不同的Postgres实例之间共享更改。 - 冲突解决机制是基于时间戳的"最后写入为准"（last-write-wins）。 - 冲突事务会被记录到一个特殊的表（pgactive_conflict_history），以便用户可以查看历史记录并进行手动解决。 - 提供了相关文档链接以支持其观点。 • [everfrustrated的观点] - 对AWS开发pgactive项目的动机表示困惑，认为该项目在其产品线中没有明显的应用场景。 - 指出AWS的RDS使用块复制（block replication），Aurora使用自己的SAN复制层，因此pgactive似乎并不符合这些现有产品的技术架构。 - 提出DMS（数据库迁移服务）可能是pgactive的一个潜在应用场景，但并不确定。 补充讨论： - pgactive项目的实现细节，特别是其依赖的Postgres逻辑复制机制和冲突解决策略，是[zknill]关注的重点。 - [everfrustrated]对pgactive的实际应用场景提出质疑，尤其在AWS已有其他复制技术的情况下，对AWS为何开发该项目表示不解。 - 争议的焦点在于pgactive的实际应用价值和AWS开发该项目的动机。

文章摘要

2025年7月14日，Cloudflare的1.1.1.1解析服务从21:52 UTC到22:54 UTC发生全球性中断，影响大部分用户，导致许多互联网服务不可用。中断原因是由于遗留系统配置错误，错误地将1.1.1.1解析服务的IP地址包含在一个未上线的地域限制服务中。当该服务配置被修改时，触发了全球网络配置刷新，导致1.1.1.1解析服务的IP前缀被错误撤回。6月6日引入的配置错误在无影响的情况下潜伏至事故发生。事故于21:52开始，22:01检测到问题并开始修复，22:20部署修复措施，最终恢复服务。此次中断并非攻击或BGP劫持所致。

Tilck是一个教育性的小型单体kernel，旨在与Linux在二进制级别兼容，目前支持i686和RISCV64架构。它允许运行Linux程序，如BusyBox，而无需自定义应用程序，这使得它成为研究内核模式的理想选择。Tilck并非旨在取代Linux，而是利用其兼容性来验证自身的正确性。未来计划包括支持嵌入式系统、网络和存储功能，并可能适配ARM架构和无MMU的CPU。Tilck不适合作为桌面操作系统，因为其目标并非多用户服务器或桌面环境，而是嵌入式系统和实时应用场景，如与FreeRTOS或Zephyr竞争。
