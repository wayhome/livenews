Million Times Million

作者: susam | 评分: 13 | 评论数: 2 | 发布时间: 2025-07-09 11:49
文章摘要

本文讨论了长尺度与短尺度两种大数命名系统。作者小时候通过一本旧字典了解了长尺度系统，其中每增加一个前缀表示将百万自乘一次，如百万自乘一次是十亿，自乘两次是万亿。然而，长大后，作者发现当今世界主要使用短尺度系统，其中百万自乘一次是万亿，自乘两次是 quintillion。短尺度系统通过每次增加一千的倍数来命名大数，如百万是千自乘一次，十亿是再乘一次，万亿则是再乘一次。尽管长尺度系统更直观，但短尺度系统在技术、金融等领域更为普遍。作者最终适应了短尺度命名法，但长尺度的记忆仍存于心中。

评论摘要
主要讨论点：不同用户对数值表示体系（长尺度与短尺度）以及老式计算设备的讨论 不同观点： • [HocusLocus] 分享了自己小时候使用老式计算器（Olivetti divisumma 24）的经历。他提到，当输入过大的数值（如百万乘以百万）时，计算器进入了无法自行恢复的机械循环，最终他的父亲通过手动拆解设备解决了问题。这一观点主要聚焦于老式机械计算设备的局限性和意外操作后果。 • [flysand7] 则对不同国家使用的数值尺度体系表示好奇，尤其是长尺度和短尺度之间的差异。他指出在俄语中使用短尺度，但没有"billion"一词，而是用"milliard"。该观点关注的是不同语言和国家在数值表示上的差异及其在翻译中的注意事项。 补充讨论： • HocusLocus 的评论中提到了机械计算器的脆弱性和物理干预的必要性，反映出早期计算设备在处理大数时的局限性。 • flysand7 提到了数值体系在不同语言中的转换问题，特别是“milliard”与“billion”之间的翻译差异，暗示了在跨文化交流中对数值理解的重要性。 • 争议焦点并不明显，但可以认为不同国家和语言对数值体系的采用和翻译差异可能导致混淆，这需要在跨文化交流中加以注意。

Ruby 3.4 frozen string literals: What Rails developers need to know

作者: thomas_witt | 评分: 56 | 评论数: 6 | 发布时间: 2025-07-06 09:58
文章摘要

Ruby 3.4开始逐步引入冻结字符串字面量，默认情况下现有代码不受影响，但可以通过启用弃用警告来提前准备未来的变化。变化分为三个阶段：3.4版本引入可选警告，3.7版本默认启用警告，4.0版本默认冻结字符串字面量。冻结字符串可以带来性能提升，如减少垃圾回收和内存使用。开发者需要关注依赖的gem可能出现的警告。要查找问题，可以在开发环境中启用警告，并使用测试套件进行检查。常见需要修改的模式包括字符串构建和就地修改等。对于新代码，建议直接编写适应冻结字符串的代码，而对于现有应用则无需急于移除魔法注释。

评论摘要
主要讨论点：编程语言在字符串可变性及类型系统上的演变和优化，以及动态类型语言是否会借鉴静态类型语言的优化特性。 不同观点： • [_flux] 提到 OCaml 也曾从可读写的字符串过渡到只读字符串，并引入了 Buffer 作为可读写的替代方案。虽然过渡有些波折，但最终还算顺利，并指出静态类型检查有助于发现问题。同时提到为了兼容旧代码，提供了一个开关让字符串和 Buffer 可以互换使用。 • [ttoinou] 提出一个更广泛的观点，讨论动态类型语言是否会逐渐引入编译型和静态类型语言的优化特性，并质疑如果 Ruby 一开始就有这些复杂的特性，是否还能成功。他还提到，很多语言最初以简洁的特性吸引开发者，但随着发展逐渐变得与其他大型编程语言相似。 • [teddyh] 指出 Ruby 之前字符串是可变的，甚至默认是可变的，直到最近才改变，并且只有字面量字符串变为不可变。相比之下，Python 一直保持字符串不可变。 • [llamataboot] 对 Python 2 到 3 的过渡经历表示不满，认为虽然字符串不可变能带来性能提升，但过渡过程会带来很多依赖管理的问题，类似于 Python 2 到 3 的过渡痛苦。 • [skywhopper] 对 Ruby 的过渡表示赞赏，认为这是一个经过深思熟虑和有计划的转变，通过多年的可选警告和强制警告来减少对用户的干扰，显示出 Ruby 团队在语言改进上的方法论和细致态度。 补充讨论： • 争议的焦点之一是动态类型语言是否应引入更多类似静态类型语言的特性，以获得更好的性能优化。 • 另一个值得注意的点是编程语言演变中的过渡痛苦，特别是从可变字符串到不可变字符串的变化，涉及到兼容性问题和依赖管理的复杂性。 • 对 Ruby 团队在语言改进上的细致态度有不同评价，部分人赞赏其方法论，而其他人则基于 Python 的经验表示担忧。

Helm local code execution via a malicious chart

作者: irke882 | 评分: 113 | 评论数: 12 | 发布时间: 2025-07-09 05:49
文章摘要

文章描述了Helm中的一个高危安全漏洞（CVE-2025-53547），影响版本<= 3.18.3。当存在恶意构造的`Chart.yaml`和`Chart.lock`文件时，更新依赖项可能导致本地代码执行。如果`Chart.lock`文件被symlink到可执行文件（如`bash.rc`），更新依赖时会将恶意内容写入该文件，导致 unwanted 执行。该问题已在Helm v3.18.4中修复。临时解决方案是确保`Chart.lock`不是symlink。CVSS评分8.5，表示高严重性，需要用户交互但无需特殊权限。

评论摘要
主要讨论点：Helm图表漏洞及其相关技术讨论 不同观点： • [ivan4th] 认为Helm和文本模板引擎生成YAML的思路本质上是有问题的，特别是需要手动处理空格和换行符等问题，将其与Lisp语言的“括号计数”问题相比较，表达了对Helm使用体验的不满。 • [yelirekim] 详细解释了漏洞的工作原理，描述了攻击者如何通过恶意Chart.yaml文件和符号链接进行攻击，最终导致任意文件写入和代码执行。 • [codebastard] 质疑该漏洞的实际威胁，认为如果攻击者已经有权限访问文件系统并在Helm仓库中放置恶意代码，那么问题可能更加严重，而不仅仅是Helm自身的问题。 • [TheDong] 对漏洞描述中的一些技术细节感到困惑，特别是关于`Chart.lock`文件如何成为符号链接的问题，并提出修复措施应该针对所有可能的符号链接，而非仅限于`Chart.lock`。 • [Sjoerd] 关注攻击场景和安全边界，提出了一系列关于攻击者如何让受害者运行恶意图表的问题，并质疑Helm是否通常以特权用户身份运行。 • [mkagenius] 提到类似工具要求shell访问权限的问题，认为允许LLM通过shell执行生成图表等操作是一个坏主意。 • [agys] 误以为讨论的是与音乐合成器相关的内容，与技术漏洞讨论无关。 • [xyst] 认为该漏洞很有趣，并讨论了个人防护措施，例如使用Nix管理配置文件，以及设置只读分区等方法来预防潜在攻击。 • [sugarpimpdorsey] 对YAML作为配置文件格式提出批评，认为YAML引发多次远程代码执行（RCE）漏洞，反映了其设计上的缺陷。 • [quotemstr] 讽刺地提到内存安全语言也会出现安全漏洞，暗示即使使用这些语言也不能完全避免安全问题。 • [qxfys] 关注LLM如何自动发现此类漏洞，询问社区是否有相关经验。 补充讨论： • 争议的焦点在于该漏洞的实际威胁程度，以及Helm在处理符号链接和文件写入时的安全性。 • 部分讨论者对漏洞的技术细节和攻击场景存在疑问，特别是如何利用该漏洞进行实际攻击以及修复措施的有效性。 • 讨论中还涉及对YAML格式本身的批评和对LLM自动发现漏洞能力的兴趣。

Most RESTful APIs aren't really RESTful

作者: BerislavLopac | 评分: 86 | 评论数: 33 | 发布时间: 2025-07-09 07:04
文章摘要

这篇文章主要讨论了Roy Thomas Fielding的论文《架构风格与基于网络的软件架构设计》，该论文介绍了代表性状态转移（REST）架构风格，旨在设计可扩展、高性能和可维护的网络系统，特别是Web服务。Fielding分析了多种网络架构风格的优缺点，强调REST专注于可扩展性、简洁性和适应性。他指出，REST是一种提供原则和约束的架构风格，而非具体的技术实现，如HTTP动词或CRUD风格API。 文章澄清了关于REST的常见误解，例如REST不等于CRUD，资源也不仅仅是持久化实体。Fielding特别强调了超媒体作为应用状态引擎（HATEOAS）的重要性，认为没有超媒体控制的API不能称为RESTful。HATEOAS通过动态发现链接减少客户端与服务器的耦合，提高系统的可演化性。 此外，文章解释了REST中的“资源”概念，指出资源是信息的抽象映射，而非具体的服务器实体，URI的语义由创建者定义，而非客户端或服务器需要理解的内容。

评论摘要
主要讨论点：REST和RESTful API的实际应用及其与理论定义的差距 不同观点： • cjpearson认为，REST API这个术语已经发生了语义扩散，实际使用中与Fielding论文中的原始定义不符。他指出，现代所谓的"REST API"通常返回JSON，使用CRUD操作映射到HTTP方法，并且在状态码使用上常常存在争议。他主张要么坚持原定义，要么接受现实，按常用理解使用该术语。 • mixedbit分享了自己的经验，指出他在深入研究Fielding的论文后发现，真正的REST在实际应用中并不总是有用。他认为Fielding的论文没有提供完整的自发现API构建方案，最终实现的自发现API往往缺乏客户端代码重用，且与特定应用的API无异。他还提到，REST的目标与良好的用户体验可能不兼容。 • _heimdall认为，REST和HATEOS在第三方作为API消费者时更有意义，而对于特定前端应用的后端API，REST的成本往往超过其收益。 • salmonellaeater指出，REST API设计适用于用户通过代理（如浏览器）导航和交互的场景，而不是针对特定Web应用的API设计。这类API更适合公开信息和交互的政府门户或开放数据项目。 • dwaltrip质疑HATEOAS的实用性，认为没有真正的客户端能够利用自动发现的API，并质疑这种客户端的必要性。 • Scarblac强调，UI设计师需要对页面外观进行详细控制，而RESTful API的自发现特性与此需求不符。 • nchmy建议通过更易懂的资源学习REST相关概念，并提供了一些参考链接。 • sublinear认为，通过引用schema定义（如JSON Schema）实现API动态导航在现实中存在问题，并质疑是否有必要在JSON响应中包含复杂的链接信息。 • osigurdson幽默地指出，集体忽视了Fielding的论文，只是喜欢使用"REST"这个词来描述HTTP/JSON的任意应用。 • makeitdouble支持实用主义，建议避免使用"RESTful"这个术语，而改用"HTTP based APIs"。 • pradn理解了Fielding的REST原则，认为其核心在于动态发现和抽象实体，允许API以更动态和通用的方式使用。 • bravesoul2反对REST和GQL，认为RPC风格更实用，强调应根据实际需求选择API风格，而非强制适应某种风格。 • 0x445442认为，REST在实践中只是通过JSON通信的分布式功能调用，开发和维护 nightmare。 • layer8认为，文章没有提供有力论据支持Fielding的REST定义应被视为标准，并指出该定义对非交互式客户端不适用，这也是其未被广泛采用的原因。 补充讨论： • cowsandmilk提到其所在公司将实际操作称为HTTP绑定，反映了业界对REST定义的实际应用差异。 争议焦点：REST的理论定义与实际应用的差距，以及HATEOAS的实用性和必要性。
