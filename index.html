The benefits of trunk-based development

作者: gpi | 评分: 25 | 评论数: 7 | 发布时间: 2025-07-23 04:50
文章摘要

文章主要讨论了基于主干开发（trunk-based development）的优势，并认为它是优于功能分支开发的交付方式。尽管持续集成实践隐含了基于主干开发，但这一方法仍存在争议。文章指出，微软、Netflix、谷歌等公司均采用基于主干开发，甚至在谷歌的大规模开发中也是如此。 基于主干开发通过促进团队协作和集体代码所有权，提升了代码质量。它减少了低信任环境，创建了安全空间，避免指责个人，而是团队共同负责质量。频繁提交代码到主线，能够更早发现和解决问题，从而内建质量，而不是后期测试。 该方法还支持按需生产发布，减少上市时间，提高交付速度。更频繁的部署加速了反馈，提升了用户满意度，并减少了在制品（WIP），从而降低了开发周期时间。文章总结，基于主干开发不仅提升了技术质量，还创造了经济优势。

评论摘要
主要讨论点： trunk-based development (TBD) 与 feature branch 开发模式的优劣对比，以及 Pull Request (PR) 的作用和意义。 不同观点： • **JimDabell 的观点**：PR 不仅仅是关于信任问题，它还是团队成员之间互相学习和保持代码库一致性的重要工具。虽然 PR 在开源社区中用于验证外部贡献有其合理性，但在企业环境中，PR 可能意味着团队对代码库没有完全的贡献权。此外，未合并的代码相当于“库存”，会占用投资而无法产生收益，减少在制品（WIP）可以缓解这个问题。 • **fjfaase 的观点**：基于个人经验，feature branch 模式会导致开发延迟、临时解决方案、合并冲突和引入 bug 等问题，开发速度因此减慢且代码质量未见提升。相比之下，trunk-based development 更加高效。 • **devjab 的观点**：认为 trunk-based development 是唯一合理的开发模式，feature branch 和其他“安全措施”只是不信任团队能力的表现。开发速度和质量更多取决于团队的管理和合作能力，而不是具体的开发策略。如果团队不能在任何时候部署代码，那代码就不应该被认为是准备好的。 • **Ozzie_osman 的观点**：对 trunk-based development 的极端形式表示怀疑，认为 PR 和分支在现代开发中不可避免。PR 如果使用得当，可以促进共享所有权，并确保代码质量和合规性。完全避免分支和 PR 的 TBD 模式在实际操作中可能不切实际。 • **safety1st 的观点**：支持 trunk-based development，特别是在快速迭代的项目中，如 web 应用开发。在这种环境中，正式的工程流程不如快速反馈和持续交付重要。TBD 通过让代码尽早暴露在关键用户面前，帮助快速解决主要问题，尽管小 bug 可能会漏掉。 • **bytefish 的观点**：认为开发模式的选择应根据具体项目、团队和组织结构来定，不应绝对化。对于一些团队来说，feature branch 模式提供了清晰的工作流程，特别是需要维护多个产品版本时。TBD 并不总是适合每个团队或项目。 补充讨论： • **争议焦点**：TBD 与 feature branch 模式的适用性以及 PR 的作用。一些开发者认为 PR 和 feature branch 是必要的质量控制手段，而另一些开发者则认为它们是延迟和复杂性的来源，更倾向于 TBD 的快速迭代和持续交付。 • **其他值得注意的讨论点**：TBD 模式在实际操作中的极端性和可行性，特别是在大型企业或合规性要求较高的行业中。不同开发模式对团队合作、代码质量和开发速度的影响也是讨论的重点。

**wtffmpeg** 是一个命令行工具，利用本地的大型语言模型（LLM）将自然语言描述的视频和音频任务转换为可执行的 **ffmpeg** 命令。其主要特点包括：自然语言界面、本地运行、交互式执行、支持GPU加速、可定制模型等。用户可以通过简单的英文描述完成复杂的 **ffmpeg** 操作，而无需查阅文档或搜索解决方案。工具支持在执行前查看和确认生成的命令，并可根据需要更换不同的LLM模型。安装过程需要配置 **Python 3.8+** 环境和 **llama-cpp-python** 以实现硬件加速，并下载合适的模型文件。使用示例包括视频格式转换、音频提取、创建片段等操作。

评论摘要
