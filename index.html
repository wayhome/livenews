A “frozen” dictionary for Python

作者: jwilk | 评分: 123 | 评论数: 19 | 发布时间: 2025-12-11 09:51
文章摘要

这篇文章介绍了Python社区提出的一项新提案PEP 814，旨在为Python添加不可变的字典类型"frozendict"。主要内容包括： 1. 提案背景：当前Python字典可变性导致并发编程中共享数据存在风险 2. frozendict特性： - 不可变字典类型 - 与常规字典类似但不继承自dict - 可哈希(当所有值都不可变时) - 支持多种创建方式 - 保留键值插入顺序 3. 应用场景： - 提高并发安全性 - 可用于字典键、集合元素等需要不可变对象的场景 4. 讨论情况： - 社区反应总体积极 - 有人建议添加O(1)的原地冻结方法 - 提案已考虑标准库中多处可用frozendict替代dict的情况 该提案旨在提供语言级别的不可变字典支持，增强Python在并发编程中的安全性。

评论摘要
主要讨论点：Python是否应该引入内置的frozendict类型，以及其潜在用途和替代方案。 不同观点： • 支持引入frozendict： - 提供并发安全性，避免字典被意外修改（如[sevensor]和[Strilanc]提到的缓存场景） - 可作为字典键使用（[xamuel]强烈要求此功能） - 已有实际应用案例（[zzzeek]提到SQLAlchemy多年使用优化版frozendict） - 其他语言（C#、Ruby）已成功实现类似功能（[mwsherman]、[ok123456]） • 反对引入frozendict： - 认为现有方案（如MappingProxyType）已足够（[polyrand]） - 质疑其真正的不可变性（[perrygeo]称其是"廉价模仿"，推荐pyrsistent） - 早期核心开发者认为"用处不大且问题复杂"（[pansa2]引述Raymond Hettinger） • 技术性质疑： - 与namedtuple的区分度问题（[sundarurfriend]提出关于有序性/API的困惑） - 性能优化可能性（[drhagen]讨论构造复杂度优化） - 类型系统整合需求（[codethief]期待类似TypeScript的类型推断） 争议焦点： 1. 必要性争议：现有方案（MappingProxyType/pyrsistent）是否已满足需求 2. 设计哲学争议：应实现"完全不可变"（perrygeo主张）还是实用主义方案 3. 使用场景争议：xamuel强调的"字典作为键"需求是否普遍重要 补充讨论： - 历史认知差异（[bilsbie]出现曼德拉效应） - 跨语言比较成为论据（C#/Ruby/TypeScript被多次引用） - 标准库引入可能推动底层优化（JIT相关讨论）

The Cost of a Closure in C

作者: ingve | 评分: 119 | 评论数: 15 | 发布时间: 2025-12-11 07:21
文章摘要

本文主要讨论了C和C++中闭包（closures）的性能问题及其设计缺陷，以及如何解决这些问题。闭包是一种编程语言构造，它包含了与输入参数和返回值无关的数据和指令。文章首先解释了闭包的概念，并指出几乎所有现代编程语言都支持闭包，但C和C++由于其“底层”特性，闭包的设计并不理想。 文章通过一个具体的例子（使用`qsort`函数时如何传递额外数据）展示了闭包在C语言中的常见问题，如静态变量的共享和线程安全问题。针对这些问题，文章列举了四种主要的解决方案： 1. 重新实现函数以接受用户数据指针（如`qsort_r`或`qsort_s`）。 2. 使用GNU嵌套函数直接引用所需数据。 3. 使用Apple Blocks直接引用所需数据。 4. 使用C++ Lambda表达式和一些额外代码来引用所需数据。 每种解决方案都有其优缺点，文章简要介绍了它们的实现方式，并指出了设计上的局限性。

主要讨论点：[C和C++中闭包和lambda实现的性能差异、静态变量用法争议、函数指针和闭包的实现方式] 不同观点： • **静态变量用法争议** - [unwind]认为作者对C中`static`变量的解释有误，指出在全局作用域中`static`仅控制变量可见性而非持久性，而在函数内部才影响持久性。 - 争议焦点：作者是否混淆了`static`的作用域和持久性语义。 • **闭包性能与实现** - [Rochus]强调现代C++ lambda通过编译时优化（如扁平化成员访问）优于动态方案，并指出`std::function`因值拷贝语义导致递归性能问题，而`std::function_ref`无此问题。 - [mgaunard]质疑测试方法，认为除分配操作外，所有lambda选项在可内联时性能应接近，差异源于内联和虚函数优化。 - [nesarkvechnep]选择C++而非Rust，因其支持静态模板lambda传递C函数指针。 • **C的闭包扩展方案** - [sirwhinesalot]主张GNU扩展的局部函数（类似C++按引用捕获的lambda）最适合C，因其直接调用且无需类型擦除。 - [RossBencina]提出"stateful函数"概念，类似`static`但状态实例化，但承认可能破坏分离编译。 - [groundzeros2015]推荐线程局部变量+包装函数解决闭包状态传递。 • **其他语言对比** - [trgn]批评JS社区过度使用hooks导致运行时膨胀，暗示应借鉴低级语言的闭包设计。 - [psyclobe]支持C++的lambda实现，认为其最终胜出。 补充讨论： • [Progge]对C代码中复杂的参数解析提出简化建议，引发对代码风格的讨论。 • [ddtaylor]提到使用GNU扩展的蹦床函数，展示C中非标准闭包实践。 • [keymasta]指出文章拼写错误，侧面反映对细节的关注。
