Java Virtual Threads Ate My Memory: A Web Crawler's Tale of Speed vs. Memory

作者: dariobalinzo | 评分: 21 | 评论数: 5 | 发布时间: 2025-05-29 13:08
文章摘要

文章讲述了作者在构建一个网页爬虫时，从使用平台线程（Platform Threads）切换到虚拟线程（Virtual Threads）以提升性能的经历。最初，作者使用传统的平台线程和固定线程池来处理URL，尽管速度尚可，但他好奇虚拟线程能否进一步提高性能。切换到虚拟线程后，URL处理速度显著提升，但很快程序因`OutOfMemoryError`崩溃。 虚拟线程本应用于解决I/O阻塞问题，因其轻量级特性可以支持更多并发操作。然而，由于虚拟线程创建不受限，导致内存被过度消耗，最终引发内存溢出错误。作者通过分析问题，指出在使用虚拟线程时需要更精细的控制，以避免性能提升同时造成内存压力。 文章最后总结，软件开发中每个工具都有权衡，解决问题的同时也可能引入新问题，开发者需平衡性能、安全性和可维护性。

评论摘要
主要讨论点：虚拟线程（Virtual Threads）在并发管理、资源控制和开发者权衡中的应用和挑战 不同观点： • koito17 认为，在没有背压（back-pressure）管理的情况下，程序会不断消耗内存，最终导致资源耗尽。他质疑“普遍异步”（pervasive async）的开发思维，特别是在有真实线程的环境中，转向虚拟线程和异步编程会放弃操作系统成熟的调度器和背压处理机制。开发者需要自行负责避免缓冲区膨胀问题。他还提到 Clojure 的 core.async 通过设置通道限制来处理背压，避免无声的资源耗尽问题。 • fjasdfwa 则认为，这是开发者在节省内存和简化代码之间的一种权衡。如果要节省内存，开发者需要使用回调、promise 链或 async-await 等机制，但这又会带来样板代码过多的抱怨。他还提到 Zig 可能提供了一种兼顾两者的方案，但需要 Zig 专家确认。 • geodel 分享了他的实际经验，他通过使用阻塞队列来限制并发任务数量，从而避免了内存过度消耗的问题。他发现将虚拟线程数量控制在并发调用外部资源的 100 倍左右时，吞吐量表现最佳。 • swsieber 引用了官方文档，强调虚拟线程虽然行为上与平台线程相同，但不应代表相同的程序概念。他指出，限制并发性应该使用专门的构造，如信号量（Semaphore）类，而不是线程池。他解释了虚拟线程和任务队列之间的等价性，帮助开发者充分利用虚拟线程。 补充讨论： • 争议的焦点在于虚拟线程是否能够有效管理资源和背压。koito17 强调了背压管理和开发者责任，而 geodel 和 swsieber 则提供了实际经验和官方文档支持，展示了如何通过适当的设计和构造来解决这些问题。 • fjasdfwa 提出的开发者权衡问题也是一个重要的讨论点，反映了在不同编程范式之间进行选择的实际困难和权衡。
