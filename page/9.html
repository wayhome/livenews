LLMs Bring New Nature of Abstraction

作者: hasheddan | 评分: 58 | 评论数: 10 | 发布时间: 2025-06-25 10:55
文章摘要

Martin Fowler探讨了生成式AI，尤其是大型语言模型（LLMs），对软件开发的深远影响。他认为，LLMs带来的变革堪比从汇编语言到高级编程语言的转变，但这次不仅是抽象层次的提升，还引入了非确定性工具的编程问题。过去，高级语言（如Ruby）使编程变得更加直观和高效，但本质上仍是以传统方式与机器对话。而LLMs的非确定性特性意味着，使用提示词与机器交互将带来根本性变化，每次输出的结果可能不同，无法通过版本控制确保一致性。这种非确定性是软件开发历史上前所未有的，虽然带来挑战，但也蕴含着尚未被完全理解的机遇，令人兴奋。

评论摘要
主要讨论点：围绕LLM（大型语言模型）和自然语言编程的讨论，包括确定性、自然语言作为编程语言的可行性以及LLM的应用前景。 不同观点： • **引用历史观点反对自然语言编程的 hype**：bwfan123 指出，应该引用 Dijkstra 多年前关于“自然语言编程愚蠢性”的文章，该文章反对“英语是一种编程语言”的炒作。这表明对自然语言编程持怀疑态度，认为这并非新概念且早已有批评。 • **LLM 的非确定性及其解决方案**：perching_aix 认为，LLM 的非确定性问题可以通过固定随机种子或使用本地模型来解决，而非远程服务。他们通过实验展示了如何获得一致的模型响应，强调LLM并非固有非确定性。 • **拒绝为未知的利益放弃确定性**：ptx 反对为了未具体说明的潜在好处而放弃确定性，认为不应轻易妥协于当前的非确定性特性。 • **自然语言缺乏编程所需的精确性**：agentultra 认为自然语言不够精确，无法用于编程，怀疑人们对LLM的兴奋点在于自动化而非真正的语言精确性。 • **改变对LLM和软件生成的理解**：abeppu 建议，应专注于让模型理解编译和执行，而不仅仅是生成代码。他们提出通过训练模型理解代码的中间表示和执行行为来提高代码生成的可靠性。 • **LLM 是否生成高级语言代码或直接生成字节码的讨论**：dingnuts 提问，如果LLM是新一代编译器，为什么不直接生成字节码而要生成高级语言代码。 • **LLM 确定性的技术细节**：sgt101 指出，LLM 是确定性的，但在特定硬件（如NVIDIA GPU）和优化开启时可能出现非确定性结果，强调这是选择问题。 补充讨论： • **对LLM革命性的质疑**：w10-1 质疑那些基于他人经验就宣称LLM带来根本性变革的观点，认为这些表达未经充分论证。 • **结合TLA+和LLM的抽象层次**：UltraSane 提出，将TLA+模型与LLM结合，生成代码，是实现有用抽象的终极方式。 • **讨论重复**：bgwalter 指出，该讨论是另一个正在下沉的重复讨论。 争议焦点： • **自然语言编程的可行性**：一方认为自然语言不够精确，无法替代传统编程语言；另一方则对LLM带来的新可能性持乐观态度。 • **LLM的非确定性及其影响**：一方认为LLM的非确定性可以通过技术手段解决，另一方则认为不应为此放弃确定性。 这些讨论揭示了对LLM及其在编程中应用的不同看法，包括技术实现、潜在优势和局限性。

c4wa – C compiler for Web Assembly

作者: 90s_dev | 评分: 86 | 评论数: 9 | 发布时间: 2025-06-24 15:52
文章摘要

**c4wa** 是一个将 C 语言的简化子集转译为 Web Assembly (WASM) 的编译器。其主要特点包括：生成精简高效的 WASM 输出，无额外嵌入库或不必要的开销，兼容任何 WASM 运行时，无需依赖 JavaScript 或 Node。它利用 WASM 的线性内存模型，支持动态内存分配，并能输出文本格式的 WAT，便于理解和手动编辑。c4wa 支持 C 语言的基本特性，如循环、条件、指针、动态内存分配等，且可使用外部 C 预处理器。其目的是在高级语言编写和底层 WASM 控制之间找到平衡，生成的 WAT 文件类似手写代码。该工具需要 Java 11 及以上版本，并可在任何安装 Java 的平台运行。生成的 WASM 文件独立于平台。

评论摘要
主要讨论点：C语言到WebAssembly（Wasm）编译工具和语言特性的支持对比，以及对编译器生成代码的信任和优化问题。 不同观点： • **对c4wa依赖Java 11的批评**：用户lioeters指出c4wa需要Java 11或以上版本，认为如果它能用C的子集编写并编译到Wasm会更好。这反映了对依赖Java环境的不满，并希望工具链更精简和原生。 • **对Emscripten优化问题的讨论**：用户comex认为在比较Emscripten和c4wa时，原文作者忽略了开启优化选项（-O），导致生成的代码质量差。comex指出，开启优化后，Emscripten的输出可以与c4wa媲美。 • **使用clang编译到Wasm的例子**：用户s-macke提到clang通过`--target=wasm32`选项可以很好地编译到Wasm，并生成较小的二进制文件。他提供了自己项目作为例子，展示clang在这方面的能力。 • **对C99特性的支持问题**：用户teo_zero对c4wa不支持C99特性表示不满，但同时指出至少它不需要K&R函数语法，这算是一个小的优点。 • **对机器生成代码的信任问题**：用户keysdev认为机器生成代码复杂化是普遍现象，比如nim的客户端JS代码。他提出问题是：是否应该信任编译器生成的代码，还是手写更简洁的代码。 • **对c4wa项目活跃度的关注**：用户Anduia提到c4wa最近一次提交是在2022年1月29日，暗示项目可能缺乏持续的开发和维护。 • **Zig语言对Wasm的支持**：用户pyrolistical提到Zig也能编译到独立的Wasm模块，这提供了另一种选择。 • **对自由Wasm模块工具的需求**：用户apitman认为更多对自由Wasm模块的支持是有益的。他正在开发一个自定义Wasm应用运行时，不希望实现完整的Emscripten或WASI API表面，希望有更多工具支持使用C/Rust的标准库函数，并定义自己的API来处理主机/模块接口。 补充讨论： • **对volatile和Wasm内存模型的讨论**：用户b0a04gl指出C中的volatile关键字用于阻止重排和强制内存读取，但在Wasm的单线程环境下，编译器保留了volatile加载，但运行时并不保证顺序，这导致了一些语义上的变化。 争议焦点： • **对不同工具链生成代码质量的争议**：主要是c4wa与Emscripten在代码优化和生成质量上的对比，特别是优化选项对结果的影响。 • **对机器生成代码的信任与手写代码的取舍**：讨论了现代编译器生成复杂代码的现象以及开发者是否应信任这些代码，还是追求手写简洁代码。

The right thing for the wrong reasons: FLOSS doesn't imply security (2022)

作者: transpute | 评分: 4 | 评论数: 0 | 发布时间: 2025-06-29 01:01
文章摘要

本文探讨了开源软件（FLOSS）的源代码可用性与安全性之间的关系，强调源代码的可用性并不直接等同于软件的安全性。作者指出，虽然源代码对于用户自由至关重要，但许多人以错误的理由支持源代码公开，例如认为源代码是确保软件透明度和安全性的唯一途径。实际上，源代码描述的是软件的设计意图，而非其实际行为，漏洞发现通常通过逆向工程和模糊测试完成，而非依赖源代码。源代码在安全修复过程中有助于理解问题，但对漏洞的发现和初步分析并不必需。此外，编译器优化、操作系统问题和代码混淆等因素可能使源代码无法准确反映程序的真实行为。作者总结，源代码的不可用并不意味着不安全，其公开也不自动保证安全性。

C++ Seeding Surprises (2015)

作者: vsbuffalo | 评分: 32 | 评论数: 5 | 发布时间: 2025-06-25 16:11
文章摘要

文章主要讨论了在C++11中正确初始化随机数生成器（RNG）的挑战，尤其是种子的质量问题。C++11提供了`std::seed_seq`来改善种子数据，但其设计存在缺陷，可能将高质量的种子数据“变差”。文章指出，使用单一32位整数作为种子是非常不可取的，因为它仅能提供约40亿种可能的初始状态，容易被预测和攻击。 更糟糕的是，这种方法还可能导致偏差，影响随机数的均匀分布。例如，在大规模应用（如Twitter应用）中，使用低质量种子可能导致大量设备生成相同的随机数序列，造成严重问题。尽管一些脚本语言（如JavaScript、Python）依赖操作系统提供高质量随机种子，C++的`std::random_device`访问操作系统随机性却不容易直接用于初始化RNG，因为C++生成器仅接受`std::seed_seq`或单个整数作为种子。 总之，文章强调了在C++中正确初始化RNG的困难，并警告开发者避免使用低质量种子。
