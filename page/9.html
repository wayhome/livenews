文章摘要

Ferron 是一个用 Rust 编写的高性能、内存安全的Web服务器。它具有以下特点：高性能（利用Rust的异步能力）、内存安全、可扩展性（模块化架构）和安全性（注重安全实践和并发处理）。主要组件包括： - **ferron**：主服务器。 - **ferron-passwd**：用于生成用户条目和密码哈希的工具。 目前，Ferron 仍在开发中，可通过克隆代码库并使用 Cargo 构建和运行： ```bash git clone https://github.com/ferronweb/ferron.git cd ferron cargo build -r cargo run -r --bin ferron ``` 服务器配置可参考 Ferron 文档。Ferron 使用 MIT 许可证，并欢迎社区贡献。

You Don't Have Time Not to Test

作者: attila226 | 评分: 39 | 评论数: 15 | 发布时间: 2025-04-02 23:33
文章摘要

文章《You Don’t Have Time Not to Test》由Doug Donohoe撰写，讨论了软件测试的重要性。尽管许多工程师认为在紧迫的项目进度下没有时间进行测试，作者强调测试实际上是必不可少的工具，而不是沉没成本。测试能帮助确保代码质量，加速团队开发速度，并防止未来可能出现的问题。作者将缺乏测试比作在陌生城市驾驶没有GPS导航，容易迷失方向。他进一步解释了测试的核心在于验证代码是否完成了预期功能，无论这是通过单元测试还是集成测试。测试可以迅速重复执行，帮助团队在早期发现和解决问题，避免日后更严重的错误。最终，作者认为即便在项目初期，放弃测试是一个错误，选择不测试实际上是选择了更大的风险。

评论摘要
主要讨论点：软件测试的价值和实践 不同观点： • **测试是最佳生产力工具**：[gcp123]、[simonw]和[angarg12]认为测试是提升开发效率的关键。他们强调了测试带来的长期收益，如提高代码可维护性、减少回归错误以及加速开发进程。尤其是[angarg12]通过实际案例展示了测试如何帮助团队更快发现问题并提高发布信心。 • **测试的类型和策略应根据具体情况调整**：[ashishb]和[roland35]提出，不同类型的代码应采用不同的测试策略。例如，算法代码适合单元测试，而集成测试更适合服务之间的“粘合代码”。[roland35]还提到在硬件开发中，测试可以帮助模拟难以重现的状态。 • **测试的执行和工具挑战**：[PaulHoule]和[Scene_Cast2]指出了在特定框架（如React）或机器学习项目中编写测试的实际困难。例如，React测试库的局限性和机器学习模型测试的复杂性使得测试编写耗时且繁琐。 • **测试的时机和优先级争议**：[wewewedxfgdf]和[jt2190]认为测试的必要性取决于项目阶段和公司背景。对于初创公司，优先任务是推出可用产品，而不是编写测试。而[jt2190]质疑在当前测试不完善的情况下，增加新测试是否值得。[kragen]进一步提出，在探索性项目中，测试可能会拖慢学习与实验的进度。 • **完美主义与实用主义的平衡**：[m463]指出，测试的编写往往在完美主义和实用主义之间挣扎。一些开发者希望达到100%的测试覆盖率，而另一些则认为基本的功能测试即可。 补充讨论： • **测试的心理与文化障碍**：[gcp123]和[angarg12]提到，很多开发者低估测试的长期价值，高估其短期成本，导致测试常常被推迟。 • **测试的商业价值争议**：[massive-fail]和[pfdietz]对测试的商业价值提出质疑，认为并非所有软件项目都值得投入测试资源，尤其是在未明确项目方向时。 争议焦点： • **测试的必要性与优先级**：在不同项目阶段和类型中，测试是否应被优先考虑存在争议。一部分人认为测试是工程的基本要求，而另一部分则认为应根据实际情况灵活处理。

Show HN: The C3 programming language (C alternative language)

作者: lerno | 评分: 168 | 评论数: 22 | 发布时间: 2025-04-03 13:55
文章摘要

C3是一种基于C语言语法和语义的编程语言，旨在进化C语言的同时保持C程序员的熟悉感。它注重实用性，仅在必要时对C语言进行修改，并保持与C的ABI兼容性，允许在同一项目中混合使用C和C3。C3的设计原则包括避免引入过多新概念，提供更高层次的便利性，以及确保C程序员容易上手。 C3与C的主要区别包括：无需强制使用头文件、新的语义宏系统、基于模块的命名空间、切片、编译时反射、增强的编译时执行、基于泛型模块的泛型编程、基于"Result"的零开销错误处理、延迟执行（defer）、值方法、关联枚举数据，以及没有预处理器。 C3提供了预编译的二进制文件，适用于Windows x64、Debian x64、Ubuntu x86和MacOS Arm64等操作系统，并提供了详细的安装说明和手册。示例代码展示了C3的泛型模块、导入外部C函数以及使用新的语言特性。

评论摘要
主要讨论点：围绕C3编程语言的评价、比较及功能讨论 不同观点： • [sfpotter] 认为C3使用的`::`语法丑陋且不必要，更喜欢D语言那样统一使用`.`的语法。 • [micklemeal] 对C3与C库（如raylib和libtmx）的集成表示赞赏，认为其在C3上遇到的问题最少，并希望C3能获得更多认可。 • [dooglius] 提问C3与Zig、Odin的比较，这些语言都有改进C语言的设计目标，并获得了一定的关注。 • [Sohcahtoa82] 喜欢C3的switch/case行为改变（默认break），虽然主要使用Python，但若需用C时会考虑C3。同时对`fn`关键字的必要性提出疑问。 • [dkersten] 虽然对某些语法选择（如`fn type identifier ()`）不完全认同，但总体上对C3表示赞赏，认为其对C的改进显著。 补充讨论： • [unclad5968] 提到使用C3进行csv解析和简单CLI工具开发，认为C3是对C的很大改进，但希望有 tagged union 类型。 • [TZubiri] 调侃为C的继任语言命名越来越困难，建议使用YACS（Yet Another C Successor）。 • [johnisgood] 关心标准库的贡献（如添加BLAKE2），并讨论了哈希表的不同实现和线程安全的需求。 • [fuzztester] 询问其他类似C的语言使用情况，并提到在另一个讨论帖中获得了许多相关评论。 • [xormapmap] 认为许多C替代语言过于复杂，希望有一种仅修复C主要设计缺陷的语言，保持简单并保留预处理器功能。 • [owlstuffing] 认为C3是较好的C替代语言，但对保留宏而放弃条件编译表示不解。 • [alcover] 提问如何在C3中表示只读指针，如C语言中的`const int* ptr`。 • [accelbred] 关心C3是否支持弱函数（weak function）和GCC的构造函数属性。 • [Surac] 认为尽管喜欢更好的'C'语言，但使用这些语言在实际项目和团队中可能导致孤立无援，特别是在公司环境中。 争议焦点： • 对C3语法（如`::`和`fn`）的接受度存在分歧，部分开发者认为这些语法不必要或令人困惑。 • 关于C3与其他C替代语言（如Zig和Odin）的比较，讨论其优劣和社区认可度。 • 使用C3在实际项目中的可行性，特别是在团队中可能导致的兼容性和支持问题。

文章摘要

**curl-impersonate** 是一个特殊版本的 curl，能够模拟 Chrome、Firefox、Edge 和 Safari 四大浏览器。其主要目的是让 TLS 和 HTTP 握手过程与真实浏览器完全一致，从而绕过基于 TLS 指纹和 HTTP/2 指纹的网站检测。该工具可以通过命令行使用，也可以作为库集成替代常规的 libcurl。 为了实现浏览器模拟，curl-impersonate 进行了多项修改，包括使用与浏览器相同的 TLS 库（如 Firefox 的 NSS 和 Chrome 的 BoringSSL），调整 TLS 扩展和 SSL 选项，以及改变 HTTP/2 设置。该项目支持多个版本的浏览器，并为每个浏览器提供了包装脚本以便于使用。 文档和安装说明可在项目目录中找到，使用时需注意某些命令行标志可能会改变 curl 的 TLS 特征从而被检测。
