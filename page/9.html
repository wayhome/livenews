The Subjective Charms of Objective-C

作者: wmlive | 评分: 68 | 评论数: 13 | 发布时间: 2025-04-15 00:58
文章摘要

本文讲述了17世纪博学家莱布尼茨梦想创造一种完美表达所有科学真理的通用语言（characteristica universalis），这一梦想虽未实现，但影响了今天的编程语言。莱布尼茨发明了二进制等，其思想在现代计算机科学中得以延续。作者以自身经历为例，讲述了他对Objective-C语言的特殊情感。尽管这种语言因其冗长和独特语法而备受争议，但在2010年代，它却是开发Mac和iPhone应用的主要工具。作者在大学后期自学Objective-C，通过一本“大黑客牧场”系列书籍掌握了这门语言，并感受到其强大的表达能力。Objective-C源自对象导向编程时代，由Tom Love和Brad Cox创造，因被乔布斯的NeXT公司采用而免于消失，后成为苹果产品核心语言。尽管Objective-C语法复杂，但它提供了一种独特的编程体验。

评论摘要
主要讨论点：Objective-C 及其与 C++、Swift 等语言的比较，以及其在编程历史中的地位和应用情况 不同观点： • **Objective-C 的优点**： - jimbokun 认为 Objective-C 比 C++ 更优雅和强大，尤其是在扩展 C 语言以实现面向对象编程方面。它通过方括号清晰地表达了 SmallTalk 风格的消息传递机制，并且仍然是 C 的超集，能够调用任何遗留代码。 - VyseofArcadia 也支持 Objective-C，认为它比 C++ 更简洁和合理，尤其是在同一个代码库中通过 Objective-C++ 混合使用时。 - ramesh31 强调 Objective-C 是唯一的包含头文件的“动态”语言，这使得代理编码工具能够更有效地工作。 • **Objective-C 未广泛传播的原因**： - hgs3 对 Objective-C 未能在 NeXT/Apple 生态系统之外流行感到遗憾，认为自由开源软件社区没有采用它是个遗憾。 - HexDecOctBin 描述了在 Windows 上尝试使用 Objective-C 的困难，指出缺乏轻量级的工作环境，并认为这是其未广泛传播的原因之一。 • **Swift 的崛起与 Objective-C 的衰落**： - JKCalhoun 对 Swift 的崛起感到不满，认为 Swift 从各种流行语言中借用特性，导致代码风格不一致。他表示对 Objective-C 被取代感到无奈。 - mistrial9 批评了对 Objective-C 的偏见，认为其在面向对象编程早期的生存和成功不应被忽视。 • **Objective-C 的历史与应用**： - pjmlp 分享了将 Objective-C/OpenGL 移植到 Windows 9X/Visual C++/OpenGL 的经历，反映了 Objective-C 在不同平台上的应用历史。 - vaxman 详细描述了 Objective-C 在 NeXTStep 和 WebObjects 中的应用及其在企业环境中的潜力，并讨论了其与 Java 的竞争和最终被 Swift 取代的过程。 补充讨论： • **技术细节与工具支持**： - HexDecOctBin 提到了在 Windows 上使用 Objective-C 的具体技术挑战，包括对 libobjc2 的依赖和自定义根类的实现问题。 - Simplestas 认为 Objective-C 的分布式对象和 XPC 功能非常出色，其他语言无法比拟。 • **个人情感与职业发展**： - JKCalhoun 和 markus_zhang 表达了对编程工作的疲惫和对隐退编程生活的向往，反映了部分开发者对技术变迁的复杂情感。 争议焦点： • **Objective-C 与 Swift 的优劣对比**：部分开发者对 Swift 的崛起持批评态度，认为其风格不一致且缺乏 Objective-C 的优雅，而另一部分开发者则接受 Swift 作为技术进步的自然演变。 总结： 评论中对 Objective-C 的评价褒贬不一，主要集中在对其技术优点、历史应用及其被 Swift 取代的感慨。开发者们对 Objective-C 的技术细节、应用挑战及其在编程历史中的地位进行了深入讨论。

Shell-secrets – GPG-encrypted environment variables

作者: mgarciaisaia | 评分: 82 | 评论数: 11 | 发布时间: 2025-04-17 19:39
文章摘要

**shell-secrets** 是一个小型工具，用于从加密的GPG文件中读取环境变量。它通过加密保护敏感信息，避免以明文存储。使用步骤如下： 1. **安装**：确保GPG已安装并配置。将 `shell-secrets.sh` 添加到系统，并在 shell 配置文件中加入 `source /path/to/shell-secrets.sh`。 2. **创建加密文件**：将敏感信息加密存储在 `~/.shell-secrets/` 目录中，例如 `foo.gpg`。 3. **登录**：使用 `login foo` 命令解密并加载环境变量，`SECRET_LOGIN` 会显示当前登录账户。支持嵌套登录。 4. **登出**：使用 `logout` 或 `Ctrl+D` 退出当前账户。 该工具支持自动补全文件名，并确保环境变量的安全性。

评论摘要
主要讨论点：GPG及其替代方案在管理和存储秘密信息（如加密密钥、密码等）中的优劣比较。 不同观点： • **不推荐使用GPG**：viraptor认为，除非需要公钥支持和团队访问，否则不推荐使用GPG，因为其维护复杂且容易出问题。他推荐了age、SSH key支持、ejson、direnv等更简单和集成的替代方案。 • **GPG工具的问题**：woodruffw指出，类似于GPG的工具（如sops）存在“神秘肉”加密/签名问题，GPG的默认设置不透明且历史表现不佳。 • **TPM作为替代方案**：ykonstant提到使用TPM存储秘密信息的可能性，但对其可靠性和潜在风险（如写入限制、锁定问题）表示担忧，并寻求有经验者的建议。 • **GPG不够用户友好**：hnlmorg认为GPG不够用户友好，暗示可能有更好的选择。 • **SOP实现**：Valodim建议使用SOP（Stateless OpenPGP）实现，认为这是当前处理此类问题的正确方式。 • **使用pass作为简单解决方案**：bitbasher和asveikau提到可以使用pass来管理秘密信息，并通过bash脚本或配置文件（如.muttrc）中调用，这是一种常见且简单的方法。 • **支持GPG**：ognarb支持GPG，认为它在共享秘密信息时非常有用，并披露自己在工作中从事GPG相关的UI开发。 • **GPG在shell中的应用**：dvektor分享了自己将秘密信息存储在GPG加密文件中，并在shell配置文件中注入环境变量的做法。 • **其他工具推荐**：pluto_modadic提到一个新的密码管理器passage，提供了另一个可选方案。 补充讨论： • 讨论中多次提到GPG的复杂性和维护成本，同时也提供了多种替代工具和方案，如age、SSH key支持、ejson、direnv、pass、SOP和passage等。 • 争议的焦点主要集中在GPG的复杂性和维护难度上，部分人认为其不够用户友好且容易出问题，而另一些人则认为它在特定情况下（如共享秘密信息）非常有用。 • ykonstant对TPM作为秘密存储方案的潜在风险表示担忧，并寻求社区经验分享。

文章摘要

本文讨论了SQLite中的虚拟表如何支持写入和事务处理。作者首先回顾了虚拟表的基础知识，然后深入探讨了支持事务的四个关键钩子函数：xBegin、xSync、xCommit和xRollback。SQLite通过回滚日志和超级日志机制确保单个或多个数据库文件的事务原子性。在两阶段提交中，xSync负责确保数据持久化，任何失败都会导致事务回滚，而xCommit和xRollback仅用于清理，不应执行可能失败的操作。作者建议虚拟表开发者将持久化操作放在xSync中，并确保xCommit和xRollback是幂等的，仅用于清理工作。

UI tip: maybe don't round percentages to 0% or 100%

作者: goranmoomin | 评分: 38 | 评论数: 7 | 发布时间: 2025-04-18 23:19
文章摘要

文章主要建议在用户界面（UI）中显示百分比时，避免将数值简单地四舍五入为0%或100%。具体来说，即使进度非常小，比如0.00001，也应该显示为1%，以免用户误以为没有进展。同样，接近完成但未完全完成时，如99.9%，应显示为99%，以免用户误以为任务已完成。文章提供了一段Python代码示例，用于实现这种显示逻辑，并指出这种方法并非适用于所有情况，但在很多场景下能提升用户体验。

评论摘要
主要讨论点：用户对设备运行状态的感知以及进度显示的准确性问题，特别是温度控制设备和进度条的设计。 不同观点： • **[lmpdev]** 认为，提供过多的信息（如精确温度显示）会让用户对设备的正常运行产生误解。用户不习惯看到温度波动，即使这是压缩机工作的正常现象。相比之下，传统家用冰箱不显示具体温度，用户也就不会产生类似的困惑。 • **[crazygringo]** 建议进度条的设计应避免过早显示接近整百的进度，例如在实际未达到50%或100%时，不应显示为50%或100%。同时提出，在显示0%进度时，可以搭配动态指示器，以表明操作仍在进行中，而不是直接显示1%造成误导。 • **[PebblesHD]** 支持不显示接近100%的进度，尤其是在任务未完全完成时，因为这可能会导致用户误以为任务已经结束。其工作中的报告工具也采用了类似的逻辑，避免在任务完成前显示100%。 • **[comrade1234]** 提出类似问题，指出洗衣机的倒计时功能常常在最后阶段让人困惑，显示1分钟剩余时间但实际需要等待更久。建议倒计时直接使用秒数显示，以减少误解。 • **[smallnix]** 提出使用非线性变换来解决进度条在1%和99%时“卡住”的问题，建议采用“ease-in-out”或sigmoid曲线，使进度变化在初期和末期更快，中期变化更平缓，从而减少用户对进度停滞的感知。 补充讨论： • **[ed_mercer]** 提到过去的经验，例如Windows文件传输对话框在实际工作未完成时就显示100%，反映了类似的问题，进一步说明了进度显示设计不当会造成用户困扰。 争议焦点： • 核心争议在于是否应向用户展示精确的运行状态（如温度或进度百分比），以及如何设计进度显示以避免用户误解。一方认为更多的信息有助于理解，另一方则认为过多的细节或不准确的显示会造成困惑。
