The Best Engineers Write Less Code

作者: funnyenough | 评分: 50 | 评论数: 11 | 发布时间: 2026-05-27 00:33
文章摘要

这篇文章强调软件开发的核心原则： **主要观点：** - AI生成代码不能改变软件质量的本质，糟糕的软件依然糟糕 - 开发时间直接等于成本，这是管理层关注进度的原因 - 优秀工程师的价值在于**避免构建不必要的功能**，而非编写更多代码 - 代码是负债，除非它解决了正确的问题 - 构建错误的东西是最大的浪费 **建议实践：** - 在开始前与利益相关者确认需求和目标 - 采用敏捷方式：短周期迭代，及时获取反馈 - 衡量工程师的标准是创造的价值与留下的复杂度之比 - 有空闲时间？去删除代码 核心思想：少即是多，正确比快速更重要。

评论摘要
主要讨论点：在LLM时代，软件开发的核心是否从“多写代码”转向“更好建模、减少无效复杂度、提升可维护性”，以及组织激励与产品思维是否跟得上变化。 不同观点： • **建模能力比编码更关键**：Frannky认为很多人只在封闭信息圈内思考，缺乏端到端建模，导致产品脱离真实需求、技术实现失效；他主张把这类人的意见当作“需净化的输入”，争议点在于这种对他人认知能力的强烈判断是否成立。 • **少写代码更好，但组织不奖励**：xingped指出现实晋升常按“写了多少代码”而非“省了多少代码”评价，“promotion driven development”因此出现；onesingleblast用Ken Thompson“高产的一天是删掉1000行代码”呼应。 • **比“代码少”更重要的是“代码寿命长、决策清晰”**：carefulfungi强调优秀开发者写的是半衰期更长的代码；kspetkov79进一步说，减少“含糊决策”比单纯减少代码更重要。 • **完美设计不可一步到位，应接受重写循环**：faangguyindia认为初版系统常因新需求被补丁侵蚀，之后靠发现更深层模式再重写；因此不再追求第一次就完美。 • **LLM不能替代好软件原则**：funnyenough认为“AI能写代码”不等于可以不写好软件，糟糕的软件无论由Claude还是人写都一样糟；paul_knox补充，如今瓶颈已从“打字速度”转向“理解与维护能力”。 • **未来应从UI中心转向数据/API中心**：saltyoldman主张人不再需要复杂前端，而需要可供个人agent/LLM调用的数据接口，让自己的智能体处理邮件、预算等，而不是被企业UI和零碎“AI按钮”限制。 补充讨论：bfkwlfkjf调侃希望AI最终让人不必再直接处理代码；tommica对“去删代码”的404链接做了轻松吐槽。

Show HN: Posthorn, self-hosted mail gateway

作者: craigmccaskill | 评分: 71 | 评论数: 17 | 发布时间: 2026-05-27 04:26
文章摘要

Posthorn 是一个统一的自托管项目邮件发送网关。它作为单一中间层，连接你所有自托管应用（如 Hugo、Ghost、Gitea 等）与你选择的邮件服务商（Postmark、Resend、Mailgun、AWS SES 等）。 **核心价值**：避免每个应用单独集成邮件服务，统一管理 API 密钥和配置。 **三种接入方式**： 1. HTTP 表单（联系表单、注册） 2. HTTP API（Worker、定时任务） 3. SMTP 监听器（Ghost、Gitea 等 SMTP 应用） **特点**：单个 Go 二进制文件，单个 TOML 配置，支持速率限制、蜜罐防护、授权认证。解决云主机（DigitalOcean、AWS Lightsail 等）阻止 SMTP 出站的问题。 **非功能**：不是邮件服务器、不存储邮箱、不做营销邮件、不提供 Webmail 界面。

评论摘要
主要讨论点：Posthorn到底算“自托管邮件”还是“自托管邮件网关/事务性邮件网关”，以及自建邮件相关方案的可行性与价值。 不同观点： • 标题不准确派：多位评论者认为“self-hosted mail”会误导，Posthorn更准确是“self-hosted email gateway”或“transactional email gateway”，不等同完整邮件服务器。相关争议焦点在于它是否应被称为“mail server”。 • 功能对比派：有人拿它和 protonmail-bridge、nullmailer、Apprise、SES 作比较，认为概念上类似“转发/提交网关”而非完整邮件系统；nullmailer适合本地 sendmail 兼容转发，但不含 HTML 表单支持，也有人质疑同一程序同时处理 HTTP(S) 与邮件提交是否合适。 • 希望扩展派：有用户认可项目切入点不错，但关心是否会从邮件扩展到更多通知服务，类似 Apprise。 • 自建邮件谨慎派：有人担心 DNS/IP 被拉黑，认为邮件是运维和 DNS 中最复杂的领域之一，因此对迁移到 VPS 自建虽有兴趣，但顾虑安全、支持和投递信誉问题。 • 自建邮件支持派：也有人明确表示愿意自托管，尤其是为了个人隐私或互联网开放性；举例使用 Postal、Postfix/Sendmail/Dovecot + Brevo + Cloudflared，认为更多 SaaS 自建邮件能倒逼微软等大厂改进粗放式封禁策略，而不是封整个网段。 补充讨论：还有人提到“Not a mail server”与“支持 SMTP 收发”之间存在表述张力；另有轻松话题是在问项目名是否致敬《W.A.S.T.E.》。

评论摘要

The Steinwinter Supercargo

作者: itronitron | 评分: 82 | 评论数: 15 | 发布时间: 2026-05-23 21:28
文章摘要

这篇文章介绍了Steinwinter Supercargo——一款1983年在法兰克福车展首次亮相的概念卡车。这款由德国工程师Manfred Steinwinter设计的商用车采用超低车身设计，旨在通过减少风阻降低油耗，并缩短车身总长以装载更多货物。它搭载奔驰8缸柴油发动机，输出276马力和753磅英尺扭矩，采用模块化设计可拖挂不同类型货箱。尽管设计前卫，但因视野受限、操控问题和可靠性不足，加上奔驰拒绝投资，项目最终失败。这款卡车后来出现在1987年电视剧《The Highwayman》和2002年《恐龙战队》中，但从未真正投入商用。

评论摘要
主要讨论点：围绕这款低矮卡车/牵引车式设计的灵感来源、实用性、美学价值，以及在现代电动自动驾驶场景下是否值得重新考虑。 不同观点： • 认为其外形很有未来感、审美上成功。有人联想到《异形》的APC、机场无杆牵引车、波音厂区拖车车头、《The Big Bus》，也有人称其内饰“不过时”，甚至像未来电动法拉利。 • 怀旧与文化联想派：有人回忆童年杂志《Das Neue Universum》对这类未来交通工具的想象，表达“没活在那个未来”的失落，说明该设计具有强烈时代幻想色彩。 • 质疑实用性者认为这类车“离地间隙糟糕、视野很差、稳定性和效率不足”，怀疑它不该超出概念图阶段；还有人提到纪录片称此类卡车空气动力学差、油耗高，后来必须重设计驾驶室。 • 有人进一步批评其可能只是“异想天开的设计”，拿老雪铁龙BX类比，质疑实际道路通过性和工程合理性。 • 也有观点认为可在今天重新评估：若用于电动、自动驾驶卡车，传感器可布置在挂车高处，无需传统驾驶室，电池放低也有利重心，因此其低矮布局反而可能有现实价值。 补充讨论： • 评论中有细节纠错：有人指出文中把方向盘说成像宝马E36不对，实际是奔驰W123方向盘，争议焦点是作者对车辆细节描述不准确。 • 整体争议核心在于：这种设计到底是“超前的未来方案”，还是“好看但不实用的概念”。

What Gets Kept

作者: lermontov | 评分: 45 | 评论数: 5 | 发布时间: 2026-05-24 16:46
文章摘要

这篇文章讲述了作者与杰克·凯鲁亚克的回忆。文章从格罗利尔俱乐部展出的凯鲁亚克遗物——一个装有56年前烟灰的烟灰缸开始，引出对这位"垮掉的一代"作家的追忆。凯鲁亚克47岁时在佛罗里达去世，虽是家喻户晓的名字，却穷困潦倒。他的遗物包括《在路上》手稿（最近以1200万美元售出）都被保存下来。作者回忆1957年21岁时与凯鲁亚克的初次见面：在格林威治村的霍华德约翰逊餐厅，那个英俊、自由不羁的黑发蓝眼男子。那次邂逅改变了她的人生，她至今保存着他的红黑格子衬衫。

评论摘要

作者分享了他的社交游戏项目 Migo Games 的开发经验。主要技术栈是 Elixir/Phoenix 后端和 Swift/SpriteKit 前端，部署在 Fly.io 上。他强调 AI 编码工具让开发变得可能，虽然代码主要由 AI 生成，但他仍理解设计架构。Elixir 的进程模型与游戏房间概念完美匹配，便于扩展。应用体积仅几 MB，避免了臃肿。他发现原生应用性能远超 Web，建议同时支持 Mac 以加快构建速度。AI 虽然降低了编码门槛，但软件成功的核心难题（如用户获取）依然存在，且竞争更激烈了。

评论摘要
主要讨论点：围绕一个多人游戏项目的技术选型与发布方式，讨论 Web vs 原生客户端、后端架构、跨平台开发效率，以及实时多人游戏所需基础设施。 不同观点： • **支持 Web 分发与快速传播**：有人认为若走 Web 而非 App Store，分发更容易、增长更自然，“分享链接即可”；也有人用自己做的网页小游戏举例，部署到 github.io 很顺手。但也指出**多人游戏需要后端**，纯静态网页方案不够。 • **后端技术选型分歧：BEAM/Elixir 是否过度**：一派认为社交/实时游戏很适合 Elixir/BEAM；另一派质疑这对项目来说可能“用力过猛”，并追问作者为何选 Elixir/Phoenix 而不是 TS，以及如何实现实时多人同步。 • **基础设施选择争议**：有人认为 Cloudflare Durable Objects 成本低、带复制数据库和实时同步，门槛更低；同时担心其未来垄断后涨价。另有人质疑 Fly.io 可靠性与 uptime，并进一步追问为何数据库用 Crunchy Data 而不是 Fly 托管 Postgres，焦点是**跨机房延迟**。 • **原生开发效率 vs Web 开发效率**：多位评论者认为原生移动端反馈循环明显更慢，尤其 iOS/Xcode/模拟器构建慢；有人建议同时支持 macOS，以加快开发调试。也有人追问作者是否找到让 agent 控制模拟器的方法。 • **跨平台框架观点**：有人建议用 Flutter，认为跨平台、图形性能和 token 效率更好；并质疑依赖 LLM“提示一下就支持新平台”会导致非确定性、反复修补的 whac-a-mole 问题。 补充讨论： • 作者补充服务器在新泽西，欧洲玩家可能高延迟，说明**地域延迟**也是体验争议点。 • 评论中还指出原帖的 Web 客户端链接失效，而作者承认已下线，导致 Web 与原生性能对比论点被削弱。
