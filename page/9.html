I built a native Windows Todo app in pure C (278 KB, no frameworks)

作者: toxi360 | 评分: 355 | 评论数: 46 | 发布时间: 2025-05-11 15:57
文章摘要

"Simple Todo (C / WinAPI)" 是一个轻量级的 Windows 待办事项应用，使用纯 C 和 Win32 API 开发，体积仅 54 KB。该应用支持创建、编辑、删除待办事项，标记任务完成，数据持久化存储在 AppData 文件夹中的二进制文件，最多可存储 100 个待办事项。它具有系统托盘集成、自动启动、原生 Windows 外观等功能。项目使用 MinGW-w64 编译，提供了构建脚本和详细的开发文档。应用界面采用现代 Windows 视觉风格，文件结构清晰，适合学习和使用。该项目基于 MIT 许可发布。

评论摘要
主要讨论点：Win32 GUI编程的技术选择与优化 不同观点： • **masternight** 认为Win32 GUI编程虽然有些特异，但通过阅读相关博客（如Raymond Chen的博客）可以理解其历史背景和设计选择。他强调使用原始C代码编写GUI应用有助于深入理解底层细节，尽管最终可能需要转向C++或使用WTL（Windows Template Library）来简化开发。此外，他指出Win32 API提供了许多C标准库功能的替代品，并建议通过优化编译选项和避免使用C标准库来减小可执行文件大小。 • **electroly** 提出了一种更传统的方法，即通过.rc文件和对话框资源布局来简化控件的创建，而不是手动调用`CreateWindow()`。这种方式不仅可以简化开发，还能通过应用manifest文件获得现代UI样式和高DPI支持。 • **broken_broken_** 分享了在Linux上使用汇编语言实现小体积GUI应用的经验，并认为在Windows上实现类似的小体积应用应该更加简单。他建议通过动态链接和特定链接选项来减小可执行文件的大小。 • **eviks** 对所谓的“现代”应用提出了质疑，指出其缺乏框架支持导致的缺陷，如模糊字体、缺少Tab支持和高DPI问题。 • **AaronAPU** 以6502编程背景幽默地表达了对278KB被视为“轻量级”的不满，暗示过去的编程更注重体积优化。 • **toxi360** 坦承自己创建该应用仅为娱乐，并承认使用C++或其他语言可能会更明智。 • **phendrenad2** 强调在Windows上用C语言开发的舒适感，并对比了在MacOS上使用ObjectiveC的繁琐。他表达了对MacOS API设计的批评，并表示不打算将C代码移植到MacOS。 • **vparikh** 建议链接到DLL而不是静态库，以显著减小应用体积。 • **dvdkon** 推荐使用GCC的优化选项`-Os`和Link-Time Optimisation (`-flto`)来优化可执行文件大小。 • **userbinator** 对应用体积超过预期表示惊讶，认为应能在10KB以内实现类似功能。 • **smusamashah** 提到一个用C编写的快速文件管理器应用File Pilot，其体积仅1.8MB，以此作为小体积应用的例子。 • **webprofusion** 分享了个人经历，回忆了1997年用C++开发Windows应用并通过直升机运送软盘更新的往事。 补充讨论： • **leecommamichael** 对围绕该话题的讨论量表示好奇，提出了一个开放性问题。 • **p0w3n3d** 表达了对尝试实现小体积应用的尊重，并提到Inno Setup使用旧版Delphi编译器实现小体积EXE的经验。 争议焦点： • 争议的焦点之一是“现代”Win32应用的定义及其在UI样式、功能支持方面的不足。 • 另一个焦点是应用体积的合理性，部分评论者认为278KB对于简单功能来说过大，并提出了多种优化建议。 总体来看，讨论围绕Win32 GUI编程的技术细节、优化方法及历史背景展开，参与者分享了各自的实践经验和观点。

The Audio Stack Is a Crime Scene

文章摘要

文章主要讨论了Linux音频系统的复杂性和常见问题。作者描述了在Linux上使用音频设备时遇到的种种困扰，例如插入耳机没有声音、设备显示为“虚拟输出”、音量设置无法保存等。这些问题源于音频栈的演变历史：从早期的ALSA到问题多多的PulseAudio，再到现代的PipeWire。虽然PipeWire在技术上更为先进，解决了PulseAudio的许多问题，但由于软件生态尚未完全适配，许多应用程序仍然依赖PulseAudio，导致兼容性问题。此外，ALSA和JACK等旧系统仍需使用，使得音频调试变得更加复杂。文章还提到，在笔记本电脑上，固件问题和未记录的 quirks 使得音频故障更加难以解决。总体而言，Linux音频系统虽然有所改进，但依然存在诸多挑战。

评论摘要
主要讨论点：Linux音频系统的复杂性、可靠性以及与其它系统（如Windows、macOS、FreeBSD）的对比 不同观点： • wormius：从Win10迁移到基于Arch的CachyOS后遇到音频失真问题，经过多次调试（涉及alsamixer、PulseAudio、PipeWire等），最终通过更换内核解决。这表明Linux音频栈的复杂性以及潜在的底层问题。 • thedanbob：在会议音频处理过程中遇到Linux音频系统（JACK和实时内核）不稳定的问题，最终切换到macOS完成任务，暗示Linux在专业音频处理方面的不足。 • ringeryless：指出Linux音频问题的核心在于单客户端ALSA驱动模型，且设备处理方式不如macOS的CoreAudio直观，导致多应用同时访问音频设备时出现问题。 • PaulHoule：认为Windows在音频方面略好，但也有类似问题，特别是涉及虚拟驱动时，表明即使在Windows系统上音频处理也并非完美。 • AHTERIX5000：强调Linux音频栈（特别是Fedora上的PipeWire和PulseAudio）在切换音频设备时的不稳定和不可靠性，批评其在多设备处理上的表现。 • duped：批评PipeWire的文档不完善，认为尽管技术先进，但由于缺乏良好的文档和清晰的API设计，导致开发者难以使用。 • nesarkvechnep：简短指出FreeBSD在音频处理方面优于Linux，暗示Linux在某些方面可能不如其它开源系统。 补充讨论： • Linux音频栈的复杂性和历史遗留问题（如ALSA的单客户端驱动模型）是导致用户遇到问题的主要原因。 • PipeWire被认为是Linux音频的未来，但其文档和API设计尚不成熟，导致开发者和用户在使用时遇到困难。 • 讨论中多次将Linux音频系统与Windows和macOS进行对比，显示出Linux在专业音频处理方面的不足。 • 内核和驱动的选择（如Bore-LTO内核）可能对音频问题的解决有显著影响。 • 用户在调试Linux音频问题时需要进行大量手动配置和试验，显示出系统在自动化和用户体验方面的欠缺。

Dotless Domains

作者: wibbily | 评分: 185 | 评论数: 28 | 发布时间: 2025-05-11 01:38
文章摘要

本文讨论了无点域名（dotless domain）的概念，即如「.com」或「.gov」这样只有一个标签的顶级域名（TLD），可通过浏览器或电子邮件服务器访问。无点域名在域名的DNS区域包含A/AAAA或MX记录时可实现。国际互联网名称与数字地址分配机构（ICANN）和互联网架构委员会（IAB）反对这种做法，并禁止通用顶级域名（gTLD）使用无点域名，但国家代码顶级域名（ccTLD）则由各国自行管理，因此历史上和目前都存在一些活跃的无点ccTLD例子。文章还列举了当前和历史上拥有无点域名的国家及其状态，并讨论了电子邮件协议对无点域名的限制。最后，文章提供了包含A/AAAA或仅MX记录的TLD表格，以及相关历史记录和截图。

评论摘要
主要讨论点：关于电子邮件地址和域名中TLD（顶级域名）以及"无点"域名的技术讨论 不同观点： • **nulbyte的观点**：ICANN的SSAC并没有定义SMTP需要至少两个标签，且RFC5321明确提到可以使用TLD作为电子邮件地址的域名部分。这表明某些技术文档中对TLD使用的限制可能被误解或夸大。 • **tech234a的观点**：浏览器可以接受十进制形式的IP地址，例如将1.1.1.1表示为http://16843009。这说明浏览器在地址解析方面具有一定的灵活性，能够处理非传统格式的输入。 • **FlamingMoe的观点**：该帖子受欢迎可能与梵蒂冈域名冗余的评论有关，暗示公众对域名使用中的特殊案例有兴趣。 • **Animats的观点**：大多数浏览器将单个词视为搜索关键字而非域名。由于公司开始拥有自己的TLD，问题随之而来。即使直接输入"amazon"或"microsoft"并加上点，浏览器仍可能将其视为搜索关键字而不是直接进行DNS查找。 • **90s_dev的观点**：在编写电子邮件验证器时发现，根据研究结果，像"a@b"这样的格式在某些情况下可以是有效的电子邮件地址，只要TLD有MX记录。 • **tzury的观点**：所有域名，包括TLD，都是"."的子域，因此在NS记录中可以看到尾随的点。 • **hirsin的观点**：曾考虑将多个域名移到一个无点域名下，以便绕过3p cookies的限制，但由于ICANN和其他组织的反对，未能实现。 • **vzaliva的观点**：曾见过非常短的电子邮件地址（如??@ua），但由于大多数系统不识别，其实用性有限。 • **zatkin的观点**：提到拥有单字母域名和单字母电子邮件地址的趣事，并展示如何通过MX记录接收邮件。 • **zoky的观点**：提到一个例子，某人将URL写成com/foo/bar.html，省略了域名部分，显示了早期网络使用中的一些误解和习惯。 • **Tsiklon的观点**：提到曾与一位能够在TLD本身发送邮件的工程师共事，显示了在特定网络环境中TLD的特殊用法。 • **cduzz的观点**：提到每十年会尝试寻找奇怪的DNS名称，其中顶级域名解析为实际地址，并解释了"无点"域名仍需要尾随的点来规范名称。 补充讨论： - 争议焦点在于TLD的使用及其在不同技术环境下的合法性和实用性，特别是在电子邮件地址和浏览器解析中的应用。 - 技术实现和标准文档（如ICANN和RFC）之间的差异和误解是讨论中的一个重要方面。 - 讨论还涉及到历史和技术背景下的趣闻轶事，增加了对TLD使用的实际理解。
