Gnutella: A Protocol Outliving the World That Created It

作者: rickcarlino | 评分: 7 | 评论数: 0 | 发布时间: 2026-05-22 02:24
文章摘要

Gnutella是一个点对点文件共享协议，诞生于2000年代初期。它作为AOL内部项目泄露后，因去中心化设计无法被关闭，迅速获得数百万用户。用户使用它主要是为了下载MP3音乐文件，而非出于对技术本身的兴趣。 协议的核心功能是点对点搜索引擎：用户通过客户端（如LimeWire）连接到网络节点，输入搜索关键词，查询在网络中传播并返回结果，然后直接从其他用户电脑下载文件。 Gnutella在2000-2010年代盛极一时，随后因音乐产业变化、流媒体兴起和用户习惯改变而衰落，但协议至今仍在运行。它证明了去中心化技术可以被普通用户大规模采用，只要能解决实际问题。

We Reverse-Engineered Docker Sandbox's Undocumented MicroVM API

作者: yakkomajuri | 评分: 78 | 评论数: 8 | 发布时间: 2026-05-21 14:50
文章摘要

Docker 悄然推出了基于 microVM 的 Sandbox API，用于安全运行 AI 编程代理的不受信任代码。与共享内核的容器不同，microVM 提供独立内核隔离，安全性更高。作者逆向工程了这个未公开的 API，发现可通过 `/vm` HTTP 端点创建和管理虚拟机，每个 VM 拥有独立的 Docker 守护进程。这为不受信任代码执行、AI 代理、多租户插件等场景提供了类似 Docker 容器的统一管理方式，但目前仅支持 macOS/Windows 且需要嵌套虚拟化。作者基于此构建了开源的 Sandbox Agent SDK。

评论摘要
主要讨论点：Docker Sandboxes 微虚拟机沙箱技术的发展、替代方案及其在 AI Agent 场景中的应用价值 不同观点： • **技术更新派（pploug）**：强调 Docker 已推出独立的 sbx 二进制文件（50MB），无需 Docker Desktop，文章信息已过时 • **Linux 支持质疑派（whimblepop, nyrikki）**：批评不支持 Linux 令人意外。指出 Podman 通过 libkrun 可在 Linux 上透明启动微虚拟机，Docker 本身也支持 KVM，只是默认不启用 • **安全价值怀疑派（andix）**：质疑容器隔离对 Agent 场景是否真正重要。认为即使有沙箱，Agent 仍有大量权限可造成危害（如植入后门、滥用 token） • **替代方案关注派（cedws, drzaiusx11）**：关注其他竞品如 lima/Colima、Microsandbox。认为 sbx 过于面向 Agent，期待更通用的 SDK 方案 补充讨论： 技术实现上，多位评论者指出这些方案本质都是在独立 Linux VM 中运行容器实例，使用平台特定虚拟化技术（macOS 用 Apple Virtualization.framework，Windows 用 Hyper-V）。建议尝试 Podman 以更好理解底层机制。

这是一个打孔卡片历史档案网站的介绍。打孔卡片曾在1950-60年代广泛用于会计、数据收集和早期计算，但很快就被淘汰并被遗忘。该档案收藏了255张打孔卡片（5种格式，来自55家印刷商和64家公司）、11件硬件设备（3家制造商）以及18份手册文档（涵盖100种产品），旨在保存这些历史文物。网站展示了包括贝尔实验室、IBM等公司的特色藏品。

评论摘要
主要讨论点：打孔卡编程时代的工作方式及其现代遗产 不同观点： • **编程效率的代际差异**（benrutter）：打孔卡时代编程极其困难，提交代码到获得结果至少需要一天，一个小错误（如漏掉分号）就会导致长时间等待。认为自己的性格无法适应那个时代的编程工作，而母亲那代人有不同的心态和耐心。 • **互联网知识分享的价值**（ktallett）：承认自己对打孔卡历史了解有限，但认为互联网上这类小众专业网站的存在很有意义，体现了互联网在知识传播方面的独特价值。 • **打孔卡技术的延续性**（foxglacier）：从技术角度欣赏边缘打孔卡的机械搜索功能，指出打孔卡的理念以虚拟形式延续至今——现代工程软件（如Abaqus和Nastran）仍使用类似打孔卡的文本格式，工程师按列号输入数据，甚至沿用"卡片"和"卡组"的术语来指代文件和行。 补充讨论：foxglacier通过儿童拼图游戏类比说明了打孔卡的物理验证机制，展示了这种古老技术的巧妙设计思想如何跨越时代影响现代工程实践。

Learnings from 100K lines of Rust with AI (2025)

作者: pramodbiligiri | 评分: 168 | 评论数: 31 | 发布时间: 2026-05-20 10:04
文章摘要

作者用3个月时间，借助AI编码工具（Claude Code、Codex等）用Rust重写了Azure的RSL共识引擎，实现了10万行代码和显著的性能提升（从2.3万ops/s优化到30万ops/s）。 核心经验包括： 1. **代码契约**：让AI编写前置/后置条件和不变量，转化为运行时断言和属性测试，有效保证正确性 2. **轻量级规范驱动开发**：从严格的文档流程转向灵活的需求-设计-任务列表方式 3. **激进性能优化**：通过AI辅助的基准测试、火焰图分析和迭代优化实现数量级提升 作者认为AI极大提升了开发效率，但仍需人工把关架构设计和正确性验证。

评论摘要
主要讨论点：AI辅助编程（特别是Rust开发）的实践效果和局限性 不同观点： • **支持派**：chadd认为多LLM协作评审能显著提升代码质量；jsLavaGoat分享成功案例，表示AI在Rust项目中表现良好，成功实现了Bash替代品和wasm计算器 • **质疑代码质量**：wren6991和cold_harbor指出AI生成的Rust代码虽能编译，但充斥`.clone()`和`Arc>`等非惯用写法，只保证安全性却牺牲了代码质量；jdw64抱怨AI无法正确处理生命周期，导致代码难以维护 • **质疑代码量**：kikimora和danbruc认为130k行代码过于臃肿（原C++版本仅36k行），staszewski认为使用agent可减少一半代码量；这反映AI可能生成冗余代码 • **质疑测试覆盖**：torben-friis指出1300个测试对应130k行代码，平均每100行一个测试覆盖率过低；icemanx质疑AI生成的测试是否经过人工审查 • **关注实际价值**：misja111提出关键问题——这个实现是否真正被Azure采用并运行良好，这比代码行数更有意义 补充讨论：pjmlp提出编程语言本身正变得不重要，重点转向agent编排工具；sltr分享反对观点认为英语永远不会成为编程语言；dxxvi好奇作者如何掌握复杂的multi-Paxos架构细节。
