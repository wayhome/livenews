文章摘要

这篇文章介绍了Macbook Neo上光标延迟问题的临时解决方案"Unlag Neo"。 **问题**:Macbook Neo在光标接近屏幕边缘或进入终端窗口时会出现延迟,原因可能是系统从硬件光标切换到软件光标时出现卡顿。 **解决方案**:通过屏幕录制功能强制系统使用软件光标来消除延迟。作者提供了一个脚本(`create_unlag_neo_app.sh`)自动创建应用程序,该应用以极低资源消耗(每10秒录制1像素到/dev/null)进行屏幕录制,只会在屏幕右上角显示录制指示器(⏺)。应用还支持全屏时自动暂停功能以隐藏指示器。 这是一个权宜之计,等待Apple正式修复该问题。

评论摘要
主要讨论点：MacBook Neo 鼠标光标延迟问题及其修复方案 不同观点： • **技术解释派**：userbinator 从 GPU 架构角度分析，认为延迟源于硬件光标切换到软件光标时需要等待 GPU 命令队列刷新。这是底层渲染机制导致的。 • **修复方案质疑派**：TheTon 强烈反对此修复方法，认为强制 WindowServer 合成光标而非使用硬件叠加层是"糟糕的修复"，虽然能解决问题但代价太大。 • **实用主义派**：exogen 分享类似经验，通过调整光标大小解决了 TV.app 的颜色处理问题，认为这个副作用可以接受甚至更好。 • **长期维护担忧派**：anotherpaul 指出 hacky fix 的隐患——bug 修复后仍在运行无用脚本，不知何时该移除这些临时方案。 • **性能退化批评派**：PaulHoule 和 whywhywhywhy 批评现代软件架构，对比老设备（1984 Mac、800MHz G4）反而没有光标延迟，质疑当前系统的倒退。 补充讨论：elicash 认为这个有趣修复能引起 Apple 注意促成真正修复；gcr 称赞代码示例展示了 Swift 最小化 App Bundle 的方法；m132 简短表达对乔布斯时代品质的怀念；amelius 和 xnx 以幽默方式评论修复方案的得失。

Zero-Downtime Deployments with Docker Compose – No Kubernetes Required

作者: canto | 评分: 36 | 评论数: 16 | 发布时间: 2026-06-24 20:20
文章摘要

这篇文章主要讲述 StatusDude 团队如何在不使用 Kubernetes 的情况下，仅用 Docker Compose 和 HAProxy 实现零停机部署。 他们最初尝试使用 Traefik，但遇到三个关键问题：多服务标签冲突导致 404 错误、扩缩容时路由表更新延迟造成 502 错误，以及最致命的——Traefik 无法将失败请求重新分发到其他健康后端，导致请求丢失。 最终他们改用 HAProxy，通过三个核心要素实现零停机：Docker Compose 的多副本部署、HAProxy 的 `redispatch` 功能（将失败请求重试到不同后端），以及逐个替换实例的滚动更新脚本。整个方案简单可靠，无需复杂的 Kubernetes 基础设施。

评论摘要
主要讨论点：关于是否需要使用 Kubernetes 来实现生产环境的零停机部署 不同观点： • **支持自建方案派**：认为小规模应用不需要 Kubernetes，作者的案例（每分钟数千次监控检查）规模很小，单个 VM 就能处理。自建方案更简单直接，避免了 K8s 的复杂性和学习成本。 • **支持 Kubernetes 派**：强调 K8s 在处理容器崩溃恢复、蓝绿部署、多区域容灾、动态扩缩容、服务发现、秘钥隔离等场景下的价值。认为自建这些功能最终会演变成"自己的 Kubernetes 版本"，反而更复杂。K8s 并不难维护，小团队也能胜任。 • **折中观点**：K8s 适合有一定规模或预期会扩展的系统。如果是小项目或独立开发者，可以暂时不用，但建议专业人员学习 K8s 以理解分布式系统的思维方式。避免 K8s 的代价可能是高昂的云服务费用（如 ECS、App Services）。 • **技术细节派**：指出原文遗漏了非幂等请求重试的安全性问题、优雅关闭机制等重要细节。推荐使用 docker-rollout 等现成工具，认为手工实现类似功能缺乏文档和可维护性。 补充讨论：有评论指出行业对 K8s 的态度已从批评转向认可；也有人提醒"快速行动，打破常规"的开发方式容易在后期引发更大问题，强调前瞻性规划的重要性。

文章揭露了强生公司两个Web应用的安全漏洞： **1. 校园招聘系统**：通过篡改前端MSAL认证代码，绕过微软SSO登录，利用硬编码的API密钥访问了近1000名学生的个人信息和面试评价。问题根源是后端未验证MSAL令牌，仅依赖硬编码密钥。 **2. 审计追踪管理系统(ATMS)**：涵盖强生及20家关联公司的内部审计系统。作者通过伪造管理员身份，绕过前端认证，直接调用未鉴权的API获取了13,600名员工信息和管理员权限，可访问所有公司的机密审计记录和会议纪要。 两个漏洞均源于前端认证未在后端验证，API缺乏适当的访问控制。
