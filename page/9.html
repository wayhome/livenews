Static as a Server

文章摘要

本文介绍了如何使用React Server Components（RSC）构建静态网站，并通过Cloudflare CDN免费托管。传统上，“服务器”和“静态”框架被视为不同工具，但现代框架 increasingly 支持两者输出模式。通过在构建时运行服务器代码并存储响应，可以实现静态网站生成。这种“混合”框架减少了工具碎片化，提供了更大的灵活性和粒度，允许按路由选择服务器或静态渲染。例如，Next.js默认生成静态网站，同时可在需要时选择服务器功能。尽管称为“服务器组件”，它们实际上可以在部署时静态运行。因此，静态网站就是提前运行的服务器。

文章摘要

本文讨论了GitHub Actions相关的安全风险，特别是近期的两次攻击事件，包括去年12月的Ultralytics供应链攻击和今年3月的"tj-actions"事件。攻击者利用GitHub Actions的漏洞和反模式，窃取个人访问令牌（PAT）并注入恶意代码。文章强调了保护GitHub环境的重要性，提出了以下安全措施：设置默认工作流权限为只读、限制仅使用经过验证的Actions、以及通过允许列表控制工作流的采用和运行位置。这些措施有助于防止类似攻击，并加强GitHub Actions的安全性。文章还介绍了相关术语和配置建议，以帮助组织更好地保护其开发环境。

评论摘要
主要讨论点：GitHub Actions的安全性及如何应对潜在的安全风险 不同观点： • [ebfe1] 介绍了一种工具来帮助固定GitHub Actions的版本，通过提示用户并保存配置以供将来使用，同时允许忽略来自知名组织的Actions以保持更新和安全性。该方案强调用户对Actions版本的控制和灵活性。 • [cyrnel] 指出即使通过固定版本，核心问题仍然存在，即某些Actions拥有过多的权限（如CAP_SYS_PTRACE），并认为GitHub缺乏对Actions的沙盒机制，导致安全隐患。强调限制Actions权限的重要性。 • [cedws] 分享了在审查第三方Actions时发现的问题，例如从未固定版本的脚本和代码中引入的安全风险，甚至认为GitHub即将推出的"Immutable Actions"可能也无法完全解决这些问题。提出了自建Actions的方案以提高安全性。 • [colek42] 介绍了一种新的工具，提供"Trusted Telemetry"功能，通过SLSA和in-toto证明来跟踪GitHub Actions的使用情况，强调透明度和可信度。 • [kylegalbraith] 强调自托管的GitHub Actions运行器可能引入更多的安全风险，尤其是如果配置不当，可能会暴露基础设施。建议使用无持久性、无权限的运行器以减少攻击面。 • [axelfontaine] 同意自托管运行器的风险，但认为公共仓库不是问题，关键在于拉取请求。主张使用短暂运行器和最小权限原则来提高安全性。 • [maenbalja] 分享了自托管运行器的实际体验，并建议在涉及SSH命令时使用自托管运行器以提高安全性。 • [gose1] 提到GitHub已经支持通过CodeQL和GitHub Code Scanning进行工作流安全分析，提供了识别漏洞的工具。 • [bob1029] 认为GitHub Actions的安全模型过于复杂，最安全的方案可能是避免使用不必要的Actions。 • [tomrod] 对如何有效应对供应链攻击表示关注，并希望找到现实的解决方案。 • [wallrat] 提到一个正在开发中的项目，可以创建可验证的校验和清单，以补充GitHub的Immutable Actions。 • [RadiozRadioz] 对使用第三方Actions的必要性提出质疑，认为简单的构建和部署可以通过基础容器和Makefile完成，而不需要依赖预制的步骤。 • [duped] 认为GitHub Actions的设计有缺陷，建议引入类似现代包管理器的锁定和验证机制，以提高安全性。 • [DGAP] 推荐了一种开源的沙盒工具，认为可以有效提高Actions的安全性。 • [MadsRC] 分享了一个检测和修复未固定依赖的工具，并正在开发递归扫描远程依赖的功能，强调自动化和检测的重要性。 补充讨论： • 争议焦点在于自托管运行器的安全性和GitHub Actions权限的过度分配问题。 • 多个评论提到了固定版本和校验和的重要性，但也指出这并不能完全解决安全问题。 • 有人对第三方Actions的必要性和安全性提出质疑，认为简单的构建和部署不需要依赖这些预制步骤。 • 提出了多种工具和方案来提高GitHub Actions的安全性，包括锁定版本、使用短暂运行器和权限限制等。
