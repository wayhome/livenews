文章摘要

微软正在取消大部分Claude Code许可证，要求数千名开发者转用GitHub Copilot CLI。尽管Claude Code在过去六个月内深受欢迎，但它削弱了微软自家工具的地位。微软体验与设备团队将在6月底前停用Claude Code，这一决定既出于统一工具策略，也是为了削减新财年运营成本。许多习惯使用Claude Code的员工（包括非技术人员）面临转型挑战，因为两款工具仍存在功能差距。微软承诺将加大对Copilot CLI的投资，使其更好地适配内部工程流程。

评论摘要
主要讨论点：微软因成本问题取消Claude Code许可，强制开发者转用Copilot CLI 不同观点： • **成本效率派**：Claude Code消耗token过快不可持续。有团队一周内烧完月度预算，甚至一天用掉一半额度。Deepseek等便宜模型更实用，开发者使用时无心理负担，能力差距不大 • **质量优先派**：不愿为省钱冒险用弱模型，绩效考核看产出速度而非token节省。Claude质量感知更高，Copilot（尤其政府云版本）输出混乱、语法错误多，几乎无法使用 • **混合使用派**：通过人工监督而非全自动agent控制成本。日常任务用免费模型，复杂问题才用Claude。GitHub Copilot $10/月计划可访问多模型（含限量Claude），无时间限制更适合工作流 • **商业动机质疑派**：这是微软推广自家Copilot的策略，与OpenAI深度合作却采购Claude本就奇怪。Claude token在GitHub定价畸高可能有意为之 补充讨论：有人指出这是12月启动的试点项目，意外烧完2026全年AI预算才在6月30日终止。另有讨论AI成本是否真比人工便宜——若工具费用失控，裁员换AI的逻辑是否成立？

Fast Factorial Algorithms

作者: nill0 | 评分: 42 | 评论数: 8 | 发布时间: 2026-05-20 03:55
文章摘要

文章介绍了5种计算阶乘 n! 的算法：SplitRecursive（简单且不依赖质因数分解时最快）、PrimeSwing（目前渐近最快，基于“摆动数”和质因数分解）、Moessner（仅用加法但很慢）、Poor Man’s（无需大整数库，适合实现）、ParallelPrimeSwing（适合多核并行）。文中还给出递归实现示例，并强调不要使用朴素递归阶乘。

评论摘要
主要讨论点：关于快速阶乘算法网站内容的评论和补充 不同观点： • **算法覆盖不足**：FiatLuxDave指出网站未提及AKS素性测试，认为其运作类似FFT用于消除模N的阶乘；dvh也质疑为何没有Stirling公式 • **实用性优先**：ipeev认为对于实际需求，使用缓存映射最佳，因为阶乘数值很快就会变得过大而无意义 • **学习体验欠佳**：smokel希望用于解决Project Euler问题，但发现算法解释不够详细，学习效果一般，需要借助ChatGPT理解。同时提到无法找到关键参考文献"Swing, divide and conquer the factorial" • **编译器优化可能性**：looneysquash好奇编译器是否能将某些实现重写为其他更优形式 • **特殊实现案例**：anthk展示了Zenlisp中使用cons实现整数的阶乘算法，强调这种从Lisp自身构建的方式类似Peano公理 补充讨论：zamadatix澄清网站末尾已链接单独页面介绍Stirling等近似公式，包含多种高级选项对比

Rubish: A Unix shell written in pure Ruby

作者: winebarrel | 评分: 143 | 评论数: 22 | 发布时间: 2026-05-23 06:32
文章摘要

Rubish 是一个用纯 Ruby 编写的 UNIX Shell：将 Shell 语法解析并编译为 Ruby，再由 Ruby VM 执行。它目标是完全兼容 Bash，可直接运行现有 bash 脚本；同时深度整合 Ruby，支持在脚本中混用命令与 Ruby 表达式、方法链、迭代器、lambda、Ruby 风格函数和自定义提示符等，适合既想保留 Shell 体验又想利用 Ruby 能力的用户。

评论摘要
主要讨论点：关于 Rubish（Ruby shell）项目的评价和对未来开源开发模式的思考 不同观点： • **实用性担忧派**：freedomben 认为虽然项目有趣，但最大障碍是远程环境部署问题——Rubish 不够轻量，需要安装，导致必须在两个世界间切换，这通常不可持续 • **AI 辅助编码质疑派**：ciconia 对"vibe-coded"（AI 辅助生成）的代码表示担忧，指出代码缺乏清晰的接口边界、存在 200 行的长方法，使得非 AI 用户难以理解和贡献。质疑这是否意味着未来贡献者也必须使用 AI 才能参与开源项目 • **学习工具支持派**：saysjonathan 希望看到更多解释型语言提供原生 shell，认为像 rush 和 scsh 这样的工具能帮助开发者沉浸式学习语言，虽然最终因人机工程学问题回归传统 shell，但作为学习机制很有价值 • **性能讨论派**：faangguyindia 和 1vuio0pswjnm7 关注性能，指出 Ruby 比 Go 慢但比 Python 快，质疑 Rubish 可能比 bash 更慢 • **命名赞赏派**：多位评论者（keyle、searls、terminalbraid 等）高度赞扬项目命名的巧妙（Rubish = Ruby + sh，也谐音 rubbish） 补充讨论：ifh-hn 表达了对传统管道操作的偏好，不喜欢方法链式调用的风格

Evaluating Spec CPU2026

作者: zdw | 评分: 18 | 评论数: 3 | 发布时间: 2026-05-23 16:13
文章摘要

SPEC CPU2026是CPU基准测试套件的最新版本，包含52个工作负载（较2017版增加9个）。文章使用GCC 14.2.0评估了该套件，发现其参考系统Ampere eMAG 8180性能过低，即使十年前的处理器也能大幅超越。测试显示AMD Zen 5和Intel Lion Cove在整数测试中表现接近，但Zen 5在浮点测试中领先，部分得益于AVX-512指令支持。与SPEC CPU2017相比，新套件的整数测试IPC分布更高更集中，浮点测试在Zen 5上IPC范围更广。

评论摘要
主要讨论点：CPU性能基准测试的方法论和实践问题 不同观点： • **测试覆盖度关注**：ksec指出Anandtech曾对x86（Intel/AMD）和Apple SoC进行SPEC基准测试对比，但现在缺少这类全面的跨平台测试站点 • **基准选择质疑**：fweimer关注选择eMAG作为基准CPU的合理性，质疑这是否会影响最终评分中各组件的权重分配 • **优化方法探讨**：jeffbee从L1i MPKI异常值出发，质疑在使用PGO（profile guidance）、LTO和BOLT等峰值优化技术后结果是否会显著不同，并具体分析cactus程序是否存在热点代码区域过大或工具链布局不佳的问题 补充讨论：三条评论分别从测试生态、测试方法论和优化技术三个层面探讨CPU性能评估，反映了业界对基准测试标准化、公平性和优化潜力的持续关注。
