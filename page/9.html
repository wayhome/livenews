Fixing a kubelet memory leak in Kubernetes 1.36

作者: compumike | 评分: 75 | 评论数: 7 | 发布时间: 2026-07-01 02:14
文章摘要

这篇文章讲述了作者如何追踪并发现 Kubernetes 1.36 中 kubelet 组件的内存泄漏问题。 作者在一个小型测试集群（2GB 内存节点）上升级到 v1.36 后收到告警，发现 Pod 被频繁重启。通过调查发现不是应用程序的问题，而是 kubelet 进程本身内存持续增长。 作者使用 Go 的 pprof 工具捕获堆内存分析，发现大量 `context.(*cancelCtx)` 相关对象积累。通过对象计数和内存使用分析，追踪到 `k8s.io/kubernetes/pkg/kubelet.(*podWorkers).startPodSync` 函数存在问题。 这是一个 Go 生命周期管理的微小 bug，每次调用 `startPodSync` 时都会泄漏一个 context 对象。因为节点内存较小，这个问题很快就暴露出来了。

评论摘要
主要讨论点：Kubernetes v1.36版本kubelet内存泄漏问题的发现及社区讨论 不同观点： • **问题识别与应急方案**：作者compumike发现v1.36.[0,1,2]版本存在内存泄漏，建议检查`process_resident_memory_bytes`指标，并在v1.36.3发布前重启kubelet作为临时解决方案 • **技术根因分析**：CamouflagedKiwi认为这是违反"不应存储contexts"最佳实践所导致的隐蔽陷阱；jeffbee质疑该问题发生在主循环中却未被发现，怀疑可能存在其他限制影响范围的因素 • **运维改进建议**：__turbobrew__提出应对kubelet进程实施健康检查并在检测失败时自动重启，将问题转化为运维实践改进 • **工具链赞赏**：lanycrost称赞golang和kubernetes工具集对调试工作的友好支持 补充讨论：社区对作者贡献持积极态度（rirze鼓励向知名项目贡献、fsuts表达赞赏），体现了开源社区的协作精神。核心争议在于该bug为何逃过质量检查流程。

We Don't Have to Be This Bad at Improving Society

作者: juunge | 评分: 52 | 评论数: 17 | 发布时间: 2026-07-02 08:26
文章摘要

作者探讨了"决策风险"概念，受一本关于丹麦政治改革失败的书启发。他观察到公共和私营部门都存在类似问题：投入大量资源却产出失败结果。 核心观点：即使在高度不确定情况下，也能降低决策风险。方法是将工作分解为最小可学习单元，在执行与学习间持续迭代，用小额投资替代单一豪赌。 关键要求：领导者应定义期望"成果"而非具体"产出"，让接近问题的团队自主探索解决方案。批评那些远离实施却擅自指定方案的决策者。 作者认为政治体系在解决重大社会问题上存在深层缺陷，但保持乐观，希望通过识别根本原因并开发相应机制来改善丹麦政治改革的有效性。这类系统性思考问题激发了他的兴趣。

评论摘要
主要讨论点：政府为何难以通过实验性政策有效改进社会，以及这种困境的根本原因 不同观点： • **既得利益困境**：政府项目一旦启动就形成依赖该项目生存的专家群体和利益相关者，他们会竭力阻止项目取消，并确保评估报告永远不会给出明确的"失败"结论（Bratmon） • **政治问责悖论**：政治家不能承认任何失败，否则被贴上"flip-flopper"标签政治生涯终结，这导致无论大小决策风险相同，政治家只能坚持错误或辞职（injidup） • **个体利益视角**：不存在"社会整体"，每个人都为自身利益工作。失败的项目对参与者可能意味着稳定收入、职业晋升或税收优惠，因此会被这些受益者持续维护（deepsummer） • **阈值效应限制**：许多政策（如公共交通、免疫接种）需要达到特定规模阈值才能成功，渐进式实验会因网络效应不足而持续失败，但全面推进风险又太大（14113） • **意识形态主导**：政府确实做过实验（如UBI试点），但领导层更关注意识形态而非证据，倾向于从智库获取"政策导向的证据"而非客观研究（PaulKeeble） • **能力质疑**：COVID-19封锁证明政府能在数周内重组整个社会，说明政府有能力解决问题，只是平时"不愿意"而非"不能"（Devasta） 补充讨论：争议焦点在于政府失灵是结构性问题（利益固化、政治成本、系统设计缺陷）还是主观意愿问题。部分人认为缺乏安全实验机制和系统思维，另有人指出选民本身不愿投票给妥协方案，导致政策在极端间摇摆。

I Don't Maintain My Homelab

文章摘要

这篇文章讲述了作者如何构建一个几乎无需人工维护的家庭实验室(homelab): **基础设施简化**:将四台服务器整合为一台,大幅降低复杂度;树莓派运行Home Assistant OS自动更新;UniFi网络设备支持定时自动更新。 **软件自动化**:通过crontab每周自动更新所有Docker服务;设置自动备份任务,包括数据库导出和文件同步到ZFS存储池。 **维护成本**:每月仅需约15分钟进行系统更新,甚至可以6个月不管也不会出问题。作者认为这种"设置后即可忘记"的方式,在隐私、安全和便利性之间达到了理想平衡,特别适合工作繁忙的情况。 核心理念:通过精简架构和自动化脚本,让系统自我维护。

评论摘要
主要讨论点：家庭服务器（homelab）如何实现低维护运行，以及这种状态是否仍算"实验室" 不同观点： • **最小维护派**：通过固定软件版本、使用Docker自动启动、限制局域网访问等策略，实现月均15分钟以下的维护时间。代表做法包括旧硬件复用、NFS共享配置文件、定期自动备份到云端 • **现实主义派**：承认总体维护已经很少，但指出某些服务（NextCloud、Immich、Minecraft服务器）仍需要人工干预，如维护模式、配置文件编辑、版本不匹配等问题 • **工具派**：通过特定技术栈实现超低维护，如NixOS（3年稳定）、Debian配合unattended-upgrade（可2年不管），甚至有人写Go程序自动监控维护 • **定义质疑派**：认为如果不需要频繁折腾，那就不再是"实验室"而是"稳定家庭基础设施"。真正的lab应该是不断尝试新硬件、学习新技术（如BGP、集群） 补充讨论：多位评论者强调稳定性对于家庭多用户场景的重要性（如配偶使用），这与企业环境的频繁更新策略不同。另有趣的是，多人期待AI agent自动维护，但原帖作者并未采用此方案。

Show HN: Pglayers – PostgreSQL extensions as stackable Docker layers

作者: iemejia | 评分: 39 | 评论数: 5 | 发布时间: 2026-07-01 16:50
文章摘要

pglayers 是一个 PostgreSQL Docker 扩展管理工具，解决了官方 PostgreSQL 镜像不包含扩展的问题。它提供两种方案：1) 预构建的完整镜像包含多个扩展；2) 通过 Docker 层叠加自定义选择扩展，无需编译。每个扩展作为独立镜像层发布，用户只需用 `COPY --from` 命令堆叠所需扩展到官方 postgres 镜像上。支持 PostgreSQL 17/18/19，提供 53+ 个扩展如 pgvector、PostGIS、pg_cron 等。

评论摘要
主要讨论点：pglayers 项目（PostgreSQL 扩展容器化方案）的技术实现和用户体验优化 不同观点： • **技术实现路线争议**：chatmasta 建议采用 PG18 的 extension_control_path 功能，通过运行时附加容器卷来加载扩展，避免构建"上帝镜像"；而 lanycrost 则认可当前使用 COPY --from 的分层组合方式，认为这是很好的设计。两者代表了"运行时动态加载"vs"构建时组合"的不同技术路线。 • **用户体验改进建议**：khurs 从产品角度提出两点建议：1) 为非技术用户添加 Docker Desktop GUI 快速入门指南；2) 购买独立域名替代 GitHub 域名，提升专业形象。 • **功能扩展需求**：securqbit 询问是否计划支持 pgvectorscale 扩展，hoppp 表达了对项目的需求和兴趣。 补充讨论：chatmasta 提到 CloudNativePG 团队为 PostgreSQL 核心贡献了 extension_control_path 功能，这是从"God images"模式向可组合模式演进的行业趋势，暗示 pglayers 可能需要跟进这一技术方向。
