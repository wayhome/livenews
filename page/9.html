MCP Server Could Have Been a JSON File

文章摘要

这篇文章质疑MCP（模型上下文协议）存在的必要性。作者认为MCP的核心功能（定义资源、工具和提示）可以用现有的标准（如OpenAPI、gRPC等）实现，且随着大模型上下文窗口的扩大（已达200万token），MCP可能只是临时解决方案。虽然MCP在企业内部服务文档不完善时可能有优势，但面向客户的SaaS API通常已有良好文档，使得MCP的附加价值有限。文章结论暗示MCP可能是技术发展过渡期的权宜之计。

评论摘要
主要讨论点：[MCP的优缺点及其是否必要的讨论] 不同观点： • **支持MCP的观点** - MCP的快速采用得益于其灵活性，可以通过本地MCP服务器作为现有API的代理，无需修改现有系统。 - MCP最初作为本地运行的“MCP Server”软件构件，配置简单，易于上手。 - REST或扩展REST API无法实现MCP的成功故事。 • **批评MCP的观点** - MCP缺乏标准化，例如没有像OpenAPI那样的统一JSON文件来描述整个MCP服务器，导致元数据交换和目录构建不标准化。 - OpenAPI虽然冗长，但可以通过优化（如简化或转换为UTCP格式）来满足LLM需求，无需另立标准。 - MCP的工具定义和资源定义过于简单（请求规范和响应定义），引发对其必要性的质疑。 • **替代方案的提议** - UTCP（https://www.utcp.io）被提出作为MCP的潜在替代方案，试图解决MCP的标准化问题。 - 可以通过“ curation ”（筛选）来优化OpenAPI文件，使其更适合AI消费，避免工具过多导致的混乱。 补充讨论： - **争议焦点**：MCP是否真的有必要，尤其是在远程API场景下，是否可以直接使用标准API协议（如REST）并优化元数据。 - **讨论关系**：pylotlight和reynaldi的评论直接回应了Fannon的观点，提出了替代方案和对MCP必要性的质疑。 - **其他注意点**：OpenAPI的冗长问题被提及，但认为可以通过技术手段解决，而非完全抛弃。
