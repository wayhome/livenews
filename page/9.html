Azure Linux 4.0 is Microsoft's first general-purpose Linux

作者: haydenbarnes | 评分: 203 | 评论数: 32 | 发布时间: 2026-06-05 03:14
文章摘要

微软在 Build 2026 上发布了 Azure Linux 4.0 公开预览版，这是首次允许用户在任何 Azure 虚拟机上运行该系统，而非仅作为 AKS 的底层主机。这标志着 Azure Linux 从专用设备发行版转变为通用 Linux 发行版。 4.0 版本基于 Fedora 43 构建，采用声明式覆盖层方式，不再手动维护每个软件包规范文件。主要更新包括：内核 6.18 LTS、dnf5 包管理器、glibc 2.42、systemd 258 等。支持虚拟机、容器、AKS 和 WSL 等多种部署场景。 Azure Linux 的特色在于可审计的供应链设计、强安全性（SELinux、FIPS 140-3 认证进行中）以及针对 Azure 优化。目前已被 Databricks、LinkedIn 等大规模采用。

评论摘要
主要讨论点：微软推出基于Fedora的Azure Linux发行版，声称为"通用目的"操作系统 不同观点： • **支持方观点**（rswail）：这是真正的通用系统，可运行容器、虚拟机或裸机应用；具备完整的SBOM供应链可追溯性，满足安全审计要求；采用只读OS设计。虽不支持随机硬件配置，但能在多种环境中运行通用应用 • **质疑"通用"定义**（froh, codycharris, reacweb）：认为这只是针对Azure优化的专用系统，不会在微软计算环境外运行；真正的通用OS应支持任意硬件并有厂商认证；实质是微软提供从WSL到云的统一Linux栈 • **批评微软动机**（bananaquant, egorfine, nullpoint420）：指责微软搭便车Red Hat的工作成果；将bleeding-edge发行版快照称为"通用"是误导，Fedora/RHEL本就有稳定性区分；怀疑是"拥抱-扩展-消灭"(EEE)策略，通过稀释"通用"术语来占领新领域 • **技术细节讨论**（aykutseker）：从tdnf迁移到dnf5值得关注，多数内部平台会越来越定制化而非通用化 补充讨论：部分评论充斥讽刺情绪，质疑微软的营销策略和AI生成内容的使用。争议焦点在于"通用目的"这一表述是否准确，以及微软的真实意图。

pg_durable: Microsoft open sources in-database durable execution

作者: coffeemug | 评分: 406 | 评论数: 21 | 发布时间: 2026-06-05 15:59
文章摘要

pg_durable 是微软开源的 PostgreSQL 扩展，在数据库内实现持久化执行（Durable Execution）。它让长时间运行的 SQL 函数具备容错能力，通过检查点机制在每步执行后保存状态，崩溃或重启后可从断点恢复，无需重新执行已完成的工作。 适用场景包括：向量嵌入管道、数据摄取、定时维护、并行聚合、外部 API 调用等。可替代 pg_cron + 状态表、外部编排器（Airflow/Temporal）、队列+工作者等传统方案，将工作流逻辑统一在 SQL 中管理，减少架构复杂度。 核心优势是消除部分失败后的手动恢复、避免长事务锁定、将重试和进度跟踪集中到 Postgres。不适合单条 SQL 语句、毫秒级同步请求，或需要复杂应用逻辑的场景。

评论摘要
主要讨论点：在 Postgres 中实现持久化工作流和队列系统的利弊 不同观点： • **支持派**：认为持久化执行是2024年最值得投资的技术，能解决精确一次执行、重试、信号驱动工作流等常见痛点。有人成功用 Postgres + PostgREST 构建了功能性作业队列。 • **质疑派-业务逻辑位置**：多位开发者质疑为何要将控制流和业务逻辑存储在数据库而非代码中。批评这类似存储过程，无法单元测试、版本控制困难、缺乏可观测性、难以隔离噪音工作负载、缺少 IO 能力（尤其是 API 调用）。 • **质疑派-工具对比**：认为 Apache Airflow 等 DAG 调度器、Temporal 等编排工具已经解决了这些问题，不理解为何需要基于数据库的方案。有人认为这是不必要的"内部平台效应"，如果编程语言支持确定性执行和状态序列化就不需要。 • **扩展性担忧**：指出数据库本就是最难扩展的基础设施，为何要增加长期运行任务的负担？ • **实际限制**：Azure Postgres 用户抱怨功能落后，无法使用现代特性。项目文档中明确不适用于跨多个异构系统的工作流，与 Temporal 的对比存疑。 补充讨论：代码优先 vs 数据库优先的开发偏好分歧明显；文档中一些实现细节（如超时处理、错误处理）不够清晰；AI 代理对消息队列代码更熟悉可能是潜在问题。

Changing how we develop Ladybird

作者: EdwinHoksberg | 评分: 838 | 评论数: 105 | 发布时间: 2026-06-05 07:26
文章摘要

Ladybird 浏览器项目宣布不再接受公开的 pull request，今后代码变更仅由项目维护者提交。这一改变主要出于两个原因：一是 AI 工具的普及让代码贡献不再能有效反映贡献者的可信度和投入程度，降低了通过贡献建立信任的传统机制；二是作为即将面向真实用户的浏览器，安全性至关重要，项目需要更严格的开发流程和明确的代码责任归属。项目仍保持开源，欢迎通过 bug 报告、测试、标准讨论等方式参与，但不会通过其他渠道接受代码补丁。所有现有的公开 PR 将被关闭。

评论摘要
**主要讨论点：** Ladybird浏览器项目宣布不再接受外部代码贡献后，社区对开源项目应对AI生成代码冲击的不同反应 **不同观点：** • **支持方**：认为AI降低了代码提交门槛，大量AI生成的PR让maintainer负担激增，代码量不再等同于付出的努力和诚意。项目有权优先保障质量和安全（Fraterkes, noIdeaTheSecond, mabedan） • **反对方**：认为这损害了开源精神，阻碍了新维护者的发现和培养；拒绝外部贡献意味着重复劳动，用户修复bug后无法直接贡献，只能让团队重新实现（nh2, koteelok, pulsartwin） • **中间立场**：理解资源有限团队的困境，但指出Chrome/Firefox等大型项目仍保持开放，值得肯定；担心失去社区的非代码贡献（想法、代码审查等）带来更大损失（domenicd, patates） **补充讨论：** - 有人质疑Ladybird作者本人也常提交大量未经审查的代码，决策存在双标（adrian17） - SQLite和Blender等成功项目早已采用类似封闭模式，这可能是大型项目的必然趋势（nathell, TeriyakiBomb） - 社区担忧这背离了Serenity/Ladybird原本的社区文化，希望至少保留未来参与的可能性（mvanveen, Deukhoofd）

文章摘要

lowfat 是一个轻量级 CLI 工具，通过过滤不必要的命令行输出来降低 AI 代理的 token 成本。它专注于本地化、可组合性和用户自主性，采用 UNIX 风格的管道设计。工具可将 git status、docker ps、ls 等命令的输出压缩 16%-96%，提供 lite/full/ultra 三个压缩级别。支持多种集成方式（Claude Code、shell、OpenCode、Pi agent），用户可通过 .lf DSL、shell 或 Python 编写自定义过滤器。相比 rtk 等同类工具，lowfat 采用最小核心 + 可扩展的设计理念，内置 6 个精选命令过滤器，用户可根据需求自行扩展。

评论摘要
主要讨论点：关于CLI输出过滤工具（如rtk、lean-ctx等）在LLM应用中的实际效果和价值 不同观点： • **支持派**：认为过滤工具有价值，可以减少token消耗和保持上下文清晰（wood_spirit分享了自己的工具经验，rahulyc建议用便宜模型做过滤，KuhlMensch表示这类工具有存在意义） • **怀疑派**：担心过滤会适得其反，导致agent混乱或丢失关键信息（jemmyw发现工具让agent更困惑、调用更多次，clutter55561质疑过滤后的输出与训练数据不符可能影响推理，devdoc83担心误删关键stack trace） • **方法论批评**：认为应该从源头解决问题而非事后过滤（fcanesin建议强制LLM自己写过滤器，tuo-lei指出根本问题是agent使用过于宽泛的命令如`kubectl get -o yaml`而非精确的jsonpath查询） • **准确性质疑**：cityofdelusion批评"节省91%token"的标题误导，强调这只是单一案例的输出token减少，不代表整体效果，呼吁proper benchmark和Amdahl定律分析 补充讨论：threecheese指出文档缺少实际行为示例和数据流图；tegiddrone提到MCP工具中JSON结构冗余问题；pradeep1177质疑coding agents是否真会执行低效命令
