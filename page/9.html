LibreCAD in the Browser

作者: devttyeu | 评分: 92 | 评论数: 11 | 发布时间: 2026-07-02 01:00
文章摘要

作者将开源2D CAD工具LibreCAD移植到浏览器中运行，使用GLM-5.2 AI模型辅助完成。通过Emscripten将C++/Qt源码编译为WebAssembly，实现了完整应用（非阅读器或简化版）的浏览器端运行。 核心技术挑战是处理模态对话框的嵌套问题。传统Asyncify方案只支持单层挂起，遇到嵌套对话框会卡死。最终采用JSPI（WebAssembly JavaScript Promise Integration）技术解决，支持任意深度的嵌套挂起。需要从源码编译Qt 6.9并启用JSPI和WebAssembly异常支持。 首次加载约18MB（Brotli压缩），之后浏览器缓存。目前仅支持Chrome/Edge 137+，因为Firefox和Safari尚未支持JSPI。整个移植过程展示了WebAssembly生态的成熟度和Qt对Wasm的良好支持。

评论摘要
主要讨论点：LibreCAD Web版的可用性、浏览器兼容性，以及Web应用与桌面应用的优劣对比 不同观点： • **技术问题方**：pockybum522遇到功能故障（Chrome 150无法绘图），gedw99解释需要Chrome/Edge 137+且启用WebAssembly JSPI支持 • **质疑Web化趋势方**：mrsssnake认为桌面版更优（仅82.7MB、无需账户、离线可用、系统统一更新），质疑为何要把桌面程序强行塞进浏览器 • **批评浏览器单一支持方**：drivingmenuts不满只支持Chrome，认为开发者不关心其他浏览器用户 • **推荐替代方案方**：felooboolooomba建议使用FreeCAD的Sketcher（支持约束），IshKebab推荐SolveSpace（已有Web版且更适合简单任务） • **支持者**：localdeclan表示感谢，认为对基础需求很实用；hersko简单点赞 补充讨论：争议焦点在于"便捷性"（无需安装、跨平台）与"实用性"（性能、兼容性、功能完整度）的权衡。技术门槛（需特定浏览器版本）降低了Web版的可访问性优势。

FoundationDB's Flow – Bringing Actor-Based Concurrency to C++11

作者: sourdecor | 评分: 75 | 评论数: 3 | 发布时间: 2026-07-02 14:41
文章摘要

Flow是FoundationDB开发的一种编程语言，旨在将actor并发模型引入C++11以应对高性能和可扩展性挑战。 Flow通过编译器将异步函数（actor）改写成使用回调的C++对象，避免阻塞操作。核心机制基于Promise和Future数据类型实现异步消息传递：Promise代表发送方承诺未来提供T类型值，Future代表接收方等待该值。 Flow引入了ACTOR、wait()等新关键字，使开发者能以同步风格编写异步代码。编译后生成标准C++11代码，最终编译为本地二进制文件。 Flow同时实现了三大工程目标：通过原生代码获得高性能、通过actor模型提高开发效率、支持确定性仿真测试以提升可靠性。

评论摘要
主要讨论点：FoundationDB 的发展困境与技术债务 不同观点： • **商业化与生态系统问题**（khurs）：FoundationDB 缺乏专业化运营，表现在网站质量低、文档不完善、缺少官方GUI工具。质疑苹果收购后是否限制了其发展，或者竞争对手数据库更具优势导致市场份额受限。 • **技术实现过时**（pjmlp）：指出代码库技术栈陈旧，当前 C++ 标准已到 C++23，而项目似乎未采用 C++20 引入的协程特性，这是更现代的异步编程方法。同时关注之前提及的 Swift 重写计划的进展。 • **历史讨论参考**（jen20）：提供了之前相关讨论的链接，暗示这是一个持续存在的话题。 补充讨论：评论反映出 FoundationDB 面临双重挑战：一是苹果收购后的战略定位和社区建设问题，二是技术债务积累。争议焦点在于其发展受阻的根本原因——是外部因素（苹果策略、市场竞争）还是内部因素（技术更新滞后、生态不完善）。

Claude-real-video － any LLM can watch a video

文章摘要

claude-real-video 是一个让大语言模型真正"观看"视频的本地工具。 **核心问题**：现有AI工具（ChatGPT、Claude）处理视频时只读字幕或固定间隔采样，会遗漏关键画面。 **解决方案**： - **智能帧提取**：基于场景变化检测提取关键帧，而非固定间隔采样 - **去重优化**：使用滑动窗口算法去除重复画面，减少冗余 - **音频转录**：通过Whisper将音频转为文字 - **本地处理**：所有操作在本地完成，无需上传 **使用方式**： ```bash pip install claude-real-video crv "YouTube链接" 或 crv 本地文件.mp4 ``` 输出：关键帧图片 + 字幕文本 + 清单文件，可直接导入Claude/ChatGPT/Gemini分析。 **技术要求**：需安装ffmpeg，支持macOS/Windows/Linux，Python 3.10+。

评论摘要
**主要讨论点**：关于使用Claude等大语言模型处理视频内容的可行性、成本和技术局限性 **不同观点**： • **成本效率质疑派**：认为使用Claude处理视频token消耗过高，建议改用Gemini或本地VLM模型。有用户直接指出这是"非常昂贵的视频观看方式" • **技术能力怀疑派**：核心争议是Claude能否真正"理解"视频。有用户明确指出"关键帧不是视频"，Claude无法从静态图像推断运动和物体持久性，只是在处理一组独立图片 • **实践效果分化派**： - 成功案例：ChatGPT通过帧差分析成功描述视频内容 - 失败案例：Claude处理DOS游戏精灵定位时，15-16个只对1-2个准确 - 部分成功：将帧组成网格图让模型查看效果较好，但仍遗漏细节 • **隐私担忧派**：质疑工具声称"视频留在本地"的说法，实际提取的帧会发送到Anthropic服务器 **补充讨论**： 有开发者分享了各种优化尝试（运动热图、模糊效果等）但效果不佳，最终发现直接文字描述反而更准确。另有用户提出将此作为评估模型运动理解能力的基准测试想法。
