文章摘要

本文由退役空军中校辛迪·塞拉诺·罗伯茨撰写，主张赋予军人"维修权"。作者以亲身经历说明，在伊拉克战场因无法自主维修关键设备（殡葬设施发电机）而险些造成严重后果，强调军队装备维修受制于承包商导致效率低下、成本增加且危及生命安全。目前美国国会正考虑将《战士维修权法案》纳入《国防授权法案》，该法案将允许军人自行维修设备，提供所需工具、零件和手册。文章指出维修权不仅能提升战备状态、保障军人安全、节省纳税人资金，更是培养军队自力更生文化的重要举措。

评论摘要
主要讨论点：军事装备维修权（Right to Repair, RtR）的必要性及其实现方式，以及国防采购和承包商问题。 不同观点： • **支持维修权立法** - 军事装备应具备用户可维修性（如越南军事博物馆的例子），减少对承包商和手册的依赖。 - 通过立法推动维修权，可能惠及民用领域（如jedberg的观点）。 • **市场杠杆解决维修问题** - 军事采购市场是寡头垄断（oligopsony），买方（如国家）应利用市场力量要求维修权（aleph_minus_one）。 - 军事需求足够大，可直接要求承包商提供可维修设计，无需依赖立法（alphazard）。 • **承包商与采购系统问题** - 承包商缺乏责任约束，设备质量差且维修成本高（如StephenHerlihyy提到的“无保修”问题）。 - 国防采购中存在腐败，合同设计应 incentivize 易维修设备（giantg2、lenerdenator）。 • **维修权的技术扩展** - 应要求承包商提供源代码和设计所有权，以支持系统迭代（arh68、jauntywundrkind）。 • **争议焦点** - 维修权的实际范围：是否包括物理部件维修或软件控制（fn-mote）。 - 维修能力的现实限制：即使有权维修，缺乏技术或备件仍无法解决问题（gwbas1c）。 补充讨论： - 政治经济因素：政府倾向于延迟支付（如服务合同）以隐藏债务（LatteLazy）。 - 讽刺性观点：军事工业复合体可能意外推动民用维修权（bluSCALE4）。 - 系统性改革呼声：需政府干预市场滥用（scotty79）。

About Containers and VMs

作者: Bogdanp | 评分: 105 | 评论数: 9 | 发布时间: 2025-08-25 07:58
文章摘要

本文主要比较了Incus支持的三种虚拟化技术：系统容器、应用容器和虚拟机。系统容器通过Linux内核特性（如命名空间和cgroups）实现隔离，共享主机内核，适合运行完整操作系统环境；应用容器（如Docker）仅打包单个应用，依赖主机内核；虚拟机则利用硬件虚拟化运行独立内核，可运行不同操作系统，但资源消耗更大。系统容器比虚拟机更轻量高效，适合与主机内核兼容的场景；当需要不同OS或特殊功能时，应选择虚拟机。

评论摘要
主要讨论点：[虚拟化技术（VM与容器）的差异、安全性及实际应用] 不同观点： • [虚拟机（VM）与容器的定义与区别] - hliyan：虚拟机让操作系统以为独占机器，容器让进程以为独占操作系统。 - mappu：虚拟机不一定需要硬件虚拟化，MMU即可实现完全隔离，并举了Alibaba的PVM和QEMU的TCG为例。 • [容器与虚拟机的用户体验] - scottyeager：Incus提供了类似容器的虚拟机体验，操作简便（如文件拷贝、Shell访问），但需虚拟机内运行代理。 - skywhopper & jiggawatts：质疑容器只能运行单个应用的说法，指出Docker容器可以托管多进程/服务，并批评页面表格中的错误（如忽略Windows容器）。 • [安全性争议] - reilly3000：询问系统容器是否比应用容器更安全。 - Ericson2314：批评内核干涉导致用户态“中间件”项目泛滥，希望Capsicum提供更合理的默认安全设置。 • [其他技术对比] - kottapar：指出Incus与BootC类似，但后者是不可变的。 补充讨论： • 域名争议：jiggawatts和skywhopper质疑“linuxcontainers.org”域名被Incus/LXC独占使用，认为其内容过于偏向特定项目。 • 幽默观点：worik以调侃方式表达对Docker的偏好，实际未提供实质性论据。

Malicious versions of Nx and some supporting plugins were published

作者: longcat | 评分: 429 | 评论数: 54 | 发布时间: 2025-08-27 01:38
文章摘要

Nx项目多个npm包（包括nx、@nx/devkit等）的21.5.0、20.9.0等特定版本被发现含有恶意代码，会扫描文件系统并窃取凭证上传至GitHub。漏洞源于一个存在Bash注入缺陷的GitHub工作流（可执行PR标题中的代码）和过度宽松的pull_request_target权限设置。攻击者利用这些漏洞获取了npm发布权限，上传了恶意版本。目前所有受影响版本已从npm下架。项目组建议用户检查是否安装了受影响版本，并立即升级到安全版本。

评论摘要
主要讨论点：[软件供应链安全、依赖管理、攻击防御措施] 不同观点： • **禁用安装脚本**：建议通过 `npm config set ignore-scripts true` 禁用 npm 安装脚本，以减少供应链攻击风险。认为当前大多数合法包无需安装脚本即可运行，对于需要脚本的包可单独处理。 • **减少依赖**：主张在添加新依赖前仔细考虑，尽可能自己编写简单功能。举例通过 LLM 生成一个简单的进度条代码，避免了引入复杂依赖。 • **安全机制缺失**：指出当前包管理器缺乏必要的安全机制，如代码签名、MFA、令牌管理等，认为这是行业整体失败，需要建立类似建筑规范的强制安全标准。 • **沙盒环境**：建议在虚拟机或容器中运行不信任的代码，特别是对于具有高风险的应用程序（如 NodeJS 应用、通过 shell 脚本安装的工具）。 • **包管理器改进**：提出包管理器应引入“最小年龄”设置，忽略新发布的包以减少风险。同时建议操作系统限制应用程序的默认文件系统访问权限。 补充讨论： • **新型攻击方式**：讨论了使用本地 LLM 通过提示词进行攻击的新形式，这种攻击绕过传统静态分析，难以防御。 • **实际案例**：提到 Grafana 的安全事件，以及 VS Code 插件通过运行 `npx` 命令被攻陷的案例，显示攻击的普遍性和易发性。 • **行业反应**：批评 Anthropic 在宣传其 AI 防犯罪能力的同时，其工具本身存在多个安全漏洞，显得 hypocritical。 • **潜在威胁**：担忧开源软件供应链攻击可能比已知的更普遍，特别是国家行为体可能利用广泛使用的依赖注入后门。 争议焦点： • **责任归属**：部分评论认为攻击成功是由于包管理器和开发者的安全措施不足，而另一些则强调攻击者的创新手段（如利用 LLM）使得传统防御无效。 • **解决方案的有效性**：禁用脚本和减少依赖是否足以应对日益复杂的攻击，还是需要更根本的系统性改革（如强制安全规范）。
