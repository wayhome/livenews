TOON – Token Oriented Object Notation

作者: royosherove | 评分: 147 | 评论数: 20 | 发布时间: 2025-10-26 22:19
文章摘要

TOON（Token-Oriented Object Notation）是一种专为大型语言模型设计的紧凑、可读的数据格式，能显著减少结构化数据的令牌使用量。相比JSON，TOON通常减少30%-60%的令牌消耗，通过简化语法（去除冗余标点）、基于缩进的结构和表格化数组等特性实现高效传输。TOON还提供明确的长度和字段列表，帮助模型验证输出。例如，一个包含用户数据的JSON对象用TOON表示可节省56.9%的令牌。TOON适用于需要高效传递结构化数据的AI应用场景，支持npm等包管理器安装。

评论摘要
主要讨论点：[TOON格式与JSON的比较及其在LLM中的适用性] 不同观点： • **支持TOON格式的观点** - 认为TOON通过更简洁的语法（如长度标记`[0]`）可以进一步减少语义模糊性（inopinatus）。 - 赞赏其创新性，认为压缩格式可能提升效率（andreygrehov、awaseem）。 • **倾向于JSON的观点** - 认为JSON已经是主流且LLM对其优化更好，新格式可能影响准确性（vessenes）。 - 提出通过JSON的紧凑表达（如列表或字符串拼接）也能达到类似效果（3cats-in-a-coat）。 - 质疑TOON的鲁棒性，尤其是基于缩进的格式（chuckadams）。 • **其他替代方案建议** - 提出类似Lisp的括号语法可能更简洁且无需特殊标记（neilv）。 - 建议比较其他格式如YAML、BAML、TOML或固定宽度文本（AvAn12、hedgehog）。 - 讨论属性名是否需引号以节省token（rs186）。 补充讨论： - **争议焦点**：TOON的实际收益 vs. JSON的主流适配性（vessenes vs. 3cats-in-a-coat）。 - **技术细节**：LLM对压缩数据的训练与推理可行性（andreygrehov）、缩进格式的脆弱性（chuckadams）。 - **无关讨论**：README字体（metalliqaz）、空格添加建议（anonymoushn）。

本文介绍了一种小型、灵活且可扩展的JSON查询语言，主要内容包括： 1. 核心功能：提供过滤(filter)、排序(sort)、选取(pick)等链式操作方法，支持管道(pipes)串联多个查询步骤 2. 语法要素： - 函数调用：如filter(.age >= 21) - 运算符：比较、逻辑、算术运算等 - 属性访问：.prop1.prop2格式 - 值类型：支持JSON所有原始类型 3. 特色功能： - 对象和数组转换操作 - 分组、聚合计算 - 字符串处理 - 条件判断 4. 使用方式：通过Playground在线测试，提供详细文档和函数参考 该语言设计简洁，可通过组合基础操作实现复杂JSON数据查询和处理需求。

评论摘要
主要讨论点：[JSON查询工具的比较和选择] 不同观点： • **jq的流处理模式** - jq的核心是流处理（stream of independent JSON terms），不是单纯的JSON列表操作 - 关键概念：`.`指向当前流元素，`select`和`map`的区别（流 vs 列表） - 支持者认为理解流编程范式后效率极高（@nothrabannosir, @cryptonector, @gcr） • **其他JSON查询工具的替代性** - JSONata：功能强大但查询语法晦涩（@pscanf, @jawns） - JSONPath：标准化程度高但灵活性不足（@HatchedLake721） - DuckDB/Malloy：用SQL或类SQL语法查询JSON（@mrtimo） - JavaScript原生：直接使用JS语法更通用（@ccvannorman, @hyperhello） • **结构化查询的工程需求** - 需要API友好、可代码化的结构化表示（如JSONLogic）（@eknkc） - 安全沙箱（如QuickJS）对JS方案是必要但复杂的（@pscanf） 补充讨论： - **争议焦点**：是否值得学习jq的独特范式 - 支持方：流处理思维能解锁高级功能（@cryptonector） - 反对方：JavaScript等通用语法更易上手（@hyperhello） - **小众方案**： - 作者自定义语言的合理性（@kunley） - 面向LLM优化的极简查询语言（@memelang） - **命名调侃**：jQuery的商标问题（@cweagans）

Cancer Survival Rates Are Misleading

作者: speckx | 评分: 10 | 评论数: 0 | 发布时间: 2025-10-28 17:59
文章摘要

这篇文章指出医学中常用的五年生存率存在严重误导性，主要观点包括： 1. 五年生存率不能准确预测个体患者的实际预后，因为它基于历史数据，受治疗手段进步、诊断方式变化等因素影响。 2. 早期诊断的高生存率并不自动证明筛查的价值，必须满足三个条件： - 筛查发现的癌症确实会发展为致命疾病 - 现有治疗能有效预防不良后果 - 筛查收益大于过度诊断等风险 3. 生存率差异可能反映诊断时间偏差（lead-time bias）和病程长短偏差（length bias），而非实际治疗效果。 文章警告医学工作者和公众要谨慎解读生存率数据，避免得出"早期发现必然提高治愈率"等错误结论。

Pass-by-Value Overhead

作者: todsacerdoti | 评分: 52 | 评论数: 3 | 发布时间: 2025-10-28 00:52
文章摘要

这篇文章通过基准测试分析了C语言中按值传递(struct by value)的性能开销。作者测试了不同大小结构体的传递性能，发现：小型结构体(32字节以下)的按值传递开销很小；256字节以下使用向量化内存拷贝；257字节以上改用`rep movs`指令；1682字节后出现周期性性能波动(每32字节周期)。结果显示按值传递的开销与数据大小成正比，但对小型结构体来说差异可忽略。

评论摘要
主要讨论点：[编程中的性能优化和实现细节] 不同观点： • **jklowden** 强调“传值”是语义概念而非实现细节，编译器可以根据需要优化，不一定实际复制数据。传递 const 引用在 C++ 中也是传值的一种形式，关键在于语义而非具体实现。 • **anonymous908213** 对特定 CPU 缺陷（AMD Ryzen 3900X 在特定数据大小下的性能问题）表示好奇，暗示硬件实现可能影响编程中的性能优化决策。 • **codedokode** 分享了使用 ChatGPT 快速生成微基准测试代码的经验，提到在特定场景下（如小规模有序数组查找），分支无关的线性扫描可能比二分查找更快，强调了实际测试的重要性。 补充讨论： - **争议点**：jklowden 的观点可能引发关于“传值”语义与编译器优化权限的讨论，是否所有场景下编译器都能安全忽略复制操作？ - **实践建议**：codedokode 的方法展示了工具（如 LLM）如何加速性能探索，但需注意防止编译器过度优化（如手动添加 workaround）。
