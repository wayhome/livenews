Cell-based architecture for resilient payment systems

作者: birdculture | 评分: 142 | 评论数: 21 | 发布时间: 2026-06-15 22:36
文章摘要

美国运通核心支付系统采用**基于单元的架构**（Cell-Based Architecture）来确保全球支付平台的高可用性和低延迟。每个单元是独立的部署单元，包含自己的微服务、数据库和组件，可独立处理支付交易。 **核心设计原则**： - **故障隔离**：单元之间相互独立，一个单元故障不会影响其他单元 - **数据本地化**：静态数据预先复制到各单元，避免处理时的远程调用 - **无跨单元同步依赖**：关键交易路径中不存在单元间的同步依赖 - **区域边界**：单元不跨多个区域，所有组件保持本地 这种架构虽增加了管理复杂度，但显著降低了故障影响范围，提升了系统韧性、降低了延迟，并支持通过增加独立单元来扩展处理能力。对于任务关键型支付系统，收益远超成本。

评论摘要
主要讨论点：对Amex基于cell架构的支付系统设计的技术评价 不同观点： • **批评派**：认为文章缺乏实质内容，未解释中间层功能、路由机制和数据同步，只是学了Kubernetes就写抽象概念（Insimwytim）；Global Transaction Router是单点故障隐患（nightshift1）；cell故障后重路由到另一个cell会导致相同错误，本质是用重试循环掩盖已有问题（chmod775） • **谨慎肯定派**：设计思路不错，但Amex可能将可用性优先于正确性，依赖事后对账处理；全局路由器的状态更新与异步故障转移数据分发之间存在时间窗口风险，可能路由到错误cell；文章未说明路由器本身的高可用方案（physix） • **技术类比派**：认为这是重新发明Erlang监督树（rdtsc）；所有微服务/集群/分区本质都是cell架构（mkhalil）；这是2022年的老概念（amne）；类似区块链支付的简化版（bozhark） • **冷嘲热讽派**：讽刺"我们把单体拆成微服务现在后悔了"（daxfohl）；质疑持久性保证和备份复杂度（neerajsi, stevefan1999）；吐槽Amex产品体验差、风控过度敏感（badlibrarian） 补充讨论：多位评论者认为此架构并非创新，Reddit已有讨论；有人因403错误未能阅读原文，以为是分布式支付网络

The AirPods Effect

作者: herbertl | 评分: 405 | 评论数: 100 | 发布时间: 2026-06-18 23:08
文章摘要

这篇文章探讨了 AirPods 等无线耳机对社会交往的影响。作者发现美国人佩戴耳机的现象极为普遍，这导致人际交流减少、社交隔离感增强。研究显示，重度耳机使用者更容易感到孤独，也更不愿与陌生人交谈。大学生用耳机来回避社交互动，在校园、办公室、商店等场合都戴着耳机，减少了自发的人际接触。作者认为，虽然耳机带来便利，但它们正在微妙地改变我们的信念，强化不安全感，并使人们彼此疏远。这种"舒适泡泡"正在侵入越来越多的日常场景，削弱了面对面交流的机会。

评论摘要
主要讨论点：耳机使用是否导致社会隔离，以及在公共空间中的社交规范变化 不同观点： • **耳机是应对不自然环境的合理方式**：拥挤嘈杂的公共交通本身就不自然，耳机帮助人们将环境"正常化"。地铁噪音、乞讨者、嘈杂音乐等让佩戴耳机成为必需，这是系统问题而非个人自私 • **文化差异而非技术问题**：不同文化对陌生人交谈的接受度本就不同。德国人在公共交通上很少交谈，美国人更健谈。耳机出现前这种差异就存在，不应归咎于技术 • **因果关系存疑**：可能是社交焦虑和孤独感驱使人们戴耳机，而非耳机导致孤独。相关性不等于因果性 • **个人选择权利**：人们有权选择舒适和专注，只要在与人交谈时摘下耳机就不算无礼。不是每个人都喜欢或需要与陌生人闲聊 • **过度社交的反思**：长期与陌生人交谈后发现对话往往肤浅重复，深度阅读可能比短暂闲聊更有价值 补充讨论： 有人提到错失"默认模式网络"时间（发呆、白日梦）可能影响创造力和问题解决能力；也有人担心耳机削弱情境感知能力带来安全隐患；听力受损者使用耳机/助听器引发的社交误解也值得关注

.gitignore Isn't the only way to ignore files in Git

作者: FergusArgyll | 评分: 564 | 评论数: 38 | 发布时间: 2026-06-18 10:29
文章摘要

Git 有三种级别的文件忽略机制： 1. **`.gitignore`** - 项目级别，随代码一起提交，团队共享 2. **`.git/info/exclude`** - 仓库级别，不提交到 Git，适合个人工作流文件（如个人笔记） 3. **`~/.config/git/ignore`** - 全局级别，影响机器上所有仓库，适合系统文件（如 macOS 的 `.DS_Store`） 可用 `git config --global core.excludesFile` 自定义全局忽略文件位置。使用 `git check-ignore -v <文件名>` 可查看某文件被哪个配置忽略。

评论摘要
主要讨论点：Git忽略文件的多种方式及其适用场景 不同观点： • **全局忽略 vs 项目忽略**：kevincox强调IDE/OS特定文件应放在用户全局配置（~/.config/git/ignore）而非项目.gitignore中，避免污染每个项目；而dofm认为像.DS_Store这类文件若团队有多个Mac用户，放在项目.gitignore更合适 • **文件放置位置的哲学分歧**：rlpb认为在源码树内放构建产物本身就是历史错误，应避免这种设计；但多数评论者接受现状，讨论如何用各种ignore机制管理 • **配置路径规范**：hk1337主张用~/.config/git/作为标准位置而非~/.gitignore_global，保持根目录整洁；wpollock澄清git的"global"实为per-user而非machine-wide 补充讨论： 实用技巧分享：judofyr创建"attic"全局忽略目录存放临时文件；rmunn用"scratch"目录+内部.gitignore避免个人笔记污染；hungryhobbit介绍.gitattributes的-diff功能隐藏package-lock.json等噪音；elyobo分享assume-unchanged别名；leleat提及skip-worktree用于已跟踪文件的本地实验 多位开发者（lmf4lol, stevage）表示从业多年才发现.git/info/exclude，反映该功能知名度不足。Hendrikto批评文章内容过于基础。
