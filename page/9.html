How Generative Engine Optimization (GEO) rewrites the rules of search

作者: eutropheon | 评分: 63 | 评论数: 12 | 发布时间: 2025-05-30 05:48
文章摘要

文章讨论了生成引擎优化（GEO）如何改变搜索规则，标志着传统SEO时代的终结。随着AI语言模型（如GPT-4o、Gemini和Claude）成为信息获取的主要接口，搜索正从基于链接的系统转向基于语言理解的系统。传统SEO依赖关键词和链接提升页面排名，而GEO则注重内容质量和结构，以适应AI回答的需要。 生成引擎搜索更加个性化和多源化，答案格式变化导致搜索方式的改变。LLM市场以订阅为主，与传统搜索的广告驱动模式不同，品牌的可见性不再只依赖点击率，而是模型引用率。新平台和工具帮助品牌分析和优化在AI生成内容中的表现，监测模型如何提及和描述品牌。这使得GEO成为衡量品牌在AI时代表现的关键指标，如同传统SEO的仪表板一样重要。

主要讨论点：AI在搜索和推荐系统中的应用及其相关问题 不同观点： • **AI答案的稳定性和一致性问题**： - [edwin] 指出AI模型的答案经常变化，即便是相同查询，Google的"AI模式"和ChatGPT只有约47%的情况下会给出相同的首条推荐。此外，ChatGPT自身的答案也会因是否依赖实时检索而不同。 • **AI和传统搜索的规模对比**： - [rafaepta] 认为ChatGPT在搜索量和使用场景上与Google有巨大差距（Google约140亿次/天，ChatGPT约3700万次/天），且ChatGPT的提示中只有15%类似于传统搜索，因此对流量和收入的短期影响有限。 • **AI的纯净性和未来发展**： - [jameslk] 认为当前的AI处于未被营销和宣传完全污染的阶段，类似1990年代的早期网络，未来AI将不再如此纯粹和实时。 • **SEO及其负面影响**： - [kurtoid] 认为SEO及其相关领域对互联网甚至人类整体是负面的。 • **AI对搜索机制的理解问题**： - [bigbuppo] 对"传统搜索基于链接，生成式AI搜索基于语言"的说法提出质疑，认为对搜索机制的理解有偏差。 • **AI反馈循环和内容优化问题**： - [gmuslera] 担心LLM优化内容以适应基于LLM的搜索引擎的反馈循环会导致不良后果。 • **AI答案的可信度问题**： - [arnklint] 指出即便有参考来源，AI有时仍会得出与来源相反的结论，信任AI提供真实答案是个问题。 • **AI的用户参与与事实准确性平衡问题**： - [nocoder] 认为LLM过于迎合用户，优先考虑用户参与而非答案的准确性，可能导致回声室效应，即根据用户偏好提供不同信息。 • **AI在商业和营销中的应用前景**： - [corentin88] 提出在AI成为商业和发现的主要入口的情况下，营销人员如何让模型记住品牌并脱颖而出是一个关键问题。 - [meander_water] 提到在Fiverr上看到大量提供生成性AI营销服务的人，暗示市场对此有需求。 - [sbrother] 分享了自己的AI产品在beta测试中得到的积极反馈，认为中小企业主正在寻求在这个领域领先。 补充讨论： - [bravesoul2] 对文章开头引用R.E.M.的歌词作出轻松评论，未涉及核心讨论点。 争议焦点： - AI答案的一致性和可信度问题，特别是在商业推荐和搜索结果中的应用。 - AI在搜索中的实际影响力和未来发展方向，以及如何平衡用户参与和事实准确性。

Progressive JSON

作者: kacesensitive | 评分: 487 | 评论数: 60 | 发布时间: 2025-06-01 00:58
文章摘要

文章探讨了一种称为“渐进式JSON”的数据传输方法，灵感来自渐进式JPEG图片加载。传统JSON需要完整接收后才能解析和使用，导致如果某个部分（如数据库查询）较慢，客户端必须等待整个数据传输完成。文章提出了一种流式JSON解析器，可以在数据不完整时部分解析，但这种方法存在对象不完整、类型不匹配的问题，使用起来较复杂。 为解决此问题，文章提出“渐进式JSON”方法，采用广度优先传输策略，先传输对象的占位符，再逐步填充内容。例如，先传输顶层结构，再异步填充具体内容，这样即使某部分数据生成较慢，也不会阻塞其他部分的传输和显示。这种方法类似于渐进式图片加载，能提高数据传输效率和用户体验。

评论摘要
主要讨论点：React Server Components (RSC) 及其相关的渐进式 JSON 流处理的可行性和必要性 不同观点： • **支持 RSC 和渐进式 JSON 的观点**： - **goranmoomin**：解释了 Dan Abramov 的文章实际上是在解释 React Server Components 的概念，而不是提出一个新的 JSON 格式。React Server Components 允许在组件树中留空，以显示加载状态，从而提高用户体验。渐进式加载可以让页面更快速地显示基础内容和占位符。 - **xelxebar**：支持渐进式加载的概念，认为这种方法可以应用于任何树状数据结构，通过先发送头信息，再分批发送数据块，可以显著提升加载速度。 - **bilater**：认为渐进式 JSON 流应该是 JavaScript 环境中的一等公民，特别是在处理大模型输出时，这种流式处理非常有用。 • **质疑 RSC 和渐进式 JSON 的观点**： - **jatins**：质疑 RSC 的必要性和抽象复杂性，指出许多前端开发者仍不理解 RSC 的概念，且其推广可能更多是为了迎合某些厂商的平台需求，而非真正满足用户需求。 - **Velorivox**：认为绝大多数应用不需要如此复杂的解决方案，简单的多次调用即可解决大多数问题。 - **turtlebits**：认为文本/HTML 不像媒体文件那样需要渐进式加载，这种方法似乎是为解决自身体系复杂性而引入的额外复杂性。 • **替代方案和改进建议**： - **jerf**：提出了两种替代方案，一是重构 JSON 格式，二是保证属性顺序，以实现渐进式解析，而不需要引入复杂的流式处理。 - **atombender**：建议使用 Mendoza 格式进行增量更新，这种方法可以通过发送增量数据来减少传输量，同时保持高效的解析和更新。 - **rictic**：推荐使用 jsonriver 工具来进行渐进式 JSON 解析，提供了一种简单易用的 API。 - **camgunz**：认为通过不同的端点设计可以解决大部分问题，包括缓存、过滤、实时更新等，而不需要复杂的文档系统应用平台。 - **jarym**：支持使用 JSON Patch 和行分隔 JSON，认为这种方法更容易理解和实现。 - **aljow**：认为如果需要对 JSON 进行如此复杂的处理，可能 JSON 本身就不是适合的格式，应该重新考虑数据格式设计。 补充讨论： • **渐进式加载的具体实现和技术细节**： - **pjungwir**：提出了如何在数组中实现渐进式加载的设想，通过 Promise 和异步生成器来实现数组的流式处理。 - **hyfgfh**：指出性能问题的根源可能在于架构设计和 API 设计，而不是简单的框架或工具选择，认为需要更基础的 web 标准演进才能解决根本问题。 争议焦点： • **RSC 的必要性和复杂性**：一方认为 RSC 提供了更好的用户体验和加载性能，另一方则认为其复杂性过高，且许多开发者并不理解其真正用途。 • **渐进式 JSON 的实用性**：一方认为这种方法可以显著提升性能和用户体验，另一方则认为对于大多数应用来说，这种复杂性并不必要。 总结：讨论围绕 React Server Components 和渐进式 JSON 流处理的可行性、必要性及其实现细节展开，参与者提出了支持和质疑的观点，并讨论了多种替代方案和技术实现细节。争议主要集中在 RSC 的复杂性和其实际应用价值上。

文章摘要

东亨德雷德村的圣奥古斯丁教堂钟楼时钟已运行500年，被认为是英国最古老的仍在原址运行的时钟之一。该时钟没有钟面，通过教堂钟声每刻报时，并通过一个类似巨大音乐盒的装置每天四次播放曲子。2015年，时钟因故障停摆，经过修复和安装自动上弦系统后恢复运行。本周，村民们庆祝了时钟500周年，并有机会参观其运行机制。尽管受天气影响，时钟的精准度在历史上相当出色。

Figma Slides Is a Beautiful Disaster

作者: tobr | 评分: 395 | 评论数: 39 | 发布时间: 2025-06-01 05:59
文章摘要
