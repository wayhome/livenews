Stealing Is a Skill

作者: bewal416 | 评分: 244 | 评论数: 63 | 发布时间: 2026-06-24 13:08
文章摘要

这篇文章阐述了"偷窃是一种技能"的观点。作者受到已故创意人 Virgil Abloh 提出的"3% 方法"启发——通过复刻他人作品来学习其精髓，然后只修改 3% 使其成为自己的创作。作者和同事在重建营销网站时，逐像素复刻了 Mintlify 的网站设计，在这个过程中深入理解了每个设计决策背后的逻辑。通过"偷窃"学习，他们最终找到了属于自己品牌的那 3% 差异化元素。作者认为，职业成功不在于创意的原创性，而在于高效识别和解决问题——而聪明人往往已经做过类似的事。因此，应该将"偷窃"变成一种技能：识别该偷什么、为何偷、偷多少。

评论摘要
主要讨论点：在设计和创作中"借鉴/抄袭"的边界问题 不同观点： • **反对直接抄袭派**：认为像素级复制他人商业网站是剽窃和盗窃行为，与真正的"伟大艺术家偷窃"概念不同。真正的"偷窃"应该是提取不可见的核心理念，而非表面复制（rglover, sandcat_, agilek, emaro） • **支持临摹学习派**：将这种做法类比为写作中的copywork练习、音乐家抄写爵士乐独奏、儿童学习语言的模仿过程。认为逐字复制是理解大师作品的有效方法，能提升自身技能（dghlsakjg, pseudosavant, darepublic, bingoMen） • **条件支持派**：认可临摹作为练习手段的价值，但强调应从多个来源综合借鉴、加入自己的创新，而非单纯复制一个作品。区分练习性质和商业用途（dinkleberg, meander_water） • **情境区分派**：指出在市场环境中这是盗窃，在社区传统中则是学习。艺术和传统在被拖入市场竞争前不是竞争关系（erikschoster） 补充讨论：多位评论者引用"好的艺术家复制，伟大的艺术家偷窃"这句话，但对其解读截然不同。争议焦点在于：商业环境下的像素级复制是否能被视为正当的学习手段。

这篇文章讲述了1995年左右，高中生Matt Wright创建了Matt's Script Archive网站，分享简单的网站工具（如留言板、访客簿、计数器）。其中WWWBoard成为早期广泛使用的论坛软件。虽然这些脚本满足了普通用户需求，但存在严重的安全漏洞和设计缺陷。2001年，伦敦Perl程序员组织推出nms项目，提供更安全的替代版本。文章指出，当某个工具被广泛使用后，安全问题不可避免会暴露。作者认为不应责怪Wright（他当时还是学生），但这揭示了普通用户需求与开发者专业标准之间的矛盾，以及广泛传播的不安全代码对互联网安全的长期影响。

评论摘要
**主要讨论点：** Matt's Script Archive在90年代的影响力及其技术遗产的评价 **不同观点：** • **怀旧与启蒙派**：多位开发者（jamiecurle、arscan、knadh等）认为Matt's Scripts是职业生涯的起点，formmail.pl等脚本让他们第一次接触动态网页开发，代码可读性强，具有教育意义，是"magical"的学习经历 • **安全批评派**：ISP工作人员（Twirrim）指出这些脚本安全性极差，在2000年代中期成为"噩梦"，经常被用于垃圾邮件中继，需要频繁清理 • **时代语境辩护派**：madrox强调不应用现代标准评判90年代作品，当时网络环境完全不同——没有大规模bot扫描、工业化恶意软件，黑客攻击更多是"炫技"而非牟利，将"vibe coding"与WWWBoard类比忽视了时代差异 • **实用主义观察派**：CM30提出关键洞察——技术质量差的工具仍会流行，只要它解决了未被满足的需求。专业开发者鄙视的"Frankenstein代码"往往因填补空白而广受欢迎 **补充讨论：** 有人尝试通过"Not Matt's Scripts"项目重写安全版本；这些脚本在当时教程中被广泛推荐；有建议建立"历史网站保护协会"来记录这段互联网历史

I can haz smoller NixOS ISOs?

文章摘要

这篇文章讲述了作者如何精简 NixOS Live ISO 镜像的过程。作者首先展示了 NixOS 可以轻松创建虚拟机和 ISO 镜像的特性，但发现基础 ISO 竟然有 458MB，远超预期。通过分析发现主要空间被 squashfs 文件系统（416MB）、initrd（26MB）和内核（13MB）占用。作者进一步挖掘 squashfs 内容，发现 Python、Systemd、Perl、glibc 等组件占用了大量空间。相比之下，Alpine Linux 的 ISO 只有 66MB，这促使作者开始移除不必要的功能以缩小镜像体积。

评论摘要
主要讨论点：NixOS系统镜像的精简化与定制化探索 不同观点： • **积极探索派**（arikrahman, craftkiller）：赞赏NixOS的灵活性，通过切换内核（如Cachy）或构建精简ISO来优化系统。craftkiller从源码构建以减少镜像体积和编译时间 • **实用主义者**（siraben）：成功将ISO压缩至91MB，但指出极端精简带来的代价——失去网络、配置切换和文本编辑器等基本功能 • **质疑派**（xyzzy_plugh）：对禁用Nix本身的做法表示怀疑，认为若不想安装Nix，或许从头构建镜像比扭曲NixOS更简单 • **技术局限关注**（nylonstrung）：指出Perl、Python和Bash作为核心依赖是个问题 补充讨论： • lordkrandel正从Arch迁移到NixOS，通过Distrobox入手 • whazor提出将此方法用于创建distroless容器的可能性 • ChrisRR和overtone1000关注文章的语言风格细节（"Can haz smol"和interrobang符号） 争议焦点：精简NixOS的边界在哪里——过度精简是否违背了使用NixOS的初衷？

LuaJIT 3.0 proposed syntax extensions

文章摘要

这是一个关于 LuaJIT 3.0 语法扩展的 GitHub issue。作者 MikePall 创建了这个总括性 issue，用于讨论和记录 LuaJIT 3.0 的语法扩展。 **主要目标：** - 仅添加已在其他语言中得到验证、能提升开发体验的语法扩展 - 不破坏向后兼容性，不引入语法歧义 - 不增加工具开发难度 作者欢迎建设性反馈，但明确表示不会采纳所有提议，也不打算引入像 Perl、Ruby、C++ 或 Rust 那样复杂的语法。未来会提供完整的语言文档，标注各扩展首次出现的版本。

评论摘要
主要讨论点：LuaJIT 3.0 引入新语法扩展（三元运算符、复合赋值、替代运算符等）引发的兼容性和语言定位争议 不同观点： • **支持语法改进派**：欢迎 += 和 ..= 等复合赋值运算符，认为这是实用的生活质量改进。三元运算符比现有的 `x and y or z` 写法更清晰。这些改进参考了其他语言的成熟实践 • **反对语法分裂派**：认为改变 `and` 为 `&&` 等语法毫无必要，只是让 Lua 不再像 Lua。批评这会造成"一件事多种写法"的混乱，增加学习和维护成本。类比为"给 Python 加花括号" • **要求更名派**：多位评论者指出 LuaJIT 已不再是兼容 Lua 5.1 的实现，而是一门新语言，应该有新名字。认为这种分裂对 Lua 生态系统有害，甚至是"hostile"的行为 • **技术实现建议**：建议用 `if x then y else z` 替代 `x ? y : z`（参考 Luau）；建议标准化 LuaJIT 字节码以支持自定义前端；反对三元运算符占用 `?` 符号，影响安全导航运算符的简洁性 补充讨论：有人指出 Lua 5.3 早在 2015 年就加入了位运算符，LuaJIT 只是在追赶。Lua 生态的特点是实现版本多样但库生态有限，这次改动可能加剧碎片化。
