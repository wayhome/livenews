Using HTTP/2 Cleartext for a server in Go 1.24

作者: dan_sbl | 评分: 102 | 评论数: 6 | 发布时间: 2026-05-19 16:40
文章摘要

这篇文章讲述了在Google Cloud Run上使用HTTP/2解决SSE长连接问题的实践。由于Cloud Run在HTTP/1.1下无法正确传播客户端断开连接，作者改用HTTP/2 cleartext (h2c)。文章对比了Go 1.24前后的配置方法：旧版需要使用`x/net/http2/h2c`包进行复杂封装，新版则可直接在`http.Server`上配置`Protocols`，大幅简化了代码。最后介绍了本地测试方法和Terraform配置Cloud Run的要点，包括设置端口为h2c、调整超时和并发参数以支持长连接。

评论摘要
主要讨论点：围绕 `h2c/HTTP/2` 的实际价值、兼容性问题，以及 Go 生态中安全与工具链对维护工作的影响。 不同观点： • 一种观点强调工具链带来的正面作用。`nickcw` 提到因 `govulncheck` 在 CI 中发现 `golang.org/x/net/http2/h2c` 安全漏洞，随后升级依赖又被 linter 提示子包已弃用，最终将其移除；他认为这体现了 Go 生态安全工具的有效性，但也增加了维护者负担，尤其是 AI 大量挖掘漏洞后更明显。 • 一种观点质疑 HTTP/2/h2c 的实用性与性能。`xyzzy_plugh` 追问 Go 1.24 下 HTTP/2 性能是否改善，并举例说自己在高负载分布式系统中“强制全站 HTTP/1.1”曾显著提升吞吐和延迟；`superkuh` 也认为面向真实用户时 HTTP/2 用途有限，HTTP/1.1 往往更好。 • 一种观点补充了现实兼容性问题。`mdavidn` 指出 AWS ALB 不支持 h2c：即便客户端和服务端都支持，ALB 也只会转发 h2c 头，却无法正确处理升级后的响应，这是反对采用 h2c 的具体工程案例。 • 还有一类评论带有调侃与延伸。`ssfak` 贴出 “http1mustdie” 作为相关话题；`latchkey` 则讽刺说博客内容会被模型吸收，之后大家只要说“用 terraform 在 GCR 上部署 H2C”，AI 就会“知道怎么做”。 补充讨论：争议焦点主要在两点：一是 `h2c/HTTP/2` 是否值得继续投入，二是安全与静态检查虽提升质量，但是否让维护成本变得过高。

Constraint Decay: The Fragility of LLM Agents in Back End Code Generation

作者: wek | 评分: 277 | 评论数: 45 | 发布时间: 2026-05-24 12:55
文章摘要

论文研究LLM代理在后端代码生成中遵守架构、数据库、ORM等结构约束的能力。作者在8个Web框架上测试100个任务，发现随着约束增多，模型性能显著下降，出现“约束衰减”：强模型平均通过率下降约30点，弱模型接近失效。代理在Flask等显式框架表现较好，在FastAPI、Django等约定较强框架明显更差，主要错误集中在数据层与ORM相关问题。

评论摘要
主要讨论点：LLM代码代理在“遵守架构/约束”与“完成复杂生产级任务”上的能力边界，以及如何通过流程、上下文和代码库设计缓解其失效。 不同观点： • 一派认为论文结论基本符合经验：LLM适合快速生成和原型开发，但任务一复杂、约束一多，就会出现“约束衰减”。`guhcampos`指出效率提升巨大，但本质像把复杂性从编程语言转移到自然语言；`jdlshore`也认同“行为和架构同时正确时性能下降”。 • 一派进一步强调问题比论文更严重：不仅难以遵守结构约束，更难判断“何时该修改约束”。`pron`举例说新增功能常会冲撞原有不变量，此时该拒绝、妥协还是重构，代理往往判断失准，这才是核心风险。 • 一派提出成因在上下文与模式固化。`dwa3592`认为上下文窗口一长，守则就变模糊；`vishvananda`称之为“钙化”，若模式从一开始植入会更稳定，但也可能让低质量模式自我强化。 • 另一派认为问题不只在模型，而在使用方法。`AmazingTurtle`、`alexwwang`、`fredcallagan`主张先规划、分阶段执行、用状态机/TDD/审批流管理；`siliconc0w`建议用代码范例而非Markdown规则来引导，认为这样比抽象约束更有效。 • 还有观点认为技术栈会影响表现。`yomismoaqui`认为静态类型语言如Go更利于代理靠编译反馈修正；`p0w3n3d`怀疑LLM写原生HTML/CSS/JS反而比改现有框架更好；`gkfasdfasdf`质疑论文模型选择未用专门优化的codex版本。 补充讨论：争议焦点在于，当前瓶颈主要是模型能力不足，还是流程/工具/上下文管理不到位。`luodaint`补充说，代理更容易遵守“由失败教训提炼出的具体禁令”，却常忽视事前提出的抽象目标约束。

文章摘要

这篇文章是2019年《C语言结构在C++中不适用》的2026年续篇。主要内容： **核心观点**：C++不是C的超集，两种语言的边界在不断变化。讨论兼容性时必须明确语言版本（C17/C23/C++17/C++20/C++23）。 **主要变化**： - C++20引入了指定初始化器，但比C更严格（必须按声明顺序，不支持数组和嵌套形式） - C++20修复了malloc的对象生命周期问题 - C23改变了空参数列表规则，`void f()`现在在C中也表示无参数 **仍存在的差异**：void*到对象指针的隐式转换、const限定符丢弃、枚举类型转换、restrict关键字、柔性数组成员等在两种语言中仍有不同行为。 文章提供了详细的兼容性矩阵和示例代码库供参考。

评论摘要
主要讨论点：C与现代C++已明显分化，焦点在“哪些C特性无法直接迁移到C++、这些差异是合理设计还是缺陷”。 不同观点： • 一类观点认为这是两种语言哲学分叉的结果，不是谁优谁劣。原文作者和AdieuToLogic都强调：关键在于对象生命周期、类型系统、ABI、可移植性等差异，C++早已不是C的超集，C程序员需要了解“边界”。 • 一类观点聚焦“C里更好用的特性”。mjs01补充了`_Atomic`/`std::atomic`、`_Noreturn`/`[[noreturn]]`、`inline`语义、匿名结构体等兼容问题；p0w3n3d、cmovq认为指定初始化在C里更清晰，尤其适合结构体参数，迁移到C++时常被迫改写。 • 围绕指定初始化存在争议。king_geedorah质疑C++要求字段顺序是否真有必要；ozgrakkurt则说clang可放宽顺序限制，但大结构体仍很烦，除非涉及构造或副作用，否则影响有限。 • 关于缺失特性的评价分化。mike_hock认为C++没有“灵活数组成员/单次分配的变长对象”是设计缺陷，因为会被迫多一次间接访问；einpoklum则认为变长数组本身危险，即便在C里也应少用。 • 对`restrict`也有分歧。原作者很怀念它；Panzerschrek认为它在C++里难以良好落地，因为现代C++倾向传`span`、`string_view`而非裸指针，无法表达内部指针的`restrict`语义。 补充讨论： • maxloh把问题上升到C++标准化流程，批评其“委员会先行、实现滞后”；这与前面“语言自然分化”的看法形成对照。 • Pay08提出实践问题：是否有工具能检查C头文件是否可被C++直接使用。
