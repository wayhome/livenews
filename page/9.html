Ghost in the machine? Legend of the 'haunted' N64 video game cartridge

文章摘要

"Ben Drowned" 是互联网上著名的都市传说，讲述了一个“闹鬼”的《塞尔达传说：梅祖拉的假面》游戏卡带。故事始于一个网名Jadusable的大学生在旧货 sale 上买了一盘没有标签、仅写着“Majora”的卡带。游戏中出现异常图形、音乐倒放，以及一个令人毛骨悚然的林克雕像频繁出现，仿佛被溺亡小孩Ben的幽灵缠身。Jadusable在论坛上详细记录了这些诡异经历，最终神秘消失。尽管该故事被广泛认为是虚构的，但它在2010年引发了全球年轻网民的恐慌，并启发了大量同人创作。Ben Drowned不仅是一个成功的都市传奇，还反映了社会对新技术和电子游戏的深层恐惧与情感联系。

The Creative Power of Constraints

作者: zhenpixels | 评分: 23 | 评论数: 6 | 发布时间: 2025-05-05 17:23
文章摘要

本文探讨了约束对创造力的积极作用。引用设计师查尔斯·伊姆斯的话，文章指出，创造力并非凭空产生，而是源于对既有事物和限制的回应与突破。适当的约束能激发创造力，而过多或过少的约束则可能限制或瘫痪创意过程。文章通过几个实例，如YouTuber pwnisher的3D挑战、东京的Famicase艺术展以及阿姆斯特丹Borneo Sporenburg住宅项目，展示了如何通过设定合理的约束条件，催生出多样且富有创意的解决方案。这些例子表明，约束与自由之间的悖论关系是创造过程的核心，适当的限制实际上能扩展可能性，推动创新。

评论摘要
主要讨论点：通过设置约束促进创造力的观点及其应用 不同观点： • **[gwern的观点]**：引用Charles Eames关于“被迫的妥协”与“自愿接受的约束”的区分，认为创造力在结构与自由的平衡中茁壮成长。他进一步提出一个具体建议，即在写作时不使用AI，以此作为一种自我设限的方式来激发创造力。 • **[cadamsdotcom的观点]**：支持设置约束来激发创造力，认为在拥有约束的前提下才能进行创新。他以时间为例，提出在有限的时间内（如20分钟）完成任务，能够激发创造潜力。 • **[dvh的观点]**：通过一个具体例子说明约束的作用。当让人们随意画马时，他们往往会拒绝，但如果要求用矩形来画马，人们反而能够创作。这表明特定的约束条件可以激发人们原本认为自己不具备的能力。 • **[kunzhi的观点]**：推荐Christopher Alexander的《形式综合论》一书，认为这是对程序员和设计师非常有价值的读物。他的观点更侧重于理论阅读对理解约束设计的重要性。 • **[recursivedoubts的观点]**：引用Orson Welles的名言“艺术的敌人是缺乏限制”，完全支持约束对艺术创作的正面作用，认为适当的限制是艺术创作的必要条件。 • **[alganet的观点]**：对过度强调约束可能导致的负面效果提出警告。他提到过去一些人将约束与禁欲主义混淆，导致设计过于简化。他以Windows Metro设计为例，认为虽然这是一个好的约束设计案例，但过多的约束也可能让人陷入困境，尤其是在技术领域，保持人性化设计是一个挑战。 补充讨论： • **对约束的正面看法**：多数评论者（如gwern、cadamsdotcom、dvh、recursivedoubts）强调了约束对创造力的积极作用，认为适当的限制能激发创造潜力。 • **对约束的潜在负面影响的警示**：alganet提醒大家注意约束过度可能带来的问题，特别是在设计和技术领域，如何保持“人性化”是一个值得关注的问题。 • **理论与实践的结合**：kunzhi推荐的书籍为讨论提供了理论背景，强调了理解和学习相关理论对实际设计工作的重要性。 争议焦点： • 约束的适度问题：评论者对约束的应用效果有不同看法，尤其是alganet提出过度约束可能带来的负面影响与其他评论者对约束的全盘肯定形成了对比。这表明在实际应用中，如何设置合适的约束是一个关键争议点。

Driving Compilers (2023)

作者: misonic | 评分: 87 | 评论数: 3 | 发布时间: 2025-05-05 02:17
文章摘要

本文作者Fabien Sanglard回顾了自己学习C和C++编程的愉快经历，特别是在阅读经典书籍如《The C Programming Language》和《Effective C++》系列时的收获。然而，学习将程序编译成可执行文件的过程却充满挑战，缺乏相关文献和指导。为此，作者撰写了系列文章，旨在填补这一空白，帮助读者更好地理解编译工具的使用。文章不涉及语言本身或如何编写编译器，而是聚焦于如何从单文件示例过渡到更复杂的项目。内容涵盖编译驱动器、预处理器、编译器、链接器以及Linux加载器，通过具体步骤和工具解释可执行文件的创建过程。示例基于Linux平台，但概念适用于其他操作系统。系列分为五部分，首先介绍编译驱动器，然后详细讲解编译的三个阶段及其输入输出。

评论摘要
主要讨论点：对编程初学者的工具、语言选择及编程细节的讨论 不同观点： • [Timwi] 认为初学者使用Turbo Pascal比C更易上手，因为Turbo Pascal屏蔽了链接器（linker）的复杂性，而C的链接器错误让人困惑。他还指出，教育材料往往缺乏对编译和链接过程的详细解释，这可能影响初学者的学习体验。30年后，他仍然觉得高层次的语言如C#（编译到VM字节码）更舒适，因为不需要处理链接器。 • [lynx97] 则聚焦于C语言中"Hello World"程序的实现细节，指出常见的使用`printf`的方式是不准确的，因为`printf`适用于需要格式化字符串的情况，而"Hello World"不需要。他建议使用`puts`，因为它更直接，只需写入字符串和换行符到标准输出。 • [stef-13013] 对原文内容表达了简单的赞赏，没有展开具体的技术讨论。 补充讨论： • [Timwi] 提到了对编译器和链接器工作原理的理解问题，特别是链接器在初学者学习过程中的障碍。他还分享了自己多年后的技术成长，但仍然对链接器工作机制感到模糊，倾向于使用更高层次的编译语言。 • [lynx97] 关注的是C语言编程中的具体编码规范问题，强调了正确使用函数（如`puts` vs `printf`）的重要性，属于对具体代码实现的细节讨论。 争议焦点： • 不同观点之间的争议并不直接，但[Timwi]认为C的链接器复杂且难以理解，而[lynx97]则关注C语言中的具体实现细节和编码规范。这体现了在编程初学阶段，学习者对语言复杂性和工具支持的不同感受和需求。

Oberon Pi

作者: tosh | 评分: 201 | 评论数: 14 | 发布时间: 2025-05-04 08:54
文章摘要

Oberon Pi 是 Richard Gleaves 将 Peter de Wachter 的 Oberon 系统模拟器移植到 Raspberry Pi OS 的版本。Gleaves 是前 UCSD Pascal 项目成员，并撰写了《Modula-2 for Pascal Programmers》一书。Oberon Pi 主要改进了用户界面，简化了新用户的学习曲线，同时保留了 Oberon 系统的核心特性。它还集成了 Andreas Pirklbauer 对 Oberon 编译器的修改，完全实现了 CASE 语句并修复了一些编译器错误。该项目提供了全面的文档和指南，包括新的用户指南和原始 Oberon 文档，并可在 Raspberry Pi 400 上运行。为在 64 位系统上运行，需对设置进行一些调整。所有资源可在 GitHub 上获取。

AI Meets WinDBG

文章摘要

Semantic unit testing: test code without executing it

作者: alexmolas | 评分: 74 | 评论数: 22 | 发布时间: 2025-05-03 09:44
文章摘要

**Semantic Unit Testing** 是一种利用LLM（大语言模型）分析代码和文档以检测实现是否符合预期行为的测试方法。与传统单元测试通过 `assert` 验证输入输出不同，语义单元测试通过分析函数的实现和文档（docstring）来判断代码是否正确。该方法依赖LLM提供上下文理解，无需实际运行代码。 作者开发了名为 **suite** 的Python库来进行语义单元测试。使用时，suite读取函数的实现和文档，递归分析内部调用的函数，并生成提示让LLM判断函数是否正确实现。例如，给定一个乘法函数，suite可以发现其实际执行的是加法，从而识别出错误。 该库通过 `inspect` 模块读取函数信息，生成包含所有必要信息的 `FunctionInfo` 对象，并将其传递给LLM以获取结构化响应，如 `{"reasoning": str, "passed": bool}`。文章还展示了如何测试扑克牌发牌函数的具体示例。 简而言之，suite 是一种利用AI进行代码审查的工具，能够自动检测代码和文档之间的不一致。

评论摘要
主要讨论点：使用LLM（大型语言模型）生成和验证代码的有效性及可行性 不同观点： • **LLM生成代码的验证问题**：[vouwfietsman] 认为LLM可以辅助编写代码，但每一行代码仍需经过验证，以确保没有逻辑和推理错误。这种验证不能由LLM自身完成，因为这可能会加剧问题。同时对一些人声称的2倍提速表示怀疑。 • **LLM引入的不确定性**：[RainyDayTmrw] 对LLM生成代码中的不确定性表示担忧，尤其是在中大型代码库中。与LLM相比，基于属性的测试（property-based testing）具有更可靠的历史记录。 • **LLM作为代码审查工具**：[dragonwriter] 认为将LLM用于代码审查而非测试更合适，并指出将其称为测试是误导性的。 • **静态类型语言与动态类型语言的对比**：[jonathanlydall] 提到静态类型语言在编译时就能提供保障，减少了额外的测试需求，而动态类型语言则需要更多测试。 • **LLM生成工具的有效性**：[yuliyp] 质疑LLM生成工具的实际效果，特别是其在捕获错误和处理误报/漏报方面的能力。 • **形式验证与LLM的对比**：[masklinn] 指出如果追求代码无错误，应该使用证明助手（proof assistant）而非LLM的“感觉审查”（vibe-reviewing）。 补充讨论： • **LLM与纯函数式编程语言的适应性**：[simianwords] 提到LLM可能更适合处理纯函数式编程，因其不含副作用且参数明确，但转换过程可能影响人类可读性。 • **LLM生成测试的随机性问题**：[rollulus] 担心LLM的随机性可能导致测试结果不稳定。 • **LLM在文档验证中的应用**：[cerpins] 认为LLM可能适用于验证文档与代码的一致性，但仅在代码或文档变更时才有意义。 • **AI辅助代码审查与自动化测试**：[jmull] 和 [stephantul] 都认为LLM更适合作为辅助代码审查工具，自动化测试仍需人工审查结果，且离线生成测试用例可能是更透明和经济的方式。 其他技术细节： • **CSS问题**：[gnabgib] 提到技术讨论外的网站CSS问题，指出在窄屏设备上显示效果不佳。 • **经典引用**：[evanb] 引用Donald Knuth的名言，强调证明代码正确性与实际尝试代码是不同的，呼应了对LLM生成代码验证的需求。 争议焦点：LLM生成代码的验证可靠性及其在中大型项目中的适用性。
