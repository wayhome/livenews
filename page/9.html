Lies we tell ourselves about email addresses

作者: theanonymousone | 评分: 161 | 评论数: 42 | 发布时间: 2026-06-08 14:24
文章摘要

这篇文章讨论了电子邮件地址验证的常见误区。主要观点包括： 1. **不要用正则表达式验证邮件地址** - 正则验证成本高、容易出错、难以维护，且规则会随时间变化。 2. **简化验证策略** - 如果必须验证，只需用简单正则（如`^[^@]+@[^@\s]+$`）检查基本格式"某内容@某内容"，避免过度限制。 3. **采用邮件验证机制** - 最佳做法是发送验证邮件让用户点击链接或输入验证码，而不是依赖复杂的格式校验。 4. **历史遗留问题** - 电子邮件系统充满历史包袱，有效地址的定义一直在演变，即使是大型服务商也不一定完全支持所有技术上合法的格式。 核心建议：不要过度思考，直接发送验证邮件即可。

评论摘要
主要讨论点：电子邮件地址验证的常见误区和实际问题 不同观点： • **过度验证派**：认为许多网站的邮箱验证规则过于严格，拒绝合法地址。例如多个点号的域名（sean@foo.bar.baz）、加号（+）地址、新顶级域名（.healthcare、.consulting）等被30%的网站错误拒绝 • **用户体验优先派**：主张应根据用户群体调整验证策略。对非技术用户，严格验证可能更友好，因为有些用户记不准自己的邮箱地址，限制顶级域名可以减少拼写错误 • **技术纯粹主义者**：强调应遵循RFC标准，指出邮箱地址技术上可以包含引号、多个@符号（源路由）、IP地址等复杂格式，尽管这些功能实际已"死亡" • **国际化质疑者**：认为非ASCII字符的国际化邮箱虽然包容但降低了可移植性，在跨语言环境中反而造成沟通障碍 补充讨论： 开发者倾向用复杂正则表达式验证邮箱，但往往适得其反。邮件系统设计初衷是容错性强（如英国邮政成功投递地址不全的信件），但现代验证逻辑过于死板。还有隐私显示问题（j*h@gmail.com vs m*l@个人全名.nl）和基于邮件的身份验证安全隐患。

Upcoming breaking changes for npm v12

作者: plasma | 评分: 470 | 评论数: 33 | 发布时间: 2026-06-09 21:01
文章摘要

npm v12（预计2026年7月发布）将引入三项重要的安全默认变更： 1. **禁用脚本执行**：`npm install` 默认不再自动运行依赖包的 `preinstall`、`install`、`postinstall` 脚本（包括 node-gyp 构建），需通过 `npm approve-scripts` 显式批准信任的包。 2. **禁用 Git 依赖**：默认不再解析 Git 依赖，需通过 `--allow-git` 显式允许。 3. **禁用远程 URL**：默认不再解析 HTTPS tarball 等远程依赖，需通过 `--allow-remote` 显式允许。 **准备方法**：升级到 npm 11.16.0+，运行安装查看警告，使用 `npm approve-scripts` 批准可信包并提交更新后的 `package.json`。

评论摘要
主要讨论点：npm v12 版本默认禁用 postinstall 脚本以应对供应链攻击 不同观点： • **支持派**：认为这是重要的安全改进，postinstall 脚本一直是 npm 包的"毒瘤"，深层嵌套且不受控制的脚本随机执行非常危险，早该移除。有人指出这个漏洞报告已有 10 年，现在修复是"迟到总比不到好" • **怀疑派**：质疑这只是将风险从安装时转移到运行时，恶意代码可以从安装脚本转移到模块本身；也有人对 npm 被 GitHub 收购表示不满，认为这不是 Node 生态系统关键部分的理想归宿 • **实用主义派**：部分开发者已转向 pnpm 等替代方案。有人指出 npm 比 pnpm 晚 18 个月才实现类似的安全防护 补充讨论： - 白名单机制支持按包名而非全局设置，便于组织级规则管理 - 关注 Node LTS 版本（22/24/26）是否会更新到 npm v12 - OSS 开发者担心这会影响通过 npm 分发预编译二进制文件的流程 - 需要 linter 工具来防止不安全的包管理器配置 - 有人询问 Yarn 是否也实施了类似的供应链攻击防护措施

The Road to the WASM Component Model 1.0

作者: emschwartz | 评分: 83 | 评论数: 12 | 发布时间: 2026-06-08 17:12
文章摘要

WebAssembly组件模型(Component Model)正迈向1.0稳定版本。该模型定义了Wasm二进制文件的打包、链接和通信方式，而WASI则提供标准化的系统API。两者关系类似微内核架构：组件模型是基础微内核，WASI是上层操作系统服务。 通往1.0的关键工作包括ABI改进：从当前的eager allocation转向lazy value handles机制，由调用方按需分配内存而非主机预先分配。这解决了堆碎片、大内存分配失败、性能开销等问题，并支持零拷贝转发。过渡采用向后兼容的渐进方式，通过0.3.x版本引入可选lazy ABI，1.0时成为默认。文章未完，但提到该改进依赖LLVM对multivalue的C ABI支持。

评论摘要
主要讨论点：WebAssembly（WASM）及其组件模型（Component Model）和WASI的发展前景与应用价值 不同观点： • **乐观派**：认为WASI将实现跨平台沙箱化应用，彻底改变运行不可信代码的方式（simonw）；组件模型的ABI改进（零拷贝转发）和非C语言库的生态解放意义重大（rohitsriram、DanielHB）；期待浏览器原生支持以改善开发体验（fyrn_、mastermage） • **技术探索派**：将WASM视为操作系统和内核扩展的潜在方案，如通过虚拟设备访问DOM（baudaux）、替代eBPF（catlifeonmars）、构建最小化WASM内核操作系统（wyager实现了eo9.org） • **怀疑派**：质疑浏览器实现组件模型的必要性，认为现有WASM已足够好，不应增加运行时复杂度（flohofwoe）；认为WASM只是重复CORBA/gRPC等旧技术，应保持在浏览器内（pjmlp）；指出WASM自2017年至今未取得突破，用户基数极小，性能问题明显（shevy-java以Autodesk Fusion为例） 补充讨论：社区已超越"WASM不会取代JavaScript"的争论阶段，开始务实探讨具体应用场景和技术实现路径。核心分歧在于WASM应专注浏览器还是扩展到通用计算平台。
