文章摘要

My Mathematical Regression

作者: aleda145 | 评分: 153 | 评论数: 27 | 发布时间: 2026-06-19 11:06
文章摘要

作者重新发现了自己10年前解决Project Euler第15题的方案。当时还是学生的他没有写代码，而是用数学方法识别出网格路径问题遵循二项式系数规律：(2n)选n，直接算出20×20网格的答案是137846528820。作者感慨现在的自己可能会用Python暴力破解或动态规划，甚至直接交给AI处理，反而失去了当年的数学洞察力。这让他既钦佩过去的自己，又为能力退化感到惋惜。

评论摘要
主要讨论点：关于网格路径计数问题的不同解法思路及其背后的数学直觉性 不同观点： • **组合数学直觉派**：认为"2n choose n"公式最直观，将问题理解为在2n步中选择n步向右（剩余n步向下），或理解为排列问题(2n)!/(n!×n!) • **动态规划递推派**：倾向于用递推公式D[A,B]=D[A-1,B]+D[A,B-1]思考，认为这是实际工作中的自然思路，然后才意识到结果是二项式系数 • **高级数学工具派**：使用生成函数等更高级方法求解，但事后反思可能过度复杂化了简单问题 • **模式识别质疑派**：警告仅凭观察前几项规律就推广是危险的（引用Moser圆问题作为反例），强调需要严格证明而非"遵循模式" 补充讨论： • 有评论指出简单解法的人才在企业环境中往往难以被认可，因为人们倾向认为复杂问题需要复杂方案 • AI时代前这种"忘记基础解法"的现象已存在，成人重做学生题时常需重新推导 • 将问题重构为"字符串排列"（如RRRDD）被认为是建立直觉的有效方法，且易于推广到多维情况

Die analysis of the 8087 math coprocessor's fast bit shifter (2020)

作者: Jimmc414 | 评分: 81 | 评论数: 7 | 发布时间: 2026-06-22 13:40
文章摘要

这篇文章介绍了Intel 8087浮点协处理器的历史和技术细节。1980年Intel推出8087芯片，使微型计算机的浮点运算速度提升100倍，但价格高达数百美元。8087采用了数值分析专家William Kahan设计的浮点架构，后来成为IEEE 754标准，影响深远。 文章重点分析了8087的二进制移位器设计。该芯片包含4万个晶体管，移位器占据了大量面积。它采用两级桶形移位器设计：第一级移位0-7位，第二级移位0-7字节，组合可实现0-63位的任意移位。移位器在浮点加减法、CORDIC超越函数运算中起关键作用，其高效设计对芯片性能至关重要。

评论摘要
主要讨论点：8087数学协处理器及其历史背景下的浮点运算硬件技术 不同观点： • **历史技术回顾派**：tasty_freeze介绍了更早期的Northstar S-100卡片，使用BCD算术和微码ROM实现浮点运算，通过4位ALU逐位数字处理，最多支持14位精度，展示了更原始但巧妙的设计思路（如通过指针移动实现归一化而非数据移动） • **性能进步感慨派**：QuadrupleA对比了8087（当时售价相当于今天500美元，性能0.00005 GFLOPS）与现代移动芯片（制造成本约20美元，CPU 50 GFLOPS + GPU 500+ GFLOPS），强调千万倍性能提升和1/25成本，同时对8087精妙设计在现代已"无用"表示惋惜 • **技术细节质疑派**：SyzygyRhythm对文章中的移位器设计提出疑问，认为应采用对数级联结构（32-16-8-4-2-1位）而非现有方案，质疑为何不用更少子级和无需单独解码器的设计 补充讨论：trollbridge幽默评论表示文章内容极具吸引力；bell-cot提供了8天前关于8087加法器的相关讨论链接；coldpie引用德语梗（"The Bart, The"）开玩笑

作者: tosh | 评分: 212 | 评论数: 20 | 发布时间: 2026-06-19 15:54
文章摘要

Codex logging bug may write TBs to local SSDs

作者: vantareed | 评分: 495 | 评论数: 40 | 发布时间: 2026-06-22 07:30
文章摘要

这是一个关于 OpenAI Codex CLI 工具的严重性能问题报告： **核心问题：** Codex 的 SQLite 反馈日志系统每年写入约 640TB 数据，可能在一年内耗尽消费级 SSD 的写入寿命（通常为 600TBW）。 **数据规模：** 21天运行期间写入 37TB，数据库保留 50万行记录，但历史插入行ID已达 55亿（10,000倍差距），显示大量日志被写入后又被清理。 **主要原因：** - 70% 来自 TRACE 级别日志 - 25% 来自 OpenTelemetry 镜像日志 - 包含高频 inotify 事件、WebSocket 原始负载等 **解决方案：** 已通过3个PR修复，可避免85%日志写入。临时方案是用 SQLite trigger 阻止日志插入。

评论摘要
主要讨论点：OpenAI Codex 存在严重的性能问题，特别是日志记录导致的 GPU 过载和磁盘占用问题 不同观点： • **严厉批评派**：认为这是灾难性失误，spinner 消息导致 M5 芯片 100% GPU 占用，风扇狂转。问题存在 6 个月未解决，反映公司内部严重问题。指出这说明"vibe coding"（AI 辅助编程）存在根本性缺陷，OpenAI 已失去竞争力 • **技术分析派**：指出这是经典的"trace/debug 日志级别错误发布到生产环境"问题。有用户发现日志文件达 27GB，通过 SQL 优化可压缩至 73MB。认为这类问题以往会导致应用崩溃而被迅速修复，但现在硬件性能掩盖了严重性 • **解决方案提供者**：分享了临时修复方法（SQLite trigger 阻止日志插入），指出 Codex 是开源的可自行修补，最终 OpenAI 工程师确认已在更新中修复 • **竞品对比派**：提到 Claude Code 去年表现不佳时 OpenAI 错失良机，现在 Codex 反而有输入延迟问题。也有人批评 Claude Code 会删除 30 天以上的会话记录 • **谨慎观望派**：表示不会立即升级工具，会等社区反馈稳定后再更新 补充讨论：有人批评 AI 生成的 GitHub 评论质量；有人呼吁统一 LLM 工具的配置文件位置；有人讽刺 OpenAI 作为资金充裕的公司却出现这种低级错误
