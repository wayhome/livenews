Automating Interactive Fiction Logic Generation with LLMs in Emacs

作者: dskhatri | 评分: 83 | 评论数: 8 | 发布时间: 2025-03-31 15:57
文章摘要

本文讲述了作者如何利用Emacs中的LLM（通过gptel包）自动生成互动小说中的交易追踪逻辑。作者正在创作一本互动儿童书籍，主角Daphne在创业冒险中赚钱、存钱或花钱。由于每个段落可能通过多种路径到达，作者需要在每个段落中添加代码来追踪交易金额及其他参数，以显示Daphne的现金余额。为了提升书籍的教育价值，作者决定展示Daphne现金余额的计算过程。为此，作者使用gptel包，通过选中整个故事文本并输入特定提示，自动更新每个段落中的代码块，添加一个"cashOperations" JSON对象，记录现金变化的操作、金额和描述。这一自动化过程大大提高了效率，使作者能够轻松实现算术解释功能。

LLM Workflows then Agents: Getting Started with Apache Airflow

作者: alittletooraph2 | 评分: 111 | 评论数: 12 | 发布时间: 2025-03-31 18:32
文章摘要

`airflow-ai-sdk` 是一个用于在 Apache Airflow 中操作大型语言模型（LLM）和 AI 代理的 SDK，基于 Pydantic AI。它允许用户直接在 Airflow 管道中调用 LLM 并编排代理任务，使用基于装饰器的任务语法，如 `@task.llm`、`@task.llm_branch` 和 `@task.agent`。SDK 提供自动输出解析、分支控制等功能，支持多种 LLM 模型（如 OpenAI、Anthropic 等）。通过该 SDK，用户可以轻松将 LLM 工作流集成到 Airflow 管道中，从简单的 LLM 调用到复杂的代理工作流均可实现。示例代码和安装说明详见 GitHub 仓库。

评论摘要
主要讨论点：关于工作流引擎和AI代理的讨论，包括对不同工具和设计模式的看法。 不同观点： • [jumski] 认为 pgflow 是一个简单、以 Postgres 为主的引擎，使用任务队列来执行实际工作，具有明确的DAG方法、强类型安全、良好的TypeScript DSL，并能够在 Supabase 上运行而不需要任何外部工具。他对即将发布的 alpha 版本感到兴奋，并邀请其他人关注其项目。 • [mushufasa] 认为 Airflow 对于新项目来说已经过时，但目前没有一个明确的替代者。他提到了多个框架（如 Prefect、Dagster、Temporal 等），并表示选择过多让人感到不知所措。他建议一篇技术博客对不同设计模式和如何整合LLM特性进行分析会很有帮助。 • [greatgib] 对使用装饰器的示例提出质疑，认为装饰器在实际应用中并没有太大作用，反而会使参数化和从配置中获取值变得困难，认为这是不好的实践。 • [drdaeman] 对 `@task.agent` 装饰器的必要性提出疑问，认为与直接使用 `return my_agent.run_sync(...)` 相比，装饰器显得更具限制性和可能不够直观。 • [itsallrelative] 对“代理”在工作流中的必要性持怀疑态度，认为在许多情况下，仅通过少量LLM增强的确定性工作流已经足够。 • [datadrivenangel] 正在探索在SQL触发器中使用LLM调用以实现代理/代理工作流，认为LLM驱动的工作流可以带来强大的结果。 • [falcor84] 提出反向思考，询问是否有人尝试过由AI代理定义和迭代长期运行的工作流。 • [nikolayasdf123] 简单地表示 Airflow 是一个合适的选择。 • [ldjkfkdsjnv] 对现有工具解决代理工作流的能力持悲观态度，认为只有 Temporal 有可能成功，因为 Airflow 等工具并非为高度动态执行设计。 补充讨论： • 讨论中多次提到 Airflow 的局限性和替代工具的选择问题，尤其是针对代理和工作流自动化的需求。 • 有人对装饰器的实用性提出质疑，认为在某些情况下，装饰器可能不是最佳设计选择。 • 对LLM在工作流中的应用和潜力存在不同看法，有人认为增强的确定性工作流已经足够，而有人则在探索更复杂的代理工作流。 争议焦点： • 现有工具（如 Airflow）是否适合用于新的代理工作流项目，以及是否需要新的设计模式和技术博客来指导选择。 • 装饰器的实际效用和其在代码中的合理性。 • LLM 在工作流中应扮演的角色和其应用潜力。
