Binary Formats Are Better Than JSON in Browsers

作者: adamkf | 评分: 61 | 评论数: 9 | 发布时间: 2025-05-13 22:30
文章摘要

文章主要讨论了在浏览器中使用二进制格式替代JSON的性能优势。过去JSON在浏览器中的表现优于其他二进制格式，但随着互联网速度的提升和网页应用复杂性的增加，这种情况发生了变化。作者指出，对于性能要求较高的网页应用，使用Avro、Protobuf或Bebop等二进制格式可能更为合适。 作者在2023年为解决服务器到Web应用的大响应问题，选择了MessagePack，但发现所有测试的二进制编码都比JSON慢。然而，最近几个月的实验显示，一些JavaScript二进制编码库在性能上已经超越了JSON。 文章还提到在浏览器中进行基准测试的挑战，包括使用Node.js而非浏览器进行测试的常见错误，选择具有代表性的数据集的重要性，以及不同输入数据类型和大小对结果的影响。最终，作者通过实验表明，二进制格式在浏览器中的表现已经优于JSON，特别是在处理大型数据集时。

评论摘要
主要讨论点：不同序列化格式（如JSON、二进制格式）在性能、工具支持和使用场景上的优劣比较 不同观点： • **[pjmlp]**：认为不需要重复CORBA和DCOM的老路，解析文本效率不高。虽然JSON-RPC比SOAP稍好，但整体上工具支持和可读性是关键。 • **[codelikeawolf]**：在VS Code代码库中发现使用自定义二进制缓冲区来编码/解码IPC消息，质疑小消息是否也有必要使用二进制编码。提出何时使用二进制编码更高效的问题。 • **[avmich]**：建议将编码问题交给压缩层处理，暗示可能通过压缩来解决性能问题而不是直接采用复杂的二进制格式。 • **[victorNicollet]**：分享了生产环境中使用自定义二进制格式的经验，指出二进制格式在数据可视化和分析中的优势，特别是在处理大型数组时能显著减少解析时间。但也提到调试二进制格式较为困难。 • **[jiehong]**：提出Apache Parquet格式是否适合比较的疑问，尤其是浏览器中的实现质量。 • **[zigzag312]**：讨论MessagePack的性能，猜测如果使用整数字段键是否能提升性能。 • **[broken_broken_]**：虽然起初不理解为何要向浏览器发送大量数据，但认可数据可视化和一些特定场景（如视频游戏和 observability 平台）的需求。 • **[naikrovek]**：强烈支持二进制格式，认为二进制格式在提取信息速度和大小上都优于JSON。认为开发者对二进制格式的恐惧是不必要的，二进制格式更高效且灵活。 • **[mannyv]**：质疑比较的完整性，指出可能缺少反序列化和验证延迟的比较。 补充讨论： • 争议焦点之一是二进制格式和JSON在性能上的实际差异，尤其是**[naikrovek]**和**[codelikeawolf]**之间的对立观点。 • 另一个值得注意的讨论点是调试二进制格式的困难，**[victorNicollet]**提到浏览器开发工具对非JSON格式的支持不足，增加了调试的复杂性。 • **[jiehong]**提出的Apache Parquet实现质量问题也是一个重要的考虑因素，特别是在浏览器环境中的适用性。 总结：讨论主要围绕不同序列化格式在性能、工具支持和特定使用场景下的优劣展开，参与者提供了各自的经验和见解。

Are the means of computation even seizable?

文章摘要

本文探讨了科技公司通过法律手段限制技术对抗性互操作性（adversarial interoperability）的能力。过去，每当科技公司做出不利于用户的选择时，总会有人开发程序来绕过这些限制，但近年来这种情况大幅减少。作者认为，这不是因为公司技术更安全，而是因为法律（如《数字千年版权法》第1201条）将绕过数字锁的行为定为非法，最高可判刑五年。这种法律保护使得公司如Apple、John Deere等可以阻止第三方维修和修改产品，甚至在应用中加入广告。作者呼吁废除这些法律，指出真正有效的技术不应依赖法律保护，而科技公司过度依赖法律恰恰说明其技术锁并不真正安全有效。

评论摘要
主要讨论点：如何应对技术产品中的“垃圾化”（enshittification）现象，以及如何通过去中心化和P2P技术打造一个不同的技术生态系统。 不同观点： • RetroTechie认为“垃圾化”现象普遍存在，但同时指出每次有公司建立壁垒（如DRM），都会有黑客找到方法“去垃圾化”。他提出了“去垃圾化”（unshittification）的概念，即通过技术爱好者和黑客的努力，抵消企业对产品的“垃圾化”操作。 • 他指出，DRM等技术能够持续存在的主要原因是大多数消费者并不在意，并继续购买这些产品。这表明消费者行为在技术产品质量和功能上的关键作用。 • RetroTechie进一步分析了当前技术生态系统的中心化问题，包括互联网接入、社交媒体、文件共享和操作系统等方面。他认为这种中心化使得供应商容易成为“守门人”，并通过资本主义的激励机制进一步强化了“垃圾化”现象。 补充讨论： • 为了减少对中心化系统的依赖，RetroTechie提出了一些去中心化和P2P技术的设想。例如，无缝、无处不在的网状网络，通过P2P方式从邻居设备下载操作系统组件；类似BitTorrent的全球去中心化文件系统；简便的微支付系统；以及基于P2P的社交网络，直接在朋友设备之间传递信息而不需要通过大型平台。 • 他承认，其中一些技术 puzzle 可能已经存在部分解决方案，但缺少一个能够默认实现上述功能并表现优异的流行设备。 争议焦点： • 消费者对技术产品中“垃圾化”现象的态度和行为是争议的焦点。RetroTechie认为消费者不在意并继续购买是问题的一部分，但改变这种行为并非易事。 • 去中心化和P2P技术在实际应用中的可行性和普及性也是一个潜在的争议点。虽然这些技术有潜力，但实现一个默认支持这些功能的流行设备仍是一个挑战。 总结： RetroTechie的评论主要讨论了技术产品中的“垃圾化”现象及其根源，并提出了通过去中心化和P2P技术构建不同技术生态系统的设想。他强调了消费者行为和中心化系统在“垃圾化”现象中的作用，并提供了一些技术解决方案的思路。争议的焦点在于消费者态度的改变和去中心化技术的实际应用。

Show HN: acmsg (automated commit message generator)

作者: qeden | 评分: 7 | 评论数: 7 | 发布时间: 2025-05-14 10:44
文章摘要

**acmsg** 是一个使用 OpenRouter API 的自动化 Git 提交消息生成工具，用 Python 编写。它可以分析 Git 仓库中的暂存更改，并通过 AI 生成上下文相关的提交消息。主要功能包括支持多种 AI 模型、可选编辑生成的消息，以及在确认后自动提交更改。安装可通过 pipx 或 Nix 包管理器进行，并需要 OpenRouter API 密钥。配置文件位于 `~/.config/acmsg/config.yaml`，初次运行时会提示设置 API 密钥。使用命令包括 `commit` 生成提交消息和 `config` 管理配置。该工具基于 MIT 许可证发布。

评论摘要
主要讨论点：大型语言模型（LLM）在生成和改进代码提交信息中的应用及其争议 不同观点： • InsideOutSanta认为没有必要在提交时保留LLM的输出，因为可以在需要时使用最合适的LLM生成信息，且此时LLM拥有更多上下文和更准确的信息。他还指出，提交信息应包含代码无法传达的内容，而不是代码本身可以展示的细节。 • pvdebbe持传统观点，认为提交信息应传达意图而非代码内容。他可能认为LLM工具的用途在于描述现有提交信息，而不是生成新的内容。 • theknarf强烈反对使用LLM生成提交信息，认为提交信息应包含代码中无法直接看到的细节，如决策原因、优缺点、相关问题链接等。 • nickcw支持theknarf的观点，强调在查看提交信息时，人们希望了解“为什么”这样做，而“什么”和“如何”做可以通过代码差异获得。如果依赖LLM工具生成提交信息，可能会缺失关键的“为什么”部分。 • alzamixer分享了一个使用LLM（如Copilot）辅助生成提交信息的脚本，展示了一种实际操作方法，表明LLM工具在某些情况下可以有效辅助开发者撰写提交信息。 • esafak补充了一个技术细节，提醒在修改提交信息时不要忘记包含代码上下文。 • infocollector关注技术实现，讨论了如何在本地运行LLM相关工具，并请求社区分享具体操作方法。 补充讨论： - 讨论中反映出开发者对LLM在提交信息生成中的作用存在分歧，一部分人认为LLM工具能提升效率，另一部分人则担心其导致关键信息缺失。 - 传统观点与现代工具应用的碰撞，尤其是在提交信息应包含哪些内容的问题上，争议较大。 - 实际操作方法（如alzamixer的脚本分享）为LLM工具的支持者提供了具体实现路径，但仍需考虑信息完整性和准确性问题。

Branch Privilege Injection: Exploiting branch predictor race conditions

作者: alberto-m | 评分: 408 | 评论数: 24 | 发布时间: 2025-05-13 16:44
文章摘要

文章介绍了名为Branch Privilege Injection的攻击（CVE-2024-45332），该攻击利用了Intel处理器中的分支预测器和指令流之间的异步更新特性，导致分支预测竞争条件，从而绕过了Intel的eIBRS和IBPB缓解措施。攻击者可以利用这种竞争条件在不同权限模式之间注入和操纵分支预测，最终泄露任意内存数据。实验显示，攻击在完全更新的Ubuntu 24.04系统上以5.6KiB/s的速度泄露内存数据。Intel已开发微码更新来修复该问题，并提供了性能评估，在某些处理器上开销为2.7%。所有自第九代（Coffee Lake Refresh）起的Intel处理器都受此漏洞影响，建议用户安装最新的操作系统和BIOS更新以进行防护。该研究将在USENIX Security 2025和Black Hat USA 2025上详细介绍。

评论摘要
主要讨论点：围绕分支预测器漏洞及其安全影响的讨论 不同观点： • 一些读者关注技术细节和论文内容： ◦ [eigenform] 认为延迟更新预测器和不阻塞特权指令的流水线处理是有道理的，但担心不同特权级之间的预测状态可能不一致，造成潜在风险。 ◦ [rini17] 提出如果CPU分支预测器能内置检查缓冲区边界和特权级的功能，问题会更容易解决，但现实中由于C语言指针的广泛使用，这种改进较难实现。 • 关于漏洞与其他攻击的关系： ◦ [rakingleaves] 提到此漏洞与刚披露的 "Training Solo" 攻击之间的关系，引发对类似攻击的关注。 • 关于不同硬件厂商的漏洞情况： ◦ [rtkwe] 质疑AMD硬件是否存在类似漏洞，并指出推测执行可能在共享处理器资源时成为难以修复的漏洞。 • 关于补丁和操作系统支持： ◦ [smartmic] 对文章只提到Windows而未提及Linux表示不满，认为Linux用户也应被关注。 ◦ [yonatan8070] 希望确认当前是否已有适用于所有主流操作系统的补丁来缓解此问题。 • 对Intel未来发展的讨论： ◦ [margorczynski] 对Intel的市场前景表示担忧，认为其在技术和生产上的劣势可能导致其被ARM和RISC-V等竞争者取代，但也提到美国芯片角度可能影响Intel的存续。 • 对漏洞披露和影响的进一步探讨： ◦ [Alcatros552] 强调此问题属于新的分支预测器漏洞，指出Intel的eIBRS无法缓解问题，并说明在问题披露时多数系统已经打了补丁。 ◦ [tannhaeuser] 对Kaby Lake处理器是否受影响表示困惑，基于博客文字难以判断。 补充讨论： • 一些评论带有幽默和讽刺性质，如[HeliumHydride]引用Mickens的学术文章调侃分支预测器问题。 • 技术解决方案的讨论，如[x3al]询问是否可以通过隔离浏览器和桌面环境来防止JavaScript攻击。 • 对安全补丁的漠不关心，如[201984]表示对关闭缓解措施无所谓。 争议焦点： • 主要集中在Intel处理器是否有效缓解了此分支预测器漏洞，以及其他硬件厂商是否面临类似问题。
