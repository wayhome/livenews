Prospero challenge, now with more garbage collection

作者: todsacerdoti | 评分: 14 | 评论数: 1 | 发布时间: 2025-03-25 17:56
文章摘要

本文介绍了Matt Keeter发起的Prospero挑战，目标是优化一个使用Python和NumPy编写的图像计算程序，使其运行更快。原始程序在执行时会占用近60GB的内存用于存储中间变量。通过引入**liveness analysis**和**garbage collection**技术，作者成功减少了内存占用，程序运行时间从40秒缩短至10秒，且内存使用控制在1GB以内。 此外，作者尝试使用CuPy（一个基于GPU的NumPy替代品），使程序在1.5秒内完成运行。然而，在尝试处理4096x4096分辨率的图像时，由于超出GPU内存限制，程序出错。 总的来说，本文展示了通过内存优化和GPU加速两种方式显著提升程序性能的过程。

Mruby/C and picoruby: high level langs in low-level devices?

作者: rahil627 | 评分: 62 | 评论数: 10 | 发布时间: 2025-03-23 09:20
文章摘要

PicoRuby 是一个专为单片微控制器设计的微型 Ruby 实现，具有小尺寸和可移植性特点。它在 32 位架构下仅需 256 KB ROM 和 128 KB 或更少的 RAM。PicoRuby 依赖标准 C 库，如 glibc 或 Newlib，并支持 Raspberry Pi Pico 等微控制器板。它提供了 API 文档和演示视频，并依赖于 mruby/c 实现的虚拟机。PicoRuby 可用于构建 PRK Firmware 键盘固件和 PicoRuby WASI WebAssembly 运行时。构建过程需要 C 工具链、git 和 Ruby 3.0 以上版本。项目仍在开发中，遵循 MIT 许可协议，并获得了 Ruby Association Grant Program 的支持。

主要讨论点：微控制器上不同编程语言和工具的适用性及优缺点 不同观点： • **支持MicroPython**：[throwaway81523] 认为MicroPython非常流行，适合在能支持它的设备上使用，尤其是像Adafruit Trinket这样具有256KB闪存和32KB RAM的设备。虽然MicroPython在只有16KB RAM的BBC micro:bit上运行比较困难，但在多数小型设备上表现良好。另外，提到Lua和Hedgehog Lisp作为更小的选择，以及Javacard和J2ME在特定设备上的使用。对于极小设备，建议放弃垃圾回收机制，使用Forth或交叉编译语言。 • **MicroPython与C的结合**：[jononor] 喜欢MicroPython，并指出它易于与C语言结合使用，这对于在微控制器设备上获得最佳性能非常必要。 • **支持picoruby**：[aidog] 推荐picoruby，认为它非常有趣，是mruby/c的更小版本。他还分享了HASUMI Hitoshi的演示视频，展示了picoruby在Raspberry Pi Pico及其他微控制器上的应用。 • **支持高层次语言在微控制器上运行**：[calebh] 介绍了Juniper，一种用于Arduino的功能反应式编程语言，证明了高层次代码（如闭包）也可以在小型设备上运行。 • **提供picoruby的资源**：[xutopia] 提供了picoruby的文档链接，供感兴趣的人查阅。 • **再次推荐MicroPython**：[TkTech] 提到MicroPython在这个领域占据主导地位，并提供了GitHub链接供进一步了解。 • **对C语言的争议**：[rahil627] 提到有些人不喜欢使用C语言，而有些人则喜欢并拥抱它。同时提出疑问，Ruby这样的复杂语言在微控制器（如传感器）上是否有意义，并表示对pico上Ruby实现的维护感到欣赏。 • **提到Shedskin Python到C++编译器**：[actionfromafar] 提到了Shedskin，一个Python到C++编译器，作为另一种选择。 • **对设备存储的看法**：[bsder] 认为256KB闪存和128KB RAM已经不算小，比1990年之前的平均计算机还大，并指出RAM和闪存的大小对微控制器的价格有很大影响。 补充讨论： • 讨论中涉及多种语言和工具，如MicroPython、picoruby、Lua、Hedgehog Lisp、Forth、Juniper、Javacard和J2ME，反映了在微控制器上运行不同类型语言的可行性和实用性。 • 争议焦点在于是否在微控制器上使用复杂语言如Ruby，以及C语言是否真的不适合这些场景。 • 不同语言和工具的支持者提供了各自的资源和演示，展示了它们在微控制器开发中的实际应用和优势。

Critical Unauthenticated Remote Code Execution Vulnerabilities in Ingress NGINX

作者: puppion | 评分: 57 | 评论数: 5 | 发布时间: 2025-03-25 10:12
文章摘要

Wiz Research发现了一系列未经身份验证的远程代码执行漏洞（CVE-2025-1097, CVE-2025-1098, CVE-2025-24514, CVE-2025-1974），影响Kubernetes的Ingress NGINX Controller，命名为#IngressNightmare。这些漏洞允许攻击者未经授权访问Kubernetes集群中的所有秘密信息，可能导致集群被接管。该漏洞的CVSS v3.1基础评分高达9.8。 研究显示，约43%的云环境易受此漏洞影响，超过6,500个集群（包括财富500强公司）公开暴露了易受攻击的Ingress控制器。建议尽快修补漏洞。 Ingress NGINX Controller是Kubernetes中常用的入口控制器，默认情况下其 admission controllers 未经身份验证可网络访问，攻击者可利用恶意入口对象实现远程代码执行。 缓解措施包括： 1. 升级到Ingress NGINX Controller的最新版本（1.12.1或1.11.5）。 2. 确保admission webhook端点不外部暴露。 3. 实施严格的网络策略，仅允许Kubernetes API服务器访问admission controller。 可以使用Nuclei模板检查暴露的Ingress-NGINX admission controllers。

评论摘要
主要讨论点：Kubernetes环境中入口控制器和准入控制器的安全性，尤其是Ingress-NGINX相关漏洞的暴露和利用风险。 不同观点： • [rollulus] 对Kubernetes准入控制器暴露在公共互联网的情况表示困惑。他认为Kubernetes API虽然暴露在互联网上，但未认证的请求都会被拒绝，因此不理解为何准入控制器会成为问题。他还质疑在什么样的错误配置下，准入控制器会暴露给外界。 • [boxed] 质疑标题中突出NGINX的问题，因为他认为问题出在Kubernetes本身，而不是NGINX。他觉得将问题归咎于NGINX有些不公平。 • [KronisLV] 提到其他入口控制器（如Traefik）并认为碎片化（即有多种不同的入口控制器选择）在一定程度上是好事，因为它限制了单一漏洞大范围影响的可能性。他还指出，使用传统网络服务器（如Caddy或Apache2）作为入口控制器的基础可能对一些长期项目或家庭实验室环境有帮助。 • [SCdF] 提供了一个讨论链接，表示该话题已在其他地方讨论过，但没有深入提出自己的观点。 • [Traubenfuchs] 澄清了漏洞利用的条件，指出要利用此漏洞，攻击者需要直接向Kubernetes资源（准入控制器）发送请求。这种情况通常只有在明显危险的错误配置或极其松散的安全标准下才会发生。正常情况下，Kubernetes资源不应从互联网访问。 补充讨论： • 争议的焦点在于准入控制器的暴露和利用风险，以及问题是否应归咎于NGINX。 • 讨论中还涉及到Kubernetes集群的安全配置问题，特别是如何避免将Kubernetes资源暴露在公共互联网中。 • [KronisLV] 提出了对入口控制器多样性的看法，认为多样性可以减少单一漏洞的广泛影响，但也担心许多用户可能不会及时更新或修复不安全的软件配置。 总结：评论主要围绕Kubernetes准入控制器的安全性、错误配置的可能性以及问题是否应归因于NGINX展开讨论。参与者对漏洞利用的具体条件和配置错误的影响有不同理解，并探讨了可能的解决方案和安全实践。

I won't connect my dishwasher to your cloud

文章摘要

作者因旧的GE洗碗机故障不得不购买新机，最终选择了Bosch 500系列。安装过程总体顺利，但发现一些功能（如冲洗循环、延迟启动和节能模式）需要通过应用程序控制，而使用这些功能还需将洗碗机连接到WiFi并注册云账户。作者对此设计感到不满，认为这是不必要的复杂化。此外，作者对比了旧GE机型的问题，如控制面板电力故障和锈蚀，最终决定换新机。尽管Bosch的安装较顺利，但作者对触控感应控制和云需求感到困惑和不便，认为简单的按钮设计更实用。

评论摘要
主要讨论点：现代家电（尤其是洗碗机）强制要求WiFi连接和应用程序使用的问题，以及消费者对隐私、安全和使用体验的担忧。 不同观点： • **接受部分功能受限的用户**：[nkurz] 认为，即使不连接WiFi，该洗碗机仍然能很好地完成洗涤任务。他承认缺少一些高级功能（如冲洗循环和清洁模式）可能不便，但总体性能令人满意。他指出，Costco版本可能缺少关键功能（如“自动空气”功能），购买时需注意。 • **强烈反对强制WiFi连接的用户**：[dorfsmay] 和 [jmholla] 表达了对Bosch强制通过应用程序操作某些功能的不满。他们指出，即使全额付款购买家电，消费者仍无法完全使用所有功能，除非注册账户并连接WiFi。这种做法引发用户反感，他们建议通过退货来抵制这种销售策略。 • **建议抵制和退货的用户**：[klipklop] 和 [jmholla] 建议消费者通过退货来抵制厂商的不合理要求，认为只有通过经济手段才能让厂商感受到压力。尽管退货麻烦，但如果消费者在意隐私和功能自主性，则必须付出额外努力。 • **支持简单传统家电的用户**：[btbuildem] 和 [dsalzman] 偏好购买功能简单、无需联网的传统家电。他们认为行业文献和维修数据更有参考价值，并指出许多“智能功能”实际上并不必要。此外，[dsalzman] 提到商用家电通常更可靠，且无需担心联网问题。 • **对未来趋势的担忧**：[NegatioN] 担心未来可能没有不联网的家电可供选择，而[Avamander] 和 [m4tthumphrey] 则对家电联网带来的隐私和安全问题表示担忧，认为本地操作应优先于云端连接，且联网设备容易遭受攻击和出现服务中断。 补充讨论： • **技术实现的讨论**：[Avamander] 和 [didgetmaster] 提到，如果设备能自动完成所有任务（如自动装载和存放碗碟），云连接或可接受。但现有技术实现不理想，且存在安全隐患和服务不稳定问题。 • **厂商应对消费者反馈的案例**：[4ndrewl] 提到一个正面案例，某厂商通过更新去除了应用程序注册要求，与大多数增加强制注册的厂商形成对比。 争议焦点： • 强制WiFi连接和应用程序使用是主要争议点，用户对此做法感到不满，认为侵犯了消费者自主使用产品的权利。 • 退货和抵制是否有效成为讨论热点，部分用户认为这是促使厂商改变策略的唯一途径，而另一些用户则认为退货过程过于麻烦且不现实。 总的来说，评论反映了对现代家电强制智能功能的广泛争议，以及消费者对隐私、安全和使用体验的深切关注。
