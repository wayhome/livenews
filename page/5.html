Welcome to the Strip Mining Era of OSS Security

作者: salsakran | 评分: 96 | 评论数: 19 | 发布时间: 2026-05-15 11:37
文章摘要

文章指出，随着LLM和编码代理能力提升，公开源码中的漏洞正被大规模、低成本地“批量挖掘”，导致安全报告激增且不少是真漏洞。短期内OSS维护者会面临更多告警和压力，但长期看，这种自动化扫描会帮助更快发现并修复问题，整体提升开源安全。

评论摘要
主要讨论点：AI/LLM辅助漏洞发现是否会加剧开源维护压力，以及这究竟是“安全灾难”“正常修复过程”还是安全市场演化。 不同观点： • 漏洞公开是好事：ahlCVA、xbar认为代码本来就有缺陷，发现并披露只是面对事实；把漏洞挖掘称为“掠夺”是倒退，真正令人困惑的是有人宁愿保留0day。类似数学证明被找出错误，应庆幸未来不再建立在错误前提上。 • 开源维护者不应被默认要求无偿救火：Macha、adamtaylor_13、hrjriritifif强调，用户和安全公司免费使用OSS，却期待维护者周末立刻修复并提供支持是不合理的；这是志愿劳动，若要SLA和紧急响应应付费。 • AI会扩大攻击面和发现速度，闭源也难幸免：_alternator_、mtlynch指出LLM可辅助反编译和理解二进制，闭源软件同样面临风险；开源只是更容易被扫描。gmuslera补充，闭源若源码泄露，漏洞可能长期暗中存在。 • 商业化安全投入会变得更重要：mtlynch认为不设或低额bug bounty的产品难吸引善意研究者，却会吸引攻击者；他举Kagi UXSS仅100美元，而Firefox/Chrome同类漏洞奖励达数千到上万美元为例。cyrusradfar认为企业需要更多人工安全投入、流程管控，并可通过local-first减少云端暴露。 • 这可能是技术成熟后的“二级安全市场”形成：likesHumidity类比2017年S3误配置事件，AWS推出Block Public Access、CSPM市场成熟；AI层也可能出现类似治理与防护市场。OSS承压结果取决于制度支持：FFmpeg获德国基金支持而改善，Ingress-Nginx因维护不可持续退役。 • 乐观派认为风暴会趋缓：marginalx认为短期内漏洞报告会激增，商业开源可能借“安全靠隐蔽”缓冲，但真正开源无法如此；长期看报告会平台化、回到可管理节奏。 • 怀疑或反对声音：krupan认为这是AI炒作；ryanackley提醒同时存在大量“AI垃圾漏洞报告”，如Turso因被无用报告淹没而关闭bug bounty。 补充讨论：争议焦点在于“漏洞发现速度提升”应被视为安全进步，还是对无偿维护体系的不可持续压榨；以及谁应为修复成本买单。

评论摘要
主要讨论点：独立/小型创业公司是否应尽早做 SOC2（或 ISO27001）认证，以及如何应对企业客户的安全合规要求。 不同观点： • 强烈反对提前做 SOC2：认为 SOC2更多是企业间“握手暗号”，并不能真正证明安全；不要为了提升销售前景而投机性认证，除非已有订单明确要求且收入能覆盖成本。 • 小公司应尽量拖延或替代：多位评论者称，早期客户常可通过安全问卷、风险接受、例外审批等方式绕过 SOC2；只要客户足够想买产品，合规要求通常可协商。 • SOC2/ISO 对单人或极小团队很难：争议集中在职责分离、内部审计、代码审核等要求是否可行。有人认为少于5人拿 SOC2反而是红旗，客户会审查报告和审计机构质量。 • 可先做“SOC2-aligned”实践：建议先建立 MFA、EDR、访问控制、备份、隐私政策、安全页面、CAIQ问卷、自评文档等，向客户展示安全意识和改进计划。 • 认证并非完全无用：有人认为若认真做，可帮助发现流程弱点；小团队范围较小，部分控制可能更简单，但仍需大量文档、流程和成本，且审计机构是否理解小公司很关键。 • 实务经验：有创业公司在拿到大客户交易后才做 SOC2；也有人建议用一次性渗透测试或第三方安全报告替代正式认证。 补充讨论：ISO27001被认为与 SOC2类似甚至更强调角色和审计分离，对1-2人公司也存在可行性疑问。争议焦点是：SOC2是必要信任证明，还是高成本、低安全价值的销售门槛。

Git Is Not Fine

作者: steveklabnik | 评分: 33 | 评论数: 6 | 发布时间: 2026-05-15 17:51
文章摘要

文章批评 Git 主要擅长分布式存储，却把协作工作流当成附带功能，导致堆叠 PR、异步开发、追踪后继提交/重写历史等场景很别扭；作者借此推荐 jj，认为它更适合现代分布式协作。

评论摘要
主要讨论点：围绕 Git 在复杂/单仓库/多分支并行开发中的不足，以及 jj、stacked PR、AI 辅助等替代或补充方案是否必要。 不同观点： • Git 难以支持“树状工作流”：luckymate 认为在增长中的 monorepo 中，多个改动同时发生且彼此依赖，Git 很难把不同改动自然分配到不同分支；worktree、stash、切分切换分支都不够顺手。LLM 让这种并行小修更多，问题更明显，因此想尝试 jj。 • Git 已足够，问题被夸大：demorro 不理解 stacked PR 的必要性，认为 commit 已能隔离工作，rebase 也不难；可能不同开发领域差异较大，比如 C++ 开发不像 JS 那样频繁提交多个 PR。 • 复杂 Git 操作可交给 AI：vintagedave 表示自己也很少手动 rebase 或改 commit message，复杂操作现在常用 AI；同时怀念基于 Mercurial 的系统，暗示 Meta 等内部工具确实更好用。 • Git 的限制源自分布式设计：alphabeta3r56 认为 Git 没有某些集中式“全局关系”能力，是为了保持完全分布式，不能简单说更差；但支持跟踪未提交状态、避免丢失工作是改进。对 workflow 问题则质疑 worktree 是否已足够。 • 反对用“稻草人”推销 jj：karmakaze 认为文章复杂度有些人为夸大；自己可通过 rebase 最后一层分支，再用 `git branch -f` 重定位其他分支处理 stacked PR。过去处理多层 submodule 也能靠熟练操作完成，但教训是少用 submodule。AI 也可辅助 rebase。 补充讨论：争议焦点在于 Git 的复杂性是工具缺陷、工作流不当，还是可通过熟练操作/AI/worktree 解决；另一个分歧是集中式便利性是否值得牺牲 Git 的分布式特性。

文章讲述澳大利亚“平图皮九人”：1984年在西澳沙漠中被发现的最后一支游牧家庭。他们长期与外界隔绝，靠水源迁徙、猎蜥蜴和袋鼠生存。被发现后与族人重聚，迁入偏远的Kiwirrkurra社区。

评论摘要
主要讨论点：评论者回忆一部 Malcolm Douglas 纪录片中关于 Pintupi 人、游牧生活消逝与传统工具被带走的片段。 不同观点： • 对传统游牧生活延续的关注：片中有一位 Pintupi 人选择回到沙漠，继续以游牧方式生活；其他人会定期外出寻找他，说明这种生活方式虽已边缘化，但仍有人试图维系。 • 对文化消逝的感伤：评论者最受触动的是，一处旧水源旁留下了用于磨草籽制面包的磨石，这些工具可能已在原地存在了几代人，却因为“不再有人使用”而被带走，象征一种生活方式的终结。 • 对纪录片记录价值的认可：Malcolm Douglas 记录了寻找这位游牧者的过程，也间接保存了关于水源、工具、食物制作和沙漠生存方式的记忆。 补充讨论：此评论没有与其他评论形成直接争论，核心情绪是怀旧、惋惜与文化断裂感。争议点不明显，但隐含的问题是：当传统生活方式无人继承时，相关遗物应留在原地作为历史痕迹，还是带走保存以免遗失。
