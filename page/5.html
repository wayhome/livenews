Cross-Account and Cross-Region Backups with AWS Backup (and Friends)

作者: terussell85 | 评分: 38 | 评论数: 3 | 发布时间: 2025-06-20 23:40
文章摘要

文章主要讨论了在使用AWS Backup时遇到的一个问题：尽管AI可能声称AWS Backup支持跨账户和跨区域备份，但实际上AWS Backup并不支持同时进行跨账户和跨区域的备份。文章指出，AWS Backup可以支持跨账户复制和跨区域复制，但无法同时实现两者，特别是在处理RDS、Aurora、DocumentDB和Neptune等数据库服务时。 作者强调，为了满足数据保护和灾难恢复的需求，同时实现跨账户和跨区域备份是必要的。跨区域备份可以防止未经授权的访问，而跨账户备份则可以在区域性灾难（如火山爆发）时保护数据。 尽管AWS Backup支持集中式备份计划，但目前仍无法同时实现跨账户和跨区域的备份。作者建议了一种临时解决方案，即使用AWS Lambda脚本在完成第一次复制后触发第二次复制，并删除第一次复制。最终，作者期望AWS未来能支持同时进行跨账户和跨区域的备份，以简化实施过程。

评论摘要
主要讨论点：AWS Backup及其在应对勒索软件等场景中的有效性与使用价值 不同观点： • **time0ut的观点：** - 认为AWS Backup在应对勒索软件场景时不够成熟（"half baked"），尤其是在将现有应用栈恢复到恢复账户时，操作复杂且费力。 - 提到了一家名为Arpio的公司，认为其服务可以补充AWS Backup的不足，能够复制更多内容，推荐其他公司考虑使用Arpio。 - 声明自己与Arpio无利益关联，只是曾与客户合作使用过。 • **nodesocket的观点：** - 质疑AWS Backup的必要性，尤其是当基础设施已经通过Terraform进行管理时，RDS、EBS快照、ElastiCache、S3等服务本身已具备备份配置选项。 - 暗示如果现有工具已经可以完成备份工作，那么AWS Backup可能没有额外优势。 • **sgarland的观点：** - 对跨区域备份的意义提出质疑，认为如果整个区域消失（非暂时性中断），可能是国家遭受攻击，这种情况下没人会关心SaaS产品是否存活。 - 暗示跨区域备份在极端情况下可能没有实际意义。 补充讨论： - **Arpio作为备选方案：** time0ut提到了Arpio作为AWS Backup的替代或补充服务，提供了实际使用经验，并认为其在多数情况下比自己动手实现备份更值得。 - **不同场景下的备份需求：** 讨论中涉及了勒索软件防护、跨区域备份、基础设施管理等不同场景，反映了不同用户对备份需求的关注点和优先级差异。 - **争议焦点：** 主要集中在AWS Backup的成熟度和必要性上。time0ut认为其功能不足且操作复杂，nodesocket则质疑其在已有工具下的附加价值，sgarland则对跨区域备份的意义提出根本性质疑。 这些观点反映了在云基础设施备份方案选择上的多样化考虑，包括工具成熟度、使用便捷性以及实际场景中的需求和价值。

Show HN: Ariadne – A Rust implementation of aperiodic cryptography

作者: ciphernomad-org | 评分: 30 | 评论数: 11 | 发布时间: 2025-06-23 03:54
文章摘要

Ariadne Protocol 是一个由 CipherNomad 提出的新型加密架构，旨在实现非周期性、状态依赖的加密转换。该协议基于 Labyrinth（一个大型确定性生成的二叉树）和 Thread（秘密的、非周期性的路径）两个核心概念。其主要创新在于通过加密虚拟机（CVM）动态计算每块数据的加密路径，而无需存储或传输路径信息。Ariadne Suite 是该协议的 Rust 实现，包含核心架构、加密原语和高层次协议等组件，如 `ariadne-core`、`ariadne-generator` 和多种 AEAD 协议。该项目为开源研究，作为公共资源发布，但仍处于实验阶段，尚未经过第三方安全审计，不建议用于生产环境。

评论摘要
主要讨论点：新协议的目的和安全性，特别是与现有AEAD（如Rust中的AEAD）相比的优势和潜在风险。 不同观点： • Medea认为该协议的目的不明确，质疑其相较于现有AEAD（如Rust中的实现）提供的额外安全保障是什么，尤其是在构建协议时有何独特优势。 • kennethallen质疑协议中PRNG使用固定大小状态的说法，认为即使周期很长（如2^256次操作），仍会有周期性。他还指出，与块加密（如AES+GCM）相比，该方案更复杂，但在保密性和篡改保护方面未见明显优势，且块加密有并行加密和解密、硬件支持等实际优势。 • conradludgate指出代码中的具体问题：在随机轮中使用Hash时，只加密了一半的数据块，另一半未加密，这可能会导致安全问题。 • willvalfar担心某些路径可能导致不安全的密码使用，进而导致更大范围的妥协。例如，程序经过类似2DES的状态时可能遭受中间人攻击，从而大大减少攻击者搜索空间。 • vintermann认为，任何算法都可以被重新描述为“自修改”、“非周期性”等，但这并不会增加安全性。这种描述只会让分析变得更困难，但并不会真正提高安全性。 • CharlieTrip作为密码学研究者，指出缺乏数学描述让分析协议安全性变得困难。他还提到协议中的OTP（一次性密码本）部分看起来奇怪，需特别关注密钥扩展和加密路径选择问题。 • ramchip将该协议与Signal中的KDF链进行比较，质疑两者在密钥派生方面的相似性和差异。 • Asraelite关注该协议是否或能否适应后量子时代。 • ur-whale质疑“该密码非周期性”的说法，认为在有限物理机器上运行的代码不可能真正做到理论上的非周期性。 补充讨论： • stop50指出链接错误，提供了一个修正链接。 • 总体来看，争议焦点在于该协议的复杂性、潜在安全性和相较于传统AEAD或块加密的实际优势。

作者: keepamovin | 评分: 182 | 评论数: 7 | 发布时间: 2025-06-22 07:27
文章摘要

这篇文章探讨了Linux中Unix管道的实现和性能优化。作者通过一个简单的测试程序逐步优化管道读写速度，从最初的3.5GiB/s提升到约36GiB/s。优化过程包括使用`perf`工具进行性能分析，介绍`vmsplice`和`splice`系统调用以提升性能，以及通过使用大页面（huge pages）进一步改进。最终，通过将轮询改为忙等待（busy looping）完成最后的优化。文章详细解释了每一步的原理，包括管道的内部实现、Linux分页机制等，并提供了代码示例和性能对比图。测试在Intel Skylake i7-8550U CPU和Linux 5.17上进行，结果会因系统环境不同而有所变化。

评论摘要
主要讨论点：Linux与Windows在管道（pipes）操作上的性能差异及技术实现细节，以及对具体技术如splice()的讨论和其未来发展的疑问。 不同观点： • [zh3] 分享了将基于Linux管道的应用程序移植到Windows上的糟糕性能体验，指出Windows在处理管道连接时的性能问题，甚至在使用C#和Win10时性能差距依然显著。 • [johnisgood] 讨论了Linux和BSD系统中不同的高效数据传输方式，特别提到splice()在Linux上的零拷贝优势，以及在BSD系统上readv() / writev()可能是更有效的方法。 • [gkfasdfasdf] 仅仅提到文章之前在其他平台被讨论过，没有提出新的技术观点。 • [lukeh] 询问现代Linux是否有类似于Solaris Doors的机制，用于低延迟的小数据量进程间通信，认为AF_UNIX可能不是最佳选择。 • [gigatexal] 对文章本身表示赞赏，未提出技术性讨论。 • [aeonik] 对文章缺乏评论表示遗憾，同时对splice()的安全性和ABI破坏问题表示关注，并好奇splice()的长期支持以及是否能默认使用splice()来优化管道性能。 补充讨论： • [johnisgood] 提到了多种数据传输函数如readv() / writev()、splice()、sendfile()等，并详细分析了splice()在Linux上的高效性，但也指出了其仅限于Linux系统的局限性。 • [lukeh] 提出了对Linux系统中进程间通信的低延迟替代方案的需求，特别是与AF_UNIX的对比。 • [aeonik] 对splice()的长期支持表示不确定，并提出是否有可能通过默认使用splice()来提升管道性能的设想。 争议焦点： • Linux和Windows在管道操作上的性能差异，尤其是Windows在处理等待连接的管道时的表现较差。 • 关于splice()在Linux上的使用及其未来发展的不确定性，特别是其安全性及ABI破坏问题。 • 对Linux系统中低延迟进程间通信机制的选择，是否存在比AF_UNIX更优的方案。

文章摘要

Git notes 是一种向 Git 提交添加元数据的方式，用于在不变更提交本身的情况下，为旧提交附加新信息，如代码审查和测试结果。它们可以存储关于任何 Git 对象（提交、blob、树）的元数据，并通过命令行操作。尽管功能强大，Git notes 使用起来较为复杂，界面不直观，导致其使用率低，且 GitHub 等平台未广泛支持。然而，一些工具和插件（如 Gerrit 的 reviewnotes 插件和 Google 的 git-appraise）展示了 Git notes 在分布式代码审查中的潜力。总体而言，Git notes 提供了强大的功能，但受限于可用性和用户体验。
