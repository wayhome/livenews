Taming the UB Monsters in C++

作者: ingve | 评分: 79 | 评论数: 10 | 发布时间: 2025-03-31 06:45
文章摘要

Herb Sutter的这篇文章讨论了C++在安全性和防护方面的进展，特别是针对未定义行为（UB）的改进。文章提到，C++社区正在努力解决UB问题，以增强软件的安全性。自C++11以来，越来越多的C++代码变得无UB。在即将发布的C++26中，编译时执行的代码已无UB，且标准库的常见越界错误也不再是UB。文章还提到，正在系统性地解决运行时UB问题，包括引入"错误行为（EB）"和"合约断言"等工具。Bjarne Stroustrup的配置文件框架也在开发中，旨在通过默认全安全选项并允许在必要时选择退出。此外，Úlfar Erlingsson提议通过一个配置文件来消除用于远程代码执行的UB。这些改进旨在解决C++中常见的内存安全和安全漏洞问题。

评论摘要
主要讨论点：C++中的未定义行为（UB）及其相关的安全问题，特别是在与内存安全和语言设计的关系中的讨论。 不同观点： • **[roca]** 认为当前没有新的措施来防御与生命周期相关的UB。引用的研究论文只是对现有动态缓解措施的总结，而这些措施并不能在语言层面解决UB问题，且在性能上存在权衡。成熟的软件如Chrome已经采用了这些措施，但仍无法彻底解决C++ UB问题。 • **[pjmlp]** 表示虽然C++的改进是积极的，但可能为时已晚。标准工作组和实际从事C/C++编译器工作的人员交集很少，因此这些改进能否以及如何在编译器中实现还有待观察。不过，任何改进都是受欢迎的，因为许多C++工具不太可能被重写为其他语言。 • **[uecker]** 指出C语言已经在C23中明确了时间旅行UB的问题，并消除了约30%的核心语言UB。同时计划添加可选的内存安全模式，提供完整的空间和时间内存安全。然而，认为突然专注于内存安全有些奇怪，因为对于长期Linux用户来说，这不是主要问题。内存安全措施只是增量改进，只要存在不安全代码，就无法实现完美的内存安全。 • **[agwa]** 质疑当前措施对零日漏洞价格上涨的实际影响，指出只有constexpr代码没有UB，而这部分代码本来就不会被攻击者利用。 • **[mafuy]** 对C++最近版本是否已消除大部分UB表示困惑，指出像`INT_MAX + 1`这样的简单操作仍然是UB。 • **[gw2]** 提问关于在C++代码库中部署缓解措施如CFI和边界检查的安全性问题，并希望得到与Rust对比的具体分析，而不仅仅是“只有Rust是安全的”这种回答。 • **[dist-epoch]** 认为C++社区过去忽视了安全问题，直到微软宣布新代码优先使用Rust，才意识到问题的严重性。 • **[qalmakka]** 指出C++的UB问题主要在于遗留代码库和旧框架，而不是现代C++。在遗留代码库中引入现代C++和引入Rust一样困难。 • **[saagarjha]** 认为当前的改进措施没有解决攻击者利用C++软件的问题，例如双重释放（double free），C++委员会因为不想大幅改变语言而没有彻底解决这些问题。 • **[techbrovanguard]** 用“否认、愤怒、讨价还价、抑郁、接受”来形容C++社区对UB问题的反应，暗示对现状的不满和无奈。 补充讨论： • 讨论的核心争议在于C++是否能够通过现有或计划中的改进措施有效解决UB问题，特别是内存安全问题。 • 不同观点反映了社区对C++和Rust在安全性和性能上的对比，以及对遗留代码库现代化困难的认识。 • 微软转向Rust被视为推动C++社区正视安全问题的关键事件。

Xfinity XB3 hardware mod: Disable WiFi and save 2 watts

作者: p1mrx | 评分: 54 | 评论数: 7 | 发布时间: 2025-03-30 20:52
文章摘要

这篇文章介绍了一种通过硬件修改来禁用Xfinity XB3（Arris TG1682P）路由器上的WiFi功能的方法，从而节省2瓦的功耗。尽管在桥接模式下操作，设备仍会广播隐藏的SSID且无法通过软件关闭WiFi。作者通过拆解设备，找到WiFi模块的电源管理芯片（TPS54328），将第1针接地以关闭WiFi。此修改使设备功耗从14.9瓦降至12.5瓦，WiFi指示灯熄灭，有线以太网仍正常工作。但需注意，这种修改可能涉及电路风险，且设备使用的Intel Puma 6芯片组曾有延迟问题，作者尚未发现明显异常。

评论摘要
主要讨论点：ISP提供硬件及相关网络设备的问题，包括用户自带设备的选择、设备性能和潜在的技术问题。 不同观点： • **[wpm]** 认为ISP应提供必要的硬件以支持单一IP地址，并允许用户轻松选择不使用ISP提供的捆绑设备。他强调用户应能够简单地选择退出使用ISP的设备，而不影响服务质量。 • **[don-code]** 质疑用户对租用设备的物理改动是否会被ISP（如Comcast）接受，并指出ISP通常通过更换设备来解决问题的标准操作程序。 • **[easton]** 提到，有时ISP的设备需要重置以解决推送的坏更新，并且在启用桥接模式之前可能需要通过WiFi网络进行初始设置。如果WiFi硬件损坏，用户可能需要更换设备。 • **[johnklos]** 对仍在使用Intel Puma芯片组的设备表示惊讶，并指出周围过多的WiFi网络对速度的影响。他主张禁用WiFi网络，并对设备在后台运行WiFi网络表示不满。 • **[quailfarmer]** 分享了自己的经历，提到ISP提供的设备有噪音问题（如风扇持续运转）。 • **[metaphor]** 提出在电费高昂的地区，通过减少设备功耗节省的费用有限，并指出设备在桥接模式下仍然广播隐藏SSID且无法关闭无线电功能的问题。 • **[rasz]** 分享了2014年Liberty Global的案例，其中用户的设备被用于提供公共WiFi热点，即使在尝试退出后，设备仍会共享网络。最终通过物理移除WiFi卡解决问题。 补充讨论： • 争议的焦点之一是用户对ISP提供设备的控制权，特别是能否有效选择退出使用ISP的捆绑设备以及关闭不必要的无线功能。 • 另一个值得注意的点是设备的技术问题，包括硬件故障、固件更新和潜在的网络安全问题（如设备被用于共享网络）。 • 不同用户对设备功耗和性能的关注程度也有所不同，特别是在电费高昂的地区。

HTTPS RR in Curl

文章摘要

RFC 9460 引入了名为 HTTPS 的 DNS 资源记录（RR），用于提供目标主机名的服务元数据。HTTPS RR 替代了未广泛使用的 SRV 和 URI 记录，并部分取代了 HSTS 和 alt-svc 头。其主要功能包括提供 ECH 配置（加密客户端问候，用于隐藏 TLS 握手时的 SNI）、ALPN 列表（指示支持的 HTTP 版本，如 HTTP/3）、目标主机名和端口等信息。当前，curl 提供了对 HTTPS RR 的实验性支持，但需要在构建时显式启用。由于标准 API 不支持 HTTPS RR，curl 使用 DoH（DNS-over-HTTPS）、本地解析器（如 c-ares）等方法获取记录。目前，该功能尚未完全实现，但已有一些网站（如 Cloudflare）开始使用 HTTPS RR。
