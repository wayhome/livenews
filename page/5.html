How fast can the RPython GC allocate?

作者: todsacerdoti | 评分: 25 | 评论数: 3 | 发布时间: 2025-06-15 19:55
文章摘要

本文介绍了作者对RPython垃圾收集器（GC）对象分配速度的基准测试过程。作者编写了一个简单的RPython程序，通过循环创建对象来测量分配速度。为了避免静态优化移除分配代码，作者使用了一种技巧，保持两个对象同时存活。基准测试包括初始化和不初始化对象字段两种情况。 在64位架构下，每次分配大约需要16字节。测试结果显示，未初始化字段时，分配速度为34.348 GB/s，初始化字段时为29.692 GB/s。相比之下，使用Boehm GC的版本速度较慢，未初始化和初始化时的速度分别为1.532 GB/s和1.538 GB/s，这是因为Boehm GC使用保守的栈扫描，无法移动对象。 作者还使用`perf`工具获取了更详细的性能统计数据，结果显示RPython GC在循环中达到了每周期超过5条指令的效率。这表明RPython GC在对象分配上的性能表现相当出色。

评论摘要
主要讨论点：不同内存分配器（allocator）的性能比较，包括在特定硬件上的分配速度、指令数量以及与传统分配器（如malloc/free）的对比。 不同观点： • **Kragen的观点**：Kragen指出，在CF Bolz的AMD Ryzen 7 PRO 7840U机器上，每个纳秒有1-2次分配，每次分配大约11条指令。这比Kragen自己的C语言分配器kmregion快2-4倍。Kragen的分配器在快速路径上也有类似数量的指令，但他测试的硬件较慢，并且测试的是16字节初始化对象且没有垃圾回收（GC）。kmregion的速度大约是malloc/free的10倍，但他并不强烈推荐使用kmregion，因为该工具从未被用于任何重大项目，只是作为一个概念验证。 • **pizlonator的观点**：pizlonator认为，CF Bolz的分配器比Boehm快，并不是因为保守栈扫描（conservative stack scanning），而是因为使用了不同的算法。他指出，可以通过保守栈扫描来移动对象，JavaScriptCore曾使用过这种方法。最快的非移动收集器（non-moving collectors）在分配速度上可以与最快的移动收集器（moving collectors）相媲美。他提到了JavaScriptCore的bump'n'pop分配器、Fil-C的SIMD turbosweep方法以及Immix方法等不同实现方式。 • **forrestthewoods的观点**：forrestthewoods对11指令和2.1周期每次分配的度量表示怀疑，认为这不符合常理。他引用自己几年前的一个基准测试，p95为25纳秒，而p99.9则在几十微秒的范围。他认为“GC占用2%的时间”可能对结果有很大影响，并表示需要看到真实的工作负载才能相信这些数据。 补充讨论： • 争议的焦点在于分配器的性能指标是否可信，尤其是对于极端优化场景下的纳秒级分配速度，部分参与者表示怀疑。 • 不同分配器的算法实现方式被讨论，包括保守栈扫描、对象移动、bump'n'pop和SIMD turbosweep等方法的优劣。 • 硬件对性能的影响也被提及，不同测试环境下的结果可能会有显著差异。

本文讨论了2025年开发者如何通过源代码对程序进行沙盒化，限制其对系统资源的访问。沙盒化是指通过代码限制程序可用的系统资源，例如使用`chroot(2)`将根文件系统更改为空目录以防止程序修改系统文件。现代操作系统提供了更多限制资源的方法，包括Linux、OpenBSD和FreeBSD等。文章比较了这些系统中可用工具的文档长度和使用示例的复杂度，以评估实现沙盒的难易程度。理想情况下，沙盒应限制程序仅能访问已打开的文件描述符和内存，禁止其他资源访问。文章还以`openssh-portable`为例，分析了其维护历史和安全实施的难度。最后，文章呼吁开源社区贡献更多数据以完善调查。

CI/CD Observability with OpenTelemetry Step by Step Guide

作者: ankit01-oss | 评分: 110 | 评论数: 8 | 发布时间: 2025-06-11 12:42
文章摘要

本文介绍了如何使用OpenTelemetry（OTel）实现对CI/CD管道（特别是GitHub Actions）的可观察性。OpenTelemetry是一个开源的可观察性框架，能够以供应商无关的方式收集 traces、metrics 和 logs。通过配置 OTel，可以捕捉 CI/CD 管道的遥测数据，提供端到端的可见性、性能优化、错误检测与调试以及依赖分析等优势。 文中详细说明了如何使用 OTel 的 GitHub Receiver 来接收 GitHub 工作流事件并将其转化为 trace 数据，以及如何通过 API 抓取指标。具体步骤包括在 GitHub 配置 webhook、设置访问令牌以及安装和配置 OTel Collector。最终，通过 OTel 可以统一监控管道运行情况，提升调试效率。
