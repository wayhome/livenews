文章摘要

Models.dev 是一个开源的 AI 模型规格数据库，提供模型定价、能力等信息。项目通过 API 提供数据访问，支持查询模型规格和获取提供商 logo。数据以 TOML 文件存储在 GitHub 仓库中，按提供商和模型组织。 贡献方式： 1. 在 providers/ 目录创建提供商文件夹，添加 provider.toml 配置文件 2. 可选添加 logo.svg（使用 currentColor） 3. 在 models/ 目录创建模型定义文件，包含名称、功能支持、定价、token 限制、支持的模态等信息 4. 对于镜像提供商，可使用 extends 字段复用现有模型定义 项目鼓励社区贡献以保持数据更新。

评论摘要
主要讨论点：这个AI模型数据库/价格表是否真正有价值，以及它要想长期有用还缺哪些关键功能与数据。 不同观点： • 支持其基础价值：有人认为统一的模型列表/API很实用，已用于开源项目；也有人称表格性能很好，是“宝藏”。核心理由是集中整理价格和模型信息，方便查询比较。 • 质疑其独特性与可持续性：有人指出类似项目已“几十个”，担心又会成为被弃坑的“综合AI模型数据库”之一。争议焦点是：该项目能否持续更新，并与现有方案形成差异化。 • 强烈要求增强筛选/交互：多条评论集中批评缺少过滤功能，只能排序不够，建议按“current”、是否闭源/非LLM、工具调用、多模态等筛选；还有人指出横向滚动不直观。此处形成较强共识。 • 认为价格信息还不够：有人希望追踪价格变动、延迟基准；也有人进一步指出“token单价没意义”，因为模型可能中途“变笨”、被路由到更便宜的变体，实际成本更高。建议持续跑任务评测质量，但也有人隐含担心提供方会“特调”结果。 • 希望加入更贴近实战的比较：有人建议不仅列模型，还应加入“harness + models”组合，并举例称 Pi Dev + DeepSeek Pro 可完成与 Claude Code + Opus 4.7 类似工作，且经Claude复核代码可用。 • 个别讨论转向具体模型/平台：有人询问 AIHubMix 上免费模型是否有隐藏限制，以及相比 opencode-zen 之类工具的实际收益，属于围绕接入与使用场景的延伸讨论。 补充讨论：整体上，大家普遍认可“统一信息入口”方向，但认为要成功，关键在于长期维护、强筛选能力，以及补充质量/延迟/路由等动态数据。

Sp.h is the standard library that C deserves

作者: dboon | 评分: 88 | 评论数: 20 | 发布时间: 2026-05-20 13:05
文章摘要

这篇文章介绍了作者开发的C语言标准库sp.h。它是一个15,000行的单头文件库，核心理念包括：直接调用系统调用而非依赖libc；摒弃传统的堆内存管理，要求程序显式管理内存分配器；用指针+长度的字符串结构(sp_str_t)替代以null结尾的字符串，提升安全性和性能；代码高度可读可修改，仅约40个系统调用是平台相关的；用C99编写，具有极强的可移植性。作者认为传统libc已成为障碍，sp.h提供了更现代、高效且符合实际需求的底层接口。

评论摘要
主要讨论点：对一个强调“极致可移植、绕过libc、反空终止字符串、小而强”的C头文件库，其设计目标、实现一致性、可读性与工程实用性的争论。 不同观点： • **质疑目标自相矛盾**：有人指出“极致可移植”与“不支持冷门平台”冲突；若只面向x86_64、aarch64、WASM，就不能同时宣称“任何编译器/系统都可用”。也有人质疑“直接对syscall编程”只在Linux稳定，其他平台未必成立。 • **部分理念获认同**：多位评论者赞同“长度+指针优于\0结尾字符串”“适度重视性能优化”“标准库尽量贴近syscall”。同时补充 FILE 抽象在如 `fopencookie`、`open_memstream` 等场景仍有价值。 • **实现与表述被批评**：有人认为示例代码噪声大、可读性差，`wc` 示例命名易误导；“There Is No Heap”却又定义堆分配接口，被指表述不清。还有人质疑原子实现：Unix下包 `pthread mutex` 仍依赖标准库，且未说明内存模型/栅栏，甚至怀疑代码质量。 • **工程层面的担忧**：包括固定 `SP_PATH_MAX=4096` 对超长路径缺少回退；header-only 需引入 `windows.h` 等导致编译变慢；若程序部分仍需 libc、以及 `main` 前初始化如何处理，也被追问。 • **定位与背景讨论**：有人觉得这种强观点风格“很有趣”，或适合作为自定义语言的编译目标；也有人提到其思想与 DJB、Zig/WTF-8 等既有传统有关，并追问文中为何未提 Zig。 补充讨论：争议焦点主要在“宣称的底层纯粹性是否与实际实现一致”，以及“可移植性、简洁性与现实兼容性”三者如何平衡。

文章摘要

ShadowCat 是一个完全离线的单文件 HTML 工具，用于通过二维码在两台设备间传输数据。主要用于无线功能（蓝牙、NFC等）损坏但摄像头和浏览器仍可用的旧手机。 **核心功能：** - 生成/扫描单个二维码 - 发送文件：将文件分块编码为循环播放的二维码序列 - 接收文件：通过摄像头扫描，自动拼接分块并验证 CRC32 **协议：** 使用 `QRX1` 格式，头部包含文件元信息，数据块采用 Base64 编码并带索引。 **性能：** 500字符×3fps 约 0.83 KB/s，100KB 文件需约2分钟传输。需通过本地 HTTP(S) 服务访问以获取摄像头权限。

评论摘要
主要讨论点：通过QR码实现设备间文件传输的技术方案及其应用场景 不同观点： • **技术优化派**：divan强调使用喷泉码（fountain codes）提升效率，从Luby升级到RaptorQ编码；tripflag建议直接使用二进制数据替代base64以减少帧数；hootz提到音频调制的替代方案 • **实用应用派**：unprovable用于从损坏手机提取数据；MattCruikshank设想用于气隙通信设备，结合加密和一次性密码本实现极致安全；thedougd指出可用于数据渗透，难以被封锁 • **怀旧对比派**：encom怀念蓝牙传输时代的便利性，质疑为何该功能消失 • **技术局限关注**：hoansdz质疑相机性能是否足以处理大量数据；acrophiliac遇到长度限制问题（85700>18672） 补充讨论： 多位开发者分享了类似项目实现（anhldbk的get-beam、Levitating的gist链接），显示这是一个活跃的技术方向。lukew和alex_suzuki对单页面HTML部署方式表示认可。jaysyrk寻求合作机会。整体氛围积极，但对实际性能和数据量限制存在疑问。
