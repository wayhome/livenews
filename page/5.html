The Future of wasi-gfx and wasi:webgpu

作者: mendyberger | 评分: 27 | 评论数: 3 | 发布时间: 2026-06-09 18:42
文章摘要

这篇文章宣布了WebAssembly图形接口的重大调整： **核心变化：** - `wasi:webgpu`作为底层标准继续保留在WASI官方命名空间中，并将迁移到P3以支持原生异步 - `wasi:surface`和`wasi:frame-buffer`迁移至新的`wasi-gfx`命名空间，允许更快速迭代 - 废弃`wasi:graphics-context`，采用更简洁的设计方案 **原因：** WASI追求十年级别的架构稳定性，与UI接口快速演进的需求不匹配。借鉴wasmCloud等项目经验，将专业领域接口从操作系统标准库中分离到用户空间库。 **配套措施：** 发布新logo，Renderlet Discord成为官方社区，相关工具链将同时支持两个命名空间。

评论摘要
主要讨论点：跨平台开发的技术挑战和 WebAssembly 技术的演进 不同观点： • **窗口系统集成是跨平台开发的最大难点**（flohofwoe）：虽然核心 3D API（D3D、Metal、Vulkan、GL）映射到相同硬件较容易，但窗口系统粘合层才是真正复杂和维护成本高的部分。不同平台在表面呈现、帧同步、事件驱动与帧驱动应用的冲突等方面缺乏统一标准，尤其 macOS 系统更新和 Wayland 带来额外问题。结果是 10% 的窗口系统代码占用了 90% 的工作量。 • **WebAssembly 的演进令人振奋**（pseudosavant）：从 asm.js 这个 JavaScript 的严格子集开始，虽然文本编码效率不高，但证明了概念可行性，使 WASM/WASI 成为自然的下一步。类比 JSON 的成功模式，认为这是技术演进的正面案例。 • **对 WebAssembly 前景持怀疑态度**（shevy-java）：用讽刺的语气表达悲观看法，将 WebAssembly 的真正突破比作"Linux 桌面年"和"GNU Hurd 安装到每个烤面包机"——这些都是技术圈长期未实现的梗，暗示 WebAssembly 的广泛应用可能遥遥无期。 补充讨论：三条评论分别关注不同技术领域，没有直接讨论关系，更像是独立的技术观察和评论。

Google proposes Open Knowledge Format based on Markdown

作者: itherseed | 评分: 13 | 评论数: 3 | 发布时间: 2026-06-13 14:33
文章摘要

Google Cloud 推出开放知识格式（OKF v0.1），这是一个供 AI 系统使用的开放标准。OKF 将知识表示为带 YAML 前置元数据的 Markdown 文件目录，解决了企业内部知识碎片化问题。当前组织的知识分散在元数据目录、Wiki、代码注释等不兼容系统中，导致 AI 代理难以获取上下文。OKF 采用"知识即 Wiki"模式，让知识以可读、可版本控制的文件形式存在，无需复杂 SDK 或特定服务，可在不同工具和组织间互操作，使 AI 代理能持续维护和更新共享知识库。

评论摘要
主要讨论点：如何在保持人类可读性的同时，让AI高效理解和处理知识表示格式 不同观点： • **sadschnitzel的立场**：认可OKF规范的简洁性，但质疑"纯Markdown"能否充分表达所有概念。强调知识表示必须兼顾AI效率和人类体验，不能为了AI可访问性而牺牲人类使用体验，特别是非技术人员更难接受"奇怪的文本格式+git"。提出成功案例包括DBML、LikeC4、Mermaid等半结构化文本格式，这些既有良好的可视化形式，又能嵌入Markdown，LLM也能很好理解。指出难点在于隐含空间布局和颜色语义的复杂工具（如电子表格、Miro）。分享了自己在数据工程领域的尝试Satsuma-lang，实现简洁的结构化文本表示，同时提供可视化和LSP工具支持。 • **mrkiouak的立场**：以讽刺口吻提及RDF/OWL语义网格式每10年被重新审视一次，暗示这类尝试反复出现但始终未能成为主流，对当前讨论持怀疑态度。 补充讨论：verdverm提供了原帖中损坏链接的修正，指向GoogleCloudPlatform的knowledge-catalog仓库和规范文档，属于技术性补充。

A key remapping daemon for Linux

文章摘要

keyd是一个Linux系统级键位重映射工具，通过内核层输入原语（evdev、uinput）实现全局按键重映射。主要特性包括：支持层（layers）和混合修饰键、按键过载（tap/hold不同行为）、键盘特定配置、即时重映射、系统级配置（可在虚拟终端使用）、Unicode支持等。采用C语言编写，响应速度快（<1ms），配置简单直观。可通过systemd安装启动，配置文件位于/etc/keyd/，支持应用程序特定的按键映射。适合需要自定义键盘布局、多键盘配置或系统级按键重映射的用户。

评论摘要
主要讨论点：keyd 键盘重映射工具的使用体验和与其他工具的比较 不同观点： • **积极支持者**：多位用户表示 keyd 运行良好，快速、易用且开箱即用。特别赞赏其"lettermod"功能，能智能识别打字状态避免误触发 homerow mods • **替代方案使用者**：部分用户转向其他工具如 Kmonad、xremap、Kanata 或 input-remapper，各有特定使用场景（如 Emacs 用户偏好 xremap 的配置方式） • **Wayland 批评**：有用户指出 Wayland 下键盘重映射和窗口选择比 X11 更困难，需要 root 权限，配置复杂度增加 • **性能质疑**：有开发者认为"<1ms"延迟目标过于宽松，应追求 1µs 级别的性能 补充讨论： 用户分享了多种应用场景（笔记本、外接键盘、鼠标键重映射、Caps Lock 改 Ctrl 等）。有开发者提到自己也开发了同名但设计理念完全不同的 keyd（采用 djb 风格的目录+可执行文件架构而非配置文件）。社区关注与 QMK、interception-tools 等工具的对比。

Introduction to UEFI HTTP(s) Boot with QEMU/OVMF

作者: jtlebigot | 评分: 65 | 评论数: 5 | 发布时间: 2026-06-12 14:50
文章摘要

这篇文章介绍了如何使用UEFI通过HTTP(S)进行网络启动，以替代传统的PXE/TFTP方案。作者在Ubuntu 26.04上使用Qemu/OVMF进行测试，演示了从netboot.xyz网站直接启动的过程。 文章首先实现了基于DHCP发现的HTTP启动，遇到并解决了关键问题：OVMF的网络栈需要随机数生成器设备（virtio-rng-pci）才能工作，这是因为网络栈的各层（从以太网到TLS）都依赖随机性。作者通过添加`-device virtio-rng-pci`参数成功解决了启动失败问题。 文章强调HTTPS启动相比传统PXE更安全，支持TLS加密和服务器认证，适合通过互联网启动且能防止中间人攻击。

评论摘要
主要讨论点：UEFI HTTP Boot技术的实用性、调试难度和安全特性 不同观点： • **技术成熟度**：naturalmovement指出Apple已使用HTTP boot技术近二十年（Internet Recovery基于旧的Apple netbooting规范），表明这并非新技术 • **调试困难**：andrewjf强烈批评UEFI HTTP boot的调试体验极差，错误信息几乎无用（如"can't get NBP file size"），DHCP配置问题难以排查，IPv6支持更加晦涩，认为开发者缺乏对网络复杂性的理解 • **HTTP优势**：nijave认为HTTP相比TFTP是重大改进，因为支持HTTP server的设备范围更广，但对TLS加密的必要性存疑——secure boot已提供完整性验证，而机密性对内核启动意义不大 • **硬件兼容性疑问**：noodlesUK关心该技术在真实物理硬件上的可行性，希望HTTP能简化现有PXE/TFTP系统 补充讨论：jeffrallen的评论表明这是对同事优秀工作的认可，暗示讨论源于某篇技术文章。整体而言，社区对HTTP boot持谨慎乐观态度，认可其潜力但担忧实际部署的复杂性。
