Memories: Edinburgh ML to Standard ML

作者: fanf2 | 评分: 4 | 评论数: 0 | 发布时间: 2025-05-12 20:42
文章摘要

这篇文章简要回顾了Standard ML的发展历史及其与Caml的分裂。作者Dave MacQueen等人编写了《Standard ML历史》一文。作者回顾了ML语言的早期发展，尤其是Edinburgh ML在定理证明方面的创新，但因ML代码通过Lisp解释导致执行缓慢。通过λ-lifting和优化currying等技术改进，ML性能显著提升。随着ML under UNIX的出现，ML语言面临分裂风险，Robin Milner因此推动标准化工作。在标准化的过程中，不同团队对ML的特性存在分歧，特别是关于非线性模式和局部声明语法等问题。最终，Standard ML的模块化方案成为争议点，尽管起初被认为复杂，但如今OCaml的模块与Standard ML相似。文章还提到ML的语法受ISWIM影响，具有一定随意性。

文章摘要

Making PyPI's test suite faster

作者: rbanffy | 评分: 113 | 评论数: 8 | 发布时间: 2025-05-08 20:54
文章摘要

Trail of Bits与PyPI合作多年，致力于提升Python打包生态系统的功能和安全性。本文聚焦于测试套件性能的优化，这对于软件安全至关重要。随着测试覆盖率增加，执行时间变长，影响了开发效率。通过一系列优化，Warehouse（PyPI后端）的测试执行时间从163秒减少到30秒，而测试数量从3,900增加到4,700以上，实现了81%的性能提升。 关键优化步骤包括： 1. 使用`pytest-xdist`并行执行测试，减少67%的时间。 2. 利用Python 3.12的`sys.monitoring`实现更高效的覆盖率检测，减少53%的时间。 3. 通过优化测试发现和配置，减少不必要的导入，降低启动开销。 这些优化对拥有不断增长的测试套件的Python项目尤为适用，显著改善了测试性能，而无需额外成本。当前，Warehouse测试套件在32核机器上的执行时间约为30秒，较之前的161秒有了显著提升。 优化过程中解决了数据库夹具和覆盖率报告等挑战，确保了并行测试的有效性和准确性。这些改进显著提升了PyPI贡献者的测试体验。

评论摘要
主要讨论点：针对使用 `pytest` 及其相关工具（如 `pytest-xdist`）进行测试优化的不同观点和建议，包括对测试速度、数据库处理、mocking 技术以及对 Python 测试框架的更广泛讨论。 不同观点： • [boyd] 认为使用 `pytest-xdist` 进行并行化测试是低成本高效益的优化方式，但 CI 管道中的额外开销（如 Github Actions 的 43 秒开销）使得进一步优化变得困难。他提到正在开发一个项目，旨在自动进行这些优化，并减少“第一次测试失败时间”到约 10 秒。 • [nine_k] 建议将测试数据库放在 RAM 磁盘（tmpfs）上，以加速所有与数据库相关的测试操作，如事务、fixture 加载和迁移。他认为这是未被提到的一个有效方法。 • [qznc] 主张避免完全使用 mocking，但承认在加速测试时，mocking 是合适的。他举例说明在他们的测试中 mocking `time.sleep` 和文件系统访问显著提高了速度，并强调单元测试应关注应用逻辑而非操作系统行为。 • [cocoflunchy] 对 `pytest` 的测试收集速度感到困惑，他们的 Django 应用测试套件需要约 15 秒收集测试。他们通过 ripgrep 工具创建了一个实用程序来加速这个过程。 • [NeutralForest] 认为隔离数据库操作是一个挑战，使用不同实例或模式可以有效隔离角色和操作，但实践中存在困难。 • [throwme_123] 提问 Trail of Bits 是否正在脱离“加密”领域，并提到他们是优秀的智能合约审计者，可能寻找更大的市场。 • [ustad] 询问使用 Python 内置的 `unittest` 是否有类似的优化建议。 • [bgwalter] 对 `pytest` 的“魔法”特性表示担忧，认为高安全性应用的测试套件应简单直接。他批评 Python 和 PSF 开发过程的复杂性和非正式性，并引用了一个泄露的 GitHub 链接来支持其观点。 补充讨论： • 争议焦点之一是 `pytest` 的复杂性和速度问题。一些评论者（如 [bgwalter]）认为其“魔法”特性导致速度慢且不适合高安全性应用，而其他评论者（如 [boyd] 和 [qznc]）则关注如何在现有框架内进行优化。 • 另一个值得注意的讨论点是对具体优化技术的建议，如使用 RAM 磁盘加速数据库测试（[nine_k]）、mocking 技术（[qznc]）以及实用程序加速测试收集（[cocoflunchy]）。 • 对 `unittest` 的使用建议也是一个讨论点，显示出社区中对不同测试框架的偏好和需求。

Scraperr – A Self Hosted Webscraper

作者: jpyles | 评分: 231 | 评论数: 16 | 发布时间: 2025-05-11 18:29
文章摘要

Scraperr 是一个自托管的网页抓取工具，允许用户通过 XPath 选择器精确提取网页数据。它提供了一个简洁的界面来管理抓取任务、查看结果和导出数据。关键功能包括队列管理、域名爬取、自定义请求头、媒体下载、结果可视化和多种数据导出格式。使用时需遵守 robots.txt 文件、网站服务条款，并设置合理的请求频率以避免服务器过载。该项目基于 MIT 许可，支持用户自定义开发和贡献。

评论摘要
主要讨论点：网页抓取工具的伦理使用、技术实现及相关争议 不同观点： • **支持伦理抓取**：[mellosouls] 和 [lucb1e] 强调了在使用抓取工具时应遵守 robots.txt 和服务条款，并提倡伦理抓取，如在用户代理字符串中包含联系方式或唯一标识符，以避免不必要的IP封锁。此外，[lucb1e] 还提到不应在请求页面后超时离开，以及应尊重 robots.txt 文件。 • **工具推荐与技术实现**： - [andrethegiant] 推广了自己的工具 https://pure.md/，具有避免机器人检测、代理轮换和无头JS渲染功能。 - [smartmic] 推荐了自托管的抓取工具 xidel，它能够跟踪链接。 - [renegat0x0] 介绍了一个网络爬虫软件 crawler-buddy，支持多种爬取方法并返回 JSON 数据。 - [3abiton] 讨论了使用 XPath 选择器的优缺点，认为需要结合其他选择器以提高可靠性。 • **技术挑战与解决方案**： - [nomilk] 提到现代网站普遍使用 Cloudflare 验证，询问如何绕过这些验证。 - [TheTaytay] 寻找一种利用LLM生成确定性抓取脚本的工具，以避免每次都使用LLM。 - [vivzkestrel] 关注抓取工具是否实现了旋转代理IP功能。 - [_QrE] 比较了 Selenium 和 Playwright，认为 Playwright 更易用且灵活，同时提到通过浏览器调整指纹的方法。 补充讨论： • **实际应用场景**：[monkeydust] 分享了使用抓取工具下载规划文件的实际案例，并结合LLM进行文档验证，显示了抓取工具在实际应用中的价值。 • **对网络开放性的担忧**：[jsemrau] 表达了对依赖抓取工具获取内容的担忧，认为应建设更有价值的可编程网络。[gitroom] 则讨论了抓取工具与网站之间的猫鼠游戏，质疑网络是否会变得更加开放。 争议焦点： • **伦理与技术边界**：如何在抓取网站内容时保持伦理，避免对网站造成负担，同时有效获取所需信息。 • **技术选择与实现**：不同工具和技术的优劣比较，如 Selenium 与 Playwright 的选择，以及如何有效绕过网站的反爬措施。
