When Is WebAssembly Going to Get DOM Support?

作者: jazzypants | 评分: 100 | 评论数: 20 | 发布时间: 2025-07-23 05:16
文章摘要

文章讨论了WebAssembly (Wasm) 是否能直接支持DOM操作，并指出Wasm可能永远不会直接访问DOM，但通过JavaScript间接调用DOM API已经足够成熟，适用于各种Web应用。Wasm与JavaScript严格分离，但通过“粘合代码”可以实现与JavaScript API的无缝集成。文章通过示例展示了如何利用JavaScript作为中介，让Wasm调用如`console.log`这样的Web API。Wasm模块通过导入和导出功能与JavaScript交互，且使用数组和整数索引来处理JavaScript对象引用。尽管未来可能引入直接调用Web API的机制，但目前的方案已能有效减少代码量并提升性能。Wasm与JavaScript的集成仍在不断发展中。

评论摘要
主要讨论点：WebAssembly（WASM）的应用、与DOM交互的挑战以及未来发展方向 不同观点： • **支持WASM与DOM交互的复杂性**：[sfvisser] 指出，在Rust和TypeScript之间通过WASM进行交互的层非常痛苦，需要大量缓慢且不安全的胶水代码。虽然WASM允许后端和前端共享逻辑，但频繁跨越边界交互并不理想。 • **WASM的潜力未被充分实现**：[apatheticonion] 认为WASM本应 revolutionize 网页开发，但多年来其应用仍限于单一线程的 niche 用例，未能充分发挥潜力。 • **性能问题和浏览器差异**：[evrimoztamur] 提到在iOS的WebKit/Safari上运行WASM图形应用时性能损失严重，而在其他浏览器上表现良好，强调了跨浏览器性能问题。 • **对WASM进展的失望与期望**：[jauntywundrkind] 表示对WASM进展缓慢感到失望，期待更多更新和明确的未来规划。虽然有进展但仍不清楚如何有效整合WASM。 • **对开源能力的担忧**：[CaptainFever] 担心WASM的广泛使用会导致网页的源代码不再默认可见，影响透明性。 • **替代方案的建议**：[gchamonlive] 提出可以通过类似Phoenix LiveView的消息传递机制来减少DOM操作的复杂性。 • **DOM访问的编码问题**：[theSherwood] 不希望WASM依赖UTF-16编码进行DOM访问，建议引入8位编码的DOMString8接口。 • **对WASM理解的困惑**：[MisterTea] 对WASM是否应理解DOM提出疑问，认为WASM不应直接与DOM交互，除非有人编写相关代码。 • **现代WASM的进展和组件模型**：[hardwaresofton] 提到Bytecode Alliance正在推进现代WASM的DOM交互支持，尽管实验性的浏览器shim仍未完善，但已有一些支持可用。 • **对DOM支持的反对意见**：[lucideer] 认为WASM增加DOM支持会带来复杂性和安全问题，不认为其必要性足够显著。 • **对简化胶水代码的需求**：[jagged-chisel] 强调需要简化与JS API互操作的胶水代码，建议允许列出WASM将调用的JS函数以减少手工编写。 • **DOM wrapper的需求**：[edg5000] 询问是否有人为C++/Rust编写了匹配JavaScript API的DOM wrapper，以便在C++/Rust应用中操作DOM。 • **在WASM中实现DOM的建议**：[amelius] 提出可以在WASM中实现DOM，以彻底解决DOM兼容性问题。 补充讨论： • 争议焦点在于是否应让WASM直接支持DOM操作以及如何简化WASM与JS的交互。 • 讨论中多次提到性能问题，特别是跨浏览器的一致性。 • 对现代WASM和组件模型的更新进展有一些积极的期望和建议。 • 部分评论者对WASM的未来感到困惑和失望，期待更明确的路线图和简化开发的方案。

Reverse engineering GitHub Actions cache to make it fast

作者: tsaifu | 评分: 136 | 评论数: 12 | 发布时间: 2025-07-23 13:17
文章摘要

本文介绍了Blacksmith如何通过逆向工程GitHub Actions缓存机制，实现无代码更改的缓存加速。最初，他们通过 fork 流行的 GitHub Actions 并指向自己的快速缓存来提升性能，但这带来了维护负担。为解决此问题，他们决定逆向工程 GitHub Actions 缓存，利用网络代理技术，将缓存请求透明地重定向到自建的 MinIO 集群，而无需用户修改代码。通过使用 NGINX 作为代理服务器，他们在 VM 内配置轻量级代理，将缓存相关的请求重定向到自建缓存，其他请求则正常处理。最终，实现了最高10倍的缓存性能提升，同时保持了用户体验的无缝衔接。

文章摘要

这篇文章讲述了一个日志管理网站如何从一个简单的报告页面演变成一个允许用户直接编写SQL查询的系统。最初，页面只允许用户输入日期范围和关键词来生成报告。随着时间推移，由于不断有增加字段、生成新报告类型的需求，开发人员逐渐通过硬编码SQL和添加功能来满足这些要求。由于报告类型不断增多，用户开始抱怨名称混乱，开发人员转而使用数据库驱动报告名称，并允许编辑报告名。随着需求进一步复杂化，有人提出让用户自行编写SQL查询，最终这个功能被秘密添加到一个未公开的页面中，成为“SQL注入即服务”。尽管后来添加了一些简单的安全措施和查询限制，系统实际上已将整个数据库暴露给用户。这个演变过程展示了在长达十年的需求累积和小修小补下，一个系统如何逐渐变得脆弱和不安全。
