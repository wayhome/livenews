Computed goto for efficient dispatch tables (2012)

作者: firephox | 评分: 26 | 评论数: 6 | 发布时间: 2026-06-17 13:51
文章摘要

这篇文章比较了在字节码虚拟机中使用GCC的computed goto扩展与传统switch语句的性能差异。作者定义了一个简单的VM，用整数作为状态，通过几个指令操作它。测试显示computed goto版本比switch版本快25%，CPython使用该技术后VM速度提升15-20%。性能优势来自两方面：computed goto减少了每次迭代的边界检查开销，且更利于CPU分支预测。文章通过汇编代码分析解释了底层原因，computed goto本质上暴露了现代CPU的间接跳转指令，使编译器能生成更高效的代码。

评论摘要
主要讨论点：switch语句与computed goto在虚拟机解释器实现中的性能差异，以及边界检查的安全性权衡 不同观点： • **优化派（variadix）**：可以通过在default分支使用`__builtin_unreachable()`消除switch的边界检查，认为switch版本对非法操作码更安全，而computed goto会触发未定义行为 • **困惑派（jdw64）**：理解基础比较操作，但对分支预测优化感到困惑，对自己的编程能力产生怀疑 • **实用派（nly）**：指出前提条件——这些优化只在操作码是连续/密集分布时才有效 • **类型系统派（kibwen）**：认为性能损失的根本原因是switch操作的是原始整数类型，如果使用真正的枚举类型（而非C语言的"数字别名式枚举"），编译器可以在编译期保证值域，从而消除运行时检查 补充讨论：核心争议在于安全性与性能的权衡——编译器强制的边界检查保证了安全但损失性能，而更强的类型系统可能是解决这一矛盾的方案。froh标注文章年份(2012)暗示这是历史讨论。

Cargo-Geiger

作者: tosh | 评分: 26 | 评论数: 3 | 发布时间: 2026-06-20 14:52
文章摘要

cargo-geiger 是一个 Rust 生态工具，用于检测和统计 Rust 项目及其依赖中 unsafe 代码的使用情况。它以 Geiger 计数器命名，将 unsafe 代码类比为需要安全控制的辐射。该工具不直接判断代码安全性，而是为代码审计提供统计数据支持。安装可通过 `cargo install cargo-geiger`，使用时在项目目录运行 `cargo geiger` 即可。项目提供三个库：cargo-geiger（内部实现）、cargo-geiger-serde（序列化报告类型）和 geiger（解耦的 cargo 组件）。目前在 GitHub 上有 1.6k star。

评论摘要
主要讨论点：关于Rust程序中unsafe代码的评估标准和实际意义 不同观点： • nu11ptr认为：所有有用的Rust程序都包含unsafe（标准库、I/O、FFI必然使用），问题不是"是否有unsafe"，而是"信任谁使用unsafe、在什么情况下使用"。限制自己和依赖crate的unsafe使用有价值，但需要理性看待。 • smasher164强调：unsafe块的数量不重要，重要的是这些unsafe代码是否会导致未定义行为。一个有缺陷的unsafe抽象会让所有使用它的代码都出问题。实际场景中unsafe主要用于内联汇编或FFI调用，语言本身几乎无法提供保证。 • Waterluvian担心：过度强调"unsafe是坏的"文化可能让合理的Rust代码背上坏名声。建议用测试覆盖率来衡量unsafe块，而不是简单统计unsafe数量。 补充讨论：三位评论者都认同简单的unsafe数量统计意义有限，核心分歧在于评估标准——信任度、正确性还是测试覆盖。讨论揭示了社区对unsafe代码评价体系的思考。

Where to Find the Colors Your Screen Can't Show You

作者: moultano | 评分: 147 | 评论数: 20 | 发布时间: 2026-06-20 03:36
文章摘要

这篇文章讲述了数字屏幕无法显示真实世界中的许多青色(cyan)。人眼通过三种视锥细胞感知颜色,它们只能以不同强度响应光波,大脑据此重建色彩。1931年CIE创建了色度图,标定了人类可见的所有颜色范围。但由于技术限制,屏幕使用的三原色(红绿蓝)混合后只能覆盖有限的色域,大量青绿色调无法呈现。早期CRT显示器使用的荧光粉进一步限制了色域范围。尽管现代技术(LED、激光)能做得更好,但我们仍然沿用了这个受限的标准,导致数字世界缺失了大量真实世界中存在的鲜艳青色。

评论摘要
主要讨论点：显示器色域的局限性与现实世界色彩的丰富性 不同观点： • **色域缺陷的重点区域**：adrian_b指出sRGB最大缺陷在橙/红/紫色域（日常花卉、水果、衣物），而非CIE图中看似更大的蓝绿区域。人眼在橙红紫区域能分辨更多色彩，建议使用Display P3或Rec. 2020色域 • **亲身体验派**：多位评论者通过实际经历验证色彩局限——TheAceOfHearts的丙烯画作（群青、普鲁士蓝）、lefra的430nm蓝色激光"尖叫般的蓝"、circadian在南极冰缝中见到的惊艳色彩，照片和屏幕都无法还原 • **技术细节补充**：orthoxerox提到ACES AP0理论色彩空间可表示所有可见色；Sharlin指出Adobe RGB在蓝青绿区域比P3更广；Stitch4223怀念80年代B&O电视的青色强度 补充讨论： • sam_lowry_和印象派画作的合成群青在现实中"从内部发光" • rollulus提出通过单独刺激视锥细胞看到"新颜色"的可能性 • frotaur质疑色彩空间为何是二维而非三维 • 文章写作质量获广泛赞赏，激发读者走出户外观察真实色彩

1969年英国ITV电视台转播彩色节目时，摄像师工会因薪资谈判未果发起罢工，他们关闭了彩色摄像机中的红绿蓝三个摄像管，只保留黑白摄像管，使节目变回黑白播出。罢工持续三个月才解决。 此期间拍摄的《楼上楼下》剧集前6集是黑白的，后续是彩色的。为向美国出售该剧，制作方用彩色重拍了第一集，并修改剧情让女仆Sarah在第一集就离开（原版她在第三集离开），以跳过黑白集数。这导致该剧第一集存在三个版本，原黑白版已遗失，形成了复杂的版本混乱问题。

评论摘要
主要讨论点：早期电视技术的制作与本地化挑战 不同观点： • [gord288] 提到《双峰》试播集的特殊版本——为防止剧集未获续订而制作的完整故事版本，警告观众不要先看这个版本以免剧透 • [malkia] 分享文化本地化的挑战案例——美剧中"猪肉作为惩罚"的情节在保加利亚失效，因为当地猪肉比牛肉更受欢迎，说明本地化需要深入理解文化差异 • [SoftTalker] 质疑那个年代的节目制作方式，认为应该是先用胶片拍摄再转换为视频播出 • [somat] 探讨美英彩色电视技术差异——NTSC为向后兼容黑白标准而妥协导致问题，英国系统则更先进；提出疑问：这是否影响了摄像机技术选择(4管vs3管) 补充讨论： [PunchyHamster] 提出技术进步可能导致的劳工问题——当新技术简化工作流程后，工人可能面临降薪。 整体讨论涵盖电视制作技术演进、文化本地化挑战、以及技术标准的历史权衡。
