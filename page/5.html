The Software Engineering Identity Crisis

作者: napolux | 评分: 88 | 评论数: 21 | 发布时间: 2025-03-23 18:37
文章摘要

文章讨论了软件工程师在人工智能（AI）时代面临的身份危机。传统上，软件工程师以亲手编写代码、解决技术问题为核心身份，但随着AI编码助手的出现，工程师的角色正从“建造者”转变为“协调者”或“管理者”。AI不仅改变了编码方式，还可能剥夺工程师在解决问题和优化算法过程中获得的成就感。 尽管有人乐观认为工程师将更多关注高层次架构和系统思维，但这种转变引发了对工程师核心身份的质疑。现实中，如Google和Y Combinator的案例显示，越来越多的代码由AI生成，传统编码技能或将被“提示工程”（prompt engineering）取代，工程师需要提升沟通能力以更好地指导AI。 像Andrej Karpathy提出的“氛围编码”（vibe coding）概念，反映了从关注代码细节到依赖AI生成内容的转变，这让人质疑：如果忘记代码，我们还是工程师吗？Gene Kim和Steve Yegge展示了如何利用AI在短时间内重构代码，进一步表明这一身份转变已是现实。

评论摘要
主要讨论点：AI在编程领域的应用及其影响 不同观点： • [dandellion] 认为AI在代码自动完成方面有帮助，但在处理复杂任务时表现不佳。他对AI取代人类编程持怀疑态度，并将当前的AI发展与自动驾驶汽车的承诺相比较，暗示这些技术可能难以实现其承诺。 • [hnthrow90348765] 预测工作要求将增加，程序员需要在多个领域之间跳跃。同时提到，AI不会取代非技术人员学习编码，并讨论了AI编码对产品质量的影响。 • [meander_water] 强调软件工程不仅仅是代码生成，还包括系统设计和架构设计等任务。人类在调试、重构和优化方面仍然具有优势，因为人类能够理解整个问题空间和背景。 • [greenie_beans] 认为AI夺走了编程的乐趣，但现在已经离不开它。他建议不要将工作与个人身份联系在一起。 • [aforwardslash] 指出AI代码生成工具需要监督，且可能导致初级开发者职位减少。他还预测未来会出现专门的AI编程语言，减少人类参与。 • [userbinator] 认为依赖AI生成代码的人是低于平均水平的，编程需要像学习语言一样掌握。他强调性能和可靠性的重要性，并担心AI会加速行业的下滑。 • [TeMPOraL] 同意一些观点，但认为文章忽略了软件工程师身份的问题。他个人对商业影响不感兴趣，只想构建东西，而不是销售或管理。 • [18172828286177] 感受到学习技术知识的无力感，因为ChatGPT可以做得更好，这削弱了他对技术的热爱。 • [roxolotl] 认为将工作视为创造欲望的出口是不明智的。工业化工作本质上是功利性的，AI不会减少个人项目中的创造乐趣。 • [kittikitti] 表示即使AI取代编码工作，他仍然会继续编码。他质疑过度炒作的AI取代程序员的情景。 • [cadamsdotcom] 认为AI减少打字和查API的时间是积极的，但人类仍需监督和理解代码。未来非工程师将能自己制作软件，而软件工程师可以帮助他们。 • [kylehotchkiss] 观察到最近开源JS库/框架的发布减少，可能与信息泡沫或个人兴趣变化有关。 • [MiiMe19] 坚决反对使用AI编码。 • [bsder] 希望AI能减轻编程中的繁琐工作，如现代化旧代码库，并对AI的实际能力持怀疑态度。 补充讨论： • AI在编程中的角色和限制：许多人认为AI在处理复杂任务和系统设计方面表现不足。 • 对AI取代人类工作的担忧：一些评论者担心AI会减少初级开发者职位，并对产品质量产生负面影响。 • 个人对编程的热爱和身份认同：部分评论者强调编程的乐趣和个人身份与工作的关系。 • 对未来软件开发的预测：一些评论者认为未来非工程师将能自行制作软件，而软件工程师的角色将转变为协助者。 • 对AI影响的不同态度：从坚决反对到积极拥抱，评论者对AI在编程中的应用持不同态度。

文章摘要

《奇迹细菌小史》一文介绍了**粘质沙雷氏菌**（*Serratia marcescens*）的科学历史及其对现代科学的影响。这种细菌因其酷似血液的红色外观，常用于研究细菌传播。1904年，英国医生M. H. Gordon在英国议会大厦前进行实验，试图通过议员靴子传播细菌以研究通风系统缺陷，但未成功。随后，他通过在议会厅内漱口并朗诵莎士比亚作品，证明了细菌可通过 speech 传播。 粘质沙雷氏菌最早在1819年因其在玉米粥上形成红色斑点而引起关注，当时被误认为是真菌。尽管其某些菌株对人类有害，但该细菌仍被广泛用于研究微生物传播。文章还提到，随着对其危险性的认识增加，这种细菌逐渐不再用于实验，但仍是生物医学研究的重要对象。

评论摘要
主要讨论点：围绕1969年一篇关于细菌的文章展开的讨论，涉及科学与历史、哲学的关联，以及科学实验的演变。 不同观点： • [dr_dshiv] 分享了一篇1969年的文章，重点介绍了细菌研究与历史哲学的关联，尤其是将血液效应追溯到毕达哥拉斯学派。他强调了文章中引用的公元170年Lucian的讽刺作品《出售信条》，展示了毕达哥拉斯学派对豆类的禁忌，并通过幽默的方式解释了其哲学背景。 • [profsummergig] 认为这种传统的科学探究方式在当代不太可能被接受，反映出对现代科学实验规范的担忧，并暗示过去某些独特的科学探究方式可能已经消失。 • [melagonster] 对文章内容感到兴奋，并表示有兴趣进一步探索相关生物学分类信息，显示出对历史文献和科学探索的个人兴趣。 补充讨论： - 讨论中涉及到毕达哥拉斯学派的禁忌与科学实验的联系，尤其是通过豆类与血液的实验来说明古代哲学与科学的交集。 - 争议焦点可能在于科学实验的伦理演变，[profsummergig] 隐含地指出过去一些实验方法在今天可能不被接受，暗示现代科学规范的限制与过去相比的变化。 - 对历史文献的兴趣和进一步探索的意愿也是一个值得注意的讨论点，[melagonster] 的回应显示出对历史和科学结合的积极态度。

Learning about Bootc

作者: nikodunk | 评分: 56 | 评论数: 13 | 发布时间: 2025-03-24 00:18
文章摘要

Next.js version 15.2.3 has been released to address a security vulnerability

作者: makepanic | 评分: 216 | 评论数: 34 | 发布时间: 2025-03-22 21:19
文章摘要

Next.js发布了15.2.3版本，修复了一个安全漏洞（CVE-2025-29927）。该漏洞允许跳过Middleware，导致关键安全检查（如授权cookie验证）被 bypass。自托管的Next.js应用，尤其是使用`next start`和`output: 'standalone'`的，应立即更新。漏洞不影响托管于Vercel或Netlify的应用，以及静态导出的应用。修复版本包括：15.x的15.2.3、14.x的14.2.25、13.x的13.5.9和12.x的12.3.5。若无法更新，建议阻止含有`x-middleware-subrequest`头的请求。Next.js团队还将改进与合作伙伴的沟通，并开设了合作伙伴邮件列表。

评论摘要
主要讨论点：Next.js 中间件系统的设计缺陷与安全问题 不同观点： • **[dminik]** 认为 Next.js 的整个中间件系统设计糟糕，存在多个问题。首先，无法官方便捷地链式调用多个中间件，必须将所有功能塞进单个函数或自行实现链式逻辑。此外，主要功能如 `next()`、`redirect()`、`rewrite()` 等作为静态成员存在于导入对象上，导致第三方中间件可能会自动执行错误操作并破坏链式功能。再者，中间件与路由处理器之间的通信机制不完善，通过 headers 传递数据既不安全也可能导致缓存失效。最后，部分请求属性被隐藏或混淆，如 `request.hostname` 始终为 `localhost`，需要从 "Host" header 中手动获取实际主机名。 • **[ratorx]** 指出，Next.js 中间件使用与用户请求相同的机制进行通信，这使得代码编写和请求验证分离，容易导致安全隐患。此外，允许用户发送除白名单外的任意 headers 也可能造成潜在问题。框架的设计似乎鼓励了不良的服务器设计模式，特别是允许跨越认证边界的递归请求可能导致安全隐患。 • **[smlx]** 提到 Next.js 历史上存在类似漏洞，并引用了一个具体的补丁（https://github.com/vercel/next.js/pull/73482/files），其中通过添加特定 header 可以触发 SSRF 漏洞。同时，批评 Next.js 团队对漏洞信息的披露不透明，且仅对部分版本提供补丁支持。 • **[mikeocool]** 认为 Next.js 增加了前端开发的复杂性，但对于大多数应用而言提供的价值有限。文件路由和服务器端渲染在某些场景下可能有用，但整体上带来的复杂性不值得。 • **[ashishb]** 认为 Next.js 的基础前提存在根本性缺陷，即浏览器和后端代码运行环境不同，安全策略应有所区分。前端代码是不可信的，后端代码是可信的，因此应分离关注点，分别编写前端和后端代码。 • **[impulser_]** 推荐使用 Tanstack Start 作为 Next.js 的替代方案，认为其在开发体验和配置简便性上更具优势，且支持全栈应用开发和多平台构建。 补充讨论： • **安全问题**：多位评论者（如 [ronbenton], [makepanic]）关注到具体的安全漏洞，尤其是通过添加 `x-middleware-subrequest: true` header 可以绕过认证，这被认为是极其严重的安全漏洞。 • **维护与披露**：[ronbenton], [smlx] 对 Next.js 团队在漏洞披露和修复时间上的表现不满，认为关键安全漏洞的响应时间过长（16天才开始处理）。 • **框架选择**：[dvektor], [butterlettuce], [ramoz] 等人对 Next.js 的设计和维护表示失望，并考虑或推荐其他替代方案。 争议焦点： • Next.js 中间件系统的设计复杂性与安全隐患之间的矛盾。 • Vercel 团队在漏洞披露和修复过程中的响应速度与透明度问题。
