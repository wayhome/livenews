Bun Rust rewrite: "codebase fails basic miri checks, allows for UB in safe rust"

文章摘要

该 GitHub issue 指出 oven-sh/bun 的 Rust 代码库存在严重内存安全问题：最基本的 Miri 检查失败，并可能在安全 Rust 中触发未定义行为（UB）。示例中 `PathString::slice` 通过 `from_raw_parts` 构造了悬垂引用；原始 `Box` 被释放后仍访问其数据。提交者批评项目用 AI 编写 Rust，建议聘请真正的 Rust 开发者修复问题。

评论摘要
主要讨论点：Bun 用 LLM 将 Zig 重写为 Rust 的可信度、必要性与工程质量，以及由此引发的营销/AI 争议。 不同观点： • 质疑派：认为这是“宣传大于实质”的 PR 操作，巨型公告放大成果，修正和问题却难被看见；且无充分 review 的 LLM 生成代码比原手写 unsafe 代码更不可信。 • 工程谨慎派：即便只是迁移阶段，仍担心暴露 UB、unsafe API 标注不当、测试/ Miri 覆盖不足；认为至少应先做更强验证，不能只靠“很快能跑”。 • 支持/理解派：认为从 Zig 直接转到 Rust 是合理的第一步，先获得更强类型系统，再逐步修 bug、收紧 unsafe 边界；稳定版仍留在 Zig，不必过度苛责中间态。 • 工具替代派：有人建议不必用 agentic AI，完全可用确定性的语言翻译工具（如 zig translate-c / c2rust）实现可控迁移。 • 现实主义派：指出部分问题只是预期中的迁移错误，真正争议焦点不是“有没有 UB”，而是“是否会把有问题的中间产物当成可发布成果”。 补充讨论：还延伸到 AI 时代代码审查文化退化、开源项目不应被非贡献者围攻，以及这类争议对整个软件工程价值判断的冲击。

Orthrus-Qwen3: up to 7.8×tokens/forward on Qwen3, identical output distribution

作者: FranckDernoncou | 评分: 5 | 评论数: 1 | 发布时间: 2026-05-15 22:38
文章摘要

Orthrus 是一种双视图扩散解码框架，在保持自回归LLM严格无损输出的同时实现并行生成。基于Qwen3模型，最高约7.8倍加速，KV缓存仅O(1)额外开销，只微调16%参数，并优于投机解码和现有扩散语言模型。

评论摘要
主要讨论点：论文 Orthrus 提出在冻结自回归 Transformer 中加入可训练扩散注意力模块，以并行草拟、AR 验证的方式加速推理，同时保持与基座模型完全相同的输出分布。 不同观点： • 作者/支持观点：Orthrus 的核心优势是“冻结主干+可训练扩散头”。扩散头一次并行预测 32 个 token，AR 头二次验证并接受最长匹配前缀；两者共享 KV cache，因此无需外部草稿模型，也没有额外 TTFT 初始化/同步成本。 • 性能论据：在 MATH-500 上最高达到 7.8x TPF、约 6x wall-clock 加速；仅训练 16% 参数、使用少于 1B tokens，8×H200 约 24 小时完成训练。平均接受长度为 11.7，高于 DFlash 的 7.9 和 EAGLE-3 的 3.5。 • 相比扩散语言模型的立场：作者认为 Dream、Fast-dLLM-v2、SDAR、Mercury、Gemini Diffusion 等会修改基座权重并损失精度，例如 Fast-dLLM-v2 在 MATH-500 上下降 11 分；Orthrus 因冻结 Qwen3-8B 主干，声称准确率与原模型完全一致。 • 相比 speculative decoding 的立场：Orthrus 不需要外部 drafter、不需要独立 KV cache，KV 额外开销为 O(1)，约 4.5 MiB，因此被认为比 EAGLE-3、DFlash 更轻量，且无 TTFT 惩罚。 • 方法细节观点：单步去噪优于多步去噪，TPF 为 6.35 vs 3.53；KL 蒸馏比交叉熵更能提高接受率。 补充讨论：主要争议或待验证点在于泛化性和适用范围：目前只在 Qwen3 上评估，且仅覆盖 greedy 与 rejection sampling；由于主干冻结，模型能力上限完全受基座模型限制，会继承其偏见、幻觉与知识缺口。

文章摘要

《Category Theory for Tiny ML in Rust》是一本工作草稿，旨在用范畴论解释并构建小型机器学习系统，将领域对象、态射、组合、训练等映射为 Rust 类型与可执行结构。书籍开放源码，配套公开工作坊，欢迎读者通过 GitHub 提交对内容、代码、术语和数学表述的反馈。

评论摘要
主要讨论点：围绕一本/一篇将 Rust、机器学习与范畴论结合的作品，讨论其范畴论是否真正有用、写作质量以及技术适配性。 不同观点： • 质疑“范畴论只是贴标签”：stschaef 认为书中范畴论内容被埋得很深，没有清晰定义对象和态射，也未给出机器学习的指称语义；期待看到 Markov categories、范畴间伴随等能推导实现性质的抽象框架，但实际更像 Rust、ML、范畴论的混合入门，三者都不够深入。 • 类似怀疑但更自省：dauertewigkeit 表示自己在研究中常遇到范畴论，即使数学背景也觉得它对描述 ML 框架帮助有限；但也承认可能是自己尚未真正理解其价值。 • 认为内容本质只是普通 typed programming：oersted 觉得示例像常规 Rust，用类型表示领域对象、函数变换对象，最多是更积极使用 newtype 限制领域；范畴论术语可以描述这种结构，但未体现特别的范畴论影响。 • 技术适配性吐槽：pshirshov 用“Rust / 无 HKT / 范畴论”暗示 Rust 缺少高阶类型，使其承载范畴论抽象不自然。 • 写作风格争议：dtj1123 和 oersted 都指出文本有明显 AI/Claude 味，语言臃肿、套路化，影响阅读；oersted 补充并非反对 AI 辅助写作，而是认为此文缺少作者性。 • 正面或中性反馈：jdw64、harrymatics 简短表示认可或鼓励。ctenb 提出术语建议，应将 ML 展开为 Machine Learning，避免与编程语言混淆。 补充讨论：争议焦点在于范畴论是否提供了可操作的抽象收益，还是仅用术语重新包装普通 Rust/ML 编程。
