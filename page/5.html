FEXPRs vs. vtable: how LispE interpreter works

作者: birdculture | 评分: 43 | 评论数: 3 | 发布时间: 2026-06-23 23:57
文章摘要

这篇文章讨论了LispE编程语言如何通过"编译对象的解释器"方式评估指令，化解了传统解释器与编译器的矛盾。 核心思想是建立等价关系：函数调用 f(a₁,..,aₙ) 等价于对象方法 F(a₁,..,aₙ).eval()。LispE将每条指令转化为派生类，都实现统一的eval方法。这样既保留了Lisp的同像性（homoiconicity）和AST结构，又能利用C++进行深度优化。 文章回顾了早期Lisp的FEXPR机制（运行时决定参数求值），指出其不可编译性问题。LispE通过将指令对象化、让对象自己携带求值规则的方式，在保持灵活性的同时实现了编译优化。数据被视为零参数指令，求值返回自身，统一了整个模型。

评论摘要
主要讨论点：围绕 LispE 的实现方式是否有技术优势，以及它作为一个 Lisp 项目的意义何在。 不同观点： • 技术质疑：`Joker_vD` 认为文中所谓“把每条指令做成带 `eval()` 的派生类、AST 常驻并用 C++ 优化”的方案，本质上仍是“树遍历解释器”。他指出主要性能开销首先来自遍历 AST，其次是频繁调用虚函数 `eval()`，最后才是各个小型 `eval()` 实现内部的效率问题，因而对其“奇迹般优化”的说法持保留态度。 • 项目背景价值：`sourdecor` 的关注点不在性能或实现细节，而在于这是一个“很酷的替代型 Lisp”，且由韩国公司 Naver 开发，认为其公司背景本身就值得注意。 • 实用主义立场：`rjsw`` 认为 Lisp 早已有成熟的原生编译器，因此没必要特别关注这种解释器路线，直接用现有优秀编译器即可。 补充讨论： • 争议焦点主要在于：LispE 的面向对象 AST + `eval()` 设计，究竟是值得称道的工程实现，还是只是传统树遍历解释器的重新包装。 • 评论之间形成了“技术批评—背景欣赏—实用替代”的不同讨论层次。

Un-0: Generating Images with Coupled Oscillators

作者: babelfish | 评分: 185 | 评论数: 19 | 发布时间: 2026-06-25 20:50
文章摘要

Unconventional AI发布了Un-0图像生成模型，这是首个基于物理动力系统（耦合振荡器）的大规模图像生成器。该模型在ImageNet 64×64数据集上达到FID 6.74，性能媲美传统方法首次发布时的水平。Un-0利用数千个相互耦合的Kuramoto振荡器来生成图像，振荡器之间的耦合强度是模型的主要可学习参数。该方法旨在通过物理计算实现约1000倍的能效提升。团队已开源模型权重、训练和评估代码，以推动基于物理动力系统的AI研究。

评论摘要
主要讨论点：利用Kuramoto振荡器进行神经网络/图像生成的新型计算方法 不同观点： • **技术可行性存疑（WhitneyLand）**：指出该方法存在n²规模扩展问题——生成4K图像需约5万亿个点对点连接，即便振荡器本身耗能为零，硬件实现也几乎不可行。64×64的演示分辨率本身就说明了局限性。 • **计算成本偏高（pizzao）**：CIFAR-10训练耗用20个B200 GPU小时、ImageNet耗用640小时，对于一个以"高效"为卖点的方法而言代价过高。 • **能效优势有待验证（ainch）**：论文以能效作为动机，但未提供与对比方法的实际能耗数据，说服力不足。 • **仅为软件模拟，需硬件落地（TaupeRanger）**：目前仍在传统硬件上仿真，要实现真正优势必须制造专用物理电路。 • **理论价值与跨领域启发（vessenes、dimatura、andybak）**：从函数空间搜索、非传统硬件计算等角度认可其学术意义；Wolfram对神经网络的观点被类比引用；《Sync》一书被推荐作延伸阅读。 • **与其他技术的相似性联想（foax、_def、fusionadvocate）**：分别联想到DCT图像压缩、FM合成音效、储层计算（reservoir computing），暗示该方法并非完全孤立的创新。 补充讨论：有人质疑该模型能否生成包含多个对象的复杂场景（如"宇航员骑马"），指向生成能力的上限问题；另有评论指出理解该研究需要一定物理背景知识，受众门槛较高。

How to Corrupt an SQLite Database File

作者: tosh | 评分: 7 | 评论数: 1 | 发布时间: 2026-06-26 18:05
文章摘要

本文介绍了SQLite数据库文件损坏的各种原因，主要包括： 1. **流氓进程覆写**：其他进程直接覆盖数据库文件，或误用已关闭的文件描述符写入数据库。 2. **文件锁问题**：文件系统锁实现不完整、POSIX锁被其他线程的close()取消、多个SQLite副本共存、不同锁协议混用、fork后继续使用数据库连接等。 3. **sync失败**：磁盘驱动器忽略sync请求，或通过PRAGMA禁用sync，导致崩溃后数据无法恢复。 4. **硬件故障**：非掉电安全的闪存控制器、虚报容量的U盘。 5. **内存损坏**：内存错误导致数据库内容被破坏。 6. **操作系统问题**：Linux线程异常、QNX上mmap()失败、文件系统损坏等。 7. **SQLite自身的历史Bug**：包括WAL模式竞态条件、表达式索引错误等已修复的漏洞。 总体而言，SQLite具有较强的抗损坏能力，但以上因素仍可能导致数据损坏。

评论摘要
主要讨论点：文章时效性与 SQLite WASM 在浏览器中运行的可行性 不同观点： • **文章内容已过时**（red1oon）：文章发表于 2022 年 1 月，彼时 SQLite 在浏览器中运行的条件尚不成熟。OPFS（Origin Private File System）同步访问句柄直到 2022 年中期才真正落地，这一关键技术使得 SQLite WASM 在浏览器环境中的运行才变得"真正可行"，因此文章的某些结论可能已不适用于当前情况。 补充讨论：该评论暗示读者应结合技术发展背景重新评估文章观点，尤其是关于浏览器端 SQLite 可行性的判断。
