The perils of UUID primary keys in SQLite

作者: emschwartz | 评分: 141 | 评论数: 18 | 发布时间: 2026-06-05 23:13
文章摘要

这篇文章探讨了在SQLite中使用UUID作为主键的性能问题。作者通过基准测试发现，使用随机UUID4作为主键比使用整数主键慢10-12倍，因为UUID4的无序性导致聚集索引的B树需要频繁重新平衡，产生大量额外的分页操作。通过性能分析图（diffgraph）证实了这一点。解决方案是使用时间有序的UUID7，其性能接近整数主键基线。文章强调了聚集索引的特性：表的物理存储顺序由索引键决定，因此主键的有序性对写入性能至关重要。这个问题不仅存在于SQLite，也适用于其他使用聚集索引的数据库。

评论摘要
主要讨论点：数据库主键选择策略——UUID vs 整数ID，特别是 UUIDv7 在 SQLite 中的性能表现 不同观点： • **反对过度使用UUID派**（blopker）：认为UUID被过度使用，bigint 在单数据库场景下更小更快，建议仅在分布式无主存储时考虑UUID，公开ID可用 Sqid 替代 • **UUIDv7实用派**（sedatk, jdthedisciple, yepyoukno）：UUIDv7 与顺序整数类似但避免暴露计数信息，在不重视插入性能且需要隐藏信息的场景下，UUIDv4 也可行；UUIDv7 应转为二进制优化存储 • **场景决定论**（adityaathalye）：本地单实例用 SQLite 自动整数 rowID 即可，但跨设备同步、实例协作场景下，顺序随机ID（如UUIDv7）价值凸显，便于合并、去重；强烈反对完全随机ID破坏树结构 • **双ID策略派**（bambax, ItsBob）：内部用整数 rowID/bigint 做主键和关联，外部暴露时用独立的UUID列，兼顾性能与安全 补充讨论： • 有人质疑脚本细节（批次数量）和性能数据来源（百万级插入速度、UUID生成耗时） • Postgres 等支持并发写入的数据库中，顺序键可能导致页面竞争 • 作者表示文章为草稿，计划补充不同行大小的影响

How LLMs work

作者: 0xkato | 评分: 380 | 评论数: 23 | 发布时间: 2026-06-03 20:15
文章摘要

这篇文章解释了大型语言模型（LLM）的工作原理。现代LLM主要通过堆叠transformer块构建。文章涵盖核心机制： 1. **分词（Tokenization）**：将文本转换为整数ID序列，使用子词级别的词汇表 2. **嵌入（Embeddings）**：通过嵌入矩阵将token ID转换为有意义的向量表示 3. **位置编码**：让模型理解token的顺序 4. **注意力机制**：token之间如何共享信息 5. **多头注意力**：同时追踪多种关系 6. **前馈网络**：存储模型的大部分结构化知识 7. **残差流和层归一化**：使深层网络可训练 8. **下一个token预测**：模型的实际输出机制 文章强调，虽然不同LLM在训练数据、规模和配置上有差异，但它们共享相同的transformer架构骨架。

评论摘要
主要讨论点：关于LLM工作原理的文章引发了对AI技术本质、解释方式和内容质量的多角度讨论。 不同观点： • **技术简单论**：[malwrar] 认为transformer架构本质上非常简单，OpenAI的突破仅在于把模型做大，AI公司成功地将其包装成"超级天才的作品"进行营销 • **能力质疑论**：[AltruisticGapHN] 质疑"预测下一个词"的解释过于简化，LLM明显具有空间推理能力（如设计渐变边框），认为算法远比主流解释复杂 • **解释充分论**：部分评论者认为理解底层架构（如transformer）就能理解LLM工作原理 • **解释不足论**：[stalfie] 反驳称仅解释transformer架构无法真正理解现代LLM行为，就像了解神经元生化机制不等于理解大脑 • **AI生成内容争议**：[cubefox] 指出讽刺现象——讲解LLM的文章本身可能是AI生成的，只能通过写作风格而非准确性来判断；[lhd1]和[vocram]就AI辅助内容的价值产生分歧 补充讨论：多位评论者指出文章存在技术错误（如位置编码解释不当）和结构问题（内容跳跃、过多旁支），建议采用更清晰的层次化讲解方式。有人推荐Karpathy的microgpt作为更好的学习资源。

Programmers Aren't People

作者: elliotbnvl | 评分: 18 | 评论数: 3 | 发布时间: 2026-06-06 21:38
文章摘要

这篇文章追溯了"computer"一词从指代人到指代机器的演变历史。最初三百年间，computer指从事计算工作的人，如19世纪法国的理发师、哈佛天文台的女性天文学家、NASA的女性计算员等。1945年ENIAC问世后，这个词迅速转移到机器身上。作者指出"programmer"面临同样命运——这些词本质上都是"动词+er"结构，描述的是功能而非人。当AI能完成编程工作时，"programmer"这个词也会像"computer"一样被机器占据，程序员需要像当年Dorothy Vaughan那样爬向更高的梯级。

评论摘要
主要讨论点：程序员职业随技术发展的演变与定义变化 不同观点： • **职业融合演变论**（greazy）：认为程序员正在经历类似"印刷工→平面设计师"的演变。随着LLM出现，多学科技能融合产生新领域，"软件工程师"可能是更准确的称呼，强调工程化思维而非单纯编码。 • **本质不变论**（turtleyacht）：编程的本质是逻辑和计算，实现介质并不重要（可以用纸带、鸟类通信、纺织品等）。当前只是恰好用机器实现，但编程的核心概念超越具体工具。 • **抽象层递进论**（msla）：程序员的工作一直在演变（从机器码到高级语言），LLM只是又一层抽象。类比COBOL时代"用自然语言编程"的理想，但始终需要人来制定规范、验证正确性和修复问题。 补充讨论：三位评论者虽然角度不同，但都认同技术变革不会消除程序员角色，而是转变其工作重心——从底层实现转向更高层次的设计、验证和问题解决能力。

Show HN: Keybench – Scriptable, extensible performance tool for key value stores

作者: alexpadula | 评分: 8 | 评论数: 0 | 发布时间: 2026-06-06 23:06
文章摘要

keybench 是一个可脚本化、可扩展的键值存储性能测试工具。用户用 Lua 编写工作负载，keybench 在一个或多个存储引擎上运行并测量每个操作的时间，报告吞吐量和延迟分布。它测量两个速率：工作负载单元数/秒（wu/s）和原始操作数/秒（ops/s），以及各操作类型的延迟分布（p50、p99、p99.9、最大值）。工具由五部分组成：引擎（负责并发）、工作负载（Lua 脚本）、存储接口（统一的8个操作）、后端插件（支持内存 skiplist、RocksDB、TidesDB 等）和报告器（控制台、TSV、时间线等输出格式）。默认构建仅需 C 编译器和 pthreads，可通过 make 参数添加持久化引擎支持。
