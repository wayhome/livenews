Stepanov's biggest blunder? The curious case of adjacent difference

作者: signa11 | 评分: 47 | 评论数: 5 | 发布时间: 2025-08-21 11:30
文章摘要

这篇文章主要讨论了C++标准库中的`std::adjacent_difference`算法的设计原理及其与微积分基本定理的联系。文章指出该算法除了计算相邻元素差值外，还会保留第一个元素不变，这种看似奇怪的设计实际上是刻意为之，目的是使其与`std::partial_sum`互为逆运算。作者通过文档ID压缩和时间戳计算等例子说明这种设计的局限性，同时揭示了该算法与微积分中求导和积分的关系：离散差分对应求导，部分和对应积分，二者互为逆运算，这正好体现了微积分基本定理的离散形式。

评论摘要
主要讨论点：[C++标准库中的设计问题和替代方案] 不同观点： • **C++缺乏通用"零"概念的问题** - 用户[fph]指出，C++没有通用的"零"概念，导致`adjacent_difference`等函数在类型稳定性方面存在问题。建议通过`zero`等方案改进设计。 • **部分算法参数设计问题** - [voidmain]补充指出`partial_sum`存在类似问题（如`T - T`可能不是`T`），并提出更通用的解决方案：将初始累加器作为单独参数传递，使算法设计更对称。 • **标准库中的历史性设计错误** - [AnotherGoodName]认为`std::vector`是更大的设计失误，批评其特化实现破坏了容器功能，并引用Herb Sutter的文章佐证这是"过早优化"的典型案例。 • **实际应用视角的观察** - [wowczarek]从实际应用角度出发，虽然承认类型系统的问题，但更关注这些函数在特定领域（如Allan方差计算）中的实用价值。 补充讨论： - 争议焦点集中在标准库设计是否应该优先考虑类型安全性（如[fph]和[voidmain]的观点）还是实用价值（如[wowczarek]的角度）。 - [getnormality]提供了延伸学习资源（Knuth的《具体数学》），暗示这些问题在离散数学中有更系统的理论支持。 - 关于标准库"最大设计错误"的争议：`adjacent_difference`的类型问题 vs `vector`的特化问题。

Ghrc.io appears to be malicious

作者: todsacerdoti | 评分: 383 | 评论数: 16 | 发布时间: 2025-08-24 23:27
文章摘要

这篇文章揭露了一个恶意域名ghrc.io的钓鱼攻击。该域名与GitHub容器镜像服务ghcr.io仅有一个字母之差，容易因拼写错误而被访问。文章发现，虽然ghrc.io表面上只是一个默认的nginx服务器，但其针对容器镜像API的/v2/路径却设置了认证请求，诱使容器工具（如Docker）将用户凭据发送到恶意服务器。这种精心设计的攻击专门针对常见的拼写错误场景，可能通过错误的登录命令或CI/CD配置窃取用户凭证。作者警告开发者要警惕这种新型的"typo-squatting"攻击手段。

评论摘要
主要讨论点：[GitHub Container Registry (ghcr.io) 域名被仿冒 (ghrc.io) 的安全风险及应对措施] 不同观点： • 安全风险观点： - 认为这是一个严重的攻击向量，因为域名 ghcr.io 和 ghrc.io 容易混淆，可能导致用户误输入或被骗。 - 指出 GitHub Container Registry 目前仅支持经典令牌（classic tokens），而非细粒度令牌（fine-grained tokens），增加了风险。 - 提到已有许多开源项目误用了 ghrc.io 域名，进一步证明问题的普遍性。 • 技术分析观点： - 讨论 Bearer token 的安全性，质疑是否存在令牌重放（token replay）风险。 - 提出疑问：OAuth 是否会跨域名重用令牌？如果不会，仿冒域名可能无法获取真实域名的令牌。 • 应对措施观点： - 建议避免使用缩写（如 ghcr），而是使用全称（如 github container registry）以减少混淆。 - 推荐使用类似 haveibeensquatted 的工具检测并提交域名滥用投诉。 - 提醒不要使用非主流 TLD（如 .io），因为其滥用处理流程可能不如 .com 顺畅。 补充讨论： - 争议焦点： - 域名混淆的实际危害程度（是否足以构成严重威胁）。 - Bearer token 在此场景下的安全性（是否容易被利用）。 - 其他讨论： - 有用户分享了之前关于此问题的 Hacker News 讨论链接。 - 有人提到可以通过 whois 查询联系域名注册商（Dynadot）的滥用投诉邮箱。

Y Combinator files brief supporting Epic Games, says store fees stifle startups

文章摘要

创业孵化器Y Combinator提交法庭意见书，支持Epic Games对苹果的反垄断诉讼，指控苹果App Store的30%抽成和禁止外链规定扼杀初创企业发展。此前法院已裁决苹果违反2021年禁令，要求其允许开发者自由添加第三方支付链接，但苹果在上诉中试图推翻该裁决。Y Combinator指出，高额抽成导致基于App的商业模式难以存活，当前裁决已重燃投资者兴趣，呼吁法院永久取消苹果的限制措施以促进创新竞争。

评论摘要
主要讨论点：苹果App Store的政策、费用及其对开发者和市场的影响 不同观点： • **自由市场观点**：认为苹果应有权自由运营App Store，但用户也应能自由选择其他应用商店（jmull）。市场应决定苹果的政策是否合理（rootusrootus）。 • **垄断监管观点**：由于苹果和谷歌在智能手机市场形成垄断，应受到监管，限制其收费和政策（rootusrootus, exabrial）。 • **开发者生态批评**：苹果的开发者生态对开发者不友好，高额费用（30%）影响公司生存和创新（bentocorp, lloyddobbler）。 • **用户保护观点**：苹果的封闭生态（“围墙花园”）为用户提供安全和便利，如严格的审核和订阅管理（pen2l）。 • **费用争议**：30%的费用是否合理？部分人认为开发者应支付，部分人认为费用过高且抑制创新（MagicMoonlight, doctorpangloss）。 • **开放标准倡导**：呼吁回归开放标准（如Web）而非依赖专有应用商店（neilv）。 补充讨论： • **争议焦点**：30%的“苹果税”是否合理？支持者认为苹果提供了平台和市场，反对者认为费用过高且垄断性。 • **监管困境**：如何平衡垄断监管与市场自由？部分人支持分拆垄断企业（exabrial），部分人认为应调整费用结构（doctorpangloss）。 • **开发者与用户利益冲突**：开发者希望更低的费用和更开放的市场，而部分用户更看重安全和便利（pen2l vs. bentocorp）。
