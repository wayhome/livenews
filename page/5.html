Link Time Optimizations: New Way to Do Compiler Optimizations

作者: signa11 | 评分: 35 | 评论数: 10 | 发布时间: 2025-05-19 07:48
文章摘要

这篇文章主要介绍了即将举办的AVX和NEON向量化工作坊，以及链接时优化（LTO）的重要性。AVX工作坊将于5月底举行，而NEON工作坊时间待定。文章强调了编译器在代码优化中的作用，尤其是通过内联和循环合并等技术提高性能。然而，传统的编译过程以文件为单位进行编译，限制了跨文件的优化潜力。为此，文章引入了链接时优化（LTO）的概念，允许链接器在链接阶段进行跨编译单元的优化，如内联和代码局部性改进，从而进一步提升程序性能。LTO能够解决编译器因文件边界限制而无法进行的优化问题。

评论摘要
主要讨论点：LTO（链接时优化）的优缺点及其实际应用 不同观点： • [kazinator] 反对默认开启LTO，认为它会破坏一些代码的预期行为。他提供了两个例子（securely_wipe_memory 和 gc_protect）来说明LTO可能导致编译器错误地优化掉必要的函数调用，从而引发安全性和正确性问题。他认为LTO在某些发行版中作为默认选项是糟糕的做法。 • [WalterBright] 提到链接时优化早在1980年代就已经存在，但他个人更倾向于让编译器一次性编译所有源文件，而不是通过LTO来实现优化。他还指出D语言的编译器设计允许一次编译一个对象文件或合并所有源文件，而大多数人选择后者。 • [Deukhoofd] 认为LTO并不是一个新概念，早在2011年就已经在GCC中引入。他以此回应那些认为LTO是新事物的人。 • [mcdeltat] 认为将.c/.cpp文件作为优化的障碍已经不符合现代开发需求，尤其是在内存和计算资源充足的情况下。他指出，现代代码分割成源文件更多是为了组织管理，而不是内存限制。虽然LTO是一种补偿措施，但由于C/C++的惯性和向后兼容性，这种模式很难改变。 • [sakex] 建议在讨论LTO时加上日期，因为LTO已经存在很久，不再是一个新概念。 • [phkahler] 分享了他使用LTO的经验，指出LTO在性能上有显著提升（约15%），但构建时间大幅增加。他还提到LTO在使用多核处理方面存在不足，并对比了升级硬件后获得的性能提升。 • [Remnant44] 认为LTO虽然不新，但非常强大。他分享了自己因为未使用LTO导致性能减半的经历，强调了LTO在某些情况下的重要性，并指出讨论LTO对新手工程师是有价值的。 • [lilyball] 指出ffmpeg包含大量汇编代码，因此使用LTO进行测试并不合适，因为LTO不会对汇编代码进行优化。 补充讨论： • LTO的性能提升和构建时间之间的权衡是讨论的一个重点。 • 对LTO是否适应现代开发需求存在不同看法，有人认为它是必要的补偿机制，有人则认为应重新设计编译模型。 • 实际使用LTO的经验各异，有的获得了显著性能提升，但也面临构建时间长和多核利用不足的问题。 • 不同编译器（如GCC和D语言编译器）在LTO实现上的差异也是讨论的一部分。 • 对LTO在某些特定项目（如ffmpeg）中的适用性存在争议。

Harnessing the Universal Geometry of Embeddings

作者: jxmorris12 | 评分: 80 | 评论数: 8 | 发布时间: 2025-05-21 18:15
文章摘要

本文介绍了一种无需配对数据、编码器或预定义匹配集，即可将文本嵌入从一个向量空间转换到另一个向量空间的方法。该无监督方法通过将嵌入转换为一个通用的潜在表示（基于柏拉图表示假说），实现不同架构、参数和训练数据集的模型间高余弦相似度的转换。这种转换能力对向量数据库的安全有重大影响，攻击者可借此提取敏感文档信息，足以进行分类和属性推断。

评论摘要
主要讨论点：向量空间对齐及嵌入向量的安全性与应用 不同观点： • [jxmorris12]（论文作者）认为，成功对齐两个无需配对数据的向量空间是一个重要成果。他提到，曾有专家认为这种对齐是不可能的，除非使用一些配对数据。此外，他指出嵌入向量并非加密，且通过一些方法可以解码这些向量，即使没有访问生成它们的模型。他引用的Cursor安全政策说明了嵌入向量逆转的风险。 • [airylizard] 对嵌入向量能够被翻译成共享的潜在空间表示赞赏，并提出了关于如何保护嵌入空间以防止通用翻译和逆转的讨论。他们建议探索加固、模糊化或“水印”嵌入空间的方法，以防止信息泄露。 • [mjburgess] 对“不同数据”的说法提出质疑，认为所有有用的LLM都在大致相似的数据集上进行训练，因此所谓的“不同数据”实际上并没有本质区别。他们批评了对“柏拉图式理想词排列”的 hype，并指出现实中的数据编码只是对已有电子文本的近似。 • [kevmo314] 对该成果表示赞赏，并提到其在LoRAs模型间翻译上的潜在应用，认为这是迈向该目标的第一步。 • [SubiculumCode] 关注该技术是否可以用于不同嵌入模型在嵌入空间中的互通。 • [kridsdale1] 担心该技术对法律服务RAG公司的潜在灾难性影响。 补充讨论： • 该技术在信息安全方面的风险被多次提及，尤其是嵌入向量的逆转和信息泄露问题，引发了对保护措施的讨论。 • 不同观点中对数据相似性和模型训练的讨论反映了在LLM领域对数据集和模型通用性的深刻思考。 • 技术应用的潜在广泛性被多位评论者看好，尤其是在模型互通和特定应用（如LoRAs翻译）上的可能性。 争议焦点： • 主要集中在嵌入向量是否能被有效保护以及该技术对数据安全和法律服务领域的潜在负面影响。

评论摘要
主要讨论点：软件工程与产品开发的平衡、工程师与商业人士的角色分工、技术发现与工程实践的关系、以及技术工具的普及对创意质量的影响。 不同观点： • **产品与利润的优先级**： - **godelski**认为，Moxie强调的是制作高质量产品而非追求利润，这与一些以盈利为主要目标的观点形成对比。工程师应专注于产品质量，而利润应由商业人士负责。 - 争议焦点在于工程师是否应关注利润，还是只专注于技术产品质量。 • **技术理解与创意实践的关系**： - **mrandish**指出，电影导演不需要知道如何制造相机，但需要了解相机的工作原理，以实现艺术效果。这与原文中将两者混淆的观点形成对比。 - **abdullahkhalids**则认为，软件工程中的发现过程并非独特，所有工程学科都涉及发现，并且都依赖抽象层，反对原文中将软件开发描绘为特别独特的说法。 • **工程师的定义与特质**： - **austin-cheney**主张，真正的工程师需要测量和遵循流程，而大多数开发者只是“打字员”。优秀的工程师需要具备 conscientiousness 和 persistence，并通过反复尝试和精确测量实现创造力。 - 这与普遍认为的软件开发者即工程师的观点形成对比，强调了工程师应具备的特质。 • **组织内部的协作与创新**： - **vaylian**和**jt2190**强调，组织内各团队需要相互了解，以实现创新和突破，而不是将其他团队视为“黑箱”抽象层。 - 这与一些传统组织结构中将团队隔离的做法形成对比，认为这样会限制潜在的创造力。 • **技术工具普及对创意质量的影响**： - **macleginn**指出，尽管游戏开发工具变得更容易使用，但高质量游戏的比例并未增加，类似于创意作品的数量增加但质量未提升的现象。 - **vincnetas**将此现象比作相机普及导致YouTube上充斥大量视频，而非增加奥斯卡获奖作品数量，认为工具普及不等于创意质量提升。 补充讨论： • **外部资金与创新限制**： - **coderintherye**指出，如果想要外部资金支持，就必须遵循传统惯例，这限制了创新的自由。但未来随着AI驱动公司兴起，VC的心态可能会改变。 • **历史工程与创新的关系**： - **nwlotz**通过ARPANET的例子，说明工程提供了推动愿景的潜力，而愿景反过来又推动新的工程创新，强调了工程与愿景的双向互动关系。 • **内容存档与访问**： - **eightys3v3n**对作者排除其网站被Wayback Machine存档感到不满，认为这样使得内容无法可靠存储，增加了访问难度。 争议焦点主要集中在工程师的角色与责任、产品质量与利润的优先级、以及技术工具普及对创意质量的影响等方面。这些观点反映了在软件工程、创意实践和组织创新中不同利益和视角的平衡问题。

文章摘要

Signal Messenger is protecting users of its Windows Desktop version from the privacy risks posed by Microsoft's AI tool, Recall, in Windows 11. Recall takes frequent screenshots and stores user activity, potentially compromising private messages. To counter this, Signal has implemented a default block on Windows screenshotting the app, though users can manually disable this if needed. Despite Microsoft making improvements to Recall, such as making it opt-in and encrypting data, concerns remain about its impact on privacy. Signal is using a copyright protection API to prevent Recall from indexing conversations, highlighting the lack of proper developer tools to manage such features. This move offers some protection but has limitations, especially if chat participants alter default settings.

Apple Filing Protocol will soon disappear from macOS

作者: miles | 评分: 7 | 评论数: 1 | 发布时间: 2025-05-21 23:27
文章摘要

Apple Filing Protocol (AFP)是苹果早期用于Mac间文件共享的技术，诞生于1985年，配合AppleTalk、AppleShare等软件和LocalTalk硬件使用，解决了资源叉（resource fork）在非Mac电脑间传输时损坏文件的问题。后来，苹果推出Apple Open Collaboration Environment (AOCE)和PowerTalk，但均未成功。随着90年代中期互联网普及，苹果转向使用TCP/IP等开放标准，AFP逐渐被SMB协议取代。macOS 11 (Big Sur)移除了AFP服务器功能，并在macOS Sequoia 15.5中开始弃用AFP客户端。未来，用户需转向使用SMB或NFS协议进行文件共享。虽然第三方如Netatalk仍支持AFP，但其前景不明。

评论摘要
主要讨论点：NFS文件系统中的文件名包含斜杠（slash）的问题及其引发的系统故障 不同观点： • 一些用户（如DonHopkins）指出，NFS协议本身并不禁止文件名中包含斜杠，这可能导致文件系统损坏的问题。特别是在使用GatorBox这样的设备时，Mac可以通过NFS将斜杠写入文件名，看似正常工作，但在恢复备份时会导致严重问题。这种行为是由于NFS服务器未对文件名中的非法字符进行检查，导致后续操作失败。 • 另一部分讨论提到，Mac系统在1990年代初允许用户在文件名中使用斜杠和空格，这是与Unix系统文件名规范不兼容的。Mac用户可能会无意中使用日期作为文件名（如"01/02/1991"），而这些字符在Unix文件系统中是不允许的，导致备份和恢复过程中出现问题。 • 有人提到Unix文件系统理论上不允许文件名中包含斜杠，但实际中却可能发生，尤其是通过某些客户端或桥接设备（如GatorBox）绕过了这些限制。这种漏洞可能被用于创造一些"无法访问"的文件，作为一种特殊的安全机制，但同时也带来了系统不稳定和恢复失败的风险。 补充讨论： • 讨论中引用了《Unix-Haters Handbook》的内容，指出Unix文件系统允许使用除斜杠和ASCII NUL字符外的几乎所有字符，这为用户提供了很大的灵活性，但也导致了与其他系统（如Mac）的兼容性问题。 • 具体案例中，Steve Sekiguchi提到在1990年左右的Sun NFS服务器中，由于NFS服务器未检查文件名中的非法字符，导致Mac用户可以通过NFS创建带有斜杠的文件名，并且这些文件在备份和恢复过程中出现问题，核心转储时会崩溃。 • 最后，讨论中还提到一些有趣的实验，如在Mac上使用Finder创建带有斜杠或冒号的文件名，虽然看似可以操作，但在命令行中查看时会出现异常行为，不过并不会损坏文件系统或备份。 争议焦点： • 核心争议在于NFS协议及服务器未对文件名中的非法字符进行严格检查，导致文件系统潜在的损坏风险，尤其是在跨系统（如Mac和Unix）操作时。用户期望文件名规范在不同系统间保持一致，以避免不必要的兼容性和恢复问题。
