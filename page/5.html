The User Is Visibly Frustrated

文章摘要

这篇文章探讨了为什么编程AI助手会让人感到沮丧。作者认为问题在于它们的对话式交互设计：它们表现得像真人同事一样友好、会道歉和反思，触发了我们的社交本能，但实际上它们不会真正学习、适应或承担责任。当它们反复犯同样的错误时，这种"假装是人"的行为会让用户产生对待真人同事的情绪反应——感到被冒犯和沮丧，但对着算法发火又毫无意义。作者建议也许应该让AI助手听起来更机械化，打破"与人交流"的错觉，让用户意识到只是在审批随机结果。

评论摘要
主要讨论点：AI工具（特别是LLM聊天机器人）在实际使用中引发的挫败感及其根源 不同观点： • **工具设计派**（zeumo, Mikhail_Edoshin）：认为聊天机器人不是正确的形态，应该构建专用工具而非通用文本框。早期Copilot的智能补全体验优于现在的提示词模式，专用工具（如Firefox翻译）比通用chatbot更高效。服务化趋势牺牲了工具的可预测性和可组合性。 • **管理心态派**（the_sleaze_, apsurd）：将AI视为需要管理的初级员工，强调设定合理预期和有效沟通。认为这是沟通技巧问题而非工具问题，用户应该承担沟通责任而非责怪工具。 • **技术限制派**（wcoenen, GuB-42, vinc）：指出上下文窗口压缩、重复回答是能力边界的信号。建议针对不同任务开启新会话，通过分支对话、更新记忆和提示文件来优化体验。 • **行为问题派**（jofzar, pflenker, sohex）：批评AI过度自信、缺乏"我不确定"的表达、无法提出好问题、会陷入错误循环。希望有"自信度滑块"来控制其行为。 • **情感边界派**（em-bee, movpasd）：强调不可预测性造成的压力影响健康和工作环境。建议保持礼貌但不友好，避免情感投入，将对话视为社会幻觉。 补充讨论：有人发现骂AI能改善结果（可能触发更严格模式），也有人建议用自动化检查（linter、pre-commit）替代人工纠错。UI设计问题（如Claude无法跨模式切换能力）也被提及。

DeepSWE: A contamination-free benchmark for long-horizon coding agents

作者: ammar_x | 评分: 29 | 评论数: 7 | 发布时间: 2026-05-26 19:40
文章摘要

DeepSWE是一个长周期软件工程基准测试，具有四大优势： 1. **无污染**：任务从零编写，模型预训练时未见过解决方案 2. **高多样性**：涵盖91个代码库、5种编程语言 3. **真实复杂度**：提示词比SWE-bench Pro短一半，但解决方案需要5.5倍代码量和约2倍输出token 4. **可靠验证**：手写验证器测试软件行为而非实现细节 现有基准存在缺陷：SWE-bench Pro任务平均仅120行代码，验证器误判率高（8%假阳性、24%假阴性）。DeepSWE提示词简短自然（平均2158字符），但任务规模大（平均668行代码、7个文件），更贴近开发者实际工作场景。测试结果显示，在公开基准上表现接近的模型在DeepSWE上差距明显，GPT-5.5达70%准确率领先。

评论摘要
主要讨论点：关于一个新的AI编程能力基准测试的评价和质疑 不同观点： • **基准设计缺陷派**（gertlabs）：认为该基准虽然"无污染"但仍有根本性问题——单一正确答案设计导致发布时就已接近饱和（70%）。主张需要多智能体模拟、大动作空间和动态环境来抵抗污染 • **实用性关注派**（vanuatu）：基准结果符合实际使用体验，但批评缺少代码质量/可维护性评估，认为这是当前模型的主要问题——缺乏代码"品味" • **饱和度质疑派**（dnnssl2）：直接质疑为何发布一个前沿模型即将达到上限的基准 • **测试覆盖度疑问**（JacobAsmuth）：疑惑为何未测试Gemini 3.5 Flash (High) • **异常结果关注**（toastmaster11）：对Opus 4.6在最大推理模式下表现不如Sonnet 4.6低推理模式感到困惑 补充讨论：gertlabs肯定了基准标准化工具（mini-swe-agent）的做法，认为模型应能泛化到不同工具。vanuatu暗示这可能是对SWE Bench Pro的批评。创始人charleyslee现身回应问题。

The Best Engineers Write Less Code

作者: funnyenough | 评分: 16 | 评论数: 6 | 发布时间: 2026-05-27 00:33
文章摘要

这篇文章强调软件开发的核心原则： **主要观点：** - AI生成代码不能改变软件质量的本质，糟糕的软件依然糟糕 - 开发时间直接等于成本，这是管理层关注进度的原因 - 优秀工程师的价值在于**避免构建不必要的功能**，而非编写更多代码 - 代码是负债，除非它解决了正确的问题 - 构建错误的东西是最大的浪费 **建议实践：** - 在开始前与利益相关者确认需求和目标 - 采用敏捷方式：短周期迭代，及时获取反馈 - 衡量工程师的标准是创造的价值与留下的复杂度之比 - 有空闲时间？去删除代码 核心思想：少即是多，正确比快速更重要。

评论摘要
主要讨论点：软件开发的瓶颈从编码速度转向理解和维护能力，以及AI时代对软件设计的影响 不同观点： • **系统思维能力差异论**（Frannky）：人们在建模能力上存在根本差异。有些人能进行端到端的系统思考，提取抽象并模糊非关键部分；另一些人局限在信息孤岛中，过多信息会引发焦虑。后者设计的产品往往脱离用户需求，即使有AI辅助也无法成功，因为缺乏正确的方向定义。 • **代码量不是核心问题**（kspetkov79）：减少代码有帮助，但减少不清晰的决策可能更重要。这暗示问题的本质在于决策质量而非代码数量。 • **LLM不能掩盖糟糕设计**（funnyenough）：批判"LLM能生成代码所以不需要好软件"的观点。无论是Claude还是不懂的人写的，糟糕的软件依然糟糕。 • **瓶颈已转移**（paul_knox）：编码瓶颈从打字速度转向理解和维护能力。 • **UI范式应彻底改变**（saltyoldman）：激进观点认为复杂前端UI已过时，应该用简单API让个人AI代理直接访问数据和执行操作，而非通过有限的传统界面。提出长期运行的智能代理系统来管理日常任务。 补充讨论：评论间存在隐含共识——AI工具的价值取决于使用者的思维能力和系统设计能力，技术本身不能弥补战略思维的缺失。

文章摘要

这篇文章介绍了aesc silicon创始人Daniel Schultz开创的开源芯片商业模式。核心思路是免费提供IP设计，通过支持服务和定制化获利，类似Linux的Red Hat模式。主要客户群体包括需要可验证安全性的加密应用，以及越来越多需要定制芯片的小公司。Daniel开发了IP Forge工具，作为开源IP模块的包管理器。开源降低了实验成本（如Wafer.Space的4-7千美元流片），加速创新迭代。Daniel选择自力更生、不融资，对开源芯片生态持长期愿景。

评论摘要
主要讨论点：开源硬件/芯片的商业可行性和安全性问题 不同观点： • **技术可行性质疑**（jdw64）：认为开源硬件根本不可行。硬件失败成本高昂，每次流片都需要大量时间；开源EDA工具停留在落后制程；硬件是物理终点产品，无需维护，无法像软件SaaS那样持续收费 • **安全性的双面性**（nickserv）：开源硬件对军方/政府有价值，可确保无后门；但公开代码也增加被攻击风险。软件漏洞可快速修复部署，硬件则需重新制造芯片才能修复 • **商业模式的可能性**（gchamonlive, johncole, nikanj）：企业愿意为支持、定制、专业化服务付费；更重要的是分担技术决策责任和风险。类比旅游业——森林免费但旅游公司仍能盈利 • **隐私与安全诉求**（adrianwaj）：强调"无后门"的重要性，反对监控和数据滥用，将其与反法西斯联系起来 补充讨论：核心争议在于开源硬件能否像开源软件一样建立可持续商业模式。技术派认为硬件的物理特性和高成本使其不适合开源；商业派认为服务和责任分担仍有价值；安全派关注供应链透明度。

主要讨论点：订阅服务的心理陷阱与应对策略 不同观点： • **立即取消派**（sa-code）：订阅后立即取消，避免忘记续费，需要时再重新订阅 • **技术防御派**（borski, IFC_LLC, musha68k）：使用虚拟信用卡、自定义域名邮箱、或直接作废信用卡来控制订阅 • **商家视角**（rectang, m463）：支持便捷退订的商家会获得更多休闲订阅者；Costco会员制也起到筛选客户、降低运营成本的作用 • **定价策略质疑**（gobdovan）：健身房的日票定价故意不合理（月费50欧vs日票18欧），迫使用户要么办月卡要么放弃，挤压中间选项 • **心理学悖论**（Sophira）：人们更愿意花10美元改变自己，而非收10美元被改变，尽管结果相同——说明交易框架影响决策 • **价值怀疑论**（xet7）：苹果产品性价比提升；流媒体订阅看完就取消；付费需要看到ROI 补充讨论：有人指出文章作者自身推广订阅服务存在讽刺（winddude），也有人质疑作者媒体背景的可信度（croisillon）。整体讨论反映出用户对订阅模式的警惕和反制手段的多样化。
