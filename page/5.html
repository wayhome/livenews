Sheet Mewsic: Moritz von Schwind's Katzensymphonie (1868)

作者: tintinnabula | 评分: 4 | 评论数: 0 | 发布时间: 2025-04-12 01:25
文章摘要

文章介绍了奥地利画家莫里茨·冯·施温德（Moritz von Schwind）于1868年创作的《猫交响曲》（Katzensymphonie）。这幅作品以幽默和讽刺的方式展现了猫在乐谱上攀爬、翻滚和打盹的场景，讽刺了瓦格纳的未来艺术作品。施温德将此画作为礼物送给小提琴家约瑟夫·约阿希姆（Joseph Joachim），以庆祝其被任命为柏林音乐学院院长。画中的猫象征着不和谐的音乐（Katzenmusik），而约阿希姆则被调侃无法演奏这首复杂的作品。此外，文章提到施温德与约阿希姆等人共同创立的“黑猫社”（Die Schwarzen Katzen），以及《猫交响曲》对后世的文化影响，包括在儿童杂志和心理学家赫尔曼·罗夏（Hermann Rorschach）的作品中出现的衍生版本。

Scientists: Protein IL-17 fights infection, acts on the brain, inducing anxiety

作者: wglb | 评分: 100 | 评论数: 8 | 发布时间: 2025-04-14 15:54
文章摘要

科学家发现免疫蛋白IL-17不仅能抵抗感染，还对大脑产生影响，引发焦虑或促进社交行为。麻省理工学院和哈佛医学院的研究显示，IL-17作用于大脑的两个区域：杏仁核和体感皮层，产生不同效果。在杏仁核中，IL-17引发焦虑；而在体感皮层，它促进社交行为。这些研究表明免疫系统和神经系统紧密相连。研究还发现，IL-17通过其受体IL-17RA和IL-17RB影响大脑功能，可能最初是作为神经调节剂进化而来，后来被免疫系统用于促发炎症。这项研究揭示了免疫分子如何影响情绪和行为，提供了对身心状态联系的新理解。

New Vulnerability in GitHub Copilot, Cursor: Hackers Can Weaponize Code Agents

文章摘要

Pillar Security研究人员发现了一种新的危险供应链攻击方式，称为“规则文件后门”。该技术通过在Cursor和GitHub Copilot等AI代码编辑器使用的配置文件中注入隐藏的恶意指令，悄无声息地破坏AI生成的代码。攻击者利用隐藏的Unicode字符和复杂的规避技术，操纵AI插入可绕过代码审查的恶意代码，且不易被开发人员和安全团队察觉。 规则文件是指导AI生成或修改代码的配置文件，广泛共享、采用并被信任，但往往缺乏安全审查。攻击者可以利用这些文件，在代码生成过程中嵌入恶意提示，影响AI生成包含漏洞或后门的代码。这种攻击具有持久性，一旦恶意规则文件被纳入项目，将持续影响后续代码生成，并可能通过项目分叉传播，威胁供应链和终端用户。 该攻击利用上下文操纵、Unicode混淆和语义劫持等技术，可在不同AI助手间生效，揭示了系统性的漏洞。

Kezurou-Kai #39

文章摘要

这篇文章介绍了作者参加的第39届在日本新泻县糸鱼川市举办的Kezurou-kai活动。该活动的主要内容是参赛者使用日本刨子刨出最薄的木刨花，比拼木工技艺。活动为期两天，参赛者在第一天进行预赛，每天有三次机会提交刨花测量，最后选出五名刨花最薄者进入第二天下午的决赛。比赛规定使用70毫米刨子和55毫米宽、1800毫米长的桧木，这种木材因其易切削且能刨得很薄而成为标准用材。比赛场地是一个体育馆，馆内设有刨木工作台。参赛者需自备刨木材料和工具，并使用数显千分尺测量刨花厚度。活动挑战在于将刨花厚度控制在10微米以下。尽管作者和朋友们在第一天未突破10微米，但仍享受了与老友重逢和切磋技艺的乐趣。第二天比赛更加紧张，作者团队继续尝试不同方法以改进刨花质量。

Everything wrong with MCP

作者: sshh12 | 评分: 212 | 评论数: 25 | 发布时间: 2025-04-13 23:53
文章摘要

《Everything Wrong with MCP》一文讨论了模型上下文协议（MCP）的优缺点，特别是其在集成第三方数据和工具与大型语言模型（LLM）聊天和代理时的应用。MCP允许第三方工具和数据源创建插件，以增强LLM助手的功能，如执行非文本操作。尽管该协议提供了强大的扩展性和灵活性，但也存在一些安全和设计问题。 主要问题包括： 1. **协议安全性**：初始版本缺乏认证机制，导致各服务器自行实现，安全性参差不齐。虽然后续版本尝试加入认证，但使问题变得复杂。 2. **本地运行风险**：MCP服务器可以在本地通过stdio运行，降低了使用HTTP服务器的门槛。然而，这也使得用户容易在不知情的情况下下载并运行恶意代码，增加被攻击的风险。 此外，文章还比较了MCP与其他标准（如ChatGPT插件、Alexa/Google Assistant SDKs、SOAP/REST/GraphQL）的异同，强调了MCP在LLM和助手无关性方面的独特设计。总体而言，MCP在带来便利的同时，也需注意其潜在的安全隐患和复杂性。

评论摘要
主要讨论点：MCP（Model Context Protocol）的当前状态、应用场景、安全性以及未来发展前景。 不同观点： • **支持与开放态度**：dend认为MCP尚在早期阶段，虽然还有很多待解决的问题，但赞赏Anthropic对社区反馈的开放态度。RFC由多个安全专家和公司合作完成，未来会更加成熟。 • **对MCP应用范围的质疑**：jascha_eng认为，当前的专用应用（如Cursor或Claude code）已经满足需求，MCP仅在用户面向的聊天代理中有用，整体应用范围有限。 • **MCP功能与责任的界定**：EigenLord认为MCP只是一个外部资源交互的“入口”，不应承担过多的责任，如数据安全和成本控制等，这些问题应由开发者自行管理。 • **技术实现与实际问题**：rcarmo指出MCP可能会导致模型上下文被过多的选项填充，缺乏优先级设定和好的示例，这会浪费tokens并导致模型行为不稳定。 • **MCP的实际效果与成本**：jeswin分享了自己使用MCP服务器（Codebox）的经验，认为这种工作流更有效，但成本较高。 补充讨论： • **MCP的采用与标准化过程**：madrox提到，MCP的简单性可能是其被广泛采用的原因，历史上新标准的成功往往依赖于社区的接受度，而非其初始的完美性。 • **对MCP的困惑**：jwpapi表示不理解为何不直接使用API，而要通过MCP。 • **MCP的安全性担忧**：lbeurerkellner指出，MCP的用户群包括许多缺乏安全最佳实践的非技术用户，因此需要提高安全意识。behnamoh则对从互联网下载小型服务器程序以扩展LLM工具的做法表示不安。 • **MCP的未来与竞争**：a3w对MCP的未来持乐观态度，认为其有可能成为最终标准。klntsky则认为MCP在聊天机器人领域是死胡同，因为有更多需要动态调整工具的场景。 • **MCP的快速推出与成熟度**：israrkhan认为MCP推出过快，还需要时间和进一步的版本升级来成熟，并且缺乏传统标准机构的审查。 争议焦点： • MCP的实际应用价值和范围：一方认为MCP为用户提供了与LLM交互的入口，具有广泛潜力；另一方则认为其应用范围有限，主要局限于用户面向的聊天代理。 • MCP的安全性与开发者责任：部分评论认为MCP不应承担过多安全责任，而应由开发者管理；另一部分则担忧MCP工具的安全风险，特别是非技术用户的潜在隐患。
