主要讨论点：将老旧游戏代码移植到 WebAssembly 的技术挑战与解决方案 不同观点： • **WASM 32位限制的质疑**：thewavelength 质疑为何 WASM 要重复 32 位指针的错误；xydone 指出 memory64 提案已合并，质疑为何还选择 32 位 • **数据序列化方式的争议**：diath 强烈反对直接读写结构体到文件，建议使用正式的序列化器以避免编译器填充差异和安全漏洞；而 hexer303 和原文作者采用了直接内存映射的方式 • **渲染架构选择**：deadbabe 提出是否应该用 WASM 做游戏逻辑、JS 做渲染；DonHopkins 详细分享了 Micropolis 项目中采用 C++ 引擎 + TypeScript/Svelte UI 的混合架构，通过 Embind 桥接实现清晰分离 • **WASM 对 Web 开发的影响**：arcadialeak 认为 WASM 模糊了 Web 和原生编程的界限，有助于 JS 开发者理解底层执行，并可能促进原生 UI 的回归 补充讨论： hexer303 分享了类似移植经验，选择用浏览器原生 API 替代 WASM 音频库；有人指出 Chrome 调试扩展可提供断点和内存监控；unwind 建议改进内存分配代码写法；DonHopkins 详述了使用 Svelte 5 runes、WebGPU 和 Embind 的复杂架构方案；rvz 提醒 C 移植到 WASM 仍会继承 C 的安全漏洞。

评论摘要
