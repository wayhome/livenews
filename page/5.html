Recreation of the 1956 IPL-I version of the Logic Theorist theorem prover

作者: abrax3141 | 评分: 19 | 评论数: 2 | 发布时间: 2026-05-13 01:54
文章摘要

该仓库用 Python 复现1956年首个公开版“逻辑理论机”（Logic Theorist），修复原 IPL-I 代码并提供解释器、运行与结果分析工具，用于按《数学原理》的命题逻辑公理、规则证明定理。

评论摘要
主要讨论点：围绕 David Moews 复活 1956 年原始 Logic Theorist（LT1/LT56）的意义、实现难度及其与后续版本（LT5/LT63）的差异。 不同观点： • 作者高度肯定 David 的工作：他为 1956 年 RAND 报告中的 IPL-I 伪代码写了解释器，并成功运行，使 RetroAI 的时间窗口又向前推进了 8 年，对 AI、Lisp、定理证明史都有价值。 • LT1 被视为更接近 Newell 与 Simon 早期认知理论的高层规格说明：其描述接近他们设想的人类定理证明“认知操作”，而非完整可执行程序。 • 与 LT5 相比，LT1 的“简单”来自历史条件：IPL-I 从未真正实现，当年靠学生甚至家人手工模拟，因此可依赖人类智能处理细节；而 LT5 为真正运行，必须补全大量实现复杂性。 • 实现复杂度差异明显：LT1 约 400 行，而后来 Shaw 为 IPL-V 重写并发表于 1963 年的 LT5 接近 3000 行，说明从理论规格到可执行系统之间存在巨大工程落差。 补充讨论：争议不明显，但核心张力在于“高层认知模型”与“真实可运行程序”之间的差别；作者强调说 LT1 更简单并非贬低 David 的成就。

My Favorite Bugs: Invalid Surrogate Pairs

作者: meysamazad | 评分: 87 | 评论数: 15 | 发布时间: 2026-05-16 12:49
文章摘要

文章讲述作者最喜欢的一个协同编辑器 Bug：在 TipTap/ProseMirror + Yjs 中，插入相邻的特定 emoji 会导致内容停止同步且无报错。原因是某些 emoji 位于 U+FFFF 以上，在 JavaScript UTF-16 中需用代理对表示；底层 CRDT 在错误位置 splice，切断代理对，产生无效字符。文章借此解释 code units、code points、grapheme clusters 的区别，以及 JS 的 `slice()` 如何可能破坏 emoji。

评论摘要
主要讨论点：围绕 Unicode 字符串处理，尤其是 CRDT/编辑器按 code unit、code point 还是 grapheme cluster 切分文本的风险与实践。 不同观点： • 反对按 code unit 操作：认为 CRDT 库在代码单元层处理文本必然出错，可能产生孤立 surrogate、无效 Unicode，JavaScript/Dart 的 substring/slice 都有类似“切半 emoji”问题。 • 对 grapheme cluster 持谨慎态度：有人认为编辑器应按 grapheme 边界切分，避免拆开 emoji；但也有人指出 extended grapheme cluster 随 Unicode 规则变化，并非长期稳定，类比 PostgreSQL 因 collation 变化导致索引损坏。 • code point/scalar 更“技术安全”但不充分：按 Unicode scalar 可避免无效 Unicode，但仍可能产生语义上奇怪的文本；emoji 往往由多个 code point 组成。 • 工具与语言支持差异：有人推荐 Intl.Segmenter、toWellFormed、Swift 的 String、属性测试；也有人提到 Windows 文件名可含无匹配 surrogate、Linux 文件名可含非法 UTF-8，因此出现 WTF-8 保留往返能力。 • 编码假设也会引发 bug：例子包括服务器 LANG 环境变量因 SSH 改变导致 Unicode 输出时好时坏，以及从 Python 移植到 Rust 时改用二进制 regex 反而简化逻辑、避免未知编码问题。 • 有人感叹 Unicode 复杂度过高，甚至提出若字符固定 64 位会更简单；也有人解释历史原因：UCS-2/UTF-16 导致 code unit 与 code point 分裂。 补充讨论：争议焦点在于“字符串 API 是否应默认按 grapheme cluster 操作”。支持者重视用户感知字符完整性，反对者强调稳定性、规范演进和底层语义复杂性。

文章摘要

加州《保护我们的游戏法案》通过众议院拨款委员会，将进入全院表决。法案要求在线游戏停服时退款或提供可离线继续游玩的版本，并提前60天通知。玩家保护组织支持，游戏行业协会则反对，称不符合现代授权与版权现实。

评论摘要
主要讨论点：围绕“在线游戏停服时是否应立法要求通知、退款、开放服务器/离线化能力”，以及该法案可能带来的副作用。 不同观点： • 支持停服保护：有人认为停服前应至少提前60天通知，避免玩家刚购买内容就失效；Clash Mini、PGA Tour 2K21等例子显示，内购或单机内容因服务器关闭而变得无用，消费者损失明显。 • 支持开放服务器或离线补丁：一种“公平方案”是停服时开源服务器代码，或至少允许社区自建服务器；也有人主张更窄的法规，例如强制发布去除联网激活/DRM的终版补丁，便于保存和继续使用。 • 反对或担忧立法过宽：部分评论认为在线游戏运营成本高，尤其涉及审核和服务器维护；若还要退款或承担额外义务，可能让小公司更难生存，甚至使停服拖垮公司。 • 担忧法案反效果：多位评论指出，法案豁免“订阅制游戏”，可能诱导厂商放弃买断制，全面转向订阅、免费游玩、广告或内购模式，以规避义务，反而损害玩家和游戏保存。 • 认为可有较好行业实践：Epic处理Unreal系列停服被举为正面例子：更新主服务器、交给OldUnreal维护、部分免费化；说明不一定要开源，也可通过社区维护和独立服务器延续游戏生命。 • 扩展到更广软件问题：有人认为问题不限于游戏，许多依赖激活服务器或在线服务的软件同样会因停服失效，立法应覆盖更广的数字产品。 补充讨论：争议焦点在于“保护玩家权益”与“增加开发商负担、扭曲商业模式”之间的平衡；具体措施上，开放源码、社区服务器、离线补丁、退款、保证金等方案各有支持与疑虑。
