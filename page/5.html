Pitfalls of Safe Rust

作者: pjmlp | 评分: 143 | 评论数: 12 | 发布时间: 2025-04-04 17:55
文章摘要

本文讨论了Rust中的"安全"不仅仅指内存安全，还需处理其他问题以确保程序健壮性。即便在"安全Rust"中，仍有一些编译器无法检测的陷阱，包括类型转换错误、逻辑错误、使用`unwrap`导致的恐慌、第三方库中的不安全代码和竞争条件等。文章提供了多个避免这些问题的建议，如使用检查算术操作防止整数溢出、避免使用`as`进行数值转换、使用有界类型确保数值合法性、确保无效状态无法表示等。此外，文章还强调了在发布模式下启用溢出检查以增强安全性，并提供了具体实现方法。通过遵循这些建议，开发者可以写出更可靠的Rust代码。

评论摘要
主要讨论点：Rust 编程中的潜在问题和一些具体实现的争议 不同观点： • **关于文章标题和内容的相关性**： - [nerdile] 认为文章标题有误导性，"Safe Rust" 的提法不准确，因为文中提到的问题不仅限于 "Safe Rust"，而且也不是 Rust 独有的问题。建议使用不那么吸引眼球的标题，例如 "Rust pitfalls: Runtime correctness beyond memory safety"。 • **关于类型转换和性能优化**： - [zk4x] 提到文章中列举的潜在问题很客观，但实际情况更复杂。他指出 `as` 类型转换有问题，并建议用 `try_from` 来替代，但也指出在某些类型转换（如 `u64` 到 `f32`）中非常困难。此外，他提到高性能计算（HPC）代码有时需要避免数学检查，并指出 `Result` 和 `Option` 引入的分支会增加性能开销，建议像 IEX 这样的库作为默认选项。 • **关于整数溢出和边界检查的工具**： - [IshKebab] 对 Flux（一种精化类型工具）表示乐观，认为它能在完全形式化验证之前提供一种轻量级的解决方案，但尚未实际使用过。 • **关于显式算术类型**： - [conaclos] 指出文章未提及 `Wrapping` 和 `Saturating` 类型，这些类型可以用于处理溢出和饱和算术。同时，他也提到 `as` 类型转换较为繁琐，推荐使用 `From::from` 替代。 • **关于内存大小计算的陷阱**： - [bennettnate5] 提到 `mem::size_of_val(&T)` 存在的陷阱，指出它可能返回引用的大小而非实际类型的大小，建议使用 `size_of::()`。 • **关于 `Path::join` 的行为争议**： - [Sharlin] 认为 `Path::join` 在处理绝对路径时的行为容易导致错误，建议返回 `Result` 或提供专门的 `absolutize` 方法。 • **关于 `as` 是否是多余的陷阱**： - [woah] 简单提出疑问，是否 `as` 是一个不必要的陷阱。 • **关于内存泄漏问题**： - [thrance] 提到在使用 `Rc` 或 `Arc` 时容易出现循环引用，导致内存泄漏，特别是在闭包和 futures 中。 • **关于溢出是否是真正的问题**： - [forrestthewoods] 认为溢出并不是一个实际问题，Rust 已经将溢出行为从 "未定义" 改为 "定义良好的二进制补码"。 • **关于数组索引和逻辑错误的处理**： - [quotemstr] 认为文章中的一些建议是错误的，尤其是数组索引部分。他指出越界访问通常表明逻辑错误，应该快速失败以避免进一步的问题，而不是用 `try-things` 来掩盖错误。 补充讨论： • **关于 Rust 和 Golang 的比较**： - [sgt] 认为如果目标是编写健壮的软件，Golang 可能比 Rust 更适合，尤其是在服务不中断的情况下。 争议焦点： • 文章标题是否具有误导性，以及 "Safe Rust" 的提法是否准确。 • `as` 类型转换的使用是否应该避免，以及是否有更好的替代方案。 • `Path::join` 在处理绝对路径时的行为是否应该改变。 • 溢出是否是一个实际存在的问题，是否需要对所有数学操作添加检查。 • 是否应该用 `try-things` 来处理数组越界等逻辑错误。

Show HN: I built a Rust crate for running unsafe code safely

作者: braxxox | 评分: 101 | 评论数: 19 | 发布时间: 2025-04-06 13:28
文章摘要

`mem-isolate` 是一个 Rust crate，旨在通过使用 `fork()` 系统调用安全地运行不安全代码。它会在子进程中执行用户提供的函数，确保该函数不会影响父进程的内存状态，实现内存隔离。主要特点包括： 1. **内存纯净性**：即使函数存在内存泄漏或堆碎片化问题，也不会影响主进程。 2. **跨进程通信**：通过管道在父子进程间传递结果，使用序列化（如 `serde`）处理数据。 3. **性能开销**：每次调用引入约 1ms 延迟，适合对内存安全要求高的场景。 4. **系统支持**：仅支持 POSIX 系统（如 Linux, macOS），不支持 Windows 和 WebAssembly。 该工具适用于运行可能导致内存问题的代码，如 FFI 调用或不安全代码，通过隔离确保主程序的稳定性。

评论摘要
主要讨论点：Rust中的内存安全与隔离方法，尤其是在处理不安全代码时的技术和工具选择 不同观点： • woodruffw认为，"safe" Rust不仅仅意味着避免空间内存错误导致的崩溃，还包括空间和时间上的内存安全。仅仅检测那些不会导致异常退出的内存不安全行为是不够的。Rust的安全性比仅仅避免崩溃要强得多。 • nextaccountic提出了一种通过将不安全代码编译为WebAssembly然后再转换为C代码的方法，以实现内存安全。这种方法将原本未定义的行为转换为逻辑错误，避免了内存损坏问题，类似于Firefox中的做法。 • destroycom和Svetlitski指出，在多线程应用中使用fork()存在风险，特别是在fork和exec之间执行的代码需要是异步信号安全的，否则可能导致死锁或内存问题。 • pjmlp主张从一开始就设计多进程应用，使用操作系统IPC和沙箱API，而不是依赖即时的伪沙箱技术，后者可能带来自身的问题。 • wavemode质疑牺牲性能来运行不安全代码的必要性，认为如果可以接受这样的性能损失，那还不如直接使用带有垃圾回收机制的语言。 • djha-skin认为fork()在某些情况下可能成本过高，应谨慎使用这种技术。 • slashdev对需要使用这种复杂技术的情况表示好奇，想知道是哪些糟糕的库或代码导致这种需求。 • TheDong指出，这种方法可能会导致函数行为不符合预期，特别是涉及内部可变性的代码，可能导致不正确的结果。 • null_investor认为，这种技术仅在处理确实无法改进的不安全代码时有用，但频繁使用可能丧失Rust相对于Python或Ruby的性能优势。 • cryptonector建议在处理大内存集的进程时使用vfork()而不是fork()，以提高速度。 • dijit提到在Windows环境下调用Win32 API时面临的内存调试困难，并寻求适合的工具帮助。 • kelnos强调在多线程程序中使用fork()的危险性，建议在crate中添加明确警告。 • corank质疑这种方法是否适用于需要内存可变的代码，例如双向链表的实现。 • jesprenj对使用管道而非共享内存进行通信的原因表示疑问。 补充讨论： - 各种方法的性能权衡，包括fork()的成本与多进程设计的优劣。 - 针对不同操作系统（如Windows和Linux）的特定工具和调试方法。 - 对内存安全和代码纯度的不同需求及其对设计的影响。
