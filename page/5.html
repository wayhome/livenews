Ornith-1.0: Self-scaffolding LLMs for agentic coding

作者: kordlessagain | 评分: 76 | 评论数: 3 | 发布时间: 2026-06-28 17:58
文章摘要

这篇文章介绍了Ornith-1.0，一个专为智能体编码任务设计的开源自我改进模型家族。该系列包含从9B到397B参数的多个版本，基于Gemma 4和Qwen 3.5预训练。 核心创新是自我改进训练框架：模型不仅学习生成解决方案，还学习生成引导解决方案的脚手架（scaffold），通过联合优化两者来发现更好的搜索路径。 性能方面，Ornith-1.0-397B在Terminal-Bench 2.1达到77.5分、SWE-Bench Verified达到82.4分，超越Claude Opus 4.7和同规模开源模型。即使是9B的轻量版本也能匹敌31B-35B规模的大型模型，证明了其在资源受限环境下的强大能力。 训练中采用了三层防护机制来防止奖励欺骗，并使用异步强化学习策略解决长轨迹的离线策略问题。

评论摘要
主要讨论点：关于 Qwen 3.6 MoE 模型在 Agent 任务中的实际表现和训练方法的讨论 不同观点： • **实测表现一般**：SwellJoe 在安全漏洞检测基准测试中发现，该模型仅用基础工具（read/grep/ls）时表现较差，即使加上完整 shell 和 Python 后发现数量翻倍，但整体仍不理想，且不如同为 Qwen 3.6 MoE 的 AgentWorld 版本 • **模型声称值得关注**：Balinares 认为"9B 模型达到 35B 能力"这一声称非常惊人，理应获得更多关注，暗示对官方宣传的性能提升持期待态度 • **训练方法质疑**：nzach 质疑该模型是否只是将"直接回答问题"改为"写代码执行来解答"，如果是这样，可能只是一种高级的提示词优化（prompt optimization），而非真正的模型能力提升 补充讨论：核心争议在于模型的实际效果与宣传声称之间的差距，以及其训练方法的创新性。SwellJoe 的测试数据显示，模型在具备工具创建能力的情况下确实有所改善，但整体表现仍未达到预期水平。

Alan Kay on the meaning of "object-oriented programming" (2003)

作者: sxx0 | 评分: 85 | 评论数: 13 | 发布时间: 2026-06-27 14:49
文章摘要

这篇文章是Alan Kay在2003年7月给Stefan Ram的邮件，阐述了"面向对象编程"的原始含义。Kay在1967年提出这个术语，其核心概念包括： 1. **消息传递**：对象像生物细胞或网络计算机，只能通过消息通信 2. **消除数据**：将数据访问也视为消息 3. **多态性**：每个对象可关联多个代数系统 4. **晚期绑定**：极致的动态绑定 Kay强调，真正的OOP意味着消息传递、状态的本地保护和隐藏，以及极致的晚期绑定。他最初刻意不包含继承机制，且不赞成后来Smalltalk向Simula回归的做法。这与后世流行的"继承、多态、封装"三要素定义有显著差异。

评论摘要
主要讨论点：面向对象编程(OOP)的本质定义和不同实现路径的争议 不同观点： • **历史溯源派**：认为OOP有两大主要血统——Simula和Smalltalk。现代语言实践上更多继承自Simula，但术语和哲学更受Smalltalk影响。Alan Kay的对象观是"像小型计算机一样通过消息通信"，而非简单的类和继承。 • **实用主义派**：强调没有一种编程范式在所有情况下都最优。OOP、函数式编程、过程式编程都可能在合适的规模和问题上表现出色，但也都容易过度使用而变成混乱。关键问题是我们通常无法在程序真正运行并满足需求前就设计好架构。 • **怀疑论者**：质疑OOP的基础理念——将程序模拟为分布式系统是否真的能简化开发。认为这种"通过增加复杂性来实现简化"的承诺本身就存在矛盾，分布式系统并不比集中式系统更简单。 • **原则至上派**：认为"职责分离"和"高内聚、低耦合"才是软件工程的核心，OOP只是建立在此之上的附加约束。好的OOP实现需要清晰到能向9岁儿童解释的架构设计，否则会导致对象间职责模糊和紧耦合。 补充讨论：有人指出Actor模型(如Elixir、Orleans)和微服务架构更接近Kay的原始OOP理念；也有人认为应区分"Kay OOP"和"Java OOP"来澄清哲学理念与语言特性的差异。

The Return of Aspect Oriented Programming

作者: thomaswc | 评分: 71 | 评论数: 23 | 发布时间: 2026-06-25 22:12
文章摘要

这篇文章讨论了编程中需要兼顾的多个关注点（如正确性、效率、安全性、可维护性等共17项），指出程序员需要同时处理所有这些问题的复杂性。文章介绍了面向切面编程（AOP）的理念——由Gregor Kiczales等人在1990年代中期提出，旨在让程序员能够分别专注于各个关注点，而不是在每行代码中同时考虑所有问题。作者认同AOP的核心思想，但对其具体实现机制"连接点模型"（join point model）持批评态度。文章似乎在探讨AOP的回归及其现代意义。

评论摘要
主要讨论点：AOP（面向切面编程）在现代开发中的价值，以及用LLM作为"织入器"生成代码的可行性 不同观点： • **反对AOP实用性**：简单场景省几分钟，复杂场景（如大批量上传、自定义事务）导致周的调试时间。AOP的关注点分离在复杂情况下会崩溃，代码可读性和可维护性下降，运行时调试困难（nmehner, guybedo） • **强烈反对LLM作为织入器**：非确定性过程修改代码是灾难，LLM只能"有时"正确处理会造成混乱（kstenerud, nmehner） • **谨慎支持改进方向**：核心思想有价值但需重新设计——建议创建从头为AOP和LLM设计的新语言，而非修补现有语言。编译时模式匹配（如Micronaut）优于运行时（jerf, amarant） • **为AspectJ辩护**：AspectJ的连接点模型实际上大部分是编译时静态确定的，只有动态残余延迟到运行时。Pointcut的类型安全状态管理能力强大，适合处理7%的横切关注点代码（w10-1） • **认可应用价值**：AOP在Java/.NET生态和特定框架（JEE、Spring）中持续使用，Effect Systems是2026年处理横切关注点的答案（pjmlp, azkalam, whartung） 补充讨论：有人提出LLM可为每个切面生成语法高亮等工具辅助开发，也有人将LLM工作方式称为"aspective coding"但此前不了解AOP。
