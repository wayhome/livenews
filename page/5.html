How We Found 7 TiB of Memory Just Sitting Around

作者: anurag | 评分: 159 | 评论数: 5 | 发布时间: 2025-10-30 18:25
文章摘要

本文讲述了团队在调试大规模Kubernetes集群时发现并解决内存浪费问题的过程。作者团队在运行包含大量命名空间的Kubernetes集群时，发现一些守护进程（如Calico和Vector）会消耗过多内存。通过深入调查，他们发现这些进程需要持续监控命名空间和网络策略，导致内存使用随节点数量线性增长。特别是Vector日志收集服务，通过修改配置使其不再监控命名空间，成功减少了50%的内存使用。这一优化不仅提升了效率，也为类似的大规模集群管理提供了参考。

评论摘要
主要讨论点：[Kubernetes资源使用爆炸性增长的原因及解决方案] 不同观点： • **Kubernetes Operator设计问题** - 观点：Kubernetes Operator的循环协调机制（reconciliation loop）容易导致资源使用爆炸性增长。 - 论据：Operator通过不断列出资源、比较规格并调整集群状态，可能导致级联资源爆炸。 - 例子：Grafana默认配置未使用推荐的日志索引算法，需手动调整以优化读写Pod比例。 • **日志系统资源消耗不合理** - 观点：某些组件（如Vector）的日志处理消耗资源极不合理。 - 论据：一个仅需120GB内存的集群因日志处理消耗了1.2TB内存。 - 争议焦点：这种资源消耗是否在设计时被忽视或低估。 • **Kubernetes标签设计的潜在问题** - 观点：Kubernetes标签（如NS标签）的内存占用问题可能是更深层次的设计缺陷。 - 论据：标签键的空间复杂度为O(logn)或更高，人类友好的键空间增长过快可能导致资源浪费。 - 例子：NodeJS Prometheus客户端通过移除标签名称节省了1/3的CPU和更多内存。 • **性能分析与优化的有效性** - 观点：深入分析和性能优化是解决资源问题的有效手段。 - 论据：通过剖析和优化可以显著减少资源消耗。 补充讨论： - **争议焦点**：是否应从根本上改进Kubernetes的设计（如标签或Operator机制），还是依赖手动优化。 - **潜在解决方案**：探讨是否有一种通用算法可以在保持名称简洁的同时减少空间复杂度。

On Having a Data Object

作者: Theaetetus | 评分: 32 | 评论数: 7 | 发布时间: 2025-10-27 11:52
文章摘要

这篇文章批评了常见的数据对象模式（如ORM），指出其四大问题： 1. 不同场景需要不同对象，强制统一会导致语义混乱； 2. 迫使不同访问模式使用相同实现，造成代码臃肿； 3. 核心类会变得过于庞大且难以维护； 4. 实际增加了系统复杂度而非简化。 作者建议根据具体场景采用更灵活的持久层管理方案，而非盲目遵循这种看似简单实则问题重重的模式。

评论摘要
主要讨论点：[数据对象（如DTOs）与原始数据结构的优缺点比较，以及在何种情况下使用何种方法] 不同观点： • **反对过度使用DTOs** - 作者认为数据对象（如User类）难以捕捉“用户”的本质，因为相关事实的组合爆炸式增长 - 举例：Login方法只需要email和password，但User类可能包含大量无关数据 - 支持使用原始数据结构（如map）而非数据对象，引用Rich Hickey的观点 • **支持选择性使用DTOs** - hexbin010认为DTOs应该在特定场景（如auth）中使用，避免单一DTO用于所有场景 - 举例：创建用户时需要password字段，但查询用户时不应包含该字段 - 承认完全遵循DDD会降低开发速度，需要找到折中方案 • **反对DTOs的过度抽象** - rokkamokka认为DTOs在大型MVC代码库中通常是多余的 - 举例：实际开发中更倾向于直接使用Models，并通过小方法映射到客户端所需格式 - 提到曾简化许多由初级开发者添加的DTOs • **支持灵活的数据访问工具** - oftenwrong建议使用基本数据访问库（如jOOQ）以提高开发效率 - 支持为特定查询创建函数，而非为特定实体类型创建函数 - 认为ORM可以在不合适时跳过使用 补充讨论： - **争议焦点**：是否应该完全遵循DDD原则，以及DTOs的使用是否增加了不必要的复杂性 - **讨论关系**：hexbin010的观点是对作者和rokkamokka观点的折中，oftenwrong则提出了另一种解决方案 - **其他注意点**：新开发者对代码的理解和维护的便利性（reillyse的观点）也是一个重要考虑因素

文章摘要

这篇文章介绍了 `linux-wasm` 项目，旨在构建一个能在 WebAssembly（Wasm）上运行的 Linux 系统。主要内容包括： 1. **项目组成**： - 使用 LLVM、Linux 内核、musl libc 和 BusyBox 等组件，并应用了多个补丁以支持 Wasm 架构。 - LLVM 提供了 clang 和 wasm-ld 工具链。 - Linux 内核增加了 Wasm 架构支持、binfmt 功能和 Web 控制台驱动。 - musl libc 和 BusyBox 也进行了修改以适配 Wasm。 2. **构建与运行**： - 提供了 `linux-wasm.sh` 脚本，用于下载、构建和运行系统。 - 支持在主机或 Docker 容器中构建。 - 构建时会生成 Linux 内核、musl libc、BusyBox 和 initramfs。 3. **运行时环境**： - 提供了一个 JavaScript Wasm 主机示例，用于启动和管理 Wasm 实例。 - Wasm 无 MMU，因此 Linux 需以 NOMMU 模式构建，程序需使用 `-fPIC/-shared` 编译。 4. **Docker 支持**： - 提供两种 Docker 容器：`linux-wasm-base`（基础构建环境）和 `linux-wasm-contained`（隔离构建环境）。 - 可通过 Docker 命令快速搭建开发环境。 该项目为在 Web 上运行 Linux 系统提供了实验性支持，适合开发者探索 Wasm 和 Linux 的结合。
