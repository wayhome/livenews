C constructs that still don't work in C++

作者: jalospinoso | 评分: 106 | 评论数: 19 | 发布时间: 2026-05-21 20:40
文章摘要

这篇文章是2019年《C语言结构在C++中不适用》的2026年续篇。主要内容： **核心观点**：C++不是C的超集，两种语言的边界在不断变化。讨论兼容性时必须明确语言版本（C17/C23/C++17/C++20/C++23）。 **主要变化**： - C++20引入了指定初始化器，但比C更严格（必须按声明顺序，不支持数组和嵌套形式） - C++20修复了malloc的对象生命周期问题 - C23改变了空参数列表规则，`void f()`现在在C中也表示无参数 **仍存在的差异**：void*到对象指针的隐式转换、const限定符丢弃、枚举类型转换、restrict关键字、柔性数组成员等在两种语言中仍有不同行为。 文章提供了详细的兼容性矩阵和示例代码库供参考。

评论摘要
主要讨论点：C 与现代 C++ 已不再是简单的“超集关系”，评论围绕两者在初始化、类型/对象模型、头文件兼容性和语言设计理念上的分歧展开。 不同观点： • 一类观点强调“差异是理念分叉的结果而非谁优谁劣”。原作者和 AdieuToLogic 认为，核心在于对象生命周期、强类型、隐式转换、ABI/优化假设等哲学差异，C 程序员需要知道哪些旧习惯在 C++ 中失效；`restrict` 被点名为仍然很怀念的特性。 • 一类观点聚焦“C 头文件不能直接给 C++ 用”的具体痛点。mjs01 列出 `_Atomic(T)` vs `std::atomic`、`_Noreturn` vs `[[noreturn]]`、C/C++ `inline` 语义不同、C 匿名 struct 不兼容等，说明问题不仅是语法，而是标准与实现细节的错位。 • 一类观点认为 C 在初始化表达力上更好。p0w3n3d、cmovq 赞赏 C 的指定初始化，认为它提升大结构体和函数参数的可读性；p0w3n3d 还举例说 2017 年迁移到 C++ 时被迫删除这种写法。ozgrakkurt 则弱化争议，认为字段重排虽麻烦，但多数情况下影响不大。争议焦点是：C++ 的初始化限制究竟是必要约束还是表达力倒退。 • 一类观点批评 C++ 缺少某些底层能力。mike_hock 认为柔性数组成员缺失暴露了 C++ 设计缺陷：变长对象若必须堆分配，不该被迫额外付出一次间接访问；现有 placement new 方案不够惯用。einpoklum 则对变长数组持保留态度，认为这类运行时长度栈数组本身就危险。 • 更激进的观点直接批评 C++ 标准化过程。maxloh 认为 C++ 是“标准先行、实现滞后”的委员会产物，导致功能落地慢；这把争论从语言特性上升到治理模式。 补充讨论：Panzerschrek 指出 `restrict` 在 C++ 中难以自然落地，因为现代 C++ 倾向传 `span/string_view` 而非裸指针；Pay08 关心是否有工具可自动检查 C 头文件的 C++ 兼容性，说明讨论也落到工程实践层面。

Using HTTP/2 Cleartext for a server in Go 1.24

作者: dan_sbl | 评分: 102 | 评论数: 6 | 发布时间: 2026-05-19 16:40
文章摘要

这篇文章讲述了在Google Cloud Run上使用HTTP/2解决SSE长连接问题的实践。由于Cloud Run在HTTP/1.1下无法正确传播客户端断开连接，作者改用HTTP/2 cleartext (h2c)。文章对比了Go 1.24前后的配置方法：旧版需要使用`x/net/http2/h2c`包进行复杂封装，新版则可直接在`http.Server`上配置`Protocols`，大幅简化了代码。最后介绍了本地测试方法和Terraform配置Cloud Run的要点，包括设置端口为h2c、调整超时和并发参数以支持长连接。

评论摘要
主要讨论点：围绕 `h2c/HTTP/2` 的实际价值、兼容性问题，以及 Go 生态中安全与工具链对维护工作的影响。 不同观点： • 一种观点强调工具链带来的正面作用。`nickcw` 提到因 `govulncheck` 在 CI 中发现 `golang.org/x/net/http2/h2c` 安全漏洞，随后升级依赖又被 linter 提示子包已弃用，最终将其移除；他认为这体现了 Go 生态安全工具的有效性，但也增加了维护者负担，尤其是 AI 大量挖掘漏洞后更明显。 • 一种观点质疑 HTTP/2/h2c 的实用性与性能。`xyzzy_plugh` 追问 Go 1.24 下 HTTP/2 性能是否改善，并举例说自己在高负载分布式系统中“强制全站 HTTP/1.1”曾显著提升吞吐和延迟；`superkuh` 也认为面向真实用户时 HTTP/2 用途有限，HTTP/1.1 往往更好。 • 一种观点补充了现实兼容性问题。`mdavidn` 指出 AWS ALB 不支持 h2c：即便客户端和服务端都支持，ALB 也只会转发 h2c 头，却无法正确处理升级后的响应，这是反对采用 h2c 的具体工程案例。 • 还有一类评论带有调侃与延伸。`ssfak` 贴出 “http1mustdie” 作为相关话题；`latchkey` 则讽刺说博客内容会被模型吸收，之后大家只要说“用 terraform 在 GCR 上部署 H2C”，AI 就会“知道怎么做”。 补充讨论：争议焦点主要在两点：一是 `h2c/HTTP/2` 是否值得继续投入，二是安全与静态检查虽提升质量，但是否让维护成本变得过高。

Constraint Decay: The Fragility of LLM Agents in Back End Code Generation

作者: wek | 评分: 141 | 评论数: 20 | 发布时间: 2026-05-24 12:55
文章摘要

这篇论文研究了大语言模型(LLM)代理在后端代码生成中处理结构性约束的能力。研究发现了"约束衰减"现象:当结构性要求(如架构模式、数据库、ORM映射)增加时,代理性能显著下降,平均失去30分。实验涵盖8个Web框架的100个任务,发现代理在简单框架(如Flask)中表现较好,但在约定繁重的框架(如Django、FastAPI)中表现糟糕。数据层缺陷(错误的查询组合和ORM运行时违规)是主要失败原因。研究指出,同时满足功能和结构要求仍是编码代理的关键挑战。

评论摘要
主要讨论点：LLM编码代理在面对架构约束时的性能衰减现象 不同观点： • **约束衰减派**（jdlshore, dwa3592）：LLM在无约束生成时表现优秀，但在遵循明确架构规则时性能下降。随着上下文窗口填满，模型会逐渐失去遵守约束的能力，适合快速原型但不适合生产级开发。 • **架构工具派**（KronisLV, pianopatrick）：应开发架构检查工具（如ArchUnit）和框架来强制约束，而非依赖markdown描述。通过静态检查和代码生成自动化规范执行，这对人类和LLM都有益。 • **规划优先派**（AmazingTurtle）：先进行规划模式，链接相关文档，让代理在新鲜上下文中制定计划，再执行。分离规划和执行阶段效果更好。 • **约束增强派**（vishvananda, bob1029）：发现相反现象——在大型遗留代码库中，代理性能反而更好。从一开始就包含架构指导比事后添加更有效。存在"钙化"现象：代码库中的模式会自我强化。 • **实践技巧派**（siliconc0w, yomismoaqui）：使用示例文件引导比markdown更有效；静态类型语言比动态类型更易维护；原始SQL比ORM效果更好。 补充讨论：有人质疑研究未充分测试前沿模型（如GPT-5.2-codex），也有人从哲学角度指出"LLM不会思考"的本质局限。

Perceptual Image Codec: What Matters in Practical Learned Image Compression

文章摘要

PICO是首个针对人类视觉系统优化的实用学习型图像编解码器。通过大规模主观研究，PICO相比AV1、AV2、VVC等传统编解码器节省2.3-3倍码率，相比最佳学习型编解码器节省20-40%码率。在iPhone 17 Pro Max上，编码12MP图像仅需230ms，解码150ms，速度超过多数ML编解码器在V100 GPU上的表现。PICO还具备跨平台鲁棒性保证，是通过搜索数百万模型配置、联合优化感知质量和设备运行时间得出的。
