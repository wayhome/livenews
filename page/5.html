Next.js version 15.2.3 has been released to address a security vulnerability

作者: makepanic | 评分: 123 | 评论数: 22 | 发布时间: 2025-03-22 21:19
文章摘要

Next.js发布了15.2.3版本，以修复一个安全漏洞（CVE-2025-29927）。该漏洞涉及内部头字段`x-middleware-subrequest`，可能导致中间件被跳过，从而绕过关键安全检查，如授权验证。自托管的Next.js应用，特别是使用`next start`和输出为"standalone"的应用，需立即更新。受影响的版本包括15.x、14.x和13.x，补丁已发布。若无法立即更新，建议阻止包含`x-middleware-subrequest`头的外部请求。Cloudflare用户可启用WAF规则防护，而Vercel和Netlify托管的应用不受影响。Next.js团队还将发布针对v12的补丁，并计划改进与合作伙伴的沟通，开设了伙伴邮件列表。

评论摘要
主要讨论点：Next.js 中间件漏洞及其安全性和设计问题 不同观点： • **ratorx** 认为，Next.js 的中间件设计存在根本性缺陷，尤其是中间件与用户输入使用相同机制进行通信，这使得用户请求验证和中间件代码分离。此外，允许除白名单外的任何头部信息通过，这像是潜在的安全隐患。同时，ratorx 质疑框架为不好的服务器设计提供支持，并提出是否存在不适用有向无环图 (DAG) 请求流程的具体用例。 • **smlx** 提到 Next.js 有类似的漏洞历史，指出之前通过添加特定头部可以导致服务器端请求伪造 (SSRF) 的问题。他还批评 Next.js 的补丁发布策略不透明，尤其是对旧版本的支持问题，并认为使用 Next.js 对于重视安全和维护的项目来说风险很大。 • **ronbenton** 关注漏洞报告后的处理时间，质疑为何该安全问题在报告后两周才开始处理，并表达了对认证可被轻易绕过的担忧。 • **mikeocool** 认为 Next.js 增加了前端开发的复杂性，但对大多数应用来说价值有限。他特别指出文件路由和服务器端渲染在一些场景下可能有用，但对于多数应用来说，复杂性远超其带来的价值。 • **makepanic** 引用了官方对漏洞的描述，指出 Next.js 内部使用 `x-middleware-subrequest` 头来防止递归请求，但该机制被绕过可能导致请求跳过关键检查，例如授权验证。 • **dvektor** 和 **urbandw311er** 都表示对 Next.js 的安全性感到不安，dvektor 明确表示不会使用 Next.js，而 urbandw311er 则对自己团队选择自托管 Next.js 感到不安。 • **butterlettuce** 和 **ramoz** 都对 Vercel 和 Next.js 的声誉提出批评，ramoz 还提到希望其他框架（如 Remix 和 TanStack）能发出质量信号并改变方向。 • **ashishb** 认为 Next.js 的基础前提有缺陷，即在浏览器和后端运行相同的代码，这导致安全态势不同。他主张前端和后端应分离，以保持后端的信任和安全性。 补充讨论： • 争议焦点在于 Next.js 的中间件设计是否存在根本性安全缺陷，以及其漏洞响应速度是否足够快。 • 另一个讨论点是 Next.js 是否适合用于对安全性和维护要求高的项目，例如政府或大公司。 • 对 Vercel 和 Next.js 声誉的批评也是一个值得注意的讨论点。

文章摘要

这篇文章讨论了如何对一个变换 \(T\) 进行平滑插值，从而使点 \(x\) 从初始位置逐渐移动到由 \(T\) 变换后的位置。具体方法是使用变换的指数和对数函数来计算随时间变化的变换 \(T(t)\)，公式为 \(x(t) = e^{\log(T) \cdot t} \cdot x(0)\)。这里，\(\log(T)\) 表示变换的速率（或切向量场），它描述了每个点在空间中的速度。通过这个方法，可以在任意时间 \(t\) 计算点 \(x\) 的位置及其速度（即 \(\log(T) \cdot x(t)\)）。文章还提供了一个交互式示例和代码实现，展示了如何利用变换的指数和对数来计算插值变换和速度向量场。
