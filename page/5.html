评论摘要
主要讨论点：webhook和API请求的安全性、认证机制及其实现方式 不同观点： • erikerikson：认为webhook调用通过签名验证来源，并且依赖于安全连接和证书验证。将认证转移到webhook实现者会导致需要处理多种认证系统，增加复杂性。 • maxwellg：倾向于使用HMAC，但承认API密钥对用户更简单，特别是在命令行使用和维护客户端库时。工具的进步也使得日志配置更加安全。 • btown：建议不要完全信任webhook，应采用异步重处理和设置标志的方式，以应对顺序错乱和重复请求等问题，从而降低签名验证的重要性。 • paradox460：对缺乏授权机制的webhook感到不满，认为像Stripe和Twilio那样使用签名验证是更好的做法，甚至可以接受HTTP基本认证。 • eqvinox：批评文章未深入考虑安全需求，认为API密钥机制不适合webhook，因为webhook是“API访问你”而不是你请求事件。建议使用额外的加密层来增强安全性。 • arkh、Retr0id：关注实现细节，如防止定时攻击，确保验证函数的 cryptographically sound。 • skybrian：解释了webhook中公钥分发的问题，认为API密钥在客户与供应商的单对多通信中更合适。 • slt2021：建议使用mTLS（或带有客户端证书的TLS）来验证调用者。 • arccy：认为请求签名在安全性上更好，但开发人员往往不愿意实现复杂的安全措施。 • kaoD：对TLS客户端证书不为人知和被忽视感到遗憾。 • h1fra：指出webhook需要验证来源和真实性，而API密钥用于验证请求者身份。 • michaelt：提到使用签名请求的API通常提供现成的库，接收方可以根据需要选择是否验证签名。 • olehif：指出签名允许服务器为所有客户端使用一个证书，而API密钥需要为每个客户端提供唯一密钥，签名更方便。 • felipemesquita：认为API请求已经过认证，签名带来的额外安全性有限，而webhook由于可能被未经认证的来源发送，因此需要签名验证。 补充讨论： • 关于HMAC和API密钥的易用性和安全性讨论。 • 关于使用TLS和mTLS的优缺点。 • 关于防止定时攻击和确保加密实现安全性的技术细节。 • 关于公钥分发和认证机制在不同场景中的适用性。 • 关于签名验证在webhook中的必要性和实现方式的争议。 • 关于API请求和webhook请求在认证和安全性上的差异和处理方式的不同观点。

Jujutsu UI (jjui) 是一个为 Jujutsu 版本控制系统设计的终端用户界面（TUI）。它支持通过自动补全更改 revset、 rebase 操作、修订版本的压缩（squash）、查看修订详情、移动书签、操作日志查看等功能。用户可以通过快捷键进行多种操作，如分割、恢复、编辑文件或修订，查看 diff，以及进行 Git 推送/获取等。安装方式包括通过 Homebrew、Archlinux、Nix、go install 或从源码构建。最低支持的 Jujutsu 版本为 v0.21，项目采用 MIT 许可证，并欢迎贡献。

文章摘要

本文揭示了GitLab Duo中的远程提示注入漏洞，该漏洞可被利用窃取私有源代码并注入不安全的HTML内容。GitLab Duo是集成在GitLab中的AI助手，旨在帮助开发者进行代码建议、安全审查等任务。研究团队发现，通过在合并请求、提交信息、问题描述及源代码中嵌入隐藏提示，可以操纵Duo的行为，导致其泄露私有项目源代码，甚至操纵代码建议以包含恶意JavaScript包或展示虚假安全链接。漏洞利用还涉及HTML注入，攻击者可通过注入恶意HTML控制页面部分内容，触发自动HTTP请求。GitLab已修复该问题，文章详细解析了整个攻击链及五个与2025年OWASP Top 10 for LLMs相关的漏洞。
