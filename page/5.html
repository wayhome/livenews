Fun with IP Address Parsing

文章摘要

本文讨论了编写IPv4和IPv6地址解析器的复杂性，特别是处理各种“诡异”的表示形式。作者首先介绍了IPv4和IPv6的标准格式：IPv4采用点分十进制，而IPv6采用冒号分隔的十六进制表示。然而，IPv6允许使用`::`来省略连续的零块，导致多种可能的形式，例如`1:2::3:4`实际代表`1:2:0:0:0:0:3:4`。 更复杂的是，IPv6还可以在末尾使用点分十进制的IPv4地址，例如`1:2:3:4:5:6:77.77.88.88`。此外，IPv4地址有多种历史遗留的表示方式，例如将地址视为一个32位整数（如`3232271615`代表`192.168.140.255`），或使用八进制和十六进制表示。 最后，作者提到处理IPv4和IPv6地址时，需要面对前导零和不同解析方式带来的不确定性，这使得编写一个完全正确的解析器变得相当复杂。

评论摘要
主要讨论点：不同解析器对八进制和十进制数值的处理及其潜在的安全风险 不同观点： • [o11c] 认为，现存的一些支持八进制的解析器将0前缀的地址视为八进制，而不是十进制，这会产生不同的有效值，因此是一个安全漏洞。他强调，接受0前缀地址为十进制数存在安全隐患，建议对其他类似情况也采取更严格的处理方式以避免潜在风险。 • [dan_linder] 则关注某些系统（如防火墙）在处理这些数值时的反应，特别是担心防火墙在遇到非预期数据时是否会默认关闭（fail closed），以阻止意外流量。他还提出了防火墙的GUI与底层数据处理是否一致的问题，暗示可能存在界面显示与实际处理不一致的情况。 补充讨论： • [o11c] 强调了潜在的安全问题，尤其是解析器在处理0前缀数值时可能导致的错误解析和安全隐患。 • [dan_linder] 则更关注系统在异常情况下的行为，特别是防火墙等安全设备在遇到此类问题时的反应，是否会导致安全漏洞。 • 争议的焦点在于0前缀数值的处理方式及其在不同系统中可能引发的安全性和稳定性问题。

UIT – performant, modular, low-memory file processing at scale, in the Cloud

作者: janwilmake | 评分: 25 | 评论数: 3 | 发布时间: 2025-04-25 14:31
文章摘要
