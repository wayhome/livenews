文章摘要

Google Chrome即将移除Manifest V2扩展支持，这标志着uBlock Origin等流行广告拦截器的终结。Chrome 150版本（6月30日发布）将移除允许继续使用V2扩展的技术漏洞标志，Chrome 151版本（7月发布）将彻底清除所有相关代码。此举源于Google多年前启动的Manifest V3迁移计划，官方称V2存在安全风险和技术债务。其他基于Chromium的浏览器如Edge和Opera可能也会跟进，但可以选择继续支持V2扩展。

评论摘要
主要讨论点：Google Chrome禁用Manifest V2扩展，影响广告拦截器的有效性 不同观点： • **支持Firefox阵营**：认为Firefox是唯一理性选择，虽不完美但好于替代品。强调Mozilla维护着开放互联网，批评Chrome本质是间谍软件，呼吁用户立即切换到Firefox • **对MV3持乐观态度**：部分用户表示uBlock Origin Lite（MV3版本）使用体验良好，运行数年没有问题。Google员工辩称此举是为了安全性和隐私，与Safari的做法一致，防止恶意扩展抓取信息 • **对Google策略的批判**：认为这是Google的长期战略——先用巨额工程投入吸引用户，待竞争对手消失后逐步将浏览器变成间谍软件。警告下一步可能让网站只在Chrome上运行，"温水煮青蛙" • **替代方案建议**：推荐使用DNS级别的广告/跟踪拦截器，可在VPS上通过Tailscale运行。也有用户使用Orion配合Kagi搜索 补充讨论：有人呼吁从零开始构建将网络视为"最敌对生态系统"的浏览器，内置强大拦截功能。另有评论指出标题具误导性，热门广告拦截器已切换到MV3，MV2已对所有用户禁用。还有人提到这是Google多年前就宣布的计划，只是等风波平息后再推进。

Iroh 1.0

作者: chadfowler | 评分: 579 | 评论数: 51 | 发布时间: 2026-06-15 15:13
文章摘要

iroh 1.0 正式发布，这是一个基于"密钥拨号"而非 IP 地址的网络连接库。核心理念是用设备自主控制的密钥替代易变的 IP 地址，实现安全的点对点连接。主要特性包括：基于 QUIC 的多路径连接、NAT 穿透、本地优先配置、支持浏览器 WASM 运行，以及可插拔的自定义传输层（如蓝牙、LoRa）。1.0 版本保证线协议和 API 的稳定性，新增 Python、Node.js、Swift、Kotlin 官方支持。项目已在数百万设备上运行，过去 30 天创建超 2 亿个端点，95% 的数据直接在设备间传输，大幅降低云端流量成本。公告同时发布了主要版本支持政策和公共中继服务器的维护时间表。

评论摘要
主要讨论点：Iroh v1.0 发布后，关于其定位、市场竞争力和应用场景的多角度讨论 不同观点： • **积极使用者**：多位用户（colinmarc, arilotter）在生产环境使用 Iroh，称赞其作为"Rust crate 的 Tailscale 式打洞"功能优秀，团队响应迅速，优于 libp2p • **质疑市场定位**：himata4113 认为这更像"待售的中继网络"，市场已被 Steam P2P 和 Tailscale 主导，难找到市场契合点 • **困惑其必要性**：Thaxll 质疑基本问题，认为 IP/DNS/IPv6/QUIC 已足够，需要供应商和主流软件支持才能获得牵引力 • **商业模式疑虑**：j4cobgarby 认为类似 IP 地址功能的协议收费很奇怪 补充讨论： 技术特性方面，开发者 rklaehn 强调自定义传输能力（支持 Tor/Nym/BLE）；多人提出与 Tailscale/Netbird 等方案对比需求（kkapelon 建议增加对比页面）；应用场景探讨包括审查规避（openscript）、Agent 间通信（ramoz）、分布式 ML 训练、VPN 实现等。overgard 提出 IPv6 本应解决此类问题的疑问。整体显示产品获技术认可但市场差异化仍需阐明。

作者在求职面试中发现，与五年前相比，现在几乎所有公司都在使用Kubernetes，即使是小型创业公司也不例外。通过与CTO们交流，作者发现他们采用K8s主要不是出于技术原因，而是看重三大组织优势：**统一性**（所有服务部署方式一致）、**标准化知识**（K8s成为通用技能，便于招聘和知识传承）、**可追溯性**（结合GitOps实现合规审计）。作者认为这种选择合理，但建议公司在第二名工程师加入时再引入K8s，因为此时团队协作、权限管理和知识传承的需求才真正显现。作者好奇为何K8s在最近几年突然主导市场，推测是托管服务成熟和人才池转变所致。

评论摘要
主要讨论点：小型团队/初创公司是否应该采用 Kubernetes 不同观点： • **反对过早采用**：mikeocool 指出 K8s 维护成本高（需安装多个控制器、频繁升级、引入不必要的网络复杂度），认为市场缺乏简单的容器部署方案。clickety_clack 认为在招第二个工程师时就用 K8s 是危险信号，说明 CTO 优先级错误。 • **支持适度使用**：liampulles 认同 K8s 核心 20% 功能（Deployment/Service 管理）配合云托管集群对小团队有价值，但警告不要陷入过度复杂化（如 DB operator、build operator）。johnsmith1840 强调容器化的必要性，K8s 是自然延伸。 • **支持全面采用**：xlii 认为有了 AI/LLM 生成配置文件后，K8s 在开发环境的使用成本大幅降低。mikgp 和 JohnMakin 指出托管 K8s 已成熟，比传统 VM+systemd 方案更便捷。reillyse 强调 AI agents 使 DevOps 工作变简单。 • **中立观察**：SamuelAdams 认为这更关乎基础设施即代码理念，而非 K8s 本身。mianos 指出"简历驱动开发"现象——为吸引人才而采用 K8s。 补充讨论：多人提到 YAML 复杂性、升级频率高（每 3-6 个月）、API 变更（如从 Ingress 迁移到 Gateway API）等痛点。Glyptodon 指出 K8s 和手动部署之间一直存在空白地带。
