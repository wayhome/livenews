Tesla Wall Connector bootloader bypasses the firmware downgrade ratchet

文章摘要

文章分析特斯拉Wall Connector Gen 3在24.44.3固件中新增的防降级机制：通过固件ratchet值拒绝旧版本。作者逆向发现bootloader不检查ratchet，仅更新流程检查；进一步利用分区表写入与擦除顺序缺陷绕过限制，使最新版设备仍可刷入旧漏洞固件并复现攻击。

评论摘要
主要讨论点：Tesla Gen 3 Wall Connector 的联网、固件控制与充电调度可靠性，以及其对用户成本和电网的影响。 不同观点： • 原帖观点：Wall Connector 一旦丢失 Wi‑Fi，可能导致充电计划失效、随机开关，尤其会影响分时电价用户；建议直接在车端设置充电定时，而不是依赖墙充。 • 反感 Gen 3 Wall Connector：有人批评其会持续创建无法关闭的 Wi‑Fi 热点（TeslaWallConnector_唯一ID），认为用户失去对设备的控制；还提到过去可降级固件绕过此问题，但可能已被 Tesla 封堵，并担心车辆可能通过充电线或 Wi‑Fi 强制更新墙充固件。 • 质疑购买必要性：有人认为直接使用 NEMA/烘干机插座加 Tesla 随车充即可，Wall Connector 像是“花钱买麻烦”，性价比不足。 • “降级固件不是黑客行为”观点：有人强调，车主主动降级固件以控制自己硬件不应被称为 hack；若攻击者能这么做，说明物理安全早已被突破。 • 安全与电网风险观点：有人担心 EV 充电器软件若被用户、黑客或 bug 修改，可能在电网不适合的时段满功率充电。以英国为例，1000万台 EV 每台 7kW 会接近/超过电网承载，甚至100万台同时充电也会增加约7GW负荷。 补充讨论：争议焦点集中在用户是否应拥有固件控制权、联网墙充是否必要，以及“个人设备自由”与“电网安全/集中管理”之间的冲突。

Mullvad exit IPs are surprisingly identifying

作者: RGBCube | 评分: 372 | 评论数: 24 | 发布时间: 2026-05-15 02:35
文章摘要

文章指出 Mullvad VPN 会按 WireGuard 公钥确定性分配服务器出口 IP，而非每次随机。作者测试 9 台服务器、3650 个公钥后发现，理论上组合巨大，实际仅出现 284 种。原因可能是 Mullvad 用公钥作种子调用 RNG，并以各服务器 IP 池大小为上限，导致不同服务器分配到相近百分位的 IP。这样多个出口 IP 组合可能成为识别用户的指纹风险。

评论摘要
主要讨论点：Mullvad 被曝不同服务器出口 IP 分配存在可关联性，可能形成用户级指纹；讨论集中在其严重性、VPN匿名预期、修复与披露流程。 不同观点： • Mullvad回应：部分行为是有意设计、部分不是；成因与原文描述不完全一致，已在部分基础设施测试补丁，并会重新评估“隐私 vs 用户体验”的取舍；同时呼吁研究者发布前先通知厂商。 • 风险严重派：认为这种跨服务器稳定映射像“情报机构会设计的VPN”，可帮助论坛管理员识别封禁用户小号；元数据仍会泄露身份。 • 质疑论证派：有人指出“>99%同一人”的说法统计上不严谨；重叠区间只能排除大多数用户，不能直接得出个体识别准确率。 • VPN定位派：认为VPN本就不等同Tor，不应期待对访问网站匿名；需要强匿名应使用Tor，且Tor也可能被出口节点攻击。 • 工程折中派：单服务器内稳定IP有用户体验价值，例如固定服务可用性；但跨服务器相关性应修复，如用 user key + server id 随机化。 • 信任Mullvad派：有评论称Mullvad过往在地理定位数据上较诚实，相信会修复。 • 站点治理派：有人认为网站运营者可利用此属性执行封禁；也有人提到持续维护VPN IP封锁列表，服务方与用户之间是“猫鼠游戏”。 补充讨论：有人追问作者是否提前联系Mullvad；还有人疑惑第三方客户端为何不能像官方客户端一样轮换WireGuard key。

英国住房部门称，已用内部专家自建系统取代Palantir为“乌克兰之家”难民安置计划提供的Foundry系统，每年节省数百万英镑，并提升灵活性、数据与代码控制。Palantir曾快速搭建系统并支持15.7万难民安置，但其低价切入后获高额合同引发采购、公私依赖及数据使用争议。

评论摘要
主要讨论点：英国政府/公共部门是否应使用 Palantir，尤其是在难民安置、NHS 数据与公共服务系统中的成本、能力、伦理和数据主权问题。 不同观点： • 反对 Palantir：多名评论认为其“邪恶”、不可信，涉及情报背景、垄断倾向、游说和“旋转门”利益输送；担心政府和 NHS 将敏感数据交给美国公司，形成供应商锁定。 • 成本与能力质疑：有人指出 Palantir 很贵，本质是咨询+定制交付；短期应急可能有用，但长期应由政府培养内部技术团队、改造数据系统，自建平台更便宜可控。 • 支持/理解阶段性使用：也有人认为，乌克兰难民项目初期需要“几天内上线”，免费试用和后续小额合同在数十亿项目总成本中不算大；之后转向自研、降低长期成本是合理路径。 • 政府自研能力观点：评论称签证、住宿匹配、数据整合是 GDS/DDAT 常做的标准工作，开源、按现有标准建设即可；尤其难民住宿匹配更像普通 CRUD/Web 应用，不应交给 Palantir。 • NHS 争议更大：有人提到 NHS 合同约 3 亿英镑，公众和 GP 不支持；另有人曾参与“数据不出公司、只输出研究结果”的英国本土方案，却输给 Palantir，认为不合理。 • 更广泛风险：有评论担心 Palantir 已进入驱逐、警务、军事目标、医疗数据等 operational decision，AI 建议可能让“人在环中”变成橡皮图章，责任链断裂。 补充讨论：有人指出实际乌克兰家庭匹配多通过 Facebook 群完成；另有少数评论认为 NHS/福利领域引入 Palantir可能是政府想绕开同情病假者的公务员体系，强制削减长期病假福利，这也是争议焦点之一。
