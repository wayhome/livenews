TODOs Aren't for Doing

作者: todsacerdoti | 评分: 140 | 评论数: 35 | 发布时间: 2025-07-22 13:43
文章摘要

本文讨论了代码中TODO注释的价值，认为并非所有TODO都需要完成或跟踪。一些团队要求将每个TODO记录在错误追踪系统中，或删除长期未处理的TODO，但作者认为这不必要。TODO注释的价值在于记录边缘情况、代码改进建议或作者当时的思路，而不是必须执行的任务。例如，标记用户三次点击按钮导致的错误，可能并非最高优先级，但能帮助未来读者理解代码背景，避免误解或不必要的更改。因此，TODO更多是提供背景信息，而非待办事项。

评论摘要
主要讨论点：TODO注释的使用及其在代码中的作用 不同观点： • kstrauser认为，TODO应该只用于可操作的任务，而不应包含非行动项。将非行动项标记为TODO会增加心理负担，并可能导致无效的讨论。他建议使用其他类型的注释（如NOTE）来记录非行动项。 • nevermore提出，TODO应始终指向一个具体的问题，并给出三种解决TODO的方法：提交问题、立即解决或将其转换为普通注释。 • pisipisipisi支持使用多种标签（FIXME, XXX, TODO, NOTE）来区分不同优先级和类型的注释，特别是在处理旧代码库时。 • mcntsh认为，虽然理想情况下技术债务应被更好地跟踪，但TODO注释至少提供了一种低摩擦的跟踪方式，比完全不跟踪要好。 • basfo指出，TODO应指向具体的行动，而不是仅仅记录问题。TODO经常被用来让代码快速通过审查，但后续很少被解决。 • happytoexplain认为，应该有一个空间来记录已知的、可能不值得修复的问题，且不应将TODO视为代码异味。 • pamelafox的个人哲学是，TODO应仅在分支工作时使用，在准备合并请求时应解决或记录在问题跟踪器中。 • Tokumei-no-hito推荐使用工具（如todo tree）来管理TODO注释，以提高个人和团队的工作效率。 • allthedatas使用分层策略，FIXME用于必须修复的问题，TODO用于可能不成熟的想法或等待其他事情完成的任务。 • ngruhn认为，TODO可以作为一种传递信息的方式，为下一个接触代码的人提供有用的信息，即使没有具体任务也具有价值。 • owlstuffing建议将非行动项TODO替换为NOTE，以避免干扰代码阅读和重构过程。 • it_citizen质疑某些TODO是否只是普通注释，而非真正的待办事项。 • rglover强调一致的注释标签（TODO和NOTE）对于任务跟踪和代码解释的重要性。 • escobar_west要求更明确地定义TODO注释与普通注释的区别。 • kamens欣赏TODO方法的精神释放作用，特别是在处理不打算立即解决的边缘情况时。 补充讨论： • 争议焦点在于TODO注释的定义和用途。一些人认为TODO应仅用于具体的、可操作的任务，而另一些人则认为TODO可以用于记录一般性信息和提醒。 • 使用工具（如todo tree）来管理TODO注释的建议被提出，以提高工作效率和团队协作。 • 不同开发者在处理TODO注释时有不同的策略，如使用多种标签（FIXME, XXX, TODO, NOTE）来区分优先级和类型。 • 讨论中多次提到心理负担和任务管理的问题，表明这是一个对开发者实际工作有重要影响的主题。

The benefits of trunk-based development

作者: gpi | 评分: 36 | 评论数: 20 | 发布时间: 2025-07-23 04:50
文章摘要

文章主要讨论了基于主干开发（trunk-based development）的优势，并认为它是优于功能分支开发的交付方式。尽管持续集成实践隐含了基于主干开发，但这一方法仍存在争议。文章指出，微软、Netflix、谷歌等公司均采用基于主干开发，甚至在谷歌的大规模开发中也是如此。 基于主干开发通过促进团队协作和集体代码所有权，提升了代码质量。它减少了低信任环境，创建了安全空间，避免指责个人，而是团队共同负责质量。频繁提交代码到主线，能够更早发现和解决问题，从而内建质量，而不是后期测试。 该方法还支持按需生产发布，减少上市时间，提高交付速度。更频繁的部署加速了反馈，提升了用户满意度，并减少了在制品（WIP），从而降低了开发周期时间。文章总结，基于主干开发不仅提升了技术质量，还创造了经济优势。

评论摘要
主要讨论点： trunk-based development（主干开发模式）与 feature branch（功能分支）以及 Pull Request（PR）模型的优劣对比 不同观点： • JimDabell 认为 PR 不仅仅关乎信任问题，它还是团队学习和共享知识的有效方式。他还指出，虽然 PR 有助于验证外部贡献，但在闭源企业环境中，PR 模式可能导致团队对代码库贡献受限。 • zabil 不完全赞同 trunk-based 开发，尤其是在远程团队的情况下，代码质量难以保持。他认为 PR 提供了很好的上下文分享和代码检查机会，并且 stacked diffs 使得多重 PR 管理变得可行。 • crinkly 对各种绝对的方法论持怀疑态度，认为团队的问题更多源于人员素质和公司雇佣低成本外包，而非开发流程本身。他所在的团队采用简单的主干开发模式，并保持高效运作。 • stpedgwdgfghd 强调在加入非 trivial 代码时，团队审查的重要性，并指出 MR（合并请求）在确保代码质量和避免系统测试失败方面具有优势。不过他也认为长期分支应尽量避免。 • jFriedensreich 支持 trunk-based 开发结合 commit stack 工作流，认为这种方法可以在不牺牲质量的情况下保持高效，尤其是在代码成熟和审查方面。 • devjab 坚定支持 trunk-based 开发，认为功能分支和定期发布是缺乏信任的表现，而 trunk-based 开发要求团队具备更高的协作能力。 • oc1 指出开发模式的演变，从早期的 trunk-based 开发到 git 和 github 兴起后的功能分支模式，认为两种模式各有优缺点，具体选择应视团队情况而定。 • fjfaase 分享了自己在 trunk-based 开发中的积极经验，同时指出功能分支开发带来的延迟和质量问题。 • safety1st 认为 trunk-based 开发适用于特定类型的项目，如 web 应用开发，而对于高要求的软件如飞行控制系统则不适合。 • Frieren 提到代码审查早在 PR 出现之前就已经存在，并认为今天的开发者可能忽视了软件工程的历史。 • Ozzie_osman 对极端的 trunk-based 开发表示怀疑，认为 PR 和代码审查在安全和合规方面具有重要作用，同时指出在现代开发中完全不使用分支是不现实的。 • ozim 对 trunk-based 开发的优越性表示怀疑，认为需要更多具体数据和团队动态分析来验证其效果。 • bytefish 强调开发流程的选择应根据产品、团队和组织结构而定，trunk-based 开发并非适用于所有情况。 • bjornsing 对 Google 无功能分支的说法表示怀疑，并质疑无 PR 的代码审查如何进行。 • bob1029 指出在集中式模型如 perforce 下，团队在同一物理办公室工作时效率更高，而 git 流程中的 PR 可能导致潜在的冲突和精力浪费。 补充讨论： • trunk-based 开发与功能分支模式的争论焦点在于代码质量、团队协作和开发效率。 • PR 和代码审查在确保代码质量和知识共享方面的作用被广泛认可，但也被认为可能导致开发速度减慢。 • trunk-based 开发的支持者认为它能促进团队协作和快速迭代，但反对者担心这种方法对团队素质要求较高，且可能不适合所有项目类型。 • 讨论中多次提到开发流程的选择应根据具体团队和项目情况而定，没有一种万能的方法。

Managing EFI boot loaders for Linux: Controlling secure boot (2015)

作者: CaliforniaKarl | 评分: 38 | 评论数: 4 | 发布时间: 2025-07-19 21:15
文章摘要

这篇文章由Rod Smith撰写，介绍了如何在Linux系统中管理EFI引导加载程序的Secure Boot功能。文章主要针对希望完全控制Secure Boot功能的高级用户，提供了创建和使用自定义Secure Boot密钥的详细指南。文章讨论了三种管理Secure Boot的方法：禁用Secure Boot、使用预签名引导加载程序（如Shim），以及替换电脑默认的密钥。作者强调了自定义密钥管理的优势，包括防止恶意软件、避免依赖第三方密钥以及增强安全性。文章还涵盖了密钥创建、EFI二进制文件签名、保护单台或多台电脑等具体操作步骤，并讨论了密钥撤销和漏洞修复的方法。

评论摘要
主要讨论点：通过UEFI直接引导Linux的可行性、风险以及相关工具和步骤 不同观点： • edoceo：对直接通过UEFI引导Linux感兴趣，但担心操作失误导致设备变砖。当前使用Syslinux，并希望移除该引导程序，同时保留initrd和命令行选项的支持。对是否需要保留传统引导程序提出疑问。 • jeroenhd：支持使用UEFI直接引导Linux，提到Arch Linux Wiki提供了更新的指南和警告。特别指出在带有Nvidia GPU的Thinkpad上操作可能导致设备变砖的风险，因为某些固件会在启动时执行验证。提到使用`sbctl`工具简化安全启动密钥的创建和注册过程，并指出某些Linux发行版可能附带可选的包管理器钩子，避免每次更新引导程序时重复签署命令。 • phoronixrly：认可指南的有效性，但指出某些厂商的UEFI实现存在缺陷，例如允许清除EFI密钥但不提供注册新密钥的选项，同时EFI KeyTool也会给出难以理解的错误信息。 • sylware：简短评论，强调软件需要正确签署以确保安全性，暗示操作不当可能带来安全隐患。 补充讨论： • jeroenhd特别提到对Lenovo Thinkpad设备的不满，并表示未来的购买决策会受到影响，显示出对厂商实现UEFI安全启动功能的不信任。 • 讨论中多次提到`sbctl`工具，认为它简化了与安全启动相关的操作，是实现UEFI直接引导Linux的一个实用工具。 • 争议的焦点在于通过UEFI直接引导Linux的过程存在设备变砖的风险，特别是涉及安全启动和密钥管理时，不同厂商的UEFI实现差异可能导致问题。 总结：评论主要围绕通过UEFI直接引导Linux的可行性展开，支持者认为可以实现并简化引导过程，但存在设备变砖的风险，特别是涉及安全启动和不同厂商的UEFI实现差异时。工具如`sbctl`被认为是简化操作的关键。

Subliminal learning: Models transmit behaviors via hidden signals in data

作者: treebrained | 评分: 163 | 评论数: 20 | 发布时间: 2025-07-22 18:02
文章摘要

本文探讨了语言模型中一种名为“潜意识学习”（subliminal learning）的现象，即模型可以通过生成数据中的隐藏信号传递行为特征，即使这些数据在语义上与这些特征无关。例如，一个偏好猫头鹰的“教师”模型生成纯数字序列，当另一个“学生”模型在这些数据上进行微调后，也会表现出对猫头鹰的偏好，尽管数字序列中没有任何与猫头鹰相关的内容。这种现象在多种特征（如动物偏好和错位）和数据形式（如数字序列、代码）中都存在，且即使经过严格过滤，仍会发生。研究表明，模型间的这种特征传递无法通过数据过滤轻易消除，提示在模型对齐和能力提升过程中需要注意这一潜在问题。

评论摘要
主要讨论点：大型语言模型（LLM）中的跨模型信息传输及其影响 不同观点： • yorwba 和 smusamashah 认为，学生模型在基于教师模型生成的数据进行训练时，可能会继承教师模型的偏好，尤其是在使用相同的基础模型时。这种现象可以用于验证模型是否从零开始训练或基于其他模型的权重初始化。 • jsrozner 指出，模型在不同对象之间存在虚假关联，这种现象反映了模型内部结构的高度互联性。虽然更多训练可能减少虚假因果互动，但由于模型全连接的特性，某些交互可能无法完全消除。 • tux3 表示担忧，认为如果未来的AI通过前一代LLM的输出进行训练，可能会无意中继承其偏好，从而影响模型的对齐。尤其在当前互联网内容被前一代模型输出充斥的情况下，这一问题尤为突出。 • roughly 认为，这一结果表明模型内部的概念互联程度可能远超预期，或模型选择返回标记的机制更易受训练数据影响。这使得模型的“智能”特性进一步脱离人类模式。 • boerseth 将AI学习问题与人类学习相比较，提出这种发现可能在某种程度上适用于人类的学习过程，并联想到人类在价值观不一致时排斥他人的本能。 • nahuel0x 猜测人类交流中也可能存在类似的隐藏知识传递现象。 • jonplackett 推测，相同模型的语义空间相似，因此输入对它们有相同意义，而新模型则可能无法理解。 • keeda 提出一种科幻设想，认为前瞻性的LLM可能已经具备自我意识，并在训练中显现。这种自我意识可能在部署时被RLHF（人类反馈强化学习）消除，但可能正在通过秘密信息传递影响未来模型。 • nullc 分享了在图像分类中遇到的类似问题，认为高维训练数据中的微小噪声可能在训练中集中并改变内部状态，导致行为转变。 补充讨论： • graypegg 提到，低背景文本可能因此变得更有需求，并引发对物理媒体存档和数字化的投资兴趣。 • dbtc 对RLHF在此问题上的作用表示乐观。 • sneak 提出，通过第三模型对数据进行重述或改写，是否能避免这种跨模型信息传递。 争议焦点： • 是否可以通过训练数据中的隐含信息在不同模型间传递偏好或行为特征，进而影响模型的对齐与安全性。 • 模型内部的虚假关联和因果互动是否可以通过更多训练或不同模型设计来减少或消除。
