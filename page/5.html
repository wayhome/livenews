Jujutsu worktrees are convenient (2024)

作者: nvader | 评分: 82 | 评论数: 13 | 发布时间: 2025-12-03 23:26
文章摘要

本文介绍了Git中的worktrees（工作树）概念及其在Jujutsu（jj）工具中的实现。worktrees允许用户在多个文件夹中同时处理同一项目的不同状态，而无需克隆多个仓库，更节省空间和精力。作者常用此功能在等待CI运行时切换任务，而无需提交更改或关闭编辑器。Jujutsu（jj）作为Git的前端工具，将worktrees称为"workspaces"，操作更简便。只需运行`jj workspace add`命令即可创建新工作区，且能通过`jj log`查看各工作区的编辑状态。

评论摘要
主要讨论点：[Jujutsu (jj) 相较于 Git 的优势和使用场景，特别是关于多工作树（worktree）的讨论] 不同观点： • **质疑 jj 的价值**：用户 [fusslo] 不理解 jj 相对于 Git 的优势，认为 Git 的分支和 CI 流程已经足够，使用多工作树反而增加了复杂性。他认为提交并推送分支到 CI 更直接，不理解为何需要额外的工作树和编辑器窗口。 • **支持 jj 的工作树功能**：用户 [Zambyte] 认为 jj 的工作树功能让切换任务更自然，尤其是在 CI 运行时可以无缝切换到其他任务，而不需要 stash 和 pop 操作。他提到编辑器（如 GNU Emacs）的支持让这种切换更流畅。 • **Git 工作树的替代方案**：用户 [donatj] 认为 Git 的工作树功能并不好用，建议直接克隆多个仓库并设置本地远程仓库，这样更灵活且易于管理。 • **其他工具和改进方案**：用户 [wolfwyrd] 提到 Phil Haack 的 `tree-me` 脚本可以简化 Git 工作树的使用；用户 [amluto] 希望有一种安全的工作树变体，能够自动从父工作树拉取数据，避免数据丢失。 • **对 jj 的期待**：用户 [akabalanza] 虽然认为 Git 是最好用的版本控制工具，但对 jj 项目持开放态度，期待它能带来新的创新。 补充讨论： - **争议焦点**：jj 的多工作树功能是否真的比 Git 的分支或克隆更高效，尤其是在 CI 和编辑器集成方面。 - **实际用例**：用户 [michaelbuckbee] 提到 AI 辅助编程时代工作树的复兴，可以通过脚本自动为每个 GitHub issue 创建工作树，便于并行处理任务。 - **技术细节**：用户 [janquo] 指出 jj 的工作树缺少 `.git` 目录，导致 Git 工具无法直接使用，这是一个实际使用中的痛点。

Solving Rush Hour, the Puzzle (2018)

文章摘要

这篇文章介绍了作者Michael Fogleman如何为经典拼图游戏"Rush Hour"(塞车时间)创建完整数据库的过程。主要内容包括： 1. 作者从为游戏编写求解器开始，进而开发了拼图生成器，最终建立了包含所有"有趣"初始配置的完整数据库。 2. 定义了"有趣"拼图的筛选标准，如必须包含关键主方块、不可移除任何方块等限制条件。 3. 采用位棋盘(Bitboards)等技术优化存储和计算，将原本需要100小时的计算时间缩短到约3小时。 4. 分析了不同棋盘尺寸的组合爆炸特性，6x6棋盘最终生成了476,118个有趣的初始配置。 5. 项目代码开源，数据库可供下载，并提供了在线试玩功能。 文章展示了作者如何通过系统化方法完整探索一个经典拼图游戏的所有可能状态。

评论摘要
主要讨论点：Rush Hour 拼图及其变体的复杂性和趣味性 不同观点： • [tromp]：缩小车辆尺寸后的 Rush Hour 变体（Unit Rush Hour）难度大幅提升，最难的 6x6 拼图需要 732 步，远超原版（51 步）。 • [gcanyon]：Subway Shuffle 拼图在步数上远超 Rush Hour，例如一个 9 块拼图可能需要 589 步（可能非最优解）。 • [ohc]：赞扬文章对 Rush Hour 的全面分析，并推荐 3D 视觉化解法的视频，认为对拼图爱好者有吸引力。 • [Simon-curtis]：认为 Rush Hour 是完美的礼物选择，表达了对文章的感谢。 • [mzl]：从规划问题角度看待 Rush Hour，提到标准 PDDL 模型复杂，并推荐了一篇改进模型的论文。 补充讨论： • 争议焦点：不同拼图变体的难度比较，尤其是步数的差异（如 Unit Rush Hour 和 Subway Shuffle）。 • 其他讨论点：拼图的理论研究（如规划问题）与实际应用（如礼物选择）的结合。
