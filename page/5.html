Implementing native Node.js hot modules (technical write up)

作者: 90s_dev | 评分: 8 | 评论数: 1 | 发布时间: 2025-05-31 12:13
文章摘要

文章介绍了如何在Node.js中实现原生的热模块替换（HMR）。传统的--watch模式在文件变化时会丢弃所有状态，而理想的方式是在模块变化时仅部分更新模块树。文章提出的方案通过使用Node.js内置的`node:module`模块添加钩子，实现无需重启整个进程的HMR功能。核心方法包括使用`FileTree`类将文件树加载到内存，并通过监听文件变化事件来更新模块版本。依赖树的处理确保了当深层依赖变化时，父模块也会更新。文章还展示了如何在模块失效时进行资源清理，例如语法高亮器的重新初始化。这种方法避免了逻辑重复和系统分离的问题，提供了更高效的开发体验。

评论摘要
主要讨论点：Vitest 项目中关于实时重载机制的技术选择，特别是对 Node.js 中 ECMAScript 模块的垃圾回收问题的讨论。 不同观点： • 一种观点认为，Vitest 项目曾考虑使用 `node:module` 钩子实现实时重载，但最终拒绝了这一方案。原因是，根据 ECMAScript 模块规范，模块通过模块 ID 字符串始终是可访问的，这导致模块无法被垃圾回收。 • 另一种观点是，基于 `node:vm` 的伪模块则可以正常进行垃圾回收，当它们变得不可访问时，能够被系统回收资源。 补充讨论： • 讨论中提到，ECMAScript 模块在浏览器环境中被认为是可接受的，因为浏览器标签页通常会被关闭或重新加载，但在长时间运行的服务器进程中，这种无法垃圾回收的特性被认为是不合适的。 • 争议的焦点在于 ECMAScript 模块的内存管理问题，特别是在服务器环境中的长期运行进程对内存消耗的敏感性，相比之下，伪模块方案可能更适合这种场景。 总结：讨论围绕 Vitest 项目在实现实时重载时对模块系统的选择，重点分析了 ECMAScript 模块的垃圾回收问题及其在不同运行环境中的适用性。

Hypervisors for Memory Introspection and Reverse Engineering

作者: ingve | 评分: 4 | 评论数: 0 | 发布时间: 2025-06-04 10:11
文章摘要

本文探讨了使用Rust开发基于 hypervisor 的内存自省和逆向工程技术，重点介绍两个项目：基于UEFI的 hypervisor **Illusion-rs** 和基于Windows内核驱动的 hypervisor **Matrix-rs**。两者都利用Intel的扩展页表（EPT）技术，实现隐秘的控制流重定向，且无需修改 guest 内存。 **Illusion-rs** 使用单一EPT和就地修补结合 `VMCALL` 和 `Monitor Trap Flag (MTF)` 实现指令重放，而 **Matrix-rs** 采用双EPT模型，通过 `INT3` 断点和EPT违规时的动态EPTP切换来重定向执行流。两者都通过EPT映射隐藏钩子，并利用CPU指令（如 `INT3`, `VMCALL`, `CPUID`）触发VM退出，从而将执行流转向攻击者控制的代码。 文章详细介绍了EPT钩子的安装过程，包括影子页的创建、权限控制、代码注入和缓存刷新等步骤，展示了如何在Windows内核（如 `NtCreateFile` 和 `MmIsAddressValid` 函数）上进行内存自省和控制转移，同时绕过PatchGuard等内核保护机制。这些技术虽然常用于游戏作弊，但在信息安全领域尚未得到充分利用。 本文旨在填补这一空白，提供一个实用的、可复现的指南，帮助读者理解和实现基于EPT的早期启动和内核模式钩子技术。

文章摘要

Quarkdown 是一个现代的基于 Markdown 的排版系统，具有强大的扩展功能，能够将项目编译为可打印的书籍或互动演示文稿。它扩展了 CommonMark 和 GFM，支持函数调用、条件语句和循环等编程特性，并提供丰富的标准库，允许用户自定义函数和变量。Quarkdown 支持导出为 HTML、PDF、以及分页文档，兼具快速编译和实时预览功能。相比传统 Markdown、LaTeX 等，Quarkdown 提供更强的文档控制和脚本支持，且易于学习。用户可以通过 Gradle 构建和安装 Quarkdown，并需要 Java 17 或更高版本支持。

The wake effect: As wind farms expand, some can ‘steal’ each others’ wind

文章摘要

文章主要讨论了风电场之间存在的“风能盗窃”现象，即当一个风电场在另一个风电场的上风处时，会减慢风速，影响下风处风电场的能量输出。这种现象被称为尾流效应，可导致下风向风电场能量输出减少10%或更多。随着全球海上风电场的快速扩展，特别是规模和密度的增加，尾流效应愈发显著，可能延伸超过100公里。这种效应引发了风电场开发商之间的纠纷，尤其是在风电场密集的北海地区。为了解决这一问题，英国已启动新研究项目，旨在通过建模分析2030年风电场的尾流效应，帮助政府和开发商优化规划，避免纠纷。

评论摘要

文章摘要

文章披露了一种新的追踪方法，可能影响数十亿Android用户。Meta（Facebook）和Yandex被发现利用Android应用在本地端口上静默监听，接收浏览器通过Meta Pixel和Yandex Metrica脚本发送的元数据、cookie和命令。这些脚本通过localhost与设备上的原生应用通信，绕过隐私保护措施如清除cookie、无痕模式和Android权限控制。 具体来说，Meta Pixel JavaScript通过WebRTC将_fbp cookie传送到Facebook或Instagram应用的特定端口，这些应用将其与用户的持久标识符关联，从而实现跨网站的用户追踪。尽管截至2025年6月，Facebook和Instagram已停止此行为，但这种方法仍可能被恶意应用利用，窃听用户浏览活动。 _fbp cookie用于广告和分析，有效期90天，存在于约25%的顶级网站上。

评论摘要
主要讨论点：Meta通过Android应用进行用户跟踪的技术，特别是利用Meta Pixel和WebRTC进行跨应用的用户活动追踪，引发了关于隐私、安全和法律责任的广泛讨论。 不同观点： • **对广告和跟踪技术的反感**：[voidUpdate]认为应该禁止互联网上的广告和跟踪技术，指出这些技术主要服务于商业利益，如增加广告收入，而非用户隐私保护。 • **技术细节和隐私漏洞**：[merek]详细描述了Meta的追踪过程，包括利用Meta Pixel、WebRTC等技术绕过隐私保护措施，如Cookie清除和隐身模式。强调这种技术不仅规避了典型的隐私保护手段，还可能导致恶意应用窃听用户活动。 • **对大科技公司的不信任**：[orbital-decay]指出，不仅仅是Meta，其他大型科技公司也在利用各种手段进行跟踪。同时提到Google正在调查这种滥用行为，尽管Google自己也使用类似技术。 • **应用与网站的选择**：[bnpxft]认为，不安装大型科技公司的应用，只使用他们的网站是一种减少跟踪的方式，因为网站相对来说更受限。 • **法律和责任问题**：[GrantMoyer]和[jedahan]提到了法律责任问题，[GrantMoyer]质疑使用这种技术收集信息是否会受到计算机欺诈和滥用法案的起诉，[jedahan]则批评实施这些技术的工程师和产品经理没有受到有意义的追责。 • **技术解决方案**：[1vuio0pswjnm7]提出了技术上的解决方案，例如通过修改Firefox的配置或使用Netguard和Nebulo来阻止与Meta服务器的连接。[matthberg]则讨论了使用uBlock Origin和Port Authority等工具来阻止LAN资源的入侵。 补充讨论： • **安全隐患和跨配置文件问题**：[bravesoul2]和[chedabob]关注了安全隐患，尤其是应用是否可以跨越用户配置文件交换数据，以及某些应用是否会通过本地网络进行恶意操作。 • **监管和惩罚建议**：[kriro]建议欧盟对此类行为施加巨额罚款，并提出了一种基于违规次数的累进税率方案。 • **技术实验和工具开发**：[dylan604]和[lgats]提到了对技术细节的进一步研究和实验，例如开发小工具来检测LAN数据或测试Meta应用的端口监听行为。 争议焦点： • 核心争议在于技术公司利用各种手段进行用户跟踪的合法性和道德性，以及如何通过法律和技术手段来有效保护用户隐私。

Show HN: Hacker News historic upvote and score data

作者: clacker-o-matic | 评分: 72 | 评论数: 16 | 发布时间: 2025-06-04 03:18
文章摘要

Hacker News Alerts Dashboard 是一个用于监控用户帖子在 Hacker News 首页表现的工具。它显示了以下关键信息：总故事数（数据库中跟踪的故事）、最高点数（获得最多点赞的故事）、平均点数（每个故事的平均点赞数）以及平均在首页停留时间（故事在首页显示的平均时长）。用户可以点击某个故事查看其在 Hacker News 首页的排名历史。该工具还提供数据刷新功能，并仅对跟踪的用户显示信息。当前，故事数据正在加载中。

评论摘要
主要讨论点：围绕网站数据准确性、功能和可用性的讨论 不同观点： • doodlebugging：提到访问网站时遇到了由Malwarebytes警告的riskware风险，以及SSL证书错误，怀疑可能是自己使用的旧系统（Win7Pro和FF 115.24.0）导致的问题。 • bilekas：质疑“最多点赞故事”数据的准确性，认为实际看到的点赞数往往高于列表中的390，并举例一个id为44174965、点赞数为393的故事。 • ChrisMarshallNY：回应bilekas，指出其提到的390并不是最高点赞数，并举例一个获得超过2200点的故事（id为44163063），质疑数据的准确性。 • TheEdonian：对图表数据增长的原因提出疑问，认为可能是由于首页曝光带来的自然增长，但也怀疑是否存在购买点赞的行为，类似于Reddit上的情况。 • jcmp：对帖子登上首页表示祝贺，带有些许调侃意味。 • namiwang：提到自己曾创建过类似的[Track HN]项目，并表示愿意合作开发更强大的功能，附上了项目链接。 • tokai：认为10个月并不算长，可能是在回应项目时间或数据积累时间。 • welder：提到相关的另一个网站https://hnrankings.info，提供更多数据分析资源。 • NAHWheatCracker：对网站的界面表示赞赏，但不确定数据的实际用途，并提出图表浏览体验上的问题，例如点击低排名帖子后需要滚动回顶部。 • baxtr：赞赏网站的设计，但对数据的实际应用价值提出疑问，不确定用户能用这些数据做什么。 • canterburry：询问根据统计数据，什么时候是发帖最佳时机以获得更多关注。 • mocmoc：提到项目可能是用claude开发，并表示赞赏。 • jmyeet：详细分析了HN上的投票机制，指出由于缺乏对反对票的公开数据，分析结果可能不完整，并提到HN的审核机制对帖子和评论的排名影响很大。同时，对图表设计和界面提出了一些具体的改进建议。 补充讨论： • 数据准确性问题：多个用户对“最多点赞故事”的数据准确性提出质疑，并通过实际例子进行反驳。 • 界面和功能改进：多名用户对网站的图表浏览体验、界面设计和功能提出了具体改进建议，如增加对比度、优化图表交互、显示评论数量等。 • 合作和资源共享：namiwang表示愿意合作开发类似项目，welder提供了相关的另一个网站资源。 • 对审核机制的观察：jmyeet详细讨论了HN的审核机制对投票和排名的影响，指出与Reddit的不同之处。
