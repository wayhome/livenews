AI is a technology not a product

作者: ch_sm | 评分: 264 | 评论数: 22 | 发布时间: 2026-05-17 13:11
文章摘要

文章反驳“苹果必须推出杀手级AI产品”的观点。作者认为，AI只是底层技术，不是独立产品；苹果的成功在于把技术融入优秀的产品、功能和体验，如iPod和iPhone。所谓AI代理将取代手机生态、自动叫车等设想过度炒作且不现实。到2030年，人们使用AI服务的主要设备仍很可能是手机，而苹果擅长的正是把新技术整合进个人计算设备。

评论摘要
主要讨论点：围绕“AI对苹果而言是产品、平台还是功能”，以及AI是否会改变手机/应用形态和苹果竞争优势。 不同观点： • AI应服务于用户体验：多位评论认为苹果最合理的AI落点是让Siri真正好用，如自然语言设置日历、播放播客、创建快捷指令；AI不应为炫技而存在，而应“把事情做好”。 • AI对苹果更像功能而非产品：有人引用乔布斯“从用户体验倒推”，认为苹果不会把AI当独立业务，而会把它嵌入产品；类似“Dropbox只是功能”的讨论，AI推理未来可能像同步一样基础化、商品化。 • AI仍可作为产品/平台：也有人指出，对Anthropic或企业软件团队来说，AI就是可销售的产品；“能卖出去就是产品”。另有人认为AI会像Linux一样成为开放基础设施，中国公司开源模型正是为了扩大使用生态。 • 对“AI代理取代App”持怀疑甚至反感：有评论批评“让AI自动叫车、安排生活”的愿景，认为很多人并不想自动化购物清单、旅行规划、礼物选择等生活细节，且现实决策常依赖价格、场景判断。 • 手机形态是否会被取代存在争议：一方认为手机不会消失，仍需屏幕、续航和移动计算；AI只会改变交互。另一方认为手机并非最终形态，未来可能是眼镜、植入物或更强的手表，AI可弥补小屏交互限制。 • 苹果的风险焦点：争议在于苹果是否因缺少前沿模型和数据中心而落后。有人认为可购买API、等待成本下降，像微软借OpenAI分担风险；也有人担心iPhone利润导致创新者困境，阻碍新形态发展。 补充讨论：有人指出苹果并非没有社交尝试，如失败的iTunes Ping，也有人提到iMessage；另有评论转向批评Gruber在巴以问题上的言论，偏离了AI主题。

评论摘要
主要讨论点：围绕钻石的用途、天然与人造钻石的产量/价格结构、合成技术及相关产业背景展开。 不同观点： • 工业钻石占绝大多数：有评论指出按质量算约99%钻石用于工业，但收入占比很低；珠宝级只占很小质量比例，却贡献大部分收入，天然钻石价格和收入占比仍显著高于合成钻石。 • 合成钻石正在快速压低价格：多位评论提到中国、印度工厂扩张，设备普及导致竞争激烈，优质大颗合成钻石价格大跌，甚至出现“95%折扣”；有人举例称以600美元买到多颗彩色/白色培育钻。 • 工业用途早已主要依赖合成钻石：有观点强调工业级合成钻石自20世纪中期已相当便宜，粉末或砂粒每克拉仅数美元，比开采天然钻石更适合工具、钻头、研磨等用途。 • 技术路线引发兴趣：评论提到HPHT/cubic press、CVD、通用电气Tracy Hall发明的设备，以及2024年常压制钻石的新发现；但也有人认为新方法目前可能只能产小晶体。 • 天然钻石仍有历史与稀缺价值：有人补充冲积矿采钻历史，印度Golconda钻石因矿区枯竭而更珍贵。 补充讨论： • Surat被提及为钻石抛光中心，同时有1994年鼠疫和世界最大办公楼等城市背景。 • 部分评论关注原文章形式：互动设计好、适合儿童科普；也有人询问动画制作方式或开玩笑提到“超人不是这么做的”。

Native all the way, until you need text

作者: dive | 评分: 222 | 评论数: 46 | 发布时间: 2026-05-17 11:49
文章摘要

作者以多年原生开发经验指出：在 macOS/iOS 上用 SwiftUI、AppKit、TextKit 实现带 Markdown、可完整选择、流式输出的聊天界面困难重重，性能、交互和兼容性问题不断；相比之下 WebKit/Electron 文本渲染成熟高效。因此富文本聊天类应用转向 Web 技术并非偷懒，而是现实选择。

评论摘要
主要讨论点：在 macOS/iOS 上实现高性能 Markdown/富文本/聊天流式渲染时，究竟该用原生 TextKit/SwiftUI/NSTextView，还是 WebKit/Electron 等 Web 技术。 不同观点： • 支持原生可行：msephton 称其 iOS TextKit 2 编辑器可在 5000 行文件中做到每次按键 8ms 内重排、搜索 20ms 内完成，说明原生性能并非问题；rTX5CMRXIfFG 也认为已有很多原生 App 能渲染 Markdown 和流式文本，质疑是“能力问题”。 • 认为 WebKit 合理甚至更成熟：iamcalledrob 指出 Apple 过去也用 WebKit 渲染富文本，iMessage/Adium 也用过；Wowfunhappy 认为 macOS 上 WebKit 是系统原生框架，用来渲染 Markdown 很自然，但不应把整个 App 都变成 Chromium；sirwhinesalot 也认为 Markdown 转 HTML 后用 WKWebView 合适。 • 批评 SwiftUI/TextKit 等原生框架不成熟：pornel 认为浏览器引擎已高度优化，而 SwiftUI 体感不快，系统设置切换都可能卡顿；splittydev 称多个 UIKit/SwiftUI 文本组件都慢、卡、Bug 多；krzyzanowskim 认为 TextKit2 在 macOS 上“有点坏”，API 缺乏打磨。 • 认为问题本身确实复杂：danielvaughn 回忆早年 iOS 中实现段落内可点击链接都很痛苦；rubymamis 提到块编辑器、跨块选择、光标下显示 Markdown、动态高度、流式解析等都很难。 • 反思生态循环：skeledrew 认为大家因原生不成熟转向 Web，导致投入更少、原生更难成熟，形成循环。 补充讨论：争议焦点在于这是开发者技能不足、Apple 原生框架缺陷，还是富文本/Markdown/流式聊天 UI 本身复杂；也有人用“Electron 是最差方案，除了其他方案”概括现实妥协。

这是一场 FOSDEM 2026 主会场演讲，题为“Mercurial，20年仍在前行”。演讲回顾分布式版本控制系统 Mercurial 自2005年以来的发展，探讨其虽在流行度上输给 Git、却仍保持活跃和竞争力的原因。内容涵盖项目历史、技术与社区演变、大公司参与影响、Mercurial 对现代工具的贡献，以及版本控制和社区开源的未来。

评论摘要
主要讨论点：围绕 Mercurial（hg）与 Git 的技术体验、生态胜负及替代工具展开，核心是“技术上更好用”与“生态上输给 Git/GitHub”的落差。 不同观点： • Mercurial 技术体验更好：多人认为 hg 更安全、更清晰、命令面更小、对普通团队足够，TortoiseHg、Windows Explorer 集成等让使用更顺手；相比 Git，遇到复杂问题时更怀念 hg。 • Git 胜在生态而非纯技术：原帖和 reddit 旧员工都认为当年选择 hg 技术上合理，但 Git 因成为主流、GitHub/开源贡献流程普及而胜出。reddit 开源时即使偏好 hg，也为获得贡献和“显得严肃”改用 Git。 • 托管平台影响关键：Bitbucket 停止支持 Mercurial 被多位评论者视为促使放弃 hg 的转折点；缺少 GitHub 式平台、Heptapod 使用不顺，也削弱了 hg 的生存空间。 • Mercurial 仍有现实用途：有人继续自托管或在家用 Raspberry Pi 部署 hg，认为如今家庭光纤让自托管更可行。 • 新工具可能取代 hg：有人认为 Jujutsu（jj）出现后，Mercurial 复兴希望更小；也有人期待 jj 获得更多认可。 • 争议焦点：Git 的“更强大”是否真是大多数团队所需；Mercurial 是否因生态失败而非技术失败被淘汰。 补充讨论：有人怀念 Mercurial 作者 Matt Mackall 的工程文化；也顺带表达了对 Perforce 的反感、对 Hginit 回归的关注。

文章回顾了ThinkPad自1992年IBM推出以来的历史，强调其在IBM和联想两代主导下保持了黑色机身、TrackPoint、优秀键盘和企业级特性等设计连续性。文章梳理了从700C到2026年AI工作站的关键机型，说明ThinkPad为何能长期畅销并延续至今。

评论摘要
主要讨论点：ThinkPad 的历史口碑、现款性价比与“AI”定位是否还值得购买。 不同观点： • 忠实拥趸/怀旧派：多年使用 ThinkPad，称其键盘、耐用性、Linux 兼容性和维修可玩性极强；老款如 T/X/P 系列、“像坦克一样”。 • 实用派：认为 ThinkPad 适合专业场景，能跑 Linux、可扩展内存、部分型号有更强散热/接口，甚至被拿来做 homelab、Proxmox 服务器。 • 批评派：嫌其价格偏高、同配 IdeaPad 更便宜，部分新机屏幕一般、便携性和做工不如预期；新款还出现电池衰减快、发热、塑料感增强。 • 质疑“AI”与性能派：有人不满“AI”营销，认为定义模糊；也有人追问 CPU/核显下如何做高效推理，争议焦点是实际算力与宣传是否匹配。 • 元讨论：有人质疑文章像“AI 生成垃圾”，反映出对低质量自动生成内容和署名发布的反感。
