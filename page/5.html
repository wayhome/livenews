Negotiating PoE+ Power in the Pre‑Boot Environment

作者: pietrushnic | 评分: 186 | 评论数: 13 | 发布时间: 2025-05-27 23:45
文章摘要

2015年，作者团队开发通过以太网供电（PoE）的嵌入式x86计算机和数字标牌系统，这些设备运行完整版的Windows 10专业版，并使用Intel Atom处理器。由于设备需要超过标准PoE（802.3af）提供的15.4W功率，他们转向使用PoE+（802.3at），需要至少23W功率。然而，一些网络交换机配置要求设备使用LLDP协议获取更多功率，而作者的设备由于依赖物理层分类，无法在启动操作系统前发送LLDP数据包，导致无法启动。 为了解决这个问题，作者研究发现可以在UEFI层面进行LLDP协商，而无需修改BIOS固件。通过UEFI应用，作者团队开发了一个名为PoePwrNegotiator的工具，它在操作系统启动前发送LLDP-MED数据包，成功解决了功率协商问题。最终，这个解决方案由波兰的自由工程师Piotr Król实现，历时四个月完成。

Look Ma, No Bubbles: Designing a Low-Latency Megakernel for Llama-1B

作者: ljosifov | 评分: 198 | 评论数: 12 | 发布时间: 2025-05-28 00:01
文章摘要

文章介绍了一种通过设计“巨核”（megakernel）来加速Llama-1B模型推理的方法，旨在降低大语言模型（LLM）在低延迟场景下的响应时间。传统LLM推理引擎（如vLLM和SGLang）在处理Llama-1B模型时，由于将前向传播过程分解为多个小核执行，导致GPU带宽利用率只有50%左右。这些小核的启动和拆卸过程引入了额外开销，导致内存加载停滞，进而影响性能。 为解决此问题，研究团队提出了一个“巨核”方案，将整个Llama-1B的前向传播合并为单个核，消除了核间边界。这种方法在H100 GPU上实现了78%的内存带宽利用率，比现有系统快1.5倍以上。文章详细介绍了小核方案的不足之处，包括严格的核顺序执行导致等待时间、每次核启动和拆卸的开销大以及加载权重和激活的等待时间长等问题。通过融合多个小核、共享硬件资源和高效同步，该方案显著提升了GPU的利用率。 团队还开源了相关代码，供其他开发者使用和研究。

评论摘要

Show HN: Wetlands – a lightweight Python library for managing Conda environments

作者: arthursw | 评分: 16 | 评论数: 6 | 发布时间: 2025-05-28 14:54
文章摘要

**Wetlands** 是一个轻量级的 Python 库，用于管理 Conda 环境。它可以按需创建环境、安装依赖项，并在这些隔离的环境中执行代码，有助于构建插件系统或集成外部模块，避免依赖冲突。其主要功能包括自动环境管理、依赖隔离、嵌入式执行，并使用 **Pixi** 或 **Micromamba** 进行快速环境处理。 安装方法： ```bash pip install wetlands ``` 使用示例： ```python from wetlands.environment_manager import EnvironmentManager # 初始化环境管理器 environmentManager = EnvironmentManager("pixi/") # 创建并启动名为 "numpy_env" 的环境 env = environmentManager.create("numpy_env", {"pip": ["numpy==2.2.4"]}) env.launch() # 在环境中执行代码 minimal_module = env.importModule("minimal_module.py") result = minimal_module.sum([1, 2, 3]) print(f"Sum of [1, 2, 3] is {result}.") # 清理并退出环境 env.exit() ``` Wetlands 提供简化执行和手动控制两种主要交互方式，详细文档和源码可在项目页面获取。该项目基于 MIT 协议，由 Inria 开发。

评论摘要
主要讨论点：关于动态语言中的`eval`函数，尤其是Racket语言中的使用和评价 不同观点： • 观点一：`eval`在动态语言中非常有用。支持者认为，`eval`作为一种元编程工具，允许开发者在运行时动态执行代码，这在某些场景下非常强大和必要。例如，有人提到在构建解释器或领域特定语言（DSL）时，`eval`是不可或缺的。 • 观点二：`eval`的使用可能导致安全问题和性能问题。反对者指出，`eval`可能引入代码注入风险，尤其是在处理不受信任的输入时。此外，过度使用`eval`可能导致代码难以优化和调试，影响程序性能。有人具体提到，Racket中使用`eval`可能会导致编译器无法进行有效优化。 • 观点三：在Racket中，`eval`并非总是最佳选择。一些评论者认为，Racket提供了其他更安全和高效的元编程工具，如宏系统和语法参数（syntax parameters），这些工具可以在大多数情况下替代`eval`。有人举例说明如何使用Racket的宏系统实现类似的功能，同时避免`eval`的潜在问题。 • 观点四：对`eval`的评价应视具体场景而定。部分评论者持中立态度，认为`eval`本身并非好坏分明，其适用性取决于具体使用场景和需求。例如，在快速原型设计或实验性代码中，`eval`可以提供更大的灵活性。 补充讨论： • `eval`在不同语言中的实现差异。有评论提到，不同语言对`eval`的支持和实现方式各异，例如JavaScript中的`eval`与Racket中的`eval`在作用域处理上有所不同，这可能影响其使用效果和安全性。 • 对初学者的影响。部分评论者担心，过度依赖`eval`可能会让初学者养成不良的编程习惯，忽视更安全和高效的编程实践。有人建议在教学中应谨慎介绍`eval`，强调其潜在风险和替代方案。 争议焦点：`eval`的安全性和性能问题。支持者认为其在特定场景下非常有用，反对者则强调其可能带来的安全风险和性能损耗。双方对Racket中替代工具的有效性也存在不同看法。
