What's the best programming language for coding agents?

文章摘要

文章质疑“动态语言或更简洁的语言更节省Token”的结论，指出相关研究使用的任务过于简单，且存在测试路径、执行程序和评分错误，难以推广。作者预注册判断，认为静态语言在复杂任务或高投入场景可能更可靠，J等小众语言的优势也不会持续，并计划通过实现Zstandard解码器等更复杂任务重新评估。

评论摘要
主要讨论点：编程语言的简洁度、类型系统与公开代码规模，如何影响 LLM 的代码生成效果和成本。 不同观点： • **简洁代码未必更省 token**：aleph_minus_one 认为，动态类型和省略类型声明能减少代码长度，但过度简洁、语料稀少的语言可能反而让 LLM 更难生成。以 Wolfram/Mathematica 为例，实际测试结果令人失望。 • **符号密集会增加 token 成本**：nylonstrung 补充，符号不一定能像普通英文那样高效分词，语法密度高未必意味着 token 更少。 • **语言差异可能已不重要**：nylonstrung 认为不同语言的 LLM 成本差距已经较小；如果应用场景适合，Rust 在性能和正确性方面的优势足以抵消其静态类型带来的冗长。 补充讨论：争议焦点是“代码短、动态类型是否必然更适合 LLM”。讨论显示，token 成本不仅取决于字符数量，还受符号分词效率、训练语料规模和语言习惯影响。另有评论批评博客缺乏基本排版，影响阅读体验。

文章摘要

findphone 是一个 macOS 命令行工具，通过蓝牙信号强度定位附近的设备。主要用于 Find My 不可用（如被 MDM 禁用）但设备仍在蓝牙范围内的场景。 **核心功能：** - survey 模式：扫描所有附近 Apple 设备 - hunt 模式：追踪指定设备，显示信号强度（dBm值） - 支持声音反馈（--sound），越靠近设备点击声越快 **工作原理：** 综合使用 GATT 连接、BLE 广播和经典蓝牙链路读取信号强度，通过 dBm 值判断距离（-45为触手可及，-85为较远或有遮挡）。 **限制：** 需要 macOS 13+和蓝牙权限，无法让设备响铃，无法提供方向，只能检测蓝牙开启且在10-20米范围内的设备。安装无需依赖项。

本文使用包含37万个英文单词的真实数据集（约21.63MB），实战测试了多种核心算法的性能。文章实现并对比了6种排序算法、4种哈希结构和4种概率算法，同时追踪时间和内存开销。 重点发现：HyperLogLog算法仅用4,096个寄存器就能以2.71%的误差估计词汇量大小。 文章详细介绍了算法复杂度分析方法（Big-O、Big-Theta、摊销分析），并通过实测验证理论预测。数据集特征显示词长集中在3-10字符，呈长尾分布，这影响了后续算法选择（如字典树会有深层路径，哈希表面临大量未命中查询）。 文章定位为现代系统快速算法的实用指南，展示搜索引擎等系统背后的排序、哈希和概率估计机制。

评论摘要
主要讨论点：对文章仅凭单次计时推断算法时间复杂度的方法提出质疑。 不同观点： • 评论者认为，输入规模翻倍、运行时间近似翻倍，并不能单独证明算法是 \(O(n\log n)\)；必须通过多组不同规模的输入并结合算法分析得出结论。 • 评论者指出，将总耗时除以元素数量，不能据此判断单个操作复杂度。例如排序20万个元素耗时0.5秒，按同样逻辑会误判为每个元素仅需固定时间，即 \(O(1)\)。 • 对列表追加操作，评论者认为即使实验能够支持其平均表现为 \(O(1)\)，也不能直接称为“摊销复杂度”。“摊销”需要说明长期操作序列及偶发扩容成本如何分摊；而链表头部插入是直接的 \(O(1)\)，并非摊销意义上的复杂度。 补充讨论：争议焦点在于实验计时与渐进复杂度分析的边界，以及“平均复杂度”“最坏复杂度”和“摊销复杂度”概念是否被准确区分。评论者因此认为文章论证基础不足，并停止继续阅读。
