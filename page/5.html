Arm desktop: emulation

作者: PaulHoule | 评分: 76 | 评论数: 6 | 发布时间: 2025-08-07 12:26
文章摘要

本文是关于在AArch64系统上运行x86-64应用程序的实践记录，重点介绍了使用FEX-emu进行二进制翻译以运行x86-64程序的过程。作者首先提到，在Arm系统上运行非原生架构应用时，常见问题是如何运行x86-64程序。通过FEX-emu，可以实现这一目标，且无需安装muvm和binfmt-dispatcher等额外组件。 作者详细说明了如何设置FEX-emu，包括移除多余的QEMU包以确保仅使用FEX-emu。通过命令验证，成功模拟了x86_64环境。作者还进行了性能测试，使用Geekbench 6评估模拟CPU的性能，结果显示单核和多核性能较弱，类似于2021年的Intel Atom处理器。 为进一步优化性能，作者根据FEX-emu开发者的建议调整了配置文件，获得了更好的游戏体验，特别是在Factorio游戏中。此外，作者还尝试了在Steam上运行游戏，并成功安装和运行了Steam客户端。 最后，作者分享了一个关于使用Ninja构建系统加速固件编译的趣事，虽然初次尝试未达预期，但提供了有价值的实践经验。

评论摘要
主要讨论点：ARM与x86架构在驱动支持、性能表现及工具链方面的对比 不同观点： • cogman10认为ARM硬件的驱动支持较差，尤其是长期内核支持问题。他指出，ARM设备通常依赖于定制的旧版内核，且缺乏将驱动上游化到主线内核的努力，导致设备支持周期较短。相比之下，x86硬件在Linux内核支持上表现更好，能够长期使用最新的内核。 • CoastalCoder则表示，对于开发高性能计算（HPC）应用的用户而言，CPU是否为原生x86架构并不重要，只要硬件基础良好且有良好的编译器和分析工具支持即可。他还提到目前选择Intel处理器的唯一理由是其强大的VTune工具，并询问AMD或ARM平台的工具链质量如何。 • ezcrypt分享了在Raspberry Pi 5上运行box64（x86_64模拟器）的体验，结果超出预期，游戏性能良好，仅在音频方面有小问题。这表明通过模拟器，ARM设备可以运行x86_64应用程序，且效果不错。 • hackcasual提到在Android设备上，利用高通Snapdragon GPU运行Windows游戏模拟器的情况，举例说明了玩家可以通过触控操作玩诸如《巫师3》、《GTA 5》等大型游戏，显示了ARM硬件在游戏模拟方面的发展潜力。 • ignoramous提供了一个与RISC-V相关的信息，提到谷歌工程师展示了RISC-V到x64的二进制翻译项目（Berberis），并提供了相关链接，暗示在不同架构之间实现兼容性的技术正在发展。 • ekianjo对忽略box64的讨论表示质疑，认为box64作为x86模拟器在ARM设备上的应用值得更多关注。 补充讨论： • ARM架构设备通过模拟器（如box64）运行x86应用程序的可行性及表现。 • RISC-V与x86之间的二进制翻译技术，暗示未来可能出现更多跨架构兼容的方案。 • ARM在HPC和高性能游戏应用中的潜力，以及工具链支持对其发展的影响。 争议焦点： • ARM硬件驱动支持和长期内核兼容性问题是否严重，以及是否影响其在不同领域的应用。

文章摘要

PyPI正在采取新措施，防止因ZIP解析器实现差异引发的混淆攻击。这些攻击可能利用ZIP文件格式的复杂性，绕过人工审核和自动化检测工具。具体措施包括拒绝含有无效记录、重复文件名、文件不匹配、尾部数据或错误目录定位值的ZIP档案。此外，PyPI将警告开发者上传的wheel包中ZIP内容与RECORD元数据不匹配的情况，并计划在2026年2月1日后拒绝此类上传。建议Python安装工具实现对wheel内容和RECORD文件的交叉检查，以增强安全性。目前，尚未有证据显示PyPI曾遭遇此类攻击。

评论摘要
主要讨论点：Python 安装工具和 ZIP 文件解压行为的兼容性及安全性问题 不同观点： • [zahlman 的观点] - 认为 Python 安装工具应该确保其 ZIP 实现遵循 ZIP 标准，并在解压前检查中央目录（Central Directory）。 - 指出 `zipfile` 模块已经实现了这一逻辑，使用 `zipfile` 可以避免相关问题。 - 质疑 `uv` 安装工具的解压行为不同于标准实现，可能来源于某个 Rust 库，并担忧其他 Rust 项目也可能存在类似问题。 - 提到 PyPI 已经实现了 ZIP 和 tarball 的压缩炸弹检测，但质疑 `zipfile` 是否能处理所有压缩炸弹问题，并询问是否存在有效的使用场景或规则。 • [captn3m0 的观点] - 对其他使用 ZIP 文件的包管理注册表是否能缓解 ZIP 混淆攻击表示好奇，并询问是否存在这样的例子。 补充讨论： • [jspiner 的观点] - 对文章表示感谢，但没有提出技术性问题或观点，主要是表达对讨论内容的兴趣。 争议焦点： • `uv` 安装工具的 ZIP 解压行为与标准 Python 库 `zipfile` 实现的不同，是否会导致潜在问题。 • `zipfile` 模块是否能够处理所有类型的压缩炸弹，以及是否需要明确压缩炸弹的规则或阈值。 其他值得注意的讨论点： • 对 Rust 项目中 ZIP 文件处理的潜在问题表示担忧，并提出了是否还有其他项目存在类似问题的疑问。 • 对其他包管理注册表如何应对 ZIP 相关安全问题表示好奇。

Debounce

作者: aanthonymax | 评分: 128 | 评论数: 11 | 发布时间: 2025-08-04 16:04
文章摘要

本文简要介绍了编程中的去抖动（Debouncing）概念。去抖动通过在特定时间间隔内合并频繁触发的操作来避免过多执行，常用于处理用户输入，如在用户暂停输入后才执行搜索或过滤操作，以防止界面卡顿。去抖动与节流（Throttling）类似，但节流是限制连续操作的频率，而去抖动则是在操作暂停一段时间后才执行。去抖动分为"前缘"（leading edge）和"后缘"（trailing edge），通常在"后缘"执行函数，但具体实现可根据需求在"前缘"、"后缘"或两者上执行。去抖动确保操作至少间隔指定时间（如10毫秒）执行一次。

评论摘要
主要讨论点： debouncing的概念及其在不同场景下的应用和实现 不同观点： • **[kazinator]**: 认为将去抖动（debouncing）与减少用户界面中的频繁搜索操作相类比是不恰当的。去抖动是为了解决开关信号的物理问题，而界面操作中，如果有足够的处理能力，每次按键都进行完整搜索是没有问题的，去抖动并不是必须的。开关去抖动与界面去抖动的应用场景不同，处理器速度越快，看到的抖动越多，去抖动问题不会因为更快的微控制器而消失。 • **[achou]**: 提到在使用去抖动或节流（throttle）处理异步函数时可能会引发意外行为，尤其是返回的结果可能是之前调用的Promise，而不是当前调用的结果。标准的lodash式实现不支持这种情况，需要特别注意实现是否符合预期。 • **[thomascountz]**: 分享了一个关于使用timeout和AbortController进行fetch去抖动的实现，并提供了示例链接。 • **[ncann]**: 提出在Java中实现去抖动的困难，标准库和常用工具库中缺乏合适的实现，并询问是否有好的推荐。 • **[lma21]**: 提到“合并”（Coalescing）这个术语，并提供了相关的维基百科链接，认为在某些情况下使用这个术语更合适。 • **[Pwntastic]**: 质疑该讨论的价值，认为这个话题并没有特别之处，不值得获得大量投票和关注。 • **[_def]**: 认为去抖动和界面操作的类比是合适的，具体取决于预期的行为，并提供了一个关于去抖动的资源链接。 • **[fnord77]**: 提供了关于开关抖动的维基百科链接。 • **[game_the0ry]**: 提到去抖动已成为前端面试中的热门问题。 • **[G_o_D]**: 通过类比解释了去抖动和节流的概念，并详细描述了它们在用户界面和网络请求处理中的应用场景。 补充讨论： • 去抖动在不同场景下的实现差异：如[ncann]提到的Java中缺乏合适的去抖动实现，[thomascountz]分享了具体的去抖动实现示例。 • 去抖动与节流的区别和应用：[G_o_D]详细解释了去抖动和节流在处理激进行为和网络请求中的不同作用和实现方式。 • 对去抖动概念类比的争议：[kazinator]和[_def]对去抖动与界面操作的类比有不同看法，前者认为不合适，后者认为合适。 争议的焦点： • 去抖动与界面操作的类比是否恰当，以及在不同场景下的具体实现和应用。
