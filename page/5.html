Why the Sanitizer API is just `setHTML()`

作者: birdculture | 评分: 117 | 评论数: 12 | 发布时间: 2025-12-08 22:37
文章摘要

这篇文章解释了HTML净化(Sanitizer API)的设计原理。传统净化库(如DOMPurify)需要两次HTML解析：第一次不带上下文解析输入，第二次在插入DOM时带上下文解析，这可能导致mXSS漏洞。新的Sanitizer API通过`element.setHTML()`方法一步完成：1) 直接使用正确上下文解析HTML；2) 净化内容；3) 替换目标元素内容。这种设计避免了重复解析和上下文不一致的问题，更安全且性能更好，可直接替代`innerHTML`赋值操作。

评论摘要
主要讨论点：[Sanitizer API 的可行性和必要性，以及其在安全性和实用性方面的争议] 不同观点： • **支持 Sanitizer API** - 认为浏览器内置的 Sanitizer API 可以替代第三方库（如 DOMPurify），提供更安全和便捷的 HTML 清理功能。 - 通过 `setHTML()` 方法避免解析-序列化-解析（MXSS）漏洞，提升安全性。 - 适用于富文本编辑器（RTE）等场景，作为防御的额外层级。 • **质疑 Sanitizer API 的可行性** - 认为 HTML 清理问题本质上是“未明确且无法满足”的，无法通过新 API 彻底解决。 - 指出 `innerHTML` 和 `textContent` 等现有工具已足够，关键在于区分信任与非信任输入。 - 认为白名单比黑名单更安全，Sanitizer API 的设计可能忽略了这一经验。 • **其他补充观点** - 建议使用 XHTML 替代 HTML，以避免解析不一致性问题。 - 认为服务器端验证仍是必要的，Sanitizer API 仅适用于客户端展示时的清理。 - 提出增加 `` 标签的替代方案，以更直观地处理非信任内容。 补充讨论： - **争议焦点**：Sanitizer API 是否能真正解决 HTML 清理的安全问题，还是仅仅转移了问题。 - **讨论关系**：支持者强调其技术优势，反对者则认为问题根源在于 HTML 本身的复杂性，而非缺乏 API。 - **其他建议**：部分用户提出替代方案（如 XHTML 或 `` 标签），并强调服务器端验证的重要性。
