Erlang/OTP 29.0

作者: pyinstallwoes | 评分: 209 | 评论数: 9 | 发布时间: 2026-05-15 23:33
文章摘要

Erlang/OTP 29.0 是重大版本，新增 unsafe 标注、原生记录、范围整数守卫、多值推导式、文档示例测试等；强化安全默认配置（SSH/SFTP、量子安全密钥交换）；改进编译器/JIT并新增多项警告，同时调整代码路径和停止 Windows 32 位构建。

评论摘要
主要讨论点：围绕 Erlang/OTP 新版本改进、安全更新、Erlang 生态现状及与 Elixir/Rails 等技术的比较展开。 不同观点： • 正面评价新特性：有人认为默认关闭 SSH daemon 和 SFTP 是良好的安全改进；io_ansi 模块有助于构建复杂 CLI，且跨节点 fwrite 体现 Erlang 分布式优势；Native Records 被视为对现有 records/tuples/maps 混用局面的重要改进。 • 关注生态影响：多位评论者好奇 Native Records 将如何影响 Elixir 和 Erlang 生态，尤其是旧 records 是否会长期共存。 • 解释背景知识：有人补充说明 OTP 是一套用于构建高可靠、容错应用的库和设计原则，源自电信领域，并推荐阅读 OTP Design Principles。 • 安全升级观点：有评论提醒生产环境应尽快升级，因为旧版本存在多个 2026 年的严重和高危 CVE。 • Erlang 使用现状争议：有人询问是否还有人在新项目中使用“纯 Erlang”，以及相比 Elixir 的理由；也有人质疑“谁还用 Erlang”。 • Web 开发生产力争议：一位评论者认为 Phoenix 难用、Rails 对独立开发者更高效，LLM 写 Rails 代码效果更好，项目稳定后再用 Go 重写，并提到 Erlang 论坛本身也使用 Rails 写的 Discourse。 • 其他讨论：有人询问 WhatsApp 是否仍基于 Erlang；也有人调侃新增 unsafe attribute 是“为 Rust 重写做准备”。 补充讨论：争议焦点主要在 Erlang/Elixir 是否仍适合新项目，以及 Rails/Phoenix/Go 在开发效率与长期维护上的取舍。

Radicle: Sovereign {code forge} built on Git

作者: KolmogorovComp | 评分: 216 | 评论数: 20 | 发布时间: 2026-05-15 12:07
文章摘要

Radicle 是基于 Git 的开源点对点代码协作平台，去中心化复制仓库，用户自主掌控数据与流程。它通过加密身份、签名数据、 gossip 协议和本地优先设计，支持离线使用、抗审查协作，并提供 CLI、Web、桌面端等模块化工具。

评论摘要
主要讨论点：围绕 Radicle 作为去中心化/本地优先 Git forge 的价值、隐私安全、部署方式、生态支持与治理风险展开。 不同观点： • 支持者认为 Radicle 很有潜力：本地优先、分布式、适合替代 GitHub；有人称其“Just Works”，也有人看好其用于 agent 工作流，因其默认具备加密身份和签名产物。 • 隐私与删除问题引发担忧：去中心化系统中很难真正删除仓库或泄露的密钥；私有仓库虽可限制复制，但历史仍可能存在，类似 Matrix、BitTorrent 的删除困境。 • 私有/敏感仓库方案被质疑：评论指出 Radicle 私有仓库未加密静态存储，只依赖选择性复制，且公私仓库缺少结构隔离，误操作或 bug 可能导致泄露。 • 本地/小团队离线部署体验不足：多人希望像 on-prem GitLab 或 Fossil 一样，只在几台机器间运行，不连接公共网络；但默认会加入公共 seed 节点，配置和文档支持不足，需要脚本化绕过。 • 许可证存在争议：有人批评未采用 AGPL，担心 SaaS 公司“拥抱、扩展、消灭”；并指出 Radworks 计划提供基于 Radicle 的服务，加剧商业化担忧。 • 功能与生态问题：有人询问是否支持 Tor、Git LFS/Git Annex；也有人希望原生支持 Jujutsu（jj）仓库，而不仅是相关集成文章。 • 联邦交互的治理问题：有人关心公开仓库的 issue/merge request 是否会被任意节点骚扰，是否存在白名单或反垃圾机制。 补充讨论：还有人提到 Radicle 近期更换域名、NixOS 已打包，部分用户准备部署常驻节点；也有用户询问其核心解决的问题是否主要是反中心化与抗审查。

文章指出，随着LLM和编码代理能力提升，公开源码中的漏洞正被大规模、低成本地“批量挖掘”，导致安全报告激增且不少是真漏洞。短期内OSS维护者会面临更多告警和压力，但长期看，这种自动化扫描会帮助更快发现并修复问题，整体提升开源安全。

评论摘要
主要讨论点：AI/LLM辅助漏洞发现是否会加剧开源维护压力，以及这究竟是“安全灾难”“正常修复过程”还是安全市场演化。 不同观点： • 漏洞公开是好事：ahlCVA、xbar认为代码本来就有缺陷，发现并披露只是面对事实；把漏洞挖掘称为“掠夺”是倒退，真正令人困惑的是有人宁愿保留0day。类似数学证明被找出错误，应庆幸未来不再建立在错误前提上。 • 开源维护者不应被默认要求无偿救火：Macha、adamtaylor_13、hrjriritifif强调，用户和安全公司免费使用OSS，却期待维护者周末立刻修复并提供支持是不合理的；这是志愿劳动，若要SLA和紧急响应应付费。 • AI会扩大攻击面和发现速度，闭源也难幸免：_alternator_、mtlynch指出LLM可辅助反编译和理解二进制，闭源软件同样面临风险；开源只是更容易被扫描。gmuslera补充，闭源若源码泄露，漏洞可能长期暗中存在。 • 商业化安全投入会变得更重要：mtlynch认为不设或低额bug bounty的产品难吸引善意研究者，却会吸引攻击者；他举Kagi UXSS仅100美元，而Firefox/Chrome同类漏洞奖励达数千到上万美元为例。cyrusradfar认为企业需要更多人工安全投入、流程管控，并可通过local-first减少云端暴露。 • 这可能是技术成熟后的“二级安全市场”形成：likesHumidity类比2017年S3误配置事件，AWS推出Block Public Access、CSPM市场成熟；AI层也可能出现类似治理与防护市场。OSS承压结果取决于制度支持：FFmpeg获德国基金支持而改善，Ingress-Nginx因维护不可持续退役。 • 乐观派认为风暴会趋缓：marginalx认为短期内漏洞报告会激增，商业开源可能借“安全靠隐蔽”缓冲，但真正开源无法如此；长期看报告会平台化、回到可管理节奏。 • 怀疑或反对声音：krupan认为这是AI炒作；ryanackley提醒同时存在大量“AI垃圾漏洞报告”，如Turso因被无用报告淹没而关闭bug bounty。 补充讨论：争议焦点在于“漏洞发现速度提升”应被视为安全进步，还是对无偿维护体系的不可持续压榨；以及谁应为修复成本买单。
