主要讨论点：关于 Riscrithm（一个 RISC-V 汇编器）的设计理念和实现方式的讨论 不同观点： • **批评派（sph）**：认为项目应该使用解析层和抽象结构，而非字符串和正则表达式操作。担心这是 AI 生成的代码（"vibe coded"），如果不是初学者的诚实作品，会更严厉批评并证实对 LLM 的偏见。 • **历史对比派（Joker_vD）**：将其归类为"高级汇编器"，类似 PL/360 或 PL-11。指出 C 语言已经彻底淘汰了这类语言，因为用 PCC、LCC 或 Tiny CC 在一周内就能为合理的指令集架构构建出不错的指令发射器。 • **实用改进派（benj111）**：对项目感兴趣，提出建设性建议：1）是否强制执行寄存器变量规则（如函数参数位置）；2）不应追求一对一指令映射，应允许指令展开以实现 while 循环和更易读的 if 语句。强调理解底层机制比严格的指令对应更重要。 • **作者立场（patrick-ghetea）**：介绍项目定位为"直观的"汇编器，语法简洁且严格对应原生机器指令。承认 v1.0.0 不完美，正在开发 v1.1.0 增加新特性。 补充讨论：核心争议在于设计哲学——是否应该保持与机器指令的严格一对一映射，以及实现质量是否达到专业水准。

Didgeridoo playing as alternative treatment for obstructive sleep apnoea (2006)

作者: kelseyfrog | 评分: 329 | 评论数: 29 | 发布时间: 2026-05-23 01:37
文章摘要

这项随机对照试验研究了吹奏迪吉里杜管（didgeridoo，澳洲土著乐器）对中度阻塞性睡眠呼吸暂停综合征的治疗效果。25名患者被分为两组，治疗组每天练习约25分钟，持续四个月。结果显示，与对照组相比，治疗组的日间嗜睡程度显著改善（-3.0分），呼吸暂停低通气指数显著降低（-6.2），伴侣报告的睡眠干扰也明显减少（-2.8分）。研究认为，定期吹奏迪吉里杜管通过训练上呼吸道肌肉，是一种有效且患者接受度高的替代治疗方法。

评论摘要
主要讨论点：迪吉里杜管（didgeridoo）及其他管乐器演奏对睡眠呼吸暂停和打鼾的治疗效果 不同观点： • **支持演奏疗法**：多位用户分享亲身经历，证实迪吉里杜管演奏有效改善睡眠呼吸暂停。Darmani通过10年练习预防复发；ElijahLynn正在进行3个月实验验证；Ringz发现演奏后鼻腔通畅效果显著 • **替代方案**：jph00通过口咽肌肉锻炼（嚼口香糖、充分咀嚼食物）完全治愈睡眠呼吸暂停，无需CPAP；hks0的朋友用吸管吹水泡取得类似效果，还意外减重；carwyn提出双簧管等需要更高气压的乐器可能效果更好 • **实用性质疑**：wiredfool和asdff指出迪吉里杜管演奏噪音大，会影响伴侣和邻居睡眠，具有讽刺意味 • **研究方法缺陷**：data-ottawa批评研究对照组仅为等待名单，未控制运气因素 补充讨论：idiocrat发现研究中吹嘴直径单位错误（应为厘米非毫米）并建议DIY制作；DTrejo提醒胃食管反流与睡眠呼吸暂停相关，推荐吸气肌训练；部分用户分享循环呼吸技巧和无关音乐推荐。

Defeating Git Rigour Fatigue with Jujutsu

作者: ikesau | 评分: 175 | 评论数: 36 | 发布时间: 2026-05-24 18:39
文章摘要

这篇文章介绍了使用 Jujutsu 版本控制系统解决"Git 严谨疲劳"的技巧。 **核心问题：** 开发大功能时，很难保持提交历史整洁。实际开发中常产生混乱的提交序列，后续提交会覆盖早期工作。 **解决方案：** 先创建理想的空提交结构（按功能模块划分），然后将所有实际改动合并到一个"大杂烩"提交中，最后使用 `jj squash -i` 交互式地将相关改动分拣到对应的空提交里。 **优势：** 比开发过程中维持严格提交规范更轻松，避免了频繁的合并冲突，可以在开发结束时一次性整理所有提交。 **缺点：** 无法保证每个提交都能编译通过。

评论摘要
主要讨论点：Jujutsu (jj) 版本控制工具相比 Git 的优劣 不同观点： • **反对派 - 分支管理问题**：y1n0 认为 jj 的分支管理极其繁琐，在多人协作场景下需要手动维护分支指向，不如 Git 的命名分支简单直接，无法满足多分支并行工作需求 • **反对派 - 工作流冲突**：gertburger 指出 jj 强制追踪所有文件的设计破坏了工作流程，无法像 Git 那样保持工作区"脏"状态，影响跨分支调试等临时性工作 • **支持派 - 工作流优势**：nozzlegear 和 danborn26 认为 jj 的"工作副本即提交"设计更符合心智模型，`jj new` 创建变更的方式比传统的先写后提交更符合直觉，解决了 Git rebase 的诸多摩擦点 • **支持派 - 历史整理便利**：stouset 和 winterqt 强调 jj 在维护理想化提交历史方面更自然，`jj absorb` 等工具比 Git 更智能地处理变更分配 • **中立派 - Git 已足够**：BobbyTables2 和 binarin 认为 Git 的 `rebase -i`、`git history split` 等功能已经能系统化地处理历史整理，actinium226 质疑 jj 与 Git 操作的本质区别 补充讨论：drdrey 反思是否值得追求"完美提交"；singiamtel 因 lazygit 工具成熟而暂不切换；sharts 质疑大多数项目是否需要 Git；nextaccountic 期待同时保留真实历史和整理后历史的 VCS
