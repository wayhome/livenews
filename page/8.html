Researchers value null results, but struggle to publish them

作者: Bluestein | 评分: 132 | 评论数: 15 | 发布时间: 2025-07-23 09:16
文章摘要

一项由Springer Nature开展的调查显示，虽然98%的科学家认可无效结果（即未证实预期假设的结果）的价值，并且85%的科学家认为分享这些结果很重要，但只有68%产生过无效结果的科研人员实际分享了这些结果，且仅30%尝试将其发表在期刊上。科研人员不愿发表无效结果的原因包括担心不被接受、不知哪些期刊会考虑发表、出版费用问题以及同行负面评价的顾虑。然而，分享无效结果有助于激发新假设、改进方法论并避免不必要的重复研究。专家指出，发布无效结果能更真实地反映科研现状，提高研究的可靠性。

评论摘要
主要讨论点：学术研究中无效结果（null results）的发表问题 不同观点： • **无效结果的价值差异**：[pacbard] 认为并非所有无效结果都一样，有些具有重要意义，如Card & Krueger (1994) 的研究推翻了增加最低工资会减少就业的假设。然而，其他由于实验设计问题或数据不精确导致的无效结果则较难发表，因为它们缺乏新意。研究人员很难预判会得到"有意义的无效结果"还是"无用的无效结果"，且后者可能影响职业发展或资金申请。 • **职业与 tenure 压力**：[BrenBarn] 指出，无效结果难以成为主流发表的原因在于学术界的职业压力，特别是在 tenure 评审过程中，无效结果的发表价值不高。除非无效结果能够帮助获得职位或 tenure，否则研究人员不会主动发表这些结果。 • **无效结果的稀缺性与实用性**：[bkanuka] 提到，在物理学领域中，找到可引用的无效结果非常困难，而这些结果在提出新实验或为非无效论文提供背景信息时是有用的。因此，提议创办"无效科学期刊"以收集这些结果。 • **无效结果的篡改为阳性结果**：[alex-moon] 强调，无效结果有时被篡改为阳性结果，以符合研究人员的假设，这会影响研究的质量。此外，研究人员可能为了对冲风险而设计研究，试图涵盖多个变量，导致无法深入研究某一问题。 • **无效结果的发表缺乏激励**：[j7ake] 认为，研究人员缺乏发表无效结果的个人激励，因为这些结果是产生"光鲜"结果的基础。发表无效结果相当于放弃竞争优势，浪费时间。 • **无效结果的发表形式**：[simpaticoder] 建议将无效结果以列表形式发表，如"10个有机化学家相信的谬误！" 然而，这也可能导致滥用，因为一些无效结果可能涉及不被广泛认可的假设，从而降低发表质量。 • **行业中的无效结果价值**：[janalsncm] 指出，在工业界，无效结果非常有价值，因为它们可以避免重复浪费时间和资源。但在学术界，研究人员可能不愿分享这些结果。 • **无效结果发表的期刊解决方案**：[andix] 建议期刊专门设立无效结果栏目，并分配固定页数，以鼓励研究人员发表这些结果。 • **无效结果发表的平台与方式**：[Nevermark] 提议创建一个专门发布无效结果的网站，具备良好的关键词搜索功能，较低的发表要求，并允许公开投票和评论，以增加研究人员的参与和反馈。 补充讨论： • **具体实例**：[sumanthvepa] 提到著名的Michelson-Morley实验，作为科学史上重要的无效结果之一。 • **期刊的偏见**：[bhk] 暗示像《Nature》这样的期刊在发表无效结果方面存在偏见。 • **自助发表的可能性**：[qcnguy] 认为研究人员可以将无效结果发布在arXiv或个人网站上，但问题在于难以获得学术界重视和职业发展所需的关注度。

What is X-Forwarded-For and when can you trust it? (2024)

作者: ayoisaiah | 评分: 59 | 评论数: 11 | 发布时间: 2025-07-23 10:18
文章摘要

《X-Forwarded-For是什么，何时可以信任它？》一文介绍了X-Forwarded-For HTTP头的作用和信任问题。该头部用于显示客户端请求的原始IP地址，尤其在请求经过多层代理或负载均衡器时，帮助后端应用了解请求的真实来源。典型情况下，服务器只能看到最后一个代理的IP，而X-Forwarded-For能提供完整的IP链路。 **应用场景**包括用户认证、负载均衡、数据本地化、内容分发、访问控制、安全过滤、防欺诈、API限流、广告定位以及日志分析等。 **信任问题**：由于HTTP头可以被伪造，X-Forwarded-For的内容不应完全信任。可通过可信代理列表或代理计数来验证IP的有效性。此外，需注意解析X-Forwarded-For头时可能遇到的多种问题，如无效IP、分隔符解析错误、多个头存在以及潜在的代码执行风险。 **替代方案**包括Forwarded头部、X-Forwarded-Host/Proto和Via头部等。总结来说，X-Forwarded-For在提供请求来源信息方面非常有用，但需谨慎处理信任问题。

评论摘要
主要讨论点：X-Forwarded-For (XFF) 头的使用、安全性和替代方案 不同观点： • francislavoie 分享了一个深入讨论 XFF 的文章链接，并提到在 Caddy 中实现了 "trusted proxies" 系统，用于安全地获取客户端 IP。 • MajesticHobo2 指出 XFF 解析错误是一个常见问题，并提到在应用程序中渲染用户 IP 时可能引发 XSS 漏洞。 • nfriedly 提到在率限制库中遇到的 XFF 配置问题，包括忽略XFF头导致负载均衡 IP 被限制，或盲目信任 XFF 头导致限制被绕过，最终通过运行时检查和文档链接降低了支持负担。 • Avamander 建议尽可能不使用 XFF，推荐使用 "Forwarded" 头，认为其更优。 • pityJuke 分享了通过更改 header 绕过地域限制观看 South Park 的经历。 • 0points 提到 XFF 可以用于绕过地理封锁。 • nodesocket 提到 Python 的 proxy_fix 模块需要配置信任的 XFF IP 条目数量。 • vlod 提到 nginx 使用中遇到的问题，希望从 Cloudflare 获取 IPv4 地址而非 IPv6 地址。 • SSchick 提供了一个关于代理后使用 Express 的指南链接。 • knorker 详细描述了如何维护信任 IP 列表并从中获取真实客户端 IP，指出文章遗漏了检查实际 TCP 连接远程地址的步骤。 • westurner 引用文章和维基百科内容，强调完全替换不可信的 XFF 数据以确保安全，并提到 RFC 7239 对 "Forwarded" 头的标准化。 补充讨论： • XFF 头的安全问题，如 IP 欺骗和 XSS 攻击，是讨论的核心。 • 不同工具和框架中对 XFF 和 Forwarded 头的处理方式不同，如 Python 的 proxy_fix 和 nginx 的配置。 • 使用 WAF（Web 应用防火墙）检测和阻止头注入攻击的建议。 • RFC 7239 对 Forwarded 头的标准化及其潜在优势。 • 实际应用中，XFF 头可能被用于绕过地域限制。 争议焦点： • XFF 头是否应继续使用，还是应被 "Forwarded" 头取代，存在不同意见。 • 如何正确配置和信任 XFF 头以防止安全漏洞，尤其是在多层代理环境下。

It's a DE9, not a DB9 (but we know what you mean)

作者: jgrahamc | 评分: 416 | 评论数: 44 | 发布时间: 2025-07-25 13:35
文章摘要

本文讨论了D-sub连接器的命名误用，特别是常见的9针串行端口连接器。虽然广泛被称为"DB9"，但技术上正确的命名应为"DE9"。"D"代表D型金属屏蔽，"E"表示壳体大小容纳9针，而"DB"实际上是指25针的连接器。这一错误源于IBM PC/AT引入9针串口时，人们习惯性地将"DB25"的命名方式套用到新连接器上，导致"DB9"这一不准确的称呼广泛传播。SparkFun在推出新的DE9连接器分线板时，选择使用正确的技术命名以推广准确性。文章强调了技术准确性的重要性，并解释了命名背后的原因。

主要讨论点：技术术语的准确使用与沟通的有效性之间的平衡 不同观点： • dlcarrier：认为在文档中应使用标准机构的术语（如8P8C），但在日常交流中可以使用更常见的术语（如RJ45），以确保沟通的清晰性。 • mark-r：对将DB-25称为旧并行端口连接器提出异议，指出其更早用于RS-232串行端口，并行端口通常使用更大的Centronics连接器。 • zettabomb：赞赏D-sub连接器的持久性，指出其在军事和现代空间硬件中的应用，尽管个人不优先选择使用。 • Cyan488：幽默地建议Sparkfun应纠正“传统电流”的长期混淆。 • 9rx：质疑“DB9”术语不准确的说法，认为即使没有实际制造，DB壳中也可以容纳9针连接器。 • alnwlsn：指出技术术语的混用常见，尤其是在连接器常用于特定用途时，如“复合视频”和其他视频相关术语。 • alnwlsn：进一步提到“Amphenol连接器”、“Cannon连接器”或“Molex连接器”类似于说“福特汽车”。 • brudgers：认为未误用D-sub术语，因为大家在玩一种不同的“语言游戏”，沟通有效即可。 • dec0dedab0de：个人习惯称串行端口，因记不住DB9，但希望记住这些细节以备将来使用。 • djaychela：认为在交流中使用更通俗的术语（如“kettle lead”）比坚持技术准确性更有效。 • shermantanktop：技术上的咬文嚼字虽有趣，但语言的首要目的是沟通，最正确的语言是能最佳传达信息的语言。 • 1970-01-01：以VGA、键盘鼠标端口为例，幽默地指出无法联系到旧打印端口（DB-25）以发表意见。 • gchadwick：好奇为何D-sub壳大小和针脚编号分开定义，质疑是否有计划在同一壳中使用更少针脚。 • Findecanor：提到存在非标准的D-subminiature连接器，如Amiga使用的23针连接器。 • andix：认为继续使用DB9术语大家都能理解，不会引起误解也不浪费时间讨论术语。 • cwillu：认为DB更容易发音，且大家都明白其含义，坚持使用DB9术语，认为标准应考虑人类习惯。 补充讨论： • 技术准确性与沟通效率之间的矛盾是主要争议焦点，部分人支持使用标准术语以保证准确性，另一部分人则认为应使用通俗术语以确保沟通顺畅。 • D-sub连接器的历史和应用也得到了讨论，展示了其在不同领域中的持久性和适应性。 • 讨论中还涉及到其他技术术语的混用现象，反映了技术语言在演变中的多样性和复杂性。
