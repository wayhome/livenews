文章摘要

**go-mcp** 是一个用于构建 MCP（Model Context Protocol）服务器的 Go SDK，提供类型安全和直观的接口，简化了服务器开发过程。其主要特点包括：类型安全、简单直观的 API、以及对开发者友好的设计。 **快速开始**： 1. **定义 MCP 服务器**：通过创建 `cmd/mcpgen/main.go` 文件生成必要代码，运行 `go run ./cmd/mcpgen` 生成代码。 2. **实现 MCP 服务器**：在 `cmd/temperature/main.go` 中实现服务器逻辑，运行 `go run ./cmd/temperature` 启动服务器。 **示例**展示了如何创建一个温度转换工具，处理温度单位转换逻辑并返回结果。该项目遵循 MIT 许可，已有 57 个星标和 1 个分支。

文章摘要

Reflections on Unikernels

作者: todsacerdoti | 评分: 4 | 评论数: 0 | 发布时间: 2025-04-17 23:19
文章摘要

Unikernels是单一用途的云计算设备，将应用程序与其所需的一切（包括内核驱动程序）打包成一个二进制文件运行。它们允许我们重新思考旧的操作系统接口，并移除过去几十年积累的不必要代码层。现代通用操作系统庞大复杂，难以实验全新设计。Unikernels也是“库操作系统”（library OSes），其中网络栈和设备驱动作为库与自定义应用程序逻辑链接成单一二进制文件。MirageOS是一个基于OCaml的unikernel项目，提供如TCP/IP栈、DNS客户端和服务器、Xen磁盘和网络驱动等库。这些库也可用于传统操作系统中，例如Docker Desktop中使用unikernel的TCP/IP栈解决网络问题。 Unikernels因仅链接所需代码，具有较小的攻击面，适合高安全性应用。例如，Xen的"xenstore"服务被移植到MirageOS上作为独立unikernel VM运行，提高了安全性，并通过OCaml Irmin库实现状态恢复。Unikernels还用于增强QubesOS等系统的安全性，使用unikernel作为防火墙组件。 Unikernels允许实验新的接口设计，例如通过网络请求生成unikernels，并通过共享内存传输TCP连接状态。自MirageOS以来，出现了其他unikernel项目，如UniKraft。

eInk Mode: Making web pages easier to read

文章摘要

Eink模式是一种专为电子墨水（E Ink）设备设计的网页浏览模式，旨在提供类似阅读纸质书的沉浸式体验。通过将网页内容以分页形式呈现，用户可以通过点击屏幕左右两侧来翻页，而不是传统的滚动浏览。该模式隐藏了大部分用户界面元素，专注于内容展示，并在屏幕右下角显示页码图标以指示浏览位置。Eink模式还支持多种手势操作，如从底部上滑跳至网页顶部，或从上往下滑到网页底部。使用E Ink设备如电子阅读器、E Ink平板或显示器时，建议将设备刷新模式设为快速刷新以获得最佳体验。网页上出现Eink图标即表示支持该模式，点击图标或从左向右滑动即可进入。

Cutting down Rust compile times from 30 to 2 minutes with one thousand crates

作者: Qadriq | 评分: 112 | 评论数: 17 | 发布时间: 2025-04-17 11:22
文章摘要

Gerd Zellweger分享了在Feldera工作中如何将Rust编译时间从30分钟大幅减少到2分钟的经验。Feldera让用户用SQL定义表和视图，这些SQL被编译成Rust代码，然后由`rustc`编译成单一二进制文件。随着新企业客户使用更复杂的SQL，生成的Rust代码达到约10万行，编译时间显著增加，达到25至45分钟。 尽管采取了多种优化措施，如类型擦除和代码去重，编译时间仍不理想。分析发现，编译时间主要消耗在LLVM和代码生成阶段，且这些过程是单线程的。作者通过一系列优化，包括减少不必要的编译单元、优化依赖管理等，成功将编译时间缩短至2分钟。关键措施包括： 1. 使用更细粒度的Crate划分。 2. 确保增量编译有效性。 3. 利用并行编译和缓存。 最终，通过这些优化，在保持发布模式性能的同时，显著缩短了编译时间。

评论摘要
主要讨论点：Rust程序编译的性能与效率问题，尤其是与C语言的对比，以及在大型项目中如何优化编译时间和处理多线程编译的挑战。 不同观点： • [1vuio0pswjnm7] 认为需要比较Rust和C在编译过程中的能量消耗、时间成本和存储成本，以明确两者之间的权衡。如果差异不大，可能值得为了更高的目标做出这种权衡。 • [wiseowise] 通过计算指出，尽管有128个线程，Rust编译时间依然较长，Amdahl’s Law（阿姆达尔定律）解释了这种现象，即并行计算的加速受限于串行部分。 • [HippoBaro] 解释了Rust编译单元（crate）的特性，指出Rust编译器的并行机会有限，因为rustc将大量工作交给主要是单线程的LLVM。同时，编译过程中会产生大量中间文件和重复工作，这影响了性能。 • [dathinab] 强调Rust的一个编译单元是一个crate，而C语言是一个文件，这种差异带来了优缺点，如需要将大型项目拆分为多个工作区以最大化并行构建。 • [hu3] 提到使用64核机器时，Rust并没有充分利用多线程，但通过拆分crate可以将编译时间从30-45分钟减少到3分钟以下，并建议将这些技巧自动化以使更多项目受益。 补充讨论： • [Crisco] 提出拆分crate是否会对最终二进制文件的性能产生影响。 • [ay] 分享了一个自动化工具，用于处理生成代码的修改过程。 • [nixpulvis] 认为Rust作为中间语言在编译/转译过程中可能并不理想，尽管Rust的类型系统有助于编译器开发。 • [jmull] 讨论了生成Rust代码的优缺点，指出虽然可以利用Rust的类型检查系统，但也被限制在Rust编译器上，可能有更直接的方法实现动态约束。 • [skeptrune] 建议Rust文档需要更多强调将代码库拆分为多个小crate是减少编译时间的“正确”方法。 • [dietr1ch] 认为编译时间缩短的线性加速在链接部分可能不会实现，甚至可能更慢，需要权衡使用过多crate的成本。 • [lesuorac] 质疑仅使用调试版本是否真的不可行，提出可以在测试时仅对部分crate进行优化编译以提高性能。 • [kzrdude] 建议对依赖项使用完全优化的编译，而对主crate使用较低级别的优化，以提高编译效率。 • [xrisk] 提出动态链接是否能缓解多crate编译的问题。 争议焦点： • Rust编译过程中的多线程利用效率问题，特别是与C语言的对比。 • 将大型项目拆分为多个crate的优缺点，尤其是对编译时间和最终二进制文件性能的影响。 • 生成Rust代码的优缺点以及是否存在更直接的方法实现动态约束。
