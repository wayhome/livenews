Upcoming breaking changes for npm v12

作者: plasma | 评分: 306 | 评论数: 26 | 发布时间: 2026-06-09 21:01
文章摘要

npm v12（预计2026年7月发布）将引入三项安全相关的默认变更： 1. **allowScripts默认关闭**：`npm install`将不再自动执行依赖包的preinstall/install/postinstall脚本（包括node-gyp构建），需通过`npm approve-scripts`显式允许可信包。 2. **--allow-git默认为none**：不再自动解析Git依赖，需显式启用。 3. **--allow-remote默认为none**：不再自动解析远程URL依赖（如https压缩包）。 **准备建议**：升级到npm 11.16.0+，运行安装查看警告，使用`npm approve-scripts`审核并批准可信脚本，将配置提交到package.json。

评论摘要
主要讨论点：npm v12 默认禁用安装脚本的安全更新 不同观点： • **积极支持派**：认为这是重要的安全进步，修复了10年前就已披露的漏洞（VU#319816），npm终于跟进了pnpm 18个月前的做法，对供应链攻击提供了防护 • **质疑有效性派**：指出恶意代码可以从安装脚本转移到模块本身，在首次运行时仍会被执行；认为这只是将攻击窗口从安装时转移到运行时，并未根本解决问题 • **改进建议派**：建议添加1天年龄限制默认值，给安全扫描器留出时间；询问是否有linter工具可以防止包管理器配置不安全的默认设置 技术关注点： • 白名单机制是否支持包级别而非全局设置（有利于组织级规则维护） • 白名单是否锁定包版本还是仅包名 • Node.js LTS版本（22/24/26）是否会更新捆绑的npm到v12 • 全局安装包时allowScripts是否也默认禁用 • yarn是否也实施了类似的供应链攻击防护 • 何时能实现只读的node_modules并摆脱vendored依赖 补充讨论：有人刚得知npm被GitHub收购，评论"这就说得通了"

Lies we tell ourselves about email addresses

作者: theanonymousone | 评分: 131 | 评论数: 32 | 发布时间: 2026-06-08 14:24
文章摘要

这篇文章主要讨论了电子邮件地址验证的常见误区。核心观点是：**不要过度验证邮件地址，直接发送验证邮件即可**。 文章指出使用正则表达式验证邮件的三大问题：性能开销大、容易出错、标准随时间演变。作者认为输入验证应该帮助用户避免简单错误，而不是用来"防范"用户。 建议的最佳实践： 1. 如果必须验证，使用最简单的正则（如`^[^@]+@[^@\s]+$`）仅确保格式为"某内容@某内容" 2. 前后端使用相同验证逻辑 3. 通过发送验证邮件来确认地址有效性，而非复杂的格式检查 文章强调邮件系统历史悠久、标准复杂多变，即使技术上"合法"的地址也可能不被主流服务支持。过度验证会误伤真实用户。

评论摘要
主要讨论点：邮箱地址验证的技术实现与用户体验之间的权衡 不同观点： • **宽松验证派**：认为应尽可能少限制邮箱格式，只需验证基本结构（如`^[^@]+@[^@\s]+$`），因为技术上合法的邮箱地址经常被错误的正则表达式拒绝。例如带多个点号的地址（sean@foo.bar.baz）、新顶级域名（.healthcare、.consulting）和特殊字符的地址被广泛误判。 • **保守验证派**：主张限制性验证以避免未来系统问题。认为应拒绝"过于不同"的邮箱格式，因为收集的邮箱会在未来多个系统中使用，兼容性比包容性更重要。建议要求域名中必须有点号等基本规则。 • **用户能力质疑派**：反对"2026年用户都会正确输入邮箱"的假设。指出许多非技术用户记不住完整邮箱地址（包括本地部分、域名、语法），单纯的邮件验证不足以发现拼写错误（如.com打错），针对特定用户群体的限制性验证反而更友好。 • **国际化争议**：关于非ASCII字符邮箱，有人认为跨语言沟通时ASCII更便携实用（如电话传递、国际交流），也有人质疑Unicode的可靠性和统一性。 补充讨论：开发者普遍使用过于复杂的正则表达式；邮箱隐私保护的不当实现（如j*h@gmail.com对个人域名无效）；Gmail地址被他人误用的困扰。

Making Graphics Like it's 1993

作者: sklopec | 评分: 909 | 评论数: 66 | 发布时间: 2026-06-09 10:46
文章摘要

Catlantean 3D是作者用业余时间开发超过一年的第一人称射击游戏项目，计划明年在Steam发布。项目核心理念是使用90年代早期的图形技术从零开始制作完整游戏，包括手工渲染、音频混音、320x240分辨率、256色调色板等严格限制。 文章重点介绍了调色板渲染技术：模仿VGA Mode 13h显示模式，每个像素用单字节索引256色调色板。作者精心设计了768字节的调色板，包含透明色、黑白、大量红色（血液）、RGB三色（钥匙门）、沙漠色调（埃及风格场景）和灰色（科技设施）。这种技术限制反而让画面更清晰锐利，如同《毁灭战士》和《毁灭公爵》的经典风格。

评论摘要
主要讨论点：一篇关于90年代风格射击游戏开发的技术文章引发的怀旧与技术讨论 不同观点： • **技术实现派**：多位开发者分享90年代图形编程经验，包括光照贴图技术、固定点数学优化、调色板动画等tricks。强调当时直接操作显存(0xA0000)的简单直接，以及在硬件限制下的创造性优化 • **引擎架构讨论**：指出文章采用类似Wolfenstein 3D的光线投射引擎(垂直墙面、恒定高度)，而非Doom的BSP引擎。后者更灵活但仍是2.5D，无法实现真正的多层结构 • **创作理念赞赏**：多人赞同自我设定限制反而能激发创造力，类似80年代街机游戏的多样性。认可"理性推理+直觉审美"的混合创作方法 • **工具链关注**：欣赏作者自制Python工具(碎片动画生成、Blender导出等)，称赞其技术与艺术的全能性极为罕见 • **文化怀旧**：详细回忆1993年作为"互联网前时代最后美好年份"的社会文化背景，将Wolfenstein/DOOM的震撼与当时技术认知局限联系起来 补充讨论：有人注意到游戏主角可能是雌性(三色猫通常为母猫)；有评论特别感慨文章没有"让AI代劳"而是真实的创作过程；现代开发者通过PlayStation等复古平台重温底层优化乐趣

Grit: Rewriting Git in Rust with agents

作者: cbrewster | 评分: 71 | 评论数: 20 | 发布时间: 2026-06-09 19:58
文章摘要

作者使用 AI agents 将 Git 用 Rust 重写，创建了名为 Grit 的项目。Grit 是基于库的、内存安全的 Rust 实现，通过了 99% 以上的 Git 测试套件（超过 42,000 个测试）。 与 C Git 不同，Grit 设计为可重入、可链接的核心库，而非依赖 fork/exec 的命令链。这使得它能够嵌入到 GitButler、Jujutsu 等工具中，解决网络功能不完整的问题。未来还可能构建 WASM 版本，在边缘函数中运行完整的 Git 命令。 目前 Grit 仍处于早期阶段，存在性能问题且未经实际使用测试，但为构建现代化的 Git 工具链提供了有前景的起点。

评论摘要
主要讨论点：关于用AI将Git用Rust重写的项目引发的争议，核心焦点集中在许可证问题、实用性质疑和AI辅助开发的意义。 不同观点： • **许可证争议方**：强烈质疑项目将GPL许可改为MIT的决定。认为即使是LLM生成的代码，基于GPL项目的完整测试套件开发仍应视为衍生作品，更改许可证是对原作者的不尊重，破坏了开源信任。这来自GitHub联合创始人让问题更严重。 • **实用性质疑方**：认为Git已经足够稳定可靠，10多年来从未出现内存溢出等问题，即使20人以上团队也很少碰到Git限制。质疑Rust重写的必要性，认为这更像是炫技而非解决实际问题。 • **AI开发乐观派**：认为AI降低了重新实现的成本，原本需要数年的项目现在几个月甚至几周就能完成。重新实现易于测试，商业护城河因实现难度而消失。有开发者分享了用类似方法重写nginx、Redis等项目的经验。 • **哲学分歧方**：反对放弃Git的Unix哲学（简单命令链接），认为Unix哲学在当前时代仍然重要，是特性而非缺陷。 补充讨论：有人提到已存在的gitoxide项目进展良好；二进制文件体积问题（31MB vs 原版4.7MB）；以及对项目长期维护策略和社区贡献模式的疑问。

这篇文章揭露苹果即将推出首款折叠屏iPhone的迹象。在2026年开发者大会上，苹果用折纸应用作为演示样本，暗示折叠设备的到来。iOS 27测试版代码中发现了"foldState"和"angleDegrees"等折叠相关参数，以及查询设备显示屏数量的新API。苹果强调应用需支持动态尺寸和纵横比，并推出可调整大小的iOS模拟器。据报道，这款名为iPhone Ultra的折叠手机配备7.7-7.8英寸内屏和5.3-5.5英寸外屏，售价约2000美元，计划9月随iPhone 18 Pro发布，由新任CEO John Ternus主导推出。

评论摘要
主要讨论点：Apple即将推出折叠屏iPhone的利弊及市场定位 不同观点： • **支持派**：折叠屏是革命性升级。用户强调阅读/浏览体验大幅提升，对非PC用户尤其重要；展开后可同时显示地图详情、消息列表等，多任务处理能力强；相机取景、文字显示等场景实用性高。已使用者表示"不会回头"。 • **怀疑派**：认为折叠屏是厂商创新枯竭的表现，更希望研发投入可持续材料和易维修设计；批评设备过厚影响便携性，屏幕尺寸从9:16变为1:1对媒体消费无实质提升；质疑耐用性问题（有用户遇到屏幕坏点）。 • **实用主义者**：iPad mini+普通手机组合成本更低（$600 vs 折叠屏高价）且更可靠；部分用户认为缺少键盘才是限制因素，折叠屏无法解决核心痛点。 • **商业视角**：有人认为Apple推出折叠屏是迫于股东压力和市场竞争（对标三星），并非真正创新需求；也有人指出折叠屏耐用性差可能成为Apple刺激换机的策略。 补充讨论：软件适配是关键挑战。Android折叠屏已运行7年但应用支持仍不完善；开发者呼吁跨屏幕尺寸的自适应设计，但也承认这会大幅增加UI复杂度。Apple的优势可能在于软件生态整合（iPhone变iPad体验）。老年用户（70岁以上）被认为是潜在目标群体。
