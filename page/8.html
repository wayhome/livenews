A SQL-Inspired Query Language Designed for Event Sourcing (2025)

作者: goloroden | 评分: 34 | 评论数: 4 | 发布时间: 2026-05-13 19:02
文章摘要

文章介绍了 EventQL：一种为事件溯源场景设计、类似 SQL 的查询语言。它能针对事件类型、主题层级、时间戳和嵌套数据进行过滤、排序、聚合与投影，适合利用索引高效查询事件流。EventQL 强调显式 `PROJECT INTO`、主题层级匹配和 SQL 式表达能力，使查询更直观且便于优化。作者还提到将原先为 GethDB 编写的 EventQL 解析器重构为独立、生产可用的 Rust 库，支持完整语法、强类型 AST 和详细错误信息。

评论摘要
主要讨论点：事件查询语言/事件数据库是否有必要，以及如何与事件驱动/事件溯源工作流结合。 不同观点： • 有人指出“EventQL”已经存在，并给出项目与演讲链接，暗示该方向并非全新。 • 有人认为方案“思路不错”，但核心问题是如何接入 reactive workflows；他更倾向于一种面向事件溯源的查询语言，而不是传统数据库式设计。 • 另一方则认为没必要单独做此类系统：事件在设计良好时可直接展开成普通表结构；借助 Trino/Presto/Athena 可对 JSON 字段深度查询，配合 Parquet、标准 envelope、rollup 和 snapshot，已能处理很大规模数据。 补充讨论：争议焦点在于“是否需要专门的事件查询语言/数据库”，还是现有通用数据库与数据湖工具已足够。

Solar-based sleep patterns compared to modern norms

作者: James72689 | 评分: 113 | 评论数: 21 | 发布时间: 2026-05-15 04:15
文章摘要

文章认为，连续八小时睡眠是现代9-5制度和人工照明的产物。传统地中海农耕社会顺应日照与季节：夏有午睡、冬有“二段睡”。作者赞赏希腊仍保留午休与分段工作，认为这更符合自然节律。

评论摘要
主要讨论点：午睡/分段睡眠（siesta、polyphasic sleep）与现代9-5工作制、商店营业时间是否冲突，以及这种作息到底是“自然”还是被浪漫化。 不同观点： • 质疑派：西班牙用户认为午睡被过度美化，虽有健康益处，但会压缩白天可用时间；8小时工作制下很难安排，学校和工作制度也因此混乱。 • 支持派：有人认为地中海作息更灵活，下午下班后商店、牙医、餐馆仍开着，方便办事；也有人觉得炎热季节“晚睡+午休”更合理。 • 历史/科学争论：有人说分段睡眠是现代工业社会前就存在的普遍模式；反对者指出缺乏确证，工业化并非处处同步。也有人补充现代平均睡眠比百年前少，睡眠时长本身就受现代生活影响。 • 现实批评：有人认为9-5和过早开工、过少服务时间在“惩罚”上班族，连办事、取包裹都困难。 • 折中观点：睡眠应因人因地而异，受纬度、光照、孩子、疲劳程度影响；与其坚持某种“标准”，不如多实验找适合自己的节奏。

Git Is Not Fine

作者: steveklabnik | 评分: 41 | 评论数: 7 | 发布时间: 2026-05-15 17:51
文章摘要

文章批评 Git 主要擅长分布式存储，却把协作工作流当成附带功能，导致堆叠 PR、异步开发、追踪后继提交/重写历史等场景很别扭；作者借此推荐 jj，认为它更适合现代分布式协作。

评论摘要
主要讨论点：Git 是否足以应对复杂分支/堆叠 PR 工作流，还是需要 jj 这类新工具。 不同观点： • 认为 Git 已够用：有人表示看不懂作者说的 workflow，也不觉得 stacked PR 有必要；自己靠 commit + rebase 就能保持整洁，常见场景下不需要 20 张图解释。 • 认为 Git 在复杂场景下很痛苦：monorepo 开发者提到同一时刻会产生多组改动，需要分别进 branch #1/#2/#3，且它们彼此依赖；切分支、stash、worktree 都不够顺手，因此更偏向 jj。 • 认为复杂度被夸大：有人觉得文章“太啰嗦、像在制造复杂性”，手工重写 PR 堆栈、`git branch -f` 也能解决；现在甚至可交给 AI 做 rebase。 • 认为问题在 Git 设计目标：有人指出 Git 强调完全分布式，因此若内建某些“可变状态/集中式便利”，会牺牲分布式特性，并非绝对优劣。 补充讨论： • 争议焦点在于：堆叠 PR、可变工作区、部分提交状态是否是“真实刚需”还是少数人的特殊需求。 • 还有人提到 Meta 用过基于 Mercurial 的内部系统，暗示大厂早已用别的方案缓解 Git 痛点。

《Category Theory for Tiny ML in Rust》是一本公开工作草稿，用范畴论指导用 Rust 构建小型机器学习系统，将对象、态射、组合、训练等落实为类型化代码。文章介绍了书籍目标、GitHub 仓库、公开 workshop、两位作者背景，并征集针对内容、代码和术语的反馈。

评论摘要
主要讨论点：评论集中在该书/文章将范畴论、Rust 与机器学习结合的必要性、深度与表达方式上。 不同观点： • 范畴论“贴上去”的批评：stschaef 认为书中范畴论内容埋得很深，缺少清晰的对象与态射定义，也没有给出机器学习的范畴语义；若使用范畴论，应能借助如 Markov categories、伴随等结构推导实现性质或定理。 • 范畴论价值存疑：dauertewigkeit 表示自己虽有数学背景，也常在研究中遇到范畴论，但尚未理解它对 ML 框架的实际增益，认为描述 ML 框架并不需要它。 • “其实只是普通 Rust/类型编程”：oersted 认为内容看起来只是用类型表示领域对象、用函数组合转换对象，最多是更积极使用 newtype 限制类型，并不显著体现范畴论影响。 • Rust 与范畴论适配性的质疑：pshirshov 用“Rust、无高阶类型、范畴论”暗示 Rust 缺少 HKT，可能不适合严肃表达范畴抽象。 • 写作风格/AI 生成感争议：dtj1123 和 oersted 都觉得文本很像 Claude/AI 编辑，语言膨胀，影响阅读；oersted 同时强调并非所有 AI 辅助内容都无价值。 • 少量正面反馈：jdw64、harrymatics 简短表示认可或鼓励。 补充讨论：ctenb 建议将 “ML” 写成 “Machine Learning”，避免与编程语言 ML 混淆。争议焦点在于：范畴论是否真正提供了抽象优势，还是仅作为术语包装普通类型化 Rust 代码。
