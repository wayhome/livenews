这篇文章总结了Scott Cooper对一起供应链攻击事件的复盘。攻击者通过向共享代码库推送恶意GitHub Actions工作流，窃取了具有广泛发布权限的npm令牌，并利用它发布了20个包含恶意代码的软件包，包括Cooper维护的@ctrl/tinycolor。尽管GitHub和npm迅速撤下了这些恶意版本，但事件暴露了共享代码库管理权限和静态令牌的安全隐患。Cooper计划未来采用更安全的OIDC/Trusted Publishing机制，并加强发布流程的管控，同时呼吁npm提供更完善的账户级安全功能。事件发生后，相关讨论在Hacker News上持续了24小时。

评论摘要
主要讨论点：[如何提升 npm 包发布的安全性，防止恶意攻击和令牌泄露] 不同观点： • **自动化发布与令牌管理** - [darkamaul] 提倡使用 Trusted Publishing，生成短期有效的令牌，减少长期令牌的风险。 - [bikeshaving] 反对自动化发布，认为大多数包不需要频繁发布，手动运行 `npm publish` 并启用 2FA 更安全。 - [cyberax] 批评令牌机制，认为静态令牌本质不安全，建议采用类似 GitHub 与 AWS 集成的动态认证方式。 • **多因素认证（MFA）与多人审批** - [mnahkies] 认为 MFA 在自动化流程中的应用不足，希望 npm 或 GitHub 提供更简便的 MFA 确认方式。 - [rectang] 建议引入多人加密签名审批，避免单点失效问题。 • **手动发布 vs. CI/CD** - [zeroq] 主张回归手动发布，认为 CI/CD 虽便捷但风险高，并以 BigBank 的严格部署流程为例。 - [waterTanuki] 指出现状不可持续，但完全依赖手动发布或依赖清理不现实，建议 npm 强制实施安全规则（如 2FA 和 OIDC）。 • **攻击案例与漏洞修复** - [drdrey] 质疑攻击者如何通过一个仓库的令牌发布其他无关包，暴露权限管理问题。 - [indigodaddy] 询问是否有工具检测受影响包，反映社区对快速响应的需求。 补充讨论： - **争议焦点**：自动化发布的必要性与风险（如 [bikeshaving] 与 [darkamaul] 的对立观点）。 - **潜在解决方案**：强制安全规则（如 [waterTanuki]） vs. 技术改进（如 Trusted Publishing）。 - **社区态度**：部分开发者对安全措施抵触（[waterTanuki]），凸显推广难度。
