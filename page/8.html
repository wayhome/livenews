文章摘要

The jank programming language

作者: akkad33 | 评分: 401 | 评论数: 19 | 发布时间: 2025-07-06 16:56
文章摘要

Jank是一种通用的编程语言，兼容Clojure，但通过C++和LLVM-based JIT实现，支持原生编译和最小运行时。它提供REPL开发环境，同时能够进行静态AOT编译生成原生可执行文件。Jank允许在Clojure代码中无缝嵌入C++代码，并支持多线程软件事务内存和反应代理系统。其编译器启动快、内存使用低，并提供高质量的错误报告。Jank还与Clojure生态工具（如Leiningen和nREPL）兼容，支持在同一文件中混合编写C++和Clojure代码。例子展示了如何利用Clojure强大的数据处理能力生成电影索引和转换字节大小为可读格式。

Helm local code execution via a malicious chart

作者: irke882 | 评分: 166 | 评论数: 12 | 发布时间: 2025-07-09 05:49
文章摘要

文章主要介绍了Helm中的一个高危安全漏洞（CVE-2025-53547）。在Helm版本≤3.18.3中，恶意构造的`Chart.yaml`文件和符号链接的`Chart.lock`文件可能导致本地代码执行。当用户运行`helm dependency update`时，某些字段会被带入`Chart.lock`文件，如果该文件被符号链接到可执行文件（如`bash.rc`或shell脚本），可能导致 unwanted 的代码执行。此问题已在Helm v3.18.4中修复。作为临时解决方案，用户应确保`Chart.lock`文件不是符号链接。漏洞的CVSS评分为8.5，属于高危级别。

评论摘要
主要讨论点：Helm图表依赖更新过程中存在的安全漏洞及其潜在的攻击向量和影响 不同观点： • [yelirekim] 详细解释了漏洞的工作原理：攻击者通过恶意构造Chart.yaml文件和符号链接（symlink）指向敏感文件，当执行`helm dependency update`时，Helm会跟随符号链接，将恶意代码写入目标文件，导致代码执行。该观点强调了Helm未验证目标文件的问题。 • [ivan4th] 对Helm整体设计提出批评，尤其是使用文本模板引擎生成YAML的机制，认为这是问题的根源。该评论更像是一种对Helm使用体验的抱怨，而非直接针对漏洞本身。 • [codebastard] 质疑攻击的实际可行性，指出攻击者需要文件系统访问权限和Helm仓库的访问权限。如果攻击者已经具备这些权限，是否还存在更大的安全隐患？该观点认为漏洞的危险性被夸大。 • [TheDong] 对漏洞描述的清晰度提出质疑，特别是关于`Chart.lock`如何成为符号链接以及为何修复只针对`Chart.lock`。该评论建议修复方案应为禁止图表包含指向根目录之外的符号链接。 • [Sjoerd] 关注攻击场景和安全边界问题，询问攻击者如何将恶意仓库传递给受害者以及Helm通常是否以特权用户身份运行。该观点认为漏洞描述缺乏对这些关键问题的解答。 • [mkagenius] 提到类似工具（如aider、claude desktop）要求shell访问权限的风险，认为允许LLM通过shell执行生成图表是一个不好的做法。 • [xyst] 认为该漏洞很有趣，并提到自己通过Nix管理配置文件，从而能够检测到恶意写入尝试。建议使用只读分区和“诱饵”文件来防御此类攻击。 • [quotemstr] 讽刺地提到内存安全语言中不应出现安全漏洞，暗示对漏洞存在的惊讶。 • [sugarpimpdorsey] 批评YAML格式本身，认为其设计有问题，并预测这不会是YAML相关的最后一个远程代码执行（RCE）漏洞。 • [qxfys] 好奇此类漏洞是否可以通过LLM自动发现，询问其他人的经验。 补充讨论： • 争议焦点在于漏洞的实际危险性和攻击的可行性。部分评论认为攻击者需要过多的权限，漏洞的威胁被夸大，而其他人则关注漏洞的根本原因和修复方案。 • 对YAML格式本身的批评以及对Helm设计的不满也是讨论中的一个分支，显示出部分用户对现有工具链的深层次不满。 • 最后，关于LLM是否能够自动发现此类漏洞的讨论，表明了对人工智能技术在安全领域应用的潜在兴趣和探索。

Desktop Publishing Tools That Didn't Make It (2022)

作者: rbanffy | 评分: 62 | 评论数: 20 | 发布时间: 2025-07-09 18:04
文章摘要
