Bootstrapping Lisp in a Boot Sector

作者: gone35 | 评分: 14 | 评论数: 0 | 发布时间: 2025-05-05 07:52
文章摘要

**sectorlisp** 是一个仅 512 字节的 LISP 实现，能够在裸机上启动 John McCarthy 的元循环求值器。该项目旨在通过以下方式简化和实现 LISP： 1. 提供一个纯 LISP 表达式实现，仅使用语言的核心功能，修复了 McCarthy 原论文中的错误并去除语法糖（见 `lisp.lisp`）。 2. 提供一个可读的、可移植的 C 参考实现，展示如何在符合 POSIX 的平台上原生启动元循环求值器，并附带类似 readline 的接口（见 `lisp.c`）。 3. 提供一个可在个人电脑 BIOS 上启动的 512 字节 i8086 LISP 实现（见 `sectorlisp.S`），这是迄今为止最小的完整 LISP 实现。 用户可通过 `make` 命令编译 C 实现，并使用 `sectorlisp.bin` 在模拟器（如 Blinkenlights 或 QEMU）中启动。项目还提供了演示视频展示如何启动和运行。

Semantic unit testing: test code without executing it

作者: alexmolas | 评分: 60 | 评论数: 21 | 发布时间: 2025-05-03 09:44
文章摘要

《Semantic Unit Testing》一文介绍了一种新的测试方法——语义单元测试。这种方法利用大型语言模型（LLM）分析函数的实现和文档说明（docstring），判断代码是否符合预期行为，而不仅依赖传统的输入输出对比。语义单元测试通过评估函数的描述和实现是否一致来发现潜在错误，无需实际运行代码。文章介绍了一个名为`suite`的Python库，它利用LLM自动检测代码中的问题。具体操作包括读取函数的实现和文档，提取相关信息并递归分析内部调用的方法，最终生成一个提示交给LLM判断。文章通过一个发牌函数的例子展示了该库的工作流程和使用方法。`suite`库通过这种智能分析方式，提高了代码审查的效率和准确性。

评论摘要
主要讨论点：LLM（大型语言模型）在软件开发和代码验证中的应用及局限 不同观点： • **LLM生成的代码需要严格的验证**：[vouwfietsman] 认为LLM可以用于辅助编写代码，但每行代码仍需经过验证，确保没有逻辑和推理上的问题。LLM本身不应负责验证，因为这可能会加剧问题。 • **对LLM接管工程的怀疑**：[RainyDayTmrw] 对LLM主导设计持怀疑态度，特别是考虑到现有代码库中不确定性（如测试不稳定）已经是一个问题。如果需要不确定性，已有更成熟的基于属性的测试方法。 • **LLM用于文档和代码比对的潜力与风险**：[lgiordano_notte] 认为LLM可以通过比对文档字符串和代码来发现问题，但需要小心过度依赖不充分的文档。 • **LLM代码审查而非测试**：[dragonwriter] 指出，LLM更多是用于代码审查，而非测试。将其称为测试是误导性的。 • **静态类型语言与动态类型语言的比较**：[jonathanlydall] 认为在静态类型语言中，很多验证工作在编译时完成，而在动态类型语言中则需要额外的测试，这可能使得LLM工具在动态类型语言中更有用。 • **AI辅助代码审查而非单元测试**：[jmull] 认为将LLM用于代码审查更合适，而不是单元测试。即使可以自动化运行测试，也需要手动审查结果。 • **LLM作为linter工具的潜力**：[brap] 认为LLM更适合作为linter规则，提供100%覆盖率，但需要选择性使用。 补充讨论： • **LLM工具的有效性分析**：[yuliyp] 指出需要对LLM工具的有效性进行分析，包括其在实际代码库中的应用效果、误报率和漏报率。 • **代码正确性的证明与尝试**：[evanb] 引用Donald Knuth的话提醒大家，即使代码被证明正确，仍需实际尝试。 • **LLM在代码语义比对和安全审查中的应用**：[JanSchu] 分享了使用LLM进行语义比对的经验，包括其在发现代码与文档不一致、安全风险和不安全调用方面的潜力，同时提醒注意模型提示的压力和错误信心问题。 • **LLM与传统测试方法的比较**：[masklinn] 认为LLM更像是“气氛审查”，而不是证明代码正确性的工具，传统测试方法如属性测试和符号执行仍然不可或缺。 • **LLM在函数式编程中的潜力**：[simianwords] 提出LLM可能在纯函数式编程中更有用，因其无副作用和明确参数传递的特性。 • **LLM测试的随机性问题**：[rollulus] 担心LLM的随机性可能导致测试结果的不稳定。 • **LLM用于文档验证的潜力**：[cerpins] 认为LLM可能适合用于验证文档与代码的一致性，而不需要在代码和文档未改变时重新运行测试。 争议焦点： • LLM在代码验证和测试中的角色和有效性：一方认为LLM可以有效辅助代码审查和文档比对，另一方则担心其不确定性和潜在误报问题。 • LLM工具的实际应用效果和覆盖率：对LLM工具在实际代码库中的应用效果和误报率、漏报率的分析需求。 总结：讨论围绕LLM在软件开发中的应用展开，主要争议点在于其验证代码的有效性和不确定性问题，同时对其在文档比对和代码审查中的潜力给予了一定认可。

Gutknecht开发了单遍编译器，其编译速度比多遍编译器快四倍，代码量也显著减少。2021年，遗失多年的单遍编译器源码被找到，并可在Lilith模拟器EmuLith中使用。此外，还有为Motorola MC68000和MC68040微处理器生成代码的编译器版本，用于Apple Macintosh系统的MacMETH。相关手册和论文提供了更多技术细节和背景信息。
