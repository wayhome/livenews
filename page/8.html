Chat Control 1.0 and 2.0 Explained

作者: gasull | 评分: 882 | 评论数: 40 | 发布时间: 2026-07-07 14:23
文章摘要

欧盟有两个并行的"聊天控制"法案： **Chat Control 1.0**（临时法规）：2021年通过，允许服务商**自愿**扫描私人消息以检测儿童性虐待内容，不涉及端到端加密通信。2026年4月4日已过期，但欧盟理事会正试图通过"新法案"快速复活。 **Chat Control 2.0**（永久提案）：2022年提出，要求平台**强制**检测和报告儿童性虐待材料。核心争议在于是否强制扫描私人通信，以及是否涉及加密消息。欧洲议会主张仅针对可疑用户且需法院授权，而理事会立场更宽泛。目前五轮三方谈判未达成协议。 两个法案引发争议的焦点是隐私保护与儿童安全之间的平衡。

评论摘要
主要讨论点：欧盟"聊天控制"法规引发的隐私、技术实施和政府动机争议 不同观点： • **反对派 - 权力扩张质疑**：认为这是以"保护儿童"为名义的独裁式权力扩张，法律范围过于宽泛，影响所有人而非精准打击犯罪者。质疑政府真实动机，指出同样的政府不谴责高层人士涉及的犯罪，怀疑目的是建立监控国家和压制反对声音 • **技术实施困惑**：多人质疑如何在端到端加密下实施扫描——是需要中间人解密还是强制设备端扫描（类似苹果CSAM方案）？"自愿"针对服务商还是用户？如何防止用户侧载开源客户端规避检测？ • **执行效率批评**：指出真实儿童虐待案件存在量刑过轻、警务资源不足问题。可以通过在游戏平台设蜜罐、渗透公开群组、与学校合作等传统警务手段打击犯罪，但政府不愿做"真正的工作" • **隐私担忧**：普通家长担心为婴儿拍摄洗澡等日常照片（如父母过去留存的成长照）会触发误报。批评科技公司通过"自动更新"完全控制客户端软件，用户无法验证数据用途和合作方 补充讨论： 有人询问Chat Control 1.0实施两年的实际效果和滥用案例，寻求实证评估。另有批评指出政客在此问题上投入的时间超过能源安全等紧迫议题。值得注意的是，即使1.0版本过期，谷歌、Meta等公司仍继续扫描私人消息。

Poison, redzones and shadows: inside KASAN

作者: rrampage | 评分: 11 | 评论数: 0 | 发布时间: 2026-07-06 20:08
文章摘要

KASAN（内核地址消毒器）是 Linux 内核中用于检测内存错误的运行时工具。由于内核主要用 C 语言编写，容易出现缓冲区溢出、释放后使用等内存管理问题，KASAN 可以有效捕获这些错误。 KASAN 的工作机制包括两部分：编译器（GCC/LLVM）在内存访问指令前插入检查代码，以及内核维护的"影子内存"用于追踪内存状态的合法性。使用时需在编译内核时启用 CONFIG_KASAN 配置项。 文章介绍了使用 virtme-ng 在虚拟环境中测试 KASAN 的方法，并展示了典型的 KASAN 错误报告格式，帮助开发者理解其内部实现和运行开销。

Why we built yet another Postgres connection pooler

作者: levkk | 评分: 221 | 评论数: 21 | 发布时间: 2026-07-07 15:36
文章摘要

PgDog 是一个新的 Postgres 连接池代理工具。与 PgBouncer、RDS Proxy 等现有方案不同，PgDog 解决了连接池的"泄漏抽象"问题，让用户无需修改应用代码或放弃数据库特性。 **核心特性：** 1. **SET 命令支持** - 通过内置 SQL 解析器追踪每个客户端的连接状态，自动在服务器端恢复状态，确保会话变量（如 RLS 策略）正常工作 2. **LISTEN/NOTIFY 支持** - 在多个 PgDog 进程间代理发布订阅消息，保留事务语义 3. **多线程架构** - 基于 Rust 的 Tokio 运行时，充分利用多核 CPU，单进程可处理更多连接 PgDog 让 Postgres 原生特性在连接池环境下"开箱即用"，无需在扩展性和功能性之间做权衡。

评论摘要
主要讨论点：PostgreSQL 连接池工具 PgDog 的功能特性、技术优势和社区反馈 不同观点： • **技术实现赞赏派**：认可 PgDog 的技术特性，特别是 prepared statements 支持（弥补了 pgpool-II 的历史缺陷）、SET 实现的清晰性、以及 AGPL 开源许可的选择 • **协议层改进派**：kardianos 提出更根本的批评，认为问题在于 PostgreSQL 的 pgwire3 协议本身设计不佳，正在开发支持命名参数、多结果集、流式传输等功能的新协议 POC • **架构方向质疑派**：rastignack 认为连接池不应作为外部工具，而应在 PostgreSQL 上游实现线程池模型和内部调度器（如 MS SQL Server） • **PostgreSQL vs MySQL 争论**：ransom1538 质疑 PostgreSQL 的市场地位，指出 Slack、YouTube 等大规模公司采用 MySQL/Vitess 分片系统，认为 PostgreSQL "战争已输" 补充讨论： **安全性关注**：petters 对连接状态泄漏问题表示震惊，质疑这种设计是否普遍存在于 Postgres 连接池中 **功能需求**：用户关注分片/多租户动态配置能力、查询缓存功能、以及 NOTIFY 性能优化是否影响事务一致性等实际应用问题 **竞品比较**：讨论涉及 ProxySQL、pgpool-II、pgbouncer 等现有方案的优劣对比

评论摘要

macOS 28 will not support encrypted HFS+ volumes

作者: Lihh27 | 评分: 22 | 评论数: 2 | 发布时间: 2026-07-08 17:11
文章摘要

macOS 28及更高版本将不再支持加密的Mac OS Extended（HFS+）磁盘格式。用户需要在升级前处理此类磁盘。 **检查方法**：在磁盘工具中查看磁盘信息，如果同时显示"Mac OS Extended"和"Encrypted"，则不兼容。 **解决方案**： 1. **重新格式化**：备份数据后，使用APFS或APFS（加密）格式抹掉磁盘 2. **解密**：解锁磁盘后，右键选择"解密"，等待完成。解密后可选择转换为APFS格式 注意：未加密的Mac OS Extended磁盘仍将被支持。Time Machine备份磁盘不适用解密方案。

评论摘要
主要讨论点：关于文件系统（可能是 HFS+ vs APFS）的支持决策，特别是加密功能的移除问题 不同观点： • **质疑移除加密支持的决策**（edude03）：认为既然已有加密代码且仍支持该文件系统本身，移除加密支持是不合理的。暗示这是一个技术上不必要的限制，因为实现代码明显存在。 • **对 HFS+ 使用场景的疑问**（nerdsniper）：质疑在有 APFS 可用的情况下，为什么还有人选择使用较旧的 HFS+ 文件系统。这反映出对保留旧技术支持必要性的怀疑。 补充讨论：两条评论虽角度不同，但都围绕同一技术决策展开。第一条关注"为什么移除"（从维护者角度），第二条关注"为什么需要"（从用户需求角度）。这可能反映了技术迁移中的常见矛盾：旧系统仍有用户需求，但维护成本促使逐步削减功能。争议焦点在于是否应该为少数仍使用旧文件系统的用户保留完整功能支持。

文章摘要

澳大利亚昆士兰大学环境化学家Cassandra Rauert的研究揭示了微塑料检测领域的重要问题。她发现当前用于检测人体血液中微塑料的分析技术存在严重缺陷:血液中的脂质会对聚乙烯(最常见的塑料)产生假阳性结果,导致微塑料含量被高估。她审查的18项先前研究都未考虑这一问题。 此外,实验室环境本身充斥着塑料制品,极易造成样本污染。为此,她的团队重建了实验室,采用玻璃和钢材以减少污染。研究表明,关于"人类每周摄入一张信用卡重量塑料"的说法已被推翻。目前科学界尚无确凿证据证明微塑料对人体的具体影响,准确测量是了解其健康风险的前提。

评论摘要
**主要讨论点：** 微塑料的检测方法可靠性、对人体影响的证据强度、以及公众和科学界对此问题的不同态度 **不同观点：** • **科学谨慎派**：强调现有证据不足，指出检测方法存在问题（脂肪会导致假阳性）、研究发现微塑料颗粒可能太大无法与细胞互动。批评学术界存在"文件抽屉问题"（负面结果不发表） • **研究能力质疑派**：认为现代医学和学术机构能力有限，无法充分回答微塑料影响的问题。实验室建设就面临挑战——测试30种建材都含塑料或添加剂，最终只能用不锈钢 • **社会批判派**：认为反塑料是新兴精英主义，批评反塑料人士行为不理性且不一致，忽视生活中大量"隐形塑料" • **无奈接受派**：以幽默或悲观态度面对，表示"已成为身体一部分"或"要到尸检才知道" **补充讨论：** 有人提出希望区分不同类型塑料的具体影响；也有积极探索解决方案的声音，如韩国泡菜益生菌可能帮助排出纳米塑料。整体而言，评论反映出科学研究与公众关注之间的张力，以及对这一新兴健康问题的不确定性和焦虑。
