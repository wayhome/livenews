Emacs: The macOS Bug

作者: xlii | 评分: 139 | 评论数: 17 | 发布时间: 2025-07-30 18:15
文章摘要

这篇文章讨论了Emacs在MacOS上的一个长期存在的性能问题，即随着使用时间的增加，Emacs的RAM占用不断上升，最终导致冻结。尽管在Linux和Windows上没有类似问题，作者发现MacOS上的Emacs在处理事件时会频繁分配和释放资源，尤其是在高DPI显示器下，这导致大量无用的缓存对象累积，从而影响性能。问题主要出现在`[NSApp run]`的调用上，它在处理系统事件时会无意中创建和销毁大量资源，如窗口、字体和图形上下文。由于MacOS高效处理事件的特性，这些问题在快速硬件上更加明显，最终导致Emacs无法正常释放资源，引发内存和CPU占用过高的问题。虽然问题复杂，但作者对代码设计并不持批评态度，而是理解其历史和维护难度。

评论摘要
主要讨论点：Emacs在不同平台（尤其是macOS）上的性能和兼容性问题 不同观点： • **Emacs与GUI框架的主循环冲突**：[rayiner] 指出Emacs希望控制主循环，而大多数GUI框架也希望控制主循环，这种冲突导致了一些问题。不过，他在Mac上的使用体验一直很好，特别是处理大型PDF文件时表现优异。 • **macOS对Emacs的严格要求有助于改进跨平台代码**：[rahen] 认为macOS对Emacs中某些“hack”的严格处理有助于改进整个Emacs代码库，并提到PGTK前端和采用SDL工具包的潜力。 • **对改进工作的感谢和兴趣**：[dwb] 表达了对Emacs开发工作的兴趣和感谢，但表示没有时间和精力参与。 • **内存管理问题**：[kkylin] 发现删除一个帧（frame）时没有释放相关联的内存，导致长时间运行时内存消耗增加，并提出了一种临时解决办法。 • **在macOS上良好的使用体验**：[mattlangston] 提到在macOS上长时间使用Emacs处理大量缓冲区时，内存使用和性能表现良好。 • **对性能问题的不同体验**：[eviks] 提到Emacs在macOS上的性能问题早已被注意到，并解释了某些操作（如拖动窗口）可能导致大量内存分配和重新分配。 • **跨平台性能差异**：[vim-guru] 提到在Linux和macOS上没有发现性能问题，但在Windows上性能显著下降，甚至需要修改代码以使其正常构建。 • **线程和LSP问题**：[lygaret] 提到在macOS上遇到线程睡眠挂起的问题，导致LSP相关功能出现问题，并提供了一个补丁链接。 • **子进程导致的性能问题**：[bitwize] 提到在使用Emacs工作流（如magit）时，由于端点安全软件的激活导致性能下降。 • **非自由操作系统上的使用体验**：[hollerith] 认为在非自由操作系统（如macOS）上使用Emacs的困难可能是由一些Emacs维护者的态度导致的。 • **NS和w32线程模型的讨论**：[quotemstr] 建议在macOS上使用类似于Windows的独立线程模型，以解决主循环问题。 • **考虑放弃Emacs**：[algo_lover] 提到在macOS上使用Emacs时遇到性能和流畅性问题，正在考虑转向其他编辑器，如NeoVim或Helix。 • **使用Jemalloc改进内存管理**：[anthk] 建议使用Jemalloc来改进Emacs在macOS上的内存管理问题，并提到Lucid构建的可能优势。 • **倾向于在终端中使用Emacs**：[jrockway] 更喜欢在终端中使用Emacs，以避免窗口系统带来的问题，并提到在Linux和macOS上使用终端的经验。 补充讨论： • **开发者对Emacs在不同平台上的性能和兼容性问题的关注和讨论**。 • **具体问题如内存管理、线程问题、GUI框架冲突等的技术细节和临时解决方案**。 • **不同用户在不同平台上的使用体验差异，以及对Emacs未来改进的期望**。

Fixing Ctrl+C in Rust terminal apps: Child process management

作者: Callicles | 评分: 100 | 评论数: 12 | 发布时间: 2025-07-29 22:05
文章摘要

本文讨论了在Rust终端应用程序中处理Ctrl+C中断时遇到的终端损坏和子进程管理问题，并提供了相应的解决方案。主要问题包括终端状态损坏、子进程输出干扰、挂起的后台进程以及竞争条件。文章提出了以下解决方法： 1. **进程输出代理**：将子进程输出重定向到日志系统，避免直接输出到终端。 2. **终端状态管理**：确保应用程序退出时恢复终端到原始状态，使用`crossterm`库实现跨平台终端操作。 3. **优雅的进程终止**：先尝试使用`SIGTERM`优雅关闭进程，必要时再用`SIGKILL`强制终止，并设置超时。 4. **线程安全的状态指示器管理**：协调交互元素与子进程输出，防止同时写入终端导致字符格式错误。 此外，文章还提供了测试策略和常见陷阱的避免方法，强调从一开始就实现这些模式以避免终端问题。

评论摘要
主要讨论点：Rust CLI 程序中的信号处理问题及其复杂性，尤其是 SIGINT 和 SIGPIPE 的处理，以及与操作系统相关的子进程管理问题。 不同观点： • mprovost：认为 Rust CLI 程序在处理 SIGPIPE 时存在问题，因为编译器在调用 main() 前会忽略 SIGPIPE，导致程序无法像其他程序一样在管道关闭时被信号杀死，而是返回写错误。虽然可以通过手动检查错误类型和退出状态码来模拟，但无法完全重现被信号杀死的情况。 • duped：认为优雅地关闭进程固然重要，但并不是所有子进程都适合被管道输出。对于某些进程（如需要 stdin 的 shell），应该为子进程分配新的 pty。此外，提出可以通过操作系统特性（如 PR_SET_PDEATHSIG 和 PID namespaces）管理子进程，而不是维护一个子进程注册表，并指出在 raw mode 下无法接收 ctrl+C 信号的问题。 • anp：同意 mprovost 提出的问题在 Rust 程序中存在，但认为这些问题并不是 Rust 特有的，其他语言的终端应用程序也会遇到类似问题。 • vlovich123：支持 anp 的观点，进一步指出这些问题在任何语言的终端应用程序中都会出现，不限于 Rust。 • silon42：质疑应用程序是否应该负责清理工作，认为这应该是 shell 或终端的责任，并提出如果使用 "kill -9" 发送 SIGKILL 信号，应用程序无法处理。 • mook：指出 Windows 系统上的情况更复杂，因为 Windows 不使用 Unix 信号，通常只有类似 SIGKILL 的信号，但可以选择加入类似 SIGINT 的信号。 • koakuma-chan：询问主进程退出后，子进程是否还能继续运行并写入 stdout/stderr。 • rendaw：抱怨代码可读性问题，认为代码对比度不够，影响阅读体验。 • windowshopping：提到标题容易引起误解，但最终避免了歧义。 • npalli：质疑 Rust 的并发处理能力，认为在生命周期管理、线程协作和整体人体工学方面，现代 C++ 可能更具优势。 补充讨论： • 争议的焦点在于应用程序是否应该负责处理子进程和信号的清理工作，还是应由操作系统（如 shell 或终端）处理。 • 讨论还涉及不同操作系统（Linux、MacOS、Windows）在信号处理和子进程管理上的差异，尤其是 Windows 系统的特殊性。 • 有人关注代码的可读性问题，建议改进代码高亮和排版以提升阅读体验。

Friction and Not Being Touched

作者: colinprince | 评分: 52 | 评论数: 5 | 发布时间: 2025-07-31 03:18
文章摘要

文章讨论了现代人工智能（AI）系统被描绘成“万能机器”（Everything Machines）的现象。这些系统被宣传为能解决一切问题，无论失败都是因为使用不当或技术不足，而不是系统本身的局限性。这种观点脱离了AI实际能力的物理和技术现实。同时，文章探讨了“无摩擦性”（frictionlessness）的概念，在科技领域，无摩擦通常被视为理想状态，但作者认为摩擦在社会和认知层面有重要作用。摩擦让我们感受到他人的存在、观点和需求，是社会互动的一部分。无摩擦性则体现了自我的、孤立的心态，让人不必承认或接触他人。AI作为万能机器的叙事本质上反映了这种不愿被他人“触碰”的心态，避免了人与人之间的互动和必要的摩擦，最终可能导致个体与社会的隔离。
