PSF has withdrawn $1.5M proposal to US Government grant program

作者: lumpa | 评分: 681 | 评论数: 58 | 发布时间: 2025-10-27 15:12
文章摘要

2025年初，Python软件基金会(PSF)首次向美国国家科学基金会(NSF)申请150万美元资助，用于改进Python和PyPI的安全防护。经过数月努力，PSF成为36%首次申请即成功的机构之一。但最终PSF董事会一致决定放弃这笔资金，原因是NSF要求受资助机构承诺"不推进任何多样性、公平和包容性(DEI)项目"，这与PSF"支持多元化国际社区"的核心使命相冲突。尽管这笔资金对PSF预算和PyPI安全升级（包括开发主动防御工具）意义重大，PSF仍选择坚守价值观。目前PSF面临资金压力，呼吁社区通过成为会员、捐款或企业赞助等方式提供支持。

评论摘要
主要讨论点：[Python软件基金会（PSF）拒绝美国国家科学基金会（NSF）150万美元资助的决定及其背后的DEI（多样性、公平性和包容性）争议] 不同观点： • **支持PSF的决定**：评论者认为PSF拒绝资助是正确的，因为这避免了未来的财务风险（如资金被追回）和潜在的政治干预。例如，[AlSweigart]指出这是一个“存在性风险”，而[7jjjjjjj]强调NSF条款可能成为“扼杀PSF的按钮”。 • **DEI的重要性**：一些人认为DEI工作对于社区的多样性和包容性至关重要。[th]通过PyCon的例子说明，主动的外展工作可以显著提高多样性，而[ghiculescu]则质疑为什么其他国家不能填补这一资金缺口。 • **法律条款的模糊性**：评论者如[djoldman]和[rileymat2]讨论了NSF条款的法律解释问题，特别是“违反联邦反歧视法”是否适用于整个DEI项目还是仅限“歧视性公平意识形态”。 • **资金问题的严重性**：多位评论者指出PSF的资金规模与其在全球技术生态系统中的重要性不成比例。[godelski]特别强调了Python在经济中的巨大价值，而[di]提供了PSF的财务背景。 补充讨论： • **争议焦点**：主要集中在DEI项目的合法性和必要性，以及NSF条款的潜在风险和模糊性。 • **替代资金来源**：一些评论者呼吁大公司（如Google、AWS、Microsoft）或国际资金支持PSF，以弥补NSF资金的缺失。 • **政治干预科学的风险**：[aspir]警告说，将政治条款强加于科学资助可能对研究产生长期负面影响。

Pass-by-Value Overhead

作者: todsacerdoti | 评分: 52 | 评论数: 3 | 发布时间: 2025-10-28 00:52
文章摘要

这篇文章通过基准测试分析了C语言中按值传递(struct by value)的性能开销。作者测试了不同大小结构体的传递性能，发现：小型结构体(32字节以下)的按值传递开销很小；256字节以下使用向量化内存拷贝；257字节以上改用`rep movs`指令；1682字节后出现周期性性能波动(每32字节周期)。结果显示按值传递的开销与数据大小成正比，但对小型结构体来说差异可忽略。

评论摘要
主要讨论点：[编程中的性能优化和实现细节] 不同观点： • **jklowden** 强调“传值”是语义概念而非实现细节，编译器可以根据需要优化，不一定实际复制数据。传递 const 引用在 C++ 中也是传值的一种形式，关键在于语义而非具体实现。 • **anonymous908213** 对特定 CPU 缺陷（AMD Ryzen 3900X 在特定数据大小下的性能问题）表示好奇，暗示硬件实现可能影响编程中的性能优化决策。 • **codedokode** 分享了使用 ChatGPT 快速生成微基准测试代码的经验，提到在特定场景下（如小规模有序数组查找），分支无关的线性扫描可能比二分查找更快，强调了实际测试的重要性。 补充讨论： - **争议点**：jklowden 的观点可能引发关于“传值”语义与编译器优化权限的讨论，是否所有场景下编译器都能安全忽略复制操作？ - **实践建议**：codedokode 的方法展示了工具（如 LLM）如何加速性能探索，但需注意防止编译器过度优化（如手动添加 workaround）。

Rust cross-platform GPUI components

作者: xvilka | 评分: 491 | 评论数: 37 | 发布时间: 2025-10-27 09:44
文章摘要

这篇文章介绍了GPUI Component，一个基于Rust的跨平台桌面应用UI组件库。主要特点包括： 1. 提供60+现代UI组件，支持多主题和自定义样式 2. 包含高性能虚拟化表格/列表、代码编辑器、Markdown渲染等功能 3. 采用无状态设计，简单易用 4. 支持macOS/Windows原生风格，同时融入现代设计 5. 体积小巧（约12MB），跨平台支持良好 该项目已在Longbridge Pro等应用中实际使用，提供丰富的示例和文档，采用Apache 2.0许可。相比Iced/egui/QT等框架，在UI风格、中文支持和大数据渲染等方面具有优势，但目前不支持Web平台。

评论摘要
主要讨论点：[Rust UI框架的成熟度、可用性和功能完整性] 不同观点： • **功能完整性支持者** - 认为该框架是目前Rust UI中最完整的之一（组件丰富），展示了强大的组件库示例（如widget gallery）。 - 对比其他流行框架（iced、egui等），认为它们在组件完整性上反而不足。 - 举例类似框架fyrox-ui，但指出其使用范围有限。 • **依赖和原生性质疑者** - 批评其依赖GTK等外部工具包，认为这是设计上的矛盾（如WhyNotHugo）。 - 质疑“原生”定义是否真正使用系统原生控件（如fidotron对比Java的教训）。 • **无障碍和可用性担忧** - 多次提到框架可能缺乏屏幕阅读器等无障碍支持（如kennydude、miki123211），认为这会限制实际应用场景。 • **工具链和工作流批评** - 指出缺乏可视化编辑器（如samiv对比Qt的拖拽设计），认为手动编码效率低。 - 批评框架强制接管事件循环（如Animats对比egui的灵活性）。 • **商业背景争议** - 对开源项目由金融/加密货币公司主导表示矛盾（如agluszak），既肯定贡献又担忧动机。 补充讨论： - **性能与扩展性**：关注电池消耗（Keyframe）和渲染到纹理的游戏兼容性需求。 - **移动端缺失**：指出未适配iPad等大屏设备（如ratatoskrt）。 - **文档与宣传**：主页未明确说明功能（unwind），影响用户理解。 - **许可证与数据**：针对对比表中的Qt信息不准确展开争论（samiv）。 争议焦点： 1. 是否真正“原生” vs 依赖其他工具包。 2. 无障碍支持的缺失是否构成致命缺陷。 3. 可视化工具的缺乏是否影响开发效率。 4. 商业公司主导开源项目的伦理争议。
