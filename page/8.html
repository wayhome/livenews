Taking Notes with Joplin

作者: sohkamyung | 评分: 86 | 评论数: 19 | 发布时间: 2025-04-19 06:56
文章摘要

Joplin是一款开源笔记应用，支持多种笔记类型和Markdown语法，具有插件系统和多媒体附件功能。它提供端到端加密同步，用户也可选择仅本地存储。Joplin 3.2版本新增多窗口支持、多列布局、增强的无障碍功能和主题检测。该项目由Laurent Cozic于2016年启动，2022年改为AGPLv3许可证。Joplin支持多平台，包括Linux、macOS、Windows及移动端。它使用SQLite数据库存储笔记，并提供多种导入导出格式。同步功能可通过Nextcloud等WebDAV兼容服务器实现，支持多设备访问和笔记共享。

Tabular Programming: A New Paradigm for Expressive Computing

作者: dgellow | 评分: 101 | 评论数: 15 | 发布时间: 2025-04-21 12:26
文章摘要

本文介绍了一种名为“表格编程”（Tabular Programming）的新编程范式，灵感来源于m8 Dirtywave音乐序列器。该范式旨在通过一个简约的表格界面来组织代码，每函数限定五个表达式，以促进代码的模块化和可维护性。硬件方面，使用类似Teensy 4.1微控制器，配备小屏幕和八个按钮，无需键盘即可完成编程。 这种设计有以下优点： 1. **减少错误**：通过选择有效选项，避免许多语法错误。 2. **强制分解**：五表达式限制促使函数的细致分解。 3. **明确数据流**：数据流在表格中视觉化。 4. **便携性**：适合随时随地编程。 文中还展示了如何用这种表格编程实现经典的demoscene等离子效果，通过调用初始化和主循环函数来实现效果。这种新范式探索了在硬件约束下如何创造出新的编程环境。

评论摘要
主要讨论点：表格化编程环境的适用性和优缺点 不同观点： • **支持表格化编程的适用场景**： - **kats**：列举了一些天然适合表格化表示的场景，如关系型数据库、硬件电路真值表、汇编语言操作码、FPGA编译输出和矩阵乘法等，认为这些场景下表格化编程具有良好的性能表现。但同时指出，将所有应用逻辑都放入表格是困难的，特别是当程序需要频繁扩展或包含复杂功能时。 - **lantry**：认为表格化编程不仅仅是将编程能力塞进有限硬件中，而是从根本上重新思考如何在硬件限制下进行编程。这种方法可能会增强创造力，而不是限制它，并提到自己作为软件工程师常常无法完全理解所构建的系统，而这种方法可能会让他更快乐。 • **对表格化编程的质疑**： - **sedatk**：认为将每个函数限制为五个表达式虽然有助于分解复杂操作，但走向极端会导致代码既不可读也不可维护。作者忽视了过度分解可能带来的问题。 • **对比其他编程范式**： - **gregschlom**：认为表格化编程类似于汇编语言，所有内容都限制在几列中，但这种方法对可用性不友好。 - **hwpythonner**：将表格化编程与工业控制系统中的梯形图进行比较，强调两者都强调线性和结构化的逻辑流。 - **Johnbot**：提到表格化编程让他想起RPG II编程语言，这种语言也有类似的固定结构。 • **其他领域应用的讨论**： - **dimatura**：提到M8设备，认为表格化编程在这种设备上是一个很好的补充功能。 - **debugnik**：提到GPU行业标准，并提出这种表格化UI是否适用于逻辑编程而不是基于栈的编程的问题。 • **对实际应用场景的质疑**： - **poulpy123**：认为表格化编程可能仅在某些特定场景（如音乐音序器）中有趣，但在常规计算机中难以找到合适的使用场景。 补充讨论： • **历史背景**： - **turtleyacht**：提到2002年的“面向表格编程”讨论，提供了一个历史视角（链接至2021年的讨论帖）。 • **提及其他编程语言**： - **gatane**：提到Forth编程语言，暗示这种语言可能与讨论的表格化编程有相似之处。 争议焦点： • 主要争议在于表格化编程是否真正能够提升代码的可维护性和可读性，以及其在常规计算机编程中的实际应用价值。一方认为表格化编程有助于分解复杂操作，提升创造力；另一方则担心过度分解和结构限制可能导致代码不可读和不可维护。

Scientists confirm vitamin B1 hypothesis from 1958

作者: geox | 评分: 25 | 评论数: 1 | 发布时间: 2025-04-22 12:16
文章摘要

Python’s new t-strings

作者: tambourine_man | 评分: 572 | 评论数: 44 | 发布时间: 2025-04-21 04:31
文章摘要

Python 3.14将引入t-strings（模板字符串），以提供更安全和灵活的字符串处理方式。t-strings是f-strings的泛化，f-strings虽然简洁强大，但常被误用于处理包含用户输入的字符串，导致安全问题（如SQL注入和跨站脚本攻击）。t-strings通过`string.templatelib.Template`类型实现，必须在处理后才能生成最终字符串，从而避免上述安全问题。t-strings还支持更灵活的处理，例如安全地处理HTML和SQL。开发者可以通过访问模板的字符串片段和插值值来自定义处理逻辑，如将内容转换为Pig Latin。t-strings的引入将提升Python在字符串处理方面的安全性和灵活性，并有望得到广泛应用和工具支持。

评论摘要
主要讨论点：Python 的新 t-strings 语言特性及其潜在影响 不同观点： • [支持观点] [serbuvlad] 认为 t-strings 提供了语法糖，简化了 SQL 查询等场景的代码编写，有助于库开发者创造性地使用 {} 扩展。此外，这种模板语法在全语言范围内的一致性是有益的。 • [工具支持关注] [florbnit] 关注 t-strings 在工具链（如 black、ruff 格式化工具、VSCode 高亮）中的支持情况，并指出当前设计中没有明确指示模板字符串内容的类型或其最终转换形式，可能导致误解。 • [简洁性担忧] [nu11ptr] 认为 Python 正在变得越来越复杂，像 Go 那样拒绝不必要功能的简洁设计可能更值得借鉴。对于新手来说，Python 可能已经不再像过去那样简单易学。 • [库实现观点] [sashank_1509] 质疑 t-strings 是否需要成为语言特性，认为这可以通过库实现，无需增加语言的复杂性。 • [安全性考虑] [mounir9912] 质疑 t-strings 在防止忘记字符串操作（如 HTML 转义）上的作用，认为现有的 f-strings 已经可以通过手动操作达到相同效果。 补充讨论： • [实际应用] [TekMol] 展示了 t-strings 在 SQL 查询中的潜在应用，认为这种用法非常简洁优雅，提升了代码可读性。 • [与其他语言特性对比] [nikisweeting] 希望 Python 引入类似 JavaScript 的解构功能，并指出当前 Python 在特性丰富性上仍有不足。 • [多样化字符串格式化] [metrognome] 调侃 Python 在字符串格式化上已经有太多方式（t-strings, f-strings, %-operator, +-operator, str.format()），可能导致初学者困惑。 • [自定义扩展] [runekaagaard] 希望 t-strings 可以像 import 一样由用户自定义前缀，而不是仅限于内置实现。 • [国际化问题] [fph] 关注 t-strings 在国际化（i18n）场景下的应用，询问是否可以加载翻译后的 t-strings，并包含变量和 lambda 表达式。 • [实现示例] [pauleveritt] 提供了一个 t-strings 在 SQL 相关库中的应用示例，展示了该特性的实际使用价值。 争议焦点： • t-strings 是否值得作为语言特性引入，支持者认为其提供了简洁的语法糖，而反对者则担心 Python 因此变得过于复杂，且某些功能可以通过库实现而非语言核心支持。
