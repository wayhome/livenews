Loading Pydantic models from JSON without running out of memory

作者: itamarst | 评分: 107 | 评论数: 12 | 发布时间: 2025-05-22 18:06
文章摘要

文章主要讨论了如何在使用Pydantic模型加载大型JSON文件时减少内存消耗。默认情况下，Pydantic加载JSON文件会导致高内存使用，可能达到文件大小的20倍。为解决此问题，文章提出了两种主要方法： 1. **使用ijson库进行增量解析**：通过流式处理JSON文件，逐项加载数据，从而减少解析时的内存占用，但速度会变慢。 2. **使用带slots的数据类**：通过Pydantic的数据类支持和slots特性，固定对象属性以减少内存使用。 最终，结合这两种方法，可以将100MB JSON文件的峰值内存使用从2000MB减少到450MB。这些方法特别适用于需要处理大型JSON文件且内存资源有限的情况。

评论摘要
主要讨论点：Pydantic库的JSON解析性能和内存使用优化，以及相关技术选择和替代方案。 不同观点： • [scolvin] Pydantic的作者介绍了即将进行的改进计划，通过迭代解析JSON来提高性能并减少内存使用。他们提到新的JSON解析器jiter已经支持迭代解析，接下来的任务是在pydantic-core中解决生命周期问题。这将使Pydantic的JSON解析速度提高约3倍，并显著降低内存开销。 • [fidotron] 质疑当前Pydantic处理大文件时的内存消耗问题，指出处理100MB文件需要2GB内存是不合理的，并将其与XML解析中的SAX和DOM方法进行类比，暗示需要一种更节省内存的解析方式。 • [jmugan] 提到在处理复杂模型（包含多层嵌套的BaseModels和联合类型）时，Pydantic无法完全加载模型，部分深层结构仍为字典。他寻求一种能够搜索不同加载方式的解析器。 • [deepsquirrelnet] 建议使用jsonl替代JSON，或者重新评估是否适合使用JSON格式，尤其对于大文件，建议考虑二进制格式。 • [dgan] 表示已放弃使用Python的dataclasses和JSON，转而使用protobufs，并为每个wire模型添加Mixin类以提供额外方法。他认为自动且静态类型化的反序列化值得投入。 • [fjasdfas] 询问在所有Python数据类型上设置`slots=True`的潜在缺点。 • [kayson] 关心dataclass版本的速度比较情况。 • [zxilly] 建议使用mmap可能节省内存，但不确定是否能在Python中实现。 • [thisguy47] 希望看到`ijson`与`json.load(f)`的比较，并提到`ujson`也值得关注。 • [m_ke] 建议放弃Pydantic，转而使用msgspec，并提供了一个参考链接。 补充讨论： - 对Pydantic性能和内存使用的关注是主要焦点，尤其是处理大文件和复杂模型时。 - 提出了多种替代技术，包括protobufs、jsonl、mmap和msgspec，每种技术都有不同的优缺点。 - 对Pydantic未来改进的期待，特别是迭代解析JSON的性能提升。 - 不同用户对性能、易用性和内存消耗的不同需求和偏好，导致了多样化的技术选择和建议。

Visual Studio Code: Text Buffer Reimplementation (2018)

作者: stefankuehnel | 评分: 52 | 评论数: 4 | 发布时间: 2025-05-20 09:34
文章摘要

Visual Studio Code 1.21引入了新的文本缓冲区实现，显著提升了性能，包括速度和内存使用。最初考虑用C++实现以节省内存，但因在原生表示和V8字符串间转换的成本高昂，性能未达预期。最终，团队通过优化JavaScript/TypeScript代码提升了性能。 旧的文本缓冲区使用线性数组，对小文件表现良好，但处理大文件时内存消耗过大，例如35MB文件会导致内存溢出。新方案采用"piece table"数据结构，初始内存占用接近文件大小，修改所需内存与编辑次数成正比。为加快行查找速度，采用了缓存机制。 新实现通过减少元数据和优化数据结构，实现了性能提升。

评论摘要
主要讨论点：不同文本编辑器使用的数据结构及其优缺点 不同观点： • [smartmic] 提问是否有关于不同文本编辑器（尤其是GNU Emacs、vi(m)、Sublime等黑客常用编辑器）使用的数据结构的概述。 • [lenkite] 认为"piece table"是一种出色的编辑器数据结构，具有概念简单、对大文件内存效率高、缓存局部性好、易于实现撤销/重做操作、原文件可以只读等优点。同时指出，新一代编辑器似乎更倾向于使用Rope数据结构。 • [joeblubaugh] 对"ordered Array"作为数据结构表示质疑，认为其性能几乎显而易见地较差。 • [timewizard] 对Rope数据结构表示兴趣，并提供了一个维基百科链接以供参考。 补充讨论： • lenkite详细列举了piece table的优点，特别是在处理大文件和实现某些编辑功能方面的效率。 • joeblubaugh对ordered Array的性能提出批评，暗示其在大规模或高性能应用中的不足。 • timewizard通过提供Rope数据结构的维基百科链接，引导进一步了解Rope的特性及其在编辑器中的应用。 争议焦点： • 对ordered Array作为文本编辑器数据结构的性能存在争议，joeblubaugh认为其性能较差，而lenkite则未直接回应这一观点，但指出了Rope作为新一代数据结构的流行趋势。 总结：讨论主要围绕文本编辑器使用的不同数据结构展开，包括piece table和Rope的优缺点，以及对ordered Array性能的争议。

Gemini Diffusion

作者: mdp2021 | 评分: 865 | 评论数: 40 | 发布时间: 2025-05-22 01:13
文章摘要

Google在I/O大会上发布了Gemini Diffusion，这是其首个使用扩散模型（而非传统的自回归方法）的大语言模型。扩散模型通过逐步优化噪声生成输出，而非直接预测文本，从而实现更快的速度和更高的质量。相较于一次生成一个词的传统模型，Gemini Diffusion能快速迭代和纠错，特别擅长编辑任务，如数学和代码处理。其生成速度高达857 tokens/秒，性能号称达到Gemini 2.0 Flash-Lite的水平，且速度是其5倍。扩散模型并非完全取代Transformer，而是替代自回归机制，仍可能使用Transformer进行处理。

文章摘要

文章主要介绍了一种名为Group Query Attention（GQA）的技术，该技术通过共享键和值的投影来减少多头注意力机制中的内存使用。与传统的Multi-Head Attention（MHA）不同，GQA使用较少的键和值头（$N_{kv}$），并将它们共享给多个查询头（$N_h$），从而降低计算成本和内存占用。具体实现中，先将输入序列通过线性变换得到查询、键和值，然后对键和值进行分组共享，以减少缓存大小。GQA在保持模型性能的同时，显著提高了推理速度并降低了内存需求，特别适用于大型模型的部署。Multi-Query Attention（MQA）是GQA的一种极端形式，其中$N_{kv}$为1。
