**Endive 1.0 发布公告摘要** Endive 1.0 是原 Chicory 项目在 Bytecode Alliance 旗下的首个正式版本，一个纯 Java、零原生依赖的 WebAssembly 运行时。 主要更新： - **WasmGC 宿主集成**：WasmGC 对象（结构体、数组、externref）现由 JVM 垃圾回收器直接管理，无需手动追踪引用。API 有破坏性变更，需用 `applyWithRefs` 替代 `apply`，并使用新的 Builder 模式构建结构体/数组。 - **尾调用优化**：修复了尾调用正确性问题，优化了栈帧分配，CPython 3.14 是主要受益者。 - **从 Chicory 迁移**：大部分情况只需替换 Maven 坐标（`com.dylibso.chicory` → `run.endive`）和包名，以及两个异常类重命名。 **后续计划**：Component Model 支持正在原型阶段，基于 Cranelift 的原生编译也在开发中。

《垃圾回收手册：自动内存管理的艺术》第二版是自动内存管理领域的权威著作，延续1996年和2012年版本的成就。本书全面介绍了60年来垃圾回收研究的核心知识，涵盖传统算法及最新的并行、增量、并发和实时垃圾回收技术。新版增加了90多页内容，包括持久化和能效感知垃圾回收的新章节，讨论现代硬件和软件带来的新挑战。书中配有伪代码和插图说明，并提供包含近3400篇相关论文的在线数据库。电子版包含37000多个超链接，方便读者深入学习。

主要讨论点：关于《The Garbage Collection Handbook》这本书的评价和相关话题 不同观点： • **高度评价派**：认为这是关于GC最好的书籍之一（pdevr：2012年版是当时最佳GC书籍；orionblastar：推荐此书但遗憾被儿子丢弃） • **术语争议派**：hamstergene批评该书将"garbage collection"作为追踪GC和引用计数的统称不恰当，这与编程社区的普遍认知冲突。按此定义，使用std::shared_ptr的C++代码也算有GC，这与业界将C++/Rust归为手动管理、区别于GC语言的共识相悖。认为"Automatic Memory Management"是更合适的术语 • **实践需求派**：piinbinary希望有类似《Crafting Interpreters》风格的实践指南，教授如何实现带精确GC的语言（从shadow stack + mark-and-sweep到stack maps + 分代GC） 补充讨论： rayiner提出前瞻性问题：AI在编写手动内存管理代码方面表现如何？这是否会改变自动内存管理的格局？另有人指出2023电子版无购买链接的问题。

文章摘要

这是一个针对OCR优化的Reed-Solomon纠错库项目。主要用于打印码、优惠券、ID和标签的错误纠正。 **核心功能：** - 基于GF(256)的Reed-Solomon编码，最多可纠正 floor(nsym/2) 个符号错误 - 提供OCR安全字符集（23456789ACDEFHJKLMNPQRTUWXY），避免易混淆字符（如0/O、1/I/l等） - 将校验字节编码为两个OCR安全字符 **应用场景：** 解决点阵打印机、低分辨率打印、标签污损等导致的OCR识别错误，在扫描质量足够且错误数量在纠正能力范围内时，可将OCR可靠性提升至接近100%。 **使用方式：** 编码消息生成OCR安全校验码，打印后即使部分字符损坏，仍可通过校验码检测并纠正原始消息。

评论摘要
主要讨论点：针对OCR场景的Reed-Solomon纠错码实现 不同观点： • **技术实现者观点（chasangchual）**：开发了专门用于OCR工作流的Python Reed-Solomon编解码器。核心特点是使用GF(256) Reed-Solomon纠错，配合OCR安全的字符集（避免0/O、1/I/l、5/S、8/B等易混淆字符）。每个校验字节编码为两个OCR安全字符，适用于点阵打印机、低分辨率扫描等退化场景。包含完整的类实现、演示和单元测试。 • **信息需求者观点（Dwedit）**：请求提供可视化证据，希望看到文本显示效果和纠错效果的实际截图，以便更直观地理解系统的工作表现。 补充讨论：这是一个技术展示帖，主要是项目作者介绍自己的实现方案，另一位用户提出了关于可视化演示的需求。讨论聚焦在如何处理物理介质（打印、扫描）导致的字符识别问题，通过纠错码和字符集优化提高OCR准确性。目前未出现明显争议，属于技术交流和补充信息的互动。
