Why does kinetic energy increase quadratically, not linearly, with speed? (2011)

作者: ProxyTracer | 评分: 356 | 评论数: 52 | 发布时间: 2026-06-26 22:43
文章摘要

这篇文章讨论了为什么动能随速度呈二次方增长而非线性增长。核心解释是：利用伽利略不变性（物理定律在不同参考系中保持一致）可以证明动能必须与速度的平方成正比。 文章通过一个思想实验说明：两个相同质量的黏土球相撞，在不同参考系（静止观察者和移动列车）中观察，由于能量守恒和参考系变换的对称性要求，可以推导出 E(2v) = 4E(v)，从而证明动能与速度平方成正比。 这个解释比传统的"功等于力乘以距离"更本质，因为它基于更基础的对称性原理，而不是循环定义。文章强调直觉理解比公式推导更重要。

评论摘要
主要讨论点：为什么动能与速度的平方成正比（E=½mv²），而非线性关系？ 不同观点： • **势能转换解释**（cubic_earth）：通过自由落体例子说明——从2倍高度落下的物体动能是2倍，但速度不是2倍。因为重力加速度恒定（速度随时间线性增长），物体在后半程速度已经很快，通过相同距离所需时间更短，获得的速度增量更少。实际需要4倍高度才能获得2倍速度。 • **能量耗散角度**（throw0101a）：用汽车刹车实例——70速和100速的车以相同强度刹车，慢车刚好停下时，快车还剩71速。因为快车初始动能（100²=10000）减去慢车动能（70²=4900）后剩余5100单位，对应√5100≈71速。 • **微分推导**（GlibMonkeyDeath）：从力=动量变化率出发，能量=力×距离。关键洞察是dE=mvdv——改变速度dv时，移动的距离也依赖当前速度v，因此能量不只与速度成正比。对所有dv求和得到½mv²。 • **对称性论证**（abetusk引用Ron Maimon）：纯粹从伽利略相对性原理推导，避免循环论证。若动能不是v²形式，则相对性原理被破坏，宇宙将存在特权参考系（以太）。 • **反事实推理**（Tazerenix）：假设E=m|v|会导致什么？推导出的运动方程违反伽利略相对性，且静止物体无论施加多大力都无法移动——这种宇宙在物理上病态，无法支持生命存在。 • **实用直觉**（electricwallaby、hyperhello）：恒力产生恒定加速度，距离随时间平方增长。能量=力×距离，因此能量也平方增长。加速运动物体需要先"追上"它，这本身就需要额外功。 补充讨论：部分评论质疑物理概念的"实在性"（jerome-jh探讨力与能量哪个更基本）、因果链的完整性（zkmon引用费曼），以及公式本身是否应被视为"直觉"（theroncross认为数学关系本就不应期待直觉）。

Enhancing x11 Application Security with LXC (2025)

作者: shirozuki | 评分: 69 | 评论数: 10 | 发布时间: 2026-06-27 21:27
文章摘要

这篇文章介绍了如何使用 LXC 容器来增强 x11 应用程序（如浏览器）的安全性。主要步骤包括： 1. **网络配置**：安装 lxc 和 lxcfs，配置网络桥接接口 lxcbr0 2. **创建容器**：建立配置文件，使用非特权容器并通过 UID/GID 映射（将容器内 ID 映射到主机上不存在的 ID 范围 100000-165535）实现隔离 3. **应用安装**：在容器中安装所需软件（如 Firefox），创建专用用户运行应用 4. **x11 配置**：挂载 x11 socket，处理 .Xauthority 授权文件以支持图形应用 核心思想是通过容器隔离，即使应用被攻破，攻击者也无法获得主机系统的有效权限，从而保护用户的家目录和敏感数据。

评论摘要
主要讨论点：在容器中运行应用程序的安全性问题，特别是X11的安全漏洞和沙箱逃逸风险 不同观点： • **X11存在严重安全缺陷**：直接访问X11服务器会造成巨大的沙箱逃逸漏洞，任何应用都能控制/监视其他应用（包括root终端）。建议使用嵌套X服务器如Xephyr或waypipe等替代方案 • **X11难以淘汰**：质疑X11是否会像IE6一样，在主流发行版计划弃用（2025/2026）后仍存在十年以上 • **容器化的实用性问题**：容器化应用听起来不错，但在需要访问文件时会遇到困难 • **替代方案建议**：推荐使用firejail（自带常用应用预制配置）、AppArmor/SELinux（无需容器）、或XNamespace扩展（X11Libre正在开发的新方案） 补充讨论： 有评论指出Firefox本身已有完善的沙箱机制，文章标题可能过度宣传容器化的安全价值，应更关注X11本身的安全问题。也有人感叹理想世界不需要这些安全措施的复杂性。

文章摘要

二战期间，美国政府为了给士兵提供娱乐，选择了塑料陶笛作为军用乐器。陶笛体积小、便携、耐用、防水、价格低廉且极易学习。政府主要采购了两款陶笛：Gretsch的"甜薯"型和Herm an的"直管"型。选择陶笛而非木制竖笛是因为当时塑料竖笛尚未发明（1946年才问世），木质乐器无法承受战场恶劣环境。陶笛指法简单，按C大调音阶排列，任何人都能快速上手演奏。这种乐器在当时流行文化中也有一定知名度。

评论摘要
主要讨论点：二战时期军用陶笛的历史引发了关于乐器、互联网商业变迁和音乐教育的多元讨论 不同观点： • **互联网商业怀旧派**（helterskelter）：90年代末互联网更有"发现感"，个人手工艺者直接销售独特产品。如今被大公司版权打压或被Alibaba代发货商以500%加价取代，失去了原有的真实性 • **乐器设计偏好派**（dofm, mrob）：四孔陶笛在设计上优于竖笛——四孔陶笛组合逻辑巧妙、音色成熟、易学；竖笛音量超100分贝需听力保护、音量控制有限，不适合学校使用。建议学校改用陶笛教学 • **军事文化研究派**（jhbadger, brudgers）：美军重视士兵娱乐以维持士气，除陶笛外还推出便携平装书。有人指出电影《第十七战俘营》中Joey的陶笛正是这一历史的体现 • **文化影响质疑派**（stevage）：尽管军用陶笛曾大量生产，但似乎未在战争电影、歌曲或流行文化中留下明显痕迹，文化影响力有限 补充讨论：英国学校普遍使用Aulos竖笛教学，师生均感厌烦。四孔陶笛自1960年代设计问世，比文中Gretsch陶笛更新，有多种造型（草莓、小丑鱼等）。美国小学曾使用tonette作为教学乐器。

Fintech Engineering Handbook

文章摘要

这是一份金融科技工程手册，介绍金融系统软件工程的核心模式。 **三大原则：** 1. 不创造数据 - 通过幂等性、去重和对账防止凭空产生金额 2. 不丢失数据 - 通过完整精度、事件溯源、审计日志保证可追踪性 3. 不信任 - 验证webhook、交叉核对数据源、对异常大声报错 **金额表示方法：** - 浮点数：快但精度不可控，几乎不应使用 - 任意精度（BigDecimal）：适合中间计算 - 最小单位整数：法币存储标准（如€12.34存为1234），加密货币类似 - 有理数：无精度损失但性能较低 **关键要点：** 序列化时用字符串或整数而非JSON数字；舍入是业务决策，应尽量推迟；舍入会破坏求和关系。

评论摘要
主要讨论点：金融科技系统中如何正确处理货币数据和系统设计 不同观点： • **货币存储格式争议**：xlii 主张用整数存储（避免浮点精度问题），lxgr 警告小单位精度策略在跨系统交互时会遇到问题（特别是稳定币场景），建议 API 中用字符串传输以避免 JSON 解析的精度损失 • **系统架构取舍**：xlii 强调事件溯源对金融数据的必要性（保证不可变性和审计追踪），belmarca 则认为标准的只追加审计日志就够用，不必所有服务都用事件溯源，避免状态计算复杂度 • **通用性 vs 领域特殊性**：benashford 认为这些原则（幂等性、重试、事件顺序）适用于所有需要准确性的系统，不限于金融；而 traceroute66 强调金融领域的特殊性（KYC/AML 合规要求），批评手册忽视了 PII 与财务数据的法律关联 • **理论 vs 实践**：trixn 从复式记账角度纠正"钱不能凭空产生"的说法（银行贷款即创造货币），lanstin 指出无论用什么数据类型，对账reconciliation 才是核心；morpheuskafka 以 Plaid 余额检查为例说明理论与实际的差距 补充讨论：多位从业者认可手册价值，jdw64 感慨不同领域经验导致观点差异体现了专业深度，koliber 和 ricardobayes 寻求更多学习资源
