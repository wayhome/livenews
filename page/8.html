When would you ever want bubblesort? (2023)

作者: atan2 | 评分: 69 | 评论数: 25 | 发布时间: 2025-12-10 21:45
文章摘要

这篇文章探讨了冒泡排序（bubblesort）在特定场景下的实际应用价值。虽然冒泡排序在大多数情况下效率低下，但作者列举了三个特殊用例：1) 作为快速排序等算法的辅助排序策略，适用于极小数组；2) 在游戏开发中用于实时渲染排序，因其可暂停且每次操作都能部分有序化；3) 用于可视化粒子动画效果。文章还提到插入排序通常更受青睐，但在某些硬件（如NVIDIA）或特定需求下，冒泡排序仍有其独特优势。最后作者指出这些用例都很小众，实践中很少需要用到冒泡排序。

评论摘要
主要讨论点：冒泡排序（Bubble Sort）的适用场景及其与其他排序算法的比较 不同观点： • **冒泡排序的实用性**： - 适用于小规模数据集（如游戏中的精灵排序，N ≤ 12），因其简单、低开销且支持部分排序（如逐帧渐进排序）。 - 在实时系统中表现良好，属于“Anytime Algorithm”（逐步优化结果的算法）。 - 例子：NES游戏中的精灵排序、卫星轨道模拟中维护最近卫星的列表。 • **其他排序算法的优势**： - **插入排序（Insertion Sort）**：在微控制器上性能优于冒泡排序（快6倍），且内存占用相近。 - **希尔排序（Shell Sort）**：时间复杂度接近O(N^1.3~1.5)，适合中等规模数据（N > 30），但非稳定排序。 - **快速排序（Quick Sort）**：大规模数据（N > 300）时性能更优，但不稳定。 - **归并排序（Merge Sort）**：稳定且O(N log N)，但需额外O(N)内存。 • **冒泡排序的争议点**： - 反对观点：除极少数场景（如极小数据集或教学）外，插入排序几乎总是更好的选择。 - 支持观点：冒泡排序的“软排序”特性（每次迭代都能部分排序）适合实时调整需求，且易于实现。 补充讨论： • **硬件限制**：在资源受限环境（如8位微控制器）中，算法选择需权衡速度、内存和代码复杂度。 • **实际应用场景**：如粒子系统或地形渲染中，冒泡排序的渐进性更贴合动态数据需求。 • **算法组合**：Timsort等混合算法（合并归并排序和插入排序）可能更适合通用场景。 争议焦点：冒泡排序是否仍有实际价值，抑或已被更优算法（如插入排序）完全取代。

Why the Sanitizer API is just `setHTML()`

作者: birdculture | 评分: 117 | 评论数: 12 | 发布时间: 2025-12-08 22:37
文章摘要

这篇文章解释了HTML净化(Sanitizer API)的设计原理。传统净化库(如DOMPurify)需要两次HTML解析：第一次不带上下文解析输入，第二次在插入DOM时带上下文解析，这可能导致mXSS漏洞。新的Sanitizer API通过`element.setHTML()`方法一步完成：1) 直接使用正确上下文解析HTML；2) 净化内容；3) 替换目标元素内容。这种设计避免了重复解析和上下文不一致的问题，更安全且性能更好，可直接替代`innerHTML`赋值操作。

评论摘要
主要讨论点：[Sanitizer API 的可行性和必要性，以及其在安全性和实用性方面的争议] 不同观点： • **支持 Sanitizer API** - 认为浏览器内置的 Sanitizer API 可以替代第三方库（如 DOMPurify），提供更安全和便捷的 HTML 清理功能。 - 通过 `setHTML()` 方法避免解析-序列化-解析（MXSS）漏洞，提升安全性。 - 适用于富文本编辑器（RTE）等场景，作为防御的额外层级。 • **质疑 Sanitizer API 的可行性** - 认为 HTML 清理问题本质上是“未明确且无法满足”的，无法通过新 API 彻底解决。 - 指出 `innerHTML` 和 `textContent` 等现有工具已足够，关键在于区分信任与非信任输入。 - 认为白名单比黑名单更安全，Sanitizer API 的设计可能忽略了这一经验。 • **其他补充观点** - 建议使用 XHTML 替代 HTML，以避免解析不一致性问题。 - 认为服务器端验证仍是必要的，Sanitizer API 仅适用于客户端展示时的清理。 - 提出增加 `` 标签的替代方案，以更直观地处理非信任内容。 补充讨论： - **争议焦点**：Sanitizer API 是否能真正解决 HTML 清理的安全问题，还是仅仅转移了问题。 - **讨论关系**：支持者强调其技术优势，反对者则认为问题根源在于 HTML 本身的复杂性，而非缺乏 API。 - **其他建议**：部分用户提出替代方案（如 XHTML 或 `` 标签），并强调服务器端验证的重要性。

文章摘要

这篇文章主要介绍了如何优化名为`simp`的简单编程语言的解析器性能。作者通过分析当前抽象语法树(AST)实现的内存问题，提出并测试了多种优化方法： 1. 初始AST实现使用大量独立分配的Box和Vec，导致内存使用效率低下 2. 采用字符串驻留技术(interning)，用ID代替实际字符串存储，减少重复字符串的内存占用 3. 测试结果显示，字符串驻留不仅减少了内存使用，还意外提高了解析速度 4. 文章提供了详细的基准测试方法和结果对比图表 这些优化使得解析器在处理大规模代码时性能显著提升，同时降低了内存消耗。

评论摘要
主要讨论点：编译器AST（抽象语法树）的内存布局设计及其对性能和可维护性的影响。 不同观点： • **性能与可维护性的平衡** - [pedrozieg] 强调AST设计需兼顾内存效率（扁平化布局）与开发者体验（易调试、遍历），建议采用分层设计（早期使用友好树形结构，后期优化为扁平化）。争议焦点在于增量编译时代是否值得长期保留友好AST。 - [munificent] 认为解析器性能提升有限（仅2倍），主张优先选择简单、易维护的AST，牺牲少量性能以降低开发成本。 • **实际案例与技术模式** - [mitchellh] 以Zig编译器为例，推荐基于句柄（handle-based）的设计，认为此类模式在系统级应用中未充分利用。 - [loeg] 指出Clang IR类似实践（子节点内联存储），并通过API隐藏实现细节。 • **优化策略与工具** - [shoo] 建议通过性能分析工具（如Linux perf）定位优化点，强调数据驱动的决策。 - [jauntywundrkind] 尝试将讨论与Sea of Nodes表示法关联（但未深入）。 补充讨论： - **争议点**：[torginus] 质疑扁平化布局可能绕过Rust的内存安全机制（如索引越界导致数据错乱），引发对安全性与设计取舍的讨论。 - **数据可视化问题**：[mediumdeviation] 提醒图表颜色与比例变化可能导致读者误解性能趋势。 - **极端观点**：[vatsachak] 主张彻底扁平化，未提供详细论据。
