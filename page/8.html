Bun Rust rewrite: "codebase fails basic miri checks, allows for UB in safe rust"

作者: ndiddy | 评分: 459 | 评论数: 53 | 发布时间: 2026-05-15 16:51
文章摘要

该 GitHub issue 指出 Bun 的 Rust 代码库未通过基础 Miri 检查，在安全 Rust 中可能产生未定义行为。示例显示 `from_raw_parts` 构造了悬垂引用。作者建议不要依赖 AI 编写 Rust，并聘请专业 Rust 开发者。

评论摘要
主要讨论点：Bun 从 Zig 迁移/重写到 Rust（疑似大量依赖 AI 生成）后出现 unsafe/UB 问题，引发对技术路线、质量验证、项目治理与宣传的争议。 不同观点： • 失去信任派：Bun 原本吸引力来自 Zig 与作者决策品味；被 Anthropic 收购后再出现这种“内部工具式”决策，让人不敢将其作为可靠工具链。 • 技术质疑派：若只是 Zig 到 unsafe Rust 的直译，应使用确定性的翻译工具，而不是“vibe coding”；AI 生成的 unsafe Rust 比手写 unsafe Zig 更难信任。 • 宽容过渡派：初始移植阶段 safe/unsafe 标注不完善可以理解，关键是不能以此状态发布；应后续用 Miri、测试和封装修正。 • 渐进改进派：先迁移到类型系统更强的 Rust，再利用 Rust 工具链逐步修复问题，可能比一开始追求完美更现实。 • 验证优先派：LLM 可快速产出代码，但验证必须大幅加强；类似 TypeScript 行为兼容的测试门槛极高。 • 宣传批评派：大规模“几周内重写为内存安全 Rust”的宣传影响远大于后续纠错，可能被营销利用，甚至像营销噱头。 • 社区治理派：GitHub issue 被刷屏、低质量评论和 AI 争论会破坏讨论；但项目若屏蔽批评也会形成围城心态。 • 反过度批评派：从 unsafe 语言和绑定迁移，不可能立刻完美；稳定版仍在 Zig，错误最终会修。 • Rust 工具链支持派：若问题原 Zig 也存在，Rust/Miri 能更容易暴露问题，反而说明 Rust 生态有价值。 • 激进反对派：认为 Anthropic 让用户发现问题、训练机器人并揽功，建议用博客/CVE公开施压。 补充讨论：争议焦点集中在“AI 生成 unsafe Rust 是否可接受”、迁移过程是否应公开合并、宣传是否夸大，以及维护者如何在开放讨论与防止刷屏之间平衡。
