Pandoc Lua Filters

作者: ankitg12 | 评分: 110 | 评论数: 4 | 发布时间: 2026-07-03 09:52
文章摘要

Pandoc Lua 过滤器是一种用于操作 Pandoc 抽象语法树（AST）的机制。相比传统的 JSON 过滤器，Lua 过滤器具有显著优势： **核心特点：** - Pandoc 2.0+ 内置 Lua 5.4 解释器，无需外部依赖 - 直接处理 Pandoc 数据类型，避免 JSON 序列化开销 - 性能接近原生速度（基准测试显示几乎无额外开销） **工作原理：** Lua 过滤器是一个表结构，以元素名为键、处理函数为值。遍历文档时，匹配的元素会被传递给对应函数处理。函数可返回 nil（保持不变）、新对象（替换）或对象列表（替换/删除）。 **使用方式：** 通过 `--lua-filter=文件名.lua` 参数调用，可链式应用多个过滤器。

评论摘要
**主要讨论点：** Pandoc 工具的发展演变、Lua filters 的实用性与兼容性问题 **不同观点：** • **实用场景分化**（kalcode）：Lua filters 适合处理 Markdown 到 DOCX 的转换问题，但对于 PDF 生成，切换到 WeasyPrint 引擎后就不再需要 Lua filters • **工具膨胀担忧**（lifthrasiir）：认为 Pandoc 日益臃肿，十年前使用 Lua filters 的经验与现在文档完全不同，担心不同版本间的 Lua 脚本兼容性问题 • **功能演进澄清**（leephillips）：指出 Lua filters 并非新功能，真正的新进展是 Pandoc 支持在浏览器中运行，提供了详细文章链接说明当前状况 • **未来发展设想**（chaoxu）：提出响应式更新的可能性，希望实现从 Markdown 到 AST 的增量更新机制，考虑利用 LLM 技术来实现这一想法 **补充讨论：** 评论间没有明显对立，更多体现了不同用户群体的关注点差异——实践者关注工具选择、老用户关注兼容性、信息提供者补充背景、前瞻者探索新方向

If you're a button, you have one job

作者: nozzlegear | 评分: 567 | 评论数: 64 | 发布时间: 2026-07-05 02:01
文章摘要

这篇文章通过对比iPhone和Android手机的图片旋转功能，揭示了一个重要的交互设计原则。 作者发现，当快速连续点击旋转按钮8次时，iPhone会缓冲所有操作并依次执行，而Android手机则会在动画播放期间忽略新的点击。这在批量处理照片时会造成明显差异。 作者提出"情境性高级用户"概念：即使是设计给普通用户的休闲界面，在特定情境下（如需要旋转大量照片）也会遇到需要高效操作的场景。这类似于"情境性残疾"理论——任何人都可能在某些情况下遇到障碍。 核心设计原则是：**永远不要强迫用户等待动画完成**。可以通过缓冲操作或中断/加速动画来实现这一点。

评论摘要
主要讨论点：UI按钮在快速点击时应该如何响应——是排队执行所有点击，还是防抖忽略重复点击？ 不同观点： • **支持完全缓冲派**：认为每次点击都应被记录并执行，用户期望点击三次就旋转三次，不应受速度限制。Android的Google Photos被举例为正确实现。 • **支持防抖/智能过滤派**：指出运动障碍或帕金森患者可能会产生非预期的多次点击，系统应该识别并忽略这些过度点击，锁定用户的真实意图。 • **动画批评派**：强调动画本应辅助用户理解状态转换，而非成为功能障碍。批评现代设计中动画阻塞交互的cargo culting现象，以及iOS在动画期间隐藏UI元素的做法。 • **反馈优先派**：认为按钮不只是"点击"这一项工作，还需要提供悬停反馈、加载状态、禁用状态等。缺乏反馈会让用户不知道操作是否生效，反而导致更多重复点击。 补充讨论：有人提到缓冲可能在设备慢时造成延迟困惑；也有人指出某些情况下需要在布局渲染时阻止输入。此外还提到了iOS计算器快速点击显示错误结果、通话时电源键行为不一致等实际案例。

Why DMARC's new "NP" tag can fail with DNSSEC

作者: matteocontrini | 评分: 37 | 评论数: 3 | 发布时间: 2026-07-05 15:00
文章摘要

RFC 9989更新的DMARC规范引入了新的"np"标签，用于指定针对不存在子域名的邮件策略。然而，该规范对"不存在域名"的定义与RFC 9824（DNSSEC紧凑型拒绝存在证明）存在冲突，导致np标签在启用DNSSEC的域名上无法正常工作。 这个问题影响所有使用Cloudflare、NS1、AWS Route 53和Azure等主流DNS提供商且启用DNSSEC的域名。具体来说，DMARC依赖NXDOMAIN响应来判断域名是否不存在，但DNSSEC的新标准可能返回不同的响应码，使得np策略无法正确应用。 作者已向IETF工作组报告此问题，问题已被确认但尚未找到解决方案。文章详细分析了DNS、DNSSEC的技术机制以及两个规范之间的不兼容性。

评论摘要
主要讨论点：DNSSEC与DMARC的np（non-present）策略在判断域名是否存在时的技术问题和设计缺陷 不同观点： • **DNS提供商实现问题**（pocksuppet）：问题根源不在DNSSEC本身，而是Cloudflare等DNS提供商为避免切换到TCP而做的优化选择。由于"域名不存在"的DNSSEC签名比"域名存在但无此类型记录"的签名长得多，提供商倾向于返回后者，导致"域名不存在"的策略无法触发。 • **实用主义解决方案**（winstonwinston）：邮件服务器实践中已有成熟做法——拒绝Envelope From域名没有MX或A/AAAA记录的邮件。DMARC验证器可以查询多种记录类型来判断子域名是否存在，无需区分NXDOMAIN和NODATA响应。 • **设计批评观点**（amluto）：DMARC的np功能语义设计本身有缺陷。质疑为何有任意DNS记录的域名就被视为"存在"，即使没有MX记录。批评这导致需要设置无关DNS记录来启用邮件发送（如noreply.company.com），且无法区分邮件用途和非邮件用途的子域名（如api.company.com）。建议应直接基于MX记录判断域名是否"存在"。 补充讨论：争议焦点在于"域名存在"的判断标准——是任意DNS记录的存在，还是应该特指MX记录的存在。这涉及技术实现、协议设计和实际应用场景的权衡。
