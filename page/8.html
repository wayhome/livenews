(On | No) Syntactic Support for Error Handling

作者: henrikhorluck | 评分: 373 | 评论数: 77 | 发布时间: 2025-06-03 16:18
文章摘要

文章讨论了Go语言中关于错误处理的冗长问题，尤其是频繁的`if err != nil`检查使代码显得繁琐。自2018年起，Go团队尝试解决此问题，最早提出了基于"check"和"handle"机制的方案，但被认为过于复杂。随后在2019年提出了简化的"try"方案，尽管进行了大量讨论和工具测试，但由于控制流不清晰和社区反对，该方案也被放弃。文章反思了过程中的失误，指出应更早引入新关键字并给予社区更多反馈空间。此后，社区不断提出新的错误处理建议，但尚未有新进展。总体而言，Go团队仍在探索如何简化错误处理，同时保持语言的简洁性和可读性。

评论摘要
主要讨论点：Go 语言的错误处理机制及其潜在改进 不同观点： • threemux 认为，很多人对 Go 团队的批评其实已经被深入讨论过，Go 团队的透明态度值得赞赏，并且其日常使用 Go 的体验依然良好。 • pie_flavor 批评 Go 的决策过程过于缓慢，尤其是在面对多个完善的提案时无法做出选择，导致问题长期得不到解决，相比之下 Rust 的决策过程更加高效。 • jamamp 支持 Go 的显式错误处理，认为这种机制让开发者在处理错误时有明确的选项，并建议在 Go 2 中引入 `Result` 类型以改进错误处理。 • maxwellg 表示逐渐喜欢上 Go 的错误处理机制，并通过使用 `panic` 来简化错误处理，尤其是在处理无效状态时。 • Mond_ 对文章中关于 Go 错误处理的语法冗长问题表示不满，认为更应该关注错误丢失、错误交互和泛型等问题。 • tsimionescu 批评手动添加堆栈跟踪作为错误处理的方式，并指出像 exceptions 这样的机制可以自动处理错误。 • d3ckard 建议 Go 引入类似 Elixir 的 `with` 语句来简化错误处理。 • JamesSwift 建议采用 Rust 的 `?` 操作符，并认为这不会导致错误被忽略，反而能强制开发者处理错误。 • hackingonempty 建议引入类似 Haskell 的 "do notation" 来处理错误、协程和生成器等，认为这是更通用的解决方案。 • reader_1000 强调堆栈跟踪的重要性，指出 Go 中缺乏堆栈跟踪导致的问题，尤其是在团队成员不一致的错误处理习惯下。 • pikzel 提到 Go 中错误遮蔽的问题，认为这会导致一种安全的错觉。 • MathMonkeyMan 认为 Go 的简洁性和一致性有其独特价值，建议不要过度添加新特性，以避免语言变得过于复杂。 补充讨论： • 争议的焦点在于 Go 错误处理机制的冗长性和显式性是否是优点，以及是否应引入其他语言（如 Rust、Elixir、Haskell）的特性来改进 Go 的错误处理。 • 另一个值得注意的讨论点是 Go 决策过程的缓慢和透明性，部分开发者认为这是优点，而另一些开发者则认为是缺点。 • 还有开发者关注错误处理中的具体问题，如错误遮蔽、错误丢失和错误交互等。 总结： Go 语言的错误处理机制在开发者社区中引起了广泛讨论，主要集中在语法冗长、错误丢失、决策过程缓慢和是否引入其他语言特性等问题上。不同开发者根据自己的经验和使用场景提出了各种改进建议和批评。

Standard Completions

作者: todsacerdoti | 评分: 19 | 评论数: 2 | 发布时间: 2025-05-31 12:00
文章摘要

本文讨论了多个提供与OpenAI兼容的Completions和Chat Completions API的供应商，如Deepseek、OpenRouter和vLLM等，虽然OpenAI已将Completions视为遗留API，且Chat Completions也被弱化以推广OpenAI Responses API。尽管OpenAI承诺无限期支持当前的Chat Completions API，但它缺乏多模态输出、输入对象存储、显式缓存和助理前缀等功能。各供应商以非标准方式添加了这些功能，导致开发者使用不便。例如，助理前缀在不同供应商中的实现方式各异，且没有标准信号来指示是否支持某些功能，开发者需尝试或检测上游供应商。文章呼吁建立一个标准化的OpenAI API超集，以简化开发者体验，并促进LLM生态系统的互操作性。感兴趣的供应商和开发者可参与Standard Completions工作组。

评论摘要
主要讨论点：关于旧的 completion API 与新的 chat creation API 哪个更优越的讨论 不同观点： • [lolpanda的观点] 认为 legacy completion API 优于新的 chat creation API。理由是 completion API 将所有输入视为单个字符串，而 chat API 则要求将输入作为消息列表处理。在处理现代的代理工作流时，模型通常需要处理大量输入数据，包括 RAG 数据、函数调用和其他元数据，用户和助手的消息仅是整体提示的一小部分。因此，将对话与其他输入数据统一格式化为一个单一的文本提示（如使用 ... 标签）更为直观。OpenAI 的新 completion API 支持单个大字符串或消息列表，这一点很不错。此外，他们提到在 Claude 工具中尝试过类似方法，将提示构建成包含指令和示例的较大提示。 • [pawanjswal的观点] 对 lolpanda 的观点表示赞同，指出许多开发者在开发过程中都会遇到这一问题。他认为指出 API 的不一致性并倡导建立一个通用基准是有益的，认可了 lolpanda 提出的改进建议。 补充讨论： • lolpanda 提到了新的 completion API 支持单个大字符串或消息列表，这表明新 API 也在尝试解决一些格式上的灵活性问题。 • 讨论中还提到 Claude 工具中的 XML 格式化方法，表明在不同平台上对提示格式的不同处理方式也是开发者关注的重点。 • 争议的焦点主要在于处理大规模输入数据时，哪种 API 格式更直观和高效。lolpanda 更倾向于使用单一的字符串格式，而新的 chat API 则采用消息列表的方式，这在处理复杂工作流时可能带来不便。

文章主要介绍了作者在学习和制作Forth编程语言过程中的经验和心得。Forth是一种简洁且基于堆栈的编程语言，作者通过几次实践，包括移植现有的Forth（如JONESFORTH）和制作极小核心的Forth，深入了解了Forth的实现和计算机工作原理。文章提出了三点建议：1. 考虑移植现有的Forth以学习语言实现；2. 制作一个极小核心的Forth，探索其最小功能集；3. 参考一些极小Forth实现，如PlanckForth、SmithForth、sectorforth、milliForth和StoneKnifeForth。作者强调，制作Forth的过程不仅能加深对语言的理解，还能带来编程的乐趣和成就感。

Fun with Futex

作者: ingve | 评分: 65 | 评论数: 5 | 发布时间: 2025-06-03 06:37
文章摘要

本文介绍了在Linux中实现优化锁的过程，重点讲解了从简单的自旋锁到使用操作系统原语的更复杂的锁。自旋锁通过不断重试来等待资源，其实现简单但会导致高CPU消耗。为了解决这一问题，文章引入了futex系统调用，它可以在锁不可用时让线程休眠，并在锁释放时唤醒它们。futex主要使用两个操作：`FUTEX_WAIT`用于让线程休眠，`FUTEX_WAKE`用于唤醒线程。这些操作依赖于一个32位整数值，线程休眠和唤醒都围绕该值进行。文章通过几个案例进一步解释了futex的行为，包括休眠与唤醒的条件以及值未改变时的行为。最终，通过使用futex，可以有效降低高并发情况下的CPU消耗。

评论摘要
主要讨论点：关于不同平台上锁和同步机制的实现及优化的讨论，重点关注futex及相关同步原语在不同操作系统内核中的表现，以及如何避免诸如优先级反转等问题。 不同观点： • [lilyball] 认为Darwin（苹果的操作系统内核）最近公开的futex API存在优先级反转的问题，因为Darwin的QoS线程优先级实现与其他内核不同。在Darwin中，低QoS线程只有在没有高QoS线程竞争时才会被处理，这会导致优先级反转问题。为了解决这个问题，建议使用`os_unfair_lock`，它可以通过优先级捐赠机制避免优先级反转。 • [skitter] 提出了一种替代futex的实现方法，即通过用户空间自行管理线程队列，例如Rust的`parking_lot`库。该方法通过一个字节来表示锁状态，并在竞争情况下使用全局哈希表存储线程队列，从而实现跨平台的紧凑锁机制。这种方法的优点是锁的尺寸小（仅1字节），并且可以更灵活地控制线程和实现不同的公平性策略，但缺点是只能在单进程内使用，无法像Linux的futex那样跨进程共享。 • [gpderetta] 对futex的工作机制进行了澄清，指出`FUTEX_WAIT`的正确理解应为“将线程休眠，除非值不是X”，而非“如果值未改变就不唤醒线程”。Futex应被视为一种边沿触发、无状态的同步原语，其核心在于避免错失唤醒（wakeups），而非关注futex位置的当前值。此外，futex不仅仅能实现互斥锁，还可以作为一种通用的等待和信号机制。 • [scottlamb] 提到了rseq（resume from userspace）的`RSEQ_SCHED_STATE_FLAG_ON_CPU`用于自适应用户空间互斥锁的可能性，并询问该技术是否已被实际应用。这种技术可以用于决定何时从自旋转为阻塞，对诸如`absl::Mutex`和`parking_lot::Mutex`等实现有潜在的帮助。 • [geertj] 讨论了锁机制中进入内核等待和唤醒的成本问题，并提出是否有可能避免持有锁的线程在释放锁时再次进入内核执行唤醒操作。他提出了一种无需系统调用的唤醒操作设想，例如利用Intel的调试寄存器来触发内核任务，但承认这种方法仍需要一个内核线程进行忙等待。 补充讨论： • 争议焦点在于如何有效实现和优化锁机制，尤其是在不同平台上（如Darwin和Linux）如何避免优先级反转、减少内核调用次数以及提高锁的性能和灵活性。 • 讨论中还涉及了futex的工作原理及其误解，特别是关于`FUTEX_WAIT`和`FUTEX_WAKE`的行为，以及futex作为一种通用同步原语的广泛用途。
