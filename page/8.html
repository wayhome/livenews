文章摘要

Structured Errors in Go (2022)

作者: todsacerdoti | 评分: 118 | 评论数: 16 | 发布时间: 2025-06-01 04:54
文章摘要

这篇文章讨论了Go语言中错误管理的问题，特别是在中型程序和HTTP API中的应用。作者通过一系列实验，提出了一种简化错误处理的方法，并开发了一个新的库来实现这一目标。Go的错误处理通常依赖于返回值，而非异常机制，最简单的错误形式是字符串。虽然这种设计简单，但缺乏结构化信息。 文章强调了结构化日志的重要性，指出在错误管理中，错误信息需要被结构化，以便于日志聚合器和报警系统处理。传统上，错误信息是简单的字符串，难以进行有效的过滤和分析。为了改善这一情况，作者建议将错误信息结构化，例如在日志中加入"account_id"等具体字段，以便更好地诊断问题。 最终，作者提出了一种方法来弥合错误值和结构化日志之间的差距，并通过一个新库来实现这一功能，以提高错误管理的效率和可维护性。

评论摘要
主要讨论点：Go 语言中错误处理和元数据管理的实现方式及其优缺点 不同观点： • atombender 认为 `WithMeta()` 的实现有缺陷，既不支持并发安全，又会修改父 map。他建议使用树状结构来管理元数据，通过父节点指向之前的元数据，避免每次都分配新的 map。同时，他提出另一种方案，主张通过返回包含已知失败操作数据的结构化错误，并在错误上行过程中逐步添加元数据，这样只需在错误发生时付出性能代价。 • RadiozRadioz 强调错误不应该仅仅作为字符串返回，而应使用类或类型来区分不同种类的错误（如 HTTP 状态码 502 和 404），否则需要通过正则表达式来解析错误，非常麻烦。他还提到堆栈跟踪的重要性，以便在捕获和包装错误时能精确定位错误来源。 • samber 分享了自己编写的错误包装库 `oops`，该库支持完整的堆栈跟踪以及丰富的元数据添加功能，如时间、标签、用户信息等。 • darthbanane 指出 `WithMeta` 函数在参数不是成对出现时会引发 panic，认为这是 Go 错误处理困难的一个例子。 • gregwebs 提到使用现有的 Go 错误库，并推荐使用 `slog` 属性来复用日志属性，从而实现添加元数据的功能。 • sethammons 支持结构化错误日志，并分享了自己编写的 Go 错误包装工具 `kverr`，同时提到在 Python 中也希望实现类似的结构化异常处理。 • fastest963 介绍了自己使用 `errctx` 库来存储错误中的键值对，并实现了错误展开以查找深层存储的键。 • weakfish 对使用第三方库进行结构化日志记录持怀疑态度，认为应该使用 Go 自带的 `slog`。 • altbdoor 认为 Go 的错误处理有些奇怪，但自己主要是在小项目中使用，因此影响不大。 • vikeri 指出错误中缺少标记特定错误代码的功能，无法轻松地对相似错误进行分组，并询问是否可以通过 "tag" 实现这一需求。 • dedicate 提问，对于中小型项目来说，这种高度结构化的错误处理是否会带来过多工作量，是否值得。 • sigmonsays 认为可以使用 Go 内置的 `errors.Wrapf` 和 `slog` 来实现类似的功能，无需额外引入复杂的库。 • aor215 分享了自己几年前写的一篇关于错误处理的文章，并提到其解决方案在多个项目中得到了成功应用。 补充讨论： • 错误处理中的并发安全性、性能代价和内存开销是争议的焦点之一。 • 使用字符串作为错误返回值的缺点被多位讨论者提到，推荐使用结构化错误或错误类。 • 堆栈跟踪和元数据（如标签、用户信息）的添加被认为是错误处理中的重要功能。 • 不同开发者对第三方库和 Go 自带工具的选择存在分歧。 • 对于中小型项目是否需要高度结构化的错误处理，讨论中提出了实用性和工作量的问题。

Hypervisors for Memory Introspection and Reverse Engineering

作者: todsacerdoti | 评分: 5 | 评论数: 0 | 发布时间: 2025-06-02 08:06
文章摘要

本文介绍了基于Rust的 hypervisors（虚拟机监视器）——`illusion-rs`和`matrix-rs`，用于Windows下的内存自省和逆向工程。两者利用扩展页表（EPT）实现控制流隐蔽重定向，且不修改客户机内存。 `illusion-rs`是基于UEFI的hypervisor，使用单一EPT和就地修补，结合`VMCALL`和`Monitor Trap Flag (MTF)`实现安全指令重放。`matrix-rs`则采用双EPT模型，主EPT映射读/写内存，辅助EPT重映射执行页，通过`INT3`和动态EPTP切换实现执行重定向。 文章详细介绍了EPT钩子技术，包括如何使用影子页隐藏内联钩子并重定向执行流。这些技术依赖于CPU指令陷阱（如`VMCALL`、`CPUID`、`INT3`）进行控制转移，并通过EPT映射实现对客户机函数的监控。 本文旨在填补信息安全领域对游戏黑客技术的应用空白，提供可复现的EPT钩子技术指南，且不依赖未公开的系统内部机制或特权SDK。

Progressive JSON

作者: kacesensitive | 评分: 487 | 评论数: 60 | 发布时间: 2025-06-01 00:58
文章摘要

文章探讨了一种称为“渐进式JSON”的数据传输方法，灵感来自渐进式JPEG图片加载。传统JSON需要完整接收后才能解析和使用，导致如果某个部分（如数据库查询）较慢，客户端必须等待整个数据传输完成。文章提出了一种流式JSON解析器，可以在数据不完整时部分解析，但这种方法存在对象不完整、类型不匹配的问题，使用起来较复杂。 为解决此问题，文章提出“渐进式JSON”方法，采用广度优先传输策略，先传输对象的占位符，再逐步填充内容。例如，先传输顶层结构，再异步填充具体内容，这样即使某部分数据生成较慢，也不会阻塞其他部分的传输和显示。这种方法类似于渐进式图片加载，能提高数据传输效率和用户体验。

评论摘要
主要讨论点：React Server Components (RSC) 及其相关的渐进式 JSON 流处理的可行性和必要性 不同观点： • **支持 RSC 和渐进式 JSON 的观点**： - **goranmoomin**：解释了 Dan Abramov 的文章实际上是在解释 React Server Components 的概念，而不是提出一个新的 JSON 格式。React Server Components 允许在组件树中留空，以显示加载状态，从而提高用户体验。渐进式加载可以让页面更快速地显示基础内容和占位符。 - **xelxebar**：支持渐进式加载的概念，认为这种方法可以应用于任何树状数据结构，通过先发送头信息，再分批发送数据块，可以显著提升加载速度。 - **bilater**：认为渐进式 JSON 流应该是 JavaScript 环境中的一等公民，特别是在处理大模型输出时，这种流式处理非常有用。 • **质疑 RSC 和渐进式 JSON 的观点**： - **jatins**：质疑 RSC 的必要性和抽象复杂性，指出许多前端开发者仍不理解 RSC 的概念，且其推广可能更多是为了迎合某些厂商的平台需求，而非真正满足用户需求。 - **Velorivox**：认为绝大多数应用不需要如此复杂的解决方案，简单的多次调用即可解决大多数问题。 - **turtlebits**：认为文本/HTML 不像媒体文件那样需要渐进式加载，这种方法似乎是为解决自身体系复杂性而引入的额外复杂性。 • **替代方案和改进建议**： - **jerf**：提出了两种替代方案，一是重构 JSON 格式，二是保证属性顺序，以实现渐进式解析，而不需要引入复杂的流式处理。 - **atombender**：建议使用 Mendoza 格式进行增量更新，这种方法可以通过发送增量数据来减少传输量，同时保持高效的解析和更新。 - **rictic**：推荐使用 jsonriver 工具来进行渐进式 JSON 解析，提供了一种简单易用的 API。 - **camgunz**：认为通过不同的端点设计可以解决大部分问题，包括缓存、过滤、实时更新等，而不需要复杂的文档系统应用平台。 - **jarym**：支持使用 JSON Patch 和行分隔 JSON，认为这种方法更容易理解和实现。 - **aljow**：认为如果需要对 JSON 进行如此复杂的处理，可能 JSON 本身就不是适合的格式，应该重新考虑数据格式设计。 补充讨论： • **渐进式加载的具体实现和技术细节**： - **pjungwir**：提出了如何在数组中实现渐进式加载的设想，通过 Promise 和异步生成器来实现数组的流式处理。 - **hyfgfh**：指出性能问题的根源可能在于架构设计和 API 设计，而不是简单的框架或工具选择，认为需要更基础的 web 标准演进才能解决根本问题。 争议焦点： • **RSC 的必要性和复杂性**：一方认为 RSC 提供了更好的用户体验和加载性能，另一方则认为其复杂性过高，且许多开发者并不理解其真正用途。 • **渐进式 JSON 的实用性**：一方认为这种方法可以显著提升性能和用户体验，另一方则认为对于大多数应用来说，这种复杂性并不必要。 总结：讨论围绕 React Server Components 和渐进式 JSON 流处理的可行性、必要性及其实现细节展开，参与者提出了支持和质疑的观点，并讨论了多种替代方案和技术实现细节。争议主要集中在 RSC 的复杂性和其实际应用价值上。
