Mullvad exit IPs are surprisingly identifying

作者: RGBCube | 评分: 372 | 评论数: 24 | 发布时间: 2026-05-15 02:35
文章摘要

文章指出 Mullvad VPN 会按 WireGuard 公钥确定性分配服务器出口 IP，而非每次随机。作者测试 9 台服务器、3650 个公钥后发现，理论上组合巨大，实际仅出现 284 种。原因可能是 Mullvad 用公钥作种子调用 RNG，并以各服务器 IP 池大小为上限，导致不同服务器分配到相近百分位的 IP。这样多个出口 IP 组合可能成为识别用户的指纹风险。

评论摘要
主要讨论点：Mullvad 被曝不同服务器出口 IP 分配存在可关联性，可能形成用户级指纹；讨论集中在其严重性、VPN匿名预期、修复与披露流程。 不同观点： • Mullvad回应：部分行为是有意设计、部分不是；成因与原文描述不完全一致，已在部分基础设施测试补丁，并会重新评估“隐私 vs 用户体验”的取舍；同时呼吁研究者发布前先通知厂商。 • 风险严重派：认为这种跨服务器稳定映射像“情报机构会设计的VPN”，可帮助论坛管理员识别封禁用户小号；元数据仍会泄露身份。 • 质疑论证派：有人指出“>99%同一人”的说法统计上不严谨；重叠区间只能排除大多数用户，不能直接得出个体识别准确率。 • VPN定位派：认为VPN本就不等同Tor，不应期待对访问网站匿名；需要强匿名应使用Tor，且Tor也可能被出口节点攻击。 • 工程折中派：单服务器内稳定IP有用户体验价值，例如固定服务可用性；但跨服务器相关性应修复，如用 user key + server id 随机化。 • 信任Mullvad派：有评论称Mullvad过往在地理定位数据上较诚实，相信会修复。 • 站点治理派：有人认为网站运营者可利用此属性执行封禁；也有人提到持续维护VPN IP封锁列表，服务方与用户之间是“猫鼠游戏”。 补充讨论：有人追问作者是否提前联系Mullvad；还有人疑惑第三方客户端为何不能像官方客户端一样轮换WireGuard key。

RTX 5090 and M4 MacBook Air: Can It Game?

作者: allenleee | 评分: 594 | 评论数: 33 | 发布时间: 2026-05-14 15:47
文章摘要

文章介绍作者将RTX 5090桌面GPU通过Thunderbolt eGPU接到M4 MacBook Air。因macOS缺乏驱动，改用macOS宿主上的ARM Linux虚拟机做PCI直通，解决BAR映射、DMA等问题，并测试游戏与AI推理性能。结论是可行但受带宽、驱动和兼容性限制。

评论摘要
主要讨论点：围绕在 Apple Silicon Mac 上通过 eGPU/RTX 5090 实现 GPU 直通、游戏运行与本地 AI 推理加速的技术意义和可行性。 不同观点： • 技术突破派：多人认为这是“疯狂科学”“真正的黑客精神”，尤其赞赏 DMA、QEMU、驱动等底层实现，突破了“Apple Silicon 不支持 eGPU”的普遍认知。 • AI 实用价值派：认为最重要的不是游戏，而是本地 LLM 推理，尤其是 prefill/TTFT 大幅改善；长上下文下 Mac 自带 GPU 解析慢，而 eGPU 可让本地推理更实用。 • 苹果支持不足派：有人长期希望 Apple 支持 VM GPU 直通或开放更好的 PCIe/eGPU能力，批评当前限制如 1.5GB window；也指出官方仅支持 Intel Mac + AMD eGPU。 • 游戏角度：游戏演示有趣，但并非理想 Mac 游戏方案；也有人指出部分问题可能通过 Vulkan/MoltenVK 支持解决，未必需要如此复杂的 RTX 5090 外接方案。 • 实操兴趣派：有用户考虑将闲置 5090 接入 M4 Mini 做本地推理，但担心供电、固定结构，以及模型并发参数如 max-num-seqs 与 max-model-len 的取舍。 • AI 辅助质疑派：有人调侃项目中先问 AI 的做法，认为 AI 常会编造或否认新硬件信息。 补充讨论：争议焦点主要在于该方案的实际应用价值：作为游戏方案偏炫技，但作为 CUDA/本地 AI 加速方案被普遍认为更有现实意义。

Spectre Programming Language

作者: asdkop | 评分: 31 | 评论数: 4 | 发布时间: 2026-05-15 23:14
文章摘要

Spectre 是面向低层系统编程的安全、契约式语言，支持类型不变量、函数前后置条件和默认不可变。其目标是在保留手动内存控制与开发便利的同时提升正确性；契约可编译期检查，必要时运行期检查。它编译到 QBE IR，并支持实验性 LLVM/C99 后端及 C 到 Spectre 转译。

评论摘要
主要讨论点：围绕该语言/工具的安全性定位、实际价值以及“trust”机制的必要性展开讨论。 不同观点： • 安全性存疑：Panzerschrek 关心它是否真正做到“安全代码无未定义行为（UB）”，还是只增加了一些安全特性，但仍存在漏洞，可能导致严重 bug。争议焦点在于其安全承诺是否足够严格、可验证。 • 价值定位不清：slowcache 认为它的生态位不明确。其主要吸引点似乎是能在函数内提供 invariants（不变量），但这并非新概念，只是变成了专门关键字；除此之外，看起来像是功能不完整的 Rust。 • 反对显式 trust 机制：yesbut 针对“IO 等底层含 unsafe 的操作必须显式 trust”提出反对，认为只需文档标注哪些操作是 impure（不纯）即可，不应强迫程序员额外输入关键字。 补充讨论：评论之间共同关注的是“形式化安全/纯度控制”是否带来足够收益。分歧在于：严格标注和不变量机制是否能显著提升安全性，还是只是增加语法负担、削弱实用性。
