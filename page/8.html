Zig: Build System Reworked

作者: tosh | 评分: 321 | 评论数: 20 | 发布时间: 2026-05-30 08:38
文章摘要

Zig编程语言在2026年5月26日对构建系统进行了重大重构。主要变化是将`build.zig`的编译过程分为两个独立进程：配置器（configurer）和制造器（maker）。配置器以调试模式编译用户的构建逻辑并生成二进制配置文件，制造器以发布模式编译并执行构建图。 这次改进带来三大性能提升：1) 每次修改只需重新编译用户的`build.zig`代码，而非整个构建系统；2) 当配置未变化时可跳过重新运行构建逻辑；3) 执行构建图的进程现在启用了优化。基准测试显示`zig build --help`命令的执行时间从150ms降至14.3ms，性能提升超过90%。此外，第三方工具如ZLS也能从序列化配置文件中受益。

评论摘要
主要讨论点：Zig 0.16.0 版本发布后，开发者对该语言的评价和使用体验 不同观点： • **积极支持派**：认为 Zig 是优秀的"工具语言"和"车库修补"语言，简单易上手，设计周到，新的 IO 机制高效且代码优雅，编译速度出色，跨平台编译能力强大（特别是 glibc 版本控制） • **谨慎观望派**：关注稳定性问题，认为像异步 IO 这样的大特性表明语言仍不稳定，询问何时会有稳定版本发布 • **对比质疑派**：质疑 Zig 相比其他语言的优势，如"为什么要用 Zig 而不是 Node.js/TypeScript"，以及 Rust 用户是否应该尝试 Zig • **功能批评派**：认可 Zig 的诸多优点，但对字符串处理感到不满，认为过于繁琐，希望有可选的 RAII 支持来简化字符串和容器管理 补充讨论： 有开发者提出"双语言编程"理念，认为 Zig 可能是高级语言之外的理想低级语言搭档，比 C++ 和 Rust 更容易在长时间中断后重新上手。社区对 0.17.0 快速发布（几周内）感到惊喜，因为 0.16 用了超过一年。另有人询问 MIT License (Expat) 的含义。

A disappearing Service Processor (2025)

作者: mooreds | 评分: 20 | 评论数: 3 | 发布时间: 2026-05-30 20:05
文章摘要

这篇文章讲述了 Oxide 团队调试服务处理器(SP)网络掉线问题的过程。SP 运行自研的 Hubris 操作系统,问题表现为 SP 从管理网络消失但主机 CPU 仍运行。团队最初怀疑是任务饥饿或栈溢出,通过 LED 闪烁等调试手段排查。最终通过 SWD 调试接口发现 CPU 无法被暂停,将问题定位到新增的 FPGA 与 STM32H7 处理器之间的并行总线通信上——可能是 FPGA 时序问题导致 CPU 在读取寄存器时永久挂起,因为未收到总线应答信号。

评论摘要
主要讨论点：FPGA Mezzanine Card (FMC) 总线配置错误导致的技术问题 不同观点： • **技术问题分析**（Animats）：核心问题是将 FMC 总线的基地址错误配置为 Normal Cached 内存类型，导致外部非内存设备被放在缓存后面。这种配置从根本上无法正常工作，只能偶尔碰巧运行。 • **历史关联**（indigodaddy）：这个问题让人联想到 Sun/Sparc 硬件和 Solaris 系统时代的类似经历，暗示这类配置错误在硬件开发历史上并非首次出现。 补充讨论：als0 提供了术语解释，指出 Service Processor (SP) 本质上是另一种 Baseboard Management Controller (基板管理控制器)，帮助不熟悉该领域的读者理解技术背景。整体讨论围绕硬件配置错误展开，没有明显争议，更多是技术问题的确认和经验分享。

Stateless Actors

作者: frizlab | 评分: 39 | 评论数: 4 | 发布时间: 2026-05-29 13:28
文章摘要

这篇文章探讨了无状态 Actor 的实用性。作者认为虽然 Actor 的主要目的是保护可变状态，但无状态 Actor 仍有价值： 1. **NetworkClient 类型**：无状态 Actor 自动具备 Sendable 特性，且方法不会在主线程执行，适合处理网络请求和 JSON 解码等耗时操作。但也有缺点：难以配合协议使用，且串行执行限制了并发性能。 2. **BackgroundActor**：虽然提供了类似 @MainActor 的后台执行方式，但存在串行执行和类型系统侵入性强的问题，不如使用语言现有的隔离控制机制。 3. **自定义执行器 Actor**：用于将 Swift 并发系统与其他队列系统（如 DispatchQueue）集成，是重要的适配工具。 总体而言，无状态 Actor 有其应用场景，但需权衡利弊。

评论摘要
主要讨论点：关于"无状态actor是否无意义"的技术讨论 不同观点： • **抽象设计观点（Nevermark）**：认为无状态概念在高度可组合的语言中有实际意义。任何事物的"null版本"都可能有用，如无状态的状态、无操作的操作、无目标的网络端口等。这是因为现有语言在抽象设计和性能之间难以平衡，导致开发者会过度或不足地使用抽象。 • **Swift技术实现观点（mayoff）**：从Swift语言角度明确反对"无状态actor"的存在。指出Swift中的actor必须实现`unownedExecutor`属性，且作为引用类型本身就携带身份状态，因此技术上不存在真正的无状态actor。 • **并发保护质疑观点（mrkeen）**：对actor的实际价值持怀疑态度。通过竞态条件的例子说明，使用私有字段、getter/setter或actor来保护可变状态，最终效果与直接操作相同，只是增加了样板代码，暗示这些机制可能只是表面功夫。 补充讨论：讨论涉及语言设计哲学、具体技术实现和实用价值三个层面，反映了理论抽象与工程实践之间的张力。

MacSurf 是一个为 25 年前的 Mac OS 9 PowerPC 系统开发的现代网页浏览器。它支持 CSS3、ES5 JavaScript、PNG 透明度和原生 TLS 1.2/1.3 加密连接，能在 233 MHz G3 处理器上运行。 该项目基于 NetSurf 移植，是首个在 Mac OS 9 上支持 CSS Grid、CSS 自定义属性和 ES5 JavaScript 的浏览器。最新版本(v1.3.1)实现了多曲线 ECDHE 和 TLS 1.3 协议，内置 121 个 Mozilla CA 证书，无需代理即可访问现代 HTTPS 网站。 目前处于早期 alpha 阶段,可运行但尚不完善。使用 C89 和 Carbon/QuickDraw 等经典工具开发,旨在让老旧 Mac 重新连接现代互联网。

评论摘要
主要讨论点：为Mac OS 9等老旧系统开发现代浏览器MacSurf的意义和影响 不同观点： • **积极支持派**：认为这是延长老旧硬件生命周期的重要尝试，体现"太阳朋克"理念，减少电子垃圾。有人提到可能延续价值上亿美元的工业设备使用寿命（如韩国和日本的仓储起重机系统） • **技术怀旧派**：多位用户表示要在自己的iMac G3、PowerMac G4等老设备上测试，怀念Classilla等老浏览器，认为老Mac OS界面经过良好的用户体验研究设计 • **技术批判派**：指出现代网络需求膨胀，运行JavaScript需要的晶体管密度是过去的2000倍以上，认为"我们真的搞砸了" • **对AI使用的保留态度**：有用户明确表示作者使用AI开发"有点令人失望"（kinda meh） 补充讨论： - 有技术细节讨论，如期待看到PowerPlant/C++或MacApp/Object Pascal实现 - 兼容性问题：需要Mac OS 9.1以上版本，9.0无法运行 - 项目已实现TLS 1.3支持，作者承诺持续改进 - 有用户希望Amiga系统也能有类似项目
