Cosmoe 是一款新的 C++ UI 库，旨在为 Wayland 创建易于开发且资源消耗低的图形应用程序。它将 BeOS 类库的优势带入现代内核和显示引擎，具有易用、多线程和高性能的特点。目前，Cosmoe 仍处于开发阶段，作为源代码技术预览提供，用户需要从 GitLab 下载并编译代码。未来的改进重点包括稳定性和兼容性，目标是实现完整的 BeOS API 支持。Cosmoe 基于 MIT 许可证发布，是 Haiku 操作系统的一个分支，而当前版本与之前的 "Cosmoe Classic" 不同，后者是 Haiku 到 Linux 内核的完整移植。开发者正专注于共享库版本的开发，以实现最大的实用价值。

Chromium Switching from Ninja to Siso

作者: hortense | 评分: 109 | 评论数: 12 | 发布时间: 2025-06-18 08:49
文章摘要

Chromium的构建系统正在从Ninja迁移到Siso，这一更改已对Google内部开发者完成，现扩展到外部贡献者。外部开发者无需手动更改，继续使用`autoninja`即可，系统将在下一次运行`gn clean`后自动使用Siso。若遇到问题，可设置`use_siso=false`以暂时切回Ninja。Ninja和Reclient将在9月底不再支持，建议在此之前完成迁移。Siso旨在支持远程执行，并正与多个远程构建服务提供商确认兼容性。如有问题，可通过Slack、Chromium Issue Tracker或邮件联系。

评论摘要
主要讨论点：Chromium项目引入新的构建工具Siso及其与现有工具（如Bazel、Ninja）的关系 不同观点： • Intexpress认为，Siso使用Starlark（Bazel的构建语言），可能是Chromium最终使用Bazel的过渡步骤。这暗示Siso可能是为了逐步引入Bazel而设计的中间工具。 • RainyDayTmrw对Chromium需要自定义构建系统表示惊讶，并质疑为何不直接使用Google已有的Bazel，而是开发新工具Siso，并认为新工具名称中还引用了Bazel。 • Ahartmetz批评Chromium团队没有采用已知的解决构建时间过长问题的方案（如物理代码设计），而是通过新工具来解决，暗示这可能是为了追求表面成果。 • Jefftk指出这是Chromium的第四个构建系统（前三个为Scons、Gyp、Ninja），对频繁更换工具表示关注。 • Pjmlp质疑Siso是否只是又一个“非我发明”（NIH）综合症的产物，并指出Ninja和CMake是C++20模块构建的唯一方式，认为Chromium可能不会采用新的工具。 • Txdv询问Siso提供了哪些Ninja不具备的功能，质疑Siso的必要性。 • Operator-name提供了Siso的官方链接，指出Siso与Ninja兼容，但针对Chromium的特定用例进行了优化和调优。 • Mrlonglong提到Siso增加了对Go语言的依赖，暗示这可能带来新的复杂性。 • Kookamamie询问Siso是否可以作为Ninja的通用替代品，是否能用于一般的Ninja项目构建。 • Charcircuit猜测AOSP（Android开放源代码项目）是否也会迁移到Siso，认为Siso作为Ninja的替代品，迁移成本可能较低，并且提到之前Bazel的迁移计划被取消。 补充讨论： • Kosolam直接批评负责Siso的Google开发者不称职，暗示对该工具的开发不满。 • 讨论中多次提到构建时间过长的问题，以及对现有成熟解决方案未被采用的失望。 • 对Siso与Ninja的兼容性、特定优化及其在不同项目中的应用前景存在疑问和争议。 争议焦点： • 是否需要开发新的构建工具Siso，还是可以直接使用现有的Bazel或Ninja。 • Siso是否真正解决了Chromium构建中的关键问题，还是只是增加了不必要的复杂性。

Verified dynamic programming with Σ-types in Lean

作者: rck | 评分: 83 | 评论数: 6 | 发布时间: 2025-06-17 14:28
文章摘要

这篇文章介绍了如何使用记忆化（memoization）技术在Lean中解决一个动态规划问题，并验证其正确性。文章以Bytelandian Gold Coins问题为例，首先描述了问题的规则：在Byteland，每个金币可以兑换为n/2、n/3和n/4三个金币，最终目标是获得最多的美元。文章提出了一个递归关系来解决这个问题，并给出了初始的递归解法。 接着，文章展示了如何将该问题记忆化，通过使用HashMap缓存子问题的解，以提高效率。记忆化解决方案通过递归地查询和更新HashMap来避免重复计算。 文章还提出了一个正确性声明，即记忆化解决方案与递归规范解等价，并讨论了证明这一声明的困难之处，强调了证明过程中对数据结构不变性的依赖。文章最后邀请读者尝试自行证明，并指出直接证明虽然可行，但过程复杂。

评论摘要
主要讨论点：Lean语言中的子类型、语法复杂性、证明技巧和Sigma类型的应用 不同观点： • [gugagore] 认为Lean中的"subtype"概念与基于类的面向对象编程语言中的子类型概念没有太多关联。他指出，类型论和集合论的一个关键区别在于，一个元素在一个类型中是唯一的。他提供了Lean文档的链接以支持其观点。 • [CSMastermind] 表达了对学习Lean的兴趣，但认为像"let rec helperMemo : Nat → HashMap Nat Nat → Nat × HashMap Nat Nat"这样的语法令人精神上难以解析，需要高度集中注意力以免忽略重要细节。 • [almostgotcaught] 认为所讨论的证明方法是穷举证明，即通过计算整个备忘表并与递归定义的返回值进行比较。他认为这种证明可以在任何支持递归的语言中实现。 补充讨论： • [jeremyscanvic] 对所讨论的技巧表示感兴趣，但没有深入讨论技术细节。 • [Gehinnn] 提供了一个不使用Σ-types的经典强归纳证明示例，并讨论了在算法内进行证明的优势，即无需复制分支结构。他还提到在证明过程中处理变量和特定语法（如r.fst/r.snd vs r=(fst, snd)）的困难。 • [xnacly] 对Sigma类型表示了简单的关注，但没有展开具体讨论。 争议焦点： • 对于Lean的语法复杂性存在不同看法。[CSMastermind]认为语法复杂且难以解析，而其他评论者如[Gehinnn]则关注具体证明过程中的技术挑战，未提及语法问题。 • [almostgotcaught]对证明方法的定性与其他评论者的技术讨论形成对比，他认为这种证明方法是穷举法，并强调其在其他语言中的可实现性。

文章摘要

本文讨论了React服务器组件（RSC）的复杂性及其背后的工程设计，重点通过**hydration（注水）**和**composition（组合）**两个角度来解释其优势和困惑。RSC并非故意复杂或为了销售服务器资源，而是为了提升用户体验（UX）和开发体验（DX）。传统客户端渲染和服务器端渲染各有优点，但RSC通过独特的设计解决了以往难以扩展的问题。 文章解释了**hydration**的高成本和过度使用问题，以及它在不同场景下的局限性，如状态共享和组件复用。通过**isomorphic rendering（同构渲染）**，整个网页在服务器端渲染后传输到客户端，但会带来全页面注水导致的性能问题，包括交互延迟。 RSC通过组合方式解决了这些问题，避免不必要的注水。文章还简要说明了注水过程及其成本，强调RSC的复杂性在于需要建立新的思维模型，但理解后会发现其设计优势。 总结：RSC通过独特的设计和组合方式，解决了传统渲染方式的扩展性问题，尽管理解复杂，但其工程设计带来了显著的性能提升。
