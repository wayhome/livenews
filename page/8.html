Show HN: Running the second public ODoH relay

作者: rdme | 评分: 117 | 评论数: 13 | 发布时间: 2026-05-14 10:44
文章摘要

文章介绍 Numa v0.14 对 ODoH（Oblivious DNS over HTTPS）的支持：通过客户端、匿名中继和目标解析器分离“用户 IP”和“DNS 查询内容”，避免单一 DNS 服务商同时看到二者。Numa 使用 HPKE/odoh-rs 加密，提供单二进制部署、无需账户，并默认搭配 Numa 公共中继与 Cloudflare 目标。作者说明了实现中的 SSRF 防护、运营方隔离检查及部署方式，也强调 ODoH 并非万能：目标仍能看到查询，递归出口仍可能泄露，小流量中继易被流量分析，公钥分发仍依赖 HTTPS/WebPKI。

评论摘要
主要讨论点：围绕 ODoH/DoH/DoHoT 等隐私 DNS 方案的实际匿名性、信任边界、部署运维和使用场景展开。 不同观点： • 自建派：Bender 认为关键问题是“谁控制代理、DoH 服务器和证书”，信任链会无限下探；因此更倾向自建 Unbound DoH，自己决定 DNS 在哪里回落到明文 UDP 53，并通过缓存、预热、迁移 cache 来减少可观察 DNS 行为。 • 质疑匿名性派：cedws 指出 ECH 普及率低，即使 ODoH 隐藏 DNS 查询，访问的服务器名称仍可能通过其他层暴露，质疑其卖点。gigatexal 也追问“真正匿名 DNS”是否可能。 • 支持公共基础设施派：binyang_qiu 肯定有人实际运行公共 ODoH，而非停留在理论隐私讨论，并关注公共 relay 最大运维痛点。 • 替代方案派：DyslexicAtheist 推荐用 dnscrypt-proxy 实现 DoHoT（DNS over HTTPS over Tor），认为缓存可缓解速度问题，但提醒要先理解威胁模型。 • 工具集成需求派：dontfeedthemac 关注零配置、Mac/Docker、作为服务运行、与 Tailscale 集成、替代 tsdproxy、通过 Docker socket 做服务发现等实用功能。 • 实现细节说明：rdme 介绍 relay 部署在 VPS systemd 上，用 Caddy TLS，做 SSRF 加固、禁止 IP literal、检查 relay 与 target 是否同运营者，并使用 Cloudflare odoh-rs/numa。 • 其他疑问：piuvas 询问架构图制作方式；skinfaxi 质疑 private TLD 的最终目标，担心是否会演变成加密货币项目。 补充讨论：争议焦点在于 ODoH 能否在现实网络中带来有效匿名性，以及应信任公共中继/解析器，还是自建并通过缓存等方式降低暴露面。

Myths about /dev/urandom (2014)

作者: signa11 | 评分: 87 | 评论数: 12 | 发布时间: 2026-05-14 11:26
文章摘要

文章澄清关于 Linux `/dev/urandom` 与 `/dev/random` 的误解：二者曾使用同一 CSPRNG，`/dev/urandom` 适合加密用途；`/dev/random` 的阻塞并非安全优势，“熵耗尽”常被误解，约256位熵已足够长期安全。现代 Linux 已重构，二者差异几乎消失。

评论摘要
主要讨论点：围绕 Linux `/dev/random`、`/dev/urandom`、CSPRNG 熵耗尽说法及其安全意义的争论。 不同观点： • 质疑实际风险：有人问除 Debian SSH 密钥事故外，是否真有严重 Linux 漏洞源于 PRNG 可预测；认为在现代 OS 攻击面中，预测内核 PRNG 可能很边缘，过度强调或成“安全剧场”。 • 反对“熵耗尽”叙事：认为 CSPRNG 本质类似加密，用少量真实熵作为种子扩展出随机流；若可预测就等于密码算法失效。`/dev/random` 阻塞和熵估算被批评为概念混乱，启动早期才是真正需要关注的场景。 • 支持持续混入新熵的防御价值：新熵可逐步替换内部状态，提供类似前向安全的防御纵深；即使状态或输出被部分猜中，后续也会越来越难预测。 • 工程实践批评：有人举 PHP CMS 页面加载被 `/dev/random` 阻塞数秒的例子，认为保留阻塞行为是糟糕设计；也说明 GDB 可用于排查脚本语言底层阻塞问题。 • 特殊攻击模型讨论：提到 Dual_EC_DRBG 这类疑似后门 PRNG，需要连续输出推断状态；在这种构造下阻塞式播种可能略有状态隐藏优势，但结论仍是“不该使用这种生成器”。 • 文章表达问题：多名评论者抱怨原文结构混乱，难以分辨“事实”“谬误”和补充评论，影响理解。 补充讨论：有人推荐 Filippo 的相关演讲；也有人追问多年后 man page 是否已修正，说明 `/dev/(u)random` 的误解长期存在。

主要讨论点：CSS Rhythmic Sizing / CSS Rhythm 提案是否有价值、是否成熟，以及它解决的问题是否被清楚表达。 不同观点： • 质疑提案成熟度：adzm指出该草案首版已接近十年，链接中的2017版之后似乎变化不大，仍有大量未解决问题，说明规范推进缓慢、状态不稳定。 • 批评用例和问题定义不清：adzm和akersten都认为提案没有充分说明使用场景。akersten尤其表示不理解“rhythmic sizing”到底解决什么问题，也看不出为什么“之后”的截图比“之前”更好。 • 认为功能过于晦涩且小众：akersten觉得“CSS会在多列中保持垂直节奏”这种描述很不透明，适用范围似乎很窄，不值得优先投入实现资源。 • 质疑优先级：akersten认为CSS还有许多更明确、被广泛请求的缺失功能，浏览器实现者应优先处理那些问题，而不是这个表达不清的提案。 • 替代方案观点：akersten提出，如果仍需手动配置间距，那直接给 blockquote 等元素设置基于 `em` 的 margin 似乎也能解决问题，因此不清楚该提案相对现有CSS的优势。 补充讨论：争议焦点在于该规范是否真正解决了重要排版问题，以及其价值是否被文档、示例和截图充分证明。评论中也提到可能存在审美或文化差异：第二张截图也许对某些排版文化更美观，但发言者本人无法感知其优势。
