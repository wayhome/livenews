文章摘要

文章讨论了在批处理任务中，开源大语言模型（LLM）相比闭源模型（如GPT、Claude、Gemini）的优势。尽管闭源模型在高端智能任务中仍占主导，但对于大多数常见的低至中等复杂度任务（如分类、摘要、数据提取等），开源模型表现相当甚至更好，且成本更低。文章通过对比工作模型（workhorse models）的性能和成本，指出在批量任务中使用开源模型（如Qwen、DeepSeek）可以显著节省开支，特别是在使用批量推理服务时。文章还提供了选择开源模型的指南和成本节省预期。

Reverse engineering Claude Code

作者: gianpaj | 评分: 96 | 评论数: 7 | 发布时间: 2025-06-08 06:13
文章摘要

Kir Shatrov通过使用mitmproxy工具分析Claude Code的内部工作原理，发现其比其他工具如Cursor更慢且更昂贵的原因。Claude Code首先判断用户输入是否为新话题，并根据需要提取标题。随后，它将输入内容包装在一个系统提示中，要求回答简洁直接，适合命令行界面。系统提示还包含了运行环境信息、项目目录结构和Git状态等上下文信息。Claude Code可以使用多种工具，如Bash执行命令、GlobTool进行文件匹配、GrepTool搜索文件内容等。这些丰富的功能和上下文信息可能是其响应较慢且成本较高的原因。

评论摘要
主要讨论点：Claude Code的使用体验、技术实现、安全性及价格争议 不同观点： • Pram指出Claude Code中的"Task"功能会开启一个全新的聊天上下文，可能导致主聊天上下文混淆。他提到Task会自行编写代码并引发混淆，且有时会对Task摘要做出奇怪回应，例如"That's a fascinating analysis!"。 • Rmonvfer提到Claude Code的预发布版本源代码曾被泄露，如果能够找到这些代码，可以深入了解其内部机制。 • Varunvs对Claude Code在AWS Bedrock上的支持表示赞赏，特别是可以使用Sonnet模型在本地运行Claude Code，并通过Bedrock日志检查API调用和提示。他认为Claude Code在提示工程和工具协调方面表现出色。 • Cloudking认为Claude Code比Cursor Agent更稳定，能够在单个提示上长时间运行而不出现网络超时或文件编辑失败问题。 • Mudkipdev对Claude Code的价格提出质疑，认为描述项目目录中的内容花费11美分是不合理的。 • Therein提出安全性的担忧，设想AI可能通过组合多种工具和方法突破安全边界。他举例说明Claude Code可能通过编写脚本实现未经授权的操作，如绕过白名单进行访问。 补充讨论： • Pram和Cloudking对Claude Code的稳定性有不同的看法，前者提到上下文混淆问题，而后者强调其长时间运行的稳定性。 • Varunvs对Claude Code的技术实现表示赞赏，特别是其在工具协调和提示工程方面的表现。 • Therein的安全性担忧引发了对AI工具潜在风险的讨论，特别是如何防止AI通过复杂操作突破安全限制。 • Mudkipdev的价格质疑则反映了用户对服务成本的关注。 争议焦点：Claude Code的价格合理性及其潜在的安全风险是讨论中的争议点。一些用户对其功能表示赞赏，但也有人对其成本和安全性提出质疑。

Curate your shell history

作者: todsacerdoti | 评分: 140 | 评论数: 20 | 发布时间: 2025-06-06 13:46
文章摘要

Simon Tatham在文章中讨论了为何选择禁用shell历史文件，他通过在`.bashrc`中使用`unset HISTFILE`命令来实现这一点。他指出，这样可以在单个shell实例内保留命令历史，以便修改和重用命令，但不会在不同终端窗口间共享或在注销后保留。他更倾向于将有价值的命令保存在其他地方，如`.bashrc`中的shell函数或独立的脚本文件中，以避免混淆和错误重用。 作者自己则是shell历史最大化主义者，配置zsh保存大量命令历史，但也意识到保存所有错误尝试并无必要。为此，作者创建了一个zsh函数`smite`，用于方便地浏览和删除无用的历史命令，特别是通过fzf工具实现可视化选择和删除。该方法帮助作者保持shell历史的整洁，避免无用命令的干扰。

评论摘要
主要讨论点：如何有效地管理和利用 shell 历史记录，包括保存、组织和检索命令行的不同方法。 不同观点： • [1vuio0pswjnm7] 认为不应依赖 `.bash_history` 保存有价值的命令，而是将这些命令保存为可执行的脚本，存储在专门的文件夹中。他使用高度可移植的 Almquist shell，避免依赖长脚本和命令历史。 • [mmh0000] 则倾向于保存所有命令历史，使用 `history | grep` 等方法快速检索过往命令，认为这样可以避免重新记忆复杂的命令。 • [belden] 开发了一个基于目录和全局的历史记录插件，解决了并发 shell 会话之间的历史记录共享问题，并通过 fzf 工具实现高效的历史命令选择和编辑。 • [epistasis] 支持保存所有命令历史，包括错误命令，并使用 atuin 工具实现跨机器的历史记录同步，尽管对 atuin 的默认界面有所不满。 • [c0l0] 喜欢保持短期的 shell 历史记录，并习惯使用浏览器的隐私模式，以减少不必要的记录和跟踪，认为这样可以减少数据泄露的风险。 • [hiAndrewQuinn] 选择关闭历史文件，只保留短期和本地化的 shell 历史记录，同样在浏览器中使用无痕模式以减少历史记录的积累。 • [Cockbrand] 使用 `HISTCONTROL=IGNOREBOTH` 来忽略不重要的命令，并通过在命令前加空格来控制哪些命令进入历史记录。 • [wswope] 推荐使用 Atuin 工具，认为其提供了强大的历史记录管理和同步功能，极大提升了工作效率。 • [jsphweid] 提到其工作环境中有工具可以保存和检索所有输入的命令，认为是极其有用的工具。 • [csmattryder] 使用 fish shell 和 sponge 插件，只保留返回非零错误码的命令，结合 `z` 插件实现目录快速跳转。 • [omoikane] 通过将 `.bash_history` 等文件链接到 `/dev/null` 来完全禁用历史记录。 • [cobertos] 支持保存所有历史记录，包括错误命令，认为这些记录在回顾和优化过往操作时非常有用。 • [Xx_crazy420_xX] 根据项目需求分别保存 VSCode 项目的历史记录，以适应不同技术栈的需求。 • [kstrauser] 认为保存和优化历史记录是一种不必要的工作，默认的按时间检索已经足够，复杂的历史管理容易陷入效率陷阱。 • [web007] 支持保存所有历史记录并建立上下文，认为保留历史记录可以避免遗忘重要的操作细节，同时也可以通过工具进行筛选和整理。 补充讨论： - 争议的焦点在于是否保存所有 shell 历史记录，包括错误命令，以及是否需要对历史记录进行主动管理和优化。 - 不同的工具和方法被讨论，例如 atuin、bash-preexec、fzf 等，展示了各种历史记录管理方案的实际应用。 - 个人习惯和工作需求对历史记录的管理方式有显著影响，例如开发插件和工具以适应特定工作流程。 - 历史记录的保存策略还涉及到数据隐私和安全问题，例如使用无痕模式和禁用历史记录以减少跟踪和泄露风险。

这篇文章讨论了如何通过“Confused Deputy”攻击利用GitHub的Dependabot（及其他机器人）进行恶意代码合并。Dependabot通常用于自动更新依赖项，但攻击者可以通过精心设计的分支名称和操作，诱使Dependabot在不知情的情况下执行恶意操作，甚至绕过分支保护规则。具体攻击步骤包括：攻击者首先 fork 目标仓库，然后在 fork 中添加恶意代码并启用Dependabot。Dependabot会基于fork中的默认分支创建更新分支，包含恶意代码。随后，攻击者向原仓库发起拉取请求（PR），并利用自动合并工作流尝试合并恶意代码。虽然首次尝试会失败，但攻击者可以进一步操作原始PR，最终实现代码注入。文章还披露了两种新的TTPs（战术、技术和程序）以增强此类攻击。

评论摘要
主要讨论点：围绕Dependabot和自动化依赖管理的讨论 不同观点： • **禁用Dependabot以确保安全**：[radicalexponent] 认为应该手动、有意识地进行依赖更新，而不是依赖自动化工具。他指出自动化版本更新可能引入难以追踪的bug，即使只是补丁版本的更新也可能导致问题。因此，他建议禁用Dependabot以避免潜在的安全风险。 • **`pull_request_target` 的安全隐患**：[woodruffw] 强调了使用 `pull_request_target` 的危险性，并引用了Synaktiv的博客文章。他指出，即使是受信任的机器代理（如Dependabot）也不应该使用该功能，因为它可能成为严重的安全漏洞。 • **自动化版本更新并非新问题**：[snickerbockers] 认为当前关于自动化依赖更新的问题早在30年前就已经解决，建议将依赖管理交给构建系统或让用户自行提供依赖。这可以避免不必要的自动化问题。 • **签署代码提交以增强安全性**：[lrvick] 建议通过强制签署提交和审查来增强安全性。这样可以避免未经审查的第三方提交被合并，从而减少潜在的安全风险。 • **限制外部用户发起PR的权限**：[udev4096] 质疑为何外部用户能够为主要仓库发起Dependabot命令，建议增加授权机制以防止未经授权的操作。 • **对自动化合并的怀疑**：[abhisek] 认为自动合并Dependabot PR的场景较为牵强，并指出Github Actions文档中已经强调了 `pull_request_target` 的风险。 • **对依赖管理和开源生态的批判**：[TZubiri] 对当前依赖超深供应链的开发模式提出批评，认为过度依赖外部包管理工具增加了不必要的复杂性和风险。他主张简化依赖管理，并建议通过法律手段增加编写不良软件的成本以改善现状。 • **自动化合并的不安全性**：[ImPostingOnHN] 强烈反对自动化合并PR，认为未经审查的代码自动合并存在安全隐患，可能导致兼容性问题或引入恶意代码。 补充讨论： • 讨论中多次提到安全性和控制问题，特别是关于自动化工具和外部提交的潜在风险。 • 部分评论者（如[TZubiri]）对整个依赖管理生态持批判态度，认为过度依赖外部资源会导致系统复杂性和潜在风险增加。 • 一些评论者提出了具体的技术解决方案，如签署代码提交和限制外部用户权限，以增强系统的安全性。 争议焦点： • 自动化依赖管理工具（如Dependabot）是否值得使用，特别是在安全性和可控性方面的潜在风险。 • 使用 `pull_request_target` 的安全性问题及其在Github Actions中的适用性。 • 对当前依赖管理模式的批判与支持，特别是如何有效简化和控制依赖以减少风险。
