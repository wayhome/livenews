I Stored a Website in a Favicon

作者: theanonymousone | 评分: 152 | 评论数: 34 | 发布时间: 2026-06-20 05:33
文章摘要

这篇文章讲述了作者将网站内容存储在favicon图标中的实验。 核心思路是：将HTML文本转换为UTF-8字节，然后写入favicon图像的RGB像素通道（每个像素存储3字节）。一个208字节的HTML页面只需9x9像素的图标即可容纳。 读取时通过JavaScript将favicon绘制到canvas，提取像素数据，逆向解码回HTML并渲染。虽然需要bootstrap加载器支持，实用性不高，但这个实验展示了如何突破常规思维，将看似固定用途的favicon转变为数据存储载体，创造出"可能是最小的网站"。

评论摘要
主要讨论点：在favicon图标中存储和传输数据的技术可行性与应用场景 不同观点： • **技术改进派**：建议使用SVG favicon直接存储标记语言，比通过像素编码更简单直接（Tepix提供了具体实现代码）；也有人指出PNG本身就支持tEXt等注释块，可以在正常图像中嵌入任意内容（Walf） • **安全隐私关注派**：指出favicon缓存可被用于跨域用户追踪和指纹识别，特别是在隐私模式下可能泄露用户信息（sheept） • **实用怀疑派**：质疑实际应用场景，并指出在启用防追踪功能的浏览器（如Brave）上无法正常加载（brtkwr） • **创意拓展派**：联想到各种另类存储方式（显示器、键盘、论坛帖子都是存储），并提到PoC||GTFO中的类似技术（MomsAVoxell）；有人想到用动态生成favicon实现流式传输来绕过网页封锁（berkes） • **内容批评派**：认为文章的AI生成文风过于生硬难读（esquivalience、titularcomment） 补充讨论：多人分享了相关技巧（SVG内联emoji作为favicon、类似的股票组合URL项目），还有人开玩笑问能否在favicon中运行DOOM游戏，体现出技术社区对这类hack的兴趣。

Cargo-Geiger

作者: tosh | 评分: 26 | 评论数: 3 | 发布时间: 2026-06-20 14:52
文章摘要

cargo-geiger 是一个 Rust 生态工具，用于检测和统计 Rust 项目及其依赖中 unsafe 代码的使用情况。它以 Geiger 计数器命名，将 unsafe 代码类比为需要安全控制的辐射。该工具不直接判断代码安全性，而是为代码审计提供统计数据支持。安装可通过 `cargo install cargo-geiger`，使用时在项目目录运行 `cargo geiger` 即可。项目提供三个库：cargo-geiger（内部实现）、cargo-geiger-serde（序列化报告类型）和 geiger（解耦的 cargo 组件）。目前在 GitHub 上有 1.6k star。

评论摘要
主要讨论点：关于Rust程序中unsafe代码的评估标准和实际意义 不同观点： • nu11ptr认为：所有有用的Rust程序都包含unsafe（标准库、I/O、FFI必然使用），问题不是"是否有unsafe"，而是"信任谁使用unsafe、在什么情况下使用"。限制自己和依赖crate的unsafe使用有价值，但需要理性看待。 • smasher164强调：unsafe块的数量不重要，重要的是这些unsafe代码是否会导致未定义行为。一个有缺陷的unsafe抽象会让所有使用它的代码都出问题。实际场景中unsafe主要用于内联汇编或FFI调用，语言本身几乎无法提供保证。 • Waterluvian担心：过度强调"unsafe是坏的"文化可能让合理的Rust代码背上坏名声。建议用测试覆盖率来衡量unsafe块，而不是简单统计unsafe数量。 补充讨论：三位评论者都认同简单的unsafe数量统计意义有限，核心分歧在于评估标准——信任度、正确性还是测试覆盖。讨论揭示了社区对unsafe代码评价体系的思考。

Can you see three trees?

文章摘要

这篇文章介绍了城市绿化标准"3-30-300法则"：每个住所应能看到至少3棵树、所在社区树木覆盖率达30%、距离公园不超过300米。这一标准由Cecil Konijnendijk提出，已被欧洲多个城市采纳。 研究显示，在862个欧洲城市中，仅约50%居民能看到三棵树，三分之一居民生活在树木覆盖率达30%的区域，近60%居民住在公园300米范围内。但同时满足全部三项标准的欧洲居民仅占14%，21%的居民一项都未达标。芬兰埃斯波和意大利瓦雷泽是仅有的两个过半居民达标的城市。北欧城市表现普遍优于南欧。

评论摘要
主要讨论点：城市绿化与树木覆盖对居住体验的影响 不同观点： • **积极案例支持者**：阿姆斯特丹居民赞赏城市停止过度修剪植被，带来更多昆虫和色彩；新加坡居民强调靠近大型公园的便利；乌拉圭居民确认其城市完全满足"三棵树测试" • **树木不足的批评**：伦敦市中心被描述为"混凝土/玻璃荒地"，缺乏人行道旁的随机树木；有人因西班牙地图显示树木稀少而放弃旅行计划 • **测试标准的讨论**：有人质疑"三棵树"听起来简单但实际测试时发现并非如此；有人要求提供照片对比以更好理解标准 • **树木质量vs数量**：指出仅满足数量测试不够，树龄、野生动物存在（如兔子、松鼠、鹿）才是衡量环境质量的更好指标；年轻树木的郊区仍可能显得荒凉 • **气候与城市设计关联**：观察到树木覆盖分布与气候区高度相关；澳大利亚地中海气候城市（珀斯、阿德莱德）树木覆盖较亚热带东海岸城市差 补充讨论：遮阴需求随全球变暖日益重要；芬兰埃斯波作为郊区化城市的特殊性；纽约等城市已实现树木精确定位数据化管理

A Perceptron in Age of Empires II

作者: EvgeniyZh | 评分: 93 | 评论数: 14 | 发布时间: 2026-06-18 07:50
文章摘要

这篇文章展示了在《帝国时代II》游戏中构建逻辑门和神经网络的实验。作者使用游戏的场景编辑器，通过地形（草地代表0，桥代表1）和山羊作为信号载体，实现了： 1. **NAND门**：用双轨制表示比特，通过移除和放置山羊来完成逻辑运算，并用冰地轨道避免竞态条件。 2. **1比特感知机**：由两个XNOR门和一个AND门组成，能计算简单的内积和阈值函数。 3. **感知机训练电路**：基于ansatz算法，包含完整的感知机和权重更新逻辑，使用不同地形编码不同逻辑门（竹林=XNOR，森林=AND，猴面包树=OR，深水=NOT）。 作者已在Verilog中验证电路可行性，正在完善脚本实现。

评论摘要
主要讨论点：关于在《帝国时代II》中实现神经网络的论文，以及该论文对LLM拟人化属性研究的哲学论证 不同观点： • **技术实现派**：认为这是意料之中的结果。图灵完备性本身就意味着可以构建和训练感知器，NAND门通过单位触发器实现类似于《万智牌》和红石电路的模式。过度泛化的触发/条件系统通常导致意外的图灵完备性。 • **哲学论证质疑派**：认为论文的逻辑存在问题。（1）论文对"假设"的定义有误——询问"LLM是否有某属性"并不等于假设其有该属性；（2）论文从图灵完备性跳跃到"不应假设LLM属性存在"的结论缺乏逻辑连贯性；（3）论文的哲学论证傲慢且缺乏依据，隐含着"人类完全独特"的教条，要求证明A≠A这样的不可能任务。 • **表征依赖派**：指出在AoE II中实现的LLM会非常慢、可能不处理文本、看起来很荒谬，因此观察者不会赋予其拟人化特征。但这个论点不需要图灵完备的嵌入——只需放慢推理速度、分离分词器、展示内部计算的荒谬表示即可。 补充讨论：有用户分享了AoE II的地图编辑器功能、相关游戏引擎应用，以及幽默讽刺人类也只是"混乱相互作用的物理物质"的评论。

文章摘要

Arch用户仓库(AUR)近期遭受持续攻击。攻击者注册新账号，领养孤立软件包并推送恶意更新，在用户系统中安装恶意软件。维护者连日疲于应对被入侵的软件包，目前已关闭新用户注册，但长期应对方案尚不明确。 AUR特别脆弱的原因在于：任何注册用户都可以无需审核直接领养孤立包并发布更新；当前有超过14,000个孤立包和141,000注册用户；允许预编译二进制文件和专有软件；用户被警告"风险自负"但实际很少审查PKGBUILD文件。这与Fedora的Copr、openSUSE的OBS等其他发行版的用户仓库模式存在重要差异。
