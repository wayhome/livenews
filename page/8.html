文章摘要

这篇文章讲述了Commodore PET 2001个人电脑的历史。1977年6月5日，Commodore在消费电子展上接到首个经销商订单，成为"1977三巨头"（PET、Apple II、TRS-80）中最早销售的预装电脑之一。PET由6502处理器设计师Chuck Peddle主导开发，售价495美元，配备内置显示器、磁带录音机和4KB内存。值得注意的是，Commodore仅支付25,000美元就获得了微软BASIC的永久授权，这让微软后来非常后悔，因为该授权延续到了后来极为畅销的C-64和VIC-20。PET首年仅生产500台，供不应求。

评论摘要
主要讨论点：80年代个人计算机的怀旧回忆和存储设备的演进 不同观点： • fipar的经历：使用过TK-90X和TK-95（改进版Spectrum克隆机），在80年代编程课程中短暂接触过某款计算机。最近在山景城计算机历史博物馆重见这些设备时情绪激动，推荐参观该博物馆，特别提到了馆内运行中的IBM 1401和打孔卡体验 • mjcohen的经历：作为PET计算机早期用户，声称获得了西海岸第一台外置磁带驱动器，但使用次数很少。真正的技术飞跃是获得软盘驱动器后，认为"可以做任何事了" 补充讨论：两位评论者都在分享个人的计算机历史体验，但关注点不同——fipar侧重于怀旧情感和博物馆体验，mjcohen则强调存储技术升级带来的能力提升。两者没有直接争议，而是在各自讲述平行的回忆。

Azure Linux 4.0 is Microsoft's first general-purpose Linux

文章摘要

微软在 Build 2026 上发布了 Azure Linux 4.0 公开预览版，这是首次允许用户在任何 Azure 虚拟机上运行该系统，而非仅作为 AKS 的底层主机。这标志着 Azure Linux 从专用设备发行版转变为通用 Linux 发行版。 4.0 版本基于 Fedora 43 构建，采用声明式覆盖层方式，不再手动维护每个软件包规范文件。主要更新包括：内核 6.18 LTS、dnf5 包管理器、glibc 2.42、systemd 258 等。支持虚拟机、容器、AKS 和 WSL 等多种部署场景。 Azure Linux 的特色在于可审计的供应链设计、强安全性（SELinux、FIPS 140-3 认证进行中）以及针对 Azure 优化。目前已被 Databricks、LinkedIn 等大规模采用。

评论摘要
主要讨论点：微软推出基于Fedora的Azure Linux发行版，声称为"通用目的"操作系统 不同观点： • **支持方观点**（rswail）：这是真正的通用系统，可运行容器、虚拟机或裸机应用；具备完整的SBOM供应链可追溯性，满足安全审计要求；采用只读OS设计。虽不支持随机硬件配置，但能在多种环境中运行通用应用 • **质疑"通用"定义**（froh, codycharris, reacweb）：认为这只是针对Azure优化的专用系统，不会在微软计算环境外运行；真正的通用OS应支持任意硬件并有厂商认证；实质是微软提供从WSL到云的统一Linux栈 • **批评微软动机**（bananaquant, egorfine, nullpoint420）：指责微软搭便车Red Hat的工作成果；将bleeding-edge发行版快照称为"通用"是误导，Fedora/RHEL本就有稳定性区分；怀疑是"拥抱-扩展-消灭"(EEE)策略，通过稀释"通用"术语来占领新领域 • **技术细节讨论**（aykutseker）：从tdnf迁移到dnf5值得关注，多数内部平台会越来越定制化而非通用化 补充讨论：部分评论充斥讽刺情绪，质疑微软的营销策略和AI生成内容的使用。争议焦点在于"通用目的"这一表述是否准确，以及微软的真实意图。

Ladybird 浏览器项目宣布不再接受公开的 pull request，今后代码变更仅由项目维护者提交。这一改变主要出于两个原因：一是 AI 工具的普及让代码贡献不再能有效反映贡献者的可信度和投入程度，降低了通过贡献建立信任的传统机制；二是作为即将面向真实用户的浏览器，安全性至关重要，项目需要更严格的开发流程和明确的代码责任归属。项目仍保持开源，欢迎通过 bug 报告、测试、标准讨论等方式参与，但不会通过其他渠道接受代码补丁。所有现有的公开 PR 将被关闭。

评论摘要
**主要讨论点：** Ladybird浏览器项目宣布不再接受外部代码贡献后，社区对开源项目应对AI生成代码冲击的不同反应 **不同观点：** • **支持方**：认为AI降低了代码提交门槛，大量AI生成的PR让maintainer负担激增，代码量不再等同于付出的努力和诚意。项目有权优先保障质量和安全（Fraterkes, noIdeaTheSecond, mabedan） • **反对方**：认为这损害了开源精神，阻碍了新维护者的发现和培养；拒绝外部贡献意味着重复劳动，用户修复bug后无法直接贡献，只能让团队重新实现（nh2, koteelok, pulsartwin） • **中间立场**：理解资源有限团队的困境，但指出Chrome/Firefox等大型项目仍保持开放，值得肯定；担心失去社区的非代码贡献（想法、代码审查等）带来更大损失（domenicd, patates） **补充讨论：** - 有人质疑Ladybird作者本人也常提交大量未经审查的代码，决策存在双标（adrian17） - SQLite和Blender等成功项目早已采用类似封闭模式，这可能是大型项目的必然趋势（nathell, TeriyakiBomb） - 社区担忧这背离了Serenity/Ladybird原本的社区文化，希望至少保留未来参与的可能性（mvanveen, Deukhoofd）

文章摘要

**pg_durable 是 Microsoft 开源的 PostgreSQL 扩展，在数据库内部实现持久化执行（Durable Execution）。** 核心功能：通过 SQL 定义长时间运行的工作流，系统自动在每个步骤间设置检查点。当数据库崩溃、重启或步骤失败时，可从最后的检查点恢复执行，无需重新开始。 适用场景：向量嵌入管道、数据摄取、定时维护、并行聚合、外部 API 调用等需要容错的后台任务。 核心优势：替代传统的 cron + 队列 + 状态表方案，将工作流逻辑、重试状态和进度跟踪统一在 Postgres 中管理，减少额外基础设施。 限制：仅适合可用 SQL 表达的工作流，不支持任意应用代码逻辑。

评论摘要
主要讨论点：pg_durable（微软开源的Postgres持久化执行框架）是否应该将业务逻辑和工作流放在数据库中 不同观点： • **支持方**：认为Postgres队列是2026年的趋势，持久化执行技术（durable execution）能解决精确一次执行、重试、信号工作流等常见痛点；对于数据库本地任务很有用 • **质疑方**：认为这类似存储过程的老问题——无法单元测试、难以版本控制、业务逻辑隐藏在数据库中、缺乏可观测性、给Postgres带来扩展压力、缺少IO能力（如API调用） • **困惑方**：不理解为什么要用数据库存储控制流而不是代码；质疑与Temporal、Airflow等DAG调度器相比有何优势；担心数据库本就难扩展，为何还要增加长时运行任务的负担 • **技术实现质疑**：指出如果编程语言/虚拟机原生支持确定性、可控步进执行和状态挂起恢复，这类工具可能就不必要了 补充讨论：有用户关注文档不够清晰（如wait_for_schedule的幂等性、错误处理机制），也有人担心AI代理不擅长理解这类新模式（因训练数据中消息队列模式更常见）
