The Best Engineers Write Less Code

作者: funnyenough | 评分: 45 | 评论数: 10 | 发布时间: 2026-05-27 00:33
文章摘要

这篇文章强调软件开发的核心原则： **主要观点：** - AI生成代码不能改变软件质量的本质，糟糕的软件依然糟糕 - 开发时间直接等于成本，这是管理层关注进度的原因 - 优秀工程师的价值在于**避免构建不必要的功能**，而非编写更多代码 - 代码是负债，除非它解决了正确的问题 - 构建错误的东西是最大的浪费 **建议实践：** - 在开始前与利益相关者确认需求和目标 - 采用敏捷方式：短周期迭代，及时获取反馈 - 衡量工程师的标准是创造的价值与留下的复杂度之比 - 有空闲时间？去删除代码 核心思想：少即是多，正确比快速更重要。

评论摘要
主要讨论点：在LLM时代，软件开发的核心瓶颈是否已从“写代码”转向“建模、决策、可维护性与真实需求理解”，以及这会如何改变工程实践和产品形态。 不同观点： • **建模与需求理解比写代码更关键**：Frannky认为很多人只在封闭信息泡泡里思考，缺乏端到端建模能力，导致产品实现脱离真实用户需求，即使会写代码或有Claude也无济于事。其论点是问题不在编码，而在“定义该做什么”的能力缺失；他还提到应把这类人的意见当作需“净化”的输入。 • **组织激励往往奖励“多写代码”而非“少写代码”**：xingped指出现实中晋升和评价常按产出代码量驱动，“promotion driven development”因此出现；做出减少新代码的理性决策，反而难获好评。 • **好工程的标准应是长期可维护性，而非代码量本身**：carefulfungi提出“优秀开发者写出的代码半衰期更长”；kspetkov79补充，与其说“少代码更好”，不如说“更少含糊决策”更重要。paul_knox则呼应：如今瓶颈已不是打字速度，而是理解和维护能力。 • **系统设计不必追求首次完美，应接受演化与重写周期**：faangguyindia认为，初版再优雅也会被新增需求逐步打补丁，直到发现更深层模式后重写，循环往复；因此不再执着一次做对。 • **LLM不会自动拯救糟糕软件，反而更凸显设计质量**：funnyenough反驳“有LLM就不必写好软件”的看法，强调无论代码由Claude还是人类写，糟糕软件依旧糟糕。 • **更激进的观点：未来应减少UI、转向数据/API + 个人代理**：saltyoldman认为用户真正需要的是开放数据访问和LLM友好的API，而不是复杂前端和零散“AI按钮”；应由个人长期运行的代理统一处理邮件、消费分析等任务。 补充讨论： • 争议焦点主要在于：**LLM时代最稀缺的到底是编码、设计决策、还是产品/需求建模能力**。 • bfkwlfkjf则表达了更极端期待：希望AI最终强到让人类无需再处理代码。 • tommica对失效链接的调侃，侧面呼应了“删代码”主题。

Are we self-sovereign PKI yet?

作者: ca98am79 | 评分: 88 | 评论数: 16 | 发布时间: 2026-05-21 22:49
文章摘要

这篇文章指出端到端加密的关键问题：虽然消息内容加密了，但几乎没人验证通信对方的密钥是否正确。Signal、iMessage、WhatsApp都提供了安全码验证功能，但用户很少使用。现有的PKI系统（如CA、DNS）都依赖中心化机构，本质上是托管关系。文章提出需要一种真正去中心化的身份系统：将人类可读的名称（如grace@key）直接绑定到公钥，无需第三方验证，永久归属用户，不可撤销或转让。这样解析名称本身就完成了密钥验证，无需额外的带外确认步骤。

评论摘要
主要讨论点：关于加密身份系统和密钥管理的技术方案争议 不同观点： • **支持区块链方案**：Spaces等项目使用Merkle树+比特币链作为共识机制，提供不可撤销、永久的加密身份。认为这解决了中心化信任问题。 • **质疑不可撤销设计**：多位评论者指出密钥不可撤销是缺陷而非优势。一旦身份被盗，用户必须放弃整个在线身份。这也会成为政府监控和企业追踪的工具，违背隐私保护初衷。 • **现有方案已足够**：NoahZuniga强调Signal/WhatsApp的密钥透明度(Key Transparency)技术已解决问题，使用Merkle树+可信见证者，比依赖比特币链更实用。批评作者重复造轮。 • **PGP仍有价值**：lrvick反驳"PGP已死"论调，指出PGP正在现代化改进，在Linux生态系统中仍广泛使用。 • **实用性担忧**：用户抱怨密钥指纹过长难记、名称混淆攻击风险、域名抢注问题，以及Spaces产品实际使用体验差(无法自选用户名)。 补充讨论：KERI协议被提及作为微账本替代方案；有创业者尝试用域名+mTLS+后量子密码学构建去中心化信任系统；技术社区对"为人类而非机器构建PKI"的根本需求存在共识，但实现路径分歧明显。

Opaque Types in Python

作者: lumpa | 评分: 120 | 评论数: 10 | 发布时间: 2026-05-23 13:17
文章摘要

这篇文章讨论了在Python中实现**不透明数据类型**（opaque data type）的设计模式。 **核心问题**：当你需要一个配置对象（如`ShippingOptions`），既要让用户能使用它，又不想暴露其内部实现和构造函数，以便未来灵活演化。 **解决方案**： 1. 使用`typing.NewType`创建公开的类型名 2. 用私有类（如`_RealShipOpts`）存储实际数据 3. 提供公开的构造函数（如`shipFast()`、`shipNormal()`） **优势**： - 用户只能通过预定义的函数创建对象 - 内部实现可以自由修改而不破坏公共API - 类型检查器能正确工作 - 避免过早承诺复杂的公共接口 这种模式特别适合需要频繁演化的配置对象，在保持API稳定的同时允许内部复杂度增长。

评论摘要
主要讨论点：Python中如何实现私有类型和封装，以及是否应该使用NewType模式来隐藏实现细节 不同观点： • **反对过度封装派**（jnwatson, OutOfHere）：Python的设计哲学是"我们都是成年人"，用下划线提示即可，不需要Java式的严格封装。直接使用ShippingOptions就好 • **支持类型安全派**（原文作者, gorgoiler）：应该在库和用户之间建立明确边界，可通过NewType、Literal类型或Enum来实现，防止用户直接构造内部类型 • **实用主义派**（sdeframond, corwinxpro）：NewType模式在实践中存在问题——难以理解、继承时类型检查失效、测试时需要导入私有实体。建议用独立的API模块来区分公共接口和内部实现 • **Java对比派**（nayuki）：批评Python在面向对象和静态类型方面不如Java完善，如私有构造函数、类型文档、强制super()调用等特性缺失或实现较晚 补充讨论： • stephenlf提到name mangling（双下划线）几乎能强制私有属性，但讨论中较少被提及 • CreRecombinase质疑：既然Python是动态类型，为何不用字典或干脆不标注类型 • tcdent吐槽代码风格：Python应该用snake_case而非camelCase

Go: Support for Generic Methods

作者: f311a | 评分: 122 | 评论数: 9 | 发布时间: 2026-05-27 09:02
文章摘要

该提案建议 Go 支持“泛型具体方法”：允许方法像函数一样声明类型参数，但仅限具体类型的方法，不扩展到接口方法。原因是接口的动态实现机制难以高效支持泛型方法调用。提案认为方法不仅用于实现接口，也适合类型相关的代码组织与链式调用。核心改动是修改语法，使方法声明可带类型参数，目标版本为 Go 1.27。

评论摘要
主要讨论点：Go 为泛型补上“泛型方法”后，社区对其价值、必要性以及是否背离 Go 简洁设计理念展开讨论。 不同观点： • 支持者认为这是对 Go 泛型能力的重要补全。有人提到自己一开始用 Go 泛型时，对“没有泛型方法”很意外；现在补上后，更符合其他语言使用者的预期，也弥补了明显短板。 • 实用派支持者强调它能改善 API 设计与工程体验。评论举例称，过去为了保持 API 可用性，不得不设计“别扭、拼凑式”的包级 API；有了泛型方法后，数据访问方法、库设计会更自然，甚至有人表示要重写自己的库，或终于能实现想做多年的 monad 库。 • 渐进演进派认为这并非“立场反复”，而是按计划推进。有人回应批评称，从最早的泛型提案开始，这项能力就是“不是现在，不是永不”，主要受限于实现复杂度；Go 团队规模不大，所以选择渐进式、稳妥地加入特性。 • 批评者认为 Go 正在背离“简洁”初心。有人讽刺说这是在“慢慢实现那些他们曾说不需要的东西”；也有人更强烈地批评，认为 Go 领导层一味追逐用户对语言特性的期待是错误路线。 • 保守/反对者把争议上升到语言哲学层面。最激烈的评论称这是“Go 悲伤的一天”，认为学院派胜利、语言简洁性已死，反映出对复杂化和特性膨胀的担忧。 补充讨论：争议焦点主要在两点：一是“泛型方法”究竟是必要补全还是不必要复杂化；二是 Go 的演进应优先满足实际开发需求，还是坚守极简设计原则。评论之间也形成回应关系：支持者不仅称赞功能本身，也直接反驳“背离初心”的批评。
