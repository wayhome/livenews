H.R. 6028 would fundamentally change the U.S. Copyright Office

作者: Cider9986 | 评分: 270 | 评论数: 12 | 发布时间: 2026-06-11 00:00
文章摘要

美国众议院通过了H.R. 6028法案，该法案将美国版权局从国会图书馆的监督下独立出来，并将版权登记官改为总统提名、参议院确认的职位。EFF认为这一变化会使版权局更加政治化，进一步集中权力。版权局近年来在版权政策辩论中立场偏向大型娱乐产业利益，曾支持备受争议的SOPA法案。该法案未经听证程序就被快速通过，EFF呼吁参议院否决这项法案，认为版权局应保持与图书馆的联系，以更好地服务公众利益而非政治议程。

评论摘要
主要讨论点：美国众议院通过H.R. 6028法案，将版权局局长从国会任命改为总统任命，引发关于权力分立和版权管理的争议。 不同观点： • **支持现状派（EFF等）**：担心总统任命会使版权局政治化，可能被AI公司等利益集团影响。认为版权局归属立法部门有历史合理性——国会图书馆自1870年起管理版权，具备专业能力且目标一致（扩充馆藏）。 • **支持改革派**：认为总统任命符合行政权归属逻辑，且法案包含10年任期限制。可能反而防止总统随意罢免（如特朗普2025年试图罢免图书馆馆长的案例）。质疑"政治化"担忧的实际意义，因版权局本身不执法。 • **AI版权争议**：有评论强烈批评AI公司"双标"——训练时无视GPL等开源协议，声称无法追溯贡献（实际模型权重可追溯），但自己的AI生成代码泄露时却用DMCA维权，尽管版权局明确AI生成内容无版权保护。 • **版权制度质疑**：个别评论认为版权本身是"社会恶"，应被废除。 补充讨论：法案仅12分钟辩论即通过（语音投票），4名发起人均为共和党；有人指出美国95%以上州立法都是无异议语音投票通过。另有深入探讨美国三权分立例外情况（如行政法法官、国会警卫等）。

Introduction to UEFI HTTP(s) Boot with QEMU/OVMF

作者: jtlebigot | 评分: 109 | 评论数: 5 | 发布时间: 2026-06-12 14:50
文章摘要

这篇文章介绍了如何使用UEFI通过HTTP(S)进行网络启动，作为传统PXE方案的现代替代。作者在Ubuntu 26.04环境下使用Qemu/OVMF进行测试，演示了从netboot.xyz网站直接启动的过程。 文章首先对比了PXE（基于DHCP和TFTP）的配置复杂性和安全问题，指出HTTPS提供了更好的安全性和高可用性。作者从简单的HTTP启动开始，通过DHCP发现启动URL。关键发现是OVMF的网络栈需要随机数生成器设备（virtio-rng-pci）才能正常工作，这个依赖关系在DxeNetLib中声明。成功配置后，系统能够通过HTTP协议启动，尽管日志显示了一些TFTP错误和IPv6启动失败的信息。

评论摘要
主要讨论点：UEFI HTTP Boot 技术的优势、实际应用和存在的问题 不同观点： • **HTTP优于TFTP**：nijave和noodlesUK认为HTTP作为TFTP替代方案是重大改进，支持HTTP服务器的设备范围更广，实施更简单。nijave提到TLS层增加了完整性和保密性保障，可将关键启动组件移出可信网络甚至部署到云端，但对secure boot是否已提供类似保护存有疑问。 • **技术并非新创**：naturalmovement指出Apple二十年前就在使用HTTP启动（Internet Recovery功能基于Apple的网络启动规范），暗示这不是创新技术。 • **调试体验极差**：andrewjf强烈批评UEFI HTTP Boot的调试困难，错误信息几乎无用（如"can't get NBP file size"），DHCP选项格式复杂，IPv6支持更加隐晦。认为错误提示由不了解网络和DHCP实际复杂性的开发者设计。 • **肯定作者贡献**：jeffrallen作为同事对作者yadutaf的工作表示高度赞赏。 补充讨论：争议焦点在于HTTP Boot虽有理论优势，但实际部署中的可用性和调试体验仍需大幅改善。物理硬件支持程度也存在疑问。

评论摘要

Google proposes Open Knowledge Format based on Markdown

作者: itherseed | 评分: 58 | 评论数: 7 | 发布时间: 2026-06-13 14:33
文章摘要

Google Cloud 推出开放知识格式（OKF v0.1），这是一个供 AI 系统使用的开放标准。OKF 将知识表示为带 YAML 前置元数据的 Markdown 文件目录，解决了企业内部知识碎片化问题。当前组织的知识分散在元数据目录、Wiki、代码注释等不兼容系统中，导致 AI 代理难以获取上下文。OKF 采用"知识即 Wiki"模式，让知识以可读、可版本控制的文件形式存在，无需复杂 SDK 或特定服务，可在不同工具和组织间互操作，使 AI 代理能持续维护和更新共享知识库。

评论摘要
主要讨论点：OKF（Open Knowledge Format）规范使用Markdown作为知识表示格式的可行性和局限性 不同观点： • **支持但有保留**（sadschnitzel）：赞赏OKF的简洁性，但质疑"纯Markdown"能否充分表达所有概念。强调需要平衡AI可访问性和人类体验，特别是非技术人员更习惯可视化工具而非"奇怪的文本格式+git"。建议结合DBML、LikeC4、Mermaid等半结构化文本标准，它们既有良好的可视化形式又能嵌入Markdown，AI也能理解 • **怀疑态度**（mrkiouak）：讽刺性地提到每10年就会重提RDF/OWL语义网格式，暗示这类标准化尝试反复出现但难以真正落地 • **技术细节关注**（bsimpson）：指出规范缺少对Markdown变体（如CommonMark）的明确定义，认为这对规范来说是重要的缺失 补充讨论： sadschnitzel提出了实际挑战——复杂电子表格和Miro等依赖空间布局和颜色传达隐含意义的工具难以找到文本替代方案，并分享了自己在数据工程领域的尝试（satsuma-lang）。matthewbarras和verdverm提供了相关资源链接。
