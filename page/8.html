The difference between "today's task" and "accretive work"

作者: hn_acker | 评分: 130 | 评论数: 17 | 发布时间: 2026-07-02 14:07
文章摘要

这篇文章探讨了AI编程中的一个悖论：为何有人用AI写出最佳代码，有人却制造技术债务？ 作者指出这是两种本质不同的活动："半人马"（主导AI使用的程序员）与"反向半人马"（被迫为AI打工的程序员）。 文章进一步区分了两类编程工作： 1. **个人工具开发** - 为自己编写的一次性代码，"让它工作"即可 2. **生产代码** - 需要他人维护和改进的代码，必须经过"规范化"处理 核心观点：个人使用的临时代码与团队协作的生产代码是完全不同的事物。前者追求快速解决问题，后者需要考虑可维护性、可扩展性和团队协作。理解这个区别，才能明白何时"够用就好"，何时需要投入更多精力构建可持续的代码基础。

评论摘要
主要讨论点：AI生成代码（"vibe coding"）的价值、一次性代码与可维护代码的权衡、以及代码"规范化"（canonization）的重要性 不同观点： • **一次性代码的价值派**：认为并非所有代码都需要可维护性，"今天的任务"有其存在价值。Excel式的临时解决方案占据了大量实际软件开发工作，AI代码填补了临时方案与专业软件之间的空白 • **质量担忧派**：批评vibe coding制造技术债务，认为AI代码虽然降低了创建代码片段的成本，但不能自动使其成为可维护系统的一部分。强调"规范化"工作（将临时代码转化为通用、可复用、高效的代码）被严重低估 • **现实主义派**：指出90%的实际程序本就质量糟糕，大多是一次性任务代码。AI相关讨论已沦为价值观的部落战争，关键在于根据代码预期寿命选择合适的复杂度级别 • **成本怀疑派**：质疑AI是否真能节省成本，可能只是"更快交付但成本相同"。质疑AI投资必须通过大规模裁员才能收回的论断 补充讨论：《模拟人生》开发案例揭示重要洞察：真正的可积累系统在开发中期可能看起来像一堆临时hack，关键是有人负责最后的"调优"阶段并获得管理层支持。这提示评判AI代码不应问"是否是垃圾"，而应问"谁负责调优，管理层能否坚持到完成"。

A software engineering interview question I like: computing the median

文章摘要

这篇文章介绍了作者喜欢的一道软件工程面试题:编写函数计算数组的中位数。 作者认为这道题虽然直接但能多角度考察候选人能力: 1. **基础编程能力** - 数组归约是基本功 2. **API设计** - 是否排序、是否修改原数组、性能影响 3. **调试能力** - 常见的off-by-one错误 4. **逻辑处理** - 奇偶长度数组的分支 5. **领域知识** - 中位数vs平均数的统计学讨论 6. **工程实践** - 可测试性和标准库使用 文章附带Python实现示例,展示了空列表处理、排序方式选择(sorted vs sort)、奇偶判断等关键点。作者认为这类实用题比脑筋急转弯式的谜题更有价值。

评论摘要
主要讨论点：技术面试中"计算数组中位数"问题的价值和有效性 不同观点： • **质疑算法题实用性派**：认为CS理论题与实际工作严重脱节，应更关注代码理解能力、业务逻辑思维、风险评估和沟通能力，尤其对3年以上经验的工程师，这类题目几乎无意义（lubujackson, ta93754829） • **重视面试过程派**：承认题目本身简单，但价值在于观察候选人如何权衡不同方案（内存大小、延迟要求、流式数据等）、如何沟通技术想法、如何应对冲突和学习新知识，而非死记硬背算法（cgearhart） • **算法深度展示派**：将此题视为展示技术功底的机会，如O(n)的quickselect算法、median-of-medians、加权中位数等进阶变体，可区分死记硬背者和真正理解者（apricot, kccqzy及多位技术讨论者） • **偏好实际场景派**：主张用业务领域的真实问题替代抽象算法题，如农业数据的告警系统、时间序列预测等，能更全面评估设计、实现、生产就绪等能力（keithnz） 补充讨论：技术层面形成小争议——文中假设"必须排序"被多人纠正，指出quickselect等算法无需完全排序即可O(n)时间求中位数，反映出即使简单问题也有优化空间。

Cloudflare Meerkat - Globally distributed consensus

作者: bobnamob | 评分: 248 | 评论数: 20 | 发布时间: 2026-07-08 13:18
文章摘要

Cloudflare推出了名为Meerkat的实验性全球共识服务，用于在其330多个数据中心间管理控制平面状态。传统共识算法（如Raft）在广域网中存在问题，因为它们依赖单一leader和超时机制，当leader失效时系统会不可用。 Meerkat采用QuePaxa共识算法，其核心优势是所有副本可同时执行写操作，且不依赖超时机制，更适合Cloudflare的全球网络环境。这是QuePaxa算法的首次大规模工业部署。 该服务旨在提供强一致性（线性一致性）保证，确保所有读取操作都能看到之前的写入，同时在部分数据中心或链路故障时保持可用。目前Meerkat仍在开发中，将首先用于管理领导权分配、资源放置等小型控制平面状态，暂时仅供内部使用。

评论摘要
主要讨论点：Cloudflare的Meerkat服务及其底层QuePaxa共识算法的技术价值与文章表达质量 不同观点： • **技术创新派**：QuePaxa是首个生产级异步共识算法，不依赖超时机制，可在消息延迟剧烈波动时保持进展，这是历史性突破（nano_o） • **实践价值派**：对经历过Raft集群在糟糕网络下leader频繁切换、选举风暴的人来说，QuePaxa的无领导者设计很有吸引力（ebeirne） • **性能担忧派**：每次读操作都需全局共识会很慢，多轮消息通信开销可能昂贵，这会限制应用场景，可能不适合数据库等场景（advisedwang, pstoll） • **文章批评派**：文章结构混乱，应该与Paxos而非Raft比较（因为QuePaxa是无领导者的），应聚焦QuePaxa算法本身而非未成熟的Meerkat实现，缺少代码链接和CAP理论讨论（m11a, eis, purpleidea） 补充讨论：多人期待Jepsen等严格测试验证其可靠性；有人建议开源以惠及更多分布式系统；关键权衡在于用消息数量增加换取无超时依赖的鲁棒性；项目尚未投产，实际表现有待观察。

Chat Control 1.0 and 2.0 Explained

文章摘要

欧盟有两个并行的"聊天控制"法案： **Chat Control 1.0**（临时法规）：2021年通过，允许服务商**自愿**扫描私人消息以检测儿童性虐待内容，不涉及端到端加密通信。2026年4月4日已过期，但欧盟理事会正试图通过"新法案"快速复活。 **Chat Control 2.0**（永久提案）：2022年提出，要求平台**强制**检测和报告儿童性虐待材料。核心争议在于是否强制扫描私人通信，以及是否涉及加密消息。欧洲议会主张仅针对可疑用户且需法院授权，而理事会立场更宽泛。目前五轮三方谈判未达成协议。 两个法案引发争议的焦点是隐私保护与儿童安全之间的平衡。

评论摘要
主要讨论点：欧盟"聊天控制"法规引发的隐私、技术实施和政府动机争议 不同观点： • **反对派 - 权力扩张质疑**：认为这是以"保护儿童"为名义的独裁式权力扩张，法律范围过于宽泛，影响所有人而非精准打击犯罪者。质疑政府真实动机，指出同样的政府不谴责高层人士涉及的犯罪，怀疑目的是建立监控国家和压制反对声音 • **技术实施困惑**：多人质疑如何在端到端加密下实施扫描——是需要中间人解密还是强制设备端扫描（类似苹果CSAM方案）？"自愿"针对服务商还是用户？如何防止用户侧载开源客户端规避检测？ • **执行效率批评**：指出真实儿童虐待案件存在量刑过轻、警务资源不足问题。可以通过在游戏平台设蜜罐、渗透公开群组、与学校合作等传统警务手段打击犯罪，但政府不愿做"真正的工作" • **隐私担忧**：普通家长担心为婴儿拍摄洗澡等日常照片（如父母过去留存的成长照）会触发误报。批评科技公司通过"自动更新"完全控制客户端软件，用户无法验证数据用途和合作方 补充讨论： 有人询问Chat Control 1.0实施两年的实际效果和滥用案例，寻求实证评估。另有批评指出政客在此问题上投入的时间超过能源安全等紧迫议题。值得注意的是，即使1.0版本过期，谷歌、Meta等公司仍继续扫描私人消息。

Why we built yet another Postgres connection pooler

作者: levkk | 评分: 256 | 评论数: 22 | 发布时间: 2026-07-07 15:36
文章摘要

PgDog 是一个新的 Postgres 连接池代理工具。与 PgBouncer、RDS Proxy 等现有工具不同，它解决了"抽象泄漏"问题，让开发者无需修改应用代码即可使用连接池。 主要特性包括： 1. **会话状态管理**：内置 SQL 解析器，自动检测和同步 SET 命令，确保连接状态正确，支持 RLS 等依赖会话变量的功能。 2. **LISTEN/NOTIFY 支持**：完整实现 Postgres 的发布/订阅功能，在多个 PgDog 进程间转发消息，保留事务语义。 3. **多线程架构**：基于 Rust 的 Tokio 异步运行时，利用多核 CPU 提升性能，避免传统连接池的分片问题。 PgDog 让开发者可以继续使用 Postgres 的原生特性，同时获得连接池的扩展能力，无需做出功能妥协。

评论摘要
主要讨论点：PgDog连接池工具的技术特性及PostgreSQL生态系统的架构讨论 不同观点： • **技术特性肯定派**：认可PgDog的prepared statements支持（弥补pgpool-II缺陷）、SET实现更清晰、AGPL开源许可证优于BSL，以及文档质量高 • **架构根本改进派**：认为连接池只是权宜之计，PostgreSQL应该在上游实现线程池模型（如MS SQL Server）和新的wire format（pgwire4）。有开发者指出现有pgwire3协议"是PostgreSQL中最糟糕的部分之一"，并展示了支持多结果集、流式传输等特性的POC • **实用功能探索派**：关注具体应用场景，询问动态分片/多租户支持、查询缓存、schema切换等功能的可行性 • **连接状态泄漏质疑**：有用户对"连接池复用导致客户端状态互相泄漏"表示震惊，质疑这是否是PostgreSQL典型设置的常见问题 补充讨论：有评论引发Postgres与MySQL的生态之争，质疑为何大规模公司（YouTube、Slack等）多使用MySQL分片系统（如Vitess），但Postgres仍保持活跃。另有讨论NOTIFY性能修复可能影响事务性的技术细节。
