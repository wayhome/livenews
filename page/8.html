Monitoring My Homelab, Simply

作者: Bogdanp | 评分: 118 | 评论数: 20 | 发布时间: 2025-07-10 11:28
文章摘要

文章介绍了一种简化的家庭实验室监控方案，作者开发了一个小型程序来进行HTTP、DNS、TLS等检测，并通过https://ntfy.sh发送通知。该方案旨在满足以下需求：出现严重故障时通知、持续故障时重复提醒、修复后通知以及易于添加检测器。程序通过一个循环运行检测器，失败时发送通知，并每小时提醒一次。作者提供了TLS检测器的示例代码，并说明了如何处理故障和恢复通知。程序设计简单，避免复杂的状态管理，且易于部署和维护。作者的目标是捕捉明显的系统问题，而非解决所有潜在故障或提供详尽的历史数据分析。

主要讨论点：各类监控解决方案的比较与选择 不同观点： • reboot81 推荐使用 https://healthchecks.io 并提供了针对不同操作系统（Windows、MacOS、Linux）的脚本链接，强调其易用性。 • Jedd 提到使用两个“死开关”（dead man switches）进行监控，并通过个人经历强调日志聚合的重要性，指出家庭实验室中日志聚合的简便性及其潜在的多重好处。 • Evidlo 推荐使用 updown.io，因其价格低廉且易于使用，特别适合单台机器的监控。 • Scaevolus 使用 Prometheus + Prometheus Alertmanager 组合，强调其功能丰富和报警表达式的可视化优势，且可通过容器化简化部署。 • danesparza 强调家庭实验室中应监控的具体指标，如RAID健康状态、磁盘空间、备份作业运行情况和SSL证书到期等。 • justusthane 计划开发一个Python程序作为监控解决方案，强调其可扩展性和插件化设计，但提到开发进度缓慢。 • Havoc 认为 Uptime Kuma 最简单，尤其因为其提供了Python API包，便于批量操作和编辑。 • compumike 自荐其团队开发的监控和报警解决方案 https://heiioncall.com/，强调其功能全面和灵活的静音设置。 • bonobocop 推荐 Cloudprober，因其易于配置和扩展，适合与Go语言集成。 • Spooky23 使用 node exporter 到 Prometheus 和 Grafana 的组合，并通过 Uptime Kuma 和 Pushover 实现报警，强调其易于设置和实用性。 • JZL003 使用 Node Express 服务器结合多个免费监控服务进行监控，通过Promise.all管理状态，并利用免费监控服务发送邮件报警。 • frenchtoast8 在工作中使用 Datadog，但认为其对于家庭实验室过于昂贵，推荐 NewRelic 和 Grafana Cloud 的免费计划，但指出学习成本问题。 • loloquwowndueo 质疑 reboot81 的方案是否重新发明了 Monit，并提到 Prometheus + Alertmanager 的Docker容器化部署简单且稳定。 补充讨论： • 争议焦点之一是解决方案的复杂性和成本之间的平衡。例如，Jedd 和 frenchtoast8 强调了高成本工具如 Datadog 在家庭实验室中的不适用性，而 Evidlo 和 Havoc 则推荐了更廉价且易用的替代方案。 • 另一个讨论点是日志聚合和历史数据的重要性，Jedd 通过个人经历强调了这一点，而其他评论者如 Spooky23 则通过具体案例说明了监控系统的实际效益。 • 可扩展性和易用性也是重要讨论点，justusthane 提出的自定义Python程序和 Havoc 对 Uptime Kuma 的API批量操作的推荐都反映了这一点。 总体而言，讨论围绕监控工具的选择展开，涉及成本、功能、易用性和扩展性等多个方面。

Bypassing Google's big anti-adblock update

作者: deryilz | 评分: 960 | 评论数: 72 | 发布时间: 2025-07-12 19:06
文章摘要

本文介绍了作者如何发现Google Chrome在MV3更新中绕过广告拦截限制的漏洞。MV3更新取消了`webRequestBlocking`权限，导致广告拦截器无法正常工作。作者发现，尽管`chrome.webRequest` API在MV3中不再支持`blocking`功能，但由于JavaScript绑定实现的漏洞，可以通过伪造事件并利用`opt_webViewInstanceId`参数绕过权限检查，从而恢复广告拦截功能。该漏洞的根本原因在于Chrome对JavaScript绑定的处理不当，使得扩展程序能够绕过安全验证。作者在2023年报告了此漏洞，并认为这是他遇到的最有趣的漏洞之一。

评论摘要
主要讨论点：Google的MV3政策及其对广告拦截器和浏览器选择的影响 不同观点： • al_borland认为，反对Google举措的唯一正确做法是放弃使用Chrome及所有基于Chromium的浏览器，以削弱Google对网络未来方向的垄断。 • breve推荐使用Firefox，因为uBlock Origin在Firefox上表现最佳，并提供了相关链接支持其观点。 • krackers质疑Google对MV3安全性的声明，指出MV3并不比MV2更安全。 • jacquesm将广告拦截器比喻为“大脑的防火墙”，批评Google在广告内容控制上的垄断地位，尤其对YouTube的广告策略表示不满。 • throwaway73945认为OP让Google修补了一个无害的“问题”，而这个问题本可以被插件开发者用来绕过MV3的限制。 • crazygringo反驳关于webRequestBlocking的普遍观点，声称uBlock Origin Lite与Chrome和MV3配合良好，并指出新版本在性能上的改进。 • raydenvm建议使用Brave浏览器，并提供相关文章链接，说明Brave对MV3的应对措施。 • zulban主张使用Firefox和Linux来避免被Google和Windows的商业模式影响，质疑“绕过”策略的长期有效性。 • pnw表示自从切换到Brave浏览器后，再也没有怀念过Chrome。 • urda简单直接地建议通过安装Firefox来绕过Chrome的问题。 • RS-232表达了对Safari的喜爱，并希望Apple能重新推出Safari for Windows。 • RockstarSprain对Firefox表示了一定的兴趣，但指出其无法安装PWAs的问题，并提到一个第三方扩展，但对其隐私安全性有所担忧。 • loloquwowndueo表示在工作笔记本上不得不使用Chrome，但在其他设备上使用Firefox，并对uBlock Origin在工作中的作用表示赞赏。 • daft_pink询问是否可以通过使用其他基于Chrome的浏览器来避免MV3的影响，并寻求隐私保护的建议。 • diebillionaires强烈建议不要再使用Chrome，甚至认为Safari在隐私保护上可能更好。 补充讨论： 1. 关于浏览器选择的讨论主要集中在Chrome、Firefox和Brave之间，用户对隐私、性能和广告拦截功能有不同偏好。 2. MV3政策对广告拦截器的影响是争议的焦点，尤其是它对用户体验和开发者社区的影响。 3. 讨论中多次提到使用非Chrome浏览器（如Firefox和Brave）作为绕过Google政策的方法，并提供了具体的技术建议和链接。 4. 对广告内容的控制和Google的垄断地位是用户不满的主要来源，尤其是对YouTube广告的不满。 5. 用户对不同浏览器的PWA支持和隐私保护功能表现出关注，尤其是Firefox在这方面的不足被提及。

Show HN: A Raycast-compatible launcher for Linux

作者: ByteAtATime | 评分: 182 | 评论数: 19 | 发布时间: 2025-07-13 16:57
文章摘要

**Raycast-Linux** 是一个为 Linux 开发的、受 Raycast 启发的开源启动器。它旨在重现 Raycast 的核心功能，包括可扩展命令面板、支持 Raycast API 的扩展、智能计算器（由 SoulverCore 驱动）、剪贴板历史记录、文本片段和 AI 集成等。由于 macOS 和 Linux 之间的差异，部分 Raycast 扩展可能不兼容，尤其是依赖 macOS 特有 API 或二进制文件的扩展。 用户可以通过 GitHub Releases 页面下载最新的 **.AppImage** 文件，并通过命令行赋予执行权限后运行。该应用需要 glibc 2.38 及以上版本，并建议 Wayland 用户配置 udev 规则以启用全局文本片段功能。若要从源代码构建，需安装 Rust、Node.js、pnpm、Tauri 及 Swift 工具链。

评论摘要
主要讨论点：Linux平台上的Raycast替代品及其相关技术讨论 不同观点： • Imustaskforhelp认为该AppImage文件过大，与其预期不符，特别是考虑到Tauri框架本应带来更小的体积。此外，他在Wayland环境下遇到EGL显示错误，并表示自己使用dmenu（fuzzel）和自定义键绑定（hyprland）作为替代方案。 • runjake对项目表示赞赏，但建议更改名称以避免潜在的商标问题。他还提到其他可扩展的Linux启动器，如KRunner和Albert。 • a022311对项目表示高度赞赏，并建议使用Deno作为运行时以解决扩展启动慢的问题，同时推荐Numbat作为Soulver计算器的替代方案，以及参考Project Gauntlet项目。 • ksynwa引用了维基百科上关于Raycast的定义，强调其最初是为macOS开发的。 • mynegation和flipcoder都提到名称问题，认为可能会引发法律纠纷，建议尽快更改名称。 • jraph提到KRunner作为另一个可扩展的Linux启动器选项。 • Sophira关注Wayland环境下的安全问题，质疑添加udev规则是否会削弱Wayland对键盘访问的保护机制。 • _seiryuu_表示项目在cosmic shell环境下表现有些异常，但在其他环境下运行良好。 • imcritic对项目的价值提出质疑，认为增加更多软件未必能显著提升效率。 • ddaletski和hiyer都表示自己正在开发类似的项目，但看到该项目后考虑贡献代码而不是继续自己的项目。 • evertedsphere的评论较为调侃，没有提供实质性意见。 • regularjack对项目开发者的年龄表示赞赏，并鼓励其继续努力。 补充讨论： • 项目的名称问题引发多次讨论，多数意见认为需要更改以避免商标纠纷。 • 关于技术实现，特别是运行时和计算器实现的选择，a022311提供了详细的建议和参考链接。 • Wayland环境下的安全机制及其可能的绕过问题引起了Sophira的关注和质疑。 • 项目在不同Linux环境下的兼容性和表现也被多位用户提及，显示出对跨平台支持的关注。

Axon’s Draft One is designed to defy transparency

作者: zdw | 评分: 249 | 评论数: 15 | 发布时间: 2025-07-11 00:21
文章摘要

Axon Enterprise's Draft One是使用生成式人工智能根据警察随身摄像头音频撰写警察报告的产品。然而，电子前沿基金会（EFF）的调查发现，该技术设计有意避免审计，缺乏透明度和问责性。审查的公开记录显示，无法区分报告中哪些部分由AI生成，哪些由警察撰写。Draft One使用ChatGPT变体处理音频并生成报告，但存在偏见、不准确或误解的风险。警察应编辑AI生成的内容，但缺乏有效的审计系统，无法追踪报告的编辑历史。当报告中出现不当语言或虚假信息时，无法确定责任在于警察还是AI。该技术缺乏透明度，可能影响司法公正，难以评估其效果和风险。

评论摘要
主要讨论点：AI在警察报告生成中的应用及其潜在的法律和责任问题 不同观点： • **[支持谨慎使用AI的观点]**：Theptip认为，AI有机会揭示和修正隐藏的偏见，但也有可能加剧偏见。因此，需要建立防护机制，特别是在涉及生死攸关的系统时。他强调了LLM输出需要有来源和测量，以防止错误和偏见被传播。 • **[质疑实际影响的观点]**：Workaccount2认为，在当前一切都被记录的时代，AI生成报告的实际影响可能有限。他指出，如果使用 body camera 和车载摄像头记录整个事件，那么警察报告的可靠性问题可能不如想象中严重。 • **[责任归属的观点]**：Mycall和Asah强调，无论报告是由AI还是由警官撰写，最终责任应由签字警官承担。Asah进一步将此与飞行员对自动驾驶仪的责任相比较，强调 accountability 的重要性。 • **[技术透明度的观点]**：Patrickhogan1指出，音频记录可以增加透明度，并且这将成为辩护律师的常规程序。任何技术问题都会很快被发现，如果警官没有纠正错误，他们将面临严重后果。 • **[法律争议的观点]**：Squirrel预测，创意律师会利用AI生成报告在法律案件中的漏洞，例如让AI作为证人出庭。他强调了报告中的措辞错误可能导致的法律问题。 • **[数据保存与法律纠纷的观点]**：Surbas担心OpenAI是否保存所有原始数据，特别是在涉及与媒体公司法律纠纷的情况下。 • **[AI引入偏见的观点]**：Moron4hire指出，警官作为目击者的不可靠性以及AI可能引入提示偏见的问题，认为这可能导致反效果。 • **[技术与法律限制的观点]**：Troupo提到欧盟AI法案对这类应用的禁止，指出法律对技术应用的限制作用。 • **[AI使用责任的观点]**：Efitz担心人们不会负责任地使用AI，并提出了一种可能的解决方案，即让AI生成不可编辑的转录和摘要，同时保留原始记录作为证据。 • **[技术依赖的担忧]**：Causal担心过度依赖AI技术可能导致部门雇佣不合格的警官。 • **[提高数据驱动能力的观点]**：Csujoy认为，AI工具可以帮助确保所有事实都被包括在内，并且更多的信息可以使警察部门更加数据驱动。 补充讨论： • 争议的焦点在于AI生成报告的可靠性、责任归属以及在法律程序中的透明度和可信度。 • 讨论中多次提到透明度和保存原始记录作为解决AI生成内容潜在问题的重要措施。 • 不同观点对AI在实际应用中的效果和风险持不同态度，从支持到谨慎再到反对都有所涉及。

主要讨论点：对《神经漫游者》及其影响的多元看法 不同观点： • **对《神经漫游者》的个人体验差异**： - [daremon] 分享了自己反复阅读《神经漫游者》超过100次的经历，认为这本书成为了他应对考试压力的一种“心灵慰藉”，并最终影响他选择了计算机科学作为专业。 - [simpaticoder] 则指出《神经漫游者》中的“网络空间”概念缺乏物理基础，且与现实技术不一致，但仍然认为这本书是伟大的。 • **技术细节与作者背景的讨论**： - [macleginn] 引用吉布森的自述，指出吉布森在写作《神经漫游者》时对计算机技术并不熟悉，并通过吉布森对早期计算机的失望来解释其作品中技术描写的浪漫化。 - [simpaticoder] 进一步指出《神经漫游者》中的技术描写更像“魔法”而非科学，并认为这使得小说更接近幻想而非科幻。 • **《神经漫游者》与其他作品的比较**： - [makeitdouble] 认为尽管《神经漫游者》是开创性的，但日本作家如士郎正宗的《攻壳机动队》也同时在探索类似的赛博朋克主题，且日本赛博朋克文化未得到足够认可。 - [johngossman] 提出约翰·布鲁纳的作品如《Stand on Zanzibar》早于吉布森和斯特林，并对后两者有重要影响。 - [GMoromisato] 列举了80和90年代科幻小说的“万神殿”，其中包括吉布森，但也提到了其他如菲利普·K·迪克和尼尔·斯蒂芬森等作家。 • **对赛博朋克风格及其演变的反思**： - [amarcheschi] 分享了一篇长文链接，讨论赛博朋克为何如今显得“过时”且未能自我革新。 - [ecocentrik] 认为吉布森虽然是赛博朋克的早期代表，但其作品不如斯蒂芬森和斯特林复杂，并推荐了沃伦·埃利斯的《Transmetropolitan》。 补充讨论： • **对《神经漫游者》细节的争议**： - [mindcrime] 和 [kevin_thibedeau] 对文章中提到的1984年24小时新闻和有线电视的普及提出异议，指出在某些地区有线电视尚未普及。 - [nocoiner] 反驳文章中关于《神经漫游者》时间线未明确的观点，指出小说三部曲中明确了故事发生在2050至2070年代。 • **推荐其他科幻作家和作品**： - [johngossman] 推荐了约翰·布鲁纳的作品。 - [kenoath69] 推荐了弗诺·文奇的作品，认为其具有严谨的逻辑结构和有意义的预测。 - [GMoromisato] 和 [ecocentrik] 分别提到了尼尔·斯蒂芬森、赛勒斯·雷德等作家的作品。 • **对阅读体验的反思**： - [cherryteastain] 认为《神经漫游者》中过多的术语使其阅读体验变得疲惫，建议电子书版可以加入解释功能以提升阅读体验。 争议焦点： • **《神经漫游者》的技术描写和现实技术的差异**，以及**其在赛博朋克文学中的地位和影响**是主要争议点。部分读者认为其技术描写不切实际，而另一些读者则强调其开创性影响和文学价值。
