Changing how we develop Ladybird

作者: EdwinHoksberg | 评分: 838 | 评论数: 105 | 发布时间: 2026-06-05 07:26
文章摘要

Ladybird 浏览器项目宣布不再接受公开的 pull request，今后代码变更仅由项目维护者提交。这一改变主要出于两个原因：一是 AI 工具的普及让代码贡献不再能有效反映贡献者的可信度和投入程度，降低了通过贡献建立信任的传统机制；二是作为即将面向真实用户的浏览器，安全性至关重要，项目需要更严格的开发流程和明确的代码责任归属。项目仍保持开源，欢迎通过 bug 报告、测试、标准讨论等方式参与，但不会通过其他渠道接受代码补丁。所有现有的公开 PR 将被关闭。

评论摘要
**主要讨论点：** Ladybird浏览器项目宣布不再接受外部代码贡献后，社区对开源项目应对AI生成代码冲击的不同反应 **不同观点：** • **支持方**：认为AI降低了代码提交门槛，大量AI生成的PR让maintainer负担激增，代码量不再等同于付出的努力和诚意。项目有权优先保障质量和安全（Fraterkes, noIdeaTheSecond, mabedan） • **反对方**：认为这损害了开源精神，阻碍了新维护者的发现和培养；拒绝外部贡献意味着重复劳动，用户修复bug后无法直接贡献，只能让团队重新实现（nh2, koteelok, pulsartwin） • **中间立场**：理解资源有限团队的困境，但指出Chrome/Firefox等大型项目仍保持开放，值得肯定；担心失去社区的非代码贡献（想法、代码审查等）带来更大损失（domenicd, patates） **补充讨论：** - 有人质疑Ladybird作者本人也常提交大量未经审查的代码，决策存在双标（adrian17） - SQLite和Blender等成功项目早已采用类似封闭模式，这可能是大型项目的必然趋势（nathell, TeriyakiBomb） - 社区担忧这背离了Serenity/Ladybird原本的社区文化，希望至少保留未来参与的可能性（mvanveen, Deukhoofd）

这篇文章介绍了作者开发的"Azure Linux Desktop"项目——一个Windows应用程序，可在窗口中启动完整的Linux桌面环境。项目结合了Microsoft Build 2026的四项技术：wslc容器运行时（通过API直接运行OCI容器）、WinUI Reactor（用C#以React方式构建UI，无需XAML）、Azure Linux 4.0（基于Fedora 43快照，通过Fedora仓库安装XFCE桌面）、以及.NET 10。应用启动后自动构建容器镜像，运行XFCE+XRDP服务器，通过嵌入的RDP客户端连接显示。作者坦言这是个实验性玩具项目，使用了不稳定的WSL源码编译版本和一些技术hack，但展示了这些新技术组合的可能性。

评论摘要
主要讨论点：关于 LLM 上下文过滤工具的效果、可靠性和实际价值的讨论 不同观点： • **支持派**：认为过滤工具有价值。wood_spirit 分享了自己的实现经验，通过按需加载工具和截断输出来优化；rahulyc 建议用廉价模型预过滤；jemmyw 推荐用子代理（subagent）保持上下文清洁 • **质疑派**：担心过滤会损害 LLM 推理能力。clutter55561 指出 LLM 是在完整输出上训练的，过滤后的"瘦身"格式可能反而增加 token 消耗；jemmyw 和 avocadoking 提到过滤工具有时会让 agent 更困惑，产生更多调用 • **方法论批评**：cityofdelusion 强调"节省 91% token"的标题不准确，只是单个案例的输出 token 减少，不代表整体效果；threecheese 批评文档缺少实际使用示例和行为说明 • **技术风险关注**：devdoc83 担心过滤会剥离关键信息（如堆栈跟踪）；alex7o 提到 rtk 存在类似问题——有时会去掉 LLM 需要的内容 补充讨论：fcanesin 提出另一思路——拒绝传递大型输出并强制 LLM 自己编写过滤器；多位用户要求提供与 rtk、caveman 等替代方案的对比和评估数据

"Maybe later" was a feature

作者: arnorhs | 评分: 94 | 评论数: 13 | 发布时间: 2026-06-04 18:31
文章摘要

这篇文章探讨了"不写代码"的价值。作者认为，团队待办事项中那些一直被推迟的功能，往往最终证明是不必要的——如果真正重要，早就会被优先实现。不构建这些功能实际上加速了团队发展，帮助聚焦真正重要的事情。 作者担心随着AI编程工具的普及，开发者会用它们构建那些本不该构建的积压功能，导致代码库膨胀、充斥难以维护的遗留代码。虽然AI也能帮助删除代码，但实际操作中很难说服团队移除已有功能。 核心观点：最有价值的代码，是那些你没有写的代码。选择不做什么，本身就是一种重要的产品和开发策略。

评论摘要
主要讨论点：AI加速软件开发后，是否应该构建更多功能，以及"maybe later"（延迟决策）机制的价值 不同观点： • **支持快速构建派（staticshock）**：认为一切都是搜索过程，AI让我们能搜索更多可能性。虽然会产生大量垃圾，但优质内容会自然浮现，就像书籍、音乐一样。进化压力会重新平衡"maybe later"机制 • **质量优先派（overgard, andai, gamerDude）**：警告用LLM快速实现功能容易事后发现是坏主意。手写代码时会更早遇到问题。主张用AI做更好的工作（测试、分析）而非堆砌功能。最好的代码是不存在的代码——无bug、无维护负担。减法能力（删除、简化）比加法更重要 • **经验主义派（patcon）**：建议将精力从"决定构建什么"转向"拆解错误构建"。基于验证经验优于假设性规划，但担心我们会失去预测未来的能力 • **怀疑幸存者偏差派（greatgib）**：质疑"未构建的功能果然没用"的结论。那些功能可能带来突破、更多客户，或避免安全漏洞。结果不确定，不能轻易下结论 补充讨论：cortesoft指出有些"nice to have"功能延迟后持续浪费时间，最终实现时后悔没早做。vegadw从非商业角度看，认为AI降低门槛让更多人实现创意项目是好事，关键看输出是否需要人类创造力
