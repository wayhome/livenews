Obfuscation: Building the final boss of cryptography (Part I)

作者: fbrusch | 评分: 66 | 评论数: 2 | 发布时间: 2026-06-29 16:35
文章摘要

这篇文章介绍了密码学中的**混淆(obfuscation)**技术。混淆可以将程序转换为"加密程序",隐藏内部逻辑但保持输入输出功能不变,是密码学最强大的原语。 混淆接近"无需信任的可信第三方"理想,结合区块链可实现安全私密的投票系统等应用。但创建安全混淆极其困难:2001年证明理想混淆不可能实现,研究转向**不可区分混淆(iO)**。 近年来取得进展:在合理安全假设下可实现iO,但运行时间是"银河级"的——涉及多层类似全同态加密的嵌套计算,时间复杂度超过λ^10(λ为安全参数,通常为100-120)。文章标题暗示这是系列文章的第一部分。

评论摘要
主要讨论点：密码学中"不可区分混淆"(indistinguishability obfuscation)技术的实用性和可信度 不同观点： • **技术怀疑派（stouset）**：从技术角度质疑不可区分混淆的定义本身是否有实际意义。核心论据包括：(1) 优化编译器已能将相同功能程序转换为统一表示，符合该定义但无实用价值；(2) 现实中不存在功能完全相同但实现不同的非平凡程序，因为复杂程序必然在边缘情况或bug上存在差异，使得该形式化定义在实践中失效 • **可信度质疑派（vrighter）**：对提出该理论的研究者本人持强烈怀疑态度，指责其"自负"且"声称能解决已被数学证明不可解的问题"，暗示这可能是学术不端或夸大宣传 补充讨论：两种批评角度截然不同——前者进行理性的技术分析，后者则带有明显的情绪化和人身攻击色彩。争议焦点在于该密码学技术是理论上不可行还是仅仅实用性不足。

Understanding the Linux Kernel: The Scheduler

作者: valyala | 评分: 28 | 评论数: 3 | 发布时间: 2026-06-27 11:16
文章摘要

这篇文章介绍了 Linux 内核调度器的核心机制。 **主要内容：** 1. **调度对象**：内核实际调度的不是"进程"或"线程"，而是统一的 `task_struct` 结构。进程和线程的区别仅在于共享资源的方式（内存、文件描述符等），但对调度器来说都是相同的可运行任务。 2. **调度状态**：每个任务内嵌一个 `sched_entity` 结构，存储调度相关的状态信息（如 vruntime、vlag、deadline 等），这是调度器做决策的依据。 3. **调度类层次**：Linux 采用多个调度器（调度类）的分层架构，按优先级堆叠。当 CPU 需要选择下一个任务时，内核从高到低询问各调度类，第一个有可运行任务的类获胜，下层调度类不参与决策。 4. **后续内容**：文章将继续探讨任务切换时机、切换成本以及 EEVDF 调度算法的具体实现。

评论摘要
主要讨论点：对Linux调度器技术文章的质量和教学方法的批评 不同观点： • **技术深度不足**（usr1106）：文章未能回答核心技术问题。单核场景下，调度器被错误地描述为"外部监督实体"，而非CPU执行的代码片段；多核场景下，缺乏对调度器数据结构同步机制和扩展性的深入解释。具体疑问包括：抢占标志设置后如何找到"安全点"？多核环境下如何避免数据结构混乱？ • **AI生成内容问题**（jurschreuder）：怀疑文章是AI辅助写作，导致内容重复且缺乏新意，呼应了usr1106关于"读过很多次"的评价。 • **教学顺序不当**（d3Xt3r）：建议先讲解CFS调度器（更简单、运行数十年），通过其局限性（如桌面交互性差）自然引出EEVDF，而非直接讲EEVDF。这样能让读者更好理解和欣赏新调度器。 补充讨论：三位评论者从不同角度指出同一篇文章的问题——技术解释的视角问题、内容原创性问题和知识组织问题，反映出技术写作中常见的多个痛点。

pglayers 是一个 PostgreSQL Docker 扩展管理工具，解决了官方 PostgreSQL 镜像不包含扩展的问题。它提供两种方案：1) 预构建的完整镜像包含多个扩展；2) 通过 Docker 层叠加自定义选择扩展，无需编译。每个扩展作为独立镜像层发布，用户只需用 `COPY --from` 命令堆叠所需扩展到官方 postgres 镜像上。支持 PostgreSQL 17/18/19，提供 53+ 个扩展如 pgvector、PostGIS、pg_cron 等。

主要讨论点：围绕pglayers项目的技术实现方法和产品改进建议 不同观点： • **技术架构建议（chatmasta）**：推荐采用PostgreSQL 18的extension_control_path功能，参考CloudNativePG的方案，实现运行时动态附加扩展的能力，避免构建"God images"（包含所有扩展的庞大镜像），提升灵活性和可组合性 • **用户体验改进（khurs）**：建议增加Docker Desktop的GUI快速入门指南，因为目标用户群可能不太熟悉命令行操作；同时建议购买专属域名以提升专业性，而非使用GitHub托管域名 • **功能扩展需求（securqbit）**：询问是否计划支持pgvectorscale扩展，表明对特定功能的需求 • **积极反馈（hoppp）**：表示项目正好满足需求，准备试用 补充讨论：评论整体呈现建设性反馈，涵盖技术架构优化、用户体验提升和功能扩展三个层面，反映出该项目受到关注且有实际使用需求。chatmasta的建议最为深入，提供了具体的技术参考和实现路径。

I Don't Maintain My Homelab

作者: surprisetalk | 评分: 44 | 评论数: 23 | 发布时间: 2026-06-29 14:15
文章摘要

这篇文章讲述了作者如何构建一个几乎无需人工维护的家庭实验室(homelab): **基础设施简化**:将四台服务器整合为一台,大幅降低复杂度;树莓派运行Home Assistant OS自动更新;UniFi网络设备支持定时自动更新。 **软件自动化**:通过crontab每周自动更新所有Docker服务;设置自动备份任务,包括数据库导出和文件同步到ZFS存储池。 **维护成本**:每月仅需约15分钟进行系统更新,甚至可以6个月不管也不会出问题。作者认为这种"设置后即可忘记"的方式,在隐私、安全和便利性之间达到了理想平衡,特别适合工作繁忙的情况。 核心理念:通过精简架构和自动化脚本,让系统自我维护。

评论摘要
主要讨论点：家庭服务器（homelab）如何实现低维护运行，以及这种状态是否仍算"实验室" 不同观点： • **最小维护派**：通过固定软件版本、使用Docker自动启动、限制局域网访问等策略，实现月均15分钟以下的维护时间。代表做法包括旧硬件复用、NFS共享配置文件、定期自动备份到云端 • **现实主义派**：承认总体维护已经很少，但指出某些服务（NextCloud、Immich、Minecraft服务器）仍需要人工干预，如维护模式、配置文件编辑、版本不匹配等问题 • **工具派**：通过特定技术栈实现超低维护，如NixOS（3年稳定）、Debian配合unattended-upgrade（可2年不管），甚至有人写Go程序自动监控维护 • **定义质疑派**：认为如果不需要频繁折腾，那就不再是"实验室"而是"稳定家庭基础设施"。真正的lab应该是不断尝试新硬件、学习新技术（如BGP、集群） 补充讨论：多位评论者强调稳定性对于家庭多用户场景的重要性（如配偶使用），这与企业环境的频繁更新策略不同。另有趣的是，多人期待AI agent自动维护，但原帖作者并未采用此方案。
