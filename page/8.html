Fusion Programming Language

文章摘要

Fusion 是一种编程语言，旨在从单一代码库为 C、C++、C#、D、Java、JavaScript、Python、Swift、TypeScript 和 OpenCL C 等多种语言实现可重用组件（库）。它能将一份代码翻译成所有这些目标语言，生成的代码轻量级（无虚拟机、模拟或依赖），人类可读，并且符合目标语言的命名规范和文档注释风格。通过一个简单的命令即可完成多语言转换。

评论摘要

Show HN: DBOSify – Drop-in Temporal replacement built on Postgres

作者: KraftyOne | 评分: 84 | 评论数: 5 | 发布时间: 2026-06-24 17:20
文章摘要

DBOSify 是 Temporal Python 的替代品,使用 Postgres 数据库(通过 DBOS Transact)替代 Temporal 服务器。它让你无需额外基础设施即可运行持久化工作流、活动、信号、更新、重试和恢复功能。 核心机制:将 Temporal 工作流作为 Postgres 支持的 DBOS 工作流运行,使用确定性解释器在虚拟事件循环上执行,所有非确定性操作都在 Postgres 中设置检查点。活动和计时器成为 DBOS 步骤,信号和更新通过 Postgres 的 LISTEN/NOTIFY 传递,支持故障恢复和精确一次执行。 注意:这不是协议兼容的替代品,不支持其他语言的 Temporal SDK,也不支持 Temporal Web UI 或 CLI。

评论摘要
主要讨论点：关于 DBOS 作为 Temporal 替代方案的技术实现和商业模式问题 不同观点： • **开源可持续性担忧**（aliasxneo）：选择 River 而非 DBOS，担心 VC 支持的公司可能会"rug pull"（撤回承诺）。认为 River 虽然也是商业产品，但因其自举融资和近期的开源友好举措更值得信赖 • **技术定位不清**（unsnap_biceps）：质疑 DBOS 的定位表述矛盾——既说替代 Temporal，GitHub 又说只替代 Python 客户端 SDK；同时指出宣传"只需 Postgres"但架构图显示需要 worker 节点，存在基础设施需求的误导 • **功能完整性疑问**（antman）：关注实际兼容性，询问 DBOS 能否通过 Temporal Python SDK 测试套件，以及是否有未实现的功能 补充讨论：创始人 Peter（KraftyOne）出现回应社区问题，但评论中尚未展开深入技术讨论。核心争议集中在：商业模式的可信度、产品定位的准确性、以及与 Temporal 的实际兼容程度。

文章摘要

1981年2月1日，澳大利亚与新Zealand在墨尔本板球场进行一日国际赛。比赛最后一球，新西兰需要击出六分才能追平。澳大利亚队长Greg Chappell指示弟弟Trevor Chappell以贴地滚球的underarm方式投球，使对手无法将球击高得分。虽然这在当时合法，但被普遍认为违背了板球运动的公平精神，引发巨大争议。此事件最终促使国际板球法规修改，禁止这种投球方式。比赛中还曾出现另一争议：Greg Chappell被接杀但裁判判其未出局。

评论摘要
主要讨论点：1981年澳大利亚对新西兰板球赛中的"underarm bowling"事件争议 不同观点： • **认为是不光彩行为**：新西兰人普遍认为这是极大耻辱，应该记入公民测试；澳大利亚人也承认这是"great shame"，新西兰永远可以拿此事说事 • **与其他运动的战术对比**：有人认为类似美式足球跪球或足球拖延时间的战术，属于规则内的合理操作；也有人对比棒球的故意四坏球保送，在棒球中被视为公平战术 • **规则vs体育精神的争议**：虽然underarm bowling在规则上合法（原本就是板球最初的投球方式），但被视为违背体育精神；类似NBA的underhand罚球虽有效却因"不够男子气概"而少有人用 补充讨论： 评论提到更严重的不当行为案例（Bodyline战术）；有人引用Douglas Adams和Bill Bryson对板球的幽默描写；BBC长波广播Test Match Special的怀旧情结；整体氛围显示板球文化中"gentleman精神"与规则技巧的微妙张力。

WordStar: A Writer's Word Processor (1996)

作者: droidjj | 评分: 140 | 评论数: 21 | 发布时间: 2026-06-27 03:30
文章摘要

科幻作家Robert J. Sawyer介绍了为何他和众多科幻作家（包括阿瑟·克拉克、乔治·马丁、安妮·赖斯等）至今仍使用WordStar文字处理软件。WordStar于1978年发布，其设计专为触摸打字者优化，通过Control键组合实现各种功能。其界面逻辑巧妙：常用的光标移动键（^E/^S/^D/^X）在键盘上呈菱形排列，其他相关功能键则围绕这个菱形分布，形成位置记忆而非字母记忆的操作模式。这种设计使创作过程更流畅高效，这是WordStar优于其他文字处理软件的关键所在。

评论摘要
主要讨论点：WordStar文字处理软件的历史回顾和使用体验，以及现代写作工具的对比 不同观点： • **怀旧派/支持者**：认为WordStar简洁高效，键位绑定易学易记，适合专注写作。有人至今仍用FreeDOS运行WordStar进行初稿创作，甚至有获奖科幻作家(如George R. R. Martin)仍在使用。 • **实用主义者**：承认WordStar在特定场景有价值(无干扰写作)，但指出其局限性——难以处理复杂文档结构、多文件交叉引用、导出分享不便，认为现代工具(Word/LibreOffice)在协作和文档管理上更实用。 • **告别过去派**：虽有时代情怀，但不留恋多键组合命令和纯文本界面，认为GUI的发明是进步，现代无干扰写作界面已能替代WordStar的优势。 • **WordPerfect对比**：部分用户更偏好WordPerfect(尤其DOS 6.0版本)用于散文写作，但也有人认为其需要键盘模板和手册，学习曲线陡峭。 补充讨论：有人分享了WordStar导致数据丢失的惨痛经历(未保存崩溃)；技术爱好者提到JOE等现代编辑器继承了WordStar键位；也有人考虑在netbook上运行FreeDOS重现复古写作体验，但面临USB支持等技术障碍。

A C++ implementation of a fast hash map and hash set using hopscotch hashing

作者: gjvc | 评分: 100 | 评论数: 6 | 发布时间: 2026-06-26 21:18
文章摘要

**hopscotch-map** 是一个C++头文件库，使用开放寻址和跳房子哈希（hopscotch hashing）实现高性能哈希表，性能优于 `std::unordered_map`，内存占用少于 `google::dense_hash_map`。 主要提供四类容器： - `tsl::hopscotch_map/set`：默认选择，速度更快，使用2的幂次增长策略 - `tsl::hopscotch_pg_map/set`：质数增长策略，适合哈希函数质量较差的场景 - `tsl::bhopscotch_map/set`：提供 O(log n) 最坏情况保证，可抵御哈希DoS攻击 核心特性包括：仅需包含头文件、支持移动语义和异类查找（heterogeneous lookup）、可缓存哈希值加速查找、可禁用异常。 与 `std::unordered_map` 的主要差异：迭代器在插入时全部失效；修改值需调用 `it.value()` 而非 `it->second`。

评论摘要
主要讨论点：关于哈希表实现的性能比较和技术选择 不同观点： • **推荐boost::unordered_flat_set + rapidhash**：认为这是当前最佳实践，SIMD优化的cacheline性能难以超越，标准库的murmurhash极慢，boost/absl/folly的实现都远超标准库 • **google::dense_hash_map更快**：根据benchmark图表，google::dense_hash_map的运行时间在所有测试方法中最低，性能优于hopscotch实现 • **倾向Robin Hood哈希**：认为hopscotch与robin hood性能曲线接近，但robin hood更为知名成熟，因此更倾向选择后者 • **实际应用中可灵活处理冲突**：指出实践中可以对部分冲突元素采用带外处理，不必像标准哈希表那样强制插入所有元素，这种灵活性在真实负载中很有价值 补充讨论：有开发者分享了10年前在游戏作弊器中使用hopscotch哈希的经历，后来学习到Cuckoo、Robin Hood等算法，理解了hopscotch是两者的结合；另有人质疑benchmark的时效性（最后更新于2019年），询问与boost unordered flat map的对比
