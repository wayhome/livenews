Strangers in the Middle of a City: The John and Jane Does of L.A. Medical Center

作者: dangle1 | 评分: 38 | 评论数: 3 | 发布时间: 2025-06-15 22:45
文章摘要

文章讲述了洛杉矶综合医疗中心努力识别身份不明的病患的故事。每年有约13万人被送往该急救中心，其中一些因昏迷、丧失能力或病重无法提供身份信息。尽管大多数病患在48小时内能被识别，但每年仍有数十人无法确认身份。这些病患因缺乏身份证明，无法被转移到更合适的医疗机构，只能长期滞留医院。 文章详细描述了一位被发现于东好莱坞、身份不明的男性病患。他没有携带任何能提供线索的物品，也无法交流。医护人员通过各种方法试图确认其身份，包括发布照片寻求公众帮助，但均未果。这种情况不仅是个行政问题，还涉及安全顾虑，因为医院无法得知病患的过敏史或用药信息。尽管医院有严格的隐私保护规定，但在涉及无法自行做医疗决定的无名病患时，加州允许医院公开寻助。

评论摘要
主要讨论点：如何处理医院患者身份识别问题及其成本分担 不同观点： • [dzink的观点] 医院通常承担主要成本，而这些成本最终会通过更高的费用转嫁给付费患者。这表明医院在身份识别不清的情况下可能会面临财务压力，并通过提高服务费用来弥补损失。 • [kylehotchkiss的观点] 地方检察官办公室可以协助“促进”身份识别。具体做法是由警官要求患者进行身份自证，若患者拒绝，则可以记录指纹并给予引用，随后决定“不立案”或撤销案件。这种方法旨在平衡患者和医院的利益，通过法律程序帮助医院确认患者身份，同时避免不必要的诉讼。 补充讨论： • [kylehotchkiss进一步讨论了具体操作流程] 提出了一种可操作的程序，通过执法部门介入，在不增加患者和医院负担的情况下解决身份识别问题。这种方式试图在患者权利和医院需求之间找到一个平衡点。 • [争议的焦点] 争议的核心在于如何有效且公平地解决医院在身份识别不清时的成本负担问题。一方关注财务影响，另一方则提出通过法律和程序手段来解决这一问题。 • [潜在的合作机制] kylehotchkiss的建议中隐含了一种合作机制，即医院和执法部门可以协同工作，以较低的成本和更高效的方式解决身份识别问题。

“Don’t mock what you don't own” in 5 minutes (2022)

作者: JNRowe | 评分: 31 | 评论数: 11 | 发布时间: 2025-06-16 01:04
文章摘要

这篇文章讨论了在测试中处理第三方依赖的常见问题，特别强调了“不要 mock 你不拥有的东西”这一原则。文章解释说，这一原则建议在使用 mock 对象时，应该替代自己编写的对象，而不是第三方对象。作者通过一个 Python 程序示例说明了 mock 第三方对象的缺点，并展示了如何避免这种情况。文章指出，直接 mock 第三方 API 会导致测试代码复杂且脆弱，建议使用假的客户端对象返回预定义的静态值来进行测试。作者还提到自己更倾向于使用简单的 stubs 和验证过的假对象，而不是传统的 mock。文章最后推荐阅读 Martin Fowler 的文章以了解 mock、stub 等测试概念的区别。

评论摘要
主要讨论点：是否应该在测试中使用 mock 以及如何有效测试复杂系统 不同观点： • [hamstergene] 支持广泛使用 mock 和抽象接口，认为这样可以减少重复工作、确保 mock 保持更新，并促进依赖注入和全面测试的采用。这种方法可以让库的作者提供最佳的 mock 实现，从而使测试更加可靠。 • [eximius] 支持使用高保真假对象（fakes），只在必要时使用 mocks，主张在实际可行的场合使用真实对象进行测试，特别是在跨团队集成测试中，这样可以提高测试的准确性。 • [molf] 对过度依赖 mock 持怀疑态度，认为测试应尽量覆盖更多的代码栈，避免在依赖更新时出现未检测到的错误。建议使用 HTTP 录制/回放库来应对复杂 API 的变化，而不是完全依赖 mock。 • [AugustoCAS] 批评了一些开发者在测试中过度使用 mock，特别是在功能编程中不恰当地使用 mock，指出这种做法可能源于对测试双的概念缺乏理解。 • [lmm] 认为如果测试只覆盖业务接口部分而不涉及可能出错的部分，那么使用 mock 可能没有必要，强调测试应关注实际可能出错的地方。 • [fellatio] 赞同使用倒置控制，但认为需要在某个层面使用真实对象进行测试，以确保系统整体运行正确。 • [ramchip] 指出讨论的观点与 2015 年 Jose Valim 提出的 "mocks 和明确合同" 类似，认为这是一个已有的实践。 • [strken] 对 "不 mock 不属于自己的代码" 这一原则提出质疑，认为其核心在于如何处理 awkward API 而不是所有权问题。 • [hmmokidk] 赞赏 Stripe 提供的 CLI 测试工具，认为其在 webhook 测试中的应用很有价值。 • [mpweiher] 分享了一篇 2014 年的文章，标题为 "为什么我不使用 mock"，暗示对 mock 的不认同。 补充讨论： • 争议的焦点在于是否应广泛使用 mock 以及如何在测试中平衡 mock 与真实对象的使用。 • 一些开发者认为 mock 会导致测试覆盖不足，特别是当依赖库发生未预期的变化时，而另一些开发者则认为 mock 能有效隔离测试环境，提高测试效率。 • 高保真假对象和 HTTP 录制/回放库被认为是 mock 的替代方案，可以提高测试的实际覆盖率和可靠性。 • 对测试双（test doubles）和 mock 的理解差异导致了不同的测试实践，特别是在不同编程范式中的应用。 • 一些评论提到了对 mock 的实际应用经验和历史讨论，显示出这一话题在开发社区中已有较长时间的争议和探索。

AMD's CDNA 4 Architecture Announcement

作者: rbanffy | 评分: 164 | 评论数: 5 | 发布时间: 2025-06-17 17:38
文章摘要

AMD's CDNA 4架构是对CDNA 3的适度升级，主要提升矩阵乘法性能，尤其针对低精度数据类型的机器学习任务。CDNA 4沿用CDNA 3的大规模芯粒设计，使用加速计算芯粒（XCDs）和基底芯粒，通过Infinity Fabric实现内存访问。相比MI300X，MI355X减少了每XCD的计算单元（CU）数量，但通过提高时钟速度弥补性能。尽管Nvidia的B200在低精度计算上更具优势，AMD依赖更大的GPU和更高的时钟速度保持总体吞吐量领先。CDNA 4的CU矩阵吞吐量翻倍，但在低精度数据处理上仍不及Nvidia。此外，CDNA 4将本地数据共享（LDS）容量增至160 KB，带宽提升至256字节每周期，有助于高性能计算任务。总体上，CDNA 4在矢量运算和高精度数据处理上保持领先，但在矩阵计算上与Nvidia竞争激烈。

评论摘要
主要讨论点：AMD在人工智能和高效能计算（HPC）领域的技术进展及前景，特别是小矩阵运算加速、多核架构以及与Nvidia的竞争对比。 不同观点： • [jauntywundrkind] 认为AMD在小矩阵运算加速上的进展（如LDS增至160KB，写入从32B增至128B）对AI应用非常有意义，并对AMD未来的UDNA统一架构（合并计算和Radeon CDNA、RDNA）表示期待和好奇。然而，他对于多核计算解决方案的扩展性持保留态度，提到之前Navi 4X的旗舰项目取消，并将其与Epyc处理器的扩展性进行对比。 • [robjeiter] 关注AMD在AI推理（inference）方面是否已经与Nvidia并驾齐驱，暗示两者之间的竞争关系，以及用户对两者性能对比的关注。 • [incomingpain] 分享了个人使用AMD Radeon 9060运行ROCm（AMD的机器学习软件）的实际体验，指出在Ubuntu系统上需要多次升级才能使驱动正常工作，表明AMD在软件支持方面仍有改进空间。他提供了具体的性能数据（约40 tokens/sec），并强调了使用过程中遇到的困难。 • [bee_rider] 提出AMD是否已经在HPC领域完全主导了单个计算节点，特别是在软件支持足够的情况下。同时，他质疑AMD是否有与Infiniband（Nvidia的高速网络技术）相当的技术，暗示AMD在HPC网络技术上的不足。 • [icf80] 对UDNA架构表示关注，直接询问是否有关于UDNA的新消息，显示出对AMD未来架构的强烈兴趣。 补充讨论： • AMD在AI和HPC领域的硬件进步（如LDS增大和矩阵运算优化）受到一定程度的认可，但软件支持和多核架构扩展性仍是讨论的焦点问题。 • 用户对AMD与Nvidia在AI推理性能上的对比有实际需求，表明两者在这一领域的竞争激烈。 • 实际使用中，AMD的ROCm软件在兼容性和易用性上存在一定问题，反映了软件生态方面的挑战。 • AMD在HPC网络技术上是否有与Nvidia Infiniband相当的解决方案，成为讨论中有关其HPC主导地位的争议点。 争议焦点： • AMD的UDNA架构及其未来多核计算解决方案的扩展性和可行性。 • AMD在AI推理性能上是否能真正与Nvidia并驾齐驱。 • AMD软件生态的成熟度和兼容性问题。 • AMD在HPC领域是否具备与Nvidia相当的完整技术栈。
