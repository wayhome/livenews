Water system controllers don't belong on the internet, says ex-NSA chief

作者: Bender | 评分: 223 | 评论数: 20 | 发布时间: 2026-08-07 21:19
文章摘要

美国至少12个州的水系统遭网络攻击,疑似伊朗所为。前NSA局长Nakasone在DEF CON大会上表示,可编程逻辑控制器(PLC)不应连接互联网,需要提高安全标准。这些PLC设备可监控水位并控制水泵开关。虽然安全研究人员高度怀疑是伊朗黑客所为,但FBI尚未正式归因。美国拥有5万个水务设施,提供90%的供水,但这些设施普遍资金不足、IT人员缺乏,构成巨大攻击面。Nakasone强调需要通过合作伙伴关系和创新方法来加强关键基础设施的网络防御能力,包括DEF CON Franklin等志愿者项目。

评论摘要
主要讨论点：关键基础设施（特别是水系统控制器）是否应该连接互联网，以及如何平衡安全性与便利性 不同观点： • **完全隔离派**：认为PLC和水系统控制器根本不应该接入互联网，应该采用物理隔离（air-gap），尤其是老旧的30年设备更容易被攻击。将关键基础设施暴露在公网上是不可原谅的失职。 • **有条件联网派**：承认远程访问能大幅提高管理维护效率，避免每次小问题都要现场处理。但前提是必须通过防火墙、VPN等安全方案，由专业人员妥善配置。认为完全隔离在实际操作中很难实现，因为需要中央监控。 • **行业现状揭露**：来自前PLC从业者的深度批评，描述行业极度落后——承包商用Windows笔记本随意备份客户项目、差点上传错误的程序、大型数据中心不了解NAS和RAID、管理层拒绝改变。认为关键基础设施的IT水平"极其原始和野蛮"。 • **安全威胁扩展**：指出漏洞不仅限于互联网连接，还包括不安全的无线RF链接、蓝牙接口、天然气管道压缩站的无线连接等，这些都可能被利用进行攻击。 • **政府责任争议**：有人呼吁政府应投入数十亿美元部署安全工程师主动加固系统，预防类似9/11规模的网络攻击；也有人讽刺NSA的虚伪，暗示其可能阻止他国加强安全。 补充讨论：多位评论者强调大规模基础设施故障可能在数周内导致数百万人死亡，领导层的失职不可原谅；也有人质疑在当前威胁环境下，哪些服务真正需要暴露在互联网上。

Mario Meets Pareto

作者: theanonymousone | 评分: 1167 | 评论数: 54 | 发布时间: 2026-08-06 11:24
文章摘要

这篇文章以《马里奥赛车8》为例,介绍了如何运用经济学家帕累托提出的"帕累托前沿"概念来解决多目标优化问题。 在游戏中选择角色、车身、轮胎和滑翔翼时,需要在速度、加速度、操控等多个属性间权衡取舍。文章指出,某些选项会被其他选项"支配"(在所有维度上都不占优),应该被排除。而帕累托前沿包含了所有未被支配的高效选项。 虽然帕累托前沿不能直接给出唯一最佳答案,但它能客观地筛选出次优选择,让玩家根据自己的偏好从高效选项中做最终决策。 文章最后指出,这个方法同样适用于其他现实场景的多目标优化问题,如选择工作、投资组合、材料设计等。

评论摘要
主要讨论点：如何理解和应用帕累托前沿（Pareto frontier）概念进行多维度优化决策 不同观点： • **实用主义派**：jerf 强调在软件开发中，很多"安全vs体验"的权衡声明是伪命题，因为系统根本还没到帕累托前沿，可以同时改善两者。关键是要先确认是否真的在前沿上，以及别忽略"成本"这个隐藏维度 • **实践应用派**：uzerfcwn 分享了用分治算法在魔兽世界装备优化中应用帕累托前沿的成功案例，将计算时间从数年降至几秒 • **理论质疑派**：cortesoft 指出帕累托分析的前提假设未必成立——"越多越好"不总是真的（如过高速度导致失控），且属性间可能存在复杂的比例关系，使分析变得困难 • **游戏策略派**：__s 和 Velocifyer 讨论马里奥赛车speedrun策略，认为加速度是"技术问题"，顶级玩家选边缘配置；但也有人指出分析遗漏了车体大小、漂移风格等重要机制 • **个人化需求派**：Agentlien 质疑将"简单"作为工作优化目标，认为有意义的工作应该有技术挑战，"简单"与"充实"可能是对立的 补充讨论：多位用户分享了个人经历（hspeiser发现被兄弟"套路"）、提供历史链接和相关项目，体现了帕累托概念在不同场景下的广泛应用价值和理解差异。

Show HN: Wyzer Programming Language

文章摘要

Wyzer是一门静态类型的编译型编程语言，具有两大核心创新： **编舞式编程（Choreographic Programming）**：开发者编写单一程序描述整个分布式系统的交互，编译器自动生成各节点的独立二进制文件，从数学上保证无死锁。 **Perceus内存模型**：采用精确引用计数实现确定性内存管理，无需垃圾回收器的暂停，也无需借用检查器的复杂标注。当变量唯一拥有时，编译器自动实现原地变异（FBIP），提升性能。 设计理念强调统一的所有权规则管理内存、线程和网络资源，网络传输通过显式的所有权转移实现，编译时验证资源安全。支持C ABI互操作，适合系统编程。

评论摘要
主要讨论点：Wyzer 编程语言的展示方式、技术实现细节和项目真实性 不同观点： • **文档结构批评**（多人共识）：jerf、jitl、rbr94 等强烈建议将 choreographic programming（编排式编程）这一核心创新点前置展示，而不是把它埋在文档后面。认为应该用"分布式计数器"等实例立即展示语言如何通过构造保证原子安全，而非先讲解基础语法。 • **技术实现质疑**：vlovich123 质疑如何保证无分布式死锁，追问是否像 Rust 那样"拒绝所有无效程序但不接受所有有效程序"。whateverboat 担心多所有者情况下的性能问题。steeleduncan 质疑不可变变量与编译时常量的实际区别。 • **技术声明纠正**：pron 详细反驳 README 中"垃圾回收使语言更慢"的说法，指出 Java 的移动式 GC 实际上比 C++ 更快，Python 的引用计数更接近 C，GC 算法覆盖广泛的性能范围，慢语言使用 GC 不等于 GC 导致慢。 • **项目真实性争议**：stack_framer 质疑发帖账号的真实性（声称有人冒充创建者发帖），hmokiguess 发现作者自称 14 岁程序员并表示"需要处理这个信息"。 补充讨论：gwbas1c 赞赏项目说明清晰但指出 Web 应用中需转译为 JS 或 WASM；nicoburns 认为 choreographic programming 类似 Next.js 的 server functions；jnpnj 和 slifin 提到 Clojure Electric 等类似项目。

Taste Is All That's Left

作者: tsak | 评分: 686 | 评论数: 113 | 发布时间: 2026-08-06 17:01
文章摘要

这篇文章探讨了AI时代软件开发的核心转变。作者认为,过去开发的难点在于"实现"本身——从想法到产品需要大量时间精力。AI工具让这个过程变得极其容易,想法到成品的距离几乎消失了。 然而,价值并未消失,而是转移了。当制作成本不再是门槛时,判断"什么值得保留"的责任落到了开发者的**品味**上。品味不是表面的偏好,而是一种压缩的、难以言说的判断力——在能解释原因之前就知道某个方案是错的。 作者强调,品味无法通过阅读优秀作品获得,只能通过"摩擦"培养:做出糟糕的东西,被迫面对失败,从中学习。这是机器无法替代的部分,也是如今最稀缺的能力。

评论摘要
主要讨论点：AI时代"品味"（taste）作为人类竞争优势的价值及其争议 不同观点： • **品味成为核心优势派**：认为AI降低了技术门槛后，品味成为关键差异。引用Sontag对品味的定义，强调品味是压缩的、难以言说的判断力，是通过长期实践和错误积累的。AI缩短了从判断到现实的时间，让好坏品味更快显现。 • **品味优势被高估派**：指出竞争对手可在数日内复制功能、UX和视觉设计（如下拉刷新），品味的半衰期正在缩短。AI正在商品化软件，就像90年代的商业模式，可能回归"百货商店式软件"。品味终将趋同为"最优选择"，如同设计系统让设计工作标准化。 • **质疑AI输出质量派**：认为LLM生成内容"几乎没有信号"，中型AI代码库需读500字才能理解模块功能。强调理解微妙错误、生产调试、长期维护等仍然昂贵，首版虽然免费但后续成本高。 • **人类独特价值派**：最终防线是"判断力"、"具身性"和"长期后果考量"能力，这些超出LLM的上下文窗口，人类进化过程与LLM训练压力根本不同。 补充讨论：有人质疑文章本身可能是AI生成（矛盾句式、短句反转），也有人批评关于品味的文章泛滥且缺乏洞见，建议参考康德《判断力批判》的经典论述。

这篇文章介绍了日本游戏设计师MTJ（三辻富贵朗，《泡泡龙》等游戏的设计者）在1989年GAMEST杂志专栏中的预见性观点。 MTJ批判了当时游戏行业的抄袭风气，并虚构了一个"近未来"场景：一台名为"Rip-O-Bot"（抄袭机器人）的机器，只需按几个按钮就能自动生成抄袭游戏——输入要模仿的游戏名，随机选择背景和角色，瞬间完成。 这个1989年的科幻设想与今天的生成式AI工具惊人相似。MTJ警告这样的时代即将到来，普通设计师将因此被大量解雇。他强调，模仿工作机器也能做，人类设计师必须专注于独创性，因为"游戏归根结底就是创意"——这是设计师"最后的武器"。

评论摘要
主要讨论点：1989年某篇文章对游戏行业被衍生作品泛滥的预测，以及这个预测在现实中的体现 不同观点： • 历史验证观点（schnevets）：认为预测的世界确实到来了——90年代有大量衍生卡通游戏，当代有廉价合作游戏和恐怖游戏等"低质量"类型。但关键论据是：即使存在大量衍生品和低质作品，创新和质量从未被真正掩埋，优质内容总能脱颖而出。以《阿拉丁》和《狮子王》横版游戏为例，虽然都是衍生品，但在动画、物理、关卡设计上的差异足以让两款游戏都有价值 • 技术乐观观点（qingcharles）：认同预测的先见之明，但提出新的思考角度——AI工具应该能促进原创性而非削弱它。论据是AI能让开发者快速原型开发、快速试错，理论上应该降低创新门槛 补充讨论：两位评论者对"衍生品泛滥"的态度不同。第一位强调生态系统的自我调节能力（cream rises to the top），第二位则关注技术如何改变创作门槛，暗示对未来抱有不同期待。

文章摘要

Signal加密通信应用现已支持将多部手机(包括Android和iPhone)关联到同一账号。此前Signal仅支持关联PC和iPad,不支持额外手机设备。 更新后,用户可在所有关联设备上同步查看和回复消息,并可选择是否将端到端加密的历史消息传输到新设备,以降低设备共享、丢失或被盗的风险。该功能已在Android 8.20版本和iOS 8.22版本中推出。 此外,Signal还针对大屏设备进行了界面优化,改进了折叠手机的使用体验,并开始支持Android平板电脑。不过Signal表示Android大屏版本仍在完善中,Chromebook应用的界面优化工作也在进行。

评论摘要
主要讨论点：Signal 的多设备支持功能及其实现方式 不同观点： • **信息分享立场（rkagerer）**：提供了 Signal 官方博客链接，认为该链接对理解多设备功能"更有信息量"，倾向于通过官方资料了解功能细节 • **批评性立场（kevincox）**：指出 Signal 的多设备支持存在架构缺陷——仍需依赖主设备作为中心节点。如果主设备离线、电量耗尽或损坏，其他副本设备将完全无法使用。认为这种架构不符合"真正的多设备支持"标准 争议焦点： Signal 当前的多设备实现是否达到了用户期待的"多设备支持"标准。kevincox 强调了主从架构的局限性：副本设备对主设备的强依赖性使得多设备功能在实际使用中可能不够可靠，特别是在主设备不可用的场景下。 补充讨论：这个讨论反映了用户对即时通讯应用多设备功能的期待——希望实现设备间的平等地位和独立性，而非简单的主从复制关系。
