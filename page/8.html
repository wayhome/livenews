Vibe code is legacy code

作者: simonw | 评分: 708 | 评论数: 77 | 发布时间: 2025-07-30 21:13
文章摘要

本文讨论了由Andrej Karpathy提出的“氛围编码”（vibe coding）概念，即一种依赖AI辅助编程的方式，程序员“忘记代码的存在”。虽然氛围编码适用于快速制作原型或一次性项目，但它往往导致技术债务（tech debt），因为生成的代码难以理解和维护。这种代码实质上就是遗留代码（legacy code），通常被开发者厌恶。文章强调，编程的核心是理论构建，而非单纯编写代码行。对于需要长期维护的严肃项目，过度依赖AI进行氛围编码可能导致问题，类似于用信用卡累积债务。文章建议在使用AI工具时要谨慎，理解其局限性，并指出编程技术专长在未来仍将至关重要。

评论摘要
主要讨论点：关于"vibe编码"（非技术人员通过简单工具和直觉编码）是否能产生有效业务，及其带来的技术债务和安全问题的讨论。 不同观点： • **支持vibe编码的观点**： - vibe编码可以快速验证商业可行性，即使代码质量不高，但能以低成本实现业务模型。例如，CharlieDigital的朋友通过vibe编码在几个月内以极少投资建立了一个可盈利的SaaS业务。 - 历史上，非技术人员通过简单工具（如Excel、Access）开发的系统也曾带来商业成功，尽管这些系统有扩展性和维护问题。 • **反对vibe编码的观点**： - vibe编码通常产生技术债务和安全隐患。评论中提到的案例包括用户数据泄露、黑客攻击和不安全的代码实现。 - 专业开发者不愿意维护vibe编码的模块，因为这些代码不可维护且质量差。 - 代码的质量和可维护性是长期成功的关键，vibe编码往往会带来更多后续工作，特别是当管理层将其视为"最终产品"时。 • **中立或综合观点**： - 所有代码最终都会变成遗留代码，无论是手写还是vibe编码。代码的质量问题不仅仅存在于非技术人员编写的代码中，专业开发者编写的代码也有类似问题。 - 代码的重点应是实现业务需求，而不是追求完美的代码。在成本和效率之间需要做出权衡。例如，一个能完成任务的100K行代码程序可能比一个优雅的30K行代码程序更具经济效益。 - AI和LLM工具可以帮助加速编码过程，但需要工程师的介入以确保代码质量和可维护性。 补充讨论： - **技术与商业的平衡**：vibe编码展示了快速原型设计和验证商业想法的能力，但需要后续专业开发者的介入来确保系统的可扩展性和安全性。 - **代码质量与维护**：讨论中多次提到代码的可维护性和长期质量问题，强调了软件工程需要更多的标准化和责任追究。 - **AI和自动化工具的影响**：AI工具在编码过程中的角色日益重要，但其生成的代码质量和可维护性仍存在争议，特别是在非技术人员的操作下。 争议焦点： - **vibe编码是否值得**：一方认为vibe编码能快速验证商业可行性，另一方认为其带来技术债务和安全隐患，不值得推广。 - **技术债务的容忍度**：一些评论者认为所有代码最终都会变成遗留代码，因此vibe编码的问题并不是独有的；另一方认为应从一开始就注重代码质量以避免后续问题。

本文作者分享了他在管理工作和编程任务中如何提升专注力的经验。他提到，许多好想法往往在洗澡时产生，但因不能一直待在浴室，他不得不接受这种限制。在首次尝试管理岗位时，他因分心于编程而表现不佳，导致管理失误并感到压力和内疚，最终回归个人贡献者角色。 作者引用了Byrne Hobart的观点，指出知识工作者的产出与专注力密切相关：专注度低于10%有被解雇风险，10-50%为普通表现，超过50%则可能成为明星员工。要达到50%以上的专注，必须真正关心工作结果，并避免多任务处理。 作者提供了几种提高专注的策略： 1. **情感投入**：必须对工作结果有直觉和情感上的投资。 2. **单任务处理**：一次只专注于一件事，即使卡住也不轻易切换任务。 3. **规避义务**：限制对他人承诺，确保只有一个主要责任。 通过这些策略，作者学会了更好地管理注意力，以提升工作效率和成果。

Ollama's new app

作者: BUFU | 评分: 531 | 评论数: 54 | 发布时间: 2025-07-30 21:19
文章摘要

Ollama推出了适用于macOS和Windows的新应用程序，用户可以通过该应用下载并与模型聊天，支持文件拖放以处理文本或PDF，并可通过调整设置增加上下文长度以处理更大文档（需更多内存）。新应用还支持多模态功能，可发送图片给兼容模型，如Gemma 3。此外，模型还能处理代码文件以帮助文档编写。用户可在macOS和Windows上下载该应用，纯命令行版本可在Ollama的GitHub页面找到。

评论摘要
主要讨论点：Ollama产品从开发者工具向普通用户工具的转型及其相关技术与市场策略的讨论 不同观点： • **产品定位变化的观察**： - [pentagrama] 观察到Ollama主页从专注于开发者工具（CLI版本）转向普通用户图形界面，尽管在GitHub上仍提供CLI版本。 - [hodgehog11] 认为Ollama专注于本地模型是偶然的，长远来看可能是为了推出基于云模型的API服务，目标是成为企业部署"开放"模型的标准接口。 • **对远程连接功能缺失的批评**： - [coder543] 指出Ollama缺乏连接远程实例的功能，这对于使用更强大计算资源的用户来说是个问题。 • **对Ollama技术实现和开源问题的质疑**： - [underlines] 提到Ollama使用专有fork（llama.cpp）和自定义注册表，可能导致供应商锁定问题。此外，未向上游贡献改进和使用闭源调整引发了GPL合规性的质疑。 - [uyzstvqs] 推荐了Jan AI，认为其支持Linux和多种模型，是一个更好的解决方案。 • **对用户界面简化和功能性的评价**： - [accrual] 赞赏Ollama UI的简洁性和易用性，适合非技术用户快速设置本地LLM，但对高级用户而言可能缺乏暴露高级参数的选项。 - [apitman] 强调需要一个能够轻松切换和查询本地、远程和云模型的界面，Msty目前是他的首选，但也不是开源的。 • **对Linux支持的需求**： - [IceWreck] 质疑为何Ollama没有Linux版本，并询问源代码链接。 - [rihegher] 指出Linux版本目前不可用。 • **对Ollama未来发展方向的担忧**： - [1dom] 表示不理解Ollama向桌面应用转型的决定，认为这与其作为本地LLM后端的定位不符，担忧其可能放弃CLI工具并转向订阅模式。 • **自定义解决方案的建议**： - [thorum] 建议有编程经验的用户自行构建定制化的聊天UI，以便根据个人需求进行灵活调整。 • **对商业化和市场策略的看法**： - [asim] 认为Ollama的UI转型是合理的，有助于渗透企业市场，并指出开源工具在获得风险投资后需要通过企业客户实现盈利。 补充讨论： • **其他工具的推荐**： - [pentagrama] 提到曾测试过LM Studio和Msty，认为它们是优秀的本地LLM应用。 - [apitman] 还在寻找一个能同时查询多个模型的理想聊天界面，列举了几个待测试的工具如Librechat、Open WebUI等。 - [syspec] 推荐Open WebUI，认为其功能丰富且表现出色。 • **具体功能需求的建议**： - [pentagrama] 提到ChatGPT桌面应用中的快捷键（Alt + Space）功能，建议本地LLM应用也可以实现类似功能以便快速提问。 争议焦点： • Ollama的技术实现是否违背了开源精神及其对供应商锁定的潜在影响。 • Ollama产品定位从开发者工具向普通用户工具转型的合理性和长远目标。
