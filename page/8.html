What's New in C# 14: Null-Conditional Assignments

作者: ivankahl | 评分: 162 | 评论数: 33 | 发布时间: 2025-09-15 18:08
文章摘要

C# 14将引入空条件赋值运算符，允许在赋值操作符左侧使用`?.`来简化空值检查。新特性支持对象属性、索引器和复合赋值操作（如`+=`），当左侧为null时会自动跳过赋值。例如原代码`if(config?.Settings!=null){config.Settings.RetryPolicy=new...}`可简化为`config?.Settings?.RetryPolicy=new...`。该特性还能与空合并赋值运算符`??=`结合使用。需要注意的是，当左侧为null时，右侧表达式不会被执行以防止副作用。开发者需安装.NET 10预览版并启用预览语言功能才能使用此特性。

评论摘要
主要讨论点：[C#新特性（左侧null条件赋值操作符`?.=`）的实用性和语言设计方向] 不同观点： • **支持新特性** - 提升语言一致性（与现有`?.`操作符对称） - 减少样板代码（如替代`if`条件语句） - 渐进式增强的灵活性（如[SeasonalEnnui]提到C#从基础到高性能的平滑过渡） - 团队可选择性采用（旧语法仍可用，如[ivankahl]所述） • **反对新特性** - 增加语言复杂性（如[maltalex]指出C#已有120+关键词，远超Java/Go） - 可读性争议（[rkagerer]认为隐式逻辑可能增加理解成本） - 滥用风险（如[ivankahl]和[coneonthefloor]警告过度使用会导致代码混乱） - 实际需求存疑（[bandyaboot]质疑跳过赋值的场景合理性，[_ZeD_]认为行为不够直观） • **中立/务实态度** - 承认简洁性优势但需代码审查约束（[peterashford]） - 对性能优化的期待超过语法糖（[reactordev]） 补充讨论： - **争议焦点**：新特性是否在语言简洁性和复杂性间取得平衡（[maltalex] vs [reactordev]） - **横向对比**：C++因特性泛滥导致代码难懂的警示（[vjvjvjvjghv]） - **替代方案**：显式null处理（[_ZeD_]）与异常抛出的语法可行性（[tekdude]） - **生态系统评价**：部分用户（如[dzonga]）肯定C#整体体验优于Java生态

Tinycolor supply chain attack post-mortem

作者: STRiDEX | 评分: 161 | 评论数: 10 | 发布时间: 2025-09-17 17:18
文章摘要

这篇文章详细描述了@ctrl/tinycolor供应链攻击事件的调查与分析。攻击者通过向共享仓库angulartics2推送恶意GitHub Actions工作流，窃取了具有广泛发布权限的npm令牌，并利用该令牌发布了20个包含恶意代码的包（包括@ctrl/tinycolor）。GitHub和npm安全团队迅速响应，撤销了恶意版本。作者随后发布了干净版本以清除缓存。 文章分析了攻击路径：攻击者利用合作者权限直接推送恶意分支（无需PR审核），工作流自动执行窃取令牌。虽然作者启用了npm来源证明，但因攻击者持有有效令牌而未能阻止攻击。 作者提出了改进方案：计划采用npm可信发布(OIDC)消除静态令牌，加强2FA验证，限制发布权限，并关注pnpm的新安全设置。最后表达了希望npm能提供一键启用可信发布等安全功能的愿望。 事件突显了供应链安全风险，特别是共享仓库和宽泛权限带来的隐患。

评论摘要
主要讨论点：[如何提高 npm 包发布的安全性] 不同观点： • **支持自动化发布但需改进安全措施** - [darkamaul] 提倡使用 Trusted Publishing，生成短期有效的令牌，减少长期令牌的风险 - [mnahkies] 建议在自动化流程中集成 MFA（多因素认证），但目前缺乏简便的实现方式 - [rectang] 提出需要多作者加密签名批准，避免单一作者被攻破导致问题 • **反对自动化发布，主张手动发布** - [zeroq] 认为手动发布更安全，以 BigBank 的严格部署流程为例 - [bikeshaving] 强调大多数 npm 包发布频率低，手动运行 `npm publish` 并启用 2FA 更安全，批评自动化发布的不必要性 • **对现有令牌机制的批评** - [cyberax] 强烈反对静态令牌，认为需要更安全的认证方式，例如 GitHub 作为 AWS 的令牌提供商 • **对 npm 安全现状的担忧与建议** - [waterTanuki] 指出现状不可持续，建议 npm 强制实施 2FA 和 OIDC，尤其是对高下载量的包 - [indigodaddy] 询问是否有工具检测易受攻击的 npm 包，反映对实际解决方案的需求 补充讨论： - **争议焦点**：自动化发布的安全性 vs. 手动发布的可行性 - 支持自动化的一方认为通过技术改进（如短期令牌、MFA）可以解决问题 - 反对的一方认为手动发布更可靠，自动化引入过多风险 - **其他讨论点**： - [drdrey] 对令牌权限范围的疑问（为何一个项目的令牌能发布其他项目的包） - [1oooqooq] 提出关于 CI 作业强制推送历史记录的潜在风险
