One million passports leaked online

作者: jruohonen | 评分: 221 | 评论数: 25 | 发布时间: 2026-06-28 11:22
文章摘要

这篇文章报道了一起大规模身份证件泄露事件：近百万本护照和身份证件被无保护地暴露在公共互联网上，任何人都能通过简单的URL访问，无需密码或加密。这些文件来自欧洲多国，由一家名为Nefos的大麻俱乐部年龄验证平台PuffPal的系统托管。泄露持续数月才被发现。安全研究员警告，这些身份文件对犯罪分子极具价值，可用于身份盗窃和文档欺诈。事件的核心问题是数据安全的严重失职：没有密码保护、没有加密、没有访问控制，将敏感身份信息视同公开相册处理。这反映了企业在收集个人数据时将安全视为次要考虑的严重问题。

评论摘要
主要讨论点：大麻俱乐部护照泄露事件暴露的数据安全问题，包括责任归属、行业普遍性和监管问题 不同观点： • **责任方认定争议**：rkagerer认为使用服务的俱乐部应承担审核供应商的责任，将个人信息视为"有毒有害物质"谨慎处理；而throwaway692675通过亲身经历指出，当发现安全漏洞时，机构往往选择掩盖问题而非通知受影响用户，甚至打击揭露者 • **数据保留必要性质疑**：tartoran和gertrude强调关键问题是"为何验证后仍保留数据"，根据GDPR存储限制原则，年龄验证完成后无需继续保存护照副本，最多保留用户照片即可 • **行业普遍现象**：shmoobadge和stef25指出这并非孤立事件——全球酒店普遍扫描护照，曼谷旅社、钻石商等行业都存在类似问题，未受保护的S3存储桶中曾发现数百本护照 • **技术安全层面**：charles_f总结了四大安全失误（无密码保护、无加密、公开URL访问、无日志监控），认为这是"安全存储反面教材" 补充讨论： 部分评论关注监管方向——monksy呼吁向议员反映年龄验证系统的风险，siar提到eIDAS 2.0可能解决问题；hahahaa指出大麻相关信息与护照结合使问题更严重；elAhmo则讽刺"数据安全警钟"说法过于乐观

Ornith-1.0: Self-scaffolding LLMs for agentic coding

文章摘要

这篇文章介绍了Ornith-1.0，一个专为智能体编码任务设计的开源自我改进模型家族。该系列包含从9B到397B参数的多个版本，基于Gemma 4和Qwen 3.5预训练。 核心创新是自我改进训练框架：模型不仅学习生成解决方案，还学习生成引导解决方案的脚手架（scaffold），通过联合优化两者来发现更好的搜索路径。 性能方面，Ornith-1.0-397B在Terminal-Bench 2.1达到77.5分、SWE-Bench Verified达到82.4分，超越Claude Opus 4.7和同规模开源模型。即使是9B的轻量版本也能匹敌31B-35B规模的大型模型，证明了其在资源受限环境下的强大能力。 训练中采用了三层防护机制来防止奖励欺骗，并使用异步强化学习策略解决长轨迹的离线策略问题。

评论摘要
主要讨论点：关于 Qwen 3.6 MoE 模型在 Agent 任务中的实际表现和训练方法的讨论 不同观点： • **实测表现一般**：SwellJoe 在安全漏洞检测基准测试中发现，该模型仅用基础工具（read/grep/ls）时表现较差，即使加上完整 shell 和 Python 后发现数量翻倍，但整体仍不理想，且不如同为 Qwen 3.6 MoE 的 AgentWorld 版本 • **模型声称值得关注**：Balinares 认为"9B 模型达到 35B 能力"这一声称非常惊人，理应获得更多关注，暗示对官方宣传的性能提升持期待态度 • **训练方法质疑**：nzach 质疑该模型是否只是将"直接回答问题"改为"写代码执行来解答"，如果是这样，可能只是一种高级的提示词优化（prompt optimization），而非真正的模型能力提升 补充讨论：核心争议在于模型的实际效果与宣传声称之间的差距，以及其训练方法的创新性。SwellJoe 的测试数据显示，模型在具备工具创建能力的情况下确实有所改善，但整体表现仍未达到预期水平。

HackerRank open sourced its ATS. My resume scored 90/100. Oh wait 74. No – 88

作者: sambellll | 评分: 980 | 评论数: 110 | 发布时间: 2026-06-29 01:44
文章摘要

这篇文章测试了HackerRank开源的AI简历筛选系统，发现严重的不稳定性问题：同一份简历在相同条件下多次运行，得分从66到99分不等。如果公司设定85分为及格线，作者有65%的概率被淘汰。 问题根源在于：AI在评判"项目质量"等主观维度时极不稳定，而"工作经验"评分虽然稳定但毫无区分度（实习生和资深工程师都得满分）。系统过度依赖开源贡献和个人项目（占65%权重），忽视了真实工作经验的价值。 作者警告：这类AI筛选工具无法真正评估候选人质量，只是在随机过滤，将招聘变成了"运气筛选器"。

评论摘要
主要讨论点：使用LLM（大型语言模型）进行简历筛选的可靠性、公平性和实际效果问题 不同观点： • **技术局限派**：LLM工作基于随机过程，温度参数并非"决定性开关"，只是影响采样分布。使用4B这样的小模型筛选简历如同随机数生成器，65%的失败率说明系统本质上不可靠。同一份简历多次评分结果差异巨大，甚至会凭空"发现"简历中不存在的GSoC经历。 • **实用效率派**：35%的通过率在海量简历场景下已经很优秀。面对每小时100+份申请，没有AI参与时，候选人的机会反而更低——如果不立即申请（使用AI机器人），就会被淹没在人海中。疲惫的招聘人员人工筛选的不一致性可能比LLM更严重。 • **法律风险派**：在欧盟，这种做法很可能因违反反歧视法而违法。AI会产生系统性偏见（如偏好AI生成的代码），且无法像人类那样通过培训来规避偏见。关键是AI偏见可以被系统性证明，将法律风险从"有限/无问题"提升到"可被系统性追责"。 • **公平性质疑派**：系统给有个人项目和开源贡献的申请者加65分，这对有家庭、抚养义务或多份工作的人极不公平，偏向富裕且只专注技术的人群。这种筛选标准存在结构性不公。 补充讨论：多位评论者指出，科技行业缺乏标准化（无正规教育、培训、学徒制要求）是导致这种乱象的根源。简历从来不是成功的良好预测指标，用LLM随机打分只是将已有问题放大。有人讽刺这和"扔掉一半简历因为不想雇佣不幸的人"的笑话本质相同。

这篇文章介绍了vLLM语义路由器的演进：从简单的模型选择工具发展为AI推理的控制平面。路由器不再只是分配请求，而是通过"循环器"(Looper)运行时系统，在保持标准API接口的同时，在后台协调多个模型协作。文章详细介绍了几种循环算法：Confidence(置信度升级)、Ratings(并行质量控制)、ReMoM(广度采样与合成)、Fusion(评审模式)和Workflows(微代理工作流)。核心理念是让模型协作成为开放的服务原语，使单次API调用背后可以运行有界的模型团队协作，从而提升能力、降低成本、增强安全性。

The Return of Aspect Oriented Programming

作者: thomaswc | 评分: 71 | 评论数: 23 | 发布时间: 2026-06-25 22:12
文章摘要

这篇文章讨论了编程中需要兼顾的多个关注点（如正确性、效率、安全性、可维护性等共17项），指出程序员需要同时处理所有这些问题的复杂性。文章介绍了面向切面编程（AOP）的理念——由Gregor Kiczales等人在1990年代中期提出，旨在让程序员能够分别专注于各个关注点，而不是在每行代码中同时考虑所有问题。作者认同AOP的核心思想，但对其具体实现机制"连接点模型"（join point model）持批评态度。文章似乎在探讨AOP的回归及其现代意义。

评论摘要
主要讨论点：AOP（面向切面编程）在现代开发中的价值，以及用LLM作为"织入器"生成代码的可行性 不同观点： • **反对AOP实用性**：简单场景省几分钟，复杂场景（如大批量上传、自定义事务）导致周的调试时间。AOP的关注点分离在复杂情况下会崩溃，代码可读性和可维护性下降，运行时调试困难（nmehner, guybedo） • **强烈反对LLM作为织入器**：非确定性过程修改代码是灾难，LLM只能"有时"正确处理会造成混乱（kstenerud, nmehner） • **谨慎支持改进方向**：核心思想有价值但需重新设计——建议创建从头为AOP和LLM设计的新语言，而非修补现有语言。编译时模式匹配（如Micronaut）优于运行时（jerf, amarant） • **为AspectJ辩护**：AspectJ的连接点模型实际上大部分是编译时静态确定的，只有动态残余延迟到运行时。Pointcut的类型安全状态管理能力强大，适合处理7%的横切关注点代码（w10-1） • **认可应用价值**：AOP在Java/.NET生态和特定框架（JEE、Spring）中持续使用，Effect Systems是2026年处理横切关注点的答案（pjmlp, azkalam, whartung） 补充讨论：有人提出LLM可为每个切面生成语法高亮等工具辅助开发，也有人将LLM工作方式称为"aspective coding"但此前不了解AOP。
