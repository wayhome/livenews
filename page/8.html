Tools: Code Is All You Need

作者: Bogdanp | 评分: 293 | 评论数: 42 | 发布时间: 2025-07-03 10:51
文章摘要

Armin Ronacher在这篇文章中讨论了他对模型上下文协议（MCP）的看法，认为MCP目前存在两大问题：缺乏真正的可组合性和对上下文的过度需求。他通过实验比较了使用GitHub MCP和gh CLI工具完成任务的效率，发现后者更高效。虽然有人认为MCP在特定领域应用中可能有价值，但Ronacher认为，由于依赖推理，MCP在当前形式下始终不如编写代码便捷。 他强调，自动化任务应关注可重复性和可靠性，代码生成是更优选择，因为它允许验证和审查过程。例如，让LLM生成Python代码进行计算，比直接让LLM计算更可靠，因为代码可以被检查和验证。Ronacher总结，在实现自动化时，应优先考虑使用代码，以确保任务能正确且高效地执行。

评论摘要
主要讨论点：大型语言模型（LLM）在实际开发和工具使用中的应用及局限性 不同观点： • pclowes 认为，LLM 当前的主要价值在于填补现有代码和工具之间的空白，其输出需要通过确定性的接口（如类型或数据库主键）进行约束。LLM 类似于3D打印机，在原型设计阶段非常有用，但在可靠性和规模化应用上仍需工程师介入，将推断结果转化为更持久和确定的解决方案。 • simonw 则强调，通过将问题简化为 LLM 可以在沙盒环境中解决的形式，并配置合适的工具和成功标准，可以高效解决问题。这需要高水平的技能和经验，但比手工试错更高效。 • antirez 指出，当前人工智能的状态下，人类在循环中的参与是必要的。LLM 在某些任务上表现出色，但容易陷入局部最优解，需要人类反馈来改进结果，将其作为同事而非完全替代程序员。 • mritchie712 和 pamelafox 分享了使用 MCP（多组件管道）工具的实际经验，认为在处理内部工具或文档不完善的API时，MCP 工具可以更有效地提供上下文和指导，但针对有良好文档的工具，传统的 CLI 或直接 API 调用更为高效。 • victorbjorklund 为 MCP 辩护，认为其在处理内部工具和专有API时具有优势，因为这些工具和API的文档不完善，使用 MCP 可以避免 LLM 需要逆向工程这些系统。 • jumploops 提出，当前我们在新旧工具之间进行无尽的追逐，但随着模型预训练集的扩大，这种区分将逐渐消失。 • elyase 比较了工具调用和代码生成的优劣，指出工具调用提供了约束和节约令牌，而代码生成提供了灵活性，未来模型可能进一步优化这一过程。 • mindwok 认为终端足以满足大部分需求，MCP 服务器只需提供基本的 shell 命令和 curl 即可。 • JyB 认为默认初始提示可以解决上下文需求问题，且 LLM 在使用适当 MCP 功能上表现良好，成本和速度也在不断改善。 • ctrlp 更倾向于让 LLM 编写工具和测试，然后使用这些工具。 • never_inline 指出 MCP 使用 JSON 格式不够表达，相比编程语言如 Python 函数签名，JSON 生成和解析会产生更多令牌，且在复杂逻辑处理上存在局限。 补充讨论： • 关于 MCP 和传统 CLI 工具的效率和适用场景存在争议，部分评论者认为 MCP 在处理复杂和文档不完善的系统时有优势，而其他评论者则认为传统工具在效率和可靠性上更优。 • 关于 LLM 在开发中的角色，存在两种主要观点：LLM 作为辅助工具，需要人类反馈和改进，或 LLM 作为完全替代部分编程工作的工具。 • 关于 JSON 格式在工具调用中的局限性讨论，指出其不够表达复杂逻辑和函数签名的问题。 • 对未来 LLM 和工具集成的发展方向有不同看法，包括模型预训练集的扩展和工具调用的标准化。

评论摘要

文章摘要

文章讨论了人工智能（AI）功能被强制集成到各类软件中，引发了一些用户的抵触情绪。作者指出，许多公司默认启用AI功能，而不是让用户自行选择，导致部分专业人士和用户对这种做法表示不信任和反感。文章列举了Adobe、Microsoft Word、Notion等软件在未征询用户同意的情况下加入AI功能的例子，批评这种做法不仅影响隐私，还牺牲了软件效率。作者认为，这种强制集成不仅让用户感到被强迫，还可能影响教育和职业技能的发展，如编程和写作能力。文章最后提出了对AI广泛集成趋势的质疑，呼吁关注其潜在的负面影响。

评论摘要
主要讨论点：对AI技术及其影响的多种看法 不同观点： • **对AI持批判态度，将其与历史上的技术变革对比：** - [agentultra] 将当前的AI技术与历史上的卢德运动对比，认为历史上对卢德主义者的负面描述是被资本持有者塑造的胜利者叙事。现代对卢德主义者的看法是“反进步”的，但实际上他们争取的是更好的工作条件、废除童工和为被机器取代的工人提供社会保障。当前AI的广泛应用可能导致类似问题，即工人权益受损。 • **对AI过度应用的担忧和反感：** - [nottorp] 认为当前的AI应用大多是为了追逐风口和获取风投资金，且用户不清楚数据流向，导致对AI的不信任。他将AI比喻为增强版的Clippy（微软Office的助手），但与Clippy不同的是，AI通常伴随着额外的收费。 • **对“默认选择加入”模式的批评：** - [Zambyte] 指出，许多公司将“选择加入”改为“选择退出”，这种做法削弱了用户的自主选择权。 • **提倡人工策展而非算法推荐的社交媒体模式：** - [mnky9800n] 提出一个由策展人主导的社交媒体平台，用户可以跟随自己欣赏品味的策展人，而不是依赖算法推荐。这一想法来源于传统的电视节目编排，用户可以创建自己的内容时间表。 • **认为AI最终会找到适合的应用场景：** - [kylecazar] 认为当前AI的广泛应用是由于其流行趋势，但最终AI会留在真正有用的产品和服务中。虽然当前存在对“无AI”产品的需求，但随着市场调整，这种需求可能会减少。 • **反AI运动的提出：** - [hyperbolablabla] 提出了“Nay-I”作为反AI运动的术语。 • **对LLM（大型语言模型）的实际效果和法律责任的质疑：** - [jonhohle] 提到在逆向工程中避免使用LLM，因为LLM会产生错误信息，且其输出可能涉及法律责任问题。 • **对AI需求数据的质疑：** - [SCdF] 质疑是否有数据支持人们真正希望在现有产品中加入AI。 • **对AI取代人类工作的担忧：** - [tensility] 认为随着AI导致更多失业，市场对“无AI”产品的需求会增加，特别是由于一些企业高层的短视决策。 • **个人对AI的反感与担忧：** - [Tistel] 表示自己是卢德主义者，并列举了多项对AI的反感理由，包括失去解决问题的乐趣、失去个人声音、不信任AI输出、以及安全问题和潜在的政治影响。 • **对过度依赖技术的文化批评：** - [momocowcow] 引用了Neil Postman的例子，指出人们难以找到不带巡航控制或电动车窗的汽车，反映了技术过度应用的问题。 • **对软件开发中过度加入AI功能的批评：** - [parsimo2010] 认为当前的问题不在于是否加入AI，而在于软件开发是否经过深思熟虑和充分测试。过度追逐AI功能的软件往往导致用户体验下降。 • **对“无AI”产品的简单选择：** - [billwear] 提到Emacs作为一个“无AI”的简单选择。 • **对未来软件趋势的预测：** - [Apocryphon] 预测未来对“无智能”产品的需求会增加，类似于目前对“非智能”电视的需求。 补充讨论： - 评论中多次提到对AI的不信任和对“无AI”产品的需求，反映出用户对当前技术应用的不满。 - 对历史事件（如卢德运动）的重新解读，提供了对当前技术变革的另一种视角。 - 对软件开发和产品管理的批评，强调了用户对产品质量和体验的关注。
