Overengineered Anchor Links

作者: matser | 评分: 370 | 评论数: 41 | 发布时间: 2025-04-03 14:36
文章摘要

本文讨论了锚链接在页面底部标题无法正确滚动到期望位置的问题，并提出了一系列解决方案。初始的简单修复是通过添加额外 padding 来解决，但这可能不被设计团队接受。接下来，作者提出调整触发线的位置，但这也可能导致标题出现在视口底部，影响用户体验。随后，作者提出通过“虚拟标题”平移触发点，允许根据每个标题位置进行不同调整。进一步优化方案是按比例平移触发点，确保标题可到达且顺序正确。最后的“终极”方案是创建自定义映射函数，通过最小化标题原始位置与虚拟位置的均方误差（MSE）来优化用户体验，同时确保标题间距合理。尽管该方案复杂，但能提升用户满意度。

评论摘要
主要讨论点：网页锚点链接和活跃状态指示器的设计与实现 不同观点： • **支持复杂设计和多活跃状态**：一些用户如 [hoten]、[jer0me] 和 [cmgriffing] 认为可以允许有多个“活跃”状态，尤其是在长内容页面中，多个标题同时高亮可以更好地指示用户当前所处的位置。这种设计在内容足够长时效果较好，但在短内容时可能会显得过于复杂。 • **对复杂设计持怀疑态度**：[LinuxAmbulance] 认为前端的一些复杂设计，例如多活跃状态，增加了不必要的复杂性，尤其是对于简单的滚动操作。这种复杂性可能对后端开发者来说显得过度设计。 • **UX设计目的的讨论**：[type_enthusiast] 指出活跃状态指示器的UX目的是帮助用户在浏览长内容时识别当前所在部分，尤其是在标题不在视野内时。如果使用基于屏幕区域的解决方案，可以避免对标题位置的复杂调整。 • **技术实现问题**：[Y-bar] 和 [inetknght] 关注技术实现，尤其是对于不使用JS的用户，可能完全没有锚点链接功能。此外，[Y-bar] 质疑为什么不直接使用HTML的 `` 元素，而要使用JS事件监听器。 • **设计美学和用户体验**：[crooked-v] 认为这种设计过于奇怪和分散注意力，而 [carlosdp] 和 [nizarmah] 则非常喜欢这种设计，认为它能提高阅读体验和用户参与度。 • **浏览器兼容性和功能性问题**：[robertlagrant] 提到在Firefox桌面版上，即使内容已经滚动到结论部分，仍然会高亮“中间部分”。[Etheryte] 指出在Chrome on iOS上，返回导航可能无法正常工作。[whirlwin] 提到现代浏览器支持文本片段功能，可以直接高亮具体文本部分，从而避免使用锚点。 补充讨论： • **移动端和桌面端的不同需求**：[wrsh07] 认为这种设计在移动端显得新颖有趣，而 [hombre_fatal] 则讨论了在不同设备上解决内容显示问题的具体方案，如不同的页面边距设置。 • **无障碍访问问题**：[inetknght] 提到没有JS的情况下锚点链接无法使用，这可能影响无障碍访问体验。

Declarative Schemas for simpler database management

作者: kiwicopple | 评分: 73 | 评论数: 14 | 发布时间: 2025-04-03 17:02
文章摘要

本文介绍了声明式 schema 如何简化复杂数据库的管理。声明式 schema 将数据库的最终期望状态存储在 `.sql` 文件中，便于集中管理和版本控制。相比直接修改数据库 schema，声明式 schema 具有以下优势：单一管理界面，减少冗余和错误；版本化迁移，确保不同环境中的一致性；简明的代码审查，无需重复复杂迁移脚本。 随着数据库 schema 复杂性增加，传统迁移方法难以维护，因为缺乏单一的整体视图。例如，在 Supabase 中，复杂的 `projects` 表涉及私有表、RLS（行级安全）、视图和触发器，修改时需多步操作，容易导致冲突。 声明式 schema 通过集中管理 schema，简化了开发流程，提高了开发效率。

评论摘要
主要讨论点：关于数据库 schema 管理中声明式与命令式方法的优缺点，以及自动生成迁移脚本的可行性。 不同观点： • [xyzzy_plugh] 认为应该使用声明式 schema，但自动生成迁移脚本不可取。他建议手写迁移脚本并验证 schema 变化，通过测试确保数据库 schema 与预期一致。 • [jackb4040] 指出 SQL 本质上是命令式的语言，无法保证 create_table 等命令的安全执行。他强调声明式 schema 文件（schema file）的重要性，而不是依赖 SQL 命令。 • [webster451] 表示声明式 API 在某些场景下是有价值的，但大多数情况下，程序员需要对变更的控制以获得更好的行为。他认为世界本质上是命令式的，提供更高的控制和可预测性。 • [bartvk] 总结新的方法是直接修改 CREATE TABLE 脚本，工具自动计算差异并应用更改，这消除了新数据库创建和现有数据库更新之间的区别。 • [joshAg] 基于实践指出自动生成迁移脚本可能导致复杂变更（如修改 enum、非空列添加、数据迁移）难以实现，而这些在迁移脚本中更容易处理。 • [neutralino1] 提到 Rails 多年来一直在使用类似的方法，通过维护 schema.sql 文件和历史迁移脚本来管理数据库变更。 • [Guillaume86] 希望有一个类似微软 SSDT 的工具，支持声明式 schema 管理并集成到 IDE 中，提供更多功能如查找引用和错误检查。 • [geocar] 警告自动生成迁移脚本可能会在团队中导致严重问题，特别是在 CI 中自动应用这些迁移，可能会在未来引发难以修复的错误。 • [ucarion] 关心是否可以手动编辑生成的迁移脚本，以实现如 "create index concurrently" 等特定操作。 • [kiwicopple] 提到结合 Postgres Language Server，可以在 IDE 中直接执行语句，提高开发效率。 • [xaas] 提到使用 ZenStack 并计划放弃 supabase，暗示可能有其他工具更适合其需求。 • [oulipo] 将此方法与 Drizzle 进行比较，询问其相似性和差异。 • [mylons] 质疑这种方法相对于直接使用 raw sql 的优势，认为两者非常相似。 • [wmanley] 提供了一个关于 SQLite 声明式 schema 迁移的文章链接，供进一步讨论和参考。 补充讨论： - 自动生成迁移脚本的潜在风险与手动控制之间的权衡。 - 声明式与命令式方法在不同工具和框架中的实现和应用，如 Rails 和 SSDT。 - 具体技术如 Postgres Language Server 和 ZenStack 的实际应用案例和未来发展方向。 - 关于迁移脚本的编辑自由度和特定数据库操作的实现方法。 - 各种工具和方法在实际开发中的优缺点和取舍。
