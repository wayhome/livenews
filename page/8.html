Why agents are bad pair programmers

作者: sh_tomer | 评分: 155 | 评论数: 25 | 发布时间: 2025-06-09 23:36
文章摘要

文章讨论了为何大型语言模型（LLM）代理在结对编程中表现不佳。主要问题在于代理编码速度过快，导致人类难以跟上，从而失去参与感和理解。文章回忆了与高效人类程序员结对时类似的负面体验，如无法跟上编码速度、缺乏沟通和最终发现构建了错误功能等。作者建议，应放弃在编辑器中使用代理模式，转向异步工作流，如GitHub的"Coding Agent"，通过拉取请求审查工作。此外，建议限制代理的编码速度，允许用户暂停代理以提问，并增加UI元素和语音聊天等功能，使代理更像人类伙伴。最终目标是让AI与人类更有效地协作。

评论摘要
主要讨论点：AI在编程中的应用及其优缺点 不同观点： • **AI应作为协作工具而非自主编码工具**：[bsenftner]认为AI应该是辅助工具，帮助批评和优化代码，而不是直接生成大量代码。这种协作方式能让开发者掌控设计过程，避免AI生成的代码风格不一致或不符合期望。 • **AI生成代码常不符合预期**：[Traster]指出，AI生成的代码往往与开发者的设想不符，导致需要花费更多时间去修改和调整。这种过程可能会让开发者觉得不如自己动手写代码更高效。 • **AI应具备更好的协作能力**：[khendron]希望AI能真正实现协作编程，而不是单独生成大量代码。开发者期望一种互动、双向的合作，而不是AI全权负责编码。 • **AI的速度问题**：[throwawayffffas]认为AI的速度不合适，既不够快让开发者专注跟随，也不够慢让开发者能同时处理其他任务。理想的协作模式应是AI能独立工作一段时间再返回结果。 • **AI不适合所有编程场景**：[bluefirebrand]指出，AI不适合所有编程场景，特别是在需要进入编程 flow 状态时，AI的自动建议功能可能打断思路，影响工作效率。 • **客户项目中的AI使用问题**：[rhizome31]关注在客户项目中使用AI的法律和合同问题，特别是涉及代码保密和客户对AI使用的限制。 • **AI工具的不可预测性和不稳定性**：[motbus3]分享了使用AI工具的经验，指出AI有时会执行不可预知或不相关的操作，导致需要频繁审查和修正，降低了整体生产力。 • **AI的过度自信和不够简洁**：[palisade]批评AI工具常常过于冗长且自信，生成不必要的代码和注释，给开发者带来额外负担。 • **寻找更主动的AI工具**：[azhenley]呼吁开发更主动的编码工具，而非仅仅依赖LLM生成大量代码。 • **AI应更具迭代性和反馈能力**：[Onewildgamer]希望AI能更好地处理迭代和反馈，避免过度自信的单向输出，更多地与开发者协作。 • **AI会坚持错误**：[shultays]分享了AI坚持错误观点的例子，即使在提供证据后，AI仍可能坚持错误，显示出其局限性。 • **AI作为参考工具而非工作流**：[ChrisMarshallNY]将AI视为按需参考工具，而非主要工作流，认为AI可以减少查找文档的时间，但不会取代开发者。 • **为AI协作制定协议**：[__MatrixMan__]建议制定一种协议或标记系统，区分人类编写和AI生成的代码，并为AI生成代码提供指导文件，以提高协作效率。 • **定制化提示文档**：[tobyhinloopen]建议使用定制的提示文档，根据个人偏好和修正不断更新，以提高AI生成的代码质量。 补充讨论： - AI在编程中的角色和期望存在较大分歧，部分开发者希望AI能完全自主处理某些任务，而另一些开发者则希望AI仅作为辅助工具。 - 讨论中多次提到AI生成代码的不可预测性和不一致性，反映出对AI工具稳定性和可靠性的担忧。 - 法律和合同问题，以及AI工具的协作模式和速度，也是讨论的重要方面。

CompactLog – Solving CT Scalability with LSM-Trees

作者: Eikon | 评分: 26 | 评论数: 3 | 发布时间: 2025-06-10 10:45
文章摘要

CompactLog是一个实现证书透明度（CT）日志的系统，基于RFC 6962标准，使用LSM树存储（通过SlateDB）来解决传统CT日志的可扩展性问题。它接受X.509证书链和预证书，颁发签名证书时间戳（SCT），维护可加密验证的Merkle树，并提供包含性及一致性证明。其核心设计包括：使用LSM树存储、STH边界版本控制、同步树更新，从而实现零合并延迟（MMD）。系统通过批处理方式收集提交，并在500毫秒内更新Merkle树，确保证书在颁发SCT前已入树。数据存储采用内容可寻址方式，实现证书链的重复数据删除，并通过异步锁保证严格的一致性。当前该项目仍在开发中，不建议用于生产环境。

评论摘要
主要讨论点：CompactLog 作为一种解决证书透明度（CT）可扩展性问题的创新方案，其设计选择和性能表现。 不同观点： • [Eikon] 介绍 CompactLog，强调其通过不改变现有 RFC 6962 API 的方式，解决 CT 日志的可扩展性问题。Eikon 解释了 CompactLog 的几个核心设计：1) 使用基于 LSM 树的存储（如 SlateDB），以解决数据库瓶颈和硬件成本问题；2) 零合并延迟架构，通过在颁发 SCT 之前将证书合并到树中，避免传统方案中的合并延迟问题；3) 智能版本控制策略，显著降低存储开销；4) 在普通硬件上实现高性能，每秒处理数千次链添加。 • [OsrsNeedsf2P] 对 CompactLog 表示赞赏，但也提出了关于具体性能表现的问题，尤其是当数据库增长到 TB 级别时的平均查找时间，并询问是否使用了布隆过滤器来提高查找效率。 补充讨论： • [emmelaich] 对 LSM 树做了简单注释，提供了一个维基百科链接以帮助其他读者理解 LSM 树的概念。 争议焦点： • 目前没有明显的争议，但 [OsrsNeedsf2P] 的提问暗示了对 CompactLog 在超大规模数据情况下查找性能的关注，尤其是 TB 级别数据库的平均查找时间及其优化手段（如是否使用布隆过滤器）。这表明虽然 CompactLog 的设计获得了一定的认可，但其在极端规模下的性能表现仍是一个值得进一步讨论的点。 总结： CompactLog 的设计通过存储层和实现层的创新，在保持现有 API 的前提下，尝试解决 CT 日志的可扩展性问题。其使用 LSM 树存储、零合并延迟架构和智能版本控制策略，在性能和存储效率上取得显著改进。然而，其在超大规模数据下的查找性能仍然是社区关注的一个问题。

What methylene blue can (and can’t) do for the brain

作者: wiry | 评分: 140 | 评论数: 18 | 发布时间: 2025-06-06 14:15
文章摘要

文章主要讨论了亚甲基蓝（methylene blue）作为一种被吹捧为能提升记忆、增加能量、改善情绪的“万能补充剂”是否名副其实。亚甲基蓝是一种已有百年历史的药物，主要用于治疗高铁血红蛋白血症、疟疾和氰化物中毒等。尽管它在体外实验中显示出多种细胞机制效应，如抑制单胺氧化酶（MAO）、帮助线粒体功能和抗氧化，但这些效果不一定能转化为人体内的显著疗效。此外，亚甲基蓝并非完全无害，过量使用可能导致不良反应。因此，文章提醒读者谨慎看待其作为“万能药物”的宣传，强调科学证据需结合具体情境解读。

评论摘要
主要讨论点：Methylene Blue的效用、安全性及其在不同社区中的使用情况 不同观点： • Aurornis认为Methylene Blue在替代医学、生物黑客和益智药论坛中被广泛讨论，但很少有人长期使用。大多数人要么感觉不到效果，要么因副作用或效果消失而停止使用。同时，Selegiline作为另一种受欢迎的药物，也面临类似的情况，且许多人对其机制存在误解。 • ChrisMarshallNY对Methylene Blue作为MAO抑制剂表示担忧，指出MAO抑制剂可能与食物产生严重副作用，甚至危及生命。不过，他认为Methylene Blue可能没有这些特定副作用，并提供了相关文献支持。 • drob518分享了个人使用经验，表示使用Methylene Blue后没有明显效果，且因其染色特性带来不便，但未经历负面健康影响。 • heavyset_go警告Methylene Blue作为强效MAO抑制剂的潜在危险，提到有人因使用其治疗抑郁症而死于严重的血清素综合症。 • cgio提醒使用者注意G6PD缺乏症的风险，Methylene Blue可能引发溶血反应，特别是在某些高风险遗传背景人群中。 • perrygeo指出Methylene Blue缺乏双盲临床研究，认为这可能与该物质无法被专利化有关，质疑临床试验作为真理唯一标准的合理性。 • neuroelectron批评相关文章对Methylene Blue的简化解释，认为其无法得出明确结论，仅表明该物质可能具有益智效果且正被实验。 补充讨论： • kweks提到Methylene Blue在治疗热带鱼的白点病方面有应用。 • HiroshiSan推荐了一个视频链接，认为其对Methylene Blue的解释更佳。 • carbocation指出Methylene Blue在医学上作为血管加压剂的用途，特别是在逆转心肺旁路后的血管麻痹方面。 • mintplant和elcapitan的评论与技术问题和幽默相关，不直接涉及Methylene Blue的讨论。 争议焦点： • Methylene Blue作为MAO抑制剂的安全性及其潜在副作用，特别是血清素综合症的风险。 • 对Methylene Blue效用的怀疑与个人使用经验之间的矛盾。 • 缺乏临床研究与其实际效用之间的讨论。

Go is a good fit for agents

作者: abelanger | 评分: 221 | 评论数: 43 | 发布时间: 2025-06-04 12:14
文章摘要

本文讨论了为何Go语言非常适合用于开发代理（agent）程序。代理通常是长时间运行的进程，具有较高的执行成本，并且常常等待I/O或用户输入。Go语言的并发模型非常适合这种场景，因为它的goroutine非常轻量，可以同时运行大量并发任务，而不会对系统造成过大负担。相比于Node.js或Python，Go在处理CPU密集型任务时表现更佳，因其利用多核CPU的能力更强。此外，Go编译成单一二进制文件，内存占用低，进一步提升了其在代理开发中的优势。总体而言，Go的高并发性、高效的I/O处理和低内存占用使其成为代理程序开发的理想选择。

评论摘要
主要讨论点：代理系统中的编程语言选择，特别是Python、Go和TypeScript等语言在代理系统中的适用性及其优缺点。 不同观点： • [_QrE] 认为Python更适合用于代理系统，因为其在AI领域的库支持非常丰富。尽管执行速度可能比其他语言慢，但在大多数情况下，用户不会在意这一点。同时，他认为代理系统的延迟主要来自于LLM调用，而不是语言本身的执行速度。 • [jeswin] 支持TypeScript作为AI系统的粘合语言，认为其类型系统更具表现力和成熟度。虽然承认Python有广泛的库支持，但指出在取消长时运行任务方面，Python和Node.js都存在困难。 • [pantsforbirds] 提出Elixir和BEAM的组合可能是当前代理系统的最佳选择，因为其并发性和可扩展性非常好，并且可以轻松创建有状态或临时代理。他还计划使用MCP服务器支持多语言代理开发。 • [lunarcave] 认为代理系统大部分时间都在等待LLM响应和执行API调用，因此语言运行时的性能不太重要，JSON序列化和反序列化的性能反而是关键。 • [huqedato] 支持[pantsforbirds]的观点，认为Elixir是代理系统的理想选择。 • [flanked-evergl] 强烈批评Go的类型系统，认为其非常有限，使得Go在许多情况下不适合使用。 • [skybrian] 指出在长时运行过程中，如果进程被杀死，所有工作都会丢失，因此建议将状态序列化到数据库中，但这会增加复杂性。 • [odyssey7] 调侃AI工程师不会使用JavaScript，并提到TensorFlow转向Swift对AI语言多样性的影响。 • [guywithahat] 希望ML领域有更好的并发模型，指出Go在ML方面的库支持不足，而Python和C++也各有其缺点。 • [rgavuliak] 提到一个名为"Modern Data Science in Go"的演讲，认为其中的许多论点具有误导性。 • [InTheArena] 不认为Go适合LLM，并分享了从Go转向Swift的经历，发现Swift在代码生成方面表现更好。 • [jillesvangurk] 认为Go和其他许多语言一样，既不特别好也不特别差。他指出代理系统涉及大量状态管理和异步任务，因此可能需要外部化状态管理，并利用现有的中间件。 • [myzie] 支持原文观点，正在使用Go构建代理系统，认为Go在并发和扩展性方面有优势，但承认Go在ML库支持方面的不足。 • [carsoon] 分享了使用Go构建代理系统的经验，认为通过序列化和去耦合可以实现高效的代理工作流，但指出Go社区在这方面的开发者较少。 • [TeeWEE] 指出Go缺乏像Python那样的自动OpenAOI生成能力，需要依赖反射，不如Python方便。 补充讨论： • 争议的焦点在于不同语言在代理系统中的适用性，特别是Python、Go和TypeScript。Python被广泛认可其库支持，但被批评在取消长时运行任务方面存在困难。Go的类型系统和并发模型受到批评，但其在并发和扩展性方面的优势也被认可。TypeScript的类型系统表现力和成熟度受到赞扬。 • 讨论中多次提到代理系统的性能瓶颈在于LLM调用和JSON序列化/反序列化，而非语言本身的执行速度。 • 有人提出外部化状态管理和利用中间件来解决长时运行代理系统的状态保持问题。
