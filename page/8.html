bootc-image-builder: Build your entire OS from a Containerfile

作者: twelvenmonkeys | 评分: 54 | 评论数: 11 | 发布时间: 2025-06-24 15:01
文章摘要

**bootc-image-builder** 是一个用于创建可启动磁盘镜像的容器工具，特别适用于基于 Fedora/CentOS 或其衍生版的系统。用户需要安装 Podman 来运行该工具，并可使用 QEMU 运行生成的虚拟机或安装介质。该工具通过容器输入构建镜像，建议基于自定义衍生镜像进行构建。 ### 主要步骤： 1. 安装 Podman 和 QEMU。 2. 拉取基础镜像（如 CentOS Stream 9）。 3. 配置 `./config.toml` 文件以注入用户配置。 4. 运行 Podman 命令构建 QCOW2 磁盘镜像。 5. 使用 QEMU 或 `virt-install` 启动虚拟机。 ### 示例命令： ```bash sudo podman run --rm -it --privileged -v ./config.toml:/config.toml:ro -v ./output:/output quay.io/centos-bootc/bootc-image-builder:latest --type qcow2 quay.io/centos-bootc/centos-bootc:stream9 ``` 生成的 QCOW2 文件可通过 QEMU 或 `virt-install` 在 Linux 或 macOS 上运行。工具支持多种架构和镜像类型，需根据具体需求配置相关参数。

评论摘要
主要讨论点：通过容器技术创建和管理操作系统镜像的各种方法和工具 不同观点： • **rgovostes** 对使用Dockerfile生成根文件系统（rootfs）持保留态度，更倾向于使用debootstrap，担心Ubuntu容器镜像可能只适合容器环境而不适合实际硬件。 • **Kudos** 支持使用容器镜像方法，特别是在带有Nvidia显卡的机器上，通过`rpm-ostree`和`systemctl`实现镜像的快速切换和更新。 • **twelvenmonkeys** 提到了一种GUI工具和其它采用“OS as a Container image”理念的项目，如Bazzite，并表示愿意解答相关问题。 • **tmaier** 提到Universal Blue的GitHub模板，提供了一种可复用的镜像模板。 • **tt726259** 推荐使用nixos和nix-build命令来生成系统镜像，并表示自己使用nixos。 • **franga2000** 希望有类似工具用于嵌入式系统镜像的部署，如Raspberry Pi。 • **hardwaresofton** 比较了该项目与linuxkit的使用情况，并询问是否有两者皆有经验的人可以分享。 • **nullify88** 对bootc的进展感到兴奋，认为它比制作coreos发行版更简单，可以从最小基础开始并通过容器注册表更新。 • **indigodaddy** 提出该方法可能比传统的Packer和ISO方法更简单，适用于esxi镜像制作。 补充讨论： • **westurner** 深入讨论了bootc-image-builder是否构建原生容器，以及原生容器是否可以作为VM镜像存储在OCI注册表中。还提到了Nvidia容器工具包和Universal Blue的相关配置。 • **yjftsjthsd-h** 指出容器部署方法可能仅限于Red Hat系列的操作系统（如Fedora、CentOS Stream、RHEL）。 争议焦点： • 对使用Dockerfile与debootstrap方法的适用性和可靠性存在不同看法。 • 不同工具和方法（如nixos、Universal Blue、linuxkit）在实际应用中的优劣和使用情况比较。

Parameterized types in C using the new tag compatibility rule

作者: ingve | 评分: 150 | 评论数: 13 | 发布时间: 2025-06-27 05:31
文章摘要

C23引入了一种新的标签兼容性规则，允许在不同翻译单元中定义的具有相同标签和字段的结构体、联合体和枚举类型相互兼容。这一变化使得使用宏进行类型参数化成为可能。以前，每个翻译单元内的定义都是不同的类型，不兼容。现在可以定义类似如下的参数化宏： ```c #define Slice(T) \ struct Slice##T { \ T *data; \ ptrdiff_t len; \ ptrdiff_t cap; \ } ``` 这允许在需要时动态生成不同元素类型的切片，例如`Slice(int)`或`Slice(float)`。此外，结合C23的`typeof`关键字，可以实现更灵活的动态数组操作，例如通用的`push`宏。然而，这种方法仍有限制，不能用于定义如`Map(K, V)`这样的复杂结构，因为宏参数必须是标识符，且嵌套使用时较为不便。总体而言，这一新规则提供了一种有限的C++模板机制，但仅限于类型参数化，函数操作上仍缺乏泛型支持。

评论摘要
主要讨论点：C语言中宏和泛型的使用以及最近提案对C语言的影响 不同观点： • [支持提案的观点] fuhsnn支持最近的#def #enddef提案，认为这将消除使用反斜杠定义可读宏的需求，使代码模式更加简洁。他期待这一特性能够被纳入C2Y标准。 • [关注其他改进的观点] JonChesterfield对提案本身不感兴趣，但提到另一个相关的改进（n3037.pdf），该改进修复了多次定义具有相同字段的结构体时的不确定行为（UB），认为这是一个很好的修复。 • [与其他语言比较的观点] Arnavion将提案中的泛型方法与Zig语言的泛型类型实现进行比较，指出Zig通过类型构造函数实现泛型，认为这是一种 neat similarity。 • [建议使用C++的观点] IAmLiterallyAB认为如果需要使用类似C++的特性，可以直接使用C++，并指出在C++中可以只使用所需特性，而不必完全转向C++风格。 • [质疑C标准引入模板的观点] wsve质疑为何C标准不直接引入模板，认为如果C代码写作方式是在模仿C++，那不如直接使用C++，没有必要遮遮掩掩。 • [提供实验性资源的观点] uecker提供了一个实验性库和Godbolt链接，供尝试使用泛型类型。 • [技术细节的讨论] rwmj对使用ptrdiff_t而不是size_t作为cap和len类型提出疑问。 • [对提案实际应用的保留意见] unwind认为这是一个有趣的改变，但作为长期C语言使用者，目前没有看到很多实际用例，不过相信可以找到。 • [对C语言泛型机制的不满] o11c提到对C语言中`_Generic`机制的不满，认为其不完善，导致项目编写困难。 • [对提案潜在问题的担忧] Surac担心提案会使不够严谨的代码更容易通过编译。 • [对新类型范式影响的质疑] tialaramex质疑提案是否会使得新的类型范式在C23中无法实现，担心不同名称但结构相同的类型会被认为是相同类型，从而导致类型安全问题。 补充讨论： • 评论中涉及多个提案和技术文档链接，展示了具体技术改进的背景和细节。 • 不同评论者对C语言的改进方向存在争议，主要集中在是否应引入类似C++的模板机制以及这些改进对代码可读性和类型安全的影响。 • 提案的具体实现细节和技术选择（如ptrdiff_t的使用）也引发了一些讨论。
