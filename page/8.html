.gitignore Isn't the only way to ignore files in Git

作者: FergusArgyll | 评分: 564 | 评论数: 38 | 发布时间: 2026-06-18 10:29
文章摘要

Git 有三种级别的文件忽略机制： 1. **`.gitignore`** - 项目级别，随代码一起提交，团队共享 2. **`.git/info/exclude`** - 仓库级别，不提交到 Git，适合个人工作流文件（如个人笔记） 3. **`~/.config/git/ignore`** - 全局级别，影响机器上所有仓库，适合系统文件（如 macOS 的 `.DS_Store`） 可用 `git config --global core.excludesFile` 自定义全局忽略文件位置。使用 `git check-ignore -v <文件名>` 可查看某文件被哪个配置忽略。

评论摘要
主要讨论点：Git忽略文件的多种方式及其适用场景 不同观点： • **全局忽略 vs 项目忽略**：kevincox强调IDE/OS特定文件应放在用户全局配置（~/.config/git/ignore）而非项目.gitignore中，避免污染每个项目；而dofm认为像.DS_Store这类文件若团队有多个Mac用户，放在项目.gitignore更合适 • **文件放置位置的哲学分歧**：rlpb认为在源码树内放构建产物本身就是历史错误，应避免这种设计；但多数评论者接受现状，讨论如何用各种ignore机制管理 • **配置路径规范**：hk1337主张用~/.config/git/作为标准位置而非~/.gitignore_global，保持根目录整洁；wpollock澄清git的"global"实为per-user而非machine-wide 补充讨论： 实用技巧分享：judofyr创建"attic"全局忽略目录存放临时文件；rmunn用"scratch"目录+内部.gitignore避免个人笔记污染；hungryhobbit介绍.gitattributes的-diff功能隐藏package-lock.json等噪音；elyobo分享assume-unchanged别名；leleat提及skip-worktree用于已跟踪文件的本地实验 多位开发者（lmf4lol, stevage）表示从业多年才发现.git/info/exclude，反映该功能知名度不足。Hendrikto批评文章内容过于基础。

The Token Compression Illusion: Why I'm Skeptical of RTK

作者: lackoftactics | 评分: 79 | 评论数: 21 | 发布时间: 2026-06-18 17:37
文章摘要

RTK（一款开发工具）声称能削减60-90%的token使用量，但作者对其持高度怀疑态度，主要原因包括： 1. **虚假节省**：宣传的节省比例仅针对命令行输出，忽略了文件读取、上下文等主要成本来源 2. **静默失败风险**：压缩过程可能丢失关键信息（如错误堆栈），且AI代理无法察觉 3. **缺乏准确性基准**：只展示token节省数据，未提供任务成功率等关键指标 4. **架构脆弱**：依赖外部层解析CLI输出，一旦工具更新格式就会失效 5. **非核心产品**：本质上是个功能特性，主流CLI工具可轻易集成类似能力 结论：为了虚荣指标而牺牲可靠性和语义完整性，不值得冒生产环境风险。

评论摘要
主要讨论点：围绕 RTK 等“LLM压缩/省token工具”是否值得使用，争论集中在节省成本、准确性与可维护性之间的权衡，以及缺乏统一评测标准的问题。 不同观点： • 质疑派：认为这类工具像“魔法盒子/蛇油”，宣传省token却缺少准确率基准；作者担心管理层只看成本，推动把各种命令都包进RTK，开发者变成“念咒”而非工程化验证。 • 支持派：认为“省下的token就是省下的token”，有人报告节省数万到数百万token、每条命令快约3秒；并强调RTK设计上过滤失败会回退原始输出，不应静默喂给代理错误内容。 • 折中务实派：承认文章对可维护性、命令输出变更导致规则失效的担忧成立，但认为现实中大公司/团队有成本压力，会自己分叉、基准测试、校验质量；对个人开发者未必必要。 • 效果有限派：指出RTK只压缩命令输出，不压缩消息主体；长时间编码会话中，真正占上下文大头的往往不是tool calls，因此整体节省可能有限。 • 评测派：认为核心问题不是RTK本身，而是“没有办法衡量AI到底有没有变好”；许多团队只能凭感觉，需要更小规模可复用的harness/eval体系。 • 替代方案派：建议直接用CLI自带的精简参数、JSON输出，或用本地小模型做代理过滤；也有人更看好只压缩JSON空白/冗余这类更保守方案。 补充讨论： • 争议焦点在于：RTK是否真的保持正确性、实际节省是否显著、以及规则/正则式方案在工具输出变化后是否可靠。 • 讨论中有人提到代理因RTK输出而绕圈，也有人表示通过告知代理压缩格式或设置 `RTK_DISABLE=1` 可规避截断与误解问题。

CS 6120是康奈尔大学Adrian Sampson开设的博士级编译器课程，现已开放为自学在线课程。课程涵盖中间表示、数据流、经典优化等通用编译器主题，以及并行化、即时编译、垃圾回收等研究性话题。学习内容包括阅读论文和使用LLVM及专为该课程设计的教育性中间表示(Bril)完成开源编程任务。课程共14个单元，涉及程序表示、局部与全局分析优化、SSA、循环优化、别名分析、内存管理、动态编译、并发并行等核心主题。所有材料开源在GitHub上，学习者可按自己节奏完成，无需遵守截止日期。

评论摘要
主要讨论点：关于CS 6120高级编译器在线课程的评价与相关讨论 不同观点： • **课程内容质量争议**：titzer认为动态编译器部分过度关注trace compilation（这是一个已被多次放弃的死胡同），应更多讲解类型反馈、推测优化、去优化以及快速编译器和分层等更重要的概念。但整体上认可课程质量。 • **课程定位质疑**：j2kun质疑课程的"高级"定位，认为死代码消除、数据流分析、支配树分析、SSA形式等主题应该属于编译器基础课程内容，而非高级课程。 • **学习需求**：awesomeMilou询问是否有基础编译器的自学课程作为前置学习，xqb64想了解本课程与Nora Sandler的"Writing a C compiler"的对比和收益差异。 • **正面评价**：ken47和flash1对课程表示感谢，认可课程材料质量。 补充讨论：tomhow提供了该课程历史讨论记录（2020-2024年三次在HN上的讨论）；sincerely询问是否有其他类似的大学级自学课程；GL26提到Rust编译器使用机器学习算法的话题；gaze对某位技术人物的现状感到好奇。
