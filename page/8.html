Chimpanzees act as 'engineers', choosing materials to make tools

作者: docmechanic | 评分: 85 | 评论数: 21 | 发布时间: 2025-03-25 14:39
文章摘要

研究发现，坦桑尼亚贡贝溪国家公园的黑猩猩在制作工具时展现出一定的工程学能力，它们故意选择具有特定机械和结构特性的植物来制作更具弹性的工具，用于钓取白蚁。研究团队使用便携式机械测试器比较了黑猩猩使用的植物材料和未使用的材料，发现未使用的植物材料要坚硬得多。黑猩猩选择的植物种类，如*Grewia spp.*，在远至5000公里外的黑猩猩群体中也用于制作工具，显示出这种基础的工程选择可能在黑猩猩的工具文化中根深蒂固。该研究揭示了黑猩猩对材料特性的直觉理解，并为研究人类工具使用能力的演化提供了重要启示。

评论摘要
主要讨论点：关于黑猩猩使用工具的研究及其文化传承 不同观点： • [mmooss] 强调研究的两个被忽视的方面：1. 早期人类祖先使用工具的证据较少，但通过功能框架可以推测我们祖先可能使用过易腐材料的工具。2. 文化传承的重要性，文化传承与基因遗传不同，具有更大的灵活性和适应性。 • [amelius] 认为黑猩猩做出的决定具有不确定性，因此更适合与炼金术士或深度学习研究人员相比，暗示黑猩猩的工具使用并不总是精确或科学的。 • [oh_my_goodness] 表示黑猩猩和工程师有很多相似的行为模式，认为这是众所周知的事情，暗示对将黑猩猩与工程师相比并不感到意外。 • [alecco] 批评标题为点击诱饵，认为研究仅仅表明黑猩猩倾向于选择更灵活的材料来获取蚂蚁，认为夸大了研究的发现。 补充讨论： • [upghost] 和 [Avicebron] 以幽默的方式回应，前者将黑猩猩与工程师和管理者的行为作类比，后者开玩笑地表示如果黑猩猩能当工程师，自己就去追求更高级的职称。 • [ggambetta] 和 [bell-cot] 以轻松的语气评论，前者称黑猩猩为“原始码农”，后者暗示未来可能会看到关于蚂蚁或植物作为“工程师”的报道。 • [3np] 和 [mofunnyman] 提供实际研究链接和存档链接，试图将讨论引导回实际研究内容。 • [KineticLensman] 以幽默方式提出选择水果时的权衡，虽然与主题不完全相关，但增添了讨论的趣味性。 • [docmechanic] 引用了研究的具体发现，重申黑猩猩在制作工具时有选择性的行为。 • [westurner] 提供了维基百科链接，介绍了非人类灵长类动物使用工具的情况，试图提供更多背景信息。 争议焦点： • 研究发现的实际意义与媒体标题的准确性存在争议。一些评论认为媒体夸大了研究发现，将黑猩猩的行为与人类工程师相比是不恰当的。

Just Write a Test for It

作者: dmit | 评分: 59 | 评论数: 14 | 发布时间: 2025-03-26 09:54
文章摘要

这篇文章讲述了作者在Rust项目中处理数据库迁移时遇到的一个问题：在已有数据的表中添加一个NOT NULL列但没有提供DEFAULT值，导致部署出错。尽管初始测试套件未能发现此问题，作者没有止步于简单修复，而是借助Rust生态中的`sqlparser`库，编写了一个集成测试来自动检测类似问题。作者赞赏Rust激励其追求更高质量的解决方案，并详细描述了如何利用`sqlparser`实现该检测功能。最终，作者成功预防了未来可能出现的类似错误。

评论摘要
主要讨论点：数据库迁移测试的有效性及复杂性，特别是关于预填充数据库与空数据库的测试方法，以及使用SQL解析工具的合理性。 不同观点： • **karparov**：认为现有的测试套件有漏洞，因为测试总是从一个空数据库开始，应用所有迁移后再运行测试代码。建议使用预填充数据库进行测试，以捕获更广泛的问题，而不仅仅是检查非空或默认值。 • **kobzol（博文作者）**：澄清博文的重点并不是解决数据库迁移的所有问题，而是展示在Rust中完成特定任务的简便性。他提到提供一个好的错误信息也是有价值的，即使有更通用的解决方案。 • **dreghgh**：反对博文中的方法，认为应该在运行迁移之前将数据放入数据库架构中，这样可以捕捉到各种未预见的错误，而不是仅仅解决特定类型的问题。 • **kleiba**：认为博文内容令人失望，主要讲述了在Rust中解析SQL查询的惊喜，没有太大的阅读价值。 • **switch007**：提到一个相关的工具——"squawk"，这是一个专注于迁移的PostgreSQL代码检查工具，可能可以解决此类问题。 • **lbreakjai**：分享了在之前工作中实现类似Neon分支的经验，每个MR都会克隆"public"架构到一个特定MR的架构中，然后运行迁移和集成测试，这样可以捕获一些在实际运行中才会出现的错误。 • **nikolayasdf123**：认为测试过于复杂，比要测试的DDL语句本身还要复杂，这种现象是人们不愿意写测试的原因之一，建议让测试变得更简单和易于维护。 • **hardwaresofton**：建议开发一个通用的SQL代码检查工具，类似于sqlint，但更专注于语义而非语法。 • **conradludgate**：推荐使用Neon的branching功能，可以在不影响生产数据和性能的情况下运行迁移测试，并提到未来可能会开发更多迁移工具。 • **bilalq**：支持使用Neon这样的支持分支的无服务器数据库进行迁移测试，可以轻松地在每个PR更改时运行，测试迁移是否对真实数据安全。 • **null_deref**：对文章中的Rust生态系统没有经过CR就直接链接PR的做法表示疑问，质疑这是否是大型语言标准库的标准做法。 • **bobnamob**：担心引入一个SQL解析器作为依赖会增加攻击面和漏洞风险，特别是在当前供应链攻击频发的情况下。 • **earnestinger**：指出文章没有说明SQL解析器是针对哪种数据库（如PostgreSQL或MySQL），建议提供更具体的信息。 • **bsaul**：作为非Rust开发者，对Rust代码中的复杂生命周期注释和长泛型类型感到困惑，询问这种代码在实践中是否常见。 补充讨论： - 测试复杂性与实用性的平衡是争议的一个焦点，部分评论者认为复杂的测试不如简单易读的测试有用。 - 使用预填充数据库进行测试的建议得到了部分支持，尤其是结合Neon分支功能的具体实现方法。 - 引入SQL解析工具作为依赖的合理性及其潜在的安全风险也被提出并讨论。

Plain – a web framework for building products with Python

作者: brylie | 评分: 286 | 评论数: 48 | 发布时间: 2025-03-29 03:55
文章摘要

Plain 是一个基于 Python 的 web 框架，是 Django 的分支，旨在引入新想法并保持 Python 生态系统的成熟模式。它支持通过单条命令进行本地开发并快速上线，包含多个独立可选的包，如处理 URL、视图、模板、表单、缓存、电子邮件、会话、后台任务和 JSON API 等功能。Plain 还提供认证包，支持传统和现代登录方式，如密码和 OAuth。其管理包允许自定义管理后台和功能标志控制，开发包优化本地开发体验，前端包则集成现代工具如 Tailwind 和 HTMX。Plain 被设计用于构建新业务、内部工具或个人项目。

It's five grand a day to miss our S3 exit

文章摘要

文章主要介绍了37signals公司计划在今年6月30日之前将数据从AWS S3迁移到自建数据中心的Pure Storage系统，以节省每年近150万美元的成本。目前，他们存储了18PB数据，并获得了AWS提供的免费60天数据迁出窗口，避免了高额的迁出费用。尽管数据传输需要约三周时间，但若未按时完成，他们将面临每天5000美元的额外支出。整体来看，使用Pure Storage在五年内可节省约500万美元，硬件成本为150万美元，支持和保修费用不到100万美元。

评论摘要
主要讨论点：云服务与自建基础设施的成本与效益分析 不同观点： • **云服务的成本合理性**： - **ifightcrime**：云服务一直以来都比较贵，但你为便利和速度付费。当公司发展到一定规模时，成本问题会变得突出。可以通过前期架构和供应商选择来缓解，但这不是新问题。 - **rvz**：云服务成本累积迅速，特别是当团队低估成本时。AWS等云供应商的定价机制会导致即使在少量使用情况下也会产生高额费用。 • **自建基础设施的成本效益**： - **comrade1234**：通过对比硬件和托管成本与AWS价格，发现自建基础设施的回本期约为三年。AWS会根据硬件成本调整价格。 - **npalli**：通过建模发现，从S3迁移到自建设施的回本期可能长达18年，即使考虑折旧周期仍需8年。初始硬件成本和后续运营费用较高。 • **功能与需求匹配**： - **andrewaylett**：AWS S3提供更多功能和弹性，如果不需要这些功能，可以避免额外费用。但需要确保支付的费用与需求匹配。 - **otterley**：建议使用S3智能分层以降低成本，特别是对于访问频率不高的数据。 • **具体实施与技术选择**： - **theptip**：Basecamp作为一个自建基础设施的典型例子，因其非风投支持且工程能力强，租赁云服务的灵活性需求较低。 - **albert_e**：逐步迁移数据并删除S3上的数据可以提前开始节省成本，前提是数据消费者能够适应。 - **Axsuul**：担心自建基础设施的硬件故障处理不如云服务优雅，可能导致严重停机。 • **技术细节与系统性能**： - **siscia**：关注新系统的具体技术指标，如每GB成本、读写延迟、并发支持和最大吞吐量。 补充讨论： • **供应商反应**： - **tgtweak**：提到如果告知云供应商离开，有时会给予一定回扣，令人感到不满。 • **硬件选择**： - **DeathArrow**：认为使用SSD是浪费，建议使用传统硬盘和RAID结构，质疑AWS是否仅使用SSD。 争议焦点： • 云服务的高成本与自建基础设施的长期效益之间的权衡。 • 不同技术选择（如SSD vs HDD，S3 vs 自建存储）在成本和性能上的优劣。 总结：评论中对云服务与自建基础设施的成本效益有明显分歧，主要围绕具体需求、功能匹配、技术选择和实施细节展开讨论。
