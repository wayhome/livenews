Agentic coding deserves more than a chat box bolted onto VS Code

作者: evanklem2004 | 评分: 82 | 评论数: 17 | 发布时间: 2026-06-17 15:26
文章摘要

Polypore是一个开源的代理桌面IDE，具有以下特点： **核心功能**：语言无关、系统无关，采用可停靠面板设计，用户可自由拆分、重排和关闭面板。内置8个面板涵盖Claude/Codex终端、实时预览、Monaco编辑器、差异对比、终端、调试、知识库和代理管理。 **架构特色**：基于Tauri 2 + React 18构建，每个面板都是沙箱化的iframe。内置MCP服务器提供22+工具，让AI代理可直接控制IDE功能（调试、内存、验证、任务等）。 **安全机制**：秘钥存储在系统密钥环，代理通过句柄间接访问，模型永不接触明文。 **扩展性**：提供SDK支持第三方插件开发，内置15个Polyflow技能命令覆盖完整开发流程。

评论摘要
主要讨论点：一个新的"代理式编码"IDE产品引发的质疑和争议 不同观点： • **产品定位不清晰**：多位评论者（kylemaxwell、avree）指出产品缺乏明确的差异化说明，只是将现有功能重新包装，缺乏原创性，描述过于模糊 • **不需要IDE集成**：mcscxv强调只需要独立的shell工具，不希望与Xcode、Android Studio等现有IDE强制集成，更喜欢像git那样的并行工作方式 • **AI过度集成的疲劳**：at-fates-hands表达了对VS Code中AI功能泛滥的不满，认为各种AI提示已成为干扰而非帮助 • **营销方式问题**：grim_io和mccoyb提到产品视频编辑奇怪（涉及蘑菇），devin指出作者发布了大量AI生成的项目描述并遭到差评 • **讽刺态度**：blitzar和theplumber用讽刺口吻质疑产品价值（"给我600亿我也能做个聊天框"） 补充讨论：部分用户要求提供截图而非视频（joshka），建议编写人工撰写的README（ricardobeat），还有人指出VS Code已有类似的agents功能（injidup）。整体氛围偏向怀疑和批评。

TREX: An AI code reviewer that runs your code

作者: dakshgupta | 评分: 55 | 评论数: 6 | 发布时间: 2026-06-17 15:29
文章摘要

Greptile构建了TREX（Test, Run, Execute）——一个能在代码审查中实际执行代码的AI工具。传统代码审查只能静态分析代码文本，无法发现运行时bugs（如UI回归、竞态条件等）。 TREX最初是独立产品，但效果不佳。后来改为与Greptile审查器共享上下文：主审查器作为orchestrator识别问题，为每个问题并行启动独立的TREX子代理，既避免了上下文重复浪费，又保持了各自的处理能力。 TREX输出多模态artifacts（截图、日志、API追踪、视频等）而非简单文字描述，让审查者能直观验证测试结果。例如动画改动会自动生成视频展示实际效果，UI功能会处理认证并截图，所有输出都可追溯验证。

评论摘要
主要讨论点：关于代码沙箱和AI代理测试能力的技术讨论 不同观点： • **技术倡导者观点（deet）**：强调沙箱环境显著提升AI代理编码质量。通过在隔离环境中运行完整技术栈（Docker容器、数据库、队列等）并进行端到端测试（如模拟视频通话），AI代理能够像真实用户一样测试复杂产品。认为这种方法填补了代码修改反馈循环的重大漏洞，建议怀疑者亲自尝试后再下结论。 • **UI/UX关注者观点（yuchi）**：偏离主题，关注网站设计本身。认为网站设计精美，移动端header的固定效果优秀，唯一建议是字体稍大一些。 • **实践质疑者观点（ygouzerh）**：提出实际应用问题——当项目依赖大量外部服务（S3存储桶、密钥管理器、第三方API等）时，这种沙箱方案如何运作？暗示对复杂依赖场景的可行性存疑。 • **安全担忧者观点（Elzair）**：从安全角度质疑，想知道这个系统多久会被攻破（pwn），暗示对沙箱安全性持怀疑态度。 补充讨论：评论展现了典型的技术讨论模式——从技术可行性、实际应用挑战到安全风险的多维度审视，但缺乏深入的技术细节交流。

Scaling opencomputer from 1 VM to 1 million sandboxes

作者: iacguy | 评分: 12 | 评论数: 0 | 发布时间: 2026-06-18 02:32
文章摘要

OpenComputer 最初在单个 Azure 区域运行，但很快遇到 300 CPU 的配额上限。为了突破单区域限制，他们将系统重构为"单元"(cell)架构：每个单元包含精简的控制平面和工作节点，可独立部署到任意云区域。通过 Cloudflare Workers + D1 构建的边缘注册中心负责全局调度，根据容量将新沙箱请求路由到最合适的单元，并通过心跳机制追踪各单元状态。这种设计让他们可以跨多个云服务商和区域无限扩展，最终实现了百万级沙箱容量。添加新容量只需部署新单元，而非迁移整个系统。

Bringing down my ZSH load times from ~3.1s to ~230ms

作者: speckx | 评分: 39 | 评论数: 11 | 发布时间: 2026-06-17 17:37
文章摘要

作者将 ZSH 启动时间从 3.1 秒优化到 230 毫秒。主要方法：1) 使用 `zprof` 模块分析性能瓶颈，发现 `conda` 和 `nvm` 占用 2.2 秒；2) 用 `fnm` 替换 `nvm`，延迟加载 `conda`；3) 硬编码 `brew --prefix` 路径节省 60 毫秒；4) 通过 `typeset -U fpath` 去除重复路径，避免 `compinit` 每次重建补全缓存，节省 430 毫秒。最后还升级了终端提示符，增加了目录聚焦、错误码显示和执行计时等功能。

评论摘要
主要讨论点：shell 启动速度优化，特别是 zsh 性能问题及替代方案 不同观点： • **Fish shell 支持者**：kstrauser 和 lanycrost 认为 fish 开箱即用，配置复杂时仍保持 85-168ms 的启动速度，语法更清晰，tab 补全更好，无需放弃 bash 兼容性 • **Zsh 优化派**：adrian_b 认为合理配置的 zsh 可达 20-60ms，TFA 文章中的最终速度仍然偏慢；basetensucks 和 jauntywundrkind 通过 zsh-snap、zimfw 等框架和性能分析工具成功优化 • **版本管理工具问题**：AprilArcus 和 ricardobeat 指出 nvm/fnm 是常见性能瓶颈；tecoholic 和 ricardobeat 推荐使用 mise 替代，可达微秒级启动 • **Nix 用户**：throwwwll 表示使用 nix 从未遇到此类问题 补充讨论：vivzkestrel 提出无关的 UI/UX 建议（博客链接失效、缺少文章归档页面）。核心争议在于是否应该切换 shell（fish）还是优化现有配置（zsh + 工具链替换），以及不同方案的性能基准差异。

文章提出了"切斯特顿的栅栏"概念的延伸——"切斯特顿的缺口"。前者告诫我们：在拆除看似无用的东西前，先理解它存在的原因。后者则描述了开源软件中的新现象：人们看到项目"缺少"某个功能，就直接提交大量代码补上，却不先询问维护者为什么没有添加该功能。作者指出，这些PR虽然代码质量不差，但往往是不必要的——维护者没有添加某功能，通常有充分理由。低成本的代码生成能力让这个问题更加突出。作者呼吁：如果想知道为什么某功能不存在，先问，而不是直接"建栅栏"。

评论摘要
主要讨论点：AI时代开源项目的价值、代码维护成本以及如何评估代码的必要性 不同观点： • **AI降低开源价值论** [jerf]：AI可以快速生成代码，使得许多开源项目失去评估价值——自己定制化prompt比评估现有项目更快，功能复杂的HTTP代理等项目优势不再明显 • **极简主义与专注性** [ChrisMarshallNY]：最佳实践是用最少代码完成工作，保持类型和API的纯粹职责范围，必要时创建新类型而非扩展现有功能，设计中"少即是多" • **PR是长期负担** [ndr引用Hipp]：Pull request是"免费小狗"——贡献者提供的"免费"功能实际要求维护者承担25年的文档、测试、维护责任，这是沉重的道德义务而非真正免费 • **重建优于修补** [JKCalhoun]：采用"Milito草地"方法——推倒重来，从零开始重建，只保留确实必要的部分，最终会有更少但理由明确的"围栏" • **PR作为灵感源** [arjie/joshka]：PR是展示可能性的原型而非成品；维护者可将其作为灵感自行实现；软件与实体围栏不同，PR不会改变现实直到被接受部署 补充讨论：[kps] 强调文档化的重要性——应该用注释和集成测试说明每段代码存在的理由，避免"切斯特顿围栏"困境
