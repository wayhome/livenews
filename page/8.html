ProofOfThought: LLM-based reasoning using Z3 theorem proving

作者: barthelomew | 评分: 206 | 评论数: 20 | 发布时间: 2025-10-04 18:34
文章摘要

这篇文章介绍了DebarghaG开发的ProofOfThought项目，这是一个结合大型语言模型(LLM)和Z3定理证明器的神经符号程序合成系统。主要特点包括： 1. 提供高级Python API和底层DSL两种接口 2. 支持单次查询和批量评估两种使用模式 3. 已在NeurIPS 2024的Sys2Reasoning研讨会上发表论文 4. 开源项目，含57星和5个分支 5. 需要安装z3-solver、openai等依赖库 该系统旨在实现可解释的稳健推理，示例展示了如何使用它回答政治相关问题并评估准确率。

评论摘要
主要讨论点：[LLM与形式化逻辑工具的结合及其效果] 不同观点： • **支持观点**： - Gemini 2.5 Pro结合Python的sympy工具解决方程问题，展现了LLM与严谨工具结合的强大效果（chrchr）。 - 使用Prolog和Datalog语法生成逻辑程序效果良好，可能与训练集中的翻译示例丰富有关（tannhaeuser）。 - 通过LEAN验证业务政策的内部知识库一致性，尤其是在法律/财务合规领域具有潜力（LASR）。 - 逻辑和概率逻辑推理引擎结合LLM可以提高结论的正确性（nextos）。 - LLM生成结构化DSL并通过Z3验证，确保答案的可证明性（sytse）。 • **质疑观点**： - LLM输出通过形式逻辑模型可能导致“垃圾进，垃圾出”的问题（0xWTF）。 - LLM生成的逻辑规则可能存在不准确性或不合逻辑的问题，51%的误报率表明LLM在逻辑建模上表现不佳（ivanbakel）。 - LLM无法解决某些需要逻辑约束的问题，因此需要转向其他方法（nakamoto_damacy）。 • **技术改进建议**： - 使用OpenAI API的结构化输出功能可以减少幻觉问题（sigmoid10）。 - 在README中添加DSL示例以便更好地理解（tonerow）。 补充讨论： - **争议焦点**：LLM与形式化逻辑工具结合的实际效果和可靠性（如51%误报率）。 - **其他讨论点**： - LLM决策过程的可解释性问题（everdrive）。 - Rices定理对LLM输出的限制（dehsge）。 - 未来研究方向：引入符号化和代理作为“裁判”的潜力（nextos）。

1Password CLI Vulnerability (2023)

作者: manchicken | 评分: 100 | 评论数: 13 | 发布时间: 2025-10-05 03:01
文章摘要

这篇文档披露了1Password CLI工具中的一个安全漏洞。作者于2023年10月通过BugCrowd进行了负责任的漏洞报告，并于2024年1月获准公开披露。该漏洞允许在用户解锁保险库后，任何从父进程派生的子进程都能保持活动会话访问权限，存在供应链攻击风险。作者提供了两个可能的攻击路径（IDE扩展和npm包管理），并附上了PoC证明代码，展示了恶意代码如何利用该漏洞窃取保险库数据。建议用户注意相关风险。

评论摘要
主要讨论点：[1Password CLI 的安全性问题和权限管理] 不同观点： • **安全性担忧** - [troad] 认为 CLI 访问权限过于宽泛，缺乏细粒度控制，违反了最小权限原则，尤其在供应链攻击频繁的背景下存在风险。 - [starburst] 强调密码管理器的核心是保护数据加密，即使代码被执行，也应限制明文数据的暴露范围，而非一次性解锁全部凭证。 • **漏洞的严重性争议** - [TheDong] 认为如果攻击者已获得用户级别的任意代码执行权限，其他安全措施（如 keylog 或二进制替换）同样会失效，因此 CLI 权限问题并非关键漏洞。 - [krater23] 支持类似观点，认为一旦机器被入侵，任何本地存储的密码都不安全，建议完全避免在机器上存储重要密码。 • **功能改进建议** - [starburst] 提出 CLI 应像 SSH Agent 一样按程序请求逐个授权，而非全局解锁。 - [oulipo2] 询问当前 `op` CLI 的默认行为是否仍存在此问题，暗示对现状的关注。 • **其他相关讨论** - [e40] 质疑漏洞披露时间过长（2年），可能影响修复效率。 - [woadwarrior01] 批评 1Password 的技术栈（Electron）导致性能问题，引发对产品整体质量的担忧。 补充讨论： - **社区反应**：[lucasqueiroz] 表示将禁用 CLI 集成，反映部分用户对安全问题的实际应对。 - **技术对比**：[hollow-moe] 将 CLI 权限问题类比为 `sudo` 的临时密码豁免，引发对权限模型的深入思考。 - **争议焦点**：是否 CLI 权限设计是真正的漏洞（如 [starburst] 强调的“最小暴露”），还是用户机器被入侵后的必然结果（如 [TheDong] 的“ airtight hatchway”理论）。

How to inject knowledge efficiently? Knowledge infusion scaling law for LLMs

作者: PaulHoule | 评分: 74 | 评论数: 5 | 发布时间: 2025-10-04 17:18
文章摘要

这篇论文研究了大型语言模型（LLM）预训练中的知识注入问题。研究发现： 1. 存在"临界崩溃点"：当注入的领域知识超过某个阈值时，模型的知识保留能力会急剧下降； 2. 规模相关性：这个崩溃点与模型规模存在比例关系。 基于这些发现，作者提出了一个"知识注入比例定律"，可以通过分析较小模型来预测大型LLM的最优知识注入量。实验验证了该定律在不同模型规模和训练预算下的有效性和普适性。这项研究为解决LLM在专业领域知识获取与通用知识保留之间的平衡问题提供了理论依据。

评论摘要
主要讨论点：[论文中关于在预训练中注入过多“知识”导致模型性能下降的发现及其解释] 不同观点： • [mtokarski]认为论文的解释可能有些夸大。他指出问题不在于知识密度本身，而在于知识注入的方式。论文中使用的是模板化的Wikidata三元组（如“X是Y的首都”），这种低熵、高度重复的分布破坏了语言的多样性，扭曲了token统计。在实际预训练或领域适应场景中，知识应以更丰富、更多样的上下文出现。关键教训不是“不要添加太多领域数据”，而是“不要过度代表任何单一格式或狭窄的句法模式”。 • [itissid]提出使用结构化提示（如编码会话中的架构设计文档、领域知识如UML、状态图等）来微调模型的可能性，并将其转化为工具调用的指令遵循。他认为目前团队管理的是一个相当复杂的LLM层，而MCPs和指令遵循依赖于一次性上下文窗口管理。 • [adsharma]希望作者能计算模型大小（参数数量）与在内存崩溃发生前可以容纳的三元组数量之间的关系图。他认为很难将知识注入的频率映射到对“一个4B参数的模型可以容纳多少知识”的实际理解。 • [daft_pink]对将此类信息注入LLM的成本表示好奇，尤其是考虑到训练LLM的高昂费用。他想知道如果要获得一个领域特定的LLM，额外的训练成本是多少。 补充讨论：[gdiamos]对领域特定数据的内容是否会影响结果表示好奇，并对在Hacker News上看到ML论文表示高兴。争议焦点主要集中在知识注入的方式（模板化vs.多样化）以及其对模型性能的实际影响上。
