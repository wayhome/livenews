Flame – BBS and MUD

作者: shakna | 评分: 47 | 评论数: 7 | 发布时间: 2025-03-31 12:54
文章摘要

Flame是一个公告板系统（BBS），虽然通过MUD（多用户迷宫游戏）形式实现，但它并非MUD、IRC或聊天室。对不同的人来说，Flame具有多种功能：可以 silent 访问，作为社交替代，灵魂探索之地或虚拟派对区。要连接Flame，可通过telnet访问flame.ucc.gu.uwa.edu.au的4242端口；若受防火墙限制，可使用flame-tunnel.ucc.gu.uwa.edu.au的任意端口。Flame还运行gopher服务器和web服务器。它始于1990年，最初是远程访问BBS，1991年出现在《Your Computer》杂志上，1992年转变为MUD，并保留了原BBS的电话连接。

评论摘要
主要讨论点：围绕MUD（多用户地牢）和类似技术的讨论，包括其历史、应用场景以及技术细节。 不同观点： • [01100011] 认为该系统类似于MUD，并联想到80年代太平洋西北地区的Citadel BBSes。提出由于天气原因，该地区技术发展蓬勃。 • [JKCalhoun] 提到在MacOS上需要通过命令行安装telnet，并分享了连接特定MUD服务器的命令。还设想了一个在MUD中会面的场景，用于 cyberpunk 风格的故事创作。 • [khimaros] 表达了对过去MUD（如GhostMOO）热闹时期的怀念，并询问是否有其他人有相同经历。 • [upghost] 赞赏MUD作为一个在线社交空间的概念，并希望这种形式能更常见。 • [captaincrunch] 表示对讨论内容感到困惑，似乎没有完全理解话题。 • [kaiyuanzg] 关注Flame的实用性，尤其是作为集群管理工具，并与其他解决方案（如Cloudify和OpenStack）进行比较，期待其未来的发展。 补充讨论： • MUD作为一种早期多人在线互动形式，具有历史和文化意义，特别是在80-90年代的技术社区中。 • 讨论中涉及到技术细节，如在现代系统上安装telnet以访问MUD。 • 对MUD的怀旧情感与对其未来发展的期待形成对比，反映出对不同技术时代的社会空间变迁的思考。 • 争议的焦点可能在于对MUD及其现代应用的认知差异，[captaincrunch] 的困惑反映了部分人对该话题的不熟悉。

Search could be so much better. And I don't mean chatbots with web access

文章摘要

文章介绍了一种新型搜索引擎MatterRank，其核心特点是让用户能够控制搜索结果的排序，而不仅仅是让算法猜测用户的需求。传统的搜索引擎通过关键词、链接和各种信号来猜测用户意图，而MatterRank允许用户用自己的语言描述如何排序结果，提供更个性化和精准的搜索体验。这不是一个简单的聊天机器人或智能自动补全工具，而是一种全新的搜索方式，让用户决定什么最重要。

Ploopy Classic 2 open source trackball

作者: namanyayg | 评分: 114 | 评论数: 12 | 发布时间: 2025-03-30 07:15
文章摘要

The Classic 2是经典款的升级版，售价144加元起，保留了原版大部分设计，同时在几个关键方面进行了改进。它将原版的USB-B接口升级为更现代的USB-C接口，提高了连接的便捷性和耐用性。针对原版滚轮在快速转动时出现的异常问题，Classic 2采用了更强大的Raspberry RP2040微控制器，使滚轮响应更快、更精准。外观和手感与原版保持一致，但优化了3D打印的便利性，去除了不必要的支撑结构。硬件方面，依然采用高性能的PMW-3360光学传感器和D2LS-21开关。Classic 2设计继续保持开源，提供完整文档，但无法从原版升级。原版将下架，但会继续提供维护支持。

Hacking the call records of millions of Americans

作者: voxadam | 评分: 117 | 评论数: 10 | 发布时间: 2025-04-02 16:37
文章摘要

文章揭示了Verizon Call Filter iOS应用中的一个安全漏洞，该漏洞允许攻击者获取Verizon无线用户的通话记录，包括来电号码和时间戳，而无需设备入侵或密码猜测。漏洞的关键在于，应用在请求通话记录时，服务器未验证请求的电话号码是否与登录用户匹配。攻击者只需修改请求中的电话号码，即可获取其他用户的通话历史。 此漏洞不仅侵犯隐私，还可能对特定人群如家暴幸存者、执法人员和公众人物构成安全威胁。通话元数据可用于重建个人日常活动、识别频繁联系人，并推断私人关系。时间戳与其他信息结合，可能暴露个人行踪和私密联系方式。 技术上，问题出在应用使用的一个未适当验证用户身份的API端点。该漏洞可能影响所有或绝大多数Verizon用户，因其Call Filter服务可能默认开启。这一漏洞不仅导致大量用户信息泄露，还可能被用作实时监控工具。

评论摘要
主要讨论点：Verizon电话号码及通话记录数据泄露的安全漏洞及其影响 不同观点： • [twalkz] 指出Verizon的服务器未能验证请求的电话号码是否与登录用户绑定，导致用户可以修改请求的电话号码，获取与其他Verizon用户相关的数据。他认为这是Verizon的一个重大疏忽，并希望公司在披露漏洞时能告知此前是否有其他人利用过该漏洞。 • [dotty-] 提到Verizon Call Filter应用使用了一个看起来非常内部化的域名来查询用户通话记录，暗示这种命名方式可能反映出安全措施不到位。 • [devmtk] 对Verizon这样的大公司出现这种低级错误感到震惊，质疑公司的渗透测试和安全责任人，并担心是否有其他数据泄露的风险。 • [adxl] 提出疑问，如何才能像发现此类漏洞的人一样找到新的安全漏洞，并建议通过逆向工程应用或监控请求来寻找漏洞，以参与漏洞赏金计划。 • [vivzkestrel] 好奇如何能发现这些漏洞，询问是否需要全职从事这种工作，或者是否可以通过系统化的方式找到未被发现的漏洞。 • [chatmasta] 指出通话记录通常会打印在每月的账单上，并可能包含短信记录，认为这些数据可能已经广泛泄露到公司内外部的多个系统中，暗示该漏洞只是冰山一角。 • [grg0] 质疑为什么这一事件没有成为新闻头条，认为政府通常夸大外国势力对公民的干扰，但对公司漏洞却视而不见，暗示大公司对媒体和国会的控制。 • [MPSFounder] 希望Verizon为这一漏洞支付高额漏洞赏金（>20k），否则认为做正确的事没有得到应有的回报，并担心公司不会从中吸取教训。 • [metalman] 认为这种行为不应被称为“黑客行为”，因为电话记录的访问没有正式的程序或规则，并暗示政府在利用电话记录进行监视活动，质疑为什么还要 bother（费心）去测试这种显而易见的漏洞。 • [coolThingsFirst] 对如何拦截移动应用的API调用感到好奇，可能是在询问技术细节。 补充讨论： • 争议焦点在于Verizon作为一个大公司，为什么会出现如此低级的安全漏洞，以及公司应如何处理和回应此类事件。 • 有人关注漏洞发现的过程和技术细节，另一些人则对漏洞的社会和政治影响感兴趣。 • 讨论中还涉及到对漏洞赏金计划的期望以及对大公司和媒体关系的批评。

A 6-Hour Time-Stretched Version of Brian Eno's Music for Airports

作者: vinhnx | 评分: 188 | 评论数: 28 | 发布时间: 2025-03-30 00:50
文章摘要

Declarative Schemas for simpler database management

文章摘要

本文介绍了声明式 schema 如何简化复杂数据库的管理。声明式 schema 将数据库的最终期望状态存储在 `.sql` 文件中，便于集中管理和版本控制。相比直接修改数据库 schema，声明式 schema 具有以下优势：单一管理界面，减少冗余和错误；版本化迁移，确保不同环境中的一致性；简明的代码审查，无需重复复杂迁移脚本。 随着数据库 schema 复杂性增加，传统迁移方法难以维护，因为缺乏单一的整体视图。例如，在 Supabase 中，复杂的 `projects` 表涉及私有表、RLS（行级安全）、视图和触发器，修改时需多步操作，容易导致冲突。 声明式 schema 通过集中管理 schema，简化了开发流程，提高了开发效率。

主要讨论点：数据库迁移和声明式 schema 管理的优缺点 不同观点： • [支持声明式 schema，但反对自动生成迁移]：xyzzy_plugh 认为声明式 schema 是有必要的，但不应自动生成迁移，因为这可能带来问题。他建议手动编写迁移并测试，以确保 schema 变更符合预期。 • [有限支持声明式 API]：webster451 认为声明式 API 在某些场景下非常强大，但并不适用于所有情况。他认为程序员对变更的控制能带来更好的结果，并指出 Kubernetes 等工具虽然提供声明式基础设施，但实现非常复杂且容易出错。 • [支持自动生成迁移]：bartvk 总结了一种新方法，即通过修改 CREATE TABLE 语句并自动生成差异迁移。他认为这种方法简化了数据库变更的管理。 • [Rails 的做法更好]：neutralino1 认为 Rails 已经实现了更好的方案，通过保持迁移和 schema.sql 文件的同步，方便测试和数据库重建。 • [需要 IDE 支持的声明式管理]：Guillaume86 希望有一个类似微软 SSDT 的工具，用于 Postgres，提供声明式 schema 管理、错误检查和更好的开发体验。 • [自动生成迁移可能导致问题]：joshAg 认为自动生成迁移可能导致一些复杂的变更（如 enum 变更、数据迁移）难以处理，建议手动编写迁移以确保灵活性。 • [关注手动编辑自动生成迁移的能力]：ucarion 关心是否可以手动编辑自动生成的迁移，以实现更复杂的操作，如并发创建索引。 • [结合 IDE 工具提升开发体验]：kiwicopple 提到结合 Postgres Language Server，可以在 IDE 中直接执行 SQL 语句，提高开发效率。 • [自动生成迁移的风险]：geocar 警告自动生成迁移可能在团队中引入严重错误，导致长期问题。 • [其他工具]：xaas 提到使用 ZenStack 并指出其未来版本将不再依赖 Supabase。 • [质疑新方法的价值]：mylons 质疑新方法相比原始 SQL 的优势，认为差别不大。 • [提供相关参考资料]：wmanley 提供了关于 SQLite 声明式迁移的文章链接，并披露自己是该文章的合著者。 补充讨论： • 争议的焦点在于自动生成迁移的可靠性和灵活性，以及声明式 schema 管理的优缺点。 • 不同开发者对声明式和命令式方法的偏好，以及对工具支持和开发体验的需求各不相同。 • 实际应用中，如何平衡自动化和手动控制的比例，以及如何确保数据库迁移的安全性和可维护性，是重要的讨论点。
