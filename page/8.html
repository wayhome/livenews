Show HN: Tsbro – TypeScript for the browser, no build step

作者: stagas | 评分: 31 | 评论数: 9 | 发布时间: 2025-07-21 11:56
文章摘要

"tsbro" 是一个让 TypeScript 直接在浏览器中运行的工具，无需构建步骤或工具链。它通过同步 XHR 绕过浏览器的模块导入系统，使用 `swc wasm` 转译代码并转换模块格式，从而实现 TypeScript 文件的直接运行。用户只需在 HTML 文件中导入 "tsbro" 并配置脚本，即可在浏览器中使用 TypeScript 编写和运行代码，甚至可以与远程包（如 Preact）一起使用。然而，该工具目前存在一些问题，如 TypeScript 无法找到模块类型，以及由于转译和 eval 导致的堆栈跟踪难以阅读。为解决类型问题，建议创建一个 `env.d.ts` 文件。该项目采用 MIT 许可。

评论摘要
主要讨论点：在浏览器中处理 TypeScript 编译的最佳方式 不同观点： • spankalee 认为使用同步 XHR 进行 TypeScript 编译性能较差，建议异步遍历 import 图，使用如 es-module-lexer 或 TypeScript 的轻量解析器解析导入标识符，然后通过编译器主机将文件传递给编译器。他提到 Lit 团队的 Playground Elements 采用了这种方法。 • altbdoor 分享了他之前的尝试，使用 service worker 拦截 TS 请求并用 sucrase 编译成 JS。但他指出 sucrase 似乎已不再维护。 • simulo 提到了 TypeScript 5.8 的 --erasableSyntaxOnly 选项，认为这可以简化工具链，因为只需 TypeScript 编译器本身。 • catapart 表示正在开发一个用于浏览器测试的自定义元素，并考虑使用 swc 来避免预先编译。他认为这个库可能比自己维护的方案更好。 • Tade0 提出是否可以在 service worker 中进行编译，拦截 *.ts 请求并在 worker 中编译。他提到曾考虑将 TS 代码发送到专用服务器进行编译，但认为这种方法过于复杂，且指出 swc WASM 包过大。 • vendiddy 表达了对浏览器功能日益复杂的担忧，认为应保持浏览器的简单性，并专注于提升 WebAssembly 的性能，以支持多种语言且保持 API 表面积小。 • ohnoesjmr 询问是否可以将 TypeScript 编译器嵌入到使用 v8 引擎的 C++ 项目中，以便动态编译代码，质疑是否存在一个 API 能够接收并返回 TS 文件字符串。 • nikisweeting 提到了 esm.sh/tsx，质疑这与讨论的方案有何不同。 补充讨论： • 讨论中涉及了多种工具和库，如 sucrase、swc 和 esm.sh/tsx，以及它们在 TypeScript 编译中的应用和限制。 • 参与者对不同方案的复杂性、性能和可维护性提出了不同看法，特别是关于 service worker 和 WASM 的使用。 • 争议的焦点在于如何在性能、复杂性和可维护性之间取得平衡，以及浏览器是否应承担更多编译职责。

There is no memory safety without thread safety

文章摘要

本文讨论了“内存安全”的定义及其局限性，指出通常所指的内存安全语言能防止使用已释放内存或越界访问内存。然而，作者认为这种细分（如内存安全与线程安全）并不实用，程序真正需要的是“无未定义行为”。文章通过Go语言的例子展示了数据竞争如何导致内存安全问题，例如Go程序中因接口类型和并发操作不当引发的崩溃。相比之下，Java通过严密的并发内存模型避免了类似问题，确保即使在数据竞争情况下也不会出现解引用无效指针的错误。作者提出，确保并发程序安全有两种方法：一是限制编译器优化以保证多字值的一致性（如Java、C#），二是通过强类型系统排除数据竞争（如Rust、Swift）。Go未能完全实现这两种方法，因此并非严格意义上的内存安全语言。
