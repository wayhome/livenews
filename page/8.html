作者: mitchbob | 评分: 99 | 评论数: 20 | 发布时间: 2025-08-04 00:41
文章摘要

2015年5月，作者与其他外科医生在波士顿市中心参加为期16小时的强制性计算机培训，学习新上线的Epic医疗软件系统。该系统耗资16亿美元，旨在使医院技术现代化。尽管Epic在美国广泛应用，但其复杂性令医生们感到困扰，尤其是面对众多相似选项卡和功能时。尽管作者早期对技术适应良好，但随着系统全面实施，医生们发现其增加了工作负担，导致工作与生活失衡和职业倦怠。2016年一项研究显示，医生每看一小时病人，需花两小时处理计算机工作，这导致许多医生感到压力和抑郁。Epic本应提高效率，但实际上增加了医生的工作量，引发广泛不满。

Modern Node.js Patterns

作者: eustoria | 评分: 820 | 评论数: 56 | 发布时间: 2025-08-03 19:16
文章摘要

Node.js经历了重大变革，从以回调和CommonJS为主的旧模式转变为更现代化、基于标准的开发体验。主要变化包括： 1. **模块系统**：ES模块（ESM）取代CommonJS成为新标准。ESM支持更好的工具链和静态分析，且与浏览器标准一致。现代Node.js使用`node:`前缀明确内建模块，避免依赖冲突。 2. **顶层Await**：无需再用async函数包裹，简化了异步初始化，使代码更直观。 3. **内建Web API**：减少外部依赖，如原生支持Fetch API，无需axios或node-fetch。还内置了超时和取消支持，简化了错误处理。 4. **AbortController**：提供标准化方式取消操作，处理超时或用户发起的取消请求。 这些变化提升了开发体验，减少了外部依赖，使Node.js在2025年更具现代化和一致性。

评论摘要
主要讨论点：Node.js 新功能及其与竞争者（如Deno、Bun.js）的比较 不同观点： • **支持Node.js新功能的观点**： - Simonw 提到 Node.js 引入类似 Deno 的文件系统和网络访问限制功能，认为这是非常好的改进。 - Farkin88 强调 Node 核心内置 fetch 和 AbortController，减少了对 axios 和 node-fetch 等外部库的依赖，显著优化了 Lambda 函数的启动时间和包大小。 - Vinnymac 指出 Node.js 现在可以自行处理文本样式，不再需要依赖 Chalk 或 picocolors 等库。 - Tyleo 提到 Node 内置的测试和文件监控功能，认为可以不再依赖 Jest 和 Nodemon。 - Gabrielpoca118 和 Wildpeaks 强调 TypeScript 支持的改进，尤其是 `erasableSyntaxOnly` 选项的引入，简化了开发流程。 • **对ESM模块的争议**： - Bilalq 认为 ESM 的采用过程困难重重，尤其是许多包现在只发布 ESM 版本，导致兼容性问题。这与 Python 2 到 3 的过渡类似，开发者感到困扰。 - 相反，Gabrielpoca118 和 Wildpeaks 认为 TypeScript 和 ESM 支持的改进显著降低了复杂性，提升了开发体验。 • **对Node.js与竞争者（Deno、Bun.js）的讨论**： - Prmph 和 Rco8786 认为 Node.js 在竞争压力下（如 Deno 和 Bun.js）不断改进，提供了更强的竞争力，这对于 JavaScript 运行时的整体发展是有益的。 - Fleebee 提到尝试制作独立可执行文件时遇到的问题，生成的二进制文件过大（110MB），并指出这是一个值得注意的缺点。 补充讨论： • **对新功能的实际应用体验**： - Bravesoul2 提到在多语言开发环境中，新功能的发现往往是偶然的，很难像单一语言（如C#）那样系统地学习和跟进。 • **对文档和示例的批评**： - Jmull 指出 "Modern Event Handling with AsyncIterators" 部分的示例代码有缺失，认为这可能是复制粘贴错误，并对互联网上越来越多的AI生成内容表示不满。 • **工具推荐**： - Theozero 推荐使用 Varlock.dev 作为更现代的 .env 文件处理方式，提供类型安全和验证功能。 • **对Node.js复兴的感慨**： - Growbell_social 对 Node.js 重新在技术社区（如 Hacker News）获得关注表示欣慰，提到在2012-2018年间 Node.js 曾被频繁 dismiss。 争议焦点： - ESM 模块的过渡引发兼容性问题，部分开发者认为改进不够平滑，尤其是对老项目和依赖库的影响较大。

AWS European Sovereign Cloud to be operated by EU citizens

作者: pulisse | 评分: 57 | 评论数: 17 | 发布时间: 2025-08-04 20:44
文章摘要

AWS宣布推出欧洲主权云（European Sovereign Cloud），这是一个独立运营的云服务，专为满足欧洲高度监管行业和公共部门客户的数字主权需求而设计。该云服务完全独立，不依赖非欧盟基础设施，仅由居住在欧盟的欧盟公民运营，确保符合欧盟法律。AWS还调整了招聘要求，规定只有欧盟公民才能操作该主权云，以增强数据安全和主权保障。此举旨在为客户提供更多选择和控制，不影响AWS的创新能力和网络安全保护。AWS计划在2025年底前推出该服务，并已投资78亿欧元支持该项目至2040年。更多信息可在aws.eu查询。

评论摘要
主要讨论点：AWS宣布推出的“欧洲主权云”是否真正具备主权性，以及其在法律和运营上的独立性。 不同观点： • **对AWS“主权云”主权性的质疑**： - **dabedee**：AWS声称其云服务“主权”且“独立”，但实际上仍由美国公司拥有，受美国法律（包括CLOUD Act）约束。底层技术、专利和公司控制权仍在美国，定价和服务细节不明，如何处理美国法律与“主权”承诺之间的冲突也不清楚。 - **greatgib**：只要该服务由美国公司运营和拥有，就受美国法律和政府意志的约束，不可能真正主权。有人可能会以“误导性营销声明”在欧洲法律下起诉AWS。很多公司可能会借此使用AWS，并假装使用了一个安全的主权云。 - **Teocali**：只要一名亚马逊的美国员工能访问这个云，它就不是主权的。 • **对AWS主权云实际控制的讨论**： - **adamcharnock**：亚马逊显然不会放弃对AWS EU的控制权，因此需要包装这个声明。我的公司与AWS竞争，因此我有偏见，但我不认为这是 cynical 的看法。 - **__turbobrew__**：只要子公司的主要所有权不在欧盟，我就不认为它是主权的。主权意味着所有权和控制权完全在欧盟境内。 - **robertclaus**：如果欧洲不希望依赖外部公司进行关键基础设施建设，那么这种做法只是建立了一个完全依赖亚马逊的壳公司。 • **对技术独立性和安全性的关注**： - **ManBeardPc**：如果开发不在欧盟进行，那就不算主权。这是由美国公司控制的专有解决方案。如果他们切断支持，欧盟云将无法获得安全更新或修复。 - **fimdomeio**：对这种做法的法律要求和实际保护感到困惑，是否有情报机构的聘用规范？ • **对CLOUD Act影响的讨论**： - **gitremote**：CLOUD Act允许美国政府通过传票获取美国公司持有的数字数据，不论数据存储在哪里。 - **tzs**：CLOUD Act有两个主要条款，一个涉及MLATs（相互法律协助条约），另一个涉及传票和搜查令。很多人忽视了MLATs的作用，而只关注数字文档的管辖权问题。实际上，数字文档的处理方式应该与物理文档一致。 补充讨论： • **对招聘政策的讨论**： - **phillipseamore**：AWS最近因为缺乏公民身份而撤销了招聘offer，这可能暗示了最近的决定。 • **对全球公司多样性的关注**： - **tensor**：这最终还是支持了一家美国公司。世界需要多样化的公司，而不仅仅是几家美国公司的子公司。 • **对美国政府和企业是否会信任类似方案的讨论**： - **Havoc**：虽然有一些实质内容，但这仍然是一个美国超大规模提供商。美国政府和企业是否会信任华为的类似方案？我认为不会。 争议焦点：AWS“欧洲主权云”是否真正具备主权性，特别是在法律管辖、技术控制和运营独立性方面。
