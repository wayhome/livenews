文章讨论了在实际计算机环境中计算矩阵特征分解时可能出现的误差，引用了Wilkinson（1965）的分析，指出由于浮点运算的特性，计算结果可能与理论值有出入，甚至在处理非对称矩阵时，实际计算的特征值可能与理论上的实特征值不一致。文章还描述了作者的同事在使用R语言进行多变量正态分布模拟时遇到的再现性问题，尽管使用了`set.seed()`来控制随机数生成器状态，但在不同机器上仍得到不同的结果。经过调查，发现问题并非出在`set.seed()`或`MASS::mvrnorm()`函数本身，而是由于浮点运算的固有误差导致的。这提醒我们，计算机运算并不总是符合预期，浮点运算的特性可能引发不易察觉的错误。

Show HN: SQLite JavaScript - extend your database with JavaScript

作者: marcobambini | 评分: 124 | 评论数: 16 | 发布时间: 2025-05-22 13:25
文章摘要

SQLite-JS 是一个将 JavaScript 功能引入 SQLite 的扩展，允许用户通过 JavaScript 创建自定义的 SQLite 函数、聚合函数、窗口函数和排序规则。用户可以编写 JavaScript 代码来处理单个行（标量函数）、多行聚合计算（聚合函数）、窗口数据操作（窗口函数）以及自定义排序（排序规则）。该扩展提供了多个创建函数的接口，如 `js_create_scalar`、`js_create_aggregate` 和 `js_create_window`，并支持直接在 SQLite 中执行 JavaScript 代码。通过这些功能，用户可以在 SQLite 数据库中实现更灵活和强大的数据操作。示例包括通过 JavaScript 计算年龄或中位数等。

评论摘要
主要讨论点： decibel（分贝）在不同工程领域中的应用及其优缺点 不同观点： • **支持分贝的实用性**： - **简化计算**：分贝可以将乘法转化为加法，方便处理增益和衰减（例如，滤波器损耗和放大器增益可以直接相加）。 - **处理极大极小值**：分贝可以方便地表示和处理数量级差异很大的数值，避免使用科学计数法或处理复杂的浮点运算。 - **多种工程领域应用**：在RF工程、音频工程、雷达等领域，分贝提供了一个统一的标度，便于比较不同数量级的信号。 - **历史惯性**：尽管分贝有其复杂性，但由于历史原因，它已成为行业标准，改变的成本高。 • **批评分贝的复杂性和不一致性**： - **单位不明确**：分贝的定义和使用在不同上下文中存在不一致，特别是相对和绝对测量的混用（例如dBm、dB(SPL)、dB(A)等）。 - **电压与功率的混淆**：分贝在处理电压与功率时采用不同的比率（电压是20倍的对数，功率是10倍的对数），容易引起混淆。 - **主观校准**：例如音频VU表的校准基于主观模型，历史上由BBC和一些美国公司定义，缺乏客观标准。 • **对分贝的矛盾态度**： - **理解难度**：尽管分贝在工程中广泛使用，但其概念和应用对新手来说可能过于复杂，尤其是不同单位之间的转换和使用。 - **历史遗留问题**：尽管认识到分贝的某些缺点，但工程师们因历史原因仍继续使用它，类似于软件工程中的某些历史遗留协议和工具。 补充讨论： • **具体应用实例**： - 分贝在音频工程中用于表示动态范围和音量变化，在RF工程中用于表示信号链路的增益和衰减。 - 分贝在图像处理领域也有应用，例如峰值信噪比（PSNR）使用分贝作为单位。 • **争议焦点**： - 分贝的定义和表示不一致，尤其是相对单位和绝对单位的混用，导致理解和使用上的困难。 - 分贝在电压与功率计算中的不同处理方式增加了混淆的可能性。 总结： 分贝作为一个广泛应用于工程领域的单位，其优点在于简化计算和处理极大极小值，但其定义和使用上的不一致以及复杂性也引发了争议。在实际应用中，工程师们往往因历史惯性和实用性继续使用分贝，尽管其概念上存在一定的混淆和不一致。

在2025年，使用iPhone播放自己的音乐变得困难，除非订阅Apple的服务或面对诸多限制。作者因对Apple Music和iCloud音乐库的限制感到沮丧，决定自行开发音乐播放器。该播放器具有全文搜索、iCloud支持和本地优先体验等功能。苹果自带应用如Files app无法提供良好的音乐管理体验，而许多第三方应用则采用订阅模式。作者最初尝试使用React Native开发，但因文件系统访问和iCloud目录遍历问题而放弃，最终选择SwiftUI。SwiftUI提供了更直接的控制和现代化的开发体验，使得数据同步和音乐播放功能得以顺利实现。作者强调，iPhone作为通用计算机，用户应能通过代码实现自定义功能。

主要讨论点：自制音乐播放器的各种实践与观点 不同观点： • prell和strunz等人分享了自己创建的本地音乐播放器项目，强调了对本地音乐库和离线播放的需求。prell的播放器是一个单页的HTML/JS应用，而strunz提供了项目的镜像和GitHub链接。 • tschumacher介绍了自己的网络应用，能够记住播放位置并在不同设备间切换，解决了YouTube Music等服务在这方面的不足。 • duxup对现有音乐应用的界面设计表示不满，认为开发新的音乐播放器值得赞赏。 • selkin对Swift中的async/await机制提出质疑，认为在复杂异步代码中，代码流和并发性更难理解，可能增加维护成本。 • johng回忆了过去在DOS时代播放音乐的经历，表达了对现代设备上播放本地音乐困难的无奈。 • nzoschke分享了自己的音乐播放器项目，使用Spotify Web Playback SDK和MP3 HTTP服务器，认为web技术足够成熟，可以实现自定义播放器。 • slmjkdbtl使用Music.app和Finder进行音乐管理，虽然对目前的解决方案不甚满意，但尚未找到更好的替代方案。 • NSUserDefaults介绍了自己的类似项目，并提到使用ffmpeg的优点，以及Apple API在文件格式支持上的局限性。 补充讨论： • koakuma-chan和shubkukreti也提到了自己的播放器项目，但没有深入讨论技术细节。 • mg提出是否可以在HTML中构建播放器，以避免安装任何软件，并提到在iOS和Android设备上通过HTML播放音视频的可能性。 • dvh分享了自己使用Lazarus和mplayer制作音乐播放器的经历。 • sandreas认为音乐播放器是经常被重新发明的轮子，并提到自己过去尝试编写跨平台播放器的经历，特别指出了耳机控制功能的重要性。他还介绍了自己目前使用的多种应用组合来满足音乐和有声书的需求。 争议焦点： • 不同开发者对使用Swift的async/await机制在代码可维护性和并发处理上的优缺点存在争议。 • 对现有音乐应用的不满主要集中在界面设计和功能限制上，如设备间切换和播放位置记忆等问题。 总结： 参与者们分享了各自在自制音乐播放器方面的经验和项目，讨论了不同技术选择和实现方法，反映了在当前流媒体时代下对本地音乐管理和自定义播放器需求的持续存在。
