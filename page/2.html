CAPTCHAs can still detect AI agents

作者: timshell | 评分: 50 | 评论数: 16 | 发布时间: 2026-05-29 15:57
文章摘要

这篇文章介绍了一项关于CAPTCHA验证码的研究。虽然AI现在能够识别验证码图像（如交通灯、消防栓），但研究发现AI和人类完成验证码的**过程**存在显著差异。研究团队开发了CogCAPTCHA30测试系统，包含30项认知任务，发现AI虽然能达到与人类相似的任务表现（输出），但在点击模式、方向变化等过程特征上明显不同。研究提出"过程图灵测试"概念，并发现前沿大模型（GPT、Claude、Gemini）反而不如小型模型（Qwen、Centaur）更接近人类行为模式。这表明AI能力提升不等于更像人类，基于过程差异仍可有效区分人类和AI代理。

评论摘要
主要讨论点：AI能否通过验证码（CAPTCHA），以及验证码系统的有效性和用户体验问题 不同观点： • **验证码已失效论**：验证码主要用于惩罚不允许追踪的用户，而非真正防止机器人。利用专用工具和代理的攻击者能轻松绕过，反而是隐私浏览器和VPN用户被拦截（andy99, Cider9986, technotarek指出CloudFlare已无法阻挡垃圾信息） • **验证码仍有效论**：LLM无法学习、不适合试错，人类可创造无限种验证码形式，因此验证码永远能战胜LLM（yrds96）。只要增加机器人的时间成本，就能有效防护（xracy） • **猫鼠游戏论**：这是持续对抗的过程。当前AI可能被简单检测，但最终会学会模仿人类行为（BiteCode_dev, docheinestages）。攻击者可直接逆向工程检测代码来规避（kjok） • **用户体验灾难**：无障碍访问极差，音频验证码"几乎令人痛苦"，盲人用户难以使用（wonkyfruit）。甚至需要"以正确方式失败"才能证明是人类（PeterStuer） 补充讨论：实际测试显示Claude Opus 4.7配合Chrome MCP有95%成功率，但仍会在hCaptcha上失败（cute_boi）。有人质疑对抗攻击技术是否仍对前沿LLM有效（cubefox）

Is AI causing a repeat of Front end's Lost Decade?

作者: xyzal | 评分: 157 | 评论数: 45 | 发布时间: 2026-05-29 11:09
文章摘要

这篇文章探讨了AI对编程工作的影响，作者将其类比为前端开发在过去十年经历的"去技能化"过程。 文章指出，JavaScript框架曾将前端开发从需要深入理解HTML、CSS、浏览器差异、可访问性等专业技能的工作，简化为任何通用程序员都能操作的任务。这降低了入门门槛，但也削弱了专业开发者的议价能力，导致工作质量下降。 如今AI正在对整个编程行业做同样的事——通过更高层次的抽象自动化编码工作，让半熟练或非熟练工作者也能完成任务。这带来成本节约，但也让程序员感到技能贬值的失落感。作者认为，虽然自动化提高了效率，但"不重要的细节"最终总会暴露问题。

评论摘要
主要讨论点：AI和框架是否导致前端开发"去技能化"，以及这种变化的利弊 不同观点： • **支持简化派**：认为所谓"深度专业知识"实际上是处理浏览器兼容性、CSS特异性等"意外复杂度"，现代框架和AI让更多人能构建产品是好事。AI对可访问性的理解可能比普通开发者更好，降低技能门槛是技术进步的自然结果 • **质疑质量派**：指出AI生成的代码容易被识别为"vibe coded UI"，缺乏竞争力。有创业公司因产品明显由AI构建而被质疑价值——"任何人都能让AI快速构建同样的东西"。强调即使用AI，仍需深入理解才能做好验证和系统集成 • **历史重复派**：将当前AI浪潮类比为10-15年前框架兴起时期。当时也出现快速开发、标准化UI、开发者对工具的认同感等现象。认为这是软件行业自动化重复工作的必然趋势，但有效使用AI本身也是需要学习的技能 • **抽象层争议**：有人认为框架创建了新抽象层隐藏底层细节，而AI只是生成代码但不改变抽象层级，仍需理解生成内容。另有观点指出问题在于"原型当产品卖"——快速工具本应用于原型，却被当作最终产品交付 补充讨论：多位评论者提到，无论工具如何进化，专业级工作仍需掌握HTML/CSS/JS基础。AI可能影响新入行者的学习路径，但有经验的开发者不会真正"失去技能"。

CVE-Bench: testing LLM agents on real-world vulnerability patches

作者: logickkk1 | 评分: 4 | 评论数: 1 | 发布时间: 2026-05-29 19:28
文章摘要

作者创建了CVE-Bench基准测试，评估五个前沿AI模型（三个OpenAI，两个Poolside）修复20个真实安全漏洞的能力。测试采用三种提示方式：完整漏洞报告、仅行为描述、仅文件位置。结果显示：最佳模型（gpt-5.5）总体成功率仅50%，最优条件下也只有60%。所有模型在缺少漏洞描述时表现明显下降。失败模式包括搜索偏离、预算耗尽和部分修复。研究基于GitHub漏洞数据库中的真实CVE，涵盖15类常见弱点，严重程度从2.1到9.8分。作者手动筛选了18个Python项目的漏洞，排除了复杂的单体仓库和需要编译工具链的项目，为每个任务提供了安全测试脚本来验证修复效果。

评论摘要
主要讨论点：AI漏洞检测工具（如Mythos和Glasswing）的实际价值与局限性 不同观点： • **发现漏洞不是核心问题**：作者认为大多数组织的真正挑战不在于发现漏洞，而在于如何平衡修复漏洞与交付新产品功能之间的资源分配。这是产品团队和安全团队之间的自然摩擦点。 • **自动修复比发现更重要**：相比仅识别漏洞，作者更关注自动化或半自动化的PR来实际修复漏洞。但简单修复可能破坏其他功能，因此并不容易。 • **人工审核仍然必要**：当前技术水平下，仍需要开发人员确保产品功能完整性，需要安全人员确保漏洞真正被修复而非仅仅被混淆。 补充讨论：作者展望未来技术成熟后，开发和安全团队的时间应该花在思考弹性软件设计和架构上，而非代码级漏洞处理。整体目标应是快速交付既安全又让客户满意的产品。

评论摘要
主要讨论点：古罗马城市生活和公寓建筑（insulae）的历史与现代启示 不同观点： • **历史还原派**：推荐通过文学作品（Lindsey Davis的Falco系列）、纪录片（Mary Beard）和影视作品（Fellini Satyricon、英剧Plebs）来感受古罗马平民生活的真实质感，强调这些作品生动再现了罗马公寓生活场景 • **城市规划反思派**：认为数千年来人们选择城市聚居有其合理性，批评现代汽车中心化和城市蔓延是错误方向，主张应建设更好的城市而非依赖自动驾驶 • **历史现实派**：指出罗马公寓（insulae）实际上是"死亡陷阱"——缺乏消防通道、几乎没有管道系统、高层漏雨、随时可能有物品从窗户掉落伤人，是罗马建筑中最糟糕的部分 • **技术愿景派**：希望有VR应用能让人穿越到不同历史时期，沉浸式体验当时的日常生活、语言、服饰和技术 补充讨论：评论中有趣的对比——有人引用古罗马诗歌描述街道危险却赞美"可步行的餐厅"，暗讽现代城市规划对walkability的过度推崇可能忽视了其他重要的生活质量因素。整体讨论在历史浪漫化与现实残酷性之间形成张力。

文章摘要

这篇文章介绍了如何设置本地 git 远程仓库。主要步骤包括： 1. 使用 `git clone --bare` 创建裸仓库作为远程仓库 2. 通过本地路径或 SSH 协议添加远程仓库：`git remote add local [路径]` 3. 设置默认分支并进行推送和拉取操作 作者分享了使用本地远程仓库的好处：当异地远程仓库不稳定或访问延迟高时，本地远程仓库提供了快速可靠的备份方案。这样既能享受本地推送的零延迟，又能保持异地备份，且无需依赖大型科技公司的服务。

评论摘要
主要讨论点：关于Git本地远程仓库的实用性和必要性 不同观点： • **支持派**：认为本地远程很实用。zenoprax用文件系统远程（如USB、S3加密存储）同步桌面和笔记本，比运行VPS简单；barnabee通过Syncthing同步个人项目；ucirello在GitHub前就这样用；cerved提到用hardlink节省空间、容器隔离等高级场景 • **质疑派**：mystifyingpoi不理解意义，认为本地分支就够了，等网络恢复再推送；globular-toast认为"本地远程"自相矛盾，除非在不同磁盘否则浪费空间，且远程的意义在于共享而非备份 • **感慨派**：joeyguerra感叹开发者重新发现Git原有能力；antiframe指出GitHub太主流导致人们忘记Git本身是分布式的 补充讨论： nasretdinov提到`git clone --reference`可节省空间和时间；cerved详细说明裸仓库的用途（如搜索邮件列表）；whax发现页面footer含Anthropic的模型拒绝触发字符串；enoint暗示VPN可能是更好方案但不便明说 争议焦点：本地远程是否有实际价值，还是只是对Git基础功能的重新包装
