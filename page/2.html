A new experimental Go API for JSON

作者: darccio | 评分: 171 | 评论数: 10 | 发布时间: 2025-09-09 14:54
文章摘要

摘要： Go团队发布了实验性的新JSON API（encoding/json/v2和encoding/json/jsontext），旨在解决现有encoding/json包的多个问题。新版本改进了JSON语法处理（如严格UTF-8验证、禁止重复字段名），修复了行为缺陷（如nil切片/映射的序列化方式），并提供了更灵活的API设计（支持更多I/O选项）。同时解决了现有API的性能限制和一致性问题。该实验性版本暂不默认启用，可能继续调整API设计。

评论摘要
主要讨论点：[Go语言中JSON处理的痛点及新版本设计的争议] 不同观点： • **Go的JSON处理设计存在问题** - [phoenixhaber]认为Go的JSON处理过于繁琐，不像Rust的serde或其他语言那样简单。 - [coldtea]指出`encoding/json`从一开始就设计不良，而非用户需求变化导致。 - [gethly]批评v2版本延续了v1的“愚蠢行为”（如`nil`处理），并表达了对新版本的失望。 • **对新版本的质疑与担忧** - [breakingcups]担心v2的采用率，因为LLM（如GPT）的训练数据中可能只有v1 API。 - [tibbe]质疑v1设计中为何将`nil`切片或映射序列化为`JSON null`。 - [gethly]提到自己不得不fork v1以修正行为，并认为v2未能解决问题。 • **与其他语言的对比** - [rjrodger]指出大多数语言的JSON解析器存在`null`与`nil`的歧义问题，但JavaScript因区分`null`和`undefined`而避免了这一问题。 - [afdbcreid]提到Go标准库多次发布v2的问题，并认为Rust的“非电池内置”标准库设计可以避免此类问题。 • **对Go生态的困惑** - [sroerick]请求非Go开发者视角的概述，质疑Go的JSON支持是否“一开始很酷但后来变糟”。 - [h1fra]对Go在常见功能（如API调用中的JSON解析）上的复杂性表示不解。 补充讨论： - 争议焦点集中在`nil`值的处理（如映射、切片和指针）以及`omitempty`与`omitnil`的行为差异。 - 部分评论者认为Go的设计问题源于早期决策，而新版本未能彻底改进。 - 与其他语言（如Rust、JavaScript）的对比凸显了Go在JSON处理上的用户体验差距。

DuckDB NPM packages 1.3.3 and 1.29.2 compromised with malware

作者: tosh | 评分: 212 | 评论数: 21 | 发布时间: 2025-09-09 10:10
文章摘要

DuckDB的npm软件包（1.3.3和1.29.2版本）被发现含有恶意代码，攻击者通过钓鱼攻击获取了发布权限，添加了干扰加密货币交易的恶意程序。受影响的具体包包括@duckdb/node-api@1.3.3、@duckdb/node-bindings@1.3.3、duckdb@1.3.3和@duckdb/duckdb-wasm@1.29.2。DuckDB团队在发现问题后4小时内采取了措施，包括标记问题版本、联系npm删除这些版本，并发布新的安全版本（1.3.4/1.30.0）。团队承认这是一次典型的钓鱼攻击，并正在审查内部流程以防止类似事件再次发生。

评论摘要
主要讨论点：[NPM包被恶意攻击的原因及防范措施] 不同观点： • **基础设施安全性不足** - 关键基础设施频繁被入侵（如NPM包被植入恶意软件） - 建议：平台应对开发者邮件进行签名（如GPG密钥），并要求开发者验证未签名邮件的真实性 - 当前2FA机制不足，建议在修改凭证后设置24小时冷却期 • **钓鱼攻击是主要问题** - 攻击者使用像素级复制的NPM官网钓鱼邮件 - 建议：邮件客户端应增加链接不可点击或显示完整链接的功能 • **代码签名与供应链安全** - 钓鱼是表象，根本问题是缺乏代码签名和工件签名 - 建议：开发者应在本地签名代码，用户验证公钥（类似Linux发行版的做法） - 争议点：NPM等平台是否应强制要求签名 • **发布流程改进** - 关键项目发布应要求多名维护者签名 - 建议：NPM应增加邮件确认链接或冷却期机制 - 争议点：冷却期是否会影响紧急修复 补充讨论： - DuckDB团队被批评忽视安全实践（如直接运行curl安装脚本） - 攻击是否仅限于NPM？PyPI和Maven是否同样受影响？ - 用户建议仅安装一周以上的包以避免新发布的恶意包
