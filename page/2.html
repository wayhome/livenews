Sp.h is the standard library that C deserves

作者: dboon | 评分: 88 | 评论数: 20 | 发布时间: 2026-05-20 13:05
文章摘要

这篇文章介绍了作者开发的C语言标准库sp.h。它是一个15,000行的单头文件库，核心理念包括：直接调用系统调用而非依赖libc；摒弃传统的堆内存管理，要求程序显式管理内存分配器；用指针+长度的字符串结构(sp_str_t)替代以null结尾的字符串，提升安全性和性能；代码高度可读可修改，仅约40个系统调用是平台相关的；用C99编写，具有极强的可移植性。作者认为传统libc已成为障碍，sp.h提供了更现代、高效且符合实际需求的底层接口。

评论摘要
主要讨论点：对一个强调“极致可移植、绕过libc、反空终止字符串、小而强”的C头文件库，其设计目标、实现一致性、可读性与工程实用性的争论。 不同观点： • **质疑目标自相矛盾**：有人指出“极致可移植”与“不支持冷门平台”冲突；若只面向x86_64、aarch64、WASM，就不能同时宣称“任何编译器/系统都可用”。也有人质疑“直接对syscall编程”只在Linux稳定，其他平台未必成立。 • **部分理念获认同**：多位评论者赞同“长度+指针优于\0结尾字符串”“适度重视性能优化”“标准库尽量贴近syscall”。同时补充 FILE 抽象在如 `fopencookie`、`open_memstream` 等场景仍有价值。 • **实现与表述被批评**：有人认为示例代码噪声大、可读性差，`wc` 示例命名易误导；“There Is No Heap”却又定义堆分配接口，被指表述不清。还有人质疑原子实现：Unix下包 `pthread mutex` 仍依赖标准库，且未说明内存模型/栅栏，甚至怀疑代码质量。 • **工程层面的担忧**：包括固定 `SP_PATH_MAX=4096` 对超长路径缺少回退；header-only 需引入 `windows.h` 等导致编译变慢；若程序部分仍需 libc、以及 `main` 前初始化如何处理，也被追问。 • **定位与背景讨论**：有人觉得这种强观点风格“很有趣”，或适合作为自定义语言的编译目标；也有人提到其思想与 DJB、Zig/WTF-8 等既有传统有关，并追问文中为何未提 Zig。 补充讨论：争议焦点主要在“宣称的底层纯粹性是否与实际实现一致”，以及“可移植性、简洁性与现实兼容性”三者如何平衡。

Deno 2.8

文章摘要

Deno 2.8 发布，这是迄今最大的次要版本更新，新增多个子命令： **deno audit fix** - 自动升级有漏洞的 npm 包到最近的补丁版本 **deno bump-version** - 更新 deno.json 或 package.json 中的版本号，支持 patch/minor/major 增量，在工作区中可基于 Conventional Commits 自动推导版本变更 **deno ci** - 专为 CI 环境设计的安装命令，强制使用 lockfile 并在不匹配时报错 **deno pack** - 将 Deno/JSR 项目构建为可发布到 npm 的 tarball，自动转译 TypeScript、生成类型声明文件、重写模块说明符以兼容 npm 生态 升级命令：`deno upgrade`

评论摘要
主要讨论点：Deno 与 Node.js/Bun 的竞争态势，以及 Deno 的发展方向争议 不同观点： • **Deno 优势派**：认为 Deno 的权限模型、TypeScript 原生支持、安全性设计体现了 Unix 精神，是 JS 生态应该前进的方向。适合小型服务和业余项目，性能持续改进令人印象深刻。 • **Node 兼容性必要派**：认为 Deno 加强 Node 兼容性（从 40% 提升到 75%）是正确方向，npm 默认支持和 lib.node 包含使迁移更容易，这些改进让 Deno 更实用。 • **方向转变质疑派**：批评 Deno 为商业原因妥协初心，默认包含 Node 类型污染了 Deno/Web 代码，过度向 Node/NPM 靠拢会失去差异化优势。担心专业项目中途因方向变化被迫回归 Node。 • **生态竞争观察**：Bun 因速度快、标准库全面且被 Anthropic 收购而增长迅速；Node 依然是稳定方案；Deno 的沙箱和导入机制优势已被商品化，吸引力下降。 补充讨论：有开发者建议 Deno 应坚持初始价值观，AI 代理的出现可能缓解技能迁移压力；也有人希望看到 Deno 用于 Python/WASM；项目融资模式（拒绝捐赠）可能带来长期压力。

Comparing an LZ4 Decompressor on Four Legacy CPUs

作者: tosh | 评分: 58 | 评论数: 3 | 发布时间: 2026-05-20 11:58
文章摘要

这篇文章讨论了作者为8位和16位复古计算机平台实现LZ4压缩算法的经历。作者最初为SNES项目压缩数据，后来为6809、68000处理器实现了版本，最近又完成了Z80、8080、8086和6502的四个新实现。 文章详细解释了LZ4的工作原理：通过交替的字面量字符串和反向引用来压缩数据。每个"序列"包含一个长度字节（高4位表示字面量长度，低4位表示反向引用长度加4）、字面量数据、以及2字节的偏移量。当长度超过15时，使用额外字节扩展长度值。 作者特别强调Z80实现非常直接，并以此为基础对比了不同CPU架构的实现差异，展示了如何将Z80代码转换为8080、x86版本，以及6502需要采用的不同实现策略。

评论摘要
主要讨论点：围绕LZ家族压缩算法及相关文章的价值，讨论其在自解压可执行文件中的适用性、文章的技术讲解方式，以及文中“限制条件”对实现效率的意义。 不同观点： • 观点一：LZ家族算法之所以常用于自解压可执行文件，是因为“简单且高效”。[userbinator]认为它像RLE的自然扩展，既能获得很高压缩率，又只需要几十字节的解压器，强调其工程实用性和体积优势。 • 观点二：文章/博客本身的价值在于“面向爱好者的循序渐进拆解”。[flomo]认为Bumbershoot很适合喜欢80年代家用电脑/主机、但不清楚底层原理的读者；作者以边研究边讲解的方式，逐步展示如何让游戏在特定系统上运行，ASM深度解析是亮点。 • 观点三：文中的技术限制设计主要是为了“避免昂贵条件判断、提升执行速度”。[msephton]指出三条限制通过“overshooting”保证流程无需频繁if测试，因此可以全速执行；他认为阅读虽有难度，但很有趣。 补充讨论： • [flomo]提出对博客的保留意见：内容很多，但导航不佳，影响检索和阅读体验。 • 评论之间基本是互补关系：一条强调算法特性，一条评价文章写法与可读性，一条补充具体实现机制。 • 争议焦点不强；较明显的分歧仅在于内容质量与站点可用性之间——技术内容受肯定，但博客组织方式被批评。

1940 Air Terminal Museum Begins Liquidation

作者: weaponeer | 评分: 114 | 评论数: 12 | 发布时间: 2026-05-22 17:05
文章摘要

休斯顿1940航空博物馆正在清算三台全尺寸飞行模拟器：西南航空737-200、比奇空中国王200和霍克700，每台售价2万美元。这些模拟器自2010年捐赠后从未通电使用，功能状态未知。买家需自行安排运输和超大型叉车（至少22700磅承重），并负责拆除临时墙体。由于737阻挡其他两台，必须先移出737才能取走其他模拟器。博物馆必须在6月底前腾空建筑，交易不提供任何保证或质保。有意者请通过邮件联系，可安排现场或视频查看。

评论摘要
主要讨论点：休斯敦一座航空相关博物馆/展馆关闭后，馆藏设备与模拟器处理引发惋惜、价格讨论，以及对历史保护和后续接手机会的关注。 不同观点： • 对博物馆关闭表达惋惜与震惊。多位评论者表示“很难过”“太可惜了”，有人住在当地六年都不知道它已关闭，遗憾自己没去参观；也有人回忆曾带孩子去，觉得这是种“不刻意包装、可自由探索”的好博物馆。 • 呼吁外界支持或寻找接手方。有人贴出背景链接，指出博物馆因租约违约，必须在6月底前搬离主楼和机库；也有人希望有能力者能资助，或由 Lone Star Flight Museum 之类机构接手。 • 对展品/模拟器的技术与收藏价值感兴趣。有人辨认图片中的机架可能是德州仪器小型机、带8英寸软盘；也有人提到737模拟器部件似乎较完整，希望像 CuriousMarc、TubeTime、Usagi 这类擅长修复复原的技术博主或团队合作重建。 • 对售价有分歧。有人认为2万美元“对飞机发烧友不算贵”，若有空间愿意收藏；也有人觉得“拿来玩挺有趣，但不值2万美元”，甚至调侃大家一起压价，卖方或许会降到2万以下。争议焦点是：这类大型、老旧、可能不完整的设备，到底应按收藏情怀还是按实际修复成本估价。 补充讨论： • 有人认为像休斯敦这样有航空公司和石油企业资源的城市，本应有足够资金维持此类机构。 • 评论中也有对建筑本身的赞赏，称其为“惊艳的装饰艺术风格”。 • 少量轻松/吐槽性质评论，如手册测试流程竟用到德摩根定理、馆方照片说明写成“asdfsd”等。
