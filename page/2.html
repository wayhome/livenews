Comparing an LZ4 Decompressor on Four Legacy CPUs

作者: tosh | 评分: 50 | 评论数: 2 | 发布时间: 2026-05-20 11:58
文章摘要

这篇文章讨论了作者为8位和16位复古计算机平台实现LZ4压缩算法的经历。作者最初为SNES项目压缩数据，后来为6809、68000处理器实现了版本，最近又完成了Z80、8080、8086和6502的四个新实现。 文章详细解释了LZ4的工作原理：通过交替的字面量字符串和反向引用来压缩数据。每个"序列"包含一个长度字节（高4位表示字面量长度，低4位表示反向引用长度加4）、字面量数据、以及2字节的偏移量。当长度超过15时，使用额外字节扩展长度值。 作者特别强调Z80实现非常直接，并以此为基础对比了不同CPU架构的实现差异，展示了如何将Z80代码转换为8080、x86版本，以及6502需要采用的不同实现策略。

Deno 2.8

文章摘要

Deno 2.8 发布，这是迄今最大的次要版本更新，新增多个子命令： **deno audit fix** - 自动升级有漏洞的 npm 包到最近的补丁版本 **deno bump-version** - 更新 deno.json 或 package.json 中的版本号，支持 patch/minor/major 增量，在工作区中可基于 Conventional Commits 自动推导版本变更 **deno ci** - 专为 CI 环境设计的安装命令，强制使用 lockfile 并在不匹配时报错 **deno pack** - 将 Deno/JSR 项目构建为可发布到 npm 的 tarball，自动转译 TypeScript、生成类型声明文件、重写模块说明符以兼容 npm 生态 升级命令：`deno upgrade`

评论摘要
主要讨论点：Deno 与 Node.js/Bun 的竞争态势，以及 Deno 的发展方向争议 不同观点： • **Deno 优势派**：认为 Deno 的权限模型、TypeScript 原生支持、安全性设计体现了 Unix 精神，是 JS 生态应该前进的方向。适合小型服务和业余项目，性能持续改进令人印象深刻。 • **Node 兼容性必要派**：认为 Deno 加强 Node 兼容性（从 40% 提升到 75%）是正确方向，npm 默认支持和 lib.node 包含使迁移更容易，这些改进让 Deno 更实用。 • **方向转变质疑派**：批评 Deno 为商业原因妥协初心，默认包含 Node 类型污染了 Deno/Web 代码，过度向 Node/NPM 靠拢会失去差异化优势。担心专业项目中途因方向变化被迫回归 Node。 • **生态竞争观察**：Bun 因速度快、标准库全面且被 Anthropic 收购而增长迅速；Node 依然是稳定方案；Deno 的沙箱和导入机制优势已被商品化，吸引力下降。 补充讨论：有开发者建议 Deno 应坚持初始价值观，AI 代理的出现可能缓解技能迁移压力；也有人希望看到 Deno 用于 Python/WASM；项目融资模式（拒绝捐赠）可能带来长期压力。

KanBots 是一个看板工具，可在每张卡片上并行运行 AI 代理（Claude Code 或 Codex）。主要特性包括：在独立的 git worktree 中并行执行多个代理任务、自动驾驶模式（自动拆分和分配任务）、决策提示交互、本地优先存储（无需云账户和遥测）、实时成本分析、GitHub 集成及 MCP 服务器支持。提供两个版本：免费开源的桌面版（个人使用）和面向团队的云端版（$19/月/席位，增加协作功能）。采用 MIT 许可，代码不离开本地机器。

评论摘要
主要讨论点：关于并行AI代理工具的实用性和设计理念 不同观点： • **需要持续监督派**：认为当前技术尚未成熟到可以让代理无监督运行。30分钟的代理活动都难以审查，更不用说整晚的工作。需要在第5分钟就介入调整，合并多个代理的工作也很繁琐（aitchnyu, speedgoose, ptengelmann） • **看好并行代理派**：认为这种方式很自然直观，能在"交互对话"和"后台任务"之间无缝切换，比追踪多个终端窗口更高效（timfsu） • **完整IDE体验派**：强烈反对"1任务=1代理=1聊天"的限制模式，主张"1任务=1工作树=1完整IDE"，希望每个任务都有完整的IDE环境，支持多模型、多对话、深度代码审查。批评现有工具（如Cursor）的代理界面过于简陋，甚至不能切换模型（jorl17） • **本地优先派**：将"本地优先、零服务器、无云账户、无遥测"视为采用此类工具的基本门槛（chrisweekly） 补充讨论：有用户提到类似项目Vibe Kanban因盈利问题停止开发的遗憾，建议借鉴其远程支持和"在VS Code中打开"等关键功能。另有技术反馈指出网站在WebKit和移动端的显示问题，以及404错误。

Wi-Wi is wireless time sync at 1 nanosecond

作者: Brajeshwar | 评分: 109 | 评论数: 7 | 发布时间: 2026-05-20 15:06
文章摘要

Wi-Wi STAMP是日本NICT开发的无线时间同步协议，使用900 MHz频段实现皮秒级时间同步和毫米级距离精度。当前原型达到20ps相位同步抖动和30ns时间同步，下一代将实现5ns精度。该技术体积小巧（智能手机大小），无线范围0.2-5公里，信号穿透力优于GNSS。在NAB展会上展示了两个应用：Meinberg用其实现远程摄像机的黑场时间同步，以及通过三个Wi-Wi单元实现毫米级定位追踪。该技术特别适用于室内或布线困难的场景。

评论摘要
主要讨论点：关于Wi-Wi无线时间同步技术的多角度评论 不同观点： • **质疑实用性**：为何需要纳秒级精度？系统只需同步一次后可自行计时，纳秒级同步似乎过度设计 • **技术细节疑问**：标题声称1ns精度，但文章内容提到30ns（目标降至5ns），存在不一致 • **成本考量**：现有GPS NTP服务器已能提供亚毫秒级同步，PTP设备过于昂贵。若Wi-Wi价格下降会有吸引力 • **隐私担忧**：Wi-Wi采用双向干涉测量，意味着获取时间的同时会暴露物理位置。GNSS时间服务更优，因为卫星无法追踪接收者位置 • **技术优势认可**：Wi-Wi信号穿透性更好，可能显著改善设备电池续航 补充讨论：有人关注命名发音问题（Why-Why还是Wee-Wee），另有评论简单表达对技术的惊叹。核心争议在于：纳秒级精度的必要性、隐私代价是否值得、以及相比现有方案的成本效益比。
