Problems with the heap

作者: todsacerdoti | 评分: 121 | 评论数: 13 | 发布时间: 2025-03-26 19:23
文章摘要

这篇文章讨论了与内存堆相关的严重技术问题。作者用一个不完美的类比描述了一个用危险材料建造的 playground，暗示某些软件工具存在重大安全漏洞。文章提到在一个实验中，使用某些工具会导致内存分配错误，例如 "malloc(): corrupted top size" 和 "Segmentation fault" 等严重问题。作者指出，虽然他不完全了解如何利用这些漏洞，但它们可能被用来执行恶意操作，尤其是在 root 用户权限下运行时，攻击者可以完全控制系统。作者建议停止使用这些工具，特别是避免以 root 身份运行它们，以防止潜在的安全风险。

评论摘要
主要讨论点：对 "atop" 工具可能存在的堆缓冲区溢出漏洞及其潜在影响的分析和讨论 不同观点： • nsxwolf 认为文章难以理解，似乎是在讨论某个未完整呈现的中间部分。 • NobodyNada 详细分析了错误信息，指出 glibc malloc 的 "top" 堆块被破坏，可能由堆缓冲区溢出导致。他提到，虽然现代 Linux 和 glibc 有一些防护措施，但仍可能被利用，并提供了一个相关挑战的解决方案链接。 • ianbutler 提到他们开发的工具 Bismuth 可能发现了相关 bug，并给出了具体 commit 的 SHA，表示会负责任地披露给维护者。 • dang 提供了一个相关讨论的链接，建议停止使用 atop。 • john-h-k 解释了 atop 因为不安全地访问被监控进程的内存，可能导致 RCE（远程代码执行），并指出因 atop 常以 root 身份运行，可能导致权限提升。 • baltimore 提到同一作者在2014年也曾遇到 atop 的段错误问题，并提供了一个历史博客链接。 • bee_rider 以幽默的方式表达了对 RachelByTheBay 文章的关注。 • ultrarunner 表示不太清楚文章是否在讨论一般的堆漏洞，还是在引用某个特定事件。 • judofyr 对讨论中的紧张气氛表示不解，质疑为何要如此处理问题。 • th0ma5 提供了一个可能相关的 GitHub issue 链接，供进一步参考。 补充讨论： - 讨论中多次提到 atop 工具的漏洞可能导致的严重后果，尤其是权限提升风险。 - 争议的焦点在于 atop 漏洞的严重性及其潜在利用方式，部分讨论者对漏洞细节和影响存在不同理解。 - 提供了多个外部链接以帮助理解和进一步探讨问题，包括历史讨论、技术分析和相关代码仓库问题。

Writing a tiny undo/redo stack in JavaScript

作者: julik | 评分: 75 | 评论数: 9 | 发布时间: 2025-03-24 08:53
文章摘要

文章主要介绍了如何实现一个简单而有效的UI撤销（undo）和重做（redo）功能，特别是一个小型的撤销栈（undo stack）。作者对比了两种撤销功能：版本历史（如Photoshop的历史记录）和撤销栈。对于大多数应用来说，撤销栈更为适用。文章详细描述了如何实现一个撤销栈，包括如何处理撤销和重做操作，并提出了使用两个栈——一个用于存储可撤销操作，另一个用于存储可重做操作——的方案，以避免使用指针和索引带来的复杂性。 作者还讨论了JavaScript中按引用传递的问题，并指出在实现撤销和重做功能时，必须确保操作函数是幂等的。最终，文章提供了一个简洁的撤销栈实现代码，避免了使用索引可能导致的错误。

评论摘要
主要讨论点：针对实现“撤销/重做”功能的复杂性和方案选择的讨论 不同观点： • **londons_explore** 认为实现撤销功能会遇到很多复杂的场景，比如状态复杂的组件（飞行中的fetch请求、循环引用、WebAssembly模块等），并且需要和浏览器自带的撤销功能（如返回按钮、文本框编辑）良好兼容。他担心最终可能会遇到很多边界情况，导致实现出现bug或者耗费大量工程时间。 • **noduerme** 对使用两个栈（undo/redo）的方案表示赞赏，认为这是一种优雅的解决方案。虽然StructuredClone他不熟悉，但他理解在某些情况下克隆对象比使用匿名函数的指针更合适。他表示期待在处理事件处理器时尝试这种方法。 • **catapart** 分享了自己将撤销功能实现为一个Web组件的经历，认为这种功能在Web应用中非常实用，并对文章中简化的方案表示赞赏。 • **atum47** 提出了使用固定大小的循环缓冲区来管理状态，每当有新状态时，最旧的状态会被丢弃。这提供了一种内存管理上的优化方案。 • **balamatom** 提到通过设置`foo.length = 0`可以清空JS数组，这是他新学到的一个技巧，表明讨论中还有人关注具体的代码实现细节。 • **hyperhello** 指出该方案没有实现系统级的撤销功能（如iPhone上的摇动撤销/重做对话框），认为除了快捷键（如Meta-Z），还应考虑菜单或其他用户交互方式，以确保兼容不同用户的操作习惯。 • **benatkin** 认为使用两个栈并不一定能让方案更健壮，他建议使用私有属性来存储栈，以提高实现的封装性和安全性。 补充讨论： • **molszanski** 提到了其他类似的实现方案和工具库，如ImmerJS和immerhin，提供了额外的参考资源。 • **evanrelf** 简单提到“拉链”（zipper）数据结构，暗示可能有其他数据结构可以用于实现撤销/重做功能，但没有展开讨论。 争议焦点： • 争议的核心在于实现撤销功能时的复杂性和边界情况处理。**londons_explore** 强调了这种复杂性，而其他人如**noduerme** 和 **catapart** 则认为文章中的方案足够简洁有效。此外，**benatkin** 对使用两个栈的健壮性提出质疑，认为私有属性可能更好。

文章主要讨论了Waymo自动驾驶汽车的安全记录，指出在行驶超过5000万英里后，Waymo的事故率远低于人类司机。尽管Waymo车辆严格遵守交通规则，但许多事故仍由人类司机的违规行为引发，如超速、闯红灯和跨双黄线等。文章提到，自2020年以来，Waymo报告了约60起涉及安全气囊或受伤的严重事故，大多数事故责任在其他司机。例如，一起致命事故是人类司机高速追尾导致六车连环相撞。Waymo车辆在停止或行驶时经常被其他车辆撞击，尽管有些事故中Waymo可能有部分责任，但绝大多数责任在人类司机。随着Waymo服务扩展，未来可能涉及更多事故，但其事故率仍远低于人类司机。文章还提到Waymo正努力通过“安全出口”计划等措施减少事故发生。

评论摘要
主要讨论点：Waymo自动驾驶汽车的安全性、技术表现、成本效益以及与人类驾驶的对比 不同观点： • **Waymo的技术表现**：[wnissen]认为Waymo在技术方面表现出色，特别是在减少严重事故方面优于人类司机，尤其是对于最差20%的司机。同时引用了研究数据支持其观点。[ikerino]则指出，虽然Waymo的事故率相对人类司机有所降低，但因为数据稀少，使用"略有恶化"这样的描述可能有误导性，建议用"持平"来描述可能更准确。 • **自动驾驶的广泛适用性与安全性**：[mjburgess]担心Waymo在面对新环境和没有高度可用路线数据的情况下，是否能保持良好的表现，并提出如果自动驾驶车辆发生大规模故障，可能会造成比人类驾驶更严重的集体事故。此外，还质疑Waymo在安全性方面的统计数据，认为需要提供置信区间以增加透明度。[shadowgovt]补充说，Waymo的车辆能记录更多事故数据，因此在事故统计上更准确。 • **与人类驾驶的比较标准**：[paxys]认为，Waymo仅仅优于"平均"司机是不够的，自动驾驶需要比"理智且有经验"的司机表现更好，否则即使替换了80%的好司机，事故率可能仍会上升。[amelius]则指出，如果人类司机也配备像Waymo一样的Lidar设备，事故率也会下降。 • **成本与市场接受度**：[nukem222]对Waymo的成本效益表示关注，质疑其是否能真正做到比人类驾驶更便宜，并表示如果价格没有优势，自己不会考虑使用自动驾驶服务。[labrador]则表示对Waymo的安全措施有信心，但不会信任仅依赖视觉提示的Tesla机器人出租车。 • **基础设施与理想交通系统**：[xlbuttplug2]提出了一种理想化的交通系统，建议通过限制车辆自由行驶来减少事故，例如使用类似有轨电车的轨道交通，但承认这种设想不太可能实现。[JKCalhoun]则提到公共交通工具如公交车可能更安全，并对私人自动驾驶车辆的普及表示怀疑。 补充讨论： • **驾驶习惯与事故分布**：[floxy]提出了关于人类司机事故率分布的问题，质疑是所有人都有相似的事故概率，还是有一小部分人更容易发生事故。 [ra7]提供了Waymo安全数据的详细链接，指出文章简要总结了Waymo的安全数据，但更详细的信息可在Waymo官网找到。 • **其他支持观点**：[nickvec]对自动驾驶车辆的未来表示乐观，认为其将挽救许多生命。[jedbrooke]则通过个人观察，指出Waymo总是使用转向灯，认为这使其比人类司机更安全。 争议焦点： • Waymo自动驾驶的安全性与事故统计数据的透明度。 • 自动驾驶是否应该比"平均"司机更好，还是要达到"优秀"人类司机的标准。 • 自动驾驶车辆的成本效益与市场接受度。

Writing Programs with Ncurses

作者: begoon | 评分: 67 | 评论数: 7 | 发布时间: 2025-03-23 13:27
文章摘要

《Writing Programs with NCURSES》是一本由Eric S. Raymond、Zeyd M. Ben-Halim编写，并由Thomas Dickey更新的指南，旨在帮助C程序员使用NCURSES库。NCURSES是一个用于终端独立屏幕绘制和输入事件处理的子程序库，能够隐藏不同终端类型的差异并自动优化输出。本文档介绍了NCURSES的基本概念、功能描述及使用方法，包括初始化、屏幕更新、窗口管理、字符属性与颜色、鼠标接口、调试等内容。此外，还介绍了面板库、菜单库和表单库的使用。NCURSES基于 terminfo 数据库，适用于字符单元终端，具有简单和向后兼容的优势，尤其适合无需位图图形和多字体的应用程序。尽管UNIX桌面环境日益被X、Motif和Tcl/Tk主导，NCURSES仍因其简便性和兼容性被广泛使用。

评论摘要
主要讨论点：NCurses及其现代替代工具在终端用户界面（TUI）开发中的使用和评价 不同观点： • [cranium] 认为 Textual 是一个现代且美观的 NCurses 替代品，尽管不是完全开箱即用的解决方案，但已经非常接近。Textual 虽然仍需要一些工作，但相比 NCurses 更易用。 • [didgetmaster] 回忆过去使用 NCurses 的经验，指出需要不断调整窗口大小以使界面看起来合适，暗示 NCurses 在使用上可能较为繁琐。 • [degrees57] 提到在 SuSE 系统上使用 YaST 的经历，认为 NCurses 和 GUI X Window System 提供相同的功能，但有时 GUI 更令人愉悦，暗示 GUI 在某些情况下优于 TUI。 • [matt3210] 简洁地表示 NCurses 是 UI 设计的巅峰之作，暗示对 NCurses 的偏好和赞赏。 • [SoftTalker] 将 NCurses 比作终端应用的 React 框架，强调其高效更新终端显示的能力，暗示其在设计上的先进性。 • [bashmelek] 提到受 Zed Shaw 的项目启发开始使用 PDCurses，并认为这是一次有趣的体验，暗示 PDCurses 是一个值得探索的替代方案。 补充讨论： • [mouse_] 提供了一个关于终端控制的参考链接（https://xn--rpa.cc/irl/term.html），为讨论提供了进一步的技术资源。 争议焦点： • 对于 NCurses 的使用体验存在分歧。一部分人（如 didgetmaster）认为 NCurses 使用繁琐，而另一部分人（如 matt3210 和 SoftTalker）则赞赏其设计和功能。 • 对于现代替代工具（如 Textual 和 PDCurses）的看法也有所不同，cranium 和 bashmelek 分别表示这些工具提供了更易用和有趣的体验。 总结： 讨论围绕 NCurses 及其现代替代工具在 TUI 开发中的使用展开，参与者分享了各自的使用经验和评价，涉及易用性、功能性和设计理念等多个方面。同时，一些参与者提供了相关的技术资源和参考链接，为讨论提供了更多的背景信息。
