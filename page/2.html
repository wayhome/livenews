Brian Eno's Theory of Democracy

作者: akkartik | 评分: 70 | 评论数: 11 | 发布时间: 2025-05-04 05:12
文章摘要

文章探讨了布莱恩·伊诺（Brian Eno）的艺术观点如何间接反映了他对民主的看法，并结合了政治学家亚当·普热沃斯基（Adam Przeworski）的民主理论。普热沃斯基在其1991年著作《民主与市场》中提出，民主是一种“政党会输掉选举”的制度，并通过博弈论解释了民主的稳定性源于执政党在未来可能重新掌权的预期和不确定性。这种理论将复杂的政治行为简化为一个简单的九字命题，并强调民主的持续性依赖于权力交替的预期和不确定性。然而，这一理论无法完全解释近年来美国等国民主倒退的现象，表明民主的稳定性可能还需要考虑更多外部冲击和其他因素。文章认为，伊诺的艺术理念与这种民主理论有相通之处，强调了多样性和组织在政治中的重要性。

A PostgreSQL planner semi-join gotcha with CTE, LIMIT, and RETURNING

作者: namanyayg | 评分: 41 | 评论数: 9 | 发布时间: 2025-05-04 01:24
文章摘要

文章描述了在PostgreSQL中使用CTE（Common Table Expression）结合`DELETE ... RETURNING`和`LIMIT`处理队列表任务时遇到的意外行为。尽管查询中明确使用了`LIMIT 1`，但有时会返回多条记录。这是因为PostgreSQL的查询规划器将查询优化为一个嵌套循环半连接（Nested Loop Semi Join），导致子查询（包括`LIMIT 1`）针对每个候选行执行多次，从而可能删除并返回多行。 问题的根源在于CTE没有被当作一个优化屏障，规划器自由地将其内联或转换。为解决此问题，作者建议避免在`DELETE`条件中使用CTE，改为直接在`WHERE`子句中使用子查询： ```sql DELETE FROM task_queue WHERE id = ( SELECT id FROM task_queue WHERE queue_group_id = 15 LIMIT 1 FOR UPDATE SKIP LOCKED ) RETURNING item_id; ``` 这样可以确保`LIMIT`在全局范围内应用，从而实现预期行为。

评论摘要
主要讨论点：对SQL查询中使用CTE和`FOR UPDATE SKIP LOCKED`的有效性和正确性的不同看法 不同观点： • [impulsivepuppet] 认为`deleted_tasks`这个CTE命名容易引起误解，因为原意是删除单个项目，但结果却删除了多个。此外，使用`FOR UPDATE SKIP LOCKED`假设了一个特定的执行顺序，而查询语法并没有明确规定这一点。他质疑如果不使用`SKIP LOCKED`是否能得到预期结果。 • [eknkc] 认为这不是一个“陷阱”，而是一个规划器（planner）的bug。 • [clhodapp] 指出子查询可能在任务队列表的每一行上重新运行，这不仅是性能问题，还涉及正确性。他个人偏好将选择部分放入CTE，而不是子查询，并对作者创建CTE的动机表示不解。 • [wordofx] 质疑为什么作者不直接返回结果，而要使用CTE来选择所有内容。 • [simonw] 提供了一个替代查询方案，并指出查询中未提及的`item_id`列，推测这是task_queue表中的未提及列。 • [swid] 对查询是否应删除多行表示困惑，并认为查询计划可能存在歧义。他期望Postgres只使用单一解释。 • [Horffupolde] 建议使用`= ANY`代替`IN`。 • [abhisek] 关注如何防止查询优化导致意外结果，建议使用linter或在CI中检测这些问题。 • [tucnak] 认为在`SKIP LOCKED`场景下使用`DELETE`会导致失败，建议只使用`UPDATE w/ SKIP LOCKED`，然后在事务中正常`DELETE`。 补充讨论： • 争议的焦点在于查询中使用`FOR UPDATE SKIP LOCKED`是否合适，以及是否会导致意外的多行删除。 • 不同的开发者对CTE的使用和必要性有不同看法，部分人认为直接使用子查询或简单查询更为合适。 • 对查询计划和执行顺序的歧义性也是讨论的一个重要方面，部分人期望数据库能提供更明确的执行保证。 • 有人提出使用linter或CI工具来提前检测潜在的SQL问题，以防止生产环境中的严重错误。

DotnetSnes: Library allowing to use C# to create SNES ROMs

作者: ingve | 评分: 28 | 评论数: 3 | 发布时间: 2025-05-02 11:29
文章摘要

**DotnetSnes** 是一个允许使用 .NET 语言创建真实 SNES 游戏 ROM 的库。它通过一个 .NET 库（DotnetSnes.Core）抽象 SNES 游戏开发中的函数和全局变量，编译后的 DLL 通过 "Dotnet To C" 转译器（dntc）转换为 C 代码，再使用 PvSnesLib SDK 工具链生成可用的 ROM。由于 SNES 的限制，编写时需注意系统级类型支持、无动态内存分配、最小化堆栈变量等。开发环境建议使用 Linux 或 WSL，依赖包括 cmake、g++、dotnet-sdk-8.0 等。项目示例包括简单的 "Hello World" 和更复杂的 "LikeMario" 游戏示例，展示了对象管理、地图、音频和手柄输入。要创建新项目，需设置 .NET 类库，引用必要库，并配置 Makefile 以定义 ROM 构建过程。

评论摘要
主要讨论点：F#与Rust的互操作性及其局限性 不同观点： • reverseblade2认为可以通过Fable工具将F#代码转换为Rust，并提供了一个GitHub链接（https://github.com/ncave/fable-raytracer），展示了一个F#到Rust的光线追踪器项目。这表明他支持通过工具链实现F#与Rust的互操作。 • SideburnsOfDoom则指出了这种方式的严重局限性，特别是缺乏动态内存分配和不支持引用类型、类实例。他认为这些限制会从根本上改变语言的特性，可能导致在实际应用中遇到很多困难。 补充讨论： • rawling提到了在三周前有相关讨论，可能暗示这个话题并非新问题，之前已有社区成员关注和讨论过。 • 争议的焦点在于F#通过Fable转换为Rust的可行性和实用性。一方认为这种工具可以有效利用，另一方则认为语言特性的改变会导致实际使用中的问题。 • 一个值得注意的细节是，SideburnsOfDoom提到的限制涉及到F#的核心语言特性，这些特性在转换到Rust后可能无法保留或实现，从而影响项目的架构和实现方式。 通过这些观点，可以看出社区对于F#与Rust互操作的关注点主要集中在工具的可行性、语言特性的保留以及实际应用中的限制和困难。
