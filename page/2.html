Vibe code is legacy code

作者: simonw | 评分: 284 | 评论数: 49 | 发布时间: 2025-07-30 21:13
文章摘要

本文讨论了“氛围编程”（vibe coding）的概念，这是一种依赖AI辅助编程的方式，程序员“忘记代码存在”并快速生成代码。然而，这种方法容易产生技术债务，因为生成的代码往往难以理解和维护，类似于“遗留代码”（legacy code）。遗留代码是普遍被厌恶的，因为它需要大量时间来理解和调试。氛围编程适用于原型和一次性项目，但不适合需要长期维护的软件。如果非程序员使用这种方法开发大型项目，就像给孩子信用卡却不解释债务概念，最终可能导致问题。作者强调，在2025年，若要构建需长期维护的软件，应谨慎使用AI，注重理论构建和技术专长。AI可以使编程更高效，但仍需人类理解代码。

评论摘要
主要讨论点：围绕“vibe编码”（非技术人员或初级开发者快速开发软件）的优缺点及其对软件工程的影响的讨论。 不同观点： • **支持vibe编码的观点**： - vibe编码使得非技术人员可以用较低成本快速验证商业想法。CharlieDigital的例子中，一个没有技术背景的人通过简单工具（Replit和Supabase）在几个月内创建了一个可盈利业务，尽管代码质量不高，但商业模式得到验证。 - ww520提到一个类似案例，几个人通过简单的Excel和Access脚本获得了大客户，尽管系统不完善，但帮助他们获得了融资。 - gleenn分享了一个通过“vibe编码”项目成功重构遗留项目的经验，表明即使是vibe编码的项目也可以用于良好的软件工程实践。 • **反对vibe编码的观点**： - pyman指出，vibe编码产生的代码往往是“遗留代码”，这些代码难以维护且寿命短暂，容易导致技术债务。他强调了不同开发阶段（如MVP、产品原型等）的区别，认为vibe编码往往混淆了这些概念，导致不良后果。 - hibikir进一步指出，所有代码最终都会变成遗留代码，vibe编码只是加速了这一过程。快速生成更多代码只会增加维护负担。 - ChrisMarshallNY提到，很多项目最初被认为是“用完即弃”的，但管理层往往最终将其作为正式产品发布，导致后续维护困难。 • **技术与工程标准的讨论**： - bdangubic作为一名资深软件工程师，认为无论是“vibe编码”还是其他人工编写的代码，大多数代码库都有类似的问题，表明编码质量与开发者经验无关。 - apimade批评了软件工程行业缺乏标准化和责任制，指出大多数组织中的代码问题并非vibe编码独有，而是普遍存在。 • **对未来编程方式的设想**： - mr_donk提出，未来的编程语言可能不再以人类可读为目标，生成的代码只需执行任务，而不必考虑可维护性。 - extr指出，软件开发正在向“以完成任务为目标”的方向发展，而不是追求数学上的正确性或优雅的代码设计。 补充讨论： • **历史对比与技术演进**： - tux1968将vibe编码现象与历史上Microsoft Access和Excel的广泛使用相比较，指出非专业开发工具的历史反复出现，并推动了专业开发者提高自己的标准。 • **术语与概念的争议**： - hugs认为“vibe编码”这一术语可能会像“云计算”一样，逐渐扩展其含义，最终被广泛使用甚至滥用。 争议的焦点： • 争议的核心在于vibe编码是否是有效的软件开发方式。支持者认为它能快速验证商业想法，反对者则担心其产生的代码质量低劣，导致技术债务和维护困难。同时，关于未来编程方式及行业标准的讨论也反映了开发者对软件工程现状与发展的不同看法。

文章摘要

本文讲述了一位嵌入式软件开发者在转向硬件设计（PCB设计）过程中遇到的组件管理问题及解决方案。起初，作者通过模块化和简化设计原则（如DRY和KISS）成功设计了电路，但随着使用多达40种不同组件的电路板增多，组件库存管理变得混乱。为解决这一问题，作者开发了一个开源的BOM（物料清单）管理工具，结合Gridfinity网格存储系统，利用3D打印的网格收纳盒管理组件。该工具通过可视化界面展示组件位置，支持从Altium Designer导入BOM，并能批量管理库存。未来，作者计划增加BOM批量采购导出功能和网格布局自定义等功能，以进一步提升工具的实用性。

文章摘要

**Optician Sans**是一款基于历史上眼科视力表和视标设计的免费字体。它由Adobe的首席设计师Khoi Vinh主导，灵感来自1862年荷兰眼科医生Snellen创建的视力表和1959年Louise Sloan设计的无衬线字母，并根据LogMAR图表的视觉原理进行调整，以确保可读性和功能性。该字体旨在为所有用户提供最佳的可视性，包含基本拉丁字母和可选替换字符，以实现更一致的外观。Optician Sans根据SIL开放字体许可证发布，可在GitHub上免费获取，并提供相关资源用于博客或网站展示。该项目由ANTI Hamar和字体设计师Fábio Duarte Martins共同创建。

Fixing Ctrl+C in Rust terminal apps: Child process management

文章摘要

本文讨论了在Rust终端应用程序中处理Ctrl+C中断时遇到的终端损坏和子进程管理问题，并提供了相应的解决方案。主要问题包括终端状态损坏、子进程输出干扰、挂起的后台进程以及竞争条件。文章提出了以下解决方法： 1. **进程输出代理**：将子进程输出重定向到日志系统，避免直接输出到终端。 2. **终端状态管理**：确保应用程序退出时恢复终端到原始状态，使用`crossterm`库实现跨平台终端操作。 3. **优雅的进程终止**：先尝试使用`SIGTERM`优雅关闭进程，必要时再用`SIGKILL`强制终止，并设置超时。 4. **线程安全的状态指示器管理**：协调交互元素与子进程输出，防止同时写入终端导致字符格式错误。 此外，文章还提供了测试策略和常见陷阱的避免方法，强调从一开始就实现这些模式以避免终端问题。

评论摘要
主要讨论点：Rust及终端应用程序中子进程的管理与清理问题，包括信号处理、进程间关系及不同操作系统间的差异。 不同观点： • [duped] 认为Rust中管理子进程并不容易，提出应为子进程分配新的pty，特别是当stdout是tty时。同时提到Linux中的一些特定技术（如PR_SET_PDEATHSIG和PID namespaces）可以避免维护子进程的注册表，并指出SIGKILL信号的特殊性。 • [silon42] 质疑应用程序是否应负责清理工作，认为这应由shell或终端解决，并提到像"kill -9"这样的情况。 • [mook] 指出在Windows系统上处理这些问题的不同之处，尤其是缺乏Unix信号机制，只有类似于SIGKILL的机制，但可以选入类似SIGINT的处理。 • [anp] 认为这些问题不仅限于Rust，其他语言的终端程序也会遇到，但希望Rust库在保持终端一致性上更加防错。 • [vlovich123] 强调这些问题与语言无关，适用于任何生成子进程的终端应用程序。 • [koakuma-chan] 询问主进程退出后，子进程是否还能继续运行并写入stdout/stderr。 补充讨论： • [rendaw] 提到代码可读性问题，认为代码片段的对比度不足，影响阅读体验。 • [windowshopping] 提到标题容易引起误解，但最终避免了歧义。 • [npalli] 讨论了Rust的并发处理能力，认为在生命周期管理、线程协作和整体人体工学方面，现代C++可能更胜一筹。 争议焦点： • 应用程序是否应负责子进程的清理工作，还是应由操作系统或终端处理。 • Rust在处理子进程管理时的复杂性与其他语言或操作系统（如Windows）的差异如何解决。

Friction and Not Being Touched

文章摘要

文章讨论了现代人工智能（AI）系统被描绘成“万能机器”（Everything Machines）的现象。这些系统被宣传为能解决一切问题，无论失败都是因为使用不当或技术不足，而不是系统本身的局限性。这种观点脱离了AI实际能力的物理和技术现实。同时，文章探讨了“无摩擦性”（frictionlessness）的概念，在科技领域，无摩擦通常被视为理想状态，但作者认为摩擦在社会和认知层面有重要作用。摩擦让我们感受到他人的存在、观点和需求，是社会互动的一部分。无摩擦性则体现了自我的、孤立的心态，让人不必承认或接触他人。AI作为万能机器的叙事本质上反映了这种不愿被他人“触碰”的心态，避免了人与人之间的互动和必要的摩擦，最终可能导致个体与社会的隔离。
