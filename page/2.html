Voxel Space

作者: davikr | 评分: 171 | 评论数: 22 | 发布时间: 2026-05-30 14:25
文章摘要

这篇文章介绍了Voxel Space渲染引擎的工作原理。1992年NovaLogic发布的游戏《Comanche》采用了这项技术,在当时呈现出惊艳的地形图形效果。 Voxel Space是一种2.5D引擎,使用高度图和颜色图来表示地形。其核心算法非常简单:从远到近绘制,对每个距离的扫描线进行光栅化,根据透视投影计算高度,然后绘制垂直线条。这种"画家算法"能够自然处理遮挡关系。 文章提供了基础渲染算法和添加旋转功能的Python代码示例,展示了如何用极少的代码实现地形渲染。这种技术虽然无法表现复杂几何体,但在CPU性能有限的年代实现了出色的视觉效果。

评论摘要
主要讨论点：关于Comanche游戏（1992）使用的体素地形渲染技术的回顾与技术讨论 不同观点： • **技术定义争议**：nine_k指出这并非真正的体素技术，而是高度图（height map）加棱柱的实现，类似Doom地图，每个棱柱有固定大小的正方形底面 • **渲染算法争议**：Jare质疑文章提到的"画家算法"说法，认为Comanche实际使用从前到后的渲染方式，没有过度绘制 • **技术影响范围**：binarymax询问Magic Carpet（1994）是否使用相同算法；totetsu好奇Excel隐藏飞行模拟器是否也用此技术 补充讨论： 多位开发者分享了复制该技术的经历（mft_用VB、Panzerschrek做动态高度图演示、a1o移植到AGS引擎）；superjan从游戏首个任务中提炼出"最小化测试"的编程理念；tdeck注意到颜色贴图内置阴影实现3D斜面效果；多人表达怀旧情感，mthoms详细回忆了青少年时期自学实现该算法并优化性能的经历，包括发明查找表和位移加法技巧。

wolfSSL releases a new product; wolfCOSE a zero alloc C embbedded COSE stack

作者: aidangarske | 评分: 65 | 评论数: 3 | 发布时间: 2026-05-30 20:42
文章摘要

wolfCOSE 是一个轻量级 C 语言库，基于 wolfSSL 实现了 CBOR 和 COSE 标准。主要特性包括：支持全部 6 种 COSE 消息类型（Sign1/Sign、Encrypt0/Encrypt、Mac0/Mac）、后量子签名算法 ML-DSA、40 种加密算法、零动态内存分配、极小体积（最小 7.5KB）、RAM 占用不到 1KB。支持的算法涵盖签名（ES256/384/512、EdDSA、RSA-PSS、ML-DSA）、加密（AES-GCM/CCM、ChaCha20-Poly1305）、MAC（HMAC、AES-MAC）和密钥分发。依赖 wolfSSL v5.8.0+ 作为加密后端，提供完整的构建配置和测试工具，通过 CI 进行全面测试和 MISRA C 合规性检查。

评论摘要
主要讨论点：wolfCOSE库的技术特性和性能声明的准确性 不同观点： • **背景说明派（magicalhippo）**：提供技术背景，解释COSE是基于CBOR的对象签名和加密标准，类似于JSON的JOSE标准，帮助不熟悉的人理解上下文 • **技术质疑派（Neywiny）**：对项目README中的性能声明提出两点批评： - .text大小数据缺乏关键信息（架构、编译标志、编译器）而变得无意义 - "零分配"的声明具有误导性——虽然.bss和.data段为零，但实际在栈上分配了大量内存（数百到数千字节），特别是在嵌入式环境中这是重要的资源消耗 补充讨论：Neywiny通过具体代码示例和嵌入式开发经验（如sscanf函数导致栈溢出的常见问题）说明了栈分配在资源受限环境中的实际影响，强调"零分配"应该包括栈分配的考量，而不仅仅是堆分配。这反映了嵌入式开发中对内存使用精确性的高要求。

文章摘要

这是对苹果Mac创始人Jef Raskin的采访。Raskin是苹果31号员工，创立了Macintosh项目并推广了图形用户界面，1981年乔布斯接管项目后离开。他强调Mac的设计理念是"简单易用的一体机"，通过商业案例说服管理层支持项目。Raskin批评现在的Mac系统过于复杂臃肿，与Windows差异不大，偏离了最初"以人为本"的设计原则。他澄清自己从未反对图形界面，只是不喜欢鼠标这种特定输入设备。他认为当前Mac需要修复的是界面，而非外观设计。

评论摘要
主要讨论点：Jef Raskin在Macintosh项目中的真实角色和贡献 不同观点： • **Raskin是启动者但非最终产品之父**：Raskin创立了Mac项目并组建了优秀团队（招募Bill Atkinson、Burrell Smith等），但最终Mac产品与他的愿景大相径庭。他反对68000处理器（偏好较弱的6809）和鼠标（偏好元键），1981年离开后项目几乎没采用他的想法 • **Jobs拯救了Mac项目**：有评论认为Raskin版本的Mac会是商业灾难，只适合Raskin自己使用。Jobs接手后做出正确决策，将Mac打造成平价版Lisa，鼠标的简洁性至关重要 • **Raskin的独立成就**：他离开Apple后创造了Canon Cat，采用纯文本界面、无鼠标无图标，完全不同于Mac，证明了他坚持自己的原始愿景 • **Raskin作为思想家的价值**：多位评论者推崇他的著作《The Humane Interface》和文章"Intuitive Equals Familiar"，认为是UI设计的经典必读，影响深远 补充讨论：有人质疑Raskin在2005年访谈中提到的"十年后会普及"的技术是否真正实现；也有人提到采访者似乎对事实了解不足，让Raskin感到不耐烦

Openrsync: An implementation of rsync, by the OpenBSD team

作者: sph | 评分: 361 | 评论数: 18 | 发布时间: 2026-05-30 10:51
文章摘要

这是 openrsync 项目的 README 文档。openrsync 是一个采用 BSD 许可证的 rsync 实现，与现代 rsync（协议 27）兼容但仅支持部分命令行参数。该项目已合并入 OpenBSD 基础系统，最初为 RPKI 验证器 rpki-client 项目开发。 核心算法包含发送端和接收端两部分：发送端管理源文件，接收端管理目标文件。双方共享文件列表（包含文件名和元数据），独立按字典序排序后，通过"块交换"机制同步文件。接收端遍历文件列表向发送端请求更新，发送端扫描并返回需要更新的数据块。 项目支持 OpenBSD 及其他 UNIX 系统，提供完整的安装和使用文档。

评论摘要
主要讨论点：OpenBSD开发的openrsync作为rsync替代方案的必要性、兼容性和安全性 不同观点： • **支持派**：认为openrsync是对原rsync"vibecoding"（AI生成代码）问题的必要回应。原rsync代码库出现AI代码导致回归问题，openrsync提供了更可靠的替代方案。macOS 15.0已采用此版本。 • **质疑派**：认为原rsync已是GPL开源软件，重新实现意义不明。质疑为何要"为资本服务"而重复造轮。 • **技术关注派**：指出openrsync依赖OpenBSD特有的pledge(2)和unveil(2)安全机制，在Linux等其他系统上可能缺失关键安全保护。担心没有这些机制时处理网络数据的风险。 • **兼容性担忧派**：openrsync不支持新rsync协议特性（如64位时间戳），无法在新文件系统间同步元数据。部分命令行为与原版不一致（如路径处理）。早期版本缺少--exclude、-z等常用选项。 补充讨论： - 实际使用反馈整体正面，多数场景可直接替换 - 该项目源于RPKI验证器开发需求 - 存在Go语言的第三方实现 - 对命令行工具稳定性的重视：用户更倾向选择变动少的工具

评论摘要
主要讨论点：关于jabber.ru遭受TLS中间人攻击的技术分析和证书安全机制的讨论 不同观点： • **攻击方式解释**（aleksejs）：攻击者通过重定向流量控制了IP地址，无需RCE漏洞即可正常申请合法证书，因为他们实际控制了域名指向的IP • **Web PKI架构缺陷**（0xbadcafebee）：当前TLS CA系统存在至少14个安全漏洞，任何CA都能为任意域名签发证书。提出应改革架构，让域名注册商成为唯一授权源，但因涉及利益相关方过多，改革难以推进 • **技术细节纠正**（nl, edelbitter）：有人指出这不是"平行重构"而是逆向工程攻击；另有人批评ACME客户端常以过高权限运行，认为应采用最小权限原则 • **安全建议**（codedokode）：强调应只使用端到端加密（E2EE）通讯工具 • **质疑与困惑**：perching_aix质疑讨论中存在误导性总结，暗示CA与国家勾结但实际情况不同；ls612困惑证书透明度机制为何未能防止此类攻击；TZubiri询问哪些合法拦截供应商能破解HTTPS 补充讨论：核心争议在于现有证书体系的根本性缺陷与改革可行性之间的矛盾

文章摘要

这篇文章主要讨论LangGraph框架的适用场景和架构设计要点。核心观点包括: **LangGraph本质**:一个用于构建有状态、多步骤AI工作流的图框架,通过节点(工作单元)和边(路由逻辑)组织逻辑,关键特性是状态管理、检查点和人工审核集成。 **适用场景**:当决策逻辑依赖前序步骤输出、多个AI调用需共享状态、需要人工审核节点,或工作流需根据运行时结果动态调整路径时,LangGraph才有价值。对于确定性工作流,Airflow/Prefect更合适;简单场景用纯Python即可。 **设计关键**:在编码前需明确三点——状态模式(节点间共享的上下文)、边路由逻辑、人工审核点。文章强调不要盲目跟风使用框架,而应根据问题复杂度选择合适工具。
