How to Think About Time in Programming

作者: rmason | 评分: 83 | 评论数: 18 | 发布时间: 2025-06-24 20:01
文章摘要

这篇文章讨论了编程中处理时间的复杂性，强调了“持续时间”和“瞬间”两个关键概念。持续时间指的是时间段，如博尔特跑完100米的时间，而瞬间指的是某个具体的时间点，如他冲线的那一刻。文章提出了“绝对时间”的概念，通过从某个参考点（称为“纪元”，如Unix时间从1970年1月1日开始）计算秒数来表示时间点。 文章还介绍了“民用时间”，如公历，它是用于标记时间的高级语言和标准。公历通过年月日时分秒来表示瞬间，并根据特定规则递增。虽然这些表示法对人类友好，但在编程中直接使用可能会导致问题，因此建议使用“秒从纪元”的模型来处理时间，以方便计算机进行计算和比较。 文章最后提到，虽然不同系统可以使用不同的纪元，但通过定义参考点，不同时间系统可以互操作。

评论摘要
主要讨论点：时间，特别是闰秒、时区和时间管理的复杂性及其在技术系统中的实现问题。 不同观点： • **Google的闰秒处理方式**：[yen223]指出Google通过将闰秒“分散”到一天中的每一秒，而不是在一天结束时增加一个额外的秒（23:59:60）。这种方法可以避免计算机系统出错，因为每一秒增加的量在NTP的误差范围内。 • **时间整体的混乱性**：[Flundstrom2]认为时间管理一直很混乱，涉及时区、夏令时、日历转换（如儒略历到格里高利历）、甚至有些国家忘记插入闰日等问题。这些问题使得时间管理更加复杂。 • **时间在编程中的挑战**：[karmakaze]提到系统时钟漂移和时间信息的消费方式对于准确性至关重要，特别是在处理照片等数据时。选择保存本地日期时间和字符串表示而不是自动调整的时间格式可能更合适。 • **UTC的命名和未来闰秒的处理**：[wpollock]补充UTC并不是缩写，并提到由于闰秒在数据中心引起的混乱，未来可能不再使用闰秒。这提供了一个关于时间标准未来发展的视角。 • **相对论效应对时间的影响**：[smurpy]提到地球运动导致的相对时间损失，目前在地球上还不明显，但在星际航天器中可能需要考虑。 • **不同时间处理需求**：[klabb3]作为程序员，将人类时间和时区视为近似值，更多关注持续时间和事件先后关系，并强调在分布式系统中处理时间的复杂性。 补充讨论： • **时间系统的技术资源**：[foota]和[quantike]提供了关于时间编程的资源链接，为深入了解时间管理和同步问题提供了参考。 • **时区数据库更新的延迟**：[nzach]提到时区规则更新缓慢可能导致系统混乱，特别是在DST规则变化时，很多系统没有及时更新。 • **单调时间的重要性**：[a_t48]强调了在经历糟糕的时间同步配置后，使用单调时间的重要性。 • **Unix时间的误解**：[zokier]指出Unix时间不应被简单视为自纪元以来的秒数，而应看作天数和秒数的组合，以避免误解。 • **夏令时对数据可视化的影响**：[glorbx]提到夏令时对数据可视化（如年天气图表）的影响，如何处理闰日和月份分隔问题令人困扰。 争议焦点： • 时间的混乱性及其在不同系统中的实现问题，特别是闰秒和时区变化带来的挑战，是讨论的主要争议点。不同的处理方法反映了技术社区在面对这些复杂问题时的不同解决方案。

Subsecond: A runtime hotpatching engine for Rust hot-reloading

作者: varbhat | 评分: 103 | 评论数: 7 | 发布时间: 2025-06-24 18:58
文章摘要

Subsecond是一个用于Rust应用程序的热补丁库，允许在不重启应用的情况下更改运行中的代码，特别适用于游戏引擎和服务器等长时间运行的应用。它通过跳转表实现函数调用重定向，不修改进程内存，确保安全性。使用时需配合第三方工具如Dioxus CLI，通过`dx serve`命令启用热重载。当前版本仅支持对主crate的补丁，不支持跨工作区和结构体热重载，且对全局变量、静态变量和线程局部变量的处理存在限制。未来计划增加完整工作区支持并改进线程局部变量的处理。在调试模式下使用不会影响性能，适合开发阶段应用。

评论摘要
主要讨论点：Rust热补丁技术的实现、优缺点及其与其他语言解决方案的比较 不同观点： • jkelleyrtp（创作者）: 介绍了热补丁技术的基本实现，包括手动驱动`rustc`、比较编译间的差异逻辑、以及对符号的打补丁等。该技术跨多种平台工作，并且在作者的机器上实现了130ms的编译补丁时间。它处理了传统dylib重载无法解决的难题，如TLS、静态变量、构造函数等。创作者还提供了多个演示链接，并表示详细文档即将发布。 • modeless: 指出该方案需要预先用特殊包装函数"call"来包裹所有可能需要更改的代码，这相比其他语言的解决方案（无需特殊注解即可修改任何函数）显得不那么吸引人。 • written-beyond: 表达了对Rust动态库（dylibs）实现的期望，尤其是希望有一种无需大量使用unsafe代码的插件系统，能够动态加载实现特定版本特性的库以改变行为。 • cyberax: 询问是否可以为Go语言实现类似的功能。 • weinzierl: 赞赏该技术的实现，但指出文档中提到的需要在源代码中修改函数调用以进行热补丁的方式可能是个大问题。尽管这种修改在发布版本中不会产生额外成本，但仍让人不愿在代码中到处添加这种调用。 • mmastrac: 表示会尝试将该技术应用于自己的Rust服务器项目，特别是为了加速编辑-编译-运行周期。认为选择一个好的"切换点"在代码库中并不难，但承认该技术目前只允许对主crate进行热补丁，这不太理想，不过可能通过改变代码结构来适应。 • prideout: 认为更倾向于使用dylib来实现可重载的部分，而不是当前的方案。 补充讨论： - 热补丁技术在不同语言中的实现和优缺点比较是一个重要的讨论点。 - 文档和实现细节，特别是对代码修改的要求，是用户关注的重点。 - 跨平台支持和处理复杂情况（如TLS、静态变量等）的能力被视为该技术的亮点。 - 关于只允许主crate热补丁的限制被认为是一个潜在的缺点，但可通过代码结构调整来缓解。

文章讨论了在语言模型中用更通用的方法替代** tokenization（ token化）**的必要性和可能性。Tokenization目前是文本处理的关键步骤，用于将文本分割成可处理的单元，但存在诸多问题，如对模型效率和表现的负面影响。文章回顾了tokenization的局限性，如对某些字符或词汇的处理不当，导致模型表现不佳，并举例说明了一些失败案例。作者主张采用更通用的方法，如**Byte Latent Transformer**，以更好地利用计算资源和数据，减少对人为设计方法的依赖。文章总结了tokenization问题的普遍性及其在多模态模型中的挑战，呼吁转向更通用、可扩展的解决方案，以应对未来更复杂的任务。

评论摘要
主要讨论点：LLM（大语言模型）中的 tokenization（ token 化）技术及其局限性和改进方向。 不同观点： • **Tokenization 在数学运算中的局限性**：smeeth 指出，tokenization 在处理数学和逻辑运算时存在问题，这可能是导致 LLMs 在数学问题上表现不佳的原因。当前的评估指标（如 BPB/perplexity）并不足够全面，需要针对 tokenization 方案设计专门的数学/逻辑基准测试。 • **增加网络深度 vs 上下文窗口大小**：marcosdumay 认为，增加网络深度可以提升模型性能，但当前模型的训练成本极高，且与产生的价值不成正比。同时，模型的上下文窗口大小是限制其智能表现的一个主要障碍。 • **混合 tokenization 方案**：broses 提出了一种混合 tokenization 的想法，利用学习权重来优化模型性能，通过部分 tokenization 和 beam search 找到最可能的 tokenization，进而提升模型处理效率。 • **计算资源的消耗与简单解决方案**：cheesecompiler 指出，过度依赖计算资源可能掩盖简单、更普遍的解决方案，过度投入某一范式（如 LLMs）可能会阻碍对底层结构的探索。 • **tokenization 的理论瓶颈**：Scene_Cast2 认为，tokenization 在预测下一个 token 时存在理论上的瓶颈，即使有 15k 独特 token 和 1k 维度的嵌入，模型的输出概率分布的表达力仍然受限于 1k 个独特的线性成分。 • **Tokenization 作为预处理的优势和局限**：resters 指出，tokenization 作为数据预处理方法有其问题，但在跨领域应用中仍然有用。人类可以直接读取 token，且模型应能够克服特定 tokenization 方案的局限。 • **简单统计 vs 专家模型**：pona-a 提到，tokenization 已经有过一次“苦涩的教训”，即让简单的统计方法引导分割比依赖专家模型更有效，当前可能需要另一个“苦涩的教训”。 • **Bytes 作为 tokenization 的局限性**：fooker 认为，bytes 作为 tokenization 方案未必是最佳选择，针对数学、推理、视频等任务可能需要更好的 tokenization 方案。 • **LLM 对 token 的计数能力**：andy99 对 LLM 能否通过 token 计数来解决某些问题提出质疑，指出 LLM 并不能“看见”文本，也不一定擅长计数。 • **对“苦涩的教训”的反思**：blixt 认为，“苦涩的教训”是在批评那些首次尝试未果的人，虽然工程技术在发展过程中会经历削减和重构，但并非所有问题都能通过简单地增加计算资源解决。 • **字节级 tokenization 的有效性**：kgeist 提到，GPT-3.5 对 Cyrillic 字母的处理表明字节级 tokenization 在某些语言（如俄语）上的有效性。 补充讨论： • **UTF-8 的挑战**：perching_aix 幽默地提到，未来模型可能会在处理 UTF-8 编码时遇到困难。 争议焦点： • **Tokenization 是否需要更复杂的解决方案**：一些评论者认为当前的 tokenization 方案（如 bytes）存在局限，需要更复杂或更智能的方案来提升模型性能，而另一些人则认为简单统计方法已经足够有效，复杂化未必是最佳路径。 • **增加计算资源是否是最佳策略**：部分评论者质疑通过增加计算资源来提升模型表现的策略，认为这可能掩盖更简单的解决方案，并阻碍对其他潜在方法的探索。
