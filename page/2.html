One year of Roto, a compiled scripting language for Rust

作者: Hasnep | 评分: 38 | 评论数: 4 | 发布时间: 2026-05-29 14:07
文章摘要

Roto是一个为Rust应用设计的JIT编译嵌入式脚本语言。过去一年主要进展包括：发布6个新版本，增加了while/for循环、List类型、枚举、字符串格式化等语言特性；语法向Rust靠拢（如使用fn和//注释）；通过library!宏大幅简化了Rust类型和函数的注册流程；设计了新logo；改进了使用手册；在EuroRust和FOSDEM会议上做了演讲；项目迁移到Codeberg平台。Roto相比其他脚本语言的优势是静态类型和JIT编译，性能更优，同时与Rust深度集成。

评论摘要
主要讨论点：Roto语言（一个Rust编写的脚本语言）的性能表现和设计选择 不同观点： • **性能关注派（ianm218）**：通过基准测试发现Roto在处理List迭代时比标量计数器慢21倍（590ms vs 28ms），质疑其性能优化方向和基准测试方法，愿意贡献更多性能测试代码 • **语言设计批评派（pveierland）**：认为Roto将IP地址、IP前缀、AS号码等网络概念作为语言内置字面量是有问题的设计。这种特定领域的内置类型会增加混淆、作用域不清晰，并可能导致类似YAML挪威问题的边界情况。建议这些功能应通过扩展/宏/库来实现，而非语言核心特性。以Nix语言的URI字面量为例说明这类设计最终会被弃用 • **实用功能需求派（evrimoztamur）**：关注Roto运行时是否支持serde序列化。基于在游戏引擎中使用Lua的经验，指出无法序列化运行时状态（用于保存/加载游戏会话）是一个重大问题 补充讨论：三位评论者从不同角度审视Roto：性能效率、语言设计哲学、实际应用需求，但彼此之间未形成直接对话或争论。

文章摘要

微软Office 2019和2021 Mac版将于2026年7月13日因许可证验证证书过期而降级为"只读模式"，用户只能查看文件但无法编辑或保存。微软在2023年曾承诺Office 2019停止支持后会"继续正常运行"，但2026年5月悄然修改了该声明，删除了这一保证。Office 2019 Mac版无法通过更新解决此问题，而Office 2021用户可升级到16.83版本避免降级。Windows和Android版本不受影响。此举被批评为微软违背了对永久许可证用户的承诺。

评论摘要
主要讨论点：微软计划终止Mac版Office永久许可证，引发用户对消费者权益和商业道德的广泛质疑 不同观点： • **法律违规论**：认为此举违反澳大利亚等地消费者保护法，侵犯了"不受干扰的产品占有权"和"产品符合宣传用途"的权利，可能引发集体诉讼 • **AI许可策略论**：推测微软急于废除永久许可是因为AI实验室用单一许可运行数千个agent，微软希望每个agent实例单独付费，加速向订阅制转型 • **用户抵制论**：大量用户表示将转向LibreOffice等替代品或彻底放弃Office，强调"愿意付费但拒绝订阅制"的立场。有用户提到21年累计购买4次永久许可 • **盗版悖论**：指出盗版版本反而更符合原始购买合同，讽刺正版用户权益受损 • **技术借口质疑**：虽然官方解释是Apple分发证书过期，但用户普遍认为这是商业策略而非技术限制 补充讨论：部分评论讽刺微软此举反而为苹果iWork套件和MacBook销售做了"免费广告"，体现出用户对科技巨头"敌视客户"趋势的失望

文章摘要

咨询公司埃森哲(Accenture)以12亿美元从Ziff Davis收购了Downdetector和Speedtest两个平台。这两个网站分别用于检测在线服务故障和测试网速。埃森哲CEO表示将利用Ookla(Speedtest母公司)的数据帮助客户安全地扩展AI应用。Ookla于2014年被Ziff Davis收购,旗下还有网络设计软件Ekahau和移动网速测量平台RootMetrics。交易完成后,埃森哲将继续维持Ookla现有业务运营,同时将其数据应用于云服务和AI领域。该交易仍需监管部门批准。

评论摘要
主要讨论点：Accenture以11亿美元收购Ookla（Speedtest母公司）的商业价值和合理性 不同观点： • **数据业务价值派**：前竞争对手和内部员工指出，真正价值在于向电信运营商出售网络数据，每年收费六位数，全球有数百家大型运营商客户。Ookla每月进行2.5亿次测试，拥有SDK、服务器网络和驱动测试公司，数据来源远超消费者认知 • **技术简单派**：多位评论者认为这些产品技术门槛不高，周末就能编写出来。特别是Downdetector被形容为"只是带留言板和计数器的网站目录"，质疑11亿美元估值过高 • **信任危机派**：担心Downdetector被咨询公司控制后会失去独立性，可能隐瞒Accenture客户的宕机信息以保护SLA承诺，建议转用其他替代服务 • **创业价值派**：承认技术简单但强调18年用户积累、企业销售策略和品牌建设的难度，认为这是长期努力的结果 补充讨论：部分评论者推荐替代服务（如挪威政府的nettfart.no、speedof.me等），也有人对Accenture企业文化表示质疑，称其"类似邪教"。

文章摘要

Racket v9.2 已于2026年5月27日发布。主要更新包括： **重要变更**： - `match` 表单增强了非线性模式检查，可能导致现有代码失败 - Typed Racket 修复了 `asin` 和 `acos` 的类型处理，可能导致编译时错误 - 支持 Unicode 17.0 - 新增 `#%foreign-inline` 核心语法形式 **其他改进**： - 新增 `terminal-file-position` 函数 - 跨阶段持久化模块支持更多引用数据类型 - Scribble 文档显示优化 - 多项文档改进和错误修复 本版本由30多位贡献者共同完成。

评论摘要
主要讨论点：Racket 9.2 版本发布后，社区成员分享使用经验和对该语言的评价 不同观点： • **怀旧派（submeta）**：强调 Racket（前身 DrScheme）的历史价值，30年前用它学习 Scheme 和 SICP，赞赏其函数式编程特性（闭包、尾递归、函数返回值），对比 Python 的设计缺陷（如 append/sort 返回 None） • **实用派（noosphr）**：聚焦当前应用价值，在工作中用 Racket 原型化深度学习模型的新几何结构，强调其"可重定义任何部分"的灵活性是独特优势，推荐《The Little Learner》作为入门资源 • **妥协派（xiaoyu2006）**：虽然 Racket 是最喜欢的语言，但因生态系统原因实际工作中仍主要使用 Python，暗示理想与现实的矛盾 补充讨论： 评论展现了编程语言选择的三个维度：教育价值（学习范式）、技术能力（灵活性）和实用性（生态系统）。submeta 和 noosphr 都肯定 Racket 的技术优势，但 xiaoyu2006 点出关键问题——生态系统仍是语言采用的决定性因素。montyanne 的评论暗示 Racket 与东北大学的学术渊源。

Openrsync: An implementation of rsync, by the OpenBSD team

作者: sph | 评分: 415 | 评论数: 20 | 发布时间: 2026-05-30 10:51
文章摘要

这是 openrsync 项目的 README 文档。openrsync 是一个采用 BSD 许可证的 rsync 实现，与现代 rsync（协议 27）兼容但仅支持部分命令行参数。该项目已合并入 OpenBSD 基础系统，最初为 RPKI 验证器 rpki-client 项目开发。 核心算法包含发送端和接收端两部分：发送端管理源文件，接收端管理目标文件。双方共享文件列表（包含文件名和元数据），独立按字典序排序后，通过"块交换"机制同步文件。接收端遍历文件列表向发送端请求更新，发送端扫描并返回需要更新的数据块。 项目支持 OpenBSD 及其他 UNIX 系统，提供完整的安装和使用文档。

评论摘要
主要讨论点：OpenBSD的openrsync项目作为rsync替代方案的价值和争议 不同观点： • **支持派**：认为openrsync是及时的替代方案，因为原rsync代码库出现"vibe-coded commits"（AI生成代码）导致质量下降和回归问题；macOS 15.0已采用；对于命令行工具，稳定性比新特性更重要 • **质疑派**：指出openrsync不支持新rsync协议（如64位时间戳），无法在新文件系统间同步元数据；存在行为差异（如目录复制逻辑与原版不同）；命名具有误导性（原rsync本就是GPL开源） • **安全性争议焦点**：开发者强调pledge(2)和unveil(2)安全特性的重要性，但有人质疑这些OpenBSD特性在Linux上的可用性，以及rsync的威胁模型是否真需要这种防护（rsync通常在信任边界内使用，不像curl面对敌对方） • **实用性反馈**：部分用户报告基本可作为drop-in替代，但存在`--exclude`与`--delete`混用等兼容性问题 补充讨论：项目源于RPKI验证器开发需求；存在Go语言实现等其他替代方案；有人认为用AI来避免AI代码的做法颇具讽刺意味

Voxel Space

作者: davikr | 评分: 171 | 评论数: 22 | 发布时间: 2026-05-30 14:25
文章摘要

这篇文章介绍了Voxel Space渲染引擎的工作原理。1992年NovaLogic发布的游戏《Comanche》采用了这项技术,在当时呈现出惊艳的地形图形效果。 Voxel Space是一种2.5D引擎,使用高度图和颜色图来表示地形。其核心算法非常简单:从远到近绘制,对每个距离的扫描线进行光栅化,根据透视投影计算高度,然后绘制垂直线条。这种"画家算法"能够自然处理遮挡关系。 文章提供了基础渲染算法和添加旋转功能的Python代码示例,展示了如何用极少的代码实现地形渲染。这种技术虽然无法表现复杂几何体,但在CPU性能有限的年代实现了出色的视觉效果。

评论摘要
主要讨论点：关于Comanche游戏（1992）使用的体素地形渲染技术的回顾与技术讨论 不同观点： • **技术定义争议**：nine_k指出这并非真正的体素技术，而是高度图（height map）加棱柱的实现，类似Doom地图，每个棱柱有固定大小的正方形底面 • **渲染算法争议**：Jare质疑文章提到的"画家算法"说法，认为Comanche实际使用从前到后的渲染方式，没有过度绘制 • **技术影响范围**：binarymax询问Magic Carpet（1994）是否使用相同算法；totetsu好奇Excel隐藏飞行模拟器是否也用此技术 补充讨论： 多位开发者分享了复制该技术的经历（mft_用VB、Panzerschrek做动态高度图演示、a1o移植到AGS引擎）；superjan从游戏首个任务中提炼出"最小化测试"的编程理念；tdeck注意到颜色贴图内置阴影实现3D斜面效果；多人表达怀旧情感，mthoms详细回忆了青少年时期自学实现该算法并优化性能的经历，包括发明查找表和位移加法技巧。
