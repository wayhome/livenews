Deno 2.8

作者: roflcopter69 | 评分: 304 | 评论数: 21 | 发布时间: 2026-05-22 11:23
文章摘要

Deno 2.8 发布，这是迄今最大的次要版本更新，新增多个子命令： **deno audit fix** - 自动升级有漏洞的 npm 包到最近的补丁版本 **deno bump-version** - 更新 deno.json 或 package.json 中的版本号，支持 patch/minor/major 增量，在工作区中可基于 Conventional Commits 自动推导版本变更 **deno ci** - 专为 CI 环境设计的安装命令，强制使用 lockfile 并在不匹配时报错 **deno pack** - 将 Deno/JSR 项目构建为可发布到 npm 的 tarball，自动转译 TypeScript、生成类型声明文件、重写模块说明符以兼容 npm 生态 升级命令：`deno upgrade`

评论摘要
主要讨论点：Deno 与 Node.js/Bun 的竞争态势，以及 Deno 的发展方向争议 不同观点： • **Deno 优势派**：认为 Deno 的权限模型、TypeScript 原生支持、安全性设计体现了 Unix 精神，是 JS 生态应该前进的方向。适合小型服务和业余项目，性能持续改进令人印象深刻。 • **Node 兼容性必要派**：认为 Deno 加强 Node 兼容性（从 40% 提升到 75%）是正确方向，npm 默认支持和 lib.node 包含使迁移更容易，这些改进让 Deno 更实用。 • **方向转变质疑派**：批评 Deno 为商业原因妥协初心，默认包含 Node 类型污染了 Deno/Web 代码，过度向 Node/NPM 靠拢会失去差异化优势。担心专业项目中途因方向变化被迫回归 Node。 • **生态竞争观察**：Bun 因速度快、标准库全面且被 Anthropic 收购而增长迅速；Node 依然是稳定方案；Deno 的沙箱和导入机制优势已被商品化，吸引力下降。 补充讨论：有开发者建议 Deno 应坚持初始价值观，AI 代理的出现可能缓解技能迁移压力；也有人希望看到 Deno 用于 Python/WASM；项目融资模式（拒绝捐赠）可能带来长期压力。

Wi-Wi is wireless time sync at 1 nanosecond

作者: Brajeshwar | 评分: 81 | 评论数: 5 | 发布时间: 2026-05-20 15:06
文章摘要

Wi-Wi STAMP是日本NICT开发的无线时间同步协议，使用900 MHz频段实现皮秒级时间同步和毫米级距离精度。当前原型达到20ps相位同步抖动和30ns时间同步，下一代将实现5ns精度。该技术体积小巧（智能手机大小），无线范围0.2-5公里，信号穿透力优于GNSS。在NAB展会上展示了两个应用：Meinberg用其实现远程摄像机的黑场时间同步，以及通过三个Wi-Wi单元实现毫米级定位追踪。该技术特别适用于室内或布线困难的场景。

评论摘要
主要讨论点：Wi-Wi（无线双向干涉测量）技术与GPS时间同步的对比 不同观点： • **隐私担忧**（Lammy）：Wi-Wi的双向特性意味着用户获取时间的同时必须暴露物理位置，不如GPS单向广播的隐私保护好——GPS可以在卫星不知情的情况下获取时间和位置 • **技术指标质疑**（NkVczPkybiXICG）：标题声称1纳秒精度，但文章正文实际说的是30纳秒（未来目标5纳秒），存在信息不一致 • **实用性评估**（ectospheno）：当前使用GPS NTP服务器已能达到亚毫秒级同步，PTP设备虽更精确但成本过高，期待Wi-Wi能降低高精度时间同步的价格门槛 • **应用前景**（simulator5g）：Wi-Wi信号穿透性更好，可能显著改善设备电池续航 补充讨论：评论整体对技术持谨慎乐观态度，关注点集中在隐私保护、技术参数准确性、成本效益和实际应用价值上。争议焦点在于Wi-Wi的双向通信机制是否值得用隐私换取更好的信号性能。

Bun support is now limited and deprecated

文章摘要

yt-dlp 项目宣布限制并弃用对 Bun 运行时的支持。主要原因： 1. **版本限制**：仅支持 Bun 1.2.11 至 1.3.14 版本。低于 1.2.11 存在安全隐患（忽略 ejs 锁文件），高于 1.3.14 的版本已用 Rust 重写且采用 AI 编码方式。 2. **弃用决定**：Bun 最近使用 Claude AI 重写为 Rust 版本，开发方向转向"vibe-coded"（凭感觉编码），这让维护者担忧未来的兼容性和维护负担。 3. **后续计划**：虽然暂时保留有限支持，但保留完全移除 Bun 支持的权利。

评论摘要
主要讨论点：Bun项目使用AI辅助将代码从Zig重写为Rust，yt-dlp项目因此决定弃用Bun，引发关于AI辅助编程（"vibe coding"）可靠性的争议。 不同观点： • **支持AI辅助开发派**：认为应该基于软件实际表现（bug数量、安全漏洞）而非开发方式来评判。强调LLMs在代码翻译方面表现良好，且能提升开发效率。类比为"因不喜欢作者用的编辑器就拒绝使用软件"一样不合理。 • **质疑AI重写质量派**：指出100万行代码无法在短时间内充分审查，担心maintainer无法真正理解非人工编写的代码库。认为AI生成的Rust代码包含大量`unsafe`代码，会持续引发问题。 • **反对过早决策派**：质疑yt-dlp在Rust重写版本尚未发布、没有实际数据支撑的情况下就做出弃用决定，认为应该等待实际测试结果。 • **中立/实用主义派**：认为软件本身就是有观点的，开发者有权选择自己的"艺术许可"。同时指出需要更精确的术语来描述LLM辅助开发的不同程度。 补充讨论：部分评论关注Zig vs Rust技术选择、yt-dlp实际使用场景（主要用Deno而非Bun），以及对当前互联网讨论极化现象的感慨。
