My LSM tree was slower than a B-tree. Then I profiled it

作者: aasheeshrathour | 评分: 11 | 评论数: 5 | 发布时间: 2026-06-15 15:42
文章摘要

作者为理解RocksDB的存储引擎原理，用Go实现了一个LSM树。初始版本写入性能仅25万次/秒，远低于B树数据库BoltDB。通过性能分析逐步优化： 1. **写入系统调用优化**（34%→2.16%）：将WAL日志改用内存映射（mmap），避免频繁系统调用 2. **GC和排序优化**（48%消除）：将压缩过程从"加载全部数据后排序"改为流式k路归并，使用最小堆逐个处理已排序的SSTable 3. **布隆过滤器bug修复**：修正了压缩后布隆过滤器大小计算错误，该bug导致读取性能显著下降 最终将写入性能从25万次/秒提升至近200万次/秒。核心经验：通过profiler定位瓶颈，逐个解决，而非凭猜测优化。LSM树通过将随机写转化为顺序写来超越B树的写入性能。

评论摘要
主要讨论点：关于LSM树实现中的性能问题和设计缺陷 不同观点： • **代码推理派（Retr0id）**：认为100位布隆过滤器存储10万个键会立即饱和，这种问题应该在编码前通过推理发现，而不是靠"vibecoding"（盲目编码）后测试才发现 • **AI代码质量质疑（teraflop）**：指出项目的基准测试程序明显是AI生成的，暗示整个项目的代码质量可能存在问题 • **持久化必要性（jmalicki）**：强调每次写入都必须写磁盘以保证数据持久性，讽刺那些为了性能牺牲可靠性的做法（"/dev/null是更快的数据库"） • **技术细节分析（dj_axl）**：怀疑布隆过滤器的配置问题，可能是误设置了最大假阳性率或BloomFalsePositive参数未被正确使用 • **异步写入方案（AtlasBarfed）**：建议采用Cassandra的做法，将写入放入队列后续压缩处理 补充讨论：核心争议在于基础设计错误（布隆过滤器容量设置）与实现方法论（先设计后编码 vs 测试驱动），以及性能与可靠性的权衡。

Show HN: Gerrymandle - Daily puzzle game where you redraw electoral districts

文章摘要

**Gerrymandle游戏玩法与背景（198字）** 这是一个模拟划分选区的策略游戏。玩家需点击相邻格子组成选区，每个选区必须连续且大小相同，所有房屋都要被分配。彩色房屋代表不同党派选民，获得最多房屋的党派赢得该选区。目标是让你的党派赢得最多选区。 游戏揭示了"杰利蝾螈"（gerrymandering）现象：通过操纵选区边界使少数票变多数席位。主要手法是"集中"（将对手选民挤入少数选区）和"分散"（将剩余对手选民分散到各区使其无法获胜）。 现实中，这种做法严重损害民主原则，导致大选失去意义、少数族裔权益受损。美国2020年以来超过25%的国会席位被重新划分，德州、加州等多州频繁操作，选区划分已成为持续的政治工具。

评论摘要
主要讨论点：关于一个Gerrymandering（选区划分操纵）主题游戏的反馈和讨论 不同观点： • **积极评价派**：多数用户认为游戏创意优秀，是教育公民课程的好工具，能有效传达选区操纵概念，寓教于乐地提升公众意识 • **机制改进派**：建议增加新手引导关卡、每日真实历史地图挑战，以及将比例代表制作为可选项来展示替代方案 • **现实主义批评**：指出"平局则无人获胜"规则不符合实际选举情况（实践中不会出现平局） • **制度改革派**：认为应推动比例代表制替代"赢者通吃"制度，从根本上解决选区操纵问题；有人提出增加众议院席位以缩小选区规模，恢复代表与选民的社区联系（建议比例从现在的76万:1降至8万:1） • **技术问题反馈**：多位用户报告SSL证书错误和游戏界面bug 补充讨论： 有用户分享了相关桌游推荐和学术论文（关于公平选区划分的数学方法），显示社区对此议题有深入兴趣。部分用户建议融入投票改革教育内容，如排序复选投票制的效果演示。

The value of employee equity depends a lot on volatility

作者: devanshp | 评分: 9 | 评论数: 2 | 发布时间: 2026-06-18 08:02
文章摘要

这篇文章讨论了初创公司股权补偿的真实价值计算。作者指出，传统计算方法（将股权价值除以4年）严重低估了实际价值，因为员工拥有"嵌入式看涨期权"——可以随时离开表现不佳的公司。 以估值5000万美元的公司为例：如果公司波动性高（5%概率1年内达到10亿美元，95%概率归零），员工预期工作时间仅1.15年却能获得50万美元股权，年化价值43.4万美元，而非简单计算的12.5万美元。波动性越高，这种期权价值越大——3个月高波动情况下年化价值可达114万美元。 当然还需考虑风险厌恶、现金薪酬和心理压力等因素，但从纯收益角度看，高波动性初创公司的股权价值远超表面数字。

评论摘要
主要讨论点：员工股权期权的实际价值 不同观点： • **悲观现实派**（throwway120385）：员工股权价值接近零，只有极少数人（5%）能获益，大多数人（95%）最终一无所获。强调不要被期望值论证误导，因为现实中各公司条件差异巨大，成功概率极低 • **风险提醒派**（gobdovan）：指出期权的额外风险——公司可能在cliff（通常是一年的等待期）到期前一天解雇员工，导致期权完全作废。这是对第一个观点的补充，揭示了期权的制度性陷阱 补充讨论：两位评论者都对员工股权持批判态度，但角度不同。第一位从统计概率质疑股权的整体价值，第二位则揭示了具体的操作风险。两者共同构成对"股权激励"承诺的警示，提醒打工者认清期权可能既没有经济价值，还存在被公司利用的制度风险。

.gitignore Isn't the only way to ignore files in Git

作者: FergusArgyll | 评分: 185 | 评论数: 17 | 发布时间: 2026-06-18 10:29
文章摘要

Git 有三个层级的文件忽略机制： 1. **.gitignore** - 项目级别，会提交到版本库，团队共享 2. **.git/info/exclude** - 仓库级别，不提交到版本库，适合个人工作流中的临时文件（如个人笔记） 3. **~/.config/git/ignore** - 全局级别，机器范围生效，适合操作系统生成的文件（如 macOS 的 .DS_Store） 可通过 `git config --global core.excludesFile` 自定义全局忽略文件路径。使用 `git check-ignore -v <文件名>` 命令可查看某文件被哪个配置忽略。

评论摘要
主要讨论点：Git中除了.gitignore之外的其他忽略文件方法及其适用场景 不同观点： • **支持用户级配置派**：认为IDE、操作系统相关文件应放在~/.config/git/ignore中，避免污染每个项目的.gitignore。项目级.gitignore应只包含构建产物、依赖目录等项目特定内容 • **支持项目级配置派**：认为.DS_Store等文件最好放在项目.gitignore中，因为如果团队有多个Mac用户，统一配置更可靠，不依赖每个人都正确设置个人配置 • **.git/info/exclude的拥护者**：喜欢用它存放个人脚本、Makefile等仅本地需要、协作者不关心的文件 • **质疑exclude实用性者**：认为exclude容易导致问题（"recipe for sadness"） 补充讨论： 评论中分享了实用技巧，如.gitattributes可隐藏package-lock.json的diff、在任意项目创建attic目录存放临时文件、使用git-check-ignore命令调试。有人指出"global"命名容易混淆（实为per-user而非machine-wide）。多位开发者表示此前不知道这些功能，感叹Git的强大。
