Jank now has its own custom IR

作者: DASD | 评分: 166 | 评论数: 7 | 发布时间: 2026-05-15 17:17
文章摘要

jank 引入自定义中间表示（IR），以 Clojure 语义为核心，弥补 LLVM IR 过低层、难优化动态特性的不足。新 IR 可表达 vars、动态调用等高层概念，便于针对 jank 做专门优化，目标是提升性能并与 JVM 竞争。

评论摘要
主要讨论点：围绕 jank/Clojure 原生编译、LLVM 优化能力、JVM 性能基线及动态语言性能权衡展开。 不同观点： • LLVM 工具链演进：有人认为长期基于 LLVM 的编译器最终都会发展出自己的 IR，clang 也在走这条路；因此 jank 自建 IR 属于自然演化。也有人追问为何不直接用 MLIR。 • JVM 基线争议：作者用 OpenJDK 21 做基准，有评论认为到 2026 年应比较 Java 26 的 OpenJDK、OpenJ9、GraalVM，并考虑多次运行后的 JIT 缓存。另有人强调 JVM 性能门槛很高，不应低估。 • 原生编译与 JIT/PGO：针对“原生世界没有 JIT 优化”，有评论指出 PGO 可通过训练运行反馈行为信息，部分承担类似角色；若目标是 WebAssembly、CLR、IBM i 等字节码环境，C/C++ 也可能进入 JIT 场景。 • 动态语义限制优化：多位评论关注 Clojure 的动态类型、GC、多态和间接调用会让 LLVM 难以优化；有人询问在大量 runtime call 降低到 LLVM 后，LLVM 还能否做 DCE 等优化。 • 性能与 REPL 动态性的张力：关于内联，有评论指出一旦函数被内联，REPL 中更新函数定义不会自动影响已编译调用者，除非重新编译，体现动态性与性能的冲突。 • 替代方案与比较对象：有人建议 benchmark 也应参考 Common Lisp、Scheme 编译器；另有人提到 Carp，并询问社区使用情况。 补充讨论：另有疑问是为何不用 C 作为 IR，焦点在于 LLVM IR 相比 C 是否更利于优化，以及是否能准确表达源语言语义。

Show HN: Semble – Code search for agents that uses 98% fewer tokens than grep

作者: Bibabomas | 评分: 279 | 评论数: 36 | 发布时间: 2026-05-17 15:37
文章摘要

Semble 是面向 AI 代理的快速代码搜索库，可用自然语言查询并返回精准代码片段，较 grep+read 节省约 98% token。它纯 CPU 运行、无需外部服务，支持 MCP、Bash、CLI/Python，本地或 Git 仓库，具备毫秒级索引与查询性能。

评论摘要
主要讨论点：围绕 Semble/类似代码搜索工具是否真正提升 AI 编程代理效率、质量与成本，及其与 grep、LSP、项目文档等方案的比较。 不同观点： • 质疑派：认为这类工具可能“让 AI 变笨”。freakynit 测试显示，引入 codebase-memory-mcp 后 token 反而更高，输出质量无提升；其简单 PROJECT.md 索引文件更省。jerezzprime 也指出模型习惯 grep，可能不信任新工具结果而反复重读，抵消节省。 • 基准质疑：esperent 认为很多工具只证明“比 grep 少 token”，但真正应评估端到端任务质量、总成本和速度；其测试中关闭 RTK/headroom 反而更好，因为工具虽降上下文，却增加轮次。 • 节省有限论：cagz、PufPufPuf 认为 grep 输出处理只占总代价小部分，且代理通常不会读完整匹配文件，因此官方节省假设可能夸大。 • 谨慎支持：aadishv 的小测试显示 Semble 有时上下文/成本更低，答案质量相近，但速度可能更慢；不同任务收益不稳定。 • 替代方案：boyter 提出“智能 grep”路线，不建索引，而用排序和代码结构感知；andai 认为小代码库可直接把全目录放进上下文，避免盲搜；derrickrburns 建议索引“seams”（代码接缝）而非一般搜索。 • 其他关注：有人询问与 LSP 的比较、安全/供应链风险、安装文档改进，也有人表达集成和合作兴趣。 补充讨论：争议焦点在于搜索工具的评估指标——单次搜索 token 节省是否足够，还是必须以完整编码会话的质量、成本、速度和模型信任度来衡量。

Prolog Coding Horror

作者: RohanAdwankar | 评分: 156 | 评论数: 12 | 发布时间: 2026-05-17 21:15
文章摘要

文章指出 Prolog 编程应避免几类“恐怖”做法：使用剪切、条件、var 等非纯构造会丢失解；用 assert/retract 修改全局状态会产生隐式依赖；直接打印结果会破坏关系式编程和测试性；依赖 is、>/2 等低级算术会增加理解和教学难度。作者主张保持纯 Prolog：用清晰数据结构、约束（如 dif/2、CLP(FD)）、元谓词和参数传递状态，让顶层输出结果，从而写出正确、可推理、可测试的程序。

评论摘要
主要讨论点：Prolog的实际用途、学习价值，以及相关文章对“编程陷阱/恐怖点”的评价是否过于夸张。 不同观点： • 支持学习与阅读：有人推荐 Markus Triska 的 Prolog 文章，尤其是 meta-interpreters，认为很启发。 • 质疑现实用途：有人说 Prolog 在真实项目里很少见，大学里显得“过于学院派”；也有人提到 OPA/Datalog 更常见。 • 类比与延伸：有人问 Prolog 和 Erlang 的关系，认为早期 Erlang 受 Prolog 启发，像“Prolog + OTP”；另有人建议先理解 four-port model。 • 争议焦点：对“coding horrors”的评价。rtpg 觉得“允许先返回部分错误答案”很有启发，类似在 P≠NP 下接受近似；crustycoder 认为文章表述过头，应叫“需要注意的点”，不是“恐怖”，并举 assertz/retract 在读 JSON+规则场景中并非绝对不可用。 • 疑问与新类比：有人不懂 Prolog 运算符、cut 的含义；也有人戏称 LLM Agent 可能是更强但不精确的“Prolog”。 补充讨论：整体分歧在于 Prolog 是实用工具还是小众学术语言，以及作者是否把风险说得太绝对。
