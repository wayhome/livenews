Ubiquiti launches UniFi OS Server for self-hosting

作者: speckx | 评分: 160 | 评论数: 23 | 发布时间: 2025-07-31 15:24
文章摘要

Ubiquiti发布了UniFi OS Server的早期访问版本，允许用户在自己的硬件上自托管完整的UniFi网络堆栈，初始支持UniFi Network和InnerSpace。与之前的自托管方案不同，UniFi OS Server还支持UniFi Identity。安装要求包括至少20GB的存储空间，Windows需要WSL 2，Linux需要Podman 4.3.1或更高版本，并开放多个指定端口。安装过程相对简单，Windows上通过设置文件安装，Linux可通过命令行安装。服务器启动后可通过localhost端口访问，并支持导入现有网络或恢复备份。当前版本不支持UniFi Protect，但未来有望添加。

MacBook Pro Insomnia

作者: speckx | 评分: 174 | 评论数: 23 | 发布时间: 2025-07-31 14:16
文章摘要

作者使用MacBook Pro Silicon M1 Max多年，一直运行良好。但后来发现笔记本在未连接电源的情况下，夜间电池耗电严重。为解决此问题，作者使用终端命令`pmset -g log`查看电源管理日志，但日志繁杂难读。于是作者编写了一个小工具来分析日志，效果有限。之后，作者尝试调整了一些设置（如`tcpkeepalive`），仍无明显改善。最终，作者使用了一款叫Sleep Aid的工具，发现“Wake for maintenance”选项被禁用，导致频繁唤醒事件。启用该选项后，问题解决，电池不再快速耗尽。

主要讨论点：MacBook 睡眠模式下的电池耗电和设备唤醒问题 不同观点： • atombender 认为，某些应用程序（如 Devonthink）会阻止 macOS 进入睡眠状态，导致设备过热和电池耗尽。他批评苹果的电源管理系统没有对此发出警报，反而对不重要的网络权限问题进行提示。 • sangeeth96 对“Wake for maintenance”选项的状态提出疑问，怀疑原文作者是否写错了选项状态，并讨论了该选项对睡眠模式的影响。 • pauljara 分享了自己的经验，路由器的 DHCP 租期设置过低会导致 MacBook 频繁唤醒以更新 IP 地址，从而引发电池耗电问题。 • teejmya 提出了一种通过设置“hibernate on lid close”来解决睡眠问题的办法，并提供了终端命令供尝试。 • dewey 表示尝试了多种方法仍未解决问题，暗示可能存在其他未被发现的进程导致 Mac 频繁唤醒。 • neilalexander 重申了使用 Activity Monitor 的“Energy”标签来识别耗电应用的方法，认为这是排查问题的有效手段。 • resters 提到自己的 iPad 即使在零使用情况下也只能持续几天，并寻求延长待机时间的解决方案。 • magic_hamster 批评了苹果设备在睡眠状态下仍积极连接无线接口的行为，认为这与常规的睡眠模式定义不符，并指出这是苹果设备的独特问题。 • marifjeren 描述了 Apple Silicon MacBook Pro 在连接 SSD 时睡眠期间过热和电池耗尽的问题，提出通过断开所有外接设备来缓解该问题。 • kylehotchkiss 提供了苹果官方指南链接，指出相关配置选项可能已经存在。 • ectocardia 发现移除 Yubikey（安全密钥）后，MacBook 意外发热和电池耗尽的问题有所改善。 • Doohickey-d 使用了一个自定义脚本，在设备进入睡眠时关闭 WiFi，并在唤醒时重新打开，以避免设备在睡眠期间进行不必要的网络活动。 • paxys 指出，雇主安装的安全软件可能是导致 MacBook 频繁唤醒和耗电的罪魁祸首。 • darknavi 对比了 Intel MBP 和 M2 MBP 的待机电池寿命，表达了对苹果硬件待机表现下降的失望。 补充讨论： • 用户普遍对苹果设备在睡眠模式下的耗电问题表示不满，尤其是某些应用程序或设置导致设备意外唤醒和过热。 • 讨论中提到了多种解决方案，包括修改系统设置、使用终端命令、移除外接设备和自定义脚本等。 • 争议焦点在于苹果电源管理系统的不足，特别是在处理第三方应用程序和无线接口行为方面的缺陷。 • 部分用户质疑苹果的电源管理设计是否合理，并与其他操作系统（如 Linux 和 Windows）进行了对比。

“No tax on tips” is an industry plant

作者: littlexsparkee | 评分: 107 | 评论数: 25 | 发布时间: 2025-07-31 21:47
文章摘要

2024年3月19日，亚利桑那州众议院商业委员会举行听证会，讨论《小费工人保护法》。该法案提议修宪，允许雇主支付小费工人的时薪比最低工资少25%。当时，亚利桑那州的最低工资为每小时11.35美元，而该法案通过后，小费工人的时薪将降至10.76美元，年收入减少约1200美元。尽管法案看似保护工人，实际目的是阻止另一项提高最低工资至18美元的提案——《公平工资法》。 听证会上，身穿“拯救小费”T恤的工人现身支持该法案，反对《公平工资法》，声称新法会取消小费。然而，这些人实际上与亚利桑那州餐馆协会有关联，并非普通服务员。例如，作证的Jaime Sarli是披萨店助理经理，另一证人Beth Cochran则是早餐连锁店高管，两人都隶属于该协会。 民主党议员Ortiz对此感到困惑，因为《公平工资法》旨在保证最低工资并保留小费。她后来发现，这些工人实际上是在为削减自己基本工资的法案背书，目的是保护管理层的利益。尽管有真正服务员反对该法案，但委员会的共和党人仍支持法案，声称工人们对其现状满意。事实上，这些工人的活动是由餐馆协会资助的政治行动。

评论摘要
主要讨论点：小费、税收与劳动者权益 不同观点： • [voidUpdate] 认为在接受服务前就被要求给小费是不合理的。例如在外卖平台上，还未收到服务就要先给小费，而账单中已经包含了配送费，因此没有必要再额外付费。 • [oellegaard] 主张取消小费制度，认为餐饮业应该通过支付合理工资来解决员工薪酬问题，而不是依赖小费。 • [littlexsparkee] 指出，有约40%的小费工作者收入低到无需缴税，因此不缴税对高收入的小费工作者如赌场发牌员更有利。同时，"不对小费征税"（NToT）运动被认为是一种转移注意力的手段，目的是避免讨论提升最低工资。 • [cherryteastain] 担心小费免税政策可能为逃税提供机会。例如，商家可以通过让顾客以小费形式支付大部分费用，以避开销售税和收入税。 • [thuridas] 认为小费和加班免税政策可能会导致对劳动者的剥削，因为这些政策使得雇主可以通过小费和加班降低成本，而劳动者可能面临更大的工作压力。 • [Larrikin] 建议减少小费金额，因为小费本质上是慈善行为，应该减少到免税前的水平。同时希望小费制度能被废除，尤其是美国的小费依赖文化。 • [shazbotter] 认为解决小费工作者问题的关键在于打击工资克扣，而非小费税，因为后者只是冰山一角。 • [augment_me] 预测传统的服务工作将转向类似Uber的模式，工作者成为独立承包商，承担全部风险，而企业主无需支付固定工资。 补充讨论： • [SSchick] 提到小费比例在下降，从原本的20%降至最多15%，并且对小费文化感到厌烦，尤其是面对羞耻营销（如服务员在看到小费屏幕时的反应）。 • [KurSix] 批评行业通过公关和管理层干预制造工人同意的假象。 • [steveBK123] 讽刺地认为所有奖金很快都会被标记为小费。 • [neuroelectron] 提到了特朗普的影响力，尽管与小费话题关联不大。 • [siliconc0w] 认为小费免税政策是一种政治策略，表面上为劳动者争取利益，实际上在其他方面损害他们的权益，如医疗和能源成本。 • [ojbyrne] 补充说明，加班免税政策在工会合同中可能不适用。 争议焦点： • 小费制度是否合理，尤其是在服务尚未提供之前就要求小费。 • 小费免税政策是否会导致逃税问题。 • 小费制度是否加剧了对劳动者的剥削，尤其是在工作风险和压力方面。 • 是否应通过立法废除小费制度，转而通过提高固定工资来保障劳动者权益。

文章摘要

"Pride Versioning 🏳️‍🌈 0.3.0" 是一种版本编号方案，格式为 PROUD.DEFAULT.SHAME。具体规则如下： - **PROUD 版本**：当你对更新感到非常自豪时增加。 - **DEFAULT 版本**：当你发布了一个还算可以的版本时增加。 - **SHAME 版本**：当你修复了一些令人尴尬的问题时增加。 例如，版本号 2.7.123 中，2 是 Proud 版本，7 是 Default 版本，123 是 Shame 版本。当增加 Proud 版本时，其他部分可重置为 0，如 1.2.3 提升 Proud 版本 1 后变为 2.0.0。该方案由 Niki Tonsky 在 GitHub 上提出。

评论摘要
主要讨论点：软件版本号命名策略及其合理性 不同观点： • **cloudbonsai**：认为OpenSSL的版本政策很有趣，引用其版本政策来说明 major releases、minor releases 和 letter releases 的区别。指出 major releases 可能会破坏兼容性，而 minor 和 letter releases 主要是新功能和修复 bug，且不会破坏二进制兼容性。同时认为这种版本政策有点疯狂，因为需要小心关注更新，尤其是在重要的安全软件中。 • **mbirth**：更喜欢使用"Gregorian versioning"（可能是指使用年月作为版本号，如年份版本），认为这样可以立即知道一个应用是否仍在更新或已被遗弃多年。 • **shredprez**：对 OpenSSL 的版本命名方案持积极态度，认为这是一个基于现实的版本方案。 • **carterschonwald**：认为 OpenSSL 的版本策略其实与其他软件的做法相似，暗示这种命名方式并不新奇，大家一直在采用类似的策略。 • **blahgeek**：支持 OpenSSL 的版本策略，认为相比表面看起来更合理，并提到 Hyrum’s law，即每个变化都可能是一个破坏性变化，因此 semver（语义化版本控制）在实际中并不完全适用。 • **neilellis**：简单表达了对 OpenSSL 版本政策的喜爱。 补充讨论： • 争议焦点在于版本命名政策的合理性和实用性。有人认为 OpenSSL 的版本政策复杂且需要小心跟进更新（cloudbonsai），而其他人则认为这种命名方式更贴近实际需求（shredprez，carterschonwald，blahgeek）。 • 另一个讨论点是版本命名是否应直接反映时间（如 Gregorian versioning），以便于用户判断软件是否仍在维护（mbirth）。
