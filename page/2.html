String Interpolation in C++ Using Glaze Stencil/Mustache

文章摘要

Glaze库通过`stencil`和`mustache`格式为C++结构体提供了字符串插值功能，允许将结构化数据格式化为字符串。其模板机制受Mustache模板语言启发，可以结合预定义模板和C++结构体生成动态输出。 ### 基本用法 定义结构体并使用模板进行插值，例如： ```cpp struct person { std::string first_name; std::string last_name; uint32_t age; bool hungry; bool employed; }; std::string_view layout = R"({{first_name}} {{last_name}} is {{age}} years old)"; person p{"Henry", "Foster", 34}; auto result = glz::stencil(layout, p); // 结果: "Henry Foster is 34 years old" ``` ### 模板语法 - **变量插值**: `{{key}}` 替换为结构体字段值，`{{{key}}}`为不转义输出（仅mustache格式）。 - **布尔节**: `{{#boolean_key}}`显示内容如果布尔值为true，`{{^boolean_key}}`为false时显示。 - **容器迭代**: `{{#container_key}}`迭代容器元素，`{{^container_key}}`容器为空时显示内容。 - **注释**: `{{! This is a comment}}`。 ### 示例 - **布尔节示例**: ```cpp std::string_view layout = R"({{first_name}} {{last_name}} {{#employed}}Status: Employed, Age: {{age}}{{/employed}})"; person p{"Carol", "Davis", 30, true, true}; auto result = glz::stencil(layout, p); // 结果: "Carol Davis Status: Employed, Age: 30" ``` - **容器迭代示例**: ```cpp struct TodoList { std::string title; std::vector items; bool has_items; }; std::string_view layout = R"({{title}}: {{#items}}{{text}} ({{priority}}) {{/items}})"; TodoList list{"My Tasks", {{"Buy milk", false, "normal", 1}, {"Call mom", true, "high", 2}}, true}; auto result = glz::stencil(layout, list); // 结果: "My Tasks: Buy milk (normal) Call mom (high) " ``` ### Mustache格式 `glz::mustache`与`glz::stencil`接口相同，但提供HTML转义： - 双括号 `{{key}}` 输出HTML转义内容。 - 三括号 `{{{key}}}` 输出原始HTML内容。 ### 错误处理 `stencil/mustache`函数返回`std::expected`，常见错误如引用不存在的字段。

Extracting memorized pieces of books from open-weight language models

作者: fzliu | 评分: 44 | 评论数: 4 | 发布时间: 2025-06-16 17:41
文章摘要

这篇文章探讨了大型语言模型（LLM）是否以及如何记忆受版权保护的书籍内容，并对其在版权案件中的影响进行了分析。作者使用了一种概率提取技术，从13个开放权重的LLM中提取了Books3数据集的部分内容。实验表明，部分LLM确实记忆了书籍的 substantial 部分，尤其是像Llama 3.1 70B几乎完整记忆了《哈利·波特》和《1984》等书籍。然而，最大型的LLM并没有显著记忆大多数书籍。文章指出，这一发现对版权案件具有重要意义，但并不单一地偏向任何一方。

评论摘要
主要讨论点：LLM（大型语言模型）中的版权侵犯问题 不同观点： • andy99认为，LLM涉及版权侵犯的情况有两种：一是使用盗版材料进行训练，例如通过种子下载未经授权的书籍；二是用户利用LLM生成侵犯版权的内容。他强调，训练本身并不构成侵权，因为知道某些受版权保护的信息并不等于侵犯版权。不过，LLM帮助用户生成侵犯版权的内容是一个需要解决的问题，类似于防止它们提供如何制造毒品的指导。 • landl0rd指出，LLM可能“记忆”了一些非常受欢迎的书籍，如《哈利·波特》和《1984》，但这并不是因为它们完整地复制了这些作品，而是因为这些书籍中的引用在训练集中大量出现。因此，这种“记忆”更多地与公平使用原则有关，而不是直接的版权侵犯。 • jrm4认为，关于LLM是否涉及版权侵犯的讨论有时过于复杂和拟人化。他强调，如果将作品放入LLM中进行训练，模型能够生成可识别的副本，这就构成了侵权。而看不到副本的存在并不意味着侵权不存在。 • billionairebro以讽刺的方式指出，要求LLM提取《哈利·波特》中的段落用于推广网站，可能会导致法律问题，暗示未经授权使用受版权保护的内容可能会带来严重后果。 补充讨论： • 争议的焦点在于LLM在训练过程中使用受版权保护的材料是否构成侵权，以及模型生成侵犯版权的内容时责任的归属问题。 • andy99和jrm4的观点之间存在一定的对立，前者认为训练本身不构成侵权，而后者则认为将作品用于训练本身就可能构成侵权。 • landl0rd提供了一种可能的解释，即模型中出现的受版权保护内容可能是由于训练集中引用的普遍性，这为讨论提供了一个中间立场。 • billionairebro的评论则通过讽刺强调了未经授权使用受版权保护内容的风险。

文章摘要

Unregistry 是一个轻量级工具，允许直接通过 SSH 将 Docker 镜像从本地推送到远程服务器，无需外部注册表。它通过建立 SSH 隧道，在远程服务器上临时运行一个 unregistry 容器，仅传输缺少的镜像层，完成后自动关闭。相比使用 Docker Hub 或自建注册表，它更简便高效，特别适合生产环境部署、CI/CD 管道以及隔离网络中的镜像分发。安装通过 Homebrew 或直接下载进行，支持多平台镜像推送。

We Can Just Measure Things

文章摘要

Public/protected/private is an unnecessary feature

文章摘要

本文讨论了面向对象编程中访问修饰符（public/protected/private）的必要性，认为它们是多余的。作者以Car类实现Vehicle接口为例，指出接口可用于编写通用代码，但无法与继承很好地协同工作。子类可以违反父类的内部不变量，而访问修饰符（如private、protected）本应用来解决此问题。然而，作者认为这种方式不理想，因为接口定义和访问控制应通过统一的机制实现。访问修饰符起源于Simula语言，当时由于未意识到虚拟方法和子类型已经足够定义接口，导致重复功能的产生。作者建议，通过接口来保护类的内部细节，避免使用访问修饰符，并推荐使用组合代替继承来实现更好的设计。

评论摘要
主要讨论点：访问修饰符（如public、private、protected）在编程语言中的作用和必要性，尤其是在面向对象编程（OOP）中的意义。 不同观点： • **支持访问修饰符的有用性**： - **jonathanlydall**：访问修饰符（如C#中的internal）有助于约束类的可访问性，特别是在重构时保护外部不可见行为。认为Visual Studio的模板更改（从public到internal）是一个积极变化，但很多代码库可能由于历史原因仍使用不必要的public类。 - **Dwedit**：限制属性的访问（如通过属性访问字段）不是不必要的功能，它有助于代码的维护和清晰性。 - **aurumque**：访问修饰符帮助开发者理解代码的使用方式，虽然不能提供绝对保护，但在使用反射等手段绕过时，责任在于使用者。强调访问修饰符对编译器和JIT的优化作用。 - **alganet**：private和protected方法有助于简化代码抽象和理解，特别是在组合模式和继承模式中使用时，能有效控制代码粒度。 • **质疑访问修饰符的必要性**： - **cherryteastain**：认为public/private等访问控制是一种“社会性”创新而非工程性必要。Python等语言没有private成员但依然成功，说明这些访问控制并非不可或缺。还提到C++中可以通过预处理指令轻松绕过private限制。 - **rerdavies**：虽然许多语言特性是“不必要”的，但它们是否有用才是关键。访问修饰符有助于限制派生类与基类的交互面，在维护上非常有用。 - **julik**：现代语言可以使用注解（如@internal）来替代语言内建的访问控制构造，认为这样更合适。 • **关于继承与组合的讨论**： - **baobun**：提到如果反对继承，private和protected就显得不那么有用。继承是访问控制的一个常见使用场景。 - **cosmicgadget**：反对仅使用接口来替代访问控制，认为继承和组合各有其正确使用场景。 补充讨论： • **对访问控制的不同设计方案**： - **PaulDavisThe1st**：希望扩展访问修饰符的功能，提出类似C++中friend声明的细粒度控制，允许指定特定类对方法的访问权限。 - **cyberax**：认为Go语言的包私有（package-private）和公开实体模型是一个很好的折中方案，能有效减少全局命名空间的污染。 争议焦点： • **访问修饰符的必要性**：一方认为访问修饰符在代码维护、抽象控制和编译优化中起关键作用，另一方则认为这些修饰符并非绝对必要，其他语言和模式也能成功实现类似功能。 • **继承与组合的优劣**：讨论中涉及继承是否为“反模式”，以及组合与继承如何在不同场景中有效应用。
