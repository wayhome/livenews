文章摘要

Let's Encrypt于2025年8月6日正式终止OCSP（在线证书状态协议）服务，改而仅通过CRL（证书吊销列表）发布吊销信息。主要原因有二：OCSP存在隐私风险，可能暴露用户访问的网站和IP地址；同时维护OCSP服务消耗大量资源。此前Let's Encrypt已在90天前停止在证书中包含OCSP URL。高峰期该服务每月处理3400亿次请求，现这些资源将用于其他业务。Akamai十年来的CDN支持也获得感谢。

评论摘要
主要讨论点：OCSP（在线证书状态协议）的优缺点及其替代方案CRL（证书吊销列表）的有效性。 不同观点： • **支持OCSP的观点**（lol768）： - OCSP提供实时证书状态验证，无需下载大型CRL。 - 通过设置`security.ocsp.require`可以避免浏览器“失败开放”问题。 - 隐私问题可以通过Must-Staple解决，OCSP响应者可仅服务于服务器和研究人员。 - 用户已将主机名发送给DNS服务器，OCSP的隐私问题被夸大。 • **反对OCSP的观点**（EPWN3D、GauntletWizard、jart）： - OCSP设计为“失败开放”，存在安全隐患。 - 在不可行场景（如安全启动）中，OCSP无法适用。 - 如果客户端不强制要求OCSP，则其无用；若强制要求，则增加了复杂性和在线依赖。 - OCSP是权力争夺的产物，应彻底移除。 • **对CRL的批评**（lol768、sugarpimpdorsey）： - CRL体积大、更新延迟，需额外技术（如Bloom过滤器）弥补。 - Chrome使用自创的CRLSets，仅下载Google预处理的黑名单，且默认不检查企业CA的CRL。 补充讨论： - **争议焦点**：OCSP是否可以通过改进（如Must-Staple）解决其问题，还是应完全摒弃。 - **技术替代方案**：CRLite（Mozilla）和CRLSets（Google）被提及，但各自存在局限性。 - **用户配置问题**（zahlman）：是否需要在Firefox中关闭`security.OCSP.require`，反映了实际使用中的困惑。

Page Object (2013)

作者: adityaathalye | 评分: 27 | 评论数: 3 | 发布时间: 2025-09-11 05:26
文章摘要

这篇文章介绍了"Page Object"设计模式在网页测试中的应用。Page Object将网页或页面片段封装成一个应用程序专用API，使测试代码可以直接操作页面元素而无需深入HTML细节。其主要原则是：1)提供与用户操作一致的接口；2)隐藏底层控件实现细节；3)按页面功能模块而非物理结构划分对象。文章还讨论了相关争议点，包括是否应在Page Object中包含断言逻辑(作者倾向于不包含)、页面导航的实现方式等。最后指出该模式不仅适用于网页测试，也可用于其他UI框架，并能处理并发问题。

评论摘要
主要讨论点：[Page Object Models (POM) 的优缺点及其在测试框架中的应用] 不同观点： • **POM 牺牲清晰性换取封装性** - 支持者认为 POM 可以让测试代码看起来更整洁，但可能隐藏实际行为。 - 例子：`await page.getStarted();` 不如直接使用 `await page.locator('a', { hasText: 'Get started' }).first().click();` 明确。 - 论据：测试代码不需要过度追求 DRY（Don't Repeat Yourself），显式代码更易于理解和维护。 • **POM 类似 MVC 模式** - 提出疑问：POM 是否类似于 MVC（Model-View-Controller）或其子集？ - 未展开讨论，但暗示 POM 可能是一种设计模式的变体。 • **Playwright 优于 Cypress 的原因之一是 POM 的支持** - 支持者认为 Playwright 天然支持 POM，而 Cypress 缺乏这种结构，导致测试代码显得混乱。 - 论据：Cypress 项目中的测试往往是过程式的，而 Playwright 项目更结构化。 - 争议点：Cypress 是否有其他模式可以实现类似效果，但实践中未被广泛采用。 补充讨论： - **争议焦点**：POM 是否真的提高了代码的可维护性，还是仅仅让代码看起来更“干净”但更难理解？ - **工具偏好**：Playwright 和 Cypress 在 POM 支持上的差异影响了开发者的选择。
