Pandoc Lua Filters

作者: ankitg12 | 评分: 110 | 评论数: 4 | 发布时间: 2026-07-03 09:52
文章摘要

Pandoc Lua 过滤器是一种用于操作 Pandoc 抽象语法树（AST）的机制。相比传统的 JSON 过滤器，Lua 过滤器具有显著优势： **核心特点：** - Pandoc 2.0+ 内置 Lua 5.4 解释器，无需外部依赖 - 直接处理 Pandoc 数据类型，避免 JSON 序列化开销 - 性能接近原生速度（基准测试显示几乎无额外开销） **工作原理：** Lua 过滤器是一个表结构，以元素名为键、处理函数为值。遍历文档时，匹配的元素会被传递给对应函数处理。函数可返回 nil（保持不变）、新对象（替换）或对象列表（替换/删除）。 **使用方式：** 通过 `--lua-filter=文件名.lua` 参数调用，可链式应用多个过滤器。

评论摘要
**主要讨论点：** Pandoc 工具的发展演变、Lua filters 的实用性与兼容性问题 **不同观点：** • **实用场景分化**（kalcode）：Lua filters 适合处理 Markdown 到 DOCX 的转换问题，但对于 PDF 生成，切换到 WeasyPrint 引擎后就不再需要 Lua filters • **工具膨胀担忧**（lifthrasiir）：认为 Pandoc 日益臃肿，十年前使用 Lua filters 的经验与现在文档完全不同，担心不同版本间的 Lua 脚本兼容性问题 • **功能演进澄清**（leephillips）：指出 Lua filters 并非新功能，真正的新进展是 Pandoc 支持在浏览器中运行，提供了详细文章链接说明当前状况 • **未来发展设想**（chaoxu）：提出响应式更新的可能性，希望实现从 Markdown 到 AST 的增量更新机制，考虑利用 LLM 技术来实现这一想法 **补充讨论：** 评论间没有明显对立，更多体现了不同用户群体的关注点差异——实践者关注工具选择、老用户关注兼容性、信息提供者补充背景、前瞻者探索新方向

Trust your compiler: Modern C++

作者: foxhill | 评分: 45 | 评论数: 7 | 发布时间: 2026-07-01 14:00
文章摘要

这篇文章主旨是"相信你的编译器"。作者指出，许多C++程序员传承的性能优化技巧（如Quake III的快速平方根倒数、XOR交换、手动循环展开等）在现代硬件和编译器环境下已经过时。 现代CPU（如AMD Zen 5）和编译器（Clang、GCC）已经足够先进，能够从简单直观的代码生成最优机器码。编写"聪明"的优化代码反而可能妨碍编译器的优化，失去向量化、内联等优势。 文章通过具体例子对比传统优化技巧与简单实现：例如Quake III的Q_rsqrt与直接使用1.0f/sqrt(x)。现代CPU提供专门的SIMD指令（如rsqrtss），编译器能自动利用这些指令，使简单代码的性能不输甚至超越手工优化。 文章配有基准测试代码，测试环境为AMD Ryzen 9 9950X + Clang 21.1.1。

评论摘要
**主要讨论点：** C++ 现代特性（ranges/algorithms）的实用性、编译器优化能力与复杂性之间的权衡 **不同观点：** • **可读性质疑派（Joker_vD）**：认为传统 for 循环比标准库算法（如 std::accumulate）更直观易读。质疑"使用 ranges 和 algorithms"的推广，认为简单场景下手写循环更清晰。 • **性能现实派（mwkaufma, kzrdude）**：指出实践中的限制——调试构建性能差、模板导致编译时间膨胀、无法全局启用激进优化选项（如 -ffast-math）。强调理论优化与实际约束的差距。 • **实现细节派（mike_hock）**：质疑某些现代特性的优化效果，例如 std::visit 可能并未如宣传的那样优化为高效的 switch，而是退化为虚拟调用。 • **替代方案派（Panzerschrek）**：针对异常性能问题，建议使用 std::expected 等替代方案，等待标准改进。 • **编译器怀疑派（Glandalf, sylware）**：批评现代编译器过度复杂、无人能完全理解，怀念 Plan 9 等简洁工具。极端观点甚至认为复杂编译器是"后门注入器"。 **补充讨论：** 争议焦点在于现代 C++ 特性是否真正提升了代码质量——支持者强调抽象和优化潜力，反对者关注实际可读性、编译成本和工具链复杂度带来的风险。

Moby Dick Workout (2022)

文章摘要

这篇文章介绍了"白鲸记测试法"——一种评估生产力应用性能的方法。 **核心观点：** 生产力应用应该能流畅处理用户自己能创建的内容量。作者认为《白鲸记》比任何人能写的内容都要长，因此适合作为测试基准。 **测试步骤包括：** 1. 打开《白鲸记》文件，检查速度 2. 滚动到末尾/中间并调整窗口大小 3. 执行全选、剪切、粘贴、撤销、重做操作 4. 在中间位置编辑内容，观察是否有输入延迟或滚动跳动 5. 检查内存使用情况 **判断标准：** 计算机性能很强，《白鲸记》文件相对很小。如果应用无法流畅通过这个测试，可能存在性能问题。 作者提供了三种格式的测试文件供不同类型应用使用。

评论摘要
