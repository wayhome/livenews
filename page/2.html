这篇文章总结了Rust语言在2025年对SIMD（单指令多数据）的支持现状。主要内容包括： 1. SIMD的用途是通过单条指令处理批量数据来提高运算效率，在x86架构上理论最高可提速64倍。 2. 不同硬件平台的SIMD实现： - ARM称为NEON，所有64位ARM CPU都支持 - WebAssembly直接称为128位SIMD扩展 - x86从SSE2到AVX-512有多种扩展 3. 兼容性问题： - x86需要处理不同CPU的SIMD支持差异 - 可通过指定目标CPU或函数多版本化解决 4. Rust中的四种SIMD实现方式： - 自动向量化（编译器优化） - 高级迭代器 - 可移植SIMD抽象 - 原始指令 5. 自动向量化的限制，特别是浮点运算需要nightly版本编译器。 文章最后提到Rust对SIMD的支持正在不断完善，但2025年某些功能仍处于开发中。

评论摘要
主要讨论点：Rust中SIMD（单指令多数据）支持的状态、稳定性和使用体验 不同观点： • **支持std::simd的立场** - 用户（如brundolf）认为std::simd易用且功能强大，即使对SIMD新手也很友好。 - mdriley提到Chromium团队选择使用std::simd（尽管是nightly版本），并尝试避免最不稳定的API。 • **对std::simd稳定性的质疑** - josephg和waffletower批评std::simd长期停留在nightly阶段，认为其稳定性进展缓慢。 - waffletower还反驳了对数据类型支持的批评，认为i64和f64已足够覆盖多数数值应用场景。 • **替代方案的讨论** - the__alchemist分享了自己实现的core::simd替代方案（仅支持x86），以规避nightly依赖，但承认其局限性（如无ARM支持）。 - jtrueb提出，对于高性能需求，直接使用汇编（asm）可能比中间层SIMD库更有效。 - 文章作者建议根据需求选择工具链：std::simd（nightly）、wide（无多版本需求）或pulp/macerator。 • **跨语言比较** - bencyoung指出C#在稳定SIMD支持上优于Rust，提供了泛型向量类型和丰富的指令集内在函数。 - andyferris对比Julia的自动向量化（通过LLVM）表现更优，认为Rust因浮点精度限制导致优化困难。 补充讨论： - **争议焦点**：std::simd的稳定性问题（如nightly限制）和数据类型支持的充分性。 - **技术细节**：用户提到x86和RISC-V的扩展支持问题（IshKebab），以及SIMD与普通代码混合时的性能考量（the__alchemist）。 - **语言中立性争议**：CashWasabi批评文章过于语言特定，呼吁更通用的内容分享方式。 - **未来展望**：用户关注Rust对RISC-V向量扩展的支持（justahuman74）。

本文主要探讨了Smalltalk对Ruby语言的重要影响，特别是其面向对象的设计理念。Smalltalk起源于1970年代的Xerox PARC，其Smalltalk-80版本影响深远。尽管Smalltalk的语法未被Ruby继承，但其对象系统的核心思想（如所有数据都是对象）深刻影响了Ruby。作者分享了个人使用Smalltalk的经历，包括在90年代教授Smalltalk课程，并提及Squeak（一个开源的Smalltalk实现）的发展及其跨平台特性。文章还对比了Smalltalk与Unix/C系语言的不同，强调Smalltalk自成一体的操作系统风格和开发环境，以及它在90年代商业应用中的辉煌历史。

主要讨论点：[Smalltalk的历史、特点、影响及与现代编程语言的比较] 不同观点： • Smalltalk的图像（image）概念是其最令人印象深刻的部分，可以冻结、分发和恢复应用程序状态，支持客户端应用更为便捷。这种图像结构可以追溯到1972年，许多现代Smalltalk系统（如Pharo、Squeak、VisualWorks）共享共同的祖先，体现了其不朽性。 • Smalltalk在图形编程方面表现出色，提供了一个极佳的编程环境，支持全屏运行，编辑、调试和运行时对象检查都在同一环境中进行。用户可以在Smalltalk中完成所有任务，包括编写视频游戏和处理几何任务规划。 • Newspeak被认为是Smalltalk的现代继承者，提供了类似的反射性和增量编译体验，适合在浏览器中使用。 • Smalltalk被认为是一种操作系统，但在部署到最终用户时，它如何在现有操作系统（如Windows）上运行仍是一个疑问。是否以“kiosk模式”运行，专门显示单一界面？ • Smalltalk在概念建模方面非常符合人体工程学，因为它将CPU抽象并压缩在虚拟机中。然而，由于CPU的胜利，我们现在使用AI来处理其偶然复杂性。 • Smalltalk的语法简单，计算模型直接，被认为是编程语言中的“足球”，而Swift和Kotlin则更像是“美式足球”或“板球”，复杂且需要导航许多细微差别。 • Ruby被认为是Smalltalk的现代化版本，适合现代开发实践和工具，如源代码控制和现成的文本编辑器，同时可用于Unix脚本。 • Smalltalk的语法被认为是一个巨大的倒退，与Ruby相比存在不足。尽管Alan Kay的愿景宏大，但他并不是一个优秀的语言设计师。Ruby和Elixir在某些方面更接近Kay的愿景，但仍未完全实现。 补充讨论： • Smalltalk的脆弱性是一个争议点。由于其基于对象网络的结构，很容易破坏系统，因此Smalltalk虚拟机具有良好的恢复功能。 • Smalltalk的“运行环境”工作方式在历史上是常见的，但在现代Unix/VMS/Win32视角下显得奇怪。这种方式虽然高效，但与程序的可重现性需求存在冲突。 • Smalltalk程序员被认为更快乐，且收入更高，尤其是在C++尚未现代化的时代。 • 有人尝试用Ruby和TCL构建类似Smalltalk的系统浏览器，展现了Smalltalk的趣味性和影响力。
