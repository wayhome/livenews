My thoughts after using Clojure for about a month

文章摘要

作者用 Clojure 重写了个人网站，并分享了一个月的使用感受。 **喜欢的地方：** - 比 Common Lisp 更统一连贯，避免了委员会设计的混乱 - 比 Scheme 更实用，标准库丰富，有 JVM 生态支持 - 数据结构人性化，列表、向量、哈希表、集合都是一等公民 **遇到的问题：** - 语法比传统 Lisp 复杂（三种括号、特殊符号等） - 依赖 Java 知识，作为托管语言需要了解 JVM 总体而言，作者认为 Clojure 虽然违背了 Lisp 的极简主义，但其实用性和人性化设计让它成为值得学习的语言。

评论摘要
主要讨论点：关于Clojure编程语言的优缺点和实用性 不同观点： • **语法简洁派**：认为Clojure语法极简是优势，一切皆列表的设计理念优雅。有人对比Lua（表）、Tcl（字符串）、Python（字典），强调Lisp的统一性 • **运行时优先派**（pdimitar）：认为语法被过度浪漫化，真正重要的是运行时性能。指出Java运行时在并发/并行方面不如Erlang/Golang，绿色线程还不够强大 • **跨平台能力派**（Jeaye）：强调Clojure的"超能力"——不绑定JVM，可通过ClojureScript、ClojureDart、jank等方言运行在多个平台，非host interop代码可跨方言使用 • **实用主义怀疑派**：有人10年使用后仍觉得是"括号地狱"，也有人指出就业机会少（"not many jobs"） • **自建工具体验派**（HiPhish）：用Clojure构建静态站点生成器体验极好（宏实现模板引擎简单），但后期发现缺少优化、CSS作用域、SSR等高级特性，最终转向Astro 补充讨论：有人赞赏Clojure社区的"共生"理念（两个语言社区协作），也有技术细节讨论（paredit编辑器插件处理括号）和站点访问问题。

这篇文章是一本字体设计词典的节选，介绍了字体排印学的基础术语： **字母表（Alphabet）**：用字母集合表示语言的书写系统，拉丁字母使用最广泛。 **替代字形（Alternate）**：字符的变体形式，包括上下文变体、位置变体、风格变体和本地化变体，通过OpenType功能实现。 **&符号（Ampersand）**：代替"and"的字符，源于拉丁文"et"的连字，多用于标题和品牌名称。 **解剖学（Anatomy）**：借用建筑和人体术语描述字母各部分的命名体系。 **锚点（Anchor）**：连接基础字母与变音符号的定位点，用于组合字符设计。 **倾斜角度（Angle）**：斜体字母向右倾斜的角度。 **孔径（Aperture）**：开放字母内部空间与外部空间的分界线。

How we index images for RAG

作者: mooreds | 评分: 121 | 评论数: 14 | 发布时间: 2026-06-02 16:13
文章摘要

Kapa 构建的 AI 助手处理技术文档中的大量图像（截图、架构图、表格等）。他们的解决方案是：在索引时用视觉模型为每张图片生成一次文本描述，存储为文本块，查询时只检索描述而非原始图像。 这种方法避免了实时多模态处理的三大问题：成本高（每次查询增加 27-51% 费用）、图像数量超出模型负载限制（平均 20-30 张图，最多超 130 张）、多模态检索对技术细节效果差。 通过索引时一次性处理，后续查询成本仅增加 1-6%，且答案质量显著提升，用户能获得精确可操作的信息而非模糊指引。微软研究团队也得出相同结论。

评论摘要
主要讨论点：在RAG系统中处理图像的方法——在索引时用视觉模型生成文本描述，而非查询时直接发送图像给模型 不同观点： • 支持者认为这是成熟的"eager processing"模式，成本效益高且检索效率好。有人已实践2年，效果良好；也有人在Obsidian中手动实现类似方案，显著改善了文本检索效果 • 质疑者指出LLM的非确定性问题：新模型可能识别出旧模型遗漏的上下文（如车辆闯红灯），需要重新处理或保留多版本结果以组合最佳答案 • 技术路线争议：有人质疑为何不直接使用多模态embedding模型，认为当前方案可能并非最优 • 批评者认为这只是产品广告，该方法并无特殊之处，其他公司都在用 补充讨论： 实践中的挑战包括需要追踪作者更新图像标题、处理图文混合内容的困难（CLIP识别风格但不识别结构意图），以及纯视觉问题的查询需要架构调整。有开发者分享了开源实现方案供参考。
