Brut: A New Web Framework for Ruby

作者: onnnon | 评分: 11 | 评论数: 1 | 发布时间: 2025-07-08 18:03
文章摘要

Brut是一个简约但功能齐全的Ruby web框架，不同于其他框架，它没有控制器、动词或资源，而是直接构建页面、表单和单一操作处理器。Brut注重低抽象和低仪式感，但并非像Sinatra那样的低级框架。它内置OpenTelemetry仪表盘、基于Sequel的数据访问层以及基于OptionParser的命令行应用。 Brut安装简便，支持Docker快速启动。其核心设计基于类和对象，避免了过多的include和动态方法。它统一了客户端和服务器端表单验证，并通过BrutJS提供自定义元素。使用esbuild处理CSS，无需PostCSS或SASS。 Brut默认设置良好实践，如内容安全策略和数据库非空约束。它使用RSpec进行测试，支持Phlex生成HTML，并避免使用YAML进行配置。Brut简化了开发，消除了不必要的抽象和辩论，让开发者专注于编写Ruby和HTML，享受构建web应用的过程。 接下来，作者将继续完善Brut并发布1.0版本。

Memstop: Use LD_PRELOAD to delay process execution when low on memory

作者: ingve | 评分: 41 | 评论数: 7 | 发布时间: 2025-07-04 21:32
文章摘要

Memstop是一个轻量级工具，通过LD_PRELOAD机制监控系统内存，在可用内存达到设定百分比前延迟程序执行，以防止内存耗尽导致的系统崩溃。它适用于并行构建系统、批处理系统和高内存应用。Memstop从`/proc/meminfo`读取内存信息，计算所需内存百分比（默认10%），并在满足条件后允许程序继续执行。安装和使用需要GCC编译器和Linux系统，通过设置环境变量（如`MEMSTOP_PERBENT`和`MEMSTOP_VERBOSE`）进行配置。该项目使用GPL-3.0许可证。

评论摘要
主要讨论点：通过特殊方法优化内存使用和避免系统崩溃的策略 不同观点： • [AnotherGoodName] 提出了一种在Android设备上绕过系统内存限制的技巧，通过生成新进程并捕获Unix信号，避免系统弹出内存使用过高的通知，从而顺利运行需要大量内存的应用（如视频转码）。这种方法利用了Android的Low Memory Killer (LMK)机制，尽管是一种hack手段，但在低端设备上可以有效工作。 • [marcodiego] 则讨论了是否可以开发一种内存感知的调度器，通过惩罚那些导致系统变慢的进程（如过度内存分配或访问），从而防止系统因内存不足而崩溃。他提到了历史上通过OOM-Killer优化系统的努力，并质疑为何没有开发内存感知的调度器，或者这种方法是否已经被探索并证明不可行。 • [meatmanek] 对使用LD_PRELOAD实现内存管理的方法提出疑问，认为直接使用命令行包装器可能更直接，并猜测LD_PRELOAD的优势在于更容易集成到已有的构建系统中，因为它是通过环境变量配置的。 • [rini17] 关注设计哲学和实现细节，指出没有提到该方法是基于RSS还是虚拟内存触发，并建议添加swap空间来存储被停止的进程，以避免潜在的死锁问题。 • [ape4] 认为这种内存管理功能可以作为systemd单元选项，增加系统级支持。 • [d00mB0t] 对该方法表示赞赏，特别是其在并行计算中的潜力，但也提醒使用LD_PRELOAD可能带来的安全问题。 补充讨论： - 争议焦点在于使用LD_PRELOAD实现内存管理的优缺点，尤其是在安全性和系统集成方面的讨论。 - 其他讨论点包括对内存管理机制的改进建议，如内存感知调度器的可行性以及swap空间的利用。

文章介绍了由Inception Labs及其团队开发的基于扩散模型的新一代大型语言模型——Mercury，特别是其针对编程应用的Mercury Coder模型。这些模型通过Transformer架构参数化，能够并行预测多个 tokens。Mercury Coder 目前有Mini和Small两个版本，在NVIDIA H100 GPU上分别实现了1109 tokens/秒和737 tokens/秒的处理速度，在保持高质量的同时，速度比其他优化模型快高达10倍。模型在多种编程语言基准测试中表现优异，并在Copilot Arena上获得第二高质量评分和整体最快速度。文章还提供了公共API和免费 playground供用户使用。

评论摘要
主要讨论点：围绕LLM代理、测试性能瓶颈、技术实现细节及应用潜力的讨论 不同观点： • **mike_hearn**：提出LLM代理将导致测试性能的CPU瓶颈问题更加严重，尤其是在CI速度已经受限的情况下。他认为很多项目在测试设置上存在改进空间，但多年来几乎没有进展。 • **true_blue**：分享了在使用LLM模型时的具体问题，模型在生成测试用例时失控，不断生成无意义的测试，且在一定数量后开始出错。 • **mxs_**：关注技术实现，提到了SEDD模型的独立实现，并讨论了模型的复杂性和运行时间。 • **fastball**：提到DeepMind的Gemini模型，并指出其速度快但质量不如其他Gemini模型。 • **mtillman**：质疑arXiv是否适合发布此类内容，认为更像是营销而不是研究。 • **chc4**：对模型的"扩散模式"可视化表示兴趣，但对其准确性表示怀疑。 • **cavisne**：质疑arXiv的上传规则，认为不应允许营销内容。 • **M4v3R**：对LLM代理的潜力感到兴奋，特别是在减少等待时间上，期待未来的改进。 • **JimDabell**：提供了模型的定价信息。 • **gdiamos**：认为LLM开发社区低估了扩散模型的潜力，强调了后训练和数据投资的重要性。 • **EigenLord**：认为扩散模型在搜索无先验信息的大规模空间时具有优势，并指出其在药物发现等领域的潜在应用。 • **amelius**：对模型速度表示赞赏，但认为如果输出质量不能提高，其实际优势有限。 • **ceroxylon**：指出模型速度虽快，但在实际应用中存在大量错误，不可用于生产环境。 • **kazinator**：提到Google的Gemini扩散模型，并分享了其在beta测试中的体验。 • **armcat**：对模型的实际使用情况表示疑问，特别是其是否真正使用了OpenAI的模型。 补充讨论： • 讨论中涉及了多个具体的技术细节，如SEDD模型的实现、扩散模型的后训练和数据投资、以及不同模型的性能比较。 • 争议焦点在于LLM代理的测试性能瓶颈问题及其解决方案，以及扩散模型的实际应用价值和arXiv发布的适宜性。 • 用户对模型的速度和质量有不同看法，部分用户认为速度的提升并未带来实际优势，而另一部分用户则对其未来潜力表示期待。
