Gemini, Gophers, and Fingers. Oh My Alternative Internets Beyond HTTPS

作者: ChrisArchitect | 评分: 41 | 评论数: 4 | 发布时间: 2026-05-27 17:24
文章摘要

文章介绍了互联网中除 HTTPS 外的另一种可能：URI 协议生态。作者批评 Chrome/Chromium 主导造成网络“单一栽培”，主张通过去中心化的 Finger、Gopher、Gemini 等协议重建更简洁、自主的网络体验。它们多为纯文本、无需 GUI 和 JavaScript，可在终端运行，拥有独立社区与美学，也体现了 IndieWeb 对抗平台垄断的理想。

评论摘要
主要讨论点：围绕 finger/.plan、Gemini/Gopher 与现代 Web 的关系，讨论“简单互联网”的价值、限制，以及问题究竟出在协议还是生态。 不同观点： • 怀旧且肯定“轻量发布”模式：有人回忆 finger 和 John Carmack 的 .plan 文件，认为它像“原始 Twitter”，没有转发、点赞、通知和平台放大机制，但依然有吸引力，说明纯内容更新本身就能建立持续阅读关系。也提到如今 finger 已不再普及，默认未安装且服务超时，反映这类机制已式微。 • 反对把 Web 问题归咎于 HTTP/HTTPS：有人批评 Gemini/Gopher 讨论常“因噎废食”，把 Chrome 市占高、开发者只测 Chrome 等生态问题，错误归因为 Web 协议本身。其核心论点是：Google/Chrome 不控制 HTTP/HTTPS，协议本身没问题，想做简单网站完全可以只用纯文本。 • 温和支持“旧式简洁网络”的实践：有人补充推荐 plan.cat，认为它延续了 finger/.plan 这种简洁发布精神，说明仍有人尝试用现代服务复活这种体验。 • 认可 Gemini 理念，但认为其限制过头：有人说 Gemini 作为项目或爱好不错，但“无 cookie、无内联图片”等设计使其连基本认证交互和信息表达都受限，甚至“不如百年前的百科全书”。因此提出折中方案：不是另起协议，而是在现有 Web 上定义“Simple Web”规范，如“cookie 仅用于认证、少/无 JS、无追踪参数、无追踪像素”等。 补充讨论：争议焦点主要有两点——一是“简单互联网”应靠新协议（Gemini/Gopher）还是改良现有 Web；二是简洁性应优先到什么程度，是否会牺牲认证、图片和互动等基本能力。

Matrix Multiplications on GPUs Run Faster When Given "Predictable" Data (2024)

作者: tosh | 评分: 108 | 评论数: 11 | 发布时间: 2026-05-23 12:11
文章摘要

文章指出：GPU做矩阵乘法时，输入数据分布会影响速度。作者发现全零、整数等“可预测”数据比随机数据更快，并非算法变了，而是因半导体的动态/开关功耗：数据越规律，晶体管翻转越少，功耗更低，更不易触及GPU功耗墙，从而减少降频，提升吞吐。结论是：基准测试若用特殊数据，可能高估真实性能。

评论摘要
主要讨论点：GPU/AI计算中，输入数据分布是否会影响乘法等运算的实际功耗、发热与性能，以及这种现象是硬件机理、推测还是已被验证。 不同观点： • 机理解释派：认为文章重点不是“算法走了特殊分支”，而是不同输入分布会导致乘法器内部晶体管翻转次数不同，进而影响能耗和发热；若发热更低，时钟节流更少，整体更快。[jetsamflotsam] 还提到似乎有SC24相关论文做过更多实验。 • 特殊路径/实现猜测派：有人猜测乘0、乘1这类情况可能像早期处理器那样被专门优化，用更简单更快的代码/硬件路径处理。[ggambetta] • 怀疑验证充分性派：质疑博客到底是在报告实测结论，还是仅提出理论并给出“看似合理”的数字；并提出也可能是内存压缩、预取等别的机制导致。[jayd16] • 安全/副作用关注派：认为若数据分布会稳定影响功耗或时序，可能形成侧信道攻击面。[amelius] • 工程与实践观察派：有人指出本地LLM推理里也有人观察到类似现象，甚至“限功率反而提升总体性能”。[gdevenyi] • 硬件设计延伸派：Tenstorrent被举例为强调可预测执行流的硬件路线，暗示可通过架构设计减少这类不确定性。[evanjrowley] 补充讨论： • 争议焦点在于：性能差异究竟来自乘法器内部电气特性，还是来自分支预测、缓存/预取、压缩等更传统机制。 • 还有旁支讨论GPU待机功耗：88W“空闲功耗”被认为很高，并质疑这是否正常。[dan_sbl] • 也有人联想到未来可能用ML自动选择更快的矩阵乘路径。[bitwize]

A Comma and a Question Mark, Redux: Quick Terminal Helpers Using Pi

文章摘要

作者受他人启发，把终端接入 AI：输入“, + 自然语言描述”即可生成对应 shell 命令，并复制到剪贴板，用户确认后再执行；输入“q + 问题”可在终端直接获得简洁答案。其实现基于已配置好的 pi CLI 与 OpenRouter，而非本地模型，核心是两个简单脚本与精简提示词。

评论摘要
主要讨论点：大家围绕“在命令行中用快捷方式/AI辅助生成并回填命令”的实践经验展开，讨论其实现方式、自动化程度和交互体验。 不同观点： • 一类观点认为，这种思路已经有较成熟实现。sync提到自己长期使用 atuin 的 `?` 快捷方式，能实现类似功能；而且现在还接入了类似 Agent 的能力，可以用自然语言提示，如“为未暂存改动生成 Conventional Commit message”，工具会在征求权限后调用 `git diff` 并生成提交信息。其重点是“自然语言驱动 + 权限确认 + 自动调用上下文命令”。 • 另一类观点更强调“直接写回命令行输入框”的轻量实现。chrisshroba 介绍自己用 shell 命令先把结果写入文件，再通过 `print -z "$(cat /tmp/command.txt)"` 直接放到命令行中，这样省去复制粘贴，只需回车或再编辑即可。其核心论据是交互顺滑、可人工调整。 • 还有观点表明，这个方向容易继续扩展成更完整的项目。remilouf 认为这个点子很酷，并表示自己已把它发展成一个“越挖越深”的项目 sigil，说明该需求可从小技巧演变为独立工具。 • 也有人补充自己已在使用类似方案。guluarte 提到 shelloracle，说明同类工具/思路并不少见，社区中已有多种实践。 补充讨论： • 评论整体偏分享经验与工具互荐，没有明显对立争吵。 • 讨论焦点主要不在“要不要做”，而在“如何做得更顺手”：是用现成工具、Agent式能力，还是用 shell 技巧实现最小可用方案。
