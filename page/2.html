文章摘要

这篇文章分析了2023年针对俄罗斯最大XMPP消息服务jabber.ru的TLS流量拦截事件。攻击者利用acme.sh（一个自动化TLS证书续期工具）的远程代码执行漏洞（CVE-2023-38198），在2023年4月18日开始签发伪造证书进行中间人攻击。漏洞涉及shell注入和ACME协议滥用，攻击者通过证书颁发机构"HiCA"实施。事件因证书过期未续期而暴露。文章详细剖析了漏洞机制、时间线和技术细节，展示了即使TLS"应该"安全运作，实际操作中仍可能被利用进行合法或非法监听。

评论摘要
主要讨论点：HTTPS/TLS证书安全性和权限管理问题 不同观点： • **权限管理批评**（edelbitter）：ACME客户端（如acme.sh）不应以管理员权限运行，尤其是定期任务。一旦文件系统结构和配置就绪，完全可以使用最小权限运行，但教程仍在教"直接用管理员权限"的不良做法 • **CA监听争议**（perching_aix）：对TLS监听和根CA签发证书的讨论存在误导性总结。批评者认为某些说法暗示CA与国家机构勾结，但实际情况可能完全不同，这种夸大表述才是让人不满的原因 • **证书透明度疑问**（ls612）：认为证书透明度（Certificate Transparency）机制应该能防止文章描述的问题，对自己的理解模型产生怀疑 • **技术能力询问**（TZubiri）：直接询问哪些合法拦截（LI）供应商能够破解HTTPS 补充讨论：讨论涉及HTTPS安全的多个层面——从运维实践（权限控制）、监管争议（CA可信度）到技术防护机制（CT日志）的有效性，反映出对TLS生态系统不同环节的关注和质疑。

Openrsync: An implementation of rsync, by the OpenBSD team

作者: sph | 评分: 236 | 评论数: 14 | 发布时间: 2026-05-30 10:51
文章摘要

这是 openrsync 项目的 README 文档。openrsync 是一个采用 BSD 许可证的 rsync 实现，与现代 rsync（协议 27）兼容但仅支持部分命令行参数。该项目已合并入 OpenBSD 基础系统，最初为 RPKI 验证器 rpki-client 项目开发。 核心算法包含发送端和接收端两部分：发送端管理源文件，接收端管理目标文件。双方共享文件列表（包含文件名和元数据），独立按字典序排序后，通过"块交换"机制同步文件。接收端遍历文件列表向发送端请求更新，发送端扫描并返回需要更新的数据块。 项目支持 OpenBSD 及其他 UNIX 系统，提供完整的安装和使用文档。

评论摘要
主要讨论点：OpenBSD开发的openrsync项目引发关于重新实现rsync的必要性和影响的讨论 不同观点： • **支持重新实现派**：认为openrsync通过OpenBSD的pledge()和unveil()提供了更好的安全性，特别是在处理网络数据时。macOS 15.0已采用此版本，适合RPKI验证等安全敏感场景 • **质疑必要性派**：原rsync已是GPL开源软件，重新实现是"为资本服务"的浪费。rsync通常在信任边界内运行，安全问题被夸大。如果rsync对端不可信，问题已经很严重 • **实用主义担忧派**：openrsync功能不完整（仅支持部分命令参数，缺少64位时间戳支持），会导致生态碎片化。Apple/Android可能采用BSD版本，Linux世界继续用GPL版本，用户需要了解各版本差异 • **技术问题反馈**：存在具体bug（如文件路径处理与原版不一致）和功能缺失（早期版本不支持--exclude和-z） 补充讨论：部分评论偏离主题，讨论AI代码渗透到开源项目的现象。命名"openrsync"引发困惑，因为原rsync本就开源，"open"前缀通常用于闭源软件的开源替代品。

Kore: Binary File Format Optimized for Modern Data Systems (Open Source)

作者: arunkore2026 | 评分: 7 | 评论数: 4 | 发布时间: 2026-05-30 20:54
文章摘要

Kore是一个高性能的列式存储文件格式，专为大数据分析优化。主要特点包括：38%的压缩率（优于Parquet的63%）、通过列裁剪和谓词下推实现131倍查询加速、零数据丢失验证（测试超过40万单元格）。支持Rust原生库和PySpark集成，提供简单的读写API。用户可以通过Rust直接操作或在Spark中使用类似Parquet的接口读写Kore文件。该项目已发布v0.1.0版本，提供完整的Spark SQL支持。

评论摘要
主要讨论点：对 Kore 项目的质疑和性能对比需求 不同观点： • **需要更多实证支持**（arpadav）：项目缺乏具体基准测试，代码风格偏"vibe-codey"不适合生产环境；压缩率仅为 Parquet 的一半；若追求速度，Python 是奇怪的技术选择 • **压缩率存疑**（theginger）：声称的压缩比低于 Parquet，但通常压缩率越高越好，对项目优势表示困惑 • **期待大规模数据验证**（microflash）：目前使用 DuckDB 处理 3 亿+记录的 Parquet 文件仅需数秒，希望看到 Kore 与 Parquet、Vortex 的对比基准测试，并建议开发 DuckDB 扩展 • **项目方宣传**（arunkore2026）：强调比 JSON 快 50 倍、压缩率提升 50-70%，支持多语言，有 VS Code 扩展，经过 3 年生产验证 补充讨论：核心争议在于 Kore 相比成熟方案（Parquet、Vortex）的实际优势不明确，社区普遍要求提供与主流列式存储格式的详细性能对比数据。

Zig: Build System Reworked

文章摘要

Zig编程语言在2026年5月26日对构建系统进行了重大重构。主要变化是将`build.zig`的编译过程分为两个独立进程：配置器（configurer）和制造器（maker）。配置器以调试模式编译用户的构建逻辑并生成二进制配置文件，制造器以发布模式编译并执行构建图。 这次改进带来三大性能提升：1) 每次修改只需重新编译用户的`build.zig`代码，而非整个构建系统；2) 当配置未变化时可跳过重新运行构建逻辑；3) 执行构建图的进程现在启用了优化。基准测试显示`zig build --help`命令的执行时间从150ms降至14.3ms，性能提升超过90%。此外，第三方工具如ZLS也能从序列化配置文件中受益。

评论摘要
主要讨论点：Zig 0.16.0 版本发布后，开发者对该语言的评价、使用场景和未来发展的讨论 不同观点： • **积极派**：认为 Zig 是优秀的"工具语言"和"车库修补"语言，简单易上手，0.16.0 的新 IO 机制带来高效代码，编译速度出色，跨平台编译能力"纯魔法" • **实用主义者**：将 Zig 定位为"双语言编程"中的低级语言选择，比 C++ 和 Rust 更易重新上手，比 C 更现代，填补了简单性与现代工具之间的空白 • **观望派**：关注语言稳定性问题，质疑异步 IO 等大特性频繁变动说明语言"非常不稳定"，询问稳定版发布时间表 • **怀疑派**：质疑 Zig 相比 Node.js/TypeScript 的优势，对字符串处理的繁琐表示不满，希望有可选的 RAII 支持 • **好奇者**：Rust 用户询问是否应该尝试 Zig，关注两者的优劣对比 补充讨论： 版本迭代速度引发关注（0.17 预计数周内发布，而 0.16 用了超过一年）；Bun 项目从 Zig 转向 Rust 引发编译时间讨论；有人询问 MIT (Expat) 许可证细节；Andrew Kelley 访谈视频激发学习兴趣

Navier-Stokes fluid simulation explained with Godot game engine

文章摘要

这篇文章介绍了如何使用Godot游戏引擎实现Navier-Stokes流体模拟。作者强调这是用于学习目的的实现，优先考虑代码可读性而非性能。核心思路是：在网格上通过速度场移动密度场来模拟流体流动，包括速度和密度的扩散与平流，并通过速度投影使流体遵守质量守恒定律。实现使用了双线性插值和高斯-赛德尔松弛法进行近似计算。文章从创建网格开始，定义了存储密度(density)和速度(u,v)的数组，其中密度表示单元格包含的材料量(0-1)，速度分为水平和垂直分量。作者提供了完整代码仓库和分章节的git提交记录供学习参考。
