Malleable software: Restoring user agency in a world of locked-down apps

作者: jessmartin | 评分: 155 | 评论数: 21 | 发布时间: 2025-06-10 15:16
文章摘要

文章主要讨论了环境对工作和生活的重要性，强调人们需要能够根据个人需求调整环境以发挥潜力。在物理世界中，人们可以轻易调整空间，如布置工具或移动家具。然而，在数字化环境中，软件的僵化限制了这种适应性。文章以软件开发和医疗记录为例，说明了 rigid（僵化）的软件如何导致效率低下和职业倦怠。尽管用户反馈可能有助于改进软件，但由于开发团队无法满足所有个性化需求，问题往往得不到及时解决。文章呼吁将更多控制权交给用户，使他们能够根据自身需求调整软件，从而提高工作效率和满意度。

评论摘要
主要讨论点：对现代软件开发工具和环境的可定制性、灵活性以及用户控制权的讨论 不同观点： • [mynegation] 认为现代 web 开发环境过于碎片化，选择过多，导致开发者缺乏信心。他怀念像 Delphi 这样的一体化、可视化的开发工具，并希望有一个现代的、流行的编程语言版本，如 Python 或 TypeScript。他还指出，现有的工具虽然能快速生成大量代码，但往往留下难以管理的混乱。 • [WillAdams] 提到了几个具有类似理念的工具，如 LyX、pyspread 和 Ipe，并认为这些工具在特定领域内提供了灵活性和可定制性。他还提到一个 JavaScript 工具 Scrappy，但指出其适用范围有限。 • [eviks] 强调了集中式开发团队难以满足所有用户需求的问题，特别是当用户需求多样化时。他还指出，过度集成的软件可能导致臃肿，但如果有良好的模块化设计，这并不是不可避免的。 • [cosmic_cheese] 认为，虽然可深度定制的软件对某些用户有吸引力，但大多数人并不感兴趣，也不会花时间学习。他指出，技术专精并不适合所有人，因此不应期望灵活的软件能迅速取代主流产品。 • [mitchbob] 强调了鼓励想象力和创造力的重要性，认为软件不应全是“黑箱”。他提到了历史上一些激发创造力的工具，如 HyperCard、Visual Basic 和 Excel。 • [momojo] 赞扬了 napari 的可访问性和透明性，指出其所有功能都可以通过 Python 控制台访问，没有任何隐藏的部分。 • [fernmyth] 关注数据共享问题，希望有一个通用的数据后端，让用户拥有自己的数据，并提到 Solid/PODs 项目，但认为其在实际应用上不够成功。 • [seltzered_] 提到了 Michel Beaudouin-Lafon 和 Alan Kay 的演讲，强调了“工具而非应用”的理念，并提供了相关的讨论链接。 • [AlexErrant] 讨论了 Patchwork 项目，并询问其开源前的里程碑，担心其功能过多导致“功能蔓延”。 • [danabramov] 提到了 atproto，认为其在用户数据拥有权和跨应用数据共享方面有潜力。 • [wagwang] 指出软件可定制性的根本问题是代码路径复杂度呈指数增长，最终会导致软件难以维护。 • [cadamsdotcom] 赞扬了 Ink & Switch 的研究工作，认为其在商业化和技术探索之间找到了平衡。 • [torginus] 从技术角度讨论了软件的可修改性，提出了一种基于游戏引擎的实时修改环境，并讨论了内存管理和数据损坏等问题。 • [zzo38computer] 同意许多观点，但提出了自己的改进方案，包括 CAQL、UTLV 和代理功能等设计理念，并提到了相关文档。 • [ge96] 提到了旧设备和软件的兼容性问题，表达了对旧技术不再可用的遗憾。 补充讨论： • 争议的焦点在于软件的可定制性和复杂性之间的平衡。一些评论者认为现代软件过于复杂和臃肿，而另一些评论者则认为可定制性对大多数用户并不重要。 • 另一个值得注意的讨论点是数据拥有权和跨应用数据共享的问题，fernmyth 和 danabramov 提到了 Solid/PODs 和 atproto 等项目，希望能有一个通用的数据后端。 • 技术实现上的讨论也是一个重要方面，torginus 和 zzo38computer 提出了具体的技术方案和设计理念，试图解决软件可修改性和数据管理的问题。

文章摘要

本文综述了现代最小完美哈希函数的研究进展。给定一个包含 $n$ 个键的集合 $S$，完美哈希函数能将这些键无碰撞地映射到前 $m \geq n$ 个整数，其中最小完美哈希函数满足 $m = n$。现代最小完美哈希函数在查询速度、空间效率和扩展性方面取得了显著进展，能够有效处理数十亿个键。不同方法在空间消耗、构建时间和查询时间上各有权衡。本文总结了最新发展，并通过大量实验评估指导实际应用中的选择。该技术广泛应用于静态哈希表、数据库、生物信息学和字符串学等领域。

评论摘要
主要讨论点：完美哈希在数据库性能优化中的应用 不同观点： • tmostak 认为完美哈希在HeavyDB中对提升GROUP BY和JOIN操作的性能起到了核心作用。他指出，完美哈希不仅可以用于常见的连续整数和字典编码字符串范围，还可以应用于分箱数值和日期范围等情况。例如，将时间戳按年分箱，每个年份一个分箱，可以覆盖非常广泛的时间戳范围。 补充讨论： • tmostak 提到，如果正确传播范围，完美哈希甚至可以处理任意表达式。他认为，虽然需要一个良好的"基准"哈希路径作为后备，但令人惊讶的是，有许多现实世界的用例可以通过完美哈希有效地覆盖。 总结： 评论主要讨论了完美哈希在数据库中的广泛应用和其在处理不同数据类型和范围时的灵活性。tmostak 提供了具体的例子，如分箱数值和日期范围，以及处理任意表达式的可能性，强调了完美哈希在实际应用中的潜力和优势。同时，他也指出了在使用完美哈希时需要有一个备用的基准哈希路径。

Denuvo Analysis

作者: StefanBatory | 评分: 209 | 评论数: 14 | 发布时间: 2025-06-09 16:50
文章摘要

这篇文章详细分析了Denuvo，一种成功的反篡改和数字版权管理（DRM）系统，主要用于保护游戏不被盗版和逆向工程。Denuvo通过独特的硬件验证和加密技术，确保游戏代码的完整性。其工作流程包括： 1. 首次启动程序时，Denuvo收集硬件信息并发送至服务器。 2. 服务器处理后返回一个许可证文件，包含加密常量和硬件信息。 3. 程序之后使用该文件进行本地验证，无需再次联网。 4. 程序执行时会检查当前硬件信息是否匹配，若不匹配则导致游戏崩溃。 Denuvo通过将部分指令移除并加密，存储在许可证文件中，只有合法用户才能正确解密并执行原始游戏指令。该系统复杂且难以破解，但也引发了对用户体验的争议。

评论摘要
主要讨论点：Denuvo DRM的技术分析、效果、争议及其对游戏行业的影响 不同观点： • **Denuvo的技术细节和问题**：[farmdve]指出Denuvo选择UD2是继承自SecuROM时代的遗留做法，并解释了某些游戏在未来可能无法正常运行的问题。他详细描述了Windows行为变化如何导致Denuvo保护的游戏出现异常，特别是CPUID钩子引发的问题。[yukIttEft]则通过LLVM尝试去除Denuvo的x86混淆，发现其使用堆栈机和大量混淆操作（MBAs），增加了破解难度。 • **Denuvo的市场和商业价值**：[2c2c2c]提到其朋友曾开发出类似于Denuvo的DRM技术，但未能成功商业化。他认为独立游戏开发者可以从类似的技术中受益，并提出是否有可能由大型发行商收购此类技术。 • **Denuvo的有效性**：[rjh29]认为Denuvo非常有效，因为即使多年后，受Denuvo保护的游戏仍然无法被破解。[tristor]支持这一观点，表示尽管自己不购买任何带有Denuvo的游戏，但承认Denuvo在反盗版方面的工程成就。 • **对Denuvo的批评和抵制**：[menthe]认为使用AI模型可以轻松解决Denuvo的保护机制，并批评AAA游戏不值得花费精力。 [shmerl]主张通过抵制购买来反对DRM。 [mdaniel]则批评Denuvo对正版用户的体验造成了负面影响。 • **对DRM和游戏行业的哲学思考**：[doctorpangloss]认为Denuvo为游戏开发者提供了反盗版选择，并讨论了DRM在不同平台上的作用和必要性，指出对DRM的反对更多是情感上的而非技术上的问题。 • **社区和个人动态**：[Traubenfuchs]提到了著名Denuvo破解者Empress的个人风格和社区动态，关注破解社区的著名人物及其影响。 补充讨论： • **技术术语的争议**：[flerchin]对“stolen constants”或“stolen instructions”的术语使用感到困惑，认为“拦截”可能是更准确的描述。 • **对开发者的赞赏**：[StefanBatory]对一位二年级计算机科学学生进行的Denuvo技术分析表示赞赏，认为其分析水平很高。 争议的焦点： • Denuvo的有效性和对用户体验的影响是主要争议点。支持者认为其在反盗版方面非常有效，而反对者则批评其对正版用户的负面影响以及对游戏体验的破坏。 • 另一个焦点是DRM在游戏行业中的必要性和道德性，涉及到对独立开发者和大型发行商的不同影响。

Another Crack in the Chain of Trust: Uncovering (Yet Another) Secure Boot Bypass

作者: vitplister | 评分: 74 | 评论数: 7 | 发布时间: 2025-06-10 19:55
文章摘要

Binarly Research团队发现了一个影响大多数支持UEFI设备的Secure Boot bypass漏洞，编号为CVE-2025-3052。该漏洞源于一个使用微软第三方UEFI证书签名的模块，攻击者可利用其内存损坏漏洞在启动过程中运行未签名代码，从而绕过Secure Boot，危害系统信任链。漏洞的根本原因是不安全处理NVRAM变量，导致任意内存写入。微软在2025年6月10日的Patch Tuesday中通过向dbx数据库添加14个新哈希来缓解此问题。Secure Boot通过验证操作系统加载器的完整性和真实性来防止此类攻击，但此漏洞使其失效，可能导致早期攻击和系统防御被破坏。

评论摘要
主要讨论点：UEFI、Secureboot与传统BIOS的优缺点及安全性 不同观点： • **质疑UEFI/Secureboot的优势**：jrm4表示不理解UEFI/Secureboot相对于传统BIOS的优势，认为用户应该对自己拥有的硬件有完全控制权，并提出对不同操作系统（如Windows或Linux）的信任问题。 • **强调UEFI安全特性**：baxtr支持UEFI和Secureboot，认为它们能有效防止攻击者在操作系统加载之前执行恶意代码，从而保护系统免受bootkit等攻击。 • **批评实现中的漏洞**：db48x将问题归因于对NVRAM变量的不安全处理，认为这是由于纯粹的无能造成的，暗示UEFI的实现可能存在缺陷。 • **提供FLOSS解决方案**：fsflover提出使用TPM（可信平台模块）与Heads作为自由开源的替代方案，并提供了一个链接，表示这种方案对他有效。 • **怀旧和简单性偏好**：jerhewet简单直接地表达了对传统BIOS的偏好，希望回到使用BIOS的时代。 补充讨论： • 争议焦点之一是UEFI/Secureboot带来的安全优势是否足以抵消其带来的复杂性和控制权限制。 • 另一个值得注意的点是用户对硬件和软件的信任问题，这涉及操作系统的选择以及对不同安全机制的信任。 • 还有对具体技术实现中的漏洞和缺陷的批评，以及对自由开源解决方案的推荐和支持。
