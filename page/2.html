C++: Maps on Chains

作者: signa11 | 评分: 11 | 评论数: 3 | 发布时间: 2025-07-11 07:27
文章摘要

文章讨论了在C++中使用`std::map`存储不重叠的整数区间时遇到的问题。默认情况下，`std::map`要求键具有严格的弱序关系，但区间之间可能存在不可比较的情况（如重叠），这违反了严格弱序的要求。文章分析了区间顺序为何不是严格弱序，并提出了一种解决方案：通过在比较操作符中检测和抛出重叠异常来避免未定义行为。这种方法通过确保每次插入的区间形成一个链来绕过问题，使得`std::map`可以在实际应用中正常工作。文章还提到通过异质查找（heterogeneous lookup）可以扩展功能，支持查找位于区间内的整数。

评论摘要
主要讨论点：如何处理C++中键为区间的map数据结构，特别是当区间重叠时的处理方式 不同观点： • [gsliepen的观点] 认为文章内容较为平淡，因为文章讨论了本不该在"disjoint map"中插入重叠区间的情况，并简单地通过抛出异常来解决。gsliepen进一步建议，更有趣的应该是展示如何实现一个适当的"interval map"（区间映射），而不是讨论抛出异常这种直接违背"disjoint map"初衷的方案。 • [Gupie的观点] 提出了一种通过修改比较运算符来解决区间重叠问题的方法，具体代码为：`bool operator<(const interval& x, const interval& y) { if (x.min < y.min) return true; if (x.min > y.min) return false; return x.max < y.max; }`。Gupie认为可以通过这种方式定义区间的排序，从而避免重叠问题，而不是简单地抛出异常。 • [z_open的观点] 强烈反对通过抛出运行时错误来解决问题，认为这是荒谬的，并支持通过修改比较运算符（如`x.min < y.min || (x.min == y.min && x.max < y.max)`)来处理区间排序问题。z_open还提到可以使用`unordered_map`作为替代方案。 补充讨论： • gsliepen对文章内容的评价更侧重于设计和实现的合理性，认为应该从根本上解决问题（实现一个适当的区间映射），而不是只处理异常情况。 • Gupie和z_open的讨论集中在技术实现层面，尤其是通过修改比较运算符来避免重叠问题。z_open进一步提出了使用无序映射（unordered_map）的建议。 • 争议的焦点在于如何处理重叠区间的问题：是通过抛出异常来阻止，还是通过修改比较运算符或使用其他数据结构来适应这种情况。

Parse, Don't Validate (For C)

作者: lelanthran | 评分: 58 | 评论数: 5 | 发布时间: 2025-07-09 08:07
文章摘要

这篇文章讨论了“解析而非验证”技术在C语言中的应用，以减少可被利用的错误风险。作者指出，常见的验证方法会导致系统深处的代码重复验证输入，增加错误机会。通过在输入边界处直接解析输入数据为特定类型（如`email_t`），可以避免系统内部重复验证的问题。文章建议使用不透明类型来替代`char *`，确保数据类型安全，防止恶意输入。这种方法不仅提高了安全性，还能借助编译器类型检查进一步减少攻击面。最终，只有边界处的函数处理原始`char *`输入，内部函数只接受已验证的类型。

评论摘要
主要讨论点：C语言中如何安全地处理数据类型和内存管理 不同观点： • [anon-3988] 认为C语言本质上是不安全的，除非通过类似newtype模式的方式对数据进行封装，比如将`char *`封装在带有大小信息的结构体中，以避免直接使用指针。该用户强调应尽量避免指针，只有在与外部库交互时才使用。 • [o11c] 反对使用`_t`作为自定义类型的后缀，因为这是为未来标准类型保留的。此外，他们认为通过将变量设为`NULL`来防止双重释放是无效的，真正的解决方案是明确所有对象的所有权，而C语言在这方面表现不佳。 • [pianoben] 同意将`char*`限制在程序边缘使用的概念，但认为实际操作中很难实现，尤其是在处理解析结果时，比如打印`email_t`类型时，又不得不回到`char*`。他们质疑是否需要自己实现I/O系统，或者是否有更好的方法来避免这些问题。 • [mrkeen] 对代码示例中使用`email_t`和`PARSE_ERROR`的混合提出质疑，认为这是一种不正确的设计，因为从逻辑上讲，`email_t`和`PARSE_ERROR`不应出现在同一个上下文中，甚至不应该通过编译。 补充讨论： • 争议的焦点之一是如何在C语言中有效地封装和处理数据类型，以避免常见的安全问题（如双重释放、指针误用等）。 • 另一个值得注意的讨论点是命名约定和类型设计，比如`_t`后缀的使用是否合适，以及如何避免在实际编码中出现类型混用的错误。 • 实用性与安全性之间的权衡也是一个核心问题，部分开发者认为在C语言中完全避免指针和低级操作是不现实的，尤其是在处理实际项目时。
