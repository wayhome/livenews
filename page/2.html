Software Is Made Between Commits

作者: jeremy_k | 评分: 135 | 评论数: 39 | 发布时间: 2026-06-11 16:28
文章摘要

Zed团队推出DeltaDB，一种新型版本控制系统，旨在取代传统的Git提交和Pull Request工作流。DeltaDB将代码变更记录为细粒度的"deltas"流，而非离散的提交快照，使得与AI代理的对话和代码编辑能够同步版本化。每条消息与其产生的代码修改并列记录，引用锚定在delta而非行号上，即使代码变动引用依然有效。这让团队成员和AI代理能实时协作，无需等待提交推送，对话本身成为软件的真正源头。Beta版即将发布。

评论摘要
主要讨论点：关于是否需要版本控制开发过程中的所有中间状态（包括AI代理的交互过程），以及这种做法的价值和隐私问题。 不同观点： • **反对派**：开发过程中的中间代码是"思考的过程"，充满混乱和死胡同，不应该被序列化和公开。提交应该是经过整理的原子化成果，而非真实的时间线记录。（tomjakubowski, Lindby, flerchin, Xotic007） • **技术怀疑派**：Git已经足够处理频繁提交，通过`--first-parent`和`--no-ff`等功能可以实现类似效果，不需要新工具。现有的issue tracker配合Git就能满足需求。（WorldMaker, pjm331, chrishill89） • **支持派**：代码审查应该更早介入，而非等到PR阶段。未来AI代理应该像团队成员一样协作，版本控制应该在后台透明进行。（Lindby部分观点, cbovis, sangeeth96） • **隐私担忧派**：这类工具会导致开发者监控问题，让人深感不适。Google已通过citc收集了十年的开发者数据。（mplanchard, jmole, tengbretson关于API密钥泄露的担忧） 补充讨论：有人认为代码库本身应该自解释，不需要额外的流程和文档（thom）；也有人担心市场竞争激烈，以及Zed可能被大公司收购（prodigycorp, mplanchard）。核心争议在于**开发过程透明度与隐私保护的平衡**。

Show HN: Boo – screen-style terminal multiplexer built on libghostty

作者: kylecarbs | 评分: 22 | 评论数: 3 | 发布时间: 2026-06-11 20:52
文章摘要

boo 是一个用 Zig 编写的终端多路复用器，类似 GNU screen。核心特性： 1. **会话持久化**：支持会话分离和重连（Ctrl-A d 分离，boo attach 重连） 2. **精准状态管理**：基于 Ghostty 的终端模拟核心解析所有输出，保存完整终端状态（内容、样式、光标、滚动） 3. **自动化友好**：提供 send、peek、wait 等命令，支持 JSON 输出，适合脚本和 AI 代理使用 4. **全屏管理界面**：boo ui 提供侧边栏管理所有会话 相比 tmux 更简单（只有会话概念），相比老旧的 screen 有现代化的终端仿真能力。典型自动化流程：创建无头会话 → 发送命令 → 等待输出稳定 → 读取屏幕状态 → 清理。

评论摘要
主要讨论点：关于某个终端复用器新项目的评价和技术问题 不同观点： • [stereo] 质疑项目定位不清：README只说明不是screen替代品，但没有解释相比screen或tmux的优势在哪里，希望了解差异化特性 • [darkteflon] 遇到技术问题但保持兴趣：在macOS Sequoia上安装后出现ReadOnlyFileSystem错误，无法使用'boo new'命令；表示对项目感兴趣，因为喜欢ghostty且发现Zellij不稳定，不需要嵌套标签功能 • [asar] 正面评价：认为项目看起来不错；分享了使用herdr作为agent终端复用器的良好体验 补充讨论：评论反映了用户对终端复用器的不同需求——有人关注产品定位和竞争优势，有人遇到实际安装问题，还有人在寻找更稳定简洁的替代方案。darkteflon的评论暗示当前终端复用器市场存在稳定性问题（Zellij崩溃）和功能过载问题（不需要的嵌套标签）。

评论摘要
主要讨论点：AI代码生成是否真正提升了生产力，以及用代码行数(LoC)作为衡量标准的问题 不同观点： • **批评LoC指标派**：工程师花费数十年强调生产力难以用简单指标衡量，代码质量比数量重要，但AI时代又回到用LoC、ticket数等衡量产出，这是倒退和尴尬的 • **怀疑AI生产力提升派**：公司声称AI提升生产力所以裁员，实际是用AI作借口纠正疫情期过度招聘，同时向投资者展示拥抱新技术；真正的生产力证据并不存在 • **技术局限派**：AI在大型企业系统中难以发挥作用，受上下文窗口限制，无法处理跨多个代码库的10万+行分布式代码；适合小型代码库和原型开发 • **组织问题派**：即使AI加速了开发，上层官僚体系不变，最终收益微乎其微；很多功能最终未上线，浪费了开发资源；公司需自上而下重建才能发挥AI价值 • **短视逐利派**：公司获得"免费"的产能提升后不是为客户创造更多价值，而是裁员省钱，老板只想短期获利 补充讨论：应将LoC视为"成本"而非资产，用"花费X行代码"的表述；人工审查代码的比例才是真正瓶颈；OpenAI博客强调百万行代码却不说产品价值，反映行业病态；AI采用紧迫性的说法(几个月内必须采用否则无法生存)缺乏依据，与其批评的夸大宣传无异
