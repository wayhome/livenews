NovaCustom – Framework Laptop alternative focusing on privacy

作者: CHEF-KOCH | 评分: 15 | 评论数: 7 | 发布时间: 2025-06-28 18:01
文章摘要

NovaCustom专注于提供注重隐私、安全和自由定制的笔记本电脑体验。他们采用开源且注重安全的Dasharo coreboot固件，不使用Google Analytics，并通过Signal和ProtonMail进行沟通。用户可以自行选择硬件配置，如内存和存储空间，甚至可以定制键盘和选择预装Linux或Windows系统。此外，NovaCustom支持自行维修和升级，提供3年保修和5年固件更新，确保设备持久耐用。他们还注重环保，重复使用包装材料，并为客户提供个性化服务，如刻字定制。NovaCustom的笔记本电脑起价1,770欧元，提供高度隐私保护和定制选项。

评论摘要
主要讨论点：NovaCustom与其他笔记本厂商（如Framework）的比较，以及对NovaCustom产品特点的评价和争议。 不同观点： • cosmic_cheese认为NovaCustom类似于System76或Tuxedo，因为它们可能使用的是Clevo/Tongfang等厂商的重新贴牌硬件，而非像Framework那样自行设计硬件。这种模式使得NovaCustom与Framework有所区别。 • necovek指出NovaCustom的主要卖点是开源的coreboot固件和禁用Intel ME（Intel管理引擎），但仅凭这些功能并不能使NovaCustom成为Framework的替代品。 • princevegeta89对NovaCustom提出的隐私问题表示困惑，认为Framework的硬件透明且可替换，软件选择自由，已经具有很高的透明度，质疑所谓的隐私问题是否真实存在。 • mgerdts对NovaCustom的高端定价与所配备的NVMe驱动器（使用主机内存缓冲HMB技术）表示不满，指出像WD SN850x这样性能更好的驱动器在亚马逊上的价格比NovaCustom标配的GOODRAM驱动器更低。 • speedgoose认为NovaCustom的8GB vRAM在2025年会显得非常有限，无法运行较大的语言模型，从而限制了其在某些高性能计算任务中的应用。 • getcrunk对NovaCustom的现代硬件和支持coreboot及Tails系统表示赞赏，但认为该公司缺乏像Framework那样的良好声誉和信任度。 • horsellama则对NovaCustom允许自定义超级键和配备Nvidia GPU表示欢迎，认为这可能是一款理想的笔记本。 补充讨论： • NovaCustom的开放源代码固件和禁用Intel ME功能是吸引部分用户的关键特点，但这些特点是否足以使其成为Framework的有力竞争者存在争议。 • 部分用户对NovaCustom的定价与硬件配置之间的匹配度提出质疑，特别是与市场上其他同类产品的对比。 • 用户对NovaCustom的硬件性能（如vRAM限制）及其公司声誉和市场信任度存在不同程度的担忧和期待。

Sirius: A GPU-native SQL engine

作者: qianli_cs | 评分: 53 | 评论数: 3 | 发布时间: 2025-06-28 14:18
文章摘要

Sirius 是一个 GPU 原生的 SQL 引擎，通过 Substrait 查询格式与现有数据库（如 DuckDB）集成，无需重写查询或进行重大系统更改。它适用于交互式分析、金融工作负载和 ETL 任务，在 TPC-H 测试中，SF=100 时相较于 CPU 查询引擎有约 10 倍的速度提升。Sirius 支持 Ubuntu 20.04 及以上版本、NVIDIA Volta 或更高版本的 GPU、CUDA 11.2 及以上，以及 CMake 3.30.4 及以上版本。用户可以通过 AWS 镜像、Docker 镜像或手动安装来配置环境。构建 Sirius 需要克隆其仓库并使用特定命令进行编译，如需使用 Python API，还需额外安装相关包。

评论摘要
主要讨论点：Substrait的应用及其在不同引擎和硬件加速上的可行性和挑战 不同观点： • cpard：对Substrait被更多地使用表示欢迎，提到它已被DuckDB等引擎支持，并指出Apache Gluten项目使用Substrait将Velox作为Spark的执行引擎。认为尽管Substrait有局限性，但需要更多这样的项目来推动其发展。 • b0a04gl：指出查询计划与其生成引擎紧密相关，包括成本模型、内存布局、并行策略和代码生成行为等。虽然Substrait实现了结构的可移植性，但实际执行效率依赖于引擎特定的重写。例如，在DuckDB中优化的计划在Sirius中可能表现不佳，除非进行重塑。 • tucnak：通过PG-Strom项目类比，讨论了GPU在数据库应用中的适应性问题。提到NVIDIA的GPUDirect技术和AMD的Alveo系列加速器。认为GPU的AI计算能力虽然常被强调，但其在计算网络中的应用（如数据移动和中间计算）可能更有前景。同时，提到Postgres的扩展性和外国数据API，指出一些替代SQL引擎可能在朝错误方向发展。 补充讨论： • tucnak引用了多个技术项目和文献（如PG-Strom、Versal、Corundum），进一步探讨了GPU和加速器在数据库和网络计算中的应用实例和潜力。 • 争议焦点之一是GPU是否适合数据库操作，尤其是在与传统SQL引擎比较时，GPU的角色和效率问题。 • 另一个讨论点是Substrait在不同引擎间的执行效率问题，以及如何在不同引擎之间实现查询计划的优化和重写。

评论摘要

本文讨论了评估长文本问答系统时面临的挑战和关键指标。随着文档长度增加，如技术文档、小说或多文档场景，信息过载、位置差异、多跳推理和模型幻觉等问题变得更加突出。评估问答系统不仅要考虑答案的准确性，还要关注**忠实性**和**有用性**两个维度： 1. **忠实性**：答案是否严格基于源文档，不添加外部信息或捏造内容。特别在法律、金融等领域，答案必须基于给定文本。系统还需知道何时应回答“不知道”。 2. **有用性**：答案是否相关、详细且简洁。它应直接回应问题，包含必要细节，且简洁明了。 此外，引文准确性也是评估标准之一，确保引用的文本支持答案。文章还提到如何构建评估数据集及使用人类标注和LLM评估问答性能，并回顾了多个基准测试。

ZeQLplus: Terminal SQLite Database Browser

作者: amadeuspagel | 评分: 40 | 评论数: 4 | 发布时间: 2025-06-28 12:32
文章摘要

ZeQL+ 是一个开源的终端 SQLite 数据库浏览器，具有快速、轻量、无依赖等特点。它可以在 macOS、Linux 和 Windows 10+ 系统上运行，支持打开任意 SQLite 数据库文件、浏览表和分页查看表行，还能运行自定义 SQL 查询并查看结果。用户可以从发布页面下载预构建的二进制文件，直接运行而无需安装。此外，ZeQL+ 使用 Vlang 开发，用户也可以从源码构建。项目遵循 MIT 许可证。

LLMs Bring New Nature of Abstraction

作者: hasheddan | 评分: 37 | 评论数: 8 | 发布时间: 2025-06-25 10:55
文章摘要

Martin Fowler探讨了生成式AI，尤其是大型语言模型（LLMs），对软件开发的深远影响。他认为，LLMs带来的变革堪比从汇编语言到高级编程语言的转变，但这次不仅是抽象层次的提升，还引入了非确定性工具的编程问题。过去，高级语言（如Ruby）使编程变得更加直观和高效，但本质上仍是以传统方式与机器对话。而LLMs的非确定性特性意味着，使用提示词与机器交互将带来根本性变化，每次输出的结果可能不同，无法通过版本控制确保一致性。这种非确定性是软件开发历史上前所未有的，虽然带来挑战，但也蕴含着尚未被完全理解的机遇，令人兴奋。

评论摘要
主要讨论点：围绕LLMs（大型语言模型）和自然语言编程的适用性、实现方式及其潜在问题的讨论。 不同观点： • **引用先前的研究和批评**：bwfan123 提到 Dijkstra 早年关于“自然语言编程的愚蠢性”的文章，认为当前对“英语作为编程语言”的炒作应被质疑，并呼吁作者引用相关文献以提供更扎实的讨论基础。 • **自然语言的精确性问题**：agentultra 认为自然语言不够精确，无法用于编程，尤其在语义和底层实现的精确性上存在问题。该评论者对“自然语言编程”持怀疑态度，并暗示人们可能混淆了自动化与自然语言编程的区别。 • **模型的改进方向**：abeppu 提出应将重点从适应LLMs转向让模型本身理解编译和执行，建议通过训练模型在代码文本、中间表示（IR）、字节码等多个层次上进行学习，以提高模型的可靠性。评论者认为当前的LLMs存在如变量不存在或方法调用不匹配等问题，并提出通过增加对代码行为和人类描述的训练来解决这些问题。 • **对非确定性的态度**：ptx 对使用LLMs带来的非确定性表示反对，认为不应为了未知的潜在好处而放弃确定性，表达了对当前趋势的怀疑。 • **对自然语言编程的怀疑**：w10-1 对自然语言编程作为“根本性变革”的说法表示怀疑，认为当前的讨论缺乏具体依据，并质疑所谓“新抽象”和“自然”的特点和来源。 • **重复讨论**：bgwalter 指出该讨论是另一个链接的重复，并提到原讨论正在快速沉没，暗示该话题可能缺乏足够的关注或价值。 • **LLMs生成代码的必要性**：dingnuts 质疑为何LLMs在自然语言编程中需要生成高级语言（HLL）代码，而不是直接生成字节码，提出了对LLMs生成代码方式的改进建议。 • **LLMs的确定性问题**：sgt101 澄清了LLMs的确定性问题，指出LLMs本身是确定性的，但特定硬件（如NVIDIA GPU）上的优化可能导致非确定性结果，强调非确定性是一个可选的设置而非LLMs的固有属性。 补充讨论： • **对自然语言编程的争议焦点**在于其精确性和可行性，部分评论者认为自然语言不够精确，无法替代传统编程语言。 • **对LLMs的改进建议**主要集中在模型对代码的理解和编译过程的参与上，通过多层次的学习和训练来提高模型的可靠性和准确性。 • **对非确定性的态度分歧**：部分评论者对LLMs带来的非确定性表示担忧，而另一些评论者则指出这种非确定性是可控的。
