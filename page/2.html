Curl-impersonate: Special build of curl that can impersonate the major browsers

作者: mmh0000 | 评分: 410 | 评论数: 20 | 发布时间: 2025-04-03 15:24
文章摘要

`curl-impersonate` 是一个修改版的 curl，能够模拟 Chrome、Firefox、Edge 和 Safari 四大浏览器。它通过调整 TLS 和 HTTP 握手过程，使其与真实浏览器的表现完全一致，从而绕过网站对客户端进行的 TLS 和 HTTP/2 指纹识别。该工具可以像常规 curl 一样从命令行使用，也可以作为库集成到项目中替代常规的 libcurl。 为了实现模拟，`curl-impersonate` 做了以下修改： 1. 使用与浏览器相同的 TLS 库（如 Firefox 的 NSS 和 Chrome 的 BoringSSL）。 2. 调整 TLS 扩展和 SSL 选项。 3. 修改 HTTP/2 连接设置。 4. 使用特定标志运行，如 `--ciphers` 和 `--curves`。 该工具支持多个版本的浏览器，并提供了包装脚本方便使用。详细使用方法和支持的浏览器列表可以在文档中找到。

Why do we need modules at all? (2011)

作者: matthews2 | 评分: 105 | 评论数: 23 | 发布时间: 2025-04-02 07:34
文章摘要

本文讨论了是否需要在编程语言中使用模块，提出了一种不同的编程方式。作者Joe Armstrong建议取消模块，所有函数拥有唯一名称和丰富的元数据，并存储在一个全局的可搜索键值数据库中。这种方式的优点包括简化代码贡献，只需添加单个函数，而不是完整的项目，同时内容经过同行评审。作者还提到当前模块系统的优缺点，例如模块提供了编译和代码分发的单元，但决定函数归属模块常常很困难，且可能破坏封装。他以Erlang中的`lists.erl`和`string.erl`为例，说明在多个模块中选择合适的一个放置函数的困惑，并介绍了自己在`elib1_misc.erl`中积累的常用函数。

评论摘要
主要讨论点：关于是否需要模块和层次命名空间的争论 不同观点： • **支持模块和层次命名空间**： - **ludston**：认为模块有助于避免搜索结果被无关代码污染，帮助组织核心功能，避免过长的函数名前缀，如匈牙利命名法。 - **bionhoward**：模块限制了开发者在同一时间需要处理的复杂性，符合人类记忆限制（7±2概念）。 - **layer8**：模块不仅能将协同工作的函数组合在一起，还能隐藏实现细节（私有函数），并作为版本控制的基本单位。 • **支持扁平命名空间**： - **Joe**：Erlang社区成员，支持扁平命名空间，认为层次命名没有逻辑性且不扩展，用例子（啤酒和薯条）说明扁平命名足够。 - **jasode**：指出即使没有模块，大型代码库中会通过元数据标签等方式重新发明层次结构，但扁平命名迫使函数名唯一，可能导致名称过长。 • **中立或反思性观点**： - **jonnycat**：虽然不完全同意反对层次命名空间的观点，但尊重提出者的专业知识，倾向于倾听和学习。 - **andrewcl**：认为设想无模块的世界有其价值，但难以实际实现，模块作为分隔手段有其必要性。 补充讨论： • **Unison语言的提及**： - **anonzzzies**和**neongreen**：提到Unison语言使用函数数据库和自由重命名标识符，可能解决部分命名空间问题。 • **对扁平命名空间的批评**： - **Etheryte**：质疑扁平命名空间只是将复杂性转移，而非解决，在海量函数中寻找特定函数变得困难。 - **immibis**：通过JavaScript的npm生态系统例子，说明单一扁平命名空间会导致混乱和管理问题。 • **安全性和动态加载**： - **friendzis**：提出全局命名空间可能导致安全问题，特别是在动态加载代码时，模块有助于限制变更的影响范围。 • **对高级功能的设想**： - **wruza**：认为函数多分类、搜索等高级功能过于理想化，现实中实现难度大。 争议的焦点：模块和层次命名空间是否必要，扁平命名空间是否能有效管理大型代码库的复杂性。

Growing Buffers to Avoid Copying Data

作者: ingve | 评分: 17 | 评论数: 6 | 发布时间: 2025-03-31 21:16
文章摘要

本文讨论了在软件项目中避免数据拷贝以提升性能的方法，特别关注操作系统层面的支持。在C语言中，`realloc`函数可以在原地扩展或缩小内存，避免数据拷贝，但在C++中没有类似功能，只能使用`new`和`delete`。对于非平凡可复制类型，甚至不能使用`realloc`，需要手动构造和销毁对象。 为解决此问题，文章提出实现一个`resize_buffer`函数，尝试在原地调整缓冲区大小。对于小于内存页的缓冲区，这种方法可能导致巨大内存开销。而对于大缓冲区，可以通过操作系统的虚拟内存功能实现扩展。 在Linux上，使用`mmap`系统调用分配内存，并通过指定`base_addr`来确保缓冲区可扩展性。文章还提到在测试环境中，让系统自动选择地址会导致扩展失败，因此必须手动提供地址。 最后，文章邀请读者联系Johnny’s Software Lab LLC讨论性能问题或获取培训。

评论摘要
主要讨论点：关于内存管理、动态内存分配及其实现优化的讨论 不同观点： • [wilted-iris] 认为测量次数过少（仅十次）使得数据的可信度存疑，指出数据可能不足。 • [kazinator] 提出在使用 `realloc` 时应通过自定义的 `sane_realloc` 函数来处理边界情况，以避免 ISO C 中 `realloc` 函数的异常行为。他详细描述了 `sane_realloc` 的实现，并指出 `malloc(0)` 不一定返回 `null`，并给出了相应的解决方案。 • [hummusandsushi] 认为 C++ 的特性经常互相冲突，尤其是在面向对象特性与传统 C 代码结合时，这些额外的特性并没有增加太多价值，反而限制了程序员的自由。 • [Dwedit] 讨论了使用 `VirtualAlloc` 动态分配内存的另一种方法，即通过内存映射文件将同一内存页映射到不同位置，从而避免不连续内存块的复制操作。不过他也提到，系统调用有额外的开销（如 Meltdown/Spectre 缓解措施），因此避免内存复制未必总是能带来性能优势。 • [edoceo] 分享了一个在 ASP3/IIS 时代的实际案例，通过预分配缓冲区（如实现 `StringBuffer`）显著提升了运行时性能（提升了500%），尽管内存使用量增加了10%。 • [xeonmc] 提到了在 Windows 10 及以上版本中，可以使用 `VirtualAlloc2`，它允许保留占位符并分配 64k 页面，提供了更灵活的内存分配选项。 补充讨论： • 争议焦点在于不同内存分配和管理方式的优劣。`kazinator` 强调了 `realloc` 函数的边界问题，并给出了优化方案；`hummusandsushi` 对 C++ 特性持批评态度，认为其在实际应用中限制了程序员；`Dwedit` 和 `edoceo` 提供了关于内存管理和优化的实际案例，强调了内存管理对性能的影响；`xeonmc` 补充了在现代 Windows 系统中更先进的内存分配方法。

本文讨论了锚链接的实现问题，尤其是当页面底部标题无法滚动到理想位置时的解决方案。作者提出了一系列从简单到复杂的解决方法： 1. **快速修复**：通过增加额外内边距来调整。 2. **实际方案**：移动触发线，但可能导致标题位于视口底部，影响用户体验。 3. **良好方案**：翻译触发点，创建虚拟标题并将其上移，允许对个别标题进行灵活调整。 4. **优秀方案**：按比例上移触发点，确保标题可达且顺序正确。 5. **极致方案**：创建自定义映射函数，最小化标题原始位置与虚拟位置的均方误差（MSE），同时保持合理的间距。 作者逐步优化解决方案，以提升用户体验并解决锚链接问题。尽管最终方案复杂，但能提供更好的用户体验。
