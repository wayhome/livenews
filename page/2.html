How fast is N tokens per second really?

作者: hexagr | 评分: 164 | 评论数: 25 | 发布时间: 2026-05-18 02:04
文章摘要

这篇文章介绍了一个可视化工具，用于直观感受LLM的吞吐速度（tok/s）。文章指出，虽然各种基准测试报告速度数据（如M3上47 tok/s，4090上180 tok/s），但数字难以直观理解。 工具提供四种模式：代码（语法高亮）、文本（散文）、思考（推理过程）和代理（工具调用）。建议从30 tok/s开始体验，然后尝试不同速度档位（5-800 tok/s）和内容类型切换。 关键洞察：代码比散文的token密度更高，相同tok/s在不同内容类型下的感知速度差异很大。英文散文平均1.3 token/词，30 tok/s约等于23词/秒。工具旨在揭示基准数字与实际感知体验之间的差距。

评论摘要
主要讨论点：AI代码生成中的token生成速度对开发体验的影响 不同观点： • **速度需求派**：认为当前速度太慢，需要更高性能。aurareturn提出AI Agent至少需要60 tok/s（而非AI之前的10 tok/s），ohadron期待600+ tok/s的体验，kirugan认为15 tok/s太慢 • **速度过快派**：dinkleberg和ricardobeat指出超高速度（100-150 tok/s）反而难以跟踪AI的操作，容易在发现问题前就消耗大量token，建议高速仅用于subagent • **质量优先派**：bjelkeman-again认为在20-30 tok/s的本地硬件上，输出质量比速度更重要；adampzakaria倾向使用中等thinking模型以保持开发节奏 • **技术细节派**：antirez强调需区分prefill速度和decoding速度，以及它们随context增长的变化。SXX和Aurornis指出thinking tokens通常占2-3倍甚至更多，实际可见输出只是一小部分 补充讨论：多位评论者提到本地推理的可接受标准（prefill 100+ tok/s，generation 10+ tok/s），以及不同使用场景（代码生成vs文本分析）对速度需求的差异。unglaublich补充指出实际速度体验还受tool-calling、metadata等背景噪音影响。

Reviving old scanners with an in-browser Linux VM bridged to WebUSB over USB/IP

作者: gmac | 评分: 44 | 评论数: 7 | 发布时间: 2026-05-18 10:08
文章摘要

这篇文章介绍了 yes-we-scan.app 网页应用的开发背景和技术原理。作者为了让旧 USB 扫描仪重新可用，利用 v86 在浏览器中模拟 x86 机器运行 Alpine Linux 和 SANE 扫描软件。技术架构包括：用 C 程序连接扫描仪并传输数据，通过 USB/IP 将 USB 数据转为 TCP 包，用 tcpip.js 处理网络协议栈，最后通过 WebUSB API 连接实体 USB 设备。扫描数据实时压缩为 JPEG 或 PNG 格式。该应用理论上支持数百款扫描仪型号，目前仅在作者的 Canon 扫描仪上测试过。

评论摘要
主要讨论点：关于一个基于WebAssembly的扫描仪网络应用项目的技术实现和开源合规性问题 不同观点： • **开源许可质疑**（ValdikSS）：项目使用了CUPS/SANE代码但未按许可证要求开源，这是第二次违规。作为贡献者保留法律追诉权利，但仍认可项目概念并希望未来能开源 • **实用替代方案**（raffraffraff, Aloha）：有人用树莓派+旧iPad自建了类似方案；也有人指出直接购买VueScan等成熟跨平台软件更简单 • **技术架构质疑**（jdub）：虽然基于SANE和CUPS合理，但在WebAssembly中模拟整个Linux内核和用户空间似乎过于复杂 • **使用场景局限**（ocdtrekkie）：不愿使用WebUSB技术，但认可USB供电扫描仪的便携性价值 • **功能扩展建议**（DeathArrow）：询问能否将此方案推广到其他旧设备，而非仅限扫描仪 补充讨论：争议焦点在于开源合规性与技术实用性之间的矛盾——项目创意获认可，但许可证违规和技术复杂度引发质疑。

Saying Goodbye to Asm.js

作者: eqrion | 评分: 244 | 评论数: 21 | 发布时间: 2026-05-20 12:01
文章摘要

Firefox 148开始默认禁用asm.js优化，并计划在未来版本中完全移除相关代码。asm.js是Mozilla在2013年推出的技术，通过识别JavaScript的严格静态类型子集实现接近原生的执行速度，为WebAssembly的诞生铺平了道路。随着WebAssembly的成功和asm.js使用量的下降，继续维护asm.js会增加维护成本和安全风险。Mozilla建议开发者将asm.js内容重新编译为WebAssembly以获得更快的执行速度和更小的二进制文件。现有asm.js代码不会中断，仍可作为普通JavaScript运行。

评论摘要
主要讨论点：Mozilla宣布停止支持asm.js，社区对此技术的回顾与WebAssembly的对比 不同观点： • **怀念派**：认为asm.js是重要的技术里程碑，曾实现了在浏览器中运行原生速度代码的突破（如Figma最初用C++通过asm.js验证可行性，Unreal Engine在浏览器运行等经典案例） • **进步派**：认为asm.js自然演进到WebAssembly是技术进步，WASM在加载时间、bundle大小等方面有明显优势（不需要解析成AST） • **实用批评派**：指出WASM的隔离性是双刃剑——虽然安全但限制了与JavaScript的互操作性，无法直接调用Web API，无法零拷贝传递buffer，而asm.js作为"纯JavaScript"在这些方面更灵活 • **技术怀旧派**：回忆当年Firefox的OdinMonkey针对asm.js优化，速度比Chrome快2-4倍的辉煌时期 补充讨论： 有开发者提出需要asm.js到WASM的转译器来处理遗留代码；也有人担心运行时动态生成WASM代码比生成JS代码更困难。多人引用Gary Bernhardt关于JavaScript的著名演讲，感慨12年前的预言成真。整体氛围是对asm.js的感激与告别，同时承认WASM是更好的未来方向。
