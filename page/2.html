Twentyseven 1.0

作者: 082349872349872 | 评分: 22 | 评论数: 2 | 发布时间: 2025-08-01 22:10
文章摘要

Twentyseven 1.0.0是一个用Haskell编写的鲁比克方块解算器，是作者的早期项目之一，最初提交于2014年，2016年在Hackage上发布0.0.0版本。该项目源于作者对Haskell的兴趣，Haskell的惰性求值特性使其成为理想的选择。1.0.0版本主要是为了纪念，并使其能在当前GHC版本上编译。项目核心算法采用迭代加深A*（IDA*）搜索算法，以处理鲁比克方块庞大的状态空间。通过预计算和投影技术，IDA*能估算剩余步数，从而找到最短解法路径。尽管Twentyseven能找到最优解，但耗时较长。相比之下，Kociemba的两阶段算法速度更快，但非最优解。第一阶段将方块定向并分离边块，第二阶段限制移动以保持定向，从而在较小状态空间内快速求解。

Self-Signed JWTs

文章摘要

这篇文章讨论了一种替代传统API密钥管理的方案，使用JWK（JSON Web Key）自生成密钥对，以简化开发流程并提高安全性。作者批评了现有API服务繁琐的设置步骤，包括创建账户、验证邮箱、添加信用卡等。他提出开发者可以通过简单的代码生成自己的ES256密钥对，从而避免这些步骤。文章还介绍了如何在服务器上存储私钥，并使用JWT（JSON Web Token）来授权操作。客户端通过反向代理将签名的JWT添加到请求中，以执行特权操作。关于收费API，作者建议当请求来自未付费的公钥时，返回支付链接；付费后，将公钥与付费账户关联。对于B2B2C场景，作者提出使用分层JWK派生方案，使开发者为其终端用户生成子密钥，并通过零知识证明验证授权。

JSON is not a YAML subset (2022)

作者: AndrewDucker | 评分: 34 | 评论数: 5 | 发布时间: 2025-08-01 21:06
文章摘要

文章主要指出，JSON并不是YAML的子集，因此不能安全地用YAML解析器来解析JSON。这会导致两种问题：JSON文档无法被YAML解析，或者被解析成语义不同的YAML结构。特别提到“挪威问题”，即YAML允许不加引号的字符串，导致意外结果。例如，YAML会将“NO”解析为布尔值false。此外，YAML 1.1和JSON在数字格式上也有差异，如YAML要求“1e2”写成“1.0e+2”。虽然YAML 1.2试图解决此问题，但JSON文档无法使用%YAML指令选择新版本解析方式，因此问题依然存在。

评论摘要
主要讨论点：YAML与JSON的兼容性、YAML 1.1与1.2的差异、YAML与Unicode处理问题、YAML与XML的比较 不同观点： • [pavel_lishin] 认为YAML 1.2的广泛采用与否并不重要，因为YAML解析器不能直接用于解析JSON文档。他质疑那些试图用YAML解析JSON的人的动机，称之为“假设的疯子”。 • [zzo38computer] 指出YAML 1.1和JSON在数字表示上的不同（如1e2在YAML 1.1中需要写成1.0e+2）。虽然YAML解析JSON有问题，但可以通过转换格式解决。他还提到，如果不需要兼容现有格式，可以选择其他格式如DER。 • [deathanatos] 讨论了YAML 1.2在Unicode转义处理上的不足，指出其在处理Unicode字符时缺乏明确规范，导致与JSON的不兼容问题。他提供了Python和Rust库的例子来说明不同语言处理上的差异。 • [sshine] 质疑YAML 1.1的广泛使用，认为YAML 1.2应该成为默认版本，从而避免不必要的YAML头部声明。他还指出JSON数字在实际语言实现中的复杂性，认为在处理科学计数法和大数时需要特别注意。 • [JonChesterfield] 强烈批评YAML的语法问题（如将 '[FI,NO,SE]' 解析为 ["FI", false, "SE"]），建议如果需要类似的功能，应该继续使用XML，认为XML在这方面更可靠。 补充讨论： • YAML 1.1与1.2版本之间的差异引发了对数字和Unicode处理的不同看法。 • YAML的解析问题和复杂性被多位评论者提及，特别是与JSON和XML的对比。 • 争议的焦点在于YAML的兼容性和规范的明确性，尤其是在处理Unicode和数字格式时。 • 对于在何种情况下使用YAML、JSON或其他格式，不同评论者有不同看法，取决于具体需求和环境。
