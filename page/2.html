Whose code am I running in GitHub Actions?

作者: ingve | 评分: 161 | 评论数: 18 | 发布时间: 2025-03-25 17:17
文章摘要

这篇文章讨论了GitHub Actions中使用可变引用（如标签）可能带来的安全风险。具体来说，有人在一周前向`tj-actions/changed-files` Action添加了恶意代码，导致秘密信息可能泄露。问题源于常用标签引用实际上是可变的，如果标签指向的提交被更改，Action将运行不同的代码。 为解决此问题，作者提供了一个shell脚本，用于检查本地仓库中所有使用的GitHub Actions，列出并统计每个Action的使用次数。作者建议使用不可变的提交ID来确保代码不变，并建议评估所使用Action的来源和必要性，优先使用来自大组织或自己编写的Action。 脚本通过Unix管道和一系列文本处理工具实现，具体步骤包括查找工作流文件、提取使用Action的行、清理和统计结果。作者最后对自己的项目进行了检查，发现大多数Action来自大组织，风险较小。

评论摘要
主要讨论点：GitHub Actions 的安全性和依赖管理问题 不同观点： • **dgl**：认为使用短 commit ID 仍然可能导致可变的引用，因为如果有人找到冲突或推送同名标签，可能会导致优先使用该标签。这种复杂性在不同服务上表现不同，例如 GitHub 禁止推送正好40个十六进制字符长的分支或标签，但其他服务可能不禁止。 • **mmmaantu**：指出即使固定了 SHA，如果依赖项本身没有固定自己的依赖项，仍然可能引入漏洞。例如通过易受攻击的标签拉取依赖项，这使得安全问题依然存在。 • **dietrichepp**：分享了个人经验，选择自己编写驱动程序来处理 CI 构建，而不是依赖公开的 GitHub Actions，以减少对 GitHub Actions 的依赖。虽然更耗时，但这样做可以更灵活地在本地运行构建。 • **ph3t**：认为 GitHub 的依赖图应该提供这种可见性，但实际体验中往往不准确，容易遗漏依赖项。此外，文章中的脚本没有涵盖 GitHub Actions 的传递依赖，如果第三方操作内部依赖于易受攻击的操作，则无法检测到。 • **bdcravens**：指出 GitHub Actions 可能被滥用，例如用于网页抓取以绕过限制，因为 GitHub Actions 使用住宅 IP 空间。 • **Joker_vD**：提出了一种设想，即在运行时检查标签是否仍然指向特定的 commit，并将这些“锁定”保存在单独的文件中，以实现依赖的锁定。 • **dqh**：不喜欢在关键构建路径中使用社区提供的 Actions，更倾向于使用官方的 actions/* 或通过 actions/github-script 调用 GitHub API。 • **donatj**：解释了 Git 标签和 commit ID 之间的权衡，指出 Git 标签的设计就是可变的，维护者可以删除和重新标记主要版本，这在社区中是默认的操作方式。 • **password4321**：提到文章回应了 Tj-actions/changed-files GitHub Action 被入侵的事件，讨论了检测工具的开发。 • **colek42**：分享了他们正在测试的解决方案，使用 `witness-run-action` 生成签名证明，以确保 Actions 的操作透明和安全，并寻求反馈。 • **ippem**：提到 GitHub 正在开发不可变 Actions，表示可以等待其实施和效果。 • **Jenk**：指出 GitHub 的文档中已经有关于使用 SHA 固定 Actions 的建议，并提到曾有工具和 linter 可以警告未使用 SHA 的情况。 • **ohgr**：认为整个软件生态系统基于“下载任意内容并运行”的模式才是更大的安全问题，相较之下 GitHub Actions 的问题只是其中一小部分。 • **dpkirchner**：批评 GitHub 自己的教程使用标签而不是完整的 commit SHA，造成了混乱。 补充讨论： - 争议的焦点在于如何有效管理 GitHub Actions 的依赖和安全性，特别是如何平衡使用标签的便利性和使用完整 SHA 的安全性。 - 提出了多种解决方案和工具，如固定 SHA、运行时检查标签和 commit 的关系、生成签名证明等，但每种方案都有其优缺点和实现难度。 - GitHub 官方正在开发不可变 Actions，这可能是未来解决这些安全问题的一个方向。

Scientists break down plastic using a simple, inexpensive catalyst and air

作者: PaulHoule | 评分: 129 | 评论数: 11 | 发布时间: 2025-03-21 20:12
文章摘要

北西部大学的研究人员开发了一种简单且经济的方法，利用空气中的湿气分解塑料废物。该过程使用无毒、环保的无溶剂方法，通过廉价的催化剂分解聚对苯二甲酸乙二醇酯（PET）的键，然后暴露在空气中，借助空气中微量的湿气将分解的PET转化为单体，这些单体是塑料的重要 building blocks。该技术比当前的塑料回收方法更安全、清洁、便宜且可持续，为创造塑料的循环经济提供了有希望的途径。该研究已发表在《Green Chemistry》上，解决了塑料废物这一全球紧迫的环境挑战。

评论摘要

Open-sourcing OpenPubkey SSH (OPKSSH): integrating single sign-on with SSH

作者: PranaFlux | 评分: 152 | 评论数: 22 | 发布时间: 2025-03-25 13:22
文章摘要

OPKSSH（OpenPubkey SSH）是一个开源项目，旨在通过集成单点登录（SSO）技术（如OpenID Connect）简化SSH密钥管理，无需手动配置SSH密钥。它利用OpenPubkey协议将公钥添加到ID Tokens中，使其能够像证书一样使用，从而支持SSH协议的SSO认证，而无需更改现有的SSH或SSO协议。OPKSSH的优势包括提高安全性，通过使用短期有效的SSH密钥减少密钥泄露风险，并提升便利性，用户只需登录身份提供商（IdP）即可生成SSH密钥。该项目解决了传统SSH密钥管理中的安全和使用难题，特别适用于需要频繁访问和权限管理的企业环境。

主要讨论点：通过ID Tokens实现SSH认证的可行性及替代方案 不同观点： • **zokier的观点**：认为ID Tokens不包含用户公钥，无法直接用于像SSH这样的安全协议。虽然SSH认证不一定要基于公钥，但这种方法缺乏直接性，错失了一个改进的机会。他建议可以通过GSSAPI或其他类似方法实现。 • **throw0101c的观点**：提出使用SSH证书的替代方案，通过建立内部SSH CA来实现短期证书认证，并提到一些自动化获取SSH证书的项目和商业产品。 • **_hyn3的观点**：比较了Userify的SSH密钥技术，认为其去中心化密钥和集中控制平面的方式更可靠，尤其是在认证服务器离线时。同时指出其依赖较多，增加了复杂性。 • **tptacek的观点**：赞赏这种证书认证方式，提到他们使用Teleport，具有类似的短 lived 证书认证功能，并强调其访问控制和审计日志的优势。 • **somat的观点**：希望看到如何通过SSH密钥登录网页，而非使用ID Tokens进行SSH认证。 • **password4321的观点**：提到一个支持X.509证书的OpenSSH分支，并提供相关技术文章链接。 • **bzmrgonz的观点**：关注该项目的安全性，质疑其代码构建的安全性，认为将认证过程转移到opkssh上需要进行安全审计。 • **samcat116的观点**：不确定这种方法与运行支持OIDC的SSH CA相比有何优势，认为服务器只需信任CA的密钥，而不必运行验证程序。 • **atonse的观点**：比较了这种方法与Tailscale SSH，并询问两者是否可能结合使用。 • **Aeolun的观点**：认为通过公钥返回标准和服务器端认证脚本来实现SSH登录并非新颖，自OpenID Connect发明以来就已可能实现。 • **kipz的观点**：对该技术表示赞赏，并愿意尝试。 • **znpy的观点**：指出通过AuthorizedKeysCommand等已有技术可以实现类似功能，认为这种方法并无太多新意，但对作者的实现表示肯定。 补充讨论： • 争议焦点在于这种新方法的实用性和创新性。部分用户认为它没有充分利用SSH协议的多认证方法特性，错失了改进机会；而另一部分用户则赞赏其创新和实用性。 • 安全性和代码审计也被多次提及，表明用户对新认证方法的安全性有较高关注。 • 多种替代方案（如SSH证书、Userify、Teleport、Tailscale SSH）被提出，展示了实现安全认证的多样性。
