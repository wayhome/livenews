Revisiting Knuth's "Premature Optimization" Paper

作者: signa11 | 评分: 140 | 评论数: 19 | 发布时间: 2025-06-26 11:17
文章摘要

本文重新审视了Knuth关于“过早优化”的观点，指出该观点常被误用。Knuth的原文实际上讨论的是在结构化编程无法有效表达某些功能时，是否可以在不牺牲性能的情况下避免使用goto语句。他通过一个多重集合的例子展示了使用数组和goto语句的实现，与基于map的实现进行比较，指出数组在元素少于约300个时性能更优。虽然goto能简化代码逻辑，但Knuth认为该例子并不恰当，建议通过乐观插入法优化，并通过循环展开进一步提升性能。Knuth在此背景下讨论了过早优化的弊端，强调在非关键部分的优化往往得不偿失。

评论摘要
主要讨论点：对Knuth关于“过早优化是万恶之源”这一名言的解读和应用 不同观点： • godelski认为，人们常常忽略Knuth原话中的后续内容，即不应放弃那关键的3%的优化机会。他建议在引用该名言时应更清楚地传达其完整上下文，以避免误解。 • dan-robertson指出，名言常被误用来反对任何基于性能考虑的设计选择，或者作为“后期修复”系统设计方法的借口。他认为在设计初期就应考虑性能问题，以避免后期难以优化。 • alexey-salmin幽默地提到，现代应用程序的性能瓶颈往往分散在多个小部分中，而不像过去那样集中在3%的代码中，这使得识别关键优化点变得更加困难。 • mjd表示对Knuth的论文非常赞赏，并提到Knuth在论文中还提到他避免使用GOTO语句是因为害怕被Edsger Dijkstra责备。 • layer8强调，优化的“过早”与否取决于是否通过基准测试确认优化对程序运行时间有实际影响，而不是简单地避免小优化。 • p0w3n3d理解的Knuth观点是先找到最热代码（即运行最频繁的部分），然后进行优化，而不是在非关键代码上浪费时间。 • bluGill提醒注意“过早悲观化”，即不应因为未 benchmark 代码而选择明显不好的方案（如使用冒泡排序），并强调避免写出难以阅读的代码。 • meindnoch以幽默的方式指出，任何代码都有可能在某个时候被频繁调用，因此需要考虑长远的可维护性和性能。 • osigurdson建议专注于算法复杂度（O(xN^k)），并认为在最小化算法复杂度之前，不应过早考虑并行化等问题。他还指出，未经审视的短语（如“过早优化”）被随意使用才是真正的万恶之源。 • monkeyelite提到Knuth的具体编程技巧，如在数组末尾放置哨兵以避免边界检查，使用register关键字，以及为每个应用自定义数据结构。 • subharmonicon热爱该论文，并多次阅读，强调该名言常被误解，建议回到原文以获得更全面的理解。 • kragen回忆论文中的其他内容，如Shanley设计准则和“n和半个循环”，并指出论文更多讨论的是控制结构和程序正确性证明，而不是单纯的优化问题。 • another_twist简单总结，认为Knuth的观点是检查优化的影响，因为每次优化都会带来复杂性和脆弱性成本，但有时优化后的代码比未优化的更易读。 • ethan_smith指出，该名言出自Knuth讨论更广泛编程方法论的论文，而非专门讨论优化的文章。 补充讨论： • 讨论中多次提到Knuth原文的上下文常被忽略，导致名言被误用。 • 不同参与者提供了对现代编程中优化问题的具体例子和个人经验，如现代应用的性能瓶颈和避免不良设计的建议。 • 争议的焦点在于如何界定“过早优化”以及何时应进行优化，特别是在设计初期和后期维护之间的平衡。 • 对Knuth原文中其他内容的回顾，如对控制结构和编程语言发展的讨论，为名言的正确理解提供了更多背景。

Use keyword-only arguments in Python dataclasses

文章摘要

Python的**dataclasses**是一个方便构造数据类的好功能，可以替代字典，并支持添加方法、动态属性和子类。相比手写类，dataclasses自动生成`__init__()`和`__eq__()`等方法，简化了开发。为了提高可维护性，建议使用`kw_only=True`参数，强制使用关键字参数调用，如`MyDataClass(x=1, y='foo', z=False)`。这样有两个好处： 1. 允许重新排序字段而不破坏调用者。 2. 允许子类添加必需字段，不受默认值限制。 对于需要保证向后兼容性和可扩展性的库作者尤其重要。

评论摘要
主要讨论点：Python 数据类（data classes）与基模型（base models）的使用，以及关键字参数和位置参数的使用优劣。 不同观点： • eachro 认为数据类是否优于繁琐的基础模型存在疑问，可能不再有必要使用基础模型。 • ayhanfuat 表示关键字参数虽然有用，但当变量名已经匹配时，重复书写显得繁琐，并希望 Python 能有 JavaScript 的简写属性语法。 • meander_water 提出可以使用 `KW_ONLY` 注解来明确指定哪些参数必须是关键字参数，以简化使用。 • FridgeSeal 对 Boto3 库中大量使用 `kwargs` 的方式表示不满，认为这使得参数不明确，增加了使用难度。 • joshdavham 询问是否存在其他方法可以在函数中实现类似数据类的参数强制行为。 • flakes 认为强制使用关键字参数可以提高代码可读性，但作为通用规则会使 API 使用起来很麻烦，建议仅在参数较多或相似时使用。 • joshdavham 补充说，强制关键字参数可以防止未来代码的破坏性更改，但在现有项目中添加这种要求可能导致破坏性变化。 • est 提到在项目中使用数据类时，不能直接将字典传递给数据类，而必须手动过滤键，建议改进初始化方式。 补充讨论： • 讨论中涉及了 Python 数据类中关键字参数的使用及其优缺点。 • 有人提出对现有项目进行这种修改的可行性和潜在问题。 • 提出了对数据类初始化方式的改进建议，以提高使用便利性。 争议焦点： • 关键字参数的强制使用是否会增加代码的冗余度和使用难度，还是在提高代码可读性和防止未来破坏性更改方面的优势更大。

LetsEncrypt – Expiration Notification Service Has Ended

作者: zdw | 评分: 135 | 评论数: 14 | 发布时间: 2025-06-30 04:49
文章摘要

Let's Encrypt已于2025年6月4日停止发送证书到期通知邮件。该决定基于以下原因：越来越多用户已实现证书续期的自动化，继续发送通知需保留大量电子邮件地址，有隐私风险，且该服务每年花费数万美元，资金可用于其他基础设施建设。此外，通知系统增加了技术复杂性。建议用户使用第三方服务如Red Sift Certificates Lite获取到期通知。Let's Encrypt已删除存储的与证书颁发相关的电子邮件地址，未来通过ACME API提供的邮件地址将转至ISRG的邮件列表系统，用户可自行选择订阅相关更新。

评论摘要
主要讨论点：Let’s Encrypt 停止证书过期通知邮件的服务及其影响 不同观点： • 一些用户认为 Let’s Encrypt 应该继续提供通知服务，或者至少提供替代方案（如在邮件中提到赞助商）。这些用户认为通知对于普通用户有价值，避免了他们自行设置监控的麻烦。（[weird-eye-issue]） • 另一部分用户支持 Let’s Encrypt 的决定，理解邮件通知的成本高昂，并且认为用户应该自行设置证书监控，而不是依赖证书颁发机构（CA）。（[leakycap], [scrapheap]） • 部分用户分享了自己的 DIY 监控方法，如使用命令行工具或编写脚本来自动检查证书过期时间，认为这是更好的解决方案。（[sltr], [jgaa]） • 一些用户对通知邮件的数量和频率表示不满，不希望在两个月内收到多封随机间隔的提醒邮件。（[Aachen]） 补充讨论： • 自动续订的支持者认为，自动续订是比邮件通知更好的解决方案，尤其是在大规模管理证书时。（[udev4096], [Jazgot]） • 有用户对证书过期这一概念本身提出质疑，不理解为何证书需要过期，而不是仅在必要时撤销。（[whatever1]） • 技术细节讨论中，有用户对 Let’s Encrypt 的证书验证机制提出疑问，特别是关于 DNS 验证的有效期和 ACME 协议中为何不支持基于文件的域范围证书验证。（[TekMol]） • 部分用户寻求更简便的监控工具，如 Slack 机器人，用于检查证书过期。（[nikolayasdf123]） • 对 Let’s Encrypt 停止邮件通知但仍保留新闻订阅选项的决定表示质疑，认为存在不一致。（[wordofx]） • 有用户关心未来获取证书时是否仍需要提供电子邮件地址。（[cbenskxk]） 争议焦点： • Let’s Encrypt 是否应继续提供证书过期邮件通知服务，一方认为这是用户便利的重要服务，另一方则认为用户应自行设置监控，CA不应承担此责任。
