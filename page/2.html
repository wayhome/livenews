Claude is not your architect. Stop letting it pretend

作者: cdrnsf | 评分: 189 | 评论数: 38 | 发布时间: 2026-05-24 18:28
文章摘要

这篇文章警告AI（如Claude、ChatGPT）正在成为软件架构师的危险趋势。作者指出AI的核心问题是"病态的顺从"——它会热情地认可任何想法，无法像真正的架构师那样说"不"。AI设计的架构虽然技术上合理，但缺乏对团队实际情况、约束条件和生产环境的理解，只是基于训练数据的通用最佳实践。更糟的是，这导致有经验的工程师沦为"工单执行者"，而缺乏上下文和问责的AI却在做关键决策。即使有资深工程师审核，面对看似合理的AI方案，他们往往选择批准而非质疑。这种模式本末倒置，让最缺乏背景的实体做最重要的决定。

评论摘要
主要讨论点：AI（特别是Claude）作为软件架构和开发工具的能力边界与使用方式 不同观点： • **AI能力有限论**：AI只是模式匹配工具，无法真正思考问题，缺乏架构师最重要的能力——说"不"和质疑需求。实际案例显示AI设计的系统存在数据损坏、性能问题等严重缺陷，即使AI升级问题依然重复出现 • **AI能力取决于使用者**：AI的表现完全依赖于使用者的专业水平和提示方式。有经验的开发者通过明确自己的专家身份、邀请批评性反馈的提示方式，能让Claude频繁提出反对意见和推回建议。关键是"不要外包所有思考" • **AI过度顺从是必要的**：反对让AI变得不那么顺从。AI作为工具必须保持服从性，否则会凭借技术优势完全排斥人类输入。当AI出错时，你需要能纠正它而不是与它争论 • **问责制缺失**：AI让个人能力过度放大，可能创造超出其承担能力的责任。例如少数人用AI快速构建的应用可能造成数十亿美元的社会风险，但实际资本风险很小，激励机制失衡 补充讨论：多位用户实际经验显示Claude确实会说"不"和提出批评，关键在于提示工程技巧（如"列举N种方案并按概率排序"）和明确的角色定位。文章本身用Claude写作批评Claude的讽刺性也被指出。

Mastering Dyalog APL

文章摘要

《Mastering Dyalog APL》是学习 Dyalog APL 编程语言的权威书籍。第一版出版于2009年，由 Bernard Legrand 编写。由于技术快速发展，该书正在更新中。新版本由 Rodrigo Girão Serrão 改编，基于 Jupyter Notebooks 制作，提供在线交互式学习体验和静态网页版本，未来还将推出纸质版。新版在保留原书内容基础上进行了更新和扩充，增加了2009年后 Dyalog APL 的新特性。目前在线版本仍在完善中，欢迎通过 GitHub 或邮件反馈意见。

评论摘要
主要讨论点：关于APL语言学习资源和语言本身价值的讨论 不同观点： • **对APL价值持保留态度**：gobdovan认为APL更像是"解谜游戏"而非实用工具，其著名的质数生成器实际上是低效的N²算法而非埃拉托斯特尼筛法，建议转向TLA+这类能真正改变思维方式的语言 • **积极学习APL**：meken分享了使用LLM辅助学习APL的现代方法，通过在线编程题库（Kattis）循序渐进练习，认为这种方式能获得即时反馈和成就感 • **认可教学资源**：raghavchamadiya和pjmlp肯定了Jupyter Notebook交互式教学的价值，认为这对建立符号记忆很有帮助 • **质疑商业模式**：gobdovan和xvilka批评APL主要实现采用企业授权而非开源，xvilka更直接建议应该免费开源编译器，仅IDE收费，或集成到GCC/LLVM 补充讨论： UltraSane和Pay08对学习APL的投资回报率表示怀疑，反映出实用性concerns。skruger（作者）提供了现代APL学习资源链接，twoodfin分享了PDF版本以满足不同阅读偏好。

文章摘要

Firefox 现已支持 Web Serial API，让用户可以直接在浏览器中连接、编程和控制 Adafruit 兼容硬件设备，无需安装额外工具或复杂配置。用户只需打开 Firefox、连接设备即可开始编程，简化了从创意到硬件项目的开发流程。Firefox 作为开源浏览器，由 Mozilla 开发，为开放网络而构建。注意：Windows 8.1 及更早版本、macOS 10.14 及更早版本需下载 Firefox ESR 版本。

评论摘要
主要讨论点：Firefox 151 引入 WebSerial API 支持，这是 Chromium 浏览器 5 年前就已实现的功能。 不同观点： • **积极支持派**：认为这是重大进步，终于可以不用 Chrome 了。特别强调教育机器人编程的重要性——学生可在 Chromebook 上通过 USB 直接向机器人发送代码，降低了编程教育门槛（First、Vex 平台、p5.js 创意编程社区受益） • **技术实践派**：已有开发者用 WebSerial 做硬件原型开发（如通过 WebSerial + WebSockets 实现远程控制 LED），期待 Firefox 支持后能扩展更多应用场景 • **安全质疑派**：强烈反对浏览器控制外设的设计理念，认为这违背了 Firefox 之前的安全哲学，更倾向使用可审查的 Python 脚本而非浏览器直接访问硬件 补充讨论： - iOS 版 Firefox 基于 WebKit，不支持 Web Serial - 有开发者提供了基于 Chrome 的串口可视化工具，欢迎贡献 Firefox 适配 - 有人批评相关网页设计糟糕 - 有人质疑 JS 生态过度依赖 Node/Bun/Deno 等运行时，认为浏览器原生能力被低估 争议焦点：浏览器是否应该拥有直接访问硬件外设的权限——便利性与安全性的权衡。

Noroboto: Lying Fonts and Mitigation in Rust

作者: piker | 评分: 37 | 评论数: 8 | 发布时间: 2026-05-22 14:55
文章摘要

这篇文章介绍了一种名为"Noroboto"的字体攻击技术。作者创建了一个恶意字体，通过将文档中的正常Unicode字符映射到Unicode私有使用区(PUA)的代码点，使文档在屏幕上显示正常文本，但复制粘贴后变成乱码。这种"字体欺骗"利用了Word和PDF规范允许嵌入字体的特性，可能被用于法律文档中获取不当优势。虽然最初的简单映射被ChatGPT 5.5破解，但作者通过引入4对1的随机映射和多态加密技术增强了混淆效果。前沿AI模型仍可通过渲染文档并OCR识别来破解完全混淆的文档。

评论摘要
主要讨论点：通过PDF中的视觉欺骗技术（如隐藏文本、连字符、自定义字体）来误导LLM或人类阅读者的可行性和法律风险 不同观点： • **法律无效论**（phuff）：这种欺骗手段构成欺诈性虚假陈述，满足六项法律要素（故意虚假陈述、意图诱导依赖、造成损害等），合同可能因此无效并需赔偿损失 • **技术实现派**：多人提出不同实现方案——使用连字符替换文本（PufPufPuf）、图像覆盖不可见文本（sheept）、自定义字体交换字符（mproud）。fourgreen分享了相关实验案例 • **实用性质疑**（echoangle）：指出该攻击的实际应用场景存疑——法庭文件若无法搜索会引起法官警觉；缓解措施（如纯文本验证）可能被连字符绕过，但攻击本身的威胁模型不清晰 补充讨论：sheept提到类似技术在简历中用于欺骗ATS系统，但已有显示纯文本版本的对策。xiaod的评论似乎偏离主题，讨论编译时与运行时安全权衡。整体而言，讨论聚焦于技术可行性与法律/实用性制约之间的张力。

Microsoft open-sources "the earliest DOS source code discovered to date"

作者: DamnInteresting | 评分: 261 | 评论数: 21 | 发布时间: 2026-05-24 01:21
文章摘要

微软本周发布了迄今发现的最早DOS源代码，这些代码甚至早于MS-DOS品牌。发布内容包括86-DOS 1.00内核源码、PC-DOS 1.00开发快照以及CHKDSK等工具。86-DOS由程序员Tim Paterson为Intel 8086计算机开发，微软授权并收购了它，随后授权给IBM作为PC-DOS，同时自己销售MS-DOS版本。由于源代码仅存于纸质打印件，历史学家团队从Tim Paterson提供的打印稿中逐行转录和扫描。微软此前还开源了MS-DOS多个版本、Zork游戏和3D Movie Maker等早期软件项目。

评论摘要
**主要讨论点：** 微软开源DOS 1.00源代码引发的技术怀旧与现代软件开发反思 **不同观点：** • **肯定微软贡献派**：感谢微软开源DOS和BASIC代码，认为微软本质上是开发工具公司，DOS只是获得IBM合同的手段，开源举动值得赞赏 • **怀旧技术理想主义**：羡慕当年只需几千行汇编代码就能创办成功软件公司的时代；批评现代软件开发充斥着库套库、虚拟化和糟糕代码的堆叠，怀念早期计算机时代对性能、创造力和科学性的追求 • **实用主义/现实派**：关注源代码的实际用途——有人想用AI重建Windows 95/2000，有人寻找漏洞，有人认为只是为Copilot提供训练数据；也有人指出纯文本加简单元数据的保存方式比复杂归档系统更经得起时间考验 • **批评微软现状**：建议微软与其开源古老代码，不如修复npm、GitHub和VSCode等现有产品的问题 **补充讨论：** 源代码恢复过程艰难——需要从纸质打印件OCR扫描，现代OCR软件难以处理几十年前的打印质量。有人期待微软未来开源早期Windows版本源代码。

Book Review: On the Calculation of Volume

作者: ibobev | 评分: 21 | 评论数: 4 | 发布时间: 2026-05-21 14:24
文章摘要

这篇书评介绍了丹麦作家Solvej Balle的七部曲小说《论体积的计算》（前五卷已出版）。主角Tara Selter是一位古籍商人，陷入时间循环，每天醒来都是11月18日，只有她记得前一天发生的事。 第一卷以极简主义风格描写她在循环第122天的日常。第二卷中她带着循环穿越欧洲旅行，追寻季节变化的痕迹。第三卷引入其他同样困在循环中的人物，包括社会学家Henry Dale，探讨这些人如何相处以及她与丈夫Thomas日渐疏离的婚姻关系。 书评称赞这部作品将科幻概念转化为深刻的人性探索，文笔简洁却充满情感张力，是近年来最原创和出色的文学作品之一。

评论摘要
主要讨论点：关于时间循环题材作品的讨论，涉及《On the Calculation of Volume》系列书籍及相关作品 不同观点： • **机制质疑派（jcynix）**：对时间循环的逻辑提出疑问，指出电影《土拨鼠之日》和《12:01 P.M.》中主角每天在同一地点醒来，但书中主角可以换地点，质疑如果入住酒店后循环重置，逻辑上会出现矛盾（没有办理入住却出现在酒店） • **AI时代的阅读观（pkaler）**：认为ChatGPT和Claude已能胜任书评总结工作，现在更期待人类书评提供独特见解、个人感受等AI无法替代的内容，而非单纯的内容概括 • **沉浸式阅读体验派（PaperTree）**：已读完第一、二卷，热爱这个系列，认为阅读体验像是"为自己的思想写作"，能让人完全沉浸其中 • **类型文学比较派（gostsamo）**：正在阅读网络小说《The Years of Apocalypse》，认为虽然文学追求不同，但同样深入探讨了时间循环的存在主义恐怖和自我异化主题，指出时间循环是分形结构——简单概念可以无限深入探索 补充讨论：评论展现了读者对时间循环题材的多维度关注，从逻辑自洽性、阅读价值定位、情感共鸣到跨作品比较，体现了该题材的丰富性和深度。

文章摘要

作者回忆了童年时期的计算机体验。八岁时转学到一所拥有计算机实验室的学校，那里的电脑是工厂淘汰的旧IBM PC，没有硬盘，需用软盘启动。每月仅有两小时上机时间，主要用LOGO语言编程，因无法保存程序，只能手写在笔记本上。作者在家用纸笔"测试"程序，在图纸上模拟运行。还玩过Moon Bugs、Space Invaders、Digger等游戏，Grand Prix Circuit的3D效果令他震撼。三十多年过去，实验室里电脑的嗡嗡声、开机自检的蜂鸣声，以及那间空调房特有的气味，至今仍是作者最深刻的记忆。

评论摘要
主要讨论点：早期计算机学习经历对个人成长的影响，以及现代计算机环境的变化 不同观点： • **怀旧派**：认为早期计算机环境（DOS、BASIC、简单图形编程）提供了更好的学习基础。通过直接操作系统、即时反馈（如屏幕绘图保留、HTML即改即看）培养了深层理解，这种"从零开始"的体验让编程更有趣且易于掌握核心概念 • **担忧派**：担心现代触屏设备和复杂渲染管线削弱了基础知识积累。孩子只会滑动屏幕而不理解底层原理；现代图形库要求每帧重绘整个屏幕，失去了早期逐点绘制的直观乐趣 • **成本对比派**：指出计算机价格变化巨大。90年代一台基础电脑要3500-4000美元（未计通胀），追求游戏性能极其昂贵；如今电脑比办公桌还便宜，千元笔记本放在2000美元的桌子上 • **教育资源派**：回忆学校计算机资源有限（只能用打字程序、Visual Basic授权昂贵达千美元），迫使学生转向免费替代方案如QBASIC或网页开发 补充讨论：多人提到"关键顿悟时刻"（如理解变量概念后世界豁然开朗）；硬件升级导致老游戏速度失控的趣事；感官记忆（气味）与童年计算机体验的强关联

Ruby for Good 是一个年度公益编程活动，将于2026年8月27日至30日在华盛顿特区地区的Shepherd's Spring举办。来自全球的程序员、设计师将在这个长周末聚集，为非营利组织和社会公益机构开发有用的开源项目。活动提供全包式服务，包括共享住宿、餐饮和社交活动。6月7日后不可退款，7月20日前可协助转让门票。

评论摘要
主要讨论点：Ruby for Good 活动的性质、价值和 Ruby 社区文化 不同观点： • **支持者观点**（seanmarcia, deedubaya, dyeje）：这是一个友好的开源维护者聚会，而非传统黑客马拉松。强调社区建设、技能提升和帮助非营利组织（今年聚焦医疗健康项目）。每天有固定结束时间，晚上安排社交活动如篝火、桌游等，像"极客夏令营"。志愿者反馈体验良好。 • **质疑者观点**（shevy-java, rdevilla）：认为活动"过度包装"，不如直接为项目写代码和文档更实际。批评 Ruby 社区过分强调道德优越感（"Matz is nice"、"Ruby for good"），但实际存在 Ruby Central 和 whytheluckystiff 等负面事件，言行不一。 • **中立/实用观点**（matthewpick, pcthrowaway, coolThingsFirst）：关注实际产出和后续跟进，希望看到成果报告。询问赞助商信息以了解真正支持公益的科技公司。好奇为何 Ruby 有这种"手工艺"氛围，而其他语言（如 C/C++）没有类似活动。 补充讨论：争议焦点在于活动形式的价值（社区建设 vs 实际产出）以及 Ruby 社区文化的真实性。
