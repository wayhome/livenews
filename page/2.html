Git Bug: Distributed, Offline-First Bug Tracker Embedded in Git, with Bridges

作者: stefankuehnel | 评分: 181 | 评论数: 17 | 发布时间: 2025-05-13 11:07
文章摘要

git-bug 是一个分布式、离线优先的 bug 追踪工具，嵌入在 Git 仓库中，通过 Git 对象管理问题、用户和评论，而非使用文件。其主要特性包括：原生 Git 存储、分布式且版本化管理、快速列出和搜索问题、支持与 GitHub 和 GitLab 等平台同步、提供 CLI、TUI 和 Web 界面，以及简易集成。项目采用 GPL-3.0 许可证，由社区贡献者和赞助者支持，初始创建者是 Michael Muré，Logo 由 Viktor Teplov 设计。

评论摘要
主要讨论点：围绕基于Git的Bug跟踪工具git-bug的实现、潜在问题及其与其他工具的对比，参与者们展开了多角度的讨论。 不同观点： • **支持并赞赏该工具的创新性**： - [AceJohnny2] 赞赏git-bug利用Git的DAG模型和不同的命名空间来存储数据，并提到类似工具如Gerrit也采用这种方法。 - [WD-42] 对本地优先软件的回归表示欢迎，并认为Github在快速连接下也变得难以使用。 - [mhh__] 认为将问题跟踪与代码靠近是非常有用的，尤其是在AI普及的时代，并且提到可以自动将Bug提升到测试套件中。 - [rzwitserloot] 长期以来一直希望有人能基于Git构建一个分布式的工单系统，并认为git-bug的实现非常令人兴奋。 • **对工具实用性的质疑**： - [hungryhobbit] 认为尽管工具整合是个好主意，但Bug跟踪器不仅是工程师的工具，其他团队如支持团队、设计团队和QA团队等也每天使用。如果需要额外工作来展示给非工程团队，那么整合的效果可能不如一个专为所有人设计的全功能跟踪器。 - [omneity] 对如何创建和解决Bug存在困惑，认为CLI缺少相关功能说明。 • **对工具分布式特性的争议**： - [IshKebab] 质疑将Bug跟踪工具分布式的必要性，认为可能带来不必要的复杂性，如需要解决Bug对话中的冲突，并指出工具解决的问题相对较小。 - [johanbcn] 提到在Firefox迁移到Github的话题中，有人曾讨论过是否应该将问题跟踪器分布式，认为git-bug的想法有趣。 补充讨论： • **工具对比与其他实现**： - [dannymi] 提到另一个类似的工具git-issue，且其依赖较少。 - [layer8] 提到2018年的TUI截图，但认为其他相关截图较少。 - [alasr] 提供了Git Bug的多个截图链接，包括TUI和Web界面的展示。 • **许可证问题**： - [tiffanyh] 指出git-bug选择GPL3许可证与Git的GPL2不兼容，这可能带来问题。 • **对社区反应的态度**： - [binary132] 对社区中一些人对此工具的负面反应表示不解，认为这些人可能过度依赖主流工具。 争议焦点： • 工具的分布式特性是否增加了不必要的复杂性。 • 该工具是否能满足非工程团队的需求。 • 许可证的兼容性问题。 总结：讨论围绕git-bug的创新性、实用性及其潜在问题展开，参与者们表达了赞赏、质疑和对比不同工具的观点，同时对分布式特性和许可证问题也有较多关注。

Migrating to Postgres

作者: shenli3514 | 评分: 129 | 评论数: 15 | 发布时间: 2025-05-14 21:39
文章摘要

文章介绍了Motion公司从CockroachDB迁移到PostgreSQL的过程。起初，CockroachDB因其水平扩展能力、高可用性和SQL兼容性被选中，但随着数据增长，运营成本增加了五倍，且出现迁移超时、ETL作业停滞等问题。迁移超时导致开发人员绕过数据库操作，甚至阻碍了CockroachDB的版本升级。此外，CockroachDB在处理某些查询时由于优化器问题导致性能不如PostgreSQL，某些查询在PostgreSQL中执行速度快二十倍。最终，Motion决定迁移到PostgreSQL，解决了超时和性能问题。

评论摘要
主要讨论点：对分布式数据库与PostgreSQL在处理大规模数据时的性能和适用性的比较与讨论 不同观点： • 一些评论者（如luhn, sreekanth850, mmiao）认为，1亿行数据量并不大，现代单节点服务器可以轻松处理，无需使用分布式数据库。他们指出，分布式数据库如CockroachDB通常在数据量达到数十亿行或需要跨区域写入时才显得必要。 • 另一方观点（如esafak, sgarland）批评了Prisma和CockroachDB的表现，指出它们在实际应用中可能导致问题，并强调在数据库设计和查询优化中的基本原则，如规范化、索引使用和查询优化。 • from-nibly提到，尽管PostgreSQL在很多情况下是理想选择，但仍可能存在PostgreSQL无法满足的特殊需求，不过从PostgreSQL迁移到其他数据库通常比反过来更容易。 补充讨论： • moonikakiss提出，PostgreSQL中的列存储（columnar storage）可能对某些慢查询有帮助，并提到他们正在开发一个工具（pg_mooncake）以实现这一功能。 • frollogaston和compton93讨论了查询优化器和索引使用的问题，特别是CockroachDB中的zigzag joins和PostgreSQL中查询 planner的成熟度。 • coolcase和hobs关注查询优化和性能问题，建议先优化不良查询，并指出在JSON操作和ORM使用中常见的问题。 • niwtsol对多区域写架构在PostgreSQL中的可行性表示关注，并探讨了GDPR合规要求是否是选择CockroachDB的主要驱动因素。 争议焦点： • 是否在数据量达到1亿行时就需要使用分布式数据库，还是应等到实际遇到性能瓶颈再进行扩展。 • Prisma和CockroachDB在实际应用中的表现及它们是否被过度使用或误用。 其他值得注意的讨论点： • PostgreSQL在处理现代应用负载中的灵活性和扩展性，特别是在使用列存储和查询优化方面。 • 对ORM（如Prisma）在数据库查询性能和设计上的影响的批评和建议。

文章摘要

The cryptography behind passkeys

作者: tatersolid | 评分: 156 | 评论数: 13 | 发布时间: 2025-05-14 11:22
文章摘要

这篇文章简要介绍了密码学中的身份验证，特别是通过加密技术实现的更安全的用户认证方式——** passkeys（通行密钥）**。虽然加密通常让人想到加密保密，但身份验证同样重要。传统的密码容易受到钓鱼攻击和数据泄露的威胁，而passkeys通过加密技术提供更强的安全性。 **Passkey的加密基础**是基于公私钥对的数字签名。注册时，网站保存公钥和标识符；验证时，网站提供挑战并等待包含该挑战的签名响应。由于服务器仅保存公钥，且用户不发送敏感信息，即使服务器被黑客攻击也不会泄露敏感数据。 然而，**WebAuthn** 规范通过绑定来源（origin binding）解决了钓鱼问题。浏览器将请求的来源传递给认证器，认证器只在请求来源与创建passkey的网站匹配时使用密钥对，从而防止钓鱼攻击。此外，WebAuthn只允许使用HTTPS的来源，确保请求来自具有有效证书的服务器。 **认证器类型**包括硬件或软件，可以验证用户的存在，某些还可以结合“用户所知”进行多因素认证。 总结来说，passkeys通过加密技术及WebAuthn规范实现了一种防钓鱼的强身份验证机制。

评论摘要
主要讨论点： passkeys技术的优缺点、同步与安全性问题、以及与现有身份验证方法的比较 不同观点： • labadal：喜欢passkeys的生物认证功能，但担心厂商锁定问题，关注标准化的进展。 • lxgr：提到一种基于密码短语的身份验证方法，但提醒这种方法类似于“脑钱包”，存在安全隐患，不建议用于重要场合。同时分享了一个自己实现的项目来展示技术可行性。 • whartung：质疑在不同设备和操作系统之间切换时，passkeys的有效性和密码恢复能力。 • petedoyle：关注passkey同步背后的加密强度，尤其是基于4-6位数字锁码的加密是否容易被暴力破解，担心实际熵值不足。 • nemoniac：质疑浏览器在passkeys流程中的必要性。 • joelthelion：询问passkeys是否正在获得实际应用。 • throw7：希望有一种平台身份验证器可以导入/导出明文的密钥对和凭证ID，以避免厂商锁定和云备份，提到目前使用TOTP的方案更为灵活。 • solarkraft：认为挑战-响应结合非对称加密的身份验证方式（如SSH）更为理想，批评passkeys缺乏备份和互操作性，并分享了一次失败的创建经历。 • andrewmcwatters：认为现有密码和密码管理器已经足够好，TOTP广泛支持，质疑passkeys的实际需求和可移植性，批评大公司推动的技术锁定。 补充讨论： • 关于passkeys同步的安全性：peteodoyle对同步过程中使用的锁码强度和实际熵值表示担忧，认为可能存在被暴力破解的风险。 • 关于passkeys的互操作性和备份问题：多个评论者（throw7, solarkraft, andrewmcwatters）提到passkeys在不同设备间的互操作性差，缺乏有效的备份和导入/导出机制，导致厂商锁定问题。 • 关于passkeys的实际应用和接受度：joelthelion和andrewmcwatters质疑passkeys是否正在获得实际应用和用户接受，认为现有方案已经能满足大部分需求。 争议焦点： • passkeys的厂商锁定问题和缺乏可移植性是主要争议点，多个评论者对此表示不满，并与TOTP等现有方案进行对比，认为后者更为灵活。 • passkeys的安全性和备份机制也是争议的焦点，尤其是同步过程中的加密强度和实际应用中的可靠性。
