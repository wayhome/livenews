这篇文章详细描述了@ctrl/tinycolor供应链攻击事件的调查与分析。攻击者通过向共享仓库angulartics2推送恶意GitHub Actions工作流，窃取了具有广泛发布权限的npm令牌，并利用该令牌发布了20个包含恶意代码的包（包括@ctrl/tinycolor）。GitHub和npm安全团队迅速响应，撤销了恶意版本。作者随后发布了干净版本以清除缓存。 文章分析了攻击路径：攻击者利用合作者权限直接推送恶意分支（无需PR审核），工作流自动执行窃取令牌。虽然作者启用了npm来源证明，但因攻击者持有有效令牌而未能阻止攻击。 作者提出了改进方案：计划采用npm可信发布(OIDC)消除静态令牌，加强2FA验证，限制发布权限，并关注pnpm的新安全设置。最后表达了希望npm能提供一键启用可信发布等安全功能的愿望。 事件突显了供应链安全风险，特别是共享仓库和宽泛权限带来的隐患。

评论摘要
主要讨论点：[如何改进 npm 包发布的安全机制] 不同观点： • **支持短期令牌和自动化流程** - 如 Trusted Publishing 方案，使用短期（15分钟有效）令牌，减少长期令牌风险 - 已在 PyPI、npm 等生态中实现，呼吁更广泛采用 - 争议点：文档是否清晰，需要更多支持（@darkamaul） • **强调 MFA（多因素认证）的必要性** - 当前 CI 流程中集成 MFA 操作复杂，需第三方工具 - 希望 npm/GitHub 提供原生支持（@mnahkies） - 争议点：自动化流程 vs 人工干预的平衡 • **质疑权限扩散问题** - 攻击者通过一个仓库的 npm 令牌为何能发布其他无关包（如 tinycolor）？ - 暴露令牌权限管理漏洞（@drdrey） • **提议多签名机制** - 单作者被入侵不足以触发发布，需多作者加密签名（@rectang） • **反对完全自动化发布** - 多数包无需频繁发布，人工 `npm publish` + 2FA 更安全 - 批评过度依赖自动化流程（@bikeshaving） • **批判静态令牌机制** - 静态令牌本质是“高级密码”，应改用动态身份验证（如 GitHub 与 AWS 的 OIDC 集成）（@cyberax） 补充讨论： - **现实落地障碍**：开发者对安全措施的抵触（如拒绝启用 2FA/OIDC）需强制政策推动（@waterTanuki） - **工具缺失**：缺乏检测漏洞包的公开工具（@indigodaddy） - **历史遗留问题**：清理旧依赖的可行性争议（@waterTanuki vs 激进简化提议） - **争议焦点**：安全性与开发便利性的权衡，以及平台强制措施的边界
