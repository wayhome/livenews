Win98-quickinstall: A framework and installer to quickly install Windows 98

作者: userbinator | 评分: 171 | 评论数: 20 | 发布时间: 2025-03-31 04:10
文章摘要

该项目是一个用于快速安装Windows 98的框架和安装程序，支持从486到现代系统的快速安装。它打包了一个已安装的Windows 98根文件系统，并允许自定义 slipstream 驱动和工具。使用Linux作为基础，配合一些工具进行硬盘分区和格式化，提供自定义安装程序和数据打包方法，从而实现从CD快速安装。在Pentium III级别机器上，安装时间约为60-90秒。支持Windows 98、98第二版和Millennium Edition，但不支持Windows 95。最低系统要求为i486 CPU和24 MiB内存。提供多种启动方式，包括CD/DVD-ROM启动、1.44M软盘启动和USB启动。构建环境需Windows 7/8.1/10/11或现代Linux版本及Python 3.5以上。

How to Secure Existing C and C++ Software Without Memory Safety [pdf]

作者: aw1621107 | 评分: 96 | 评论数: 15 | 发布时间: 2025-03-31 07:36
文章摘要

该文章讨论了如何在不实现内存安全的情况下，提高现有C和C++软件的安全性。作者Úlfar Erlingsson指出，虽然内存安全能防止许多漏洞被利用，但对于未修改的C/C++软件，可以通过消除软件内存损坏时的执行交错来实现类似的安全效果。文章介绍了几种实用的编译器和运行时机制，这些机制无需特殊硬件支持，且开销较小，已经在一些平台上投入使用。通过在开发工具链中整合这些机制，可以显著增强C和C++软件对抗远程代码执行攻击的能力。

评论摘要
主要讨论点：内存安全和防护机制的有效性及其实际应用 不同观点： • pizlonator认为isoheap（按类型分区分配）在防止use-after-free漏洞方面有一定作用，但其扩展性差，且无法防御类型混淆或堆缓冲区溢出等攻击。他基于自己的实际经验指出，大规模部署isoheap会导致巨大的内存和时间开销，且无法阻止攻击者通过单个指针访问控制整个堆。 • linux_security质疑内存安全防护技术的实际效果，指出尽管iPhone、Chrome、Android等广泛应用了这些技术，内存安全漏洞利用仍然频繁发生。他进一步质疑这些技术的成本，如对设备性能的影响（如电池寿命和速度）。 • gizmo认为，通过重新编译遗留软件以增强堆栈和堆漏洞利用防护是可取的，但不同意将服务器软件重写为Go或Rust的建议。他强调，利用内核提供的进程隔离和权限管理机制才是解决服务器安全问题的根本途径。 • lambdaone和pjc50对论文中提出的四种完整性（栈完整性、控制流完整性、堆数据完整性、指针完整性和不可伪造性）的实际效果持怀疑态度，认为这些措施只能减少而非消除内存损坏的影响。 • cadamsdotcom赞同论文的务实态度，认为完全重写遗留代码是不现实的，并指出行业内对重写的抵触情绪。 • saagarjha指出，攻击者仍然可以绕过现有的缓解措施实现远程代码执行（RCE），且许多绕过方式是全新的和未被解决的，这要求对缓解措施进行重新设计。 • MattPalmer1086认为，尽管这些技术无法解决所有内存损坏问题，但确实显著提高了攻击门槛。 • mre强调，论文中的机制主要是攻击检测和缓解，而非预防，且这些技术仍需广泛的开发周期集成才能发挥实际效果。他进一步指出Rust等内存安全语言的必要性，因为它们在编译时预防内存安全问题。 补充讨论： • tzs提出了一个与主讨论关系不大的问题，即是否存在支持goto的快速内存安全语言，并讨论了使用goto来精确匹配表格计算的必要性。 • sebstefan怀疑论文是否由AI撰写，但未进一步阐述具体理由。 • tonyhart7和m00dy的评论较为简短，前者提及“内存 arena”可能相关，后者简单评论C++的缺陷。 争议焦点： • 这些内存安全防护技术的实际效果和可扩展性，尤其是它们是否足以防止复杂攻击（如RCE）。 • 是否应将遗留软件重写为内存安全语言（如Rust和Go），以及这种重写的可行性和必要性。 • 进程隔离与内存安全技术在不同环境（如手机与服务器）中的相对有效性和优先级。

Public secrets exposure leads to supply chain attack on GitHub CodeQL

作者: cyberbender | 评分: 250 | 评论数: 9 | 发布时间: 2025-03-30 19:54
文章摘要

本文介绍了GitHub CodeQL潜在供应链攻击的发现过程。攻击始于一个公开暴露的秘密，有效时间仅1.022秒。利用这一秒，攻击者可以在使用CodeQL的GitHub Actions工作流中执行代码，影响GitHub云平台和GitHub Enterprise。攻击者可能借此窃取私有代码库的源代码、盗取GitHub Actions中的凭证、在内网基础设施上执行代码，并进一步发动供应链攻击。 研究人员通过自建的Actions Artifacts Secret Scanner工具发现了这一漏洞（CVE-2025-24362）。GitHub Actions工作流会生成GITHUB_TOKEN，用于与代码库交互，若权限过高，令牌泄露将导致严重后果。尽管发现了潜在风险，GitHub表示尚未发现其平台或系统受到实际攻击的证据。

评论摘要
主要讨论点：GitHub Actions的安全性、临时令牌权限、CI/CD环境的分离以及自建CI系统的建议 不同观点： • [Sytten] 认为GitHub应推出不可变动作（immutable actions）以减少当前约70%的攻击风险。他提到这是解决GitHub Actions安全问题的关键，并暗示GitHub在这方面的进展缓慢。 • [nyrikki] 质疑临时令牌为何拥有创建新部署和生成工件证明的权限，指出GitHub的修复措施（禁用调试日志）未能解决临时令牌权限过大的问题。 • [ashishb] 主张将CI和CD环境完全分离，以防止CI的妥协导致CD相关令牌泄露，强调了两者分离的重要性。 • [udev4096] 建议不要使用公共GitHub Actions，认为分析工作流程序是必要的，并推荐使用自建CI系统（如Woodpecker、Circle、Travis、GitLab等）以提高安全性。 补充讨论： • [junto] 对GitHub的响应速度表示赞赏，认为其反应时间非常快。 • [helsinki] 提及个人对域名的兴趣，与主要讨论点无关。 • [ryao] 分享其在OpenZFS项目中使用CodeQL的经验，指出由于代码非保密，因此不存在相关问题。 • [atxtechbro] 直接询问问题是否已修复，未提供具体论据。 • [bloqs] 抱怨GitHub页面性能差，影响用户体验，但未涉及安全和技术细节。 争议焦点： - 临时令牌权限的适当性及其安全风险是讨论中的一个争议点，nyrikki指出GitHub的修复未完全解决问题。 - 使用公共GitHub Actions的安全性以及是否应使用自建CI系统是另一个争议点，udev4096强烈建议自建系统以提高安全性。 总结：讨论主要围绕GitHub Actions的安全性、临时令牌权限管理、CI/CD环境分离的必要性以及自建CI系统的优劣展开，各方对GitHub当前的解决方案和安全性措施存在不同看法。
