Bttf is a command line datetime Swiss army knife

作者: burntsushi | 评分: 102 | 评论数: 10 | 发布时间: 2026-05-28 02:58
文章摘要

Biff是一个命令行工具，用于处理日期时间的算术运算、解析、格式化等操作。主要功能包括：打印当前时间、在不同时区间转换、添加或减去时间段、计算时间跨度、格式化时间戳、生成日期序列（如每月第二个星期二）、从日志文件中提取和转换时间戳等。支持多种时间格式（RFC3339、RFC9557等）、时区处理、时间舍入、相对时间表达式（如"next sat"、"1 week ago"）。该工具采用MIT或UNLICENSE双重许可，提供详细的用户指南和命令行帮助文档。

评论摘要
主要讨论点：BurntSushi 发布的命令行时间处理工具 Bttf/Biff 及其技术特性 不同观点： • **工具命名混淆**：多位用户指出工具名称是"bttf"（Back to the Future 的缩写）而非"biff"，但评论中普遍混用两个名称。有用户提到"biff"是早期 Unix/BSD 的邮件通知工具 • **技术创新认可**：jibaoproxy 强调 Biff 的核心优势在于正确区分"民用时间"和"绝对时刻"两种类型，这是 GNU date 和多数标准库 API 的常见缺陷。指出其设计源自 TC39 的 Temporal 标准，这是 JS 首次在时间处理领域引领创新 • **实用价值肯定**：onceonceonce 表示该工具可替代约 40 行 bash 脚本来处理复杂的时间计算（如"节假日后的第二个周二"）；smartmic 提到会对比现有工具 dateutils 的易用性 • **开发难度共鸣**：sherr 回忆起用 Perl 处理日期时间的痛苦经历，充满边界情况和陷阱，对作者表示敬意 补充讨论：作者展示了用 Bttf 查询 Git 仓库文件最近修改时间的复杂用例，并询问 `git log -n1` 是否是获取单文件最近提交时间的最快方法。工具底层使用并行化提升性能，基于 Rust 的 Jiff 库构建。

文章摘要

评论摘要
主要讨论点：Meshtastic/MeshCore等去中心化网状网络技术的实用性、局限性和发展前景 不同观点： • **技术乐观派**：认为去中心化、太阳能供电的网状网络对应急通信和摆脱企业控制至关重要，即使断电也能工作，是互联网的重要替代方案（smlacy） • **实用怀疑派**：认为这些技术仍是"有趣的玩具"而非严肃解决方案，存在致命的可扩展性问题，类似早期wardriving社区，缺乏足够结构和大众吸引力难以普及（Groxx, rcarmo） • **网络稀疏问题**：多位用户反映节点密度不足，即使理论上有附近节点也难以稳定连接，标准天线范围仅500米，需要更多固定节点扩展网络（rta5, LelouBil） • **技术路线争议**：Meshtastic的"洪泛"消息机制被认为不可扩展，需要实现路由协议如BATMAN；而Reticulum被部分人视为更严肃的解决方案（lormayna, 原文作者） 补充讨论： • 硬件成本是阻碍（LoRa设备比Zigbee/WiFi贵） • 设备间直接通信优势明显，现代智能手机反而缺乏这种能力 • 瑞士等地区出现活跃使用案例 • 缺乏统一的国际应急网状网络标准 • 文本为主的"准互联网"设计可能天然避免垃圾信息和非法内容

Creusot helps you prove your Rust code is correct

文章摘要

Creusot 是一个用于 Rust 代码的演绎验证器，可验证代码不会出现 panic、溢出和断言失败等问题。它通过将 Rust 代码转换为 Why3 平台的中间验证语言 Coma 来工作，利用 Why3 的能力自动或半自动地验证程序正确性。项目提供了丰富的示例（如向量二分查找、排序等），支持通过 rustup 和 opam 安装，并有活跃的社区支持。CreuSAT 是使用 Creusot 构建的已验证 SAT 求解器项目。该工具已获得 1.7k stars，持续更新维护中。

评论摘要
主要讨论点：关于 Creusot（Rust 形式化验证工具）的初步反馈和疑问 不同观点： • **技术对比角度**（Trung0246）：关注 Creusot 与现有工具 Verus 的差异，希望了解技术定位和独特优势 • **实用性探索角度**（rendaw）：对形式化验证感兴趣但不知如何入门，关注实际应用场景（如 CRUD 应用）、适用问题类型、集成方式（增量集成 vs 从零设计）、标准库支持限制等具体实践问题 • **积极支持角度**（Loic 和 giltho）：对项目表示认可，Loic 特别提到喜欢项目命名（Le Creusot 是法国工业城市），giltho 称赞这是出色的工作 补充讨论：评论整体呈现早期项目发布的典型反应模式——技术人员关注工具对比和实用性，而支持者表达鼓励。rendaw 的问题最具代表性，反映了形式化验证工具推广的核心挑战：如何降低学习门槛并明确实际应用价值。目前缺少项目维护者的回应来解答这些关键问题。

What Apple and Google are doing to push notifications

作者: iamacyborg | 评分: 168 | 评论数: 28 | 发布时间: 2026-05-27 19:24
文章摘要

文章指出，推送通知正重演邮箱的路径：苹果和谷歌从“传输管道”变成“主动中介”。出于电量、体验和注意力管理，平台通过通知分级、频道、权限、专注模式和设备端模型，对推送进行过滤、降权、汇总甚至改写。结果是品牌对触达用户的控制持续减弱，推送越来越由平台算法而非发送方决定。

评论摘要
主要讨论点：手机推送通知应服务于用户而非营销；平台（Apple/Google）是否应限制通知，以及用户应拥有多大控制权。 不同观点： • 用户注意力优先派：多数人认为通知只应限于电话、消息、银行、健康、停车等真正紧急或事务性信息；促销、连击、推荐、配送更新不值得打扰。有人用长期勿扰、删App、关通知、过滤邮件等方式自保。 • 支持平台强管控派：认为Apple/Google压制营销推送是好事，推送应主要用于transactional notifications；广播和促销被削弱“完全没问题”。 • 强调更细粒度控制派：希望系统提供“关闭所有营销通知”“更好的摘要/digest”“按通知类型单独管理”。有人称Android在通知内直接细分控制优于iOS。 • 担忧平台中心化派：虽认可平台替用户挡垃圾，但担心APNS/FCM宕机、审查或过度控制；主张自托管或替代推送方案，如Unified Push、Home Assistant直连通知。 • 开发者/发送者视角受质疑：评论者指出作者把发送者与接收者利益对立化；也有人不关心开发者困境，认为营销团队滥用推送才是根源。 补充讨论： • 争议焦点在于：平台限制通知究竟是保护用户，还是过度掌控基础通信渠道。 • 有业内例子称推送延迟、抑制、合并自2011年前后就存在，说明平台干预并非新鲜事。
