Shopify replaced Redis with MySQL for inventory reservations–and it scaled

作者: adletbalzhanov | 评分: 235 | 评论数: 28 | 发布时间: 2026-08-08 22:32
文章摘要

Shopify在结账库存预留系统中用MySQL替换了Redis,以解决超卖问题。原Redis方案将预留和库存账本分离在两个系统中,无法保证原子性,可能导致超卖或少卖。新方案利用MySQL 8的SKIP LOCKED特性,采用"一行一个库存单位"而非"一行一个商品"的设计,将预留和账本放在同一数据库中,通过ACID事务保证一致性。系统为每个商品/地点组合维护最多1000行的可用行池,预留操作从池中消费行,补充流程从账本补充。该方案成功支撑了2025年黑色星期五每分钟510万美元的销售峰值。

评论摘要
主要讨论点：Shopify库存系统从Redis迁移到MySQL的技术方案设计 不同观点： • **方案支持者**：认为这是针对Shopify特定问题的合理解决方案，不应过度泛化批评（progx）；有人理解其设计逻辑，认为reserved_quantities本质上是临时数据（firasd）；部分读者欣赏真实案例分享（mrloopex） • **方案质疑者**：多位评论者提出技术改进建议 - 建议用购物车级别而非固定1000行池来管理库存（bijowo1676，认为此设计不符合高级工程师水平）；建议通过分片和状态更新替代删除行的方式（codedokode）；提出用事务+后台GC的更简单流程（isignal） • **根本性批评**：质疑为何如此规模的公司仍依赖MySQL而非自建专用系统（nurettin）；批评NoSQL运动是对SQL优化不足的逃避（pjmlp） • **非技术讨论**：质疑文章由AI生成，影响对Shopify工程师的信心（ramon156）；提及Shopify隐私问题（sureglymop）和CEO争议言论（pythonRon） 补充讨论：有评论者从业务角度指出，部分商家能容忍超卖并通过客户服务补救（arichard123），暗示技术复杂度可能存在过度设计的问题。

You might want to build your WebApp in Canvas instead of HTML

作者: wolframhempel | 评分: 18 | 评论数: 8 | 发布时间: 2026-08-03 11:11
文章摘要

本文探讨了为何Google Docs、Excel网页版、Miro等大型Web应用选择Canvas而非HTML构建界面。 **Canvas的优势**: - **性能更快** - 避免DOM解析和复杂渲染,减轻浏览器负担 - **精确控制** - 适合无限画布、缩放、平移等需要自主管理渲染的场景 - **跨设备一致性** - 输出结果完全可控 - **可移植性** - 易于适配其他平台 **Canvas的劣势**: 失去浏览器原生提供的输入处理、焦点管理、无障碍支持等功能。 **适用场景**: 大量绝对定位元素、不规则图形、需要缩放/平移/虚拟化渲染、或应用已有强大内部状态模型的情况下,Canvas是更好的选择。对于常规Web应用,HTML仍是首选。

评论摘要
主要讨论点：使用 Canvas 进行 Web 应用开发的技术路线争议 不同观点： • **反对派（可访问性角度）**：Canvas 严重破坏 Web 无障碍功能，屏幕阅读器无法解析 Canvas 内容，而 DOM 天然支持可访问性。Canvas 也会让浏览器开发工具失效，难以调试和检查。 • **反对派（历史教训角度）**：这类方案有失败先例，从 Java Applets、ActiveX、Flash、Silverlight 到 Flutter，用浏览器作为"黑盒渲染引擎"的尝试都未成功，问题根源在于难以兼容开发工具生态和浏览器扩展。 • **反对派（性能质疑角度）**：Canvas 并不保证性能优势，反而放弃了浏览器 C++ 引擎的原生优化。用 JavaScript 这种没有原生整数类型的语言很难超越浏览器内置渲染。微软等公司的 Web 应用已经很卡顿，证明这条路径有问题。 • **反对派（开放性理念角度）**：Canvas 损害 Web 的开放性本质，破坏了 View Source 等自由特性，这是企业利益侵蚀互联网开放性的表现。 • **支持派**：HTML/CSS 对浏览器引擎而言不够自然和高效，存在边界情况问题。考虑构建基于 Canvas 的替代方案可能更直接。 补充讨论：有极端用户表示会主动屏蔽 Canvas 内容，反映了部分开发者对这一趋势的强烈抵制。争议焦点集中在技术效率与 Web 核心价值（可访问性、开放性）之间的权衡。

A domain can now say it is for sale, in DNS

作者: shaunpud | 评分: 215 | 评论数: 29 | 发布时间: 2026-08-08 13:26
文章摘要

`_for-sale` 是 RFC 10023 定义的保留 DNS 节点名称,用于标识域名可供出售。它通过在 DNS 中发布 TXT 记录(如 `_for-sale.example.com`)来传递出售信号,而不影响网站正常运营。 记录格式为 `v=FORSALE1;` 加一个标签值对,可包含联系方式(furi)、价格(fval)或说明文本(ftxt)。多个信息需分别发布为独立记录。 该机制专为经纪人和自动化服务设计,与域名停放不同——网站继续运行,记录可随时添加删除。实施要点包括:强制版本标签、每记录一个标签值对、TTL不超过3600秒、使用DNSSEC签名、不再出售时立即移除。 这为域名交易提供了标准化的可发现渠道,避免了冷邮件和隐私保护带来的沟通障碍。

评论摘要
主要讨论点：围绕DNS域名销售标记新标准（RFC 10023）及域名投机问题的多角度讨论 不同观点： • **支持新标准派**：认为标准化的"域名待售"标记能提高透明度，方便买家找到愿意出售的域名（如temp0826分享成功获得心仪域名的经历） • **反对域名投机派**：Anoian直接表示应该禁止域名投机而非改善投机者体验；anigbrowl批评域名系统在30年间过度金融化，认为这对整体生态无益 • **提出替代方案派**：asdfman123建议采用Georgism税收模式——域名持有者自定价格但需按价格的2-5%缴纳年费，以激励投机者将域名卖给真正使用者 • **技术实现质疑派**：Tiberium和kmoser指出标准存在逻辑矛盾（既说不打算卖别加记录，又说记录不构成义务）；Bender担心允许在任意DNS层级添加标记会造成混淆 补充讨论：comrade1234的Sony案例引发关于商标仲裁的讨论——公开表示域名待售可能被视为不实际需要该域名的证据；1970-01-01和gguncth提出对标准被恶意利用的担忧（AI操纵交易、借机没收投机域名）
