WebMonkeys: parallel GPU programming in JavaScript (2016)

作者: surprisetalk | 评分: 107 | 评论数: 8 | 发布时间: 2025-05-04 17:00
文章摘要

WebMonkeys 是一个允许在 GPU 上进行大规模并行任务的 JavaScript 库，提供简单易用的 API，适用于浏览器和 Node.js 环境，兼容 ES5 且无需 WebGL 扩展。通过 `set` 和 `get` 方法在 GPU 和 JavaScript 之间传递数据，使用 `work` 方法指定并行任务数量和任务内容，任务语言基于 GLSL 1.0。该库简化了 GPU 编程的复杂性，隐藏了 WebGL 使用中的细节问题，如数据转换和精度损失。性能方面，建议减少 `set/get` 调用，尽量在 GPU 内部处理数据以提升速度。首次调用 `work` 时由于程序编译较慢，但后续调用速度较快。

Protein-slayer drugs could beat some of the cruellest cancers

作者: gnabgib | 评分: 6 | 评论数: 0 | 发布时间: 2025-05-07 19:41
文章摘要

这篇文章讨论了利用PROTACs（蛋白降解靶向嵌合体）这一新型药物策略来对抗儿童癌症，如神经母细胞瘤。传统药物通常通过阻断蛋白质功能起作用，而PROTACs则通过引导细胞的蛋白降解机制彻底清除致病蛋白质。由于许多致病蛋白质被认为是“不可药用的”，PROTACs为开发新疗法提供了可能。儿科肿瘤学家Yael Mossé正领导团队开发针对这些“不可药用”蛋白质的PROTACs，特别是针对神经母细胞瘤和其他儿童实体瘤。尽管该技术早期被质疑，但目前已有30多种PROTACs进入临床试验，针对乳腺癌、前列腺癌、白血病等。Mossé团队预计其首批PROTACs将在未来几年进入临床试验，这可能为治疗残酷的儿童癌症开辟新途径。

Migrating a JavaScript Project from Prettier and ESLint to BiomeJS

作者: unripe_syntax | 评分: 49 | 评论数: 16 | 发布时间: 2025-05-07 10:12
文章摘要

BiomeJS是一款新兴的JavaScript工具，旨在替代Prettier和ESLint，通过集成代码格式化和代码检查功能，简化工作流并提升性能。它源自于已终止的Rome项目，但已发展成独立的工具链，使用Rust编写，具备多线程能力，速度比Prettier快25倍，比ESLint快15倍。Biome的格式化功能与Prettier类似，但语言支持较少；其代码检查功能受ESLint启发，支持自定义规则和多语言。安装和使用简单，通过NPM分发，无需配置文件即可开始使用。Biome通过`format`和`lint`命令分别进行代码格式化和检查，并提供详细的错误和警告信息。是否从Prettier和ESLint迁移到Biome，取决于项目需求和语言支持情况。

评论摘要
主要讨论点：围绕Rome/Biome、Prettier和ESLint等前端开发工具的讨论，涉及工具的性能、实用性、生态支持以及迁移过程中的问题。 不同观点： • **对Rome/Biome的批评与反思**： - [jemmyw] 认为Rome在实际工具发布前就获得了大量关注和讨论，但最终没有实现承诺。这种现象类似于一些过度炒作但最终失败的公司。作者对Rome背后的驱动因素感到困惑，质疑其目的和吸引力。 - [egorfine] 提到前端开发工具的快速变化和对生态系统的不信任感，指出Rome的消亡是其中一个例子。作者引用了“红皇后的赛跑”来比喻前端开发需要不断奔跑才能保持在原地。 • **对Prettier和ESLint的肯定与依赖**： - [mrbluecoat] 表示虽然Biome声称能合并工具节省时间，但实际影响微乎其微，自己只需要每三年在VSCode中点击一次。 - [progx] 提到虽然Biome有性能优势，但在需要自定义时还是会回到Prettier，认为性能并不是真正的问题。 - [zoogeny] 经过分析后选择了Prettier和ESLint，认为Biome仍在追赶中，稳定性不足。 - [DGCA] 和团队成员都不喜欢Biome，迁移回Prettier和ESLint后发现了很多之前未报告的问题。 • **对Biome的有限支持与迁移挑战**： - [exiguus] 分享了迁移到Biome的经验，指出在TypeScript项目中效果不错，但在React和Angular项目中遇到性能问题。迁移整个公司代码规范到Biome几乎不可能，因为依赖许多ESLint插件。 - [sibeliius] 也遇到了类似问题，Biome在处理嵌入式语言（如GraphQL）时不够完善，最终回到了Prettier。 • **对工具生态和开发体验的讨论**： - [horsawlarway] 认为文章更像是营销材料，缺乏实际迁移过程中的成本、问题和收益分析。 - [difosfor] 提到Biome缺少许多ESLint插件支持，最终只能结合使用。 - [herpdyderp] 对Prettier的插件系统不满，认为其存在持续的bug且难以编写插件。 • **对工具未来发展的期待**： - [Alifatisk] 和[jmisavage] 对Biome的统一工具链理念表示兴趣，询问是否有实际使用经验和收益。 - [7bit] 对Prettier的HTML格式化问题表示不满，期待其他替代方案。 补充讨论： - 争议的焦点在于Rome/Biome是否能够真正替代Prettier和ESLint，特别是在大型项目中的实用性和稳定性。 - 讨论中多次提到工具的性能优势与实际需求之间的差距，许多开发者认为现有工具已经足够快，性能并不是主要问题。 - 另一个值得注意的点是前端开发工具的生态系统和插件支持，许多开发者在迁移过程中遇到了插件兼容性问题，这成为了Biome等新工具推广的主要障碍。

`docker2exe` 是一个可以将 Docker 镜像转换为可执行文件的工具。用户可以生成包含 Docker 镜像的可执行文件，并发送给其他人使用。主要功能包括： 1. **安装**：从发布页面下载二进制文件，并确保设备上安装了 Docker、GoLang 和 gzip。 2. **使用方法**：通过命令行创建可执行文件，例如 `docker2exe --name alpine --image alpine:3.9`，将生成不同系统下的可执行文件。 3. **执行**：运行生成的可执行文件时，工具会检查系统中是否存在指定镜像，若不存在则自动拉取。 4. **嵌入模式**：可将镜像打包进可执行文件中，运行时自动加载镜像。 该工具适用于小型镜像，生成的可执行文件体积较小（如小于10MB）。项目主要使用 Go 语言编写。
