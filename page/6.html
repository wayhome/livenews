文章指出 Safari 和 Firefox 会针对特定大站点内置“兼容性补丁”，按域名修改渲染、API、UA 等，以修复网站只适配 Chrome 或自身代码问题；Chrome 不需要这样做，反映其市场主导造成的 Web 兼容性循环。

评论摘要
主要讨论点：围绕浏览器兼容性、站点特定“quirk/fix”列表，以及网站对非主流环境的支持不足展开。 不同观点： • Chrome/WebKit是否也有类似兼容性列表：有人以为 Chrome 有类似机制，后来认为可能是与 WebKit 混淆，并举出 WebKit 中针对某站点的 quirk 代码作为例子。 • 非主流平台会被网站排斥：有用户提到长期使用 Linux 桌面时遇到网站无法工作，怀疑一些站点会根据 User-Agent 过滤“Linux”，这被认为很糟糕。 • 网站开发应主动覆盖多浏览器：有人认为 Web 服务团队至少应有人使用 Firefox、有人使用 Safari；其客户项目至少保证 Chrome 和 Firefox 可用，Safari 则取决于客户是否有 Mac，且未收到投诉。 • 不能假设 Safari 和 Firefox 的兼容修复相同：有人反驳称，如果 Safari 和 Firefox 拥有完全相同的网站列表和修复措施才可能同意，但现实并非如此。 • 用市场压力促使网站改进：有人主张直接放弃 Chrome，让网站运营者看到 Chrome 流量下降，从而重视其他浏览器。 补充讨论：争议焦点在于浏览器兼容问题应由浏览器通过站点特定修复解决，还是由网站开发者主动支持多浏览器/平台；同时也涉及用户是否应通过改变浏览器选择来影响网站行为。

文章摘要

文章称，Linux 游戏用户在 Steam 占比首次突破5%，受 Windows 10 停止支持和 Steam Deck 推动。Linux 游戏性能提升正从 Wine/Proton 扩展到内核层，NTSYNC 驱动为 Windows 游戏提供原生同步机制，减少开销，显著提升兼容性与速度。

评论摘要
主要讨论点：Linux 游戏生态在 Proton/Wine、NTSync、Steam Deck/Bazzite 等推动下快速成熟，但性能证据、反作弊、驱动与兼容边界仍是争议焦点。 不同观点： • 乐观派认为“Windows 才能玩游戏”的时代正在过去。多位用户表示旧游戏、新游戏和 Mod 环境在 Proton 下已能“点运行即可”，如 ESO 的 Windows 插件客户端、Returnal、Stellar Blade 都运行良好，睡眠恢复等体验也接近主机化。 • 经济与产业角度支持 Linux：云游戏厂商不愿为 Windows 授权付费，因此有动力用 Linux+Proton+Vulkan+AMD 机器串流游戏；Steam Deck 也降低了普通玩家接触 Linux 的门槛。 • 兼容性派强调 Wine/Proton 的价值：Linux 反而成为优秀的 WinAPI 平台，能跑 30 年前 Windows 游戏，甚至 16 位程序；相比之下，原生 Linux 老程序常因依赖库被废弃而无法编译或运行。 • 技术进展派提到 NTSync/Wine 锁机制改进，尤其实现 Win32 事件、信号量、互斥量和 WaitForMultipleObjects，可改善多线程同步性能；也有人预测未来可能发展成类似“Linux Subsystem for Windows”的低开销 NT 内核兼容层。 • 谨慎/怀疑派要求更多数据：不仅要 FPS，还要帧时间、延迟等端到端对比；此前一些测试显示 Linux 仍落后 Windows 5%-30%，且 Nvidia 支持仍有顾虑。 • 最大争议集中在反作弊：BattlEye、Vanguard、Battlefield、Warzone、League 等竞技游戏若不支持 Linux，将阻碍主流玩家迁移，也可能决定市场临界点是否到来。 • 另有用户从历史类比谈兼容层价值：早年 CTOS 通过实现少量 trap 就能跑 DOS 命令行程序，说明接口兼容可带来巨大生态收益。 补充讨论：有人讨论 NTSync 为何不用 epoll/eventfd 形式实现；也有人从情感上表示，转向免费开源后反而更愿意感谢和回馈开源开发者。

主要讨论点：围绕书摘/文章对“货币”的批判展开，讨论货币是否只是有缺陷的抽象、经济学如何解释货币、以及现代货币制度是否损害储蓄与信任。 不同观点： • 文章形式批评：有人认为原文铺垫过多、隐喻冗余，应直接表达观点；也有人只是抱怨网页弹窗影响阅读。 • 货币是必要抽象：Bratmon认为作者把“货币”作为对生产劳动和资产的抽象，发现其会“泄漏”后就认为应废除，这是误解。类比软件工程，抽象虽不完美但对复杂经济至关重要，不能因失效场景否定其价值。 • 货币崇拜批评：justonceokay用“coin sickness”形容重视金钱多于实际物质财富的人，例如只认服装品牌却不懂面料和做工，呼应对货币符号化的批判。 • 经济学批判：imtringued认为主流经济学对“货币中性”与“货币降低交易成本”存在概念偷换。若货币提高劳动生产率，就类似资本品，可产生收益；高利贷因此可能榨取分工带来的巨大剩余。中央银行通过设定利率、提供货币，压低既有持币者的收益。 • 硬通货/反通胀立场：mikewarot主张“真正的钱”应是金属等稳定、可储蓄的实物媒介，批评现代货币制度鼓励投资股市、侵蚀储蓄，2%通胀目标和缩水式涨价削弱社会信任。 • 讽刺性回应：underlipton以调侃方式总结为“以物易物回来了、格林斯潘是魔鬼、政府在通胀上撒谎”，并指出原文讨论的时代背景与沃尔克冲击、日本失落十年等宏观历史相关。 补充讨论：有人推荐两本关于货币史和现代公司的书，作为理解货币与商业制度的延伸阅读。

文章介绍 Numa v0.14 对 ODoH（Oblivious DNS over HTTPS）的支持：通过客户端、匿名中继和目标解析器分离“用户 IP”和“DNS 查询内容”，避免单一 DNS 服务商同时看到二者。Numa 使用 HPKE/odoh-rs 加密，提供单二进制部署、无需账户，并默认搭配 Numa 公共中继与 Cloudflare 目标。作者说明了实现中的 SSRF 防护、运营方隔离检查及部署方式，也强调 ODoH 并非万能：目标仍能看到查询，递归出口仍可能泄露，小流量中继易被流量分析，公钥分发仍依赖 HTTPS/WebPKI。

评论摘要
主要讨论点：围绕 ODoH/DoH/DoHoT 等隐私 DNS 方案的实际匿名性、信任边界、部署运维和使用场景展开。 不同观点： • 自建派：Bender 认为关键问题是“谁控制代理、DoH 服务器和证书”，信任链会无限下探；因此更倾向自建 Unbound DoH，自己决定 DNS 在哪里回落到明文 UDP 53，并通过缓存、预热、迁移 cache 来减少可观察 DNS 行为。 • 质疑匿名性派：cedws 指出 ECH 普及率低，即使 ODoH 隐藏 DNS 查询，访问的服务器名称仍可能通过其他层暴露，质疑其卖点。gigatexal 也追问“真正匿名 DNS”是否可能。 • 支持公共基础设施派：binyang_qiu 肯定有人实际运行公共 ODoH，而非停留在理论隐私讨论，并关注公共 relay 最大运维痛点。 • 替代方案派：DyslexicAtheist 推荐用 dnscrypt-proxy 实现 DoHoT（DNS over HTTPS over Tor），认为缓存可缓解速度问题，但提醒要先理解威胁模型。 • 工具集成需求派：dontfeedthemac 关注零配置、Mac/Docker、作为服务运行、与 Tailscale 集成、替代 tsdproxy、通过 Docker socket 做服务发现等实用功能。 • 实现细节说明：rdme 介绍 relay 部署在 VPS systemd 上，用 Caddy TLS，做 SSRF 加固、禁止 IP literal、检查 relay 与 target 是否同运营者，并使用 Cloudflare odoh-rs/numa。 • 其他疑问：piuvas 询问架构图制作方式；skinfaxi 质疑 private TLD 的最终目标，担心是否会演变成加密货币项目。 补充讨论：争议焦点在于 ODoH 能否在现实网络中带来有效匿名性，以及应信任公共中继/解析器，还是自建并通过缓存等方式降低暴露面。
