文章摘要

临床决策中常将连续风险数据简化为基于整数阈值的离散等级，这种做法可能扭曲风险评估并导致次优治疗结果。研究者开发了可解释的机器学习模型，通过模拟和真实数据研究发现：整数阈值会导致死亡率风险出现不连续性和反因果悖论，例如肌酐值3.5mg/dL的阈值可能造成治疗不足或过度。尽管医学进步，这些异常现象仍然存在，表明需要采用更动态、细致化的风险评估方法。研究建议临床实践中（尤其是重症监护）应持续优化阈值设定，使其更符合风险的连续本质，从而改善患者预后。

评论摘要
主要讨论点：[药物自我管理剂量中的合规性与治疗安全性] 不同观点： • **支持固定剂量分组的观点** - 以年龄和/或体重分组简化家长操作，如对乙酰氨基酚（Paracetamol）在儿童中的使用 - 固定剂量分组虽然可能导致轻体重儿童相对过量而重体重儿童相对不足，但能有效防止危险过量（如肝毒性） - 固定剂量和明确阈值有助于降低致命风险，即使可能增加非致命风险 • **支持个体化剂量计算的观点** - 提出按体重（mg/kg）计算剂量（如抗生素的使用）更精确 - 但存在计算错误的风险，部分家长可能因错误的风险认知故意过量给药 - 需要设计指数风险曲线，标明“安全区”和“危险区”以及关键阈值，并针对年龄/体重定制 • **关于治疗阈值设置的争议** - 有评论指出二元治疗（如是否给予治疗）可能导致“悖论风险”，即高风险患者治疗后风险低于未治疗的低风险患者 - 认为这是反对二元治疗的有力论据，或建议将治疗阈值设得足够低，使得治疗后的改善效果最小化 补充讨论： - 有评论提到一篇相关论文，指出其可能因未被顶级期刊接受而发表在较小众的期刊，并质疑其传播范围 - 讨论还扩展到其他依赖指标驱动的领域，显示该问题的广泛适用性

Django 6.0引入了一个内置后台任务框架django.tasks，但暂不会取代Celery等现有方案。该框架仅提供任务创建和队列API，不包含执行机制，仍需外部服务处理任务执行。文章通过一个使用ntfy.sh发送手机通知的示例项目，演示了如何定义任务（使用@task装饰器）、排队任务（通过enqueue方法）以及获取任务结果。项目包含了一个基于数据库的后端实现和工作进程，并展示了使用HTMX轮询任务状态的前端实现。框架目前只提供立即执行和不执行两种后端，功能较为基础，但为统一任务队列API奠定了基础。

主要讨论点：[Django 背景任务队列解决方案的比较与选择] 不同观点： • **支持使用 Procrastinate** - JakaJancar 推荐 Procrastinate，认为其架构清晰、测试完善、代码量少（仅为 Celery 的十分之一），并支持同步/异步、重试/取消等功能。 - elliot07 补充批评 Celery 在规模扩展时难以维护，并询问迁移经验。 • **倾向云服务或其他轻量方案** - delbronski 认为 Celery/Procrastinate/Chancy 均不够理想，更倾向于使用 GCP Cloud Tasks，因其简单易用，适合中小型项目。 - vforgione 推荐 django-tasks，称其数据库后端和简单接口适合不需要额外基础设施的场景。 • **对事件驱动模型的偏好** - adamcharnock 指出任务队列在复杂业务场景中可能成为错误抽象，建议改用事件流（如 Lightbus），以解耦任务触发与后续逻辑。 - 争议焦点：任务队列 vs. 事件流的选择取决于业务模型复杂度。 • **对新功能的期待与质疑** - frankhsu 关注重试/ACK 行为、可观测性（仪表盘、指标）、类型提示和测试后端切换的实际体验。 - Grollicus 提出进度报告 API 的缺失问题，认为这是长任务管理的明显需求。 - matsemann 强调类型支持的重要性，批评许多 Python 装饰器的弱类型化导致运行时错误。 补充讨论： - **生态对比**：leonkenneth 批评 Django 生态相比 Rails 缺乏“开箱即用”的生产级工具，但认可新改进的价值。 - **迟到的改进**：fud101 直言 Django 在此功能上落后十年，导致用户长期依赖临时解决方案。 - **测试与兼容性**：ethagnawl 肯定透明后端切换的潜力，但质疑是否能解决 Celery 的早期 ACK/重试等问题。
