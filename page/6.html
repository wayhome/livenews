Define policy forbidding use of AI code generators

作者: todsacerdoti | 评分: 506 | 评论数: 37 | 发布时间: 2025-06-25 23:26
文章摘要

QEMU项目当前政策拒绝接受包含或衍生自AI生成内容（如ChatGPT、Copilot、Llama等工具）的贡献。这是因为AI生成内容的版权和许可状态不明确，存在法律风险。QEMU贡献者需根据开发者原产地证书（DCO）规则，确保对提交内容的版权和许可有完全理解。由于AI工具的输出无法满足DCO要求，项目不允许在提交的补丁中使用这些工具生成的内容。不过，AI工具在研究API、算法、静态分析或调试等非提交相关用途上仍可使用。此政策可能随AI工具和法律情况成熟而调整，但目前需逐案申请例外并证明输出内容的版权和许可状态。

评论摘要
主要讨论点：AI生成代码对开源和自由软件的影响，尤其是在版权和法律问题、代码质量审查、项目管理等方面的挑战。 不同观点： • **benlivengood**：认为开源和自由软件特别容易受到AI生成代码的版权问题影响。如果AI生成的代码被判定为侵权或公共领域，项目可能会陷入法律诉讼，且开源项目通常没有足够资金应对。此外，AI生成的代码经过人类修改后是否仍属于侵权衍生作品存在不确定性。如果AI生成代码被视为公共领域，则开源许可的约束力会削弱。 • **JonChesterfield**：对AI生成代码持批评态度，认为不应接受开发者自己都不理解的代码，也不愿意合并这种代码。这种立场比LLVM项目的政策更加严格。 • **acedTrex**：指出AI生成代码打破了传统上通过隐藏能力标记判断贡献质量的方式。AI生成的代码虽然看起来专业，但缺乏实际经验支撑，可能对经验丰富的开发者造成困扰。未来，可能需要更多依赖社交证明等方式来评估贡献者。 • **ants_everywhere**：认为RedHat等大公司关注AI生成代码的风险，主要是因为AI可能输出属于其他项目的代码，尤其是涉及闭源和可能引发诉讼的代码。 • **Havoc**：质疑一些项目反对AI生成代码的动机，认为可能不仅仅是因为法律问题，而是因为对低质量AI提交感到厌烦。 • **saurik**：指出QEMU项目由于其仿真器性质，已经面临较大的法律 scrutiny，因此需要比其他项目更加保守地对待AI生成代码，以避免增加法律风险。 • **hughw**：希望能够在使用LLM作为IDE的自动补全工具和生成实质性代码之间做出区分。虽然这是一个灰色地带，但希望使用AI工具节省劳动力的同时，不涉及版权问题。 • **bgwalter**：认为反对AI生成代码的政策可能只是为了在使用AI生成代码时有合理的否认权，实际上这些政策可能根本无法执行。 • **Aeolun**：认为执行反对AI生成代码的政策几乎不可能，因为现代编辑器普遍提供AI辅助代码提示，且无法区分这些提示和手动输入的代码。 • **daeken**：分享了自己使用Claude Code工具调试代码的经验，发现AI工具在复杂项目中目前还不能提供实际价值，虽然未来可能有潜力。 • **flerchin**：认为使用AI生成代码的贡献者需要对其代码负责，并深入理解代码，以应对审查中的质疑。 • **wyldfire**：认为除了拒绝AI生成代码外，还可以指定某些部分允许使用AI生成内容，并设立防护措施。 • **tqwhite**：认为担心AI生成代码是合理的，但政策不应禁止使用AI，而是确保不留下使用痕迹。同时，AI生成的程序未来可能会像从前一样具有版权。 • **zoobab**：暗示RedHat等大公司现在控制了QEMU项目，可能影响项目的独立性。 • **randomNumber7**：认为AI生成代码仍然比手动编写快，开发者可以阅读和检查AI生成的代码以确保其符合需求。 补充讨论： • 争议焦点在于AI生成代码的版权归属和质量问题，以及如何在开源项目中有效管理AI生成代码的使用。 • 不同项目对AI生成代码的态度和政策有所不同，部分项目采取严格禁止的立场，而其他项目可能允许在特定条件下使用。 • 实际操作中，如何区分和监管AI生成代码的使用仍然是一个复杂且未完全解决的问题。

Learnings from building AI agents

作者: pomarie | 评分: 128 | 评论数: 20 | 发布时间: 2025-06-26 12:45
文章摘要

本文介绍了构建AI代码审查工具的过程和经验，特别是如何减少噪音问题。最初的AI代理产生了过多的低价值评论和误报，导致开发者忽略其反馈。通过三次重大架构修订和大量离线测试，团队成功将误报减少了51%，且不影响召回率。关键改进包括：1）要求AI在反馈前明确陈述理由，以便追踪决策过程并减少任意性结论；2）简化工具集，专注于核心工具以减少错误；3）采用专门的微代理代替通用规则，每个代理处理特定问题（如安全、重复代码等）。这些改进在实际项目中显著提升了工具的精确度和开发者信任度。

评论摘要
主要讨论点：LLM（大型语言模型）在代码审查中的应用及其有效性和局限性 不同观点： • Oras认为，LLM总是会尝试返回一个结果，即使使用"micro-agents"作为营销术语，LLM的反馈在某些情况下是合理的，比如在代码审查中对注释掉的代码提出疑问。 • elzbardico指出，LLM提供的置信度值（confidence value）并不准确，可能具有误导性。 • singron认为，文章中给出的例子过于简略，没有提供足够的背景信息，尤其是对于注释掉代码的情境，可能存在更复杂的原因，值得进一步探讨。 • nico分享了自己的经验，提到使用大型系统提示（system prompts）来处理边缘情况，并提出是否存在使巨型提示有效工作的技巧。 • jstummbillig对多代理（multi-agent）系统持怀疑态度，认为AI应在提供足够描述和上下文的情况下自行解决问题，而不需要人为拆分任务。 • h1fra指出，使用多个工具进行代码审查时，PR描述通常无用，且大部分评论是错误或无关的，认为这种方法可能不值得。 补充讨论： • mattas提到，非确定性软件（如AI代理）的开发更多依赖于试错和结果评估，与确定性软件开发不同。 • kurtis_reed引用了一篇关于如何减少LLM无效评论的博客文章，认为文章为限制问题范围提供了实用建议，但缺乏数据支持。 • nzach同意限制问题范围可以提高LLM的实用性，并提到虽然经验上简单问题比复杂问题反馈更好，但缺乏数据支持。 • shenberg对"51% fewer false positives"和"Median comments per pull request cut by half"的数据表示怀疑，认为需要更多关于真阳性率的信息。 • jangletown质疑如何测量"51% fewer false positives"的数据，询问是否使用了内部或基准数据集。 • b0a04gl分享了实验结果，显示即使输入相同，LLM的推理路径和解释也可能有所不同，提示需要更严谨的提示设计。 • vinnymac基于自身经验认为，经过几个月的测试，LLM的表现有所改善，变得更安静且更有用。 • N_Lens认为文章内容模糊，缺乏细节，更像是一种营销宣传。 • EnPissant质疑文章的专业性，认为更像是营销博客，并指出某些模型默认就会进行推理解释，即使没有明确输出。 争议焦点： • LLM在代码审查中的实际效果和可靠性，尤其是置信度值的准确性和注释掉代码的处理方式。 • 多代理系统的实用性以及是否需要人为拆分任务。 • 巨型系统提示的有效性及其应用技巧。 • 数据支持的缺乏，尤其是在减少误报和评论数量方面的具体测量方法和结果。

文章摘要

Howdy 是一个为 Linux 提供类似 Windows Hello™ 面部认证功能的软件。它利用内置的红外发射器和摄像头进行面部识别，通过 PAM 系统实现登录、锁屏、sudo 等场景下的密码替代。Howdy 支持 Debian/Ubuntu、Arch Linux、Fedora 和 openSUSE 等发行版，安装方式各有不同，部分需要额外配置。它依赖于 Python 3.6+、meson、ninja 等工具构建，并可通过命令行管理面部模型。安装后需运行 `sudo howdy add` 进行面部录入。如遇问题，可通过查看 Wiki 或 GitHub 上的类似问题进行排查。用户还可以通过贡献代码或提交功能请求参与项目。

评论摘要
主要讨论点：开源面部识别认证项目的质量和功能与商业版本的比较，以及技术实现和应用场景的讨论 不同观点： • **[bsimpson]** 认为开源项目的面部识别认证可能会有更多的误报/漏报，因为商业版本需要支持所有人使用，经过了大量测试，而开源项目可能在广泛适用性上有所欠缺。 • **[aitchnyu]** 关注用户体验问题，希望在系统处理面部识别时有提示，特别是当识别失败时，可以有一个重试按钮。同时，也对红外照片是否会欺骗模型提出了疑问，并对红外摄像头的实验表示兴趣。 • **[joelthelion]** 表示希望能有更好的指纹识别支持，暗示面部识别并不是其首选的认证方式。 • **[charcircuit]** 指出该开源项目与Windows Hello的不同之处，包括它仅通过2D图像提取特征，缺乏深度重建，容易被纸张等简单手段欺骗。此外，还提到该项目在功能上不如Windows的面部识别广泛，仅用于用户认证，且保存面部特征点文件时使用明文，存在安全问题。 • **[mouse_]** 表达了对预桌面认证功能的期待，认为这是一个非常吸引人的特性，希望能看到其实现。 • **[seany]** 关注开源面部识别模型在NIST/iBeta排名中达到较好性能所需的条件，暗示开源项目在性能上与商业模型存在差距。 • **[deafpolygon]** 对项目依赖Python2表示不解，可能在考虑技术更新和维护的必要性。 • **[fsateler]** 注意到项目虽然活跃，但最后一个版本发布于2020年，质疑为何没有新的版本发布。 补充讨论： • 项目在技术实现上的局限性（如2D图像 vs 深度重建）以及安全性问题（明文保存特征点）是主要的技术争议点。 • 用户体验和多因素认证方式（如指纹识别与面部识别的对比）也是讨论的重要内容。 • 开源项目与商业版本在性能、可靠性及功能广泛性上的对比是潜在的争议焦点。

A new PNG spec

作者: bluedel | 评分: 616 | 评论数: 50 | 发布时间: 2025-06-24 13:01
文章摘要
