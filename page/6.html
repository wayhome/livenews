Deno 2.4

作者: hackandthink | 评分: 112 | 评论数: 9 | 发布时间: 2025-07-07 08:44
文章摘要

Deno 2.4 恢复了 `deno bundle` 命令，用于创建单文件 JavaScript 捆绑包，支持服务器和浏览器平台，兼容 npm 和 JSR 依赖，并通过 esbuild 实现自动树摇和压缩。此外，新增 `--unstable-raw-imports` 标志，允许直接导入文本和二进制文件，简化非 JavaScript 文件的处理。同时，捆绑功能也支持与 `deno compile` 结合使用，可将资源嵌入最终编译的二进制文件中。其他更新包括内置 OpenTelemetry 稳定化、使用 `--preload` 修改环境、更简单的依赖管理等。`deno bundle` 目前为实验性功能，未来计划增加运行时 API 和插件支持。

Corrected UTF-8 (2022)

作者: RGBCube | 评分: 54 | 评论数: 16 | 发布时间: 2025-07-03 15:29
文章摘要

文章讨论了UTF-8编码的一些设计错误，并提出了修正方案，称为"Corrected UTF-8"。这些错误部分源于设计者的失误以及ISO和Unicode内部的政治因素。文章提出了三项主要修改：1. 消除过长编码，确保每个编码都是唯一表示；2. 不编码C1控制字符和Unicode替代字符，避免潜在误解和不必要字符；3. 移除编码上限，恢复最初的UTF-8设计，允许编码高达U+8421109F的字符，并保留未来扩展的可能性。这些修改旨在防止安全漏洞，并确保编码系统的长期适用性。

评论摘要
主要讨论点：对现有文本编码标准的改进建议及其争议 不同观点： • Dwedit认为，提出与现有标准不兼容的新编码标准不会获得广泛接受。他以WTF-8为例，指出其解决了特定问题（即表示无效的16位字符），而新提案缺乏实际应用场景。 • maxdamantus提出了WTF-8b方案，利用非法超长编码来处理无效Unicode字符，并希望在保留无效字符的前提下进行扩展。他提供了具体技术细节和个人实践经验。 • josephg主张在新编码标准中强制使用Unicode规范化形式，认为这是解决复杂性和模糊性的必要步骤。 • philipwhiuk质疑剔除某些字符的必要性，并担心新方案会导致现有字符无法表示。 • chowells反对禁止特定字符编码的提议，认为这会增加使用新编码的难度，尤其是在处理文本时。 • eviks对剔除如水平制表符等C0控制字符表示不解，并质疑是否有现代设计系统敢于做出如此激进的改变。 • omoikane认为有意使某些代码点无法编码是不安全的，主张所有代码点都应可编码，即使它们不应被使用。 • duskwuff全面批评了多项提议，包括打破ASCII兼容性、处理UTF-16代理对问题、质疑扩展代码点空间的必要性，以及反对重新引入BOM。 • lifthrasiir提到UCSX作为扩展代码点空间的解决方案，认为其由Unicode贡献者设计，具有权威性。 • oleganza反对使用魔术前缀（如BOM），认为这会破坏兼容性，影响标准的接受度。 • _kst_对“UTF-16已过时”的说法表示怀疑，指出UTF-16仍在广泛使用。 • moonshadow565建议设计一种无需大表查询字符类别的编码方案。 • timbray提供了一个相关IETF草案链接，指出该草案列出了不应使用的字符，并认为这是在当前UTF-8限制下的实际解决方案。 • kmeisthax详细讨论了扩展超过U+10FFFF代码点的技术挑战，包括对UTF-16系统的兼容性和处理代理对的复杂性，提出了一种复杂的扩展方案，但同时承认需求很低。 补充讨论： • 争议焦点包括是否应强制使用Unicode规范化形式、是否应剔除某些控制字符、新编码方案的ASCII兼容性及其在实际应用中的可行性。 • 多个评论者提到UTF-16的广泛使用和兼容性问题，认为任何新标准都需要考虑现有系统的过渡和兼容。 • 有评论者提到具体技术如WTF-8、WTF-8b等的应用场景和局限性，以及对编码复杂性的担忧。 • 对未来代码点空间的需求预测和现有编码系统的寿命也是讨论的重要内容。
