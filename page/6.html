Designing an FPGA Calculator from Scratch

文章摘要

这是一个从零开始构建计算器的硬件项目系列文章。作者在2021年德州停电期间受HP-41CV启发，决定自制计算器。项目涵盖：用基础运算实现复杂数学函数的数值方法、搭建跨平台测试框架（ModelSim/Verilator/Qt/WebAssembly）、设计PCB硬件（键盘矩阵和OLED显示屏）、为BCD运算定制CPU指令集、编写微码实现计算器功能、从开发板过渡到带3D打印外壳的成品设备，最终在2025年重写算法以实现完整的16位BCD精度、三角函数、内存寄存器和随机数生成器。整个过程展示了硬件和软件开发的完整流程。

评论摘要
主要讨论点：关于一个从零开始构建BCD科学计算器的FPGA项目 不同观点： • **积极评价派（defrost）**：认为这是一个优秀的项目演示，从逻辑门到数学原语的完整实现路径，适合想了解底层硬件设计的人学习。强调项目的完整性——涵盖架构设计、数值算法（CORDIC三角函数、对数）、自定义CPU设计（12位指令集）、汇编器开发、微码编程，直到物理硬件实现 • **技术特色关注**：项目采用BCD（二进制编码十进制）格式，与HP 1970年代计算器相同，每个十进制数字用4位表示，确保完美的十进制精度，避免浮点转换误差。设计了专门的nibble寻址内存和针对16位BCD尾数的寻址模式 • **潜在学习者（foota）**：表达了对FPGA应用的兴趣，但目前缺少实际应用场景来驱动学习 补充讨论：评论展现了FPGA项目的教育价值与实际应用门槛之间的对比——一方认为这是绝佳的学习材料，另一方则在寻找实际应用动机。项目的十章结构提供了从理论到实践的完整学习路径。

My domain got abused on GitHub Pages

作者: rmeertens | 评分: 46 | 评论数: 9 | 发布时间: 2026-05-19 07:28
文章摘要

作者在非洲旅行时收到Google Search Console通知，发现有人在其域名下创建了未授权的子域名kafka.immersivepoints.com。问题源于GitHub Pages的机制：作者使用通配符DNS将所有子域名转发到GitHub服务器，而GitHub允许任何用户通过在仓库中添加CNAME文件来声明域名所有权。攻击者利用这一漏洞，在私有仓库中托管了赌博诈骗网站。作者认为GitHub应加强域名验证机制，建议要求用户验证域名所有权或添加特定DNS记录。事后发现GitHub确实提供域名验证功能，但入口不够明显，容易被忽略。

评论摘要
主要讨论点：GitHub Pages 自定义域名配置不当导致的安全风险，特别是通配符域名和域名验证机制的问题。 不同观点： • **GitHub 应改进验证机制**（Gigachad）：GitHub 应要求用户通过添加 TXT 记录来验证域名所有权，而不是仅检查域名是否指向 GitHub 就允许任何仓库使用。 • **用户配置错误是主因**（est, halapro, pigbearpig）：问题根源在于用户将通配符域名指向 GitHub，这本身就很危险。将 NS 转发到不属于自己的平台，出现问题是"预期行为"，用户应该对 DNS 配置后果有更深入的理解。 • **问题普遍存在且由来已久**（ardeaver, tamimio, usagisushi）：类似问题不仅限于 GitHub Pages，在 DigitalOcean 等其他 DNS 服务中也存在。这个 CNAME 漏洞至少从 2015 年就已为人所知，存在约 10 年。即使域名处于待验证状态，GitHub Pages 负载均衡器仍会根据 Host 头路由请求。 • **技术限制因素**（CodesInChaos）：CNAME 记录不能用于顶级域名（TLD+1），只能用于子域名，因此必须使用更容易出错的配置方式。 补充讨论：有人提到可以利用 nip.io/sslip.io 等通配符 DNS 服务作为别名域名，展示了该漏洞的技术细节。

Earth's Radio Bubble: Every signal we've ever sent into space

作者: jonbaer | 评分: 63 | 评论数: 14 | 发布时间: 2026-05-18 08:36
文章摘要

自20世纪初以来,人类的无线电信号以光速向外扩散,形成了一个直径约240光年的"无线电气泡"。这个气泡包含了我们发送的所有音乐、电视广播、雷达信号和太空信息。然而,240光年仅占银河系(直径10万光年)的0.000002%。文章追溯了关键里程碑:1936年柏林奥运会、1969年登月直播、1974年阿雷西博信息等,这些信号仍在传播中。目前已有数千个恒星系统位于这个气泡内,包括距离最近的比邻星。在宇宙尺度上,人类只是刚刚宣告了自己的存在。

评论摘要
主要讨论点：地球无线电信号在太空中的可探测性及其作为文明标志的局限性 不同观点： • **技术悲观派**：即使是强大的Arecibo望远镜，在土星距离外也无法探测到地球的FM广播；Alpha Centauri的类地文明信号我们也接收不到（JPL专家证实） • **信号衰减论**：现代通信技术趋向光纤、低功率、扩频技术，信号越来越像噪声，人类的"无线电泡泡"可能只是薄薄一层外壳，探测窗口期很窄 • **替代信号派**：大气中的氧气是比无线电更持久、更有意义的文明标志，存在时间远超人类文明 • **技术细节讨论**：多普勒效应会显著改变波长和频率，地球和太阳系的运动会影响信号接收；有人提出核爆炸可能是最强的非定向传输 补充讨论： 电影《Contact》（1997）准确描绘了这一现象，1936年柏林奥运会首次大规模电视广播成为情节关键点。有趣的是，美国WBCQ电台声称用调制激光向太空广播节目（50美元/小时）。也有人担忧：我们真的想被发现吗？如果外星文明不友好怎么办？另有观点认为，宇宙中至少某些方向没有类似信号，可能意味着发出信号的文明最终都会消亡。

Understanding Singleflight in Go

文章摘要

这篇文章介绍了Go语言中的singleflight包，用于消除冗余工作。当多个goroutine同时请求相同资源时，singleflight确保只执行一次操作，并将结果共享给所有调用者。它通过Group类型实现：首次请求时执行函数，后续并发请求等待，完成后共享结果。主要优势包括提高效率、减少服务负载、优化资源使用。文章提供了基础示例和天气服务缓存的高级应用场景，展示如何在实际项目中使用singleflight防止重复的API调用或数据库查询。

评论摘要
主要讨论点：Go语言中singleflight库的实现、使用场景和不同变体的选择 不同观点： • **历史溯源派（bradfitz）**：详细追溯singleflight从2013年为dl.google.com开发，到在Camlistore/Perkeep、groupcache、Go标准库internal包，再到Tailscale泛型版本的演变历程，强调该模式的广泛应用 • **实用主义派（jzelinskie）**：批评文章标题应改为"使用singleflight"而非"理解"，因为内容未深入讲解实现细节和权衡（如是否为首次执行创建goroutine）。认可其对p95延迟的巨大改善，但建议根据具体场景定制实现 • **使用场景质疑派（potato-peeler）**：对"不适合缓存或结果频繁变化"的使用场景存疑，指出即使是天气服务查询的例子也使用了缓存，认为普通并发请求前也可加缓存层 • **实现选择派（theowaway213456）**：推荐janos/singleflight实现优于标准库，因为它支持context • **功能对比派（mholt）**：质疑singleflight与sync.Once的区别和使用场景差异 补充讨论：争议焦点在于singleflight的实际应用价值——是否真的比缓存+并发控制更优，以及不同实现版本的技术权衡。

这是一门关于AI编码代理工程的课程，教授如何通过系统化的环境设计、状态管理、验证和控制系统，让AI编码工具（如Codex和Claude Code）变得可靠。课程内容包括理论讲座、实践项目和资源库。核心机制是建立一个闭环工作系统来约束AI行为，而非让模型"更聪明"。学习内容涵盖：用明确规则约束代理行为、跨会话维护上下文、防止代理过早宣告成功、通过测试验证工作、以及使运行时可观测和可调试。课程提供可复用的模板资源。

主要讨论点：关于AI代理"harness"（工具框架）的价值和内容质量的争议 不同观点： • **支持派（vibe42, kestiny）**：认为harness有实际价值。vibe42通过重复验证提示词获得了良好效果，多次运行后模型能收敛到更准确的结果。kestiny强调好的harness能约束行为边界，让审查从"阅读整个diff"转变为"验证是否在任务范围内"，提升可控性和可审查性。 • **质疑派（zaep）**：承认概念合理，但对实际效果存疑。认为设置成本和token成本是明显缺点，不太相信其价值。 • **批评派（mindwok, relativeadv, AIorNot）**：强烈批评内容为"AI slop"（AI垃圾内容），认为主要目的是自我推广而非教育，建议直接研究Claude代码库本身。 • **误解派（zaep, anonymousiam, myself248）**：最初以为讨论的是卫星/车辆线束工程（Wire Harness Engineering），对AI话题感到失望。 补充讨论：argee注意到网站使用了Vitpress构建工具，认为该技术本身值得关注。整体争议焦点在于内容的原创性、实用性和动机的真实性。
