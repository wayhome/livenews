.localhost Domains

作者: todsacerdoti | 评分: 51 | 评论数: 22 | 发布时间: 2025-04-10 14:19
文章摘要

作者分享了一种为本地运行的网页应用配置自定义域名的方法，使其可以通过如"appname.localhost"访问，而无需使用"localhost:4333"。具体做法是：通过设置每个应用为一个launchd守护进程监听唯一端口，并在`/etc/hosts`中重定向这些域名到127.0.0.1。然后使用Caddy服务器将127.0.0.1的流量转发到正确的端口。例如，一个运行在端口5050的应用，会在`/etc/hosts`中有一条记录，并在Caddyfile中配置反向代理和TLS等。虽然目前是手动配置，但作者希望未来能通过一个命令简化这一过程，并且提到使用dnsmasq可以进一步优化这一方案。

评论摘要
主要讨论点：本地开发环境中域名设置和解析的方法 不同观点： • **使用 `.internal` 域名**：hardaker 提到 `.internal` 域名最近被批准用于本地环境，并提供了维基百科链接作为参考。 • **使用 `.localhost` 域名**：jFriedensreich 指出 Chrome 和 Firefox 默认将 `.localhost` 域名解析到本地主机，无需手动添加到 hosts 文件，并描述了使用 Docker 代理的自动化设置。 • **使用系统默认解析**：lima 提到在 Linux 机器上使用 systemd-resolved，开箱即用，无需额外配置，并给出了命令示例。 • **使用自定义子域名**：thorvaldsson 使用自定义子域名 `local.`，并通过 Let's Encrypt 和 Traefik 生成证书，成功运行了一段时间。 • **Safari 浏览器问题**：chuckwnelson 指出 Safari 不识别 `.localhost` TLD，需要在 URL 后添加斜杠来解决。 • **使用单独注册的域名**：mrweasel 提到使用单独注册的域名，如 `webui.company-test.com`，可以实现类似的功能，但感觉不太必要。 • **使用 `.test` TLD**：andrewstuart2 建议使用 IETF 保留的 `.test` TLD，认为这是用于开发目的的最佳选择，并提到多年前 Firefox 的一些问题。 • **使用真实域名和 DNS 记录**：donatj 和 _def 提到添加真实域名记录或配置 DNS 服务器，以实现任意子域名的解析，但 _def 对这种方法的依赖性表示不满。 补充讨论： • **避免使用 `.local` 域名**：mohsen1 建议避免使用 `.local` 域名，因为 Chrome 在 HTTPS 下解析速度很慢，并提到曾发现相关的 Chrome 漏洞。 • **其他历史方法**：defraudbah 提到过去使用 `localtest.me` 域名进行测试，并提供了参考链接。 • **企业级解决方案**：accrual 描述了一个复杂的设置，使用 CSV 文件和脚本在 OpenBSD 上进行设备名称和 IP 地址的映射，实现自动化配置。 争议焦点： • **不同浏览器对 `.localhost` 和 `.local` 的支持差异**：部分用户提到不同浏览器对 `.localhost` 和 `.local` 域名的解析行为不同，尤其是 Safari 和 Chrome 的问题。 • **手动配置与自动化设置的优劣**：一些用户偏好自动化设置，如使用 Docker 代理或系统默认解析，而另一些用户则选择手动添加 hosts 文件或使用真实域名记录。 总结： 讨论围绕本地开发环境中域名设置和解析的各种方法展开，用户分享了使用 `.internal`、`.localhost`、`.test` 等 TLD 的经验，并讨论了不同浏览器和系统的兼容性问题以及自动化与手动配置的优劣。
