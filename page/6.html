文章摘要

TapTrap是一种针对Android设备的新型攻击，允许无权限的应用滥用屏幕动画。攻击者可以秘密打开不可见的权限提示等屏幕，诱导用户在不知情的情况下进行敏感操作，如授予相机权限或擦除设备数据。该攻击通过自定义长时间的透明动画，使用户点击隐藏屏幕上的敏感区域，从而绕过Android的权限机制。 **影响：** - 未经授权访问相机、位置、通知等。 - 可能启用“设备管理员”权限，允许远程擦除设备。 - 攻击不仅限于应用，还可针对网站，如劫持点击操作。 **检测难度：** - 在一项20人的用户研究中，无人察觉到攻击。 **技术细节：** - 攻击通过启动新活动并使用自定义透明动画实现。 - 即使在最新的Android版本上，TapTrap依然有效，尽管主要浏览器已修复此问题。 这种攻击广泛影响Google Play上的应用，约76%的应用易受攻击。

What is X-Forwarded-For and when can you trust it? (2024)

作者: ayoisaiah | 评分: 8 | 评论数: 1 | 发布时间: 2025-07-23 10:18
文章摘要

《What is X-Forwarded-For and when can you trust it?》一文介绍了X-Forwarded-For（XFF）HTTP header的作用及其信任问题。XFF用于记录客户端请求经过的多个代理服务器IP地址，帮助服务器识别请求的真实来源，尤其在使用代理、负载均衡或CDN时非常有用。其典型应用场景包括用户认证、负载均衡、数据本地化、地理内容分发、访问控制、安全防护、反欺诈、API速率限制、定向广告及日志分析等。 然而，XFF头信息可能被伪造，因此不能完全信任。为确保安全性，可以结合可信代理列表或可信代理计数来选择正确的IP。此外，需要注意解析XFF头时的各种潜在问题，如无效IP、分隔符解析错误、多个头存在及可能的代码执行风险。 文章还介绍了其他相关头信息，如Forwarded、X-Forwarded-Host/Proto和Via头，作为XFF的替代或补充标准。在使用XFF时，需谨慎处理并结合其他安全措施。

评论摘要
主要讨论点：如何处理和保护 X-Forwarded-For 头以及相关的安全问题 不同观点： • 一种观点认为，最安全的做法是在不信任整个调用链的安全性和可靠性时，完全丢弃外部不可信的 X-Forwarded-For 值，并在面向外部的反向代理中替换该头部信息。这可以防止后续的代理和后端应用盲目信任不安全的数据，从而减少潜在的安全风险。 • 另一种观点指出，仅记录 X-Forwarded-For 字段并不足够，因为该字段不包含请求链中最后一个代理的 IP 地址。为了完整性，Web 服务器应同时记录请求的源 IP 地址和 X-Forwarded-For 字段信息。这可以确保在需要时获取完整的请求路径信息。 • 还有观点提到，HTTP 头注入是一种潜在的安全威胁，攻击者可能利用类似 X-Forwarded-For 的头部进行 IP 欺骗攻击。OWASP 列出了一些与 IP 欺骗相关的头部，如 X-Forwarded-For 和 X-FORWARDED-foR。有效的 Web 应用防火墙 (WAF) 应该能够检测并阻止此类攻击。 • 最后，有人提到 RFC 7239 对 X-Forwarded-For 进行了标准化，定义了新的 "Forwarded" 头部，用于更安全和标准化的请求转发信息传递。这一标准自 2014 年起可用，采用 Forwarded 头部可以更好地解决传统 X-Forwarded-For 头部的不足和安全隐患。 补充讨论： • X-Forwarded-For 头部的安全性和标准化问题：讨论中提到了 RFC 7239 的 Forwarded 头部作为 X-Forwarded-For 的替代方案，以更安全和结构化的方式传递请求转发信息。 • 实际应用中的安全措施：包括如何在实际应用中结合 WAF 检测可疑活动，以及记录完整请求信息以确保能够追踪潜在攻击的来源。 争议焦点： • 是否应完全丢弃外部 X-Forwarded-For 值，还是应尝试记录和验证这些信息。这涉及到对调用链中其他组件的信任程度以及安全性和数据完整性之间的权衡。

这篇文章介绍了一款开源手持CNC雕刻机——Compass CNC。该设备结合了CNC技术的精准性和手动工具的灵活性与低成本，适合不想制作夹具或手不稳的人使用。它能够在实时自动校正，消除用户误差，同时提供手工操作的满足感。其3D设计、固件和电子设备均为开源，用户可以在GitHub上获取所有必要的资料来制作和修改自己的设备，并可通过电子邮件订阅加入社区。

评论摘要
主要讨论点：如何检测"异常构建模式"及构建系统的设计与安全性，尤其是关于可重现构建和信任风险的讨论。 不同观点： • [riffraff] 对系统如何检测"异常构建模式"表示好奇，尤其是如何识别如xz后门这样的问题。他提问系统是否依赖诸如"构建文件必须来自单个目录"或"不应使用存储库中已有的二进制文件"之类的规则，还是更通用的检测机制。 • [lrvick] 认为需要一个不可变的、确定性的、全源代码引导的操作系统来最小化信任风险，并介绍了ReprOS项目来解决此问题。该项目通过在一次性虚拟机中构建，并在主机上签署构件结果，以减少攻击风险。 • [simonw] 对项目表示兴奋，但指出需要一个web界面来减少使用Go CLI工具带来的摩擦。他还分享了通过"gsutil"命令获取构建列表的方法，并提供了相关Gist链接。 • [Flux159] 提到该系统是否要求通过CI系统而非开发者本地机器进行构建，并指出npm包的发布和Docker构建结果不一致的问题。他还询问该项目是否主要针对pypi、npm和crates，而忽略了Linux发行版如Debian的包。 • [WhatIsDukkha] 认为该项目是一个不彻底的措施，因为它不提供客户端构建功能。他提到Guix可以通过客户端机器重现上游二进制文件，并认为分布式重现能力更为优越。 • [Weethet] 质疑创建一个更狭窄版本的必要性，指出Nixpkgs已经有107158个打包的库和可执行文件，且Nix基础设施支持任意构建系统和创建Docker镜像。 • [bgwalter] 提到开源软件的价值为12万亿美元，但只有打包者、安全专家和SaaS公司从中获利。对Google项目的长期持续性表示怀疑，认为其可能只能维持两年。 • [ChrisArchitect] 引用xkcd漫画"Dependency"来暗示开源项目中复杂的依赖关系问题，可能在讨论中具有相关性。 补充讨论： • 争议焦点在于如何有效检测异常构建模式及系统的安全性，是否依赖集中式服务器或分布式重现能力更为优越。 • 另一个值得注意的讨论点是项目对用户界面的需求，以及不同构建系统和包管理器之间的不一致问题。 • 对Google项目长期持续性的怀疑也是一个值得注意的观点。
