Shrimple – A Simpler, Nicer Markdown

作者: usrbinenv | 评分: 27 | 评论数: 18 | 发布时间: 2026-07-06 02:24
文章摘要

Shrimple 是一个更简洁的 Markdown 替代品，旨在让源文档既清晰可读又能渲染成美观的 HTML。 **主要特性：** - 使用 Go 编译，通过命令行转换文档 - 链接通过脚注引用 URL，避免源文档混乱 - 代码块用 6 个空格缩进，支持语法高亮 - 支持无序和有序列表，两级标题（h1/h2） - 注释块功能，用于创建特殊说明区域 - **解析和渲染字典**：最强大的功能，可以在不修改源文档的情况下，通过外部字典文件高亮或标记特定词汇 - 静态网站生成器：可将多个 Shrimple 文件转换成完整的文档网站，自动生成导航菜单 核心理念是保持源文档的可读性，同时提供强大的渲染能力。

评论摘要
主要讨论点：关于Markdown替代方案Shrimple的设计理念和实用性争议 不同观点： • **支持者观点**：URL脚注设计优雅（trencedamp），向后兼容是正确方向（gritzko以StrictMark为例） • **标准泛滥担忧**：多位评论者（annzabelle, ssuds）引用XKCD标准漫画，认为Markdown问题微小，新标准弊大于利；w10-1指出djot等先例也未获广泛采用 • **语法设计批评**： - 标题需要两行编辑，增加复杂度（LunicLynx） - 缩进代码块难以粘贴和输入，三重反引号更好（SwellJoe） - 链接脚注在跨文档复制时需更新编号，不便利（genzer） • **功能限制质疑**： - 仅支持h1/h2两级标题不足以应对复杂文档（vekntksijdhric, tonnydourado） - 缺少表格支持（llagerlof） - 代码块不应改变原始缩进（llagerlof） • **信息缺失**：rendaw质疑未说明"更好更干净"的依据；roshanroyj要求侧边对比 补充讨论：ser0提到这是个拥挤的领域，建议与RST比较；arthurofbabylon提供了类似项目参考

SPLIT PARTITION` 命令，可以一句话将现有分区拆分成多个更小的分区。例如将季度分区拆分为月度分区，Postgres 会自动将数据迁移到对应的新分区中。 整个操作是事务性的，可以中途回滚。新分区必须完整覆盖原分区范围，不能有间隙或重叠。这大大简化了分区管理，使分区策略调整变得更加灵活高效。

Do you hate XML? (2010)

文章摘要

本文讨论了XML技术从热捧到遭受批评的演变过程。作者曾是XML的狂热支持者，但在2004-2005年XML热潮达到顶峰后，网络上"讨厌XML"的声音开始增多。 文章引用了2004年一场会议演讲"开发者讨厌XML"，指出核心问题：使用XML需要开发者成为特定领域的专家，掌握XSLT等专用工具。作者认为这个问题并非XML独有，SQL等技术同样存在，任何对象关系建模都需要领域知识。 作者还探讨了"hatred"（讨厌）这个词的文化差异，认为人们对技术的"爱恨"更像是对音乐风格的偏好表达，而非真正的情感仇恨。XML的主要优势在于提供了可互操作的传输语法。

评论摘要
主要讨论点：XML 作为数据交换和标记语言的适用性及其历史定位 不同观点： • **技术缺陷派**：认为 XML 存在根本性问题——属性和子元素的选择造成歧义（如国家名为何用属性而排名用子元素？），类型和基数需要 Schema 才能确定，解析后的 AST 难以转换为编程语言的数据结构，且存在安全解析难题和字符编码识别问题 • **过度工程化批评**：承认 XML 本身设计良好，但 2000 年代的滥用（SOAP、WS-* 标准、Apache Cocoon）导致人们厌恶。问题不在 XML 本身，而在于过度复杂的应用场景 • **工具生态派**：强调 XML 拥有成熟的工具链（Schema、XSLT、XPath、IDE 集成），而 JSON/YAML 后来不得不重新开发类似工具。XML Schema 比 JSON Schema 强大得多 • **实用主义者**：认为 JSON 更符合编程语言的对象模型，语法更简洁，学习曲线更平缓。对大多数只需要结构化数据的场景，XML 过于复杂 • **怀旧与复兴派**：认为 XML 被不公平地批评，预测会像黑胶唱片一样回归，年轻一代应以新视角审视其价值 补充讨论：核心分歧在于使用场景定位——XML 作为标记语言适合文档，但被错误地用于数据交换；属性vs元素的二元性是最被诟病的设计；实践中"无 Schema"的 JSON 因更有趣而获胜

Dependencies should be fetched directly from VCS

作者: mrngm | 评分: 36 | 评论数: 9 | 发布时间: 2026-07-05 20:44
文章摘要

这篇文章对比了 Go 和 Ruby 的依赖管理安全性。Go 直接从版本控制系统（如 Git）获取依赖，无需"发布包"步骤，审计依赖只需查看 git 提交历史，简单透明。而 Ruby、npm、PyPI 等需要将代码打包上传到中心仓库，这个发布环节容易被注入恶意代码，且审计困难。近期的供应链攻击（如 xz、event-stream）都利用了发布步骤。作者认为应重新思考"发布包"模式，而非仅依赖 AI 扫描来解决安全问题。

评论摘要
主要讨论点：包管理系统应该依赖版本控制系统（VCS）还是中心化注册表 不同观点： • **支持Go的混合模式**（jchw）：Go同时支持模块代理和直接从VCS获取，两者完全冗余。代理可选但不强制，VCS保持真实源地位。sumdb独立保证不可变性。这种既有中心化便利又保持去中心化选项的设计罕见且优秀。 • **质疑VCS方案的可行性**： - 安全性问题（brunoarueira）：VCS多次被投毒，需要大幅改进安全 - 可靠性问题（nijave）：依赖多个VCS保持在线不够可靠 - 技术限制（arcatek）：包发布需要构建、编译等处理，安装时运行任意命令风险太大，Git难以规模化 • **倾向分离的注册表系统**： - 架构独立性（cygx）：不应让包创建者的VCS提供商成为语言基础设施；版本控制文件和发布包文件不一定对应 - 灵活性（tikkabhuna）：独立注册表能在Git仓库改名或删除时存活，VCS和注册表分离可提供不同功能 - 不可变性保证（kibwen）：引用left-pad事件，强调专用注册表的关键优势是可以禁止取消发布，这是GitHub等平台不保证的 补充讨论：Go更适合源码分发因其纯Go生态广泛，而解释型语言因性能敏感部分用编译语言实现，需要多种工具链支持
