Redis 8.8: New array data structure, rate limiter, performance improvements

作者: ksec | 评分: 179 | 评论数: 10 | 发布时间: 2026-06-03 10:05
文章摘要

Redis 8.8 正式发布，带来显著性能提升和多项新功能。性能方面，多种数据类型的操作吞吐量提升最高达83%，持久化和复制速度提升60%。新功能包括：全新的通用数据结构array（索引可寻址的动态数组）、内置的窗口计数器限流器、Streams消息NACK支持、哈希字段的子键通知、JSON数值数组存储的显式控制、时序查询支持多聚合器，以及有序集合的COUNT聚合器。这些改进为现有用例提供了更好的灵活性和效率，并开启了新的应用场景。

评论摘要
主要讨论点：Redis 8.8 新功能发布及 Redis 项目现状 不同观点： • **技术细节纠正派（simonw）**：指出官方描述有误，rate limiter 实际使用的是 GCRA（通用信元速率算法）而非窗口计数器，这是一种漏桶算法，只需为每个限流键存储单个整数（理论到达时间），算法设计精巧且受 Brandur Leach 的 redis-cell 项目影响 • **功能需求派（9dev）**：认可 Redis 作为外部数据结构工具的价值，但指出两大不足：1) 缺乏像 SQLite 那样的嵌入式能力；2) 高可用方案过于复杂，需要阅读大量文档理解两种多节点方案，且存在诸多限制使其在许多应用场景不实用 • **许可证担忧派（tapoxi, ShakataGaNai）**：质疑 Redis 许可证变更后是否还有继续使用的理由，提到 Redis/Valkey 分裂事件，以及 Kubernetes operator 停止维护等问题 • **AI 动机质疑派（fga_qwrh）**：认为 Redis 作者突然热衷 AI 是因为数组数据结构在 AI 中的应用，这一动机在数周前就已明显 补充讨论：有用户（caraphon）对新功能持积极态度，认为 rate limiter 和数组功能值得尝试。另有提及 Redis 与 DeepSeek 可能存在合作关系（focusgroup0）。

Changing how we develop Ladybird

作者: EdwinHoksberg | 评分: 838 | 评论数: 105 | 发布时间: 2026-06-05 07:26
文章摘要

Ladybird 浏览器项目宣布不再接受公开的 pull request，今后代码变更仅由项目维护者提交。这一改变主要出于两个原因：一是 AI 工具的普及让代码贡献不再能有效反映贡献者的可信度和投入程度，降低了通过贡献建立信任的传统机制；二是作为即将面向真实用户的浏览器，安全性至关重要，项目需要更严格的开发流程和明确的代码责任归属。项目仍保持开源，欢迎通过 bug 报告、测试、标准讨论等方式参与，但不会通过其他渠道接受代码补丁。所有现有的公开 PR 将被关闭。

评论摘要
**主要讨论点：** Ladybird浏览器项目宣布不再接受外部代码贡献后，社区对开源项目应对AI生成代码冲击的不同反应 **不同观点：** • **支持方**：认为AI降低了代码提交门槛，大量AI生成的PR让maintainer负担激增，代码量不再等同于付出的努力和诚意。项目有权优先保障质量和安全（Fraterkes, noIdeaTheSecond, mabedan） • **反对方**：认为这损害了开源精神，阻碍了新维护者的发现和培养；拒绝外部贡献意味着重复劳动，用户修复bug后无法直接贡献，只能让团队重新实现（nh2, koteelok, pulsartwin） • **中间立场**：理解资源有限团队的困境，但指出Chrome/Firefox等大型项目仍保持开放，值得肯定；担心失去社区的非代码贡献（想法、代码审查等）带来更大损失（domenicd, patates） **补充讨论：** - 有人质疑Ladybird作者本人也常提交大量未经审查的代码，决策存在双标（adrian17） - SQLite和Blender等成功项目早已采用类似封闭模式，这可能是大型项目的必然趋势（nathell, TeriyakiBomb） - 社区担忧这背离了Serenity/Ladybird原本的社区文化，希望至少保留未来参与的可能性（mvanveen, Deukhoofd）

Azure Linux 4.0 is Microsoft's first general-purpose Linux

作者: haydenbarnes | 评分: 203 | 评论数: 32 | 发布时间: 2026-06-05 03:14
文章摘要

微软在 Build 2026 上发布了 Azure Linux 4.0 公开预览版，这是首次允许用户在任何 Azure 虚拟机上运行该系统，而非仅作为 AKS 的底层主机。这标志着 Azure Linux 从专用设备发行版转变为通用 Linux 发行版。 4.0 版本基于 Fedora 43 构建，采用声明式覆盖层方式，不再手动维护每个软件包规范文件。主要更新包括：内核 6.18 LTS、dnf5 包管理器、glibc 2.42、systemd 258 等。支持虚拟机、容器、AKS 和 WSL 等多种部署场景。 Azure Linux 的特色在于可审计的供应链设计、强安全性（SELinux、FIPS 140-3 认证进行中）以及针对 Azure 优化。目前已被 Databricks、LinkedIn 等大规模采用。

评论摘要
主要讨论点：微软推出基于Fedora的Azure Linux发行版，声称为"通用目的"操作系统 不同观点： • **支持方观点**（rswail）：这是真正的通用系统，可运行容器、虚拟机或裸机应用；具备完整的SBOM供应链可追溯性，满足安全审计要求；采用只读OS设计。虽不支持随机硬件配置，但能在多种环境中运行通用应用 • **质疑"通用"定义**（froh, codycharris, reacweb）：认为这只是针对Azure优化的专用系统，不会在微软计算环境外运行；真正的通用OS应支持任意硬件并有厂商认证；实质是微软提供从WSL到云的统一Linux栈 • **批评微软动机**（bananaquant, egorfine, nullpoint420）：指责微软搭便车Red Hat的工作成果；将bleeding-edge发行版快照称为"通用"是误导，Fedora/RHEL本就有稳定性区分；怀疑是"拥抱-扩展-消灭"(EEE)策略，通过稀释"通用"术语来占领新领域 • **技术细节讨论**（aykutseker）：从tdnf迁移到dnf5值得关注，多数内部平台会越来越定制化而非通用化 补充讨论：部分评论充斥讽刺情绪，质疑微软的营销策略和AI生成内容的使用。争议焦点在于"通用目的"这一表述是否准确，以及微软的真实意图。

"Maybe later" was a feature

文章摘要

这篇文章探讨了"不写代码"的价值。作者认为，团队待办事项中那些一直被推迟的功能，往往最终证明是不必要的——如果真正重要，早就会被优先实现。不构建这些功能实际上加速了团队发展，帮助聚焦真正重要的事情。 作者担心随着AI编程工具的普及，开发者会用它们构建那些本不该构建的积压功能，导致代码库膨胀、充斥难以维护的遗留代码。虽然AI也能帮助删除代码，但实际操作中很难说服团队移除已有功能。 核心观点：最有价值的代码，是那些你没有写的代码。选择不做什么，本身就是一种重要的产品和开发策略。

评论摘要
主要讨论点：AI加速软件开发后，是否应该构建更多功能，以及"maybe later"（延迟决策）机制的价值 不同观点： • **支持快速构建派（staticshock）**：认为一切都是搜索过程，AI让我们能搜索更多可能性。虽然会产生大量垃圾，但优质内容会自然浮现，就像书籍、音乐一样。进化压力会重新平衡"maybe later"机制 • **质量优先派（overgard, andai, gamerDude）**：警告用LLM快速实现功能容易事后发现是坏主意。手写代码时会更早遇到问题。主张用AI做更好的工作（测试、分析）而非堆砌功能。最好的代码是不存在的代码——无bug、无维护负担。减法能力（删除、简化）比加法更重要 • **经验主义派（patcon）**：建议将精力从"决定构建什么"转向"拆解错误构建"。基于验证经验优于假设性规划，但担心我们会失去预测未来的能力 • **怀疑幸存者偏差派（greatgib）**：质疑"未构建的功能果然没用"的结论。那些功能可能带来突破、更多客户，或避免安全漏洞。结果不确定，不能轻易下结论 补充讨论：cortesoft指出有些"nice to have"功能延迟后持续浪费时间，最终实现时后悔没早做。vegadw从非商业角度看，认为AI降低门槛让更多人实现创意项目是好事，关键看输出是否需要人类创造力
