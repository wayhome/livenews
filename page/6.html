文章摘要

这篇文章讨论了美国税法中一项鲜为人知的修改，即2017年《减税与就业法案》（TCJA）对《国内税收法》第174条的调整，如何悄然影响了美国科技公司的研发投资逻辑。此前，企业可以当年全额扣除研发支出，激励了国内的研发活动和就业。然而，修改后，企业需要在5到15年内逐步摊销这些费用，削弱了研发投资的吸引力。这一变化在2022年开始显现影响，导致包括微软、Meta在内的科技公司大规模裁减高薪白领岗位，总数达数十万。尽管目前国会正试图通过两党合作撤销这一修改，但其带来的广泛影响已引发广泛关注和反思。文章指出，这一税法调整不仅与推动制造业回美的政治口号背道而驰，还揭示了税收政策对科技行业的深远影响。

主要讨论点：美国税法第174条修订对企业及科技行业的影响，特别是对研发费用摊销的新要求及其是否是科技行业大规模裁员的根本原因。 不同观点： • **[mensetmanusman]** 认为这可能是大企业支持的政客有意为之，目的是 disrupting 软件基础设施。这种观点暗示了政策变动背后的潜在政治动机和企业利益驱动。 • **[potato3732842]** 则认为，从长远来看，研发费用的摊销对大企业影响有限，因为它们可以在5年或15年的时间内分摊扣除，且这一变化已经酝酿多年，大公司的会计师应该早有准备，因此财务上不应受到太大冲击。该评论还指出，大公司对这一变化应具有足够的适应能力，尤其是那些有长期规划的公司。 • **[dtagames]** 反驳了前述观点，指出研发费用摊销无法解释大规模的科技行业裁员，因为被裁的多数员工并不从事研发工作，而是从事常规软件开发（如游戏开发）。该评论进一步强调，游戏行业尽管利润丰厚，依然进行了大规模裁员，认为这是企业贪婪的表现，而非单纯的财务或政策原因。 补充讨论： • **争议焦点**：第174条修订是否是科技行业大规模裁员的主因。 - [potato3732842] 认为政策对大企业影响不大，并质疑裁员是否真的与政策变化直接相关。 - [dtagames] 则明确反对将裁员归因于政策变化，认为行业利润和企业决策中的贪婪因素才是裁员主因。 • **政策时间线**：[potato3732842] 提到这一政策变化已经酝酿多年，企业应有足够时间准备，暗示裁员潮可能与其他因素（如市场环境或企业内部决策）有关。 • **企业规模影响差异**：[potato3732842] 指出大公司因其长期规划能力受影响较小，而 [dtagames] 则关注到即使是高利润行业（如游戏行业）也进行了大规模裁员，质疑这一论点。 总体来看，评论中对于政策变化的影响存在不同看法，有的认为影响有限，有的则认为另有其他原因（如企业贪婪）导致了裁员潮。

Standard Completions

文章摘要

本文讨论了多个提供与OpenAI兼容的Completions和Chat Completions API的供应商，如Deepseek、OpenRouter和vLLM等，虽然OpenAI已将Completions视为遗留API，且Chat Completions也被弱化以推广OpenAI Responses API。尽管OpenAI承诺无限期支持当前的Chat Completions API，但它缺乏多模态输出、输入对象存储、显式缓存和助理前缀等功能。各供应商以非标准方式添加了这些功能，导致开发者使用不便。例如，助理前缀在不同供应商中的实现方式各异，且没有标准信号来指示是否支持某些功能，开发者需尝试或检测上游供应商。文章呼吁建立一个标准化的OpenAI API超集，以简化开发者体验，并促进LLM生态系统的互操作性。感兴趣的供应商和开发者可参与Standard Completions工作组。

评论摘要
主要讨论点：关于旧的 completion API 与新的 chat creation API 哪个更优越的讨论 不同观点： • [lolpanda的观点] 认为 legacy completion API 优于新的 chat creation API。理由是 completion API 将所有输入视为单个字符串，而 chat API 则要求将输入作为消息列表处理。在处理现代的代理工作流时，模型通常需要处理大量输入数据，包括 RAG 数据、函数调用和其他元数据，用户和助手的消息仅是整体提示的一小部分。因此，将对话与其他输入数据统一格式化为一个单一的文本提示（如使用 ... 标签）更为直观。OpenAI 的新 completion API 支持单个大字符串或消息列表，这一点很不错。此外，他们提到在 Claude 工具中尝试过类似方法，将提示构建成包含指令和示例的较大提示。 • [pawanjswal的观点] 对 lolpanda 的观点表示赞同，指出许多开发者在开发过程中都会遇到这一问题。他认为指出 API 的不一致性并倡导建立一个通用基准是有益的，认可了 lolpanda 提出的改进建议。 补充讨论： • lolpanda 提到了新的 completion API 支持单个大字符串或消息列表，这表明新 API 也在尝试解决一些格式上的灵活性问题。 • 讨论中还提到 Claude 工具中的 XML 格式化方法，表明在不同平台上对提示格式的不同处理方式也是开发者关注的重点。 • 争议的焦点主要在于处理大规模输入数据时，哪种 API 格式更直观和高效。lolpanda 更倾向于使用单一的字符串格式，而新的 chat API 则采用消息列表的方式，这在处理复杂工作流时可能带来不便。

文章摘要

Go语言的错误处理冗长问题一直是开发者抱怨的焦点，主要集中在需要频繁检查`if err != nil`。这种模式在涉及大量API调用的程序中尤为明显，导致代码中充斥大量与核心逻辑无关的错误处理代码。尽管社区对引入新机制的呼声很高，Go团队多年来尝试解决此问题，但未找到理想方案。 2018年，Go团队提出基于“检查和处理”（check and handle）机制的方案，但因过于复杂而被放弃。2019年，提出简化的“try”方案，虽然尝试通过工具`tryhard`评估影响，但因其隐藏控制流且返回机制不透明，再次被拒。 反思过程中，Go团队认识到应更早引入新关键词，并给予社区更多反馈空间。近期，有新提案回归原始设计并改进不足。尽管过程曲折，Go团队将继续听取反馈，探索更优错误处理方案。

评论摘要
主要讨论点：Go语言的错误处理机制及其可能的改进 不同观点： • 支持现有错误处理机制：一些开发者，如[threemux]和[maxwellg]，表示欣赏Go团队对错误处理的透明态度，并认为经过一段时间的适应后，现有的错误处理方式是可以接受的。他们认为显式的错误处理提供了更多的控制和灵活性，并且不希望为了改进而破坏向后兼容性。 • 提议增加语法糖：[_jab]和[packetlost]等人建议增加语法糖，以区分常见的`if err != nil`和不常见的`if err == nil`，从而减少错误发生。他们认为这将提高代码的可读性和安全性。 • 对比其他语言：[jamamp]和[JamesSwift]对比了Go和Rust等其他语言的错误处理方式，认为Rust的`Result`类型和`?`操作符提供了更好的错误处理机制，可以考虑引入类似功能。 • 对过程和决策的不满：[pie_flavor]批评Go团队在错误处理改进上的决策过程，认为他们在多个完美提案之间犹豫不决，导致问题长期未解决。 • 创新IDE插件可视化：[ajkjk]提出了一种创新的方式，通过IDE插件以可视化方式处理错误，从而提高代码的可读性和逻辑流的可视化。 补充讨论： • 错误处理的常见模式：[jamamp]详细描述了Go中处理错误的四种常见模式，强调了Go中显式处理错误的好处。 • 对错误处理改进的需求：[arp242]提到尽管大多数用户没有对错误处理提出抱怨，但仍有部分用户认为可以做出一些改进。 • 引入高级语言特性：[hackingonempty]和[ziml77]讨论了引入高级语言特性如“do notation”或“monadic-let”的可能性，认为这些特性可以提供更简洁的错误处理方式。 争议焦点： • 是否引入新的语法或机制：部分开发者认为现有的错误处理机制已经足够，而另一部分开发者则认为需要引入新的语法或机制来改进错误处理。 • 改进过程的透明性和效率：一些开发者对Go团队在错误处理改进上的决策过程表示不满，认为他们在多个提案之间犹豫不决，导致问题长期未解决。 总结： Go语言的错误处理机制在开发者社区中引起了广泛讨论，部分开发者支持现有的显式错误处理方式，而另一部分开发者则提议引入新的语法糖或高级语言特性来改进错误处理。同时，也有开发者对Go团队在错误处理改进上的决策过程提出批评，认为需要更高效的决策和透明度。

Lingo.dev 是一个开源的 AI 驱动工具包，用于网页和移动应用的本地化与翻译。它包括三大工具：Lingo.dev CLI（快速翻译应用和 Markdown 内容）、Lingo.dev CI/CD（自动保持翻译更新）和 Lingo.dev Compiler（在构建时让 React 应用支持多语言，无需修改组件）。用户可以自带大型语言模型（LLM）或使用 Lingo.dev 提供的引擎。该项目欢迎社区贡献，并提供了详细的文档和演示。

主要讨论点：使用LLM（大型语言模型）和编译工具进行代码库的国际化（i18n）和本地化（l10n）的优缺点及实际应用中的挑战。 不同观点： • **benbayard**：认为当前应用未处理好复数形式等复杂翻译问题，尤其是俄语、日语等语言。对LLM在真实生产环境中的表现持怀疑态度，建议使用ICU兼容的JSON。同时指出日语等RTL（从右到左）语言会带来UI和本地化挑战。 • **cluckindan**：认为应与现有的翻译管理格式或服务集成，而非依赖LLM。LLM在处理专业术语翻译时表现不佳，尤其对于技术或专业内容网站，当前方案可能不如传统方法。 • **exhaze**：分享了自己类似的工具项目，强调日本本地化的文化差异，以及日语在语言和设计上的独特性。支持使用LLM，并通过实例展示了LLM（如Gemini 2.5）在日语翻译中的优势。 • **halflife**：对LLM方案持怀疑态度，更偏向Angular的编译时i18n解决方案，而非React的运行时方案。希望编译器能与大型组织现有的本地化工作流集成。 • **lukol**：关注法律和品牌相关的特定措辞如何在翻译中保持不变，询问是否允许开发人员手动翻译特定字符串。 • **stared**：认为只需使用Cursor等工具进行少量提示即可开始翻译，并通过实例展示了如何在科学内容中验证翻译结果，强调在特定领域（如科学、工程）中翻译验证的重要性。 • **jjani**：作为早期用户，提出了一些改进建议，包括按语言设置模型、支持多源语言、修复某些技术问题等。 • **thrance**：强烈反对使用自动翻译工具进行本地化，认为机器翻译质量差，会给用户带来不好的体验，建议雇佣专业翻译人员。 补充讨论： • **techn00** 和 **splix** 关注该工具是否适用于React Native（Expo）和桌面应用（Electron、Tauri），以及在没有React Router的项目中的适用性。 • **maelito** 和 **jackconsidine** 表达了对该工具在具体项目（如carte.app、Next.js）中的应用兴趣。 争议焦点： • LLM在翻译和技术术语处理上的可靠性与准确性。 • 自动翻译工具与专业人工翻译的质量对比。 • 不同语言（尤其是具有复杂文化背景和语言结构的语言）的本地化挑战。 • React运行时i18n解决方案与Angular编译时解决方案的对比。

A manager is not your best friend

作者: thisismytest | 评分: 110 | 评论数: 22 | 发布时间: 2025-06-04 01:29
文章摘要

文章主要讨论了管理者为何应避免与下属抱怨和共鸣（commiseration），因为这种行为会对组织造成破坏，导致低信任环境，并形成小团体。文章指出，虽然人们习惯通过共鸣寻求安慰，但在管理角色中，共鸣往往是有害的，会引发优越感并阻止其他团队改进。管理者应像“好 therapist”一样，倾听但不过度附和，通过提问澄清事实，而非简单地附和情绪。文章建议，管理者应避免使用消极语言，尽量从乐观角度解释其他团队的行为，并专注于客观事实而非主观批评。最终目标是通过建立同理心来促进高效协作。
