you_can::turn_off_the_borrow_checker

作者: striking | 评分: 46 | 评论数: 10 | 发布时间: 2026-05-22 20:31
文章摘要

这是一个Rust宏库文档，介绍了`turn_off_the_borrow_checker`宏。该宏通过将引用包装在`borrow_unchecked()`函数中来解绑生命周期，从而抑制借用检查器的错误提示。文档强调这**不应在生产代码中使用**，仅用于教育目的。它允许创建多个可变引用等不安全操作，但会导致未定义行为和潜在的运行时错误。宏的工作原理是识别代码中的`&`、`&mut`、`ref`等引用操作符，并用unsafe包装绕过编译器的别名保证。文档附带了多个讨论链接，解释为什么不应该这样做。

评论摘要
主要讨论点：对一个通过宏或技巧突破 Rust 安全/借用限制的项目，大家在“好玩、实用、风险和实现方式”上的不同看法。 不同观点： • 觉得这是有趣的边界探索与玩梗作品。有人称其是“Cool idea”，也有人说“Disgusting. I love it.”；还有人把它联想到 Perl 的 ACME 模块、以及早年 C++“多种访问私有成员的方法”，强调其娱乐性和实验性。 • 期待它不只是“关闭借用检查器”。有评论认为目前 `you_can` 更像 `turn_off_the_borrow_checker`，希望以后加入更多反例，去扩展“Rust 里哪些事不是不能做，只是要非常规手段”的展示。 • 从实用角度，有人分享替代做法：在单线程、无需释放或关机后无需清理的场景下，可先 `Box` 再 `Box::into_raw`，以获得多个可变引用。这说明类似需求并非纯理论，也有人用更直接的 `unsafe` 方案解决。 • 对安全性持警惕或讽刺态度。像“Even more unsafe rust, great!” 体现出对项目增加不安全性的担忧或调侃。 • 关注技术细节和代价。有人追问宏是否能偷偷插入 `unsafe` 块，另有人关心这类做法是否会明显影响编译时间。 补充讨论：争议焦点主要在于，这类项目究竟是有教育意义的边界演示，还是在削弱 Rust 的安全承诺；同时也涉及“宏隐藏 `unsafe`”的透明性问题。

评论摘要
主要讨论点：围绕文章中提到的“C64/老式计算机风格字体”的来源、个人记忆联想，以及少量对硬件操作细节的质疑。 不同观点： • 字体识别与来源联想：有人认为这字体在德国最像《CHIP》杂志/logo（`rob74`），也有人联想到 `Master of Orion`、`Paradroid`、以及70-80年代常用于表现“电脑/科技感”的 `MICR` 风格字体（`cousin_it`、`jansan`、`bitwize`）。这些评论彼此呼应，核心是从不同文化和软件记忆中辨认字体。 • 怀旧与个人实践经验：多位评论者借题回忆早期计算机经历，如自制 C64、用 dead test 卡排障、因接线缺失和芯片错误导致花屏（`dusted`）；也有人提到 1986-87 年常见的 letter maker 软件和 Rob Hubbard 音乐，认为这类字体曾启发自己入门汇编（`_the_inflator`）。 • 审美认可与再使用意愿：有人直接称赞文章与字体，表示曾在自己 UI 中大量使用 `Westminster`，甚至想重新启用（`krige`）；也有人把讨论延伸到老 Mac 系统字体和设计史（`hankbond`）。 • 对文章风格与真实性的轻松反馈：有人认为文中的拼写错误反而像“真人写作”的痕迹，增加趣味（`Chaosvex`）。 • 争议点在硬件操作：`snvzz` 质疑“把芯片焊进插座”这种做法，认为比直接插入更怪，尤其还是把原芯片剪掉后再套接，虽可行但不合理。这是评论中少数明确的反对意见。 补充讨论：整体氛围偏正面，主要是集体考古式补充记忆；真正的分歧集中在字体到底像什么，以及硬件维修手法是否合理。

Noroboto: Lying Fonts and Mitigation in Rust

文章摘要

这篇文章介绍了一种名为"Noroboto"的字体攻击技术。作者创建了一个恶意字体，通过将文档中的正常Unicode字符映射到Unicode私有使用区(PUA)的代码点，使文档在屏幕上显示正常文本，但复制粘贴后变成乱码。这种"字体欺骗"利用了Word和PDF规范允许嵌入字体的特性，可能被用于法律文档中获取不当优势。虽然最初的简单映射被ChatGPT 5.5破解，但作者通过引入4对1的随机映射和多态加密技术增强了混淆效果。前沿AI模型仍可通过渲染文档并OCR识别来破解完全混淆的文档。

评论摘要
主要讨论点：利用字体/Unicode/排版技巧让文档“人眼所见”与“机器读取”不一致，这种做法的法律风险、技术可行性、实际威胁模型与副作用。 不同观点： • 法律上难成立或可被追责：`phuff`认为这更像“欺诈性虚假陈述”，若故意误导签约方，合同效力和赔偿责任都可能受影响，因此未必经得起法律审查。 • 技术上并不新，且有更直接手法：`PufPufPuf`、`mproud`、`sheept`认为连字、字体字符对调、可见图像叠加不可见文本等都能达到类似效果；`echoangle`甚至说直接贴截图也行。 • 应重视这类新漏洞：`chaidhat`肯定其创意，认为提前认识这类攻击面有价值，不该一味苛责。 • 实际威胁有限且副作用大：`echoangle`质疑法院等真实场景是否会接受这种不可检索文档；`laserbeam`认为这本质像替换密码，LLM可能能解，反而更会伤害无障碍工具、复制粘贴和普通使用。 • 工程与流程上应靠防御措施：`projektfu`提到 Paperless-NG 会栅格化并 OCR PDF 来防字体混淆，甚至认为合同场景应默认这样做。 补充讨论：争议焦点在于“这算不算新型有效攻击”。一方强调它揭示了真实风险；另一方认为已有更简单变体，且在法律、可用性和审查流程下未必实用。`fourgreen`还指出自己更早提出过类似想法。

文章摘要

这篇文章介绍了如何让90年代至2000年代初的老电脑联网。作者怀念Windows 9x/XP时代，但这些老电脑的WiFi模块过时，无法连接现代WPA加密网络。 解决方案很简单： 1. 购买USB-C转以太网适配器 2. 连接到Android手机和老电脑的以太网口 3. 在手机设置中启用"以太网网络共享" 手机会通过DHCP自动为电脑分配IP地址，将WiFi连接桥接到有线网络。这个方法适用于所有带以太网口的老电脑，无需降低WiFi安全性或额外布线。作者测试了USB-C扩展坞也可行，但需要外接电源。

评论摘要
主要讨论点：如何让老旧电脑（特别是只有以太网接口的设备）连接到现代WiFi网络 不同观点： • **购买专用硬件方案**：建议购买WiFi转以太网桥接器（约40美元）或GL-MT300N-V2 Mango设备（30美元），简单直接且功能更强大，还可为智能电视等设备提供VPN支持 • **利用现有设备方案**：通过Android手机USB网络共享、旧路由器刷OpenWRT/DD-WRT固件、树莓派Zero W作为USB-WiFi桥接等方式，无需额外花费即可实现连接 • **硬件升级方案**：对于ThinkPad T系列等老设备，可通过修改BIOS并更换mPCI WiFi芯片来原生支持WiFi，或使用支持Windows XP的USB WiFi适配器 • **软件解决方案**：使用EasyTether等软件（约10美元），在Linux系统上即插即用，将手机识别为USB以太网设备 补充讨论：有评论提到现代以太网已支持Auto MDI-X自动协商功能，不再需要像过去那样使用交叉网线。也有人对文章标题表示期待更"戏剧性"的解决方案，以及开玩笑希望连接时能发出老式调制解调器的声音。

微软本周发布了迄今发现的最早DOS源代码，这些代码甚至早于MS-DOS品牌。发布内容包括86-DOS 1.00内核源码、PC-DOS 1.00开发快照以及CHKDSK等工具。86-DOS由程序员Tim Paterson为Intel 8086计算机开发，微软后来授权并收购了它，为IBM PC提供操作系统。由于代码年代久远未数字化存储，历史学家团队从纸质打印件中艰难转录扫描。微软此前已开源过MS-DOS 1.25、2.0、4.0等版本及其他早期软件项目。

评论摘要
主要讨论点：微软开源DOS 1.0源代码引发的历史回顾与技术反思 不同观点： • **怀旧派**：羡慕早期计算机时代，认为几千行汇编代码就能创业成功，当时的编程更注重性能、创造力和科学性，批评现代开发充斥着库、虚拟化和糟糕的代码堆叠（nananana9, teamsolid） • **历史价值派**：赞赏微软开源举措，强调BASIC语言同样重要，认为微软本质上是开发工具公司。关注早期计算架构选择对x86影响深远，期待未来数字考古学领域的发展（jmward01, danborn26, 9dev） • **技术实践派**：成功在DOSBox中运行DOS 1.0，证明代码依然流畅可用；关注源码保存不易（需OCR纸质打印件）和实际应用场景（wpnx, locusofself, imoverclocked） • **历史八卦派**：讨论IBM与微软合作的偶然性——IBM本想要CPM系统，但Digital Research拒签保密协议，成为计算机历史转折点（acomjean） 补充讨论：有用户指出这是重复帖子，并提供了更早版本86-DOS二进制文件的信息。部分人期待微软开源早期Windows源代码。

Silk: Open-source cooperative fiber scheduler

作者: animetyan | 评分: 118 | 评论数: 14 | 发布时间: 2026-05-20 17:15
文章摘要

Silk 是 ClickHouse 开源的 Linux 协作式纤程调度器，采用每 CPU 调度线程、`io_uring` 集成和按拓扑感知的工作窃取。它提供轻量级栈式协程、异步 IO、睡眠取消及多种同步原语，并包含性能基准、调试工具和完整构建测试流程，目标是在低开销下实现高并发。

评论摘要
主要讨论点：围绕一种基于 fiber/协程的运行时库，讨论其在高并发 I/O、系统服务、CPU 递归任务中的适用性，以及它与现有并发模型的关系和潜在问题。 不同观点： • 支持其在系统级与高并发场景中的价值。`cyphar` 提到 systemd 已加入 fiber 支持，认为这类模型对 `pid1` 这类不适合用线程的程序很有用；`nasretdinov` 进一步推测 ClickHouse 可借此缓解“每连接一线程”模型线程过多、活跃连接数难超千的弱点，尤其适合 async INSERT。 • 认为这并非全新方向，而是已有成熟实践。`audidude` 说 GNOME 多年来就在用类似方案，且能力更广，包括 `io_uring`、线程池调度、work stealing、可轮询信号量和 profiler 集成。 • 强调应区分不同运行时目标。`enduku` 认可其与 `Cilk` 的关联，但指出仍有只专注 fork/join 递归的小型运行时空间；其项目只面向 CPU 密集递归，不是通用 async I/O fiber 运行时。`jeffreygoesto` 则将其与 SeaStar 对比，体现“它属于哪一类框架”的讨论。 • 持怀疑或批评态度。`feverzsj` 质疑异常展开时切换任务可能不具备异常安全；`bbkane` 注意到基准测试依赖已归档的 MinIO，质疑后续基准可信度；`znnajdla` 则讽刺这类设计是在“重新发明 Erlang/Elixir VM 与 OTP”。 补充讨论：争议焦点主要在三点：这类库到底是新突破还是旧思路重演；它更适合通用 async I/O 还是特定 CPU 递归场景；以及实现细节上是否足够安全、基准是否可靠。
