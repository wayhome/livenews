A skyscraper that could have toppled over in the wind (1995)

作者: georgecmu | 评分: 47 | 评论数: 14 | 发布时间: 2025-06-15 15:40
文章摘要

1978年6月，著名结构工程师威廉·勒梅苏里耶接到一名工程学生的电话，学生质疑他设计的花旗集团中心大厦的柱位置是否错误。勒梅苏里耶耐心解释，由于教堂位置限制，柱子设在大楼每边中心而非角落，以悬挑结构让出教堂空间，并且这种设计能有效抵御斜向风力。他本想向学生展示这一设计的精妙，但在后续验证中意外发现，大楼在45度风向下的支撑强度不足。这一发现促使他采取紧急补救措施，最终避免了一场潜在灾难。

How fast can the RPython GC allocate?

作者: todsacerdoti | 评分: 25 | 评论数: 3 | 发布时间: 2025-06-15 19:55
文章摘要

本文介绍了作者对RPython垃圾收集器（GC）对象分配速度的基准测试过程。作者编写了一个简单的RPython程序，通过循环创建对象来测量分配速度。为了避免静态优化移除分配代码，作者使用了一种技巧，保持两个对象同时存活。基准测试包括初始化和不初始化对象字段两种情况。 在64位架构下，每次分配大约需要16字节。测试结果显示，未初始化字段时，分配速度为34.348 GB/s，初始化字段时为29.692 GB/s。相比之下，使用Boehm GC的版本速度较慢，未初始化和初始化时的速度分别为1.532 GB/s和1.538 GB/s，这是因为Boehm GC使用保守的栈扫描，无法移动对象。 作者还使用`perf`工具获取了更详细的性能统计数据，结果显示RPython GC在循环中达到了每周期超过5条指令的效率。这表明RPython GC在对象分配上的性能表现相当出色。

评论摘要
主要讨论点：不同内存分配器（allocator）的性能比较，包括在特定硬件上的分配速度、指令数量以及与传统分配器（如malloc/free）的对比。 不同观点： • **Kragen的观点**：Kragen指出，在CF Bolz的AMD Ryzen 7 PRO 7840U机器上，每个纳秒有1-2次分配，每次分配大约11条指令。这比Kragen自己的C语言分配器kmregion快2-4倍。Kragen的分配器在快速路径上也有类似数量的指令，但他测试的硬件较慢，并且测试的是16字节初始化对象且没有垃圾回收（GC）。kmregion的速度大约是malloc/free的10倍，但他并不强烈推荐使用kmregion，因为该工具从未被用于任何重大项目，只是作为一个概念验证。 • **pizlonator的观点**：pizlonator认为，CF Bolz的分配器比Boehm快，并不是因为保守栈扫描（conservative stack scanning），而是因为使用了不同的算法。他指出，可以通过保守栈扫描来移动对象，JavaScriptCore曾使用过这种方法。最快的非移动收集器（non-moving collectors）在分配速度上可以与最快的移动收集器（moving collectors）相媲美。他提到了JavaScriptCore的bump'n'pop分配器、Fil-C的SIMD turbosweep方法以及Immix方法等不同实现方式。 • **forrestthewoods的观点**：forrestthewoods对11指令和2.1周期每次分配的度量表示怀疑，认为这不符合常理。他引用自己几年前的一个基准测试，p95为25纳秒，而p99.9则在几十微秒的范围。他认为“GC占用2%的时间”可能对结果有很大影响，并表示需要看到真实的工作负载才能相信这些数据。 补充讨论： • 争议的焦点在于分配器的性能指标是否可信，尤其是对于极端优化场景下的纳秒级分配速度，部分参与者表示怀疑。 • 不同分配器的算法实现方式被讨论，包括保守栈扫描、对象移动、bump'n'pop和SIMD turbosweep等方法的优劣。 • 硬件对性能的影响也被提及，不同测试环境下的结果可能会有显著差异。

An origin trial for a new HTML element (2024)

作者: tentacleuno | 评分: 71 | 评论数: 29 | 发布时间: 2025-06-15 10:54
文章摘要

Chrome的权限团队正在试验一种新的HTML 元素，作为声明式请求权限的方法，以解决命令式请求权限带来的问题。目前，网页应用通过命令式方法请求权限，例如使用Geolocation API请求用户位置，或通过Notification.requestPermission()请求通知权限。然而，这种方式会导致“权限垃圾信息”问题，即网站在用户未交互时就弹出权限提示，影响用户体验。 浏览器通过要求用户手势（如点击）来缓解此问题，但这并不总是有效。此外，权限提示常显示在不易察觉的位置，且用户一旦拒绝权限，重新启用较为困难。 新的元素旨在通过声明式方法简化权限请求流程，目前正在Chrome 126中进行初步试验，目标是实现标准化。这将帮助开发者更好地管理权限请求，提升用户体验。

评论摘要
主要讨论点：Google提出的元素及其在浏览器中的实现和标准化问题 不同观点： • **支持观点**：有人认为该提议解决了网站通过虚假提示获取权限的问题，并将权限提示移到页面内容中，由浏览器控制，减少了网站对用户的干扰。这被认为是一种更好的模型，有助于避免网站滥用权限提示。 • **反对观点**：一些人认为该提议绕过了标准流程，可能带来新的问题，例如点击劫持攻击。还有人担心这会改变权限提示的方式，使提示成为用户体验设计的一部分，而非浏览器控制，这可能导致用户在视觉上受到误导。 • **对Google动机的质疑**：有评论质疑Google推动此提案的动机，认为Google可能从中获得商业利益，例如通过减少广告屏蔽能力来保护其广告业务。还有人担心该提案可能使用户更难明确地拒绝权限。 补充讨论： • **技术实现问题**：有评论指出该元素在技术实现上的难点，例如如何防止点击劫持攻击，以及在元素上叠加其他元素可能导致的漏洞。还有人担心浏览器团队将面临大量的维护问题。 • **用户体验问题**：一些评论认为该元素的样式限制过于复杂，可能会导致用户难以区分真假权限提示。同时，有人提出了一种替代方案，即通过一种不可完全自定义但可视化的元素来显示权限信息，以提高用户理解和安全性。 • **争议焦点**：提案中的权限提示方式及其对用户的安全性和易用性影响是争议的主要焦点。特别是如何在提供便利的同时，避免用户被误导或被迫授予过多权限。 通过这些讨论，可以看出各方对于新提案的潜在影响存在不同看法，主要围绕安全、用户体验和商业动机展开。

How easy is it for a developer to "sandbox" a program?

作者: zdw | 评分: 58 | 评论数: 17 | 发布时间: 2025-06-11 16:57
文章摘要

本文讨论了2025年开发者如何通过源代码对程序进行沙盒化，限制其对系统资源的访问。沙盒化是指通过代码限制程序可用的系统资源，例如使用`chroot(2)`将根文件系统更改为空目录以防止程序修改系统文件。现代操作系统提供了更多限制资源的方法，包括Linux、OpenBSD和FreeBSD等。文章比较了这些系统中可用工具的文档长度和使用示例的复杂度，以评估实现沙盒的难易程度。理想情况下，沙盒应限制程序仅能访问已打开的文件描述符和内存，禁止其他资源访问。文章还以`openssh-portable`为例，分析了其维护历史和安全实施的难度。最后，文章呼吁开源社区贡献更多数据以完善调查。

评论摘要
主要讨论点：不同平台和应用的沙盒机制及其存在的问题 不同观点： • **Defletter**：认为当前的沙盒和权限系统不够细致。以Discord和Android为例，指出用户需要给予应用过多权限才能执行简单操作，如访问文件或使用相机。他质疑这些系统是否真正有效，因为一旦应用获得权限，就可以随意访问资源。 • **simonw**：对macOS上的沙盒工具被弃用但仍广泛使用的情况感到沮丧，期望有一个简单、文档齐全的方式来限制二进制文件的资源访问和网络请求。 • **codedokode**：指出Linux上的沙盒实现不完善，很多应用无法被有效限制。认为虚拟机是更可靠的解决方案，并提到Flatpak的局限性。 • **PhilippGille**：提到Deno和WebAssembly作为沙盒化运行JavaScript和WebAssembly的示例，强调其在文件系统和网络访问上的显式权限控制。 • **Joker_vD**：认为是否对程序进行沙盒化处理应该是用户而非开发者的责任，用户有权决定如何运行程序。 • **godelski**：建议使用systemd的service或nspawn来实现程序的沙盒化。 • **petermcneeley**：指出Chromium有详细的沙盒机制，并提供了源代码链接。 • **hdjrudni**：关心能否在沙盒中运行完全不受信任的代码，并限制其网络和文件系统访问及资源使用。 • **jbverschoor**：认为只要开发者标记所有权限且在分发层面进行检查，具体实现细节不重要。 • **user_7832**：询问Windows平台上的有效沙盒方法，认为Hyper-V不适合频繁安装软件的场景。 • **ForHackernews**：认为沙盒化应由操作系统和用户处理，而非应用开发者。 • **charcircuit**：指出Android自动处理应用沙盒，认为如果需要开发者手动实现，大多数人不会去执行。 • **smartaz42**：提到Cosmopolitan作为一个简单的沙盒解决方案。 • **nesarkvechnep**：推荐Capsicum与Casper结合使用，认为其功能强大且灵活。 • **ZeroConcerns**：指出讨论中未区分协作式和未经修改的程序，认为在实际应用中开发者未必会使用或部署复杂的沙盒机制。 补充讨论： - 讨论中多次提到Android和iOS在沙盒机制上的成熟度较高，而Linux和macOS则存在较多问题。 - 用户和开发者对沙盒机制的期望不同，用户更关注实际使用中的安全性和便利性，而开发者则可能更在意实现的复杂度和必要性。 - 提到了一些特定技术如Flatpak、Deno、WebAssembly、Capsicum等作为可能的解决方案，但各有其局限性和适用场景。 - 虚拟机被认为是当前一种可靠的沙盒解决方案，但设置复杂度较高。

CI/CD Observability with OpenTelemetry Step by Step Guide

作者: ankit01-oss | 评分: 110 | 评论数: 8 | 发布时间: 2025-06-11 12:42
文章摘要

本文介绍了如何使用OpenTelemetry（OTel）实现对CI/CD管道（特别是GitHub Actions）的可观察性。OpenTelemetry是一个开源的可观察性框架，能够以供应商无关的方式收集 traces、metrics 和 logs。通过配置 OTel，可以捕捉 CI/CD 管道的遥测数据，提供端到端的可见性、性能优化、错误检测与调试以及依赖分析等优势。 文中详细说明了如何使用 OTel 的 GitHub Receiver 来接收 GitHub 工作流事件并将其转化为 trace 数据，以及如何通过 API 抓取指标。具体步骤包括在 GitHub 配置 webhook、设置访问令牌以及安装和配置 OTel Collector。最终，通过 OTel 可以统一监控管道运行情况，提升调试效率。

An Introduction to the Hieroglyphic Language of Early 1900s Train-Hoppers

作者: squircle | 评分: 42 | 评论数: 6 | 发布时间: 2025-06-15 19:55
文章摘要
