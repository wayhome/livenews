AbsenceBench: Language models can't tell what's missing

作者: JnBrymn | 评分: 250 | 评论数: 20 | 发布时间: 2025-06-20 22:26
文章摘要

文章介绍了一个名为AbsenceBench的基准测试，用于评估大型语言模型（LLM）识别缺失信息的能力。尽管LLM在识别意外信息方面表现出色，但在识别明显遗漏的信息时仍存在困难。AbsenceBench通过数值序列、诗歌和GitHub拉取请求三个领域，要求模型在给定原始和编辑上下文的情况下，识别文档中被故意删除的部分。实验显示，即使是最先进的模型，如Claude-3.7-Sonnet，在处理平均5K tokens的上下文时，F1得分也只有69.6%。分析表明，这是由于Transformer注意力机制难以关注文档中的“空白”，因为这些缺失不对应于任何可被注意的特定键。研究揭示了模型在某些任务上的超人表现与在识别缺失信息任务上的意外崩溃之间的紧密关系。

评论摘要
主要讨论点：LLM（大型语言模型）在识别信息缺失和处理图像旋转等任务中的表现及其局限性 不同观点： • birdfood 分享了 Claude 模型在识别 Kanizsa 三角形图像时的表现差异：在未旋转时能正确识别，旋转后无法正确识别。这引发了对模型视觉处理能力的讨论。 • cs702 提到即使是最新模型在识别上下文变化时的表现也较差，并引用了作者关于 Transformer 注意力机制无法处理被移除 tokens 的观点。 • yousif_123123 提出三个观点：首先，质疑为何 LLM 无法接近识别缺口位置；其次，指出较短输入更难处理的现象；最后，讨论了推理模型在处理此类任务时的优势，并提出是否存在更多未被识别的智能方面。 • XenophileJKO 认为无法检测未分类遗漏是预料之中，因为注意力机制需要明确的目标，而检测遗漏需要比较完整上下文。 • OsrsNeedsf2P 对新的基准测试表示兴奋，认为这是正确方向的推进。 • kadonoishi 认为检测缺失是高级神经任务，并质疑 LLM 是否缺乏这种能力，这可能是生物特有的能力。 • yandie 分享了视觉模型在处理单个图像和翻转图像时的表现差异，发现模型在翻转图像时表现较差。 • pkoird 询问是否有文档记录 LLM 擅长和不擅长的任务。 • b0a04gl 认为 LLM 无法检测缺失是架构上的遗漏，因为模型假设输入是完整的，建议需要训练目标和输入编码来处理缺失情况。 • itsgrimetime 提出使用 diff 工具可能解决部分问题，但承认这并非研究重点。 • ThrowawayTestr 和 obscure-enigma 都提到使用外部工具（如 diff 工具）或更复杂的测量方法来处理和评估 LLM 的表现。 • TZubiri 提出使用 OpenAI 提供的 logprobs 方法来测量响应中的不确定性。 • AlienRobot 分享了 ChatGPT 处理随机输入的例子，指出 LLM 无法真正识别“未知”，而是将所有输入归类。 补充讨论： • 讨论中涉及到 LLM 在处理缺失信息时的基本架构限制，以及可能的改进方向，如使用外部工具或调整训练目标。 • 视觉模型的表现和其在不同任务中的局限性也被多个评论者提及，特别是旋转图像处理的问题。 • 对 LLM 是否具备处理缺失信息的能力及其在智能任务中的表现存在争议，部分评论者认为这是生物特有的高级能力。 • 对新的基准测试和 LLM 评估方法的开发表示了积极态度，认为这是推动模型改进的重要步骤。

Chromium Switching from Ninja to Siso

作者: hortense | 评分: 109 | 评论数: 12 | 发布时间: 2025-06-18 08:49
文章摘要

Chromium的构建系统正在从Ninja迁移到Siso，这一更改已对Google内部开发者完成，现扩展到外部贡献者。外部开发者无需手动更改，继续使用`autoninja`即可，系统将在下一次运行`gn clean`后自动使用Siso。若遇到问题，可设置`use_siso=false`以暂时切回Ninja。Ninja和Reclient将在9月底不再支持，建议在此之前完成迁移。Siso旨在支持远程执行，并正与多个远程构建服务提供商确认兼容性。如有问题，可通过Slack、Chromium Issue Tracker或邮件联系。

评论摘要
主要讨论点：Chromium项目引入新的构建工具Siso及其与现有工具（如Bazel、Ninja）的关系 不同观点： • Intexpress认为，Siso使用Starlark（Bazel的构建语言），可能是Chromium最终使用Bazel的过渡步骤。这暗示Siso可能是为了逐步引入Bazel而设计的中间工具。 • RainyDayTmrw对Chromium需要自定义构建系统表示惊讶，并质疑为何不直接使用Google已有的Bazel，而是开发新工具Siso，并认为新工具名称中还引用了Bazel。 • Ahartmetz批评Chromium团队没有采用已知的解决构建时间过长问题的方案（如物理代码设计），而是通过新工具来解决，暗示这可能是为了追求表面成果。 • Jefftk指出这是Chromium的第四个构建系统（前三个为Scons、Gyp、Ninja），对频繁更换工具表示关注。 • Pjmlp质疑Siso是否只是又一个“非我发明”（NIH）综合症的产物，并指出Ninja和CMake是C++20模块构建的唯一方式，认为Chromium可能不会采用新的工具。 • Txdv询问Siso提供了哪些Ninja不具备的功能，质疑Siso的必要性。 • Operator-name提供了Siso的官方链接，指出Siso与Ninja兼容，但针对Chromium的特定用例进行了优化和调优。 • Mrlonglong提到Siso增加了对Go语言的依赖，暗示这可能带来新的复杂性。 • Kookamamie询问Siso是否可以作为Ninja的通用替代品，是否能用于一般的Ninja项目构建。 • Charcircuit猜测AOSP（Android开放源代码项目）是否也会迁移到Siso，认为Siso作为Ninja的替代品，迁移成本可能较低，并且提到之前Bazel的迁移计划被取消。 补充讨论： • Kosolam直接批评负责Siso的Google开发者不称职，暗示对该工具的开发不满。 • 讨论中多次提到构建时间过长的问题，以及对现有成熟解决方案未被采用的失望。 • 对Siso与Ninja的兼容性、特定优化及其在不同项目中的应用前景存在疑问和争议。 争议焦点： • 是否需要开发新的构建工具Siso，还是可以直接使用现有的Bazel或Ninja。 • Siso是否真正解决了Chromium构建中的关键问题，还是只是增加了不必要的复杂性。

文章摘要

本文介绍了如何使用记忆化（memoization）技术在Lean中解决一个动态规划问题，并验证其正确性。问题名为“Bytelandian金币问题”：给定一枚金 coin n，它可以被兑换为 n/2、n/3 和 n/4 三个整数金 coin（向下取整），也可以直接按1:1兑换为美元。目标是计算这枚金 coin 能换取的最大美元数。 解决方案采用递归关系定义：当 n ≤ 8 时，直接兑换为 n 美元；否则，选择 n 与 n/2、n/3、n/4 兑换后总和的最大值。为了优化计算，采用记忆化技术缓存子问题结果。 文中首先给出了直接递归实现作为规范，随后展示了记忆化实现，利用哈希表缓存子问题结果。最后，提出正确性证明的挑战，即证明记忆化实现与规范实现结果一致。证明的难点在于确保哈希表正确存储和查询子问题结果。文章邀请读者尝试证明，并指出证明中的关键在于理解数据结构的不变性。

评论摘要

Wikimedia DNS

文章摘要

Wikimedia DNS是一个由维基媒体基金会Site Reliability Engineering (SRE)/Traffic团队运行和管理的公共DNS解析服务，支持DNS-over-HTTPS (DoH)和DNS-over-TLS (DoT)协议。该项目旨在通过加密DNS查询来防止对维基媒体项目及其它网站的监视和审查。传统DNS查询未加密，易被第三方观察和拦截，导致隐私风险和内容审查。DoH和DoT通过加密DNS查询和响应来防止此类问题。Wikimedia DNS目前处于小规模测试阶段，其可靠性和未来可用性尚未保证，但其目标是为维基媒体社区提供更安全的网络连接。

评论摘要

Mathematicians hunting prime numbers discover infinite new pattern

作者: georgecmu | 评分: 115 | 评论数: 11 | 发布时间: 2025-06-19 03:28
文章摘要

数学家们通过整数分拆的概念，发现了一种新方法来识别质数，并将数学的两个领域意外地联系起来。质数是大于1且仅能被1和自身整除的数，识别小质数较容易，但随着数变大，识别质数的难度急剧增加。美国弗吉尼亚大学的数学家Ken Ono及其同事利用分拆理论，证明质数是特定多项式方程的解，这些方程被称为丢番图方程。这一发现为质数提供了无限多种新定义，并揭示了分拆理论在检测质数方面的强大应用。该研究发表于《美国国家科学院院刊》，被认为是科学卓越性和原创性的代表。
