Goiânia Accident

作者: ycollet | 评分: 5 | 评论数: 2 | 发布时间: 2026-08-06 21:12
文章摘要

1987年9月13日,巴西戈亚尼亚市发生严重放射性污染事故。一台被遗弃在废弃医院的放射治疗设备被盗贼发现,设备内含有约93克高放射性铯-137。盗贼和废品场主人用工具打开设备,暴露了铯-137晶体。废品场主人Devair Ferreira将这些发光的晶体带回家,与家人和邻居分享,导致多人接触放射性物质。 事故造成4人死亡(包括Ferreira的两名家人和两名员工),约112,000人接受检查,249人被确认受到污染。清理行动中需要移除多处表层土壤并拆除数座房屋。该事故被《时代》杂志和国际原子能机构列为世界最严重的放射性事故之一。

Celld: Self-hosted, distributed Durable Objects

作者: calvinfo | 评分: 267 | 评论数: 17 | 发布时间: 2026-08-05 16:50
文章摘要

celld 是一个开源守护进程，允许在自有机器上运行 Cloudflare Workers 和 Durable Objects。核心特点包括：每个对象是独立的 SQLite 数据库，通过用户拥有的 S3 兼容存储桶进行状态复制和节点协调，无需控制平面或共识服务。系统采用对象存储的 compare-and-swap 机制确保同一时间只有一个节点拥有某个单元，避免共享数据库的竞争问题。每个节点嵌入 V8 引擎执行代码，持续将 SQLite 数据库复制到存储桶。当单元迁移或唤醒时，新所有者从存储桶恢复数据库并继续执行。空闲单元可休眠以节省资源。系统提供命令行工具和 Docker 容器两种部署方式，支持 AWS S3 及其他兼容服务。

评论摘要
主要讨论点：Deno 团队推出的 celld（支持自托管 durable objects 的技术）引发了关于技术应用、AI 对开源影响以及架构设计的多方面讨论。 不同观点： • **AI 对开源贡献的影响存在分歧**：sakesun 引用某项目禁用 PR 的声明，担心 AI 工具让低质量、缺乏上下文的大规模修改泛滥，增加维护者负担；ironqcold 则认为 AI 只是让垃圾贡献更容易产生，优质贡献者的价值反而更高，AI 本身不会杀死开源。 • **对技术价值的认可**：khalidx、dzonga、myshapeprotocol 等积极评价 durable objects 概念的价值，认为"每个对象是自己的 SQLite 数据库"这一抽象简洁而强大，支持自托管和去中心化是重要进步。jumploops 分享了实际应用案例证明其可行性。 • **技术对比需求**：多位评论者希望了解 celld 与其他技术的区别，包括 Cloudflare workerd、Temporal、Restate、Azure Durable Functions 等，meowtimemania 特别希望看到性能基准测试。 • **架构可靠性质疑**：jiveturkey 对依赖 S3 作为底层存储表示担忧，质疑正确性是否过度依赖黑盒服务，希望看到更自包含的方案。 补充讨论：jauntywundrkind 详细分析了技术时机和架构细节（V8 隔离、低开销运行时），hhthrowaway1230 和 vmg12 提出了本地运行和 spot 实例支持等功能需求。

Prime Agent: A self-improving RLM agent

作者: Xeophon | 评分: 238 | 评论数: 18 | 发布时间: 2026-08-05 21:11
文章摘要

Prime Agent 是一个开源的自我改进编码代理系统，基于两个核心抽象构建：递归语言模型（RLM）和持续性线束（Continual Harness）。RLM 将上下文视为变量，通过持久的 IPython REPL 实现子代理委托和工具调用，使代理能够处理任意长的会话而不丢失历史信息。Continual Harness 允许代理动态创建、修改和删除自身状态（提示、技能、内存和子代理），结合代理间通信实现跨会话协作。系统提供文本界面和代理视图，支持会话的附加、分离和恢复，所有历史记录存储为 JSONL 文件。Prime Agent 可与现代前沿模型配合使用，适用于编码辅助、长期自主评估和研究协作。

评论摘要
主要讨论点：AI代理的自我改进系统（harness）的设计与实用性 不同观点： • **harness必要性存疑派**：认为随着基础模型能力提升，复杂的harness系统已不再必要，甚至可能限制模型推理能力。有用户分享实践经验，表示简单的.md文件存储上下文就能满足需求 • **实现质量批评派**：指出LLM生成的代码存在严重臃肿问题（单文件近万行、switch语句超千行），认为应该追求更小的代码库来引导自我改进。同时批评安装方式不规范、缺少卸载方法 • **经济可行性质疑派**：担心自我改进循环会消耗大量token，在当前经济模型下不可行。RL训练的harness工程也可能产生过多冗余代码 • **技术探索派**：对ARC-AGI-3基准测试表现感兴趣，好奇在其他基准和日常编程中的实际表现，希望看到具体任务的性能数据 补充讨论：核心争议在于"过度工程化"问题——复杂harness是否真正提升了模型能力，还是反而成为负担。多数评论倾向于认为简洁方案可能更优。
