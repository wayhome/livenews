Select FOR UPDATE considered harmful in PostgreSQL

作者: samokhvalov | 评分: 15 | 评论数: 1 | 发布时间: 2025-06-19 17:41
文章摘要

本文讨论了在PostgreSQL中使用`SELECT FOR UPDATE`可能导致数据库并发问题，尤其是在涉及外键约束时。作者解释了PostgreSQL如何使用不同类型的行级锁（如`FOR KEY SHARE`、`FOR UPDATE`、`FOR NO KEY UPDATE`等）来维护数据一致性。大多数情况下，`UPDATE`语句并不会使用`FOR UPDATE`锁，因为它们不会与外键引用的`INSERT`操作冲突。然而，不当使用`SELECT FOR UPDATE`会过度锁住行，阻止其他事务的`INSERT`操作，导致性能问题和死锁。作者建议开发者了解这些锁机制，避免在不必要的情况下使用`SELECT FOR UPDATE`，以减少并发问题。

评论摘要
主要讨论点：在数据库操作中，针对"SELECT FOR NO KEY UPDATE"与其他锁机制的选择和使用场景 不同观点： • 观点一（支持使用"SELECT FOR NO KEY UPDATE"）：Rickette建议在大多数情况下，除非需要删除行或修改关键列，都应该使用"SELECT FOR NO KEY UPDATE"。其主要论据是，这种操作可以避免不必要的锁竞争，同时保证数据的一致性，特别是在只读场景下。选择这种方法可以提高数据库的并发性能，因为它只对相关行加锁而不影响其他操作。 • 观点二（针对特定场景使用不同的锁机制）：部分开发者认为应根据具体场景选择不同的锁机制。例如，如果需要修改行的主键或删除行，"SELECT FOR NO KEY UPDATE"可能不够，需要更强的锁机制如"SELECT FOR UPDATE"。该观点强调锁机制的选择应基于具体的数据操作需求，确保数据完整性和一致性。 • 观点三（关注并发性和性能）：有开发者指出，使用"SELECT FOR NO KEY UPDATE"的优势在于它能减少锁的竞争，提升并发性能。特别是在高并发环境中，选择适当的锁机制对于系统性能至关重要。此观点的论据主要集中于系统性能优化，认为在非必要情况下不应使用更强的锁。 补充讨论： • 争议焦点：争议的焦点在于锁的强度与性能之间的平衡。部分开发者认为应尽量减少锁的使用以提高并发性，而另一些开发者则认为应优先确保数据完整性，视具体操作需求选择锁机制。 • 使用场景的重要性：讨论中多次提到，选择何种锁机制应根据具体场景决定，不能一概而论。例如，在数据修改频繁的场景下，"SELECT FOR NO KEY UPDATE"可能不足以保证数据一致性，需要更强的锁。 • 实际操作中的权衡：部分开发者提到，在实际应用中，需要权衡锁的开销与数据一致性要求，特别是在大型系统中，错误的锁策略可能导致严重的性能瓶颈。

Double-Entry Ledgers: The Missing Primitive in Modern Software

作者: pgr0ss | 评分: 5 | 评论数: 0 | 发布时间: 2025-06-19 16:17
文章摘要

文章主要讨论了双 entries 记账模型在软件开发中的未充分利用，并介绍了一个名为 "pgledger" 的纯 PostgreSQL 实现。双 entries 记账包含几个核心概念：当前余额、余额变化的历史记录以及资金来源。这种模型通过原子性的记录确保数据的一致性和错误检查，同时提供审计日志功能。 文章以在线业务为例，展示了如何使用双 entries 记账来记录订单、付款和退款。通过这种方法，可以明确记录每个资金转移，并方便地回答如“我们还在等多少钱？”或“为什么余额不对？”等问题。相比传统单表记录方式，双 entries 记账能更清晰地追踪资金流动，减少自定义错误检查逻辑的需要。 总的来说，文章提倡在更多系统中使用双 entries 记账，以提高数据一致性和可追溯性。

本文讨论了如何为Retrieval-Augmented Generation (RAG) 系统（如Kapa）优化文档，使其既适合人类阅读，又能被AI有效处理。文档质量直接影响AI回答的准确性，低质量文档会导致AI生成错误答案。AI通过检索器、向量数据库和生成器三个主要组件处理文档，将内容分解为小块并存储，根据用户提问检索相关信息，最后生成回答。为了提高AI处理效果，文档应明确、自包含且上下文完整，避免隐含信息和不必要的关联。通过合理分块和结构化内容，可以提升AI的检索精度和回答质量。优化文档的技巧包括使用标准化的语义HTML等，以提高机器可读性。
