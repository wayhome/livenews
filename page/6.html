作者: p_stuart82 | 评分: 109 | 评论数: 7 | 发布时间: 2026-05-14 20:41
文章摘要

文章分析特斯拉Wall Connector Gen 3在24.44.3固件中新增的防降级机制：通过固件ratchet值拒绝旧版本。作者逆向发现bootloader不检查ratchet，仅更新流程检查；进一步利用分区表写入与擦除顺序缺陷绕过限制，使最新版设备仍可刷入旧漏洞固件并复现攻击。

评论摘要
主要讨论点：Tesla Gen 3 Wall Connector 的联网、固件控制与充电调度可靠性，以及其对用户成本和电网的影响。 不同观点： • 原帖观点：Wall Connector 一旦丢失 Wi‑Fi，可能导致充电计划失效、随机开关，尤其会影响分时电价用户；建议直接在车端设置充电定时，而不是依赖墙充。 • 反感 Gen 3 Wall Connector：有人批评其会持续创建无法关闭的 Wi‑Fi 热点（TeslaWallConnector_唯一ID），认为用户失去对设备的控制；还提到过去可降级固件绕过此问题，但可能已被 Tesla 封堵，并担心车辆可能通过充电线或 Wi‑Fi 强制更新墙充固件。 • 质疑购买必要性：有人认为直接使用 NEMA/烘干机插座加 Tesla 随车充即可，Wall Connector 像是“花钱买麻烦”，性价比不足。 • “降级固件不是黑客行为”观点：有人强调，车主主动降级固件以控制自己硬件不应被称为 hack；若攻击者能这么做，说明物理安全早已被突破。 • 安全与电网风险观点：有人担心 EV 充电器软件若被用户、黑客或 bug 修改，可能在电网不适合的时段满功率充电。以英国为例，1000万台 EV 每台 7kW 会接近/超过电网承载，甚至100万台同时充电也会增加约7GW负荷。 补充讨论：争议焦点集中在用户是否应拥有固件控制权、联网墙充是否必要，以及“个人设备自由”与“电网安全/集中管理”之间的冲突。

Welcome to the Strip Mining Era of OSS Security

作者: salsakran | 评分: 96 | 评论数: 19 | 发布时间: 2026-05-15 11:37
文章摘要

文章指出，随着LLM和编码代理能力提升，公开源码中的漏洞正被大规模、低成本地“批量挖掘”，导致安全报告激增且不少是真漏洞。短期内OSS维护者会面临更多告警和压力，但长期看，这种自动化扫描会帮助更快发现并修复问题，整体提升开源安全。

评论摘要
主要讨论点：AI/LLM辅助漏洞发现是否会加剧开源维护压力，以及这究竟是“安全灾难”“正常修复过程”还是安全市场演化。 不同观点： • 漏洞公开是好事：ahlCVA、xbar认为代码本来就有缺陷，发现并披露只是面对事实；把漏洞挖掘称为“掠夺”是倒退，真正令人困惑的是有人宁愿保留0day。类似数学证明被找出错误，应庆幸未来不再建立在错误前提上。 • 开源维护者不应被默认要求无偿救火：Macha、adamtaylor_13、hrjriritifif强调，用户和安全公司免费使用OSS，却期待维护者周末立刻修复并提供支持是不合理的；这是志愿劳动，若要SLA和紧急响应应付费。 • AI会扩大攻击面和发现速度，闭源也难幸免：_alternator_、mtlynch指出LLM可辅助反编译和理解二进制，闭源软件同样面临风险；开源只是更容易被扫描。gmuslera补充，闭源若源码泄露，漏洞可能长期暗中存在。 • 商业化安全投入会变得更重要：mtlynch认为不设或低额bug bounty的产品难吸引善意研究者，却会吸引攻击者；他举Kagi UXSS仅100美元，而Firefox/Chrome同类漏洞奖励达数千到上万美元为例。cyrusradfar认为企业需要更多人工安全投入、流程管控，并可通过local-first减少云端暴露。 • 这可能是技术成熟后的“二级安全市场”形成：likesHumidity类比2017年S3误配置事件，AWS推出Block Public Access、CSPM市场成熟；AI层也可能出现类似治理与防护市场。OSS承压结果取决于制度支持：FFmpeg获德国基金支持而改善，Ingress-Nginx因维护不可持续退役。 • 乐观派认为风暴会趋缓：marginalx认为短期内漏洞报告会激增，商业开源可能借“安全靠隐蔽”缓冲，但真正开源无法如此；长期看报告会平台化、回到可管理节奏。 • 怀疑或反对声音：krupan认为这是AI炒作；ryanackley提醒同时存在大量“AI垃圾漏洞报告”，如Turso因被无用报告淹没而关闭bug bounty。 补充讨论：争议焦点在于“漏洞发现速度提升”应被视为安全进步，还是对无偿维护体系的不可持续压榨；以及谁应为修复成本买单。

Mullvad exit IPs are surprisingly identifying

作者: RGBCube | 评分: 372 | 评论数: 24 | 发布时间: 2026-05-15 02:35
文章摘要

文章指出 Mullvad VPN 会按 WireGuard 公钥确定性分配服务器出口 IP，而非每次随机。作者测试 9 台服务器、3650 个公钥后发现，理论上组合巨大，实际仅出现 284 种。原因可能是 Mullvad 用公钥作种子调用 RNG，并以各服务器 IP 池大小为上限，导致不同服务器分配到相近百分位的 IP。这样多个出口 IP 组合可能成为识别用户的指纹风险。

评论摘要
主要讨论点：Mullvad 被曝不同服务器出口 IP 分配存在可关联性，可能形成用户级指纹；讨论集中在其严重性、VPN匿名预期、修复与披露流程。 不同观点： • Mullvad回应：部分行为是有意设计、部分不是；成因与原文描述不完全一致，已在部分基础设施测试补丁，并会重新评估“隐私 vs 用户体验”的取舍；同时呼吁研究者发布前先通知厂商。 • 风险严重派：认为这种跨服务器稳定映射像“情报机构会设计的VPN”，可帮助论坛管理员识别封禁用户小号；元数据仍会泄露身份。 • 质疑论证派：有人指出“>99%同一人”的说法统计上不严谨；重叠区间只能排除大多数用户，不能直接得出个体识别准确率。 • VPN定位派：认为VPN本就不等同Tor，不应期待对访问网站匿名；需要强匿名应使用Tor，且Tor也可能被出口节点攻击。 • 工程折中派：单服务器内稳定IP有用户体验价值，例如固定服务可用性；但跨服务器相关性应修复，如用 user key + server id 随机化。 • 信任Mullvad派：有评论称Mullvad过往在地理定位数据上较诚实，相信会修复。 • 站点治理派：有人认为网站运营者可利用此属性执行封禁；也有人提到持续维护VPN IP封锁列表，服务方与用户之间是“猫鼠游戏”。 补充讨论：有人追问作者是否提前联系Mullvad；还有人疑惑第三方客户端为何不能像官方客户端一样轮换WireGuard key。

主要讨论点：围绕 GGUF 作为开源 AI 模型格式的优势、缺陷及未来改进展开。 不同观点： • 支持 GGUF 的“一文件”理念：Philpax 和 badsectoracula 认为 GGUF 本应把模型相关内容集中在单文件中，投影模型被拆出去违背初衷；视觉模型需额外下载文件带来困惑。 • 肯定 GGUF/GGML 生态价值：uyzstvqs 强调 llama.cpp、whisper.cpp、stable-diffusion.cpp 等项目跨平台、跨硬件表现稳定，对开源 ML/AI 很重要。 • 认为 GGUF 并非唯一好方案：prashantk_ 表示 safetensors + metadata 文件也够用；Sharlin 指出图像生成领域模型长期就是单文件，safetensors 也能嵌入元数据，不一定需要 GGUF。 • 批评可读性与接口设计：amelius 讽刺某些模板格式比 XML 更难读；badsectoracula 不满 llama.cpp 中硬编码聊天格式，希望有真正的 Jinja2 模板解析接口，尤其支持 tool calling。 • 主要技术缺口：theapadayo 和 monocasa 都指出 GGUF 未存储完整计算图，只记录架构字符串和参数元数据，导致每种新模型架构都需消费端新增代码；建议用 DSL 描述模型图，或从 PyTorch 模块转换为 GGML ops。 • 其他讨论：sbinnee 认为 tool calling 格式会推动 LLM 向 agent 发展；halyconWays 提到 GGUF 命名与早期贡献争议；kenreidwilson 注意到发布日期疑似异常。
