C array types are weird

作者: signa11 | 评分: 120 | 评论数: 16 | 发布时间: 2026-05-25 05:05
文章摘要

这篇文章讨论了C语言数组类型的奇怪之处。主要问题包括： 1. **自动转换**：数组类型`T[n]`会自动转换为指针`T*`，指向首元素，但`sizeof`是例外。 2. **函数参数**：函数参数中的数组会被解释为指针，长度信息丢失，导致`sizeof`行为不一致。 3. **混淆性**：这种设计让初学者困惑——修改函数内的数组会影响外部，但结构体不会。 作者建议：数组应该像结构体一样按值传递，保留长度信息。如需指针行为，应显式写`&arr[0]`。这样能使语言更清晰易懂，避免隐式转换带来的困惑。 文章还对比了函数类型的类似行为，指出函数指针的处理方式虽相似但更一致。

评论摘要
主要讨论点：C语言中“数组与指针”的设计、历史成因、实际价值，以及它在多维数组、安全性和现代语言互操作中的问题。 不同观点： • **主张C缺少更安全的“切片”抽象**：Animats认为若C有slice，就能覆盖大多数“指向数组中间”的需求，且语义更合理；他还提到自己曾尝试给C补上slice，但受政治/生态阻力失败。the__alchemist也赞成把“集合抽象”和“裸指针/MMIO”分开，提到Rust FFI常把C指针API包装成`&[]`。 • **认为C的数组/指针设计虽怪，但有现实价值**：danborn26指出“数组衰变为指针”虽易坑新手，却让传参非常轻量。uecker补充说，`[static n]`和“指向数组的指针”写法虽难读，但能带来编译器警告和边界检查。 • **批评其在多维数组上尤其不直观**：alexey-salmin认为二维数组暴露出严重不对称性，`a[i][j]`既可能是连续内存，也可能是`char**`指向分散内存，内存布局和汇编表现完全不同，说明“数组≈首元素指针”在多维情形下失效。moktonar也强调`int x[n]`和`int *x`在内存布局上本质不同，尤其影响结构体定义。 • **从历史解释这种设计**：kazinator追溯到B语言，称“数组产生指针”原本在更早语言里是实际存在的隐藏指针机制，C是沿袭/简化了旧设计。fooker则认为C所处年代不能“没有数组”，因为当时Fortran主导，语言设计必须回应这种预期。 补充讨论： • 争议焦点在于：这是“简单高效的低层设计”还是“不合适且历史包袱重的抽象”。 • 其他评论多在调侃其怪异性，如`3[x] == x[3]`、`register`数组取地址的UB，以及“C很简单”的反讽。

文章摘要

What Is a Direct Attach Copper (DAC) Cable

作者: teleforce | 评分: 74 | 评论数: 11 | 发布时间: 2026-05-25 22:43
文章摘要

这篇文章介绍了DAC（Direct Attach Copper，直连铜缆）的基本概念和应用。DAC是一种两端带有模块的铜质双绞线缆，用于设备间的直接通信。文章解释了DAC的工作原理、分支DAC线缆（breakout DAC）的用途，以及DAC的传输距离限制（通常5米以内）。随着网络速度提升至100GbE以上，DAC线缆变得更粗更硬，灵活性降低。相比光纤，DAC的主要优势是成本更低，包括硬件成本和运营成本，因此在机架内短距离连接中仍广泛使用。

评论摘要
主要讨论点：在高速网络布线中，DAC、光纤、铜缆各自的优缺点，以及它们在机房/家庭网络中的实际适用性。 不同观点： • 支持DAC：认为DAC便宜、快、几乎不耗电，适合机柜内短距离连接，尤其ToR放中间时1–5米已足够；还能避免光模块转换和现场熔接的麻烦。有人补充，部分10GbE DAC甚至可“破解”跑25GbE。 • 支持光纤：认为光纤传输距离更远、发热更低，高速下比金属线更有优势；OM3/OM4和SFP+价格已较可接受，家用/实验室也值得上，且“隐形光纤”适合家庭走线。 • 偏向铜缆/质疑光纤维护性：有工程经验者指出，铜缆现场端接又快又稳定，而光纤端接/熔接更脆弱，受施工环境、器材质量和后续误操作影响大，失败率更高；不少客户虽偏爱光纤低时延和小体积，但后续常因维护问题回头改铜。 • 家庭升级实践派：有人因搬家和2.5Gbps FTTP接入，直接规划10G内网，二手购入SFP+交换机和网卡，体现“直接上更高规格避免后续瓶颈”的思路。 补充讨论： • 争议焦点在于：短距离场景选DAC还是光纤；核心比较是距离、发热、功耗、施工维护复杂度与整洁度。 • 还有人提醒DAC的实际问题：线缆较重、容易在整柜中形成“线团”；且两端EEPROM兼容性可能导致识别失败。 • 另有用户追问DAC是否具备电气隔离，说明其在工程安全层面也受关注。

Show HN: Posthorn, self-hosted mail gateway

作者: craigmccaskill | 评分: 66 | 评论数: 16 | 发布时间: 2026-05-27 04:26
文章摘要

Posthorn 是一个统一的自托管项目邮件发送网关。它作为单一中间层，连接你所有自托管应用（如 Hugo、Ghost、Gitea 等）与你选择的邮件服务商（Postmark、Resend、Mailgun、AWS SES 等）。 **核心价值**：避免每个应用单独集成邮件服务，统一管理 API 密钥和配置。 **三种接入方式**： 1. HTTP 表单（联系表单、注册） 2. HTTP API（Worker、定时任务） 3. SMTP 监听器（Ghost、Gitea 等 SMTP 应用） **特点**：单个 Go 二进制文件，单个 TOML 配置，支持速率限制、蜜罐防护、授权认证。解决云主机（DigitalOcean、AWS Lightsail 等）阻止 SMTP 出站的问题。 **非功能**：不是邮件服务器、不存储邮箱、不做营销邮件、不提供 Webmail 界面。

评论摘要
主要讨论点：这个项目究竟是“自托管邮箱服务器”还是“自托管事务邮件网关”，以及自建邮件相关的可行性、需求和现实问题。 不同观点： • 标题/定位不准确：多位评论者认为“self-hosted mail”会误导，项目更像“自托管事务邮件网关”而非完整邮件服务器；因为它主要处理邮件投递/API/SMTP，而不是完整收发邮箱体系。对此还有人补充：“既然支持 SMTP 收发，就很难说不是 mail server”，争议焦点在“mail server”的定义边界。 • 偏好更简单、职责单一的方案：有人提到用 nullmailer 做本地 sendmail 兼容转发，稳定可靠；但不希望同一二进制同时处理 HTTP(S) 表单入口和邮件提交，认为功能耦合过多。 • 认可项目方向并期待扩展：有人觉得这是不错的起步，拿 Apprise 做类比，询问未来是继续专注邮件，还是扩展到更多通知服务。 • 自建邮件有现实门槛：有人想尝试，但担心 VPS/DNS/IP 被拉黑，认为邮件是 sysadmin/DNS/服务器里最复杂的领域，也在比较继续用托管邮箱还是迁移到可 SSH 自主部署的服务。 • 自建邮件仍有明确需求：有人反驳“没人想自建邮件”，表示出于隐私、个人控制权或脚本 API 发送需求，个人邮箱自托管很有价值；也有人分享实际方案，如 cloudflared tunnel + Brevo，或使用 Postal。 补充讨论： • 有人指出像 SES 这类服务可走 443/TLS，暗示可绕开部分投递/端口限制。 • 还有文化向提问：Posthorn 是否致敬《万有引力之虹》中的 W.A.S.T.E.。
