Show HN: Selector Forge – browser extension for AI-generated resilient selectors

作者: ahmadilaiwi | 评分: 31 | 评论数: 2 | 发布时间: 2026-06-22 14:21
文章摘要

这篇文章介绍了 Selector Forge——一个浏览器扩展工具（支持Chrome和Firefox）。它帮助用户在网页上直接选取元素，自动生成可靠的CSS或XPath选择器。 **核心工作原理：** 1. 用户在页面上选择目标元素 2. 扩展捕获DOM快照并发送到后端 3. AI后端生成候选选择器 4. 扩展在真实DOM中重新验证每个候选项 5. 只返回经过验证的选择器 **主要特点：** - 支持单元素选择和列表选择两种模式 - 浏览器DOM是真实性验证的最终裁判，AI只负责提议和排序 - 适用于编写端到端测试、构建爬虫和页面自动化 该项目使用TypeScript开发，包含完整的单元测试、浏览器测试和端到端测试体系。

评论摘要
LLMs struggle with generating good selectors by default for several reasons: **Lack of runtime context** - LLMs don't see the actual rendered DOM structure, dynamic IDs, or how elements appear in practice. They guess based on common patterns rather than inspecting what's actually there. **Fragility vs specificity tradeoff** - Without seeing the page, they can't balance between overly specific selectors (that break with minor changes) and overly generic ones (that match multiple elements). Good selectors require understanding the page's structure and stability patterns. **Dynamic content blindness** - Modern web apps generate IDs dynamically, use framework-specific attributes, or rely on data attributes. LLMs can't distinguish between stable semantic attributes and volatile generated ones without page inspection. **No feedback loop** - When a human writes a selector, they test it immediately and see what breaks. LLMs generate based on probabilities from training data, not real-time validation against the target page. **Context window limitations** - Including full HTML in prompts is often impractical. Without complete DOM context, LLMs resort to generic patterns that may not match the actual implementation. The solution is usually: inspect the actual page first (via browser tools or programmatic scraping), then generate selectors based on real structure rather than assumptions.

Self-Harness: Harnesses That Improve Themselves

作者: jonnonz | 评分: 10 | 评论数: 0 | 发布时间: 2026-06-22 19:45
文章摘要

这篇论文提出了Self-Harness范式，让基于大语言模型的智能体能够自主改进其操作框架，无需人工工程师或更强外部模型的介入。该方法通过三个迭代阶段实现：弱点挖掘（从执行轨迹识别模型特定的失败模式）、框架提议（生成针对性的最小化修改方案）和提议验证（通过回归测试接受候选编辑）。在Terminal-Bench-2.0基准测试中，使用三个不同模型族的实验显示，Self-Harness将测试通过率分别从40.5%提升至61.9%、23.8%提升至38.1%、42.9%提升至57.1%，证明了该方法能有效将模型特定弱点转化为可执行的框架改进。

UUID: NewV7() always generates a UUID with 7000 on browsers (Golang)

作者: mfrw | 评分: 36 | 评论数: 3 | 发布时间: 2026-06-22 08:59
文章摘要

这是一个 Go 语言的 bug 报告。在 js/wasm 目标平台上，`uuid.NewV7()` 函数生成的 UUID 总是在特定位置包含 `7000`，而这部分本应包含随机字节。用户在 Go 1.27rc1 版本中发现，无论运行多少次，生成的 UUID 都会在版本号后出现固定的 `000` 模式（如 `019ee60f-29b3-7000-a12b-...`），这违反了 UUID v7 规范中应该填充随机数据的要求。该问题仅在浏览器/WebAssembly 环境中出现。

评论摘要
主要讨论点：UUID v7 生成器在浏览器环境下的时间戳精度问题及其修复方案 不同观点： • **JdeBP的技术分析观点**：指出问题根源在于时钟精度不足（浏览器仅支持毫秒级），当前修复方案虽然针对 `GOOS == "js"` 做了处理，但在时间戳唯一性检查时错误地将12位随机数据当作时间戳的一部分进行递增，需要进一步修正以正确处理毫秒精度的情况。同时提到多进程场景下计数器实现困难，现有实现回避了这个问题。 • **paulddraper的解决方案观点**：认为问题描述不完全准确，虽然 `Date.getTime()` 只有毫秒精度，但现代浏览器大多支持 `Temporal.Now.instant()` API，它可以提供更高精度。建议在支持的情况下优先使用 Temporal API，并保留 Date 作为降级方案。 • **OsrsNeedsf2P的批评观点**：批评维护者最初想以"按设计工作"为由关闭问题的做法，认为这是"只见树木不见森林"，忽视了实际存在的问题。 补充讨论：核心争议在于如何在浏览器环境正确实现 UUID v7 的时间戳和单调性保证，涉及平台兼容性、API选择和实现细节的权衡。
