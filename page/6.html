文章摘要

LogitLoom是一个用于探索指令模型和基础模型上**token轨迹树**的工具。用户可以通过指定API和模型来生成和扩展树结构，支持设置深度、最大子节点数和Top P等参数。工具提供可视化token概率信息，并允许将部分结果添加到预填充内容中以便后续生成。当前支持Deepseek-v3作为聊天模型API，以及Hyperbolic的405-base作为基础模型API，且API密钥仅在本地存储和使用。工具存在UTF-8字符处理问题，且目前未授权。开发上使用Bun进行打包和热更新。

Working on complex systems: What I learned working at Google

作者: 0xKelsey | 评分: 265 | 评论数: 18 | 发布时间: 2025-05-13 09:35
文章摘要

《The Coder Cafe：处理复杂系统》一文由Teiva Harsanyi撰写，讨论了复杂系统的概念以及在Google工作期间获得的见解。文章首先区分了“复杂问题”和“繁杂问题”：繁杂问题虽复杂但可预测并有结构化解决方案，而复杂问题则需要适应性和新颖的解决方案。例如，优化打车软件中的司机-乘客匹配属于繁杂问题，而Google的大规模机器学习基础设施则涉及真正的复杂问题。 文章进一步描述了复杂系统的五大特征： 1. **涌现行为**：系统整体行为无法通过单独分析其组成部分预测。 2. **延迟后果**：行动的后果可能不会立即显现，而是延迟出现。 3. **局部与全局优化**：优化某一部分不一定改善整体，有时甚至适得其反。 4. **滞后效应**：系统过去的状态继续影响其行为。 理解这些特征有助于识别和处理复杂系统，避免用解决繁杂问题的方法处理复杂问题，从而更有效地应对挑战。

评论摘要
主要讨论点：复杂系统和复杂性在不同领域中的应用与理解 不同观点： • **braza** 认为复杂性应区分可控的复杂性和环境/偶然的复杂性。前者如软件实现中的复杂性，开发者有较多控制权；后者如海运物流等领域，具有许多内在且难以解决的限制。他批评一些文章未做此区分，并指出谷歌等大公司面临的问题未必是最复杂的。 • **dmoy** 提到在谷歌，不可能的事情通常被视为困难但可解决，而简单的事情反而可能变得困难。这反映了一种自信，但也可能导致对问题难度的误判。 • **destring** 从数学背景出发，指出软件工程师缺乏系统建模的词汇，并推荐阅读《Thinking in Systems》一书以提高理解。 • **neilv** 强调自信在解决问题中的重要性，但同时警告这种自信可能演变为 arrogance 和 exceptionalism，忽视谦逊和事实。他提到需要尊重努力和过程，但也应警惕自我优越感。 补充讨论： • **RenThraysk** 和 **Pavilion2095** 提到技术文章中出现的技术问题（如cookie策略弹窗bug），虽然与主讨论点关系不大，但指出了技术实现中的实际问题。 • **quantum_state** 指出复杂系统的特性在物理学和生物学中已有数十年的研究，认为大组织或大代码库只是这些特性的另一个例子。 • **ggm** 反驳了两个迷思：复杂系统不一定是坏的，简单系统也不一定总是好的。例如，武装部队和DNA的复杂性有其必要性。 • **tunesmith** 讨论了复杂和复杂的定义，认为复杂系统常因未纳入外部因素而被误解。他还质疑是否存在具有“涌现行为”的真正封闭系统。 • **kossTKR** 认为许多中小型互联网项目中的问题（如异步编程中的调试困难）与复杂系统的行为有相似之处。 • **carom** 对文章中的语法错误持正面态度，认为这表明文章不是由LLM生成，显示出对生成式AI的某种不信任。 争议焦点： • 复杂性和复杂系统的定义与区分，特别是在实际应用中的理解和处理。 • 自信与谦逊在解决复杂问题时的平衡，以及如何避免自信演变为 arrogance。 总体来看，讨论围绕复杂系统的定义、实际应用中的挑战以及对自信与谦逊的反思展开。

I don't like NumPy

作者: MinimalAction | 评分: 261 | 评论数: 48 | 发布时间: 2025-05-15 16:05
文章摘要

文章讨论了作者对NumPy的一些不满和其在处理复杂数组操作时的局限性。虽然NumPy在处理简单矩阵运算时表现优雅，例如解决线性方程组，但当面对更复杂的数组操作时，它显得不够直观和易用。作者指出，NumPy缺乏一种理论来处理多维数组的复杂操作，用户常常需要使用一些晦涩的技巧，如插入新的维度（使用`None`）和复杂的广播机制。这些技巧不仅容易出错，而且代码可读性差。尽管有一些函数如`np.tensordot`可以简化部分工作，但其使用仍然复杂且不易理解。作者认为，NumPy在处理三维及以上数组时的表达能力不足，导致用户常常需要反复试验才能找到可行的解决方案。

评论摘要
主要讨论点：NumPy及其替代工具（如Xarray、Julia、PyTorch等）在处理多维数据时的优缺点，以及NumPy API的设计和使用体验。 不同观点： • **支持Xarray作为多维数据处理的更好选择**： - WCSTombs认为，对于多于两个维度的数组，Xarray是一个更好的选择。Xarray通过为维度命名，使得广播和自动对齐变得更容易，无需手动转置或添加哑轴。虽然Xarray在某些方面（如线性代数）功能不如NumPy全面，但可以轻松退回到NumPy，并通过辅助函数解决特定需求。 • **NumPy在多维数据处理上的不足**： - borsco和brosco指出，NumPy在处理多维数据时缺乏一致性和直观性，函数参数和操作方式不统一，导致需要频繁查阅文档。相比Matlab和Julia，NumPy的向量化操作不够直观，且对于特定维度操作需要重写函数。 • **从Matlab和Julia过渡到NumPy的困难**： - ChrisRackauckas和blululu提到，从Matlab过渡到NumPy会感到编程效率下降，需要花更多时间在“性能工程”上。Julia提供了更灵活的编程体验，可以根据需要选择向量化或循环，而不必为了性能而强行向量化。 • **NumPy类型和API设计的问题**： - vector_spaces指出NumPy中存在类型转换不一致和返回类型不统一的问题，例如`np.poly1d`的操作。这类问题在调试时非常麻烦。 • **NumPy与其他工具的互操作性问题**： - SirHumphrey提到Python数据科学生态系统缺乏标准化，不同库之间的数据格式转换需要大量样板代码。相比之下，Julia的各个库之间交互更好。 • **对NumPy API的复杂性和广播机制的批评**： - munchler和CreRecombinase批评NumPy API的设计过于灵活和模糊，导致掌握难度大。虽然这种灵活性使得入门容易，但精通却很难。CreRecombinase还提到，很多人试图让Python表现得像Fortran一样，这可能并不理想。 补充讨论： • **NumPy的性能问题**： - threeducks提到在使用`np.einsum`进行矩阵链乘法优化时，虽然性能有所提升，但仍不如朴素的循环实现。这表明NumPy在某些情况下的性能优化存在局限性。 • **NumPy的替代方案**： - 一些评论者提到使用其他工具如Torch、numpysane、gnuplotlib等来改善NumPy的使用体验。这些工具在特定领域可能提供更好的解决方案。 争议焦点： • **NumPy API的设计和使用体验**： - 一方面，有人认为NumPy的API设计不一致且复杂，导致使用不便和调试困难。另一方面，也有人认为NumPy的灵活性和广播机制在某些情况下是非常有用的。 • **多维数据处理的最佳工具选择**： - 对于多维数据处理，Xarray被认为是更好的选择，但也有评论者指出其在某些功能上不如NumPy全面，需要根据具体需求选择合适的工具。 总的来说，评论者们对NumPy的多维数据处理能力、API设计和性能优化提出了多种看法，同时也探讨了其他工具如Xarray、Julia和PyTorch在不同场景下的优劣。

Pathfinding

作者: sebg | 评分: 136 | 评论数: 12 | 发布时间: 2025-05-15 12:32
文章摘要

JuhrJuhr在其游戏开发日志中介绍了NPC路径寻找的实现方法，特别强调了适应动态物理环境、保持与障碍物的距离、以及游戏区域边界环绕等独特需求。为了处理动态环境，他采用A*搜索算法，结合空间分区树来减少每次路径查询的计算量。空间分区树将游戏区域划分为不同层次的节点，通过缓存和定期刷新（每500毫秒）来保持路径的实时更新。路径选择上，算法优先选择离障碍物较远但必要时可以靠近的路线，并支持类似《Asteroids》游戏的边界环绕效果。这种方法有效平衡了路径搜索的效率和自然性。

这篇文章讨论了美国海军舰船建造中存在的延误和超支问题，并提出了改进建议。文章指出，当前海军舰船设计复杂、功能多重，导致成本和建造时间大幅增加。例如，福特级航母配备的高端雷达增加了设计复杂性和成本，而 littoral combat ship (LCS) 因尝试承担多种角色而提前退役。文章建议：1) 设计更简单、用途单一的舰船；2) 将设计工作从第三方收回，由海军内部完成，并增加海军建筑师人数；3) 在设计基本完成前，不应开始建造。这些措施旨在减少成本超支和工期延误，提高海军舰船建造效率。

Lua for Elixir

作者: davydog187 | 评分: 164 | 评论数: 17 | 发布时间: 2025-05-13 13:03
文章摘要

Git: Move files from one repo to another with history (2021)

作者: transpute | 评分: 5 | 评论数: 0 | 发布时间: 2025-05-16 07:23
文章摘要

本文介绍了如何使用Git命令行和`filter-repo`命令将文件及其历史记录从一个代码仓库迁移到另一个。传统方法如`filter-branch`和patching存在复杂性和问题，而`filter-repo`更为高效。首先，需要单独安装`filter-repo`。然后，通过以下步骤完成迁移： 1. **清理源仓库**：使用`filter-repo`命令包含或排除文件和文件夹及其历史。 2. **添加源仓库为目标仓库的远程源**：在目标仓库目录中添加源仓库路径。 3. **获取并合并更改和历史**：从远程源获取更改并合并到目标分支。 4. **清理**：删除远程源和临时分支。 示例命令包括： - 包含文件和文件夹：`git filter-repo --path --path ` - 排除文件和文件夹：`git filter-repo --path --path --invert-paths` - 添加远程源：`git remote add ` - 获取并合并：`git fetch ; git merge --allow-unrelated-histories` - 清理：`git remote rm ; git branch -d ` 这样可以成功将文件及其历史记录迁移到新仓库。
