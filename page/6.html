H1-B visas hurt one type of worker and exploit another

作者: 1vuio0pswjnm7 | 评分: 33 | 评论数: 6 | 发布时间: 2025-06-28 18:50
文章摘要

本文由参议员伯尼·桑德斯撰写，批评H-1B签证计划伤害美国工人并剥削外籍劳工。文章指出，该计划本应用于解决高技能人才短缺，但实际上被大公司用来雇佣廉价外籍劳工，取代美国员工，导致美国技术人员失业。同时，外籍劳工面临不公平工作条件，签证受制于雇主。桑德斯呼吁，应大幅提高签证费用，确保该计划仅作为短期解决方案，长期应通过教育提升美国竞争力，而非依赖廉价外籍劳工。

评论摘要
主要讨论点：H1-B签证计划及其相关费用、移民过程的合理性、以及对美国工人的影响。 不同观点： • [sxp] 认为应该大幅增加大公司支付的客工费用，以资助美国工人的奖学金、学徒和职业培训。他还建议将H1-B计划改为拍卖制度，取消配额和抽签，让公司通过竞拍获得签证，并从联邦所得税中扣除费用。他认为如果公司想要全球最优秀的人才，就应该为此付出代价。 • [digianarchist] 部分同意[sxp]的观点，但指出目前已有“优秀人才”签证（O1签证），而H1-B是人们通过就业移民美国的唯一合理途径。他还提到，大多数雇主不会选择更为复杂的EB2/3移民签证程序，因为他们希望员工能立即为其他公司工作。 • [1vuio0pswjnm7] 没有直接表达观点，但提供了另一个相关的调查报告链接，供对该话题感兴趣的人参考。 • [downrightmike] 强调外包问题比签证问题严重得多，暗示外包对美国工人的影响更为负面。 • [ergocoder] 以自身经历为例，认为通过H1-B签证在美国获得高薪工作（300K - 1.2M年薪）并不能被视为剥削，反而显示了H1-B签证计划对技术移民的积极作用。 补充讨论： • 争议焦点在于H1-B签证计划是否对美国工人造成了剥削，以及是否应该通过增加费用或改变程序来保护美国工人。 • [sxp] 和 [digianarchist] 对H1-B签证的适用范围和公司支付费用的合理性存在不同看法。 • [downrightmike] 提出的外包问题虽未深入讨论，但指出了另一个影响美国就业市场的因素。 • [ergocoder] 以个人高薪为例，反驳了H1-B签证计划剥削外国工人的观点，提供了实际案例支持其立场。

Use Plaintext Email (2019)

作者: cyrc | 评分: 97 | 评论数: 19 | 发布时间: 2025-06-28 18:10
文章摘要

这篇文章主要介绍了互联网中两种主要的电子邮件格式：纯文本和HTML，并强调了技术社区更偏好使用纯文本邮件。文章提供了如何在不同邮件客户端中设置纯文本邮件的指南，推荐了如aerc、alpine、Claws Mail等支持纯文本的客户端，并详细说明了在Apple Mail、Gmail、Thunderbird等流行客户端中设置纯文本的方法。此外，文章还介绍了纯文本邮件的礼仪建议，如引用文本和底部发帖的规范，并解释了为什么纯文本优于HTML。文章最后由sourcehut平台赞助，该平台使用纯文本邮件进行软件开发协作。

评论摘要
主要讨论点：电子邮件的格式选择（ plain text 与 HTML 格式）以及隐私和安全问题 不同观点： • **支持 plain text 邮件**： - **rsync**: 认为 plain text 邮件美观、轻量、高效，并且可以避免网络跟踪和像素追踪。同时，通过 SSH 发送邮件可以避免邮件在网络上传输，增强安全性。 - **SoftTalker**: 偏好 plain text 邮件，尤其是删减无关引用内容并进行 inline 回复，但认为主流邮件客户端不鼓励这种做法。 - **dsp_person**: 偏好类似 Markdown 的格式，希望有基本的标题、列表和内嵌图片功能，而不是完整的 HTML 邮件。 - **tonymet**: 开发了发送 plain text 邮件的工具，认为 Gmail 的 SMTP 网关会破坏 plain text 格式，而 RESTmail 则能保留格式。 • **反对 plain text 邮件**： - **colonial**: 认为撰写技术性强的消息时，plain text 会导致信号与噪声比下降，富文本格式能更直观地传达信息。 - **alkonaut**: 认为应根据收件人的偏好和使用的客户端选择邮件格式，大多数企业和收件人更习惯 HTML 邮件。仅为了小众偏好切换到 plain text 并不实际。 - **sneak**: 认为坚持 plain text 是“老旧 Unix 用户”的传统，认为富文本和可变宽度字体都是现代邮件的重要功能。 • **中立或实用主义**： - **beached_whale**: 建议设置邮件客户端不自动下载图片，以防止发送方追踪阅读行为，但未明确支持或反对某种邮件格式。 - **nailer**: 质疑为何要将邮件限制为 78 字符宽的 monospace 格式。 - **geor9e**: 提出通过将显示切换为灰度、禁用浏览器中的 JavaScript 等方法来增强隐私保护，同时用幽默的方式表达对现代网络服务的不满。 补充讨论： - 关于邮件格式选择的争议焦点在于**plain text 的简洁性和隐私优势**与**HTML 的丰富表现力和现代性**之间的权衡。 - **隐私和安全问题**也被提及，如避免邮件中的跟踪像素和使用 SSH 发送邮件以增强安全性。 - 提到了一些技术解决方案和工具，如 **dodo** 和 **restmail**，用于改善 plain text 邮件的使用体验。 - 历史讨论链接提供了更多背景信息，显示出这一话题的长期性和持续性争议。

James Webb Space Telescope reveals its first direct image of an exoplanet

作者: divbzero | 评分: 213 | 评论数: 22 | 发布时间: 2025-06-27 17:44
文章摘要

天文学家使用詹姆斯·韦伯空间望远镜（JWST）在距离地球约111光年的年轻恒星TWA 7周围发现了一个微弱红外光源，可能是一颗系外行星，名为TWA 7 b。这是JWST首次通过直接成像可能发现的系外行星。研究团队利用JWST的日冕仪阻挡恒星强光，从而识别出这颗潜在行星。TWA 7 b质量与土星相近，温度约120华氏度，位于恒星 debris 盘的间隙中，距离恒星约为地球到太阳距离的50倍。尽管存在该光源可能是背景星系的微小可能性，但模拟和观测结果强烈支持其为系外行星。这一发现有助于理解行星系统的多样性及形成过程。

评论摘要
主要讨论点：詹姆斯·韦伯空间望远镜（JWST）首次通过直接影像发现系外行星的相关技术和科学意义 不同观点： • [meatmanek] 认为标题不准确，这不是JWST第一次拍摄到的系外行星图像，但之前的图像并非用于发现未知行星。此次是首次使用直接影像发现新行星。 • [GMoromisato] 指出，由于距离遥远，获得的行星图像通常只有一个像素大小，要获得更高分辨率的图像需要极大的技术突破，比如建造跨度数百公里的望远镜或太空光学干涉仪。 • [jl6] 对研究中依赖计算机模型验证观测结果的做法持保留态度，认为模型基于假设和预期，而非实际数据，因此作为假设支持的力度较弱。 • [thebruce87m] 对研究中可能的误差范围表示关注，认为新发现的物体有可能其实是背景星系，虽然理解研究难度，但仍觉得误差范围有些滑稽。 • [bane] 曾经对JWST持怀疑态度，认为投资过早，但如今看到其取得的成就，认为这是科学的一大胜利，象征着人类对宇宙理解的飞跃。 补充讨论： • [danparsonson] 提到，之前已经有多个直接成像的系外行星，并提供维基百科链接供参考，但同时肯定JWST的成就依然非常了不起。 • [ryanisnan] 表达了对未来可能获得更高分辨率图像的期待，特别是对类地行星的直接观测，认为这将是历史性的时刻。 • [BitwiseFool] 展望未来，认为随着超级重型运载火箭的发展，未来的望远镜将更加强大。 • [imoverclocked] 和 [sylware] 关注文章中的技术细节和链接问题，前者指出文章中的拼写错误，后者询问是否有直接图片链接。 • [padjo] 提到德雷克方程中的行星存在概率（f_p）在几十年间从猜测的0.5上升到几乎确定的1，反映了人类对宇宙生命存在可能性的认知进步。 • [neom] 提供了相关研究的论文链接，为讨论提供了进一步的科学依据。 争议焦点： • 主要争议在于对计算机模型在科学研究中作用的评价，以及对此次发现可能的误差范围的看法。部分评论者对模型的可靠性表示怀疑，而另一些评论者则关注发现过程中可能存在的技术误差。

Transmitting data via ultrasound without any special equipment

作者: todsacerdoti | 评分: 128 | 评论数: 17 | 发布时间: 2025-06-27 17:02
文章摘要

本文讨论了通过声音，尤其是超声波，在设备间传输数据的概念。文章首先解释了电磁波如何在空中传输秘密信息，然后引出如何在不依赖同一网络的情况下，利用声音在设备间传递数据。文章详细介绍了声音的频率分解和超声波的定义（频率高于20000 Hz的声波），并指出普通电脑的麦克风和扬声器实际上可以处理超声波。通过将数据编码成高频音频信号，可以在设备间传输信息。文章最后提供了一个网页示例，演示如何使用频率偏移键控（FSK）技术通过超声波在设备间传输二进制数据。

评论摘要
主要讨论点：通过音频传输数据的技术及其应用 不同观点： • **achairapart**：分享了一个使用Progressive Web App和Quiet.js实现的音频导览项目，通过手机麦克风接收房间内的信号来触发音频。但由于Safari对频率的限制，不得不调整为靠近特定扬声器来接收音频。该方案在实际应用中效果良好。 • **kiicia**：提到了在购物中心使用超声波进行监测的案例，如通过超声波音调进行速度检测、广告投放等。这与achairapart的项目有相似之处，但应用场景不同。 • **thijson**：建议研究调制解调器通过电话线传输数据的技术，如格状编码调制和均衡技术，以解决多径效应问题。此外，提出可以使用扩频编码（如CDMA）来增强信号传输距离。 • **lxe**：指出18-20kHz不属于超声波范围，许多人仍能听到这一频率范围的声音，并且这种声音可能让人感到不适。相比之下，医疗超声波的频率要高得多（2-20MHz）。 • **TrackerFF**：提到过去曾有商业产品使用超声波数据传输，通过手机接收音频信号来实现某些功能（如灯光效果），无需依赖WiFi覆盖。 • **adzm**：对web工具进行了测试，发现其在噪音环境下表现良好，但超过一定噪音强度后无法识别信号。认为可以通过有趣的方式来解决噪音干扰问题。 • **jnwatson**：指出Chromecast曾使用超声波代替配对码进行连接。 • **echoangle**：质疑了某个频率域图示的准确性，认为其显示的是音量随时间的变化，而不是频率的强度随时间的变化。 • **ac29**：提供了ggwave项目的链接，作为相关技术参考。 • **vishnuharidas**：提到LG电器使用音频诊断系统（LG Smart Diagnosis）的案例，类似于讨论中的音频传输技术。 • **amelius**：从动物保护角度出发，反对使用高于20kHz的音频传输技术，担心对宠物造成影响。 • **kragen**：认为虽然通过麦克风和扬声器传输数据并不新颖，但在某些设备上（如Arduino）实现超声波编码仍具有挑战性，目前尚未见到成功的实现。 补充讨论： • 争议焦点之一是18-20kHz是否属于超声波范围，以及这种频率的声音对人的舒适度影响。 • 另一个讨论点是技术实现的细节，如是否需要使用特殊的编码调制技术来增强信号传输效果。 • 不同应用场景下的技术实现和限制也被多次提及，如购物中心监测、Chromecast连接、LG电器诊断等。 • 动物保护问题也被提出，认为技术应用需要考虑对宠物的影响。

Why the moon shimmers with shiny glass beads

作者: PaulHoule | 评分: 8 | 评论数: 2 | 发布时间: 2025-06-24 23:09
文章摘要

文章介绍了月球表面发现的微小玻璃珠的形成原因及其科学价值。这些玻璃珠形成于约33至36亿年前月球的火山喷发，当时月球仍年轻。每个珠体如同月球内部的微小时间胶囊，保存了古代月球火山活动的记录。研究团队利用现代显微分析技术，如纳米二次离子质谱仪和扫描电子显微镜，对这些珠体进行了详细分析。研究发现，这些玻璃珠不仅颜色和形状独特，其化学成分也与地球上的物质不同，揭示了月球火山喷发风格随时间的变化。该研究发表在《Icarus》期刊上，为理解月球早期地质活动提供了重要线索。

评论摘要

c4wa – C compiler for Web Assembly

作者: 90s_dev | 评分: 77 | 评论数: 9 | 发布时间: 2025-06-24 15:52
文章摘要

**c4wa** 是一个将 C 语言的简化子集编译为 Web Assembly (WASM) 的编译器。它生成的 WASM 输出精简且高效，没有额外的嵌入库或不必要的开销，并且与任何 WASM 运行时完全兼容，不依赖 JavaScript 或 node。该编译器充分利用 WASM 的线性内存模型，支持动态内存分配，并且可以输出文本格式的 WAT，便于理解和手动编辑。 **c4wa** 支持 C 语言的基本特性如循环、条件、指针、结构体、数组和动态内存分配等，适用于日常编程任务。与其它编译器相比，它避免了生成臃肿的 WASM 代码，提供了一种介于高级语言和手写 WAT 之间的中间方案。 该工具需要 Java 11 或更高版本，使用预处理器时需要外部 C 编译器如 gcc。生成的 WASM 文件跨平台，可以在任何支持 WASM 的运行时中执行，包括浏览器。

评论摘要
主要讨论点：围绕将C代码编译为WebAssembly（Wasm）的各种工具和方案的讨论，包括代码优化、功能支持、编译器选择以及Wasm运行时的语义问题。 不同观点： • keysdev认为机器生成的代码往往变量众多且难以理解，提出了是否应该完全信任机器生成代码的问题，并主张编写简洁的代码。他以Nim生成JavaScript代码为例，质疑机器生成代码的可读性和可维护性。 • lioeters对需要Java 11或以上版本的工具表示失望，认为如果工具能用C的子集编写并编译成Wasm会更好，表达了对跨语言依赖的不满。 • comex指出在Emscripten与c4wa的比较中，作者忘记开启优化选项，认为开启优化（-O选项）后，Emscripten生成的代码质量与c4wa相当，暗示比较不公平。 • s-macke展示了使用clang并通过`--target=wasm32`选项编译成Wasm的成功案例，强调其生成的小型二进制文件，并给出具体项目示例，表明clang在Wasm编译中的优势。 • teo_zero指出c4wa不支持C99引入的新特性，并对c4wa不要求K&R函数语法表示肯定，暗示对旧语法支持的解脱。 • Anduia只是提到项目最后一次提交时间为2022年1月29日，暗示项目可能不够活跃。 • pyrolistical提到Zig也可以编译成自由站立的Wasm，提供了一个额外的工具选项。 • apitman表示支持更多的自由站立Wasm模块工具，并分享了在自定义Wasm应用runtime开发中遇到的挑战，特别是对C/Rust标准库函数的支持需求，同时希望有更多工具来简化API定义。 • b0a04gl讨论了C语言中的`volatile`关键字在Wasm中的语义变化，指出Wasm单线程运行时无法保证内存操作顺序，暗示编译通过但语义可能丢失。 补充讨论： • 代码优化是讨论的一个重点，特别是优化选项对生成代码质量的影响。 • 不同工具对C语言特性和Wasm支持的程度不同，选择合适的编译器和工具链成为开发者关注的问题。 • 对Wasm运行时语义变化的关注，特别是对多线程和内存操作语义的理解，显示出Wasm在某些应用场景中的潜在问题。 争议焦点： • 机器生成代码的可读性和可维护性问题，是否应该完全信任编译器和bundler。 • 不同工具链对C语言特性和Wasm支持的优劣比较，特别是对新旧语法和特性的支持。
