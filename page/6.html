tsplat 是一个用 Rust 编写的 3D 高斯溅射（Gaussian Splatting）渲染工具，可在终端中运行，纯 CPU 实现，无需 GPU 或显示服务器，支持 SSH 远程使用。它通过 Unicode 半块字符或图形协议将 3DGS 场景直接渲染到终端。 主要特性包括：支持 INRIA 3DGS .ply 格式场景文件、可调节溅射数量上限、提供相机控制（平移、旋转、缩放）和自动环绕模式。 技术实现上，每个高斯溅射由位置、缩放、旋转、颜色和不透明度表示。渲染管线包含五个步骤：投影溅射（构建 3D 协方差矩阵并投影到 2D）、计算边界框、深度排序、瓦片分箱和 alpha 合成。项目还包含高斯溅射原理的详细教程文档。

A disappearing Service Processor (2025)

作者: mooreds | 评分: 20 | 评论数: 3 | 发布时间: 2026-05-30 20:05
文章摘要

这篇文章讲述了 Oxide 团队调试服务处理器(SP)网络掉线问题的过程。SP 运行自研的 Hubris 操作系统,问题表现为 SP 从管理网络消失但主机 CPU 仍运行。团队最初怀疑是任务饥饿或栈溢出,通过 LED 闪烁等调试手段排查。最终通过 SWD 调试接口发现 CPU 无法被暂停,将问题定位到新增的 FPGA 与 STM32H7 处理器之间的并行总线通信上——可能是 FPGA 时序问题导致 CPU 在读取寄存器时永久挂起,因为未收到总线应答信号。

评论摘要
主要讨论点：FPGA Mezzanine Card (FMC) 总线配置错误导致的技术问题 不同观点： • **技术问题分析**（Animats）：核心问题是将 FMC 总线的基地址错误配置为 Normal Cached 内存类型，导致外部非内存设备被放在缓存后面。这种配置从根本上无法正常工作，只能偶尔碰巧运行。 • **历史关联**（indigodaddy）：这个问题让人联想到 Sun/Sparc 硬件和 Solaris 系统时代的类似经历，暗示这类配置错误在硬件开发历史上并非首次出现。 补充讨论：als0 提供了术语解释，指出 Service Processor (SP) 本质上是另一种 Baseboard Management Controller (基板管理控制器)，帮助不熟悉该领域的读者理解技术背景。整体讨论围绕硬件配置错误展开，没有明显争议，更多是技术问题的确认和经验分享。

Stateless Actors

作者: frizlab | 评分: 39 | 评论数: 4 | 发布时间: 2026-05-29 13:28
文章摘要

这篇文章探讨了无状态 Actor 的实用性。作者认为虽然 Actor 的主要目的是保护可变状态，但无状态 Actor 仍有价值： 1. **NetworkClient 类型**：无状态 Actor 自动具备 Sendable 特性，且方法不会在主线程执行，适合处理网络请求和 JSON 解码等耗时操作。但也有缺点：难以配合协议使用，且串行执行限制了并发性能。 2. **BackgroundActor**：虽然提供了类似 @MainActor 的后台执行方式，但存在串行执行和类型系统侵入性强的问题，不如使用语言现有的隔离控制机制。 3. **自定义执行器 Actor**：用于将 Swift 并发系统与其他队列系统（如 DispatchQueue）集成，是重要的适配工具。 总体而言，无状态 Actor 有其应用场景，但需权衡利弊。

评论摘要
主要讨论点：关于"无状态actor是否无意义"的技术讨论 不同观点： • **抽象设计观点（Nevermark）**：认为无状态概念在高度可组合的语言中有实际意义。任何事物的"null版本"都可能有用，如无状态的状态、无操作的操作、无目标的网络端口等。这是因为现有语言在抽象设计和性能之间难以平衡，导致开发者会过度或不足地使用抽象。 • **Swift技术实现观点（mayoff）**：从Swift语言角度明确反对"无状态actor"的存在。指出Swift中的actor必须实现`unownedExecutor`属性，且作为引用类型本身就携带身份状态，因此技术上不存在真正的无状态actor。 • **并发保护质疑观点（mrkeen）**：对actor的实际价值持怀疑态度。通过竞态条件的例子说明，使用私有字段、getter/setter或actor来保护可变状态，最终效果与直接操作相同，只是增加了样板代码，暗示这些机制可能只是表面功夫。 补充讨论：讨论涉及语言设计哲学、具体技术实现和实用价值三个层面，反映了理论抽象与工程实践之间的张力。
