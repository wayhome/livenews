Azure Linux 4.0 is Microsoft's first general-purpose Linux

作者: haydenbarnes | 评分: 116 | 评论数: 27 | 发布时间: 2026-06-05 03:14
文章摘要

微软在 Build 2026 发布了 Azure Linux 4.0 公开预览版，这是首次允许用户在任何 Azure 虚拟机上运行，标志着它从专用设备发行版转变为通用 Linux 发行版。 4.0 版本基于 Fedora 43 构建，采用声明式覆盖层方式，不再手动维护每个软件包。主要更新包括：Linux 6.18 LTS 内核、dnf5 包管理器（替代微软自研的 tdnf）、glibc 2.42、systemd 258 等现代化组件栈。 该版本支持虚拟机、容器、AKS、WSL 等多种部署场景，强调安全性（SELinux、FIPS 140-3 认证）和供应链可审计性。微软内部服务及 Databricks、LinkedIn 等已大规模采用。这使 Azure Linux 从"基础设施组件"转变为用户可主动选择的云原生发行版。

评论摘要
主要讨论点：微软发布基于Fedora的Azure Linux作为"通用目的"操作系统引发的争议 不同观点： • **Azure专用派**：认为这只是为Azure优化的专用系统，不是真正的通用OS，没人会在微软计算环境外运行它（codycharris） • **通用OS质疑派**：传统通用OS应该能在任意硬件上运行并获得厂商认证支持，Azure Linux只是微软在云端提供的统一Linux方案，类似SUSE/RedHat/Canonical，但仅限微软技术栈（froh） • **基础通用派**：虽然是Azure/WSL专用，但基于通用Linux（Fedora），能访问大量软件包，具有通用基础（reacweb） • **稳定性担忧派**：微软使用前沿发行版Fedora快照并称其"通用目的"，暗示可用于各类生产环境，但实际并不稳定——这正是Fedora/RHEL分离的原因（bananaquant） • **战略怀疑派**：认为这是微软"拥抱、扩展、消灭"策略的延续，通过淡化"通用目的"一词来占领新领域（egorfine, nullpoint420） 补充讨论：有用户对微软从专有tdnf转向标准dnf5表示意外，认为内部平台通常会越来越定制化而非标准化；也有人提醒微软从Xenix时代就支持Unix系统。

Learn SQL Once, Use It for 30 Years

作者: karakoram | 评分: 295 | 评论数: 69 | 发布时间: 2026-05-31 17:16
文章摘要

SQL是唯一可以学一次用30年的编程语言，因为它基于数学而非潮流。1995年的SQL查询今天仍能运行，而JavaScript等语言每隔几年就需重写。SQL建立在关系代数之上，这是数学，没有版本迭代。你描述想要什么，数据库引擎决定如何获取，引擎改进但查询不变。对初级开发者，深入学习SQL是最值得的投资，在任何技术栈中都能用几十年。SQL的稳定性代价是积累了许多缺陷（如NULL逻辑、日期处理），但向后兼容性保证了它的持久价值。

评论摘要
主要讨论点：SQL作为编程语言的学习价值和特殊性 不同观点： • **SQL是最值得投资的技能**（aledevv, vbezhenar）：SQL教会底层逻辑思维，20-30年不过时，与C语言、Unix工具同属长青技能，AI时代依然重要 • **重点应是数学思维而非语法**（TonyAlicea10, perrygeo）：应学习集合论和关系代数等底层数学模型，理解数据库的ACID特性、索引策略和数据建模，SQL语法只是表层 • **SQL并非完美，存在设计缺陷**（wodenokoto）：SQL语法不一致（如"="的双重含义、"AS"的位置变化），最初想做自然语言接口但失败了，只是因为普及而成功 • **从ORM回归原生SQL**（ciconia）：原生SQL更简单、显式、可控且性能更好，构建围绕查询的模型即可 • **存在更好的替代方案**（teleforce, veqq）：D4M基于关联数组代数比关系代数更通用，Datalog和kSQL等声明式查询语言也值得关注 补充讨论： • 需持续学习而非一劳永逸（sdevonoes） • SQL在演进，各厂商方言差异大（kermatt, WA） • 高级SQL学习曲线陡峭，缺乏进阶资源（AnonHP） • AI可辅助生成schema和复杂查询（Kuyawa）

Sum-product, unit distances, and number fields

作者: robinhouston | 评分: 59 | 评论数: 3 | 发布时间: 2026-06-01 05:54
文章摘要

这篇文章讨论了最近对单位距离猜想和和积猜想的反例构造。作者通过一个加法组合学的例子引入"张量幂技巧"：先找到一个小规模的特殊集合（如|A+A|≥|A-A|^1.012），然后通过构造d维笛卡尔积B=A^d，将这个常数优势放大到任意大的集合。文章指出，单位距离和和积问题的反例也采用类似思路：找到"平凡"构造获得常数因子优势，再通过高维版本放大这个优势。但挑战在于必须在ℝ或ℝ²中构造集合（而非ℝ^d），同时保证加法之外的运算（乘法或距离）也能正确缩放。

评论摘要
主要讨论点：关于AI在数学研究中的应用及其成果呈现方式 不同观点： • **正面评价AI的可解释性**（pfdietz）：AI为单位距离问题创造的新方法被人类数学家成功应用到sum-product猜想的反驳中。人类数学家简化了AI结果并提取了有用见解。这与"AI产生难以理解结果"的担忧相反，实际上AI的结果是可以被理解和改进的。 • **技术呈现问题**（fithisux）：内容在浏览器中无法正确显示，希望提供LaTeX或PDF格式以便阅读。 • **符号解释不足**（amelius）：文章使用了未解释的数学符号（|·|），导致阅读体验不佳，影响理解。 补充讨论：评论反映了两个层面的关注——pfdietz关注AI在数学研究中的实质性贡献和可解释性，而fithisux和amelius则指出了内容呈现和可读性方面的技术问题。没有明显的观点冲突，更多是从不同角度评价同一主题。

文章摘要

Elixir v1.20 正式发布，成为渐进式类型语言。该版本实现了首个开发里程碑：无需类型注解即可对所有 Elixir 程序进行类型推断和检查，能够高效发现死代码和"已验证的错误"（guaranteed runtime failures）。 Elixir 的类型系统具有三大特点：健全性、渐进性和开发者友好。核心是 `dynamic()` 类型，它具有兼容性和类型窄化两个重要特性。与其他语言的 `any()` 不同，`dynamic()` 只在提供类型与接受类型完全不相交时才报告类型违规，从而实现极低的误报率，仅报告必然在运行时失败的错误。 该系统在"If T: Benchmark for Type Narrowing"基准测试中通过了 13 个类别中的 12 个，展示了从动态类型代码中恢复精确类型信息的能力。

评论摘要
主要讨论点：Elixir 1.20 引入渐进式类型系统的利弊及与其他语言的比较 不同观点： • **支持渐进类型化**：多位开发者（yeetosaurusrex, losvedir, gworkman）对类型系统表示欢迎，认为编译器能"免费发现 bug"，且升级无破坏性变更。有人提到虽然想念静态类型，但不可变性和避免 OO 抽象的权衡值得 • **质疑动态类型语言价值**：teleforce 认为非类型语言是"技术债务"，列举 Twitter、Airbnb、Shopify 从 Ruby 迁移的案例，认为在 AI 辅助编程时代，非类型语言缺乏优势且难以扩展 • **后天类型化的效果存疑**：alprado50 认为后期添加类型的语言效果不如"原生"静态类型语言。tines 指出讽刺现象：动态语言都在变类型化，但没有静态语言反向发展 • **转向其他语言**：anonyfox 分享从 Elixir 转到 OCaml 的经历，强调"真正的类型系统"不可妥协，批评 Elixir 用大量测试弥补类型缺失，认为 Beam 虽强大但部署繁琐、演进缓慢 • **实用主义立场**：satvikpendem 询问与 Gleam 对比，指出 Phoenix/LiveView 是 Elixir 优势。bad_haircut72 担心类型化会削弱 Elixir 作为 Lisp 的灵活性 补充讨论：有人关注性能（sestep 询问渐进类型对程序复杂度的影响）和实际效果（losvedir 想知道与 dialyzer 的对比）
