Surprise, pay $1000

文章摘要

这篇文章讲述了 Forestwalk 团队使用 GitHub Actions 替代品 Blacksmith 的经历。他们在"免费试用、无需信用卡"的情况下使用该服务，超出免费额度后收到了"避免服务中断请添加信用卡"的警告。但团队继续使用，最终收到了 1081 美元的账单和逾期通知。 关键问题是：Blacksmith 没有在超出免费额度时停止服务，而是继续运行并累积费用。虽然条款技术上允许这样做,但这违背了用户对"免费试用"的常规预期——大多数 SaaS 服务会在免费额度用尽时切断服务。文章质疑这种做法的合理性,认为让未提供支付信息的用户累积欠款是不良商业实践。

评论摘要
主要讨论点：Blacksmith（CI服务提供商）在免费试用期后向未提供付款信息的用户发送账单，引发关于商业实践合理性的争议 不同观点： • **反对派（多数）**：认为这是违反常规的"陷阱式"收费。传统上免费试用结束后服务应停止，而非自动转为付费并事后账单。类比奥地利域名注册商的强制续费、移动运营商的隐藏流量费等案例，指出打破"预付费惯例"的商业模式本质上是欺诈手段 • **务实派**：承认虽然体验糟糕，但考虑到实际使用了服务并获得价值（相比GitHub Actions仍便宜50%），从商业角度可以理解。建议保持使用但避免深度绑定，直到公司行为模式更明朗 • **技术替代派**：质疑为何CI月账单高达$1000，分享自建runner方案（成本降低6倍以上）和优化建议（缓存、更大规格机器、性能分析等），认为不值得为此类服务冒财务风险 补充讨论：有评论指出条款本身存在矛盾——明确要求提供付款信息才能计费，却在未提供时仍然开账单。多人强调此举破坏信任、损害长期商誉，呼吁Blacksmith公开解释。整体倾向是：小型运营者应避免此类风险服务。

文章摘要

本文深入分析了Linux内核AF_UNIX垃圾回收器的重写过程。该GC负责回收无法从用户空间访问但仍被内核保持活跃的套接字。文章解释了核心概念：当套接字通过SCM_RIGHTS发送时会进入"in flight"状态，若file_count等于inflight计数，说明只剩下困在其他套接字接收队列中的引用，需要被回收。 旧GC通过遍历inflight图并标记循环来判断是否可回收。新GC采用基于图论和强连通分量(SCC)的模型重写，使用Tarjan算法将图划分为SCC。新方案避免锁定每个套接字队列，减少了对系统的影响。GC触发条件包括：inflight套接字超过16000个，或套接字关闭时存在inflight对象。文章还提及该子系统仍存在Use-After-Free等漏洞风险。

文章摘要

这篇文章介绍了Rust异步编程的教学方法。作者认为AI能帮助学习，但每篇文章仍需20-25小时打磨。文章重点阐述了Rust与JavaScript在异步处理上的根本差异：JavaScript内置事件循环自动运行Promise，而Rust不提供事件循环，需要开发者自己构建或引入（如Tokio）。文章通过对比两种语言中的Future/Promise概念，解释了Rust的Future是需要手动轮询(poll)的占位符，而JavaScript的Promise由运行时自动处理。这个系列旨在搭建"理解异步原理"与"实际应用"之间的桥梁，通过手动构建执行器来深入理解异步机制。

评论摘要
主要讨论点：关于 Rust 异步编程教程的评论，涉及教程质量、异步机制本身的价值以及学习资源 不同观点： • 教程质量认可派：认为教程写作清晰易懂，语言平易近人，避免了过多 Rust 术语，具有实际教育价值，是 AI 内容泛滥时代的优质人工创作 • 异步机制批评派：认为异步功能破坏了 Rust，主张用线程代替异步，理由是线程将 CPU 视为资源而异步会锁定 CPU，类比垃圾回收暂停的问题 • 教程设计质疑派：认为将 JavaScript 异步作为 Rust 教程的预备知识很奇怪 • 评论异常怀疑派：质疑评论区过多好评不符合 HN 风格，怀疑有机器人刷评 补充讨论： 有用户指出 Tokio 官方已有类似深度教程，通过构建玩具运行时来理解异步机制。另有评论提到该教程也帮助理解了 JavaScript 引擎流程，认为 Rust 的异步流程更自然。整体争议焦点在于异步编程范式本身是否适合 Rust，以及是否应该用多线程替代。

文章摘要

Macaroni Messenger 是一个用单个 HTML 文件实现的分布式消息系统。它将 GitHub 仓库作为后端存储消息，无需传统服务器。用户可以直接在浏览器中打开 HTML 文件使用，通过 GitHub token 读写仓库中的消息数据。消息存储在 `.macaroni/` 目录下的 JSON 文件中。项目支持离线使用，但依赖 GitHub API，存在速率限制。公开仓库意味着消息公开，私有仓库则限于有权限者可读。这是一个极简主义的去中心化通讯方案，强调"无后端、无注册、无服务器"的理念。

评论摘要
**主要讨论点：** Macaroni Messenger项目声称是"单文件分布式消息系统"，但实际依赖GitHub作为后端存储，引发关于其"无后端"声明真实性的争议。 **不同观点：** • **质疑派**：boomlinde和vincnetas认为依赖GitHub就是有后端，"无后端"说法自相矛盾。antran22批评最严厉，指出代码完全围绕GitHub API构建，并非真正的provider-agnostic Git操作，标题具有误导性，整个项目像是AI生成的"vibeslop"。BrenBarn也认为需要GitHub才能工作，"单文件"说法误导。 • **技术建议派**：littlecranky67建议使用WebRTC实现真正的P2P连接，推荐结合Trystero项目。torginus对单HTML文件打包所有资源的部署方式感兴趣。msyea分享了类似理念但用OAuth PKCE让用户自带后端的方案。 • **正面反馈派**：Hugsbox觉得README有趣，项目很酷。andai喜欢其开源协议。 • **关联项目派**：kristopolous分享了通过图片传递消息的chat系统；rcfox提到类似的giscus评论系统；ventana指出俄语文档揭示项目可能与俄罗斯封锁messenger有关，有更深层动机。 **补充讨论：** fibo纠正拼写应为"Maccheroni"；utilize1808将其类比为浏览器版applet；_def回忆起用base64 URI通过短网址服务部署HTML的往事。
