PostgreSQL and the OOM killer: Why we use strict memory overcommit

作者: furkansahin | 评分: 138 | 评论数: 17 | 发布时间: 2026-07-03 13:00
文章摘要

这篇文章解释了为什么PostgreSQL数据库必须使用Linux的严格内存过量分配（strict memory overcommit）设置。 核心问题：Linux默认允许进程分配超过物理内存的虚拟内存，当内存耗尽时会触发OOM Killer强制终止进程。PostgreSQL的架构特殊——主进程为每个连接创建后端进程，这些后端共享内存段（存储缓冲区、锁表等）。如果OOM Killer终止某个后端，可能导致共享内存状态不一致，进而造成数据损坏。 PostgreSQL的防护机制：一旦检测到任何子进程被杀死，主进程会立即终止所有其他后端进程，防止使用可能已损坏的共享内存。 解决方案：启用严格内存过量分配，让内存分配请求在早期就失败（返回错误），而非等到触发灾难性的OOM kill和全库重启。文章还分享了他们的配置经验（80%物理内存+2GB）和遇到的内核bug案例。

评论摘要
主要讨论点：Linux内存过度分配（overcommit）机制的配置争议及其在生产环境中的实际问题 不同观点： • **批评派**：认为Linux默认内存管理在2026年仍然落后，系统在内存压力下会死机或冻结，OOM killer表现不佳，Windows和macOS的默认配置明显更优秀。桌面环境经常需要硬重启。 • **严格overcommit支持派**：Ubicloud等Postgres托管服务商认为，在大规模数据库场景下，启用严格内存overcommit（mode 2）比默认设置更可靠，但承认这不适合所有场景。 • **实践权衡派**：在混合部署（如Go应用+PostgreSQL同机）时，既面临虚拟内存分配过多导致的不稳定，又遇到严格限制下的分配失败。建议通过经验调整参数或分离服务到不同服务器。 • **现代方案倡导派**：强烈反对手动调整CommitLimit，认为这是过时且容易出错的方法。主张使用OOM Score Adjust作为现代解决方案，并指出文章对Mode 0的描述已过时（复杂启发式算法已移除近十年）。 • **数据库最佳实践派**：建议像成熟数据库那样实现自己的内存记账系统和分配器，确保每个分配路径都能从OOM恢复。 补充讨论：多位开发者提到云服务商VM不使用Swap加剧了问题；有人建议需要一个专门在禁用overcommit下运行良好的Linux发行版；还有观点认为这是Rust相对于其他语言的优势案例（内存安全）。

We put a Redis server inside our runtime

作者: eandre | 评分: 30 | 评论数: 7 | 发布时间: 2026-07-01 10:11
文章摘要

Encore在其运行时（runtime）中内置了一个内存Redis服务器，用于本地开发和测试环境。 **核心实现：** - 最初Go版本使用miniredis库（Go实现的内存Redis） - 为支持TypeScript应用的Rust runtime，团队将miniredis移植到Rust（约25,000行代码） - 内存Redis作为库运行在runtime进程内部，而非独立进程 **技术特点：** - 实现完整的Redis协议（RESP）和常用数据类型（字符串、哈希、列表、集合、流、发布订阅、事务、Lua脚本） - 内置时钟管理和键清理机制 - runtime根据配置自动选择连接真实Redis或启动内存服务器 **优势：** 无需安装和维护Docker容器，本地开发环境自动获得与生产环境行为一致的Redis支持，简化了开发流程。

评论摘要
主要讨论点：Encore项目用25,000行Rust代码实现Redis服务器用于本地开发，但生产环境仍使用真实Redis 不同观点： • **强烈反对派**（sudowood0）：认为直接用Docker容器运行Redis非常简单，25,000行Rust代码仅用于本地开发是"疯狂的"决定，完全没有必要 • **逻辑矛盾批评**（drdexebtjl, nitwit005）：指出项目声称不用mock是因为担心行为差异，但自己实现的Rust版本同样会与真实Redis存在差异，需要额外测试来发现。生产环境用真Redis而开发环境用Rust实现，反而引入了环境不一致的风险，还要永久维护这个实现 • **讽刺派**（iwantitez）：用一行代码"const cache = {}"讽刺项目过度工程化 • **条件支持派**（sshine）：如果作为库使用，Rust重写有价值，但质疑维护版本一致性的必要性，建议直接依赖自己的分支 • **激进重构派**（khurs）：以Cloudflare用Rust重写Nginx为例，建议与其移植不如直接重写整个Reddit，清除2009年以来的技术债务 补充讨论：核心争议在于投入产出比和维护成本——大量工程投入却只服务于本地开发环境，且引入了开发/生产环境不一致的新风险

Best Simple System for Now (2025)

文章摘要

这篇文章探讨软件开发中"快速粗糙"与"完美主义"之间的矛盾。作者用山路比喻：左路（快速但临时）vs 右路（稳固但耗时），并提出第三条路径——"当前最佳简单系统"(BSSN)。 核心理念：构建**最简单**的系统来满足**当前**需求，达到**适当**的质量标准。关键是避免过度设计和预测未来。 文章批评程序员习惯性地寻求通用解决方案（如状态机、规则引擎），这源于模式匹配的本能。但预测往往是错误的，导致要么绕过错误假设，要么重构代码。 BSSN强调：专注于解决眼前的真实问题，而非臆想的未来需求，既不积累技术债务，也不过度工程化。

评论摘要
主要讨论点：软件开发中"快速实现"与"稳健设计"的工程权衡问题 不同观点： • **支持前瞻性设计**：国家公园小径隐喻说明适度的预先投资（如承重桥梁）能为未来扩展铺路，避免后期代价高昂的重建 • **强调情境依赖**：核心业务系统需稳健架构，创业公司追求产品市场契合时应快速迭代。经验丰富的工程师的标志是知道何时选择哪种方法 • **问题本质论**：区分"发明解决方案"与"发现解决方案"。应深入理解问题类别，寻找优雅通用的解决方案，而非仅解决单个实例 • **极性管理视角**：短期vs长期是永恒的张力而非可"解决"的问题，关键是识别何时倾斜过度并持续调整平衡 • **AI时代质疑**：在代理驱动的开发中，架构重塑变得容易，可能改变传统权衡逻辑 • **文化批判与身份焦虑**：YAGNI易导致部落知识，文档和模式具有社交价值。质疑硅谷文化的普适性，担心过度简化忽视团队协作需求和知识传承 补充讨论：多位评论者指出文章实质是重述YAGNI/KISS等经典原则。有人批评作者声称"中间路径"但实际倾向快速实现。最后一位评论者的长篇反思揭示了不同组织环境（尤其非硅谷）中开发者面临的现实困境，包括权力结构对代码设计的影响和个人职业身份认同问题。
