Verified dynamic programming with Σ-types in Lean

作者: rck | 评分: 77 | 评论数: 6 | 发布时间: 2025-06-17 14:28
文章摘要

本文介绍了如何使用记忆化（memoization）技术在Lean中解决一个动态规划问题，并验证其正确性。问题名为“Bytelandian金币问题”：给定一枚金 coin n，它可以被兑换为 n/2、n/3 和 n/4 三个整数金 coin（向下取整），也可以直接按1:1兑换为美元。目标是计算这枚金 coin 能换取的最大美元数。 解决方案采用递归关系定义：当 n ≤ 8 时，直接兑换为 n 美元；否则，选择 n 与 n/2、n/3、n/4 兑换后总和的最大值。为了优化计算，采用记忆化技术缓存子问题结果。 文中首先给出了直接递归实现作为规范，随后展示了记忆化实现，利用哈希表缓存子问题结果。最后，提出正确性证明的挑战，即证明记忆化实现与规范实现结果一致。证明的难点在于确保哈希表正确存储和查询子问题结果。文章邀请读者尝试证明，并指出证明中的关键在于理解数据结构的不变性。

评论摘要
主要讨论点：Lean语言中的类型理论、子类型概念及其在证明和算法中的应用 不同观点： • **gugagore** 指出Lean中的"subtype"概念与面向对象编程语言中的子类型概念没有太大关联，并强调了类型理论和集合理论之间的关键区别：在类型理论中，一个元素恰好属于一个类型。 • **CSMastermind** 表示对学习Lean感兴趣，但对某些复杂语法感到困扰，例如`let rec helperMemo : Nat → HashMap Nat Nat → Nat × HashMap Nat Nat`，认为这种语法难以解析，容易忽略重要细节。 • **Gehinnn** 分享了使用经典证明方法（通过强归纳法）的实例，并指出了在算法中进行证明的优点，即不需要复制外部证明的分支结构。同时，Gehinnn提到在Lean中处理变量和语法细节（如r.fst/r.snd与r=(fst, snd)的区别、.get? k与[k]?的混淆）时遇到的困难。 补充讨论： • **jeremyscanvic** 对某个技巧表示了兴趣，但没有深入展开。 • **almostgotcaught** 认为该证明是通过穷举法实现的，指出这种证明方法可以在任何支持递归的语言中实现，并提到如果不使用递归，可以转化为自底向上的公式。 • **xnacly** 提到了sigma类型，但没有进一步展开讨论。 争议焦点： • CSMastermind对Lean的复杂语法表示不满，而其他用户如Gehinnn则更关注在Lean中进行证明和处理具体细节时遇到的挑战。这反映了对Lean语言学习曲线的不同看法。

Show HN: lambda-nat-proxy – Serverless proxy using Lambda and UDP NAT punching

作者: danvittegleo | 评分: 15 | 评论数: 4 | 发布时间: 2025-06-17 19:01
文章摘要

**Lambda NAT Proxy** 是一个无服务器代理实现，利用NAT打洞技术通过AWS Lambda函数建立QUIC隧道。其工作原理分为三个阶段：首先通过STUN协议获取公共IP并写入S3桶以触发Lambda函数；然后通过UDP包进行NAT打洞，建立双向NAT映射；最后通过QUIC协议建立加密隧道，用于流量转发。该系统无需EC2实例或SSH隧道，只需配置Lambda函数和S3。用户通过配置SOCKS5代理（localhost:1080）使用该代理服务，流量路径为：浏览器 → SOCKS5 → QUIC隧道 → Lambda → 互联网。系统支持不同性能模式，并自动管理会话和资源清理。

评论摘要
主要讨论点：在不同技术方案下实现数据处理和网络隧道的成本与技术复杂性 不同观点： • [pbnjay] 认为使用大量数据通过某些服务（如AWS Lambda）可能会变得相当昂贵，并提出如果在Lambda上实现Tailscale DERP服务器会很有趣。这暗示了对成本的关注以及对技术创新的兴趣。 • [robcohen] 提出了另一种方案，即使用Nix flake生成基于Solo5的微VM镜像，运行MirageOSunikernel，并通过UDP hole punching和relay fallback实现NAT traversal。这种方法可以在Fly.io上部署，作为轻量级、自动扩展的Firecracker VM，并且是按秒计费，成本可能低于Lambda。他质疑使用Lambda的必要性，认为其云无关的方案可能更具成本效益。 • [shayonj] 对[robcohen]的概念表示兴趣，并表达了对廉价且“一次性”的隧道设置方法的渴望，希望减少对出口节点的负担。这反映了对简单易用和低维护成本的解决方案的需求。 • [danfritz] 对整体方案表示兴趣，但更关注实际成本，表明了对潜在高成本的担忧。 补充讨论： • 争议的焦点主要集中在成本和实现复杂性上。一方面，[pbnjay]和[danfritz]关注的是使用某些服务（如Lambda）的潜在高成本；另一方面，[robcohen]提出了一个他认为更具成本效益和灵活性的替代方案，但该方案可能涉及更高的技术复杂性。 • [shayonj]的观点补充了对易用性和低维护成本的用户需求，这在讨论中增加了一个新的维度，即不仅要考虑成本，还要考虑用户体验和实现的简便性。 • 讨论中提到的技术细节（如Tailscale DERP服务器、MirageOS unikernel、UDP hole punching等）展示了实现网络隧道和NAT traversal的不同技术路径，反映了技术社区中对创新和效率的持续追求。
