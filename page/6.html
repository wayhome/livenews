Intelligent Kubernetes Load Balancing at Databricks

作者: ayf | 评分: 111 | 评论数: 7 | 发布时间: 2025-10-01 05:06
文章摘要

Databricks面临Kubernetes默认负载均衡在高吞吐量gRPC连接时的性能瓶颈，包括尾部延迟高、资源利用不均等问题。为此，他们构建了一个客户端驱动的负载均衡系统，通过自定义RPC客户端和xDS控制平面实现应用层（L7）的每请求负载均衡。相比Kubernetes默认的L4代理方案，新系统支持更复杂的路由策略（如P2C、区域亲和），减少了DNS依赖，提高了资源利用率并降低了尾部延迟。该系统采用轻量级客户端模型，在保持高性能的同时提供了更精细的流量控制能力。

评论摘要
主要讨论点：[Databricks 采用的 gRPC 客户端负载均衡方案及其替代方案] 不同观点： • **支持现有方案的观点** - shizcakes 提到他们自 2018 年起使用 kuberesolver 进行 gRPC 客户端负载均衡，效果稳定可靠。 - bbkane 指出 gRPC 标准也在向“无代理”模型发展，例如通过 xDS 实现客户端负载均衡。 • **提出替代方案的观点** - jedberg 质疑为什么没有使用 rendezvous hashing（HRW），认为这种方案完全符合需求，且无需实时更新主机列表。 • **对方案适用性的疑问** - dilyevsky 对跨集群负载均衡的必要性提出疑问，尤其是在数千个客户隔离集群的环境中是否真的需要这种功能。 • **对现有技术的补充说明** - thewisenerd 指出 kube-proxy 实际上支持更多负载均衡算法（如加权轮询），但 Kubernetes 本身无法表达这些细节（如权重）。 - 他还提到 HTTP 长连接也存在类似问题，但可以通过配置连接 TTL 缓解。 补充讨论： - 争议焦点在于是否需要引入服务网格（service mesh），thewisenerd 认为 Databricks 的方案（客户端 xDS 同步）比服务网格更简单且故障模式更优。 - 讨论还涉及不同负载均衡算法的适用性（如 HRW vs. Power of Two Choices）。

这篇文章主要介绍了Electron应用在MacOS Tahoe系统上导致全局卡顿的问题，并提供了检测和临时解决方案： 1. **问题描述**：Electron某些版本（低于36.9.2、37.6.0、38.2.0、39.0.0）会在MacOS Tahoe系统上引发系统级卡顿。 2. **检测脚本**：提供了一个shell脚本，用于扫描系统中所有Electron应用并标注未修复版本（显示❌）。 3. **临时解决方案**： - 运行`launchctl setenv CHROME_HEADLESS 1`命令（会禁用窗口阴影） - 提供了创建launch agent的xml配置方法使设置永久生效 4. **修复版本**：列出了已修复的Electron最低版本号（36.9.2、37.6.0等） 5. **示例输出**：展示了多个常见Electron应用（如VSCode、Slack等）当前版本均未达修复标准。 文章最后作者推广了自己开发的天气应用Weathergraph。

CDC File Transfer

作者: GalaxySnail | 评分: 269 | 评论数: 21 | 发布时间: 2025-10-01 02:38
文章摘要

这篇文章介绍了Google存档的CDC File Transfer工具库，主要包含cdc_rsync和cdc_stream两个工具，用于在Windows和Linux之间高效同步和传输文件。这些工具基于内容定义分块（CDC）技术，特别是FastCDC算法，能够智能识别文件变化部分，仅传输差异内容。与标准rsync相比，cdc_rsync速度快3倍（测试中75秒vs 210秒），尤其适合游戏开发等需要频繁传输大文件的场景。文章还简要解释了CDC技术相比传统固定分块方法的优势，以及该工具在Stadia游戏开发环境中的实际应用背景。

评论摘要
主要讨论点：[Content Defined Chunking (CDC) 技术的性能优势及其在文件同步工具中的应用] 不同观点： • EdSchouten 认为 FastCDC 算法可以通过前瞻性优化显著提升性能，并提供了自己的实现。 • MayeulC 和 bilekas 质疑 CDC 的创新性，指出 rsync 已经使用了类似的技术，并讨论了 rsync 的压缩功能是否足够高效。 • tgsovlerkhgsel 和 phyzome 强调了 CDC 在性能上的优势，并提到类似技术在 borg 备份工具中的应用。 • est 提出将 CDC 技术应用于 git，以优化哈希计算过程。 • mikae1 和 AnonC 关注工具的跨平台支持，询问是否支持 Linux 到 Linux 的文件传输。 补充讨论： • rekttrader 和 Sammi 提到了项目的开源状态和潜在的社会价值。 • syngrog66 指出 CDC 名称容易与 USB CDC 混淆。 • modeless 和 janpmz 分别讨论了 Steam 游戏更新和 Tailscale 文件传输的替代方案。 争议焦点： • CDC 技术是否真正创新，还是仅仅是 rsync 现有技术的优化。 • 工具的跨平台支持是否足够广泛，特别是 Linux 到 Linux 的传输。
