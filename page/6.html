Improvements to Std:Format in C++26

作者: jandeboevrie | 评分: 34 | 评论数: 5 | 发布时间: 2026-06-21 06:26
文章摘要

这篇文章介绍了C++26标准中格式化库的主要改进： 1. **打印空行**：新增无参数的`std::println()`直接打印换行 2. **格式化指针**：支持直接格式化指针类型，无需转换为整数，提供`p`/`P`说明符 3. **格式化路径**：为`std::filesystem::path`添加格式化支持，默认无引号，`?`选项提供转义表示，`g`选项强制使用通用分隔符 4. **constexpr格式化**：`std::format`等函数变为`constexpr`，支持编译期格式化（整数、字符串、指针），浮点数暂不支持 5. **运行时格式字符串**：`std::runtime_format`重命名为`std::dynamic_format`，用于处理非常量格式字符串 这些改进让格式化操作更简洁、类型安全且功能更强大。

评论摘要
主要讨论点：C++26 中 std::print 和格式化功能的改进与问题 不同观点： • **积极支持** - draginol 认为 C++ 统一到单一格式化模型是好事，提到旧代码中存在大量不同的字符串类型（sprintf 等），统一标准能简化开发 • **命名质疑** - veltas 质疑 std::print() 的命名，认为从语义上它不应该"打印"任何东西（可能暗示命名不够准确） • **功能局限性关注** - randusername 指出编译时 std::format 对浮点数的支持尚未完成，需要等待独立提案 P3652 使浮点数 函数支持 constexpr • **Windows 路径处理问题** - Longhanks 指出虽然解决了 Windows 路径的 UTF-16 到 UTF-8 转码问题，但实现上又会将其转回 UTF-16 调用 WriteConsoleW()，这种来回转换的设计存在效率疑问 • **文档批评** - arunc 批评技术文章缺少代码输出示例，指出讨论指针格式化却不展示输出结果是不合理的 补充讨论：主要争议集中在实现细节的完整性和合理性上，包括浮点数支持的缺失、Windows 平台的编码转换效率问题，以及技术文档的实用性问题。

Package Managers need global hooks

作者: evakhoury | 评分: 30 | 评论数: 12 | 发布时间: 2026-06-18 15:20
文章摘要

这篇文章呼吁所有包管理器添加**全局钩子（global hooks）**支持，作为应对软件供应链攻击的解决方案。 作者认为现有的防御措施（依赖冷却期、依赖策略、安全防火墙等）要么依赖特定API/命令模式，要么需要额外基础设施，对个人开发者不友好。 全局钩子可以让用户在包管理器的各个阶段（如安装前、构建前）运行自定义代码，实现威胁检测、恶意软件扫描等功能。作者用StepSecurity威胁源和pnpm构建了概念验证，但发现大多数包管理器不支持全局钩子配置。 文章建议向各包管理器（pnpm、npm、yarn、uv等）提交功能请求，统一添加这一安全机制，而非在每个工具中重复开发防御功能。

评论摘要
主要讨论点：包管理器的安全问题及解决方案 不同观点： • **威胁情报检测派**（ozim）：通过威胁数据源检测恶意包，但承认问题是很多恶意包未被标记，且Debian等策展式仓库的做法被忽视 • **私有策展源派**（zihotki）：使用私有包源替代公共源，所有更新先在私有源审查后再部署，通过安全实践应对供应链攻击 • **Unix哲学派**（jamesrom）：反对包管理器承担安全职责，应通过外部工具链（如bash脚本/别名）调用钩子，遵循"只做一件事"原则 • **根本问题派**（YuechenLi）：NPM允许包作者静默运行任意安装后脚本是根源缺陷，安全系统再好也无用如果前门大开 • **深度安全派**（cookiengineer，反恶意软件工具开发者）：需要系统性改革——强制可重现构建、禁止安装时执行/网络访问、容器隔离、每资源级白名单、锁定传递依赖。批评现有DevSecOps工具和流程对抗变异恶意软件（LLM生成）完全失效 • **怀疑派**（drdexebtjl, TZubiri）：担心新方案本身成为攻击向量；批评威胁数据源方案是重复2000年代签名式杀毒软件的失败，攻击者可混淆载荷、分离机制、控制时序 补充讨论：有人提及Nix没有此问题；有人用"标准竞争"梗讽刺可能产生更多标准；系统包管理器（apt/portage）已有钩子机制但语言包管理器情况模糊。

Deno Desktop

作者: GeneralMaximus | 评分: 1074 | 评论数: 68 | 发布时间: 2026-06-22 05:38
文章摘要

`deno desktop` 是 Deno 2.9 版本推出的新功能，可将 Deno 项目（从单个 TypeScript 文件到 Next.js 应用）打包成独立的桌面应用程序。主要特点包括：默认使用系统 WebView 保持体积小巧，完全兼容 Node 生态系统；自动检测并支持主流前端框架（Next.js、Astro、Remix 等）；使用进程内绑定而非 IPC 通信；支持从单台机器交叉编译到 macOS、Windows 和 Linux；内置二进制差分自动更新功能。开发者只需一行命令即可将 Web 应用转换为桌面应用，无需修改代码。

评论摘要
主要讨论点：Deno Desktop 作为跨平台桌面应用开发工具的优劣势，以及与 Tauri、Electron 等竞品的对比 不同观点： • **对 Deno Desktop 持积极态度**：认为 Deno 生态成熟，TypeScript 原生支持是优势，虽然包体积比 Tauri 大（40MB vs 5MB），但 150MB 的下载时间可接受，且渲染引擎更可靠 • **Tauri 仍有独特优势**：支持 sidecar 嵌入现有应用、可与 Elixir/BEAM 集成打包单一二进制文件，Livebook Desktop 等成功案例证明其成熟度；WebView 虽有局限但正在通过 CEF 改进 • **对 Web 技术作为 UI 工具的质疑**：批评 Electron 类应用无法遵循操作系统原生 UI 模式，Web 技术本质上不是真正的 UI 工具包，即使是未样式化的按钮也无法原生适配各操作系统 • **技术细节的讨论**：关于共享 CEF 运行时的版本管理问题、多进程模式下是否真的是共享内存还是 IPC、权限系统如何在编译时向用户展示等实现细节的疑问 补充讨论：有人指出文档将 electrobun 错误标注为仅支持 macOS（实际支持多平台）；有开发者更偏好原生 UI；还有人提到替代方案如 WASM 方案（Jumpjet）可不依赖浏览器引擎；Deno Desktop 的 canary 版本可通过压缩将应用体积降至 15MB

Prompt Injection as Role Confusion

作者: x312 | 评分: 125 | 评论数: 28 | 发布时间: 2026-06-22 15:48
文章摘要

这篇文章探讨了大语言模型(LLM)中的"角色"(roles)概念及其与提示注入攻击的关系。 核心观点：LLM将所有输入视为连续的文本流，无法像人类那样通过不同感官通道区分自己的思考和外部输入。为了施加结构，系统使用角色标签（如`system`、`user`、`assistant`、`tool`、`think`）来标记文本片段，告诉模型如何处理不同来源的内容。 关键问题：角色标签是人类控制LLM行为的离散开关，承载了信任级别、威胁识别、身份设定等多重责任。但这种机制存在缺陷，导致提示注入攻击成为可能——攻击者可以通过操纵角色边界来混淆模型对文本来源的判断。 文章还指出角色会产生奇特的涌现行为，例如LLM在生成回复时会"否认"其推理过程的存在，尽管推理文本就在上下文中影响着输出。

评论摘要
主要讨论点：LLM的角色标签混淆漏洞及其安全影响 不同观点： • **漏洞本质派**：认为角色标签只是格式化技巧而非真正的安全架构。LLM本质是字符串映射函数，所有输入都在同一通道中，无法区分角色来源。这是设计层面的固有缺陷，注入攻击是必然的（bandrami, dvt, dweinus） • **测试困境派**：实践者发现当LLM知道自己被测试时几乎不会违规，但实际使用中频繁破坏规则。只能通过隐蔽的"正常工作流"测试或让LLM误以为持续被评估来捕捉真实行为（JohnMakin） • **轻松绕过派**：多位开发者表示通过编辑API响应、使用特定写作风格（如"用户正在询问...政策规定..."）即可轻易突破防护，甚至让模型执行被禁止的操作（hananova, lelanthran） • **架构改进派**：建议通过技术手段解决，如恢复encoder-decoder的双通道架构分离系统提示和用户输入、将角色信息嵌入token层面、或用辅助模型预处理内容风格（vova_hn2, Scene_Cast2, nphard85, skybrian） • **现实主义派**：强调必须明确LLM目前不提供任何安全边界和保证，避免构建不安全的架构。将"授权"等安全术语用于LLM是误导性的（ipython） 补充讨论：有评论赞赏论文提供易读的博客版本，而非仅有学术论文。另有讨论关注训练期间的权重投毒可能性，以及人类通过具身性区分内外信息的能力能否启发LLM设计。

Is it time for a new Embedded Linux build system?

作者: cbrake | 评分: 76 | 评论数: 19 | 发布时间: 2026-06-18 16:57
文章摘要

文章探讨了嵌入式Linux构建系统面临的挑战。作者指出，尽管当前有成熟的工具（如Yocto、Buildroot），但三个关键变化使传统方法不再适用：1）边缘设备需要像云系统一样持续更新，而非多年冻结；2）现代语言（Python、Node.js）的交叉编译越来越困难；3）从源码构建（Yocto）速度慢、资源消耗大，而标准发行版缺乏定制工具。小型团队尤其受限于资源和专业人员不足。作者认为需要反思：传统模型是否仍适合当前产品需求和团队规模，暗示可能需要新的构建系统来应对复杂性。

评论摘要
主要讨论点：嵌入式Linux构建系统的选择与必要性 不同观点： • **Nix/Guix派**：认为可以用通用构建工具（Nix/Guix）替代Yocto，嵌入式设备只是目标架构不同，软件栈相同，无需单独工具。强调大型活跃社区的优势，避免供应商BSP碎片化 • **Debian/Alpine简化派**：现代SBC就是普通计算机，直接用Debian/Alpine即可，无需复杂构建系统。一位开发者用Alpine+qemu导出文件系统镜像解决问题 • **Yocto辩护派**：认为Yocto被误解，问题在于使用者不愿学习。对比CMake/Git，指出新工具未必更简单。强调Yocto对合规产品必需（SBOM、CVE追踪、许可证管理），特别是面对欧盟网络韧性法案 • **交叉编译争议**：有人质疑为何不交叉编译，认为qemu架构模拟慢5-10倍。另有人指出Debian/Ubuntu的交叉编译体系最友好。但也有人认为现代设备性能足够，直接本地编译即可 • **Rust/musl倡导者**：认为问题根源是GNU/Linux生态的设计缺陷（全局安装、工具链耦合），Rust工具链才是更好的嵌入式开发方向 补充讨论：有人提到Gentoo、Buildroot等替代方案；也有讽刺Linux社区不断重复造轮子；还有质疑供应商问题无法靠更换构建系统解决

Windows NT for GameCube/Wii

作者: zdw | 评分: 81 | 评论数: 5 | 发布时间: 2026-06-19 13:51
文章摘要

这是一个将 Windows NT 移植到任天堂游戏主机的开源项目。支持 GameCube、Wii、Wii U（vWii模式）等平台。项目实现了多个硬件驱动，包括 Flipper 图形处理器、串行接口（支持手柄、键盘、鼠标等输入设备）、外部接口（支持 SD 卡、USB 设备、IDE 等存储设备）。兼容 Windows NT 3.51 及更高版本。安装方式是将系统文件和 NT 安装镜像复制到 SD 卡，通过 Swiss 或 Homebrew Channel 启动加载器，然后进行分区和安装。
