bashblog 是一个用单个 Bash 脚本创建博客的极简工具。核心特点：无需安装依赖，下载 bb.sh 即可使用；通过 `./bb.sh post` 命令写文章；生成纯静态内容，只需服务器的公共文件夹；兼容 GNU/Linux、OSX 和 BSD 系统；支持 Markdown、草稿、标签分类、RSS、Disqus 评论、Twitter 分享、Google Analytics 等功能；代码仅约 1000 行，配置简单，可通过编辑脚本或创建 .config 文件自定义博客标题、作者等信息；自动生成索引页、标签页和备份文件。

主要讨论点：使用 Bash 脚本构建博客系统的合理性 不同观点： • **支持派**：认为 Bash 脚本适合轻量级场景，特别是资源受限的服务器（128MB RAM、1GB 磁盘）。强调掌握 Shell 的实用价值和趣味性，就像了解基础工具的重要性。多位开发者分享了自己用 Shell 构建博客的成功案例（gaigalas、hkt、4mitkumar 等）。 • **反对派**：认为超过几行的 Bash 脚本难以阅读和维护，开发体验糟糕（语法高亮经常失效）。主张即使是简单任务也应使用 Python 等现代语言，因为没有实际优势，且 AI 可以轻松生成。有开发者明确表示"hate bash"，认为其甚至不如 C 语言适合此类任务。 • **折中建议**：amaze_28 提出改进方案——脚本读取本地 .md 文件并部署，而非在终端中直接写作。chiply314 呼吁发明新的轻量级运行时，既小巧又具备现代语言特性。 补充讨论：争议焦点在于"Bash 不需要额外运行时"的论点被质疑（因为用的是 bash 而非 sh）。bluebarbet 关注安全性，希望此类工具通过官方仓库分发而非 GitHub。整体而言，技术选型的讨论反映了实用主义与现代开发体验之间的权衡。

Linux Kills Strncpy

作者: ingve | 评分: 24 | 评论数: 9 | 发布时间: 2026-06-26 06:19
文章摘要

Linux内核历经六年、超过360个补丁，彻底移除了不安全的C字符串函数strncpy。strncpy因无法保证字符串以NULL结尾且会进行不必要的缓冲区填充，容易导致安全漏洞。新的替代函数如strscpy明确分离了字符串保护和缓冲区填充功能，保证目标缓冲区始终是有效字符串，并提供更好的错误返回机制。这次改进在保持效率的同时显著提升了内核安全性，体现了良好API设计的重要性。

评论摘要
**主要讨论点：** Linux内核用strscpy替代strncpy的决策及C字符串函数的问题 **不同观点：** • **支持替换派（okl）：** 详细分析了strncpy、strlcpy、strscpy各自的缺陷。strncpy有填充行为问题，strlcpy的strlen操作不受size参数限制，strscpy是明显改进但仍需注意边界情况（当src未终止且sizeof src < sizeof dest时可能越界读取） • **批评Linux决策派（rakel_rakel）：** 认为Linux应该采用已广泛部署的strlcpy而非自创strscpy。strlcpy可用于用户态，而strscpy的失败返回值超出范围，无法在用户态使用 • **澄清范围派（wpollock, jmclnx）：** 强调这是Linux内核的helper函数替换，不是C标准库的改动。移除的是内核中的strncpy，不影响glibc。若从glibc移除会对应用程序造成严重影响 • **术语批评派（parasti）：** 指出文章标题"C string library"不准确，C只有标准库中的字符串相关函数，不存在独立的"C字符串库" **补充讨论：** uecker分享了自己的字符串和字符串视图类型实验项目作为参考实现
