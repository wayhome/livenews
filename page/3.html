Comptime.ts: compile-time expressions for TypeScript

作者: excalo | 评分: 104 | 评论数: 6 | 发布时间: 2025-08-03 19:11
文章摘要

**comptime.ts** 是一个简单的 TypeScript 编译器工具，允许在编译时评估标记为 `comptime` 的表达式，从而将运行时计算移至编译时，优化代码性能。其灵感来源于 Bun macros 和 Zig comptime。使用时需确保标记的表达式在编译时安全评估，因为该工具不提供隔离。`comptime` 导入仅限于项目文件，但可以从 `node_modules` 导入。 ### 示例 1. **简单求和函数**：编译时计算结果并替换。 2. **零运行时 CSS 库**：将 `emotion` CSS 转换为编译时计算的类名。 3. **常量计算**：如时间单位在编译时转换为具体数值。 ### 安装与使用 - 安装：通过 `bun`, `pnpm` 或 `npm` 安装。 - 使用：支持 Vite 和 Bun 打包工具，通过插件配置启用。 ### 特性 - 支持函数调用和模板字符串等复杂表达式。 - 结果必须可序列化为 JSON。 - 提供 CLI 和 API 使用方式。 - 支持强制编译时评估和 Promise 解析。 ### 注意事项 - `comptime` 标记的 import 语句在输出中会被移除。 - 编译时计算可大幅优化性能，但需谨慎处理副作用和依赖管理。

评论摘要
主要讨论点：对 import 属性使用和编程语言特性的不同观点与期望 不同观点： • [spankalee] 认为使用 `type` 作为 `import` 属性是一种不合理的做法，因为 `type` 应该对应模块的 MIME 类型，如 "json" 和 "css"。在此情况下，JavaScript 文件的 MIME 类型仍然是 `application/javascript`，所以不应滥用 `type` 属性。建议选择其他不同的 import 属性。 • [apatheticonion] 表达了对 Rust 风格的宏和过程宏（proc macros）的渴望，希望在 JavaScript 中使用类似功能。例如，通过类似 JSX 的语法直接定义组件，或者使用 WebAssembly 直接用 Rust 编写 Web 应用。 • [mdarens] 提到了 Zig 语言的编译时特性，并指出当前的讨论特性似乎不适用于像 Zig 中类型级别的编译时泛型。他认为这种能力可以解决 TypeScript 中“联合类型过大”的问题，并认为这是一个强大的特性。 • [Thom2000] 对 `import-with` 语法表示陌生，并指出很难找到相关文档，质疑这是否是一种语法扩展。 • [stevage] 认为这种 import 属性可能对预编译 Markdown 文件有用，显示了对该功能在实际应用场景中的潜力持乐观态度。 • [shortrounddev2] 希望这种 import 属性能够返回命名的函数，显示了对该功能在代码结构和可读性方面的改进需求。 补充讨论： • 对新语法的陌生感和文档缺乏的问题，如 [Thom2000] 所指出的文档不足。 • 不同编程语言特性之间的比较和期望，如 [apatheticonion] 和 [mdarens] 对 Rust 和 Zig 特性的讨论，反映了对 JavaScript 功能扩展的需求。 • 对实际应用场景的关注，如 [stevage] 对预编译 Markdown 的设想，和 [shortrounddev2] 对代码结构改进的期望。

文章摘要

HMPL是一种面向服务器、可定制的JavaScript模板语言，旨在通过向服务器发送可定制的请求并处理成现成的HTML，以减少JavaScript文件的大小。它集成了JSON5和DOMPurify，支持类似于HTMX和Alpine.js的功能，但更加轻量。HMPL使用块状语法，允许开发者在模板中定义请求和响应指示器。例如，当按钮被点击时，可以从服务器获取点击数据并动态更新页面内容。此外，HMPL还支持不依赖JavaScript的DOM操作，通过额外的`hmpl-dom`模块，组件可以直接从服务器挂载到DOM中。HMPL的优势在于其灵活的请求定制、自动生成表单body和缓存支持，适合替代传统的重型前端框架。

Breaking the sorting barrier for directed single-source shortest paths

作者: baruchel | 评分: 132 | 评论数: 8 | 发布时间: 2025-08-06 14:43
文章摘要

文章介绍了一种突破经典算法速度限制的新方法，用于解决计算机科学中的最短路径问题。传统的最短路径算法，如1956年Edsger Dijkstra提出的算法，通过逐步扩展已探索区域来找到从起点到其他所有节点的最短路径。然而，由于最终结果需要排序，这种方法受限于“排序障碍”，无法进一步提升速度。 过去的研究在特定条件下打破了这一障碍，但对任意权重的图仍然无解。直到2021年，清华大学的段然提出了一种新算法，成功打破了排序障碍。该算法的关键在于每一步选择下一个探索节点的策略，避免了排序过程，从而提高了速度。这一成果被视为计算机科学领域的重大突破。

评论摘要
主要讨论点：新算法复杂度及其在图算法中的应用 不同观点： • [o11c] 认为该算法在高度密集图中的表现会更复杂，尤其是当边的数量 `m` 远大于节点数量 `n` 时。他还指出，对于某些图类型（如开放网格图），Dijkstra算法中的前线节点数量是有限的（如`sqrt(n)`），并且提到非基于比较的排序方法（如桶排序）可能在这种算法中更有效。 • [karussell] 关注该算法在社区中的传播，指出这个算法经过多次提交才引起更广泛的关注，带有一定的幽默感。 • [polytely] 对该算法的发现过程表示赞叹，认为这种算法虽然看起来可能在游戏开发中偶然发现，但实际上其发现过程非常了不起。 • [ljlolel] 提到其算法教授Tarjan，并指出Tarjan发明了许多算法，暗示对新算法的创造性持保留态度。 • [aDyslecticCrow] 觉得文章过于冗长且细节不足，期待论文中更详细的描述，并关心新算法如何保证Dijkstra所能提供的“全局最小值”，担心前线节点的聚集可能会导致遗漏某些解。 • [flafla2] 对新算法的复杂度O(m log^2/3 n)表示赞叹，认为这是一个巨大的成就。 • [ape4] 认为新算法比Dijkstra算法复杂得多，但这是算法发展的自然趋势。 • [crawfordcomeaux] 提出将该算法与随机性结合使用，以进一步加快算法的可能性。 补充讨论： • 不同用户对算法复杂度的关注点不同，有的关注数学和复杂度分析（如[o11c], [flafla2]），有的则关心算法的实际应用和潜在改进（如[crawfordcomeaux], [aDyslecticCrow]）。 • 对新算法的发现和传播也有一定的讨论，[karussell]和[polytely]对此表现出一定的兴趣和感慨。 • 争议焦点在于新算法是否能在所有情况下替代Dijkstra，尤其是关于“全局最小值”的保证和前线节点处理的潜在问题([aDyslecticCrow])。

Zig Error Patterns

作者: Bogdanp | 评分: 97 | 评论数: 9 | 发布时间: 2025-08-06 15:03
文章摘要
