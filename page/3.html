文章摘要

AI coding tools can reduce productivity

作者: gk1 | 评分: 71 | 评论数: 12 | 发布时间: 2025-07-10 23:38
文章摘要

文章报道了一项由METR进行的实验，研究AI编程工具对有经验的开发者在成熟项目中的生产力影响。结果显示，使用AI工具的开发者生产力反而下降了19%，尽管他们自己预估AI提高了20%的生产力。研究采用随机对照试验，涉及16名开发者及246项任务。开发者需预估任务完成时间，并随机分配到“允许使用AI”或“不允许使用AI”组。结果表明，AI工具实际上减缓了工作进度，尽管其能快速生成代码，但未必加快整体工作。研究排除了多种干扰因素，如开发者可能因“对抗机器”而更努力工作。文章提醒，AI编程工具虽有潜力，但目前仍有显著局限。

评论摘要
主要讨论点：LLM（大型语言模型）在开发者工作中的实际影响和生产力提升的有效性 不同观点： • **xarope**：担心开发者过度依赖AI生成代码，导致他们将精力放在修正AI输出上，而不是提升自身的编码和研究能力。这类似于在PowerPoint中过度关注格式而非内容。 • **tomcam**：认为40年来一直缺乏对程序员生产力的有效评估方法，对当前关于AI影响的讨论感到困惑。 • **JKCalhoun**：个人经验显示，LLM帮助完成了一些以前不愿意做的任务，例如使用不熟悉的工具（如LeafletJS），从而提升了完成项目的意愿和效率。 • **freetime2**：对研究的方法论提出质疑，指出小样本量和任务分配的随机性可能导致数据不准确。同时，对研究结果的可重复性表示关注。 • **kylecazar**：LLM对不同开发者的影响因人而异，对某些人（如前端开发者）有显著帮助，而对其他人（如低级代码开发者）则作用有限。 • **latenightcoding**：LLM对不常做的前端工作有显著提升（10-20倍），但对低级代码（如C/C++）的帮助主要在于替代StackOverflow搜索。 • **raggi**：质疑额外生成的代码是否必要，是否能降低技术债务和提高长期稳定性。认为需要更深入的理解和分析。 • **softwaredoug**：担心如果社区过度关注LLM带来的短期生产力提升，可能会忽略语言设计和工具创新的长期潜力，导致陷入局部最优。 • **budududuroiu**：发现LLM在UI开发上的表现显著提升，但后来意识到这是由于UI库的功劳而非模型本身的智能。 • **dearilos**：认为通过早期和频繁的代码审查可以抵消生产力的下降，强调好的代码审查流程的重要性。 • **strangescript**：认为当前关于AI影响的讨论是基于AI不会持续改进的前提，而如果AI继续以每月5-10%的速度进步，这种讨论就如同1999年认为互联网是昙花一现。 • **hluska**：经历过多次技术炒作周期，认为生成式AI目前处于“一切都糟透了”的阶段，感到重复和厌倦。 补充讨论： • **研究方法论争议**：freetime2对研究的小样本量和随机任务分配提出质疑，认为这可能导致数据不准确。 • **长期影响和创新**：softwaredoug和raggi都提到需要更深入理解LLM对代码质量和技术债务的长期影响，以及对创新潜力的关注。 • **个人经验差异**：多个评论者（如JKCalhoun、kylecazar、latenightcoding）分享了个人使用LLM的经验，显示出对不同任务和角色的影响差异。 • **AI进步速度**：strangescript和hluska对AI进步速度和当前讨论的局限性提出了不同看法，一个认为AI会快速进步，另一个则对当前的炒作周期感到厌倦。

Diffsitter – A Tree-sitter based AST difftool to get meaningful semantic diffs

作者: mihau | 评分: 97 | 评论数: 11 | 发布时间: 2025-07-10 12:51
文章摘要

**Diffsitter** 是一个基于 **tree-sitter** 的工具，用于生成具有语义意义的代码差异，忽略格式差异（如空格）。它通过比较文件的抽象语法树（AST）而非文本内容来实现这一点。该工具支持多种编程语言，如 Bash、C#、C++、Go、Java、Python、Rust 等。与标准 `diff` 工具不同，diffsitter 能识别出代码结构上的变化，而非仅仅文本格式变化。 用户可以通过配置文件过滤 AST 节点，选择哪些节点参与差异比较。Diffsitter 提供了终端友好的输出格式和详细的日志记录。它支持多种安装方式，包括预编译二进制文件、Cargo、Homebrew、Alpine Linux 和 Docker 等。 示例显示，对于两个 Rust 文件，diffsitter 能准确识别函数内容的增删，而忽略无关紧要的格式变化。

评论摘要
主要讨论点：语义差异工具及其替代方案、应用场景和工具整合 不同观点： • jbellis认为语义diff工具在处理语法无效文件时表现不佳，因此在Brokk项目中选择了标准文本diff。他提到https://github.com/GumTreeDiff/gumtree作为一个更完整且积极维护的选项。 • mertleee更偏好使用langium来解析结构化数据，尤其是在处理更复杂的应用时，并指出Typescript作为开发工具的优点。 • ilyagr提供了另一个选择，https://github.com/Wilfred/difftastic，并分享了相关设计文章链接，推荐了Difftastic工具。 • vrm指出语义diff与AI模型监督之间的深层联系，提出人类编辑和AI生成结合的工作流，并分享了相关研究链接。 • esafak建议开发一个能将大提交分解为小而有意义的原子提交的工具。 • fjfaase提到之前在https://news.ycombinator.com/item?id=27875333已经讨论过类似话题。 • 1-more补充了Difftastic工具的更多信息及其支持的语言。 • pmkary简单称赞了这个想法。 • dcre推荐了https://mergiraf.org/，一个利用AST解决部分合并冲突的工具。 • the__alchemist询问是否存在反tree-sitter版本的工具。 • Iwan-Zotow关注VSCode的整合可能性。 补充讨论： • 讨论中涉及多个工具和资源链接，展示了语义diff工具的多样性和应用场景。 • 争议焦点似乎集中在不同工具的适用场景和优缺点上，例如jbellis对语义diff工具在语法无效文件上的表现不满，而mertleee则偏好langium的性能。 • 还讨论了工具整合的可能性，如VSCode插件和AI模型监督工作流，显示了语义diff工具在实际开发中的潜在应用价值。

评论摘要

Is Gemini 2.5 good at bounding boxes?

文章摘要

文章主要评估了Gemini 2.5 Pro在对象检测任务中的表现，特别是在MS-COCO数据集上的 bounding box 检测能力。结果显示，Gemini 2.5 Pro 的表现与2018年的Yolo V3模型相当。作者通过多种设置（包括有无结构化输出和不同token预算）进行了测试，发现Pro版本优于Flash和Flash-Lite版本，且不使用思考预算时表现更好。整体来看，Gemini 2.5在对象检测上表现尚可，但并未超越传统的CNN模型。

Yamlfmt: An extensible command line tool or library to format YAML files

作者: zdw | 评分: 29 | 评论数: 5 | 发布时间: 2025-07-07 18:13
文章摘要

`yamlfmt` 是由 Google 开发的一个可扩展命令行工具或库，用于格式化 YAML 文件。其主要目标包括创建易于分发的单一二进制命令行工具，并支持通过自定义格式化器进行扩展，还可以作为库使用。该工具目前由 @braydonk 维护，尚未得到 Google 的官方支持。 安装方式包括通过 Go 安装或直接下载二进制文件，二进制文件无需依赖，可直接运行。它支持基本用法、目录递归处理和双星号 glob 模式搜索文件。此外，`yamlfmt` 还可以在 CI/CD 管道中使用，并支持通过 Docker 镜像运行。 工具的配置可通过 `.yamlfmt` 文件实现，并提供了验证发布工件真实性的步骤。
