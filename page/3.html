How to harden GitHub Actions

作者: moyer | 评分: 161 | 评论数: 21 | 发布时间: 2025-05-06 02:07
文章摘要

本文总结了GitHub Actions相关的安全风险及其近期两个攻击事件。首先，去年12月，攻击者利用GitHub Actions漏洞在Ultralytics Python包中植入加密挖矿程序。随后，今年3月发生了“tj-actions”事件，攻击者利用多种反模式进行供应链攻击。具体步骤包括：利用spotbugs漏洞获取访问令牌，推送恶意工作流，泄露GitHub秘密，最终攻击tj-actions代码库。为防范此类风险，建议采取以下措施：1) 将工作流权限默认设为只读；2) 限制使用经过验证的Actions，并使用允许列表；3) 控制工作流的使用和限定运行器至特定代码库。这些措施旨在加强GitHub Actions的安全性，配合GitHub官方指南，提升代码安全。

评论摘要
主要讨论点：GitHub Actions的安全性及其使用中的潜在风险和解决方案 不同观点： • [ebfe1] 提出了一种工具，用于将GitHub Actions中的版本替换为提交哈希，以提高安全性。该工具允许用户控制哪些操作需要固定版本，并提供了忽略某些来自知名组织的操作的选项。 • [20thr] 强调在其公司Namespace中，GitHub任务默认运行在受限的cgroup中，并且需要显式选择才能启用完全权限模式。他们认为多层保护是构建安全系统的关键。 • [cyrnel] 指出，尽管上述建议有帮助，但并没有解决tj-actions/changed-files问题的核心，即不必要的CAP_SYS_PTRACE权限导致的安全问题。建议通过限制依赖项的能力来减少风险。 • [RadiozRadioz] 质疑使用大量第三方Actions的必要性，并认为基础的构建和部署可以通过简单的脚本和容器完成，而不需要依赖过多的预制步骤。 • [duped] 批评GitHub Actions的设计缺乏锁定机制，建议引入类似现代包管理器的校验和验证功能，以防止安全漏洞。 • [newman314] 提到Step Security工具可以帮助保护GitHub Actions的安全性，并提供了一个链接。 • [kylegalbraith] 强调GitHub Actions面临多种安全风险，尤其是自托管 runner 的使用可能引入更多潜在风险，建议使用无持久性的runner来减少攻击面。 • [axelfontaine] 对自托管 runner 不应与公共仓库一起使用的观点提出异议，认为通过使用即时令牌和临时runner可以实现安全性。 • [cedws] 分享了在工作中审查第三方Actions时发现的危险做法，如运行未固定的安装脚本，并表示正在开发内部替代方案。 • [tomrod] 表示支持广泛使用GitHub Actions，但对其供应链攻击的风险表示担忧。 • [wallrat] 提到正在关注一个项目ghasum，它可以为所有Actions创建可验证的校验和清单。 • [bob1029] 强调最安全的GitHub Action是尽量不使用，并指出过于复杂的权限配置容易导致安全问题。 • [diggan] 认为在使用第三方Actions时，审查代码本身比依赖流行度或其他指标更为重要。 • [MadsRC] 分享了一个用于检测和修复未固定依赖项的CLI工具，并提到正在开发递归扫描功能。 • [DGAP] 提到一个开源的沙箱工具bullfrogsec，认为其对保护GitHub Actions有帮助。 补充讨论： • 争议焦点在于如何有效保护GitHub Actions的安全性，包括是否应使用第三方Actions、如何处理权限配置、是否需要固定版本及校验和机制等。 • 不同工具和方法被提及，如自动替换哈希的工具、cgroup限制、沙箱工具和校验和清单等，显示出社区对解决安全问题的多样化尝试。 • 自托管runner的使用及其潜在风险也被广泛讨论，强调了无持久性和最小权限原则的重要性。

Using Coalton to implement a quantum compiler (2022)

作者: andsoitis | 评分: 29 | 评论数: 2 | 发布时间: 2025-05-05 06:31
文章摘要

本文介绍了使用Coalton语言为量子编译器实现新功能的过程。量子编译器quilc是一个用Common Lisp编写的先进优化编译器，负责将量子程序编译和优化为适应多种量子计算架构的代码。然而，由于动态类型语言的局限性，quilc存在运行时类型错误和缺乏静态类型系统支持的抽象问题。Coalton作为一种严格类型的语言，能够解决这些问题。 文章重点介绍了“离散编译”这一新功能，它通过将任意复杂的量子操作分解为一组基本的原生操作（如RX、RZ、CNOT等），实现了量子计算的通用性。文章还展示了如何利用Coalton简化这一功能的实现，并通过具体矩阵分解示例说明了编译过程。最终，通过这种方法，成功将复杂的量子操作编译为IBM量子计算机的原生操作。

评论摘要
主要讨论点：Coalton语言的应用及其在量子编译器中的实现 不同观点： • [dang] 引用了两个过去的讨论链接，指出在2022年9月和2023年6月都有关于使用Coalton实现量子编译器的讨论，但每个链接只有一条评论，表明这些讨论可能没有深入展开或者没有引起广泛关注。 • [reikonomusha] 认为Coalton目前仍在积极开发中，并且已经被一些公司采用。他强调Coalton在设计和实现时直接针对实际产品或研究项目的需求，因此性能并不是事后考虑的因素。他还提到在波士顿地区有一些软件工程职位可以参与Coalton编译器的工作，包括代数类型系统、优化、高性能计算、开发工具等，且这些职位与自主、实时的 firm realtime 系统有关，而与量子计算无关。 补充讨论： • [reikonomusha] 提供了实际的工作机会信息，表明Coalton在实际产品开发中的应用，特别是在高性能计算和实时系统中的使用。这说明Coalton的应用范围可能比仅仅在量子编译器中的使用更为广泛。 • 争议焦点：目前没有明显的争议，但[dang]引用的过去讨论链接显示，关于Coalton在量子编译器实现中的应用可能缺乏广泛讨论和关注，而[reikonomusha]则强调了Coalton在其他实际应用中的价值。 总结：讨论主要围绕Coalton在量子编译器实现中的潜在应用及其在更广泛领域中的实际使用情况展开。不同观点集中在Coalton的应用范围和其在实际产品开发中的价值。

Show HN: Using eBPF to see through encryption without a proxy

作者: tylerflint | 评分: 147 | 评论数: 15 | 发布时间: 2025-05-08 16:49
文章摘要

Qtap 是一个基于 eBPF 的代理工具，能够在 Linux 内核中捕获加密前的网络流量，提供有关出口连接及其发起进程的详细上下文。它通过附着到 TLS/SSL 函数来截获加密前后的数据，并将其传递给灵活的插件，提供完整的可见性（进程、容器、主机、用户、协议等）。Qtap 无需修改应用程序、安装代理或管理证书，即可帮助理解出口流量的详细情况。它适用于安全审计、网络问题调试、API 开发、第三方集成故障排查、协议学习与探索、遗留系统调查和验证测试等多种场景。Qtap 要求 Linux 内核 5.10+ 并启用 BPF Type Format (BTF)，且需要提升权限来运行。项目目前处于早期开发阶段，欢迎社区反馈和贡献。

评论摘要
主要讨论点：通过eBPF技术拦截和分析加密流量的方法及其相关工具的讨论 不同观点： • bbkane认为，Go程序在进程内完成加密，数据在eBPF拦截前已经被加密，因此eBPF可能无法拦截Go二进制文件的加密数据。 • eptcyka质疑在能够使用strace追踪二进制文件的情况下，为什么不能直接导出 session keys，并提出该方法可能不适用于Android上的应用程序中间人攻击（mitm）。 • compscidr分享了在Android手机上进行VPN类网络工作的经验，表示目前已经通过拦截数据包并使用pcap文件或tcp sockets进行分析，但希望简化密钥设置过程。 • worldsavior指出已经存在诸如frida等工具可以用于查看加密请求，质疑使用eBPF的优势。 • pclmulqdq提到要hook OpenSSL需要动态链接或在用户空间程序中编译钩子，而Go和一些Rust、C++二进制文件通常倾向于静态链接，质疑该解决方案的可行性。 补充讨论： • zxilly提到一个类似的工具ecapture（https://github.com/gojue/ecapture）。 • Severian询问是否有类似的Windows工具，并表示需要在不关闭和替换现有构建的情况下进行TLS通信的实时检查。 • kristopolous提到另一个相关工具httpdbg（https://github.com/cle-b/httpdbg），并询问其他用户的体验。 • nikolayasdf123担心这种技术可能成为复杂CVE攻击链中的一环，询问如何确保安全性。 • da hateb询问该工具是否适用于Android，指出eBPF在Android上也可用。 • 0nethacker1喜欢该工具不影响性能的特点，相比mitm解决方案有优势。 • armitron指出类似的实现有很多，但都存在一些不足：uprobes可能带来性能开销，EBPF需要提升权限且在Linux外不广泛可用，无法用于JVM、Rust等不使用钩子函数的运行时环境。 • delusional询问使用模式是否需要root权限，并表示希望在容器内更容易地进行流量嗅探。 • adampk询问设置过程的难易程度，以及是否需要深度集成到生命周期的每一步。 争议焦点： • 该技术是否适用于所有类型的二进制文件和运行时环境（如Go、Rust、JVM）。 • 在能够使用strace或类似工具追踪二进制文件的情况下，是否还需要eBPF来导出session keys。 • 该工具的性能优势与安全性如何权衡。 总结： 讨论围绕eBPF技术在拦截和分析加密流量方面的应用展开，参与者提出了对该技术适用性、性能、安全性及与其他工具对比的多种看法，并分享了在不同平台和环境中的使用经验。
