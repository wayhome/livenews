C++ Trailing Return Types (2022)

作者: susam | 评分: 4 | 评论数: 0 | 发布时间: 2025-07-17 09:16
文章摘要

C++11引入了尾随返回类型语法，作为声明函数返回类型的一种替代方式。传统方式是在函数名前声明返回类型，而尾随返回类型则是在函数名和参数后声明，使用`auto`作为占位符。这种语法在函数模板中特别有用，尤其是当返回类型依赖于模板参数时。例如： ```cpp template auto multiply(A a, B b) -> decltype(a * b) { return a * b; } ``` 使用尾随返回类型的优点包括语法的一致性、更接近数学表示法、以及提高可读性。然而，缺点是大多数开发者不熟悉这种语法，可能导致代码与现有C++生态不一致，并且对于简单函数，这种语法可能需要更多输入。 C++14引入了返回类型自动推导，进一步简化了某些情况下的代码书写： ```cpp template auto multiply(A a, B b) { return a * b; } ``` 总体而言，尾随返回类型有其优势，但缺乏熟悉度和增加输入量是需要考虑的因素。

How we tracked down a Go 1.24 memory regression

作者: gandem | 评分: 83 | 评论数: 3 | 发布时间: 2025-07-17 20:02
文章摘要

文章主要讲述了在升级到Go 1.24版本后，作者的团队发现服务内存使用量意外增加了约20%。尽管Go 1.24本应通过新的"Swiss Tables"特性减少内存和CPU开销，但升级后系统级指标显示内存增加，而Go运行时指标却没有变化。团队通过排查主要更新、深入分析系统级内存指标，发现问题在于虚拟内存更多地被提交到物理内存，导致系统指标与Go运行时指标不一致。最终，团队确认问题根源是运行时 refactor 引入的细微内存分配器回归问题，并与Go团队合作确认了原因。文章还预告下篇将介绍如何利用Go 1.24的"Swiss Tables"显著减少内存使用。

评论摘要
主要讨论点：CPU缓存和内存布局对数据查找性能的影响，特别是针对键值对存储结构的优化以及现代数据结构的学习资源。 不同观点： • [dh2022] 认为当前的桶内存布局（[k1,v1],[k2,v2],[k3,v3]）在迭代查找时，由于每个键值对的大小接近CPU缓存行的大小（64字节），导致每次迭代都需要从RAM中获取数据，降低了性能。他提出了一种替代布局，即先存储所有键，再存储所有值（k1,k2,k3,...,v1,v2,v3），认为这种布局可以在查找时将多个键加载到缓存中，从而提高迭代速度。不过他也指出了这种方法的缺点，即如果查找的键通常是桶中的第一个键，那么当前的布局可能更好，因为键值对都在同一个缓存行中。 • [neuroelectron] 对[dh2022]的评论表示赞赏，但没有提出技术性意见，而是表达了对以前工作的怀念。 • [nitinreddy88] 对讨论的优化问题兴趣不大，更关注于学习现代数据结构（如Swiss tables）的实现，尤其是那些利用现代硬件特性（如SIMD）进行优化的数据结构。他询问了学习这些现代数据结构的最佳资源。 补充讨论： • 争议的焦点在于两种内存布局的性能权衡。[dh2022]提出的替代布局在查找性能上可能更优，但其缺点是如果查找通常命中桶中的第一个键，则当前布局更好。这涉及到具体应用场景的选择和权衡。 • [nitinreddy88] 提出了对现代数据结构实现的学习需求，特别是那些利用现代硬件特性的数据结构，这是一个值得进一步讨论的方向。 总结：评论主要讨论了内存布局对性能的影响以及现代数据结构的学习资源。不同的观点集中在内存布局的性能权衡以及学习资源的推荐上。

Zig Interface Revisited

作者: ww520 | 评分: 89 | 评论数: 7 | 发布时间: 2025-07-16 16:52
文章摘要

这篇文章介绍了如何在Zig语言中通过动态分派实现多态性，特别是使用虚拟函数表（VTable）接口模式。Zig没有内置的接口机制，但可以通过其他方式实现多态，如泛型和编译时调度、标记联合以及VTable接口。文章重点讲解了如何利用VTable构建接口，使得不同类型的实现（如日志记录器）能够共享同一接口并支持动态分派。文章给出了一个示例，展示了如何为控制台日志和文件日志实现独立的日志记录器，并通过VTable接口模式将它们统一起来使用。这种方法实现了接口与实现的清晰分离，且无需修改实现类型，同时支持通过函数指针进行完全的动态分派。

评论摘要
主要讨论点：Zig 编程语言的接口支持、语法一致性以及动态分派和 vtable 的使用 不同观点： • [lenkite] 认为 Zig 缺乏原生的接口支持，导致手动处理函数指针和分派机制非常繁琐且容易出错。建议在标准库中增加辅助工具或代码生成器来简化这些操作。虽然 Zig 是低级编程语言，但现代编程中接口支持应是基础功能。否则，用户可能会创建自定义的代码生成器，导致不一致性。 • [int_19h] 讨论了 Zig 中 vtable 设计的不同之处，指出 Zig 的 vtable 是附加在每个实例上的，而非共享的。这种设计在实现对象时仍需额外的间接调用。与传统的 C++ vtable 设计相比，这种做法显得不够优化。 • [billmcneale] 对 Zig 的语法不一致性提出批评，指出在命名约定中存在驼峰命名（Camel case）和蛇形命名（Snake case）混用的情况，并提到 "anyopaque" 等不明确的关键字，增加了语言的混乱。 • [justinhj] 表示，通常开发者会认为自己不常使用的语言如果加上自己喜欢语言的某个功能就会变得完美。暗示对 Zig 添加接口支持的需求可能只是个人偏好。 • [kingstnap] 认为将 `pub fn implBy(impl_obj: anytype)` 放在不寻常的位置是不合理的，建议学习 Zig 中分配器的做法，通过 `getLogger` 函数来创建 logger，以保持实现的私有性，并提高代码的清晰度和可维护性。 • [andsoitis] 提出关于动态分派和 vtable 使用的疑问，询问是否所有代码库都使用相同模式，以及这种设计是否会影响应用程序和库之间的互操作性。 • [ozgrakkurt] 支持使用 vtable，认为 vtable 在编译时间和代码整洁性上具有优势，相比使用泛型更加清晰。 补充讨论： • 争议的焦点在于 Zig 是否需要原生的接口支持，以及现有 vtable 设计的合理性。 • 语法一致性和命名约定也是部分开发者关注的重点。 • 动态分派和 vtable 的使用优劣在不同开发者之间存在不同看法。

Erythritol linked to brain cell damage and stroke risk

作者: OutOfHere | 评分: 46 | 评论数: 6 | 发布时间: 2025-07-20 02:02
文章摘要

一项由科罗拉多大学博尔德分校进行的研究显示，广泛使用的糖替代品——赤藓糖醇，可能并非无害。尽管赤藓糖醇因低热量和不影响胰岛素水平而被推荐给肥胖和糖尿病患者，但新研究发现，即使是少量赤藓糖醇也会损害脑血管细胞，导致血管收缩、血栓形成和炎症，从而增加中风风险。实验中，研究人员用相当于无糖饮料中赤藓糖醇含量的样本处理血管细胞，发现这些细胞的一氧化氮减少，内皮素-1增加，血栓分解能力降低，自由基增多。尽管该研究是在细胞层面进行，但作者建议消费者留意食品标签，控制赤藓糖醇摄入。

评论摘要
主要讨论点：关于赤藓糖醇（erythritol）研究结果是否能用于指导人类健康行为的争议 不同观点： • **duffpkg的观点**：认为该研究只是在细胞培养中进行的，不能直接影响人类健康行为的建议。指出文章做了许多研究本身不支持的推论，并提供了研究的原始链接，强调需要谨慎对待研究结论。 • **jcynix的观点**：提到赤藓糖醇天然存在于一些水果和发酵食品中，如奶酪、蘑菇、李子、草莓和开心果。质疑实验室实验的条件可能与日常摄入量不符，实验中使用的剂量可能高于正常饮食中的摄入量。 • **IcyWindows的观点**：对实验中使用的剂量表示怀疑，质疑是否整个饮料的量都会作用于细胞培养。 • **MichealCodes的观点**：以个人经验为例，提到自己已经摄取大量赤藓糖醇超过10年，询问应该注意哪些健康指标，如血压。 • **mixwpl0j的观点**：质疑选择人工甜味剂替代天然糖分的人群的健康状况，认为这些人可能本身健康状况就不佳，暗示选择人工甜味剂可能反映出其他健康问题。 • **Eisenstein的观点**：指出该研究是体外研究，引用了一项人类研究（Witkowski et al., 2023）来支持其对人类影响的主张，但该研究存在一些问题，包括研究对象多为心血管疾病患者、未考虑体内天然产生的赤藓糖醇、未区分赤藓糖醇的来源是摄入还是自然产生等。此外，另一项研究（Khafagy et al., 2024）得出了相反的结论，指出没有证据支持赤藓糖醇增加心代谢疾病风险。 补充讨论： • 争议的焦点在于该研究的适用性及其结论的可靠性，特别是在人类健康方面的推论。 • 讨论中提到了天然赤藓糖醇和人工添加赤藓糖醇的区别，以及实验剂量与日常摄入量的差异。 • 个人经验与科学研究之间的对比和如何将研究结果应用于日常生活也是讨论的重要方面。 • Eisenstein的评论特别指出了引用研究的局限性和潜在矛盾，增加了讨论的复杂性。
