Djevops: Self-Host Django Easily

作者: mherrmann | 评分: 11 | 评论数: 2 | 发布时间: 2026-06-18 08:47
文章摘要

djevops 是一个用于将 Django 应用部署到 Linux VPS 的命令行工具。其主要特点包括： **核心优势**：不使用 Docker，部署速度快（秒级），配置比 Ansible 简洁，专为 Django 优化。 **主要功能**： - 自动生成和续期 SSL 证书 - 支持 SQLite 和 PostgreSQL 数据库 - 自动数据库备份（通过 Litestream 或 pgBackRest） - 错误邮件通知 - 支持 Celery 后台任务和 Redis - 便捷的日志管理 **使用方式**：通过简单的配置文件定义服务器、Git 仓库、数据库、邮件等设置，执行 `djevops deploy` 即可完成部署和更新。适合需要快速自托管 Django 应用的开发者。

评论摘要
主要讨论点：应用部署方式的选择——容器化 vs 传统方案 不同观点： • **容器化阵营（mmarian）**：偏好使用 Docker，认为即使在低成本环境（5美元/月 VPS）也能有效运行 Docker Swarm 集群，管理约10个服务，证明容器方案的成本效益 • **传统方案阵营（spwa4）**：质疑过度工程化趋势，建议回归 Apache 的 mod_php、mod_python 等传统模块，强调这些方案部署简单、依然有效，特别是在运行多个小型站点时效率更高，且无需完美隔离 补充讨论：核心争议在于**复杂性 vs 效率**的权衡。一方展示容器化在资源受限环境下的可行性，另一方则质疑是否需要如此复杂的隔离机制，认为传统共享托管模式在特定场景下更务实。两种观点代表了现代云原生架构与经典 Web 托管理念的碰撞。

Developers don't understand CORS (2019)

作者: toilet | 评分: 130 | 评论数: 27 | 发布时间: 2026-06-21 01:35
文章摘要

这篇文章指出许多开发者不理解CORS（跨域资源共享）的工作原理。作者以Zoom的安全漏洞为例：Zoom在本地运行web服务器时，为绕过CORS限制，采用了图片尺寸编码数据的方式，而非正确设置`Access-Control-Allow-Origin`头。这导致所有网站都能访问该服务器，造成严重安全隐患。正确做法应该是设置CORS头仅允许`https://zoom.us`访问。作者强调这不是个例，很多开发者因不理解CORS而采用不安全的解决方案，呼吁开发者正确使用CORS而非绕过它。

评论摘要
主要讨论点：开发者对CORS机制的普遍误解及其难以理解的原因 不同观点： • **CORS的实际作用被误解**：muvlon指出文章错误理解了CORS——它不能阻止其他网站向服务器发请求，只是控制JavaScript能否读取响应。请求本身总会发生，后端必须自行验证安全性。 • **威胁模型难以理解**：frogulis和somat认为CORS难懂的根本原因是其安全模型"反直觉"——不同于常规的"服务器验证客户端权限"，CORS是为了防止"自我注入攻击"（如恶意广告代码），本质上是"不信任自己应用中的代码"。 • **遗忘问题**：mparnisari和ozim表示CORS是需要周期性复习的知识，因为它属于"设置后遗忘"的配置，后端开发者日常很少遇到，只在新项目初始化时碰到。 • **实践困难**：piyh和thomask1995提到CORS调试困难——错误信息被故意简化、难以区分故障类型，且在本地开发、CI和生产环境需要不同配置，特别是使用隧道和代理时。 补充讨论：kartoshechka指出文档问题（多从实现而非"为什么"角度编写）和团队协作问题（前后端需配合但开发者不爱沟通）。stephbook表示仍不理解威胁模型，认为没有Cookie/JWT的跨站请求本就会失败。
