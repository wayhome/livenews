Redis 8.8 正式发布，带来显著性能提升和多项新功能。性能方面，多种数据类型的操作吞吐量提升最高达83%，持久化和复制速度提升60%。新功能包括：全新的通用数据结构array（索引可寻址的动态数组）、内置的窗口计数器限流器、Streams消息NACK支持、哈希字段的子键通知、JSON数值数组存储的显式控制、时序查询支持多聚合器，以及有序集合的COUNT聚合器。这些改进为现有用例提供了更好的灵活性和效率，并开启了新的应用场景。

评论摘要
主要讨论点：Redis 8.8 新功能发布及 Redis 项目现状 不同观点： • **技术细节纠正派（simonw）**：指出官方描述有误，rate limiter 实际使用的是 GCRA（通用信元速率算法）而非窗口计数器，这是一种漏桶算法，只需为每个限流键存储单个整数（理论到达时间），算法设计精巧且受 Brandur Leach 的 redis-cell 项目影响 • **功能需求派（9dev）**：认可 Redis 作为外部数据结构工具的价值，但指出两大不足：1) 缺乏像 SQLite 那样的嵌入式能力；2) 高可用方案过于复杂，需要阅读大量文档理解两种多节点方案，且存在诸多限制使其在许多应用场景不实用 • **许可证担忧派（tapoxi, ShakataGaNai）**：质疑 Redis 许可证变更后是否还有继续使用的理由，提到 Redis/Valkey 分裂事件，以及 Kubernetes operator 停止维护等问题 • **AI 动机质疑派（fga_qwrh）**：认为 Redis 作者突然热衷 AI 是因为数组数据结构在 AI 中的应用，这一动机在数周前就已明显 补充讨论：有用户（caraphon）对新功能持积极态度，认为 rate limiter 和数组功能值得尝试。另有提及 Redis 与 DeepSeek 可能存在合作关系（focusgroup0）。

Ladybird浏览器项目宣布不再接受公开pull request，今后代码变更仅由项目维护者提交。这一改变源于AI工具的普及降低了代码贡献的信任成本——过去高质量补丁意味着投入和诚意，现在AI可快速生成看似优质的代码，使恶意贡献更难识别。对于处理互联网不可信输入的浏览器，一个隐蔽漏洞就可能造成严重后果。项目认为在迈向首个alpha版本的关键阶段，需要更严格的开发流程和明确的责任归属。项目仍保持开源，欢迎bug报告、测试反馈等非代码贡献。

评论摘要
主要讨论点：Ladybird浏览器项目停止接受外部代码贡献引发的开源社区争议 不同观点： • **支持方**：认为AI生成的大量低质量PR已经压垮了维护者，代码量不再能反映贡献者的诚意和能力。SQLite等项目长期采用这种模式证明其可行性。审核AI生成代码的成本已超过自己编写的成本 • **反对方**：这违背了开源精神，切断了发现和培养新维护者的渠道。用户发现bug并修复后却不能直接提交补丁，让维护者重新解决已被解决的问题，极其低效。代码审核应基于质量而非提交者身份或"努力程度" • **中立/观察方**：Chrome、Firefox等大型项目仍保持开放得益于大公司的资源支持。这反映了开源项目规模越大就越难接受外部贡献的客观现实，Blender等成功项目实际上早已这样运作 补充讨论：多人提到这是整个开源生态面临的普遍问题。有人建议建立信任或担保系统来筛选贡献者。也有人对AI时代软件工程的本质变化感到困惑和焦虑，担心这种转变会摧毁开源社区的非代码价值（如思想交流、代码审查等）。
