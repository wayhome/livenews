C extensions, portability, and alternative compilers

作者: xngbuilds | 评分: 138 | 评论数: 11 | 发布时间: 2026-05-25 14:15
文章摘要

文章指出：现实中的 C 代码很少严格遵循 ISO C，往往依赖编译器扩展、库实现细节和大量条件编译。作者以 glibc、`limits.h`、`epoll`、SDL 等为例，说明很多“可移植性”判断其实只兼容 GCC/Clang/tcc，其他编译器即使实现了相同特性也会被排除。核心观点是：C 生态的兼容性常建立在历史包袱和特定编译器假设之上，替代编译器很难真正无缝支持现实代码。

评论摘要
主要讨论点：现实世界中的 C 代码与头文件常依赖 GCC/Clang 扩展和特定平台行为，导致可移植性差；争议集中在“这是普遍现实还是可改进的问题”，以及“应由项目方还是编译器方适配”。 不同观点： • 可移植性批评者：`whizzter` 指出很多 Linux/C 项目是“works on my machine”，在 FreeBSD/Windows 常因 `__attribute__`、systemd 依赖、非 POSIX 行为而失败；`meghprkh` 认为应改用更细粒度、特性检测式判断，而不是只认 GCC/Clang。 • 编译器适配现实派：`WalterBright`、`fuhsnn`、`rurban` 认为现状就是大量工程默认 GCC 生态，做新编译器要兼容这些“怪癖”。例子包括 `math.h` 的 `NAN` 输出、`__attribute__((always_inline))`、`-fvisibility`、坏掉的 VLA/alloca 回退、glibc/NetBSD 头文件限制；`rurban` 甚至主张直接伪装成 GCC 并实现其扩展。 • 标准/可移植性仍常见派：`einpoklum` 反驳“严格 ISO C 很少见”，认为在库、FOSS、嵌入式和多目标平台中，坚持 C99/C89 和可移植性很常见，只是不同领域情况不同。 • 生态演化参考：`kscarlet` 用 Common Lisp 举例，认为多实现并行、扩展竞争、再由可移植库沉淀为事实标准，是更健康的演进方式。 • 强硬开源责任论：`cocodill` 认为嫌不兼容就自己移植到“小众编译器”，责任主要在使用者一侧。 补充讨论：`ndesaulniers` 呼应“连 Clang 编 Linux 内核都需双方打补丁”，强化现实复杂性；`gritzko` 提出如何覆盖“编译器×操作系统”测试矩阵，是讨论中的实际落点。

美国商务部宣布20亿美元CHIPS法案量子计算投资计划，其中IBM获得10亿美元政府资助和10亿美元自有资金，在纽约奥尔巴尼建立Anderon——美国首个纯量子芯片代工厂，采用300mm超导硅晶圆技术。另外9家量子公司（包括GlobalFoundries、D-Wave、Rigetti等）分获3.75亿至3800万美元不等的资金。这一资金分配策略反映了美国政府押注超导硅路线的制造规模优势，同时对离子阱、光子和中性原子等竞争技术保持小额投资以对冲技术风险。IBM认为该业务到2030年代中期可实现数十亿美元年销售额。

评论摘要
主要讨论点：IBM将量子芯片制造拆分/独立化及其获得政府支持，是否合理、是否有利于量子技术发展。 不同观点： • 质疑IBM母体不适合做前沿增长业务。`mathattack`和`postalcoder`认为IBM长期靠审计、回购、裁员和咨询驱动，像Watson曾被当作销售工具而非真正落地产品，因此量子业务若留在IBM内部也可能被同样消耗，拆分是更现实的选择。 • 认为真正重点不在“20亿美元”，而在“独立foundry”。`madanparas`强调共享制造基础设施可服务多家量子硬件公司，优于各自重复建设洁净室；`amelius`补充欧洲已有公司在研究规模并正走向工业化，暗示这不是IBM独有领先。 • 对政府资金投向量子计算持反对态度。`Scubabear68`认为量子仍处极早期、暂无实用性，用CHIPS Act支持它像是在给IBM输送利益，争议焦点是产业政策应投“未来潜力”还是“当前实用”。 • 讨论技术路线与报道偏向。`caminante`批评文章偏亲IBM，且忽略陷阱离子路线在稳定性、精度、工作温度上的潜在优势；`stogot`借微软先前“新物态”争议，延伸出对量子行业宣传可信度的怀疑。 • 一部分评论偏旁观或调侃。有人困惑IBM如今到底是咨询公司还是仍有科研能力，也有人问芯片能否跑Shor、帮助推理、甚至“跑Doom”，反映大众对量子计算实用性的好奇与陌生。 补充讨论：多条评论还批评原文写作与排版差、信息重复，认为新闻稿反而更清楚。
