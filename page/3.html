I got fooled by AI-for-science hype–here's what it taught me

作者: qianli_cs | 评分: 146 | 评论数: 22 | 发布时间: 2025-05-20 04:57
文章摘要

文章由物理学家Nick McGreivy撰写，讲述了他对AI加速科学研究的期望如何落空。McGreivy曾希望利用AI解决等离子物理中的偏微分方程（PDEs），但发现AI方法的效果远不如宣传的那样好，许多声称AI优于传统数值方法的研究存在不公平比较和数据泄露问题。尽管AI在科学领域的应用迅速增加，但他认为AI对科学的实际影响可能被夸大，科学界正面临可重复性危机。他警告说，AI在科学中的成功可能不如表面看起来那样显著，科学家们倾向于采用AI更多是为了自身利益，而非科学进步。最终，他对AI是否能逆转科学生产力下降的趋势持怀疑态度。

评论摘要
主要讨论点：对AI在科研和实际应用中的效果及其局限性的不同看法，以及对AI研究领域现存问题的讨论。 不同观点： • **AI是否带来实质性进展**： - **plasticeagle**认为，尽管很多人宣称AI将带来重大发现，但实际并未看到AI在任何领域带来显著的突破或渐进式改进，质疑AI是否仅是重新包装现有知识。 - **Flamentono2**则持相反观点，认为AI已经在多个方面带来了突破性进展，例如图像生成和代码自动生成，并强调AI在提高科研效率方面的潜力。 • **AI研究中的问题**： - **nicoco**指出，AI领域并非唯一存在夸大宣传的领域，整个科研出版体系都存在类似问题，负面的结果往往不被发表。 - **sublimefire**提到，AI相关研究的论文质量参差不齐，许多结果难以复现，模型更新换代快，导致难以验证研究结论的普适性。 • **AI对社会和工程技术的影响**： - **therebase**认为，讨论不应仅限于AI带来的技术成果，还应关注其对人类社会的影响，引用了关于AI侵蚀工程技术的文章。 • **科研激励机制和职业化问题**： - **rhubarbtree**认为，学术界的问题如追求引用和职业主义，同样体现在AI研究中，这些问题导致科研不再以追求真理为核心。 • **对AI工具的合理期望和使用**： - **omneity**指出，原文对AI的批评主要集中在特定架构（如PINN）的过度宣传上，而非全盘否定AI在科学计算中的作用。 - **tonii141**和**pawanjswal**强调，AI并非万能，正确理解神经网络的数学基础和适用场景是有效使用这些工具的关键。 补充讨论： • **科研激励和误导问题**： - **raesene9**和**KurSix**提到，理解科研人员的激励机制有助于识别潜在的误导性言论，并将AI研究中的问题与可重复性危机相比较。 • **AI在科研中的实际应用**： - **shalmanese**认为，文章实际上反映了学术界对如何正确解读学术声明的素养问题，强调科学输出是复杂社会技术系统的产物，需要经验积累来正确评估。 争议焦点： • AI是否在实际科研和应用中带来了与其宣传相符的实质性进展，以及AI研究中夸大宣传和难以复现结果的问题是否比其他科研领域更为严重。

Claude Code SDK

作者: sync | 评分: 342 | 评论数: 16 | 发布时间: 2025-05-19 18:04
文章摘要

Anthropic的Claude Code SDK允许开发者将Claude Code集成到应用中，通过命令行运行非交互模式的任务，如执行单个提示、继续多轮对话、自定义系统提示等。SDK支持JSON格式输出和流式JSON输出，并可通过Model Context Protocol（MCP）扩展额外工具和资源，如文件系统和GitHub访问。使用MCP时需通过--allowedTools明确允许工具使用，以确保安全性。SDK还提供多种CLI选项，如--print、--resume、--output-format等，帮助开发者灵活控制操作。TypeScript和Python SDK即将推出。

评论摘要
主要讨论点：Claude Code及其在AI代码助手领域的应用和竞争 不同观点： • d_watt认为Claude Code的"unix toolish"哲学和其在自动化中的应用使其成为理想的编码代理工具，尤其是其能够桥接自动化和无头使用（headless usage）。他还提到针对AI优化的代码库工具（如Rules, MCP）应具备可配置性，并认为Cursor和Windsurf等本地编辑器是死胡同，因为它们无法集成到CI中。 • Vanclief支持Claude Code的使用体验，但希望有一个开源版本，允许用户选择和比较不同的模型，而不是被锁定在某个特定生态系统中。他认为这是消费者最大的担忧，也可能是LLM模型提供商的最大恐惧。 • anotherpaulg提到Aider早已支持Python和Shell脚本，并分享了一个展示其强大功能的截屏视频，展示了如何通过Aider进行脚本编程和支持新编程语言的扩展。 • swyx提供了更多关于Claude Code团队的背景信息，强调了其作为"linux"实用工具的吸引力，以及未来在沙盒、分支和持久性代理模型方面的路线图。 • woah认为将AI代码助手锁定在特定基础模型提供商上是不可取的，除非我们已达到模型效能的稳定期，且所有基础模型的性能趋于一致。 • jiangplus推荐了Codebuff作为一个优秀的CLI代码助手，可以节省大量token成本，并声明自己并非该项目的关联方。 • Wowfunhappy对Claude Code的新功能感到困惑，认为其非交互模式和命令行使用并无新意，质疑其真正的新增价值。 • bionhoward对服务条款中的竞争限制提出了质疑，担心其法律条款的模糊性和执行力度，并对如何拥有和使用AI生成的输出表示担忧。 • karn97对当前模型的编码能力表示不满，希望推出更实用的模型。 • hosainnet对Claude Code的GitHub Action集成表示赞赏，但对其Max计划的API密钥使用限制感到困惑。 • cube2222对GitHub Actions的集成表示赞赏，认为这是他一直想要的功能。 • mirekrusin表示由于工作要求，只能使用Copilot，无法使用Claude Code。 • andrewstuart认为Gemini在功能上已经超越了Claude，尤其是其百万token会话和上传整个代码库的支持。 • m3kw9指出模型锁定是一个大问题，如果出现更先进的模型，已有的基础设施投资可能成为累赘，即使开放使用，也可能因特定CLI的训练问题而失败。 • doctorpangloss表示已取消订阅，未说明具体原因。 补充讨论： • 争议焦点在于Claude Code的模型锁定和开源需求，以及其在生态系统中的竞争力和使用条款的限制。 • 用户对Claude Code的新功能和实用性存在不同看法，部分用户对其集成和自动化能力表示赞赏，而另一些用户则对其新增价值和限制表示不满。 • 对服务条款中竞争限制的法律问题引发了一些用户的担忧，尤其是关于AI生成输出的所有权和使用权。

文章摘要

文章摘要

Ryan Dahl在2025年5月20日的文章中回应了近期对Deno及相关技术（如Deno Deploy、KV、Fresh）的批评。他承认部分批评是合理的，特别是在公司对未来方向沟通不充分方面。然而，关于Deno即将消亡的传闻则严重夸大。自Deno 2发布以来，用户数量已翻倍，平台的速度、简易性和功能性都得到了提升。 关于Deno Deploy，区域减少并非由于失败，而是基于实际使用情况的优化。大多数应用不需要全球部署，而是需要快速、合规和易于调试。Deno Deploy正在演变为一个托管应用的平台，支持更多功能并允许自定义区域部署。 Deno KV作为一个零配置的键值存储受到开发者欢迎，但它并非通用数据库。团队正致力于引入传统关系数据库，并受Cloudflare启发开发新的计算与状态绑定系统。 Fresh框架也在顺利开发中，虽然Fresh 2的发布有所延迟，但这是为了确保质量。团队承诺不久将分享更多进展。

评论摘要
主要讨论点：Deno及其发展方向，尤其是其与Node.js的兼容性、商业化路径以及技术决策的争议。 不同观点： • **对Deno商业化路径的怀疑**： - [afavour] 认为Deno由风投资助，导致其优先考虑投资者期望的财务增长，而非技术创新。Deno被迫转向Node兼容性以减少摩擦，背离了最初作为一个全新JS生态系统起点的愿景。 - [mattlondon] 同样对Deno放弃最初不兼容Node的承诺感到失望，认为这使其失去了独特性。 • **技术决策的批评**： - [sholladay] 指出Deno为了兼容Node，增加了复杂性，导致其比Node更复杂，且存在许多边缘情况未实现的API或选项。 - [rafram] 质疑Deno试图同时成为包管理器、代码格式化工具、编译器、捆绑器等多重角色的合理性，认为不可能在所有领域都做到最好。 - [dbushell] 对Deno的一些技术决策表示失望，尤其是Deno Deploy的区域缩减和Fresh框架的重构。 • **对Deno兼容Node的支持**： - [k__] 认为Deno通过兼容Node保持了生命力，否则可能无法与Bun和Node.js竞争。 • **对Deno Deploy的质疑**： - [nicce] 对Deno Deploy减少可用区域的解释表示怀疑，认为这与实际需求不符。 补充讨论： • **对公司透明度的期望**： - [diggan] 希望Deno能更坦诚地面对批评，并列出其优缺点，以增加用户信任。 • **对Deno未来发展的建议**： - [yahoozoo] 认为Deno偏离了最初的简化和速度优势，变得复杂且多元化，类似于Vercel的多产品策略。 - [NHQ] 建议Deno应专注于浏览器引擎创新，而非仅仅作为一个JS运行时。 争议焦点： • Deno是否应继续坚持其最初不兼容Node的愿景，还是为了市场接受度而妥协。 • Deno的多重角色定位是否合理，以及其技术决策的优先级是否符合用户需求。 总结：评论主要围绕Deno的技术决策、商业化路径及其在市场中的定位展开，反映出用户对其初衷与现实发展的矛盾感受。

Kilo: A text editor in less than 1000 LOC with syntax highlight and search

作者: klaussilveira | 评分: 191 | 评论数: 14 | 发布时间: 2025-05-19 20:28
文章摘要

Kilo是一个小型文本编辑器，代码不到1000行，具有语法高亮和搜索功能。它不依赖任何库，甚至不使用curses库，而是利用标准的VT100终端转义序列。基本用法包括打开文件、保存（CTRL-S）、退出（CTRL-Q）和查找字符串（CTRL-F）。项目处于alpha阶段，代码借鉴了作者其他的项目（load81和linenoise）。Kilo鼓励开发者作为起点，创建更先进的编辑器或命令行界面。该项目由Salvatore Sanfilippo（antirez）编写，并根据BSD 2条款许可证发布。

主要讨论点：文本编辑器的开发与终端使用体验 不同观点： • akkartik认为Kilo项目让他最终放弃了终端，并选择在一个简单的画布上进行编程开发，使用了一个自制的文本编辑器（text2.love），该编辑器功能简单但足够处理复杂文本如《Moby Dick》。 • giancarlostoro分享了自己使用Lazarus开发类似编辑器的经验，并提到使用FreePascal或创建Neovim的GUI的可能性，同时也提到自己在Qt和C++项目中的挫折。 • lor_louis指出Kilo作为基础并不适合开发更复杂的文本编辑器，并推荐使用更适合的数据结构如“piece table”，同时分享了自己的项目cedit，并提供了VS Code相关的参考资料。 • thomasdziedzic推荐了一个教程，该教程详细介绍了如何从头构建类似Kilo的文本编辑器，认为该教程非常优秀。 • anonzzzies表达了对现代编辑器如Vim、Emacs、VS Code的不满，认为它们功能冗余且缺乏实用功能，并有意自己开发一个更好的编辑器。 • JdeBP指出代码中的一些部分可以进一步简化，例如可以利用C库中的现有函数cfmakeraw()。 • 90s_dev认为阅读和构建类似Kilo的代码是一个学习C语言和文本编辑器工作原理的入门仪式，可以学到很多底层知识。 • nodesocket认为Nano已经很好用，Kilo项目可以作为Nano的替代品，但并没有太多改进。 • nulld3v提到Kilo项目启发了类似的Rust项目kibi，但该项目在处理Unicode时使用了unicode-width库，稍微有些“作弊”性质。 • lbj对大家急于脱离终端表示不解，认为终端仍然是很好的开发环境。 • revskill提出文本编辑器是否仅仅是网格操作的问题，引发了对编辑器核心功能的讨论。 • jonstewart简短地提到ed是标准的文本编辑器，暗示其简单和基础性。 • fuzztester幽默地指出，尽管项目名称听起来很“重”，但实际产品却非常轻量。 补充讨论： • 争议的焦点之一是Kilo是否适合作为开发复杂文本编辑器的基础，lor_louis明确反对，推荐piece table结构。 • 另一个讨论点是现代文本编辑器的功能冗余问题，anonzzzies对此表示强烈不满，认为需要更简洁和强大的工具。 • 大家对终端开发的看法不一，有人如akkartik和lbj对终端开发持保留态度，而其他人则认为终端仍然是有效的开发环境。 这些观点展示了不同开发者对文本编辑器开发的多元看法，以及对现代编辑器功能和终端使用体验的不同偏好。
