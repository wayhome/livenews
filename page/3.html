Compaq’s Rod Canion broke IBM's hold on the PC market

作者: vinnyglennon | 评分: 59 | 评论数: 12 | 发布时间: 2025-08-04 01:31
文章摘要

本文讲述了康柏（Compaq）公司及其CEO罗德·卡尼恩（Rod Canion）如何在20世纪80年代挑战IBM在个人电脑（PC）市场的主导地位。IBM曾试图通过专有技术重新掌控PC市场，但卡尼恩决定创建并分享开放标准，与竞争对手共同维护创新，而不是接受IBM提出的垄断合作提议。这一决定打破了IBM的垄断，改变了计算行业的发展方向。文章还介绍了康柏的创立故事，卡尼恩与他的伙伴们原是德州仪器（TI）的员工，因不满上司而决定创业，并看好PC市场的潜力。本文基于历史资料和多本相关书籍，以及对关键人物的采访，展现了康柏与IBM之间的市场争夺战及其深远影响。

Comptime.ts: compile-time expressions for TypeScript

作者: excalo | 评分: 114 | 评论数: 7 | 发布时间: 2025-08-03 19:11
文章摘要

**comptime.ts** 是一个简单的 TypeScript 编译器工具，允许在编译时评估标记为 `comptime` 的表达式，从而将运行时计算移至编译时，优化代码性能。其灵感来源于 Bun macros 和 Zig comptime。使用时需确保标记的表达式在编译时安全评估，因为该工具不提供隔离。`comptime` 导入仅限于项目文件，但可以从 `node_modules` 导入。 ### 示例 1. **简单求和函数**：编译时计算结果并替换。 2. **零运行时 CSS 库**：将 `emotion` CSS 转换为编译时计算的类名。 3. **常量计算**：如时间单位在编译时转换为具体数值。 ### 安装与使用 - 安装：通过 `bun`, `pnpm` 或 `npm` 安装。 - 使用：支持 Vite 和 Bun 打包工具，通过插件配置启用。 ### 特性 - 支持函数调用和模板字符串等复杂表达式。 - 结果必须可序列化为 JSON。 - 提供 CLI 和 API 使用方式。 - 支持强制编译时评估和 Promise 解析。 ### 注意事项 - `comptime` 标记的 import 语句在输出中会被移除。 - 编译时计算可大幅优化性能，但需谨慎处理副作用和依赖管理。

主要讨论点：JavaScript中的宏、编译时计算以及导入语法的使用和扩展 不同观点： • [apatheticonion] 希望在JavaScript中引入Rust风格的宏和过程宏（proc macros），以便用更简洁的方式编写JSX代码，甚至希望通过WebAssembly直接用Rust编写Web应用。这一观点侧重于提高开发效率和代码简洁性，使用其他语言如Rust来增强JavaScript的开发体验。 • [spankalee] 对当前`type`导入属性的使用提出批评，认为这种用法不符合`type`属性在规范中的定义，即应该用于表示导入文件的MIME类型。`spankalee`认为这种扩展使用是不恰当的，建议选择其他导入属性，而不是滥用现有的属性。这一观点关注的是规范的遵循和语义的准确性。 • [stevage] 认为这种语法可能对预编译Markdown等场景有用，支持这种导入语法在特定用例中的应用。这一观点强调了该功能的实用性和潜在应用场景。 • [mdarens] 提到Zig语言中的编译时计算功能，特别是其在类型系统中的应用，如编译时泛型和类型映射。他们认为这种功能在TypeScript中可以解决一些类型系统的局限性问题，如过大的联合类型。这一观点关注的是编译时计算在类型系统中的强大应用。 • [Thom2000] 对`import-with`语法表示陌生，并指出难以找到相关文档，询问这是否是某种语法扩展。这一观点反映了对新语法缺乏了解和文档支持的困惑。 • [revskill] 简单表达了对无需框架即可实现某些功能的满意态度，支持该功能的独立性和简便性。 • [shortrounddev2] 希望该功能可以返回具名函数，提出了对当前功能的一个具体改进建议，关注点在于功能的完善性和实用性。 补充讨论： • 争议焦点之一是`import`属性的使用是否恰当，[spankalee]认为当前用法不符合规范，而其他评论者则关注该功能的实际应用效果。 • 另一个讨论点是编译时计算功能在不同编程语言中的实现和潜力，如[mdarens]提到的Zig语言中的类型系统应用。 • 文档和学习资源的缺乏也是一个值得注意的问题，如[Thom2000]所指出的文档不足，可能影响新语法的推广和使用。

Out-Fibbing CPython with the Plush Interpreter

作者: Bogdanp | 评分: 9 | 评论数: 0 | 发布时间: 2025-08-06 23:18
文章摘要

本文讨论了作者正在开发的名为Plush的玩具编程语言及其解释器的性能优化。Plush具有基于actor的并行机制，并已能支持2D/3D图形和多核并行处理。作者特别关注Fibonacci微基准测试（fib），因为它强调函数调用的执行速度。在测试中，Plush运行fib(38)需要9.10秒，比CPython 3.13.5的5.70秒慢了60%。 为了优化性能，作者首先将bytecode指令中的`push`和`call`合并为`call_direct`，减少了指令分派开销，使时间缩短至8.44秒。接着，作者使用Linux的`perf`工具分析解释器的主要开销，发现延迟编译机制（即函数首次调用时才编译为bytecode）虽然节省了时间和内存，但也增加了函数查找的开销。 作者通过这些优化措施，旨在提升Plush解释器在fib基准测试上的性能，使其能够超越CPython。

Breaking the sorting barrier for directed single-source shortest paths

作者: baruchel | 评分: 132 | 评论数: 8 | 发布时间: 2025-08-06 14:43
文章摘要

文章介绍了一种突破经典算法速度限制的新方法，用于解决计算机科学中的最短路径问题。传统的最短路径算法，如1956年Edsger Dijkstra提出的算法，通过逐步扩展已探索区域来找到从起点到其他所有节点的最短路径。然而，由于最终结果需要排序，这种方法受限于“排序障碍”，无法进一步提升速度。 过去的研究在特定条件下打破了这一障碍，但对任意权重的图仍然无解。直到2021年，清华大学的段然提出了一种新算法，成功打破了排序障碍。该算法的关键在于每一步选择下一个探索节点的策略，避免了排序过程，从而提高了速度。这一成果被视为计算机科学领域的重大突破。

评论摘要
主要讨论点：新算法复杂度及其在图算法中的应用 不同观点： • [o11c] 认为该算法在高度密集图中的表现会更复杂，尤其是当边的数量 `m` 远大于节点数量 `n` 时。他还指出，对于某些图类型（如开放网格图），Dijkstra算法中的前线节点数量是有限的（如`sqrt(n)`），并且提到非基于比较的排序方法（如桶排序）可能在这种算法中更有效。 • [karussell] 关注该算法在社区中的传播，指出这个算法经过多次提交才引起更广泛的关注，带有一定的幽默感。 • [polytely] 对该算法的发现过程表示赞叹，认为这种算法虽然看起来可能在游戏开发中偶然发现，但实际上其发现过程非常了不起。 • [ljlolel] 提到其算法教授Tarjan，并指出Tarjan发明了许多算法，暗示对新算法的创造性持保留态度。 • [aDyslecticCrow] 觉得文章过于冗长且细节不足，期待论文中更详细的描述，并关心新算法如何保证Dijkstra所能提供的“全局最小值”，担心前线节点的聚集可能会导致遗漏某些解。 • [flafla2] 对新算法的复杂度O(m log^2/3 n)表示赞叹，认为这是一个巨大的成就。 • [ape4] 认为新算法比Dijkstra算法复杂得多，但这是算法发展的自然趋势。 • [crawfordcomeaux] 提出将该算法与随机性结合使用，以进一步加快算法的可能性。 补充讨论： • 不同用户对算法复杂度的关注点不同，有的关注数学和复杂度分析（如[o11c], [flafla2]），有的则关心算法的实际应用和潜在改进（如[crawfordcomeaux], [aDyslecticCrow]）。 • 对新算法的发现和传播也有一定的讨论，[karussell]和[polytely]对此表现出一定的兴趣和感慨。 • 争议焦点在于新算法是否能在所有情况下替代Dijkstra，尤其是关于“全局最小值”的保证和前线节点处理的潜在问题([aDyslecticCrow])。

Zig Error Patterns

作者: Bogdanp | 评分: 97 | 评论数: 9 | 发布时间: 2025-08-06 15:03
文章摘要
