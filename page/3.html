The Speed of VITs and CNNs

作者: jxmorris12 | 评分: 52 | 评论数: 4 | 发布时间: 2025-05-02 04:53
文章摘要

本文讨论了视觉Transformer（ViT）和卷积神经网络（CNN）在计算机视觉任务中的速度和扩展性。作者通过实验证明，ViT在分辨率高达1024x1024px²时表现良好，并且在许多现代GPU上速度优于CNN。实验包括在不同设备和批量大小上进行基准测试，结果显示ViT在推理速度、FLOPs和内存使用方面具有优势。作者还指出，高分辨率对于大多数图像处理任务并不必要，常见场景如自然图像和文本图像在较低分辨率下即可满足需求。ViT和CNN的性能差异不仅仅体现在FLOPs上，还涉及实际运行速度和内存效率。总体而言，ViT在扩展性和实用性方面表现优异，适用于大多数计算机视觉任务。

评论摘要
主要讨论点：对"高分辨率"的定义及VITs（Vision Transformers）与ConvNets（Convolutional Neural Networks）在处理高分辨率图像上的实用性讨论 不同观点： • John7878781认为1024x1024不算高分辨率，并以自己使用的4096x2048图像为例，说明在需要保留极高细节的情况下，VITs不切实际。他支持LeCun的观点，不认为LeCun的评论是轻率的。 • ninamoss对原文帖子表示赞赏，并分享了他们使用VITs的积极经验，能够在普通硬件上实现亚秒级的图像评估，同时保持高精度和召回率，暗示VITs在实际应用中是可行的。 • kookamamie同意John7878781的观点，认为1024x1024不算高分辨率，并举例1920x1080视频的分割需求，强调高分辨率的必要性。 • GaggiX反驳了某个评论中关于448px²足够处理文本、图表等的观点，并以自己提供的图表为例，暗示在某些情况下需要更高的分辨率。 补充讨论： • 争议的焦点在于"高分辨率"的定义以及在处理图像时ConvNets和VITs的适用性。部分用户认为VITs在处理高分辨率图像时不如ConvNets实用，而其他用户则认为VITs在优化和调参后可以达到良好的效果。 • 例子如4096x2048图像和1920x1080视频被用来支持高分辨率需求的论点，而不同用户对VITs在实际应用中的表现有不同的体验和看法。

What went wrong with wireless USB

作者: goldenskye | 评分: 296 | 评论数: 20 | 发布时间: 2025-05-04 02:03
文章摘要

本文简要探讨了无线USB技术的历史和其消亡原因，以及与Wi-Fi和蓝牙的比较。作者最初尝试通过Palm OS智能手表进行移动网络连接，但设备缺乏内置网络功能。作者设想通过无线USB解决这一问题，回顾了无线USB曾短暂存在的平行技术世界。无线USB基于超宽带（UWB）技术，旨在提供短距离高带宽通信。然而，由于竞争标准和Wi-Fi的普及，无线USB很快在市场上消失。文章还解释了窄带和宽带无线电传输的区别，以及UWB与雷达脉冲技术的渊源。最终，Wi-Fi和蓝牙的普及使得无线USB未能广泛应用。

评论摘要
主要讨论点：无线USB技术的发展、应用及争议 不同观点： • **Variaga**：认为无线USB技术在2008-2010年期间功能上可行，但未能广泛普及，主要问题在于USB接口同时提供电力，而无线USB仍需通过线缆供电，降低了其价值。此外，还存在“鸡生蛋、蛋生鸡”的采用困境，制造商不愿增加成本去支持一个没有必须外设的技术，而外设厂商也不愿生产无线USB设备。 • **Jauntywundrkind**：提到了无线USB之后的802.11ad和802.11ay（WiGig）技术，这些技术在视频传输和VR应用中得到了使用。同时提到无线USB的替代方案如USB over IP，以及低功耗UWB技术的发展，希望看到更多通用外设互联的应用。 • **M000**：认为无线USB是“锤子法则”（即“如果你只有锤子，所有问题看起来都像钉子”）的案例，USB-IF过于注重硬件解决方案，而忽视了软件解决方案如USB over IP。在ARM架构的单板计算机（SBCs）和WiFi普及的时代，无线USB未能适应新的技术趋势。 • **Marsymars**：提到2017年的Essential Phone使用了无线USB技术进行模块化配件的数据传输，但实际应用非常有限。 • **Brudgers**：认为无线USB听起来很吸引人，但实际上并没有解决重要的实际问题，只是一种“听起来像未来”的噱头，因为无线USB只能消除一根USB线，而WiFi已经能很好地完成类似任务。 • **Liftyee**：对无线传输的带宽限制表示关注，并希望深入理解其中的技术限制。 • **Londons_explore**：主张现代无线协议应支持全IP网络，以实现更多连接可能性。例如无线USB打印机只能单主机连接，而支持IP的打印机可以全网络使用。 补充讨论： • **Ajross**：提到无线USB的竞争技术在遥控车领域（如Spektrum无线电）仍有应用，表明部分无线USB芯片技术在其他市场得以延续。 • **Kensai**：质疑无线USB是否因为标准进展缓慢和竞争标准（如WiFi和蓝牙）的优势而未能普及，并询问关于不同无线标准在实际使用中的能耗对比。 • **Shahzaibmushtaq**：认为在某些情况下，即插即用的有线接口仍然优于无线媒介。 争议焦点： • 无线USB未能普及的原因：技术本身的缺陷（如供电问题）、市场采用困境（鸡生蛋问题）、以及与其他无线技术（如WiFi、蓝牙）的竞争。 • 无线USB的价值：部分评论认为无线USB只是噱头，没有解决实际问题，而其他评论则认可其技术创新和潜力，尤其是在特定应用场景中。

Feather: Feather: A web framework that skips Rust's async boilerplate and jus

作者: todsacerdoti | 评分: 30 | 评论数: 7 | 发布时间: 2025-05-04 16:01
文章摘要

Feather 是一个轻量级的 Rust web 框架，注重开发者体验（DX），灵感来源于 Express.js，但充分利用了 Rust 的性能和安全性。其主要特点包括： 1. **中间件优先架构**：所有功能如路由处理、认证、日志等都是中间件，可组合和重用。 2. **使用 Context API 管理状态**：方便管理全局状态，无需使用提取器或宏。 3. **模块化和可扩展性**：只选择和使用所需功能。 4. **内置 JWT 认证**：通过 Cargo 特性激活。 5. **无 async**：简化开发，避免使用异步编程。 Feather 的目标是成为最易上手的 Rust web 框架，注重模块化和开发者体验。框架提供了 CLI 工具，使得创建 API 和 web 服务器变得简单。示例代码展示了如何使用中间件、管理状态和进行 JWT 认证。

评论摘要
主要讨论点：Rust在web开发中的适用性及Feather框架的设计和性能 不同观点： • [tczMUFlmoNk] 认为Feather框架的单线程设计使其无法实现并发，与Rust提倡的安全并发特性相悖。他通过实验证明该框架在处理多个请求时存在排队延迟，认为这与Rust的性能和安全性设计不符。 • [M4v3R] 表示不推荐使用Rust进行web开发，理由是web开发环境过于动态和混乱，而Rust的强类型系统和所有权模型会降低开发速度。他还提到，Rust在游戏开发领域的热度也在消退。 • [serial_dev] 质疑Feather框架缺乏异步支持，指出大多数后端应用需要处理异步任务，如数据库和外部服务请求，认为缺乏异步支持可能使该框架不实用。 • [ivape] 关心Rust web服务器是否能提供更高的原始性能，并提到Go语言在这方面的优势，暗示高性能聊天或游戏服务器可能是一个适用场景。 补充讨论： • [wishinghand] 提到Feather框架名称可能与JavaScript的Feathers框架混淆。 • [shmerl] 询问DX（开发者体验，Developer Experience）的具体含义。 • [refulgentis] 对Feather框架中`MiddlewareResult::Next`的作用感到困惑，希望了解其在服务器应用中的具体用途。 争议焦点： • Feather框架的单线程设计是否违背了Rust的并发安全性理念。 • Rust在web开发中的实际应用价值和异步支持的重要性。 • Rust在高性能服务器场景中的优势和适用性。
