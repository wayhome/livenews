Lies, Damn Lies and Database Benchmarks

作者: eigenBasis | 评分: 32 | 评论数: 6 | 发布时间: 2026-06-23 02:27
文章摘要

这篇文章讨论数据库基准测试的公平性问题，以ClickBench为例。ClickBench对100多个数据库系统运行相同的分析查询工作负载，测量冷运行和热运行性能。文章指出基准测试存在隐藏的不对称性：自托管数据库需要清除缓存和重启服务器进行真正的冷运行测试，而云托管服务无法做到这点，导致结果偏向云服务。作者聚焦于热运行结果，并解释ClickBench的评分机制是基于各数据库相对于最快系统的几何平均比率。文章强调完全公平的数据库基准测试像独角兽一样难以实现，不同类型数据库的比较尤其复杂。

评论摘要
主要讨论点：数据库基准测试的可信度问题，以及针对基准测试的优化行为 不同观点： • **历史视角（kjellsbells）**：90年代数据库厂商（Oracle、Sybase、IBM等）为TPC-C等基准测试专门优化以获得营销优势；对冷启动测试的质疑需结合实际重启频率分析——五年重启一次则20分钟预热可接受，每小时重启则不可行 • **实用关注（jaapz）**：寻求QuestDB生产环境使用经验，考虑从InfluxDB迁移（因其开源政策反复和频繁重构产品） • **普遍现象（bitlad & N_Lens）**：基准测试作弊是跨领域问题，类比Terminal Bench争议和LLM基准测试；指出合规监督薄弱时必然被利用，如印度教育中"应试而非学习"的现象 • **技术参考（dkdcdev）**：推荐DuckDB团队关于数据库性能测试常见陷阱的论文 补充讨论：ozgrakkurt对QuestDB博客质量表示认可，认为其文章视角和写作都值得尊重

评论摘要
主要讨论点：俄罗斯文学经典（尤其是陀思妥耶夫斯基和托尔斯泰作品）的可读性、翻译质量及阅读体验 不同观点： • **高度赞赏派**：认为《罪与罚》《卡拉马佐夫兄弟》等作品极具感染力，情节紧张刺激如惊悚小说，人物刻画生动。陀思妥耶夫斯基能将伟大文学写得引人入胜 • **阅读困难派**：俄罗斯名字难记是最大障碍，需要做笔记或查维基百科；《卡拉马佐夫兄弟》读到600页仍感吃力；有读者读了几百页《罪与罚》后放弃，认为过多无关人物的生活琐事 • **教育批判派**：俄罗斯本土读者质疑将这些作品列入中学必读清单，认为青少年难以理解角色动机，应该成年后再读才能真正欣赏 • **作家排名争议**：Norm Macdonald认为托尔斯泰是史上最伟大作家，陀思妥耶夫斯基不及托尔斯泰、契诃夫、果戈理等人。但多数评论者更推崇陀思妥耶夫斯基 补充讨论： 翻译版本影响巨大——90年代后的新译本（如Pevear & Volokhonsky）大幅提升可读性，但也有批评认为他们过于逐字翻译，遗漏了幽默和自然表达。有人建议用有声书帮助记忆名字发音。《战争与平和》前200页较难但之后流畅且现代感强。

RubyLLM是一个统一的Ruby AI框架，支持所有主流AI提供商（OpenAI、Claude、Gemini等）。它提供统一接口处理聊天、图像/视频/音频分析、文档解析、图像生成、嵌入向量、内容审核等功能。核心特性包括：工具调用（让AI执行Ruby方法）、可复用的Agent、结构化输出、流式响应、Rails集成等。仅依赖三个库（Faraday、Zeitwerk、Marcel），API简洁统一，无需为不同AI提供商学习不同接口。支持800+模型，包含内置的模型能力检测和定价信息。

PR spam today looks like email spam in the early 2000s

这篇文章分析了 OpenClaw 项目 PR 激增现象。主要发现： 1. **PR 数量暴增但质量下降**：从每周2个增至3400个，合并率从48%降至9.3%。大量低质量 PR 由 AI 编程助手生成，有人一天提交106个 PR。 2. **需要贡献者信誉系统**：类似早期邮件垃圾问题，需要通过信誉过滤。数据显示老贡献者合并率（18.6%）高于新手（8.2%）。 3. **AI 导致思维趋同**：多人用相同 AI 工具提交重复 PR，削弱开源多样性优势。 4. **深度理解更重要**：需要深入理解代码库的重构类 PR 合并率（35%）远高于功能类（9%）。AI 时代，思考比编码更关键。

评论摘要
主要讨论点：开源项目遭遇AI生成的垃圾PR问题及应对方案 不同观点： • **邮件反垃圾机制不适用论**（andix）：邮件反垃圾依赖服务器IP和域名声誉，由组织管理用户行为。但PR/issue是个人行为，无法套用同样机制 • **技术限制派**（guidoiaquinti, giancarlostoro）：GitHub已推出可配置的PR限制功能；建议通过仓库规则集锁定PR权限来防止垃圾提交 • **人工审核派**（j2kun）：要求新贡献者首次PR前必须与维护者进行非文字形式会面，适合小型项目 • **声誉系统倡导**（haneul）：建议建立类似邮件的声誉基础设施，并提供类似uBlock Origin的退订列表 • **讽刺质疑**（janalsncm）：指出文章抱怨AI垃圾PR却发生在OpenClaw（AI工具）自己的仓库，认为维护者应更新工具防止其提交PR到自己项目 • **经济激励方案**（Retr0id）：建议让人们直接向开源项目捐赠代币额度，由维护者决定使用方式 补充讨论：多位评论者（DeepYogurt, fecal_henge）质疑制造垃圾PR的动机和盈利模式；benj111质疑用AI对抗AI垃圾的逻辑矛盾；elzbardico感慨营销思维破坏了互联网早期的美好交流环境。usernametaken29则批评文章本身就是AI工具广告。

评论摘要

文章摘要

Google DeepMind 在 Gemini 3.5 Flash 中内置了计算机使用功能,使开发者能够构建可跨浏览器、移动端和桌面环境进行交互的智能代理。该功能此前仅作为独立的 Gemini 2.5 计算机使用模型提供,现已原生集成到主模型中。为应对提示注入风险,3.5 Flash 采用了对抗性训练,并提供企业级安全防护系统,包括敏感操作确认和自动拦截恶意注入。开发者可通过 Gemini API 和企业代理平台使用该功能,适用于软件测试自动化和企业知识工作等长期任务场景。

评论摘要
主要讨论点：Google Gemini 3.5 Flash 的"computer use"功能发布，以及 Gemini 模型的整体表现和可用性问题 不同观点： • **对 Gemini 模型能力的失望**：用户报告 Gemini 在简单任务上失败（PDF 表格提取后自认无法完成、错误执行 git reset --hard 命令），认为其无法理解基本指令，远不如 Claude 和 GPT • **对"computer use"技术路线的质疑**：部分开发者认为基于截图的方案缓慢、不安全、成本高且容易出错；建议使用可访问性树或直接调用 API 的方式更高效（成本可降低 100 倍） • **Google 生态缺失问题**：Gemini 缺少类似 Codex/Claude 的代码助手界面，没有 MCP 支持，无法进行代码仓库操作和 PR 管理；agy cli 体验差，用户宁愿用免费计划的竞品 • **限制过度的安全护栏**：用户频繁遇到无理由的拒绝响应（SIM 卡转移、备份建议、代码评估等正常需求被拒），体验远不如 ChatGPT • **费率限制恶化**：Google 取消了早期慷慨的 API 限制后，用户大量流失 • **命名和营销问题**：批评"computer use"这个术语过于笼统且误导 补充讨论：用户期待 Gemini 3.5 Pro 版本，质疑 Google 的基准测试图表存在误导性展示
