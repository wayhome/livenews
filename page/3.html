文章摘要

PicoRuby 是一个专为单片微控制器设计的微型 Ruby 实现，具有小尺寸和可移植性特点。它在 32 位架构下仅需 256 KB ROM 和 128 KB 或更少的 RAM。PicoRuby 依赖标准 C 库，如 glibc 或 Newlib，并支持 Raspberry Pi Pico 等微控制器板。它提供了 API 文档和演示视频，并依赖于 mruby/c 实现的虚拟机。PicoRuby 可用于构建 PRK Firmware 键盘固件和 PicoRuby WASI WebAssembly 运行时。构建过程需要 C 工具链、git 和 Ruby 3.0 以上版本。项目仍在开发中，遵循 MIT 许可协议，并获得了 Ruby Association Grant Program 的支持。

评论摘要
主要讨论点：不同微控制器开发语言和工具的比较与选择 不同观点： • **支持MicroPython**：throwaway81523和TkTech认为MicroPython由于其流行性和易用性，是微控制器开发的不错选择，尤其在256KB闪存和32KB RAM的设备上运行良好。即使在资源受限的设备（如BBC microbit）上也能运行，尽管资源紧张。 • **支持picoruby**：aidog和xutopia推荐picoruby，认为它是mruby/c的精简版，非常适合小型设备，且Raspberry Pi Pico上的Ruby REPL展示了其灵活性。aidog还提供了具体参考资料（视频链接）。 • **结合C语言的灵活性**：jononor表达了对MicroPython的喜爱，但也指出C语言在微控制器开发中的重要性，尤其是在需要优化性能时，结合C语言可以获得更好的开发效果。 • **对C语言的争议**：rahil627提到有些人不喜欢C语言，而有些人则非常喜欢，并质疑在微小设备上使用复杂语言（如Ruby）的必要性，同时对C语言的优劣进行了讨论。 • **其他工具的提及**：actionfromafar提到Shedskin Python到C++编译器，提供了一种将Python编译为C++的选项，拓宽了工具选择的范围。 • **资源大小的讨论**：bsder认为256KB闪存和128KB RAM并不算小，指出这比1990年之前的平均计算机资源要多，并强调RAM和闪存的大小直接影响微控制器的成本，因此资源优化仍然重要。 补充讨论： • 讨论中还提及了其他语言和工具，如Lua、Hedgehog Lisp、ulisp、Javacard和J2ME，显示出在微控制器开发中有多种选择。 • 讨论焦点之一是不同语言在资源受限设备上的适用性及其优劣对比，尤其是MicroPython和picoruby的对比。 • 资源的定义和重要性也被提及，特别是在成本和性能优化方面。

Autology: A Lisp with access to its own interpreter

作者: simonpure | 评分: 104 | 评论数: 17 | 发布时间: 2025-03-21 10:37
文章摘要

Autology是一个用Clojure编写的函数式Lisp语言，其特点是能够访问和修改自身的解释器。通过将解释器功能绑定到一个特殊变量`*i*`，程序可以在运行时动态地改变语言的行为和语法。与通常在编译时使用的宏不同，Autology允许在运行时进行语法重写和功能扩展。例如，可以添加函数定义、改变求值顺序或实现 continuation passing style 等。尽管Autology并非实用语言（因其速度慢且资源消耗高），但它是一个探索Lisp元编程的有趣实验工具。

评论摘要
主要讨论点：Lisp及其方言中的内部结构和解释器可访问性，及其在其他语言中的潜在应用和扩展 不同观点： • jlarocco：在Common Lisp中，编译器或解释器通常提供与内部结构交互的包（如SBCL中的`sb-c`、`sb-vm`等）。这种特性允许开发者检查类型、类、函数以及编译器使用的内部数据结构，甚至可以修改编译器的“虚拟操作”并生成不直接支持的汇编代码。这种能力在其他语言中较为罕见，但值得借鉴。 • abeppu：提到Nada Amin和Tiark Rompf的“towers of interpreters”研究，通过显式的分阶段操作来消除解释器开销，并提供相关论文链接。这与讨论中的项目有相似之处。 • bandrami：指出能够访问解释器、扫描器、解析器和编译器是Lisp区别于其他语言的核心特点，这也是Lisp的本质特征之一。 • Kimbsy：这是其项目，并计划在多个会议中讨论。项目灵感来源于John Sturdy的论文，主要探索解释器塔和双向修改的能力。目前尚未发现实际应用，但寻求更多想法。 • ludston：在Common Lisp中，可以通过“Reader Macro”完全控制解释器，并给出了一个玩笑性质的项目示例（fizzbuzz DSL）。 • sargstuff：提出关于Lisp在运行时生成嵌入式虚拟机的问题，并讨论了如何在系统调用fork和lisp列表复制中应用diff操作，还提到并发支持和调试。 • johnisgood：对Kimbsy项目中的“跨语言”示例表示兴趣，并寻求使用场景和想法。 • Cieric：曾尝试创建可修改自身语法的语言，尤其关注如何修改解释器的抽象语法树（AST），但未解决如何实现树结构修改的问题。 • ape4：由于项目使用Clojure并运行在JVM上，建议引入*jvm*变量。 • timonoko：感叹用Lisp自身编写更好的语言，并回忆起在汇编语言上浪费的时间，同时提到时间旅行调试的限制。 • souenzzo：赞赏用1000行Clojure代码探索大量想法的可能性。 • bsima：推荐Shen语言，认为对该话题感兴趣的人会喜欢。 • lifthrasiir：提到CosmicOS项目，认为其具有类似的无缝引入特殊形式的想法。 • JoelMcCracken：联想到Kernel编程语言。 补充讨论： - 讨论中提到了多个相关项目和研究，如“towers of interpreters”研究、CosmicOS、Shen语言和Kernel编程语言，显示出对解释器和语言设计的高度兴趣和探索精神。 - 争议焦点在于Lisp的解释器可访问性是否为Lisp独有的核心特征，bandrami认为这是Lisp的本质，而其他人则探讨了其他语言中类似特性的可能性。 - 项目实际应用场景的缺乏引发了关于其潜在用途的广泛讨论和想法征集。

文章摘要

文章探讨了为什么许多程序员或其他科技工作者常表达想从事手工劳动的愿望，比如木工、务农等。这种情绪通常伴随着对当前工作的不满，尤其是对琐碎且无意义的任务感到厌倦。文章提到，这种趋势在科技行业尤为明显，许多人渴望摆脱办公室、电脑、会议和邮件，追求更具实质意义的手工劳动。这种愿望不仅仅限于个别群体，而是一种更广泛的现代倦怠感。作者以自身经历为例，他曾在佛蒙特州的农场长大，了解手工劳动的价值，并认为这种回归手工劳动的愿望可能反映了人们对现代生活的不满和对简单生活的向往。文章还提到，近年来有关理想化乡村生活的内容越来越受欢迎，这可能也体现了这种文化思潮。总的来说，文章分析了科技工作者渴望从手工劳动中寻找意义的现象及其背后原因。

评论摘要
主要讨论点：技术从业者对非技术、手工或农场生活的向往与现实之间的矛盾 不同观点： • [mauvehaus] 认为自己从软件开发转向家具制作等手工工作后感到更加满足，尤其是能够亲手创造 tangible 的东西。然而，他并不认为农场生活如人们想象中那样浪漫，自己也没有农业方面的实际经验。 • [wglb] 基于自己在农场的成长经历，指出人们往往对农场生活抱有不切实际的幻想。现实中的农场生活充满风险和经济压力，并不像很多人想象的那样轻松或理想化。他提到了一些成功实现自给自足的案例，比如 YouTube 上的某些博主，但强调这需要极高的努力和创造力。 • [Fuzzwah] 强调技术工作中的“无意义感”和短暂性，尤其是看到自己过去的工作成果在几年后就被取代。相比之下，手工或农场工作能带来更长久的成就感，因为这些工作成果是 tangible 且持久的。 • [xandrius] 认为手工和农场工作提供了在物理世界中解决问题的机会，并且技术从业者在这些领域仍然可以运用技术来解决问题。他不同意将这种向往归因于某种 mythos。 • [munificent] 认为人们对 tactile 技能和自我资源管理的需求是天生的，这种需求在现代技术工作中得不到满足。技术工作的高度专业化和抽象性让人们感到焦虑，担心一旦失去现有职业，自己将无所适从。 • [jrowen] 强调了选择和必要性的区别。技术从业者之所以向往农场或手工生活，是因为他们有经济和时间上的自由去追求这种生活方式，而真正出于经济 necessity 从事这些工作的人往往不会感到浪漫。 • [TrackerFF] 基于自己在农场和体力劳动工作中的经历，认为很多人对农场生活抱有不切实际的浪漫幻想，真正体验过农场生活的艰辛后，这种幻想往往会破灭。 • [sublinear] 对“cottagecore”这一名称感到荒谬，认为这可能是文章没有被认真对待的原因之一。 • [racl101] 提到技术工作往往缺乏 tangible 的成果，程序员在 debug 和处理抽象问题时容易感到无力和无成就感。相比之下，蓝领工人的工作成果更加 visible 和 tangible，这让一些技术从业者感到自己“被宠坏了”。 • [dole] 引用古希腊哲学家的故事，表达了自己对技术工作长期压力的厌倦，并向往更加简单的农场生活。 • [rapind] 认为人们向往农场或手工生活的原因包括简化生活、增加自主性和与自然的接触。然而，他也指出这种生活方式的 negativity 可能源于很多人试图通过社交媒体成为 influencer 并从中获利。 • [Arch-TK] 对技术工作对社会的负面影响持批判态度，认为大多数技术公司只关注利润最大化，而忽视了社会责任。 • [Aurornis] 强调很多人对农场生活的幻想是不现实的，他们低估了实际工作的艰辛。真正追求这种生活方式的人往往会发现现实与幻想之间的巨大差距。 补充讨论： • 争议的焦点在于人们对农场或手工生活的浪漫化幻想与实际艰辛的现实之间的差距。一些人认为这种生活方式能带来更大的成就感和满足感，而另一些人则认为这种想法是不切实际的，且忽视了其中的经济和体力压力。 • 技术工作的高度抽象性和专业化让一些从业者感到焦虑和无意义，他们向往能够亲手创造 tangible 成果的工作。然而，真正从事手工或农场工作的人往往指出其中的艰辛和现实挑战。 • 社交媒体和 influencer 文化的兴起也让人们对农场和手工生活的幻想更加复杂化，一些人认为这种生活方式被过度美化和商业化。

Quadlet: Running Podman containers under systemd

作者: gjvc | 评分: 224 | 评论数: 20 | 发布时间: 2025-03-24 00:27
文章摘要

本文介绍了如何使用Quadlet在systemd下运行Podman容器，替代已被弃用的`podman generate systemd`方法。Quadlet简化了将Podman容器作为systemd服务运行的过程，特别适用于需要在后台运行并希望在服务器重启后自动启动的容器。 过去的方法需要手动创建容器、生成systemd服务文件并进行配置，步骤繁琐且不易管理。而Quadlet通过在`~/.config/containers/systemd`目录中创建`.container`文件来定义容器配置，使用类似INI文件的格式，包含容器和systemd相关设置。这不仅简化了操作，还提供了更多灵活性，允许使用systemd的所有功能。 例如，创建一个PostgreSQL容器的配置文件`test-db.container`，可以指定镜像、自动更新、端口映射、卷和环境变量等。Quadlet使得Podman在功能和易用性上接近Docker Compose，同时更好地与systemd集成。

评论摘要
主要讨论点：Quadlet 作为 Docker Compose 的替代方案在开发和生产环境中的使用及其优缺点 不同观点： • psadauskas：Quadlet 适合在生产环境替代 Docker Compose 来管理容器，但在开发环境中并不理想。主要问题在于 Quadlet 的配置文件位于 `~/.config/containers/systemd`，不方便项目隔离和共享，且大多数开发者仍在使用 Docker。此外，手动处理卷的权限问题也较为麻烦。 • l11r：支持 Quadlet，尤其是在 rootless 环境下。它支持 systemd 的 socket 激活功能，可以有效解决 rootless 环境下保留源 IP 的问题，非常适合自托管环境（如 homelab）。 • stryan：高度推荐 Quadlet，认为其比 Docker 的类似方案更简洁，且与 systemd 深度集成。但承认 Quadlet 在本地开发环境中并不理想，仍需依赖 Docker Compose 来完成开发工作流。 • smjburton：认为 Quadlet 提供了一个从 Docker 迁移的良好替代方案，特别是对于那些因为 Docker Compose 而犹豫迁移到 Podman 的用户。强调了 Podman 在安全性方面的优势。 • kccqzy：通过其他教程使用过类似 Quadlet 的配置，但未意识到其正式名称，表明对 Quadlet 的认知度较低。 • brirec：对 Quadlet 作为 Docker Compose 的替代品持怀疑态度，指出 Quadlet 不支持多 YAML 文件的叠加，且其开发活跃度并不比 Podman-Compose 高。 • cvhc：赞赏 Quadlet 的清晰格式和 systemd 集成，但因为 Podman 在 Debian/Ubuntu 上的支持不足，最终回到了 Docker Compose。 • muti：使用 openSUSE MicroOS 和 Quadlet 搭建了自我托管的环境，对目前的设置感到满意，但承认在本地开发时仍会选择 Docker Compose。 • alexellisuk：提到 Quadlet 的一个实际应用案例，展示了其与 Kubernetes 的结合使用，认为这是 Quadlet 的一个潜在优势。 • eulenteufel：喜欢 Quadlet 将容器作为系统服务管理的方式，但指出 rootless 容器在用户 session 中运行，与系统 session 隔离，使用体验不够流畅。 • lukaslalinsky：在非 Kubernetes 环境中使用 Quadlet，认为其是 Docker 在生产环境中的理想替代品，特别是对 Linux 原生支持更好。 • mati365：展示了使用 Ansible 部署 Quadlet 的模板，认为 Quadlet 易于部署和管理。 • sunshine-o：多年来一直尝试使用 Quadlet，但总觉得不够成熟，预计到 2025 年可能才真正成熟。质疑为何花了近十年时间才实现容器与服务管理器的基本集成。 • aprilfoo：使用 Quadlet 数月，认为其值得更多关注，特别是 Red Hat 对其与 systemd 的整合做得很好。建议创建社区维护的 Quadlet 仓库以促进其普及。 • bityard：对 Quadlet 的命名和其必要性感到困惑，不理解为何需要一个特殊的名称。 补充讨论： - Quadlet 与 Docker Compose 在开发和生产环境中的优劣对比。 - Quadlet 的 rootless 模式在实际应用中的问题。 - 社区对 Quadlet 的认知度和接受度较低，部分用户对其命名和定位感到困惑。 - Quadlet 与 Kubernetes 的结合使用及其在自托管环境中的优势。 - Podman 和 Quadlet 在不同 Linux 发行版上的支持情况及其对用户选择的影响。
