Why the Sanitizer API is just `setHTML()`

作者: birdculture | 评分: 114 | 评论数: 11 | 发布时间: 2025-12-08 22:37
文章摘要

这篇文章解释了HTML净化(Sanitizer API)的设计原理。传统净化库(如DOMPurify)需要两次HTML解析：第一次不带上下文解析输入，第二次在插入DOM时带上下文解析，这可能导致mXSS漏洞。新的Sanitizer API通过`element.setHTML()`方法一步完成：1) 直接使用正确上下文解析HTML；2) 净化内容；3) 替换目标元素内容。这种设计避免了重复解析和上下文不一致的问题，更安全且性能更好，可直接替代`innerHTML`赋值操作。

评论摘要
主要讨论点：[Sanitizer API 的安全性和必要性] 不同观点： • **支持Sanitizer API** - 该API能替代DOMPurify等库，内置浏览器更安全（[brainbag]）。 - `setHTML()`避免了字符串多次解析的MXSS漏洞，上下文相关规则更可靠（[bikeshaving]、[cobbal]）。 - 开发者长期需要安全注入HTML的功能，浏览器原生支持更合理（[socketcluster]）。 • **质疑Sanitizer API的可行性** - HTML消毒问题本质未解决，无法满足“按需处理”的需求（[cxr]）。 - 应使用白名单而非黑名单策略（[IshKebab]）。 - 服务器端验证仍不可或缺（[dec0dedab0de]、[jagged-chisel]）。 • **其他技术建议** - 使用XHTML避免HTML解析的不稳定性（[nayuki]）。 - 新增``标签处理未信任内容（[dec0dedab0de]）。 补充讨论： - 争议焦点：MXSS漏洞是否常见？Sanitizer API是否能根本解决问题（[bikeshaving] vs [cxr]）。 - 开发体验：文章交互设计获好评（[jamesbvaughan]）。 - 遗留问题：`innerHTML`仍可能引发安全隐患（[philipwhiuk]）。
