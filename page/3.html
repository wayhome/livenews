Deno 2.4

作者: hackandthink | 评分: 90 | 评论数: 7 | 发布时间: 2025-07-07 08:44
文章摘要

Deno 2.4 恢复了 `deno bundle` 命令，用于创建单文件 JavaScript 捆绑包，支持服务器和浏览器平台，兼容 npm 和 JSR 依赖，并通过 esbuild 实现自动树摇和压缩。此外，新增 `--unstable-raw-imports` 标志，允许直接导入文本和二进制文件，简化非 JavaScript 文件的处理。同时，捆绑功能也支持与 `deno compile` 结合使用，可将资源嵌入最终编译的二进制文件中。其他更新包括内置 OpenTelemetry 稳定化、使用 `--preload` 修改环境、更简单的依赖管理等。`deno bundle` 目前为实验性功能，未来计划增加运行时 API 和插件支持。

评论摘要
主要讨论点：Deno的采用、兼容性、安全性及其在生产环境中的应用 不同观点： • **Deno的节点兼容性及其采用前景**： [voat] 认为Deno提供的节点兼容性被低估了，尤其是通过设置环境变量可以促进其被更多人采用。他建议可能需要一个自动启用兼容性的命令（如denon）。 • **Deno在FreeBSD上的可用性问题**： [blinkingled] 指出Deno在FreeBSD上不可用，原因是Rust V8绑定尚未移植到该平台，这限制了Deno在一些环境中的应用。 • **Deno在生产环境中的使用及漏洞数据库的缺乏**： [eranation] 认为Deno未被广泛用于生产环境的原因之一是缺乏标准化的漏洞数据库。此外，Deno没有集中化的包管理器（这是设计使然），这使得使用和管理包变得具有挑战性。 • **Deno的发展方向及风险**： [duesabati] 对Deno的未来持积极态度，认为它是Node本应成为的样子。但他担心Deno团队可能因竞争压力而追求短期热门功能，从而偏离长期稳定发展的轨道。 • **对Deno的好奇和兴趣**： [deafpolygon] 表示对Deno的好评有所耳闻，并可能因此尝试使用JavaScript。 • **Deno安装方法的安全性问题**： [bflesch] 对Deno官方文档中推荐的`curl | sh`安装方式表示担忧，认为这种方法忽略了安全性，尤其是在防范供应链攻击方面。他建议使用如`npm install -g deno`这样的方式，因为这种方式可以提供基本的文件完整性检查和恶意软件扫描。 补充讨论： • **JavaScript引擎的选择**： [sylware] 对Deno使用的JavaScript引擎表示关注，希望不是V8引擎，并提到其他可能的引擎如QuickJS和MuJS。 争议焦点： • **`curl | sh`安装方式的安全性**： [bflesch] 认为`curl | sh`是一种不安全的实践，容易受到中间人攻击和恶意软件注入。而官方文档中推荐这种安装方式，可能给用户带来安全隐患。 • **Deno的包管理模式**： [eranation] 指出Deno缺乏集中化的包管理器，虽然这是设计上的选择，但在实际应用中可能造成管理和安全上的挑战。 总结： 评论中涉及Deno的多个方面，包括其节点兼容性、在不同操作系统上的可用性、在生产环境中的使用、安装方法的安全性及JavaScript引擎的选择。争议主要集中在`curl | sh`安装方式的安全性及Deno包管理模式的优劣。

Heirloom apps项目提供了现代化的Windows经典应用程序，包括Heirloom File Manager和Heirloom Program Manager。File Manager是Windows File Manager的衍生版本，支持高DPI屏幕、回收站、书签、拖放操作以及创建和提取zip压缩文件。Program Manager则是经典Program Manager的重制版，用作启动快捷方式的Start菜单替代品。这些应用程序免费且开源，File Manager基于Microsoft Corporation的许可，而Program Manager则基于Brian Luft的许可。项目包含7个版本，最新版为2025年7月发布的12.1.0，主要使用C++编写。
