Jjui – A Nice TUI for Jujutsu

作者: Curiositry | 评分: 155 | 评论数: 9 | 发布时间: 2025-05-26 02:16
文章摘要

Jujutsu UI (jjui) 是一个为 Jujutsu 版本控制系统设计的终端用户界面（TUI）。它支持通过自动补全更改 revset、 rebase 操作、修订版本的压缩（squash）、查看修订详情、移动书签、操作日志查看等功能。用户可以通过快捷键进行多种操作，如分割、恢复、编辑文件或修订，查看 diff，以及进行 Git 推送/获取等。安装方式包括通过 Homebrew、Archlinux、Nix、go install 或从源码构建。最低支持的 Jujutsu 版本为 v0.21，项目采用 MIT 许可证，并欢迎贡献。

评论摘要
主要讨论点：用户对版本控制工具 jj 的使用体验、功能评价以及与 Git 等其他工具的比较 不同观点： • **mtndew4brkfst** 是一位有多年 Magit 使用经验的用户，他认为 jj 目前缺少像 Magit 那样的强大功能，但 jjui 是他目前最喜欢的 jj TUI。他对其他 jj TUI（如 Lazyjj 和 jj-fzf）的表现不太满意，认为它们有延迟或不稳定的问题。 • **cube2222** 对 jj 非常满意，认为它已经成为了他工作流中不可或缺的一部分，尤其是与 Git 相比，jj 提供了更好的历史管理体验，并且解决了 Git 中一些令人不快的问题（如 stash 管理）。他还积极推荐其他人尝试 jj。 • **dcre** 认为 jj CLI 已经足够好用，即使他从 GitUp 切换过来也没有感到太大的不便。他指出 jj 的 TUI 让日志操作更加交互化，并且在需要交互的场景下提供了很好的支持。 • **endtime** 对 jj 的总体体验是正面的，但也提出了一些痛点，包括缺乏 GitHub PR 同步功能、原生后端不支持推拉变更、以及某些工具依赖 .git 目录导致兼容性问题。 • **skeptrune** 对 jj 没有特别强烈的需求，但赞赏社区愿意尝试和构建新的 VCS 生态系统的精神。 • **account-5** 对 jj 试图解决的问题持怀疑态度，认为目前 fossil 已经足够好用，不清楚 jj 相较于 Git 有什么显著的优势。 • **silvanocerza** 对 jj 表示了初步的兴趣，认为它可以帮助他更好地理解一些复杂的操作。 • **sam_goody** 提到 jj 目前缺乏一个好的 GUI，并对 VC 资金追逐已有成熟生态的领域而忽视 jj 这样的工具表示惊讶。 补充讨论： • **争议焦点**：主要集中在 jj 是否需要一个像 Magit 那样的强大 TUI，以及 jj 相较于 Git 的优势和痛点。部分用户（如 mtndew4brkfst 和 endtime）指出了 jj 目前存在的一些功能缺失和稳定性问题，而另一些用户（如 cube2222 和 dcre）则对 jj 的现有功能表示满意并积极推荐。 • **功能需求**：endtime 和其他用户提到了一些 jj 目前缺乏但非常有用的功能，如 GitHub PR 同步和推拉变更支持，这些问题对 jj 的广泛应用和推广造成了一定的阻碍。 • **工具兼容性**：endtime 和 silvanocerza 提到了一些旧有工具和脚本对 .git 目录的依赖问题，这显示了 jj 在兼容性方面还需要进一步改进。 总体来看，讨论围绕 jj 的使用体验、功能完善度、以及与 Git 等其他工具的比较展开，用户对 jj 的未来发展充满期待但也指出了一些亟待解决的问题。

Demoting i686-PC-windows-gnu to Tier 2

作者: ingve | 评分: 56 | 评论数: 6 | 发布时间: 2025-05-26 14:16
文章摘要

Rust 1.88.0将把i686-pc-windows-gnu目标从Tier 1降级为Tier 2。降级后，该目标的标准库和编译器构建仍将分发，但测试和支持力度会减少。目前，GNU工具链主要用于跨平台编译和避免MSVC的许可问题，但由于缺乏维护者及使用率低，32位windows-gnu目标问题频发。若未来仍无改善，可能进一步降级。依赖该目标的用户若具备相关经验，欢迎成为维护者。详见RFC 3771。

评论摘要
主要讨论点：Rust平台支持和跨平台编译工具的讨论，特别是对Windows 32位目标平台的支持减少及其影响。 不同观点： • [malkia] 提到有跨平台工具如`clang-cl`和`lld`，可以在无需Wine的情况下针对"MSVC"链接Windows可执行文件，暗示这些工具可以减轻跨平台开发的困难。 • [kstrauser] 认为Rust开发团队不再为少数人使用的平台（如32位Windows）放慢开发进度是合理的，并提供了数据支持，指出x86_64-unknown-linux-gnu平台的下载量远远超过32位Windows平台，显示主流用户的需求。 • [flohofwoe] 质疑此举是否仅影响32位目标平台，并指出目前是否还有支持的32位Windows版本存疑，暗示对32位Windows支持的必要性可能已经降低。 • [mmastrac] 同意此决定，指出调试Windows平台上的 obscure bugs 令人沮丧，尤其在没有本地Windows设置的情况下，开发体验更差，分享了在Deno工作的经验。 • [dblohm7] 表达了对维护*windows-gnu目标的兴趣，但因时间限制无法参与，显示出社区中有愿意贡献但受限于时间的潜在维护者。 • [jmclnx] 关注此决定对OpenBSD和NetBSD的影响，提到OpenBSD可能因此放弃更多依赖Rust的i386软件包，并推测NetBSD也可能受到影响，但目前因Cross-Compiling的假设尚未成为问题。 补充讨论： • 争议焦点在于Rust团队是否应继续支持32位Windows平台，一方认为应照顾主流用户需求，另一方则认为即便有少数用户依赖，也应尽力提供支持。 • 社区中存在愿意贡献的潜在维护者，但时间和精力是制约因素。 • 此决定对其他操作系统（如OpenBSD和NetBSD）的潜在影响也被提及，显示出跨平台开发中各平台之间的相互依赖性。

Google is burying the web alive

文章摘要
