.gitignore Isn't the Only Way to Ignore Files in Git

作者: FergusArgyll | 评分: 141 | 评论数: 13 | 发布时间: 2026-06-18 10:29
文章摘要

Git 有三个层级的文件忽略机制： 1. **.gitignore** - 项目级别，会提交到版本库，团队共享 2. **.git/info/exclude** - 仓库级别，不提交到版本库，适合个人工作流中的临时文件（如个人笔记） 3. **~/.config/git/ignore** - 全局级别，机器范围生效，适合操作系统生成的文件（如 macOS 的 .DS_Store） 可通过 `git config --global core.excludesFile` 自定义全局忽略文件路径。使用 `git check-ignore -v <文件名>` 命令可查看某文件被哪个配置忽略。

评论摘要
主要讨论点：Git 忽略文件的不同方式及其最佳实践 不同观点： • **全局配置派**：[kevincox][hk1337] 强调应使用用户级全局配置（~/.config/git/ignore）来忽略 IDE、操作系统特定文件，避免污染每个项目的 .gitignore。规则是：项目级 .gitignore 仅用于项目特定内容（构建输出、依赖文件夹），用户工具配置应在个人配置中 • **本地排除派**：[bryancoxwell] 大量使用 .git/info/exclude 来处理仅本地需要的脚本和 Makefile，协作者不会用到也不关心 • **项目共享派**：[dofm] 指出如果团队有多个 Mac 用户，将 .DS_Store 放在项目 .gitignore 中更好，避免每个人都要配置 • **怀疑派**：[barbazoo] 认为 exclude 会带来麻烦；[uptown] 讽刺这不是新闻 补充讨论： • [judofyr] 分享技巧：全局忽略 "attic" 目录名，可在任何项目创建此目录存放临时文件 • [wpollock] 澄清术语：Git 中 "global" 指用户级而非机器级，"system" 才是机器级（/etc） • [tonymet] 建议使用 Git hooks 按文件类型（如二进制文件）忽略，而不仅按文件名 • [jeremyscanvic] 发现了 git-check-ignore 命令这个新工具

Unity vs. Floating Point

作者: ibobev | 评分: 38 | 评论数: 3 | 发布时间: 2026-06-15 11:53
文章摘要

这篇文章分析了Unity中数学函数的性能问题。主要发现： 1. **System.MathF优于UnityEngine.Mathf**：Unity的Mathf会将float转换为double计算后再转回float，而System.MathF直接使用float实现，效率更高。 2. **Unity存在隐藏的双精度计算**：Unity使用的Mono运行时会将所有float运算都以double精度执行，导致大量隐式类型转换。IL2CPP和Burst则不存在此问题。 3. **性能对比**：通过平方根循环测试，System.MathF比Mathf快约34%。在IL2CPP下两者性能相近。Burst编译器配合Unity.Mathematics能达到最佳性能，与C++和.NET原生性能持平。 **建议**：优先使用System.MathF；追求极致性能则使用Burst + Unity.Mathematics。

评论摘要
主要讨论点：Unity引擎中浮点数精度问题及其带来的bug 不同观点： • **corysama的核心问题**：Unity的AsyncOperation.progress使用单精度float(0.9f)，而开发者常用双精度double(0.9)进行比较，导致`0.9f < 0.9`判断失败。进度实际停在0.9f（比0.9少几百万ulp），而非文档声称的0.9，造成逻辑错误 • **Zarathruster的相关发现**：在世界原点(0,0,0)附近进行物理计算时遇到奇怪的"引力井效应"bug，怀疑可能与浮点精度问题相关 • **koolala的技术期望**：希望JavaScript或开源数组语言能支持单精度浮点数，认可文章展示汇编代码分解的做法 补充讨论：这些评论反映了游戏引擎开发中浮点精度是常见陷阱。Unity的API设计（float类型）与开发者习惯（使用double字面量）之间的不匹配，加上不精确的文档说明，容易引发难以调试的bug。

Seven Perfect Shuffles Randomize a Deck of Cards. But How Many Sloppy Ones?

作者: layer8 | 评分: 60 | 评论数: 12 | 发布时间: 2026-06-18 09:08
文章摘要

1992年，数学家证明了七次"鸽尾洗牌"（将牌分两堆后交错混合）足以随机化一副扑克牌，且会出现"截止现象"——前六次洗牌时牌序相对有序，第七次突然变得高度随机。但该证明要求精确地将牌分成均等两堆。2026年，三位数学家（Sellke、Shi、Wang）扩展了这一结果，证明即使切牌不均等，截止现象依然存在。这一突破对理解动力系统中的相变现象具有重要意义，应用范围超越纸牌游戏本身。

评论摘要
主要讨论点：关于扑克牌洗牌次数与随机性的数学研究，特别是对"7次洗牌足够随机"这一经典结论的质疑和新研究结果（14次）的讨论。 不同观点： • **技术质疑派**（possiblywrong）：原文对GSR模型的描述不够准确。"对半切牌"这个说法过于宽松，实际约五分之一的情况会出现21-31的不对称切分。真正的渐近结果应该接近9次而非7次，7次只是总变差距离首次低于0.5的点。 • **悖论指出者**（vessenes, have_faith）：完美的对称交错洗牌7-8次会让牌回到原始顺序，因此标题对于"完美洗牌"这一特殊情况是错误的。但认可新研究结果（14次半随机洗牌）很有价值。 • **人文体验派**（RNanoware）：从游戏体验角度，不完美的人工洗牌带来的牌组"个性"（如出现前局的牌序）反而增添乐趣，完美随机会失去这种人性化元素。 • **实用怀疑派**（soared）：质疑日常玩牌场景中，仅洗几次的牌组实际随机程度如何，以及这种不完全随机是否真的影响游戏，因为玩家通常缺乏利用这种偏差的知识和技能。 补充讨论： 有人质疑概率模型假设（每张牌掉落概率与剩余牌数成正比是否符合实际），有人关注实验中如何给每张牌嵌入追踪标签的技术细节，还有人询问这对伪随机数生成器评估是否有启发。
