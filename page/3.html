Migrating from Go to Rust

作者: jabits | 评分: 133 | 评论数: 21 | 发布时间: 2026-05-24 18:31
文章摘要

这篇文章是关于从 Go 迁移到 Rust 的指南，作者 Matthias Endler 主要面向后端开发场景。文章指出 Go 到 Rust 的迁移讨论重点不在性能或类型系统，而是**正确性保证、运行时权衡和开发体验**。 作者坦承自己不喜欢 Go 的设计（如 nil 到处存在、错误处理方式），但承认 Go 很成功。文章对比了两种语言的工具链：Go 和 Rust 都有"开箱即用"的工具链，`cargo` 甚至比 `go` 提供更多内置功能。两者都采用了统一的代码格式化工具（gofmt/rustfmt），消除了代码风格争论。 文章承诺会讲解：Go 和 Rust 的异同、模式映射、借用检查器的优势、何时该保留 Go 或迁移到 Rust，以及如何增量迁移服务。作者披露自己经营 Rust 咨询公司，建议读者同时参考相反观点的文章以获得平衡视角。

评论摘要
主要讨论点：Go与Rust在Web后端开发中的选择权衡 不同观点： • **Go更适合Web服务派**：Go的goroutines并发模型优秀，标准库成熟且经过Google大规模验证，依赖树简洁（多数功能由标准库覆盖）。Rust的异步编程（tokio）复杂，包管理导致依赖爆炸（一个简单项目可能有400+依赖），不如Go务实。 • **Rust技术优势派**：Rust在编译时捕获数据竞争，无GC停顿，性能优20-50%，内存安全保证更强。适合关键业务系统、需要确定性行为的场景（如确定性模拟测试）。`match`等语法特性优于Go。 • **务实中立派**：选择取决于是否需要托管运行时。已有系统用原语言重写即可，不必为语言争论。Python/Node才是真正的对手，Rust vs Go是"小圈子内战"。绿地项目可选Rust，棕地项目保持现状更经济。 • **AI时代经济性考量**：Go增量编译快，在AI辅助开发场景下成本更低。Rust编译慢消耗更多token，对普通CRUD应用性价比不高。LLM生成Go代码质量明显优于Rust。 补充讨论：Rust运维体验差（日志冗长无用、错误缺乏上下文、内存泄漏）；Go 1.28将改进错误处理冗长问题；build.rs存在安全风险；技术选型常受炒作驱动而非实际需求。

评论摘要
主要讨论点：软件系统中嵌入式虚拟机和字节码解释器的普遍性及其利弊 不同观点： • **支持方观点**：嵌入式VM提供了强大的可扩展性。grishka分享了在Fediverse服务器中使用字节码VM实现API方法和垃圾邮件过滤；drob518承认"对可扩展系统有好感"；多位开发者兴奋地分享各种实现案例 • **安全担忧方**：drob518指出核心问题——每个子系统携带图灵完备字节码和JIT会大幅增加攻击面，所有组件都需要无bug才能保证系统安全；superjan用iOS的JBIG2 PDF漏洞作为实际安全威胁的例证 • **技术考古派**：大量评论者列举历史案例证明这是长期存在的模式——从1971年Busicom计算器、Quake游戏引擎、TrueType字体、到Excel公式解释器、ACPI配置、比特币交易脚本等 补充讨论： 评论展现了技术社区的典型分歧：实用主义者欣赏VM带来的灵活性和跨平台一致性（如Excel跨架构保持浮点精度），而安全专家警告代码复杂度带来的系统性风险。讨论未形成明确共识，更多是知识分享和案例交流。

主要讨论点：用户对 `Geomatic` 的上手体验、示例设计、可用性与产品模式提出反馈，核心集中在“新手是否容易理解并顺利使用”。 不同观点： • 新手引导不足：`herpdyderp` 认为示例页体验很差，打开示例后不能输入命令，而且看到的是大段说明文字，不是直观可看的“示例”；这与其“先看例子再理解工具”的预期冲突。 • 有价值但学习门槛偏高：`sowow` 表示整体喜欢，但花了较长时间才看懂，并推荐另一篇“getting started”页面，说明更好的入门材料能显著改善理解。 • 功能/实现存在 bug：`felooboolooomba` 指出在“Draw a single n-star”操作中弹出“unknown command: n-star”，这是明确的功能错误反馈。 • 工程质量应看异常场景：`hbwang2076` 肯定实现干净，但强调真正可用的工具要看“出错时如何降级”和错误处理是否完善。 • 适配性问题：`roger_` 认为产品对移动端不够友好，说明界面或交互在手机上体验欠佳。 • 商业模式疑问：`dmos62` 关注一次性付费为何优于低价订阅制，讨论点转向定价策略。 • 基础概念解释不足：`ddxv` 直接问“autodiff 是什么”，反映部分读者连核心术语都未被充分解释。 补充讨论：争议焦点主要在“产品展示应先给直观示例还是先给说明文字”以及“技术实现是否已达到可稳定使用的成熟度”。
