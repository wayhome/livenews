The Theatre of Pull Requests and Code Review

作者: todsacerdoti | 评分: 95 | 评论数: 39 | 发布时间: 2025-09-25 10:35
文章摘要

本文讲述了作者参加Goatmire Elixir Conf会议后，对Saša Jurić关于代码审查和Pull Requests（PRs）演讲的感悟。演讲指出工程师常因PR过大、复杂而草率审查，导致代码质量下降。Saša建议：1）将难理解的PR退回作者；2）PR审查应控制在5-10分钟内；3）每个PR最好不超过300行代码；4）通过有叙事的提交信息帮助审查。他还演示了如何用13个细致的提交处理152行代码变更，强调迭代过程和保持提交历史的清晰性。文章提倡通过小范围、故事化的PR提升团队协作和代码质量。

评论摘要
主要讨论点：[GitHub PR界面的用户体验、代码审查的最佳实践、PR大小的合理性、提交信息的质量] 不同观点： • GitHub PR界面不够友好，难以逐提交审查（WorldMaker） - 提交选择器过于关注提交范围而非单个提交 - 缺少快速跳转至上一/下一提交的快捷键 - 提交描述在Files视图中难以阅读 - 提交选项卡默认隐藏大部分提交描述 • PR审查应注重共享理解和明确意图（jvanderbot） - 直接在代码行上标记具体变更并提问更有效 - "把代码扔到墙上等待解释"式的PR容易成为低优先级任务 • PR大小不应仅以代码行数衡量（davedx, epage） - 拆分过小的PR会增加认知负荷和合并冲突 - 关键取决于变更的争议性而非代码量 - 需要根据经验和与审查者的沟通判断 • 提交应讲述连贯故事（danielfalbo, necrotic_comp） - Jane Street的系统将每个提交作为独立分支审查 - 每个PR应能独立提交和发布 - 需要包含清晰的描述和测试证据 • PR的主要价值在于工作透明度（bob1029） - 代码审查更多是确保合并的干净度 - 信任团队成员的能力比反复"纯度测试"更重要 补充讨论： • 争议焦点： - PR的理想大小：300-500行规则是否合理 - 逐提交审查的必要性和可行性 - 代码审查的核心目的（质量把关vs.知识共享） • 其他重要观点： - 不同代码区域可能需要不同审查强度（ekidd） - 审查策略应取决于组织实际需求（conartist6） - Linux内核式PR模式与集体开发模式的差异（osigurdson） - 真实开发过程中的提交往往难以保持故事性（parpfish）

作者: pdubroy | 评分: 18 | 评论数: 6 | 发布时间: 2025-09-25 18:07
文章摘要

本文讲述了数据库公司Haydex在30天内将查询性能从零提升到每秒1786亿行的技术突破。核心优化包括：1）将数千次小读取改为单次大读取，彻底改变I/O架构；2）通过性能分析发现并消除70%的CPU和90%的内存分配开销；3）采用Lambda架构实现分布式重构，使索引速度提升6倍；4）各项优化相互叠加，最终峰值吞吐达6738亿行/秒。文章特别指出，初始优雅设计(V0)因过度细粒度I/O而失败，而成功方案(V1)遵循了网络物理特性。这些优化帮助解决了海量数据下的"大海捞针"查询难题。

评论摘要
主要讨论点：[对1780亿行每秒处理能力的质疑及其技术原理] 不同观点： • **质疑数据处理能力的真实性** - ccleve认为1780亿行的处理并非真正的实时处理，而是通过排除不可能的部分数据来实现的，类似于在杂货店挑选商品时排除其他无关商品的过程。 - 论据：以杂货店购物为例，说明技术可能是通过筛选而非全量处理。 • **技术原理可能与Bloom过滤器相关** - jacquesm指出这种技术可能是Bloom过滤器的变种，并分享了自己类似的经历，认为这种思路在计算机科学中早已存在。 - 论据：引用Bloom过滤器的概念，说明技术并非原创。 • **对EventDB的来源和性质的疑问** - mrbluecoat询问是否是开源的EventDB（链接指向GitHub项目）还是专有技术。 - 争议焦点：技术的开放性与专有性。 • **对数据的简化表述** - alexfromapex调侃性地表示自己通常简称为“1780亿”，未深入讨论技术细节。 • **对宣传风格的批评** - timhigins认为宣传文案读起来像动作小说或战争小说，暗示其夸张或不严谨。 补充讨论： - dmitrygr通过数学计算（178.6e9行/秒/30天）得出了每秒平方的处理能力（66150行/秒²），可能是对数据处理能力的另一种量化尝试，但未进一步解释其意义。 - 争议焦点集中在技术实现的真实性和原创性，部分评论者倾向于认为这是已有技术的包装或夸大宣传。

Video models are zero-shot learners and reasoners

作者: meetpateltech | 评分: 66 | 评论数: 3 | 发布时间: 2025-09-25 13:13
文章摘要

这篇论文探讨了视频模型是否可能像大型语言模型(LLMs)那样发展为通用视觉理解的基础模型。研究者展示了Veo 3模型在未经专门训练的情况下，能零样本解决多种视觉任务，包括物体分割、边缘检测、图像编辑、物理属性理解等。这些能力使Veo 3能够进行早期形式的视觉推理，如解决迷宫和对称性问题。研究表明，视频模型正在成为统一、通用的视觉基础模型，这与LLMs在语言领域的发展轨迹相似。

评论摘要
主要讨论点：[视频训练模型是否适用于单帧输出，以及通用模型的潜力] 不同观点： • [技术可行性] ricardobeat 提出了一个技术问题，即是否可以使用视频训练的模型来输出单帧图像，这暗示了对模型泛化能力的探讨。 • [学术支持] liuliu 表达了对系统性研究的赞赏，并提到之前通过非正式渠道（Reddit）了解到类似方法，显示了对该技术实际应用的兴趣和认可。 • [通用模型前景] ThouYS 则从更宏观的角度提出，这可能预示着未来会出现一个能够处理所有任务的通用模型（The One Model），反映了对AI发展方向的乐观态度。 补充讨论： • 争议焦点可能在于视频训练模型的具体能力和限制，以及是否真的可以实现通用模型的愿景。 • liuliu 的评论还提到了信息保存和引用的重要性，暗示了在快速发展的技术领域中，知识的整理和传承也是一个值得注意的问题。
