Diagnosing bugs preventing sleep on Windows

作者: donpedro1337 | 评分: 42 | 评论数: 8 | 发布时间: 2025-04-02 10:40
文章摘要

本文描述了一次对Windows程序导致无法自动锁屏和休眠的调查过程。作者的同事发现，运行软件的某些构建版本时，系统不会自动锁屏。初步分析显示，问题出在程序持续请求系统保持显示器开启，从而阻止了锁屏和睡眠。通过设置断点和分析调用栈，发现问题源于使用CEF（Chromium Embedded Framework）显示一个包含视频的浮动对话框，即使关闭对话框，请求仍未解除。最终确认是该对话框仅被隐藏而非关闭，导致问题持续。使用工具如Spy++验证了这一猜想，并通知相关团队修复了问题。文章还提到其他工具如powercfg和WDK中的pwrtest可用于类似问题的诊断。

文章摘要

**Model-Signing 1.0.0** 是一个用于签署和验证机器学习（ML）模型的工具，旨在增强ML供应链的安全性。它通过提供可验证的声明，确保模型完整性和来源可靠性，使用户能够自行检查声明的真实性。该工具支持使用Sigstore生成透明签名，也支持传统签名方法（如公钥或签名证书）。签署过程生成一个包含验证材料的sigstore bundle，并以JSON格式存储。验证过程则检查签名的有效性，并重新计算模型文件哈希值以进行比对。CLI工具提供`sign`和`verify`子命令，用于签署和验证模型。Sigstore的签署事件会被记录到透明日志中，方便追踪和监控。

主要讨论点：Sigstore在机器学习（ML）领域的应用及其相关工具（如Witness、SLSA for ML）的未来发展，尤其是模型验证和签名功能的价值和实用性。 不同观点： • [积极支持与期待] vishnudeva认为Sigstore在ML领域的进展令人兴奋，并期待未来几个月推出更多针对ML的功能，特别是对SLSA for ML概念验证（PoC）的进一步发展。他还提到有意使用Witness进行模型训练。 • [质疑其实际需求] lordofgibbons对该解决方案的必要性提出质疑，认为只需在发布模型时分享模型哈希即可，类似于Mistral分享磁力链接的方式。 • [补充验证功能] jasonmorton指出，Sigstore的验证功能可以帮助验证模型的签名，但不能验证模型决策的来源。他提到了自己的项目ezkl，作为一个可以验证模型推断的工具。 • [对用户接受度的担忧] clacker-o-matic表示对该功能实际用户使用情况的担忧，尤其是对签名功能了解不多的用户，并质疑该功能是否会像哈希一样被使用，或者是否会集成到模型软件中。 • [对问题存在的质疑] mountainriver直接质疑当前是否存在需要解决的问题，暗示可能没有实际的需求。 补充讨论： • 有人关注Witness在长时间和高强度的模型训练过程中的适用性。 • 讨论中提到了其他工具（如ezkl）作为补充或替代方案。 • 对该技术在实际应用中的用户接受度和集成度存在疑虑。 • 争议的焦点在于该解决方案的实际必要性和用户需求的真实性。

Rich Text, Poor Text (2013)

文章摘要

文章《Rich Text, Poor Text》讨论了文本表现形式（如粗体、斜体等）与标点符号的关系，认为这些形式与标点一样具有表达作用。作者指出，早期电子传输为了简约，可仅用字母、空格和换行，但这样缺乏表达的细致性和灵活性。虽然传统ASCII编码由于空间限制无法包含表现性信息，但后来的Unicode虽扩展了字符集，仍未解决表现属性的编码问题。作者建议采用32位编码，其中高8位用于表现属性，低24位用于字符，以解决这一问题。最后，作者反思自己将“标记”与“标点”混为一谈可能过于草率，但认为探讨文字的书写形式与风格的界限仍有价值。

评论摘要
主要讨论点：Unicode与标记语言在文本格式化中的应用及局限性 不同观点： • **ht_th的观点**：Unicode已经可以实现一些粗体、斜体和上标格式，尤其是ASCII字符范围内的符号。但是，Unicode对非ASCII字符和标点的支持有限。尽管如此，通过Unicode格式化的ASCII字母在一定程度上可以实现"排版"效果。 • **II2II的观点**：实现富文本需要使用标记语言或控制代码。粗体、斜体、下划线和删除线等效果需要位来表示，并且不同组合需要更复杂的位表示法。虽然可以通过有限的Unicode字符实现部分格式化，但对于技术应用（如上下标）有明显局限性。最终，需要更丰富的标记语言才能实现真正的表达力，且用户期望更多的格式选项（如字体选择和表格处理）。 • **tinthedev的观点**：认为目前解决方案不够优雅，但也不认为有真正的优雅解决方案。质疑如果要编码粗体，为什么不将字体也编码进标准。个人更倾向于使用Markdown，尽管它可能污染了文本的“纯洁性”。 • **timeflex的观点**：批评Markdown的使用者忽视了HTML5提供的强大语义标记功能。偏好使用具有SQLite支持的词法编辑器来存储数据。 • **hello_computer的观点**：认为ht_th引用的观点混淆了Ted Nelson关于内容、结构和特效分层的理论，错误地将所有内容都塞进Unicode。 • **AlienRobot的观点**：认为人们受限于工具。作者主张将粗体、斜体编码进纯文本是因为其接触的工具限制。如果今天写这篇文章，作者可能会主张将表情符号也纳入Unicode。指出一些社交媒体平台（如Tumblr）允许更多文本格式和效果。 补充讨论： - 关于Unicode和标记语言在处理文本格式化方面的局限性和复杂性。 - 对于富文本格式化的需求和期望，包括字体选择和表格处理。 - 对现有解决方案的不满和对更优雅解决方案的探索。 - 不同用户对工具和格式的偏好，以及对技术演进的看法。 争议焦点：是否应将文本格式化信息直接编码进Unicode，还是依赖标记语言实现更丰富的文本表达力。
