Tabular Programming: A New Paradigm for Expressive Computing

作者: dgellow | 评分: 95 | 评论数: 12 | 发布时间: 2025-04-21 12:26
文章摘要

本文介绍了一种名为“表格编程”（Tabular Programming）的新编程范式，灵感来源于m8 Dirtywave音乐序列器。该范式旨在通过一个简约的表格界面来组织代码，每函数限定五个表达式，以促进代码的模块化和可维护性。硬件方面，使用类似Teensy 4.1微控制器，配备小屏幕和八个按钮，无需键盘即可完成编程。 这种设计有以下优点： 1. **减少错误**：通过选择有效选项，避免许多语法错误。 2. **强制分解**：五表达式限制促使函数的细致分解。 3. **明确数据流**：数据流在表格中视觉化。 4. **便携性**：适合随时随地编程。 文中还展示了如何用这种表格编程实现经典的demoscene等离子效果，通过调用初始化和主循环函数来实现效果。这种新范式探索了在硬件约束下如何创造出新的编程环境。

评论摘要
主要讨论点：关于表格编程环境的概念及其潜在应用和局限性 不同观点： • AdieuToLogic认为，表格编程本质上是有限状态机的重新发现，并非全新的编程范式。他通过维基百科链接提供了有关有限状态机的参考，强调这种方法早已存在。 • lantry支持表格编程的潜力，认为它不仅适用于类似Game Boy的设备，还可以在特定硬件限制下重新思考编程方式，从而增强创造性表达。他以自己作为软件工程师的经历为例，说明对系统全面理解的价值。 • hwpythonner将表格编程与工业控制系统中的梯形图进行比较，指出两者都强调逻辑的线性、视觉结构化流动，但未明确支持或反对。 • hcarvalhoalves最初对表格编程有不同预期，提供了关于表格思考的不同视角的视频链接，引导进一步的讨论。 • gregschlom认为表格编程类似于汇编语言，具有简洁的格式（如标签、操作码、操作数、注释），但质疑其可用性。 • Johnbot将表格编程与IBM RPG II进行类比，指出其历史渊源和可能的局限性。 • sedatk认为，限制每个函数为五个表达式虽然鼓励分解复杂操作，但可能导致代码过于碎片化，影响可读性和可维护性。 • poulpy123对表格编程的实际应用持怀疑态度，认为其可能仅适用于音乐音序器等特定场景，而非普通计算机。 • debugnik以GPU行业标准为例，提出将表格编程用于逻辑编程而非基于栈的编程的可能性，并提出新的UI设计思路。 • turtleyacht提到2021年关于表格导向编程的讨论，提供了一个历史讨论链接，引导进一步阅读。 补充讨论： • 讨论中多次提及历史相似物和现有技术，如有限状态机、梯形图、汇编语言和IBM RPG II，显示出对表格编程创新性的质疑。 • 可读性、可维护性和实际应用场景是争议的焦点，不同参与者对表格编程在这些方面的表现有不同看法。 • 一些评论者如lantry和debugnik，提出了表格编程在特定硬件或UI设计中的潜在优势，扩展了讨论的范围。

Adding keyword parameters to Tcl procs

作者: BoingBoomTschak | 评分: 45 | 评论数: 5 | 发布时间: 2025-04-21 16:55
文章摘要

这篇文章介绍了在Tcl语言中为`proc`（过程）添加关键字参数（keyword parameters）的功能。作者对某些编程语言缺乏关键字参数以及未向用户提供内置功能感到不满，因此通过几小时的工作，实现了在Tcl中支持关键字参数的方案。文章展示了如何通过包装`proc`来实现这一功能，并给出了具体代码示例，如使用`proc*`定义支持关键字参数的过程，并演示了不同调用方式的结果。此外，作者还比较了使用关键字参数与传统位置参数的性能开销，显示该方法在保持灵活性的同时，性能影响较小。文章最后提到，这种实现借鉴了Tcl中通过强制位置参数来区分选项的特性。

评论摘要
主要讨论点：Tcl语言中关于添加命名参数功能的讨论和不同实现方案 不同观点： • jrapdx3 支持使用自己的 nxproc 扩展来实现 Tcl 中的命名参数功能。他认为 nxproc 提供了全面的功能，包括命名参数、位置参数、'rest'参数，以及类型检查等特性。他还提到 nxproc 支持 TclOO（Tcl 对象导向编程），并且提供了跨平台的二进制文件。 • blacksqr 则建议将 OpenACS 工具包中的 ad_proc 过程变成 Tcl 的内置命令。他认为 ad_proc 提供了添加开关、内联文档等实用功能，对 Tcl 开发很有帮助。 • tracnar 提到自己曾经实现过类似的功能，并认为不需要特别的 "quasiquote" 函数，使用 [list {*}$args] 和换行符就能解决问题。他还分享了自己进一步实现的 "pyproc"，可以通过调用 Python 来模拟 Tcl 过程。 • RicoElectrico 提到 Synopsys 工具中通过在值后面跟随名字的方式实现命名参数，例如 `measureFoo $signal threshold 0.9 edge last`。 • andrewshadura 对 Tcl 进行了简要的赞扬，认为 Tcl 作为一种简单、逻辑、一致的 shell 语言，已经做得很好，暗示可能不需要额外的复杂功能。 补充讨论： • jrapdx3 和 blacksqr 提供了不同的扩展方案，分别代表了外部扩展（nxproc）和内置命令（ad_proc）两种不同的实现路径。 • tracnar 的观点更多是技术实现上的细节分享，提供了对命名参数实现的一种不同思路，同时也展示了与 Python 的交互。 • RicoElectrico 提供的例子展示了其他工具中命名参数的实现方式，为讨论提供了一个参考。 • andrewshadura 的评论相对简单，但代表了一种对 Tcl 现状的肯定态度，可能暗示反对过度复杂化。 争议的焦点：是否需要将命名参数功能内置于 Tcl 中，以及哪种实现方式（外部扩展或内置命令）更为合适。
