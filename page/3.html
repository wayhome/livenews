GPUHammer: Rowhammer attacks on GPU memories are practical

作者: jonbaer | 评分: 198 | 评论数: 6 | 发布时间: 2025-07-16 00:05
文章摘要

《GPUHammer: 对 GPU 内存的 Rowhammer 攻击是可行的》一文介绍了首个在 GPU 内存上实现 Rowhammer 位翻转攻击的研究。该攻击在 NVIDIA A6000 GPU 的 GDDR6 内存上成功实施，绕过了如 TRR 等内存内防御机制，利用用户级的 CUDA 代码在所有测试的 DRAM 库中诱发了位翻转。攻击者可借此在共享的、时间分片的 GPU 环境中篡改其他用户的数据。在一项概念验证中，研究人员通过单个位翻转将深度神经网络模型的准确率从 80% 降至 0.1%。虽然启用错误校正码（ECC）可以缓解此风险，但会对 GPU 的机器学习推理任务造成最高 10% 的性能下降。 研究通过逆向工程 GPU 的 DRAM 地址映射，克服了 GDDR 内存的高延迟、未知映射和不透明防御机制等挑战，成功实现了多线程、多线程束的高强度锤击攻击，并通过与内存刷新的同步绕过了内存防御。

评论摘要
主要讨论点：围绕硬件漏洞（特别是内存相关问题）的技术讨论及其潜在影响 不同观点： • [PeterStuer] 认为内存锤击攻击（hammering attacks）具有哲学上的吸引力，因为它通过操控虚拟宇宙中的模式，影响了底层的物理基础，从而逃脱虚拟环境的限制。这种攻击让人联想到是否有可能对我们所处的现实宇宙进行类似的操作。 • [userbinator] 指出，虽然位翻转（bitflips）在图形处理时代并不受关注，但在使用GPU进行计算任务时，这些问题变得重要。讨论中还提到ECC（错误校正码）对性能的影响，以及通过位翻转攻击来破坏深度神经网络（DNN）模型的准确性，带有一定的讽刺意味，因为这些模型旨在模拟现实中的错误和不精确性。 • [privatelypublic] 对是否存在大量共享GPU计算资源的实例表示怀疑，并询问是否有实际的例子。他认为大多数情况下，GPU都是专用的。 • [perching_aix] 作为一个硬件新手，对内存锤击问题如何在开发阶段的电磁（EM）模拟中被遗漏表示好奇，并提到尽管现代芯片复杂度高，但内存模块由于结构的规律性，应该有可能进行更全面的验证。 • [sylware] 提到优化的汇编代码可能比编译器生成的代码更容易引发内存锤击问题，因为优化后的代码可能会更频繁地“锤击”内存。 • [iFire] 直接询问自己的Nvidia RTX 4090显卡上的ECC模式是否能防止这种攻击，表明用户对实际解决方案的关注。 补充讨论： - 讨论的核心围绕内存锤击攻击的技术细节、实际案例及其防护措施。 - 争议的焦点包括ECC对性能的影响以及是否能有效防止此类攻击。 - 不同的技术背景（硬件、软件、虚拟化）导致了对问题理解和关注点的差异，例如硬件结构的复杂性与优化的代码可能带来的风险。 - 用户对实际应用场景和防护手段的关注，如ECC是否足够有效。

Show HN: BloomSearch – Keyword search with hierarchical bloom filters

作者: dangoodmanUT | 评分: 18 | 评论数: 2 | 发布时间: 2025-07-13 16:02
文章摘要

BloomSearch是一个针对大规模数据集的关键字搜索引擎，利用层次化的Bloom filters实现高效搜索。其主要特点包括：低内存占用（Bloom filters大小恒定）、可插拔存储（支持自定义后端）、快速过滤（通过分区和Bloom filters进行层次化修剪）、灵活查询（支持按字段、标记或组合条件查询）以及存储与计算的分离。它适用于日志、JSON文档和高基数关键字搜索。使用示例展示了如何初始化存储、摄取数据及执行查询操作，并支持异步插入和结果处理。引擎通过Bloom filters实现快速过滤，同时利用分区和MinMax索引提升查询效率。

评论摘要
主要讨论点：如何使用Bloom filters替代传统日志以及其具体实现方法 不同观点： • SwiftyBug质疑Bloom filters是否可以替代当前的日志系统，并指出Bloom filters的主要优势在于确认某元素**肯定不存在**于集合中。他提出核心问题：在这种情境下，Bloom filters的“集合”到底是什么？换句话说，如何通过Bloom filter查询数据集？ • 隐含的观点是，Bloom filters虽然擅长高效确认不存在性，但可能不适合作为日志的全面替代方案，因为Bloom filters对存在性只能提供**概率性保证**，即它可以告诉你某个元素可能存在，但不能完全确定某个元素一定存在。SwiftyBug对如何具体操作和查询位于Bloom filter背后的数据集表示困惑。 补充讨论： • Bloom filters的应用场景一般是在需要快速判断某个元素是否**肯定不在**集合中的情况下，比如缓存查找、网络路由等。然而，当日志系统需要精确记录和查询每个事件时，Bloom filters可能并不合适，因为它存在误报的可能性。 • 对于Bloom filters的查询操作，通常做法是：首先查询Bloom filter，如果返回“不存在”，则可以确定该元素不在集合中；但如果返回“可能存在”，则需要进一步查询实际的数据存储以确认。因此，SwiftyBug对如何在这种架构中查询数据集提出了实际应用中的关键问题。 争议焦点：Bloom filters是否可以作为日志系统的替代方案，尤其是在需要高精度和查询功能的场景下，其概率性特性是否会成为障碍。

cppyy: Automatic Python-C++ Bindings

作者: gjvc | 评分: 60 | 评论数: 7 | 发布时间: 2025-07-16 12:39
文章摘要

cppyy 是一个自动的 Python-C++ 绑定生成工具，能够在运行时实现 Python 与 C++ 的互调，支持跨语言调用、延迟加载、模板实例化、异常映射等功能。它基于 C++ 解释器 Cling，无需语言扩展或手写代码，支持大型 C++ 项目，并能无缝集成如 Boost 等复杂 C++ 库。cppyy 适用于 CPython 和 PyPy，具备高性能，支持 STL、回调和跨继承等特性，简化了 C++ 库在 Python 中的使用。通过预编译头文件和动态加载等技术，cppyy 可以处理包含大量类和代码的 C++ 项目。

评论摘要
主要讨论点：Cppyy 作为 Python 和 C++ 结合的工具，其功能、性能及实际应用的讨论。 不同观点： • [rich_sasha] 认为 Cppyy 类似于已经废弃的 scipy.weave，可以结合 C++ 和 Python。他关注 Cppyy 是否能替代 scipy.weave，尤其是性能方面是否能超越 Numba 和 Cython。他指出 Cppyy 通过 Cling 解释 C++ 而不是生成真正的二进制文件，并质疑其在 CPython3 上的性能表现。虽然找到了一些基准测试，但这些测试并没有直接对比 Python 实现。 • [ashvardanian] 提供了一个使用 Cppyy 的实际用例，展示如何通过 Cppyy 结合 C++ 内核与 Python 进行实验，还提到了 Numba 和 PeachPy 等其他工具，展示了 Cppyy 在实际项目中的应用场景。 • [f1shy] 提出了 Cppyy 与 LLM（大型语言模型）在“AI 编程”中的对比，表示自己在使用 Cppyy 时得到了不错的效果，询问其他人的使用体验。 • [dang] 提供了一个相关的讨论链接，指向 2019 年关于 Cppyy 的讨论，引导读者参考之前的讨论内容。 • [actinium226] 关注实际应用中的分发问题，担心如果在项目中使用 Cppyy 并打包成 pip 包，用户是否需要自行安装 C++ 编译器，或者 Cppyy 是否自带编译器。 • [wslh] 推荐了 SWIG 作为另一种支持多种编程语言的绑定工具，暗示 SWIG 可能是 Cppyy 的一种替代方案。 补充讨论： • [bogeholm] 对项目名称进行了幽默评论，没有涉及技术讨论。 争议焦点： • Cppyy 是否真正能替代 scipy.weave，尤其是在性能和实用性方面。 • Cppyy 在实际项目分发中的可行性，特别是对用户环境的要求。 基准测试和性能对比是讨论的核心，尤其是对 Cppyy 在 CPython3 上的性能表现缺乏明确的答案。
