Why DeepSeek is cheap at scale but expensive to run locally

作者: ingve | 评分: 241 | 评论数: 21 | 发布时间: 2025-06-01 07:31
文章摘要

文章主要讨论了AI模型在不同环境下的性能表现，特别是DeepSeek-V3这类模型在规模化服务时速度快且成本低，但在本地运行时却速度慢且成本高的问题。这主要源于**批量推理**（batch inference）的机制，以及**吞吐量**和**延迟**之间的权衡。 GPU擅长处理大规模矩阵乘法（GEMMs），一次处理大量数据比多次处理小数据效率更高。这是因为每次GPU操作都有一定的开销，且频繁的内存读取会降低效率。因此，推理服务器通常会将多个用户请求进行批量处理，以提高吞吐量，但这也增加了延迟。 对于像DeepSeek-V3这样的混合专家模型（mixture-of-experts），由于其结构包含多个子网络（专家），导致GPU计算效率低，必须依赖批量处理来提升实用性。这类模型在低批量情况下表现不佳，因此在本地运行时速度慢且成本高，而在规模化服务中通过批量处理能达到高吞吐量和较低成本。

评论摘要
主要讨论点：Deepseek V3 等大型模型的本地运行成本、性能优化及批处理的必要性 不同观点： • ryan_glass 认为，使用无GPU的CPU系统（如EPYC 9004系列）可以有效运行Deepseek V3，成本较低且功耗低。他强调通过大内存和优化模型（如Unsloth Dynamic GGUF），可以在不牺牲性能的前提下实现高效推理。 • ipieter 指出，大型语言模型（LLM）推理的瓶颈在于从显存加载权重，而非计算能力。他强调批处理的重要性，因为每次加载权重后可以进行大量操作，从而提高效率。 • perching_aix 支持批处理推理的必要性，指出批处理可以通过同时处理多个请求来节省时间，但也提到这可能导致回复的变异性。 • bick_nyers 认为，软件优化仍有很大空间，尤其是针对具有适度VRAM的系统。他提到模型的稀疏性和专家的选择性激活可以进一步优化性能。 • freehorse 提出，Apple Silicon的统一内存架构适合运行MoE模型，因为它们可以在较低带宽下运行，且内存较大。 • jsnell 对批处理的原理和效果表示困惑，质疑批处理是否真的能提高效率，并指出缺乏对不同供应商模型响应时间的具体数据支持。 • slavboj 认为，通过使用较旧的硬件（如DDR4内存）和优化软件（如llama.cpp），可以以较低成本获得不错的推理速度。 • corey_moncure 讨论了多GPU系统中通过PCI-E带宽加载模型权重的可行性，并提出可以通过优化批大小来匹配计算时间。 补充讨论： • angry_octet 深入探讨了计算调度和负载平衡的问题，特别是在大规模LLM推理中的优化方法，并提到在安全应用中批处理可能导致的问题。 • briian 提到AI推理的经济规模效应，认为未来可能只有少数几家公司能主导LLM市场。 • comrade1234 和 philipodonnell 关注Deepseek的成本优势和可能的商业机会，如通过时间不敏感的推理服务进行套利。 争议焦点： • 批处理的实际效果和必要性：部分评论者（如ipieter和perching_aix）强调批处理对效率的提升，而jsnell则对其原理和效果表示质疑。 • GPU与CPU系统的优劣：ryan_glass支持使用CPU系统，而其他评论者（如ipieter和freehorse）则讨论了GPU系统在不同场景下的优势。

Structured Errors in Go (2022)

作者: todsacerdoti | 评分: 118 | 评论数: 16 | 发布时间: 2025-06-01 04:54
文章摘要

这篇文章讨论了Go语言中错误管理的问题，特别是在中型程序和HTTP API中的应用。作者通过一系列实验，提出了一种简化错误处理的方法，并开发了一个新的库来实现这一目标。Go的错误处理通常依赖于返回值，而非异常机制，最简单的错误形式是字符串。虽然这种设计简单，但缺乏结构化信息。 文章强调了结构化日志的重要性，指出在错误管理中，错误信息需要被结构化，以便于日志聚合器和报警系统处理。传统上，错误信息是简单的字符串，难以进行有效的过滤和分析。为了改善这一情况，作者建议将错误信息结构化，例如在日志中加入"account_id"等具体字段，以便更好地诊断问题。 最终，作者提出了一种方法来弥合错误值和结构化日志之间的差距，并通过一个新库来实现这一功能，以提高错误管理的效率和可维护性。

评论摘要
主要讨论点：Go 语言中错误处理和元数据管理的实现方式及其优缺点 不同观点： • atombender 认为 `WithMeta()` 的实现有缺陷，既不支持并发安全，又会修改父 map。他建议使用树状结构来管理元数据，通过父节点指向之前的元数据，避免每次都分配新的 map。同时，他提出另一种方案，主张通过返回包含已知失败操作数据的结构化错误，并在错误上行过程中逐步添加元数据，这样只需在错误发生时付出性能代价。 • RadiozRadioz 强调错误不应该仅仅作为字符串返回，而应使用类或类型来区分不同种类的错误（如 HTTP 状态码 502 和 404），否则需要通过正则表达式来解析错误，非常麻烦。他还提到堆栈跟踪的重要性，以便在捕获和包装错误时能精确定位错误来源。 • samber 分享了自己编写的错误包装库 `oops`，该库支持完整的堆栈跟踪以及丰富的元数据添加功能，如时间、标签、用户信息等。 • darthbanane 指出 `WithMeta` 函数在参数不是成对出现时会引发 panic，认为这是 Go 错误处理困难的一个例子。 • gregwebs 提到使用现有的 Go 错误库，并推荐使用 `slog` 属性来复用日志属性，从而实现添加元数据的功能。 • sethammons 支持结构化错误日志，并分享了自己编写的 Go 错误包装工具 `kverr`，同时提到在 Python 中也希望实现类似的结构化异常处理。 • fastest963 介绍了自己使用 `errctx` 库来存储错误中的键值对，并实现了错误展开以查找深层存储的键。 • weakfish 对使用第三方库进行结构化日志记录持怀疑态度，认为应该使用 Go 自带的 `slog`。 • altbdoor 认为 Go 的错误处理有些奇怪，但自己主要是在小项目中使用，因此影响不大。 • vikeri 指出错误中缺少标记特定错误代码的功能，无法轻松地对相似错误进行分组，并询问是否可以通过 "tag" 实现这一需求。 • dedicate 提问，对于中小型项目来说，这种高度结构化的错误处理是否会带来过多工作量，是否值得。 • sigmonsays 认为可以使用 Go 内置的 `errors.Wrapf` 和 `slog` 来实现类似的功能，无需额外引入复杂的库。 • aor215 分享了自己几年前写的一篇关于错误处理的文章，并提到其解决方案在多个项目中得到了成功应用。 补充讨论： • 错误处理中的并发安全性、性能代价和内存开销是争议的焦点之一。 • 使用字符串作为错误返回值的缺点被多位讨论者提到，推荐使用结构化错误或错误类。 • 堆栈跟踪和元数据（如标签、用户信息）的添加被认为是错误处理中的重要功能。 • 不同开发者对第三方库和 Go 自带工具的选择存在分歧。 • 对于中小型项目是否需要高度结构化的错误处理，讨论中提出了实用性和工作量的问题。
