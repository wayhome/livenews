AlphaDec: A human-readable alternative to ULID/Snowflake IDs

作者: firasd | 评分: 33 | 评论数: 5 | 发布时间: 2025-07-24 22:14
文章摘要

**AlphaDec** 是一种时区无关的时间格式，适用于人类、机器和人工智能。它将 UTC 时间编码为可读字符串，并按字典顺序排序，方便数据库使用。其结构为 `YYYY_PaBt_MMMMMM`，其中： - **YYYY**: UTC 年份。 - **P**: 年分为26个周期，用字母 A-Z 表示，每个周期约14天。 - **a**: 每个周期分为10个弧，每个弧约33.7小时。 - **B**: 每个弧分为26个条，每个条约77.8分钟。 - **t**: 每个条分为10个节拍，每个节拍约7.8分钟。 - **MMMMMM**: 当前节拍内的毫秒数。 AlphaDec 具有以下特点： 1. **字典顺序可排序**: 可按字符串顺序排序，适合作为数据库主键。 2. **时间序列友好**: 可截取字符串进行高效的时间范围查询。 3. **人类可读且紧凑**: 一眼可大致了解时间位置。 4. **AI 原生**: 结构化、可标记，适合AI系统中的时间推理和日志分析。 5. **无碰撞**: 不同于本地时间格式，避免混淆。 该项目提供 JavaScript 和 PHP 的实现示例，确保语言无关性。

评论摘要
主要讨论点：关于时间编码方案的优缺点及其实际应用的讨论 不同观点： • akdor1154：对项目设计表示认可，但提出关于有理数定义的不安，并建议使用整数秒或毫秒的定义以确保往返转换的明确性，特别是在考虑闰秒交互的情况下。 • firasd：介绍其项目AlphaDec，强调其设计的可读性、时区无关性及在LLM等环境中的安全性，并提供了实例和在线演示链接，展示其项目的实际应用。 • andoando：质疑AlphaDec的可读性，认为ISO 8601格式（如2025-06-14T23:37:42.814Z）比AlphaDec格式（如202025_L0V3_001827）更为直观。 • rfoo：对项目声称的LLM和AI原生特性表示怀疑，认为偏离常规（OOD）的设计在此类应用中未必有优势。 • burnt-resistor：提醒注意使用UTC而非TAI的问题，并提供了一个关于UTC和TAI的参考链接（https://cr.yp.to/proto/utctai.html）。 补充讨论： • 关于时间编码的可读性和实际应用的平衡：不同用户对时间编码的可读性和应用场景有不同看法，尤其是在涉及AI和LLM时。 • 关于闰秒和时间标准的讨论：有用户提到UTC与TAI之间的选择问题，提示在实际应用中需要考虑更广泛的时间标准问题。 • 项目展示与技术细节：firasd提供了详细的示例和链接，展示其项目的实际应用和技术细节，帮助其他用户更好地理解其设计和优点。 争议焦点： • 时间编码的可读性和实用性：andoando与firasd之间对于AlphaDec格式的可读性存在争议，前者认为ISO 8601更直观，后者强调AlphaDec在特定应用中的优势。 • AlphaDec在AI和LLM应用中的实际效果：rfoo对项目声称的AI和LLM原生特性表示怀疑，认为偏离常规的设计未必有优势，这与其他用户对项目的积极评价形成对比。

The many JavaScript runtimes of the last decade

作者: LinguaBrowse | 评分: 145 | 评论数: 18 | 发布时间: 2025-07-27 14:28
文章摘要

过去十年中，JavaScript运行时和引擎大量涌现，使JavaScript得以在云端、边缘计算、智能电视、移动设备甚至微控制器等多种环境中运行。这种多样性源于不同场景对任务精确度的需求。2002年，Akamai推出首个“边缘计算”解决方案，但直到2009年Node.js出现，JavaScript才开始被用于服务器端。2014年，AWS Lambda使Node.js进入无服务器领域。2016年，AWS推出Lambda@Edge，使JavaScript真正进入边缘计算。然而，Cloudflare Workers在2017年迅速崛起，成为直接产品化的JavaScript运行时，获得巨大成功。随后，Deno于2018年出现，成立Deno Land Inc并推出Deno Deploy，挑战Cloudflare。2022年，WinterCG成立以统一新运行时标准，Bun和Wasmer也相继推出新边缘计算解决方案。 不同运行时使用不同引擎，如Deno用V8，Bun用JavaScriptCore，WinterJS用SpiderMonkey，LLRT用QuickJS，Cloudflare Workers用workerd。在微控制器领域，轻量级引擎如Duktape、Espruino、JerryScript、Moddable和elk应运而生，支持低资源设备。最后，一些JavaScript引擎基于已有虚拟机，实现与其他语言的零成本互操作。

评论摘要
主要讨论点：JavaScript 运行时和引擎的多样性及其发展趋势 不同观点： • Laurencerowe 指出，尽管 Deno 延续了 Node.js 使用 V8 引擎的传统，但其他运行时如 Bun 使用 JavaScriptCore，WinterJS 使用 SpiderMonkey，LLRT 使用 QuickJS，Cloudflare Workers 则使用定制的 workerd 运行时。不过，Laurencerowe 认为 Cloudflare 的 workerd 实际上仍然使用 V8 引擎，纠正原文中关于 workerd 使用不同引擎的描述。 • Weiliddat 补充提到 QuickJS，特别是 Bellard 的 QuickJS 分支，强调其活跃性并提供了相关链接，认为这是值得注意的信息。 • Willquack 分享了自己参与过的其他未列出的 JavaScript 运行时项目，如 PythonMonkey 和 DCP，并描述了这些项目如何嵌入或利用其他运行时和引擎来实现特定功能，如在浏览器中运行 Python 工作负载。 • Rorylaitila 对 GraalVM/GraalJS 表示印象深刻，认为其易于集成并能很好地与 Java Web 应用协作，特别是在处理 handlebars.js 和测试服务器与客户端共享的 JavaScript 代码库时。 • Ksherlock 提到被忽略的 Microsoft JScript，指出其在1996年既能用于客户端也能用于服务器端（ASP）和脚本（WSH），并提及 JScript.NET，认为这些早期技术也应被提及。 • Dfee 对文章未提及不同 JavaScript 运行时生态系统可能面临的衰退表示关注，质疑 Deno 和 Bun 等运行时在未来十年的生存能力，并提出代码互操作性的问题。 • Sytten 纠正关于 LLRT 的描述，强调其主要是社区贡献，并指出许多企业正在使用 LLRT 模块，同时对基于 QuickJS 的 Rust 运行时给予高度评价。 • Asn0 提到 Nombas ScriptEase，一个90年代的商业运行时，特别指出其在操作詹姆斯·韦伯太空望远镜中的应用，认为这是值得补充的历史信息。 • Tom1380 对在微控制器上使用 JavaScript 表示不解，提出质疑。 • Cat-whisperer 好奇新运行时如何处理异步上下文跟踪，询问它们是否依赖 Async Hooks 或实现自己的解决方案。 • Michaelsbradley 提到 Ejacs 项目，认为其未被文章提及是一个缺失。 • Righthand 对原文关于 JavaScript 在 GUI 编程中的主导地位提出质疑，认为尽管有其他语言竞争，JavaScript 仍然占据主导地位，并质疑原文是否暗示其他语言在桌面端 GUI 编程中的应用趋势。 补充讨论： • LinguaBrowse 提到自己花了一年时间撰写了一篇详细介绍各种 JavaScript 运行时和引擎的文章，邀请大家阅读并表示其中包含许多新信息。 • Ottod 对文章的质量表示赞赏，认为其内容详实且参考丰富，建议其成为维基百科页面的基础。 • NeutralForest 感谢文章的同时，提出如何保持链接长期有效的实际问题，担心未来可能无法访问原始页面。 争议焦点： • JavaScript 运行时生态系统的多样性与未来生存能力，特别是 Deno 和 Bun 等新兴运行时在未来十年的发展潜力及代码互操作性问题。 • JavaScript 在 GUI 编程中主导地位的持久性，是否会面临其他语言的进一步竞争。
