RISC-V Router

作者: janandonly | 评分: 121 | 评论数: 13 | 发布时间: 2026-05-14 20:06
文章摘要

这是一个募资项目页面，目标软上限为25万美元，目前已筹集24,934美元，完成约10%。项目仍在进行中，共有90名贡献者参与，并提供“Contribute”按钮供用户继续捐助。

评论摘要
主要讨论点：围绕 Start9 推出的基于 OpenWrt 分叉的 RISC-V 路由器，其开放性、硬件规格、价格、可信度和实际适用性展开讨论。 不同观点： • 质疑软件路线：有人认为小型创业公司维护 OpenWrt 自定义分叉风险很高，许多硬件众筹项目因软件栈过度定制而失败；更希望使用原生 OpenWrt，避免后续“再维护”负担。 • 质疑“最开放”宣传：评论指出 OpenWrt One、Turris 等已有开放启动栈、内核和硬件文档，甚至提供 Gerber 文件；该 RISC-V CPU并不比某些 ARM 芯片更“开放”。 • 质疑价格与性能：多人认为 25 万美元目标和产品规格不匹配，要求看到路由吞吐、VPN吞吐等真实基准；1Gb WAN + 1Gb LAN 被认为在 2026 年过时，至少应有多口、SFP+ 或 2.5/10GbE。 • 对硬件配置不满：只有两个网口无法满足备份 WAN、自托管隔离网络等需求；有人希望使用 USB-C 供电。 • 与竞品比较：Turris Omnia NG 被认为更成熟，具备 10Gb SFP+ 和 2.5GbE，且社区活跃；BananaPi 类似 CPU 板卡约百美元，引发“Start9 是否有实质差异”的疑问。 • 信任与合规疑虑：有人不熟悉 Start9，认为页面像骗局；也有人担心外国产处理器和 WiFi 模块是否会受美国 FCC 外国路由器禁令影响。 补充讨论：WiFi 固件开放性被单独讨论，有人认为现代 WiFi 缺乏开放固件，可能受行业规范和监管限制，除非建立开放 WiFi 标准并推动监管认可。

OVMS: Open source electric vehicle remote monitoring, diagnosis and control

作者: BHSPitMonkey | 评分: 77 | 评论数: 6 | 发布时间: 2026-05-14 21:50
文章摘要

Open Vehicles（OVMS）是开源电动车远程监控系统，可通过手机实时查看电量、温度、胎压和故障，接收告警，并远程控制充电、空调等。它支持网页/手机App、MQTT集成、数据记录，并为开发者提供CAN、OBD2等工具。

评论摘要
主要讨论点：围绕用 OVMS/开放工具替代车厂联网服务时，车辆 CAN/OBD 访问限制、硬件成本、车型支持和隐私价值展开。 不同观点： • 车辆访问受限派：2023 Nissan Leaf 已加入 CAN gateway，类似“防火墙”，会过滤 CAN 写入命令，OBD-II 基本只能在通电时只读访问；评论者认为越来越多车会这样，可能需要改造 CAN tap 线缆获得不受限接口。 • 隐私与替代服务支持派：Ioniq 5 车主认为即使 OVMS 硬件约 350 美元、再加低流量 SIM 月费，也值得用于提升隐私，并替代现代每年 100 美元、功能少且不稳定的软件服务；但抱怨上手文档和硬件获取信息不足。 • 项目价值背景派：有人指出 OVMS 并非新项目，但在近期关于现代汽车内置联网系统侵犯隐私的讨论中很相关。 • 成本质疑派：认为 345 美元作为一个 OBD bridge 价格偏高，暗示门槛可能影响普及。 • 兼容性探索派：有人询问是否支持 F-150 Lightning；也有人猜测 comma.ai 设备可能实现类似功能。 补充讨论：争议焦点主要在开放车辆数据访问是否会被厂商网关限制，以及高价第三方硬件相较车厂订阅服务是否划算。

What's in a GGUF, besides the weights – and what's still missing?

作者: bashbjorn | 评分: 146 | 评论数: 15 | 发布时间: 2026-05-14 17:21
文章摘要

GGUF 是 llama.cpp 使用的单文件模型格式，除权重外还包含运行模型所需的元数据。文章重点介绍三类内容：聊天模板（Jinja2 脚本，用于格式化对话、工具调用、多媒体等）、特殊 token（如 eos、bos、工具调用和对话轮次标记，用于控制生成与语义结构）、采样器配置（推荐的温度、采样链等参数，现可直接写入 GGUF）。作者认为 GGUF 提升了模型分发便利性，但仍需完善对复杂运行需求的覆盖。

评论摘要
主要讨论点：围绕 GGUF 作为开源 AI 模型格式的优势、缺陷及未来改进展开。 不同观点： • 支持 GGUF 的“一文件”理念：Philpax 和 badsectoracula 认为 GGUF 本应把模型相关内容集中在单文件中，投影模型被拆出去违背初衷；视觉模型需额外下载文件带来困惑。 • 肯定 GGUF/GGML 生态价值：uyzstvqs 强调 llama.cpp、whisper.cpp、stable-diffusion.cpp 等项目跨平台、跨硬件表现稳定，对开源 ML/AI 很重要。 • 认为 GGUF 并非唯一好方案：prashantk_ 表示 safetensors + metadata 文件也够用；Sharlin 指出图像生成领域模型长期就是单文件，safetensors 也能嵌入元数据，不一定需要 GGUF。 • 批评可读性与接口设计：amelius 讽刺某些模板格式比 XML 更难读；badsectoracula 不满 llama.cpp 中硬编码聊天格式，希望有真正的 Jinja2 模板解析接口，尤其支持 tool calling。 • 主要技术缺口：theapadayo 和 monocasa 都指出 GGUF 未存储完整计算图，只记录架构字符串和参数元数据，导致每种新模型架构都需消费端新增代码；建议用 DSL 描述模型图，或从 PyTorch 模块转换为 GGML ops。 • 其他讨论：sbinnee 认为 tool calling 格式会推动 LLM 向 agent 发展；halyconWays 提到 GGUF 命名与早期贡献争议；kenreidwilson 注意到发布日期疑似异常。

How Claude Code works in large codebases

作者: shenli3514 | 评分: 161 | 评论数: 28 | 发布时间: 2026-05-15 04:15
文章摘要

文章介绍大型代码库中采用 Claude Code 的最佳实践：它通过本地文件遍历、grep 和引用追踪工作，而非依赖易过期的索引。成功关键在于搭建好“harness”：CLAUDE.md、hooks、skills、plugins、MCP、LSP 和子代理，逐层提供上下文、自动化改进与团队规范支持。

评论摘要
主要讨论点：围绕 Claude Code“像工程师一样浏览代码库、无需索引”的说法是否合理，以及其在大型代码库、工程实践和质量保障中的真实效果。 不同观点： • 反对“无需索引”：多位评论者认为工程师实际依赖 LSP、IDE 索引、自动补全、符号跳转和记忆；IDE 索引在 JetBrains 等工具中已被证明有效，Claude 也应能利用本地索引，而不是从零遍历文件。 • 支持/补充替代方案：有人提出代码依赖图或 AST 分析比简单读文件更有效，可回答“改这里会影响什么”，并减少 token 和工具调用；这与“纯 agentic search”形成对比。 • 对代码质量存疑：有用户举例 Claude 曾只读取每个文件前 40 行，后来才修正为 AST 分析；认为它能修复局部明显错误，但难以处理由许多看似合理的小决策累积出的系统性低质量。 • 对脚手架与配置困惑：多人询问 CLAUDE.md/AGENTS.md、skills、LSP 插件到底如何有效使用；质疑如果某些提示能稳定提升性能，为何不内置到系统提示中，并希望看到可复制的优秀示例。 • 对宣传语和成功标准怀疑：评论认为文章空泛、缺少实证；质问“大型代码库成功模式”的衡量标准是什么，如团队速度、代码寿命、生产事故减少等。 • 使用体验分歧：有人表示常用且喜欢 Claude Code；也有人称它漏读关键代码、幻觉完成情况，并认为很多团队已转向 Codex。 补充讨论：还有人质疑“本地可复制的 monorepo 是否算大型代码库”、Claude 是否把大量代码上传给模型，以及为何 C/C++/Java/PHP 被特别强调为“不常关联 AI 编码工具”的语言。

微软宣布将大幅优化 WinUI 3 性能，重点改进应用启动时间，并以文件资源管理器和记事本为主要基准。目前文件资源管理器启动中 WinUI 部分已实现：内存分配减少41%、临时分配减少63%、函数调用减少45%、WinUI代码耗时减少25%。改进将陆续进入 winui3/main，并尽可能纳入 WinAppSDK 2.x。部分优化可能涉及破坏性变更，需应用主动选择启用，未来版本或默认开启。

评论摘要
主要讨论点：围绕 WinUI/Windows 应用性能优化展开，重点是微软 UI 技术栈是否过慢、是否应统一到 WinUI，以及开发体验和跨平台能力是否足够。 不同观点： • 性能批评派：多位评论认为 WinUI 3 明显慢于 WPF/UWP，甚至老技术更快；Windows 11 中计算器、文件管理器、图片查看等基础应用启动或响应迟缓，被视为微软忽视性能的例子。 • 质量改进期待派：有人认为微软开始关注质量和性能是好事，希望这些优化能真正影响系统应用，并促使 WinUI 成为统一的 Windows 应用开发框架。 • 质疑技术方向派：有人讽刺“又需要新标准”，认为 UI 等早已解决的问题被重新发明，却变得更耗资源；争议焦点在于新框架是否带来真实价值。 • 开发者体验批评派：有开发者表示 WinUI 3 开发体验糟糕，文档不足，需要大量 hack，甚至要读控件底层实现；对用 XML 重新实现文本框等做法感到不安。 • 跨平台诉求派：有人希望 WinUI 支持 macOS，或质疑为何不用 EGUI、Avalonia 等跨平台方案；也有人提出需要 F#、C 接口和多语言绑定支持。 • 类比其他平台：有人提到 macOS Finder 在 Apple Silicon 上仍显得慢，说明性能问题并非微软独有，但希望厂商都能重视基础应用体验。 补充讨论：争议核心在“优化单个组件是否足以改善整体体验”，以及微软是否真正把技术质量置于管理目标之上。
