文章摘要

Prusa Research推出开源ColorMix色彩混合模型，让多材料3D打印机突破物理装载颜色限制。该技术借鉴2D打印的CMYK原理，通过交替打印青、品红、黄、黑、白五色薄层实现数十种色调。ColorMix基于社区项目发展而来，采用MIT许可证开源，已集成到PrusaSlicer和EasyPrint切片软件中。相比现有方案，它提供更准确的色彩预览和更简便的工作流程。Prusa还推出专用的Prusament CMYKW耗材套装，在五喷头XL打印机上可实现约40种色彩组合，让3D打印色彩效果更接近绘画。

Floor and Ceil versus Denormals on CPU and GPU

作者: ibobev | 评分: 32 | 评论数: 4 | 发布时间: 2026-05-26 13:22
文章摘要

这篇文章探讨了浮点数运算中floor和ceil函数在处理非规格化数(denormals)时的行为差异。 核心问题是：`floor(-1.175493930432748e-38)`的结果是什么？ 文章首先解释了floor、ceil、trunc、round四个函数的舍入规则。关键在于，该输入值是一个非规格化数（接近零的极小值）。不同平台对非规格化数的处理方式不同： - **保留非规格化数**：`floor(-1.175...e-38) = -1.0` - **将非规格化数归零**：`floor(-1.175...e-38) = -0.0` 这种差异可能导致CPU和GPU之间、不同GPU厂商之间的不确定性行为。作者测试发现，x86-64架构的CPU（使用Visual Studio 2022编译）在各种编译选项下都保留非规格化数。

评论摘要
主要讨论点：GPU/CPU 浮点数非正规化数（denormals）的处理方式及其性能影响 不同观点： • **直接归零派**（yosefk）：建议将非正规化数直接归零处理。指出即使是非正规化数的发明者也难以编写正确处理它们的代码，引用了相关论文附录作为证据 • **性能优化派**（crote）：从实践角度支持归零处理。提到 CPU 处理非正规化数会导致约 10 倍性能下降，对于大多数应用场景，非正规化数与零的差异可以忽略，建议启用编译器的 denormals-to-zero 标志来获得性能提升 • **正确性质疑派**（kevmo314）：质疑为什么正确实现会影响性能，表示不理解舍入的典型实现方式，暗示可能存在更好的实现方法 • **标准改革派**（andrepd）：认为这是 IEEE 浮点数设计的多个问题之一，呼吁认真考虑新的浮点数设计方案，提出 Posits 作为可能的替代或补充标准 补充讨论：评论暗示 Nvidia 为追求 GPU 最大性能而采取了某种"捷径"实现，这可能是引发讨论的导火索。核心争议在于正确性与性能之间的权衡取舍。

文章摘要

MacSurf 是一个为 25 年前的 Mac OS 9 PowerPC 系统开发的现代网页浏览器。它支持 CSS3、ES5 JavaScript、PNG 透明度和原生 TLS 1.2/1.3 加密连接，能在 233 MHz G3 处理器上运行。 该项目基于 NetSurf 移植，是首个在 Mac OS 9 上支持 CSS Grid、CSS 自定义属性和 ES5 JavaScript 的浏览器。最新版本(v1.3.1)实现了多曲线 ECDHE 和 TLS 1.3 协议，内置 121 个 Mozilla CA 证书，无需代理即可访问现代 HTTPS 网站。 目前处于早期 alpha 阶段,可运行但尚不完善。使用 C89 和 Carbon/QuickDraw 等经典工具开发,旨在让老旧 Mac 重新连接现代互联网。

评论摘要
主要讨论点：为Mac OS 9等老旧系统开发现代浏览器的意义和实践 不同观点： • **技术怀疑派**：认为现代网页对硬件要求过高，老旧设备运行JavaScript需要比当年高2000倍以上的晶体管密度，暗示这类项目实用性有限 • **环保未来派**：认为AI辅助编程能为老旧、废弃硬件带来新功能，这是减少电子垃圾、实现"太阳朋克"可持续未来的希望 • **实用体验派**：提到Classilla浏览器在iMac G3上表现不错（开发至2021年），说明老系统浏览器确有实际价值 • **极简主义派**：考虑用老Mac OS系统搭建低干扰、高专注的工作环境，认为当年基于用户体验研究设计的UI仍有优势 • **怀旧爱好者**：多位用户表达热情，计划在自己的老设备（Bondi Blue iMac G3、PowerMac G4 MDD等）上尝试 补充讨论：评论整体氛围积极，用户对项目表示支持和喜爱，没有明显争议。技术局限性的提及更像是客观陈述而非批评。

The dead economy theory

评论摘要
主要讨论点：AI自动化对就业和经济的影响，以及社会应如何应对 不同观点： • **乐观派**：AI会提高生产力，失业工人可找到收入更高的新工作，企业会用AI工具扩大市场份额而非裁员，这是零和思维的陷阱（czhu12, alex_young） • **悲观派**：大规模失业将导致消费需求崩溃，企业失去客户基础，最终形成恶性循环。引用马匹数量在汽车出现后暴跌88%的历史类比（spondelkryp, wcfrobert） • **UBI支持者**：普遍基本收入是必然趋势，但文化尚未接受，可能需经历多轮危机才会实施。人们需要的是社区和意义，而非被迫工作（andai, spongebobstoes, wonkyfruit） • **政府干预派**：应将AI公司国有化作为公共设施，利润用于基建和探索性项目（如太空探索），类比1930年代大萧条时期的基建计划（pacifi30） • **技术怀疑派**：LLM距离真正AGI还很远，当前AI更像是工具升级而非革命，且训练数据获取存在根本矛盾（riazrizvi, rootusrootus） 补充讨论：多位评论者指出经济循环的核心是货币流通（引用Terry Pratchett小说），强调民主制度可能通过选举迫使变革，以及AI公司IPO后财务数据公开将揭示真实盈利能力。

主要讨论点：Liquid AI 发布的 LFM2.5-8B 模型的性能表现和实际应用价值 不同观点： • **性能质疑派**：实测表现不佳。代码修复基准测试中仅修复12%的bug，远低于两年前的Qwen2.5-Coder-3B（50%）；有用户反馈前代模型"宣传大但实际表现差"；简单问题回答也出现错误 • **性能认可派**：8B模型表现"非常出色"，长文本摘要执行良好；小模型整体进步显著，结合量化和MoE技术可在本地硬件运行，逐步替代付费订阅服务；对实时VLA模型应用前景看好 • **技术争议派**：训练数据量38T tokens相对8B参数过大，可能存在过度训练；是Chinchilla缩放定律的1800倍，远超常规；担心知识压缩遇到数学极限，基准测试可能过拟合 • **许可证警告**：官方宣称"无限制下载和部署"具有误导性，实际许可证对年收入超1000万美元的组织有重大限制 补充讨论：模型在基准测试中表现优于对比对象，但实际应用场景存在明显差距；CPU运行可行性获得关注。

Bijou64: A variable-length integer encoding

作者: justinweiss | 评分: 173 | 评论数: 22 | 发布时间: 2026-05-29 15:03
文章摘要

这篇文章介绍了一种名为bijou64的可变长度整数编码方案。作者在开发Subduction CRDT同步协议时，为解决签名验证中的规范性问题而设计了它。 传统的变长整数编码（如LEB128）存在一个问题：同一个数字可以有多种表示方式（如0可以编码为0x00、0x80 0x00等），这在需要签名验证的场景中会导致安全问题。 bijou64通过两个设计巧思实现了"构造性规范化"： 1. 首字节双重用途：0-247直接表示数值，248-255作为标签指示后续字节数 2. 每个数字只有唯一的编码方式，无需额外的规范性检查 意外收获是：bijou64的运行速度比LEB128快数倍，因为其设计减少了不必要的工作量。

评论摘要
主要讨论点：变长整数编码方案的优劣比较，特别是 Bijou64 与 LEB128 等方案的权衡 不同观点： • **性能优先派（kstenerud）**：认为 SIMD 指令下 LEB128 或哨兵值方案因并行化优势表现更好，即使文本解析也能超越 Bijou64 这类方案 • **规范编码支持派（i2talics, michaelmure）**：强调非规范编码在某些场景（如 DWARF/WASM 链接）有实际用途，LEB128 允许用最宽编码避免重定位；同时指出单一编码方式便于模糊测试 • **实用主义派（boricj, stebalien）**：认为应根据场景选择，若性能重要且整数有界则用定长编码；LEB128 在 2^14 内保持 2 字节效率更高，适合标签/长度场景 • **安全关注派（aDyslecticCrow, nine_k）**：警告需防范恶意输入（如声称 255 字节但无后续数据），质疑为何安全相关项目测试中缺少对抗性输入 补充讨论： 多人提及类似方案（UTF-8 过长编码、SQLite varint、ISO 7816-4 BER-TLV），显示这是编码设计中的常见问题。wahern 分享了 Yubikey 4 因过长编码导致的实际漏洞案例，印证了规范化的重要性。willtemperley 困惑为何编码器会生成 LEB128 允许的填充字节。
