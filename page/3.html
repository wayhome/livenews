Phoenix LiveView 1.2

作者: ksec | 评分: 146 | 评论数: 7 | 发布时间: 2026-06-14 04:53
文章摘要

Phoenix LiveView 1.2 发布了！主要新特性是**协同定位CSS（Colocated CSS）**，允许开发者直接在 HEEx 模板中编写 CSS 样式。通过在编译时提取样式到特殊目录，并利用 CSS 的 `@scope` 规则实现样式作用域隔离，避免不同组件间的样式冲突。LiveView 通过在 HTML 元素上添加 `phx-r` 和 `phx-css-*` 属性来标记模板边界，实现精确的样式范围控制。由于 `@scope` 浏览器支持度有限，1.2 版本提供了自定义作用域策略的行为接口。此外还包含一些小改进。升级只需更新 mix.exs 中的版本号。

评论摘要
主要讨论点：Phoenix/Elixir框架及LiveView技术的使用体验和评价 不同观点： • **积极支持派**：认为Phoenix和Elixir生态系统优秀，BEAM内置功能强大，开发体验愉快。有用户用Phoenix构建了Etsy替代品，称赞Ash框架用于数据建模。另有用户强调LiveView相比NextJS更简洁，性能更好，Phoenix原生提供缓存、后台任务和认证等功能。 • **后端渲染SPA方案认同者**：喜欢以后端为主的SPA架构，认为这种方式快速、易维护、组件少。实践案例显示通过优化（Early Hints、压缩、内联CSS）可达到极致性能，适合中等复杂度网站。 • **谨慎观望派**：对Phoenix的CSS集成和colocated JS特性持保留态度，担心会造成代码混乱，类似Rails 2.x时代的rjs问题——JS片段分散在代码库中难以调试和维护。倾向等待几年观察成熟度后再尝试。 补充讨论：有用户关注LLM对Elixir/Phoenix代码生成的支持程度，计划通过实际项目测试。另有用户询问与ASP.Net/Blazor的对比，但未得到回应。

文章摘要

施乐PARC研究中心在70年代开发了革命性的EARS系统（Ethernet、Alto、RCG和SLOT激光打印机），解决了个人电脑高质量打印的难题。关键创新包括：将处理任务从主机转移到专用硬件RCG；开发所见即所得文字处理软件Bravo；创建页面描述语言Press来压缩和传输文档信息。这套系统通过以太网实现网络打印，在PARC内部大获成功。然而施乐高层将其商业化为售价29.5万美元的独立产品9700，虽然年收入超10亿美元，但错失了分布式个人计算的真正潜力。这些技术后来启发了苹果LaserWriter和Adobe公司的诞生。

评论摘要
主要讨论点：Interpress 与 PostScript 在页面独立性和保护机制上的设计哲学差异 不同观点： • **Interpress 的强制保护立场**：语言系统必须强制保证某些有用的特性，页面被定义为独立的，页面之间不可能相互影响，保护机制是强制性的 • **PostScript 的可选保护立场**：语言系统应该为用户提供实现这些特性的手段，但由用户决定是否使用。通过文档结构约定（Document Structuring Conventions）和 SAVE/RESTORE 等工具，用户可以复制 Interpress 的组织方式并获得相同的好处，但这不是强制要求 • **设计哲学类比**：这种强制 vs 可选保护系统的争论，不仅存在于编程语言社区，也类似于摩托车头盔佩戴的强制与自愿之争 补充讨论：PostScript 最初使用注释来声明和分隔文件不同部分，这实际上不是 PostScript 语言本身的一部分。Brian Reid 作为这段历史的关键见证人（Xerox PARC 顾问、参与 Interpress 设计、导师是 Interpress 三位架构师之一），于 1985 年在 fa.laser-lovers 社区发表了这一权威的第一手历史记录。

Beagle: Git, URIs and all the dirty words

作者: gritzko | 评分: 22 | 评论数: 4 | 发布时间: 2026-06-11 18:05
文章摘要

Beagle是一个git兼容的版本控制系统，通过HTTP URI和标准HTTP动词简化git操作。它将git的复杂命令分解为六个正交的基本操作：GET（从仓库获取到工作树）、HEAD（干运行）、POST（提交）、PUT（编辑引用日志）、DELETE（删除）、PATCH（应用变更）。传统git中令人困惑的merge、rebase、squash、cherry-pick等操作被统一表达为这些基本操作的组合。例如rebase是先PATCH应用提交，再POST复用原消息；merge是PATCH应用整个分支，POST添加新消息并保留父引用。Beagle用URI查询参数处理版本信息，使git操作更清晰标准化。

评论摘要
主要讨论点：关于用HTTP类比简化Git界面的尝试 不同观点： • **怀疑HTTP类比的有效性**（PufPufPuf）：认为HTTP类比过于晦涩，不如传统的"checkout分支，提交代码"等概念清晰。"post ?branch!"这样的表述反而让人困惑，即使作者试图简化Git，但这种类比并不成功。 • **质疑简化方向的选择**（oakinnagbe）：承认简化Git的努力值得肯定，但质疑将Git做成HTTP风格是否真的是用户需要的简化方式。 • **支持底层思路但反对具体实现**（quantummagic）：赞同在Git原语之上构建新UI的理念，但认为REST启发的模型不够人性化，应该寻找更友好的交互模型。 • **讽刺增加复杂度**（OJFord）：用"yo dawg"梗讽刺这个尝试反而让本已混乱的版本控制CLI变得更加confusing。 补充讨论：所有评论者的共识是Git确实需要改进，但HTTP/REST类比被普遍认为是错误的方向，反而增加了认知负担而非降低门槛。

这篇文章讲述了阿拉伯文网页排版中的一个技术问题。作者接到一个工单：阿拉伯文段落无法实现两端对齐。问题根源在于，传统阿拉伯书法通过拉长字母间的连接笔画（kashida/taṭwīl）来填满行宽，而非像拉丁文那样增加词间距。但现代网页技术无法自动实现这种传统排版效果，CSS的`text-align: justify`只会拉伸空格。作者追溯了这一技术债务的历史渊源，涉及五百年的印刷与数字化演变，包括Unicode编码问题、PDF库缺陷等多个层面的技术困境。文章揭示了阿拉伯文数字排版长期被忽视的现状。

评论摘要
主要讨论点：阿拉伯文在现代计算机系统中的排版和渲染问题，以及技术界对此的忽视 不同观点： • **问题严重性认知**：多数评论者（samat、throw-the-towel、qingcharles）强调阿拉伯文用户面临的实际困境——光标异常跳转、双向文本混乱、数字显示错误等日常问题严重影响使用体验，甚至导致资深工程师放弃编写双语邮件 • **技术复杂性解释**：部分评论者（evmar、evilturnip、jansan）从技术角度分析，认为阿拉伯文本身的复杂性（连写、上下文变形、双向排版）与拉丁文的复杂性（变宽字符、连字、断字）本质相似，只是主流系统以拉丁文为默认导致阿拉伯文支持不足 • **解决方案分歧**：jansan提出在渲染层实现拉伸功能的技术方案；mohamedkoubaa建议使用断开式字体；而anal_reactor则激进地建议创造新文字系统（遭到隐含反对，因为已有阿拉伯数字拉丁化实践） • **历史与文化视角**：文章提到"简化阿拉伯文"历史及其创造者被暗杀的悲剧，slim指出IE 5.5曾短暂实现正确的阿拉伯文对齐，凸显技术进步的不连续性 补充讨论：多位评论者感叹技术行业优先级错位——数亿人的基本文字需求被忽视，资源却投入到"AI杂货"等噱头项目
