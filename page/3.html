这篇文章讲述了一份被称为"最美遗嘱"的故事。遗嘱由美国伊利诺伊州律师Charles Lounsberry在精神病院去世前写下。James Barrie爵士在伦敦作家俱乐部晚宴上提及此事。 遗嘱内容充满诗意：将田野的花朵、树林、溪流留给孩童；将运动场地、河流湖泊留给男孩；将星空、玫瑰、音乐留给恋人；将力量和友谊留给青年；将回忆和诗歌留给成年人。 这份遗嘱没有财产价值，却被认为是最感人的遗愿，因为它将世间美好分配给后人，提醒人们珍惜生命中的简单快乐。

评论摘要
主要讨论点：关于一份据称由精神病院病人Charles Lounsberry撰写的"最美遗嘱"的真实性和评价 不同观点： • **虚构说**（technothrasher）：经过调查，这篇文章实际上是Williston Fisk在1898年为Harper's Weekly撰写的虚构作品，后来被赋予了各种不同的背景故事 • **质疑现代写作能力**（LucifersCat）：即使作者真的在精神病院，其写作水平也远超当代普通人——能写得如此连贯优美，反而说明作者并非真正的"精神病患者" • **法律悖论**（1970-01-01）：指出遗嘱开头声称"神智健全"（sound and disposing mind）与作者身处精神病院、被认定"完全疯癫"的背景存在直接矛盾，引用法律术语说明这一矛盾 • **文学价值肯定**（FpUser）：不确定"最美"的评价是否恰当，但承认这份遗嘱确实写得很美 补充讨论：核心争议在于这份遗嘱的真实性——从虚构作品到作者身份，再到法律效力上的自相矛盾，但多数评论者认同其文学价值。

WASI 0.3

作者: mavdol04 | 评分: 216 | 评论数: 13 | 发布时间: 2026-06-12 13:51
文章摘要

WASI 0.3 正式发布，WebAssembly 组件模型原生支持异步。主要变化：将异步原语（stream、future、async func）直接集成到组件模型的规范 ABI 中，由宿主统一管理事件循环，替代了 WASI 0.2 中每个组件独立事件循环的设计。这使得组件间可以协同工作，简化了 API 签名，消除了繁琐的 start/finish/subscribe 模式。采用基于完成的异步模型（类似 io_uring），各语言绑定生成器可生成符合语言习惯的异步接口。流错误处理也得到改进，通过独立的 future 返回状态。

评论摘要
主要讨论点：WASI 0.3 发布后，社区对 WebAssembly 组件模型方向和开发透明度的争议 不同观点： • **支持者立场**：yoshuaw 发布官方公告，强调 0.3 增加了异步功能和流处理；hmry 关注技术实现细节（stack-switching）；_jsdw、ilaksh 等表达学习兴趣 • **反对复杂化**：garganzol 认为 WASI 应保持简单稳定，批评组件模型是"CORBA式的怪物"，过度复杂化偏离了 Unix-like API 的初衷；认为组件模型应独立发展，不应绑定到 WebAssembly 生态 • **批评开发流程**：b33j0r 强烈不满开发不透明（"在阴影中工作"），近两年难以追踪进度；质疑组件模型未兑现承诺，市场需要动态热加载，但 WASI 要求静态链接，"击败了 99% 的用例"；已转向自定义集成方案 • **替代方案**：syrusakbary（Wasmer 团队）指出 WASI 0.3 打破向后兼容性，仅一个运行时支持，浏览器不支持；推荐 WASIX 作为编译 C/C++ 程序的更实用选择 • **质疑实用性**：shevy-java 质疑 WebAssembly 十年来未取得真正突破，使用率依然很低；lifty 询问实际使用案例和相比容器/VM 的优势 补充讨论：社区对工具链成熟度（Rust 0.3 目标支持）、功能需求（模块自省能力）表达关注

文章摘要

这篇文章批评美国联邦通信委员会(FCC)以打击骚扰电话为名，提议要求电话运营商在提供服务前收集用户身份信息的"了解你的客户"(KYC)规则。作者认为这是披着消费者保护外衣的监控措施，不会有效阻止犯罪分子，却会侵犯普通人隐私。文章指出预付费手机对家暴受害者、记者、抗议者等群体至关重要，KYC规则可能剥夺匿名通信权利。作者还警告该提案可能导致无辜者被列入黑名单、身份信息长期保留面临泄露风险，以及执法范围扩大等问题。

评论摘要
主要讨论点：FCC提议对预付费电话实施"了解你的客户"(KYC)实名制以打击诈骗电话，引发隐私、安全和有效性的激烈争论。 不同观点： • **支持技术解决方案派**：认为应从源头解决，要求电信运营商停止允许来电显示欺骗，实施STIR/SHAKEN全认证，只接受完整认证的来电。主张透明显示真实付费方信息，而非强制收集用户数据。 • **反对KYC派**：强烈反对实名制。理由包括：(1)电信公司频繁数据泄露，不可信任敏感个人信息；(2)预付费手机持续广播位置，实名后隐私完全丧失；(3)KYC/AML本质是规避正当程序，将执法权交给私企，普通人无申诉渠道；(4)大型洗钱案(如HSBC)证明KYC只限制普通人，犯罪分子仍能绕过。 • **系统重构派**：认为传统电话系统已过时，应推动WebRTC等新技术，设计可随时丢弃的一次性号码，取消号码回收制度，增加视频通话预览等反诈功能。 • **问责企业派**：建议"了解你的公司"而非用户，应公开骚扰电话背后企业信息，让消费者掌握主动权。 补充讨论：多位用户抱怨FCC意见提交系统存在技术障碍(reCAPTCHA无法通过)且会公开个人信息，讽刺政府一边要求收集隐私一边泄露隐私。争议焦点在于：是否应为打击诈骗而牺牲预付费用户的匿名权。

Encrypted Spaces An architecture for collaborative applications

作者: _____k | 评分: 60 | 评论数: 5 | 发布时间: 2026-06-12 12:22
文章摘要

**加密空间(Encrypted Spaces)**是一个研究项目,旨在构建协作应用架构,使数据加密存储在不受信任的服务器上。核心理念是:服务器作为数据存储和同步中心,但无法读取用户明文数据;通过密码学证明验证服务器行为正确性;系统自动处理成员管理、密钥管理和加密。 该项目解决云协作工具的三大风险:数据泄露、失去控制权、自我审查。技术实现包括五个组件:成员状态、可验证数据库、密钥管理、密钥保留系统和应用操作。团队正在开发类似Firebase的同步引擎原型,为开发者提供熟悉的API,底层自动处理加密和验证。

评论摘要
**主要讨论点：** 加密协作系统的实用性与技术实现方式 **不同观点：** • **历史成功案例（rozzie）：** Groove系统（1997-2005）证明去中心化加密架构在高安全需求场景下确实可行，曾被美国国防部、情报机构、NGO广泛使用。但同时指出，即使技术成熟，企业和消费市场对去中心化方案兴趣不大。 • **技术期待落差（krunck）：** 认为当前系统仍是服务器存储加密数据的传统模式，期望看到真正的全同态加密（FHE）实现——服务器可直接对加密数据进行计算，而非只做存储。 • **用户验证机制质疑（ebb_earl_co）：** 对"用户验证加密证明以确保服务器行为正确"这一设计持悲观态度，类比PGP密钥签名会从未真正普及的历史，暗示这种依赖用户主动验证的机制不现实。 • **元数据泄露担忧（brianwmunz）：** 指出核心问题在于"服务器为支持富查询能看到什么"——任何可查询内容都是可能泄露或被传唤的元数据（成员关系、访问模式、查询频率），这对活动家/记者等高敏感用户才是真正的风险点。 **补充讨论：** 争议焦点集中在加密系统的实用性权衡——技术可行性与用户接受度、查询功能与隐私保护之间的矛盾。

Looking Forward to Postgres 19: It's About Time

作者: xngbuilds | 评分: 125 | 评论数: 19 | 发布时间: 2026-06-12 16:44
文章摘要

这篇文章讨论了数据库中的时态表(temporal tables)技术发展。传统方法中,Postgres使用btree_gist扩展和排除约束来防止时间范围重叠,但这种方式不直观且数据库无法真正理解时态数据。SQL:2011标准早在十多年前就定义了时态表规范,其他数据库较快采用,但Postgres直到19版本才引入原生支持。文章还介绍了Henrietta Dombrovskaya开发的pg_bitemporal扩展,它通过PL/pgSQL实现双时态表管理,同时追踪"有效时间"(事实真实时间)和"事务时间"(数据库记录时间),可回答"上周二我们认为价格是多少"这类复杂查询。

评论摘要
主要讨论点：PostgreSQL 新增的时态表（temporal tables）功能，用于处理数据的时间版本管理 不同观点： • **积极支持派**：多数开发者表示这个功能非常有用且期待已久。pjungwir（该功能贡献者）希望继续改进并征求反馈；MBCook 认为这比手动用日期范围+GIST索引方便很多，解决了外键约束的痛点；mrinterweb、bhaak、oveja 等表示在实际项目中迫切需要此功能。 • **实现方案讨论**：IgorPartola 提出更复杂的需求——不仅需要时间追踪，还需要版本控制。例如税率数据录入错误时，既要保留错误版本（用于核对历史发票），又要记录正确版本，这需要同一时间段的多版本支持。 • **性能担忧**：fabian2k 担心时态表在查询当前数据时的性能问题，询问是否可以通过分区将活跃数据和历史数据分离，类似手动版本管理中的主表+归档表模式。 • **设计质疑**：larsnystrom 质疑为何要存储时间段（起止日期）而不是仅存储生效日期；ris 对 UPDATE 操作会添加新行感到不安，认为这打破了 DBA 的常规假设。 补充讨论：bonesmoses 认为 PostgreSQL 19 是自 v10 以来新特性最多的版本；speedbird 提到早期 Postgres 曾有时间旅行功能；cherryteastain 指出该功能对交易系统很有价值。

Kimi K2.7-Code: open-source coding model with better token efficiency

作者: nekofneko | 评分: 303 | 评论数: 22 | 发布时间: 2026-06-12 10:42
文章摘要

Kimi K2.7 Code 是基于 K2.6 构建的编程专用模型，采用 MoE 架构（1T 总参数，32B 激活参数），支持 256K 上下文长度。该模型在复杂软件工程任务上表现显著提升，思考 token 使用量减少约 30%。在多项编程和智能体基准测试中表现优异，包括 Kimi Code Bench V2（62.0）、Program Bench（53.6）等。模型支持原生 INT4 量化，可通过 Moonshot 平台 API 访问，兼容 vLLM、SGLang 等推理引擎部署。

评论摘要
主要讨论点：Kimi K2.7 Code模型的性能表现、定价策略，以及中美AI模型的竞争格局 不同观点： • **价格敏感派**：认为中国模型性价比优势明显。Kimi K2.6定价($0.7/$3.4)远低于Opus($5/$25)，只要质量接近就值得切换。有用户表示每月$100账单压力大，希望降低成本 • **性能优先派**：愿意为顶级模型付费。认为Opus 4.7/4.8和Fable仍有明显优势，虽然贵但物有所值。有人提到曾预期中国模型会追上但实际未达预期 • **阈值理论**：认为模型发展会达到"足够好"的临界点，之后价格竞争将成为主导。届时即使顶级模型更好，用户也会选择便宜的替代品 • **实用主义**：部分开发者认为对于函数级编程任务，模型差异不大，工作流程更重要。K2.7相比K2.6减少token使用，已足够理由切换 • **benchmark派**：引用数据显示GPT-5.5(62.7%)和Opus 4.8(62.2%)领先K2.7(56.3%)和K2.6(48.2%)约6-14个百分点 补充讨论：有用户质疑Anthropic护城河是否仅靠"美企不能向中国传数据"；DeepSeek v4被视为新的性价比标杆；有人关注开源模型的安全性审查；K2.7改进了自定义工具调用和UI生成能力
