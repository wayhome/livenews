ClickHouse gets lazier and faster: Introducing lazy materialization

作者: tbragin | 评分: 310 | 评论数: 20 | 发布时间: 2025-04-22 16:03
文章摘要

ClickHouse引入了“懒惰物化”（lazy materialization）机制，进一步优化了数据查询速度。其核心理念是尽可能避免不必要的数据读取和处理，从而加速查询。懒惰物化通过延迟读取列数据，直到真正需要时才进行处理，特别适用于排序和大限制条件的"Top N"查询场景。 ClickHouse已有多种I/O优化技术，如列式存储、稀疏主索引、次级数据跳过索引、PREWHERE过滤等，这些技术通过跳过不相关的数据块和列来减少I/O。然而，这些方法仍假设所有通过WHERE过滤的行数据都需要被读取。懒惰物化则更进一步，仅在查询执行计划需要时才读取列数据，从而显著提升性能。 在实际测试中，一个查询从219秒加速到139毫秒，性能提升了1,576倍，而SQL语句未做任何修改。这种优化特别适用于分析和观测场景中的常见查询模式。

评论摘要
主要讨论点：ClickHouse的性能、优化、使用体验及与其他数据库的比较 不同观点： • tnolet：认为ClickHouse显著提升了数据处理性能。尽管Postgres可以通过大量优化达到可接受的响应时间，但ClickHouse无需过多优化就能实现高效性能。 • dangoodmanUT：赞赏ClickHouse的性能和社区贡献，但对该团队在竞争处理上的做法（如删除GitHub上的竞争对手引用）表示质疑，同时希望其在使用体验上能像DuckDB一样友好。 • jurgenkesker：对ClickHouse的快速和易用表示赞赏，认为相比之前的解决方案有显著提升。 • tmoertel：关注ClickHouse在随机采样查询上的优化，特别是对大列数据的延迟物化（lazy-materialization）优化，并希望确认这种优化是否适用于复杂的ORDER BY子句。 • simonw：对ClickHouse的极速查询性能感到惊讶，特别是其在现代硬件上的表现，并提到文章清晰易懂，提供了很好的图示和解释。 • mmsimanga：认为如果ClickHouse有原生的Windows版本，它会比DuckDB更受欢迎，并以MySQL为例说明Windows安装包对流行度的影响。 • xiasongh：提出ClickHouse与StarRocks在Join性能上的比较，并询问当前情况是否有所变化。 补充讨论： • kwillets：引用了关于后期物化（Late Materialization）的研究文献，为讨论提供了学术背景。 • skeptrune：赞赏文章的技术内容和叙述方式，认为其兼具技术性和可读性。 • jangliss：幽默地提到自己误以为是在看Clickhole.com，增加了讨论的趣味性。 • justmarc：高度评价ClickHouse的工程设计和性能表现。 • higeorge13：关注优化是否适用于LIMIT OFFSET查询。 • vjerancrnjak：强调ClickHouse相对于行式数据库的速度优势，并提到其在压缩和性能上的潜力。 • ohnoesjmr：关心优化如何在子查询和CTE中传播。 • simianwords：认为延迟物化优化似乎是显而易见的，但对ClickHouse在行业中的领先地位表示认可。 争议焦点： • ClickHouse团队在竞争处理上的做法（如删除GitHub上的竞争对手引用）引发了一定的质疑和讨论。

本文报道了一种基于二维材料的闪存，通过二维增强热载流子注入机制，实现了400皮秒的编程速度，超越了传统闪存的速度限制。该闪存利用了二维Dirac石墨烯通道，支持电子和空穴注入，具有非易失性和超过550万次循环的耐久性。通过优化水平电场分布，注入电流提升至60.4 pA/μm，且二维半导体二硒化钨展现出不同的热空穴注入行为。该技术突破了非易失性内存的速度瓶颈，甚至超过了最快的高速静态随机存取存储器（SRAM），为未来高性能计算提供了可能。尽管如此，新兴内存技术仍面临诸如热干扰、缩放困难等挑战。

评论摘要
主要讨论点：新型皮秒级闪存设备的稳定性和耐久性，以及在实际应用中的限制和挑战。 不同观点： • [userbinator] 对设备在60,000秒（约16小时）后的稳定性表示怀疑，认为文章中提到的10年寿命和550万次循环耐久性不够清晰，可能存在仅关注耐久性而忽视数据保留能力的问题。他还提到了一篇关于USB驱动器耐久性测试的旧论文，指出只关注编程耐久性而忽视数据保留的类似问题。 • [kvemkon] 引用了另一篇关于皮秒级闪存设备的研究文章，将讨论引导至近期关于闪存技术发展的其他研究，提供了一个扩展阅读的链接。 • [thund] 直接引用研究内容，强调该闪存设备在400皮秒编程速度、非易失性存储以及超过550万次循环的 robust 耐久性等技术参数。 • [bob1029] 提出即使内存本身速度极快，实际应用中还需要考虑与内存进行通信的物理距离问题。他认为内存的空间距离比单个元件的速度更为关键，并质疑为何L1缓存不能任意扩展。 补充讨论： • 关于闪存设备耐久性测试的争议焦点在于是否只关注了设备的耐久性而忽略了数据保留能力，userbinator 通过引用旧论文指出了类似问题。 • bob1029 提出的物理通信距离问题引出了实际应用中内存技术面临的另一个重要限制，即不仅仅是速度，还有与内存交互的其他因素同样关键。

Rowboat 是一个由 OpenAI 的 Agents SDK 驱动的多代理工作流构建工具，可以在几分钟内通过 AI 构建多代理工作流。用户可以通过简单的文本描述（如为食品配送公司创建助手）开始，系统将自动构建相应的工作流。用户可以将 MCP 服务器连接到 Rowboat，并通过 HTTP API 或 Python SDK 将代理集成到自己的应用程序中。快速入门包括设置 OpenAI 密钥、克隆代码仓库并启动 Docker。Rowboat 提供详细的 API 和 SDK 文档，支持通过 REST API 或 Python 代码与代理进行交互。该项目使用 Apache-2.0 许可证，代码主要由 TypeScript 和 Python 编写。
