Everything I know about good API design

作者: ahamez | 评分: 242 | 评论数: 21 | 发布时间: 2025-08-24 19:10
文章摘要

这篇文章主要探讨了API设计的原则和最佳实践。作者指出好的API应该"无聊"且易于使用，开发者不应过多思考API本身而是专注于目标。API一旦发布就难以更改，因此设计时需要平衡简单性和灵活性。文章强调"不破坏用户空间"原则，任何更改都可能影响下游应用。对于必要的重大变更，建议采用版本控制策略（如/v1/和/v2/），并给予用户充足时间迁移。作者认为API设计应当以稳定性优先，避免为追求完美而进行不必要的修改。

评论摘要
主要讨论点：[API 设计与稳定性、版本控制、幂等性及用户体验] 不同观点： • **API 稳定性与版本控制** - [dwattttttt] 强调内核 API 的稳定性与声明的重要性，指出“永不破坏用户空间”但内核 API 可以随时变更。 - [pixl97] 建议从一开始就引入版本化 API，以应对未来的不可预测变化。 - [wener] 反对通过 /v1、/v2 路径进行版本控制，认为应通过字段或参数扩展功能，而非强制用户更改基础 URL。 • **幂等性实现争议** - [achernik] 质疑 Redis 存储幂等键的可靠性，认为需与操作原子性绑定，避免中间状态导致数据不一致。 - [barapa] 支持将幂等键与写入操作放在同一事务中存储，确保一致性。 - [mrkeen] 提出幂等性可能需保证相同异常重复抛出，而不仅是操作执行一次。 • **API 设计与用户体验** - [runroader] 认为内部用户同样是用户，需避免频繁变更 API 设计，建议通过“自用测试”确保稳定性。 - [claw-el] 批评过度抽象的 API 资源设计会增加理解与调试难度，尤其对新用户不友好。 - [canpan] 指出非技术用户（如销售、学生）可能缺乏基础技能（如时区转换），API 需考虑易用性。 补充讨论： - **历史视角**：[0xbadcafebee] 提醒 API 概念源自 1940 年代，建议从早期案例中汲取设计经验。 - **文档质量**：[JimDabell] 认为 API 质量与文档获取难度成反比，隐藏文档可能预示设计糟糕。 - **行业案例**：[frabonacci] 点名批评 Spotify、Reddit 等公司违反“不破坏用户空间”原则。 - **外部资源**：[tiffanyh] 推荐了额外的 API 设计指南链接。 争议焦点： - 幂等性实现是否必须依赖事务性存储（如数据库）而非独立缓存（如 Redis）。 - 版本控制应通过路径（/v1）还是参数扩展实现，后者是否更灵活。

文章摘要

这篇文章揭露了一个恶意域名ghrc.io的钓鱼攻击。该域名与GitHub容器镜像服务ghcr.io仅有一个字母之差，容易因拼写错误而被访问。文章发现，虽然ghrc.io表面上只是一个默认的nginx服务器，但其针对容器镜像API的/v2/路径却设置了认证请求，诱使容器工具（如Docker）将用户凭据发送到恶意服务器。这种精心设计的攻击专门针对常见的拼写错误场景，可能通过错误的登录命令或CI/CD配置窃取用户凭证。作者警告开发者要警惕这种新型的"typo-squatting"攻击手段。

主要讨论点：[GitHub Container Registry (ghcr.io) 域名容易被仿冒 (ghrc.io) 的安全风险] 不同观点： • [安全问题严重性] - GitHub Container Registry 不支持细粒度令牌，使用经典令牌，增加了风险（nicce） - 这是一个相当有说服力的攻击向量，因为域名问题不容易被察觉（Atreiden） - 可以轻易从 CI 作业中捕获拼写错误并进行恶意操作（a1o） • [域名仿冒的具体问题] - ghrc.io 和 ghcr.io 的字符顺序容易被混淆（arjvik） - 应该避免使用缩写，而使用完整的名称以避免陷阱（usr1106） - 许多开源项目已经在使用这个仿冒域名（aussieguy1234, iojcde） • [解决方案建议] - 联系域名注册商 Dynadot 的滥用邮箱（gruez） - 避免使用非主流 TLD，优先选择 .com 等常见域名（TZubiri） - 讨论 DNSSEC 是否能解决此类问题（deknos） 补充讨论： • [争议焦点] - Bearer 令牌的安全性：是否容易被重放攻击（engcoach） - OAuth 令牌是否会在不同域名间重复使用（engcoach） • [其他注意事项] - 这个问题之前已经在 Hacker News 上讨论过（JdeBP） - 用户对 ghcr 缩写的误解（usr1106）

Stepanov's biggest blunder? The curious case of adjacent difference

作者: signa11 | 评分: 47 | 评论数: 5 | 发布时间: 2025-08-21 11:30
文章摘要

这篇文章主要讨论了C++标准库中的`std::adjacent_difference`算法的设计原理及其与微积分基本定理的联系。文章指出该算法除了计算相邻元素差值外，还会保留第一个元素不变，这种看似奇怪的设计实际上是刻意为之，目的是使其与`std::partial_sum`互为逆运算。作者通过文档ID压缩和时间戳计算等例子说明这种设计的局限性，同时揭示了该算法与微积分中求导和积分的关系：离散差分对应求导，部分和对应积分，二者互为逆运算，这正好体现了微积分基本定理的离散形式。

评论摘要
主要讨论点：[C++标准库中的设计问题和替代方案] 不同观点： • **C++缺乏通用"零"概念的问题** - 用户[fph]指出，C++没有通用的"零"概念，导致`adjacent_difference`等函数在类型稳定性方面存在问题。建议通过`zero`等方案改进设计。 • **部分算法参数设计问题** - [voidmain]补充指出`partial_sum`存在类似问题（如`T - T`可能不是`T`），并提出更通用的解决方案：将初始累加器作为单独参数传递，使算法设计更对称。 • **标准库中的历史性设计错误** - [AnotherGoodName]认为`std::vector`是更大的设计失误，批评其特化实现破坏了容器功能，并引用Herb Sutter的文章佐证这是"过早优化"的典型案例。 • **实际应用视角的观察** - [wowczarek]从实际应用角度出发，虽然承认类型系统的问题，但更关注这些函数在特定领域（如Allan方差计算）中的实用价值。 补充讨论： - 争议焦点集中在标准库设计是否应该优先考虑类型安全性（如[fph]和[voidmain]的观点）还是实用价值（如[wowczarek]的角度）。 - [getnormality]提供了延伸学习资源（Knuth的《具体数学》），暗示这些问题在离散数学中有更系统的理论支持。 - 关于标准库"最大设计错误"的争议：`adjacent_difference`的类型问题 vs `vector`的特化问题。
