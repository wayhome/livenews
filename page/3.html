评论摘要
主要讨论点：围绕 Git 分布式 issue tracker 的可行性、目标用户、数据架构与交互方式展开。 不同观点： • 谨慎/质疑派：Izkata 提到十多年前类似工具曾短暂流行，但设计上常有硬伤；关心是否避免把数据直接塞进 Git 导致的问题，以及自动同步能否解决冲突、协作等历史难题。 • 面向团队的担忧：goyozi、joeblubaugh 认为 TUI 很适合开发者，但若产品经理、设计师等也要参与，强制使用终端不现实；建议提供本地 Web UI，或让 UI 与数据层解耦。 • 架构建议：goyozi 建议默认使用中心化 issues 仓库，或支持跨仓库关联；因为代码和 issue 演进节奏不同，修改 issue 不应总是和本地 WIP 代码一起提交。 • 支持派：SidVikJay 赞赏用“用户级不可变事件日志”避免 Git 冲突，认为这是优雅的分布式 issue 状态方案。samuell 认为它适合 repo 本地 issue、纯 Git 分发、个人任务管理，并能减少切换到 Web 工具的成本。 • 参考与生态：joshka 建议参考 git-bug，吸取已有分布式 issue tracker 的经验教训。 • AI/自动化接口争议：nextaccountic、swoorup 对 MCP 必要性存疑，认为 agent 可直接使用 CLI，或提供单二进制加 skill 即可。 补充讨论：核心争议在于该工具应只服务开发者，还是扩展到完整协作团队；以及 issue 数据应紧贴代码仓库，还是与代码生命周期适度分离。
