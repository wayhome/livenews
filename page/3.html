Convert Linux to Windows

作者: pbohun | 评分: 56 | 评论数: 21 | 发布时间: 2025-03-29 21:34
文章摘要

文章主要讨论了Linux环境中的二进制兼容性问题，指出Linux在不同版本和发行版之间运行旧二进制文件的能力不稳定，且缺乏良好的二进制分发方式。文章提出了一个设想：创建一个默认通过Wine运行Windows二进制文件的Linux发行版。这个新发行版将预装Wine，并对Linux内核进行小修改，使Windows应用程序可以像在Windows上一样无缝运行。通过这种方式，用户可以在Linux系统上轻松运行Windows应用，同时隐藏复杂的Linux底层操作。文章还提到，这种方法可以实现跨平台兼容性，并应对未来MacOS和Windows操作系统逐渐增加的封闭性和隐私问题。

评论摘要
主要讨论点：是否需要新的Linux发行版来运行Windows应用，以及如何在Linux上更好地兼容和运行Windows程序。 不同观点： • **不需要新发行版，使用容器化的Wine**：coderenegade认为不需要新发行版，建议使用容器化的Wine来确保一致性和兼容性，但承认这种方法可能存在空间浪费和许可问题。 • **提到现有解决方案Linspire**：petepete指出Linspire（曾经的Lindows）已经尝试过这种方法。 • **使用现有打包工具的反对意见**：devit认为通过flatpak/snap/appimage等工具已经可以实现完美的二进制兼容，无需新发行版或容器。可以通过静态链接和shell脚本加载器来解决依赖问题。 • **关于binfmt_misc的补充**：nneonneo提到binfmt_misc和wine-binfmt已经可以自动通过Wine运行Windows可执行文件，不需要新的内核补丁。 • **反向需求：运行Windows内核和驱动**：xtracto希望能够在Linux用户界面下运行Windows内核和驱动，以解决硬件兼容性问题。 • **Linux ABI的向后兼容性**：mappu认为Linux ABI的向后兼容性已经很好，20年前的二进制文件在现代glibc系统上依然可以运行。 • **提到ReactOS**：lucasoshiro建议使用ReactOS，这是一个开源的Windows兼容操作系统，而不是创建新的Linux发行版。 • **应用隔离和安全模型**：gmuslera指出Flatpak/Snap不仅是打包工具，还提供了应用隔离和安全保护，这在Windows中不存在。 • **Steam Deck作为现有解决方案**：ajross提到Valve的Steam Deck已经实现了在Linux上运行Wine可执行文件作为原生应用环境，技术上已经存在。 补充讨论： • **对旧软件的需求争议**：adamtaylor_13认为讨论旧软件的向后兼容性没有实际意义，因为他从未需要运行20年前的软件。 • **完全隐藏Linux的愿景**：win32lover支持创建一个用户看不到Linux痕迹的系统，认为这是一个好主意。 • **关于Linux环境稳定性的争论**：mrbluecoat用导弹控制系统为例，强调Linux环境的稳定性。 • **ABI兼容性修复的难度**：pizlonator认为修复Linux用户空间的ABI兼容性问题比将Linux转换为Windows环境更容易。 争议焦点：是否需要新的Linux发行版来解决Windows应用兼容性问题，还是通过现有工具和解决方案（如容器化、打包工具、ReactOS等）已经足够。

An Ode to the Game Boy Advance

作者: Brajeshwar | 评分: 40 | 评论数: 3 | 发布时间: 2025-03-30 14:35
文章摘要

2001年，任天堂发布了Game Boy Advance（GBA），这是一款配备32位ARM CPU的先进掌机，速度是Game Boy Color（GBC）的两倍，仍使用两节AA电池供电。GBA销量火爆，在英国首周销量是PlayStation 2的四倍。虽然延续了横井军平的“枯萎技术横向思考”设计理念，但GBA的技术规格更为突出，价格为99.99美元。其首发游戏如《Castlevania: Circle of the Moon》、《Super Mario Advance》和《F-Zero: Maximum Velocity》展示了GBA的强大性能，但也暴露了无背光屏幕的缺点，尤其在昏暗场景中体验不佳。 GBA兼容GB和GBC游戏，通过第二颗CPU实现无损兼容。其横向屏幕设计提供了不同显示选项。任天堂持续通过硬件修订和兼容性策略延长了Game Boy系列的寿命，这种策略在其后续掌机如Nintendo DS和3DS中也得到延续。

评论摘要
主要讨论点：GBA的技术特性、便携性以及与现代设备的比较 不同观点： • [Dwedit的观点] GBA具有在水平消隐间隔期间自动执行DMA传输的功能，这类似于SNES的HDMA技巧，只是编码方式不同。GBA没有使用扫描线数字，而是通过水平消隐期间传输每一行的原始数据。 • [gxd的观点] 自GBA时代以来，移动设备的屏幕尺寸明显增大，例如Switch和手机。虽然大屏幕有吸引力，但便携性受到影响，现代“便携”设备大多无法轻松放入口袋。 • [zoklet-enjoyer的观点] 个人体验表明，原版GBA是最舒适的手持设备，完美贴合手部和口袋，具有出色的便携性。其在使用体验上的优势让人印象深刻。 补充讨论： • 技术实现的讨论：Dwedit解释了GBA的DMA传输技术，澄清了与SNES HDMA的区别，强调了GBA在技术实现上的不同。 • 便携性与屏幕尺寸的争议：gxd提出了屏幕尺寸增大对便携性的影响，而zoklet-enjoyer则通过个人体验强调了原版GBA在便携性和舒适度上的优势，两者之间存在一定的争议焦点。 • 怀旧与现代的对比：zoklet-enjoyer的评论带有怀旧色彩，强调了过去设备在设计上的某些优点，与现代设备的变化形成了对比。 争议的焦点：大屏幕与便携性之间的平衡如何把握，以及技术进步是否必然导致便携性下降。

The way we're thinking about breaking changes is silly

作者: luu | 评分: 46 | 评论数: 18 | 发布时间: 2025-03-27 19:59
文章摘要

文章讨论了现代编译器在处理破坏性变更时的局限性，尤其是它们缺乏时间概念，导致依赖更新时可能出现错误。当前，编译器将代码视为始终处于当前状态，而不考虑历史变更，这导致函数类型变化（如从`Int`到`Maybe Int`）可能破坏原有代码调用。为解决此问题，文章提出两种方案： 1. **自动类型迁移**：通过迁移声明，将旧类型自动转换为新类型，例如从`Int`到`Maybe Int`，确保调用点自动适应新类型。 2. **迁移文件**：为每个API变化添加迁移文件，定义如何将旧调用转换为新调用，编译器在升级依赖时自动应用。 此外，文章建议扩展迁移机制至其他场景，如解决函数名冲突和Rust中的trait实例问题。通过迁移机制，编译器可自动处理代码变更，减少手动修复，提高开发效率。

评论摘要
主要讨论点：处理代码和数据库中的 breaking changes 的方法 不同观点： • kmeisthax 认为，处理 SQL 中的 breaking changes 应通过视图（views）而非迁移（migrations），迁移只适合单个应用程序将 SQL 作为数据存储使用的情况。在代码中，可以通过保留旧定义并重定向到新函数来处理 breaking changes，类似于使用 API 版本控制。 • ivan_gammel 反驳原帖的观点，认为讨论过于浅显，没有考虑到业务需求的变化。例如，当引入新的必填参数而没有合理默认值时，自动迁移无法可靠地解决问题，必须手动修复代码。 • steego 认为，自动插入迁移会增加复杂性，尤其是在强类型推断的语言中，可能会导致类型不匹配并波及整个代码库。这种方法只是将维护成本转移到了其他地方，并可能牺牲代码的清晰性和可预测性。 • morsecodist 指出，某些 breaking changes 需要根据调用点的具体情况进行不同的处理，编译器无法在运行时确定如何处理这些情况。例如，当函数返回值从 int 变为 int 或 null 时，需要手动决定如何处理 null 情况。 • wavemode 认为，处理 breaking changes 的等效方法是编写新函数并让旧函数进行必要的类型转换和调用。如果无法自动转换，那么数据库风格的自动迁移也不可行。 • lolinder 提到，Kotlin 的 ReplaceWith 注解提供了一种有限的解决方案，可以在不修改现有名称的情况下引入新行为，并通过 IDE 工具自动应用。 • oftenwrong 建议采用函数不可变的模型，以避免 breaking changes，例如 Unison 语言的做法。 • tags2k 质疑数据库迁移是否真的不算 breaking changes，因为迁移到新版本的模式时，旧查询可能不再有效。 • bluGill 认为，自动翻译系统需要提前规划，并且假设转换的性能和内存成本是可以接受的，但实际情况往往并非如此。 • blixt 认为，针对类型和函数的迁移可能很复杂，建议从某个检查点开始进行整体迁移，而不是单独处理每个类型。 • chromanoid 提到，OpenRewrite 工具提供了一些迁移方案，如从 javax 到 jakarta，但在大项目中可能有一些局限性。 • AnthonBerg 认为，依赖类型（dependent types）可以自然地解决此类问题，将软件自动化进一步提升。 • Guthur 指出，数据库迁移并不能完全解决 breaking changes 问题，特别是在多语言互操作的情况下，数据形状的变化可能导致未预料的错误。 • esafak 建议为每个接口及其聚合版本化，以便识别哪些部分发生了 breaking changes，尽管这会引入复杂性。 补充讨论： - breaking changes 的自动处理方案是否可行及其实际复杂性。 - 不同语言和工具（如 Kotlin、Unison、OpenRewrite）提供的解决方案及其局限性。 - 业务需求变化对 breaking changes 的影响。 - 手动处理与自动迁移之间的权衡和争议。

LVGL（Light and Versatile Graphics Library）是一个成熟、开源的嵌入式图形库，用于为各种微控制器（MCU）、微处理器（MPU）和显示类型创建美观的用户界面（UI）。它获得了Arm、STM32、NXP、Arduino等知名厂商的支持，具有丰富的功能，包括30+内置控件、强大的样式系统、类似Flexbox和Grid的布局引擎，以及支持多语言的排版系统。LVGL仅需32kB RAM和128kB Flash，兼容多种显示设备，并可在多种操作系统下运行。它基于MIT许可，适用于商业项目，提供MicroPython和PikaScript绑定，支持Make和CMake构建系统，并允许在PC上开发并移植到嵌入式设备。LVGL团队还提供UI设计和咨询服务，用户可通过GitHub Sponsors进行捐赠以支持其发展。
