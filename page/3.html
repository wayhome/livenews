How memory safety CVEs differ between Rust and C/C++

文章摘要

这篇文章探讨了Rust和C/C++在内存安全漏洞报告方面的根本差异。作者指出，虽然Rust程序仍可能出现CVE漏洞，但其处理方式与C/C++截然不同。以curl库为例，作者展示了一个简单的C程序（向`curl_getenv`传入NULL指针）会导致段错误，但这不被视为curl的漏洞，而是"错误用法"。这是因为C语言类型系统有限，无法精确表达API契约，库作者通常不会详尽描述所有错误用法。文章强调，比较Rust和C/C++的CVE数量时，需要理解这种报告机制上的本质区别——Rust通过类型系统在编译期就能防止许多此类"错误用法"。

评论摘要
主要讨论点：Rust与C/C++在内存安全和漏洞方面的对比，以及编程语言选择的实际意义 不同观点： • **CVE数量无意义论**（john_strinlai）：认为用CVE数量比较语言安全性是最无用的指标，应该被忽略 • **C++现代化可解决问题论**（Bjarne Stroustrup/Decabytes引述）：现代C++和强化库能解决大部分内存安全问题，90%以上问题源于C风格代码；C++26的边界检查和强制初始化可捕获70-80%内存问题 • **Rust优势明显论**（shevy-java）：Rust正在侵占C/C++领域，如Ladybird的HTML解析器改用Rust后性能提升10% • **Rust并非完美论**（chilljinx/jurschreuder）：Rust标准库充满unsafe代码，仍可能触发UB；借用检查器只解决20%的use-after-free问题，对普通开发者实际价值有限 • **供应链风险权衡论**（bitbasher）：Rust虽提供内存安全，但引入了供应链风险 • **bug严重性需具体分析论**（fweimer）：不能绝对判断库bug是否构成漏洞，需考虑实际影响；Rust的panic也可能是DoS漏洞 补充讨论：多位评论者指出不应将50年前的C代码和现代C++混为一谈；普通开发者面临的主要威胁是供应链攻击、API密钥泄露、输入验证等问题，而非内存安全

Machine0 是一个专为长时间运行任务设计的虚拟机服务平台。提供 NixOS 或 Ubuntu 预装系统，支持通过 CLI 命令操作，具备专用资源（最高 60 vCPU、240GB RAM）、静态 IP 和 HTTPS 端点。采用按分钟计费模式，起价 $0.013/小时，支持挂起虚拟机以停止计费。可用于可复现的开发环境、运行自主 AI 代理（如 OpenClaw、Hermes）以及 Web 应用托管。覆盖美国、英国、欧盟和亚洲四个地区，承诺 99.99% 的正常运行时间。

评论摘要
主要讨论点：machine0推出NixOS支持后，开发者对基于Nix构建声明式服务和VM管理的不同实践方法和应用场景。 不同观点： • **不可变基础设施派**（EnigmaCurry）：主张VM应完全不可变，OS镜像只读，状态仅存于应用层。提出三种模式：完全不可变、半可变（临时overlayfs）、可变，认为对于服务部署应追求无状态，对AI代理使用则需要可变根系统。已开发类似的libvirt/Proxmox模板。 • **实用主义用户**（nc, Bnjoroge, GeoffNN）：关注实际应用效果，认为machine0易用性好，特别适合与Claude Code配合、GPU实验、homelab容器部署等场景，强调开箱即用的价值。 • **云迁移关注者**（setheron, dmmalam）：担心vendor lock-in问题，希望确认能否迁移到AWS等其他云平台，认为服务组合的可移植性是关键考量。 • **技术扩展者**（cdevr, Pet_Ant）：探讨移植到其他技术栈的可能性，如Proxmox VE、Guix系统，或反向用machine0替代现有方案。 补充讨论：JeanEdern提出状态漂移检测和恢复的实践问题；部分用户询问NixOS入门资料和许可证信息；整体反馈积极，认为产品解释清晰、价值明确。
