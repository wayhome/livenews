Orthrus-Qwen3: up to 7.8×tokens/forward on Qwen3, identical output distribution

作者: FranckDernoncou | 评分: 33 | 评论数: 2 | 发布时间: 2026-05-15 22:38
文章摘要

Orthrus 是一种双视图扩散解码框架，在保持自回归LLM严格无损输出的同时实现并行生成。基于Qwen3模型，最高约7.8倍加速，KV缓存仅O(1)额外开销，只微调16%参数，并优于投机解码和现有扩散语言模型。

评论摘要
主要讨论点：一种将可训练扩散注意力模块注入冻结AR Transformer、以提升推理速度且尽量不改动基座模型的新方法（Orthrus），以及它与现有扩散LM/Speculative Decoding的对比。 不同观点： • [xiphias2] 认为这个思路最有意思的地方在于“居然之前没实现过”，因为从直觉上很合理；并补充说类似DTree的技巧在这里也可能适用。 • [FranckDernoncou] 作为作者详细介绍论文：在冻结骨干上加入扩散attention，AR头二次验证，输出分布与基座模型严格一致；强调相比改权重的扩散LM，Orthrus保持准确率不掉。 • [FranckDernoncou] 重点对比Speculative Decoding：不需要外部drafter、无需独立cache、没有TTFT开销，且KV开销近乎常数；在MATH-500上给出7.8x TPF等结果。 • [FranckDernoncou] 也指出局限：只在Qwen3上评测、仍受冻结基座模型的偏见/幻觉/知识缺口限制，且目前只支持greedy+rejection sampling。 补充讨论： • 争议焦点主要在“新方法是否真有必要/是否只是已有思路变体”，以及“速度提升能否在不牺牲准确率的前提下稳定泛化”。

文章摘要

image-blaster 是一个借助 Claude、World Labs 和 FAL 的工具，能把单张图片快速生成可探索的 3D 环境、动态物体模型、静态场景点云/gaussian splat 以及环境和物体音效，适合游戏、DCC 和网页应用。

评论摘要
主要讨论点：围绕“由单张/多张图片或文本生成3D场景、网格与游戏资产”的AI建模工具现状、可用性和管线整合展开。 不同观点： • 乐观派认为近一年AI 3D管线进步很快，World Labs、Meshy.ai、VLLM像素级图像理解、自动贴图/绑定等能力已可把想象快速变成资产，行业管线仍停留在“艺术家交付文件”的旧假设中。 • 惊喜体验派将其类比早年 Microsoft PhotoSynth：过去需多张照片重建环境，现在单图生成3D更令人震撼，值得尝试。 • 质疑派指出 World Labs 实测结果不稳定，单图外推会产生不合逻辑的幻觉内容，尤其画面外、墙外、物体背后区域；有人反而觉得 GPT Image 2 更可用。 • 技术探讨派关注底层架构：看起来像受单视角限制的 Gaussian Splatting，但因团队背景含 NeRF 作者，猜测可能不止朴素 splatting。争议焦点在于“单图3D”到底能否生成可编辑、可用、几何一致的场景。 • 游戏/资产开发者关注实用管线：有人想用它做游戏，也有人苦于AI难以稳定生成等距静态/动画精灵，纠结是用3D网格转等距还是继续寻找可靠sprite生成方案。 • 成本与本地化也是问题：TRELLIS、Meshy.ai可用于图像到3D角色/3D打印，但本地模型少，商业服务费用累积较快。 补充讨论：还提到多照片重建3D网格、角色动画工具 Uthana、是否必须使用 Claude，以及“银翼杀手式照片分析”正在变成现实。

Radicle: Sovereign {code forge} built on Git

文章摘要

Radicle 是基于 Git 的开源点对点代码协作平台，去中心化复制仓库，用户自主掌控数据与流程。它通过加密身份、签名数据、 gossip 协议和本地优先设计，支持离线使用、抗审查协作，并提供 CLI、Web、桌面端等模块化工具。

评论摘要
主要讨论点：围绕 Radicle 作为去中心化/本地优先 Git forge 的价值、隐私安全、部署方式、生态支持与治理风险展开。 不同观点： • 支持者认为 Radicle 很有潜力：本地优先、分布式、适合替代 GitHub；有人称其“Just Works”，也有人看好其用于 agent 工作流，因其默认具备加密身份和签名产物。 • 隐私与删除问题引发担忧：去中心化系统中很难真正删除仓库或泄露的密钥；私有仓库虽可限制复制，但历史仍可能存在，类似 Matrix、BitTorrent 的删除困境。 • 私有/敏感仓库方案被质疑：评论指出 Radicle 私有仓库未加密静态存储，只依赖选择性复制，且公私仓库缺少结构隔离，误操作或 bug 可能导致泄露。 • 本地/小团队离线部署体验不足：多人希望像 on-prem GitLab 或 Fossil 一样，只在几台机器间运行，不连接公共网络；但默认会加入公共 seed 节点，配置和文档支持不足，需要脚本化绕过。 • 许可证存在争议：有人批评未采用 AGPL，担心 SaaS 公司“拥抱、扩展、消灭”；并指出 Radworks 计划提供基于 Radicle 的服务，加剧商业化担忧。 • 功能与生态问题：有人询问是否支持 Tor、Git LFS/Git Annex；也有人希望原生支持 Jujutsu（jj）仓库，而不仅是相关集成文章。 • 联邦交互的治理问题：有人关心公开仓库的 issue/merge request 是否会被任意节点骚扰，是否存在白名单或反垃圾机制。 补充讨论：还有人提到 Radicle 近期更换域名、NixOS 已打包，部分用户准备部署常驻节点；也有用户询问其核心解决的问题是否主要是反中心化与抗审查。
