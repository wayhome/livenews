Lvgl: Embedded graphics library to create beautiful UIs

作者: tosh | 评分: 135 | 评论数: 9 | 发布时间: 2025-03-29 18:42
文章摘要

LVGL（Light and Versatile Graphics Library）是一个成熟、开源的嵌入式图形库，用于为各种微控制器（MCU）、微处理器（MPU）和显示类型创建美观的用户界面（UI）。它获得了Arm、STM32、NXP、Arduino等知名厂商的支持，具有丰富的功能，包括30+内置控件、强大的样式系统、类似Flexbox和Grid的布局引擎，以及支持多语言的排版系统。LVGL仅需32kB RAM和128kB Flash，兼容多种显示设备，并可在多种操作系统下运行。它基于MIT许可，适用于商业项目，提供MicroPython和PikaScript绑定，支持Make和CMake构建系统，并允许在PC上开发并移植到嵌入式设备。LVGL团队还提供UI设计和咨询服务，用户可通过GitHub Sponsors进行捐赠以支持其发展。

主要讨论点：LVGL库的使用体验、与不同平台和工具的比较、以及其他相关工具和库的推荐 不同观点： • whitehexagon：认为LVGL简单易用，特别适合嵌入式UI开发。通过Zig和WASM进行开发，避免了直接操作GPU（如OpenGL ES）的复杂性。同时，对LVGL的文档和示例表示赞赏。但也提到在将LVGL编译为WASM时遇到C头文件依赖的问题。 • nabilt：推荐使用NXP的GUI Glider作为免费的简单UI编辑工具，作为不使用官方付费工具的替代方案。 • karmicthreat：认为构建简单的嵌入式UI时，LVGL比较方便，但初始设置可能有一定难度。提到有一个独立的UI编辑器，但个人更希望其作为VSCode插件提供。 • amelius：对LVGL作为“无外部依赖的库”的说法提出疑问，询问其如何与屏幕进行交互。 • transpute：提供了一个基于Linux帧缓存和shell脚本的PoC项目链接，展示如何使用LVGL。 • kunjanshah：询问是否有将LVGL与inkplate EPDs结合使用的经验。 • throwaway290：将LVGL与Dear ImGui进行比较，认为Dear ImGui更小巧、适合嵌入式，并且速度更快。 • einpoklum：质疑LVGL是否在重复造轮子，指出已经存在多个C语言的GUI库/工具包。 • ashishb：询问适用于构建纯Web UI的类似高层次库，希望生成小型独立的JavaScript/CSS文件，用于静态网站。 补充讨论： • LVGL的优点在于其简单性和对嵌入式平台的支持，尤其是通过帧缓存方式避免了复杂的GPU操作。 • 不同用户对LVGL的编辑器和开发工具（如VSCode插件）有不同需求和偏好。 • 关于LVGL与Dear ImGui的比较，throwaway290认为后者更适合嵌入式开发，因其更小巧和快速。 • einpoklum提出了对LVGL存在意义的质疑，认为可能存在其他类似的C语言GUI库。 • 一些用户提到具体的应用场景，如与EPDs（电子纸显示器）的结合使用，以及对Web UI开发的需求。

Just Write a Test for It

这篇文章讲述了作者在Rust项目中处理数据库迁移时遇到的一个问题：在已有数据的表中添加一个NOT NULL列但没有提供DEFAULT值，导致部署出错。尽管初始测试套件未能发现此问题，作者没有止步于简单修复，而是借助Rust生态中的`sqlparser`库，编写了一个集成测试来自动检测类似问题。作者赞赏Rust激励其追求更高质量的解决方案，并详细描述了如何利用`sqlparser`实现该检测功能。最终，作者成功预防了未来可能出现的类似错误。

评论摘要
主要讨论点：如何有效测试数据库迁移以避免潜在问题 不同观点： • **karparov** 认为现有的测试套件存在盲点，因为测试总是从一个空数据库开始，应用所有迁移后再运行测试代码。他建议使用预先填充的数据库进行测试，以捕捉更多潜在问题，而不仅仅是对非空默认值的检查。 • **dreghgh** 反对 karparov 的方法，认为应该在尝试运行迁移之前向数据库添加数据。他认为这样做可以发现各种未预料的错误，而现有的复杂解决方案仅能捕获特定类型的错误。 • **lbreakjai** 分享了以前工作中的类似经验，他们通过克隆公共模式到一个限定于合并请求的模式来运行迁移和集成测试。他指出，有些错误只有在对真实数据运行代码时才会发现。 • **conradludgate** 和 **bilalq** 提到 Neon 的分支功能，可以通过零拷贝快照隔离数据库实例进行测试，这样不会影响生产数据和性能。他们认为这是一种轻量且有效的方法，但 conradludgate 也指出在性能方面可能存在的问题。 • **nikolayasdf123** 对测试的复杂性表示担忧，认为复杂的测试比所测试的代码更难写和理解，这会让人不愿意写测试。 • **null_deref** 对引入 SQL 解析器作为依赖表示担忧，认为在当前供应链攻击和依赖漏洞日益增加的情况下，这种做法可能会扩大攻击面和漏洞风险。 补充讨论： • **kleiba** 认为文章本身不够吸引人，只是讲述了作者发现可以用一个 Rust 库来解析 SQL 查询的经历。 • **switch007** 提到一个 PostgreSQL 的迁移工具 "squawk"，可以解决此类问题。 • **earnestinger** 指出文章没有明确说明使用的 SQL 解析器类型，是 PostgreSQL 还是 MySQL 等。 • **bsaul** 对 Rust 代码的可读性提出疑问，特别是与其他更复杂的 Rust 代码相比。 争议焦点： • 测试数据库迁移时，是使用预先填充的数据库还是空数据库。 • 引入 SQL 解析器作为依赖是否会增加安全风险。 • 测试的复杂性和可维护性问题。

The way we're thinking about breaking changes is silly

作者: luu | 评分: 6 | 评论数: 1 | 发布时间: 2025-03-27 19:59
文章摘要

文章讨论了现代编译器在处理破坏性变更时的局限性，尤其是它们缺乏时间概念，导致依赖更新时可能出现错误。当前，编译器将代码视为始终处于当前状态，而不考虑历史变更，这导致函数类型变化（如从`Int`到`Maybe Int`）可能破坏原有代码调用。为解决此问题，文章提出两种方案： 1. **自动类型迁移**：通过迁移声明，将旧类型自动转换为新类型，例如从`Int`到`Maybe Int`，确保调用点自动适应新类型。 2. **迁移文件**：为每个API变化添加迁移文件，定义如何将旧调用转换为新调用，编译器在升级依赖时自动应用。 此外，文章建议扩展迁移机制至其他场景，如解决函数名冲突和Rust中的trait实例问题。通过迁移机制，编译器可自动处理代码变更，减少手动修复，提高开发效率。

评论摘要
主要讨论点：有关依赖类型（dependent types）在软件自动化中的作用和意义 不同观点： • AnthonBerg 认为依赖类型可以自然涵盖并解决某些软件自动化的问题，即依赖类型是对自动化本身的进一步自动化。这种观点强调依赖类型在提高软件开发自动化程度方面的潜力。 补充讨论： • AnthonBerg 通过简洁的类比“软件是自动化，依赖类型是自动化的自动化”来强调依赖类型在软件开发中的重要性。这个类比意在说明依赖类型不仅能实现软件功能的自动化，还能对开发过程中的其他自动化需求进行进一步的优化和控制。 • 讨论中并未出现直接反对的观点，但潜在的争议可能在于依赖类型在实际应用中的复杂性和学习曲线，这可能导致一些开发者对这种方法的可行性或实用性持怀疑态度。 总结：评论主要围绕依赖类型在软件自动化中的作用展开，强调其能够进一步提升自动化的能力和效率，同时提出了一个形象的类比来帮助理解这一概念。潜在的争议可能涉及依赖类型的实际应用难度。
