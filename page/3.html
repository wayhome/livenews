Branchless Quicksort faster than std:sort and pdqsort with C and C++ API

作者: birdculture | 评分: 183 | 评论数: 15 | 发布时间: 2026-06-02 20:00
文章摘要

这篇文章介绍了blqsort（无分支快速排序）算法及其实现。核心思想是通过避免CPU分支预测失败来提升性能。算法采用辅助缓冲区实现无分支分区，虽然增加了拷贝操作，但避免了分支预测错误带来的性能损失。针对小数据集使用排序网络，大数据集采用中位数策略选择枢轴。提供C和C++单线程/多线程四个版本。性能测试显示，在Apple M1和AMD Ryzen上排序5000万double数据，blqsort比std::sort和pdqsort快约30-60%。对于自定义结构体排序同样表现优异，使用简单灵活。

评论摘要
主要讨论点：关于新排序算法blqs的性能、实现细节和分支预测优化的技术讨论 不同观点： • **Rust标准库排序更优**：orlp指出ipnsort和driftsort已集成到Rust标准库，在多数场景下性能优于blqs，特别是driftsort在部分有序数据上表现极佳（0.29s vs blqs 1.89s） • **无分支代码的争议**：bagxrvxpepzn认为文章对无分支优化的说法有误导性，现代CPU的分支预测如此优秀，通常有分支代码更好，因为无分支会引入数据依赖限制指令级并行；而作者推崇无分支以避免分支预测失败 • **C++实现的局限性**：quuxplusone批评C++版本假设类型可默认构造且拷贝开销低，对于字符串等高拷贝成本类型可能不适用，存在不必要的构造和拷贝操作 • **比较范围不全**：mgaunard质疑为何不与Intel的向量化bitonic sort等实现对比；Aardwolf指出对于任意长度字符串等比较器开销大的场景，quicksort变体可能不占优势 补充讨论： - 有人对无分支代码的实际机制存疑（kvuj认为`numbers[i] < 500`仍是分支） - 代码细节问题（命名规范、循环等价性理解） - 网站导航问题的反馈

文章摘要

这篇文章介绍了Go语言的实验性特性机制。Go通过实验性特性在正式发布前收集用户反馈，包括新标准库包、编译器改动或行为变更。实验特性通常默认关闭，通过GOEXPERIMENT环境变量启用。生命周期一般为：默认关闭评估→正式发布默认开启→可选的过渡期。例如Go 1.25的testing/synctest包和新垃圾收集器都经历了这个过程。部分实验可能被搁置或取消，如内存arenas。还有一些"永久实验"特性（如字段追踪）不会成为默认功能，仅用于特殊场景。文章指出当前可用实验特性的信息较难获取。

评论摘要
主要讨论点：Go语言的实验性功能和特性发展 不同观点： • **JSONv2支持者（klodolph）**：认为JSONv2虽非默认但性能和API更优，建议新代码直接启用使用，预计1.27版本会成为默认选项。提到部分边缘场景存在性能回退，但典型场景下表现更好。 • **SIMD优化期待者（nasretdinov）**：强烈期待SIMD成为Go标准特性。指出通过SIMD内联（区别于当前的汇编实现），Go可达到C语言80%性能，相比当前Go落后C语言2-3倍的状态是巨大提升。SIMD本身可带来10倍以上加速。 • **学习者视角（losthobbies）**：提到购买了Go学习资料但未深入学习，代表初学者群体。 • **Arena内存管理兴趣者（ktpsns）**：关注arena实验特性，认为如果实现得当，整个程序可以用arena集合来构建。 • **流程改进建议者（jiehong）**：建议Go社区参考Java的JEP或Python的PEP，更好地文档化功能及其生命周期状态。 • **特性标志质疑者（yjftsjthsd-h）**：质疑这些实验性功能本质上是否就是功能标志（feature flags）。 补充讨论：verdverm提到CUE语言（Go的分支）也有类似实验能力并扩展到文件级作用域，再次强调Go工具链的优势。

这篇文章介绍了ANSI转义码——一个诞生于1979年、延续近50年的终端标准。ANSI转义码通过在文本流中嵌入特殊字符序列（以ESC字符开头），让终端能够控制光标位置、文本格式和颜色。例如`\x1b[31m`设置红色文本，`\x1b[1m`加粗。这个标准至今仍是CLI交互的基础，现代工具如chalk、Spectre.Console都基于它实现彩色输出、进度条等功能。甚至Vim、htop等复杂终端UI也依赖ANSI码的光标定位和屏幕操作。文章还提供了一个交互式组件让读者实验不同的转义序列效果。
