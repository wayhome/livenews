Disabling Intel Graphics Security Mitigation Boosts GPU Compute Performance 20%

作者: rcarmo | 评分: 50 | 评论数: 4 | 发布时间: 2025-06-23 07:01
文章摘要

文章主要介绍了通过禁用Intel图形安全缓解措施，可以提高GPU计算性能达20%。Ubuntu的开发公司Canonical正与Intel合作，计划在Ubuntu软件包中禁用这些缓解措施，以恢复性能损失。具体方法是通过使用"NEO_DISABLE_MITIGATIONS"构建选项，该选项仅影响Intel计算运行时堆栈，而不涉及Linux内核的安全缓解措施。尽管这一改变可能带来安全风险，但Intel和Canonical的安全团队已同意这一调整，因为Spectre漏洞已在 kernel 层面得到缓解，且Intel在其GitHub上的计算运行时包中也默认禁用了这些缓解措施。Ubuntu 25.10版本预计将包含这一改动。

评论摘要
主要讨论点：Ubuntu在Intel GPU计算 runtime中禁用Spectre缓解措施是否合适，及其性能与安全性的权衡 不同观点： • [phoronixrly] 认为当前的标题具有误导性，让人以为Canonical重新打开了Spectre漏洞以换取性能提升。实际上，Intel和Canonical的安全团队达成一致，认为在GPU的Compute Runtime层面不再需要对Spectre进行缓解，因为内核层面已经解决了该问题。他还建议更改标题以避免误解，并提供原始链接。 • [rurban] 提出反对意见，质疑禁用缓解措施是否会重新启用CVE-2019-0155漏洞。他提到Intel研究人员发现Intel图形处理器允许用户空间通过Blitter Command Streamer对MMIO进行写操作，从而修改页表项，导致可能的特权提升和信息泄露。他担心这可能会暴露内核内存信息，允许本地用户提升其在机器上的特权。 • [gotoeleven] 对整体安全模型提出质疑，认为在共享资源的计算机上通过用户隔离来保证安全是困难的。他提出一种替代方案，即设计计算系统时假设所有用户最终都可以获得root权限，从而简化安全问题。他认为，如果只允许可信任的用户获得root权限，许多漏洞可以自然地被缓解。 • [CjHuber] 指出，缓解措施会导致显著的性能下降是众所周知的事实，他认为没有人会对此持异议。 补充讨论： • 讨论中的一个焦点是性能与安全性之间的权衡。一部分人关注禁用缓解措施带来的性能提升，而另一部分人则担心这会重新引入安全漏洞。 • 另一个值得注意的讨论点是对整体安全模型的质疑，这涉及到计算机系统设计中对用户权限管理的根本性问题。

主要讨论点：2048游戏的64位状态实现及其技术细节 不同观点： • [eurleif] 认为实现的亮点在于用不到200行的bash脚本完成，而不是64位状态的实现。他解释了用4位可以表示一个格子的12种可能状态（包括空格），从而总状态可以用64位表示。 • [rossant] 建议将其实现为一个C语言函数`int64 run_2048(int64 state, int input)`，将状态和输入（上下左右）作为参数，返回新的状态，认为这可以作为一个有趣的代码高尔夫练习。 • [lotyrin] 强调了将复杂状态空间映射到简单线性序列的技巧，并举例说明如何将有限字符集编码映射到数字序列中，认为这是很多人忽略的技巧。 • [bvanderveen] 赞赏了简洁的实现，但指出了一个bug：使用“角策略”时，有时左上角的格子会随机变小。 • [nneonneo] 分享了类似的技巧，其2048 AI允许格子达到32768，并使用每个半字节表示一个格子，从而将整个游戏板打包到一个寄存器中。 • [carra] 提到原版2048游戏在达到2048后仍可继续，而该实现为了实现64位状态去掉了这一选项，但仍认为这是一个聪明的实现。 补充讨论： • [enriquto] 通过数学计算论证了在不超过2048的情况下，总状态数为11^16，约需要56位，因此64位是足够的，认为这是一个紧凑的实现。 • [Normal_gaussian] 和 [meta-level] 没有直接讨论技术细节，而是提到安装命令和自己的bash脚本，更多是表达对该实现的兴趣或对比自己的经验。 • [kinduff] 简单赞赏了代码行数和实现的聪明。 • [mark_undoio] 表达了对作者的赞赏和对其创造力的惊讶。 争议焦点： • 主要争议点在于实现中的潜在bug，[bvanderveen] 指出的“角策略”问题是否存在及如何修复。 • 另一个讨论点是64位状态实现的实际限制和原版游戏的差异。
