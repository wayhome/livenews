From OpenAPI spec to MCP: How we built Xata's MCP server

作者: tudorg | 评分: 15 | 评论数: 2 | 发布时间: 2025-05-25 08:41
文章摘要

文章介绍了如何利用Kubb、自定义代码生成器和Vercel的Next.js MCP适配器，基于OpenAPI规范构建Xata的MCP服务器。MCP（Model Context Protocol）是一种让AI模型实时与工具和API交互的标准。构建MCP服务器需要暴露一组“工具”供大型语言模型（LLM）调用，以执行任务。 文章描述了从OpenAPI规范自动生成MCP服务器的好处，包括节省时间并保持API和MCP定义同步，但也指出直接将所有REST API端点映射为MCP工具可能让LLM困惑。解决方案是利用OpenAPI自动生成基础代码，然后进行精简和优化。 具体步骤包括： 1. **迁移到Kubb**：取代传统OpenAPI代码生成器，获得更灵活的解决方案。 2. **自定义Kubb生成器**：生成TypeScript API客户端和MCP工具。 3. **使用Next.js创建MCP服务器**：利用Vercel的MCP适配器、路由处理器和认证中间件实现。 Kubb配置简单且高度可定制，支持一次生成多种输出，如API客户端和MCP工具。通过命令触发代码生成，实现高效开发。

评论摘要
主要讨论点：[是否需要通过MCP表示来处理OpenAPI规范，以及MCP服务器的安全性问题] 不同观点： • [alooPotato] 认为没有必要将OpenAPI规范转化为中间的MCP表示，可以直接将其提供给LLM。他认为LLM能够处理API文档，且不认同文档会使LLM过载的观点。 • [_pdp_] 则关注MCP服务器的安全性问题，指出当前有关MCP服务器数据泄露攻击的讨论较多，建议引入安全专家确保其安全性，防止低级漏洞。 补充讨论： • [alooPotato] 的观点基于个人经验，对“API文档会使LLM过载”的说法持怀疑态度，倾向于简化处理流程。 • [_pdp_] 强调了当前MCP服务器面临的实际安全威胁，指出在继续推进之前需要进行安全审查，以防止潜在的攻击漏洞。 • 争议的焦点之一在于是否需要MCP作为中间表示，[alooPotato] 质疑其必要性，而 [_pdp_] 则关注安全问题，间接支持更谨慎和全面的处理方式。

文章摘要

文章主要讨论了技术进步如何影响软件开发领域，特别关注从无代码（NoCode）到人工智能辅助开发的演变。每次新技术出现时，都会有人宣称它将取代开发人员，但实际情况往往是转变而非取代。无代码运动没有消除开发者，而是催生了新的专业角色，如无代码专家和后端整合者，且薪资更高。同样，云计算没有取代系统管理员，而是将他们转变为薪资更高的DevOps工程师。 目前，人工智能辅助开发正经历类似过程。尽管AI能生成代码，但高级工程师仍需花费大量时间验证和修正其输出。软件开发中最有价值的技能并非写代码，而是系统架构设计，这是AI无法替代的核心能力。 总之，技术革新往往提升而非消除专业技能，开发人员需不断适应并学习新技能以应对变化。

LiveStore是一个基于反应式SQLite和事件溯源的下一代状态管理框架，支持实时同步和跨平台使用。它通过提交事件来更新数据库并同步到其他客户端，具有嵌入式SQLite数据库，并支持与多种UI框架（如React、Solid等）集成。开发者通过定义事件和物质化器（materializers）来映射事件与数据库状态的变化，实现响应式查询和状态管理。LiveStore旨在替代Redux、MobX等库，提供更高效的客户端数据层解决方案。
