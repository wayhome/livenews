这篇文章通过一个寓言故事解释了Lisp宏的工作原理。故事讲述了一家公司的程序员因为懒惰，在代码中留下注释描述需要编写的代码，而不是实际编写。公司雇佣了名叫Mac的初级程序员，负责根据这些注释编写代码并插入程序。随着工作量增大，Mac与编译器集成，接收注释并返回代码。程序员逐渐发现，注释越精确，Mac返回的代码越准确。最终，程序员开始在注释中直接写Lisp程序来生成所需代码，并定义可重用的函数。这些定义性注释被标记为"Definition for Mac, Read Only"，最终简化为"DEFMACRO"。这个故事形象地说明了宏作为元编程工具，在编译时将代码转换为其他代码的机制。

What's the best programming language for coding agents?

作者: chaychoong | 评分: 89 | 评论数: 22 | 发布时间: 2026-08-10 16:28
文章摘要

文章质疑“动态语言或更简洁的语言更节省Token”的结论，指出相关研究使用的任务过于简单，且存在测试路径、执行程序和评分错误，难以推广。作者预注册判断，认为静态语言在复杂任务或高投入场景可能更可靠，J等小众语言的优势也不会持续，并计划通过实现Zstandard解码器等更复杂任务重新评估。

评论摘要
主要讨论点：编程语言对LLM代码生成的适用性及评估方法 不同观点： • **Go派（一致性优先）**：认为Go因其"只有一种做法"的设计哲学和一致的训练数据，比Python更适合LLM。Python训练数据被非专业代码"污染"，存在多种实现方式。工具链优势（快速编译、良好的linting）缩短迭代周期 • **类型系统派**：强调静态类型、编译检查的价值。Rust在编译时就能发现错误，比Python运行时错误更快迭代。有人期待Ada等更强类型系统带来更好的自纠错能力 • **语言特性派**：认为"对人类友好"的特性（编译、强类型、不可变、纯函数、模式匹配）同样对LLM友好。小众语言如Gleam表现出色支持这一观点 • **流行度派**：质疑Python因训练数据最多，是否应是最佳选择。观察到LLM服务默认选择Python • **评估方法质疑派**：认为复现知名软件的测试无法真正评估能力，可能只是检索训练数据的能力。建议用标准化的等效任务测试。token密度不等于实际成本，因为符号的token化效果差 • **反简洁性派**：用Wolfram语言的失败案例说明，极度简洁且训练数据少的语言效果反而差 补充讨论：实际应用中不同语言在创意任务vs技术任务上表现有差异；应更关注用户角度的正确性保障而非单纯的token成本

主要讨论点：围绕1958年NEC参数元计算机NEAC-1101，讨论早期计算技术的多样路线、磁逻辑的国际发展及其后续潜力。 不同观点： • NEAC-1101代表日本早期计算突破：采用后藤英一发明的参数元、浮点运算和磁芯存储，可靠且成本较低，服役约8年，并推动NEC后续参数元计算机发展。 • 计算史并非简单的“真空管→晶体管→集成电路”：磁芯逻辑、转磁器、低温开关、隧道二极管、微波及电致发光逻辑都曾是候选路线，只是后来被主流叙事遗忘。 • 量子磁通参数元被认为仍有潜力：可达GHz、支持绝热计算，并可利用约瑟夫森结和SQUID构建复杂电路；但必须维持极低温，这是现实限制。有人认为它比当前量子计算更有前景。 • 类似技术并非日本独有：美国1958年的UNIVAC Solid State采用磁放大器逻辑，英国Elliott 803也使用磁芯逻辑；评论者推测其发展受到V2火箭磁放大器的推动。 • 参数元相较真空管、继电器和早期点接触晶体管更稳定、便宜且容错性强。对“真空管寿命短”的说法，有人以使用数十年的真空管音响反驳；回应认为计算机含数百至数千只管，整体故障概率会被放大。 补充讨论：有人提到网页长链接引发横向滚动，并讨论CSS换行方案；另有“万物皆可运行Doom”、动漫《石纪元》及“Goto”姓名与编程语句的趣味联想。
