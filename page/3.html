AI code review: Should the author be the reviewer?

作者: sebg | 评分: 101 | 评论数: 15 | 发布时间: 2025-05-01 13:50
文章摘要

文章探讨了使用AI编写代码后，是否也应由AI进行代码审查的问题。作者Daksh是Greptile的联合创始人，他们的产品使用AI审查pull request以发现人类可能忽略的错误和不良模式。作者通过分析用户提交PR的数据，发现某些用户提交的PR数量远多于其他人，且一个名为“devin-ai-integration[bot]”的AI bot提交的PR数量最多。 文章指出，传统上不希望代码作者自己审查，因为需要“新鲜的视角”。然而，LLM（大型语言模型）是无状态的，每次调用都是独立请求，因此让AI审查自己的代码也算是“新视角”。此外，AI工具在执行任务时的“脚手架”（工作流程）不同，使得代码生成和审查实质上是两个不同的过程，类似于两辆车使用相同引擎但车体不同。 文章还提到，AI提高了程序员的速度和效率，但可能降低代码质量，因为提示（prompt）并不完美，工程师容易低估这一点且未仔细审查AI生成的代码。AI生成的代码常包含人类不易察觉的错误，而AI在发现这些错误方面比人类更有效。 总结：尽管AI生成代码需要更严格的审查，但AI审查工具在发现错误方面优于人类，因此用AI审查AI生成的代码是可行且有效的。

评论摘要
主要讨论点：AI生成代码的审查过程及其与人工审查的关系 不同观点： • **svieira** 认为，工程师在审查自己编写的代码时，会进行即时的自我审查，而AI生成的代码则缺乏这种实时审查的过程。同时提到，AI让优秀和一般工程师的代码质量趋于平均化。 • **rbren** 分享了OpenHands项目中的实际问题：AI生成的PR可能没有经过第二人审查就被合并，导致责任不明确和潜在问题。他们的解决方案是确保每个PR都有明确的负责人。 • **gonzan** 强调了AI工具在不同阶段（编写和审查）的差异，认为即使同一AI工具也可以在不同阶段发现不同问题。同时指出AI工具仍不完美，需要人工审查的辅助。 • **SOTGO** 对AI发现的bug数量表示怀疑，认为可能会产生许多误报，质疑其有效性。 • **flimflamm** 建议将AI审查视为类似linter的工具，认为AI可以先进行初步审查，但最终仍需人工确认代码的正确性和意义。 • **simonw** 强调程序员的责任，认为无论是否使用AI辅助，提交PR时程序员都应对代码负责，且应根据公司政策进行人工审查。 • **black3r** 指出，即使AI在不同情境下生成代码和审查代码，仍可能缺乏对代码库和任务细节的全面理解，建议至少有一名有经验的工程师进行最终审查。 • **_heimdall** 提出，审查代码时应考虑未来维护的责任，不建议完全依赖AI进行审查。 • **pjmlp** 认为，未来技术架构师可能只需对交付物进行最终审查。 • **devrandoom** 强调自我审查的局限性，认为很难发现自己的错误，主张必须有他人审查代码。 • **aussieguy1234** 分享了使用AI进行“预审查”的经验，认为AI可以有效捕捉明显问题，加速代码审查过程，但仍需人工最终审查。 • **allisonee** 认为，AI可以进行初步审查，但人工审查仍具有重要价值，特别是在构建共享理解和捕捉高级问题方面。 • **JonChesterfield** 对AI自我审查的合理性表示怀疑，认为这种做法可能导致错误被忽视，类似于历史上计算机误判的情况。 • **logicchains** 提出，AI可以编写大量单元测试，并进行初步审查，但人工审查仍需提供高层次的视角和协作。 • **gitroom** 信任人工审查多于AI，但承认AI在发现潜在问题方面有一定优势。 补充讨论： • AI生成代码的审查过程需要考虑责任分配和代码质量问题，特别是在团队合作和项目维护中。 • AI工具在编写和审查代码方面的应用仍需人工辅助，以确保代码的正确性和质量。 • 不同工程师对AI工具的信任程度和使用方式存在差异，反映了技术应用中的实际挑战和局限性。 • 讨论中多次提到需要人工审查提供高层次的视角和协作，以弥补AI工具在理解和判断方面的不足。

C++26: more constexpr in the standard library

文章摘要

本文讨论了C++26中将成为constexpr的几个标准库特性。首先提到P2562R1提案，建议使与稳定排序相关的算法（如`std::stable_sort`、`std::stable_partition`等）可在常量表达式中使用，这得益于constexpr容器的引入。接着讨论P1383R2提案，旨在使``和``中的函数在常量表达式中可用，同时接受浮点计算结果的某些差异。然后是P3074R7提案，解决了实现constexpr友好的unions时遇到的问题，通过最小化用户体验的改变来实现。最后，P3372R2提案旨在使几乎所有容器和适配器成为constexpr，除了`std::hive`和需要自定义哈希功能的无序容器。

评论摘要
主要讨论点：C++的编译时常量计算及其复杂性，以及标准委员会在解决语言问题上的优先级 不同观点： • WalterBright认为D语言在2007年就已经实现了编译时的常量函数计算，而无需对语法进行更改，只是增强了常量折叠以处理函数调用。他不理解为什么在C++中这个问题如此复杂。 • gitroom表示虽然经常看到不断的更新，但感觉一些主要的痛点问题长期未得到解决，有时觉得标准在追逐错误的问题。 • nokeya讽刺地说，这项功能即使在所有主要编译器都支持的情况下，也要到2040年左右才能在实际中看到。 • kubav027基于自己的职业经历认为，某些功能（如constexpr排序）非常小众，不应成为C++标准的一部分。 • brooke2k对"constexpr排序"表示担忧，认为这可能会引发编译时的问题。 • dvratil则认为委员会没有优先解决语言和标准库中的更大问题，比如用简短的代码实现异步网络请求，而是在处理一些相对次要的技术细节。 补充讨论： • 争议的焦点之一是C++标准委员会的优先级问题，一些开发者认为委员会在解决小问题的同时，忽略了语言和库中更大的、更实际的问题。 • 另一个值得注意的点是对constexpr功能（如排序）的实用性存在质疑，部分开发者认为这些功能过于小众，不应成为标准的一部分。 • 还有对C++功能实现的时间进度表示不满，认为新功能的实际可用性被严重延迟。
