Icons in Menus Everywhere – Send Help

作者: ArmageddonIt | 评分: 179 | 评论数: 34 | 发布时间: 2025-12-08 19:44
文章摘要

这篇文章批评了现代软件界面中普遍存在的“默认给每个菜单项添加图标”的设计趋势。作者以Google Sheets和最新macOS Tahoe系统为例，指出这种设计增加了视觉干扰和认知负担，许多图标既无必要又缺乏一致性。他特别反对设计师“为填空间而加图标”的懒惰做法，认为应该基于实际需求慎重考虑每个图标的价值。作者发现苹果公司的新设计甚至违背了自己2005年的人机界面指南，该指南明确警告过滥用图标会导致视觉混乱。尽管承认某些场景下图标确实有用（如窗口布局预览），但作者仍对当前无处不在的菜单图标感到困扰，认为这反映了不良的设计潮流。

评论摘要
主要讨论点：菜单中是否应该包含图标（Icons）以及图标的设计和功能价值 不同观点： • **支持菜单中包含图标** - 图标可以帮助快速定位功能（如Google Docs中的"Insert Link"图标），减少阅读时间（usaphp, socalgal2） - 图标有助于非母语用户或本地化不完善的场景（socalgal2, 0manrho） - 图标+文本组合适合新老用户，文本辅助新手，图标帮助老用户形成肌肉记忆（DeathRay2K） - 图标可以作为工具栏功能的视觉映射（dexwiz） - 彩色且独特的图标更具辨识度，避免视觉噪音（zamalek, linguae） • **反对菜单中滥用图标** - 抽象或重复的图标增加认知负担，尤其是当图标设计相似时（hinkley, nvader） - 不一致的图标使用（如部分条目有图标而部分没有）导致排版混乱（daemin） - 图标可能沦为填充空间的装饰，而非功能辅助（0manrho引用原文观点） - 纯文本或仅状态指示图标（如勾选标记）更简洁（zzo38computer） • **中立或条件性支持** - 图标需满足高辨识度（颜色、形状）和明确语义（如经典“保存”图标是否过时）（arcbyte, hinkley） - 部分场景需要权衡：专业软件（如AutoCAD）可能依赖图标，而通用软件需兼顾多样性（sixtyj） 争议焦点： 1. **图标的功能性 vs. 视觉噪音**：支持者认为图标提升效率，反对者认为劣质图标适得其反。 2. **一致性要求**：是否所有菜单项必须统一带图标？daemin批评苹果菜单的缩进不一致，而arcbyte原认为全图标更一致，后受文章影响动摇。 3. **设计成本与普适性**：0manrho指出图标+文本需设计投入，但苹果等大公司无理由回避；nvader则认为图标滥用可能是设计者自我满足的结果。 补充讨论： - **历史与趋势**：早期彩色图标（如Office 97）可能更有效，现代扁平化设计削弱了辨识度（linguae）。 - **可访问性**：图标需兼顾色盲用户（hinkley），且与文本互补（0manrho）。 - **符号语义演变**：如“软盘保存”图标是否仍直观（arcbyte）。

Brent's Encapsulated C Programming Rules (2020)

这篇文章总结了作者在编写完全封装的C语言程序时总结的一些规则和建议。主要内容包括： 1. **纯封装方法**：通过隐藏结构体成员实现完全封装，仅通过头文件暴露接口，避免开发者直接修改结构体内容。 2. **性能与封装的平衡**：纯封装可能影响性能，因此在性能关键代码中可以适当暴露结构体成员，但使用`const`修饰以防止误修改。 3. **内存管理**：强调良好的内存所有权管理，建议避免使用全局变量和静态变量，使用标准布尔类型，以及明确的内存分配和释放策略。 4. **代码规范**：推荐使用UTF-8字符串、避免过度复杂的字符串处理、优先使用内联函数而非宏、函数应单一职责、模块化设计等。 5. **其他建议**：包括零初始化结构体、使用浮点数误差检查、遵循标准规范等。 这些规则旨在帮助开发者编写高效、可维护且封装良好的C代码。

Gamma是一种自托管的C语言预处理器，旨在通过简单的模板化数据结构扩展C语言功能。它作为C的超集，无需解析C代码即可实现模板功能。Gamma可通过设置环境变量启用，支持生成目标文件和静态库，并能与普通C目标文件链接。该项目小巧便携，可轻松集成到其他项目中。Gamma由Matthew和Akshay开发，提供了排序、打印等泛型功能示例以及通用向量数据结构实现。最新版本还推荐了类似项目MaC，后者支持更强的类型反射功能。

主要讨论点：[在C语言中添加模板/泛型/反射机制的可行性与实用性] 不同观点： • [支持实验性方法的观点] - 作者提出Gamma和MaC两种实验性方法，尝试在C语言中实现模板功能。 - Gamma的局限性在于难以处理类型定义和循环依赖（如struct tree_node包含list::[struct tree_node]）。 - MaC通过完全解析头文件解决了这些问题，更可靠，并支持GNU-C特性。 - 作者指出"不解析代码"的方法无法实现类型推断，尝试过基于DWARF信息的动态分发但复杂。 • [质疑实用性的观点] - sfpotter质疑这类语言的实用场景，认为直接使用C++的模板或D语言的模板是更好的选择。 - 指出调试问题：需要通过生成的C代码调试，不如直接调试原始源码方便。 - 提出名称修饰(name mangling)如何处理的疑问。 补充讨论： • 争议焦点在于： - 是否值得在C语言中重新实现模板机制 - 与现有更成熟方案(C++/D语言)相比的优劣 • 技术难点： - 类型推断的实现 - 循环依赖处理 - 调试支持 - 名称修饰方案
