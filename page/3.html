Anti-Personnel Computing (2023)

文章摘要

"Anti-personnel computing"是一个新术语，用于描述21世纪初主流计算的特点。它指计算设备的使用损害用户利益，而使第三方实体受益。具体来说，"anti-personnel computer"指的是一种主要用于损害用户利益、为第三方实体谋利的计算设备。该词源自“反人员地雷”（anti-personnel mine）以及“个人计算”（personal computing）和“个人电脑”（personal computer）等词，反映了技术对用户的不利影响。

主要讨论点：关于“反个人计算”（anti-personnel computing）及其相关概念的讨论，涉及技术对用户的负面影响、隐私问题以及可能的解决方案。 不同观点： • JohnMakin认为当前软件行业的氛围与90年代末和2000年初的互联网泡沫时期相似，当时网页上充斥着广告和恶意软件，而现在类似的现象再次出现，反映出过度追求高估值和营收的狂热可能导致崩溃。 • vanschelven引用了GNU哲学，强调保持对计算的控制，以避免被技术控制。 • fmajid和praptak对术语提出质疑和建议。fmajid认为“反个人计算”这个术语不准确，建议用“浮士德式计算”（Faustian computing）。praptak则更倾向于使用“反特性”（antifeatures）这个更精确的术语。 • Tepix指出，当前软件系统越来越难以避免对用户不利的影响，利润最大化的驱动是这种现象的根源，并提到Cory Doctorow对“恶化”（enshittification）的描述，尽管引起了广泛关注，但非盈利和去中心化服务仍未占据较大市场份额。 • pjc50认为“用户 hostile”或“hostile architecture”更适合描述那些对用户不利的系统，而“反个人”应保留用于那些真正危险的应用，比如用于识别种族的监控摄像头。 • keisborg喜欢“反个人计算”这个术语，因为它利用了负面联想来引发讨论，并提议禁止“反个人计算”。 • DonHopkins回忆了Mac电脑崩溃时的炸弹图标，以及Windows 9x的非法操作提示，这些设计曾让用户感到恐慌。 • casey2区分了“反个人计算”和“反特性”，前者包括数据收集、封闭生态系统、暗模式和不透明程序，后者指那些对用户有害或控制用户的行为。 • 6510讨论了中国和西方在数据使用上的差异，提出可以通过加密和智能使用时间和地点来保护隐私，并提出探索“反个人计算”和有用应用之间的边界，认为可能存在互利空间。 补充讨论： • 讨论中涉及的术语争议，包括“反个人计算”、“浮士德式计算”和“反特性”，反映了人们对技术负面影响的关注和术语准确性的追求。 • 对技术系统中利润最大化驱动带来的负面影响及其解决方案的探讨，包括Cory Doctorow的“恶化”概念和加密技术的潜在应用。 • 对隐私和数据使用的不同看法，有人担心技术对个人的控制和隐私侵犯，也有人认为在某些情况下可以通过技术手段实现互利。 争议焦点： • 术语“反个人计算”是否准确和合适，以及如何定义和区分不同类型的技术负面影响。 • 如何在技术系统中平衡利润最大化和用户利益，以及如何有效保护隐私和避免技术对用户的控制。

Detecting if an expression is constant in C

作者: signa11 | 评分: 16 | 评论数: 4 | 发布时间: 2025-05-09 17:09
文章摘要

本文讨论了如何在C语言中创建一个宏，验证表达式是否为编译时常量，并在保持原始类型的情况下返回该常量。不同方法适用于不同的C标准和编译器支持情况： 1. **C23的constexpr复合字面量**：使用C23标准引入的`constexpr`和`typeof`，定义宏`#define C(x) ( (constexpr typeof(x)){x} )`，确保表达式为常量。缺点是C23尚未广泛支持。 2. **GNU扩展的`__builtin_constant_p`**：利用GNU扩展，通过`__builtin_choose_expr`选择常量表达式，否则触发编译错误。缺点是依赖GNU扩展。 3. **C11的`static_assert`**：使用C11的`static_assert`结合`sizeof`和匿名结构，验证表达式是否为常量。缺点是可能改变表达式类型。 4. **sizeof + 复合字面量和数组类型**：利用C99的变长数组特性，通过复合字面量验证常量。优点是无需C11支持，但继承了`static_assert`的问题。 5. **sizeof + 枚举常量**：利用枚举常量必须是整型常量表达式的特性，但存在枚举常量“泄漏”的问题。 不同方法各有优缺点，选择取决于具体需求和环境。

评论摘要
主要讨论点：如何在编译期判断表达式是否为常量表达式，以及在C语言中处理此类问题的复杂性与可能的解决方案。 不同观点： • [sleirsgoevy] 认为可以通过使用Linux内核中的一种技巧来判断表达式是否为编译时常量，而无需中断编译过程。他提供了一个宏定义 `__is_constexpr(x)`，并解释了其工作原理：利用三元表达式的特性，在常量表达式情况下返回特定类型的大小，从而进行判断。此外，他还提到可以通过一些技巧实现编译时的"类型三元表达式"（TYPE_IF），但未提供具体实现。 • [bobbyi] 尝试使用 `sizeof` 操作符来判断表达式是否为编译时常量，但遇到问题。他引用了标准中的规定，指出对于可变长度数组，`sizeof` 操作会在运行时计算，而不是编译时。这导致他的方法未能如预期工作。 • [wahern] 回应了关于编译器警告的问题，指出在使用匿名枚举时，GCC和Clang会发出警告。他提供了一种使用 `_Pragma` 来抑制警告的解决方案，但同时也提到GCC对 `_Pragma` 的使用位置更为严格，并且GCC 14没有合适的开关来禁用匿名枚举警告。 • [pjc50] 对上述复杂的技巧持批评态度，认为学习一种可以通过类型系统强制执行此类检查的语言会更好。他建议使用支持 `constexpr` 的语言版本，而不是依赖C语言中的这些技巧。 补充讨论： • 讨论中涉及的具体实现技巧，如 `__is_constexpr(x)` 和 `C(x)`，展示了在C语言中处理编译时常量判断的复杂性。 • 编译器行为和警告处理也是讨论的一个重要方面，特别是如何抑制特定警告以及不同编译器之间的差异。 • 对使用现代C++特性（如 `constexpr`）的建议，反映了对更简洁和类型安全解决方案的需求。

2019年5月5日，俄罗斯国际航空（Aeroflot）1492航班在莫斯科谢列梅捷沃机场着陆后起火，导致机上41人遇难，37人幸存。这架苏霍伊超级喷气机100（Sukhoi Superjet 100）在着陆过程中遭遇雷暴和飞控系统故障，多次撞击跑道后起火。机尾迅速被火焰吞噬，部分乘客因毒烟丧生。事故引发了关于航空公司、飞机、机组人员及乘客责任的争议，尤其是一些乘客在撤离时仍试图拿取随身行李。经过近六年的调查，独立调查委员会发布了一份近600页的报告，指出事故原因复杂，包括天气、技术故障及人为因素。这起事故揭示了一个涉及广泛、技术复杂且带有悲剧性的故事。
