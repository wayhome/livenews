Declarative Schemas for simpler database management

作者: kiwicopple | 评分: 57 | 评论数: 12 | 发布时间: 2025-04-03 17:02
文章摘要

本文介绍了声明式 schema 如何简化复杂数据库的管理。声明式 schema 将数据库的最终期望状态存储在 `.sql` 文件中，便于集中管理和版本控制。相比直接修改数据库 schema，声明式 schema 具有以下优势：单一管理界面，减少冗余和错误；版本化迁移，确保不同环境中的一致性；简明的代码审查，无需重复复杂迁移脚本。 随着数据库 schema 复杂性增加，传统迁移方法难以维护，因为缺乏单一的整体视图。例如，在 Supabase 中，复杂的 `projects` 表涉及私有表、RLS（行级安全）、视图和触发器，修改时需多步操作，容易导致冲突。 声明式 schema 通过集中管理 schema，简化了开发流程，提高了开发效率。

评论摘要
主要讨论点：数据库迁移和声明式 schema 管理的优缺点 不同观点： • [支持声明式 schema，但反对自动生成迁移]：xyzzy_plugh 认为声明式 schema 是有必要的，但不应自动生成迁移，因为这可能带来问题。他建议手动编写迁移并测试，以确保 schema 变更符合预期。 • [有限支持声明式 API]：webster451 认为声明式 API 在某些场景下非常强大，但并不适用于所有情况。他认为程序员对变更的控制能带来更好的结果，并指出 Kubernetes 等工具虽然提供声明式基础设施，但实现非常复杂且容易出错。 • [支持自动生成迁移]：bartvk 总结了一种新方法，即通过修改 CREATE TABLE 语句并自动生成差异迁移。他认为这种方法简化了数据库变更的管理。 • [Rails 的做法更好]：neutralino1 认为 Rails 已经实现了更好的方案，通过保持迁移和 schema.sql 文件的同步，方便测试和数据库重建。 • [需要 IDE 支持的声明式管理]：Guillaume86 希望有一个类似微软 SSDT 的工具，用于 Postgres，提供声明式 schema 管理、错误检查和更好的开发体验。 • [自动生成迁移可能导致问题]：joshAg 认为自动生成迁移可能导致一些复杂的变更（如 enum 变更、数据迁移）难以处理，建议手动编写迁移以确保灵活性。 • [关注手动编辑自动生成迁移的能力]：ucarion 关心是否可以手动编辑自动生成的迁移，以实现更复杂的操作，如并发创建索引。 • [结合 IDE 工具提升开发体验]：kiwicopple 提到结合 Postgres Language Server，可以在 IDE 中直接执行 SQL 语句，提高开发效率。 • [自动生成迁移的风险]：geocar 警告自动生成迁移可能在团队中引入严重错误，导致长期问题。 • [其他工具]：xaas 提到使用 ZenStack 并指出其未来版本将不再依赖 Supabase。 • [质疑新方法的价值]：mylons 质疑新方法相比原始 SQL 的优势，认为差别不大。 • [提供相关参考资料]：wmanley 提供了关于 SQLite 声明式迁移的文章链接，并披露自己是该文章的合著者。 补充讨论： • 争议的焦点在于自动生成迁移的可靠性和灵活性，以及声明式 schema 管理的优缺点。 • 不同开发者对声明式和命令式方法的偏好，以及对工具支持和开发体验的需求各不相同。 • 实际应用中，如何平衡自动化和手动控制的比例，以及如何确保数据库迁移的安全性和可维护性，是重要的讨论点。

InitWare是一套中间件套件，用于将服务和系统资源作为逻辑实体（称为单元）进行管理。其主要组件是一个服务管理系统，能够在NetBSD、GNU/Linux及其他现代BSD系统上运行。InitWare通过作业调度器根据依赖关系自动调度单元，并提供用户会话管理器和系统日志。它可以作为init系统或辅助服务管理系统运行，源于systemd的分支，并在许多接口上保持与systemd的兼容性。当前为alpha版本，建议在生产环境中谨慎使用，直到发布首个稳定版本。InitWare根据LGPL-2.1许可证发布，支持多种平台，并提供了详细的构建和贡献指南。

评论摘要
主要讨论点：围绕InitWare项目及其与systemd的比较，讨论不同init系统的优缺点，以及在桌面环境和容器操作系统中的适用性。 不同观点： • 支持InitWare的观点： - InitWare项目提供了模块化和可选的服务管理，不像systemd那样强制整合过多功能（LinuxBender）。 - InitWare的Dropped Components部分令人鼓舞，可能成为Debian系统上替代systemd的选择，避免systemd的过度干预（foresto）。 - InitWare的轻量化和可选性使其更适合那些不喜欢systemd掌控一切的用户（travisgriggs）。 • 批评systemd的观点： - systemd变得过于庞大，试图掌控系统的一切，而InitWare更接近理想中的服务控制管理器（donnachangstein）。 - systemd的复杂性和频繁更新会导致用户花费大量时间解决兼容性问题，而InitWare提供了一种更简洁的选择（exceptione）。 • 中立/比较观点： - 提到macOS的launchd，认为如果能在Linux上适用，可能会成为统一的init系统（dontlaugh）。 - 比较InitWare与dinit（matu3ba），指出两者在目标上的相似性。 - 提到其他替代方案如supervisord，认为其在Alpine上表现良好（udev4096）。 补充讨论： • 项目活跃度问题： - 指出InitWare项目在过去几年中提交不活跃，可能需要更多贡献或资金支持（WD-42, LinuxBender）。 • 安全性和公司支持： - 认为默认拒绝所有访问并明确选择进程需要的权限是更好的安全策略，而systemd的默认允许所有访问不够安全（egberts1）。 - 提到systemd的优势在于有公司支持，使得捐赠和项目维护更加可行（Vilian）。 • 幽默和讽刺： - 有些评论以幽默和讽刺的方式表达了对新项目出现的态度（betimsl, johnea）。 争议焦点： • systemd的复杂性和功能扩展是否合理及其对系统管理的影响。 • InitWare及其他替代init系统的可行性和活跃度。

Binary Distribution Rebuilds

作者: JNRowe | 评分: 9 | 评论数: 1 | 发布时间: 2025-03-31 12:22
文章摘要

本文总结了作者在重建Debian和Ubuntu软件包（amd和arm64架构）方面的实验，并与新推出的Reproduce.Debian.net项目进行比较。作者的实验使用最新版软件包进行重建，而Reproduce.Debian.net则使用与发布包相同的构建输入以实现更高的可重现性。作者指出，虽然Reproduce.Debian.net有可能达到100%的可重现性，但还需更进一步，实现“幂等重建”（Idempotent Rebuild），即通过反复重建最终得到一致的档案。当前，由于时间戳和不确定输出等问题，N（重建次数）可能为无穷大，但理想情况是实现N=1。作者计划发布阶段#0的构建产物以进一步实验，但目前尚未取得更多技术进展。

评论摘要
主要讨论点：Debian main是否能够自我重建，特别是涉及非自由固件和非Debian签名的二进制文件的影响。 不同观点： • 观点一：Debian main可能已经无法自我重建。提出者认为，由于存在非自由固件和非Debian签名的二进制文件，Debian main的自我重建能力可能已经被破坏。这种观点强调需要解决这些问题以实现Debian的完全可重建性和自举能力。 • 观点二：可以通过在无二进制blob的平台上引导Guix，并从该平台交叉构建Debian来解决。这一观点提出了一种技术解决方案，即利用Guix在无专有固件和二进制文件的环境中完成Debian的构建，从而绕过当前的问题。 补充讨论： • 争议焦点：主要在于是否存在使用非自由包作为构建输入的情况。如果确实存在，那么即使在无二进制blob的环境中引导也可能无法彻底解决问题。 • 技术实现：讨论中提到了具体的技术实现方法，例如使用Guix进行无blob平台的引导和交叉构建Debian，这表明社区内对于技术解决方案有一定的探讨和可行性分析。 • 重建能力：核心问题仍然是Debian main是否具备完整的自我重建能力，尤其是在涉及非自由软件组件的情况下如何确保系统的纯粹性和可重建性。
