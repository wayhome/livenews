Slowing the flow of core-dump-related CVEs

作者: jwilk | 评分: 75 | 评论数: 5 | 发布时间: 2025-06-10 20:07
文章摘要

文章主要讨论了Linux内核在处理崩溃进程的核心转储（core dump）时存在的安全问题及改进措施。核心转储用于记录进程崩溃时的状态，但其处理机制长期以来导致了许多安全漏洞（CVEs）。当前的问题在于，核心转储处理程序作为用户模式助手，以完全特权运行，成为攻击目标。攻击者可以通过竞争条件漏洞，利用崩溃进程的PID替换，获取敏感信息如`/etc/shadow`文件内容。为解决此问题，6.16内核引入了改进措施，包括新增格式标识符`%F`，使处理程序能够通过pidfd准确识别崩溃的进程，从而减少此类漏洞。文章强调需要更安全的API来处理核心转储。

评论摘要
主要讨论点：Linux系统中核心转储（core dump）机制的设计缺陷及其安全与实用性问题 不同观点： • inopinatus提到一个历史事件，通过利用核心转储处理不当的情况解决了实际问题，这可能暗示了核心转储机制在早期存在实际可利用的漏洞，带有一定的怀旧和技术分享色彩。 • 10000truths认为Linux核心转储机制存在设计缺陷，主要问题在于其作为全局设置且只能由root用户访问。他建议通过命名空间隔离或委派给reaper/subreaper进程来改进设计，并提到社区曾讨论过这些想法，但似乎未有实质进展。他提供了相关讨论链接以支持其观点。 • mort96对讨论中出现的"**** API"表示困惑，不确定其真实含义，质疑这是否意味着API存在问题，还是仅表达了作者的一种情绪。这反映出讨论中用词不清可能导致的误解问题。 • DeepYogurt简短地指出，CVE（常见漏洞与暴露）推动设计变革是好事，暗示安全问题确实促进了核心转储机制的改进。 • charcircuit深入探讨了核心转储处理以用户模式助手方式运行的问题，质疑为何不以专用核心转储用户身份运行。他还提到核心转储套接字传递给助手功能存在的漏洞，并对其在容器环境中的实用性提出质疑，认为共享崩溃报告基础设施可能更合理。 补充讨论： • 核心转储机制的全局性和权限问题成为讨论焦点，不同用户对设计缺陷的严重性和改进方向有不同看法。 • 讨论中还涉及用词不清（如"**** API"）导致的潜在误解，表明清晰沟通在技术讨论中的重要性。 • charcircuit对核心转储在容器环境中的应用提出进一步的技术和安全质疑，拓展了讨论的范围。

Self-Adapting Language Models

作者: archon1410 | 评分: 188 | 评论数: 17 | 发布时间: 2025-06-13 19:03
文章摘要

文章介绍了一种名为SEAL（Self-Adapting Language Models）的框架，使大型语言模型（LLMs）能够通过生成自己的微调数据和更新指令进行自我适应。SEAL模型在接收到新输入时，会生成自编辑内容，这些内容可以重构信息、指定优化超参数或调用工具进行数据增强和基于梯度的更新。通过监督微调（SFT），这些自编辑会导致持久的权重更新，实现持续适应。为了训练模型生成有效的自编辑，文章使用了一个以更新后模型的下游性能作为奖励信号的强化学习循环。实验表明，SEAL在知识整合和少样本泛化方面表现出色，是语言模型自我导向适应的有前景的一步。相关代码和网站已提供。

评论摘要
主要讨论点：大型语言模型（LLMs）的自适应学习能力及其实用性 不同观点： • **perrygeo**：LLMs缺乏像人类一样的持续学习能力，它们的训练和推理过程是分离的。这种静态特性导致人们误以为AGI（通用人工智能）即将到来，但实际上LLMs在推理结束后就停止了学习。 • **gavinray**：提到NEAT/HyperNEAT算法，这种算法通过演化网络拓扑来优化学习，与LLMs通过调整权重来学习的做法形成对比。他的两位从事ML早期的朋友坚信强化学习（RL）和演化算法是ML的未来方向。 • **xianshou**：赞赏自我编辑方法通过RL优化模型重构信息的能力，指出该方法可以发现更好的训练格式，但仍存在灾难性遗忘问题和高计算开销。他认为该方法适用于高价值文档处理，但限制于需要明确评估指标的任务。 • **libraryofbabel**：对LLMs在实际应用中“边做边学”的能力表示关注，质疑为何当前研究不更多关注这一方向，并指出这可能是实现AGI的关键障碍。 补充讨论： • **cma**：提到Anthropic最近关于自我微调的研究，提供了一个相关的文献链接。 • **neuroelectron**：幽默地提到模型在实际应用中被限制为只读模式，类似于科幻电影中的情节。 • **all2**：提供了一个包含代码和示例的网站链接。 • **khalic**：引用研究预测到2028年LLMs将用尽所有公开的文本数据，指出合成数据增强的重要性，并建议通过元训练一个专门的SEAL合成数据生成器模型来解决数据墙问题。 • **Centigonal**：提出“正确遗忘”问题比“正确学习”问题更迫切，指出当前模型在遗忘不相关信息方面的能力不足。 • **b0a04gl**：质疑自我编辑模型的调试难度，担心如何确定错误输出是源于基础模型还是模型的自我编辑，并进一步讨论优化器行为监控的必要性。 • **yahoozoo**：质疑SEAL方法的创新性，认为其仅是利用HuggingFace库进行LoRA适配器的合并。 • **mackenziebowes**：对SEAL命名表示不满，认为SAL更为合适。 • **bravesoul2**：简单提到正接近重大突破。 • **ivape**：指出持续微调在云端LLMs上的可行性问题，认为当前硬件条件尚不支持这一设想。 争议焦点： • LLMs的持续学习能力及其实际应用的可行性。 • 自我编辑方法的创新性和实用性。 • 调试和监控自我学习模型的难度。 • 数据墙问题及合成数据增强的潜在解决方案。

Student discovers fungus predicted by Albert Hoffman

作者: zafka | 评分: 122 | 评论数: 10 | 发布时间: 2025-06-11 00:36
文章摘要

文章摘要

FileDB 是一个受 Bitcask 启发的键值存储系统，使用 Zig 语言实现。它通过日志结构的哈希表存储记录元数据，并以仅追加模式将记录插入到一个磁盘文件中。当文件达到上限或重启时，文件会轮转，旧文件只读。FileDB 定期进行压缩，将多个文件合并为一个并更新元数据。它通过保持文件打开实现高吞吐量，元数据存储使记录获取成为 O(1) 操作。FileDB 还提供了与 Redis 兼容的客户端，并展示了较高的请求处理速度和较低的延迟。

Using `make` to compile C programs

作者: mfrw | 评分: 38 | 评论数: 10 | 发布时间: 2025-06-11 03:24
文章摘要

本文介绍了在不同系统上编译C/C++程序的基本步骤和常见问题，主要以Mac系统为例。具体步骤包括： 1. **安装C编译器**：在Ubuntu上可以通过`sudo apt-get install build-essential`安装，而在Mac上需要安装Xcode命令行工具。 2. **安装程序依赖**：C语言没有依赖管理器，需要手动安装。可以通过系统的包管理器安装，例如在Debian系统上使用`apt`。在Mac上使用Homebrew，但要注意包名的不同。 3. **运行`./configure`（如果需要）**：有些程序需要运行此脚本来生成`Makefile`。 4. **运行`make`编译**：使用`make`命令编译程序，如果出错，通常是依赖问题。需要根据错误信息调整编译器和链接器的参数。 文中还提到编译分为编译和链接两个步骤，需要正确设置编译器和链接器的环境变量以找到依赖库。例如，遇到`library not found`错误时，需要指定库的路径。

评论摘要
主要讨论点：Makefile和相关构建工具的使用与技巧 不同观点： • [kazinator] 解释了 CPPFLAGS、CXXFLAGS、LDFLAGS 和 LDLIBS 等环境变量的区别和用途。他强调 CPPFLAGS 与 C 预处理器程序相关，而 CXXFLAGS 专用于 C++。LDLIBS 和 LDFLAGS 则是链接器选项，LDLIBS 通常用于指定库，且必须在目标文件之后使用。 • [jwrallie] 分享了一个无需 Makefile 的简单用法，指出可以直接通过命令行对单文件 C 程序使用 Make 工具，这种方法简化了小项目的构建流程。 • [ashishb] 表达了对 Makefile 的喜爱，并提到 Makefile 适用于多种编程语言项目，如 Go、Rust、Python 等，认为 Makefile 提供了统一的高层次命令，如 `make format`、`make build`，即使底层工具变化，上层命令仍保持一致。 • [brunokim] 对 Autotools 这种通过尝试编译来适应不同环境的构建工具表示理解但不太喜欢，认为其复杂性让人不愿深入学习，表达了对这种工具的抵触情绪。 • [jiehong] 希望更多项目包含 Dockerfile，通过 Docker 容器环境来确保编译环境的一致性，并简化构建流程，尤其是当基础镜像与目标架构匹配时，能够更方便地获得可执行文件。 • [singpolyma3] 回应了关于 C 语言缺乏依赖管理器的观点，指出像 apt、cargo、homebrew 等都是常见的依赖管理工具，暗示 C 语言生态中并不缺乏依赖管理手段。 • [zabzonk] 简短地点评了 "C/C++" 这一表述，认为如果需要特别强调 "C/C++"，可能需要重新思考使用的语言或场景，暗示 C 和 C++ 的差异较大，不应混为一谈。 补充讨论： • 不同用户分享了各自在使用 Makefile 和其他构建工具（如 Autotools、Docker）时的经验和偏好。 • 对 C 语言项目中环境变量（如 CPPFLAGS 和 CXXFLAGS）的正确使用进行了技术性解释。 • 争议的焦点包括对 "C/C++" 这一表述的质疑以及对 Autotools 复杂性的不满。 • 用户们提供了在不使用复杂构建系统的情况下，如何简化构建流程的实用建议，如直接使用 Make 命令或通过 Docker 确保环境一致性。
