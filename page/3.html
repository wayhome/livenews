Fable created novel 4D splat format

作者: adamraudonis | 评分: 50 | 评论数: 6 | 发布时间: 2026-07-04 15:49
文章摘要

splat4d是一个动态3D高斯场景的压缩格式，能将数百MB的原始帧数据压缩至原大小的1/58（如427MB压缩到7.4MB）。 **核心技术**： - 静态/动态分离：不动的背景只存储一次 - 死区跟踪：仅在数值变化超过阈值时更新 - H.265风格GOP分组：支持独立解码和快速跳转 - 熵编码栈：Morton排序+字节平面shuffle+zstd压缩 **特点**： - 提供误差边界保证（位置±2mm、颜色±4/255等） - 支持从S3等对象存储通过HTTP Range请求流式传输 - 首帧显示快（141-157ms本地，791ms@50Mbps） - 跳转到关键帧仅需145ms - 使用WebGPU渲染，60fps播放 可通过Python命令行工具（pip install splats4d）将.splat帧序列编码为单个可seekable文件。

Designing DB partitions you don't have to babysit

作者: rtolkachev | 评分: 46 | 评论数: 4 | 发布时间: 2026-07-01 13:05
文章摘要

这篇文章讨论了数据库按时间字段（如 `created_at`）分区的常见问题： **核心问题：** - 按 `created_at` 分区后，查询必须包含时间条件才能实现分区裁剪，否则会扫描所有分区导致性能下降 - 分区键必须加入主键，将 `PRIMARY KEY (id)` 变成 `PRIMARY KEY (id, created_at)`，破坏了 `id` 的唯一性保证 - 查询优化器无法再将单 `id` 查询视为常量查找，性能从 `const` 降级为 `ref` - 分区键泄漏到应用层，所有查询都需要添加日期过滤器，增加维护负担 **推荐方案：** 按主键（如 `id`）分区而非时间字段，由后台服务根据实际增长情况管理分区边界。这样查询可以继续使用现有的键，分区裁剪自动工作，分区逻辑不会侵入应用代码。

评论摘要
**主要讨论点：** 如何处理大规模时间序列数据的存储和查询架构选择 **不同观点：** • **质疑传统分区方案**（yasaheblasa）：认为使用 id 作为主键在分区场景下存在问题，因为 id 不用于用户搜索且不可见，这会导致查询需要扫描所有分区索引。建议考虑使用创建日期等更符合查询模式的字段进行分区。 • **转向专用分析数据库**（djfobbz）：建议放弃 PostgreSQL 分区方案，改用 ClickHouse 等列式数据库做数据仓库，每天导入数据。提供实际案例：170美元/月的 VPS 处理500+亿行无压力，认为分区不断增长的 OLTP 表反而更复杂。 • **ID 生成方案的技术补充**（piterrro）：推荐 Snowflake ID 或 UUID7 模式作为替代方案，指出 bigint（64位）和 UUID（128位）的区别，强调需要根据具体需求权衡。 • **另一数据库选择**（leprechaun1066）：简短推荐 kdb+ 数据库，声称日处理10亿行是常规工作负载。 **补充讨论：** 核心争议在于架构选择——是优化现有 PostgreSQL 方案（分区策略、主键选择），还是直接迁移到专为时间序列/分析优化的数据库系统。反映了 OLTP 和 OLAP 场景下不同的技术权衡。

Postgres data stored in Parquet on S3: LTAP architecture explained

作者: andrenotgiant | 评分: 151 | 评论数: 15 | 发布时间: 2026-07-01 12:48
文章摘要

这篇文章介绍了 Lakebase 数据库的创新架构。传统数据库将写前日志（WAL）和数据文件存储在单机磁盘上，导致数据丢失风险、读副本成本高、分析查询拖累事务性能等问题。 Lakebase 通过将 Postgres 的计算层无状态化，把日志和数据文件外部化到独立云服务（SafeKeeper 和 PageServer），实现了无限存储、弹性计算、持久写入和即时分支，且无明显延迟增加。 LTAP（湖仓事务分析处理）架构更进一步，在存储层统一运营数据，使用开放列式格式，让 Postgres 和湖仓引擎都能读取同一份数据。这样分析可以实时运行在最新的事务数据上，无需 CDC 管道、无需数据复制、不拖慢事务工作负载。与 HTAP 在单引擎统一不同，LTAP 在存储层统一，为不同任务保留最佳引擎。

评论摘要
**主要讨论点：** LTAP（OLTP+OLAP统一架构）是否是真正的技术创新，还是只是现有方案的重新包装 **不同观点：** • **质疑派**（dsauerbrun, saisrirampur）：认为LTAP本质上只是通过缓存层实现，并非真正创新；怀疑单一存储引擎能否在性能上与专用的Postgres和ClickHouse竞敌；担心在高并发OLTP场景（50K+ tps）下格式转换无法跟上 • **支持派**（Avalaxy, dzonga）：认为消除CDC和ETL管道是游戏规则改变者；能用统一的Postgres接口处理分析和事务是重大突破；对热数据的实时分析能力有价值 • **技术实现讨论**（lmeyerov, ianberdin）：指出缺乏开放的LTAP写入协议标准，目前是专有方案；多家公司都在做基于S3的分块存储方案，但面临延迟、上行带宽（需5-10 Gbps）和对象存储可靠性挑战 • **实际应用担忧**（andrenotgiant, PunchyHamster, hasyimibhar）：如何处理历史数据追踪（SCD Type 2）；S3带宽成本可能很高；Postgres主版本升级时能否真正零停机 **补充讨论：** 技术趋势上OLAP数据库已走向Lakehouse架构，OLTP跟进是自然演进；但统一方案必然面临性能权衡，难以在所有场景下达到专用系统的最佳性能

Game Boy Advance Dev: Logging to the Console

作者: jandeboevrie | 评分: 16 | 评论数: 1 | 发布时间: 2026-07-04 17:12
文章摘要

这篇文章介绍了在mGBA模拟器中为GBA游戏添加控制台日志功能的方法。 **核心原理**：mGBA提供了三个特殊的内存映射寄存器（REG_LOG_ENABLE、REG_LOG_BUFFER、REG_LOG_SEND），通过向这些寄存器写入数据来实现日志输出。 **实现步骤**： 1. 向REG_LOG_ENABLE写入特殊值0xC0DE启用日志 2. 将日志内容写入REG_LOG_BUFFER 3. 向REG_LOG_SEND写入日志级别（ERROR/WARNING/INFO/DEBUG）触发输出 **实用技巧**： - 可封装成mgbalog()函数简化使用 - 支持printf风格的格式化输出 - 可从命令行查看日志（使用--log-level参数） - 建议通过MGBALOG宏定义控制，仅在开发时启用，避免增加最终版本的二进制大小和性能开销

评论摘要
主要讨论点：C语言宏定义的最佳实践——是否应该用 `do { } while (0)` 包装日志宏 不同观点： • **推荐做法**：无论启用或禁用状态，都应将宏包装在 `do { } while (0)` 中，使其在语法上等同于单条语句。这样可以避免空宏在条件语句中产生的孤立分号，防止触发编译器警告（如GCC的`-Wempty-body`警告），特别是在使用`-Wextra`或将警告视为错误的项目中 • **当前实现的问题**：如果禁用版本使用空宏替换，虽然在大多数情况下可以工作（留下一个独立的`;`），但存在潜在风险：①在`if`语句中会产生空语句体；②如果后续宏扩展为多条语句，会导致`if-else`结构断裂，`else`无法正确匹配`if` 补充讨论：作者强调这是"防御性建议"和"更符合惯例且面向未来"的做法，即使当前的空宏在简单的`mgbalog(...);`调用场景下可能不会出错，但统一使用`do-while(0)`模式是更安全和可维护的选择
