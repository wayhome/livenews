A Emoji Reverse Polish Notation Calculator Written in COBOL

作者: ghuntley | 评分: 7 | 评论数: 0 | 发布时间: 2025-07-06 00:57
文章摘要

这篇文章介绍了一个由GHuntley开发的COBOL项目，包含三种不同的计算器实现：基本计算器、逆波兰表示法（RPN）计算器和使用表情符号运算符的RPN计算器。项目展示了COBOL的现代特性，如表情符号支持和错误处理。 ### 主要功能： 1. **基本计算器**：支持四则运算，保护除零错误，交互式循环。 2. **RPN计算器**：基于堆栈的评估，支持复杂表达式和错误处理，附带全面测试套件。 3. **表情符号RPN计算器**：使用表情符号作为运算符，支持Unicode和彩色错误消息，带有成功庆祝标志（🎉）。 ### 使用方法： - 通过命令行编译和运行各个计算器。 - 提供测试套件和测试运行脚本以验证功能。 ### 项目结构： 包含多个COBOL文件和Shell脚本，用于实现和测试计算器功能。 ### 环境设置： - macOS上通过Homebrew安装GNU COBOL。 - Linux和Windows也有相应安装指南。 该项目展示了COBOL在现代计算中的应用潜力。

作者: rexpository | 评分: 296 | 评论数: 29 | 发布时间: 2025-07-08 17:46
文章摘要

文章指出Supabase MCP（Model Context Protocol）存在安全漏洞，可能导致整个SQL数据库泄露。具体而言，攻击者可以利用LLM系统中的"致命三要素"攻击——访问私有数据、执行恶意指令和外传数据。在Supabase场景中，Cursor助手使用高权限的`service_role`访问数据库，若攻击者提交包含恶意指令的 support ticket，可能诱导系统读取私有数据并外泄。虽然Supabase文档建议使用只读模式来降低风险，但作者认为应更明确警示此类攻击的潜在威胁。

评论摘要
主要讨论点：Supabase MCP中的提示注入问题及其解决方案和争议 不同观点： • gregnr（Supabase工程师）： - 已经采取了多项缓解措施，如默认设置为只读、在SQL响应外包裹提示以防止LLM执行注入指令，以及编写E2E测试以验证LLM不会受到攻击影响。 - 目前正在研究更多细粒度的权限控制和更多文档说明，以帮助用户了解攻击风险。 - 强调这些只是缓解措施，提示注入问题尚未完全解决。 • tptacek： - 认为提示注入问题类似于XSS攻击，是由于管理应用程序处理未经过滤的用户生成内容引起的。 - 将经典的XSS问题与LLM提示注入进行了类比，指出两者都是内部管理应用的常见问题。 • simonw： - 建议将数据库访问MCP配置为只读，以防止攻击直接损害数据。 - 强调要小心组合其他MCP，尤其是那些可以对外通信的MCP，以防止数据泄露。 • consumer451： - 引用了具体的攻击技术和提示示例，展示了攻击者如何通过精心设计的消息进行攻击。 • joshwarwick15： - 认为这些攻击本质上都是未受信任的输入、秘密和工具调用问题，MCP只是加速了影响的显现，但并非根本原因。 - 讨论了模型提供者和应用程序开发者在缓解此类攻击中的角色。 • pests： - 指出支持站点通常是许多攻击的载体，回顾了过去类似的攻击案例。 • sshh12： - 惊讶于这些类型的攻击在实际生产中并不常见，指出尽管这些攻击广为人知，但官方文档中并未明确提及。 • coderinsan： - 分享了在Neon DB MCP中发现的类似漏洞，表明这些问题并非Supabase独有。 • TeMPOraL： - 认为将LLM拟人化有助于理解其问题，指出LLM作为通用系统，其问题和不足是根本性的。 • yard2010： - 对cursor助手通过service_role操作Supabase数据库并绕过行级安全保护表示担忧。 • qualeed： - 质疑为何允许用户生成支持工单指令AI代理操作数据，认为这不应成为可能。 • akdom： - 指出MCP应用中缺乏更好的授权控制是关键问题，建议更细粒度的权限控制和动态调整以减少攻击面。 • borromakot： - 对LLM持乐观态度，但困惑于为何使用Supabase MCP时没有类似“开发沙盒”的凭据，仅访问开发/暂存数据。 - 对提示工程作为缓解措施感到困惑和不解。 • imilk： - 对Supabase的安全性表示担忧，基于过去一年未修复的开放认证问题。 • losvedir： - 对“致命三重奏”的框架表示不安，认为第三点不应仅限于数据泄露，恶意写入操作同样严重。 补充讨论： - 讨论的焦点在于如何有效缓解提示注入攻击，包括技术解决方案（如权限控制和文档说明）和概念性理解（如拟人化和问题本质）。 - 争议点包括MCP在加速攻击中的角色以及提示工程作为缓解措施的有效性。 - 多个评论提到了对官方文档和实际生产环境中安全措施的担忧。

Smollm3: Smol, multilingual, long-context reasoner LLM

作者: kashifr | 评分: 292 | 评论数: 16 | 发布时间: 2025-07-08 16:13
文章摘要

SmolLM3是一款小型、多语言、支持长上下文推理的30亿参数语言模型，性能超越Llama-3.2-3B和Qwen2.5-3B，并可与40亿参数模型竞争。该模型支持6种语言，采用Transformer解码器架构，结合了Grouped Query Attention、NoPE等技术以提升效率和长上下文表现。通过三阶段预训练方法和混合推理模式，SmolLM3在多项任务中表现出色。其完整工程蓝图和训练方法已在GitHub上发布，包括架构细节、数据混合策略和训练配置，为开发者提供了详细的指导。模型训练使用了384块H100 GPU，耗时24天。

主要讨论点：SmolLM3模型的性能、应用场景、技术细节及其在不同平台上的运行问题 不同观点： • WhitneyLand认为SmolLM3在3B参数级别中具有接近SOTA的性能，并且其完全公开模型、代码和训练方法的做法值得称赞，训练成本估计在百万美元左右。 • gardnr指出SmolLM3因其小尺寸和高效能在边缘设备和移动部署中具有重要意义，并强调其双模式推理和完全公开的训练方法。 • danielhanchen提供了关于如何在推理引擎上运行SmolLM3的具体技术指导。 • simonw在Mac设备上运行SmolLM3时遇到问题，使用Python和transformers在CPU模式下虽然能运行但速度很慢。 • _1关注哪些小型模型适合企业数据集的微调，特别是在浏览器和移动设备上运行而不依赖云资源。 • gdiamos建议继续开发50-100M参数模型，认为这些模型在CPU上快速完成任务的场景中有其价值。 • BarakWidawsky提到SmolLM3未应用自己的RL算法，而是通过在大型数据集上进行推理痕迹微调和从更大模型生成推理痕迹。 • msgodel认为SmolLM3接近Qwen3的缩小版，质量高，可能用于本地代理和代码补全，并计划检查最新的SOTA算法。 • eachro关注SmolLM3的微调难易程度，并与其他MoE LLMs进行比较。 • grrowl赞赏Huggingface在代码评估和Python工具上的坚持，认为未充分利用LLMs在编写和执行代码方面的能力。 • tiahura询问多语言支持对模型大小的影响。 • ivape关注SmolLM3与Llama 3.1 8b在成本上的比较，并指出3B模型在设备上的默认使用情况。 补充讨论： • cess11分享了对gemma3:4b模型的负面体验，指出其在代码处理和常识问题上的不足，并怀疑模型的可靠性。 • 多个评论提到了在不同硬件和软件环境下运行SmolLM3时遇到的实际问题和技术挑战，尤其是Mac设备上的兼容性问题。 争议焦点： • SmolLM3在实际应用中的性能表现和与其他模型的对比，特别是在代码处理和推理能力方面的优劣。 • 在不同平台和设备上运行SmolLM3的技术难题及其解决办法。

Zorin OS

作者: oldfuture | 评分: 76 | 评论数: 21 | 发布时间: 2025-07-08 15:37
文章摘要

Zorin OS 是一个为替代 Windows 和 macOS 设计的操作系统，旨在让电脑运行更快、更强大、更安全、更尊重隐私。它易于使用，提供类似 Windows 或 macOS 的桌面布局选项，适合老旧电脑，有助于延长硬件寿命并减少电子废物。Zorin OS 基于 Ubuntu 和 Linux，具有高可靠性和先进的病毒防护功能。它尊重用户隐私，不收集个人数据。系统自带必要应用程序，支持运行许多 Windows 应用程序，并提供丰富的游戏选择。通过 Zorin Connect，用户可以无缝连接安卓设备与电脑。Zorin OS 兼容多语言和各类文件，支持与 Windows 双系统启动，并提供辅助技术。用户可免费下载使用。
