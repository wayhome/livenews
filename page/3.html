文章摘要

本文介绍了名为Porffor的JS引擎/运行时，它能将JavaScript提前编译为WebAssembly和本地二进制文件，生成体积小（<1MB）、速度快（毫秒级）的可执行文件。相比Node和Bun等传统运行时，Porffor编译后的文件更小且执行速度更快（测试显示比Deno快59倍，比Bun快25倍）。作者还展示了Porffor在AWS Lambda上的性能表现，其冷启动速度比Node快12倍，比Amazon的实验性运行时LLRT快4倍，成本也更低。不过Porffor仍处于早期阶段，JavaScript支持有限且缺乏完善的I/O功能。作者邀请有兴趣的公司尝试Porffor，并公开了完整的测试数据和代码。

评论摘要
主要讨论点：[Porffor作为TS/JS到WASM/C的工具链的潜力及其在Lambda冷启动中的表现] 不同观点： • **支持Porffor的潜力** - Oliver的工作验证了Porffor的正确方向，未来12个月内可能有突破性进展。 - 通过WASM作为中间表示，带来了可移植性优势。 - 无GC的设计在某些场景（如Web请求）中可以通过进程复用或简单内存分配器实现高性能。 • **对Porffor实用性的质疑** - 实现完整的JS特性（包括Node API）是一项艰巨任务，可能难以主流化。 - 与其他工具（如Biome）类似，初期性能优势可能在实现完整功能后消失。 - 冷启动问题不仅仅是初始化时间，还包括数据库连接等状态初始化。 • **替代方案讨论** - 使用Golang等语言可以显著减少冷启动时间和运行时延迟。 - AWS Lambda可通过预留实例或优化现有Node功能（如V8代码缓存）来缓解冷启动问题。 - 提供WASM运行时选项可能进一步优化冷启动时间。 补充讨论： - **争议焦点**：Porffor是否能在保持性能优势的同时实现完整的JS/Node兼容性。 - **其他讨论点**： - WASMGC的出现可能解决无GC设计的限制。 - 冷启动问题在实际生产中的影响因使用场景而异，某些用户并未遇到显著问题。 - 类似工具（如GraalVM）的成功案例为Porffor提供了参考。
