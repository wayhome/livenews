Make ZIP files smaller with ZIP Shrinker

作者: zdw | 评分: 36 | 评论数: 7 | 发布时间: 2026-05-17 00:26
文章摘要

作者开发了 ZIP Shrinker，一个浏览器工具，用于压缩 ZIP 文件及其变体格式（APK、EPUB、JAR 等）。工作原理包括三步：(1) 使用 libdeflate 算法重新压缩文件以提高压缩率；(2) 删除所有元数据；(3) 移除目录条目。作者为此创建了 libdeflate.js 的 WebAssembly 封装。测试结果显示可节省 5-30% 的空间。该工具在保持向后兼容性的同时减小文件大小，可用于降低带宽和服务器成本。

评论摘要
主要讨论点：关于ZIP文件优化工具的功能设计和潜在问题 不同观点： • **工具推荐派**：lifthrasiir推荐ECT作为该领域最佳解决方案，认为它虽不流行但效果出色 • **删除空文件夹的强烈反对**：ChrisNorstrom明确反对自动删除空文件夹，强调这违反了程序设计的基本原则——绝不应在未告知用户的情况下自动删除内容。理由包括：用户保留空文件夹有其目的（结构、提醒、占位符），某些程序依赖特定文件夹结构才能正常运行 • **技术实现建议**：seritools认为删除空文件夹会不可避免地破坏功能，但建议排除这些文件夹不应太难实现 • **格式选择质疑**：akx质疑在Zstd时代是否还有必要使用.bz2格式的新归档文件 补充讨论： • billpg关注ZIP注释的元数据用途，认为保留的注释可能有其存在理由 • jurgenkesker指出APK文件需要zipalign处理，但工具未提及此功能 • stuaxo对该工具在docx文件上的效果表示好奇 争议焦点：自动删除空文件夹的设计决策，这是最激烈的讨论点。

Show HN: Hsrs – Type-Safe Haskell Bindings Generator for Rust

作者: suis_siva | 评分: 36 | 评论数: 3 | 发布时间: 2026-05-19 04:06
文章摘要

hsrs 是一个让 Rust 和 Haskell 之间实现类型安全互操作的 FFI 绑定生成工具。 **核心功能：** 通过在 Rust 代码中添加注解（如 `#[hsrs::data_type]`、`#[hsrs::value_type]`、`#[hsrs::function]`），自动生成 Haskell 绑定代码。工具处理内存管理、序列化和类型转换，将 Rust 的 `Result`/`Option`/`Vec`/`String` 自动映射为 Haskell 的 `Either`/`Maybe`/列表/`Text`。 **使用流程：** 1. 标注 Rust 代码 2. 运行 `hsrs-codegen` 生成绑定 3. 在 Haskell 中直接调用 支持不透明指针类型（通过 `ForeignPtr` 自动管理内存）、值类型（通过 Borsh 序列化）和枚举类型，提供类型安全的跨语言调用体验。

评论摘要
主要讨论点：Rust 与 Haskell 互操作工具的技术特性和生态影响 不同观点： • **技术改进建议**（yccs27）：关注类型系统互操作的深度，提出三个具体改进方向——为 Rust 库类型自动生成绑定、允许标记纯函数避免 IO 包装、以及在两种语言间转换类型类（type classes） • **性能与 GC 的权衡**（_flux）：指出类型安全语言间互操作的根本挑战在于垃圾回收机制的差异，以 ocaml-rs 为例说明 GC 会带来摩擦，认为如果不追求极致性能可能会更容易 • **生态扩展机会**（rienbdj）：从实用角度看待此工具的价值，认为可以利用 Rust 生态（特别是那些已有 Python 绑定的库）来扩展 Haskell 生态系统 补充讨论：三条评论代表了不同关注层面——类型系统设计细节、底层运行时兼容性挑战、以及生态系统战略价值，共同构成了对跨语言互操作工具的全面评估视角。

When can the C++ compiler devirtualize a call?

作者: lionkor | 评分: 68 | 评论数: 10 | 发布时间: 2026-05-17 08:58
文章摘要

这篇文章探讨了C++编译器何时能够去虚拟化（devirtualize）函数调用。主要有两种情况： **1. 已知实例的动态类型**：当编译器能通过数据流分析确定对象的确切类型时（如局部对象），可以去虚拟化。不同编译器的分析能力差异很大，GCC表现最好。 **2. 已知"叶子性证明"**： - 使用`final`关键字标记类或方法是最可靠的方式 - 内部链接的类（如匿名命名空间中的类）也可被优化，因为编译器知道它们不会在当前编译单元外被继承 现代编译器对`final`方法的去虚拟化较为可靠，但在复杂场景下各编译器表现不一。文章未涉及LTO（链接时优化）的全程序分析。

评论摘要
主要讨论点：C++虚函数去虚化（devirtualization）优化的可靠性、性能影响及与其他语言的对比 不同观点： • **悲观派**：去虚化优化过于脆弱且易出错。MSVC的LTO去虚化因bug和性能问题被禁用；应在性能关键代码中避免虚函数调用以确保性能 • **技术细节派**：去虚化存在复杂的边界情况。如clang的PGO去虚化与BOLT的ICF交互导致崩溃；C++中即使明确知道动态类型，placement new等机制也可能使优化失效 • **语言对比派**：其他语言处理更好。Java能在运行时有效去虚化单态调用点；Rust通过显式区分静态多态（泛型）和动态多态（dyn trait）避免了猜测，默认静态已知 • **质疑派**：现代C++代码较少使用继承，虚派发可能已不是主要问题 补充讨论： Rust的dyn trait去虚化行为不确定，可能由MIR或LLVM处理。有开发者认为Rust的显式动态性虽初期不便，但长期来看避免了对编译器启发式的依赖，提供了更可预测的性能特征。
