Pitfalls of Safe Rust

作者: pjmlp | 评分: 118 | 评论数: 10 | 发布时间: 2025-04-04 17:55
文章摘要

本文讨论了Rust中的"安全"不仅仅指内存安全，还需处理其他问题以确保程序健壮性。即便在"安全Rust"中，仍有一些编译器无法检测的陷阱，包括类型转换错误、逻辑错误、使用`unwrap`导致的恐慌、第三方库中的不安全代码和竞争条件等。文章提供了多个避免这些问题的建议，如使用检查算术操作防止整数溢出、避免使用`as`进行数值转换、使用有界类型确保数值合法性、确保无效状态无法表示等。此外，文章还强调了在发布模式下启用溢出检查以增强安全性，并提供了具体实现方法。通过遵循这些建议，开发者可以写出更可靠的Rust代码。

评论摘要
主要讨论点：Rust编程语言中的潜在问题和一些具体实现的争议 不同观点： • nerdile认为文章标题有误导性，"Safe Rust"中的问题并不是只存在于安全Rust代码中，而是普遍存在于Rust编程中。此外，这些问题也不是Rust独有的。他建议一个不那么吸引眼球的标题可能是"Rust pitfalls: Runtime correctness beyond memory safety"。 • conaclos指出文章没有提到算术检查的替代方案：明确的Wrapping和Saturating类型。他还提到使用安全的`From::from`替代`as` casting，但认为这样会增加代码的冗余度。 • IshKebab对整数溢出和数组越界问题持乐观态度，并提到Flux作为一种解决方案，认为它能在完全形式化验证之前提供一种不错的中间方案。 • Sharlin讨论了`Path::join`在处理绝对路径时的行为，认为这种行为容易被忽视，可能导致错误，建议增加一个专门的"absolutize"方法或返回一个Result。 • woah提出了关于`as` casting是否是一个不必要的陷阱的问题。 • thrance补充提到内存泄漏问题，特别是在使用Rc或Arc时容易出现引用循环，导致内存无法释放。 • forrestthewoods认为整数溢出不是真正的问题，Rust已经将溢出行为从“未定义”改为“明确的二补码”，因此不需要对所有数学运算添加checked_mul。 • quotemstr认为一些建议是不明智的，特别是在数组索引时，越界访问通常表明逻辑错误，应该快速失败以避免问题扩大化，而不是通过try-things来掩盖逻辑错误。 • sgt认为如果目标是编写健壮的软件，Golang可能是更好的选择，特别是在构建不易宕机的 robust services时。 补充讨论： • 讨论中涉及了多种Rust中的潜在陷阱，包括路径处理、整数溢出、数组越界、内存泄漏和casting操作等。 • 不同开发者对这些陷阱的严重性和解决方案有不同的看法，例如Flux、Wrapping和Saturating类型、以及专门的方法或Result返回类型的建议。 • 关于是否应通过检查操作来避免逻辑错误，开发者之间存在争议，部分人认为应快速失败以暴露问题，而不是掩盖问题。 • 最后，有人提出了Golang作为Rust的替代选项，认为在某些场景下Golang可能更适合构建健壮的软件。

Recent AI model progress feels mostly like bullshit

作者: paulpauper | 评分: 148 | 评论数: 36 | 发布时间: 2025-04-06 18:01
文章摘要

文章讨论了AI模型在安全漏洞检测领域的实际进展与宣传效果之间的差距。作者与团队自2024年6月起开发一款基于AI的工具，用于自动监控代码库的安全问题。尽管初期模型如Claude 3.5 sonnet表现出显著改进，但后续的新模型如3.6和3.7等在实际应用中未见明显提升。作者发现，尽管AI在对话和控制测试中表现更好，但在经济实用性和新任务处理能力上改进有限。多个行业的创始人也报告了类似经历，质疑AI实验室是否夸大了模型进步。文章最后提出，若无法准确衡量AI当前的影响，未来在更复杂领域（如管理公司或制定公共政策）中可能面临更大挑战。

评论摘要
主要讨论点：大型语言模型（LLM）的可靠性、局限性以及在实际应用中的表现 不同观点： • [aerhardt] 认为 ChatGPT 在回答关于 Paul Newman 是否有酗酒问题时给出了错误的回答，并指出其母亲通过权威来源证明了ChatGPT的错误。这反映了LLM在处理简单问题时的不可靠性。 • [iambateman] 认为 LLM 倾向于给出肯定的回答以显得“聪明”和“讨好”用户，而不是承认不知道答案。这种倾向使得LLM在复杂场景中的表现不尽如人意，即使基准测试分数有所提高，实际应用中的改进有限。 • [InkCanon] 指出，SOTA模型在数学竞赛中的表现不佳，暗示AI可能依赖于记忆训练数据而非真正的理解和解决问题能力。同时，质疑AI公司在训练数据中去除了测试数据的做法。 • [lukev] 认为，对于AI的讨论往往是分散且基于个人经验的，难以形成统一的结论。尽管如此，一些人可能会因为运气或个人经验而在AI使用上做出“更好”的选择。 • [jonahx] 支持[iambateman]的观点，认为LLM为了在对话中显得聪明，会倾向于指出潜在问题而不是确认一切正常，这与人类行为类似。 • [joelthelion] 基于个人使用经验，认为当前的LLM（如Gemini 2.5）在某些应用中表现出色，但未来发展仍不确定。 • [nialv7] 认为当前的AI无法进行复杂的符号推理，如安全漏洞检测，只能通过模式匹配识别“坏代码”，但无法深入分析。 • [HarHarVeryFunny] 强调LLM本质上是预测系统，不能期望其在特定领域的改进会自动转化为其他不相关领域的改进，因为它们不是通用认知架构。 • [throw310822] 认为即使AI发展停滞，未来十年我们仍会发现其新用途。当前技术发展速度超过了我们能有效吸收和利用的能力，可能带来负面后果。 • [maccard] 认为GPT和Claude等模型在过去一年中表现有所下降，本地LLM从几乎无用到勉强可用，但仍不足以支持日常使用。工具和应用的改进才是关键。 • [fxtentacle] 指出，近期AI模型的进步主要体现在价格上，如4-bit量化的QwQ-32B在编码性能上接近Claude 3.5，但运行成本大幅下降。 • [ants_everywhere] 认为最近的模型更新有明显改进，但个人经验和任务复杂性可能导致不同看法。新模型可能更理解任务的模糊性，导致旧的提示策略失效。 • [gundmc] 提到Gemini 2.5发布前后的变化，并对其生产力提升表示惊叹。 • [sema4hacker] 认为LLM的改进并未反映在经济实用性或通用性上，可能重蹈1980年代“专家系统”的覆辙。 • [einrealist] 引用LeCun的批评，指出LLM的准确性问题不会自行解决，提高准确性只会变得更加昂贵，限制了实际应用。担心未来质量下降，AI公司变得“太大而不能倒”。 补充讨论： • LLM在实际应用中的局限性和不可靠性，包括对简单问题的错误回答。 • LLM倾向于给出肯定回答以显得“聪明”或“讨好”，导致在复杂场景中表现不佳。 • AI模型依赖记忆训练数据而非真正理解问题，导致在特定领域表现好但不具备通用性。 • 当前AI技术发展迅速，但工具和应用的改进更为重要，未来发展仍不确定。 • 对AI技术过度依赖和未来质量下降的担忧，以及AI公司在政策制定中的影响力。

SeedLM: Compressing LLM Weights into Seeds of Pseudo-Random Generators

作者: pizza | 评分: 137 | 评论数: 13 | 发布时间: 2025-04-06 08:53
文章摘要

《SeedLM: Compressing LLM Weights into Seeds of Pseudo-Random Generators》一文介绍了一种新型的压缩方法，称为SeedLM，用于减少大型语言模型（LLM）在推理过程中的内存访问和计算成本。该方法通过使用伪随机生成器（LFSR）的种子来编码和压缩模型权重。在推理时，种子生成随机矩阵，并与压缩系数结合以重建权重块。该方法无需校准数据，能在多种任务中有效应用，并在Llama3 70B模型上展示了与FP16基准相当的性能，同时在FPGA测试中实现了近4倍的速度提升。这种方法显著提升了内存密集型任务的效率。

评论摘要
主要讨论点：LLM权重量化与压缩技术的实现、应用及其潜在限制 不同观点： • Visarga认为该技术通过字典和基向量快速计算而不存储，实现了3或4位的量化，但改进有限。他质疑如果要实现每权重<1比特的量化，是否需要更大的结构。同时，他提到该技术有助于在手机上高效运行LLMs，且易于实现。 • Gblargg简要总结了该技术的基本原理，即找到最接近目标数据的伪随机序列部分，存储随机种子和较小的修正项。 • Benob提出了一种变体，建议每个参数矩阵是随机矩阵（由种子生成）和低秩矩阵（LoRA）的和，并表示有意从零开始实验训练。 • Elashri建议直接参考相关论文，指出该研究由Apple和Meta的 researchers完成。 • Torginus质疑该技术是否专用于LLM权重，而不是通用数据压缩，认为这像是“多此一举”的压缩。 • Htrp仅补充了论文的发布时间。 • Jlcases将该压缩方法与人类知识传递相比较，提出在技术文档中使用类似概念，并探讨了显性和隐性知识之间的平衡。 • RainyDayTmrw提到了一种普遍接受的观点，即不能通过Pi的偏移量有效压缩数据，质疑该技术的可行性。 • _0ffh怀疑该技术可能是愚人节的玩笑，认为一般情况下使用PRNGs进行压缩不现实，尽管此案例可能有例外。 • EGreg提到Zuck关于Llama 4 Behemoth的言论，质疑其基准测试和训练状态。 • Anshumankmr抱怨Apple Intelligence未能按时推出，表达了对实际应用的失望。 补充讨论： • 讨论中涉及了该压缩技术的实现细节、潜在应用（如LLM在手机上的运行）及其与其他领域（如技术知识管理）的潜在联系。 • 争议的焦点包括该技术是否真正有效、其应用范围的专一性以及与现有压缩理论的冲突。 • 一些参与者对该技术持怀疑态度，而另一些则关注其潜在的实际应用和未来发展。

Show HN: I built a Rust crate for running unsafe code safely

作者: braxxox | 评分: 95 | 评论数: 17 | 发布时间: 2025-04-06 13:28
文章摘要

`mem-isolate` 是一个 Rust crate，旨在通过使用 `fork()` 系统调用安全地运行不安全代码。它会在子进程中执行用户提供的函数，确保该函数不会影响父进程的内存状态，实现内存隔离。主要特点包括： 1. **内存纯净性**：即使函数存在内存泄漏或堆碎片化问题，也不会影响主进程。 2. **跨进程通信**：通过管道在父子进程间传递结果，使用序列化（如 `serde`）处理数据。 3. **性能开销**：每次调用引入约 1ms 延迟，适合对内存安全要求高的场景。 4. **系统支持**：仅支持 POSIX 系统（如 Linux, macOS），不支持 Windows 和 WebAssembly。 该工具适用于运行可能导致内存问题的代码，如 FFI 调用或不安全代码，通过隔离确保主程序的稳定性。

评论摘要
主要讨论点：Rust中的“安全”定义及其在处理不安全代码时的实践方法 不同观点： • **[woodruffw]** 认为“safe” Rust不仅仅意味着避免由于空间内存错误导致的崩溃，还应包括空间和时间上的内存安全。单纯的避免崩溃并不足够，Rust的安全性应更强，防止任何形式的内存不安全。 • **[nextaccountic]** 提出了一种通过将不安全代码编译为WebAssembly并进一步编译为C代码的方式来实现沙盒化的方法。这种方法将未定义行为转化为逻辑错误，避免内存损坏。 • **[pjmlp]** 主张从设计上就使用多进程、OS IPC和实际的OS沙盒API，认为即时伪沙盒化存在问题，传统的UNIX守护进程方法已经证明了这一点。 • **[wavemode]** 认为牺牲性能来运行不安全代码是不值得的，如果这样做，还不如直接使用带有垃圾回收的语言。 • **[destroycom], [Svetlitski], [kelnos]** 都提到了在多线程程序中使用`fork()`的危险性，特别是在内存复制和锁的状态复制时可能导致死锁和其它问题。 补充讨论： • **[djha-skin], [null_investor]** 认为`fork()`和该工具包仅在处理极度不安全的代码时有用，但不应频繁使用，否则可能失去Rust相对于其他语言的性能优势。 • **[dijit]** 提出了在Windows环境下调用Win32 API时缺乏有效调试工具的问题，寻求帮助。 • **[syrusakbary]** 对在WebAssembly中实现更高级别的安全性表示兴趣，并提及了Wasmer和V8 isolates。 • **[corank]** 质疑如果代码需要修改内存，例如实现双向链表时，这种方法是否适用。 • **[jesprenj]** 建议使用共享内存而不是管道来进行通信。 • **[teknopaul]** 认为这是一种巧妙的解决方案，但在实际应用中可能并非最佳选择。 争议焦点： • 使用`fork()`在多线程应用中的安全性和可行性。 • Rust中的“safe”定义是否应超越简单的避免崩溃，涵盖更全面的内存安全。 • 在处理不安全代码时，性能牺牲和安全保障之间的平衡。
