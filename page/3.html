Benchmarking SurrealDB 3.x vs. Postgres, Mongo, Neo4j and Redis (With Fsync)

作者: itsezc | 评分: 61 | 评论数: 5 | 发布时间: 2026-05-29 14:53
文章摘要

SurrealDB 3.x 性能基准测试报告显示了显著提升。测试在相同硬件（AMD Threadripper 9970X，128GB内存）上进行，所有数据库均启用完全持久化（fsync开启）以确保公平对比。 **核心改进：** - 相比2.x版本，CRUD吞吐量提升31%，全表扫描快11,894%，索引查询快136% - 混合CRUD达到141k ops/s（1.x仅78k） **对比主流数据库：** - 写入吞吐量超PostgreSQL 52%，超MySQL 482% - 读取略低于Postgres但优于MySQL - 全表count查询比Postgres快50%，比MySQL快250% 测试使用开源工具crud-bench，针对500万-1500万行混合数据类型记录，128客户端并发。所有配置文件已开源可审计。

评论摘要
主要讨论点：关于数据库性能基准测试的可信度和实用性 不同观点： • **测试透明度不足**（pgaddict）：批评基准测试缺乏关键细节，如具体的数据库版本（Postgres 14还是18？）和配置参数。举例指出WAL设置为2-16GB但不知数据集大小，认为应该清晰记录各数据库的参数配置，而非让用户自己去源码中查找。 • **许可证问题**（llimllib）：指出SurrealDB的文档存在误导，声称"开源"但实际使用BSL许可证，应该称为"源码可用"而非真正的开源。 • **实用性质疑**（PunchyHamster）：认为50%的写入性能提升但读取慢25%的权衡不值得，因为读取通常是主要工作负载。质疑为何要放弃PostgreSQL成熟的生态系统。 • **基准测试本质缺陷**（redwood）：指出基准测试具有根本性误导性，不仅因为可调参数使对比不公平，更重要的是不同引擎的优化涉及不同权衡、数据模型和索引策略，难以真正做到同等比较。 补充讨论：评论整体对该基准测试持批评态度，从方法论、透明度、实用价值等多角度质疑其可信度。

Decades of Effort Restore Steelhead and Salmon Passage on Alameda Creek

文章摘要

经过近30年的努力，加州阿拉米达溪（Alameda Creek）最后一道鱼类洄游障碍被清除。该项目由加州鳟鱼协会和太平洋燃气电力公司在NOAA资助下完成，迁移了天然气管道并恢复了河道。这条溪流曾是旧金山湾最大的钢头鳟和奇努克鲑鱼产地，但自1967年起鱼类无法到达上游产卵地。如今，受威胁的中加州海岸钢头鳟50年来首次能够自由洄游至上游栖息地。该项目清除了沿溪18处障碍，为恢复这一重要鱼类种群带来希望。

评论摘要
主要讨论点：关于恢复鲑鱼通道和栖息地保护项目的多角度讨论 不同观点： • **技术实施角度**（chihuahua）：提到华盛顿州I-90公路下类似的鱼类通道恢复工程，强调在州际公路下恢复河床是重大工程。特别关注Kokanee Salmon（陆封型鲑鱼）的保护，指出Lewis Creek目前仅有半英里可通行区域，但2021年仍有约1000条鱼回流产卵。 • **政策支持角度**（Shalomboy）：赞扬NOAA栖息地保护团队的工作，认为鱼梯是对近海渔业未来的优秀投资，但表示向公民和企业传达这一价值存在困难。 • **生态疑问**（Dansvidania）：提出关键生态问题——鲑鱼会回到出生地产卵，那么通道被切断后，该区域的鲑鱼种群如何维持？是否需要人工重新引入，还是原有种群会持续尝试回归？ • **信息透明度质疑**（burner420042）：质疑为何报道中提到"湾区基金会"却不公开具体名称，对这种报道惯例表示不解。 • **休闲推广角度**（kiernanmcgowan）：从个人爱好出发，推荐飞钓运动，强调与自然互动的乐趣。 • **企业责任认可**（anenefan）：肯定PG&E等大公司参与恢复鱼类繁殖地，认为即使是双赢局面也值得赞赏。 补充讨论：评论中未出现明显争议，整体氛围积极，但Dansvidania提出的生态恢复机制问题未得到解答，这是讨论中的知识空白点。

The SLAX Scripting Language: An Alternate Syntax for XSLT

作者: thefilmore | 评分: 27 | 评论数: 5 | 发布时间: 2026-05-30 08:00
文章摘要

SLAX是XSLT的替代语法，旨在解决XSLT基于XML语法难以阅读和编写的问题。它借鉴了PERL和C的语法风格，将XSLT的核心概念提升为一级语言结构，使脚本开发和维护更加容易。 libslax是SLAX的开源实现，基于libxslt和libxml2构建，可以解析执行SLAX文件并在SLAX和XSLT之间转换，还包含调试器和性能分析器。该项目最初由Juniper Networks为JUNOS操作系统开发，采用BSD许可证发布。 文档涵盖了SLAX语言概述、语句参考、内置函数、以及libslax工具集的使用说明。

评论摘要
主要讨论点：关于SLAX（XSLT的简化语法）是否有实际价值 不同观点： • **质疑合规性**（codeulike）：认为SLAX可能违反XML官方规范，尽管声称更易开发维护 • **怀疑实际改进**（pitched）：从文档示例来看，SLAX与标准XSLT几乎相同，看不出明显优势 • **时代价值论**（nullorempty）：过去微小改进有价值，但现在需要重大创新才值得引入新方案；认为LLM将擅长编写标准XSL，降低了简化语法的必要性 • **工具生态问题**（petesergeant）：承认语法更简洁，但指出XSLT用户已深度依赖IDE和配套工具链，切换到新语法无法解决实际问题 补充讨论：核心争议在于**增量改进的必要性** —— 是否值得为了语法简化而引入新标准，特别是在已有成熟工具链和AI辅助编码的背景下。多数评论持保守态度，认为收益不足以抵消学习和迁移成本。

Blorp Language

作者: croottree | 评分: 53 | 评论数: 12 | 发布时间: 2026-06-01 07:35
文章摘要

Blorp是一门追求低摩擦、高性能的编程语言。核心特性包括：纯函数与显式副作用分离、值语义配合ARC/COW优化、类型化的Option/Result错误处理、结构化并发、编译期边界检查。语法简洁易读，采用缩进和关键字操作符。编译到C语言生成原生代码，性能接近手写C，在多数基准测试中优于Go和Python。使用Hindley-Milner类型推导和Perceus所有权分析，兼顾安全性与执行效率。设计目标是让代码可信、快速、易上手且持久可维护。

评论摘要
主要讨论点：对 Blorp 编程语言设计选择的评价，特别是语法风格和语言特性 不同观点： • **支持简洁语法**：有人认为语法类似 Ruby/Python 的现代化版本，看起来不错，像"C 语言的 CoffeeScript" • **反对强制缩进**：认为可读语法配合强制缩进是个问题，结束标记应该明确而非依赖缩进缺失，缩进应由格式化工具处理；复制粘贴代码时会有问题 • **反对链式调用语法**：指出链式调用在 Java Stream 和 TypeScript 中已证明是陷阱，容易从 O(n) 变成 O(2n)；"第一参数原则"允许 `func(x)` 和 `x.func()` 两种写法会导致混乱 • **反对隐式返回**：不喜欢自动返回最后一条语句，难以看出函数在哪里返回，guard clause 实现会很别扭 • **反对 `pure` 关键字设计**：质疑为何 `pure` 需要显式标记而默认是 impure，这会阻碍程序员标记纯函数；建议学习 Nim 用 `func`(纯)/`proc`(非纯)区分 补充讨论：有人希望看到更多创新实用的想法而非个人偏好的变体，并分享了针对无状态 Web 服务优化的语言设计构想；另有人询问内存模型是否类似 Rust；还有关于"Blorp"名称来源的趣味讨论

Using Git's rerere feature to escape recurring conflict hell

作者: ankitg12 | 评分: 39 | 评论数: 5 | 发布时间: 2026-06-01 07:06
文章摘要

这篇文章介绍了 Git 的 `rerere` 功能（Reuse Recorded Resolution，重用已记录的解决方案）。当合并分支时遇到重复的冲突，`rerere` 可以记住你之前如何解决冲突，并在相同冲突再次出现时自动应用相同的解决方案。 启用方法：运行 `git config --global rerere.enabled true` 工作原理：首次遇到冲突时，`rerere` 会记录冲突状态和你的解决方式。当相同冲突再次出现时，Git 会自动应用之前的解决方案，无需手动处理。这大大减少了在合并或变基过程中反复解决相同冲突的痛苦。

评论摘要
主要讨论点：Git 分支合并策略和冲突处理的最佳实践 不同观点： • **单向合并+rebase策略**（dools）：只在一个方向合并（向main合并），在feature分支上rebase以避免静默回归。规则是"远离main时rebase，朝向main时merge"，所有冲突都在分支上通过rebase解决，从未在main上遇到冲突或静默回归问题。 • **严格的分支层级流程**（adithyassekhar）：认为开发者之间不应直接合并分支，只从master拉取已完成的代码。如果有多环境，应遵循单向流程：feature > dev > staging > master，避免跨级合并。强调这是规划问题而非技术问题。 • **配置优化派**（0123456789ABCDE 和 davidelettieri）：通过Git配置提升体验，推荐启用rerere（自动记住冲突解决方案）、pull.rebase、autoSquash、zdiff3冲突样式、autoSetupRemote等选项。 补充讨论：cautiouscat表达了对Git复杂性的感慨，反映出即使有经验的开发者也持续在学习Git的高级特性。讨论整体聚焦于通过工作流规范和工具配置来预防问题，而非事后处理。

评论摘要
主要讨论点：AV2视频编解码器的发布及其性能特点 不同观点： • **性能担忧派**：AV2解码复杂度是AV1的5倍，仅25%的压缩率提升不值得淘汰所有现有AV1硬件解码设备，软件解码在现有硬件上难以实时运行 • **技术乐观派**：编解码标准的设计理念值得肯定——专注于定义解码规范而非编码方式，为编码创新留出空间；期待看到低码率下与AV1的对比测试 • **实用主义派**：优先支持SSSE3+等较老桌面芯片的汇编优化，而非仅关注AVX2，因为媒体消费设备升级压力小于工作站 补充讨论： 多条评论反映网站因HN流量过载返回429错误；有人提及编解码标准需要至少一个现场实现的解码器才算完成，现场实现往往成为事实标准；少数离题评论涉及名称相似的其他主题（Dave2D、D4vd等）
