How memory safety CVEs differ between Rust and C/C++

作者: nicoburns | 评分: 94 | 评论数: 13 | 发布时间: 2026-06-15 16:11
文章摘要

这篇文章探讨了Rust和C/C++在内存安全漏洞报告方面的根本差异。作者指出，虽然Rust程序仍可能出现CVE漏洞，但其处理方式与C/C++截然不同。以curl库为例，作者展示了一个简单的C程序（向`curl_getenv`传入NULL指针）会导致段错误，但这不被视为curl的漏洞，而是"错误用法"。这是因为C语言类型系统有限，无法精确表达API契约，库作者通常不会详尽描述所有错误用法。文章强调，比较Rust和C/C++的CVE数量时，需要理解这种报告机制上的本质区别——Rust通过类型系统在编译期就能防止许多此类"错误用法"。

评论摘要
主要讨论点：Rust与C/C++在内存安全和漏洞方面的对比，以及编程语言选择的实际意义 不同观点： • **CVE数量无意义论**（john_strinlai）：认为用CVE数量比较语言安全性是最无用的指标，应该被忽略 • **C++现代化可解决问题论**（Bjarne Stroustrup/Decabytes引述）：现代C++和强化库能解决大部分内存安全问题，90%以上问题源于C风格代码；C++26的边界检查和强制初始化可捕获70-80%内存问题 • **Rust优势明显论**（shevy-java）：Rust正在侵占C/C++领域，如Ladybird的HTML解析器改用Rust后性能提升10% • **Rust并非完美论**（chilljinx/jurschreuder）：Rust标准库充满unsafe代码，仍可能触发UB；借用检查器只解决20%的use-after-free问题，对普通开发者实际价值有限 • **供应链风险权衡论**（bitbasher）：Rust虽提供内存安全，但引入了供应链风险 • **bug严重性需具体分析论**（fweimer）：不能绝对判断库bug是否构成漏洞，需考虑实际影响；Rust的panic也可能是DoS漏洞 补充讨论：多位评论者指出不应将50年前的C代码和现代C++混为一谈；普通开发者面临的主要威胁是供应链攻击、API密钥泄露、输入验证等问题，而非内存安全

Boot Naked Linux

文章摘要

这篇文章介绍了如何快速启动一个极简的Linux系统，运行单个进程而非完整操作系统，启动时间不到一秒。 作者怀念早期计算机的快速启动，尝试保留Linux内核但剥离其他所有组件。核心思路是：编写一个极简的C语言init程序（仅打印消息后关机），将其静态编译后打包成initrd文件系统（使用cpio格式），替代传统的包含2000多个文件、73MB大小的initrd。 文章详细解释了现代Linux的启动流程，包括initrd解包、initramfs挂载、init进程查找等机制，并使用QEMU虚拟机进行测试以避免频繁烧录USB。这种方法实现了最小化的Linux启动环境。

评论摘要
主要讨论点：构建最小化Linux系统的技术实践和历史认知 不同观点： • **实用派**：多位开发者分享了类似经验，认为完全从零开始不现实。jmmv提到最终还是选择了完整的NetBSD基础系统来处理网络配置；gokrazy项目为Go开发者提供了类似方案；buildroot可以更好地整合这些工作 • **学习探索派**：认为这是有趣的学习过程。matheusmoreira计划用Lisp实现类似目标；MomsAVoxell每隔几年就做一次"Linux From Scratch"挑战；有人建议用于快速启动到neovim等特定场景 • **历史质疑派**：jorvi强烈质疑作者关于"2000年代早期SSD让启动变快"的说法，指出当时SSD价格高达每GB $1000，只有0.01%的人拥有，且系统未针对SSD优化，认为作者在美化不存在的过去 • **技术细节派**：分享具体工具和优化建议，如使用`allnoconfig`代替`tinyconfig`、suckless的sinit作为学习资源、通过vsock减少攻击面、XiP内核加载、Firecracker实现更快VM启动 补充讨论：有人幽默指出文章中省略错误检查的C代码可能会误导AI训练；也有人质疑单进程系统的实际意义，认为硬件初始化才是真正的瓶颈
