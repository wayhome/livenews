Censors Ignore Unencrypted HTTP/2 Traffic (2024)

作者: ArinaS | 评分: 35 | 评论数: 4 | 发布时间: 2025-04-14 18:23
文章摘要

文章主要探讨了使用未加密的HTTP/2协议绕过 censorship 的可能性。研究发现，在中国和伊朗，未加密的HTTP/2流量未被审查，可通过此方法访问被封锁的网站。尽管没有任何浏览器直接支持未加密的HTTP/2，研究检测到最多6.28%的网站支持这种协议。文章介绍了两种建立HTTP/2连接的方法：直接使用HTTP/2（Prior Knowledge）和通过HTTP/1.1升级（Upgrade Mechanism）。由于HTTP/2采用二进制格式，与文本格式的HTTP/1.1相比，解析难度增加，导致审查系统未能有效拦截。文章还提供了一种工具来检测网站是否支持未加密的HTTP/2。然而，作者提醒不要通过未加密的HTTP/2传输敏感数据，因为存在被窃听的风险。这一发现为规避网络审查提供了新的技术手段。

主要讨论点：关于研究中提到的问题是否容易被修复以及加密在通信中的作用 不同观点： • **puttycat的观点**：认为该研究中提到的问题可能在报告发布后十分钟内就被修复了。这暗示问题并不严重，或者很容易被解决，表现出对问题持久性的怀疑态度。 • **userbinator的观点**：提出可以在请求和响应体中使用（可能是混淆过的）TLS连接，从而创建另一种隧道方法。这个观点关注在通过技术手段绕过潜在的监控或限制，强调了技术对抗的可能性。 • **Naru41的观点**：认为ASCII和二进制在实际应用中没有本质区别，并且由于没有未加密的HTTP/2流量，因此没有 censorship 的动机。这个观点质疑了讨论中某些技术细节的重要性，并对 censorship 的实际需求提出质疑。 • **exabrial的观点**：强烈支持需要未加密的QUIC模式，理由是“特洛伊木马”也可以被好人利用。这个观点暗示了在某些情况下，未加密通信可能有其正当用途，尤其是在对抗恶意软件或进行安全测试时。 补充讨论： • 争议的焦点在于是否需要未加密的通信模式，特别是exabrial和Naru41之间的观点对立。前者认为未加密模式有其价值，而后者则认为加密通信已经足够普及，未加密通信没有实际需求。 • 另一个值得注意的讨论点是userbinator提出的技术绕过手段，这表明在加密和监控的博弈中，技术专家不断寻找新的方法来隐藏或保护通信。 • puttycat对问题修复速度的评论则反映了对安全问题实际影响和持久性的不同看法。

Show HN: Zero-codegen, no-compile TypeScript type inference from Protobufs

作者: 18nleung | 评分: 88 | 评论数: 15 | 发布时间: 2025-04-14 15:41
文章摘要

`protobuf-ts-types` 是一个用于从 Protobuf `message` 自动推断 TypeScript 类型的工具，无需代码生成和编译。它通过利用 TypeScript 的模板字面量类型实现类型推断，支持从 Protobuf 定义的 `message` 结构中提取类型信息。用户可以在 TypeScript 中直接使用这些推断出的类型，并获得类型检查的支持。该工具目前处于概念验证阶段，存在一些限制，例如不支持 `service`、`rpc`、`oneof`、`map` 以及 `import` 等特性。使用时需要通过 npm 安装，并将 Protobuf 定义作为字符串传递给工具进行类型推断。

评论摘要
主要讨论点：TypeScript 中高级类型系统及其应用，特别是使用类型来处理类似 Protobuf 的功能 不同观点： • mubou 认为，这种利用 TypeScript 类型系统实现复杂功能的做法非常惊人，但他质疑这是否是将精力用在了正确的地方，因为 TypeScript 正在将类型系统变成一种图灵完备的元语言，而不是用更合适的静态类型语言替代 JavaScript。 • jitl 强调了 TypeScript 类型的灵活性，但认为在生产环境中使用这种复杂类型系统会降低编译速度，因此更倾向于使用 TypeScript 生成 Protobuf 的定义，因为 TypeScript 的类型系统比 Protobuf 更强大且更具组合性。 • mherkender 对高级类型系统持批评态度，认为它们逐渐演变成了一种独立的语言，导致编译速度慢、错误信息混乱且缺乏调试工具。 • spankalee 希望 TypeScript 能增加对标记模板字面量的类型推断功能，以便在 lit-html 中实现类型安全的模板，并提到相关 issue，但指出该 issue 最近没有太多进展。 • throwanem 对编译错误产生的效果感到兴奋，认为这种复杂的 Protobuf 处理方式会生成有趣的编译错误。 • mifydev 提出这种方法是否可以用于 TypeScript 中的 schema 生成，并表示希望在 Typeconf 项目中直接加载 Typespec 而不是通过转换步骤。 • pragma_x 赞赏 TypeScript 通过类型系统实现类似 PEG 解析器的功能，并对作者的实现表示钦佩。 • aappleby 以幽默的方式表达了对 TypeScript 开发者展示技术能力的赞赏。 • catapart 和 jillyboel 对项目的酷炫程度表示赞赏，但 jillyboel 担心性能问题，建议使用 codegen。 • recursive 指出该方法需要将整个 `.proto` 声明内联在源码中，并提到 TypeScript 无法导入非 JavaScript 内容的问题，认为这可能需要额外的构建依赖或手动同步 `.proto` 文件。 • meindnoch 调侃 TypeScript 似乎在羡慕 Swift 的编译速度。 • tim1994 认为这种方法仅限于内联字符串字面量，无法读取文件，质疑其在实际数据交换场景中的应用价值，认为这可能只是一个有趣的玩具项目。 • porridgeraisin 期待相关 issue 得到解决，认为这将使该方法能够从文件中解析内容，从而更加实用。 补充讨论： - 高级类型系统在实际应用中的优缺点，特别是在生产环境中的性能和可维护性问题。 - TypeScript 类型系统的灵活性和强大性，以及其在不同场景下的应用潜力。 - 对未来 TypeScript 功能改进的期望和当前存在的技术限制。

本文介绍了Janet语言中基于Parsing Expression Grammars (PEGs) 的解析引擎的实现。作者受到REBOL和LPeg的启发，选择在Janet中加入PEG解析库，而排除了正则表达式等其他解析工具。PEG比正则表达式更通用，且能捕获错误位置。Janet的基本数据结构和解释器的简单性使得PEG引擎的开发非常顺利。 文章简要介绍了PEG的基本概念，如选择操作符（+）、序列操作符（*）和布尔反转操作符（!）。通过这些操作符和递归，PEG可以表达复杂的上下文无关语法。文章还展示了一个简单的PEG匹配函数，该函数用Janet实现，但可以轻易翻译为其他语言。最终的实现虽不支持捕获等高级功能，但展示了PEG解析的基本原理和应用。

Monte Carlo Crash Course: Sampling

文章摘要

本文简要介绍了蒙特卡罗方法中的采样技术，特别是拒绝采样法。首先，文章指出计算机通过伪随机数生成器（PRNG）生成看似随机的数列，这些数列在均匀性、独立性和非周期性上接近真正随机数。PRNG生成均匀随机标量，通过简单算法可以扩展到复杂、高维分布的采样。 文章详细介绍了**均匀拒绝采样**：在一个简单区域 $D$ 内生成样本，并通过一个接受函数筛选出属于目标区域 $\Omega$ 的样本，从而得到 $\Omega$ 内的均匀样本。文章还推导了该采样方法的概率密度函数（PDF），证明其在 $\Omega$ 上的均匀性。 接着，文章讨论了**非均匀拒绝采样**，适用于非均匀分布。通过设定一个上界 $c$，并以 $\frac{f_\Omega(\mathbf{x})}{cf_D(\mathbf{x})}$ 的概率接受样本，实现从 $f_D$ 分布到 $f_\Omega$ 分布的转换。 总结来说，文章解释了如何利用PRNG和拒绝采样法实现对复杂区域的均匀和非均匀采样。

评论摘要
主要讨论点：通过拒绝采样方法估计π的值以及高维空间中体积的变化（尤其是n维球体体积），并涉及“维度灾难”的影响。 不同观点： • [vitus] 认为拒绝采样方法估计π值是一个常被提及但并不实用的例子。他解释了通过生成两个0到1之间的随机数并检查满足 x^2 + y^2 <= 1 的点比例，可以估计π/4。但同时指出，拒绝采样仅在 f_Omega 能利用 f_D 中大部分概率密度时才高效。他还提到高维空间中n球体的体积随着维度增加而迅速减少，这与机器学习中的“维度灾难”有关。 • [atum47] 提到自己曾创建过一个使用蒙特卡罗方法计算随机形状体积的应用，并分享了相关GitHub链接。他的评论更侧重于实际应用，展示了如何通过编程实现蒙特卡罗方法来解决具体问题。 补充讨论： • [vitus] 强调了高维空间中的一个现象：随着维度 d 的增加，超球体的体积相对于超立方体的体积变得微不足道。他引用了维基百科中关于“维度灾难”的讨论，进一步说明这一现象在机器学习中的影响。 • [atum47] 的评论虽然没有直接讨论高维问题，但通过分享实际应用项目，间接回应了蒙特卡罗方法在处理复杂几何问题中的实用性。 争议焦点：虽然没有直接的争议，但 [vitus] 对拒绝采样方法在实际应用中的效率提出了质疑，尤其是高维空间中的体积问题，而 [atum47] 的实际应用展示了蒙特卡罗方法在某些情况下的可行性。这表明了两者在方法实用性上的潜在不同看法。
