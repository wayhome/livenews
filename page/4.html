The Theatre of Pull Requests and Code Review

文章摘要

本文讲述了作者参加Goatmire Elixir Conf会议后，对Saša Jurić关于代码审查和Pull Requests（PRs）演讲的感悟。演讲指出工程师常因PR过大、复杂而草率审查，导致代码质量下降。Saša建议：1）将难理解的PR退回作者；2）PR审查应控制在5-10分钟内；3）每个PR最好不超过300行代码；4）通过有叙事的提交信息帮助审查。他还演示了如何用13个细致的提交处理152行代码变更，强调迭代过程和保持提交历史的清晰性。文章提倡通过小范围、故事化的PR提升团队协作和代码质量。

评论摘要
主要讨论点：[GitHub PR界面的用户体验、代码审查的最佳实践、PR大小的合理性、提交信息的质量] 不同观点： • GitHub PR界面不够友好，难以逐提交审查（WorldMaker） - 提交选择器过于关注提交范围而非单个提交 - 缺少快速跳转至上一/下一提交的快捷键 - 提交描述在Files视图中难以阅读 - 提交选项卡默认隐藏大部分提交描述 • PR审查应注重共享理解和明确意图（jvanderbot） - 直接在代码行上标记具体变更并提问更有效 - "把代码扔到墙上等待解释"式的PR容易成为低优先级任务 • PR大小不应仅以代码行数衡量（davedx, epage） - 拆分过小的PR会增加认知负荷和合并冲突 - 关键取决于变更的争议性而非代码量 - 需要根据经验和与审查者的沟通判断 • 提交应讲述连贯故事（danielfalbo, necrotic_comp） - Jane Street的系统将每个提交作为独立分支审查 - 每个PR应能独立提交和发布 - 需要包含清晰的描述和测试证据 • PR的主要价值在于工作透明度（bob1029） - 代码审查更多是确保合并的干净度 - 信任团队成员的能力比反复"纯度测试"更重要 补充讨论： • 争议焦点： - PR的理想大小：300-500行规则是否合理 - 逐提交审查的必要性和可行性 - 代码审查的核心目的（质量把关vs.知识共享） • 其他重要观点： - 不同代码区域可能需要不同审查强度（ekidd） - 审查策略应取决于组织实际需求（conartist6） - Linux内核式PR模式与集体开发模式的差异（osigurdson） - 真实开发过程中的提交往往难以保持故事性（parpfish）

Tracing JITs in the Real World CPython Core Dev Sprint

作者: todsacerdoti | 评分: 60 | 评论数: 4 | 发布时间: 2025-09-25 18:40
文章摘要

文章主要内容：作者参加了CPython核心开发者冲刺活动，主要关注三个领域：1）C API改进，探讨PyNI（Python本地接口）的设计；2）fancycompleter功能，为Python REPL添加彩色补全；3）JIT相关工作，分享PyPy的经验教训。作者还做了关于追踪JIT（即时编译器）的演讲，比较了CPython和PyPy的JIT实现，指出JIT会改变代码性能特性，并强调实际代码与基准测试的差异。文章旨在传递JIT开发中的挑战和经验，帮助CPython开发者更好地优化性能。

评论摘要
主要讨论点：[不同JIT（即时编译）技术在动态语言（如JavaScript、Python、Julia）中的应用和优劣比较] 不同观点： • **JavaScript JIT的经验**（pizlonator）： - 追踪JIT（Tracing JIT）在JavaScript中被放弃，因为它难以扩展到真实世界的代码。 - 现代JavaScript JIT（如JSC）没有“追踪阻塞”问题，能够独立优化代码片段。 - 追踪JIT更像是基准测试的“技巧”，真正的优化JIT（如JS、Java、.NET中使用的）虽然编译成本高，但能带来更可预测的性能提升。 • **Julia JIT的潜在启发**（wbpaelias）： - Julia的JIT基于函数接收的类型进行编译，完全不依赖追踪。 - Python可以借鉴Julia的JIT设计，替换LLVM步骤为Python的IR（中间表示），可能带来显著性能提升。 - 但Python缺乏多重分派（multiple dispatch），这可能简化编译过程。 • **PyPy的实践与优势**（v3ss0n、Qem）： - PyPy已经长期实践JIT技术，并且表现良好。 - CPython的JIT团队与PyPy开发者之间的知识共享可能帮助PyPy进一步优化。 - PyPy的开发者可能从CPython的新尝试中获得启发，反之亦然。 补充讨论： - **争议焦点**：追踪JIT是否真的过时？支持者认为它无法适应复杂代码，反对者可能认为它在特定场景仍有价值。 - **技术迁移的可行性**：Julia的类型驱动JIT是否适合Python这样的动态语言，尤其是Python缺乏类型系统支持的情况下。 - **社区合作的价值**：PyPy与CPython之间的经验共享是否能够推动JIT技术的进一步发展。
