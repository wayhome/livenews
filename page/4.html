Show HN: Sinkzone DNS – Forwarder that blocks everything except your allowlist

作者: dominis | 评分: 57 | 评论数: 15 | 发布时间: 2025-08-06 16:08
文章摘要

Sinkzone 是一个本地 DNS 解析器，旨在帮助用户消除干扰，专注工作。它默认阻止所有域名，只有明确允许的域名才能访问，从而在网络层面阻止通知、社交媒体和新闻等分散注意力的内容。Sinkzone 具有 DNS 级别阻止、专注模式、通配符支持、HTTP API 和终端用户界面（TUI）等功能，适用于 macOS、Linux 和 Windows。它通过终端界面提供实时流量监控和允许列表管理，支持命令行操作，并且无需浏览器扩展或云服务。Sinkzone 专为需要深度工作的用户设计，帮助他们在无干扰的环境中工作。安装和使用指南可在项目文档中查看。

评论摘要
主要讨论点：Sinkzone工具的功能、使用场景及其与其他工具的比较 不同观点： • **支持使用Sinkzone并提出功能建议**： - [a022311] 认为Sinkzone的调度和专注模式非常有用，并建议增加不同配置文件（如"focus"、"work"、"kids"），以便更灵活地管理允许的域名。 - [eszpee] 提到目前使用的Pomodoro应用已有类似功能，但建议Sinkzone可以与Apple Shortcuts集成，实现自动化。 • **与其他工具的比较**： - [a022311] 提到目前使用OpenSnitch作为系统级防火墙，但缺少配置文件和调度功能，因此希望Sinkzone能提供更好的解决方案。OpenSnitch通过eBPF在进程级别进行拦截，比DNS级拦截更有效。 - [doodlebugging] 回忆起多年前使用过的SyGate防火墙，也具有类似的允许规则设置功能，但已被大公司收购并整合进其产品中。 - [artooro] 质疑Sinkzone相对于Pi-hole的优势，认为Pi-hole也能实现类似的允许模式。 - [q2dg] 提出AdGuardHome也能满足相同需求。 • **对工具实用性的看法**： - [fasouto] 最初认为Sinkzone有些过度，但承认自己在网站被屏蔽时会转而使用手机，因此愿意尝试。 - [buzicsotto] 和 [Duchambe_Double] 表示希望Sinkzone能在iOS设备上运行，否则无法有效防止分心。 • **技术实现和兼容性问题**： - [pozsi] 担心Sinkzone在连接公司VPN时可能会干扰公司的私有DNS配置。 - [mlhpdx] 质疑Sinkzone是否支持DoH（DNS over HTTPS），并指出浏览器本身常常是分心的来源。 • **替代方案**： - [lpman] 提到自己通常通过编辑hosts文件来屏蔽不需要的域名，但认为Sinkzone的方法更优雅。 补充讨论： - **进一步的安全措施**： - [rookderby] 认为Sinkzone优于自己使用的自动化工具，但指出直接使用IP地址的应用可能仍会绕过DNS拦截，并询问是否有其他网络安全措施的建议，如设置PF路由器或使用反向代理。 - **幽默评论**： - [cagenut] 以幽默的口吻称使用这种工具为"devops pro contrarian move"，即通过破坏DNS来提高工作效率。 争议焦点： - Sinkzone相对于其他类似工具（如OpenSnitch、Pi-hole、AdGuardHome）的优势和独特性。 - 工具在不同平台（特别是iOS）上的可用性及其对工作环境（如公司VPN）的兼容性。

Show HN: HMPL – Small Template Language for Rendering UI from Server to Client

作者: aanthonymax | 评分: 7 | 评论数: 1 | 发布时间: 2025-08-06 10:41
文章摘要

HMPL是一种面向服务器、可定制的JavaScript模板语言，旨在通过向服务器发送可定制的请求并处理成现成的HTML，以减少JavaScript文件的大小。它集成了JSON5和DOMPurify，支持类似于HTMX和Alpine.js的功能，但更加轻量。HMPL使用块状语法，允许开发者在模板中定义请求和响应指示器。例如，当按钮被点击时，可以从服务器获取点击数据并动态更新页面内容。此外，HMPL还支持不依赖JavaScript的DOM操作，通过额外的`hmpl-dom`模块，组件可以直接从服务器挂载到DOM中。HMPL的优势在于其灵活的请求定制、自动生成表单body和缓存支持，适合替代传统的重型前端框架。

评论摘要
主要讨论点：不同轻量级前端技术（如HMPL、htmx、Alpine.js）的比较及是否值得从htmx切换到HMPL 不同观点： • **相似性观点（tosh）**： - tosh认为HMPL与htmx非常相似，因为它们都采用后端渲染HTML片段并在前端更新DOM的模式。 - 他提到如果已经在使用htmx，是否还有必要切换到HMPL，因为两者似乎属于同一类轻量级前端方案。 - 他将HMPL、htmx和Alpine.js归为同一类，认为它们是不同风格的轻量前端技术，直接竞争。 - 他认为这些技术的主要目的是让开发者重新思考是否需要复杂的大型前端架构，还是选择更轻量的方案。 • **潜在差异与竞争（隐含观点）**： - 虽然没有直接说明，但可以推断出，HMPL可能提供了一些不同于htmx的特性或优化，否则不会有“是否应该从htmx切换”的疑问。 - 潜在的差异可能体现在性能、易用性、生态系统支持或特定功能实现上。 补充讨论： • **技术选择的思考**： - 评论中隐含了对技术选择深层次的思考，特别是在前端框架日益复杂化的背景下，是否真的需要“重型”前端框架（如React、Vue.js）或选择更轻量的解决方案。 - 不同技术（HMPL、htmx、Alpine.js）间的细微差别可能影响具体项目的技术选型，但核心是它们都针对简化前端开发提出了不同的解决方案。 • **争议焦点**： - 焦点在于HMPL与htmx的实际区别，以及是否值得从已经使用htmx的项目中切换到HMPL。这涉及到开发者对学习新工具的成本与潜在收益的权衡。 - 另一个潜在争议是这些技术是否真的能完全取代复杂的前端框架，还是在某些场景下仍然需要更重的解决方案。

文章摘要

文章讨论了构建计费系统的复杂性，尽管表面上看起来只是定期向客户收费。作者解释了不同计费模式的挑战，如订阅制（包括基础、进阶、高级套餐）、按席位收费模式，以及近年来兴起的按使用量计费模式。每种模式都带来了独特的技术难题，如处理试用期、中途升级或降级、实时使用跟踪、高吞吐量事件处理、以及灵活适应不断变化的定价模型等。 计费系统不仅仅是开具发票，它涵盖了整个收入管理流程，包括合同管理、产品供应、使用量计量、权限管理、发票生成与交付、付款处理和收入确认。因此，计费系统是企业经济命脉，其复杂性远超预期，涉及大量技术和架构挑战。

Git-fetch-file – Sync files from other repos with commit tracking and safety

作者: andrewmcwatters | 评分: 27 | 评论数: 5 | 发布时间: 2025-08-06 22:45
文章摘要

`git-fetch-file` 是一个可以从其他 Git 仓库中获取和同步单个文件或文件集的工具，具有提交跟踪和本地更改保护功能。它类似于一个简化的子模块，但仅针对你想要的文件。主要功能包括：从远程仓库拉取单个文件或文件集，通过 `.git-remote-files` 文件记录来源和提交信息，支持强制覆盖本地更改和更新跟踪的提交。它提供简单的命令行接口，可以通过 Git 别名或直接保存到 PATH 进行安装。主要命令包括 `add`（跟踪文件）、`pull`（下载跟踪文件）和 `status`（查看跟踪文件状态）。该工具采用 GPL-2.0 许可证。

评论摘要
主要讨论点：如何有效管理和追踪跨代码仓库的文件依赖问题 不同观点： • neomantra认为使用子模块（submodules）过于繁重，因此建议通过CI脚本比较选定文件的校验和（checksums），从而验证文件的一致性和完整性。这种方法被认为是通用且有效的解决方案。 • Bukhmanizer以一种讽刺的口吻提出，可以将跨代码仓库拼接文件的做法视为一种艺术项目，暗示这种做法可能会导致过于复杂的系统设计。 • dpsych表示完全认同neomantra的观点，并认为这是他所寻找的解决方案。 • andrewmcwatters提出了另一种需求，即需要从其他项目中获取特定文件，并且能够固定版本或保持最新。他建议使用类似于`git fetch-file`的命令来追踪文件，并提到通过`.git-remote-files`来记录这些文件的来源和状态。 补充讨论： • neomantra和andrewmcwatters都反对使用子模块作为解决方案，认为子模块过于复杂且不适合他们的需求。 • andrewmcwatters提供了一种具体的技术实现方案，即使用自定义的git命令来管理和追踪从其他仓库获取的文件。 • Bukhmanizer的观点则更具讽刺性，暗示这种跨仓库拼接文件的做法可能会导致不必要的复杂性。 争议焦点： • 是否应该使用子模块来管理跨仓库文件依赖。 • 哪种技术方案更适合管理和追踪跨仓库的文件，CI脚本校验和方法还是自定义git命令方法。

More than two hard disks in DOS

本文探讨了Microsoft OS/2 1.21磁盘驱动程序的异常行为，并追溯到Compaq的EXTDISK.SYS驱动程序。研究发现，DOS 5.0之前的版本不支持系统BIOS暴露的两个以上硬盘，若硬盘过多，系统启动时可能挂起。这种限制源于技术问题而非架构设计，因为早期PC无法安装超过两个全高5¼英寸硬盘。Compaq通过其Deskpro 386/25系统支持最多四个硬盘，但通过EXTDISK.SYS驱动解决DOS的限制。Adaptec的AHA-1540/1542 SCSI卡也面临类似问题，通过ASPI4DOS.SYS和ASPIDISK.SYS解决。DOS 5.0之前的版本在处理超过两个硬盘时会出现挂起问题，因其未验证INT 13h返回的硬盘数，导致系统在计算文件系统参数时陷入无限循环。此问题在DOS 2.0到4.0版本中普遍存在，直到DOS 5.0才修复。
