Show HN: A CSS 3D Engine (no WebGL)

作者: rofko | 评分: 55 | 评论数: 8 | 发布时间: 2026-06-01 13:58
文章摘要

PolyCSS 是一个 CSS 多边形网格库，可将 3D 模型（OBJ/MTL、GLB、VOX）渲染为真实的 HTML 元素，通过 CSS `matrix3d()` 变换实现 3D 效果。支持颜色、纹理、光照、阴影、形状和动画。提供 React、Vue 和原生 JavaScript 三种使用方式。核心组件包括 PolyCamera（视角控制）、PolyScene（场景和光照）、PolyMesh（加载模型）。支持轨道控制、第一人称控制等交互方式，可导出独立的 HTML 快照。每个多边形由顶点、颜色或纹理定义，可直接渲染并绑定 DOM 事件。

评论摘要
主要讨论点：使用CSS实现3D渲染的技术可行性和实用价值 不同观点： • 支持CSS 3D方案：认为DOM事件处理是关键优势，CSS可以直接使用onClick处理单个面的点击，而WebGL需要复杂的光线投射(raycasting)。对特定用例来说这是决定性优势 • 质疑CSS方案：认为应该使用WebGL，因为它更广泛可用、效率更高、渲染质量更好，并提供了对比示例链接 • 实践探索者：分享了十年前尝试用CSS做类似《最终幻想战略版》游戏的经历，因未能及时抽象化而失败，对这类技术挑战表示欣赏 • 应用场景探讨：询问CSS 3D是否适合制作RTS或简单城市建设游戏 补充讨论：有人提到corru.observer网站也仅用CSS transforms实现了3D地图；还有人开玩笑说15分钟内就会有人用它移植《毁灭战士》游戏。整体氛围积极，对技术创新表示赞赏。

Tracing HTTP Requests with Go's net/HTTP/httptrace

作者: speckx | 评分: 167 | 评论数: 6 | 发布时间: 2026-05-28 16:46
文章摘要

这篇文章介绍了Go标准库中的`net/http/httptrace`包。该包自Go 1.7起就存在，但很少被使用。它通过在`context.Context`中附加`ClientTrace`来追踪HTTP请求的各个阶段（DNS解析、连接建立、TLS握手、数据传输等），而不是通过传统的接口或中间件方式。 这种基于context的设计有三个优势：追踪信息随请求传播、支持并发请求使用不同追踪配置、未使用时开销极小。`ClientTrace`是一个包含可选函数字段的结构体，只需设置关心的钩子函数即可。 文章演示了如何构建类似`curl --trace`的CLI工具，通过在各个钩子中记录时间戳来计算请求各阶段的耗时。

评论摘要
主要讨论点：Go语言的HTTP连接追踪功能及其开发体验 不同观点： • **Go生态系统优势论**：认为Go的优势不仅在于语法，更在于端到端的开发流程。内置工具链完整，无需频繁依赖外部工具。将Go与C#/.NET并列为注重完整开发体验的平台 • **Go语言学习体验**：新手开发者对Go的并发特性（goroutines和channels）印象深刻，认为其简洁性类似Ruby，特别是在处理websockets等复杂场景时优于Node.js • **连接追踪的实用价值**：强调HTTP连接复用追踪在性能基准测试和服务评估中的重要性。指出连接池使用不当会导致文件描述符耗尽等问题 补充讨论： • 作者分享了该功能在probes.dev项目中的实际应用 • 有开发者表示两年前遇到类似需求时自行实现了连接追踪方案，体现了这一功能的实际需求 • 讨论整体氛围积极，参与者从不同角度（语言设计、学习体验、实际应用）肯定了Go的价值

Using Git's rerere feature to escape recurring conflict hell

作者: ankitg12 | 评分: 83 | 评论数: 8 | 发布时间: 2026-06-01 07:06
文章摘要

这篇文章介绍了 Git 的 `rerere` 功能（Reuse Recorded Resolution，重用已记录的解决方案）。当合并分支时遇到重复的冲突，`rerere` 可以记住你之前如何解决冲突，并在相同冲突再次出现时自动应用相同的解决方案。 启用方法：运行 `git config --global rerere.enabled true` 工作原理：首次遇到冲突时，`rerere` 会记录冲突状态和你的解决方式。当相同冲突再次出现时，Git 会自动应用之前的解决方案，无需手动处理。这大大减少了在合并或变基过程中反复解决相同冲突的痛苦。

评论摘要
主要讨论点：Git 工作流中如何避免合并冲突和代码回退问题 不同观点： • **单向合并派（dools）**：严格遵循"远离 main 用 rebase，朝向 main 用 merge"原则，所有冲突只在功能分支上通过 rebase 解决，从不在 main 上处理冲突。这种方法彻底解决了神秘的静默回退问题。 • **配置优化派（0123456789ABCDE, davidelettieri）**：通过配置 git rerere（自动记录冲突解决方案）、zdiff3（改进冲突显示）、autoSquash、autoStash 等选项来提升 Git 体验，减少重复劳动。 • **严格分支管理派（adithyassekhar）**：认为开发者之间不应直接合并分支，只从 master 拉取更新。如果需要他人未完成的代码，说明存在更大的规划问题。环境晋升应单向进行：feature > dev > staging > master。 • **工具替代派（mamcx）**：认为 Git 的用户体验问题在于需要全员严格遵守纪律，rerere 在团队环境中效果有限。转用 Jujutsu 后问题得到解决，因为它能更好地适应不同的工作流。 补充讨论：barchar 提到可用 rerere-train 脚本从现有合并中填充 rerere，在 bisect 调试时特别有用。cautiouscat 感叹 Git 知识的深度。
