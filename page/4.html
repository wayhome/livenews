Show HN: Nxtscape – an open-source agentic browser

作者: felarof | 评分: 289 | 评论数: 49 | 发布时间: 2025-06-20 16:35
文章摘要

Nxtscape是一款开源的智能浏览器，主打本地运行的AI代理功能，注重用户隐私保护。它提供类似Google Chrome的界面，兼容所有Chrome扩展，用户可自行选择API密钥或使用本地模型（通过Ollama）。主要特点包括：隐私优先，数据保留在本地；AI代理自动化任务；开源社区驱动。相比Chrome、Brave、Arc等浏览器，Nxtscape专注于AI增强浏览体验，不涉及广告和搜索业务。用户可以下载安装、导入Chrome数据、连接AI提供商后开始使用。未来计划包括MCP商店和内置AI广告屏蔽器。项目欢迎社区贡献和反馈。

Unexpected security footguns in Go's parsers

作者: ingve | 评分: 135 | 评论数: 13 | 发布时间: 2025-06-18 11:35
文章摘要

文章主要讨论了Go应用程序中解析不可信数据带来的安全风险，特别是在JSON、XML和YAML解析器中的意外行为可能被攻击者利用，导致认证绕过、授权控制突破以及敏感数据泄露。文章通过三个攻击场景具体说明： 1. **(Un)Marshaling意外数据**：Go解析器可能暴露开发者本想保密的字段数据。 2. **解析器差异**：不同解析器处理相同输入的差异可能被利用来绕过安全控制。 3. **数据格式混淆**：解析器处理跨格式数据时可能产生可被利用的结果。 文章还列举了多个实际案例，并给出强化解析器配置的建议，包括如何应对Go标准库中的安全缺口。例如，使用结构体标签控制字段的序列化和反序列化行为，以及如何避免暴露敏感字段等。最后，文章总结了这些解析器的潜在安全问题和应对策略。

评论摘要
主要讨论点：Go 语言中处理 JSON、XML 等数据格式时的潜在问题及其解决方案 不同观点： • **octo888 的观点**：指出在 "create user" 请求的 DTO 中包含 "IsAdmin" 字段是不合适的，建议不应直接将数据模型重用于不同的请求/响应结构，而应为不同用途定义不同的数据结构。例如，`CreateUserRequest` 和 `UserView` 应该分开定义，而不是直接映射到数据库模型。 • **fainpul 的观点**：建议通过将结构体中的字段设为小写私有字段来避免外部直接访问，例如 `isAdmin` 字段，这样可以防止敏感字段被外部请求直接修改。 • **em-bee 的观点**：认为数据解析后应进行数据验证步骤，而不是依赖解析器来保护数据结构。解析器只负责解析，代码应主动从解析结果中提取合法字段，忽略未知字段，从而避免潜在的安全问题。 • **glenjamin 的观点**：指出禁用未知字段（DisallowUnknownFields）会使得 API 在前后兼容性方面变得更加困难，而这种兼容性通常是必要的。 • **asimops 的观点**：认为不应将客户端的数据直接传递给认证服务，这是设计上的错误。正确的做法是先解析数据，再对解析后的数据进行处理，而不是简单地验证数据。 • **anitil 的观点**：对 JSON、YAML、XML 等多种格式可以被同一个字符串解析感到惊讶，尤其是 Go 的默认 XML 解析器接受前后多余的内容，这让人意识到不同格式解析中的潜在问题。 • **tptacek 的观点**：指出不应该信任使用 `encoding/xml` 的 Go SAML 实现，因为该库并不是为这种用途设计的，建议自行编写解析器以确保安全。 • **e_y_ 的观点**：认为 Go 使用字符串作为字段元数据的方式相比其他语言（如 Rust 的宏或 Java 的注解）显得较为落后，尤其是 `omitempty` 等字段的处理可能会引发一些潜在问题。 • **piinbinary 的观点**：赞赏作者清晰易懂的写作风格，并对 JSON、YAML、XML 可以被同一个字符串解析的现象感到震惊。 • **aintnolove 的观点**：认为像 Protocol Buffers 这样的序列化/反序列化工具可以提供跨语言的一致体验，避免像 JSON、XML 这样的格式带来的问题。 • **jerf 的观点**：认为很多问题是由于用户错误和 JSON、XML 本身的复杂性所致，而非 Go 语言本身的缺陷。并指出在不同语言中处理 JSON 重复键等问题时都会遇到类似的困境，无法通过简单的解析器设计来解决。同时强调，接受用户输入到敏感变量是常见错误，但这是开发者的责任而非语言本身的问题。 • **neuroelectron 的观点**：认为这些协议语言中的问题似乎是故意设计的，长期以来一直存在。 • **vlowther 的观点**：认为很多安全漏洞源于开发者不了解语言和库的功能和设计，依赖直觉和复制粘贴代码，而不是深入理解问题领域。除了 JSON 键不区分大小写的问题外，其他大多数问题都是合理的工程权衡。 补充讨论： • **争议焦点**：如何处理解析过程中的未知字段和敏感字段。一方认为解析器应具备一定的保护功能，另一方则认为这是代码的责任，解析器只负责解析。 • **不同格式解析的复杂性**：评论中多次提到 JSON、XML、YAML 等多格式解析的复杂性和潜在问题，尤其是在跨语言和跨库的情况下。 • **Protocol Buffers 的优势**：提到 Protocol Buffers 提供的跨语言一致性体验可能是一个更好的选择，避免了 JSON、XML 带来的许多问题。
