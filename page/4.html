pg_durable: Microsoft open sources in-database durable execution

作者: coffeemug | 评分: 406 | 评论数: 21 | 发布时间: 2026-06-05 15:59
文章摘要

pg_durable 是微软开源的 PostgreSQL 扩展，在数据库内实现持久化执行（Durable Execution）。它让长时间运行的 SQL 函数具备容错能力，通过检查点机制在每步执行后保存状态，崩溃或重启后可从断点恢复，无需重新执行已完成的工作。 适用场景包括：向量嵌入管道、数据摄取、定时维护、并行聚合、外部 API 调用等。可替代 pg_cron + 状态表、外部编排器（Airflow/Temporal）、队列+工作者等传统方案，将工作流逻辑统一在 SQL 中管理，减少架构复杂度。 核心优势是消除部分失败后的手动恢复、避免长事务锁定、将重试和进度跟踪集中到 Postgres。不适合单条 SQL 语句、毫秒级同步请求，或需要复杂应用逻辑的场景。

评论摘要
主要讨论点：在 Postgres 中实现持久化工作流和队列系统的利弊 不同观点： • **支持派**：认为持久化执行是2024年最值得投资的技术，能解决精确一次执行、重试、信号驱动工作流等常见痛点。有人成功用 Postgres + PostgREST 构建了功能性作业队列。 • **质疑派-业务逻辑位置**：多位开发者质疑为何要将控制流和业务逻辑存储在数据库而非代码中。批评这类似存储过程，无法单元测试、版本控制困难、缺乏可观测性、难以隔离噪音工作负载、缺少 IO 能力（尤其是 API 调用）。 • **质疑派-工具对比**：认为 Apache Airflow 等 DAG 调度器、Temporal 等编排工具已经解决了这些问题，不理解为何需要基于数据库的方案。有人认为这是不必要的"内部平台效应"，如果编程语言支持确定性执行和状态序列化就不需要。 • **扩展性担忧**：指出数据库本就是最难扩展的基础设施，为何要增加长期运行任务的负担？ • **实际限制**：Azure Postgres 用户抱怨功能落后，无法使用现代特性。项目文档中明确不适用于跨多个异构系统的工作流，与 Temporal 的对比存疑。 补充讨论：代码优先 vs 数据库优先的开发偏好分歧明显；文档中一些实现细节（如超时处理、错误处理）不够清晰；AI 代理对消息队列代码更熟悉可能是潜在问题。

Moving beyond fork() + exec()

作者: jwilk | 评分: 184 | 评论数: 21 | 发布时间: 2026-06-06 14:34
文章摘要

这篇文章讨论了Linux内核中进程创建的优化提案。传统的`fork()`和`exec()`模式存在效率问题：`fork()`复制整个进程状态成本高昂，而紧随其后的`exec()`又会丢弃这些复制的内存。Li Chen提出了"spawn templates"方案，通过预先缓存可执行文件信息来加速重复运行同一程序的场景，基准测试显示约2%的性能提升。但评审者Mateusz Guzik指出，真正的优化应该跳过`fork()`步骤，直接创建全新进程，而不是优化现有模式。该提案虽不会被采纳，但为未来的进程创建原语指明了方向。

评论摘要
主要讨论点：fork() + exec() 模型是否应该被废弃，以及如何设计更好的进程创建机制 不同观点： • **支持废弃 fork()：** fork() 是1970年代的产物，现已过时成为负担。它成本高昂（需复制整个进程状态），且通常紧随 exec() 调用会丢弃刚复制的内存。即使有 copy-on-write 优化，复制页表项仍是 O(N) 操作。概念上也不合理——启动新进程却要先克隆当前进程。 • **反对废弃 fork()：** fork() + exec() 的优雅在于分离关注点，fork 后可用所有常规 API 配置进程（如 dup2、设置进程组、信号处理、文件描述符、命名空间、seccomp 等）。任何试图用单一调用替代的方案都需要把所有配置选项作为参数，难以扩展且容易混乱。有经验的开发者认为这个模型经过时间检验，比线程编程更易理解。 • **Windows 模型对比：** CreateProcessW 更直接自然，但接口更窄、不灵活，通过结构体传递初始值限制了可扩展性。 补充讨论：posix_spawn 已提供类似 Windows 的接口；有提议创建空白进程后强制执行系统调用序列；或使用类似 eBPF 的钩子机制实现可定制的进程创建流程。

The perils of UUID primary keys in SQLite

作者: emschwartz | 评分: 141 | 评论数: 18 | 发布时间: 2026-06-05 23:13
文章摘要

这篇文章探讨了在SQLite中使用UUID作为主键的性能问题。作者通过基准测试发现，使用随机UUID4作为主键比使用整数主键慢10-12倍，因为UUID4的无序性导致聚集索引的B树需要频繁重新平衡，产生大量额外的分页操作。通过性能分析图（diffgraph）证实了这一点。解决方案是使用时间有序的UUID7，其性能接近整数主键基线。文章强调了聚集索引的特性：表的物理存储顺序由索引键决定，因此主键的有序性对写入性能至关重要。这个问题不仅存在于SQLite，也适用于其他使用聚集索引的数据库。

评论摘要
主要讨论点：数据库主键选择策略——UUID vs 整数ID，特别是 UUIDv7 在 SQLite 中的性能表现 不同观点： • **反对过度使用UUID派**（blopker）：认为UUID被过度使用，bigint 在单数据库场景下更小更快，建议仅在分布式无主存储时考虑UUID，公开ID可用 Sqid 替代 • **UUIDv7实用派**（sedatk, jdthedisciple, yepyoukno）：UUIDv7 与顺序整数类似但避免暴露计数信息，在不重视插入性能且需要隐藏信息的场景下，UUIDv4 也可行；UUIDv7 应转为二进制优化存储 • **场景决定论**（adityaathalye）：本地单实例用 SQLite 自动整数 rowID 即可，但跨设备同步、实例协作场景下，顺序随机ID（如UUIDv7）价值凸显，便于合并、去重；强烈反对完全随机ID破坏树结构 • **双ID策略派**（bambax, ItsBob）：内部用整数 rowID/bigint 做主键和关联，外部暴露时用独立的UUID列，兼顾性能与安全 补充讨论： • 有人质疑脚本细节（批次数量）和性能数据来源（百万级插入速度、UUID生成耗时） • Postgres 等支持并发写入的数据库中，顺序键可能导致页面竞争 • 作者表示文章为草稿，计划补充不同行大小的影响

First Commodore PET sold, June 5, 1977

作者: erickhill | 评分: 10 | 评论数: 1 | 发布时间: 2026-06-06 16:16
文章摘要

这篇文章讲述了Commodore PET 2001个人电脑的历史。1977年6月5日，Commodore在消费电子展上接到首个经销商订单，成为"1977三巨头"（PET、Apple II、TRS-80）中最早销售的预装电脑之一。PET由6502处理器设计师Chuck Peddle主导开发，售价495美元，配备内置显示器、磁带录音机和4KB内存。值得注意的是，Commodore仅支付25,000美元就获得了微软BASIC的永久授权，这让微软后来非常后悔，因为该授权延续到了后来极为畅销的C-64和VIC-20。PET首年仅生产500台，供不应求。
