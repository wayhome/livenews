Critical Unauthenticated Remote Code Execution Vulnerabilities in Ingress NGINX

作者: puppion | 评分: 57 | 评论数: 5 | 发布时间: 2025-03-25 10:12
文章摘要

Wiz Research发现了一系列未经身份验证的远程代码执行漏洞（CVE-2025-1097, CVE-2025-1098, CVE-2025-24514, CVE-2025-1974），影响Kubernetes的Ingress NGINX Controller，命名为#IngressNightmare。这些漏洞允许攻击者未经授权访问Kubernetes集群中的所有秘密信息，可能导致集群被接管。该漏洞的CVSS v3.1基础评分高达9.8。 研究显示，约43%的云环境易受此漏洞影响，超过6,500个集群（包括财富500强公司）公开暴露了易受攻击的Ingress控制器。建议尽快修补漏洞。 Ingress NGINX Controller是Kubernetes中常用的入口控制器，默认情况下其 admission controllers 未经身份验证可网络访问，攻击者可利用恶意入口对象实现远程代码执行。 缓解措施包括： 1. 升级到Ingress NGINX Controller的最新版本（1.12.1或1.11.5）。 2. 确保admission webhook端点不外部暴露。 3. 实施严格的网络策略，仅允许Kubernetes API服务器访问admission controller。 可以使用Nuclei模板检查暴露的Ingress-NGINX admission controllers。

评论摘要
主要讨论点：Kubernetes环境中入口控制器和准入控制器的安全性，尤其是Ingress-NGINX相关漏洞的暴露和利用风险。 不同观点： • [rollulus] 对Kubernetes准入控制器暴露在公共互联网的情况表示困惑。他认为Kubernetes API虽然暴露在互联网上，但未认证的请求都会被拒绝，因此不理解为何准入控制器会成为问题。他还质疑在什么样的错误配置下，准入控制器会暴露给外界。 • [boxed] 质疑标题中突出NGINX的问题，因为他认为问题出在Kubernetes本身，而不是NGINX。他觉得将问题归咎于NGINX有些不公平。 • [KronisLV] 提到其他入口控制器（如Traefik）并认为碎片化（即有多种不同的入口控制器选择）在一定程度上是好事，因为它限制了单一漏洞大范围影响的可能性。他还指出，使用传统网络服务器（如Caddy或Apache2）作为入口控制器的基础可能对一些长期项目或家庭实验室环境有帮助。 • [SCdF] 提供了一个讨论链接，表示该话题已在其他地方讨论过，但没有深入提出自己的观点。 • [Traubenfuchs] 澄清了漏洞利用的条件，指出要利用此漏洞，攻击者需要直接向Kubernetes资源（准入控制器）发送请求。这种情况通常只有在明显危险的错误配置或极其松散的安全标准下才会发生。正常情况下，Kubernetes资源不应从互联网访问。 补充讨论： • 争议的焦点在于准入控制器的暴露和利用风险，以及问题是否应归咎于NGINX。 • 讨论中还涉及到Kubernetes集群的安全配置问题，特别是如何避免将Kubernetes资源暴露在公共互联网中。 • [KronisLV] 提出了对入口控制器多样性的看法，认为多样性可以减少单一漏洞的广泛影响，但也担心许多用户可能不会及时更新或修复不安全的软件配置。 总结：评论主要围绕Kubernetes准入控制器的安全性、错误配置的可能性以及问题是否应归因于NGINX展开讨论。参与者对漏洞利用的具体条件和配置错误的影响有不同理解，并探讨了可能的解决方案和安全实践。
