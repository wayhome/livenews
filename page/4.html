Mruby/C and picoruby: high level langs in low-level devices?

作者: rahil627 | 评分: 62 | 评论数: 10 | 发布时间: 2025-03-23 09:20
文章摘要

PicoRuby 是一个专为单片微控制器设计的微型 Ruby 实现，具有小尺寸和可移植性特点。它在 32 位架构下仅需 256 KB ROM 和 128 KB 或更少的 RAM。PicoRuby 依赖标准 C 库，如 glibc 或 Newlib，并支持 Raspberry Pi Pico 等微控制器板。它提供了 API 文档和演示视频，并依赖于 mruby/c 实现的虚拟机。PicoRuby 可用于构建 PRK Firmware 键盘固件和 PicoRuby WASI WebAssembly 运行时。构建过程需要 C 工具链、git 和 Ruby 3.0 以上版本。项目仍在开发中，遵循 MIT 许可协议，并获得了 Ruby Association Grant Program 的支持。

Quadlet: Running Podman containers under systemd

作者: gjvc | 评分: 224 | 评论数: 20 | 发布时间: 2025-03-24 00:27
文章摘要

本文介绍了如何使用Quadlet在systemd下运行Podman容器，替代已被弃用的`podman generate systemd`方法。Quadlet简化了将Podman容器作为systemd服务运行的过程，特别适用于需要在后台运行并希望在服务器重启后自动启动的容器。 过去的方法需要手动创建容器、生成systemd服务文件并进行配置，步骤繁琐且不易管理。而Quadlet通过在`~/.config/containers/systemd`目录中创建`.container`文件来定义容器配置，使用类似INI文件的格式，包含容器和systemd相关设置。这不仅简化了操作，还提供了更多灵活性，允许使用systemd的所有功能。 例如，创建一个PostgreSQL容器的配置文件`test-db.container`，可以指定镜像、自动更新、端口映射、卷和环境变量等。Quadlet使得Podman在功能和易用性上接近Docker Compose，同时更好地与systemd集成。

评论摘要
主要讨论点：Quadlet 作为 Docker Compose 的替代方案在开发和生产环境中的使用及其优缺点 不同观点： • psadauskas：Quadlet 适合在生产环境替代 Docker Compose 来管理容器，但在开发环境中并不理想。主要问题在于 Quadlet 的配置文件位于 `~/.config/containers/systemd`，不方便项目隔离和共享，且大多数开发者仍在使用 Docker。此外，手动处理卷的权限问题也较为麻烦。 • l11r：支持 Quadlet，尤其是在 rootless 环境下。它支持 systemd 的 socket 激活功能，可以有效解决 rootless 环境下保留源 IP 的问题，非常适合自托管环境（如 homelab）。 • stryan：高度推荐 Quadlet，认为其比 Docker 的类似方案更简洁，且与 systemd 深度集成。但承认 Quadlet 在本地开发环境中并不理想，仍需依赖 Docker Compose 来完成开发工作流。 • smjburton：认为 Quadlet 提供了一个从 Docker 迁移的良好替代方案，特别是对于那些因为 Docker Compose 而犹豫迁移到 Podman 的用户。强调了 Podman 在安全性方面的优势。 • kccqzy：通过其他教程使用过类似 Quadlet 的配置，但未意识到其正式名称，表明对 Quadlet 的认知度较低。 • brirec：对 Quadlet 作为 Docker Compose 的替代品持怀疑态度，指出 Quadlet 不支持多 YAML 文件的叠加，且其开发活跃度并不比 Podman-Compose 高。 • cvhc：赞赏 Quadlet 的清晰格式和 systemd 集成，但因为 Podman 在 Debian/Ubuntu 上的支持不足，最终回到了 Docker Compose。 • muti：使用 openSUSE MicroOS 和 Quadlet 搭建了自我托管的环境，对目前的设置感到满意，但承认在本地开发时仍会选择 Docker Compose。 • alexellisuk：提到 Quadlet 的一个实际应用案例，展示了其与 Kubernetes 的结合使用，认为这是 Quadlet 的一个潜在优势。 • eulenteufel：喜欢 Quadlet 将容器作为系统服务管理的方式，但指出 rootless 容器在用户 session 中运行，与系统 session 隔离，使用体验不够流畅。 • lukaslalinsky：在非 Kubernetes 环境中使用 Quadlet，认为其是 Docker 在生产环境中的理想替代品，特别是对 Linux 原生支持更好。 • mati365：展示了使用 Ansible 部署 Quadlet 的模板，认为 Quadlet 易于部署和管理。 • sunshine-o：多年来一直尝试使用 Quadlet，但总觉得不够成熟，预计到 2025 年可能才真正成熟。质疑为何花了近十年时间才实现容器与服务管理器的基本集成。 • aprilfoo：使用 Quadlet 数月，认为其值得更多关注，特别是 Red Hat 对其与 systemd 的整合做得很好。建议创建社区维护的 Quadlet 仓库以促进其普及。 • bityard：对 Quadlet 的命名和其必要性感到困惑，不理解为何需要一个特殊的名称。 补充讨论： - Quadlet 与 Docker Compose 在开发和生产环境中的优劣对比。 - Quadlet 的 rootless 模式在实际应用中的问题。 - 社区对 Quadlet 的认知度和接受度较低，部分用户对其命名和定位感到困惑。 - Quadlet 与 Kubernetes 的结合使用及其在自托管环境中的优势。 - Podman 和 Quadlet 在不同 Linux 发行版上的支持情况及其对用户选择的影响。

A USB Interface to the "Mother of All Demos" Keyset

作者: zdw | 评分: 311 | 评论数: 20 | 发布时间: 2025-03-23 15:31
文章摘要

Douglas Engelbart在1960年代初开始探索计算机如何增强人类智力，并开发了许多现代计算的特性，如鼠标、超文本、共享文档、窗口和图形用户界面。在1968年的联合计算机会议上，他通过一场开创性的演示（被称为“所有演示之母”）展示了这些创新。这场演示包括使用一种名为"keyset"的输入设备，但它并未普及。Engelbart的演示还展示了层次文档编辑、图形绘制以及通过远程连接与同事协作，预示了现代计算的许多功能。他的工作受到Vannevar Bush 1945年文章《As We May Think》的启发，旨在增强人类解决复杂问题的能力。Engelbart在斯坦福研究所创立了增强研究中心，并开发了名为NLS的系统，该系统支持交互式文档编辑、代码浏览和数据库检索。这场演示使用了当时先进的硬件和通信技术，连接了Menlo Park和旧金山的会场。
