Int a = 5; a = a++ + ++a; a =? (2011)

作者: e-topy | 评分: 123 | 评论数: 40 | 发布时间: 2026-05-12 14:14
文章摘要

文章讨论 C/C++ 表达式 `int a=5; a = a++ + ++a;` 的未定义行为。作者分析求值顺序和后置自增覆盖/延后导致的不同结果，说明编译器可能给出 11、12 或 13，并强调此类代码不可依赖。

评论摘要
主要讨论点：C/C++中类似 `a += a++ + a++` 的表达式是否有确定结果、为何是未定义行为，以及这类题是否适合作为面试/考试题。 不同观点： • 反对把此类代码当“求输出”题：susam、sangeeth96 等认为很多面试官/教师误以为某个编译器输出就是标准答案，忽视 UB 和 sequence points；不同编译器结果不同，说明题目误导性强。 • 强调“未定义行为意味着任何结果”：Boxxed、koliber、Someone 指出只要触发 UB，理论上不只 11/12/13，崩溃、任意数值都可能。 • 质疑为何语言不定义顺序：Aardwolf、magicalhippo 认为这不像有符号溢出那样依赖硬件，语言本可规定从左到右或完整语句后再自增。 • 维护 UB 设计的现实解释：compiler-guy 认为已有编译器可能各自形成事实扩展，若标准强行定义会破坏兼容；更好的做法是报错或用 UBSan 等工具诊断。 • 实践派建议避免写法：yason、tombert、HelloNurse 认为重点不是算答案，而是识别危险并写成多行明确逻辑；写这种代码应视为严重代码异味。 • 语言差异观点：Timwi 指出在 C# 中有左到右顺序，因此结果可为 12，说明问题取决于语言规范。 • 更细节的 UB 讨论：kazinator 提到非原子/分片更新下甚至可能读到“撕裂值”，不仅是简单顺序差异。 补充讨论：争议焦点在于“UB 是否应被标准定义”以及教育/面试中是否应考察这类陷阱题。

评论摘要
主要讨论点：围绕“用现代微控制器/FPGA等高速设备介入复古硬件总线或ROM空间，从而让老硬件呈现超出原本时代能力的效果”。 不同观点： • 技术乐观派：认为现代设备速度远超旧ROM/总线需求，可通过“插入器”或替换ROM/RAM，在正确时序提供数据，让复古硬件实现原本不可能的图形效果。举例提到NES“反向模拟”、C64 Ultimate 48MHz演示、可能替换C64字符ROM或RAM来叠加色彩属性。 • “现代硬件驱动旧外设”视角：有人概括为“把CGA当低端显示器使用”，属于用强大现代处理器在复古硬件上做荒诞但有趣的实验。 • 玩笑式延展：评论者调侃下一步会做2D精灵引擎、3D精灵引擎、OpenGL命令，最后让《Crysis》跑在IBM PC上，突出这种思路的想象空间和荒诞感。 • 复古硬件发现派：认为这类项目展示了旧硬件中未被当年充分利用的潜力，联想到2015年“8088 MPH”在CGA上实现1024色的demo。也有人以Amiga用户身份开玩笑称“文化挪用”。 • 硬件兼容/扩展设想：有人希望把类似卡带插进支持实体卡带的FPGA NES模拟器；也有人讨论是否能把CGA属性色单元细化到8x1，以提升色彩控制精度。 补充讨论：争议不强，核心焦点在于这些效果到底算“老硬件能力”还是“现代硬件外挂能力”；多数评论将其视为兼具技术炫技、复古探索和幽默想象的实验。
