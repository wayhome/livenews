Why not object capability languages?

作者: mike_hearn | 评分: 59 | 评论数: 14 | 发布时间: 2025-05-11 18:57
文章摘要

本文讨论了使用对象能力模型（object capability model）解决软件供应链攻击等安全问题的潜力与挑战。能力模型通过不透明的对象（如“魔法钥匙”）限制程序行为，防止未经授权的操作。尽管句柄、文件描述符和JWT token等都是能力模型的实例，但在单个程序内广泛应用该模型仍面临诸多困难。 文章分析了实现能力模型语言的难点，包括威胁模型的选择、防止组件篡改内存、跨语言互操作性等。例如，C/C++和动态语言如JavaScript、Python都不完全支持这一模型。作者通过Joe-E语言（Java的子集）展示了实现能力模型的具体要求，如去除反射、全局方法和可变全局变量等，以确保组件间的隔离性。 尽管Joe-E是研究项目，但其部分理念已融入Java模块系统中。文章最后指出，创建全新的编程生态系统非常复杂，但理解这些挑战有助于探索这一领域。

评论摘要
主要讨论点：如何在硬件和软件层面实现安全的代码执行环境，特别是在涉及能力模型（Capability-based model）和权限管理时。 不同观点： • Veedrac认为底层硬件的默认设置不安全，导致每次与硬件交互时都需要代理和中间语言，增加了复杂性。但他指出，如果代码执行默认是安全的，许多问题将迎刃而解，JavaScript的成功便是一个例子。 • Jauntywundrkind指出WASI系统库采用了基于能力的API设计，确保WebAssembly与外界交互时的沙盒特性，从而提升安全性。 • RainyDayTmrw将Rust的`unsafe`块与能力模型进行类比，认为可以在函数内部使用不安全代码，但对外仍保证安全。他认为这种方法有潜力，但尚未看到相关研究。 • Kumavis提到Caja及其后续项目HardenedJS和LavaMoat，这些项目旨在通过消除环境权限和限制npm包的全局能力来保护JavaScript应用。OCapN项目则致力于标准化分布式能力协议。 • Salmonellaeater为文章中的"god object"模式辩护，认为这种模式与依赖倒置原则类似，只需在初始化时使用一次，之后不再引用，因此不应被视为问题。 • Vvanders提到Android的Binder机制，这是一种类似于对象能力模型的RPC机制，能够在不同进程间安全地传递能力。 • Duncanbeevers提到BreakApp项目，该项目通过修改Node.js的`require`函数来指定安全范围，从而提供了一些新的供应链攻击防护措施。 • Rawkode提到Pony语言，这是一种较少被提及但具备能力安全特性的编程语言。 • Jerf认为，尽管能力模型问题很难解决，且目前主要停留在研究阶段，但可以通过一些简单的注解和外部工具来标记那些不需要特殊权限的库，从而减少攻击面。 • Jfriedensreich提到Workerd的隔离机制，认为这是向正确方向迈出的一步，尽管目前能力委托和降级功能尚不完善。 • Coolcase认为，移动操作系统如iOS和Android在权限管理上做得较好，而桌面系统则相对较差。他建议为库设计简单的能力系统，尽管不能解决所有安全问题，但可以减少潜在的攻击面。 • Hyperpape对Joe-E为何禁止使用`finally`关键字感到困惑，认为这是一个值得讨论的小问题。 • Jdougan提到Newspeak可能在这一领域有潜力。 • Burnt-resistor提到形式化验证方法，如应用于seL4的那些方法，认为提高安全性需要综合使用多种实践，而不仅仅是测试或单一解决方案。 补充讨论： • 讨论中涉及多个具体项目和语言，如Rust的`unsafe`、Pony语言、WASI、LavaMoat、BreakApp等，展示了当前在能力模型和安全代码执行方面的多种尝试和实践。 • 争议的焦点之一是如何在实际应用中平衡安全性和复杂性，特别是在现有语言和生态系统中实现能力模型。 • 另一个值得注意的讨论点是关于库的权限管理，如何通过简单的注解和外部工具来减少攻击面，尽管不能完全解决问题，但可以作为一种有效的权宜之计。

Booting the RP2350 from UART

作者: hugolundin | 评分: 63 | 评论数: 5 | 发布时间: 2025-05-11 14:26
文章摘要

本文介绍了如何通过UART引导Raspberry Pi的RP2350微控制器，以解决PWM通道和GPIO不足的问题。作者考虑过使用端口扩展器，但最终选择使用第二个RP2350作为扩展器。RP2350具有UART引导加载程序功能，可以通过简单的"解锁"模式和32字节数据块发送固件镜像。虽然固件需运行于SRAM中且每次启动时通过UART加载需要一定时间，但该方法简化了硬件设计。作者还编写了Python脚本用于发送固件，并讨论了数据传输速率和效率问题。最终目标是将RP2350的固件嵌入到主微控制器的固件中，以实现可靠的连接和引导。

评论摘要
主要讨论点：RP2040子芯片的固件更新和启动方式的优化方案 不同观点： • [bluehex] 提出使用 UART 启动作为传输固件更新的手段，以解决每次启动需要通过 UART 加载的问题。其建议是通过 UART 传输一个小程序，该程序接收更大的固件映像并写入闪存，以供后续启动使用。这种方法旨在解决作者提到的 SRAM 和启动时间的问题。 • [vardump] 支持通过发送二进制 stub 来设置快速的 CPU 时钟速度，并在 RP2350 端解压固件，以提高速度。其引用了旧式计算机的解压技术，如 C64 和 Amiga 的解压工具，以及 Fabrice Bellard 的 LZEXE。 • [duskwuff] 提出可以通过 SWD 启动 RP2040，尽管编码上会更困难，但技术上是可行的。 • [mrheosuper] 提到一些 BLE 控制器的启动方式也类似于上述讨论的方式。 • [mschuster91] 以幽默的方式评论了手动焊接组件的外观，并感谢了文章的撰写。 补充讨论： • [bluehex] 和 [vardump] 都提出了解决固件更新和启动速度的方案，但侧重点不同。[bluehex] 关注于通过 UART 传输固件以解决实际应用中的问题，而 [vardump] 更关注于通过解压技术提高速度。 • [duskwuff] 提供了一种替代的启动方式（SWD），尽管实现难度更大，但提供了另一种技术思路。 • [mrheosuper] 的评论指出了类似技术的实际应用案例，增加了讨论的实用性和参考价值。 • 争议的焦点可能在于哪种方案更为实际和高效，特别是在开发难度和速度优化之间的权衡。

文章摘要

GlassFlow for ClickHouse Streaming ETL 是一个实时流处理工具，旨在简化 Kafka 到 ClickHouse 的数据管道构建与管理。其主要功能包括实时数据去重和时间序列连接，支持配置时间窗口（最长7天）和去重/连接键。它内置 Kafka 连接器，通过 NATS-Kafka Bridge 自动提取数据，并优化了 ClickHouse 数据写入。该工具提供直观的web界面，支持Docker部署和本地开发，具备高吞吐量处理能力和简化的管道配置流程，适合数据工程师使用。

评论摘要
主要讨论点：GlassFlow项目与ClickHouse中ReplacingMergeTree (RMT) 的比较，以及对去重机制的实现细节和适用场景的讨论。 不同观点： • hodgesrm：认为RMT虽然需要在读取时付出一定代价，并且需要针对性能优化设计模式，但其去重行为相对容易理解。相比之下，GlassFlow的去重机制可能需要更多的细节来证明其优势。 • caust1c：对去重系统的可扩展性表示怀疑，指出需要考虑网络延迟、数据源流的 partitioning/sharding、以及处理写入目标失败等问题。他提到曾维护过类似的去重管道，对细节不足的系统持谨慎态度。 • ram_rar：提出RMT可以有效解决去重问题，并通过查询时过滤进一步优化，质疑GlassFlow的必要性。 • YZF：关注如何避免ClickHouse中的重复行，提出插入失败和去重服务器崩溃等场景下的数据一致性问题。 • maxboone：对NATS直接流配置表示关注，询问通过NATS桥接Kafka的配置工作量。 • saisrirampur：询问去重是否仅针对整行重复，还是可以处理部分列冲突，并指出若在数据摄入ClickHouse前去重，可能仅能处理前者。 • darkbatman：关注项目的负载测试结果，希望了解其在高规模下的表现。 • the_arun：询问项目为何仅限于ClickHouse和Kafka，是否能通用化，并关注默认负载测试情况。 • brap：赞赏设计，关心是内部开发还是外包。 • oulipo：对去重的具体场景表示疑惑，询问Kafka或ClickHouse为何不能通过主键自行去重，并描述IoT设备数据批量摄入的用例。 补充讨论： • 争议焦点：GlassFlow去重机制的必要性及其相对于RMT的优势。 • 关注点：去重系统的可扩展性、失败场景下的数据一致性、系统负载测试结果、以及通用性。 • 实用场景：包括Kafka重复行发送、IoT设备数据批量摄入等。

JEP 515: Ahead-of-Time Method Profiling

作者: cempaka | 评分: 92 | 评论数: 6 | 发布时间: 2025-05-11 14:43
文章摘要

JEP 515 旨在通过提前收集方法执行概要信息来改善Java应用程序的预热时间。具体做法是在应用程序的"训练运行"阶段收集方法概要信息，并存储在AOT缓存中，以便在生产运行时直接使用。这使得HotSpot JVM在应用启动时即可利用这些信息进行即时编译（JIT），从而更快达到峰值性能。该方案不改变应用代码，也不引入新的约束或工作流，而是利用JEP 483引入的AOT缓存机制。通过提前收集概要信息，应用在生产环境中的预热时间大幅缩短，同时JVM仍会在运行时继续进行动态优化，确保适应生产环境中的行为变化。

评论摘要
主要讨论点：JEP 对 Java 标准库及 JVM 性能提升的影响，以及与其他技术或语言的比较和关联。 不同观点： • [motoboi] 认为该 JEP 如果能够使 Java 标准 API 的大部分实现 AOT 编译，将极大提升 Java 程序的运行速度，尤其是在 Stream API 等已经成熟且广泛使用的部分。他还提到，虽然 JVM 的 JIT 编译已经非常高效，但 AOT 可以使 Java 程序更加敏捷。 • [indolering] 指出 OpenJ9 已经具备类似的功能，并表示看到解释型语言和编译型语言之间的界限变得模糊是很令人欣喜的。 • [rst] 从历史角度出发，提到这个优化思路与最早的优化编译器 Fortran I 有相似之处，尤其是通过模拟流图来检测热点并进行优化的方法。 • [tikkabhuna] 提问该 JEP 是否与 Azul Zing 的 ReadyNow 功能类似或相同，暗示可能存在功能重叠或竞争关系。 • [nmstoker] 提出是否可以将这种方法应用于 Python 的性能优化中，尤其是 Faster Python 项目，虽然他也提到这可能已经被考虑过。 • [mshockwave] 建议除了存储配置文件外，还可以缓存一些本地代码，以消除热点函数的 JIT 开销。他还补充说明，这一点在 JEP 的“替代方案”部分被描述为未来的工作方向。 补充讨论： • 该 JEP 涉及的 AOT 编译技术与历史上其他语言的优化编译技术（如 Fortran I）有概念上的相似性。 • 不同 JVM 实现（如 OpenJ9 和 Azul Zing）之间的功能比较和竞争。 • 讨论了该技术在其他编程语言（如 Python）中应用的可能性和潜在价值。 • 对未来工作方向的建议，如缓存本地代码以进一步优化性能。 争议焦点： • 该 JEP 与 Azul Zing 的 ReadyNow 功能是否存在相似性或竞争关系（tikkabhuna 的提问）。 • 该技术的创新性与历史上已有优化技术的相似性（rst 的评论）。

An Introduction to Solid Queue for Ruby on Rails

作者: amalinovic | 评分: 105 | 评论数: 10 | 发布时间: 2025-05-08 07:58
文章摘要

Rails 8引入了一个新的背景任务处理库——Solid Queue。虽然已有多种队列系统如Sidekiq和Resque，但Solid Queue旨在减少对额外基础设施（如Redis）的依赖，仅使用数据库。其主要优势在于无需额外依赖，同时满足Rails开发者对性能、可靠性和兼容性的高要求。 Solid Queue包含两个核心组件：Jobs和Workers。Jobs是ActiveRecord模型，用户通过它与系统交互，定义和执行后台任务。Workers则负责执行这些任务，根据配置生成并后台运行。 Solid Queue使用多个数据库表来管理任务的不同状态，如准备、调度、执行和失败。任务的生命周期从创建、入队到执行，所有操作都依赖数据库表记录。 总之，Solid Queue通过仅依赖数据库实现背景任务处理，简化了Rails应用的部署和运维，同时满足高效和可靠的要求。

评论摘要
主要讨论点：Solid Queue及其替代方案在性能、架构复杂性和可操作性方面的比较 不同观点： • [shayonj] 认为Solid Queue在性能上存在瓶颈，特别是在高并发任务处理（数十万任务/秒）时，无法与Sidekiq + Redis组合的性能相比。他建议使用PG进行编排和决策，同时保留Sidekiq + Redis作为消息总线以提高任务处理速度。 • [Justsignedup] 支持简化基础设施复杂性的哲学，认为对于小型Rails应用，只需管理数据库比管理复杂的系统更容易。虽然在大规模扩展时可能需要更复杂的架构，但在小规模场景下没必要过早引入复杂性。 • [cpursley] 建议使用pgmq库，认为这是一个有前景的方案，并提到一个基于pgmq和Supabase Deno edge functions的项目（pgflow.dev），表明在其他技术栈中也能实现类似功能。 • [bdcravens] 更偏好Good Job，认为它比Solid Queue更接近Sidekiq的功能和特性，尤其是在用户界面和功能对等方面。 • [latchkey] 提出可以使用GCP Cloud Tasks来减少操作开销，通过实现HTTP端点来提交和处理任务，避免使用workers/listeners，简化架构。 • [rietta] 支持使用delayed_job，曾经使用过Sidekiq + Redis，但因复杂事务逻辑导致的时序问题和解决方案复杂性而放弃，认为如果数据库是唯一的状态来源，问题会更少。 • [neerajdotname2] 提到对"UPDATE SKIP LOCKED"机制的理解不足，并为此写了一篇博客进行解释。 • [wang_zuo] 询问是否有在其他语言或框架中实现类似功能的尝试。 • [Trasmatta] 表示将继续使用Sidekiq，认为其API易用、速度快、可扩展性强，且Redis依赖在当下也变得非常简单。 • [nwhnwh] 对高层次接口持怀疑态度，认为其不够“solid”（可靠）。 补充讨论： - 性能是主要争议焦点，尤其是在高并发场景下Solid Queue与Sidekiq + Redis的比较。 - 基础设施复杂性和操作开销是另一个讨论重点，不同开发者在选择技术栈时对此有不同偏好。 - 提到了具体技术如pgmq和Good Job作为Solid Queue的替代方案，并讨论了各自的优缺点。 - 有人提出使用云服务（如GCP Cloud Tasks）来简化架构，表明对托管服务的倾向。
