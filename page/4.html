作者: mgh2 | 评分: 3 | 评论数: 0 | 发布时间: 2026-07-05 04:18
文章摘要

加州理工学院研究团队开发了一种革命性的脑机接口技术，使用功能性超声（fUS）来读取大脑活动。与现有需要植入电极的侵入性脑机接口不同，这项新技术是微创的，可以100微米的分辨率精确映射大脑深层区域的神经活动。 该技术通过超声波测量大脑血流的微小变化来检测神经活动——当大脑某区域变得活跃时，血流会增加。研究证明，这种方法可以准确预测运动意图，其精度接近电极植入技术，但创伤性大大降低。 这项突破为开发高性能、低侵入性的脑机接口开辟了新路径，有望让更多瘫痪患者受益，而无需承受脑部手术的风险。研究成果已发表在《Neuron》期刊上。

评论摘要
**主要讨论点：**西雅图市中心办公空间空置率高达37%（全美平均23%）的原因及解决方案 **不同观点：** • **金融机制论**（Schiendelman）：问题根源是商业地产的融资结构，而非政策失败。西雅图小公司租赁多、租期短，租户流失后房东因贷款合约无法降价，导致空置。这是市场滞后现象，新业主以合理价格收购后可正常出租 • **税收政策论**（hnburnsy, 33MHz-i486, a34729t）：西雅图对营业额超10万美元企业征收总收入税（不扣除成本），加上工资税，到2030年高收入边际税率将达56%，为全国最高。这是企业外流的主因 • **多因素综合论**（vessenes, a34729t）：商业环境恶劣、城市品质下降、政府对商业敌意、东岸贝尔维尤等周边城市竞争力更强（学校更好、税收更低）、亚马逊近十年持续将招聘转向东区办公室 • **乐观派**（wxw）：西雅图仍是优秀科技城市，相信会复苏 • **结构性变革论**（Animats）：提出根本问题——社会是否已达"办公空间峰值"，真的需要这么多办公室吗？ **补充讨论：** 争议焦点在于归因——是市场机制滞后、税收政策失当，还是城市竞争力整体下降。解决方案上，多人建议将办公楼转为住宅，但面临分区法规障碍。租金僵化（贷款合约限制降价）加剧了空置问题。

文章摘要

这篇文章详细解释了Linux系统中htop/top命令显示的各项指标含义： **Uptime（运行时间）**：显示系统持续运行的时间，数据来自`/proc/uptime`文件。 **Load Average（负载平均值）**：显示1分钟、5分钟和15分钟的系统平均负载，数据来自`/proc/loadavg`文件。负载值并非简单的CPU使用率，而是统计"运行中"和"不可中断等待"的进程数量，使用指数衰减移动平均算法计算。 **进程信息**：显示当前运行进程数/总进程数。"运行中"指正在CPU上执行或等待CPU调度的进程，不包括休眠(sleep)状态的进程。 文章还介绍了使用`strace`工具追踪程序读取系统文件的方法，帮助理解这些指标的数据来源。

评论摘要
主要讨论点：Linux系统监控工具的选择与使用技巧，重点是htop及其替代方案 不同观点： • **工具升级派**：推荐迁移到更现代的btop，认为其界面更好、功能更丰富（显示功耗、GPU、网络等信息），两位用户明确建议替换htop • **优化配置派**：主张通过调整htop设置提升体验，建议禁用用户线程显示（减少混乱）、启用进程树视图（更易追踪进程来源，如编译器进程），认为这应成为默认配置 • **替代工具派**：提出其他监控方案，如procs（提供差异化报告和系统级报告）、nmon（特别适合磁盘吞吐和I/O监控） • **基础应用派**：表示主要用htop查找PID和CPU占用，对其他功能了解有限；也有人分享基本技巧如top中用">"按内存排序 补充讨论： 一位用户深入解释了内存指标的常见误区：虚拟内存（Windows任务管理器默认显示）不可靠，常驻内存才是准确指标。内存映射文件会虚增虚拟内存数值但实际未占用物理内存，Chrome曾因用户误解而放弃使用内存映射。这反映出工具显示指标的选择会直接影响用户判断。

It's not me, it's the compiler

作者: SVI | 评分: 77 | 评论数: 9 | 发布时间: 2026-07-01 07:41
文章摘要

这篇文章讲述了作者在重构 Rust 编写的 JavaScript 引擎解析器时遇到的一个神秘 bug。作者将一个带有条件分支的函数 `consume_test` 重构为更简洁的版本，使用 `x as u32` 进行类型转换来替代 if-else 分支。重构后，解析 for 循环语句时出现了错误。但当作者明确使用 `if x { 1 } else { 0 }` 替代 `x as u32` 时，代码又能正常工作了。 作者对此感到困惑，因为 `bool as u32` 应该是标准的类型转换方式。在排除了自己的代码问题后，作者怀疑这是一个罕见的编译器 bug。文章标题"It's not me, it's the compiler!"反映了程序员常说但通常是错误的抱怨，而这次作者相信自己遇到了真正的编译器问题。

评论摘要
**主要讨论点：** Rust编译器的miscompile bug（误编译），这是一个被标记为p-critical和i-miscompile的严重问题，讨论集中在bug的严重性、成因以及编译器优化的哲学。 **不同观点：** • **激进的优化反对派（norir）：** 认为死代码消除不应自动进行，应该改为警告让开发者自己决定。主张编译器应显示优化建议而非静默应用，以防止误编译和缩短编译时间。这是最具争议性的观点。 • **审慎的关注者（rtpg, bayesnet）：** 强调这类bug的稀有性（61K issues中仅7个同时标记为p-critical和i-miscompile）和危险性，质疑为何能在经过严格审查的MIR优化管道中出现，尤其是在safe code中容易触发。 • **代码可读性优先（recursivedoubts）：** 认为原始的if语句版本虽然稍长，但更清晰易调试，暗示过度优化可能损害代码质量。 • **经验分享者（jackmott42, bitwize, Panzerschrek）：** 从个人经历验证编译器bug确实存在但罕见。jackmott42提到从"编译器永远是对的"信念到实际发现多个编译器bug的转变。 **补充讨论：** 评论整体反映出对编译器优化本质的深层思考——优化极易出错，可能大多数错误优化因为会在早期破坏某些功能而被发现，这种"幸运"机制可能是当前质量保证的隐藏支柱。

文章摘要

这是加缪《断头台旁的沉思》的开篇。文章讲述作者父亲的经历：1914年前，一名农场工人残忍杀害农民一家包括儿童，父亲认为死刑太轻，决定首次观看行刑。然而目睹斩首后，父亲回家即呕吐不止——他看到的不是正义伸张，而是被砍头的颤抖身体。 加缪由此质疑死刑的正当性：如果极刑让正直公民感到恶心而非安慰,它如何能维护社会秩序？死刑本身和犯罪一样令人厌恶，是在原罪上增添新的污点。文章还指出社会对死刑的回避——官员和媒体使用委婉语，人们像谈论癌症般避讳直言。加缪批判将死刑美化为"令人遗憾但必要"的虚伪论调，揭示其本质的野蛮性。

评论摘要
**主要讨论点：** 死刑的道德正当性与国家权力问题 **不同观点：** • **支持死刑但警惕国家权力**（quantummagic）：认为某些罪犯确实应该被处死，死刑本身并非不道德。核心担忧不在于死刑制度本身，而在于授予国家这种生杀大权的危险性。明确反对"死刑与犯罪同样令人厌恶"的观点。 • **哲学反思视角**（winter_blue）：通过引用加缪1957年的反死刑论文《对断头台的反思》，暗示死刑可能在道德上存在问题。加缪在该文中论证死刑与其要惩罚的犯罪同样令人厌恶。 **补充讨论：** 这场讨论揭示了死刑辩论中的经典张力：即使认为某些罪行"应该"受到死刑惩罚，将执行权力交给可能出错或滥用权力的国家机构，仍然构成根本性的实践困境。这种"原则上支持但实践中反对"的立场，与纯粹的道德反对（如加缪的立场）形成对比。
