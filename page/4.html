Stdio(3) change: FILE is now opaque

作者: gslin | 评分: 140 | 评论数: 11 | 发布时间: 2025-07-20 18:18
文章摘要

2025年7月17日，OpenBSD的-current分支中，stdio(3)的FILE类型结构体被设为不透明（opaque），相关库版本也已更新。具体改动包括将__sFILE定义移至libc/hidden/_stdio.h，并暂时保留某些符号以方便过渡，但这些符号将很快被删除。这一重大变更影响了许多系统组件，建议从源代码构建的用户使用快照升级以顺利过渡。

评论摘要
主要讨论点：FreeBSD 中 FILE 类型的非透明性及其相关更改 不同观点： • **loeg** 提到 FreeBSD 曾尝试将 FILE 类型变为不透明，但更改被回退，目前在主分支中仍为非透明。他提供了相关的代码提交链接以支持其观点。 • **JdeBP** 认为，当对 C 库进行此类更改时，首先应关注 stdin、stdout 和 stderr 的变化，因为这些标准流的历史实现方式可能会导致链接问题。他指出，改变这些标准流可能导致未重新编译的代码无法链接。 • **Cadwhisker** 质疑更改的原因，询问是否出于安全原因或为未来变化做准备，强调好的评论应说明“为什么”。 • **abnercoimbre** 表示自己一直将 FILE 视为不透明类型，但没想到有人会深入探究其内部结构，暗示对 FILE 内部的依赖可能是不好的实践。 • **severino** 引用了 Linux/GNU 中的代码，询问这种定义是否意味着类型是不透明的，提供了具体的代码示例。 • **cperciva** 补充，非不透明 FILE 允许与将 FILE 放入结构中的代码兼容，因为不透明 FILE 没有大小。 • **p0w3n3d** 质疑为何要依赖 FILE 的内部结构，认为这是一种不良实践。 • **xpressvideoz** 对提交信息和公告文章中未提及理由表示不满，认为这种做法令人不安。 • **notepad0x90** 赞赏 *bsd 的勇气，认为它们不惧变化，而 Linux 应从中学习，并指出 Windows 因不愿打破旧有体系而导致的问题。 • **somat** 通过对比 OpenBSD 和 Linux，指出 Linux 在更改 ABI 方面的困难和顾虑，并分析了 Linux 的特殊情况，如闭源软件的支持和项目规模的影响。 补充讨论： • **quotemstr** 提到 CHERI 可以在无需切换地址空间的情况下防止对内部数据结构的访问，为讨论提供了一种技术解决方案。 争议焦点： • 主要争议在于是否应将 FILE 类型设为不透明，以及依赖 FILE 内部结构是否为不良实践。部分参与者认为更改应有明确理由，并对当前做法表示担忧。

SIOF (Scheme in One File) – A Minimal R7RS Scheme System

作者: gjvc | 评分: 60 | 评论数: 4 | 发布时间: 2025-07-19 11:17
文章摘要

SIOF（Scheme In One File）是一个用于R7RS Scheme语言的轻量级解释器，全部代码包含在一个C源文件（siof.c）中。它具有高度可移植性，不依赖特定操作系统、硬件或编译器特性，无需额外构建工具或依赖包，只需使用C编译器编译即可。SIOF支持基本的Scheme特性，如精确垃圾回收、尾递归、call/cc、dynamic-wind、多返回值、卫生宏和库系统，兼容R7RS-small标准，但有一些限制，如不支持大数、Unicode和某些高级特性。SIOF提供交互式REPL环境，支持从.sld文件动态加载库，所有R7RS-small的过程和语法形式都直接暴露在交互环境中。
