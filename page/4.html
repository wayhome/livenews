More honey bees dying, even as antibiotic use halves

作者: pseudolus | 评分: 203 | 评论数: 18 | 发布时间: 2025-07-29 19:37
文章摘要

尽管加拿大限制了养蜂业中抗生素的使用，蜜蜂的死亡率仍在上升。一项由圭尔夫大学研究人员主导的研究发现，随着抗生素使用减半，蜜蜂的越冬死亡率反而从不到20%上升到超过40%。研究表明，抗生素的减少可能导致蜜蜂对致病微生物的抵御能力下降，因为它们的微生物群受到破坏。此外，二氧化氮（NO2）污染也被发现是蜜蜂死亡率上升的一个意外因素，因为它干扰了蜜蜂的觅食能力。研究人员呼吁采用“同一健康”方法，综合考虑人类、动物和环境健康，寻找替代抗生素的解决方案，如益生菌。目前，加拿大正在开展一个全国性项目，研究蜜蜂的微生物群以应对这一问题。

评论摘要
主要讨论点：蜜蜂和传粉者的保护及其面临的威胁 不同观点： • JumpCrisscross认为，蜜蜂并非北美本土物种，它们的引入对本地传粉者如大黄蜂构成威胁，导致生物多样性下降。此外，工业化农业依赖蜜蜂传粉，而个人在后院放置蜂箱可能会无意中破坏本地蝴蝶和大黄蜂的种群。 • mushroomba指出，现代养蜂实践类似于工厂化养殖，并提到Tim Rowe的"The Rose Hive Method"利用进化来改善蜜蜂的活力。然而，由于对蜂蛰过敏，他无法实践这些方法，并认为商业养蜂的当前实践无法持续。 • miellaby批评某些文章将问题归因于抗生素，而不是广泛认可的新烟碱类农药，指责农业行业的误导性声明。 • imzadi认为，停止使用抗生素可能会导致蜜蜂健康状况下降，因为之前的抗生素使用可能已经杀死了健康的细菌。 • alionski强调，工业和政府应 equally 关注野生蜂的衰退，指出“拯救蜜蜂”实际上是指野生蜂，而非蜜蜂。 • ceedan引用研究指出，蜂群崩溃症可能是由于瓦螨传播的病毒和/或杀虫剂引起的。 • endo_bunker认为，抗生素与蜂巢死亡的关联可能是因为抗生素通常用于不健康的蜂巢。 • horacemorace提到，过去夏天每周都需要清理挡风玻璃上的虫渍，而现在不再需要，暗示昆虫数量的减少对生态系统有巨大影响。 • westurner引用研究指出，病毒和瓦螨是导致蜜蜂 colony collapse 的主要原因。 • giantg2认为，细菌问题对养蜂人来说并不是主要问题，除了可以治疗的欧洲 foulbrood 外，只有美国 foulbrood 是无法治疗的，并提到一些关于生物群研究的有趣内容。 • thebees对非洲化蜜蜂在某些地区成为主要的蜂蜜生产者的现象感到有趣。 • animitronix和7734128认为，问题主要是杀虫剂而非抗生素。 • moomoo11建议购买和支持有机产品，认为自然生长的产品会更好。 • more_corn简洁指出，问题在于杀虫剂。 补充讨论： - 争议的焦点在于蜜蜂健康问题的主要原因：抗生素、病毒、瓦螨还是杀虫剂。 - 不同观点中，有人关注蜜蜂的工业化利用对本地物种的影响，有人讨论现代养蜂实践的可持续性，还有人关注具体病害和农药的影响。 - 支持有机农业和减少化学药剂使用的建议也被提出作为解决方案。

Maru OS – Use your phone as your PC

作者: fsflover | 评分: 181 | 评论数: 28 | 发布时间: 2025-07-29 19:24
文章摘要

Maru是一个将手机与桌面计算结合的操作系统，可以让手机通过连接HDMI屏幕和键鼠，变身为一个轻量级的桌面电脑。它基于Android Oreo构建，无预装软件，运行流畅。当手机连接显示器时，Maru会自动启动桌面模式，并在5秒内启动。桌面模式支持多任务处理和生产力应用，底层为Debian Linux，可自由定制。手机和桌面环境共享存储和网络连接，实现无缝切换。Maru让个人计算更简单，所有工作在一台设备上即可完成。

Playing with Open Source LLMs

作者: zer0tonin | 评分: 54 | 评论数: 8 | 发布时间: 2025-07-29 18:36
文章摘要

本文介绍了作者探索使用大型语言模型（LLM）在终端中进行代码编写的过程。作者首先提到当前流行的工具Claude Code，虽然功能全面，但作者担心被绑定到不盈利公司的工具上。因此，他转而寻找开源替代方案。经过尝试，作者选择了Qwen3:8b模型，该模型由阿里巴巴开发，支持现代AI工具，并且在本地运行良好。作者使用Ollama搭建本地API来运行LLM，并通过Aider实现与模型的配对编程。Aider允许用户通过命令行与模型交互，指导其修改代码、运行检查工具并提交更改。尽管模型并不完全自主，需要用户引导，但整体体验较为高效。

评论摘要
主要讨论点：开放大型语言模型（LLM）的使用、实用性、技术细节以及开源与免费软件的区分。 不同观点： • roadside_picnic认为开放模型最有价值的地方在于其透明性，用户可以深入了解和修改模型的内部结构，而不仅仅是运行它们。他分享了几个有趣且有教育意义的技术项目，如实现推测解码和强制结构化输出。 • simonw则从实用角度出发，认为在实际操作中，使用LLM生成代码的效率低于手动编辑，尤其是在使用较小模型时，时间和精力成本较高。 • v3ss0n指出模型选择的重要性，认为应该使用更好的模型如qwen3 8b-14b，而不是使用Deepseek R1 8B，后者是Qwen2的蒸馏版本。 • channel_t认为这种实验具有教育价值，但最终可能还是会转向使用大公司拥有的闭源模型。 • runningmike对使用开源机器学习工具的更新表示赞赏，认为这节省了大量时间。 • BoorishBears澄清Deepseek R1 8B的归属问题，指出其并非真正的Deepseek产品，类似于自己微调Llama并不意味着成为Llama的创造者。 • 44za12以讽刺的语气表示对开放源LLM的失望，认为其表现不佳，自己的工作因此更加安全。 • lrvick强调区分 freeware 和开源软件的重要性，指出只有所有源代码在OSI许可下发布并可重现的软件才是真正的开源软件。 补充讨论： • 模型选择和性能表现是讨论的一个焦点，尤其是较小模型在实际应用中的局限性。 • 开源模型的透明性和教育价值得到部分用户的认可，但也有人认为最终可能还是会依赖闭源的大模型。 • 开源与免费软件的区分在技术社区中是一个重要的讨论点，lrvick提供了明确的定义和标准。

Show HN: A GitHub Action that quizzes you on a pull request

作者: dkamm | 评分: 81 | 评论数: 16 | 发布时间: 2025-07-29 18:20
文章摘要

**PR Quiz** 是一个 GitHub Action，利用 AI 根据 pull request 生成测验，帮助开发者检验对代码的理解。它要求用户拥有 OpenAI API Key 和 ngrok 认证 token，并在 GitHub 仓库中设置为 secrets。当 pull request 通过审核后，系统会触发测验生成，并在临时 web 服务器上通过 ngrok 提供访问。测验有时间限制和尝试次数限制，还可以排除特定文件。该工具确保代码不会发送给第三方，仅与 OpenAI 模型交互，也可修改为支持自托管模型。

评论摘要
主要讨论点：AI生成代码的理解和审核问题 不同观点： • [klntsky] 认为大型语言模型（LLMs）在理解原创且涉及复杂数学技巧的代码时表现不佳，但对于大多数应用来说可能足够好。他提出了一个问题：如果AI生成代码出错，工作流程该如何处理？ • [sunrunner] 强调不仅要理解AI生成的代码，还要理解其他人类编写的代码。他指出有效的代码审查需要审查者具备对任务的预先心理模型，否则审查更像是模糊的标准 compliance。他质疑通过问答式互动能获得多少理解。 • [azhenley] 提到在2019年有一个类似的NSF资助项目，通过程序分析来验证开发者对自己代码的解释。该项目最初应用于课堂设置，并提供了一篇相关论文的链接。 • [robotsquidward] 和 [frenchie4111] 以幽默的方式评论了当前开发环境的变化和未来可能出现的工具。 • [throwaway889900] 开玩笑地建议提交一个删除该操作的PR，质疑如果开发者不审查代码，他们是否会注意到这种更改。 • [rmnclmnt] 对代码被发送到模型提供商（如OpenAI）的隐私声明表示担忧，认为这类似于GDPR之前移动应用 harvesting 用户数据的时代。 • [donatj] 支持使用AI来审查非AI生成的人类编写的PR，指出当前很多人批准他们并不理解的PR，并分享了一个相关的愤怒推文。 • [drunken_thor] 认为制作机器人来问答其他机器人是一个噩梦。 • [hk1337] 和 [waynesonfire] 对该工具表示了一定的兴趣，但并不打算实际使用。 • [ElijahLynn] 认为这个工具实际上可能非常有用。 • [henriquegodoy] 询问是否可以自动化回答PR问题的过程。 • [h4ck_th3_pl4n3t] 指出该工具假设LLMs知道他们在编码什么，但实际上他们不知道，这就是为什么我们需要PR审查。 补充讨论： • 隐私和数据安全问题被 [rmnclmnt] 提出，认为将代码发送给第三方模型提供商的隐私声明存在潜在问题。 • 工具实用性和自动化程度被多次提及，[henriquegodoy] 询问自动化回答PR问题的可能性，[donatj] 则强调当前代码审查中的问题并支持AI辅助审查。 • 对AI生成代码的理解和审核流程的有效性存在争议，[klntsky] 和 [h4ck_th3_pl4n3t] 对LLMs的理解能力表示怀疑，而[sunrunner] 和 [donatj] 强调了对人类编写代码的理解也同样重要。
