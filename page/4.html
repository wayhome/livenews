Are you expected to run five Python type-checkers now?

作者: ocamoss | 评分: 123 | 评论数: 20 | 发布时间: 2026-06-08 12:24
文章摘要

这篇文章讨论了Python库维护者如何应对多个类型检查器（mypy、Pyright、Pyrefly等）的问题。 **核心观点**：库维护者应该优先在测试套件上运行尽可能多的类型检查器，而不是在源码上。 **原因**： - 在源码上运行类型检查器只是测试内部逻辑 - 在测试套件上运行多个类型检查器，能确保公共API对使用不同类型检查器的用户都友好 - 用户关心的是公共API体验，而非内部开发实践 **实践案例**：文章以Polars库为例，说明在源码上适配多个类型检查器会导致大量type-ignore注释，代码变得混乱。但在测试套件上运行多个类型检查器则相对简单，因为只需确保按预期使用时不报错。 **结论**：测试公共API的类型正确性比检查内部实现更重要且更实用。

评论摘要
主要讨论点：Python类型检查系统的问题与争议 不同观点： • **应转向静态类型语言**：多位评论者认为既然要严格类型检查，不如直接用静态类型语言获得性能优势。特别指出动态语言在AI编码时代会衰落，因为静态类型提供了确定性。 • **类型系统设计缺陷**：批评Python类型检查是"事后添加"的，需要运行5个不同的检查器，大量使用ignore注解。对比TypeScript可无需ignore实现重载，认为Python类型生态"一团糟"。 • **理想类型系统应完全推断**：提出应基于代码约束自动推断类型，而非强制显式标注。只在需要收紧约束时才手动注解，避免"既付出duck typing代价，又失去duck typing灵活性"的困境。 • **工具选择分歧**：mypy被批评缓慢且检查不严格，Django切换工具会遇到"错误墙"；ty和PyCharm的类型检查器获得推荐；有人认为除uv、ty、ruff外其他工具都已过时。 补充讨论： 类型窄化规范不完善，API测试vs内部mock测试的类型检查策略不同，以及对`__eq__`返回非bool类型的质疑。有评论指出文章内容疑似AI生成。总体反映Python在大型代码库中的成熟度不足。

评论摘要
主要讨论点：Thunderbird在用户主目录下创建`~/thunderbird/`目录的问题，引发了关于软件污染home文件夹的广泛讨论。 不同观点： • **强烈反对派**：认为软件在home目录创建可见的系统级目录是不可容忍的行为，类比为"把汽车引擎放在乘客座位上"，担心普通用户误删造成问题。Ubuntu snap的`~/snap/`目录问题已存在十年未解决。 • **实用主义者**：提出各种变通方案——使用systemd监控并自动删除目录、创建`~/thunderbird/`空目录阻止程序创建、或干脆在home下建立`real_home`文件夹存放真正的个人文件，将~当作"垃圾场"。 • **无所谓派**：表示从不直接浏览home目录内容，通过路径直接访问文件，因此不受目录混乱困扰。 • **彻底放弃派**：因太多软件都这样做，保持整洁成为持续负担，已放弃维护干净的home目录。 补充讨论： 有用户指出Thunderbird还有其他问题（多标签页混乱、邮件格式、搜索不可靠），建议改用Betterbird或Evolution。部分用户期待Thunderbird能像Firefox那样支持XDG标准目录。技术方案包括使用systemd的PathExists监控和%h路径指定符。

Fooling Go's X.509 Certificate Verification

作者: hasheddan | 评分: 52 | 评论数: 7 | 发布时间: 2026-06-06 13:52
文章摘要

这篇文章讨论了X.509证书验证中的一个微妙问题。作者提供了两个看似相同的CA根证书，使用OpenSSL验证时都能成功，但在Go程序中使用`x509.Verify`时，第一个证书会失败并报"unknown authority"错误，而第二个证书则能正常验证。 通过字节级对比发现，两个证书仅有2字节的差异。问题的关键在于证书中Subject字段的编码方式不同：第一个使用`PrintableString`(0x13)，第二个使用`UTF8String`(0x0c)。Go的x509包在验证时对这种编码差异更加严格，导致即使证书在密码学上有效，也会因为字段编码不匹配而验证失败。这揭示了不同证书验证工具在实现标准时的细微差异。

评论摘要
主要讨论点：Go语言的X.509证书验证器要求Issuer和Subject字段字节完全相同，而非按RFC 5280规定的LDAP stringprep算法比较，这是否合理。 不同观点： • **支持Go做法**（agwa, woodruffw）：Go遵循旧规范要求字节完全相同是明智的。RFC 5280的LDAP stringprep算法极其复杂（需要Unicode归一化），在安全关键的验证器中实现风险大。CA/Browser Forum的基准要求也强制字节相同，Go的行为不会错误拒绝公开信任的证书。OpenSSL甚至无法正确实现该算法，只用了近似方法。 • **认为这是已知老问题**（pseudohadamard）：这是30多年前就知道的问题，Go重新发现了而已。DN的唯一规则应该是"只有memcpy()编码，只有memcmp()匹配"。Go尝试重新编码字符串已经落入陷阱，可能容易受到通过字符串编码技巧规避excludedSubtrees等攻击。 • **实践角度**（briansmith, entrope）：CA们清楚必须用相同方式编码以确保互操作性。这不算"欺骗"Go，只是触发了对可疑特征的拒绝。标题误导，Go的行为是正确的。 补充讨论：pqpdf指出这体现了格式复杂性带来的安全问题——多个实现对同一数据的不同解释会在边缘情况下产生安全隐患，X.509、PDF、Office文档都存在此类问题。fsmv确认相关讨论已在2019年结束。

Doing something that’s never been done before (2025)

作者: surprisetalk | 评分: 33 | 评论数: 12 | 发布时间: 2026-06-05 14:30
文章摘要

这篇文章探讨如何确保自己做的项目是原创的，而不是第50个做同样事情的人。作者提出四个关键因素： 1. **时间成本** - 项目耗时越长，别人完成的可能性越低 2. **难度** - 越困难或步骤越多的项目，完成者越少 3. **obscurity(小众性)** - 越冷门的想法，被他人发现的概率越低 4. **渐进依赖** - 后续步骤需要完成前置步骤才能发现，形成"漏斗效应" 结论：想做真正原创的事，就选择小众、耗时、高难度且具有未知性的项目。这些特征叠加越多，成为首创者的概率越高。

评论摘要
主要讨论点：追求原创性在工作和创作中的价值和必要性 不同观点： • **原创性被高估派**：originality会自然涌现，不必刻意追求。Ovid的例子说明所有故事都是重复和混搭，但依然有价值。不担心原创反而能让人更享受创作过程（Mikhail_Edoshin, mikrl） • **执行力优先派**：成功的决定因素是执行而非原创。大多数值得做的事情其实很明显，关键在于如何实现（Stevvo） • **个人成长派**：相比做"从未有人做过的事"，做"自己从未做过的事"可能更有满足感。即使不能商业化，成长过程本身就有价值（doodlebugging, gmuslera） • **重新发现派**：探索被遗忘的旧事物并加入自己的精神，同样充满乐趣和探索空间（chaps） 补充讨论：munificent指出原创清单的盲点——原创不等于有价值，用养狼獾、意面编织等荒诞例子说明。socketcluster作者分享了做原创项目14年仍"太早"的困境，说明沟通原创价值的难度。cortesoft用洗牌比喻讽刺"唯一性"的廉价。争议焦点在于：原创性本身是否值得作为目标？
