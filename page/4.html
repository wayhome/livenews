Show HN: Boo – Screen-style terminal multiplexer built on libghostty

作者: kylecarbs | 评分: 69 | 评论数: 8 | 发布时间: 2026-06-11 20:52
文章摘要

boo 是一个用 Zig 编写的终端多路复用器，类似 GNU screen。核心特性： 1. **会话持久化**：支持会话分离和重连（Ctrl-A d 分离，boo attach 重连） 2. **精准状态管理**：基于 Ghostty 的终端模拟核心解析所有输出，保存完整终端状态（内容、样式、光标、滚动） 3. **自动化友好**：提供 send、peek、wait 等命令，支持 JSON 输出，适合脚本和 AI 代理使用 4. **全屏管理界面**：boo ui 提供侧边栏管理所有会话 相比 tmux 更简单（只有会话概念），相比老旧的 screen 有现代化的终端仿真能力。典型自动化流程：创建无头会话 → 发送命令 → 等待输出稳定 → 读取屏幕状态 → 清理。

评论摘要
主要讨论点：一个基于 libghostty 的新终端复用器项目的评价与比较 不同观点： • 质疑派：README 缺乏与 screen/tmux 的对比说明，不清楚优势在哪（stereo）；功能限制明显，每个会话只能一个窗口，不如老旧的 screen（Scarbutt） • 竞品对比派：指出已有类似项目 zmx 和 Cmux，都基于 libghostty，询问差异化优势（ac29, johnfn） • 积极试用派：认可极简设计理念，计划测试（boltguo）；重度 tmux 用户，配合 ghostty 和 AI 编码使用，询问技术挑战（lavaman131） • 问题反馈派：macOS Sequoia 安装后出现 ReadOnlyFileSystem 错误，Zellij 不稳定，寻求替代方案（darkteflon） • 其他方案推荐：提到 herdr 作为 AI agent 场景下的终端复用器效果很好（asar） 补充讨论： 争议焦点集中在项目定位不清晰、功能完整度（单窗口限制）、与现有方案（zmx/Cmux）的差异化不明确。用户群体呈现分化：有技术探索者关注架构创新，也有实用主义者质疑实际价值。ghostty + AI 编码场景成为新兴需求点。

Faking keyword arguments to functions in C++

作者: ibobev | 评分: 26 | 评论数: 7 | 发布时间: 2026-06-09 12:05
文章摘要

这篇文章介绍了如何在C++中模拟Python的关键字参数特性。Python的关键字参数让API简洁易读，但C和C++原生不支持此特性，通过语言标准添加需要15-20年。虽然有宏和模板的实现尝试，但未普及。文章展示了利用现代C++特性的解决方案：通过传递一个结构体参数，配合designated initializers（指定初始化器），在额外的花括号内用点号语法指定字段值，其他字段使用默认值。这样就实现了类似关键字参数的效果，只需忽略额外的花括号即可。

评论摘要
主要讨论点：C++中实现命名参数/关键字参数的不同技术方案 不同观点： • **选项结构体派**：偏好使用options struct处理多个可选参数，认为designated initializers语法清晰，避免了位置参数的强制传递问题（aleksiy123） • **历史回顾派**：指出designated initializers是C99特性而非"现代"特性，C++20才引入；有人7年前在C项目中已使用此模式（kccqzy, p0w3n3d） • **性能关注派**：提醒跨翻译单元调用时struct传参有性能代价，因为结构体不适合寄存器形状，期待未来的调用约定改进（seeknotfind） • **术语纠正派**：认为文章混淆了"keyword arguments"（如SQL的DATEDIFF中的hour关键字）和"named arguments"（如C#、Swift中的命名参数）概念（DaiPlusPlus） • **语法黑客派**：分享通过运算符重载实现伪中缀运算符语法的技巧（如`5 3`），属于模板元编程的创意应用（akoboldfrying） 补充讨论：asalahli推荐了Richard Powell的2018年CppCon相关演讲作为学习资源。整体讨论涵盖实用性、历史演进、性能权衡和语言设计哲学等多个维度。
