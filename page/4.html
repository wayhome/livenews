FreeOberon – Open-Source, Cross-Platform, Free Pascal/Turbo Pascal-Like Language

作者: peter_d_sherman | 评分: 112 | 评论数: 8 | 发布时间: 2026-06-11 14:34
文章摘要

Free Oberon是一个跨平台的Oberon语言集成开发环境，采用经典的伪图形界面（蓝屏风格）。Oberon是Pascal和Modula-2的直接继承者，比它们更简洁且功能更强大。该项目提供Windows、macOS和Linux版本，包含IDE和命令行编译器Fob。安装需要Allegro、Git、GCC等依赖。使用时编写Oberon代码后按F9即可编译运行，支持多模块程序自动编译链接。源码保存在Programs目录，可执行文件在bin目录。当前版本1.1.0-alpha.7发布于2023年1月。

评论摘要
主要讨论点：关于FreeOberon项目和Pascal/Oberon语言的评价与回忆 不同观点： • **怀旧但不实用派**（SwellJoe）：承认早期使用Pascal/Turbo Pascal带来的"掌控计算机"的兴奋感，但认为这些语言虽然怀旧却并不优秀，一旦接触到C和Perl就不再使用它们 • **设计权衡派**（sys42590）：指出Modula-2/Oberon使用大写关键字是历史原因（当时缺乏语法高亮），但在现代开发环境中这种设计增加了不必要的输入负担，显得过时 • **IDE体验肯定派**（stuaxo）：认为这类Borland风格的IDE是最喜欢的类型之一，FreeOberon的实现"近乎完美" • **语言特性批评派**（rurban）：质疑项目为何没有引入Ada的Spark证明系统，认为这比图形功能更有价值 • **内容争议派**（lysace）：批评项目网站使用苏联最高苏维埃议会大厦的视频缩略图，认为这是"极其差的品味" 补充讨论：有用户分享了相关的怀旧资源（2021年的纯文本Pascal博客），另有用户关注Mac平台的安装说明，整体显示社区对小型强大语言的持续兴趣。

Windows 1.0 and the WinAPI, 40 Years Later

作者: jhack | 评分: 45 | 评论数: 11 | 发布时间: 2026-06-11 16:14
文章摘要

作者为Windows 1.0开发了一款Xonix游戏，以测试40年来WinAPI的兼容性。使用1980年代的Microsoft C 4.0编译器，他发现尽管Windows内部经历巨大变化，但核心API架构（窗口过程、消息循环、定时器等）remarkably稳定。同一份16位代码无需修改即可在Windows 1.x到32位Windows 10上运行，仅在Windows 95和64位系统上存在兼容问题。这展示了微软在保持二进制级兼容性方面的成功，证明了最初WinAPI设计的前瞻性——40年前编写的代码至今仍可识别、编译和运行。

评论摘要
主要讨论点：Windows API 的向后兼容性及其在软件开发中的价值 不同观点： • **赞赏 Windows 兼容性**：Windows 的向后兼容性是行业标杆，Win32 API 自1980年代以来保持稳定，旧代码仍能在现代系统运行，这种稳定性节省了大量开发时间 • **批评 Linux 生态**：Linux 缺乏接口稳定性，迫使开发者不断重写代码以适应新接口，浪费人力。GTK 被认为是 Linux 桌面的"原罪"，应该保持 Motif/CDE 等已建立的标准 • **质疑原文质量**：文章过于简略，缺乏深度和故事性，像是 AI 生成而非人类撰写。真正有价值的技术文章应该包含实现过程中的困难、有趣之处和思考 • **技术补充观点**：现代 React/移动项目升级后难以构建，与 Windows 的兼容性形成对比；标准化的重要性（如 M6 螺栓自1898年至今兼容）证明长期兼容并不难 补充讨论：有人提供技术细节（64位 Windows 不原生支持16位应用但可通过 OTVDM 运行；文中游戏应称为 Qix 而非 Xonix），也有人指出 WinAPI 虽功能扩展但未遵循 C 标准的类型规范。

Tribblix是由Peter Tribble创建的开源操作系统，基于illumos，融合复古风格与现代组件。最新动态：2026年6月12日发布Milestone 40版本；4月21日发布SPARC m34 ISO镜像，支持从m33升级。重要变化：已完全移除32位硬件支持。SPARC版本测试不足、硬件支持有限，但x86版本较为稳定，可供下载、安装和使用。

Python 3.14 garbage collection rigamarole

作者: eatonphil | 评分: 81 | 评论数: 13 | 发布时间: 2026-06-12 11:59
文章摘要

这篇文章讨论了Python 3.14版本的垃圾回收机制变化。Python 3.14.0引入了新的增量垃圾回收器，取代了传统的分代垃圾回收，旨在大幅减少大堆内存的暂停时间，并将垃圾回收代数从三代简化为两代（年轻代和老年代）。然而，由于用户报告了更高的内存使用问题，Python团队在3.14.5版本中撤销了这些改动，恢复了传统的垃圾回收机制。文章还介绍了Python的引用计数机制作为垃圾回收的基础，并通过构建两个不同版本的Python来演示和对比两种垃圾回收器的行为差异。

评论摘要
主要讨论点：Python 3.14 引入的增量垃圾回收器因内存占用问题被回退 不同观点： • **理解派**：_old_dude_ 认为这是 GC 在内存和 CPU 性能之间的常见权衡，暂停时间短必然需要更多内存，问题在于缺少配置选项 • **改进派**：vlovich123 认为不必完全回退，可通过按对象大小优先检查存活性等方式调优 3.14.4，不满意的用户可继续用 3.13 或手动调用 gc.collect() • **质疑派**：functionmouse 批评决策过程——既然上线就说明有充分理由认为新 GC 更好，那就不该轻易回退；如果理由不充分就不该发布 • **流程派**：watt 质疑如此重大改动为何未经正式 PEP 流程就进入 Python • **Python 批评派**：tannhaeuser 借此吐槽 Python 整体混乱缓慢，版本管理和打包是主流语言中最差的，Django 等框架充满隐式行为和魔法命名 补充讨论：zzzeek 作为 SQLAlchemy 开发者分享实际影响——3.14 的 GC 行为变化影响了测试套件，加上其他运行时 API 变更，3.14 过渡比 3.12/3.13 更颠簸，期待 3.14.5 能缓解问题。争议焦点集中在技术决策流程和权衡取舍的合理性。
