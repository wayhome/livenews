I used to prefer permissive licenses and now favor copyleft

作者: bpierre | 评分: 13 | 评论数: 0 | 发布时间: 2025-07-09 22:48
文章摘要

本文讨论了作者在开源软件许可方面的观点转变：从偏好宽松许可（如MIT）转向支持 copyleft 许可（如GPL）。宽松许可允许任何人自由使用和再发布作品，几乎没有限制；而 copyleft 许可则要求衍生作品也必须以相同许可发布，并公开源代码。作者早期倾向于宽松许可，因为希望最大化作品的采用和分发，并避免与企业的版权做法冲突。然而，随着开源软件变得主流，企业更愿意接受开源，作者逐渐转向 copyleft，认为它能确保自由共享的精神得以延续。此外，作者认为 copyleft 是一种利用版权保护自由的巧妙法律手段，符合其哲学观念。

Why LLMs Can't Write Q/Kdb+: Writing Code Right-to-Left

作者: gabiteodoru | 评分: 130 | 评论数: 23 | 发布时间: 2025-07-08 10:40
文章摘要

文章讨论了大型语言模型（LLMs）在编写q/kdb+代码时遇到的困难，主要问题在于评估顺序的不同。q/kdb+及其祖先语言如APL、J、k采用从右到左且无运算符优先级（RL-NOP）的评估方式，而LLMs在这种方式下表现不佳。例如，在处理表达式时，LLMs常混用Python和q的语法，导致错误。文章还指出，尽管右到左书写在代码中是必要的，但LLMs不擅长这种模式，因为它们的训练数据中q代码相对稀缺，且这种训练可能需要对模型架构进行重大修改。由于经济激励不足和训练数据的匮乏，行业不太可能为这些小众语言重新训练大型模型。文章最后提出了一种实用解决方案，即引入Qython作为桥梁，以帮助LLMs更好地处理RL-NOP语言的代码编写。

评论摘要
主要讨论点：LLM（大型语言模型）在处理非线性、不同语言评估顺序以及代码生成方面的能力和局限性。 不同观点： • clord认为当前的LLM在处理非线性思维（如从数据或返回值反向推导代码）时存在困难，并提出未来LLM是否能够处理非线性结构，或在非线性空间中工作再映射回线性输出。 • FeepingCreature指出，LLM在生成Python代码时，有时会插入不必要的导入语句，这是因为模型对可能需要的模块进行了对冲导入。 • am17an提到，LLM在生成代码时会插入随机的空白字符，似乎存在不同长度的空白标记。 • trjordan认为，训练数据集的大小也可能影响LLM的表现，并建议对不同语言的错误进行量化分析。 • briandw提到，扩散模型有可能解决非线性问题，例如扩散编码模型可以训练为从右到左生成代码。 • electroly对比了APL和NumPy的语法顺序，认为如果APL在今天开发，可能会更倾向于从左到右的评估顺序。 • i000指出，R语言的右赋值语法（`1 -> x`）似乎被LLM过度使用。 • sitkack建议，可以通过允许模型在一个方向上思考并反转输出结果来克服顺序问题。 • vessenes认为，从右到左的评估需要从末尾开始或在工作记忆中保持表达式，而这正是LLM不擅长的。 • aghilmort讨论了主流模型缺乏可逆因果推理能力，并提出了一些技巧和方法来改进模型在这方面的表现。 • knome提到，LLM在解析和生成某些自定义语言代码时，经历了从糟糕到逐渐改善的过程。 • tantalor认为，难以被LLM处理的语言也对普通大众不友好，建议语言设计者使语言更LLM友好，这也有助于提高语言的人类友好性。 • cess11指出，LLM在处理不同编程语言时存在混淆和不稳定的情况，并质疑使用LLM进行软件开发的实用性。 • leprechaun1066认为，LLM在处理如q语言等不同范式语言时的困难，不仅仅是因为评估顺序，而是因为训练数据和思维方式的局限。 补充讨论： • 讨论中提到了多种改进LLM处理非线性和不同评估顺序语言的方法，包括训练扩散模型、使用因果标记、优化输入输出格式等。 • 有争议的焦点在于LLM是否能够有效地处理非线性结构和不同评估顺序的语言，以及如何改进模型的表现。 • 语言设计者是否应该使语言更LLM友好，以同时提高语言的人类友好性，也是一个值得注意的讨论点。

Helm local code execution via a malicious chart

作者: irke882 | 评分: 113 | 评论数: 12 | 发布时间: 2025-07-09 05:49
文章摘要

文章描述了Helm中的一个高危安全漏洞（CVE-2025-53547），影响版本<= 3.18.3。当存在恶意构造的`Chart.yaml`和`Chart.lock`文件时，更新依赖项可能导致本地代码执行。如果`Chart.lock`文件被symlink到可执行文件（如`bash.rc`），更新依赖时会将恶意内容写入该文件，导致 unwanted 执行。该问题已在Helm v3.18.4中修复。临时解决方案是确保`Chart.lock`不是symlink。CVSS评分8.5，表示高严重性，需要用户交互但无需特殊权限。
