The 5 levels of configuration languages

作者: kaycebasques | 评分: 31 | 评论数: 19 | 发布时间: 2025-04-12 20:00
文章摘要

本文讨论了配置语言的五个层次，从简单到复杂，探讨了各自的特点和使用场景。 1. **Level 1：文件中的字符串** 最简单的键值对形式，如Linux的`/proc`文件系统。 2. **Level 2：列表** 文件内容为列表或键值对列表，如INI文件，支持更多表达能力，但不能嵌套。 3. **Level 3：嵌套数据结构** 使用JSON、YAML、XML等格式，支持复杂嵌套结构，但缺乏计算能力。 4. **Level 4：全功能编程语言（非图灵完备）** 支持计算但保证终止，如XSLT、Jsonnet、Dhall，工具支持较少。 5. **Level 5：完整编程语言** 使用Python、JavaScript等图灵完备语言，灵活但可能导致配置与代码间的循环依赖问题。 选择配置语言的原则是尽量使用较低层次以保持简单，但预测未来的需求往往困难。在同一层次内争论优劣并无太大意义。

评论摘要
主要讨论点：配置语言的级别和复杂性 不同观点： • **alexambarch** 认为 Terraform/HCL 作为第4级配置语言很流行，但当配置变得复杂时，会觉得不如直接使用第5级语言。第4级语言的定位比较尴尬，跳到第5级可能更值得。 • **susam** 提到一种可以称为“第0级”的配置模式，通过文件的存在与否进行配置，例如 `/opt/foo/foo.txt` 文件存在与否决定软件行为。 • **ks2048** 质疑“完全编程”和“图灵完备”的区别，认为即使是非图灵完备的语言，也可能因为其他原因导致配置文件挂起。 • **sgeisenh** 不认同只在同一级别内讨论，认为 YAML 比 JSON 复杂且容易出错，支持使用更简单的格式如 JSON 或 TOML。 • **ajb** 认为不应仅从“可表达性”单一维度来讨论，还应考虑“可验证性”等其他因素。 • **18172828286177** 反对将 JSON 和 YAML 视为差不多，认为 YAML 比 JSON 更容易使用。 • **ks2048** 补充支持 XML，尽管个人常用 JSON 或 YAML，但认为 XML 有更好的工具支持和明确性，尽管有些冗长。 • **chewbacha** 提到“配置复杂性时钟”的概念，指出这些配置形式是周期性的。 • **waynecochran** 介绍 Jsonnet 作为更强大的 JSON 形式，并提到在第5级语言中可以考虑使用 JavaScript。 • **throw0101d** 倾向于使用类似 ISC BIND 的配置方式，介于自由式配置（如 INI）和结构化配置之间。 • **bob1029** 认为 SQL 是一种优秀的第4/5级配置语言，具体取决于 SQL 方言和使用方式。 • **iambvk** 提出在第3级和第4级之间存在一种允许配置值之间交叉引用的级别，形成配置图。 • **chubot** 提供了一个不同的配置语言分类体系，并质疑“完全编程语言”的定义，认为像 Starlark 这样的语言不应因为图灵完备性而被分类，而应根据其快速执行和无外部I/O等特性。 • **rdtsc** 认为第4或第5级配置系统往往变得复杂，最终可能回归到第3级，形成一个循环。 • **kristopolous** 指出第3级和第4级之间的差距较大，并以 CSS 为例说明。 补充讨论： - 配置语言的级别争论主要集中在表达能力、复杂性和工具支持等方面。 - 争议的焦点在于是否需要图灵完备性，以及如何平衡配置文件的简洁性和功能性。 - 讨论中多次提到 JSON、YAML、XML 等常见配置格式，并对其优缺点进行了比较。 - 配置复杂性时钟的概念提示了配置语言的演化可能是周期性的。

Minestom – An open-source, lightweight Minecraft server built from the ground up

文章摘要

Minestom 是一个轻量级的服务器软件，具有 minimal（最少）的功能，这使得它更加高效，并允许用户根据需要轻松扩展其功能。这种设计使得 Minestom 更加灵活，适用于需要自定义和优化的 Minecraft 服务器环境。

评论摘要
主要讨论点：Minestom库的定位和目标用户 不同观点： • Tmpod认为Minestom的目标受众是开发非原版（non-vanilla）/生存类玩法服务器的开发者，例如小游戏、PvP对决等。他认为Minestom主要是一个开发者API，不是为普通终端用户设计的。 • 隐含的观点是Minestom与Mojang的原版服务器不同，它默认不包含任何功能，但提供了完整的API，让开发者可以自由创建各种类型的服务器。这暗示了Minestom的灵活性和定制性，适合那些希望创建独特游戏体验的开发者。 补充讨论： • Minestom的定位是提供一个高度灵活的开发框架，而不是一个开箱即用的服务器软件。这意味着其主要用户应具备一定的编程能力，能够利用API创建自定义功能。 • 例子中提到的小游戏和PvP对决服务器，说明这种灵活性特别适合需要大量自定义规则和玩法的服务器类型。 • 争议的焦点可能在于Minestom的复杂性与灵活性之间的权衡。对于希望快速搭建服务器的用户来说，Minestom可能过于复杂，而对那些寻求高度定制化的开发者而言，这正是其优势所在。 总结：讨论围绕Minestom库的定位展开，主要争议在于其高度灵活但缺乏默认功能的特性是否适合终端用户，还是更适合具备开发能力的用户群体。

p2panda是一个模块化框架，旨在构建注重隐私和安全的现代本地优先应用。它采用灵活的模块设计，兼容多种数据类型和CRDT，支持移动和桌面应用开发，避免框架锁定。通过使用如BLAKE3、Ed25519、QUIC等标准和技术，p2panda确保在离线和不稳定连接下仍能进行协作、加密和访问控制。项目包括多个库，如p2panda-net（网络发现）、p2panda-sync（数据同步）、p2panda-blobs（文件传输）等，并积极研究分布式数据类型。未来项目包括Aardvark文本编辑器和Toolkitty协调工具。社区参与和开源是p2panda的重要组成部分。

文章摘要

You might not need WebSockets

作者: hntrl | 评分: 135 | 评论数: 24 | 发布时间: 2025-04-11 22:27
文章摘要

WebSocket是一种允许客户端与服务器之间建立双向通信的协议，适用于实时应用。然而，WebSocket消息不具备事务性，无法确保消息的顺序和处理状态，这可能导致在处理状态对象或需要确认的消息时出现复杂性。例如，当操作导致错误时，由于消息流无法直接关联，错误处理变得困难。此外，WebSocket需要管理连接的生命周期，包括处理连接的打开、关闭和错误事件。对于需要确认的操作，使用HTTP等更具事务性的协议可能更为合适。WebSocket适合处理无需确认的消息，如心跳或键盘输入。因此，在某些情况下，可能并不需要WebSocket。

评论摘要
主要讨论点：WebSocket、HTTP2、SSE（Server-Sent Events）、长轮询（Long Polling）等通信技术在不同场景下的优缺点及适用性 不同观点： • [hombre_fatal] 认为在严肃的应用中使用 `send(message).then(res => ...)` 这种带有请求/响应周期的API是值得的，虽然WebSocket与HTTP服务器的整合确实有些混乱，但这些特性是可以习惯和适应的。相比EventSource，WebSocket的浏览器API更易用。 • [osigurdson] 反驳了关于视频流通过WebSocket实现的观点，指出视频流通常是通过范围请求（range requests）分块加载的，而不是通过单一的长连接实现的。 • [socketcluster] 认为HTTP2的服务器推送功能是后来添加的，增加了不必要的开销和安全挑战。WebSocket则是为双向通信设计的更简单的协议，提供了对数据流和连接状态的更好控制，并且在处理认证和访问控制时更为简便。 • [notpushkin] 提出可以使用SSE（Server-Sent Events）作为替代方案，认为它是一个更简单的选择。 • [toomim] 推荐了Braid-HTTP协议，认为它通过扩展HTTP事件流，能够提供一个健壮的状态同步协议。 • [collingreen] 表达了对在项目中使用WebSocket后看到相关讨论的感慨，暗示了对WebSocket复杂性的担忧。 • [djfobbz] 分享了其使用WebSocket构建工业级监控应用的经验，认为WebSocket是非常稳定且易于维护的，质疑文章中将WebSocket复杂化的倾向。 • [efortis] 提供了长轮询的实现示例，展示了在没有WebSocket的情况下如何通过长轮询实现类似的实时功能。 • [oneoverten] 质疑WebSocket的必要性，认为即使使用流式传输，仍然需要处理连接管理和同步问题。 • [wewewedxfgdf] 分享了自己的经验，放弃了WebSocket而选择HTTP长轮询和POST请求，认为这更简单。 • [sneilan1] 建议使用AWS AppSync事件服务而不是自己实现WebSocket服务器，质疑自己构建服务器的必要性。 • [givemeethekeys] 认为复杂性可以通过使用框架来解决，框架可以让WebSocket像REST一样易用。 • [bmitc] 将WebSocket视为一种增强版的TCP，用于实现消息功能，而不是HTTP的替代品。 • [almosthere] 欣赏vert.x的策略，能够根据可用性无缝降级连接形式，提供灵活性。 • [RajT88] 支持简化技术选择，认为很多技术潮流（如Kubernetes、云、复杂数据库）增加了不必要的复杂性，支持更简单的解决方案。 补充讨论： - 争议焦点：WebSocket的复杂性和适用场景。部分开发者认为WebSocket提供了更好的控制和性能，而另一些开发者则认为HTTP2、SSE、长轮询等技术更简单且足够用。 - 其他技术如SSE、长轮询和框架的使用被认为是简化WebSocket复杂性的替代方案或解决方案。 - 强调了技术选择的复杂性和不必要复杂性的风险，支持更简单和适合具体场景的技术方案。
