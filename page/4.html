文章摘要

本文讲述了作者在2017年因其增强现实（AR）导航演示走红后，被一家大型零售商高层联系，探讨如何改进其店内导航应用。该高管希望打造不“糟糕”的应用，增加室内地图和导航功能，以帮助顾客找到商品并获取促销信息。然而，室内导航面临巨大挑战，因为GPS在室内无效，且现有技术如蓝牙信标、WiFi、磁力计和计算机视觉等都存在精度不足、用户体验差或无法扩展的问题。作者意识到这是一个尚未解决的难题，涉及室内地图、导航和定位三大相互交织的问题。在深入研究后，作者开始专注于解决这一问题，希望找到能改善数十亿人生活的突破口。

You might not need tmux

作者: elashri | 评分: 84 | 评论数: 35 | 发布时间: 2025-08-01 09:04
文章摘要

文章讨论了作者对终端复用器 **tmux** 的长期使用体验以及最终寻找替代方案的过程。作者曾是 **tmux** 的忠实用户，依赖其会话持久性、窗口管理等功能。然而，受一个 GitHub 讨论和一次采访启发，作者认识到 **tmux** 存在一些问题，如颜色渲染不正确、滚动条使用不便、不支持新的终端协议等。尽管传统命令如 `ctrl-z` 和 `nohup` 可部分替代 **tmux** 的会话持久性功能，但在窗口管理和远程 SSH 会话中的表现不佳。 作者尝试了几个轻量级工具如 **dtach**、**abduco** 和 **shpool**，它们更符合 Unix 哲学，专注于会话持久性，但功能上仍不及 **tmux** 完善。最终，作者发现 **shpool** 最符合需求，尽管存在一些小问题。

评论摘要
主要讨论点：Tmux 的使用、替代方案及其优缺点 不同观点： • [d4rkp4ttern] 认为 Tmux 的可脚本化特性非常有用，能够通过 Tmux-cli 工具让 Claude Code 与交互式 CLI 脚本进行交互，实现自动化测试和调试，并提出这种工具开启了很多可能性。 • [jelder] 强调 Tmux 在 Mac 和 iTerm2 环境下的出色表现，特别是其无缝的远程开发体验，甚至不需要掌握 Tmux 命令。 • [pure-orange] 认为 Tmux 虽然在终端生态中有些麻烦，但它是必需的工具。与其寻找替代方案，不如从协议角度重新思考如何让这些功能更原生。 • [JdeBP] 指出 TERM 设置问题不是 Tmux 特有的，而是所有终端模拟器共有的问题，设置 TERM 是使用终端设备的必要步骤。 • [wkat4242] 支持 Tmux，认为其通过翻译转义代码实现的功能非常有用，特别是对旧设备的支持，并表示个人只关心工具是否好用，而非架构是否优雅。 • [nickjj] 喜欢 Tmux 的多会话管理功能，特别是其键盘发送功能，能简化配置文件的批量处理，并分享了具体的使用经验。 • [esjeon] 提到 suckless 社区的终端工具不打算重现 Tmux 的功能，显示出与 Tmux 用户不同的设计理念。 • [sevensor] 同时使用 Kitty 和 Tmux，前者在家中使用，后者在工作中使用，因为 Tmux 的会话恢复功能在远程工作时非常关键。 • [plett] 将 Tmux 比作浏览器标签页，认为当处理多个终端会话时，Tmux 提供的功能不可或缺。 • [mickeyp] 推荐使用 Emacs 作为终端多路复用工具，认为其可以替代 Tmux。 • [c120] 需要在无法安装 Screen 的远程 Linux 机器上使用 Tmux，认为没有其他工具可以替代 Tmux 的会话保持功能。 • [panki27] 通过 WezTerm 消除了对 Tmux 的依赖，但仍需要 Tmux 来处理服务器端会话。 • [tombert] 对 Tmux 的键盘快捷键非常依赖，认为其是开发工作流中不可或缺的工具。 • [nobleach] 提到 Tmux 的两个问题：复制多行文本需要缩放窗口和从滚动缓冲区复制到剪贴板的麻烦，但其他解决方案都不如 Tmux 好用。 • [canistel] 指出 Tmux 是唯一能通过键盘选择滚动缓冲区内容的多路复用器，这是其独特的优势。 补充讨论： • Tmux 的替代方案如 WezTerm 和 Emacs 被一些用户推荐，但大多数用户仍认为 Tmux 的某些功能（如会话恢复和键盘操作）无可替代。 • 争议焦点在于 Tmux 的复杂性和设置问题，部分用户认为这些是必要的权衡，而另一些用户则寻求更简化和原生的解决方案。 • Tmux 在远程开发和多终端会话管理中的实用性被广泛认可，特别是在需要保持会话连续性的场景中。

The world's first passenger jet was a death trap. Now it's brought back to life

作者: rmason | 评分: 26 | 评论数: 5 | 发布时间: 2025-07-29 20:14
文章摘要

这篇文章介绍了世界上第一架商用喷气式飞机——德哈维兰DH106彗星号（Comet G-ALYP）的首航历史及其影响。1952年5月2日，这架飞机从伦敦机场起飞，历时23小时，中途停留五次，飞行7000英里抵达约翰内斯堡。这标志着航空旅行进入喷气时代，提供了比螺旋桨飞机更舒适和快速的体验。然而，由于一系列事故，彗星号机队很快被停飞并进行破坏性测试。如今，德哈维兰飞机博物馆恢复了该飞机的内饰，让人们可以一窥当年的飞行体验。博物馆还展示了二战时期的蚊式战斗机原型等珍贵航空文物。

评论摘要
主要讨论点：De Havilland Comet飞机的历史、设计及其在航空史上的影响 不同观点： • [rwmj的观点] 强调了Comet飞机在博物馆中的展出情况，特别是其独特的五人制驾驶舱（包括飞行工程师和导航员），并提及博物馆中的其他展品如Mosquito和Chipmunk，带有怀旧情绪。 • [SoftTalker的观点] 提到最初Comet飞机的方形窗户设计被认为会导致应力集中，从而引发结构问题，但随后指出维基百科上关于这一说法不准确。同时，指出如今的飞机普遍采用圆形或椭圆形窗户以避免类似问题。 • [dangle1的观点] 认为Comet飞机的设计美观，但指出其结构问题（如窗户设计）即便解决了，发动机安装在机翼上的设计仍可能导致引擎火灾等新问题，暗示这种设计存在固有的安全隐患。 补充讨论： • 关于Comet飞机方形窗户设计是否导致结构问题存在一定争议。SoftTalker最初认为存在问题，但随后承认这一观点可能有误，而dangle1则暗示即便窗户问题解决，其他设计缺陷仍可能导致事故。 • 讨论中还涉及Comet飞机的发动机设计，dangle1认为这种设计可能导致进一步的安全隐患，尤其是与现代将发动机置于翼下的设计对比。 • 提到的博物馆展品（如Mosquito和Chipmunk）增加了讨论的历史背景，显示出Comet在航空史中的地位。

Design patterns you should unlearn in Python

作者: zeitlupe | 评分: 71 | 评论数: 20 | 发布时间: 2025-08-01 16:29
文章摘要

这篇文章主要讨论了在Python中盲目使用“设计模式”（特别是“四人帮”GoF模式）的问题。文章指出，许多这些模式是为Java和C++等语言设计的，这些语言缺乏Python具备的特性，如一等函数和动态类型。在Python中照搬这些模式会导致代码更难读、测试和维护。文章以Singleton模式为例，展示了其在Python中的常见错误实现、其在C++中的合理性以及更简洁的Python替代方案。在C++中，Singleton解决了全局对象的管理问题，而在Python中，使用模块级别的对象即可轻松实现相同功能。文章建议Python开发者避免不必要的复杂模式，采用更简洁的实现方式。

评论摘要
