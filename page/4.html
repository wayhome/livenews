Mill: A better build tool for Java, Scala, and Kotlin

作者: lihaoyi | 评分: 66 | 评论数: 17 | 发布时间: 2025-07-16 15:45
文章摘要

Mill 是一个针对 JVM 生态系统（Java、Scala、Kotlin）的构建工具，旨在提升传统工具如 Maven 和 Gradle 的性能和易用性。它通过积极的缓存和并行任务处理，构建速度比 Maven 和 Gradle 快 3-6 倍。Mill 内置丰富的功能，减少了对插件的依赖，支持 JVM 版本管理、代码检查、打包、发布等常见工作流。其配置和自定义逻辑使用简洁的类型检查 JVM 代码编写，具有模块树和任务图，有助于及早发现配置问题。Mill 还具有灵活性和可扩展性，适用于从小型项目到大型多模块项目的构建，并支持多种语言和框架。Mill 通过内置支持和第三方插件生态，提供了高效的开发体验。

主要讨论点：关于Mill构建工具的优缺点及与其他JVM构建工具（如Maven、Gradle、SBT）的比较 不同观点： • **支持Mill的观点**： - **简洁性和透明性**：有用户认为Mill通过去除不必要的抽象和复杂性，使其更加“无聊”（褒义），并且能够更好地追踪构建过程。相比SBT，Mill的这种简洁性更具吸引力（switchbak）。 - **性能优势**：Mill声称可以显著减少构建时间，这对于大型项目尤其有吸引力。虽然有些用户对引入Scala生态系统持保留意见，但其性能优势不容忽视（pi_22by7）。 - **IDE集成**：Mill提供的IDE集成和导航功能使其更易于理解和调试构建过程（switchbak）。 • **支持Maven的观点**： - **简单和稳定性**：有用户认为Maven已经足够好，尤其是对于不需要复杂构建逻辑的项目。Maven只是一个配置文件，不需要编写构建脚本，这使得它更易于使用（ivolimmen）。 - **成熟和习惯**：作为Maven的“高级用户”，有用户表示在过去五年内仅需使用少数几个常用插件，并且更喜欢Maven的标准化构建方式，而不是像Gradle那样非标准化的方式（frant-hartm）。 • **中立或多角度观点**： - **多样化需求和偏好**：不同的人和团队对构建工具有不同的需求和偏好，没有一种工具能满足所有需求。有些人偏爱可编程的构建工具（如bld），而另一些人则希望构建工具尽可能简单（elric）。 - **对Scala和构建工具的顾虑**：虽然Mill的性能和透明性受到赞赏，但有用户对其依赖Scala生态系统感到不满，认为这会增加不必要的复杂性（pi_22by7）。 • **对Bootstrappable的关注**： - **自举能力**：有用户关注Mill是否真正具备自举能力，而不是依赖于从服务器下载二进制文件。Maven和Gradle在这方面存在不足，Kotlin和Scala的编译器也存在类似问题（HiPhish）。 • **其他工具的提及**： - **JeKa**：有用户提到JeKa，认为它不需要学习单独的语言或奇怪的配置，提供了一种不同的选择（zcw100）。 - **Bazel的比较**：有用户询问Mill与Bazel的比较，认为Mill的比较对象主要集中在JVM专用工具上，而忽略了像Bazel这样的更广泛使用的工具（pbh101）。 - **对统一构建系统的期望**：有用户提出每个编程语言应该有一个优秀的统一构建系统，并建议在需要更多功能时编写自定义脚本，而不是依赖复杂的框架（octopoc）。 补充讨论： • **对现有工具的不满**：许多用户对Gradle和SBT的复杂性表示不满，并愿意探索其他替代方案（smrtinsert, switchbak）。 • **对Rust等新兴技术的期望**：有用户半开玩笑地期望新的工具能用Rust等新兴技术构建，反映了对性能和现代化工具的潜在需求（xg15）。 • **构建文件的复杂性**：有用户指出某些构建文件（如c3p0项目的Mill构建文件）过于复杂，可能影响工具的易用性（spullara）。 争议焦点： • **Mill是否值得切换**：虽然Mill的性能优势明显，但其引入的Scala生态系统和切换成本让一些用户犹豫是否值得（pi_22by7, frant-hartm）。 • **是否需要统一的构建系统**：有用户认为应为每种语言设立一个优秀的统一构建系统，而其他用户则认为多样化的需求需要多样化的工具来满足（octopoc, elric）。

To be a better programmer, write little proofs in your head

文章摘要

本文介绍了一种帮助更快、更准确编写代码的技巧，即在编写代码时，在脑海中构思一个证明，确保代码能按预期工作。这需要在不打断编程思路的情况下进行，最初可能较难，但熟练后能显著提高代码的正确性。文中还讨论了几种具体方法，如关注代码的单调性（monotonicity），通过记录状态或日志（如检查点、LSM树）确保代码只能向前推进，避免回退。此外，还提到了不变性（immutability），即对象一旦创建就不能修改，从而排除某些错误场景。最后，介绍了前置条件和后置条件（pre- and post-conditions）的概念，用于明确函数运行前后的状态，帮助验证函数实现的正确性。这些方法有助于在编码时更清晰地推理和验证代码行为。

评论摘要
主要讨论点：如何通过证明和不变量提升编程质量和正确性 不同观点： • **支持编写代码时进行证明和不变量思考**： - hiAndrewQuinn 强调二分查找等算法中使用循环不变量来避免错误，并引用了Jon Bentley的实验，指出专业程序员在实现简单算法时也常犯错误。 - nayuki 支持在代码中使用前置条件、后置条件、循环不变量和结构归纳等理论计算机科学中的技术，并提供了相关学习资源。 - irchans 表示希望通过实践文中所提概念（如单调性、不变量、归纳等）来改善编程质量，尽管具体效果尚不明确。 - wrs 提到在大学课程中学到的这些方法非常有效，特别是将递归和归纳等价理解后，解决了算法设计中的试错问题。 - xg15 补充了不变性和不可变性在理解程序状态中的重要性，特别是在多线程环境下。 - agnishom 认为在编写代码时在脑海中构建简单的命题是理所当然的，这是编写代码的正确方式。 • **工具和自动化方法的应用**： - runeblaze 表示自己不进行手动证明，而是使用Lean/Rocq等工具进行正确性验证，不依赖测试和测试覆盖率。 - gregorygoc 认为编写正确的证明和程序验证是困难的，主张通过编写符合语言惯用法的代码来减少对不变量和前置/后置条件的依赖，并推荐《The Practice of Programming》一书。 • **测试驱动开发（TDD）和其他方法的结合**： - w3news 提倡在编写代码前写测试和类型证明，并使用OpenAPI/GraphQL等工具进行验证，认为代码的重要性低于规格说明。 - pclowes 认为测试驱动开发是将证明方法融入编程的最佳方式，通过编写失败的测试用例和最简代码实现来覆盖前置/后置条件和不变量。 • **实践中的挑战和复杂性**： - bluetomcat 指出在全新项目中应用这些方法较为可行，但在跨单元边界调用函数或涉及全局状态和多开发者的情况下，证明方法的应用变得困难。 - GMoromisato 分享了通过具体案例分析解决bug的经验，强调从具体案例中学习比从一般原则中学习更为有效，尽管后者也很重要。 补充讨论： • **历史背景和理论基础**： - tristramb 提到程序设计中的证明思想可以追溯到1959年T. Running a million-board chess MMO in a single process

作者: isaiahwp | 评分: 169 | 评论数: 10 | 发布时间: 2025-07-12 10:56
文章摘要

cppyy: Automatic Python-C++ Bindings

作者: gjvc | 评分: 60 | 评论数: 7 | 发布时间: 2025-07-16 12:39
文章摘要

cppyy 是一个自动的 Python-C++ 绑定生成工具，能够在运行时实现 Python 与 C++ 的互调，支持跨语言调用、延迟加载、模板实例化、异常映射等功能。它基于 C++ 解释器 Cling，无需语言扩展或手写代码，支持大型 C++ 项目，并能无缝集成如 Boost 等复杂 C++ 库。cppyy 适用于 CPython 和 PyPy，具备高性能，支持 STL、回调和跨继承等特性，简化了 C++ 库在 Python 中的使用。通过预编译头文件和动态加载等技术，cppyy 可以处理包含大量类和代码的 C++ 项目。

评论摘要
主要讨论点：Cppyy 作为 Python 和 C++ 结合的工具，其功能、性能及实际应用的讨论。 不同观点： • [rich_sasha] 认为 Cppyy 类似于已经废弃的 scipy.weave，可以结合 C++ 和 Python。他关注 Cppyy 是否能替代 scipy.weave，尤其是性能方面是否能超越 Numba 和 Cython。他指出 Cppyy 通过 Cling 解释 C++ 而不是生成真正的二进制文件，并质疑其在 CPython3 上的性能表现。虽然找到了一些基准测试，但这些测试并没有直接对比 Python 实现。 • [ashvardanian] 提供了一个使用 Cppyy 的实际用例，展示如何通过 Cppyy 结合 C++ 内核与 Python 进行实验，还提到了 Numba 和 PeachPy 等其他工具，展示了 Cppyy 在实际项目中的应用场景。 • [f1shy] 提出了 Cppyy 与 LLM（大型语言模型）在“AI 编程”中的对比，表示自己在使用 Cppyy 时得到了不错的效果，询问其他人的使用体验。 • [dang] 提供了一个相关的讨论链接，指向 2019 年关于 Cppyy 的讨论，引导读者参考之前的讨论内容。 • [actinium226] 关注实际应用中的分发问题，担心如果在项目中使用 Cppyy 并打包成 pip 包，用户是否需要自行安装 C++ 编译器，或者 Cppyy 是否自带编译器。 • [wslh] 推荐了 SWIG 作为另一种支持多种编程语言的绑定工具，暗示 SWIG 可能是 Cppyy 的一种替代方案。 补充讨论： • [bogeholm] 对项目名称进行了幽默评论，没有涉及技术讨论。 争议焦点： • Cppyy 是否真正能替代 scipy.weave，尤其是在性能和实用性方面。 • Cppyy 在实际项目分发中的可行性，特别是对用户环境的要求。 基准测试和性能对比是讨论的核心，尤其是对 Cppyy 在 CPython3 上的性能表现缺乏明确的答案。
