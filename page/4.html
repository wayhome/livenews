Zig breaking change – initial Writergate

作者: Retro_Dev | 评分: 157 | 评论数: 22 | 发布时间: 2025-07-04 04:11
文章摘要

这篇文章介绍了Zig编程语言中的一个重大变更，主要涉及标准输入输出（std.io）的读者（Reader）和写者（Writer）接口。新的`std.io.Reader`和`std.io.Writer`不再使用泛型，但在接口内包含缓冲区，以优化性能。变更非常重大，尤其影响格式化打印功能。多个旧的API被弃用或删除，如`std.fs.File.reader`改为`std.fs.File.deprecatedReader`等。文章提供了升级指南，帮助开发者将旧API适配到新API，并介绍了新的便捷功能和独特概念，如读取时的丢弃（discarding）和写入时的散布（splatting），以及文件句柄的关键信息缓存等。这些变更旨在提高性能和易用性。

评论摘要
主要讨论点：Zig语言的 breaking changes 及其影响 不同观点： • **dnautics** 认为 Zig 的 breaking changes 并没有造成太大困扰。作为 Zig 与 Elixir 接口库的维护者，他通过自动化测试和代码扫描来快速应对变化，且感觉近年来 breaking changes 影响变小、变少。他认为抱怨 changes 的人并非 Zig 的日常用户。同时，他指出新手可能因为网上过时的示例代码而遇到困难。 • **mtlynch** 表达了对 breaking changes 的失望，尤其是在 Zig 0.12.0 版本中构建系统的重大变化未得到充分解释，导致下游开发者无所适从。他希望 Zig 团队在未来能提供更好的迁移指导。 • **ww520** 关注旧的 reader/writer 模式在结构体中存储的困难，并询问新变化是否解决了这一问题。 • **dnautics** 再次对新的 API 设计提出疑问，特别是关于异步函数中的 suspend 点是否仍然支持，并询问用户是否能构建带有 yield 点的函数。 • **90s_dev** 表示可以接受 breaking changes，只要能在一天内解决。相比 C/C++ 的跨平台编译困难，Zig 如果能解决这一问题将非常有吸引力。 • **Aissen** 建议 Zig 应该有自动化工具来处理语言和标准库的语义变化，类似于 Go 的 `go fix` 工具，以帮助开发者应对 breaking changes。 • **blippage** 分享了尝试 Zig 用于微控制器项目时的负面体验，由于语法变化和依赖更新，最终选择回归 C，并认为 C 在低级编程中难以被超越。 • **brabel** 认为 Zig 不断重新设计自己，而其他语言如 Odin 早已“出货”，质疑 Zig 是否陷入了完美主义综合症。 补充讨论： • **thrwyexecbrain** 对新的 `Reader.stream` 和 `Writer.sendFile` API 表示赞赏，认为其设计优雅，适用于构建基于推送的数据转换管道。 • **kristoff_it** 提供了 Zig 2026 路线图的视频链接，为讨论提供了背景信息。 • **ksynwa** 和 **GolDDranks** 的评论较为轻松，前者开玩笑询问 "Writergate" 是否为技术术语，后者表示虽然目前对 Zig 的 breaking changes 持谨慎态度，但仍期待其稳定版本，同时继续使用 Rust。 争议焦点： • Breaking changes 的合理性及其对开发者的影响是主要争议点。一部分开发者（如 dnautics）认为影响不大，而另一部分开发者（如 mtlynch）则认为缺乏足够的迁移指导，给开发者带来了困扰。 • Zig 是否过度追求完美，导致频繁 redesign 而未能稳定发布，也是讨论中的一个争议点。

Lens: Lenses, Folds and Traversals

作者: hyperbrainer | 评分: 70 | 评论数: 8 | 发布时间: 2025-07-01 12:08
文章摘要

该`lens`包是Haskell中用于操作数据结构的库，提供了 lenses、folds、traversals 等工具。它支持为常见Haskell类型自动生成 lenses，并提供了丰富的组合子以灵活操作数据。用户也可以为自己定义的数据类型手动创建 lenses 和 traversals，而无需依赖该库。此外，该库还包括 getters、setters、isomorphisms 等功能，支持多种数据结构如数组、列表、Map等。该库提供了详细的文档、示例和教程，帮助开发者理解和使用这些功能。

评论摘要
主要讨论点：Haskell及其他语言中使用lenses（透镜）的优缺点及复杂性 不同观点： • **反对使用运算符**：[kccqzy] 认为应避免使用Haskell中的lens运算符（如^.、^..、^?等），因为它们看起来像乱码，难以记忆。建议使用具名函数（如toListOf），以提高代码可读性和清晰度。 • **对lenses的入门与进阶的质疑**：[moomin] 认为如果想要理解或进阶学习lenses，该评论并不是合适的起点，暗示讨论中的建议对初学者和进阶用户都不太适用。 • **推荐其他语言的类似工具**：[0_gravitas] 提到Clojure中的Specter库是Optics的另一种实现，功能和哲学上与Haskell的lenses类似，建议在Clojure环境中使用Specter。[eigenspace] 推荐Julia中的Accessors.jl包，认为其比Haskell版本更易理解。 • **学习资源推荐**：[srik] 建议学习者使用《Optics by Example》这本书，而非通过视频学习，认为该书更系统且节省时间。[haskman] 则推荐PureScript中的光学指南，认为其对Haskell用户更易接受。 • **语法层面的简化建议**：[rrgok] 质疑为何Haskell不能在语法层面提供更直接的命令式接口（如`foo.bar.baz = 1`的设置方式），以便简化lens操作，尽管Haskell已有do-notation来模拟命令式代码。 • **对Haskell复杂性的批评**：[johnfn] 批评Haskell社区在面对简单问题时引入了过多复杂性（如113个新运算符和20个新的依赖库），认为虽然Haskell带来了Maybe和Either等有用的概念，但在实际操作中显得过于复杂。 补充讨论： • **对Haskell运算符的复杂性感受因人而异**，部分评论者如[kccqzy]和[johnfn]认为运算符难以理解和记忆，而其他评论者则接受或未直接批评这种设计。 • **不同语言中的类似工具对比**，如Clojure的Specter和Julia的Accessors.jl，这些讨论显示了不同编程语言社区在处理类似问题时的不同思路。 • **争议焦点**在于Haskell中lens运算符的复杂性与可读性之间的权衡，部分开发者认为运算符导致代码难以理解，而另一部分开发者可能习惯或接受了这种设计。

Show HN: BunkerWeb – the open-source and cloud-native WAF

作者: bnkty | 评分: 75 | 评论数: 11 | 发布时间: 2025-07-04 11:55
文章摘要

BunkerWeb是一款基于NGINX的下一代开源Web应用防火墙（WAF），旨在通过默认安全的方式保护web服务。它可以无缝集成到Linux、Docker、Swarm、Kubernetes等环境，并提供高度可配置性，支持通过插件系统扩展功能。BunkerWeb具备自动化的HTTPS支持（使用Let's Encrypt）、集成的ModSecurity WAF和OWASP核心规则集、自动封禁可疑行为、连接和请求限制、机器人验证等安全功能。此外，它还提供了一个便捷的网页用户界面（UI）来管理配置，并可以通过专业的服务获得技术支持。如果不希望自行托管，还可以选择BunkerWeb Cloud，这是一个全托管的SaaS服务。
