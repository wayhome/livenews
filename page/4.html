Standard Completions

作者: todsacerdoti | 评分: 19 | 评论数: 2 | 发布时间: 2025-05-31 12:00
文章摘要

本文讨论了多个提供与OpenAI兼容的Completions和Chat Completions API的供应商，如Deepseek、OpenRouter和vLLM等，虽然OpenAI已将Completions视为遗留API，且Chat Completions也被弱化以推广OpenAI Responses API。尽管OpenAI承诺无限期支持当前的Chat Completions API，但它缺乏多模态输出、输入对象存储、显式缓存和助理前缀等功能。各供应商以非标准方式添加了这些功能，导致开发者使用不便。例如，助理前缀在不同供应商中的实现方式各异，且没有标准信号来指示是否支持某些功能，开发者需尝试或检测上游供应商。文章呼吁建立一个标准化的OpenAI API超集，以简化开发者体验，并促进LLM生态系统的互操作性。感兴趣的供应商和开发者可参与Standard Completions工作组。

评论摘要
主要讨论点：关于旧的 completion API 与新的 chat creation API 哪个更优越的讨论 不同观点： • [lolpanda的观点] 认为 legacy completion API 优于新的 chat creation API。理由是 completion API 将所有输入视为单个字符串，而 chat API 则要求将输入作为消息列表处理。在处理现代的代理工作流时，模型通常需要处理大量输入数据，包括 RAG 数据、函数调用和其他元数据，用户和助手的消息仅是整体提示的一小部分。因此，将对话与其他输入数据统一格式化为一个单一的文本提示（如使用 ... 标签）更为直观。OpenAI 的新 completion API 支持单个大字符串或消息列表，这一点很不错。此外，他们提到在 Claude 工具中尝试过类似方法，将提示构建成包含指令和示例的较大提示。 • [pawanjswal的观点] 对 lolpanda 的观点表示赞同，指出许多开发者在开发过程中都会遇到这一问题。他认为指出 API 的不一致性并倡导建立一个通用基准是有益的，认可了 lolpanda 提出的改进建议。 补充讨论： • lolpanda 提到了新的 completion API 支持单个大字符串或消息列表，这表明新 API 也在尝试解决一些格式上的灵活性问题。 • 讨论中还提到 Claude 工具中的 XML 格式化方法，表明在不同平台上对提示格式的不同处理方式也是开发者关注的重点。 • 争议的焦点主要在于处理大规模输入数据时，哪种 API 格式更直观和高效。lolpanda 更倾向于使用单一的字符串格式，而新的 chat API 则采用消息列表的方式，这在处理复杂工作流时可能带来不便。

The wake effect: As wind farms expand, some can ‘steal’ each others’ wind

作者: JumpCrisscross | 评分: 39 | 评论数: 17 | 发布时间: 2025-05-31 12:21
文章摘要

文章主要讨论了风电场之间存在的“风能盗窃”现象，即当一个风电场在另一个风电场的上风处时，会减慢风速，影响下风处风电场的能量输出。这种现象被称为尾流效应，可导致下风向风电场能量输出减少10%或更多。随着全球海上风电场的快速扩展，特别是规模和密度的增加，尾流效应愈发显著，可能延伸超过100公里。这种效应引发了风电场开发商之间的纠纷，尤其是在风电场密集的北海地区。为了解决这一问题，英国已启动新研究项目，旨在通过建模分析2030年风电场的尾流效应，帮助政府和开发商优化规划，避免纠纷。

评论摘要
主要讨论点：风电场的风能争夺及相关环境与法律问题 不同观点： • **JohnKemeny**：引用《Mine》一书，讨论了当资源归属不明时，人们如何争论资源的归属问题。他以风电场为例，说明当前一个风电场的涡轮机会减弱下游风电场的风速，从而引发资源争夺，并提出需要更好的规则来解决此类冲突。他还列举了其他类似情况，如水电站影响下游潜力、树木遮挡邻居的太阳能等。 • **glkindlmann**：指出评论中未提到“权利”概念，并引入了“风权”的讨论。他通过“水权”类比，解释了风电场在某块土地上获取风能的合法性问题，并提到关于上游和下游风能用户冲突的法律问题。 • **roxolotl**：提到一项关于风力涡轮机对飓风影响的研究，指出涡轮机逐步吸收飓风的能量，从而减弱风暴的破坏力，尽管这种情况不太可能实际发生，但研究本身很有趣。 • **g42gregory**：担忧风电场对环境的长期影响，尤其是如果风电场数量足够多，是否会导致环境风速下降，并进一步影响鸟类、气候、昆虫种群等生态因素。他还质疑风电场的正面效益是否显著超过其负面影响。 • **polishdude20**：提出一个科幻的后末日设想，即一个在风暴地区建立基地的殖民地，通过巨大风力机器吸收风暴能量，从而在背风侧创造出平静的生活环境。 • **glumreaper**：引用数据淡化风电场尾流损失的严重性，认为这些损失对风电场整体寿命影响较小，因此不值得过度担忧。 • **morkalork**：指出风电场尾流可以延伸至100公里外，并减少另一个风电场10%的输出，提出需要在全国范围内优化风电场布局以最大化整体输出。 • **amai**：认为风向变化会改变风电场之间的风能争夺情况，因此尾流损失问题并非固定不变。 • **acyou**：惊叹于人类能够有效利用环境能量，并讨论了全球变暖对风电场输出的潜在影响，提出温暖潮湿的空气虽然密度较低，但整体系统能量增加。 • **collinmcnulty**：希望将风电场对风速的影响与其他障碍物（如普通建筑）进行比较，以更好地理解风电场影响的规模。 • **p0w3n3d**：认为风电场减少风速是能量守恒定律的基本常识，不值得大惊小怪。 • **aaron695**：批评媒体夸大风电场的“神秘”问题，认为这些报道是危言耸听，并暗示竞争性风电场之间的利益冲突。 补充讨论： - 风电场的尾流损失问题及其对整体输出的影响是讨论的核心，部分评论者认为问题被夸大，而其他人则关注其潜在的环境和经济影响。 - 风权和风电场法律问题也被提及，显示出技术问题之外的法律和权利争议。 - 有评论者提出全球变暖对风电场输出的潜在影响，扩展了讨论的范围。

Quarkdown: A modern Markdown-based typesetting system

作者: asicsp | 评分: 215 | 评论数: 35 | 发布时间: 2025-06-03 08:06
文章摘要

Go语言的错误处理冗长问题一直是开发者抱怨的焦点，主要集中在需要频繁检查`if err != nil`。这种模式在涉及大量API调用的程序中尤为明显，导致代码中充斥大量与核心逻辑无关的错误处理代码。尽管社区对引入新机制的呼声很高，Go团队多年来尝试解决此问题，但未找到理想方案。 2018年，Go团队提出基于“检查和处理”（check and handle）机制的方案，但因过于复杂而被放弃。2019年，提出简化的“try”方案，虽然尝试通过工具`tryhard`评估影响，但因其隐藏控制流且返回机制不透明，再次被拒。 反思过程中，Go团队认识到应更早引入新关键词，并给予社区更多反馈空间。近期，有新提案回归原始设计并改进不足。尽管过程曲折，Go团队将继续听取反馈，探索更优错误处理方案。
