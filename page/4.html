Mounting git commits as folders with NFS (2023)

作者: pvtmert | 评分: 104 | 评论数: 18 | 发布时间: 2026-05-19 07:32
文章摘要

这篇文章介绍了作者开发的 git-commit-folders 项目，它将 Git 仓库挂载为文件系统，每个提交都显示为一个文件夹。作者希望通过这种方式帮助人们直观理解 Git 的工作原理——提交本质上就像包含目录列表的文件夹。 项目支持 FUSE 和 NFS 两种挂载方式（避免了 Mac 上 FUSE 需要内核扩展的麻烦）。在这个文件系统中，分支和标签都是指向提交文件夹的符号链接，反映了 Git 的底层实现。 实际用途包括：搜索已删除的函数、快速查看其他分支的文件、跨分支搜索代码等。虽然这些操作用 Git 命令也能完成，但文件系统导航对作者来说更直观易用。

评论摘要
主要讨论点：将Git仓库通过FUSE挂载为文件系统的技术实现与实用性 不同观点： • **技术实现路径**：有人建议在Mac上用VM运行FUSE再通过NFS导出以规避内核扩展问题，但会带来性能损耗；有人推荐使用FSKit作为Mac原生方案替代WebDAV/NFS • **心智模型争议**：有人认为将commits作为文件夹不合适，因为在commit中删除/添加文件会创建新commit，这与文件系统操作逻辑冲突；有人建议用Jujutsu的changes替代，因其在rebase时更稳定 • **实用性评价**：部分人认为这是"cursed but useful"的有趣实现，会立即使用；也有人质疑实用性，认为传统git命令（如git show、git log -S）更高效，只是语法难记 • **技术细节优化**：有人指出tree/blob ID本身已是哈希值，无需再次哈希来生成inode，直接取前8字节即可 补充讨论：评论中提到Fossil和ClearCase等版本控制系统已有类似功能；有人认为随着LLM和AI编程的发展，这种跨commit文件比较方式值得重新审视；作者因此项目还为Git贡献了文档改进。

文章摘要

OpenAI的一个模型解决了离散几何中的一个核心猜想——平面单位距离问题。这个由数学家Erdős在1946年提出的问题，近80年来一直困扰着数学界：在平面上放置n个点，最多能有多少对点之间的距离恰好为1？ 长期以来，数学家们认为"方格网格"构造是最优解。但OpenAI的模型推翻了这一猜想，找到了一个多项式级别的改进方案，并运用了代数数论的高级工具。 这是AI首次自主解决数学子领域的重要开放问题，标志着AI推理能力的重大突破。菲尔兹奖得主Tim Gowers称其为"AI数学的里程碑"，数学家们认为这证明了AI不仅是辅助工具，更能产生原创性的天才想法并将其实现。

评论摘要
主要讨论点：OpenAI模型解决数学难题（Erdős猜想）的意义及其对AI能力的评价 不同观点： • **乐观派**：数学博士后认为这是令人兴奋的突破，LLM能帮助科学家应对知识爆炸和超专业化问题，打破领域壁垒；有评论指出AI已达到"博士级智能"，目标柱不应移至莱布尼茨级别 • **谨慎派**：质疑训练数据透明度——OpenAI可能使用专家生成的原创训练数据，无法确定模型是否真正"独立"解决问题；关注成本和尝试次数，想知道是一次成功还是千万次尝试中的一次 • **技术分析派**：指出这是通过反例证伪而非正面证明，相对不那么深刻；认为模型仍在"连接现有想法"而非创造新数学理论，但离理论创新已不远 • **怀疑派**：参考Anthropic的Mythos事件保持警惕，质疑论文写作过程中人类参与程度；批评AI成果归属于公司而非实际工作的人 补充讨论： - 模型输出缺少引用归属是重要问题 - 125页推理链规模惊人 - 为何只听说Erdős问题被解决 - "插值训练数据"的哲学辩护：数学本就是展开公理中隐含内容

FatGid: FreeBSD 14.x kernel local privilege escalation

作者: WhyNotHugo | 评分: 82 | 评论数: 5 | 发布时间: 2026-05-21 12:15
文章摘要

这是一份关于 FreeBSD 14.x 内核本地提权漏洞（CVE-2026-45250）的技术报告。漏洞存在于 `setcred(2)` 系统调用中，由于 `sizeof` 类型错误导致内核栈缓冲区溢出。任何非特权本地用户都可在权限检查前触发该漏洞，实现从内核崩溃到完全提权的攻击。研究者开发了针对启用 SMAP/SMEP 保护的 amd64 GENERIC 内核的工作利用链（仅需加载 zfs.ko）。该漏洞在 2025 年 11 月已在主分支静默修复，但未回溯到稳定版本，FreeBSD 14.4-RELEASE 仍受影响。

评论摘要
主要讨论点：关于某个BSD系统安全漏洞的披露方式和影响范围 不同观点： • **质疑披露形式**：有人认为一个本地提权漏洞(LPE)不值得专门建立网站和命名，这种做法过于夸张 • **关注实际影响**：指出FreeBSD被广泛应用于TrueNAS和网络设备中，这个漏洞对运维人员的影响比想象中更大 • **对OpenBSD安全性好奇**：有人想测试LLM能否在以严谨开发著称的OpenBSD中发现问题，这是对项目质量的好奇而非质疑 • **补丁状态存疑**：有评论指出漏洞信息显示"未修补"与实际情况不符，因为14.4版本的修复通知已在前一天发布 补充讨论：评论反映了安全社区对漏洞披露方式的不同态度——既有对"过度营销"安全漏洞的批评，也有对实际影响范围和修复状态准确性的关注。

这是一个打孔卡片历史档案网站的介绍。打孔卡片曾在1950-60年代广泛用于会计、数据收集和早期计算，但很快就被淘汰并被遗忘。该档案收藏了255张打孔卡片（5种格式，来自55家印刷商和64家公司）、11件硬件设备（3家制造商）以及18份手册文档（涵盖100种产品），旨在保存这些历史文物。网站展示了包括贝尔实验室、IBM等公司的特色藏品。

评论摘要
主要讨论点：打孔卡编程时代的工作方式及其现代遗产 不同观点： • **编程效率的代际差异**（benrutter）：打孔卡时代编程极其困难，提交代码到获得结果至少需要一天，一个小错误（如漏掉分号）就会导致长时间等待。认为自己的性格无法适应那个时代的编程工作，而母亲那代人有不同的心态和耐心。 • **互联网知识分享的价值**（ktallett）：承认自己对打孔卡历史了解有限，但认为互联网上这类小众专业网站的存在很有意义，体现了互联网在知识传播方面的独特价值。 • **打孔卡技术的延续性**（foxglacier）：从技术角度欣赏边缘打孔卡的机械搜索功能，指出打孔卡的理念以虚拟形式延续至今——现代工程软件（如Abaqus和Nastran）仍使用类似打孔卡的文本格式，工程师按列号输入数据，甚至沿用"卡片"和"卡组"的术语来指代文件和行。 补充讨论：foxglacier通过儿童拼图游戏类比说明了打孔卡的物理验证机制，展示了这种古老技术的巧妙设计思想如何跨越时代影响现代工程实践。
