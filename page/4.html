Max severity RCE flaw discovered in widely used Apache Parquet

作者: andy99 | 评分: 95 | 评论数: 10 | 发布时间: 2025-04-06 17:21
文章摘要

研究人员发现Apache Parquet存在一个最高严重级别的远程代码执行（RCE）漏洞（CVE-2025-30065，CVSS v4评分10.0），影响1.15.0及之前所有版本。该漏洞源于反序列化不可信数据，可能让攻击者通过特制的Parquet文件控制目标系统、窃取或修改数据、中断服务或植入勒索软件等恶意 payload。该漏洞已在1.15.1版本中修复。利用此漏洞需要诱导用户导入恶意文件，因此主要威胁来自外部来源的文件。广泛使用Parquet的大数据平台如Hadoop、AWS、Google和Azure，以及Netflix、Uber等公司受影响。建议用户尽快升级至1.15.1版本，并加强监控和验证文件安全性。目前尚未发现实际攻击，但风险极高。

评论摘要
主要讨论点：Parquet文件解析漏洞的严重性及其CVSS 10分的合理性 不同观点： • **对CVSS 10分的质疑**： - [jtchang] 认为CVSS 10分过高，除非无条件接受Parquet文件，否则影响有限。相比之下，解析图像、XML、JSON、HTML、CSS的漏洞更为严重。 - [tptacek] 认为CVSS高分没有实际意义，高分不一定代表严重性，甚至表示对高分漏洞越来越不重视，提到Heartbleed的CVSS分数为7.5。 • **对漏洞报告的困惑**： - [g-mork] 质疑漏洞报告的模糊性，认为这是一个典型的序列化bug，并提供了一个GitHub链接展示相关代码变更。 • **对漏洞影响的澄清**： - [3eb7988a1663] 建议标题应注明是解析器漏洞而非文件格式本身的问题，避免误解为需要重新编码数据。 • **讽刺和调侃**： - [lpapez] 以讽刺口吻预测未来可能会出现“Quake PAK文件携带恶意软件，关键10/10漏洞”的报道。 • **对具体应用影响的关注**： - [ustad] 关心Pandas是否受影响，因为Pandas在底层使用Parquet进行数据帧的序列化/反序列化。 - [formerly_proven] 回应称根据概念验证（PoC），这是典型的Java反序列化RCE，可以实例化任意类，确认Pandas受影响。 • **对RCE漏洞严重性的讨论**： - [nikanj] 抱怨“最高严重性RCE”不再意味着“任何未经身份验证的参与者都能进行RCE”，而是需要导入恶意文件才能利用，暗示CVE评分的“通货膨胀”。 补充讨论： - 评论中多次提到CVSS评分的合理性问题，尤其是对高分（10分）的质疑和调侃。 - 对漏洞影响的实际范围存在争议，特别是对Parquet文件在实际应用中受影响的场景有不同看法。 - 讨论中涉及到具体应用如Pandas的受影响情况，以及Java反序列化RCE的具体风险。

Show HN: I built a Rust crate for running unsafe code safely

作者: braxxox | 评分: 101 | 评论数: 19 | 发布时间: 2025-04-06 13:28
文章摘要

`mem-isolate` 是一个 Rust crate，旨在通过使用 `fork()` 系统调用安全地运行不安全代码。它会在子进程中执行用户提供的函数，确保该函数不会影响父进程的内存状态，实现内存隔离。主要特点包括： 1. **内存纯净性**：即使函数存在内存泄漏或堆碎片化问题，也不会影响主进程。 2. **跨进程通信**：通过管道在父子进程间传递结果，使用序列化（如 `serde`）处理数据。 3. **性能开销**：每次调用引入约 1ms 延迟，适合对内存安全要求高的场景。 4. **系统支持**：仅支持 POSIX 系统（如 Linux, macOS），不支持 Windows 和 WebAssembly。 该工具适用于运行可能导致内存问题的代码，如 FFI 调用或不安全代码，通过隔离确保主程序的稳定性。

评论摘要
主要讨论点：Rust中的内存安全与隔离方法，尤其是在处理不安全代码时的技术和工具选择 不同观点： • woodruffw认为，"safe" Rust不仅仅意味着避免空间内存错误导致的崩溃，还包括空间和时间上的内存安全。仅仅检测那些不会导致异常退出的内存不安全行为是不够的。Rust的安全性比仅仅避免崩溃要强得多。 • nextaccountic提出了一种通过将不安全代码编译为WebAssembly然后再转换为C代码的方法，以实现内存安全。这种方法将原本未定义的行为转换为逻辑错误，避免了内存损坏问题，类似于Firefox中的做法。 • destroycom和Svetlitski指出，在多线程应用中使用fork()存在风险，特别是在fork和exec之间执行的代码需要是异步信号安全的，否则可能导致死锁或内存问题。 • pjmlp主张从一开始就设计多进程应用，使用操作系统IPC和沙箱API，而不是依赖即时的伪沙箱技术，后者可能带来自身的问题。 • wavemode质疑牺牲性能来运行不安全代码的必要性，认为如果可以接受这样的性能损失，那还不如直接使用带有垃圾回收机制的语言。 • djha-skin认为fork()在某些情况下可能成本过高，应谨慎使用这种技术。 • slashdev对需要使用这种复杂技术的情况表示好奇，想知道是哪些糟糕的库或代码导致这种需求。 • TheDong指出，这种方法可能会导致函数行为不符合预期，特别是涉及内部可变性的代码，可能导致不正确的结果。 • null_investor认为，这种技术仅在处理确实无法改进的不安全代码时有用，但频繁使用可能丧失Rust相对于Python或Ruby的性能优势。 • cryptonector建议在处理大内存集的进程时使用vfork()而不是fork()，以提高速度。 • dijit提到在Windows环境下调用Win32 API时面临的内存调试困难，并寻求适合的工具帮助。 • kelnos强调在多线程程序中使用fork()的危险性，建议在crate中添加明确警告。 • corank质疑这种方法是否适用于需要内存可变的代码，例如双向链表的实现。 • jesprenj对使用管道而非共享内存进行通信的原因表示疑问。 补充讨论： - 各种方法的性能权衡，包括fork()的成本与多进程设计的优劣。 - 针对不同操作系统（如Windows和Linux）的特定工具和调试方法。 - 对内存安全和代码纯度的不同需求及其对设计的影响。

Pitfalls of Safe Rust

作者: pjmlp | 评分: 147 | 评论数: 13 | 发布时间: 2025-04-04 17:55
文章摘要

本文讨论了Rust中的"安全"不仅仅指内存安全，还需处理其他问题以确保程序健壮性。即便在"安全Rust"中，仍有一些编译器无法检测的陷阱，包括类型转换错误、逻辑错误、使用`unwrap`导致的恐慌、第三方库中的不安全代码和竞争条件等。文章提供了多个避免这些问题的建议，如使用检查算术操作防止整数溢出、避免使用`as`进行数值转换、使用有界类型确保数值合法性、确保无效状态无法表示等。此外，文章还强调了在发布模式下启用溢出检查以增强安全性，并提供了具体实现方法。通过遵循这些建议，开发者可以写出更可靠的Rust代码。

评论摘要
主要讨论点：Rust 编程中的潜在问题和语言特性使用 不同观点： • **nerdile**：认为文章标题有误导性，"Safe Rust"中的问题并不是特有的，这些问题在其他语言中也存在。建议标题改为"Rust pitfalls: Runtime correctness beyond memory safety"以减少哗众取宠的效果。 • **IshKebab**：对整数溢出和数组越界问题持乐观态度，提到Flux（基于精化类型的工具）可以在不完全依赖正式验证的情况下提供帮助。 • **conaclos**：指出文章未提及替代检查算术的方法，如显式使用Wrapping和Saturating类型，并提到`as`类型转换的替代方案（如`From::from`）虽然更安全但语法较为冗长。 • **zk4x**：认为文章列出的问题很客观，但实际情况更复杂。支持移除`as`转换，但指出某些类型转换（如u64到f32）非常困难。同时，强调性能问题，特别是在高性能计算中需要能够选择退出数学检查，并提到Results和Options带来的分支对性能的影响。 • **bennettnate5**：提到`mem::size_of_val(&T)`的问题，指出其在多重引用类型下返回的结果与预期不符，建议仅使用`size_of::()`。 • **Sharlin**：讨论了`Path::join`在处理绝对路径时的意外行为，认为这是一个潜在的陷阱，并建议可能需要返回`Result`或引入专用方法来处理绝对路径。 • **woah**：质疑`as`是否是一个不必要的陷阱。 • **nurettin**：反对使用`checked_mul`等方法处理溢出问题，认为应该通过编译器标志或静态检测来处理。 • **thrance**：补充提到内存泄漏问题，特别是在使用`Rc`或`Arc`时容易出现引用循环，导致内存无法释放。 • **forrestthewoods**：不认为溢出是一个严重问题，指出Rust已经将溢出行为从“未定义”改为“定义良好的二补码”。 • **quotemstr**：认为文章中关于数组索引的建议是不明智的，数组越界通常表明逻辑错误，应快速失败以防止问题扩大，而不是通过try-things掩盖逻辑错误。 • **sgt**：提出Golang可能在编写健壮软件方面更优，暗示Rust在这方面可能不如Golang。 补充讨论： • 争议的焦点包括`as`类型转换的安全性、检查算术（如`checked_mul`）的必要性、以及`Path::join`在处理绝对路径时的行为是否是陷阱。 • 性能和代码简洁性也是讨论的重要方面，特别是在高性能计算场景中，如何平衡安全性和性能成为一个关键问题。 • 不同的开发者对如何处理潜在问题（如溢出、数组越界）有不同的看法，部分开发者倾向于通过工具和编译器支持来解决，而另一些开发者则强调快速失败和逻辑错误检测。
