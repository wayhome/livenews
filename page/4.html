Building Pi with Pi

作者: mplanchard | 评分: 151 | 评论数: 15 | 发布时间: 2026-05-24 17:22
文章摘要

这篇文章讨论了使用AI代理（Pi）开发Pi本身的经验。作者指出，AI生成的issue报告质量低下（"slop"），常包含错误诊断和过度自信的分析，反而增加工作量。作者建议issue应简洁明了，只包含人类实际观察到的事实：运行的命令、预期结果、实际结果和错误日志。文章还批评AI倾向于过度工程化，在遇到问题时添加容错机制而非修复根本原因，导致系统复杂度膨胀。作者强调应保持系统不变性，防止错误状态产生，而非处理各种异常情况。

评论摘要
主要讨论点：围绕“clanker/agent”等称呼、LLM代理的行为边界，以及用代理开发代理的工程与商业可行性展开讨论。 不同观点： • 反对把机器拟人化或赋予“被冒犯/有意识”属性。`burakemir`认为把“clanker”当高度侮辱性词，暴露了类比的限度；他举童书《The Clanker》为例，强调模型没有感受，担心这种意识形态反过来影响下一代模型行为。 • 认为“agent”并非误称，机器确实有一定“agency”。`0xbadcafebee`用字典定义和汽车控制燃油/传感器的例子论证机器具行动能力；但同时反对用“clanker”这类带情绪色彩的蔑称，认为会制造偏见、削弱理性判断。 • 关注工程治理而非命名争论。`visarga`主张记录用户原始消息日志，便于核对计划与执行；`andai`认为应依靠严格 issue 模板区分“观察/假设”，并追问系统不变量是否有文档、是否被遵守。 • 对“人要求机器做自己都不做的验证”提出讽刺。`gslepak`直接质疑：既然人类自己不独立验证，却要求机器这样做，还顺带贬称它，为何机器要配合？ • 看好“agent 开发 agent”成为稳定模式。`bigcat12345678`从经济性、产业演化、团队协作类比和工程技能分化四方面论证其会成为主流。 补充讨论：争议焦点主要在两处：一是“agent/clanker”命名背后的拟人化与贬义问题；二是代理失控、忽视不变量、报告失真时，责任应更多落在模型能力、流程设计还是人类使用方式上。另有少量轻松评论关注字体、动画、项目命名相似度等。

Defeating Git Rigour Fatigue with Jujutsu

作者: ikesau | 评分: 93 | 评论数: 22 | 发布时间: 2026-05-24 18:39
文章摘要

这篇文章介绍了使用 Jujutsu 版本控制系统解决"Git 严谨疲劳"的技巧。 **核心问题：** 开发大功能时，很难保持提交历史整洁。实际开发中常产生混乱的提交序列，后续提交会覆盖早期工作。 **解决方案：** 先创建理想的空提交结构（按功能模块划分），然后将所有实际改动合并到一个"大杂烩"提交中，最后用 `jj squash -i` 交互式地将相关改动分拣到对应的空提交里。 **优势：** 比开发过程中维持严格提交规范更轻松，避免了 `jj absorb` 的误判和 `jj split` 的反复操作，最终状态保证无冲突。 **缺点：** 无法保证每个提交都能编译通过。

评论摘要
主要讨论点：Jujutsu (jj) 与 Git 的工作流对比，特别是关于提交历史管理和分支处理的不同方式 不同观点： • **反对 jj 的立场**：y1n0 认为 jj 的分支管理极其繁琐，在多人协作场景下需要手动维护分支指向正确的提交，这对于同时维护多个分支的工作流来说不可行。Git 的命名分支机制简单易用。 • **支持 jj 的立场**：nozzlegear 和 xyzsparetimexyz 等用户完全转向 jj，认为其工作流更符合人体工程学。特别是 `jj new` 创建新变更的方式更符合心智模型，`jj split` 等交互式工具比 `git add -p` 体验更好。 • **实用主义观点**：drdrey 表示已接受 squash PR 的做法，认为追求"完美提交"是浪费时间；jadar 使用 `git reset --soft` 在推送前重写历史；codemog 建议让 AI 代理处理 Git 操作。 • **工具辅助派**：singiamtel 指出 lazygit 已经很好地解决了 Git 的痛点，但 jj 的类似工具 lazyjj 还不够成熟；mcookly 提到 Magit 可能也能高效完成类似操作。 补充讨论：everybodyknows 强调每个提交都应该能编译通过，这是结构性标准；nextaccountic 希望 VCS 能同时保存真实历史和清理后的历史；关于 `jj absorb` 的智能程度存在技术细节讨论。

文章摘要

数月来,诈骗者利用漏洞从微软内部邮箱地址(msonlineservicesteam@microsoftonline.com)发送垃圾邮件。该地址通常用于发送合法账户通知,诈骗者通过注册新微软账户获得访问权限,发送伪装成官方通知的钓鱼邮件,诱导用户访问诈骗网站。反垃圾邮件组织Spamhaus表示此问题已持续数月。微软回应称正在调查并采取行动,加强检测和拦截机制。这是近期多起利用公司系统进行诈骗的事件之一。

评论摘要
主要讨论点：大型科技公司（微软、谷歌等）的邮件系统存在安全漏洞，允许攻击者通过官方域名发送钓鱼邮件，绕过反欺诈保护。 不同观点： • **域名管理混乱问题**：微软等大公司拥有过多域名（如microsoftonline.com），连内部可能都没有完整清单，导致用户难以辨别真伪。公司要求用户检查域名防钓鱼，却不公布官方域名列表，存在矛盾。 • **技术漏洞被利用**：攻击者利用微软、谷歌、Akamai等公司的邮件端点或API漏洞，从官方域名发送完全自定义的钓鱼内容，完全绕过SPF等反欺诈机制。多位用户报告收到来自google.com、paypal.com等官方域名的垃圾邮件。 • **报告机制失效**：用户向微软、谷歌等公司报告安全问题极其困难，找不到有效联系渠道，提交后也无人处理。有评论提到可能需要通过HN等公开渠道曝光才能引起重视。 • **视觉欺骗手段**：除了域名漏洞，攻击者还利用字体相似性（如"m"和"rn"在Outlook中难以区分）进行钓鱼。 补充讨论：有人建议使用子域名（如internal.microsoft.com）统一管理，但这一方案似乎遥不可及。FBI也曾遭遇类似攻击，说明问题的普遍性和严重性。

Constraint Decay: The Fragility of LLM Agents in Back End Code Generation

作者: wek | 评分: 141 | 评论数: 20 | 发布时间: 2026-05-24 12:55
文章摘要

这篇论文研究了大语言模型(LLM)代理在后端代码生成中处理结构性约束的能力。研究发现了"约束衰减"现象:当结构性要求(如架构模式、数据库、ORM映射)增加时,代理性能显著下降,平均失去30分。实验涵盖8个Web框架的100个任务,发现代理在简单框架(如Flask)中表现较好,但在约定繁重的框架(如Django、FastAPI)中表现糟糕。数据层缺陷(错误的查询组合和ORM运行时违规)是主要失败原因。研究指出,同时满足功能和结构要求仍是编码代理的关键挑战。

评论摘要
主要讨论点：LLM编码代理在面对架构约束时的性能衰减现象 不同观点： • **约束衰减派**（jdlshore, dwa3592）：LLM在无约束生成时表现优秀，但在遵循明确架构规则时性能下降。随着上下文窗口填满，模型会逐渐失去遵守约束的能力，适合快速原型但不适合生产级开发。 • **架构工具派**（KronisLV, pianopatrick）：应开发架构检查工具（如ArchUnit）和框架来强制约束，而非依赖markdown描述。通过静态检查和代码生成自动化规范执行，这对人类和LLM都有益。 • **规划优先派**（AmazingTurtle）：先进行规划模式，链接相关文档，让代理在新鲜上下文中制定计划，再执行。分离规划和执行阶段效果更好。 • **约束增强派**（vishvananda, bob1029）：发现相反现象——在大型遗留代码库中，代理性能反而更好。从一开始就包含架构指导比事后添加更有效。存在"钙化"现象：代码库中的模式会自我强化。 • **实践技巧派**（siliconc0w, yomismoaqui）：使用示例文件引导比markdown更有效；静态类型语言比动态类型更易维护；原始SQL比ORM效果更好。 补充讨论：有人质疑研究未充分测试前沿模型（如GPT-5.2-codex），也有人从哲学角度指出"LLM不会思考"的本质局限。

you_can::turn_off_the_borrow_checker

作者: striking | 评分: 46 | 评论数: 10 | 发布时间: 2026-05-22 20:31
文章摘要

这是一个Rust宏库文档，介绍了`turn_off_the_borrow_checker`宏。该宏通过将引用包装在`borrow_unchecked()`函数中来解绑生命周期，从而抑制借用检查器的错误提示。文档强调这**不应在生产代码中使用**，仅用于教育目的。它允许创建多个可变引用等不安全操作，但会导致未定义行为和潜在的运行时错误。宏的工作原理是识别代码中的`&`、`&mut`、`ref`等引用操作符，并用unsafe包装绕过编译器的别名保证。文档附带了多个讨论链接，解释为什么不应该这样做。

评论摘要
主要讨论点：对一个通过宏或技巧突破 Rust 安全/借用限制的项目，大家在“好玩、实用、风险和实现方式”上的不同看法。 不同观点： • 觉得这是有趣的边界探索与玩梗作品。有人称其是“Cool idea”，也有人说“Disgusting. I love it.”；还有人把它联想到 Perl 的 ACME 模块、以及早年 C++“多种访问私有成员的方法”，强调其娱乐性和实验性。 • 期待它不只是“关闭借用检查器”。有评论认为目前 `you_can` 更像 `turn_off_the_borrow_checker`，希望以后加入更多反例，去扩展“Rust 里哪些事不是不能做，只是要非常规手段”的展示。 • 从实用角度，有人分享替代做法：在单线程、无需释放或关机后无需清理的场景下，可先 `Box` 再 `Box::into_raw`，以获得多个可变引用。这说明类似需求并非纯理论，也有人用更直接的 `unsafe` 方案解决。 • 对安全性持警惕或讽刺态度。像“Even more unsafe rust, great!” 体现出对项目增加不安全性的担忧或调侃。 • 关注技术细节和代价。有人追问宏是否能偷偷插入 `unsafe` 块，另有人关心这类做法是否会明显影响编译时间。 补充讨论：争议焦点主要在于，这类项目究竟是有教育意义的边界演示，还是在削弱 Rust 的安全承诺；同时也涉及“宏隐藏 `unsafe`”的透明性问题。
