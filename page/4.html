Sirius: A GPU-native SQL engine

作者: qianli_cs | 评分: 100 | 评论数: 5 | 发布时间: 2025-06-28 14:18
文章摘要

Sirius 是一个 GPU 原生的 SQL 引擎，通过 Substrait 查询格式与现有数据库（如 DuckDB）集成，无需重写查询或进行重大系统更改。它适用于交互式分析、金融工作负载和 ETL 任务，在 TPC-H 测试中，SF=100 时相较于 CPU 查询引擎有约 10 倍的速度提升。Sirius 支持 Ubuntu 20.04 及以上版本、NVIDIA Volta 或更高版本的 GPU、CUDA 11.2 及以上，以及 CMake 3.30.4 及以上版本。用户可以通过 AWS 镜像、Docker 镜像或手动安装来配置环境。构建 Sirius 需要克隆其仓库并使用特定命令进行编译，如需使用 Python API，还需额外安装相关包。

主要讨论点：Substrait项目的应用和其在不同硬件（如GPU）上的可行性及挑战 不同观点： • cpard：对Substrait被更多地使用感到乐观，提到它已被DuckDB等引擎支持，主要应用案例是Apache Gluten项目结合Velox作为Spark的执行引擎。虽然项目有野心且存在局限性，但需要更多类似的项目推动其发展。 • RachelF：指出Volta 7是家庭使用的高端硬件，对于个人在家实验而言要求过高。 • b0a04gl：提出查询计划与引擎紧密相关，包括成本模型、内存布局、并行策略和代码生成行为等。Substrait提供了结构上的可移植性，但实际执行效率依赖于引擎特定的重写。例如，在DuckDB中优化的计划在Sirius中可能表现不佳，除非进行调整。 • tucnak：将Substrait与PG-Strom（Postgres的GPU相关扩展）进行比较，讨论了GPU在数据库应用中的适合性。提到Xilinx的Alveo系列加速器和AI设备（如Versal）在计算和网络中的应用。强调了计算网络的重要性，并指出PostgreSQL的扩展性和外键数据API的应用。 • Joel_Mckay：回顾PostgreSQL多年前已有GPU加速器的使用，但对GPU的故障率和可靠性表示担忧，特别是NVIDIA卡可能导致的整个主机电源系统故障。认为在数据库可靠性要求高的情况下，不应使用GPU。 补充讨论： • tucnak和Joel_Mckay关于GPU在数据库中应用的可行性和风险的讨论，涉及到硬件故障和可靠性问题。 • tucnak提出的计算网络概念，认为这是当前的趋势，类似于MapReduce在十年前的流行。 • 提到的各种技术链接和参考资料，如PG-Strom、Alveo系列加速器、Corundum开源NIC设计，为讨论提供了进一步的技术背景。 争议焦点： • GPU在数据库应用中的适用性和风险，特别是对系统可靠性和硬件故障的担忧。 • Substrait在不同引擎间查询计划的优化和执行效率问题。
