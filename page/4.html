Riscrithm – An intuitive RISC-V assembler and optimizer coded in Go

作者: patrick-ghetea | 评分: 25 | 评论数: 2 | 发布时间: 2026-05-25 21:01
文章摘要

这篇文章是 Riscrithm 的开发手册，介绍了一种可编译为纯 RISC-V 汇编的高级宏汇编方言。内容涵盖其 CLI 用法、文件结构要求（`header`、`entrypoint`、`define`）、基于缩进的标签语法、可直接嵌入原生汇编的 `!!` 原始块，以及中断、陷阱、等待等核心指令映射。同时说明了变量、标签、常量的命名规范与表达式/内存操作的设计思路。

评论摘要
主要讨论点：Riscrithm 这类“更易写的汇编语言”是否有实际价值，以及它与传统高级汇编/直接用 C 生成代码之间的关系。 不同观点： • `Joker_vD`持怀疑态度：认为 Riscrithm 本质上像 PL/360、PL-11 这类“高级汇编”。其核心论据是，这类语言的生存空间早已被 C 挤压；如果目标 ISA 比较正常，直接基于 `PCC`、`LCC`、`TinyCC` 改一个指令生成器，一周左右就能做出质量尚可的方案，因此没必要单独发展这种语言。 • `patrick-ghetea`作为项目作者，强调 Riscrithm 的定位不是取代高级语言，而是做“更直观的 RISC-V 汇编器”。论据包括：语法更简洁、但仍严格贴合原生机器指令；仓库里已有 v1.0.0 的详细说明和开发手册；v1.1.0 正在补充重要特性；并且工具链已支持多平台。 补充讨论： • 争议焦点在于：这是“过时的高级汇编思路”，还是“仍有价值的、更易用的汇编表达方式”。 • 两条评论是直接回应关系：前者从语言演化和工程效率角度质疑必要性，后者则从具体产品定位、可用性和后续迭代计划进行澄清与辩护。

CPPL: A Circuit Prompt Programming Language

作者: chrsw | 评分: 22 | 评论数: 3 | 发布时间: 2026-05-21 11:50
文章摘要

这篇论文提出了CPPL（电路提示编程语言），一个编译器中介的硬件设计框架。针对大语言模型(LLM)难以直接生成可验证的RTL代码的问题，CPPL提供了Python前端DSL和基于JSON的电路中间表示，使LLM生成的代码可被编译器静态检查、优化，并最终通过CIRCT生成可综合的Verilog。在RTLLM基准测试中，CPPL相比直接生成Verilog或CIRCT IR提高了功能正确性，CIRCT优化还降低了综合后的AIG节点数。该方法将LLM辅助硬件设计转化为可检查的前端问题，提升了可靠性和可优化性。

评论摘要
主要讨论点：这篇论文对“LLM可用于RTL设计自动化”的论证是否成立，以及论文应采取怎样的批判性分析方式。 不同观点： • `genxy`认为这是一篇适合本科生拿来“拆解”的论文，重点不是直接接受结论，而是用“对抗式总结”“倒金字塔写法”等方式找出论文可改进之处；其核心立场是作者应更主动、更严厉地审视自身工作。 • `artemonster`强烈反对论文开头“LLM在RTL设计自动化中已展现前景”这一表述，认为这一主张缺乏有力证据。他的论据是：LLM在网页应用代码生成上表现较好，部分原因是代码模块化、可组合、易推理；但RTL涉及状态爆炸、时序依赖强、难以组合，本质上更像复杂机械构造而非普通代码，因此LLM很难真正理解。 • `artemonster`还进一步举例说明：即便有清晰的信号协议、时序行为描述、甚至可被形式验证工具利用的断言，顶级LLM依然难以“弄懂”RTL；他也否定“通过低质量DSL/netlist抽象就能解决问题”的思路。 补充讨论：两条评论存在递进关系：前者是方法论上的“应更批判地读/写论文”，后者则直接给出实质性质疑。争议焦点集中在：`LLM是否真的已经在RTL自动化中显示出可靠前景`，以及论文是否提供了足够证据支持这一前提。

Bytecode VMs in surprising places (2024)

作者: azhenley | 评分: 111 | 评论数: 20 | 发布时间: 2026-05-22 14:12
文章摘要

这篇文章介绍了字节码虚拟机在一些意想不到的地方的应用： **eBPF**：Linux内核中的扩展机制，包含字节码解释器和JIT编译器。最初用于网络数据包过滤（1993年），后来演变为通用的内核虚拟机，拥有10个通用寄存器和上百个操作码。 **DWARF表达式**：编译器在二进制文件中嵌入的调试信息格式。使用基于栈的表达式语言，让调试器能够计算局部变量的值（可能在寄存器、栈上或被优化掉）。 **GDB代理表达式**：GDB的另一个字节码解释器，用于远程调试时在目标机器上执行表达式求值，避免传输完整的符号表达式。采用简单的字节码语言，约40个操作码，适合实时应用。

评论摘要
主要讨论点：软件系统中嵌入式虚拟机和字节码解释器的普遍性及其利弊 不同观点： • **支持方观点**：嵌入式VM提供了强大的可扩展性。grishka分享了在Fediverse服务器中使用字节码VM实现API方法和垃圾邮件过滤；drob518承认"对可扩展系统有好感"；多位开发者兴奋地分享各种实现案例 • **安全担忧方**：drob518指出核心问题——每个子系统携带图灵完备字节码和JIT会大幅增加攻击面，所有组件都需要无bug才能保证系统安全；superjan用iOS的JBIG2 PDF漏洞作为实际安全威胁的例证 • **技术考古派**：大量评论者列举历史案例证明这是长期存在的模式——从1971年Busicom计算器、Quake游戏引擎、TrueType字体、到Excel公式解释器、ACPI配置、比特币交易脚本等 补充讨论： 评论展现了技术社区的典型分歧：实用主义者欣赏VM带来的灵活性和跨平台一致性（如Excel跨架构保持浮点精度），而安全专家警告代码复杂度带来的系统性风险。讨论未形成明确共识，更多是知识分享和案例交流。
