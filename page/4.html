Migrating away from Rust

作者: rc00 | 评分: 238 | 评论数: 42 | 发布时间: 2025-04-28 18:47
文章摘要

文章主要讲述了作者在2023年底开始使用Bevy游戏引擎和Rust语言开发游戏《Architect of Ruin》，最初因个人兴趣和Bevy社区的开放性而选择这一组合。尽管Bevy的ECS模型和Rust的编译时检查让开发初期非常顺利，但随着项目进展，一些实际问题逐渐显现。 主要挑战包括：与新手弟弟合作时，Rust的学习曲线陡峭，影响了他的贡献效率；Rust的低层次抽象虽强大，但不利于快速迭代高层次的游戏机制；Bevy作为年轻引擎，快速更新带来了API不稳定和迁移负担。一次渲染问题引发的挫败感促使作者重新评估，最终在2025年初将项目转向C#和Unity。 尽管Bevy和Rust有许多优点，但为了更高效地实现游戏玩法，作者决定承受转换引擎带来的短期生产力下降，以追求长期的可行性。

评论摘要
主要讨论点：游戏开发中不同工具和语言的选择，包括商业引擎（如Unity、Unreal）与开源引擎（如Godot、Bevy）的比较，以及编程语言（如Rust、Go、C#）在游戏开发中的适用性。 不同观点： • 一些开发者认为商业引擎（如Unity）由于其成熟的功能和广泛的支持，仍然是快速迭代和发布游戏的最佳选择。尽管Unity有历史包袱和一些问题（如API变更），但其整体便利性和成熟的生态使其难以替代。 • 另一部分开发者则支持使用Rust和Bevy等新兴技术进行游戏开发。他们认为Rust和Bevy提供了更好的性能和代码安全性，但承认这些工具在快速迭代和易用性方面还有不足，特别是在处理并发和复杂游戏逻辑时。 • 有开发者从Rust转向Go以加快迭代速度，尤其是在处理API和金融类项目时。他们认为Go的简洁性和速度足够应对大部分需求，只有在极高性能要求的场景下才需要结合Rust。 • 一些开发者指出Bevy和Godot等开源引擎的质量和社区支持正在不断提升，但目前在易用性和稳定性方面还不如Unity和Unreal。他们表示，尽管这些开源引擎在未来有很大潜力，但目前仍在发展阶段，不适合所有项目。 • 还有开发者提到游戏开发中并不总是需要极高的内存安全性和性能，因此Rust的复杂性在某些情况下可能并不值得。C#等带有垃圾回收机制的语言在许多游戏开发场景中已经足够。 补充讨论： • 一些开发者提到使用不同工具时的实际开发经验，如Unity的“电话主页”间谍软件问题和Godot的社区文化。这些问题可能影响开发者对工具的选择。 • 另一个值得注意的讨论点是，规划和选择合适的工具对项目成功至关重要。有开发者建议在项目初期进行详细规划，选择合适的工具和语言，而不是仅凭个人偏好。 • 最后，有开发者提到不同游戏类型和平台可能需要不同的引擎和工具，没有一个万能的解决方案。开发者应根据项目需求灵活选择。 争议的焦点： • 主要争议在于Rust和Bevy等新兴技术是否能够在游戏开发中取代商业引擎（如Unity）。支持者认为Rust和Bevy提供了更好的性能和安全性，反对者则认为这些工具在易用性和稳定性方面还有较大差距。 • 另一个争议点是C#和Rust在游戏开发中的适用性。一些开发者认为Rust的复杂性在游戏开发中并不总是必要，C#等带有垃圾回收机制的语言已经足够应对大部分需求。

Show HN: I built a hardware processor that runs Python

作者: hwpythonner | 评分: 935 | 评论数: 70 | 发布时间: 2025-04-28 11:44
文章摘要

PyXL 是一种定制硬件处理器，直接在硬件上执行 Python 代码，无需虚拟机、JIT 或解释器。它通过自定义工具链将 Python 文件编译为 CPython 字节码，并转换为自定义汇编代码，最终在基于 Zynq-7000 FPGA 的硬件上运行。相比之下，MicroPython 运行在软件虚拟机上，导致性能较低。在 GPIO 往返测试中，PyXL 仅需 480 纳秒，而 MicroPython 需要约 15,000 纳秒，PyXL 速度快 30 倍，甚至在时钟速度归一化后快 50 倍。PyXL 通过直接在硬件上执行 Python 字节码，实现确定性时序和实时行为，而无需经过解释器或 C 函数调用。

评论摘要
主要讨论点：PyXL项目及其技术实现的讨论 不同观点： • [zik] 认为项目的宣传有夸大成分。他指出，PyXL并不是直接执行Python代码，而是通过编译成二进制代码运行，类似于其他CPU的操作，因此建议修改宣传语为“一个支持Python的定制架构处理器”。 • [Y_Y] 对项目的局限性以及设计过程表示兴趣，尤其是为何选择为动态语言如Python设计定制处理器，并认为这一领域最近未被充分探索。 • [hwpythonner] 作为项目参与者，提供了项目的早期 benchmark，并展示了PyXL在GPIO操作上的速度优势，相较于MicroPython快30倍。 • [jonjacky] 提到了2012年类似的Python硬件项目pyCPU，并指出其仅支持非常有限的Python子集，以此对比当前项目的进展。 • [boutell] 赞赏项目的同时，提出了与创建一种具有Python语法但类型安全的语言并编译为原生代码相比，定制硬件的最终特性集是否更大这一问题。 补充讨论： • [sunray2] 关注PyXL的物理极限，如时序精度、延迟和抖动，并将其与ARTIQ项目比较，指出PyXL在简化用户操作方面的潜在优势。 • [obitsten] 质疑为何Python社区普遍不使用编译，而是直接使用源文件，并探讨编译的潜在好处。 • [rthomas6] 询问了设计处理器所用的硬件描述语言（HDL）、处理器的汇编语言，以及与在现有处理器上编译Python相比的优势。 • [rkagerer] 提到曾期待有原生执行.Net字节码的处理器，并对PyXL项目表示赞赏。 • [thenobsta] 称赞项目的同时，提到了未能成功的Tabula FPGA项目，表示遗憾。 • [froh] 确认了对项目技术细节的理解，并表示项目有趣，但对其具体实现如ASIC和微码表示好奇。 • [JadoJodo] 邀请Python开发者讨论Python语言的特点、过去实现类似项目的困难、Python在此类项目中的优势，以及对Python生态系统的一些抱怨。 • [tsukikage] 质疑使用定制工具链、定制指令集和定制处理器的优势，与现有工具如Cython、Nuitka等相比，有何不同。 • [yanniszark] 询问为何不直接编译为ARM汇编，而是使用PySM汇编，PySM是否为适应Python特性而特别设计。 • [Jean-Papoulos] 提到PyXL不支持C库，这将排除大量Python包的使用。 争议焦点： • PyXL是否如宣传所言“直接执行Python代码”，还是仅仅是通过编译运行，与其他处理器类似。 • 定制硬件处理器相对于现有工具和架构的实际优势和局限性。

The 12-bit rainbow palette

作者: rguiscard | 评分: 269 | 评论数: 21 | 发布时间: 2025-04-28 23:12
文章摘要

这篇文章介绍了12位彩虹调色板的设计过程，专为National Grid: Live设计，包含12种颜色，考虑了人眼对亮度、色度和色相的感知。调色板使用12位色彩深度，每个颜色用四个字符的十六进制代码表示，如#817。与RGB色彩空间不同，LCH色彩空间根据亮度、色度和色相定义颜色，更符合人眼感知。简单RGB彩虹调色板在相邻颜色间亮度变化大，而LCH调色板通过控制亮度变化，使黄色最亮，红色和蓝色适中，避免了不良视觉效果。尽管12位色彩深度限制了可用颜色，但通过微调亮度、色度和色相，最终调色板实现了色相均匀分布、色度变化小、亮度平滑过渡。

评论摘要

文章摘要

这篇文章介绍了Haskell中对"压缩数据"（packed data）格式的支持。传统上，数据在网络传输或持久化时需要序列化（如JSON或XML），接收时需要反序列化，这既耗时又增加数据体积。文章提出一种二进制压缩数据格式，可以在发送和接收数据时跳过这些步骤，直接使用数据，提高效率，尤其是减少指针跳转，更好地利用L1缓存。 文章介绍了一个名为`packed-data`的Haskell库，它利用类型系统和模板Haskell实现数据的打包、解包和遍历，而无需修改编译器。该库自动生成代码，支持任意数据类型的打包与解包，并提供自定义的模式匹配功能。关键概念包括`NeedsBuilder`类型，它通过phantom types控制打包过程中的数据需求。 这一方法受到Cap'n Proto等项目的启发，但Haskell是首个通过纯类型系统实现该功能的语言。

评论摘要
主要讨论点：Haskell中的新型二进制数据格式"packed"格式及其优势和相关技术比较 不同观点： • [nine_k] 介绍了"packed"数据格式，强调其无需反序列化步骤，能够直接使用内存中的数据。该格式通过内联数据结构字段，避免了指针跳转，从而充分利用L1缓存，提升了遍历速度。同时提到这种方法与Cap’n Proto有相似之处，适用于直接将子树或子图通过网络传递。 • [NetOpWibby] 提出了一个问题，询问"packed"格式是否类似于Haskell中的MessagePack，暗示可能存在其他类似技术的比较和混淆。 • [tlb] 对[nine_k]的观点提出了一些补充，认为序列化后的数据通常比内存中的表示要大，但指出二进制序列化比JSON等格式要小。同时，提到为了支持快速查找和可变性，像map这样的数据类型在内存中必然会更大。 • [lordleft] 对文章的写作质量表示赞赏，但没有提出技术性讨论。 • [gitroom] 表达了对这种减少内存操作步骤的技术的好感，认为减少内存中的跳跃操作能提升效率并让人满意，暗示支持这种优化方式。 补充讨论： • 争议焦点在于序列化数据大小与内存表示大小的比较。虽然[nine_k]没有直接提到数据大小的比较，但[tlb]补充了这一方面的讨论，指出序列化数据通常较大，但二进制序列化一般比文本格式（如JSON）要小。 • [NetOpWibby]的评论引发了对"packed"格式与其他序列化格式（如MessagePack）之间异同的思考和澄清需求。 • [gitroom]的观点反映了开发者对性能优化的普遍需求，特别是希望减少不必要的内存操作以提高程序效率。
