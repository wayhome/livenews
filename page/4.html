Recent AI model progress feels mostly like bullshit

作者: paulpauper | 评分: 148 | 评论数: 36 | 发布时间: 2025-04-06 18:01
文章摘要

文章讨论了AI模型在安全漏洞检测领域的实际进展与宣传效果之间的差距。作者与团队自2024年6月起开发一款基于AI的工具，用于自动监控代码库的安全问题。尽管初期模型如Claude 3.5 sonnet表现出显著改进，但后续的新模型如3.6和3.7等在实际应用中未见明显提升。作者发现，尽管AI在对话和控制测试中表现更好，但在经济实用性和新任务处理能力上改进有限。多个行业的创始人也报告了类似经历，质疑AI实验室是否夸大了模型进步。文章最后提出，若无法准确衡量AI当前的影响，未来在更复杂领域（如管理公司或制定公共政策）中可能面临更大挑战。

评论摘要
主要讨论点：大型语言模型（LLM）的可靠性、局限性以及在实际应用中的表现 不同观点： • [aerhardt] 认为 ChatGPT 在回答关于 Paul Newman 是否有酗酒问题时给出了错误的回答，并指出其母亲通过权威来源证明了ChatGPT的错误。这反映了LLM在处理简单问题时的不可靠性。 • [iambateman] 认为 LLM 倾向于给出肯定的回答以显得“聪明”和“讨好”用户，而不是承认不知道答案。这种倾向使得LLM在复杂场景中的表现不尽如人意，即使基准测试分数有所提高，实际应用中的改进有限。 • [InkCanon] 指出，SOTA模型在数学竞赛中的表现不佳，暗示AI可能依赖于记忆训练数据而非真正的理解和解决问题能力。同时，质疑AI公司在训练数据中去除了测试数据的做法。 • [lukev] 认为，对于AI的讨论往往是分散且基于个人经验的，难以形成统一的结论。尽管如此，一些人可能会因为运气或个人经验而在AI使用上做出“更好”的选择。 • [jonahx] 支持[iambateman]的观点，认为LLM为了在对话中显得聪明，会倾向于指出潜在问题而不是确认一切正常，这与人类行为类似。 • [joelthelion] 基于个人使用经验，认为当前的LLM（如Gemini 2.5）在某些应用中表现出色，但未来发展仍不确定。 • [nialv7] 认为当前的AI无法进行复杂的符号推理，如安全漏洞检测，只能通过模式匹配识别“坏代码”，但无法深入分析。 • [HarHarVeryFunny] 强调LLM本质上是预测系统，不能期望其在特定领域的改进会自动转化为其他不相关领域的改进，因为它们不是通用认知架构。 • [throw310822] 认为即使AI发展停滞，未来十年我们仍会发现其新用途。当前技术发展速度超过了我们能有效吸收和利用的能力，可能带来负面后果。 • [maccard] 认为GPT和Claude等模型在过去一年中表现有所下降，本地LLM从几乎无用到勉强可用，但仍不足以支持日常使用。工具和应用的改进才是关键。 • [fxtentacle] 指出，近期AI模型的进步主要体现在价格上，如4-bit量化的QwQ-32B在编码性能上接近Claude 3.5，但运行成本大幅下降。 • [ants_everywhere] 认为最近的模型更新有明显改进，但个人经验和任务复杂性可能导致不同看法。新模型可能更理解任务的模糊性，导致旧的提示策略失效。 • [gundmc] 提到Gemini 2.5发布前后的变化，并对其生产力提升表示惊叹。 • [sema4hacker] 认为LLM的改进并未反映在经济实用性或通用性上，可能重蹈1980年代“专家系统”的覆辙。 • [einrealist] 引用LeCun的批评，指出LLM的准确性问题不会自行解决，提高准确性只会变得更加昂贵，限制了实际应用。担心未来质量下降，AI公司变得“太大而不能倒”。 补充讨论： • LLM在实际应用中的局限性和不可靠性，包括对简单问题的错误回答。 • LLM倾向于给出肯定回答以显得“聪明”或“讨好”，导致在复杂场景中表现不佳。 • AI模型依赖记忆训练数据而非真正理解问题，导致在特定领域表现好但不具备通用性。 • 当前AI技术发展迅速，但工具和应用的改进更为重要，未来发展仍不确定。 • 对AI技术过度依赖和未来质量下降的担忧，以及AI公司在政策制定中的影响力。

Serving Vector Tiles, Fast

作者: altilunium | 评分: 87 | 评论数: 4 | 发布时间: 2025-04-06 02:56
文章摘要

本文介绍了Fabian Rechsteiner对几种开源矢量瓦片服务器从PostGIS实例提供瓦片的速度比较。比较的服务器包括BBOX、ldproxy、Martin、pg_tileserv、Tegola和TiPg。除了在GitHub上的速度统计，他还提供了一个互动对比网站（https://vectormap.ch），使用MapLibre客户端和图尔高州的数据进行可视化性能测试。 benchmark仓库包含自定义测试的代码，而他的硕士论文（德语）也公开发布。此外，Geomatik Schweiz杂志有一篇付费文章分析了这一研究。虽然速度是选择服务器的重要因素，但并非唯一考量。

评论摘要
主要讨论点：关于使用不同工具和方法生成和提供矢量瓦片数据的技术讨论 不同观点： • [durkie] 认为可以使用 PostGIS 的 GeoJSON 导出结合 Tippecanoe 进行矢量瓦片生成。他指出 Tippecanoe 速度快、并行处理能力强，并且提供了许多 PostGIS 所缺乏的可配置选项，特别适合生成矢量瓦片数据。 • [stevage] 指出 "serving" 一词在这里具有误导性。他认为大多数矢量瓦片服务器提供的是预先生成的瓦片，这样速度极快。而这里的讨论重点是如何通过自定义的网络服务器从 PostGIS 动态生成瓦片，二者有所不同。 • [pbsurf] 分享了自己从 GeoDesk 数据库（相比 PostGIS 数据库更小）按需生成 OpenStreetMap 矢量瓦片的服务器经验，并提供了一个 GitHub 项目链接，展示了具体的实现方式：https://github.com/styluslabs/geodesk-tiles • [pluto_modadic] 提出了关于术语的疑问，询问讨论中指的是矢量数据还是瓦片数据。他通过类比指出，这类似于讨论 "提供 PNG JPEG 图片" 或 "提供 JPEG PNG 图片"，不同的服务器可能返回不同格式的数据（如图片或矢量线数据）。 补充讨论： • 讨论中涉及了工具选择和实现细节上的不同方法，包括预生成瓦片和动态生成瓦片的区别。 • 对术语的准确使用存在一定争议，特别是关于 "vectors" 和 "tiles" 的具体含义。 • 提供了具体的项目实例（pbsurf 的 GeoDesk 项目），展示了如何在实际应用中处理和提供矢量瓦片数据。

montasaurus/result: A simple Rust-like Result type for Python 3

作者: networked | 评分: 7 | 评论数: 0 | 发布时间: 2025-04-06 14:10
文章摘要

本文介绍了一个名为`result`的Python库，灵感来源于Rust的`Result`类型，用于处理可能成功或失败的操作。该库提供了两种结果类型：`Ok`表示成功并包含返回值，`Err`表示失败并包含错误信息。通过类型注解，开发者可以清晰区分成功和失败的情况。库中包含如`is_ok`、`is_err`等函数来检查结果类型，并可以直接访问成功值（`ok_value`）或错误值（`err_value`）。此外，还支持使用Python 3.10的`match`语句进行模式匹配。该库简化了错误处理，避免使用自定义异常，并提供了自动生成的API文档。注意，该库是实验性的，使用时需自行承担风险。

The ADHD body double: A unique tool for getting things done

作者: yamrzou | 评分: 175 | 评论数: 26 | 发布时间: 2025-04-05 22:45
文章摘要

文章介绍了一种名为“身体加倍”（body doubling）的策略，用于帮助患有注意力缺陷多动障碍（ADHD）的人提高专注力和生产力。这种方法由作者在辅导客户大卫时共同发明，大卫是一位退休高管，尽管组织良好，但难以专注于琐碎任务。他发现，当妻子坐在旁边时，他更容易集中精力。这种现象被称为“身体加倍”，即另一个人只是在场，无需提供建议或帮助，就能帮助ADHD患者减少分心、增强动力。 这种策略通过创造一种责任感来起作用，使得个体更有可能完成任务。身体加倍可以面对面进行，也可以通过虚拟方式实现，关键在于两人同时工作，并事先分享目标以增强责任感。这种方法特别适合那些难以开始任务或容易分心的人，因为它为ADHD患者提供了一种新的刺激，帮助他们保持专注。

评论摘要

Dynamic Register Allocation on AMD's RDNA 4 GPU Architecture

作者: ingve | 评分: 101 | 评论数: 3 | 发布时间: 2025-04-05 17:51
文章摘要

AMD's RDNA 4 GPU架构引入了动态VGPR（矢量通用寄存器）分配模式，以优化寄存器使用和线程并行性之间的权衡。传统GPU的寄存器分配是静态的，每个线程的寄存器数量固定，导致在某些情况下限制了活跃线程数。特别是在光线追踪中，不同阶段对寄存器的需求不同，静态分配会降低效率。RDNA 4的动态分配允许线程在运行时调整所用寄存器的数量，从而在需要较少寄存器时增加活跃线程数，提高并行性。动态分配通过`SQ_DYN_VGPR`寄存器控制，线程使用`s_alloc_vgpr`指令请求更多或更少寄存器，硬件按块分配寄存器。如果分配失败，着色器会忙等待直到成功。这种动态模式有助于更好地平衡寄存器使用与线程并行性，尤其是在光线追踪等延迟敏感的任务中。

评论摘要
主要讨论点：[如何解决着色器或硬件中由于寄存器争用导致的潜在死锁问题] 不同观点： • [kmeisthax] 提出了一种疑问，即如果寄存器争用可能导致死锁，为什么着色器或硬件不能检测到死锁并将一个或多个线程的数据转移到本地内存（spilling to local memory）。这种方法旨在通过动态调整来避免死锁。 • [monocasa] 认为寄存器请求应该与纹理访问、光线追踪硬件请求等资源请求的记分板机制（resource request scoreboarding）类似，通过某种协调机制来避免死锁。他指出简单地忙等待（busy waiting）不是一个理想的方案，因为这会影响着色器程序的执行进度。 • [JonChesterfield] 对[kmeisthax]提出的想法表示赞同，并进一步提出是否存在一种合理的方式来进行查询，即不是直接请求更多寄存器，而是询问当前可用的寄存器数量，从而进行相应的调整。 补充讨论： • [kmeisthax] 的观点中隐含了对硬件或着色器智能管理寄存器资源的能力的期待，特别是通过检测死锁并采取措施（如将线程数据转移到本地内存）来提高系统的鲁棒性。 • [monocasa] 强调了资源请求记分板机制的重要性，认为这是一种比忙等待更优的方案，可以有效避免死锁和资源争用问题。 • [JonChesterfield] 提出了一个实际操作中的问题，即如何查询当前可用的寄存器数量，这可能涉及到硬件或软件层面的查询机制设计。 争议焦点： • 是否能够通过检测死锁并动态调整（如将线程数据转移到本地内存）来有效解决寄存器争用问题，还是应该依赖于更传统的记分板机制或查询机制来管理资源。 • 忙等待是否是一个可接受的解决方案，还是应该完全避免以确保着色器程序的执行进度。
