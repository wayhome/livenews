"Night of the Living Dead" accidentally became public domain (2019)

作者: edavis | 评分: 54 | 评论数: 6 | 发布时间: 2025-05-06 20:14
文章摘要

《活死人之夜》是由乔治·罗梅罗执导的经典恐怖片，奠定了现代僵尸的形象：无智力的行尸走肉，渴望活人 flesh。该片因发行商忘记添加版权声明而进入公共领域，导致罗梅罗损失了数百万潜在收入。尽管如此，影片因其易得性而成为经典，影响了如《行尸走肉》和《僵尸之地》等众多作品。罗梅罗后续拍摄了五部僵尸电影，其中《活死人黎明》被认为是最出色的续作。尽管他在好莱坞未获足够认可，但罗梅罗作为僵尸电影教父的地位无可撼动。

评论摘要
主要讨论点：电影《Night of the Living Dead》因版权声明缺失而进入公有领域的事件，以及与此相关的版权法变迁和其影响。 不同观点： • **gus_massa**：指出电影发布于1968年，而当时的版权法与现在不同。在1978年1月1日至1989年2月28日之间发布的作品，如果省略了版权声明，可能会在一定时间内失去版权保护。而1968年的作品根据1909年版权法，若没有正确标注版权声明，版权将永久丧失。 • **mathgeek**：对该电影因错误进入公有领域表示矛盾情感，质疑这一情况是否真的“不幸”。 • **Malic**：提到类似情况也发生在1963年的电影《Charade》，该电影同样因版权问题进入了公有领域。 • **nico**：认为版权的持续时间过长（作者一生加上死后70年）是不合理的，对此表示质疑。 • **wodenokoto**：质疑发行方是否真的拥有足够的版权所有权来发布修改版进入公有领域，并提到类似情况曾发生在smart.fm的语言学习材料上，他们无意中将材料以左版许可证发布。 • **teddyh**：反驳“版权错误导致损失惨重”的说法，认为这类似于“如果Linus Torvalds对Linux收费，他现在会很富有”的论调，实际上并不成立。同时指出，正是由于该电影可以自由获取，才让它成为经典，否则可能只是一个历史注脚。 补充讨论： • 争议的焦点之一是版权法的历史变迁及其对作品保护状态的影响，尤其是早期法律对版权声明的严格要求。 • 另一个讨论点是对作品因进入公有领域而获得的广泛传播是否对其经典地位的形成起到了积极作用。 • wodenokoto提出的版权所有权问题引发了对版权持有和发布权利的合法性讨论，特别是无意中进入公有领域的情况。 这些观点共同构成了对版权法复杂性及其对文化作品影响的广泛讨论。

Implementing a Struct of Arrays

作者: mpweiher | 评分: 105 | 评论数: 13 | 发布时间: 2025-05-09 10:52
文章摘要

本文介绍了如何使用C++26的反射机制实现一个结构体数组（Struct of Arrays, SoA），以替代传统的数组 of 结构体（Array of Structs, AoS）模式，从而提高内存使用效率和性能。文章借鉴了Andrew Kelley在Zig编译器中的优化思路，将原本组合在一起的结构体成员拆分为独立的数组存储。 文章首先解释了Zig语言中如何通过简单的代码修改实现这一优化，然后转向C++26，利用其反射特性来实现类似的`SoaVector`。通过`std::meta::define_aggregate()`函数，文章展示了如何动态生成包含每个非静态数据成员指针的聚合结构体。接着，文章讨论了如何实现`push_back`和`grow`函数来管理动态数组，并确保每个数据成员数组同步增长。 文章的核心在于利用C++26的反射功能简化SoA模式的实现，避免手动处理每个成员的独立数组操作，同时提高代码的可维护性和性能。

评论摘要
主要讨论点：Struct of Arrays (SoA) 与 Array of Structs (AoS) 的性能比较及其在不同编程语言中的实现和抽象机制。 不同观点： • Dwedit 认为，SoA 和 AoS 的性能差异主要取决于内存缓存和访问模式。如果顺序访问对象并查看所有字段，两者性能相近；如果只查看部分字段，SoA 表现更好；而如果随机访问并查看所有字段，AoS 表现更优。此外，AoS 在计算元素地址时需要乘法步骤，而 SoA 则通常通过位移操作实现。 • PessimalDecimal 对现代 C++ 的复杂性提出批评，认为文章虽然讨论了性能优化，但更多展示了 C++ 的臃肿。 • Gr4vityWall 对文章展示的现代 C++ 的复杂性表示认同，并提到使用 Haxe 宏在编译时将 AoS 转换为 SoA 的做法，同时质疑这种方法的可读性。 • Perihelions 提供了 Common Lisp 中实现 SoA 的代码示例，以满足对该语言实现方式的好奇。 • Monkeyelite 提到了“元对象协议”的概念，认为可以在类定义和实现之间增加一个阶段，选择实例的布局和访问方法，以优化性能和易用性。 • The__alchemist 分享了在 Rust 中使用 SoA 进行数值和科学计算的经验，并提到在 GPU 编程中使用 SoA 的优势，同时对文章中 C++ 的抽象机制表示困惑。 • TheHideout 认为文章展示的方法允许像 OOP 一样使用结构体，同时获得 ECS（实体组件系统）的数组优势。 • Mac3n 提到 JOVIAL 语言中的 TABLE 结构，可以声明为 SERIAL 或 PARALLEL，与 SoA 和 AoS 的概念类似。 • Sph 和 adzm 讨论了使用 C++ 反射和模板实现 SoA 的技术细节，并提出了一种基于反射的操作符。 • Gpderetta 提供了一种基于模板的 SoA 实现方法，并与文章中使用反射的实现进行了对比。 • Jayd16 认为文章的核心在于反射的使用，并对直接访问字段的假设提出了幽默的批评。 • Enthouan 认为文章讨论的内容在 C 中会更简单，对 C++ 的复杂性表示不解。 补充讨论： • 讨论中涉及了多种编程语言（C++, Rust, Common Lisp, JOVIAL）的 SoA 和 AoS 实现方式，展示了不同语言在处理性能优化和抽象机制上的差异。 • 文章中提到的现代 C++ 的复杂性和反射机制成为讨论的焦点，部分评论者对这种复杂性表示批评，认为不如其他语言简单直接。 • 讨论中还涉及了编译时优化、模板和宏的使用，以及在 GPU 编程中 SoA 的优势。

文章摘要

Anarchitecture小组是1970年代活跃于美国纽约的一个艺术家团体，成员包括Laurie Anderson等人，核心成员Gordon Matta-Clark受过建筑教育。小组名称结合了“无政府主义”（anarchy）和“建筑”（architecture），通过非正式讨论进行合作。1974年，他们举办了一场同名展览，批判当时文化中现代主义倾向，特别是建筑作为文化弊端的象征。他们反对文化态度的停滞和建筑对变革的抗拒，所有展览作品均为匿名，以强调集体合作。这一批判态度可能源于Matta-Clark在康奈尔大学接受的建筑教育背景。

评论摘要
主要讨论点：对20世纪艺术家Matta-Clark的作品评价及其在现代艺术中的地位 不同观点： • Aaronbrethorst认为Matta-Clark是他最喜欢的20世纪艺术家之一。他特别提到Matta-Clark的作品如《Splitting》、《Conical Intersect》和《Office Baroque》非常聪明且发人深省。他还指出，即使有人认为大部分现代艺术是垃圾，Matta-Clark的作品仍然具有价值。 补充讨论： • 评论中提到了具体的作品名称，如《Splitting》、《Conical Intersect》和《Office Baroque》，这些作品被视为Matta-Clark艺术成就的代表。 • 提到了现代艺术的争议性，暗示了现代艺术在公众中可能存在两极分化的评价，但Matta-Clark的作品即使在批评现代艺术的背景下，仍然能够获得认可。 • 该评论没有直接涉及对Matta-Clark作品的负面评价，但暗示了可能存在的对于现代艺术的普遍批评，即有些人认为现代艺术没有价值或质量不高。 争议焦点： • 公众对现代艺术的价值存在争议，一些人可能认为现代艺术没有实质内容或不值得欣赏，而像Aaronbrethorst这样的支持者则认为像Matta-Clark这样的艺术家具有独特的艺术价值和思想深度。

Show HN: Hyper – Standards-first React alternative

作者: tipiirai | 评分: 44 | 评论数: 23 | 发布时间: 2025-05-09 13:59
文章摘要

Hyper是一种以标准为核心的标记语言，用于构建用户界面，强调使用HTML、CSS和JavaScript，追求简洁和可扩展性。与React的混合逻辑、结构和样式的单体架构不同，Hyper实现了React 2013年最初的愿景：一个无头视图层。Hyper通过语义HTML和少量类名实现复杂UI，如其表格组件仅需3.9KB的JS，而现代React需要91.3KB。Hyper的设计系统允许通过一个32行的CSS文件实现主题转换，避免了React中通过CSS-in-JS或Tailwind造成的紧耦合和大量维护工作。Hyper通过严格的分离关注点，实现真正的可重用组件和零样板代码，使应用在扩展时仍保持简单。

评论摘要
主要讨论点：前端框架和工具的比较与争议 不同观点： • **React与Nue的功能对比**：[rustc] 提到在"Complex components"代码对比中，React版本包含更多功能（如完整样式、图标、可排序列等），而Nue似乎通过简单的类自动注入这些功能，质疑这种对比是否公平。[__jonas] 进一步讨论了React中使用外部CSS的惯用方式，反驳了认为React不常用classNames和外部CSS的观点，并指出React文档中并未提到Tailwind等工具是惯用方式。 • **Hyper与EJS的比较**：[mg] 偏好EJS，因为其语法简单，只需要了解"<% 开始JS" 和 "%> 结束JS"，其余部分是纯HTML和JS，而Hyper的语法较为复杂。 • **框架逻辑嵌入HTML属性的争议**：[faefox] 认为Angular/Vue将应用逻辑嵌入HTML属性的方式在演示中效果很好，但在实际应用中可能导致两种结果：要么过于简单，需要用JS实现所有功能；要么为了迎合所有需求导致复杂的DSL（如ngFor）。相比之下，JSX更为实用并最终胜出。 • **HARC Stack的简洁性与功能性**：[librasteve] 赞赏简洁且富有表现力的代码，展示了用HARC Stack实现的基本表格例子，但承认HARC Stack目前没有可排序、可过滤的表格组件，且使用了HTMX。同时提到不应进行“逐行代码”的比较。 • **React的复杂性与功能平衡**：[vessenes] 认为React在功能与复杂性之间存在平衡，虽然React的功能丰富，但复杂度较高。理想的框架应在功能与简洁性之间做出明智选择，优化价值与复杂性的比率。 • **虚拟化渲染与性能问题**：[jitl] 询问如何在Hyper中实现100,000项表格的虚拟化渲染。 • **React Server Components的类似问题解决**：[nicce] 提出Nue如何解决与React Server Components类似的问题，如消除后端与前端之间的网络实现差距，使组件定义与动态功能添加无缝衔接。 • **类似框架的参考**：[superchris] 提到Nue看起来像Sprae，并分享了使用Sprae连接模板与Elixir后端的项目，认为这是一个被忽视的优秀工具。 • **框架命名冲突**：[streptomycin] 提到前端框架名称冲突问题，指出多个框架名称相似。 补充讨论： • [internetter] 提供了Nue的发布帖链接，为讨论提供了背景信息。 • [dleeftink] 询问Nue是否是Riot.js的进化或新方向，探讨了Riot.js对Nue的影响。 争议焦点： • React与Nue的功能对比是否公平，以及不同框架的简洁性与功能性之间的平衡问题。 • 框架命名冲突和框架逻辑嵌入HTML属性的实用性与复杂性。

A Taxonomy for Rendering Engines

作者: ibobev | 评分: 39 | 评论数: 4 | 发布时间: 2025-05-06 18:34
文章摘要

Hollow Core Fiber (HCF)

作者: giuliomagnifico | 评分: 49 | 评论数: 6 | 发布时间: 2025-05-09 13:25
文章摘要

Hollow Core Fiber (HCF)是一种通过中空核心传输光信号的光纤，与传统实心玻璃或塑料核心的光纤不同。HCF的中心是空心，通常充满空气或真空，外部由特殊结构的包层包围，利用光子带隙或反共振效应引导光传输。与传统光纤相比，HCF具有更低的信号衰减，因为光在空气或真空中传输时，吸收和散射损耗更小。此外，HCF还具有更低的延迟，因为光在空气中的传播速度快于实心材料，适用于高频交易和实时通信等需要高速的应用。同时，HCF能够承受更高的功率，减少非线性效应和材料损伤风险。HCF在数据传输效率和性能方面具有显著优势，有望革新光纤通信领域。

The Linux Kernel's PGP Web of Trust

作者: JNRowe | 评分: 57 | 评论数: 3 | 发布时间: 2025-05-09 10:39
文章摘要

Linux内核开发过程中使用PGP签名，主线维护者需在提交给Linus Torvalds的拉取请求中使用签名标签。由于密钥服务器概念存在问题，Konstantin Ryabitsev通过一个Git仓库维护相关密钥，目前有602个有效密钥。要加入该仓库，密钥需在5步信任路径内与Linus的密钥相连。当前有2个密钥因信任路径丢失受影响。GnuPG 2.4.x开始拒绝使用SHA-1算法的第三方签名，尽管这暂时不影响内核PGP密钥库，因为信任路径检查不依赖GnuPG的签名信任。然而，若全部SHA-1签名被弃用，将有大量密钥失去信任路径，包括多位知名内核开发者的密钥。为改善此问题，将在Embedded Recipes 2025会议期间举办密钥签名活动，参与者需在2025年5月12日前提交公钥。
