The current state of LLM-driven development

作者: Signez | 评分: 88 | 评论数: 21 | 发布时间: 2025-08-09 16:17
文章摘要

本文总结了作者在过去几周尝试各种新AI编程工具的体验。主要观点包括：LLM（大型语言模型）在编码工作流中的学习曲线很平缓，但无法自动生成生产级代码；如果开发者不能识别代码问题，LLM在概念验证阶段后难以继续使用。LLM在处理中等规模代码库时组织能力差，尤其在不主流的语言和框架上表现不佳。使用LLM可能让开发者减少阅读文档和思考的时间，从而影响技能提升。关于“代理”，其本质是让LLM通过API调用其他工具并反复处理结果，没有真正的“智能”。工具的稳定性是个问题，模型和硬件更新频繁导致依赖的工具可能突然变为付费或不可用。作者在多个项目中测试了这些工具，发现对于常见任务表现良好，但在处理罕见组件时（如Flutter的Token Field）失败。目前广泛使用的模型包括Claude 4、Gemini 2.5 Pro和GPT 4.1/5，其中Claude 4在代理工作流中表现最佳，而GPT 4.1/5在严格指导下也能取得不错结果。本地模型目前尚无法与大型闭源模型竞争。

评论摘要
主要讨论点：LLMs（大型语言模型）在编程工作流中的应用及其优缺点 不同观点： • tptacek认为，将LLMs整合到编码工作流中非常简单，没有学习曲线，且如果当前不适合自己的工作流，完全可以忽略它们。他批评了文章中对LLMs的负面评价，认为那些成功使用LLMs的人往往发现了其中微妙且反直觉的使用方法。 • ebiester则持不同意见，认为虽然刚开始使用LLMs看似简单，但要获得更好的结果需要对工作流和模型的使用进行调整。如果一开始尝试的任务并非LLMs擅长的领域，容易产生失望感。 • kodisha分享了实际使用LLMs进行编码的经验，特别是在处理结构良好的代码库时，LLMs能够有效地生成所需的代码文件，减少繁琐和易出错的工作。 • joshuamoyers指出，LLMs确实在非主流编程语言和框架上表现不佳，但这个问题可能是暂时的，且类似于团队扩展中的问题。 • simonw认为，LLMs在处理不常见代码或创新性任务时表现较差，这实际上是使用LLMs的一个学习曲线，掌握这些技巧需要经验和技能。 • randfish对LLMs的评价是否为少数意见表示好奇，并提到LinkedIn和个人网络的反馈与Hacker News社区的讨论可能存在差异。 • spenrose建议，许多文章应在标题中注明“我的经验”，以避免将个人经验泛化为普遍现状。 • stephc_int13认为，LLMs在处理无聊或繁琐的任务时很有帮助，但在需要创造性或高智力的任务上表现不佳。 • stopachka使用Clojure语言，发现Opus和GPT-5在处理JVM和Clojure相关任务时表现良好，并认为使用最好的模型是值得的。 • bachmeier在D语言编程中发现，即使是非主流语言，Copilot也能提供有效的帮助，特别是在模板和DLL互操作方面。 • dezmou提到Claude代码的VSCode扩展，虽然仍是终端操作，但具备显示更改差异和理解编辑器上下文的能力。 • singularity2001认为，LLMs在遵循测试驱动开发和代码原则的情况下，表现非常出色，偶尔的错误也可以通过回滚或额外指导来修正。 • infoseek12指出文章中的一些错误，例如Gemini CLI的token问题可以通过设置免费API key解决。 • sudhirb提到，除了文中提到的工具，还有其他背景代理初创公司可能解决作者提到的问题。 • philipwhiuk简单提及IntelliJ的GitHub Copilot扩展，认为虽不完美但尚可。 补充讨论： • 争议焦点在于LLMs在编程工作流中的实际效果和学习曲线。部分人认为LLMs易于使用且效果显著，另一部分人则认为需要调整工作流和模型使用方式，且在处理创新性或非主流任务时表现不佳。 • 讨论还涉及到LLMs对不同编程语言的支持以及在实际项目中的具体应用经验，有些用户分享了成功的案例，而另一些则指出了存在的问题和局限性。

一项新研究发现，土豆起源于约九百万年前安第斯山麓的一次古老杂交事件，当时今天的番茄植物祖先与另一种称为Etuberosum的植物杂交，形成了最早的土豆祖先。这一事件使得早期土豆能够形成地下块茎，从而迅速多样化，最终演变为今天的一百多种土豆物种。土豆是世界重要粮食作物之一，但其遗传特性复杂，具有四倍体染色体，使得培育新品种非常困难，往往需要几十年时间。面对气候变化，科学家正努力引入野生土豆的多样性以增强作物的适应性，但进展缓慢。由于土豆多以无性繁殖为主，许多国家仍在使用数十年前未变的品种，这对未来粮食安全构成挑战。

POML: Prompt Orchestration Markup Language

作者: avestura | 评分: 89 | 评论数: 17 | 发布时间: 2025-08-10 06:26
文章摘要

POML（Prompt Orchestration Markup Language）是一种新型标记语言，旨在为大型语言模型（LLM）的高级提示工程提供结构化、可维护和多功能的解决方案。它通过类似HTML的语法规构，如``、``、``等语义组件，提升提示的可读性、可复用性和可维护性。POML支持整合多种数据类型（如文本、表格、图片），并通过类似CSS的样式系统分离内容与展示，解决LLM对格式敏感的问题。它还提供模板引擎、IDE扩展（如Visual Studio Code）、SDK（Node.js和Python）等开发工具，支持动态生成复杂的提示并进行实时预览和测试。用户可通过VS Code市场安装POML扩展，并配置LLM模型、API密钥和端点以进行测试。

评论摘要
主要讨论点：LLM（大型语言模型）提示词的结构化和是否需要专用语言或标记语言 不同观点： • nine_k认为，LLM的提示词原本应该是非正式的文本，但随着需求的精确性增加，提示词逐渐变得结构化，类似于法律文件的语言。他预测未来可能会出现专门的代码语言来帮助精确表达用户的需求。 • ultmaster是POML（一个用于管理LLM提示词的结构化语言）的开发者，他认为提示词需要一个视图层来处理数据和样式，以减少用户对具体呈现格式的关注。尽管POML最初面临一些挑战，但随着AI技术的发展，他重新看到了POML的潜力，尤其是在多提示代理工作流中的应用。 • aaronvg介绍了一个名为BAML的DSL（领域特定语言），它像函数一样处理提示模板，并解决了结构化输出的问题。BAML的语法类似于TypeScript类型声明，避免了YAML/XML的痛苦编写体验。 • LudwigNagasena质疑为何不直接在DSL中使用一些命令式语法，而要把代码放在字符串中，认为像JSX但更差的语法设计并不理想。 • ulrischa提到GitHub已有.prompt.yaml格式，并希望看到标准化的发展，尤其是来自微软的技术。 • AbuAssar指出微软没有为其C#/.Net技术提供SDK，仅支持Node.js和Python，这让人担忧。 • liamkinne和baggiponte质疑POML与XML的区别，认为POML看起来只是XML的变种。 • Involution和gregman1提到POML与SignalWire的Prompt Object Model（POM）相似，质疑是否存在IP抢注的问题。 • leke询问是否必须通过Node.js或Python安装POML，还是仅需VSCode插件。 • rco8786认为POML作为库的存在理由尚不明确。 • stitched2gethr表示会继续使用markdown，对新语言持保留态度。 • tannhaeuser以幽默的方式提到SGML（标准通用标记语言）的回归。 补充讨论： • 提示词结构化与标准化的必要性是讨论的焦点，部分开发者认为现有的工具和格式已经足够，而另一些人则认为需要更专业的语言和工具来处理复杂的提示需求。 • POML作为一种解决方案，其设计理念和实现细节受到了多方关注，同时也面临与现有技术的比较和竞争。 • 微软的技术选择和支持策略也引发了一些讨论，特别是对不同编程语言的支持程度。

Zig's Lovely Syntax

文章摘要

本文简要讨论了Zig语言的语法特点，认为Zig在保持简洁性和可读性方面比Rust更出色。文章首先提到Zig的整数字面量不使用后缀，而是通过编译时推断类型并强制转换，例如`comptime_int`。Zig的字符串字面量支持原始字符串和多行字符串，避免了Rust中复杂的原始字符串语法问题。在记录字面量中，Zig采用类似C的语法，但更注重字段赋值的可搜索性。Zig的类型前缀语法简化了复杂类型的表示，函数声明中去掉了Rust中的箭头符号，使语法更简洁。总体而言，Zig在语法细节上做出了一些优化，提升了代码的可读性和编写体验。

A CT scanner reveals surprises inside the 386 processor's ceramic package

作者: robin_reala | 评分: 291 | 评论数: 17 | 发布时间: 2025-08-09 17:17
文章摘要

英特尔于1985年发布了386处理器，这是x86系列中的首款32位芯片。该芯片封装在一个带有132个金镀引脚的陶瓷方块中，这些引脚与主板上的插座连接。通过3D CT扫描揭示了芯片内部的复杂结构，其中包括六层复杂的布线。芯片采用132针陶瓷封装，以满足高针数、良好散热和低噪声电源的需求。封装内部类似一个六层的陶瓷印刷电路板，通过金 bond wires将硅芯片与封装的焊盘连接。制作过程包括陶瓷片加工、钨膏布线、层压和高温烧结，最后安装芯片并进行封装和测试。电源层和信号层通过金属迹线和过孔连接，以确保电气性能。

Don't “let it crash”, let it heal

作者: ahamez | 评分: 147 | 评论数: 20 | 发布时间: 2025-08-06 12:08
文章摘要

文章讨论了Elixir编程中"let it crash"这一常见理念的误解和问题。作者指出，虽然BEAM虚拟机允许进程崩溃后自动重启，但这一理念常被错误理解为可忽视所有错误处理。实际上，盲目应用这一理念会导致糟糕的用户体验（如频繁重置连接）和无法向用户反馈错误信息。作者建议采取折中方案：对不可恢复的异常情况允许崩溃，但对可预见的错误应进行适当处理并向用户提供有用反馈，而非简单地让进程崩溃重启。

评论摘要
主要讨论点：Elixir/Erlang中的"let it crash"哲学及其在构建可靠系统中的应用 不同观点： • **强调Joe Armstrong博士论文的重要性**：hesus_ruiz认为解释"let it crash"概念时应提及Joe Armstrong的博士论文，这是理解可靠分布式系统的关键文献。 • **错误处理的阶段性改进**：valenterry提出了错误处理的四个阶段，从运行时检测崩溃到编译时检测潜在崩溃，并认为文章中描述的哲学仅停留在第一阶段，有待改进。 • **"Let it heal"的讨论**：goosejuice和stcg讨论了"Let it heal"这一表述，认为其不如"Let it crash"引人注目，但更贴近Joe Armstrong的思想。 • **"Let it crash"的误解**：tmcb和IshKebab指出，很多人仅从字面上理解"Let it crash"，误以为其意味着忽略错误处理，而实际上这是一种设计系统的策略，确保崩溃不会导致系统灾难性失败。 补充讨论： • **崩溃后重启的有效性**：HexDecOctBin质疑如果进程因缺少文件而崩溃，重启后问题仍存在，如何通过重启来解决问题。monkeyelite补充说明，这种策略在BEAM中有效，而在其他环境如fast-cgi进程中则无此必要。 • **与Kubernetes等系统的比较**：refactor_master将"let it crash"与Kubernetes中容器崩溃后重启的机制进行比较，认为两者在概念上有相似之处，但应用层次不同。 • **监督树和错误处理**：Jtsummers详细解释了Erlang中监督树的概念，以及其与传统语言中错误处理的差异，强调了BEAM中进程的轻量级特性和监督树的重要性。 • **哲学的进一步阐述**：juped引用了Joe Armstrong论文中的相关内容，进一步阐述了"let it crash"的哲学，强调了在程序遇到无法处理的错误时应崩溃，并由其他进程处理错误。 • **不同系统哲学的比较**：anthk比较了不同系统哲学，如Unix/BSD的"Crash, fix, restart"和GNU/MIT/Lisp的"Detect, offer a fix, continue"。 • **"Reset on error"的建议**：adastra22建议用"Reset on error"来替代"Let it crash"，认为这种表述更能准确传达该哲学的核心思想。 争议焦点： • **"Let it crash"是否意味着忽略错误处理**：一些人认为该哲学意味着忽略错误处理，而实际上其强调的是设计一个能够容错和自愈的系统。 • **该哲学的适用范围和有效性**：讨论了在不同环境和系统中该策略的适用性和有效性，包括与Kubernetes等系统的比较。 总结：评论中对"let it crash"哲学的理解存在多种观点，主要集中在对其误解、适用范围、与其他系统的比较以及更准确的表述等方面。
