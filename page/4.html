JMAP for Calendars, Contacts and Files Now in Stalwart

作者: StalwartLabs | 评分: 323 | 评论数: 20 | 发布时间: 2025-10-22 17:26
文章摘要

Stalwart宣布全面支持JMAP协议家族，成为首个完整实现JMAP日历、联系人、文件存储和共享功能的服务器。这套基于JSON的新协议取代了传统的WebDAV、CalDAV等技术，解决了XML格式冗长复杂、iCalendar/vCard标准陈旧等问题。JMAP及其配套的JSCalendar、JSContact提供了更简洁高效的JSON数据模型，统一了邮件、日历等协作功能的实现方式。该项目获得了NLNet的资金支持，目前已完成核心功能开发，正朝着1.0稳定版迈进。多个客户端项目已开始适配这些新协议，预计将推动协作软件的创新发展。

评论摘要
主要讨论点：JMAP协议的优缺点及其在实际应用中的前景，以及与现有协议（如IMAP、WebDAV、CalDAV等）的对比。 不同观点： • **支持JMAP的观点**： - JMAP是一种创新的协议，适合构建现代化的电子邮件客户端（solarkraft）。 - JMAP解决了HTTP层之上的API设计问题，简化了开发流程（solarkraft）。 - Stalwart作为首个JMAP服务器实现，为客户端开发提供了基础（solarkraft）。 - JMAP在文件存储方面可能是WebDAV的替代方案，有望解决WebDAV的慢速和笨重问题（commandersaki）。 - JMAP的集成服务器（邮件、联系人、文件）简化了部署和管理（Mailtemi）。 • **质疑JMAP的观点**： - JMAP是否真的需要基于HTTP和JSON，而不是更高效的二进制协议（9dev）。 - 现有协议（如IMAP、Sieve）的功能未被充分利用，JMAP可能无法解决客户端停滞的问题（blacklion）。 - 新协议缺乏广泛的客户端支持，可能难以普及（blacklion, sylens）。 - 现有协议（如CalDAV、CardDAV）虽然设计复杂，但已被广泛采用且稳定（NoboruWataya）。 • **中立或补充观点**： - Fastmail等服务需要尽快实现JMAP的日历和联系人功能（vamega）。 - Apple和Google等大厂对JMAP的反应尚不明确（kridsdale1）。 - Stalwart在实际生产环境中表现良好，但缺乏自动更新机制（woleium, matesz）。 - Nylas提供了类似JMAP的现代JSON API，但价格较高（btown）。 补充讨论： - **争议焦点**： - JMAP是否能真正替代现有协议（如IMAP、WebDAV），还是仅仅增加了复杂性。 - 新协议的普及是否需要客户端先行，还是服务器先行的策略更有效。 - **其他讨论点**： - JMAP在资源受限环境中的适用性（woleium）。 - JMAP与Solid协议在文件系统方面的对比（apitman）。 - 现有协议（如CalDAV）的兼容性和互操作性问题是否被夸大（NoboruWataya）。

Why SSA?

作者: transpute | 评分: 208 | 评论数: 12 | 发布时间: 2025-10-22 20:13
文章摘要

这篇文章简明介绍了SSA（静态单赋值）形式在编译器优化中的重要性。SSA是一种中间表示（IR），通过确保每个变量只被赋值一次来简化程序分析和优化。文章解释了SSA如何将带有状态变化的命令式代码转换为易于分析的组合逻辑电路，从而帮助编译器高效地进行优化，例如常量折叠和消除无用代码。SSA广泛应用于各种编译器（如LLVM、GCC等），因其简化数据流分析和优化过程的优势而成为现代编译器设计的标准方法。

评论摘要
主要讨论点：SSA（Static Single Assignment）的优势、局限性及其在编译器和编程中的角色。 不同观点： • **SSA的优势**： - SSA作为统一的中间表示（IR），适用于多遍优化编译器（A -> A），便于循环优化。 - 它将带状态的函数转换为无状态的组合电路，易于分析和优化。 - 对人类阅读代码也有帮助（mbauman）。 • **SSA的局限性**： - SSA的“简单性”基于忽略状态，但在处理别名、内存模型或并发时可能失效（zachixer）。 - SSA转换过程复杂，且某些操作变得更困难（pubby）。 • **SSA与函数式编程的关系**： - SSA本质上是函数式的，与CPS（Continuation Passing Style）和ANF（Administrative Normal Form）相似（noelwelsh）。 - 过程式代码可编译为函数式框架，暗示过程式编程是函数式的语法糖（torginus）。 补充讨论： - **争议焦点**：SSA是否值得其复杂性？部分人认为其优势显著（pubby、noelwelsh），而另一些人指出其在复杂场景中的局限性（zachixer）。 - **历史与实现**：GCC早期采用SSA的历史（mhh__），以及MLIR等现代框架对SSA的改进（anon291）。 - **技术细节**：SSA的定义和示例（rdtsc），以及1位乘法器的修正（KeplerBoy）。

Element: setHTML() method

作者: todsacerdoti | 评分: 179 | 评论数: 20 | 发布时间: 2025-10-22 09:03
文章摘要

这篇文章介绍了`Element`接口中的`setHTML()`方法，这是一个实验性技术，用于安全地将HTML字符串解析并插入DOM中。该方法通过内置的XSS防护机制自动移除不安全元素和属性，可替代不安全的`innerHTML`。文章详细说明了其语法、参数（包括可选的自定义消毒器配置）、返回值及异常情况，并通过基础用法示例和实时演示展示了如何使用默认和自定义消毒器来处理未经验证的HTML输入。由于该方法在某些主流浏览器中不可用，使用时需谨慎检查兼容性。

评论摘要
### 主要讨论点： 新引入的 `setHTML()` 方法及其在 DOM API 中的作用，特别是在防止 XSS（跨站脚本）攻击方面的意义。 ### 不同观点： • **支持 `setHTML()` 的引入**： - `CaptainOfCoit` 和 `padjo` 认为这是一个期待已久的功能，填补了 DOM API 的空白，尽管它来得太晚。 - `textlanes33` 认为这是 `innerHTML` 的一个更安全、更可预测的替代方案。 - `xnorswap` 指出 LLM 生成的代码容易存在 XSS 漏洞，`setHTML()` 可以作为一个安全的后备方案，减少错误的发生。 • **对 `setHTML()` 设计的质疑**： - `ishouldbework` 不理解为什么即使明确允许 `script` 标签，它仍然会被剥离，认为这种无法覆盖的过滤设计很奇怪。 - `ibowankenobi` 认为 API 设计可以更好，建议允许重用文档片段（DocumentFragment）并添加可选参数。 • **技术实现和浏览器支持**： - `evilpie` 提到 Firefox Nightly 已经默认启用了这一功能。 - `redbell` 指出该功能尚未被主流浏览器广泛支持，仍处于早期阶段。 - `cheeaun` 分享了一个 polyfill 链接，帮助在不支持的浏览器中使用这一功能。 • **相关扩展讨论**： - `_the_inflator` 建议在 JavaScript 文档的开头引入类似 `use strict` 的配置对象，以定义脚本选项（如消毒和其他配置）。 - `CGamesPlay` 询问“XSS-unsafe”是否有明确定义，认为在这个上下文中假设是不安全的。 - `Traubenfuchs` 询问这是否是 `innerHTML` 与 `DOMPurify.sanitize` 结合的更简单内置替代方案。 ### 补充讨论： - **争议焦点**： - `setHTML()` 的设计是否过于严格，尤其是无法覆盖的过滤规则（如 `script` 标签的处理）。 - 该功能的浏览器支持现状及其未来的普及前景。 - **其他讨论**： - 关于如何进一步改进 JavaScript 的安全性配置（如 `_the_inflator` 的建议）。 - 对 XSS 漏洞防护的更深层次技术讨论（如 `xnorswap` 提到的逃逸与消毒的区别）。
