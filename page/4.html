Tram Trains

作者: ortegaygasset | 评分: 38 | 评论数: 13 | 发布时间: 2025-07-23 14:37
文章摘要

本文讨论了如何在较小城市中建设经济实惠的公共交通，重点介绍了“ tram-train”（电车-火车）系统。许多城市面临铁路线在市中心终止而不延伸到另一侧的问题。为解决此问题，一些大城市通过建设隧道或高架桥实现铁路贯通运行，但这成本高昂。对于小城市，如德国卡尔斯鲁厄（Karlsruhe），则采用了tram-train模式，将电车与火车网络结合。卡尔斯鲁厄通过改造轨道和供电系统，使电车可以直接驶入市中心，减少换乘，提高效率。尽管tram-train速度较慢，因为它需要与道路交通共享空间，但该系统大幅提高了客流量，例如布雷滕线的客流量增加了400%。如今，该网络每年载客1.7亿人次，总长超过660公里。

评论摘要
主要讨论点：不同城市和地区在轨道交通系统中的整合与创新模式，包括轻轨、市际铁路（interurban）、有轨电车-火车（tram-train）等模式的可行性及其实施挑战。 不同观点： • **Charlotte的交通网络**：[kposehn]认为夏洛特的低密度城市结构不适合像慕尼黑那样的交通网络，虽然可以利用现有的轻轨网络连接货运铁路，但由于美国货运铁路与轻轨系统的碰撞标准差异，无法在同一轨道上共存。[kposehn]提出，若空间足够，可以沿线建设新的轨道。 • **Interurban模式的复兴**：[PLenz]提出可以借鉴历史上**市际铁路**（interurban）的模式，重新发明城市间的轨道交通连接。[standardUser]补充了一些美国仍然存在的市际铁路系统，并提供了维基百科链接。 • **科隆的混合交通网络**：[xg15]指出科隆将有轨电车、地铁和部分私人铁路整合为一个网络，但仍然与国家铁路网或S-Bahn（市郊火车）分离。相比之下，柏林和维也纳的地铁和S-Bahn有时会在同一车站的不同轨道上并行。[xg15]认为这更接近“直通运行”的概念。 • **伦敦的铁路终点站问题**：[Animats]提到伦敦的13个主要火车站都是尽头站，直到Crossrail项目才提供了一些东西向的直通服务。 • **卡尔斯鲁厄的混合交通问题**：[xxmarkuski]指出卡尔斯鲁厄的交通模式虽然表面上成功，但存在严重的质量问题，如网络节点问题、车辆容量不足、基础设施合作不力等，导致可靠性差。 • **其他城市的有轨电车-火车模式**：[trollied]提到谢菲尔德的有轨电车-火车模式，已经在英国实施，并使用国家铁路线。[fjfaase]提供了全球有轨电车-火车解决方案的维基百科链接。[trgn]提到布鲁塞尔的火车短暂变成地铁，且没有票价检查。 • **墨尔本的电车与轻轨混合系统**：[Peteragain]分享了墨尔本的电车系统经验，指出虽然有地下火车环线，但电车在城市最后一段的交通中更有效率。 • **未来交通模式的想象**：[euroderf]提出结合市际铁路、高尔夫球车、电动滑板等多种交通工具，创造丰富的城市交通环境。 补充讨论： • **巴黎地铁的速度争议**：[Scoundreller]质疑有轨电车-火车与完全隧道化的巴黎地铁的速度比较，认为影响速度的关键在于交通流量和轨道分离，而非是否在隧道中运行。巴黎地铁因车站密集而速度较慢。 争议焦点： • **卡尔斯鲁厄模式的实际效果**：一部分评论者（如[xxmarkuski]）认为卡尔斯鲁厄的混合交通系统存在严重问题，而另一部分可能隐含认为该模式总体上可行，但在具体实施中需要改进。

Interactive Programming in C (2014)

作者: ofalkaed | 评分: 54 | 评论数: 4 | 发布时间: 2025-07-23 17:16
文章摘要

这篇文章介绍了如何在C语言中实现交互式编程，即在程序运行时修改和扩展功能。这种方法特别适用于游戏开发等非批处理应用，可以减少调试和调整的繁琐过程。关键技巧是将几乎整个应用程序构建为共享库（shared library），并且避免在全局或静态变量中保存状态。文章通过一个简单的“生命游戏”示例演示了这种方法：编辑代码后，无需重启程序，修改会立即生效。共享库通过一个结构体（struct）封装的API与主程序交互，避免使用函数指针产生的问题。这种技术可以在Linux等类Unix系统上使用libdl实现，类似于Windows上的DLL方法。文章还详细介绍了API的五个主要函数：`init()`、`finalize()`、`reload()`、`unload()`和`step()`，用于处理状态初始化、资源释放和动态加载。

评论摘要
主要讨论点：热代码重载（hot code reloading）技术的不同实现方式及其相关挑战 不同观点： • [lkuty] 提到 Tsoding 在 C 语言中实现了热代码重载，并在两个不同的项目中演示了该技术。这表明该技术在不同场景下的实用性，尤其是在动画引擎和常规代码开发中的应用。 • [RustyRussell] 提出了 Andrew Tridgell 的 KnightCap 项目使用了一种不同的方法，通过将数据转储到文件并重新执行（re-exec）来实现热重载，同时保持网络文件描述符（fds）的开放以实现零停机时间。这种方法的优势在于可以处理重启，尽管需要重新连接网络。 • [uticus] 关注了错误处理策略，特别是在查找 GAME_API 结构失败时应如何处理，强调了当热代码重载失败时，应该有适当的回退机制和错误处理策略。 • [90s_dev] 分享了一个个人项目经验，即为 Love2D 开发了一个名为 live2d 的 VS Code 扩展，用于在游戏运行时进行开发。虽然该项目功能完善，但由于使用难度高且无人问津，最终被放弃，源代码也丢失了。他还提到了一种名为 "magic tables" 的辅助工具，但未详细说明其实际功能。 补充讨论： • 热代码重载技术在不同应用场景中的实现方式各有不同，比如 Tsoding 的 C 语言实现和 Andrew Tridgell 的 KnightCap 方法。 • 错误处理和回退状态是实现热代码重载时需要重点考虑的问题，尤其是在生产环境中。 • 个人项目的经验展示了该技术在特定开发者社区中的受欢迎程度和实用性可能存在差异。 争议焦点： • 不同实现方式的优劣比较，特别是 Tsoding 的方法与 KnightCap 的 re-exec 方法在实际应用中的效果和适用场景。 • 热代码重载失败时的错误处理策略和机制选择，如何在保证系统稳定性的同时实现功能的灵活性。

Manticore Search: Fast, efficient, drop-in replacement for Elasticsearch

文章摘要
