Radicle: Sovereign {code forge} built on Git

作者: KolmogorovComp | 评分: 216 | 评论数: 20 | 发布时间: 2026-05-15 12:07
文章摘要

Radicle 是基于 Git 的开源点对点代码协作平台，去中心化复制仓库，用户自主掌控数据与流程。它通过加密身份、签名数据、 gossip 协议和本地优先设计，支持离线使用、抗审查协作，并提供 CLI、Web、桌面端等模块化工具。

评论摘要
主要讨论点：围绕 Radicle 作为去中心化/本地优先 Git forge 的价值、隐私安全、部署方式、生态支持与治理风险展开。 不同观点： • 支持者认为 Radicle 很有潜力：本地优先、分布式、适合替代 GitHub；有人称其“Just Works”，也有人看好其用于 agent 工作流，因其默认具备加密身份和签名产物。 • 隐私与删除问题引发担忧：去中心化系统中很难真正删除仓库或泄露的密钥；私有仓库虽可限制复制，但历史仍可能存在，类似 Matrix、BitTorrent 的删除困境。 • 私有/敏感仓库方案被质疑：评论指出 Radicle 私有仓库未加密静态存储，只依赖选择性复制，且公私仓库缺少结构隔离，误操作或 bug 可能导致泄露。 • 本地/小团队离线部署体验不足：多人希望像 on-prem GitLab 或 Fossil 一样，只在几台机器间运行，不连接公共网络；但默认会加入公共 seed 节点，配置和文档支持不足，需要脚本化绕过。 • 许可证存在争议：有人批评未采用 AGPL，担心 SaaS 公司“拥抱、扩展、消灭”；并指出 Radworks 计划提供基于 Radicle 的服务，加剧商业化担忧。 • 功能与生态问题：有人询问是否支持 Tor、Git LFS/Git Annex；也有人希望原生支持 Jujutsu（jj）仓库，而不仅是相关集成文章。 • 联邦交互的治理问题：有人关心公开仓库的 issue/merge request 是否会被任意节点骚扰，是否存在白名单或反垃圾机制。 补充讨论：还有人提到 Radicle 近期更换域名、NixOS 已打包，部分用户准备部署常驻节点；也有用户询问其核心解决的问题是否主要是反中心化与抗审查。

'No way to prevent this,' says only package manager where this regularly happens

作者: alligatorplum | 评分: 280 | 评论数: 25 | 发布时间: 2026-05-16 00:36
文章摘要

文章讽刺 npm 生态在供应链攻击后将灾难视为“不可避免”，批评其过度依赖层层嵌套、缺乏审查的第三方包和默认执行脚本等风险；对比 Go、Rust 等生态更强标准库与验证机制，暗示此类事故本可预防。

评论摘要
主要讨论点：围绕 npm/PyPI 等包管理生态的供应链攻击，讨论“冷却期”、默认安全配置、脚本权限、生态文化与不同语言/工具链的安全差异。 不同观点： • 支持“冷却期”防护：认为多数恶意版本会在数小时内下架，设置 1～3 天延迟安装可避免 axios、tanstack 等近期攻击；但遇到紧急 CVE 修复时需允许绕过。pnpm、DepsGuard、cooldowns.dev、Artifactory/Nexus 等被举为方案。 • 认为应改进默认安全配置：有评论称在每台开发机部署安全 npm 配置很痛苦，包管理器应默认更安全。 • 主张禁用 postinstall 脚本：认为没有正当理由让依赖安装时自动执行脚本，npm 应停止对新发布包运行 postinstall。 • 认为问题不只在 npm：有人指出 RubyGems、PyPI、XZ Tools 也曾遭攻击，不能把 npm 当唯一问题；攻击者常利用开发者环境中的密钥，秘密管理也应负责。 • 认为 npm/JS 生态文化更脆弱：有人批评 JavaScript 生态依赖过多、开发者经验参差、频繁更新且不读 changelog；冷却期本质上是强制耐心。 • 比较其他生态：有人问 Go/Rust 是否有实际安全保证，还是只是目标价值较低；也有人称 Rust 开发者更专业、不易被攻破。另有评论认为 pip 因缺少 lockfile 比 npm 更危险，uv 可改善但普及慢。 • 替代工具链观点：使用 Nix 沙箱、C++/Conan、自建 recipes 和预构建产物被认为能降低联网依赖和大规模包生态带来的风险。 补充讨论：部分评论以讽刺方式回应文章标题，另有人认为标题套用灾难梗“Thoughts and Prayers”品味不佳。争议焦点在于：问题是 npm 特有、JS 文化问题，还是所有开放包管理生态共有的供应链风险。
