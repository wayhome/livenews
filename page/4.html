文章摘要

文章描述了作者在搬进无家具公寓后，与一位拥有CNC路由器的朋友合作设计平板包装床的过程。设计要求包括：适应200厘米 x 180厘米的床垫，床下有50厘米的储物空间，并从正面和侧面遮挡储物空间。床需由一张波罗的海桦木板（2440毫米 x 1220毫米）CNC切割而成，可能使用Ikea的LÅNSET床板。作者参考了Christoffer Martens的Siebenschlafer床设计，但发现其简约设计无法遮挡床下储物，且内部支撑需要粘合/螺钉固定，不够美观。 由于木材成本高，作者希望通过CNC精确切割设计节省材料，可能使用藤条或布料遮挡床下杂物。作者使用Autodesk Inventor进行设计，但觉得过程繁琐，探索了其他2D切割设计工具如CutList Optimizer、Cuttle.xyz、FlatFab和Kyub，以优化设计流程。文章最后表示仍在寻找更高效的设计工具和方法。

The many JavaScript runtimes of the last decade

作者: LinguaBrowse | 评分: 194 | 评论数: 20 | 发布时间: 2025-07-27 14:28
文章摘要

过去十年中，JavaScript运行时和引擎大量涌现，使JavaScript得以在云端、边缘计算、智能电视、移动设备甚至微控制器等多种环境中运行。这种多样性源于不同场景对任务精确度的需求。2002年，Akamai推出首个“边缘计算”解决方案，但直到2009年Node.js出现，JavaScript才开始被用于服务器端。2014年，AWS Lambda使Node.js进入无服务器领域。2016年，AWS推出Lambda@Edge，使JavaScript真正进入边缘计算。然而，Cloudflare Workers在2017年迅速崛起，成为直接产品化的JavaScript运行时，获得巨大成功。随后，Deno于2018年出现，成立Deno Land Inc并推出Deno Deploy，挑战Cloudflare。2022年，WinterCG成立以统一新运行时标准，Bun和Wasmer也相继推出新边缘计算解决方案。 不同运行时使用不同引擎，如Deno用V8，Bun用JavaScriptCore，WinterJS用SpiderMonkey，LLRT用QuickJS，Cloudflare Workers用workerd。在微控制器领域，轻量级引擎如Duktape、Espruino、JerryScript、Moddable和elk应运而生，支持低资源设备。最后，一些JavaScript引擎基于已有虚拟机，实现与其他语言的零成本互操作。

评论摘要
主要讨论点：JavaScript 各种运行时和引擎的分析与比较 不同观点： • LinguaBrowse 认为文章覆盖全面，读者能学到新知识，强调文章的广度和深度。 • Laurencerowe 指出 Cloudflare 的 workerd 运行时使用的是 V8 引擎，而非自定义引擎，纠正原文中的不准确之处。 • Weiliddat 补充提到 Bellard 的 QuickJS 仍然活跃，并提供了相关链接，认为需要在讨论中提到这一点。 • Willquack 分享了自己参与的其他未被提及的 JavaScript 运行时项目，如 PythonMonkey 和 DCP，并描述了这些项目的特点和用途。 • Ksherlock 提到微软的 JScript 也应该被提及，尽管其历史久远，但其服务器端应用（如ASP）仍有历史价值。 • Asn0 补充了90年代的 Nombas ScriptEase 运行时，并给出了相关链接。 • Sytten 纠正了 LLRT 运行时的贡献者情况，强调其社区贡献的特性，并指出其在 Rust 环境中的优势。 补充讨论： • Ottod 和 Podgorniy 对文章质量表示赞赏，认为其具有很高的参考价值。 • Dfee 提出了对不同 JavaScript 运行时未来生存能力的担忧，特别是面对竞争和生态系统整合时，如何确保代码的互操作性。 • NeutralForest 关心如何保持文章中链接的有效性，担心未来可能无法访问原始页面。 • Dehrmann 回忆了 Rhino 作为 Java 内置 JS 解释器的历史，并提到当时没有内置 JSON 解析器的问题。 • Cat-whisperer 对新运行时如何处理异步上下文跟踪提出了疑问，关心它们是使用 Async Hooks 还是自定义解决方案。 • Tom1380 对在微控制器上使用 JavaScript 表示不解，提出了其实际应用场景的问题。 争议焦点： • 关于 Cloudflare workerd 运行时使用的引擎存在争议，laurencerowe 认为其使用的是 V8 引擎，而非原文所述的自定义引擎。 • 不同历史时期的 JavaScript 引擎和运行时（如 JScript、Nombas ScriptEase）是否应被纳入讨论，ksherlock 和 asn0 提出了补充意见。

Why does a fire truck cost $2m

作者: Guid_NewGuid | 评分: 113 | 评论数: 23 | 发布时间: 2025-07-28 00:56
文章摘要

文章探讨了为何消防车价格飙升至200万美元以上。主要原因包括私募股权公司对消防车制造行业的整合，形成了垄断。例如，美国工业合伙公司（AIP）通过收购多家小型企业，创建了REV集团，成为美国三大消防车制造商之一。这导致了生产选择减少、交付时间延长（2至4.5年）以及价格大幅上涨。由于市场控制力增强，厂商可以在下单后更改价格，使得各地消防部门难以负担新车，只能继续使用老旧车辆。例如，芝加哥消防部门的老旧车辆频发故障，其他地区如洛杉矶和亚特兰大的消防部门也面临类似困境。文章指出，这种垄断不仅推高了价格，还加剧了公共安全的风险。

评论摘要
主要讨论点：消防车成本高昂及其与军事开支、通货膨胀和供应链问题的比较 不同观点： • **军事支出与消防车成本的比较**： - **crystal_revenge**：指出军事武器（如导弹、炮弹）的成本极高，相比之下，消防车的成本虽然也高，但人们往往没有意识到军事冲突中的巨额开支。 - **flowmerchant**：提到一些奢侈休闲用品（如豪华快艇）成本高昂且无实际救生功能，相比之下，消防车的成本显得更合理。 • **消防车成本上升的原因**： - **softgrow**：指出消防车使用寿命长，但行驶里程低，且维护成本高。同时提到不同部门（如警察和救护车）的车辆更新策略不同。 - **phendrenad2**：认为消防车成本上升主要是由于通货膨胀，与其他商品价格上涨类似。 - **petra303**：强调经济规模效应，如果缺乏标准化零件，制造消防车的成本会更高。 • **供应链与市场问题**： - **daft_pink**：提到疫情后车辆价格普遍上涨，如Toyota Sienna等车型也需要等待并支付高额溢价。 - **chmod775**：指出美国消防车制造商可能存在垄断问题，建议通过进口车辆来降低成本。 - **Invictus0**：质疑为何不购买中国制造的消防车或由新进入者生产更便宜的消防车。 • **消防车对社区的影响**： - **trailrunner46**：强调小社区因税收基础小而难以负担昂贵的消防车，且等待时间长和成本不确定性增加了困难。 - **bensonn**：以志愿消防员的身份描述了志愿消防部门面临的资金不足和设备老化问题，强调了消防车对社区响应能力的重要性。 • **其他建议与批评**： - **Animats**：建议考虑使用欧洲广泛使用的MAN消防车，质量好且被广泛认可。 - **fitsumbelay**：批评公共部门中的腐败和不当行为可能助长了消防车成本的不合理上涨。 补充讨论： - 讨论中多次提到垄断、通货膨胀和疫情对车辆价格和供应链的影响，这些因素共同导致了消防车成本的上升。 - 还提到了不同国家（如中国、德国）制造的消防车可能提供成本更低的选择，这引发了对美国市场现状的反思。 - 最后，讨论中涉及了志愿消防部门在资源有限情况下的艰难处境，强调了设备对社区安全的重要性。

BlueOS内核是一个用Rust编写的操作系统内核，注重安全性、轻量化和通用性，兼容POSIX接口并支持Rust标准库。目前支持ARM32、ARM64、RISCV32和RISCV64架构，QEMU平台也受支持，硬件板支持正在开发中。内核包含CPU架构支持、系统调度器、内存管理、文件系统、网络和设备子系统等核心组件。相关技术文档和教程可在BlueOS官网的内核页面找到。项目还包括基于Rust的libc实现和各种示例应用。该项目使用Apache-2.0许可证，已有507个星标和30个分支。

AlphaDec: A human-readable alternative to ULID/Snowflake IDs

作者: firasd | 评分: 38 | 评论数: 9 | 发布时间: 2025-07-24 22:14
文章摘要

**AlphaDec** 是一种时区无关的时间格式，适用于人类、机器和人工智能。它将 UTC 时间编码为可读字符串，并按字典顺序排序，方便数据库使用。其结构为 `YYYY_PaBt_MMMMMM`，其中： - **YYYY**: UTC 年份。 - **P**: 年分为26个周期，用字母 A-Z 表示，每个周期约14天。 - **a**: 每个周期分为10个弧，每个弧约33.7小时。 - **B**: 每个弧分为26个条，每个条约77.8分钟。 - **t**: 每个条分为10个节拍，每个节拍约7.8分钟。 - **MMMMMM**: 当前节拍内的毫秒数。 AlphaDec 具有以下特点： 1. **字典顺序可排序**: 可按字符串顺序排序，适合作为数据库主键。 2. **时间序列友好**: 可截取字符串进行高效的时间范围查询。 3. **人类可读且紧凑**: 一眼可大致了解时间位置。 4. **AI 原生**: 结构化、可标记，适合AI系统中的时间推理和日志分析。 5. **无碰撞**: 不同于本地时间格式，避免混淆。 该项目提供 JavaScript 和 PHP 的实现示例，确保语言无关性。

主要讨论点：时间戳格式的可读性、压缩性和适用性 不同观点： • nine_k认为可以通过使用类似base64的编码来压缩时间戳表示，同时保持可读性和可排序性。他提出使用6字符表示36位时间戳，并讨论了使用base60来直接表示时间单位，如分钟和秒。 • Dylan16807指出ISO 8601格式在未零填充时不友好，但可以通过去除分隔符来缩短长度。他质疑AlphaDec的压缩是否牺牲了太多可读性，并建议将月、日、时分别编码为一个字符。 • nivertech批评AlphaDec格式为“鲁布·戈德堡机械”，认为其增加了不必要的复杂性，并指出在精度低于一分钟时使用该格式具有误导性。 • firasd作为AlphaDec的设计者，解释该格式旨在提供人类和AI都能读取的UTC编码，具有时间区域无关性、可逆性和安全性，并提供了项目示例和在线示例。 • akdor1154对格式中使用的有理数表示怀疑，但承认设计得很好，并建议可能需要考虑整数秒或毫秒的定义以确保往返转换的明确性。 • rfoo质疑项目中声称的LLM和AI原生特性，认为这在实际应用中可能不实用。 • burnt-resistor提醒注意使用UTC而不是TAI的问题，提供了一个相关链接。 • satisfice认为AlphaDec的可读性不如ISO 8601格式，并以QR码为例进行比较。 • andoando直接比较ISO 8601和AlphaDec，认为前者更直观可读。 补充讨论： • 争议焦点在于AlphaDec格式的实际可读性和其相对于ISO 8601的优越性。 • 讨论还涉及时间戳格式的压缩性、可排序性、以及在文件名和数据库中的适用性。 • 不同的技术背景和应用需求导致了对各时间戳格式的偏好和批评。 • 对LLM和AI系统中的时间戳格式应用也进行了探讨，反映出不同技术社区的不同需求。
