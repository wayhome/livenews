Reversing a Fingerprint Reader Protocol (2021)

作者: thejj100100 | 评分: 58 | 评论数: 6 | 发布时间: 2025-07-19 22:02
文章摘要

本文描述了作者对联想笔记本指纹读取器（Goodix FingerPrint Device，型号27c6:55a2）的逆向工程过程，目标是在Linux系统上实现对其支持。指纹读取器在Windows上工作正常，但Linux下的驱动未完善。作者通过捕获和分析Windows驱动程序与设备间的USB通信数据，发现该设备使用TLS-PSK加密协议。作者成功修改PSK并编写Python脚本，实现了从传感器读取图像的功能，帧率约15 FPS。图像格式和协议细节通过逆向工程Windows驱动和USB数据包获得，最终代码已发布在GitHub上（tlambertz/goodix-fingerprint-reversing）。尽管目前libfprint尚未支持该设备，但已有一个Discord社区致力于支持Goodix设备。

主要讨论点：Goodix设备的安全漏洞及相关技术细节 不同观点： • [JJJollyjim] 提到通过逆向工程在Goodix设备上利用固件更新系统插入了额外的漏洞，并从中提取了预共享密钥（PSK）。他还在链接的视频中详细讨论了这一过程，展示了如何利用这些漏洞。 • [Liftyee] 表示原以为指纹数据会被加密且不会离开传感器硬件，对操作系统层级访问指纹图像表示担忧，认为存在安全风险，但也为替代用途提供了可能性。 • [th0mas] 作为文章作者，对讨论出现在HN上表示意外，并邀请读者提问，显示出愿意进一步解释和讨论的开放态度。 • [johnflan] 对图像格式的字节顺序表示困惑，寻求更详细的解释，表明对技术细节的关注和需求。 • [ge96] 强调了软件之下的实际工作，比如无法编写相机驱动程序但感谢其他人能做到，并对获取原始图像数据表示赞赏。 • [abstractspoon] 仅简单表示赞赏，没有提出具体观点或问题。 补充讨论： • 争议焦点：JJJollyjim展示的漏洞利用方法是否会引发更大的安全问题。Liftyee对此表达了安全风险的担忧，而JJJollyjim则从技术角度展示了其实现过程。 • 技术细节需求：johnflan对图像格式的技术细节有疑问，表明部分读者对具体实现细节有深入理解的需求。 • 实际应用与可能性：Liftyee提到操作系统层级访问带来的替代用途可能性，显示出对技术应用前景的开放态度。 整体来看，讨论围绕技术实现、安全风险、实际应用及技术细节展开，体现了不同背景的参与者对同一技术话题的多角度关注。

Tram Trains

作者: ortegaygasset | 评分: 38 | 评论数: 13 | 发布时间: 2025-07-23 14:37
文章摘要

本文讨论了如何在较小城市中建设经济实惠的公共交通，重点介绍了“ tram-train”（电车-火车）系统。许多城市面临铁路线在市中心终止而不延伸到另一侧的问题。为解决此问题，一些大城市通过建设隧道或高架桥实现铁路贯通运行，但这成本高昂。对于小城市，如德国卡尔斯鲁厄（Karlsruhe），则采用了tram-train模式，将电车与火车网络结合。卡尔斯鲁厄通过改造轨道和供电系统，使电车可以直接驶入市中心，减少换乘，提高效率。尽管tram-train速度较慢，因为它需要与道路交通共享空间，但该系统大幅提高了客流量，例如布雷滕线的客流量增加了400%。如今，该网络每年载客1.7亿人次，总长超过660公里。

评论摘要
主要讨论点：不同城市和地区在轨道交通系统中的整合与创新模式，包括轻轨、市际铁路（interurban）、有轨电车-火车（tram-train）等模式的可行性及其实施挑战。 不同观点： • **Charlotte的交通网络**：[kposehn]认为夏洛特的低密度城市结构不适合像慕尼黑那样的交通网络，虽然可以利用现有的轻轨网络连接货运铁路，但由于美国货运铁路与轻轨系统的碰撞标准差异，无法在同一轨道上共存。[kposehn]提出，若空间足够，可以沿线建设新的轨道。 • **Interurban模式的复兴**：[PLenz]提出可以借鉴历史上**市际铁路**（interurban）的模式，重新发明城市间的轨道交通连接。[standardUser]补充了一些美国仍然存在的市际铁路系统，并提供了维基百科链接。 • **科隆的混合交通网络**：[xg15]指出科隆将有轨电车、地铁和部分私人铁路整合为一个网络，但仍然与国家铁路网或S-Bahn（市郊火车）分离。相比之下，柏林和维也纳的地铁和S-Bahn有时会在同一车站的不同轨道上并行。[xg15]认为这更接近“直通运行”的概念。 • **伦敦的铁路终点站问题**：[Animats]提到伦敦的13个主要火车站都是尽头站，直到Crossrail项目才提供了一些东西向的直通服务。 • **卡尔斯鲁厄的混合交通问题**：[xxmarkuski]指出卡尔斯鲁厄的交通模式虽然表面上成功，但存在严重的质量问题，如网络节点问题、车辆容量不足、基础设施合作不力等，导致可靠性差。 • **其他城市的有轨电车-火车模式**：[trollied]提到谢菲尔德的有轨电车-火车模式，已经在英国实施，并使用国家铁路线。[fjfaase]提供了全球有轨电车-火车解决方案的维基百科链接。[trgn]提到布鲁塞尔的火车短暂变成地铁，且没有票价检查。 • **墨尔本的电车与轻轨混合系统**：[Peteragain]分享了墨尔本的电车系统经验，指出虽然有地下火车环线，但电车在城市最后一段的交通中更有效率。 • **未来交通模式的想象**：[euroderf]提出结合市际铁路、高尔夫球车、电动滑板等多种交通工具，创造丰富的城市交通环境。 补充讨论： • **巴黎地铁的速度争议**：[Scoundreller]质疑有轨电车-火车与完全隧道化的巴黎地铁的速度比较，认为影响速度的关键在于交通流量和轨道分离，而非是否在隧道中运行。巴黎地铁因车站密集而速度较慢。 争议焦点： • **卡尔斯鲁厄模式的实际效果**：一部分评论者（如[xxmarkuski]）认为卡尔斯鲁厄的混合交通系统存在严重问题，而另一部分可能隐含认为该模式总体上可行，但在具体实施中需要改进。

SQL Injection as a Feature

作者: foxfired | 评分: 88 | 评论数: 14 | 发布时间: 2025-07-21 17:59
文章摘要

这篇文章讲述了一个日志管理网站如何从一个简单的报告页面演变成一个允许用户直接编写SQL查询的系统。最初，页面只允许用户输入日期范围和关键词来生成报告。随着时间推移，由于不断有增加字段、生成新报告类型的需求，开发人员逐渐通过硬编码SQL和添加功能来满足这些要求。由于报告类型不断增多，用户开始抱怨名称混乱，开发人员转而使用数据库驱动报告名称，并允许编辑报告名。随着需求进一步复杂化，有人提出让用户自行编写SQL查询，最终这个功能被秘密添加到一个未公开的页面中，成为“SQL注入即服务”。尽管后来添加了一些简单的安全措施和查询限制，系统实际上已将整个数据库暴露给用户。这个演变过程展示了在长达十年的需求累积和小修小补下，一个系统如何逐渐变得脆弱和不安全。

评论摘要
主要讨论点：用户通过非正规手段获取数据、SQL注入风险及安全措施、用户直接执行SQL查询的利弊 不同观点： • EvanAnderson分享了一个案例，用户通过利用过滤字段在应用程序中执行SQL注入以获取未提供的数据过滤功能，虽然用户展示了 ingenuity，但这种做法存在严重的安全隐患，尤其是当应用程序以超级用户权限运行时。 • adontz认为在某些大企业系统中，用户可能对原始数据没有权限，但对包含聚合数据的报告有权限，因此报告权限不能从基础CRUD权限推断。他支持通过限制查询为SELECT、使用超级用户编辑查询和参数化查询来提高安全性。 • dml2135讲述了自己在旧工作中通过发现搜索技巧来改进工作流程的经历，虽然当时意识到潜在风险，但并未深入探索。 • ivanjermakov质疑仅通过字符串搜索来防止SQL注入的有效性，建议通过限制数据库连接权限来实现更好的保护。 • heckintime建议直接给用户提供DBeaver或Bigquery访问权限，并通过限制访问特定视图来避免昂贵的查询。 • louis_saglio认为直接给用户SQL访问是SQL的初衷。 • lenkite描述了为分析师提供SQLite快照副本的做法，让他们在副本上自由操作。 • zihotki分享了通过SQL解析器和AST walker验证查询安全性的技术方案，以防止SQL注入并限制允许的SQL子集。 • LikesPwsh建议让分析师使用IDE而不是在文本框中构建自己的IDE。 • zX41ZdbW展示了基于自由形式SQL查询的公共应用程序例子，如adsb.exposed和play.clickhouse.com。 • fifticon对故事结尾引用“机器解雇我”文章表示疑惑，不确定是否暗示SQL操作可能导致被解雇。 • crazygringo认为现代多用户数据库可以轻松限制用户仅执行SELECT查询，并设置超时以防止风险。 • codingdave指出某些UI仅供系统管理员使用，以快速查询数据库，而不授予额外访问权限。 • EGreg描述了Qbix框架中实现的特性，允许通过审计员角色签署的有效载荷执行特权操作，包括SQL查询、智能合约等，以增强安全性。 补充讨论： • 讨论中多次提到SQL注入的风险及通过限制权限、使用解析器和审计机制来提高安全性。 • 不同的技术方案被提出，如参数化查询、使用SQLite副本和IDE工具，以平衡用户灵活性和系统安全性。 • EGreg的评论引入了更复杂的权限管理和量子计算抵抗方案，显示了对安全性的高度关注。

Checking Out CPython 3.14's remote debugging protocol

作者: ingve | 评分: 70 | 评论数: 7 | 发布时间: 2025-07-23 09:57
文章摘要

Python 3.14引入了一个新功能，允许通过`python -m pdb -p pid`将pdb调试会话连接到一个正在运行的Python进程。这使得开发者可以在无需提前修改代码或重启程序的情况下，动态调试运行中的进程。文章介绍了如何使用`sys.remote_exec`方法向指定进程ID的Python进程注入并执行代码。具体来说，开发者可以在一个Python REPL中调用`sys.remote_exec(pid, script_path)`，让目标进程执行指定的脚本。文章通过一个简单的累加整数的程序演示了该功能的实际应用，展示了如何在不中断程序运行的情况下，远程注入代码以查看调用栈信息。这一新功能降低了调试Python程序的门槛，简化了调试流程，并减少了对CPython内部细节的依赖。

评论摘要
主要讨论点：Python 3.14 可能引入的调试功能改进及其对开发者的影响 不同观点： • [jasonjmcghee] 分享了一个官方资源链接（PEP 768），认为这是关于该主题的良好参考。 • [BossingAround] 提到新功能包括无需修改或停止程序即可打印堆栈跟踪，以及在运行时进入程序。对 remote_pdb 被提及表示困惑，因为该工具自 2.7 起就存在。希望 Python 3.14 能引入更好的调试工具，特别是与 VSCode 的远程调试能力相当的标准化工具。认为更好的开发者可能不需要远程调试，但自己非常依赖它。 • [skeledrew] 提到 pyrasite 和 ptpython，并计划将其发展成类似 Pharo/Smalltalk 的实时编码体验，显示出对现有工具的扩展和自定义兴趣。 • [maeln] 认为新功能对调试 GUnicorn、Celery 等多进程/线程应用非常有用，目前的 pdb 使用不便，Debug Adapter Protocol 虽然有效，但只有 VSCode 的实现比较完善。个人喜欢简单的 shell 式调试（如 gdb）。 • [poulpy123] 希望有一个调试器能够从断点或异常回溯时间，提出了对新功能的需求和期望。 • [whinvik] 询问是否需要客户端和被调试脚本都运行 3.14，担心旧版本的脚本无法使用新版本的调试脚本。 • [frou_dh] 对可能需要第三方库（remote_pdb）表示担忧，但欣慰地看到可以通过 OOTB 工具将 pdb 附加到同一机器上的任何运行进程。 补充讨论： • 争议焦点之一是 remote_pdb 的提及及其在 Python 3.14 中的变化，部分评论者对其存在和使用表示困惑。 • 另一个讨论点是远程调试工具的现状和需求，特别是对 VSCode 的远程调试能力的认可和期望标准化。 • 不同的开发者对调试工具的需求和偏好也有所不同，例如对 shell 式调试的偏好和对实时编码体验的追求。 • 最后，关于 Python 3.14 新功能的使用条件和限制也引起了关注，特别是旧版本的兼容性问题。

When Is WebAssembly Going to Get DOM Support?

作者: jazzypants | 评分: 100 | 评论数: 20 | 发布时间: 2025-07-23 05:16
文章摘要
