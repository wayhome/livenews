Async I/O on Linux in databases

作者: jtregunna | 评分: 150 | 评论数: 21 | 发布时间: 2025-07-20 06:20
文章摘要

本文描述了作者在开发简单键值数据库过程中，对I/O性能优化的探索。最初使用内存哈希表和简单的追加日志实现持久化，但性能不佳。之后，作者转向研究Linux的io_uring机制，它通过共享环形缓冲区在应用与内核间实现真正的异步I/O，大幅提升吞吐量。然而，异步I/O导致数据持久性和一致性问题，作者通过引入双写前日志（WAL）设计解决该问题：一个记录操作意图（异步写入），另一个记录操作完成，只有两者齐备时才在恢复时应用操作，确保一致性。最终，作者使用Zig语言实现了该方案，并通过实验验证其性能和可靠性。

评论摘要
主要讨论点：io_uring 与同步 API 的性能比较及其在数据库中的应用，特别是关于持久性（durability）和正确性的讨论。 不同观点： • **quietbritishjim** 认为文章中比较的是有 fsync 调用和无 fsync 调用的性能，而不是同步 API 和 io_uring 的真正性能对比。他认为如果同步代码中去掉 fsync，也能获得类似的性能提升。此外，io_uring 也可以通过某些方法实现 fsync 的功能，因此文章的比较是不对等的。 • **jorangreef** 指出 TigerBeetle 始终使用 fsync 来保证持久性，并且他们的设计目标不是性能而是正确性。TigerBeetle 的双 WAL（写前日志）设计是为了协议感知的恢复，而不是简单的性能优化。 • **sethev** 认为文章中的逻辑有误，指出如果第4步（等待完成记录写入 WAL）正确执行，那么第3步（等待意图记录持久化）就是多余的。他怀疑第4步可能没有正确执行，导致误解。 • **jmpman** 担心如果系统崩溃后，客户端收到成功的请求可能没有对应的完成记录，这违反了 ACID 原则。 • **avinassh** 同意 jmpman 的观点，认为如果完成记录是异步的且可能未完成，那么服务器的持久性保证就会有问题。 • **tlb** 和 **BeeOnRope** 都质疑意图记录的必要性，认为如果只有完成记录是持久化的，那么单独记录意图记录似乎没有意义。 • **leentee** 认为文章中的方案不能保证持久性，并且认为好的同步代码比坏的异步代码更可取，尤其是对于现代 NVMe 存储而言，同步 IO 已经足够快。 • **lstroud** 分享了在 Linux raid 驱动中遇到的死锁问题，并通过移除 lvm 解决了吞吐量问题。 • **ptrwis** 提到目前只有一个人在为 PostgreSQL 实现异步直接 IO。 • **tobias3** 对双 WAL 操作比单个同步 IOPS 更快的说法表示怀疑，认为这可能意味着数据库根本没有持久性。 • **jtregunna** 在更新中澄清了需要等待完成记录写入后再响应客户端，并指出双 WAL 方法在批量处理时有优势，但在接近单次写入时成本更高。 • **ozgrakkurt** 分享了自己实现 crash-resilient LSM 树的经验，并好奇双 WAL 方法与 append/rename 方法的 trade-off。 • **eatonphil** 提到目前似乎没有很多数据库在生产环境中默认使用 io_uring，并希望有人能做这样一个调查。 • **jasonthorsness** 质疑 NVME 存储接口是否应该比 Linux 抽象层更简洁，并提出某些高性能应用可能更适合作为特殊用途的 unikernels。 补充讨论： • 争议的焦点在于文章中比较的合理性和持久性保证，特别是 fsync 在异步和同步代码中的作用。 • 另一个值得注意的讨论点是双 WAL 设计的必要性和意图记录的作用。 • 一些评论者分享了实际操作中的经验和解决方案，比如 lstroud 的死锁问题和 ozgrakkurt 的 crash-resilient 方法。 • 还有评论者对 io_uring 在生产环境中的使用情况表示关注，并希望有更多调查和数据。

Java was not underhyped in 1997 (2021)

作者: SerCe | 评分: 73 | 评论数: 16 | 发布时间: 2025-07-17 05:37
文章摘要

本文讨论了Java在1997年时的巨大影响力以及其后来为何失去关注。作者Dylan Beattie回忆了1997年他在大学学习计算机科学时，Java是必修课，并且被广泛应用于各种课程中。Java在当时因其自动垃圾回收、并发处理、异常处理等创新特性备受推崇，甚至被认为能解决所有问题，取代桌面应用和微软Windows系统。Corel等公司曾计划将重要软件移植到Java平台，Java applets被视为网络应用的未来。然而，Java的实际表现不如预期，在桌面应用和游戏开发方面不如Visual Basic、C++，而在服务器端网络编程方面则面临Perl、PHP等竞争。Java虽好，但并未能如 hype 所预期的那样彻底改变计算机世界。

评论摘要
主要讨论点：Java的“ hype”（宣传）历史及其技术能力和市场影响 不同观点： • **Java技术能力被低估 vs 市场过度宣传**： - **观点1**：Jackson Roberts的文章认为Java的技术特性（如类型系统和包管理器）被低估，因为这些特性在实际开发中能有效减少错误（jasode）。 - **观点2**：Java在1990年代被过度宣传，例如“Write Once, Run Anywhere”的承诺未能实现，微软的Windows继续主导桌面市场，Java也未能在网页应用和桌面应用中取代JavaScript和C/C++等语言（jasode）。 • **Java在1990年代的野心过大**： - **观点1**：当时有人希望用Java重写一切，包括办公软件和网页浏览器，这种做法比近年用Rust重写的潮流更不现实（whobre）。 - **观点2**：Sun公司通过学术策略和广告投放，将Java推广到大学教育中，并通过大量资金推动其进入市场，但当时的硬件和Java本身还不够成熟，导致体验不佳（vanschelven, jerf）。 • **Java在企业中的表现**： - **正面观点**：Java和JVM本身非常优秀，问题在于Java企业开发中常用的Spring IoC容器等工具，因其“魔法”特性导致复杂性增加（rr808）。 - **反面观点**：企业环境中的Java开发体验较差，特别是在1990年代末，Java因广告宣传而被迫使用，导致了许多糟糕的体验（jerf）。 • **Java的长期影响和现状**： - **观点1**：尽管Java在桌面和网页应用上的表现不如预期，但它在服务器端应用中占据了重要地位，且对互联网技术的发展产生了深远影响（jmyeet）。 - **观点2**：Java如今仍被许多大公司（如Google和Amazon）使用，证明了其稳健性和实用性（lordleft）。 - **观点3**：尽管Java的宣传和销售策略存在问题，但其在开发工具（如PyCharm、Android Studio）中的应用证明了其成功之处（nurettin）。 补充讨论： • **Java的局限性和技术细节**： - **技术缺陷**：一些开发者指出Java缺乏对无符号数值的原生支持，这是其技术上的一大局限（binarymax）。 - **复杂性**：一些开发者分享了使用Java（尤其是Spring框架）时遇到的复杂性问题，并反思了过度设计带来的困扰（liampulles）。 • **对“hype”一词的批评**： - **观点**：有些评论者认为“hype”这个词常被无理由地用来攻击新事物，且常缺乏正当性（vardump）。 • **Java历史与市场竞争**： - **市场竞争**：Java的推广过程中涉及与微软等公司的竞争，例如IBM通过Eclipse和SWT与Borland竞争，而微软则在Java许可上产生了法律纠纷（w10-1）。 争议焦点： • Java在1990年代的宣传是否过度以及其是否实现了当时的承诺。

“The Bitter Lesson” is wrong. Well sort of

作者: GavCo | 评分: 45 | 评论数: 12 | 发布时间: 2025-07-20 16:33
文章摘要

文章主要讨论了AI研究中两种方法的平衡问题：基于“人类知识”的方法和依赖“数据+计算”的通用方法。作者反对Rich Sutton在“苦涩的教训”一文中提出的观点，即仅依靠数据和计算就能取得长期进展，认为人类知识和数据驱动方法需要相互补充和平衡。文章指出，没有纯粹依赖人类知识或完全无需人类指导的机器学习模型。人类知识在模型构建的各个阶段，从设计到评估，都发挥着重要作用。尽管随着技术发展，模型可能更多依赖“有影响力的”方法，但人类知识的直接应用仍然不可或缺。作者以大型语言模型为例，说明在模型生命周期的不同阶段，如何平衡这两种方法以构建有效的AI模型。

评论摘要
主要讨论点：对“苦涩的教训”（The Bitter Lesson）的不同理解和争议 不同观点： • [aabhay] 认为“苦涩的教训”背后还有更“苦涩的现实”，即虽然可以通过增加计算资源和数据来扩展模型，但要得到高质量的模型，仍需要大量人工筛选和标注的高质量数据。现代最好的模型背后是数十亿计的资金投入，用于获取和处理这些数据。 • [rdw] 提出“苦涩的教训”之所以令人失望，是因为AI研究人员原本希望通过构建类似人类智能的系统来理解人类智能，而不仅仅是构建一个有效的“黑箱”模型。这一教训反映了在未完全理解智能的情况下构建智能系统的无奈。 • [rhet0rica] 质疑“苦涩的教训”的普遍性，指出历史上确实存在基于纯人类知识构建的专家系统（如MYCIN），因此认为该教训并未充分考虑已有研究成果，并批评相关讨论缺乏研究深度。 • [rhaps0dy] 认为Sutton的“苦涩的教训”讨论的是AI的长期进展，而不是短期生产需求。短期内，手动添加一些知识对模型仍然重要，但长期来看，这种方法对推动AI进步作用有限。 • [macawfish] 强调“苦涩的教训”核心在于更多依赖机器学习而非人工调整，有效利用已有数据，而不是简单地通过增加计算和数据来解决问题。 • [roadside_picnic] 结合自身经验指出，在实际工作中，数据往往比架构和基础设施更具限制性。在数据不足的情况下，简单且可解释的模型往往比复杂的神经网络模型更有效。他主张根据问题的信息量选择合适的模型。 • [godelski] 认为虽然“规模就是一切”的观点是错误的，但规模的增加确实带来了显著进步。然而，AI的发展不仅仅依赖于规模，还需要算法创新、数据收集方式的改进等。他强调AI领域仍有大量创新空间。 • [grillitoazul] 指出“苦涩的教训”仅在一定范围内有效。例如，LLM在处理某些特定任务（如大数相加）时表现不如传统算法，表明在某些情境下，仍需要新的智能算法来突破现有局限。 • [littlestymaar] 通过Leela Chess Zero与Stockfish的案例说明，结合计算资源和人类知识可以取得最佳效果。虽然纯粹依赖计算资源可以取得进展，但同时拥有计算资源和人类知识的方案往往更具优势。 补充讨论： • 争议的焦点在于“苦涩的教训”是否适用于所有情境，尤其是当前模型是否仅通过增加数据和计算资源就能取得最佳效果，还是需要结合人类知识和智能算法。 • 讨论中多次提到数据质量和模型可解释性的重要性，尤其是在实际应用中，简单模型在数据有限的情况下可能比复杂模型更有效。 • 有人质疑“苦涩的教训”是否被过度简化和误解，历史上的专家系统被作为反例提出。 • 总体上，讨论反映了对AI发展路径的多元看法，从依赖规模到结合人类知识和智能算法，不同观点强调了不同因素的重要性。
