Staged publishing and new install-time controls for npm

作者: brianmcnulty | 评分: 48 | 评论数: 7 | 发布时间: 2026-05-22 19:49
文章摘要

npm发布两项供应链安全更新： 1. **分阶段发布正式上线**：包不再直接发布，而是先上传到暂存队列，需维护者明确批准后才能安装。强化了发布验证，即使CI/CD自动化流程也需人工审批。建议配合可信发布(OIDC)使用，CI推送到暂存队列，维护者从可信设备批准。需npm CLI 11.15.0+。 2. **新增安装源控制标志**：新增`--allow-file`、`--allow-remote`、`--allow-directory`三个标志，配合已有的`--allow-git`，可精确控制npm install从哪些非注册表源安装依赖。每个标志可设为`all`或`none`。`--allow-git`在v12版本将默认改为`none`。

评论摘要
主要讨论点：如何应对软件包供应链攻击，尤其是“延迟发布/延迟安装”这类缓解措施是否有效，以及是否应结合更主动的安全手段。 不同观点： • 支持更主动的代码分析：supriyo-biswas认为，不应只靠“推迟更新”来回避风险，静态分析和动态分析代码可能是更有前景的方案。其核心论点是：与其延后暴露问题，不如直接识别恶意或异常代码。 • 质疑分阶段发布/延迟策略：weinzierl表示，乐观看这只是“创可贴”，现实地看，长期甚至可能伤害构建更安全基础设施的努力。争议焦点在于：这类措施是有效过渡方案，还是会让行业依赖权宜之计、忽视根本治理。 • 认可延迟安装的现实价值：madarco举例称，pnpm 10.x默认不会下载发布时间不足一天的包，说明生态里已出现类似防护思路。这是在提供实践案例，暗示“冷静期”机制具备可操作性。 • 认为可缓解近期攻击：koinedad持较正面态度，认为这种做法“也许能帮助应对最近的一些攻击”，强调其短期防御价值。 补充讨论：评论之间形成了“短期缓解 vs 长期治理”的对照：有人认为延迟机制能降低近期风险，也有人担心它掩盖根本问题；代码分析被提出为更深入的替代或补充方向。

Sp.h is the standard library that C deserves

作者: dboon | 评分: 88 | 评论数: 20 | 发布时间: 2026-05-20 13:05
文章摘要

这篇文章介绍了作者开发的C语言标准库sp.h。它是一个15,000行的单头文件库，核心理念包括：直接调用系统调用而非依赖libc；摒弃传统的堆内存管理，要求程序显式管理内存分配器；用指针+长度的字符串结构(sp_str_t)替代以null结尾的字符串，提升安全性和性能；代码高度可读可修改，仅约40个系统调用是平台相关的；用C99编写，具有极强的可移植性。作者认为传统libc已成为障碍，sp.h提供了更现代、高效且符合实际需求的底层接口。

评论摘要
主要讨论点：对一个强调“极致可移植、绕过libc、反空终止字符串、小而强”的C头文件库，其设计目标、实现一致性、可读性与工程实用性的争论。 不同观点： • **质疑目标自相矛盾**：有人指出“极致可移植”与“不支持冷门平台”冲突；若只面向x86_64、aarch64、WASM，就不能同时宣称“任何编译器/系统都可用”。也有人质疑“直接对syscall编程”只在Linux稳定，其他平台未必成立。 • **部分理念获认同**：多位评论者赞同“长度+指针优于\0结尾字符串”“适度重视性能优化”“标准库尽量贴近syscall”。同时补充 FILE 抽象在如 `fopencookie`、`open_memstream` 等场景仍有价值。 • **实现与表述被批评**：有人认为示例代码噪声大、可读性差，`wc` 示例命名易误导；“There Is No Heap”却又定义堆分配接口，被指表述不清。还有人质疑原子实现：Unix下包 `pthread mutex` 仍依赖标准库，且未说明内存模型/栅栏，甚至怀疑代码质量。 • **工程层面的担忧**：包括固定 `SP_PATH_MAX=4096` 对超长路径缺少回退；header-only 需引入 `windows.h` 等导致编译变慢；若程序部分仍需 libc、以及 `main` 前初始化如何处理，也被追问。 • **定位与背景讨论**：有人觉得这种强观点风格“很有趣”，或适合作为自定义语言的编译目标；也有人提到其思想与 DJB、Zig/WTF-8 等既有传统有关，并追问文中为何未提 Zig。 补充讨论：争议焦点主要在“宣称的底层纯粹性是否与实际实现一致”，以及“可移植性、简洁性与现实兼容性”三者如何平衡。

这篇文章讲解如何用数组语言K进行编程思维。文章以矩阵乘法为例，展示了从命令式编程到K语言风格的转换过程：首先将传统算法直接翻译成K代码（包含大量全局变量、嵌套循环和修改操作），然后逐步简化——消除全局变量、用fold替代循环累加、利用转置和each操作符处理行列配对，最终将冗长的代码精简为简洁的`{x{+/x*y}\:y}`。文章强调K编程是持续简化模式的过程，通过REPL迭代开发，将复杂模式转化为声明式、易读的代码。

评论摘要
主要讨论点：开源数组语言项目是否存在，以及K/APL系语言在真实项目中的可用性、生态与可维护性。 不同观点： • 原提问者希望看到“真实世界”的数组语言开源代码库，而不只是短小示例或“K支撑金融系统”的传闻，关注点是实际工程案例。 • 有人补充了过往HN讨论链接，说明“如何用数组语言思考”已被反复讨论，侧面表明这个话题更常停留在理念/范式层面，而非直接给出大型开源项目实例。 • 有观点认为APL很有趣，并试图厘清生态：K似乎是较常被推荐的APL衍生语言；虽然K本身是专有的，但存在一些开源兼容实现。该观点进一步追问：除K外，还有哪些用户群活跃、值得深入了解的APL衍生语言。 • 另一种明显保留甚至质疑的观点认为，K/Q/APL类语言“像数学版正则”：极度简洁、表达力强，适合交互式使用；但也因此近似“只写不读”，若把大量程序保存成这种风格，维护性会成为严重问题。 补充讨论：争议焦点主要在于“强大简洁”与“可读可维护”之间的权衡；同时，评论中对开源实现、专有语言本体与社区活跃度的区分也很关键。
