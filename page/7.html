Oxlint 宣布推出基于类型感知的代码检查功能，重点包括 no-floating-promises 等规则。该预览版通过文档化决策过程和技术细节，寻求社区合作讨论。用户可通过安装 oxlint-tsgolint 并使用 --type-aware 标志快速体验。性能测试显示，相比 typescript-eslint 耗时1分钟的项目，现在可在10秒内完成，这得益于使用 Go 编写的 typescript-go 技术。技术架构采用 Rust 编写的 oxlint 作为前端，Go 编写的 tsgolint 作为后端，通过简单管道通信。团队评估了多种方案后，选择不自行开发类型检查器，而是通过调整 typescript-go 的内部 API 来实现类型检查。虽然存在维护挑战，但团队认为这是当前最优解。

评论摘要
主要讨论点：[Oxlint 作为 ESLint 替代者的优势和潜在挑战] 不同观点： • [Oxlint 的优势和进步] - Oxlint 是基于 Rust 的工具链 Oxc 的一部分，由开发 Vite 和 Vitest 的团队 Void0 打造，性能优秀且受到高度评价。 - Oxlint 解决了之前不支持类型感知 linting 的问题，通过整合 Microsoft 新的基于 Go 的 TypeScript 编译器实现了这一功能。 - "Decision Process" 部分受到特别好评，因为它详细讨论了多种假设场景，帮助用户理解全局。 • [Oxlint 的潜在挑战] - 需要持续跟进 Go 编译器的内部更新，这对维护团队提出了较高要求。 - 目前不清楚 Microsoft 是否会为新的编译器提供程序化接口，这可能影响 Oxlint 的长期可用性。 - 插件系统的可行性存疑，插件是 ESLint 生态的重要组成部分，Oxlint 需要解决这一问题才能真正取代 ESLint。 补充讨论： • 争议焦点：Oxlint 能否长期保持与 Go 编译器的兼容性，以及插件生态的构建是否可行。 • 讨论关系：tkcranny 的评论是对 jauntywundrkind 的补充，既肯定了 Oxlint 的进步，也指出了潜在的挑战。

Branch prediction: Why CPUs can't wait?

作者: signa11 | 评分: 28 | 评论数: 5 | 发布时间: 2025-08-16 05:45
文章摘要

这篇文章主要探讨了CPU分支预测的重要性及其对程序性能的影响。作者通过学习LLVM编译器优化时意识到，即便最先进的编译器优化也无法解决硬件层面的分支预测问题。文章解释了程序计数器（PC）如何顺序执行指令，并介绍了现代CPU通过指令流水线技术实现并行处理的不同阶段（取指、解码、执行、内存访问、写回）。然而，当遇到不可预测的分支（如条件跳转）时，流水线会被中断，导致性能损失。分支预测失误的代价高昂（约5纳秒），可能抵消多个编译器优化的效果。文章强调了理解分支预测机制对程序员优化代码的重要性。
