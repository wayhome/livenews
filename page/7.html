Context engineering

作者: chrisloy | 评分: 81 | 评论数: 7 | 发布时间: 2025-11-02 08:52
文章摘要

这篇文章介绍了从"提示工程"（prompt engineering）到"上下文工程"（context engineering）的演变过程。随着大型语言模型（LLM）从简单的对话聊天机器人发展为复杂系统中的决策组件，传统的提示工程（依靠精心设计的提示词来引导模型响应）显示出局限性。文章解释了LLM如何通过上下文窗口处理标记序列，以及如何通过"对话框架"（chat framing）和"上下文学习"（in-context learning）等技术改进模型输出。作者指出，上下文工程是一种更结构化、动态和精确的方法，它系统地考虑输入模型的每个标记，而不是依赖试错式的提示词设计。文中以"最佳科幻电影"为例，展示了不同方法如何影响模型输出。

评论摘要
主要讨论点：[关于上下文工程和代理系统是否可以被视为工程学的争议] 不同观点： • [voidhorse] 认为制作提示和上下文更像是一门手艺而非工程学，缺乏精确性和形式化语言，模型行为的不稳定性使得这种方法不可靠。他批评滥用“工程”一词是为了自我满足或获取利益。 • [aeve890] 和 [sgt101] 质疑这种方法是否真的可以被称为“工程”，认为缺乏证据和衡量标准，仅仅是个人观点的堆砌。 • [alecco] 直接质疑文章内容的真实性，认为可能是由AI生成的劣质内容。 • [grigio] 则对博客内容本身表示了兴趣，希望获取RSS订阅，与其他讨论形成对比。 补充讨论： • 争议的焦点在于“上下文工程”是否具备工程学的严谨性和科学性，以及是否有足够的证据支持其有效性。 • [voidhorse] 提到了自然语言的模糊性和数学的精确性之间的对比，进一步强化了他对手艺而非工程的看法。 • [sgt101] 强调缺乏实证和衡量标准，呼应了[voidhorse]的观点。

Why do AI models use so many em-dashes?

文章摘要

这篇文章探讨了AI生成文本中频繁使用破折号的现象。作者否定了几个常见解释：训练数据模仿人类文本、破折号的灵活性优势或节省token的说法。重点分析了两个可能原因：一是非洲英语影响（RLHF阶段可能引入非洲英语工作者的偏好），但数据表明非洲英语实际破折号使用率更低；二是训练数据来源变化（2022年后AI实验室可能扫描了大量印刷书籍，而印刷媒体历史上破折号使用率较高）。值得注意的是，GPT-3.5并不常使用破折号，但后续版本使用量激增10倍。最终，文章指出这种现象的确切成因仍不明确。

评论摘要
主要讨论点：为什么AI模型（如GPT）频繁使用em-dashes（长破折号），以及人类与AI在使用em-dashes上的差异。 不同观点： • **训练集假设**：em-dashes在高端出版物（如《The Atlantic》《The New Yorker》）中频繁出现，这些内容被AI模型视为高质量文本并被强化学习（RLHF）加权（lordnacho、spuz）。 - 补充：Medium的创始人偏爱em-dashes，其平台的高质量写作可能影响了AI的偏好（spuz）。 • **水印假设**：em-dashes可能是OpenAI用于识别AI生成文本的统计水印之一，类似于“delve”等标志性词汇（sixhobbits、0xbadc0de5）。 - 争议点：缺乏直接证据支持水印假设，但技术可行性存在（sixhobbits）。 • **功能性与计算效率**：em-dashes能高效连接句子，减少AI重写句子的计算成本（keiferski）。 - 补充：人类作者也可能因功能性偏好em-dashes（iansteyn、adi_kurian）。 • **Unicode与输入限制**：人类因键盘输入限制（如ASCII为主）较少使用em-dashes，而AI直接生成Unicode字符（numpad0）。 - 关联点：OCR可能误将短破折号识别为em-dashes（xg15）。 • **多语言影响**：其他语言（如俄语、欧洲语言）中em-dashes的规则可能通过训练数据影响AI（danielodievich、Etheryte）。 - 例子：俄语用em-dashes标记对话（danielodievich）。 • **合成数据循环**：后续模型可能通过合成数据（含强制em-dashes）强化了这一偏好（spidersouris）。 补充讨论： - 文化因素：科幻作家海因莱因的粉丝（如互联网先驱）可能间接推广了em-dashes（kentbrew）。 - 人类态度分化：部分用户认为em-dashes被过度批评，实际是有效的修辞工具（adi_kurian、iansteyn）。

Claude Code can debug low-level cryptography

作者: Bogdanp | 评分: 426 | 评论数: 20 | 发布时间: 2025-11-01 18:41
文章摘要

这篇文章讲述了作者在Go标准库中实现NIST新推出的后量子签名算法ML-DSA时遇到的验证签名失败的bug。在作者疲惫放弃调试后，意外发现AI工具Claude Code在几分钟内就准确找到了bug原因：作者在Verify函数中错误地对w1值进行了两次高位处理。此外，作者还测试了Claude Code在解决其他两个低级密码学bug（错误的Montgomery常数和长度错误的值）时的表现，发现AI工具能有效辅助调试复杂的密码学代码。尽管AI提供的修复方案不完全理想，但它显著节省了调试时间，展示了AI在专业技术领域的实用价值。
