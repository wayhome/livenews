Declarative Web Push

作者: janandonly | 评分: 73 | 评论数: 14 | 发布时间: 2025-03-31 12:06
文章摘要

本文介绍了**Declarative Web Push**及其在WebKit中的实现，旨在提高能效和隐私保护。与传统Web Push依赖服务工作线程（service worker）处理推送通知不同，Declarative Web Push允许开发者在不使用服务工作线程的情况下显示通知，从而减少电池消耗和隐私风险。它通过直接描述用户可见的通知内容，避免了因服务工作线程故障而无法显示通知的问题。此外，WebKit强制要求推送订阅时设置`userVisibleOnly`标志，确保所有推送都会显示通知，防止网站偷偷进行后台操作。文章还讨论了隐私保护的重要性，尤其是通过Intelligent Tracking Prevention（ITP）等机制保护用户数据隐私。Declarative Web Push更易用、更高效，并兼容现有Web Push系统。

评论摘要
主要讨论点：浏览器推送通知（Web Push Notifications）的技术实现、用户体验、隐私保护及其与原生应用的比较 不同观点： • fidotron和alana314指出当前浏览器推送通知在不同平台（Android和iOS）上的实现存在问题，尤其在延迟、通知管理和用户体验方面。alana314认为推送通知没有实际用途，并且用户经常被请求权限的提示轰炸，因此选择关闭通知功能。 • hackernudes和alabastervlog则关注技术细节，特别是iOS中“Declarative Web Push” API的实现方式，以及其与原生应用推送通知服务（APNs）的关系。他们好奇iOS如何处理来自网站的推送，以及新的API是否简化了开发流程。 • mirkodrummer和joekrill对浏览器推送通知和原生应用之间的不公平待遇提出质疑。他们认为，尽管浏览器推送通知被限制以保护隐私和电池寿命，但原生应用却没有类似的限制，质疑这是否是故意让原生应用更具优势。 • notepad0x90强调了推送通知技术被滥用的风险，尤其是恶意网站利用通知进行垃圾信息推送。他们建议加强浏览器和操作系统对推送通知的审核机制，如引入EV TLS证书或信任评估机制，以减少滥用。 • ftbsqcfjm和EGreg对新的“Declarative Web Push” API持乐观态度，认为这是一种简化开发流程的进步，但同时担心其可能带来的性能影响和灵活性降低问题。EGreg还希望未来不再需要用户手动将网页添加到主屏幕以接收推送通知。 补充讨论： • mary-ext提到对ITP（智能跟踪预防）机制的影响的关注，质疑新提案是否会豁免自动清理机制，并对ITP的正当性提出质疑。 • butz关注浏览器的“Alarms API”实现，表示期待利用该API开发提醒类应用。 • therein分享了对WebKit命名方式的个人理解，指出其与其他Apple框架（如AppKit、UIKit）的相似性。 • andrewmcwatters批评苹果允许企业将广告推送到用户锁屏界面的做法，认为这降低了用户体验。 争议焦点： • 浏览器推送通知的限制是否真的出于保护隐私和电池寿命，还是为了打压网页应用以维护原生应用的市场优势。 • 新的API是否能真正解决现有问题，并平衡开发者需求与用户体验。

Show HN: The C3 programming language (C alternative language)

作者: lerno | 评分: 91 | 评论数: 15 | 发布时间: 2025-04-03 13:55
文章摘要

C3是一种基于C语言语法和语义的编程语言，旨在进化C语言的同时保持C程序员熟悉的特性。C3强调与C语言的ABI兼容性，可以轻松在同一项目中混合使用C和C3代码。其设计原则包括保持C语言的核心特性，仅在必要时进行修改，并引入一些高层次的便利功能。C3没有强制性的头文件，采用基于模块的命名空间，支持切片、编译时反射、增强的编译时执行、基于泛型模块的泛型编程、基于"Result"类型的零开销错误处理、延迟执行（defer）、值方法、关联枚举数据等特性。C3的灵感来源于C2语言，旨在迭代C语言而不是创造一种全新的语言。预编译的二进制文件适用于Windows x64、Debian x64、Ubuntu x86和MacOS Arm64等操作系统。

评论摘要
