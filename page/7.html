The .a file is a relic: Why static archives were a bad idea all along

作者: eyalitki | 评分: 61 | 评论数: 19 | 发布时间: 2025-07-19 08:59
文章摘要

文章探讨了C语言SDK中的静态链接库（.a文件）的缺点，以及为何静态档案并非理想解决方案。作者以自身在开发C语言SDK的经验为例，指出静态链接在满足客户需求方面的不足，尤其是在易用性、兼容性和维护性方面存在问题。动态链接库（.so文件）则提供了更好的灵活性，比如安全补丁可以通过更新库版本来实现。作者建议对ELF文件头进行更新，引入新的“静态捆绑对象”类型以替代现有的静态档案。文章最后强调，这是作者的个人观点，不代表其雇主的立场。

评论摘要
主要讨论点：静态链接与静态库（.a文件）的优缺点及可能的改进 不同观点： • TuxSH认为在静态链接的二进制文件中，未使用的解密函数（如AES256）可能会被包含，而实际上并不需要。他提到使用`-ffunction-sections -fdata-sections`和`-Wl,--gc-sections`可以解决部分问题，但这些方法并未广泛使用。他还指出不应依赖静态初始化顺序。 • amiga396反驳TuxSH的观点，认为他所描述的问题只是特例，并提出可以通过宏或者特定的LDFLAGS来解决。他强调静态链接在防止动态链接器漏洞方面有其优势，并指出通过适当命名和使用命名空间可以避免符号冲突。 • kazinator支持TuxSH的部分观点，指出如果需要在运行时调用初始化函数，需要确保符号被引用。他提到U-boot等项目已经解决了这个问题，并解释了.a档案在链接速度上的优势，特别是在处理大型软件时。 • kazinator进一步解释了.a档案在处理循环依赖和减少链接时间和内存消耗方面的优势，并提到Linux内核构建过程中使用.a档案来优化链接。 • rixed对文章标题的绝对性表示质疑，引用Chesterton’s Fence原则，暗示对静态链接的批评可能忽视了一些历史背景和实际需求。 • cryptonector认为静态链接没有像动态链接那样发展，并提出可以通过在.a文件中记录依赖元数据来改进静态链接，使其具备动态链接的一些优势。 • EE84M3i对为什么不能静态链接.so文件表示疑惑，并询问在创建共享对象时丢失了哪些信息。 • tux3介绍了自己开发的工具armerge，该工具通过将静态库中的所有对象合并为一个对象来解决不对称问题，并认为这是一个临时解决方案，直到新的ET_STAT格式出现。 • jhallenworld和uecker提到部分链接（partial linking）和符号可见性问题，并提出了一些可能的解决方案。 • dzaima建议创建一个工具，将多个.o文件合并为一个，并解决私有符号泄漏问题。 • flohofwoe认为库文件本身不是问题，问题在于将SDK作为预编译二进制分发。他指出.a/.lib文件最初可能只是作为编译器和链接器之间的中间文件格式。 • stabbles提到可以在静态库中引入类似于动态库的元数据文件，并指出binutils的`libdep`功能已经部分实现了这一点，但还不够完善。 • dale_glass分享了一个静态链接导致的构造函数多次调用的问题，强调了静态链接中符号重复的潜在风险。 • layer8质疑是否缺少.so文件的某些特性使其不能用于静态链接，并建议理想情况下应只分发一个库版本，让第三方选择静态或动态链接。 补充讨论： • 静态链接中的符号冲突和构造函数多次调用问题被多次提及，显示出这些是实际开发中的常见问题。 • 提出了多种技术解决方案，如armerge工具、部分链接、符号可见性控制等，显示出社区对改进静态链接的积极探索。 • 对静态库和动态库各自的优势和局限性进行了深入讨论，特别是.a文件在处理大型软件和循环依赖方面的优势。 • 对静态链接元数据记录和依赖解析的改进建议，显示出对静态链接现代化和功能扩展的潜在需求。

NonRAID – fork of unRAID array kernel module

作者: qvr | 评分: 47 | 评论数: 3 | 发布时间: 2025-07-22 20:16
文章摘要

NonRAID 是一个基于 unRAID 存储阵列的内核驱动 fork，旨在让用户在 Ubuntu 等系统上使用类似 unRAID 的存储阵列功能，而无需安装 unRAID 系统。与 unRAID 不同，NonRAID 驱动被分离为独立的内核模块（md_nonraid），通过 DKMS 安装在 Ubuntu 和 Debian 系统上，无需替换标准内核驱动。它替换了 raid6_pq 模块以支持校验计算。该项目仍处于实验阶段，未经过广泛测试，使用时有数据丢失风险。用户需手动管理阵列磁盘，并通过超级块文件存储和恢复阵列配置。安装后，通过 modprobe 命令加载驱动并指定超级块文件来管理阵列。注意，该驱动不提供自动化管理，需用户自行操作。

评论摘要
主要讨论点：关于unRAID与常规MD（软件RAID）的区别以及文件系统中前向纠错（FEC）的实现讨论 不同观点： • [miffe] 提问：对unRAID不熟悉，想了解它与常规MD（软件RAID）有何不同。他认为这可能涉及一些技术差异，但缺乏具体背景知识。 • [nullc] 回应并提出文件系统中的文件级前向纠错（FEC）问题： - 指出当前是否有文件系统支持文件级别的FEC。 - 提出文件级别的FEC可以通过增加少量空间来大幅提高数据完整性，尤其是在大文件和冷数据存储场景下。 - 强调RAID 5/6的局限性，尤其是在磁盘未完全损坏但出现坏块时，FEC可以更好地处理这种问题。 - 提到现有工具如par虽然能实现一些纠错功能，但缺乏与文件系统的无缝集成，无法充分利用文件系统自带的校验和功能。 • [hebocon] 认为：这个讨论或内容更适合作为“Show HN”类型的帖子，表明他可能认为这是一个值得展示的技术话题，而非普通的讨论。 补充讨论： - [nullc] 的观点中隐含了对现有RAID技术和文件系统在数据保护方面不足的批评，尤其是对大容量冷数据存储在坏块处理上的不足。 - 争议的焦点可能在于文件系统是否应该或如何实现透明的FEC功能，以提高数据可靠性。 - [hebocon] 的评论则反映出对话题性质的不同看法，认为该讨论具有展示价值。

Immediately-Invoked Function Expression (2010)

作者: motorest | 评分: 14 | 评论数: 6 | 发布时间: 2025-07-19 09:24
文章摘要

本文由Ben Alman撰写，讨论了JavaScript中的立即调用函数表达式（IIFE）。作者指出，许多人误称为“自执行匿名函数”的术语并不准确，并解释了该模式的实际工作原理。IIFE利用函数作用域创建私有变量，避免外部访问。在JavaScript中，函数声明和函数表达式有区别，直接使用函数表达式会抛出SyntaxError。解决方法是将函数表达式用括号包裹，使其被解析为表达式而非声明。常见的IIFE写法有两种：`(function(){})()` 或 `(function(){}())`。作者强调使用准确的术语有助于理解复杂概念。

评论摘要
主要讨论点：IIFE（Immediately Invoked Function Expression，立即调用函数表达式）在JavaScript中的使用及其相关技巧 不同观点： • [insin]: 支持使用void函数表达式，特别是在不需要返回值的情况下，认为这种做法在某些场景下（如浏览器扩展开发）非常实用，尤其是当需要在非异步上下文中等待时。他还提到这种写法可能会让不熟悉这种技巧的JavaScript开发者感到困惑。 • [domlebo70]: 提到了一篇博客文章，表示自己经常使用类似的技巧来编写面向表达式的程序，暗示这种做法有助于提高代码表达能力。 • [motorest]: 指出博客文章被Mozilla的IIFE页面引用，提供了一个参考链接，表明这种技巧在社区中具有一定的认可度。 • [jelder]: 提到在使用switch/case语句时，经常使用IIFE，认为这是一种将语句转换为表达式的便捷方法，尽管可能看起来有点奇怪。 • [zahlman]: 表达了对长链IIFE写法的不满，认为这种方式在过去的JavaScript开发中造成了很多混乱，主张函数命名和扁平化结构优于嵌套结构。 • [apothegm]: 表示对在修改第三方库行为时使用IIFE的做法感到不满，认为这种方法限制了选择，主张在现代JavaScript中有更好的方式来实现封装。 补充讨论： • IIFE在不同场景下的实用性：[insin]和[jelder]都提到了IIFE在特定开发场景中的便利性，如在浏览器扩展开发和switch/case语句中。 • 代码风格和结构：[zahlman]强调了代码扁平化的重要性，反对过多的嵌套结构，这与其他开发者对IIFE的积极看法形成对比。 • 现代JavaScript中的替代方案：[apothegm]提出了在现代JavaScript中有更好的封装方法，暗示IIFE可能不再是最佳选择。 争议焦点： • IIFE在现代JavaScript开发中的适用性和必要性：部分开发者认为IIFE在某些场景下仍然非常有用，而另一些开发者则认为有更好的替代方案，这反映了在JavaScript社区中对IIFE的评价存在分歧。
