Everything I know about good API design

作者: ahamez | 评分: 242 | 评论数: 21 | 发布时间: 2025-08-24 19:10
文章摘要

这篇文章主要探讨了API设计的原则和最佳实践。作者指出好的API应该"无聊"且易于使用，开发者不应过多思考API本身而是专注于目标。API一旦发布就难以更改，因此设计时需要平衡简单性和灵活性。文章强调"不破坏用户空间"原则，任何更改都可能影响下游应用。对于必要的重大变更，建议采用版本控制策略（如/v1/和/v2/），并给予用户充足时间迁移。作者认为API设计应当以稳定性优先，避免为追求完美而进行不必要的修改。

评论摘要
主要讨论点：[API 设计与稳定性、版本控制、幂等性及用户体验] 不同观点： • **API 稳定性与版本控制** - [dwattttttt] 强调内核 API 的稳定性与声明的重要性，指出“永不破坏用户空间”但内核 API 可以随时变更。 - [pixl97] 建议从一开始就引入版本化 API，以应对未来的不可预测变化。 - [wener] 反对通过 /v1、/v2 路径进行版本控制，认为应通过字段或参数扩展功能，而非强制用户更改基础 URL。 • **幂等性实现争议** - [achernik] 质疑 Redis 存储幂等键的可靠性，认为需与操作原子性绑定，避免中间状态导致数据不一致。 - [barapa] 支持将幂等键与写入操作放在同一事务中存储，确保一致性。 - [mrkeen] 提出幂等性可能需保证相同异常重复抛出，而不仅是操作执行一次。 • **API 设计与用户体验** - [runroader] 认为内部用户同样是用户，需避免频繁变更 API 设计，建议通过“自用测试”确保稳定性。 - [claw-el] 批评过度抽象的 API 资源设计会增加理解与调试难度，尤其对新用户不友好。 - [canpan] 指出非技术用户（如销售、学生）可能缺乏基础技能（如时区转换），API 需考虑易用性。 补充讨论： - **历史视角**：[0xbadcafebee] 提醒 API 概念源自 1940 年代，建议从早期案例中汲取设计经验。 - **文档质量**：[JimDabell] 认为 API 质量与文档获取难度成反比，隐藏文档可能预示设计糟糕。 - **行业案例**：[frabonacci] 点名批评 Spotify、Reddit 等公司违反“不破坏用户空间”原则。 - **外部资源**：[tiffanyh] 推荐了额外的 API 设计指南链接。 争议焦点： - 幂等性实现是否必须依赖事务性存储（如数据库）而非独立缓存（如 Redis）。 - 版本控制应通过路径（/v1）还是参数扩展实现，后者是否更灵活。

本文报道了数学家们寻找“忙碌海狸数”（Busy Beaver numbers）的最新进展。忙碌海狸数序列与计算机科学中最难的问题之一——停机问题密切相关。前五个忙碌海狸数已经确定，其中第五个BB(5)直到2024年才被主要由业余数学家组成的在线团队确定。目前BB(6)的确切值仍未知，但数学家们已证明它大到无法用普通十进制表示。2022年，研究者们发现BB(6)的下限已经超出宇宙原子总数所能表示的范围。2025年6月，研究者又两次刷新了这一下限，显示出这些数字的巨大性远超想象。这些发现展示了计算理论的复杂性，以及即使是简单程序也能产生难以想象的庞大数字。
