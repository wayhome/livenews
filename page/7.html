Designing DB partitions you don't have to babysit

作者: rtolkachev | 评分: 61 | 评论数: 6 | 发布时间: 2026-07-01 13:05
文章摘要

这篇文章讨论了数据库按时间字段（如 `created_at`）分区的常见问题： **核心问题：** - 按 `created_at` 分区后，查询必须包含时间条件才能实现分区裁剪，否则会扫描所有分区导致性能下降 - 分区键必须加入主键，将 `PRIMARY KEY (id)` 变成 `PRIMARY KEY (id, created_at)`，破坏了 `id` 的唯一性保证 - 查询优化器无法再将单 `id` 查询视为常量查找，性能从 `const` 降级为 `ref` - 分区键泄漏到应用层，所有查询都需要添加日期过滤器，增加维护负担 **推荐方案：** 按主键（如 `id`）分区而非时间字段，由后台服务根据实际增长情况管理分区边界。这样查询可以继续使用现有的键，分区裁剪自动工作，分区逻辑不会侵入应用代码。

评论摘要
主要讨论点：大规模数据场景下的分区策略和ID管理方案选择 不同观点： • **传统分区方案的技术约束**：指出分区表的唯一性保证问题——MySQL和PostgreSQL要求唯一约束必须包含分区键，但AUTO_INCREMENT和SERIAL可以提供解决方案 • **质疑ID主键的实用性**：认为如果用户不搜索ID且ID不可见，使用ID作为主键意义不大；按创建日期分区时，用户搜索会扫描所有分区索引，效率存疑 • **数据仓库替代方案**：建议放弃OLTP分区，改用ClickHouse等专门的分析型数据库，声称$170/月VPS即可处理每天500+亿行查询，认为这比分区OLTP表更简单 • **特殊ID模式**：推荐Snowflake ID或UUID7模式，提醒注意bigint（64字节）与UUID（128字节）的权衡 • **专用数据库方案**：提及kdb+可轻松处理每天10亿行数据 补充讨论：争议焦点在于是优化传统关系数据库的分区方案，还是直接采用专门的分析型数据库或时序数据库来处理大规模数据场景。

Curveball

Curveball 是作者为开源游戏 Neverball 开发的曲线生成工具，使用 Rust 编写，可在网页或桌面端运行。 作者开发它是因为现有工具 curve.c 只能生成圆弧曲线，无法满足复杂关卡设计需求。Neverball 关卡由"brushes"（几何体）组成，每个 brush 通过半空间交集定义，必须是凸形状。 Curveball 的核心创新是采用"挤出"抽象：先定义 2D 轮廓，再沿路径挤出到 3D 空间。工具使用凸包算法（chull 库）自动生成形状，通过组合 m 种轮廓和 n 种路径，可以生成 m×n 种不同曲线，大大提高了创作效率和灵活性。

It's not me, it's the compiler

作者: SVI | 评分: 84 | 评论数: 12 | 发布时间: 2026-07-01 07:41
文章摘要

这篇文章讲述了作者在重构 Rust 编写的 JavaScript 引擎解析器时遇到的一个神秘 bug。作者将一个带有条件分支的函数 `consume_test` 重构为更简洁的版本，使用 `x as u32` 进行类型转换来替代 if-else 分支。重构后，解析 for 循环语句时出现了错误。但当作者明确使用 `if x { 1 } else { 0 }` 替代 `x as u32` 时，代码又能正常工作了。 作者对此感到困惑，因为 `bool as u32` 应该是标准的类型转换方式。在排除了自己的代码问题后，作者怀疑这是一个罕见的编译器 bug。文章标题"It's not me, it's the compiler!"反映了程序员常说但通常是错误的抱怨，而这次作者相信自己遇到了真正的编译器问题。

评论摘要
**主要讨论点：** 编译器误编译bug的存在性、频率、严重性，以及如何看待"永远不是编译器的问题"这一经验法则 **不同观点：** • **经验派**：多位开发者分享亲身经历证实编译器bug确实存在。有人在2006年遇到ATMega编译器错误修改循环外变量；有人30年前遇到Java SDK布局bug；有人在Nim beta版和LLVM中发现多个bug。这些经历挑战了"永远不是编译器"的经验法则 • **频率认知分歧**：一方认为编译器bug"surprisingly common"，只是多数人未察觉，在大规模代码库和完整测试套件中更易发现。另一方通过Rust的统计数据指出，在61K+问题中仅7个同时标记为p-critical和i-miscompile，显示此类严重bug相对罕见 • **优化哲学之争**：有人主张编译器应更保守，死代码消除应仅在链接时优化中进行，编译器应发出警告而非静默优化。认为编译器应展示优化建议让程序员自行重写，既防止误编译又减少编译时间。这与主流编译器设计理念形成对比 • **安全性担忧**：针对Rust案例，开发者指出这类误编译在安全代码中也容易触发，违反了语言的安全契约。对MIR优化管道的晚期pass出现此类问题感到意外，质疑审查机制 **补充讨论：** 有人认为原始代码虽冗长但更清晰易调试；编译器开发者承认追踪此类bug很棘手；多人呼吁对误编译进行事后分析以改进流程
