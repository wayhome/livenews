Show HN: FilterQL – A tiny query language for filtering structured data

作者: genshii | 评分: 63 | 评论数: 12 | 发布时间: 2025-08-24 18:55
文章摘要

FilterQL是一个小型结构化数据查询语言，包含TypeScript库和语言规范。主要功能包括：1) 支持多种比较运算符（==、*=、~=等）和逻辑运算符（&&、||、!）；2) 提供字段别名和布尔简写功能；3) 支持分组查询和排序操作；4) 包含大小写敏感/不敏感选项。该库可通过npm或bun安装，适用于CLI工具等场景，能高效过滤JSON数据。项目采用MIT许可证，鼓励其他语言实现。

评论摘要
主要讨论点：[FilterQL 查询语言的设计、功能扩展及与其他技术的结合] 不同观点： • **ANTLR 语法支持** - [arnley] 提到基于 ANTLR 语法实现类似功能（如嵌套过滤），并推荐了 Bouygues Telecom 的开源实现。 - 论据：轻量级且功能完备，可直接复用现有工具链。 • **语言独立性与 Lisp 风格提议** - [sandreas] 质疑为何缺乏通用标准，建议采用 Lisp 风格语法（如 `(OR (IN id (1 2 3))...)`）以实现简洁性和跨语言解析。 - 争议点：现有 DSL（如 FilterQL）是否优于 Lisp 式表达？后者可能更易解析但牺牲可读性。 • **MongoDB 风格 vs 简洁 DSL** - [nnnnico] 倾向 MongoDB 查询语法，认为其嵌套/数组操作更强大，但承认 FilterQL 对非技术人员更友好。 - 补充：提出是否支持嵌套值的疑问，暗示功能扩展需求。 • **极简主义与 Lisp 扩展** - [gritzko] 从自身需求出发设计极简查询语言，但考虑引入 Lisp 表达式支持。 - 讨论点：是否需要系统化总结现有查询语言（如 Datalog、GraphQL）的特性。 • **API 设计建议** - [drinkcocacola] 指出 API 命名与功能不匹配（如 `filter` 方法实际包含排序/分页），建议拆分方法或重命名为 `query`。 - 争议焦点：库的核心定位是单一过滤还是完整查询管道？ 补充讨论： - **功能扩展需求**：多位用户提到嵌套查询（[olivergregory]）、集合操作（[cdaringe]）、JSONSchema 支持（[MoyoGeorge]）等潜在方向。 - **替代方案质疑**：如 [h1fra] 认为直接使用类型安全查询构建器（如 Kysely）可能更高效，引发 DSL 必要性的讨论。 - **生态工具链**：[silicon_laser] 询问 Python 类似实现，反映跨语言适配需求。 - **文档认可**：[LtdJorge] 高度评价 README 的完整性，侧面强调文档对开源项目的重要性。

SDS: Simple Dynamic Strings library for C

作者: klaussilveira | 评分: 107 | 评论数: 6 | 发布时间: 2025-08-25 15:27
文章摘要

这篇文章介绍了SDS（Simple Dynamic Strings）——一个用于C语言的动态字符串库。SDS通过前缀头信息的设计优化了字符串处理，相比传统C字符串具有二进制安全、更高效率和兼容C字符串函数等优点。文章详细说明了SDS的工作原理、与常规字符串库的差异，以及其优缺点：虽然需要重新赋值修改后的字符串且共享字符串时需谨慎，但能直接兼容C字符串函数且支持高效字符访问。SDS最初用于Redis，现已成为独立项目，适合高性能场景。

评论摘要
主要讨论点：[Simple Dynamic Strings (SDS) 库的设计选择和使用场景] 不同观点： • **const char* vs char* 的设计争议** - xenotux 认为 SDS 应使用 `const char*` 别名而非 `char*`，以避免因误用修改字符串的库函数（如 libc）而导致 SDS 元数据不一致。`const` 设计能在编译时提供警告，同时不影响合法用例（如 `printf`）。 - （未明确反对观点，但原设计选择 `char*` 可能出于历史兼容性或灵活性考虑） • **Redis 的后续开发状态** - antirez 指出 Redis 项目中包含更高级的 SDS 版本，暗示当前讨论的可能是旧版实现。 • **API 设计选择（sdscat vs stscat）** - aidenn0 提问为何选择返回新指针的 `sdscat(s,...)` 而非传递指针地址的 `stscat(&s,...)`，怀疑是否出于性能考虑。 - （未回复具体原因，可能涉及接口简洁性或历史因素） • **语言选择争议（C vs C++）** - zoddie 质疑为何不使用更现代的 C++（如 `std::string` 和 `string_view`），认为坚持使用 C 是“自虐”，并强调现代语言的记忆安全性和效率优势。 - （隐含争议点：C 的轻量级/可控性 vs C++ 的抽象安全性） 补充讨论： - dang 提供了过往相关讨论链接，显示 SDS 长期存在设计争议（如 2014 和 2019 年的讨论）。 - jgarzik 的简短评论“enums > defines”可能指向代码中宏定义的可维护性问题，但未展开。

文章摘要

Anthropic正在为Chrome浏览器测试Claude AI扩展程序，旨在让AI直接在浏览器中辅助用户工作，例如管理日程、填写表格等。目前该功能面向1000名高级用户试点，未来将逐步扩大范围。 由于AI在浏览器中运行存在安全风险，尤其是可能遭受"提示注入攻击"（恶意指令诱导AI执行危险操作），团队已实施多项防御措施： 1. 权限控制：用户可限制访问特定网站 2. 高风险操作需确认 3. 屏蔽高风险网站类别 4. 开发检测可疑指令的分类器 测试显示安全措施将攻击成功率从23.6%降至11.2%，但团队仍在完善防护系统。该试点项目旨在收集反馈，确保AI浏览器助手的安全性。

评论摘要
主要讨论点：[Claude for Chrome的安全隐患与浏览器代理技术的可靠性] 不同观点： • **安全风险担忧** - [dfabulich]指出Claude for Chrome存在"致命三要素"（访问私人数据、接触不可信内容、数据外泄能力），攻击者可利用这些漏洞窃取数据 - [biggestfan]和[rafram]强调即使有安全缓解措施，11%的攻击成功率仍过高 - [Yeroc]建议该扩展应仅限于隐身模式使用 • **技术局限性** - [parsabg]认为当前技术不成熟，网页信息密度太低，LLM处理DOM如同用汇编编程 - [aliljet]通过实践发现Claude在浏览器交互中容易失去上下文，特别是处理复杂元素（如单选按钮）时表现不佳 • **替代方案探讨** - [endymion-light]质疑浏览器代理的必要性，认为应直接使用API而非模拟人工操作 - [shardullavekar]提出"记录-重放"方案，通过HTML快照和确定性计划提高长期任务可靠性 • **社会影响争议** - [mrs6969]担忧AI泛滥导致网络内容失去意义，人类活动被AI取代 - [sfink]指出不良的网页可用性可能迫使人们使用不安全的自动化工具 补充讨论： • 实施案例： - [parsabg]分享了自己的BrowserBee扩展项目 - [shardullavekar]介绍其100x.bot的长期任务处理方法 • 行业影响： - [stusmall]惊讶于AI公司公开承认产品危险性 - [chatmasta]认为这将为安全行业带来新机遇 争议焦点：浏览器代理技术是否值得在现有安全风险下继续发展，以及AI自动化是否会导致网络生态恶化。
