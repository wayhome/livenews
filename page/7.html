Why we built yet another Postgres connection pooler

作者: levkk | 评分: 221 | 评论数: 21 | 发布时间: 2026-07-07 15:36
文章摘要

PgDog 是一个新的 Postgres 连接池代理工具。与 PgBouncer、RDS Proxy 等现有方案不同，PgDog 解决了连接池的"泄漏抽象"问题，让用户无需修改应用代码或放弃数据库特性。 **核心特性：** 1. **SET 命令支持** - 通过内置 SQL 解析器追踪每个客户端的连接状态，自动在服务器端恢复状态，确保会话变量（如 RLS 策略）正常工作 2. **LISTEN/NOTIFY 支持** - 在多个 PgDog 进程间代理发布订阅消息，保留事务语义 3. **多线程架构** - 基于 Rust 的 Tokio 运行时，充分利用多核 CPU，单进程可处理更多连接 PgDog 让 Postgres 原生特性在连接池环境下"开箱即用"，无需在扩展性和功能性之间做权衡。

评论摘要
主要讨论点：PostgreSQL 连接池工具 PgDog 的功能特性、技术优势和社区反馈 不同观点： • **技术实现赞赏派**：认可 PgDog 的技术特性，特别是 prepared statements 支持（弥补了 pgpool-II 的历史缺陷）、SET 实现的清晰性、以及 AGPL 开源许可的选择 • **协议层改进派**：kardianos 提出更根本的批评，认为问题在于 PostgreSQL 的 pgwire3 协议本身设计不佳，正在开发支持命名参数、多结果集、流式传输等功能的新协议 POC • **架构方向质疑派**：rastignack 认为连接池不应作为外部工具，而应在 PostgreSQL 上游实现线程池模型和内部调度器（如 MS SQL Server） • **PostgreSQL vs MySQL 争论**：ransom1538 质疑 PostgreSQL 的市场地位，指出 Slack、YouTube 等大规模公司采用 MySQL/Vitess 分片系统，认为 PostgreSQL "战争已输" 补充讨论： **安全性关注**：petters 对连接状态泄漏问题表示震惊，质疑这种设计是否普遍存在于 Postgres 连接池中 **功能需求**：用户关注分片/多租户动态配置能力、查询缓存功能、以及 NOTIFY 性能优化是否影响事务一致性等实际应用问题 **竞品比较**：讨论涉及 ProxySQL、pgpool-II、pgbouncer 等现有方案的优劣对比

Tenda firmware (multiple versions) contains hidden authentication backdoor

作者: miniBill | 评分: 177 | 评论数: 20 | 发布时间: 2026-07-08 00:08
文章摘要

多个版本的Tenda路由器固件存在严重的隐藏认证后门漏洞（CVE-2026-11405）。该后门位于Web管理界面的登录功能中，当正常密码验证失败后，系统会使用明文比较方式检查配置文件中存储的备用密码。攻击者使用任意用户名配合该后门密码即可绕过身份验证，获得完全管理员权限。 成功利用后，攻击者可完全控制设备，修改网络配置、禁用安全功能，进而威胁整个本地网络。目前厂商未响应协调，暂无补丁发布。建议用户禁用设备的远程管理功能，并限制本地网络访问以降低风险。 受影响的固件版本包括FH1201、W15E、AC10、AC5和AC6等多个型号。

评论摘要
主要讨论点：Tenda路由器存在硬编码后门密码（rzadmin/rzadmin），多个型号受影响，引发关于产品安全性、制造商责任和地缘政治信任的讨论。 不同观点： • **技术无能论**（chirsz, Havoc）：认为这是业余级别的安全漏洞，源于公司技术能力不足而非恶意后门。Tenda市场份额远低于TP-Link印证了其技术水平问题。 • **恶意后门论**（RetroTechie, matltc）：直接将其定性为中国公司故意植入后门，建议抛弃所有深圳制造的产品。 • **双重标准质疑**（HDBaseT, like_any_other）：讽刺性指出美国/以色列产品可能存在类似问题却不被追究，质疑为何制造商不受惩罚而安全研究者反被打击。 • **自力更生派**（drnick1）：选择用Linux和通用硬件自建路由器/防火墙以避免此类风险。 补充讨论：dhx进行了深入固件分析，发现新固件已加密难以审计，还在W18EV2型号中发现相同漏洞，并识别出可疑的云管理/远程调试功能和密码获取机制。fusslo担忧Tenda可能仅通过改密码敷衍了事。emsign强调网络设备漏洞的连锁影响范围。

l: A new runtime for k and q

作者: skruger | 评分: 164 | 评论数: 21 | 发布时间: 2026-07-07 18:08
文章摘要

l是k和q语言的新运行时引擎，核心创新是将**压缩向量作为执行单元**。 **主要特性：** - **完全兼容**：k4、q、qSQL代码无需改写即可运行 - **端到端压缩**：数据在存储、内存和传输中始终保持压缩，原语直接在压缩字节上执行，无需解码 - **透明优化**：自动选择SIMD、多线程或硬件加速（支持NEON、AVX-512、GPU/NPU），无需手动标注 - **显著提速**：基准测试显示2.35-3.57倍性能提升 **核心理念**：现代硬件的瓶颈是带宽而非计算力，通过减少数据移动实现加速。同样的语法和原语，在新引擎上自动获得更高性能。

评论摘要
**主要讨论点：** 关于新k/q语言运行时"L"的发布，核心讨论围绕其商业定位、开源性、以及与现有实现（特别是昂贵的kdb+）的关系。 **不同观点：** • **商业机会派**：认为这是了不起的成就，可以通过低于kx.com的价格获得商业成功，对不使用kdb+品牌表示疑惑，期待成为kdb+的经济替代方案 • **开源倡导派**：明确指出闭源对许多人是"非开端"，虽然承认APL/K家族常见专有许可，但更推崇开源实现如ktye.github.io • **技术务实派**：不在意网站质量（"vibecoded"），关注项目本身价值，认为k语言很迷人，欢迎新变体出现 • **性能质疑派**：要求提供与其他k解释器（Shakti、ngn、klong等）的完整性能对比，认为当前基准测试不充分 • **项目维护者**：强调目标是"完整生产数据库兼容性"，区别于其他优秀但功能有限的开源实现 **补充讨论：** 有人吐槽单字母命名泛滥，有人科普k/q是华尔街量化工具专为金融tick数据设计，也有人推荐类似项目如KlongPy。争议焦点在于闭源商业模式是否合理，以及网站质量是否影响项目评价。
