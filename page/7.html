文章摘要

文章主要讨论了关于使用长破折号（em-dashes）与AI写作之间的误解。有人认为文本中的长破折号是AI写作的标志，因此有人会特意删除它们以隐藏AI的痕迹。作者指出这种做法并不明智，因为长破折号是优秀写作和排版的常用工具，能够帮助读者更好地理解文本。删除长破折号可能导致句子变得平淡或不通顺。作者强调，AI使用长破折号是因为它从优秀的人类写作中学习，人们应该效仿而非刻意去除。好的排版可以提升阅读体验，而不应被对AI的偏见左右。

评论摘要
主要讨论点：对em dash（长破折号）的使用及其在书面语和口语中的效果的看法 不同观点： • neom认为em dash令人讨厌且迂腐，尤其是在朗读时，不清楚应该暂停多久，觉得用逗号会更清晰。他个人更喜欢逗号，而不是em dash。 • damhsa反驳neom的观点，认为短横线（有空格隔开）显然是标点符号，而不是连接词，认为neom的批评是没有道理的。 • mattl提供了一个背景信息，表示自己在加入FSF（自由软件基金会）之前也不使用em dash。FSF遵循《芝加哥手册》的风格，这可能解释了为什么他们会广泛使用em dash。 补充讨论： - 争议的焦点在于em dash在阅读和朗读时是否造成了不必要的困扰。neom觉得它带来了不确定性，尤其是在口语表达中，而damhsa则为em dash的用法进行辩护，认为其功能明确。 - mattl的评论提供了一种可能的解释，即不同组织或出版物可能有不同的风格指南，这影响了em dash的使用频率。 - 讨论中还隐含了对不同标点符号（em dash与逗号）在书面表达中的效果和偏好的个体差异。

评论摘要
主要讨论点：编程语言中对分派语句（dispatch statements）的编译时检查的重要性，特别是涉及和处理 sum types 的情况。 不同观点： • JonChesterfield 认为，详尽的编译时检查（特别是在分派语句中）是非常重要的，尤其是那些认为 sum types 奇怪且小众的语言通常缺乏这种检查。他强调了 sum types 在某些语言中的缺失是一个遗憾。 • gitroom 支持 JonChesterfield 的观点，并补充说，缺乏这些检查会让他们感到困扰，形容这种感觉像是“为什么让我悬而未决”。这表明对更严格编译时检查的渴望。 • swiftcoder 提出了 Elm 和 Rust 在这方面做得很好，暗示这两个语言在处理 sum types 和编译时检查方面是值得借鉴的例子。这提供了一个正面的例子，表明有些现代语言已经开始重视并实现了这种检查机制。 补充讨论： • 争议的焦点似乎在于，某些流行语言在处理 sum types 和编译时检查方面的不足，而一些用户明确表达了对更严格类型检查的需求和偏好。 • 另一个讨论点是 Elm 和 Rust 作为成功案例，展示了如何有效地实现这些检查，满足了像 JonChesterfield 和 gitroom 这样的开发者需求。 • 整体讨论反映了对语言设计中类型安全和错误预防的关注，特别是如何在编译时捕捉潜在错误以提高代码可靠性。
