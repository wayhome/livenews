文章摘要

文章讨论了在Ruby中使用异步编程来处理大型语言模型（LLM）应用的优势。作者Carmine Paolino对比了Ruby和Python在异步编程上的发展，指出Ruby的异步模型在应对LLM应用的独特需求（如长时间连接和逐字响应）上更加高效。传统基于线程的并发模型（如SolidQueue、Sidekiq）在处理大量并发对话时面临资源浪费和性能瓶颈，而Ruby的异步模型通过Fibers实现了更好的资源利用和性能提升。文章详细分析了线程与异步在调度和管理资源上的区别，强调Ruby的异步模型无需重写代码即可提升性能，是应对现代AI应用挑战的理想选择。

主要讨论点：Ruby的异步编程及其性能和实用性 不同观点： • [horsawlarway] 认为作者的宣传具有讽刺意味，因为示例中仍然包含类似 "async do" 和 "end.map(&:wait)" 的结构，削弱了其简洁性。此外，他认为使用像 pgbouncer 这样的工具可以有效解决数据库连接的问题，并且从性能角度来看，Ruby 并不是处理长期运行的 LLM 任务的最佳选择。他指出，如果追求速度和效率，Ruby 并不是首选语言。 • [hakunin] 赞赏作者的写作清晰，认为作者很好地传达了其思路。他支持 Ruby 的异步编程方式，认为 Ruby 库允许直接插入任意 Ruby 代码是其优点，而不必遵循特定的声明式函数调用。他批评了那些试图接管代码编写方式的库，并主张利用 Ruby 的灵活性来进行运行时类型检查等操作。 • [knowitnone] 对 Ruby 的性能提出质疑，认为如果性能是主要考虑因素，那么选择脚本语言如 Ruby 是不明智的，因为即使是微秒级的延迟也会累积成实际的延迟。 • [Alifatisk] 对 Ruby 异步的视角表示兴趣，并对 I/O 多路复用示例感到着迷，表明对 Ruby 异步实现的技术细节持有积极态度。 补充讨论： - 争议的焦点在于 Ruby 的异步编程是否真正简洁，以及其在性能要求较高的场景（如 LLM 任务）中的适用性。 - 讨论还涉及 Ruby 与其他语言（如 Python）在生态系统和性能上的比较，以及使用中间件（如 pgbouncer）是否能有效缓解 Ruby 的性能问题。 - 部分评论者（如 hakunin）强调了 Ruby 的灵活性和其在代码表达方面的独特优势，认为这是 Ruby 的核心价值所在。

The jank programming language

作者: akkad33 | 评分: 401 | 评论数: 19 | 发布时间: 2025-07-06 16:56
文章摘要

Jank是一种通用的编程语言，兼容Clojure，但通过C++和LLVM-based JIT实现，支持原生编译和最小运行时。它提供REPL开发环境，同时能够进行静态AOT编译生成原生可执行文件。Jank允许在Clojure代码中无缝嵌入C++代码，并支持多线程软件事务内存和反应代理系统。其编译器启动快、内存使用低，并提供高质量的错误报告。Jank还与Clojure生态工具（如Leiningen和nREPL）兼容，支持在同一文件中混合编写C++和Clojure代码。例子展示了如何利用Clojure强大的数据处理能力生成电影索引和转换字节大小为可读格式。

评论摘要
主要讨论点：围绕新语言Jank的开发、设计选择、名称、工具及其与Clojure的关系等的讨论。 不同观点： • Jeaye（Jank的创建者）认为Jank通过LLVM和C++互操作性实现了独特的功能，如JIT编译和无缝的C++集成，且保留了Clojure的核心特性如nREPL。他计划在年底发布第一个alpha版本，并定期更新开发进展。 • Densh基于其在Scala Native上的经验，提出几点建议：避免提供向后兼容的JVM API子集，避免自己实现GC而是使用mmtk，重视多线程和并发，以及不过度优化单线程性能。 • Catfacts提到另一个类似的项目Clapp（Common Lisp在C++中使用LLVM），并指出Clapp的进展缓慢和编译时间长的问题。他对Jank能否避免类似问题表示关注，并建议从其他类似项目如ECL和Julia中吸取经验。 • Lisbbb对如何通过这些小众语言谋生表示疑问，回忆起Clojure在过去十几年的低迷，并对2025年还能看到Clojure或LISP的复兴表示惊讶。 • Mgdev表达了对项目的喜爱，但建议更改名称，以避免因名称问题在工作中受到限制。 • Norir建议采用一个更小的自举子集来简化设计，并通过C编译器和共享库实现REPL功能，认为当前的设计可能会导致不必要的复杂性。 • Lewdwig对Clojure曾经的辉煌和后来的停滞表示感慨，并希望Jank能为其带来新的活力。 • Jhoechtl提到与Janet语言的相关性。 • Padjo对Jank作为一个真实语言而不是一个深奥或玩笑语言表示惊讶。 • Lyngbakr关注Jank的工具链，希望其工具能像Gleam一样开箱即用。 • Defo10对Jank的错误报告功能表示期待，并希望看到与JVM的性能对比基准。 • Sideeffffect关心跨平台的Clojure库是否能在Jank中直接使用，以及需要做的调整。 • Jankjankjank幽默地表示感觉自己已经在写Jank代码了。 • Axblount质疑除了缺少JVM外，还有什么因素阻碍Jank成为Clojure的替代品。 补充讨论： • 争议的焦点之一是Jank是否应该提供向后兼容的JVM API子集，以及如何平衡新功能和复杂性。 • 另一个关注点是编译时间和性能优化，特别是与Clapp等类似项目的比较。 • 多线程和并发支持被认为是设计初期需要重视的问题，以避免后期改造的困难。 • 工具链和错误报告功能也被多次提及，显示出社区对这些方面的重视。 • 名称问题虽然是一个小问题，但在实际应用中可能会影响项目的接受度。

Helm local code execution via a malicious chart

作者: irke882 | 评分: 166 | 评论数: 12 | 发布时间: 2025-07-09 05:49
文章摘要

文章主要介绍了Helm中的一个高危安全漏洞（CVE-2025-53547）。在Helm版本≤3.18.3中，恶意构造的`Chart.yaml`文件和符号链接的`Chart.lock`文件可能导致本地代码执行。当用户运行`helm dependency update`时，某些字段会被带入`Chart.lock`文件，如果该文件被符号链接到可执行文件（如`bash.rc`或shell脚本），可能导致 unwanted 的代码执行。此问题已在Helm v3.18.4中修复。作为临时解决方案，用户应确保`Chart.lock`文件不是符号链接。漏洞的CVSS评分为8.5，属于高危级别。

评论摘要
主要讨论点：Helm图表依赖更新过程中存在的安全漏洞及其潜在的攻击向量和影响 不同观点： • [yelirekim] 详细解释了漏洞的工作原理：攻击者通过恶意构造Chart.yaml文件和符号链接（symlink）指向敏感文件，当执行`helm dependency update`时，Helm会跟随符号链接，将恶意代码写入目标文件，导致代码执行。该观点强调了Helm未验证目标文件的问题。 • [ivan4th] 对Helm整体设计提出批评，尤其是使用文本模板引擎生成YAML的机制，认为这是问题的根源。该评论更像是一种对Helm使用体验的抱怨，而非直接针对漏洞本身。 • [codebastard] 质疑攻击的实际可行性，指出攻击者需要文件系统访问权限和Helm仓库的访问权限。如果攻击者已经具备这些权限，是否还存在更大的安全隐患？该观点认为漏洞的危险性被夸大。 • [TheDong] 对漏洞描述的清晰度提出质疑，特别是关于`Chart.lock`如何成为符号链接以及为何修复只针对`Chart.lock`。该评论建议修复方案应为禁止图表包含指向根目录之外的符号链接。 • [Sjoerd] 关注攻击场景和安全边界问题，询问攻击者如何将恶意仓库传递给受害者以及Helm通常是否以特权用户身份运行。该观点认为漏洞描述缺乏对这些关键问题的解答。 • [mkagenius] 提到类似工具（如aider、claude desktop）要求shell访问权限的风险，认为允许LLM通过shell执行生成图表是一个不好的做法。 • [xyst] 认为该漏洞很有趣，并提到自己通过Nix管理配置文件，从而能够检测到恶意写入尝试。建议使用只读分区和“诱饵”文件来防御此类攻击。 • [quotemstr] 讽刺地提到内存安全语言中不应出现安全漏洞，暗示对漏洞存在的惊讶。 • [sugarpimpdorsey] 批评YAML格式本身，认为其设计有问题，并预测这不会是YAML相关的最后一个远程代码执行（RCE）漏洞。 • [qxfys] 好奇此类漏洞是否可以通过LLM自动发现，询问其他人的经验。 补充讨论： • 争议焦点在于漏洞的实际危险性和攻击的可行性。部分评论认为攻击者需要过多的权限，漏洞的威胁被夸大，而其他人则关注漏洞的根本原因和修复方案。 • 对YAML格式本身的批评以及对Helm设计的不满也是讨论中的一个分支，显示出部分用户对现有工具链的深层次不满。 • 最后，关于LLM是否能够自动发现此类漏洞的讨论，表明了对人工智能技术在安全领域应用的潜在兴趣和探索。
