Adding keyword parameters to Tcl procs

作者: BoingBoomTschak | 评分: 45 | 评论数: 5 | 发布时间: 2025-04-21 16:55
文章摘要

这篇文章介绍了在Tcl语言中为`proc`（过程）添加关键字参数（keyword parameters）的功能。作者对某些编程语言缺乏关键字参数以及未向用户提供内置功能感到不满，因此通过几小时的工作，实现了在Tcl中支持关键字参数的方案。文章展示了如何通过包装`proc`来实现这一功能，并给出了具体代码示例，如使用`proc*`定义支持关键字参数的过程，并演示了不同调用方式的结果。此外，作者还比较了使用关键字参数与传统位置参数的性能开销，显示该方法在保持灵活性的同时，性能影响较小。文章最后提到，这种实现借鉴了Tcl中通过强制位置参数来区分选项的特性。

评论摘要
主要讨论点：Tcl语言中关于添加命名参数功能的讨论和不同实现方案 不同观点： • jrapdx3 支持使用自己的 nxproc 扩展来实现 Tcl 中的命名参数功能。他认为 nxproc 提供了全面的功能，包括命名参数、位置参数、'rest'参数，以及类型检查等特性。他还提到 nxproc 支持 TclOO（Tcl 对象导向编程），并且提供了跨平台的二进制文件。 • blacksqr 则建议将 OpenACS 工具包中的 ad_proc 过程变成 Tcl 的内置命令。他认为 ad_proc 提供了添加开关、内联文档等实用功能，对 Tcl 开发很有帮助。 • tracnar 提到自己曾经实现过类似的功能，并认为不需要特别的 "quasiquote" 函数，使用 [list {*}$args] 和换行符就能解决问题。他还分享了自己进一步实现的 "pyproc"，可以通过调用 Python 来模拟 Tcl 过程。 • RicoElectrico 提到 Synopsys 工具中通过在值后面跟随名字的方式实现命名参数，例如 `measureFoo $signal threshold 0.9 edge last`。 • andrewshadura 对 Tcl 进行了简要的赞扬，认为 Tcl 作为一种简单、逻辑、一致的 shell 语言，已经做得很好，暗示可能不需要额外的复杂功能。 补充讨论： • jrapdx3 和 blacksqr 提供了不同的扩展方案，分别代表了外部扩展（nxproc）和内置命令（ad_proc）两种不同的实现路径。 • tracnar 的观点更多是技术实现上的细节分享，提供了对命名参数实现的一种不同思路，同时也展示了与 Python 的交互。 • RicoElectrico 提供的例子展示了其他工具中命名参数的实现方式，为讨论提供了一个参考。 • andrewshadura 的评论相对简单，但代表了一种对 Tcl 现状的肯定态度，可能暗示反对过度复杂化。 争议的焦点：是否需要将命名参数功能内置于 Tcl 中，以及哪种实现方式（外部扩展或内置命令）更为合适。

Local LLM inference – impressive but too hard to work with

文章摘要

本文讨论了本地运行大语言模型（LLM）推理的潜力和挑战。作者在开发文本到SQL产品的过程中，研究了是否能将生成型BI堆栈集成到浏览器中，从而深入探索了本地推理。尽管通过开源软件，普通笔记本电脑现在可以在浏览器中免费运行强大的LLM，但本地推理尚未完全准备好作为开发者平台用于生产环境。 本地计算的优势包括成本低、隐私保护、速度快和支持离线使用。虽然iPhone面部解锁等应用已经证明了本地推理的可行性，但在软件开发中广泛采用仍面临模型选择和部署的困难。当前的本地推理框架如llama.cpp、Ollama和WebLLM在性能上各有优劣，但均不及云端解决方案。此外，小型模型的下载和加载时间较长，影响了用户体验。 作者认为，本地LLM推理技术已具备一定基础，但开发工具尚需成熟，才能在实际应用中广泛使用。未来需要简化模型训练和部署，并实现与云端LLM的无缝集成。

Pipelining might be my favorite programming language feature

作者: Mond_ | 评分: 356 | 评论数: 70 | 发布时间: 2025-04-21 12:16
文章摘要

本文讨论了编程中的"管道化"（pipelining）或"方法链式"编程风格的优势，特别对比了通过点操作符实现的链式调用与传统嵌套函数调用的可读性和编辑便利性。作者认为，管道化风格更直观、易读，因为每个操作按顺序逐行书写，无需引入多余变量或过度嵌套。例如，使用迭代器方法的链式调用比将所有函数嵌套在一起更清晰。此外，作者指出，这种风格不仅限于编程语言的功能特性，还涉及到代码的可读性和编辑便利性。尽管承认语法不如语义重要，但作者仍主张在适当情况下采用管道化风格以提升代码可读性。

评论摘要
主要讨论点：编程中的"pipelining"（流水线）与"method chaining"（方法链）等技术及其优缺点 不同观点： • **"Pipelining" vs "Method Chaining"**： - **invalidator** 认为作者混淆了"pipelining"和"method chaining"。他指出，像Bash中的流水线操作可以并行执行，而Ruby中的方法链是顺序执行的，且每次操作会生成完整的数组，不利于调试。 - **davemp** 也认为术语使用不当，"pipelining"应指代某种并行操作，而方法链应称为"composition chain"。 • **对Pipelining的喜好与实用性**： - **bnchrch** 喜欢Elixir的`|>`语法，认为这种流水线操作很直观。 - **amai** 指出，虽然Pipelining看起来简洁，但在调试和异常处理时很困难，尤其在处理"happy path"以外的情况时。 - **epolanski** 和 **kordlessagain** 提到，虽然pipelining有其优势，但实际在代码库中，命令式编程往往更易于调试和维护。 • **其他语言的实现与扩展**： - **Straw** 提到Lisp宏可以解决链式调用问题，并提供了Clojure的线程宏作为例子。 - **duped** 认为流水线操作本质上是部分应用（partial application）的受限形式，并希望非Haskell语言能更早引入部分应用。 - **SimonDorfman** 提到R语言的tidyverse包中也有类似的管道操作。 - **bjourne** 介绍了Factor这种基于栈的语言如何实现严格的左关联评估，认为这种方法比其他语言的"pipelining"更直观。 - **andyferris** 建议在语句块中引入隐式引用上一个值的符号，类似MATLAB或Julia中的`ans`。 • **对流水线操作的争议**： - **rocqua** 认为函数的左关联性与英语阅读习惯不符，建议使用逆波兰表示法，但承认这种改变的成本太高。 - **vitus** 认为SQL中的流水线操作解决了执行顺序与查询顺序不一致的问题，是一种进步。 - **osigurdson** 提到C#早在17年前就有类似的Linq语法。 补充讨论： • **术语和定义的模糊性**： - **kordlessagain** 指出文章中对"pipelining"的定义不断变化，涉及方法链、操作符重载和一等函数等不同概念，导致理解困难。 • **社区实践与反馈**： - **epolanski** 提到effect-ts社区在实践中更倾向于使用命令式生成器而非pipeline，认为这更易于调试和维护。 - **singularity2001** 曾尝试说服Julia作者采用类似Nim的语言特性，但未被接受。 总体来看，讨论主要围绕pipelining和method chaining的定义、实际应用中的优缺点以及不同编程语言中的实现方式展开。调试难度、术语混淆和语法偏好是争议的焦点。

Python’s new t-strings

作者: tambourine_man | 评分: 572 | 评论数: 44 | 发布时间: 2025-04-21 04:31
文章摘要

Python 3.14将引入t-strings（模板字符串），以提供更安全和灵活的字符串处理方式。t-strings是f-strings的泛化，f-strings虽然简洁强大，但常被误用于处理包含用户输入的字符串，导致安全问题（如SQL注入和跨站脚本攻击）。t-strings通过`string.templatelib.Template`类型实现，必须在处理后才能生成最终字符串，从而避免上述安全问题。t-strings还支持更灵活的处理，例如安全地处理HTML和SQL。开发者可以通过访问模板的字符串片段和插值值来自定义处理逻辑，如将内容转换为Pig Latin。t-strings的引入将提升Python在字符串处理方面的安全性和灵活性，并有望得到广泛应用和工具支持。

评论摘要
主要讨论点：Python 的新 t-strings 语言特性及其潜在影响 不同观点： • [支持观点] [serbuvlad] 认为 t-strings 提供了语法糖，简化了 SQL 查询等场景的代码编写，有助于库开发者创造性地使用 {} 扩展。此外，这种模板语法在全语言范围内的一致性是有益的。 • [工具支持关注] [florbnit] 关注 t-strings 在工具链（如 black、ruff 格式化工具、VSCode 高亮）中的支持情况，并指出当前设计中没有明确指示模板字符串内容的类型或其最终转换形式，可能导致误解。 • [简洁性担忧] [nu11ptr] 认为 Python 正在变得越来越复杂，像 Go 那样拒绝不必要功能的简洁设计可能更值得借鉴。对于新手来说，Python 可能已经不再像过去那样简单易学。 • [库实现观点] [sashank_1509] 质疑 t-strings 是否需要成为语言特性，认为这可以通过库实现，无需增加语言的复杂性。 • [安全性考虑] [mounir9912] 质疑 t-strings 在防止忘记字符串操作（如 HTML 转义）上的作用，认为现有的 f-strings 已经可以通过手动操作达到相同效果。 补充讨论： • [实际应用] [TekMol] 展示了 t-strings 在 SQL 查询中的潜在应用，认为这种用法非常简洁优雅，提升了代码可读性。 • [与其他语言特性对比] [nikisweeting] 希望 Python 引入类似 JavaScript 的解构功能，并指出当前 Python 在特性丰富性上仍有不足。 • [多样化字符串格式化] [metrognome] 调侃 Python 在字符串格式化上已经有太多方式（t-strings, f-strings, %-operator, +-operator, str.format()），可能导致初学者困惑。 • [自定义扩展] [runekaagaard] 希望 t-strings 可以像 import 一样由用户自定义前缀，而不是仅限于内置实现。 • [国际化问题] [fph] 关注 t-strings 在国际化（i18n）场景下的应用，询问是否可以加载翻译后的 t-strings，并包含变量和 lambda 表达式。 • [实现示例] [pauleveritt] 提供了一个 t-strings 在 SQL 相关库中的应用示例，展示了该特性的实际使用价值。 争议焦点： • t-strings 是否值得作为语言特性引入，支持者认为其提供了简洁的语法糖，而反对者则担心 Python 因此变得过于复杂，且某些功能可以通过库实现而非语言核心支持。
