Mounting git commits as folders with NFS (2023)

作者: pvtmert | 评分: 104 | 评论数: 18 | 发布时间: 2026-05-19 07:32
文章摘要

这篇文章介绍了作者开发的 git-commit-folders 项目，它将 Git 仓库挂载为文件系统，每个提交都显示为一个文件夹。作者希望通过这种方式帮助人们直观理解 Git 的工作原理——提交本质上就像包含目录列表的文件夹。 项目支持 FUSE 和 NFS 两种挂载方式（避免了 Mac 上 FUSE 需要内核扩展的麻烦）。在这个文件系统中，分支和标签都是指向提交文件夹的符号链接，反映了 Git 的底层实现。 实际用途包括：搜索已删除的函数、快速查看其他分支的文件、跨分支搜索代码等。虽然这些操作用 Git 命令也能完成，但文件系统导航对作者来说更直观易用。

评论摘要
主要讨论点：将Git仓库通过FUSE挂载为文件系统的技术实现与实用性 不同观点： • **技术实现路径**：有人建议在Mac上用VM运行FUSE再通过NFS导出以规避内核扩展问题，但会带来性能损耗；有人推荐使用FSKit作为Mac原生方案替代WebDAV/NFS • **心智模型争议**：有人认为将commits作为文件夹不合适，因为在commit中删除/添加文件会创建新commit，这与文件系统操作逻辑冲突；有人建议用Jujutsu的changes替代，因其在rebase时更稳定 • **实用性评价**：部分人认为这是"cursed but useful"的有趣实现，会立即使用；也有人质疑实用性，认为传统git命令（如git show、git log -S）更高效，只是语法难记 • **技术细节优化**：有人指出tree/blob ID本身已是哈希值，无需再次哈希来生成inode，直接取前8字节即可 补充讨论：评论中提到Fossil和ClearCase等版本控制系统已有类似功能；有人认为随着LLM和AI编程的发展，这种跨commit文件比较方式值得重新审视；作者因此项目还为Git贡献了文档改进。

News outlets are limiting the Internet Archive’s access to their journalism

作者: jaredwiener | 评分: 167 | 评论数: 27 | 发布时间: 2026-05-21 16:59
文章摘要

超过340家美国地方新闻网站正在限制互联网档案馆（Internet Archive）访问其新闻内容。这些网站主要属于McClatchy、Advance Local、Tribune Publishing等大型报业集团。出版商担心AI公司可能从档案馆的Wayback Machine抓取内容用于训练数据。这一限制影响了研究人员、历史学家和记者的工作，他们依赖这些档案进行研究和报道。尽管互联网档案馆强调其采取了防滥用措施，但随着新闻业利润率下降，出版商更加重视保护知识产权，这场关于信息自由与版权保护的争议仍在持续。

评论摘要
主要讨论点：新闻网站限制互联网档案馆访问的利弊权衡 不同观点： • **支持限制访问派**：新闻机构需要保护知识产权以维持盈利，广告模式崩溃后付费墙是必然选择。当利润空间收窄时，防止免费获取内容变得更重要。认为应通过延迟开放（如一周后）来平衡商业需求和档案价值。 • **反对限制访问派**：历史项目研究者强调档案馆对挖掘已消失网站的重要性，担心50年后大量内容永久丢失。指出本地实体档案虽存在但不如在线访问便利，且部分档案已因收购等原因消失。 • **技术批评派**：认为新闻网站应优化技术而非限制访问，批评40MB臃肿JS和广告泛滥。建议采用文字免费、图片付费的模式降低带宽成本。 • **历史篡改担忧派**：警告失去原始历史记录可能导致AI辅助改写档案以符合当权者叙事，类似"历史由胜利者书写"演变为"历史被当前胜利者改写"。已观察到旧书新版删除争议内容的现象。 • **商业模式怀疑派**：质疑绕过付费墙的用户本就不会付费订阅，阻止访问不会带来增量收入。认为PE公司控制的新闻业只追求利润最大化而非延续存在，产品质量已让位于收益生成。 补充讨论：有人提议建立微支付系统让AI公司为访问内容付费；也有人建议新闻机构与档案馆协商延迟发布协议，在内容变旧后开放访问。

评论摘要
主要讨论点：VSCode扩展和开发工具的安全漏洞问题，由GitHub内部仓库被未授权访问事件引发 不同观点： • **安全模型缺失派**：VSCode扩展缺乏权限系统和沙箱机制是根本问题。扩展默认拥有文件系统、token和环境变量的完全访问权限，这种"ambient access"模式极其危险。建议Microsoft优先实现沙箱功能和显式权限系统 • **供应链风险派**：现代开发环境从IDE、包管理器到构建流水线都在拉取大量未经审计的代码，攻击面巨大。开发者安装扩展过于随意，很难区分官方扩展和恶意扩展，即使是百万级下载量的扩展也可能被攻陷 • **操作系统层面派**：问题不仅在应用层，操作系统本身的安全模型就有缺陷。应用默认能访问所有文件和网络是不合理的，需要从OS层面进行根本性改变。Linux上的沙箱实现尤其困难（如Electron的SUID问题） • **实用主义派**：部分开发者转向Zed等使用WASM扩展和dev-container隔离的替代方案，或只安装官方扩展，或将MCP服务器改为本地脚本而非npm包以控制访问范围 补充讨论：此次攻击链为Tanstack → Nx Console → GitHub，暴露出密钥轮换的困难性。即使发现风险，全面轮换所有密钥也是巨大工程，容易遗漏。

FatGid: FreeBSD 14.x kernel local privilege escalation

作者: WhyNotHugo | 评分: 98 | 评论数: 6 | 发布时间: 2026-05-21 12:15
文章摘要

这是一份关于 FreeBSD 14.x 内核本地提权漏洞（CVE-2026-45250）的技术报告。漏洞存在于 `setcred(2)` 系统调用中，由于 `sizeof` 类型错误导致内核栈缓冲区溢出。任何非特权本地用户都可在权限检查前触发该漏洞，实现从内核崩溃到完全提权的攻击。研究者开发了针对启用 SMAP/SMEP 保护的 amd64 GENERIC 内核的工作利用链（仅需加载 zfs.ko）。该漏洞在 2025 年 11 月已在主分支静默修复，但未回溯到稳定版本，FreeBSD 14.4-RELEASE 仍受影响。

评论摘要
主要讨论点：关于某个BSD系统安全漏洞的披露方式和影响范围 不同观点： • **质疑披露形式**：认为一个本地提权漏洞(LPE)不值得专门建立网站和命名，过度营销化 • **关注实际影响**：指出FreeBSD被广泛应用于TrueNAS和网络设备中,漏洞影响范围比想象中更大 • **对OpenBSD安全性好奇**：想测试LLM能否在以严谨开发著称的OpenBSD中发现问题,并非质疑其质量 • **补丁状态存疑**：质疑网站信息准确性,称官方已在昨天发布14.4版本的修复通知 补充讨论：评论反映了安全社区对漏洞披露方式的不同态度——既有对过度包装的反感,也有对实际影响的务实关注,同时存在对信息准确性和时效性的质疑。
