Posit floating point numbers: thin triangles and other tricks (2019)

作者: fanf2 | 评分: 39 | 评论数: 10 | 发布时间: 2025-06-19 14:42
文章摘要

本文讨论了使用两种不同的32位数字格式——IEEE binary32（单精度浮点数）和posits（es=2）——来计算一个薄三角形的面积，并展示了它们在精度上的差异。作者通过一个具体的计算示例，比较了这两种格式在处理浮点运算时的表现。结果显示，posits在精度上优于binary32，尤其是在处理边界条件时。作者认为，posits提供了一种更为精确且适应现代计算需求的替代方案。文章还提到，虽然binary32可以表示非常大的数，但在实际计算中精度较差，而posits在保持较大表示范围的同时提供了更高的精度。最后，作者通过几个不同的数值示例进一步展示了这两种格式的差异。

评论摘要
主要讨论点：Posit数值表示格式的优缺点及其在不同应用场景中的适用性 不同观点： • **dnautics（Posit的创造者之一）**： - Posit在科学计算中不太适合，因为误差传播难以解决。Posit更多是为低位数表示设计的，适用于不太关心误差传播的机器学习（ML）应用。 - 提到Posit的一个变体——valids，可以追踪误差，但需要算法上的转变。 - 实际硬件实现中，Posit的加法操作占用更多空间，且现有GPU管道更容易处理定量化整数操作。 • **mserdarsanli**： - 通过构建交互工具展示了Posit和IEEE浮点数之间的权衡。认为Posit在接近1的数值上有更好的精度表现，但理解起来较为困难。 • **phkahler**： - 对Posit的兴趣不在精度，而在于没有符号零和NaN（非数字）。希望运算结果始终是最接近的可表示值，而不是非数字的结果。 • **adrian_b**： - 认为展示Posit精度优于IEEE FP32的例子具有误导性。Posit和IEEE浮点数能表示的数值数量是相同的，只是分布不同。 - Posit在靠近零的区间有较好的精度，但在远离零的区间误差较大，类似于固定点格式。 - 由于Posit的相对误差是操作数数值的函数，难以预估误差，因此在科学计算中不太实用。 - 只有在非常特定的、已知数据范围的问题中，Posit才可能比IEEE FP32有显著优势，且需要硬件实现才能有好的性能。 • **im3w1l**： - 提出纯指数格式的可能性，如s * 2 ^ (e / C)，认为这种格式可以保留一些特殊情况（如0，±inf，NaN）。 补充讨论： • **burnt-resistor**： - 提供了一个类似IEEE的格式速查表，展示了不同数值表示的实现。 • **antiquark**： - 提到Posit与"type III unum"有关，提供了维基百科链接供进一步了解。 • **andrepd**： - 对Posit及IEEE浮点数替代方案感兴趣，认为讨论中提供了许多有见地的观点。 争议焦点： • Posit在科学计算中的适用性及其相对于IEEE浮点数的实际优势。adrian_b和dnautics认为Posit在科学计算中不太实用，而其他评论者则指出在特定场景下Posit可能有优势。 • Posit精度示例的代表性问题。adrian_b认为展示Posit精度的例子是经过挑选的，不具普遍性。 这些讨论揭示了Posit在不同应用场景中的潜力和挑战，并强调了在选择数值表示格式时需要权衡的多个因素。

Show HN: Unregistry – “docker push” directly to servers without a registry

作者: psviderski | 评分: 646 | 评论数: 52 | 发布时间: 2025-06-18 23:17
文章摘要

"Unregistry" 是一个轻量级工具，允许直接通过 SSH 将 Docker 镜像从本地推送到远程服务器，无需外部注册表。它通过创建临时容器来传输缺失的镜像层，从而实现快速高效的传输。相比于使用 Docker Hub 或自建注册表，"unregistry" 更简便，且避免了完整镜像重复传输的问题。它适用于 macOS、Linux，暂不支持 Windows。典型应用场景包括生产服务器部署、CI/CD 管道优化以及在隔离网络中分发镜像。

评论摘要
主要讨论点：Docker设计及其在容器部署中的改进建议 不同观点： • shykes（Docker创始人）认为理想的设计应将Docker引擎和Docker注册表合并为一个服务器，具备存储、传输和运行容器的能力，避免引擎和注册表在存储镜像上的差异。他还建议使用推送至集群的部署方式，以替代当前的推送镜像到注册表、配置集群、节点从注册表拉取镜像的脆弱和低效流程。 • richardc323提到曾在2015年尝试通过PR将此功能添加到Docker主线，但被引导到其他领域贡献，认为这可能是因为不需要注册表的设计对Docker的商业模式影响过大。 • nine_k赞赏`pussh`命令的命名，认为其易记且自明。 • alisonatwork认为此设计可以很好地与现有工具（如Ansible）集成，并提到其作为热修复部署机制的潜力。同时关注是否能与OCI工具（如buildah）无缝集成，或是否需要完整的Docker安装。 • metadat表示Docker注册表过于复杂，支持简化设计，认为其违背了黑客精神。 • lxe发现此讨论启发其寻找类似于dokku但更强大的解决方案，用于项目服务器设置。 • amne描述其复杂管道流程，认为此设计能简化其工作流。 • modeless认为Docker未默认采用这种设计是愚蠢的，对此设计表示赞赏。 • matt_kantor将其与自己写的docker-pushmi-pullyu进行比较，好奇为何psviderski要实现自己的注册表。 • revicon质疑此方法与使用远程Docker上下文的区别，描述其通过SSH管理远程服务器的简单方法，认为可能比Docker Swarm和Kubernetes更简单。 • scott113341自我托管Zot以替代昂贵的注册表服务，询问是否存在易配置、价格合理且基于使用的私有注册表服务。 • fellatio认为此设计可能将部署与服务耦合，提出扩展或红/绿部署的挑战，但随后发现uncloud项目解决了这些问题。 • actinium226和larsnystrom提到使用`docker save | ssh`的方法，认为传输仅改变的层是此设计的优势，但对他们而言，目前的方案已经足够。 • bradly提到当前使用Docker注册表进行Kamal部署，询问此设计是否能移除第三方依赖。 补充讨论： • 关于是否需要完整的Docker安装以及如何与现有OCI工具集成是部分用户关注的重点。 • 讨论中多次提到现有Docker设计中的复杂性和效率问题，用户对简化设计和降低成本的方案有明显兴趣。 • 不同的用户根据自身经验提出了多种替代方案和工具，如self-hosting Zot、使用远程Docker上下文和`docker save | ssh`方法等。 • 争议的焦点在于Docker设计是否应简化以及如何在不同场景中实现高效的容器部署。

PWM flicker: Invisible light that's harming our health?

作者: SLHamlet | 评分: 154 | 评论数: 47 | 发布时间: 2025-06-18 17:32
文章摘要

本文讨论了LED灯光因脉宽调制（PWM）引起的闪烁问题，以及这种闪烁如何导致不适，尤其是对部分敏感人群。作者在一个历史悠久的法国城堡中举办会议时发现，某些房间在LED灯光下感觉不舒服，尽管这些灯发出温暖的光。通过相机拍摄，作者观察到LED灯的快速闪烁，尽管人眼难以直接察觉，但这种闪烁可能引发眼疲劳、不适甚至偏头痛。PWM是一种控制灯光亮度的方法，通过快速开关灯光来实现调光，导致人眼无法察觉的闪烁。尽管多数人不受影响，但对敏感人群来说，这种闪烁可能造成不适。文章建议使用更先进的调光系统，以减少闪烁带来的负面影响。

评论摘要
主要讨论点：LED灯闪烁对人的影响及相关技术讨论 不同观点： • **LED闪烁对健康的影响**： - mtalantikite：LED闪烁引发眼部偏头痛，个人经历表明更换到LED后出现严重健康问题。 - loph：荧光灯和LED灯的闪烁会加重偏头痛，只能通过使用白炽灯缓解。 - hinterlands：承认PWM可能导致特定人群头痛，但认为这是调光技术中不可避免的问题。 • **LED与白炽灯的优劣对比**： - mtalantikite：不喜欢LED的过渡使用，认为户外LED过亮，影响生活质量。 - zzo38computer：认为LED灯太亮、颜色不对，更喜欢使用白炽灯或自然光。 - thePhytochemist：虽然客户担心闪烁，但LED在能耗、寿命和颜色选择上具有优势。 • **技术讨论：PWM与闪烁问题**： - hinterlands：解释LED调光通过PWM实现，虽然人眼无法直接感知高频PWM，但可能产生频闪效应。 - spiffyk：怀疑普通建筑中的灯具不会使用PWM，而是因为AC整流导致的闪烁。 - julik：指出要完全消除闪烁需要昂贵的设备和特殊的供电，普通LED使用PWM是为了降低成本。 - voidUpdate：能够察觉到低频PWM的闪烁，特别是在某些廉价灯具上。 • **汽车头灯与闪烁感知**： - shanemhansen：对现代汽车头灯的闪烁感到困惑，不确定是否是PWM引起。 - ajb：提出不同光源的PWM频率差异可能导致"拍频"现象，这会使闪烁更加明显。 • **市场与消费者选择**： - mdip：在更换家中的灯泡时发现很难找到不使用PWM的智能灯泡，且制造商很少提供PWM频率信息。 - orwin：认为讨论中涉及的健康风险类似“偏执狂”的担忧，但仍觉得讨论有趣。 - monster_truck：认为讨论类似于对WiFi辐射的偏执，但对某些人来说闪烁确实带来困扰。 补充讨论： - perching_aix：不关心健康风险，但反感因技术问题导致的闪烁现象，尤其是冰箱灯的闪烁。 - leakycap：新Apple设备的PWM调光使其眼睛不适，因此继续使用旧设备。 争议焦点：LED灯闪烁是否对健康有显著影响，以及是否存在有效的解决方案以消除闪烁对敏感人群的影响。

文章摘要

Makefile Style Guide

作者: leetrout | 评分: 32 | 评论数: 1 | 发布时间: 2025-06-20 12:14
文章摘要

本文介绍了使用GNU Make工具管理软件项目的结构和细节。一个项目目录包含源文件、版本控制和一个根目录的构建文件（build file），用于生成不在版本控制下的目标文件。构建文件不仅是自动化工具，还记录了项目的使用方法。选择合适的构建工具和文件格式很重要，其中GNU Make是一个广泛使用的工具。 Makefile通常分为四个部分：includes、prologue、environment variables、rules和targets。对于小项目，includes部分可以省略。prologue部分设置了一些默认行为和选项，如使用bash shell和pipefail选项，确保命令失败时整个管道失败。environment variables部分讨论了环境变量的声明和使用，强调所有环境变量应为大写，并建议使用条件赋值操作符`?=`。还提到如何处理未定义的环境变量以避免错误。最后，强调了清理和错误处理的重要性，如使用`.DELETE_ON_ERROR`删除失败目标，防止使用不完整的目标文件。

Glaze库通过`stencil`和`mustache`格式为C++结构体提供了字符串插值功能，允许将结构化数据格式化为字符串。其模板机制受Mustache模板语言启发，可以结合预定义模板和C++结构体生成动态输出。 ### 基本用法 定义结构体并使用模板进行插值，例如： ```cpp struct person { std::string first_name; std::string last_name; uint32_t age; bool hungry; bool employed; }; std::string_view layout = R"({{first_name}} {{last_name}} is {{age}} years old)"; person p{"Henry", "Foster", 34}; auto result = glz::stencil(layout, p); // 结果: "Henry Foster is 34 years old" ``` ### 模板语法 - **变量插值**: `{{key}}` 替换为结构体字段值，`{{{key}}}`为不转义输出（仅mustache格式）。 - **布尔节**: `{{#boolean_key}}`显示内容如果布尔值为true，`{{^boolean_key}}`为false时显示。 - **容器迭代**: `{{#container_key}}`迭代容器元素，`{{^container_key}}`容器为空时显示内容。 - **注释**: `{{! This is a comment}}`。 ### 示例 - **布尔节示例**: ```cpp std::string_view layout = R"({{first_name}} {{last_name}} {{#employed}}Status: Employed, Age: {{age}}{{/employed}})"; person p{"Carol", "Davis", 30, true, true}; auto result = glz::stencil(layout, p); // 结果: "Carol Davis Status: Employed, Age: 30" ``` - **容器迭代示例**: ```cpp struct TodoList { std::string title; std::vector items; bool has_items; }; std::string_view layout = R"({{title}}: {{#items}}{{text}} ({{priority}}) {{/items}})"; TodoList list{"My Tasks", {{"Buy milk", false, "normal", 1}, {"Call mom", true, "high", 2}}, true}; auto result = glz::stencil(layout, list); // 结果: "My Tasks: Buy milk (normal) Call mom (high) " ``` ### Mustache格式 `glz::mustache`与`glz::stencil`接口相同，但提供HTML转义： - 双括号 `{{key}}` 输出HTML转义内容。 - 三括号 `{{{key}}}` 输出原始HTML内容。 ### 错误处理 `stencil/mustache`函数返回`std::expected`，常见错误如引用不存在的字段。
