Decoding the obfuscated bash script on a Uniqlo t-shirt

作者: speerer | 评分: 1413 | 评论数: 80 | 发布时间: 2026-07-08 08:46
文章摘要

这篇文章讲述了作者在Uniqlo商店发现的一件特殊T恤。T恤背面印有一段经过混淆的bash脚本代码,这是CDN服务商Akamai为其"Peace for All"公益活动设计的复活节彩蛋。 脚本使用base64编码,作者通过OCR技术识别并解码了T恤上的完整代码。解码后发现这是一个精心设计的bash动画脚本,运行时会在终端中以正弦波动画形式显示"♥PEACE♥FOR♥ALL♥"的循环消息,使用渐变色彩(青色到橙色)。 脚本代码包含友好的注释(含中英日文祝贺语),体现了技术与艺术的创意结合。作者称赞这是一个非常酷的设计,将代码文化带入了日常服饰。

评论摘要
主要讨论点：Uniqlo x Akamai联名T恤上印有可执行bash脚本代码的真实性、可读性及其技术细节 不同观点： • **代码真实性验证**：部分用户起初怀疑T恤代码仅为装饰不可运行，但实际验证后发现确实可执行并输出有趣的ASCII动画效果 • **OCR识别难度争议**：多数认为该T恤故意设计成OCR困难（设计师视频确认为intentional），有人提出可用AI视觉模型分行识别；但有评论质疑为何不直接手打而要依赖OCR工具后再修复 • **排版技术问题**：专业观察指出使用Roboto Mono字体但排版非等宽（存在kerning），推测使用InDesign的optical kerning功能，这不符合代码显示规范 • **脚本优化建议**：建议在循环中添加`sleep 0.1`使终端输出更易读；指出非英语locale环境下decimal separator会导致部分功能崩溃，需设置`LC_NUMERIC=C` 补充讨论：评论中分享了相似作品（Quine Clock、Go程序T恤、DeCSS源码T恤），以及购买动机（"看起来像malware所以买了"）体现极客文化认同感

Chatto 是一款新推出的开源群组聊天应用,现已正式开源并支持自托管。 **核心特点:** - 轻量快速,界面紧凑流畅 - 极易自托管,运行单个可执行文件即可 - 资源占用低,前端响应迅速 - 数据隐私优先,个人和聊天数据完全加密存储 - 内置端到端加密的语音视频通话和屏幕共享功能 - 每个服务器对应单个社区,无第三方追踪 **部署方式:** - 免费自托管(支持 Linux/macOS/Windows) - 即将推出 Chatto Cloud 付费托管服务(欧洲基础设施) **当前状态:** 版本 0.4,预计 6-12 个月达到 1.0.0。可通过 Homebrew 快速安装试用。

**主要讨论点：** Chatto作为新的开源聊天应用的技术优势、市场定位和实际可行性 **不同观点：** • **技术架构派（积极）**：赞赏单一二进制文件、易于自托管、使用NATS和LiveKit等轻量级组件的设计哲学，认为这是"无聊软件"（boring software）的正确方向，降低了部署和调试门槛 • **市场怀疑派（批判）**：指出最核心的问题——网络效应。Slack/Discord的替代品面临的不是技术问题，而是用户已经在使用现有平台，供应商和同事都在那里。市场上已有数十个Discord替代品（Zulip、Element、Guilded等），Chatto缺乏明确的差异化定位和有效的营销材料 • **功能需求派（务实）**：关注具体可用性问题——移动端支持情况、端到端加密（目前只有静态加密）、服务器资源需求、与Zulip等成熟方案的对比、社区成员能否自由加入和搜索 • **开放标准倡导者**：认为真正的解决方案需要开放协议（类比电子邮件），而不是又一个封闭的替代品 **补充讨论：** 双重许可策略引发疑问（后端AGPL、前端Apache 2.0）；欧洲数据主权可能受chat control法规影响；Homebrew为主的安装方式限制了跨平台可访问性；开发者使用AI辅助编码完成项目引人注目

Rewriting Bun in Rust

文章摘要

这篇文章讲述了Bun运行时从Zig重写到Rust的原因。Bun最初用Zig开发,功能广泛(包含JS/TS转译器、打包工具、包管理器、测试运行器等),Zig让快速开发成为可能。但随着项目成长,出现大量内存安全问题——主要是use-after-free和内存泄漏等bug。核心矛盾在于JavaScript的垃圾回收机制与Zig的手动内存管理难以协调。尽管团队采用了ASAN、模糊测试等多种防护措施,这类bug仍频繁出现。作者认为需要更系统性的解决方案,而不是继续逐个修复bug,这促使团队决定重写到Rust以从根本上提升稳定性。

评论摘要
主要讨论点：Bun项目使用AI将50万行Zig代码重写为Rust，引发了关于AI辅助开发、语言选择和项目管理的多维度讨论 不同观点： • **AI能力肯定派**：认为这是技术突破，展示了人机协作的未来。11天完成本需一年的工作，强测试套件配合LLM验证是关键。预测Rust将成为AI编码时代的主流语言 • **成本质疑派**：指出$165k的token成本被忽略。若非Anthropic合作伙伴无法承担。质疑是否真比雇佣团队更经济，建议对比50人11天的人工重写成本 • **职业影响担忧派**：认为这标志着软件工程就业市场的重大变革。普通开发岗位将被AI取代，只有顶尖工程师（FAANG L6级别）能保住饭碗。预测美国160万软件开发者将大幅减少 • **Zig语言批评派**：重写修复内存泄漏、提高稳定性、缩小20%二进制体积、提升5%性能，这些对Zig不利。认为Zig过于冗长、缺乏抽象和现代特性，讽刺地说"Zig最适合由LLM编写" • **项目管理批评派**：不满Bun团队处理方式——无LTS支持、遗留3MB内存泄漏等重大bug、零社区沟通。负责人像运营个人项目而非成熟开源项目 • **重写经验派**：基于自身经验认为重写通常能改善质量。好奇纯Zig到Zig的同等规模重写会有何效果，质疑改进是否主要来自语言切换 • **LLM文风厌倦派**：批评博客明显由AI撰写，充斥"honestly""genuinely"等词汇却毫无真诚感。认为网络上独特声音被统一的AI文风取代，令人疲惫和失望 补充讨论：多人提到使用了内部Fable模型而非Opus，能力被低估。有人指出Claude Code自6月17日起已默默使用Rust版本。部分评论认为2026年仍不用内存安全语言难以理解

Unicode's transliteration rules are Turing-complete

作者: beefburger | 评分: 121 | 评论数: 20 | 发布时间: 2026-07-08 09:44
文章摘要

这篇文章证明了Unicode的UTS #35音译规则（transliteration rules）在理论上是图灵完备的。作者通过将2-tag系统（一种已被证明具有通用计算能力的模型）编译成音译规则来证明这一点。 音译规则使用模式匹配和替换语法（L { x } R > y），支持"重新访问"功能，允许将光标放置在新生成的文本中以触发后续规则。作者以Collatz函数为例，展示了如何用三条规则模拟2-tag系统的运算。 这意味着判断某个规则文件在给定输入上是否会终止是不可判定的。虽然ICU库实现了重写次数限制（每个码点最多16次）以防止无限循环，但规范本身并未定义这种限制。这些规则广泛应用于操作系统、浏览器和数据库的国际化处理中。

评论摘要
**主要讨论点：** Unicode转写规则（UTS #35 transliteration rules）被证明是图灵完备的 **不同观点：** • **实用性质疑派（SonOfLilit）：** 认为这个发现不够有趣，因为这只是供库实现者使用的内部DSL，规则作者本身就能运行任意代码，不会产生像"DNS解析图灵完备"那样的安全风险。设计者很可能知道它是图灵完备的，避免无限循环是规则作者的责任。 • **复杂性必然派（psidebot）：** 从Unicode需求角度解释，考虑到要处理全球7200种语言、双向文本、上下文塑形、连字等复杂特性，拥有图灵完备的格式选项反而不令人惊讶，这是灵活性需求的自然结果。 • **设计趋势观察（anankaie）：** 指出当前的趋势是确保格式不能计算反而比确保它能计算更困难，暗示图灵完备性已经成为常态。 • **安全担忧派（flenserboy）：** 从安全角度警告，向LLM开放的图灵完备系统可能成为安全漏洞。 **补充讨论：** 多位评论者分享了类似案例（Word自动更正、PowerPoint图灵机），显示"意外图灵完备"是一个普遍现象。有人询问实现细节和潜在的浏览器执行风险。
