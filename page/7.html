`deno desktop` 是 Deno 2.9 版本推出的新功能，可将 Deno 项目（从单个 TypeScript 文件到 Next.js 应用）打包成独立的桌面应用程序。主要特点包括：默认使用系统 WebView 保持体积小巧，完全兼容 Node 生态系统；自动检测并支持主流前端框架（Next.js、Astro、Remix 等）；使用进程内绑定而非 IPC 通信；支持从单台机器交叉编译到 macOS、Windows 和 Linux；内置二进制差分自动更新功能。开发者只需一行命令即可将 Web 应用转换为桌面应用，无需修改代码。

评论摘要
主要讨论点：Deno Desktop 作为跨平台桌面应用开发工具的优劣势，以及与 Tauri、Electron 等竞品的对比 不同观点： • **对 Deno Desktop 持积极态度**：认为 Deno 生态成熟，TypeScript 原生支持是优势，虽然包体积比 Tauri 大（40MB vs 5MB），但 150MB 的下载时间可接受，且渲染引擎更可靠 • **Tauri 仍有独特优势**：支持 sidecar 嵌入现有应用、可与 Elixir/BEAM 集成打包单一二进制文件，Livebook Desktop 等成功案例证明其成熟度；WebView 虽有局限但正在通过 CEF 改进 • **对 Web 技术作为 UI 工具的质疑**：批评 Electron 类应用无法遵循操作系统原生 UI 模式，Web 技术本质上不是真正的 UI 工具包，即使是未样式化的按钮也无法原生适配各操作系统 • **技术细节的讨论**：关于共享 CEF 运行时的版本管理问题、多进程模式下是否真的是共享内存还是 IPC、权限系统如何在编译时向用户展示等实现细节的疑问 补充讨论：有人指出文档将 electrobun 错误标注为仅支持 macOS（实际支持多平台）；有开发者更偏好原生 UI；还有人提到替代方案如 WASM 方案（Jumpjet）可不依赖浏览器引擎；Deno Desktop 的 canary 版本可通过压缩将应用体积降至 15MB

British Columbia, Time Zones, and Postgres

作者: sprawl_ | 评分: 130 | 评论数: 18 | 发布时间: 2026-06-22 19:21
文章摘要

本文讨论了2026年3月英属哥伦比亚永久采用夏令时(UTC-7)后，Postgres时区存储面临的问题。文章指出，使用timestamptz存储未来预约时间会因时区规则变更导致时间偏差——原本存储的10点预约，在tzdata更新后查询会显示为11点。 **解决方案**：采用"双列模式"存储： 1. local_time（本地时间戳） 2. timezone_name（IANA时区名） 3. starts_at_utc（计算得出的UTC时间） 这种模式适用于需要保留"本地意图"的未来事件（如预约、日历事件），而历史事件或以UTC为准的数据（日志、交易记录）仍应使用普通timestamptz。

评论摘要
主要讨论点：英属哥伦比亚省取消夏令时后，如何在数据库和软件系统中正确存储和处理时间数据 不同观点： • **未来事件存储本地时间+时区，历史事件用UTC**：未来预约（如医生预约）应存储事件发生地的本地时间和时区，因为即使时区规则改变，预约时间的本地意义不变（周一早上8:30仍是8:30）；历史事件则用UTC时间戳 • **只存储UTC时间戳**：数据库中只应存储UTC的Unix时间戳（本质是计数器，全球同一瞬间数值相同），所有时区转换交给经过充分测试的软件库处理，避免手动处理时区带来的风险 • **使用SQL标准类型DATE和TIME**：对于与地点绑定的预约，应使用ANSI SQL的DATE和TIME类型，时区转换应在表示层完成，不属于数据库层 • **双字段存储法**：文章建议的两列存储方法可行，但仍应依赖成熟的软件库处理 补充讨论： 多位评论者强调**必须使用tzdata等成熟库**，不要自己实现时区转换逻辑；有人指出本地时间存储在时钟回拨时会产生**歧义问题**（同一小时出现两次）；也有人认为这类时区变更极少发生，倾向于**事后快速修补数据**而非提前过度设计；BC省内部不同地区时区选择仍在争议中，增加了复杂性。

The new HTTP QUERY method explained

作者: CommonGuy | 评分: 163 | 评论数: 22 | 发布时间: 2026-06-23 06:05
文章摘要

HTTP新增了QUERY方法（RFC 10008）来解决复杂查询的问题。传统上，GET请求通过URL参数过滤数据，但复杂查询会导致URL过长、编码问题和结构表达困难。虽然GET理论上可以带请求体，但各种客户端和服务器实现不一致，可能导致兼容性问题。POST虽支持请求体，但语义上是非幂等的创建操作，不适合查询场景，也无法被缓存。QUERY方法填补了这一空白，它类似GET但支持请求体，被定义为安全和幂等的，可缓存。但目前支持有限，需要谨慎使用，简单查询仍应使用GET，需要分享链接的场景也不适合QUERY。

评论摘要
主要讨论点：HTTP QUERY 新方法的必要性及其与 GET 方法带 body 的争议 不同观点： • **支持 QUERY 方法**：GET 带 body 是 hack 行为，不符合规范，显式的 QUERY 方法更合理；解决了大规模 GET 请求的痛点，body 解析支持不统一的问题 • **反对 QUERY 方法**：应该直接标准化 GET 的 body 支持更简单；新增方法语义与现有方法不匹配，设计不够优雅；CoAP 已支持 GET body，新方法反而造成代理转换摩擦 • **实用性担忧**：企业防火墙和旧版浏览器可能长期不支持 QUERY；昂贵的 SSL 代理设备仅支持 HTTP/1.1，可能导致 DoS；HTTPS 加密导致 CDN 无法缓存 QUERY body，需重构互联网拓扑才能真正受益 补充讨论：有人质疑过度关注 HTTP 方法设计 RESTful 接口的做法，认为 RPC 场景下优先考虑可缓存性元信息不合理；也有人担心网站会用 QUERY 阻止链接分享；DELETE 方法也存在类似 body 支持问题但影响较小。

In praise of memcached

作者: j03b | 评分: 180 | 评论数: 20 | 发布时间: 2026-06-23 01:15
文章摘要

这篇文章对比了 Redis 和 memcached 作为缓存的使用场景。作者指出 Redis 虽然功能丰富，但常被误用为持久化数据库，导致运维负担加重。相比之下，memcached 更适合作为纯缓存使用：它不支持持久化，故障处理简单（客户端自动忽略连接异常），集群配置通过客户端哈希实现（无需服务端支持），可作为无状态服务部署。作者建议优先使用 memcached 作为缓存，并提醒在引入缓存前应先优化数据库查询和索引。

评论摘要
主要讨论点：Redis vs Memcached 在缓存场景下的选择争议 不同观点： • **Redis职责混乱派**（downsplat, kijin）：Redis试图同时做持久化存储和易失性缓存两件事，导致问题。建议缓存用Memcached，需要数据结构时才用Redis。需要严格配置（强制过期时间、分离数据库、设置内存上限）才能安全用作缓存。 • **Redis实用主义派**（kylewpppd, tempest_, AussieWog93）：虽然Redis有各种生产问题（内存溢出、AOF失败、数据被误当持久化），但Memcached的架构限制更大，大团队最终还是会引入Redis，不如一开始就用。Redis API设计优秀且稳定。 • **Memcached技术优势派**（nasretdinov）：Memcached所有操作都是O(1)，避免了Redis单线程架构下复杂操作导致的随机延迟，这是被忽视的关键优势。 • **中立/质疑派**（bawolff, jdw64, drchaim）：问题不在技术本身而在使用方式——把易失性缓存当持久化存储是配置错误。开源项目功能膨胀是必然趋势，没有绝对答案。质疑何时真正需要这些技术（PostgreSQL未必不够用）。 补充讨论：有人推荐替代方案（Aerospike、Valkey），有人指出Redis的范围查询能力是关键差异（TreeMap vs HashMap），还有人批评文章观点属于稻草人谬误。
