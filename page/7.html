arXiv moving from Cornell servers to Google Cloud

作者: ColinWright | 评分: 158 | 评论数: 32 | 发布时间: 2025-04-18 10:21
文章摘要

arXiv，作为康奈尔大学的一部分，正在招聘多个软件工程职位，包括普通软件工程师、DevOps专家和科学家/软件开发员。这些职位均为康奈尔大学员工，需具备在美国工作的合法权利，不提供签证 sponsorship。工作地点主要在纽约市的康奈尔科技校区，但也可能提供混合或远程工作选项。 当前，arXiv 正在进行将其服务迁移至谷歌云的“Cloud Edition”项目，旨在提升可扩展性和现代化基础设施。具体任务包括替换旧的Perl和PHP代码、实现异步处理、容器化服务、改进监控和日志系统，以及建立可靠的CI/CD管道。 招聘的职位要求具备多种编程语言和环境的经验，特别是Web开发和SQL。DevOps专家将专注于现代化开发运维体系，使用基础设施即代码原则和Google Cloud工具。科学家/软件开发员需有科学研究背景和arXiv使用经验，代表科研社区的利益。

Salmon Exposed to Anti-Anxiety Medication Pollution Take More Risks

作者: chimpanzee | 评分: 18 | 评论数: 1 | 发布时间: 2025-04-18 21:16
文章摘要

研究显示，药物污染正影响野生动物行为。瑞典研究团队给幼年大西洋鲑鱼服用抗焦虑和睡眠药物氯巴占（clobazam），剂量模拟鲑鱼在野外可能接触到的水平。结果显示，服药鲑鱼比未服药的更快到达大海，且更容易通过水坝。然而，这种加速迁徙可能带来负面影响，因为这些鲑鱼变得更加独立，减少群体活动，增加被捕食风险。药物还改变了鲑鱼的社交行为，即使在捕食者附近，它们也更倾向于单独行动。研究人员指出，药物污染对水生生物构成潜在重大威胁，但改善废水处理和开发更快降解的药物可以减轻这种影响。研究发表于《Science》期刊。

评论摘要
主要讨论点：气候变化背景下的风险承担策略及其潜在后果 不同观点： • K0balt认为，在气候迅速变化或崩溃的情况下，适度增加风险承担可能是一个好的策略。他提出，进化可能会自行调整这种平衡，如果这种策略不合适，进化过程将筛选出适应的物种。这一观点暗示了自然选择在应对气候变化中的潜在作用。 • K0balt同时也表达了对反向适应的担忧，即如果物种在适应过程中发生变化，可能会导致更具破坏性的后果。他质疑这是否会使某些物种依赖于持续的“药物治疗”才能生存，暗示了人类或物种可能因为适应气候变化而产生对技术或外部干预的长期依赖。 补充讨论： • K0balt的评论中隐含了对人类干预和自然进化之间张力的思考，即在面对气候变化时，是应该通过技术手段主动干预，还是应该依赖自然进化来调整生态平衡。 • 评论还提到了风险承担的利弊权衡，一方面适度风险可能带来新的适应机会，另一方面也可能导致不可预见的负面后果。这种不确定性是讨论中的一个关键点。 • 最后，K0balt提出了对依赖性增加的担忧，尤其是如果适应气候变化意味着某些物种将需要持续的外部支持，这可能改变物种的自然生存状态。

本文讲述了17世纪博学家莱布尼茨梦想创造一种完美表达所有科学真理的通用语言（characteristica universalis），这一梦想虽未实现，但影响了今天的编程语言。莱布尼茨发明了二进制等，其思想在现代计算机科学中得以延续。作者以自身经历为例，讲述了他对Objective-C语言的特殊情感。尽管这种语言因其冗长和独特语法而备受争议，但在2010年代，它却是开发Mac和iPhone应用的主要工具。作者在大学后期自学Objective-C，通过一本“大黑客牧场”系列书籍掌握了这门语言，并感受到其强大的表达能力。Objective-C源自对象导向编程时代，由Tom Love和Brad Cox创造，因被乔布斯的NeXT公司采用而免于消失，后成为苹果产品核心语言。尽管Objective-C语法复杂，但它提供了一种独特的编程体验。

主要讨论点：Objective-C 及其与 C++、Swift 等语言的比较，以及其在编程历史中的地位和应用情况 不同观点： • **Objective-C 的优点**： - jimbokun 认为 Objective-C 比 C++ 更优雅和强大，尤其是在扩展 C 语言以实现面向对象编程方面。它通过方括号清晰地表达了 SmallTalk 风格的消息传递机制，并且仍然是 C 的超集，能够调用任何遗留代码。 - VyseofArcadia 也支持 Objective-C，认为它比 C++ 更简洁和合理，尤其是在同一个代码库中通过 Objective-C++ 混合使用时。 - ramesh31 强调 Objective-C 是唯一的包含头文件的“动态”语言，这使得代理编码工具能够更有效地工作。 • **Objective-C 未广泛传播的原因**： - hgs3 对 Objective-C 未能在 NeXT/Apple 生态系统之外流行感到遗憾，认为自由开源软件社区没有采用它是个遗憾。 - HexDecOctBin 描述了在 Windows 上尝试使用 Objective-C 的困难，指出缺乏轻量级的工作环境，并认为这是其未广泛传播的原因之一。 • **Swift 的崛起与 Objective-C 的衰落**： - JKCalhoun 对 Swift 的崛起感到不满，认为 Swift 从各种流行语言中借用特性，导致代码风格不一致。他表示对 Objective-C 被取代感到无奈。 - mistrial9 批评了对 Objective-C 的偏见，认为其在面向对象编程早期的生存和成功不应被忽视。 • **Objective-C 的历史与应用**： - pjmlp 分享了将 Objective-C/OpenGL 移植到 Windows 9X/Visual C++/OpenGL 的经历，反映了 Objective-C 在不同平台上的应用历史。 - vaxman 详细描述了 Objective-C 在 NeXTStep 和 WebObjects 中的应用及其在企业环境中的潜力，并讨论了其与 Java 的竞争和最终被 Swift 取代的过程。 补充讨论： • **技术细节与工具支持**： - HexDecOctBin 提到了在 Windows 上使用 Objective-C 的具体技术挑战，包括对 libobjc2 的依赖和自定义根类的实现问题。 - Simplestas 认为 Objective-C 的分布式对象和 XPC 功能非常出色，其他语言无法比拟。 • **个人情感与职业发展**： - JKCalhoun 和 markus_zhang 表达了对编程工作的疲惫和对隐退编程生活的向往，反映了部分开发者对技术变迁的复杂情感。 争议焦点： • **Objective-C 与 Swift 的优劣对比**：部分开发者对 Swift 的崛起持批评态度，认为其风格不一致且缺乏 Objective-C 的优雅，而另一部分开发者则接受 Swift 作为技术进步的自然演变。 总结： 评论中对 Objective-C 的评价褒贬不一，主要集中在对其技术优点、历史应用及其被 Swift 取代的感慨。开发者们对 Objective-C 的技术细节、应用挑战及其在编程历史中的地位进行了深入讨论。

The Size of Packets

作者: todsacerdoti | 评分: 80 | 评论数: 12 | 发布时间: 2025-04-18 00:59
文章摘要

本文讨论了互联网中数据包大小的选择及其历史演变。作者指出，尽管分组交换网络已运行数十年，但“数据包应该多大”这一基本问题仍无明确答案。当前，互联网数据包默认大小为20到1,500字节，过大可能导致分片和丢包，过小则会截断包头。1981年RFC 791建议主机应能接收最大576字节的数据包。以太网的出现及其简单、去中心化的设计使其成为局域网的主流技术，其帧 payload 大小在46到1500字节之间。以太网帧大小与其碰撞检测机制相关，帧必须足够大以确保碰撞信号能在传输结束前返回，否则可能导致未检测到的碰撞。最大包大小则通过牺牲部分时序完整性来提升传输效率。这些问题最终与电磁波在铜缆中的传播速度，即接近光速相关。

评论摘要
主要讨论点：与网络通信中的MTU（最大传输单元）相关的问题和解决方案，特别是由市场数据组件的延迟问题引发的讨论。 不同观点： • hliyan描述了一个由于市场数据消息大小略微超过以太网帧大小限制而导致延迟急剧增加的问题。通过调整消息内容，使消息大小回到限制以内，暂时解决了问题。 • Veserv认为，如果默认行为是截断并转发超大包，MTU发现过程会更容易。这种方法可以让端点协议进行MTU发现，并具有认证优势，同时能立即识别MTU变化。 • cryptonector指出PMTUD（路径MTU发现）未被广泛采用，尤其是在Linux上仍默认禁用。他呼吁更广泛地启用被动PMTUD。 • jiehong认为委员会因为无法达成一致而不愿意改变现状，但提议开始可能需要多年才能实现的改变。 • posnet提到"Jumbogram"（巨型包）在高速网络中的应用及其序列化时间问题。 • roeles对网络设备如hub在现代网络中的使用情况表示兴趣。 • nayuki讨论了电缆中光速和电压传播速度与介电材料的关系。 • beeburrt只是提到字体大小问题，与主要讨论点无关。 • 2OEH8eoCRo考虑了以太网帧前导码的计算问题。 • nullc寻找在不使用两个VLAN的情况下，让Linux主机在本地子网处理9k巨型帧，同时对外通信保持1500字节的方法。 • jeffbee认为大帧大小在私有网络中是有益的，但在互联网环境中可能并不必要，当前的网络状态已经是相对最优的。 补充讨论： • 讨论中涉及的具体技术问题包括MTU发现、以太网帧大小、光速和电压传播速度、以及巨型帧在不同网络环境中的应用。 • 争议的焦点在于是否应广泛采用PMTUD以及如何有效管理网络中的MTU设置，特别是在不同网络环境（本地与外部通信）之间的差异。 • 另一个值得注意的点是不同技术背景的参与者从各自角度提出的实际问题和解决方案，如hliyan的实际案例和nullc的Linux配置问题。
