TwoFold (2f), CLI text expander/template engine

作者: croqaz | 评分: 10 | 评论数: 1 | 发布时间: 2025-05-11 18:28
文章摘要

TwoFold (2✂︎f) 是一个命令行工具，使纯文本文件具有动态文件的功能，介于文本扩展器和模板引擎之间。它受 Emacs Org-mode、Python Jupyter Notebooks 和 React JS 启发，通过处理文本文件中的 LISP/XML 样式的标签，生成动态内容。它支持 XML、HTML 文档，并可自定义标签样式如 lisp、jinja2 等。TwoFold 可实时监控文件变化，支持实时协作，适用于验证信息、计算统计、检查拼写错误等。它兼容多种文本文件格式，但不适配二进制文件。标签分为单次使用和可刷新两类，用户可自定义标签并通过命令行加载。首次运行需使用 Bun 下载和启动，提供预构建的可执行文件。使用时通过 XML 样式的标签调用 JavaScript 函数，可以扫描文件查看可用标签并进行渲染。

ZJIT has been merged into Ruby

作者: tekknolagi | 评分: 37 | 评论数: 3 | 发布时间: 2025-05-14 12:18
文章摘要

ZJIT，一个新的Ruby即时（JIT）编译器，已合并到Ruby中。与YJIT不同，ZJIT采用高层次的SSA型中间表示（HIR），并一次性编译整个方法，而不是逐个基本块编译。它从解释器读取历史类型信息，而不是使用懒惰基本块版本控制（LBBV）来分析类型。ZJIT具有模块化的高层次优化器，工作在HIR上，而不是在将YARV降低到LIR时进行优化。ZJIT旨在构建一个更传统的“教科书式”编译器，以便社区更容易贡献代码。ZJIT接受YARV字节码，构建IR，进行优化并生成机器码。例如，处理`add`函数时，ZJIT将字节码中的操作码（如`opt_plus`）重写为修改版本（如`zjit_opt_plus`）以记录输入类型，并在编译时通过HIR处理控制流和数据流。

评论摘要
主要讨论点：Ruby 的新 JIT 编译器（ZJIT）的设计及其潜在影响和效率问题 不同观点： • [burnt-resistor] 认为 ZJIT 可能在未来成为 "Crystal killer"（即，ZJIT 的出现可能使 Crystal 语言失去竞争力）。该评论暗示 ZJIT 的性能提升可能让 Ruby 在与 Crystal 的竞争中占据优势，从而影响 Crystal 的使用和推广。 • [sabslikesobs] 对 YJIT 和 ZJIT 之间的区别进行了讨论。他们提到，尽管 YJIT 能加速 Ruby 代码的运行，但它在编译和优化代码时会消耗内存和CPU资源，特别是在大型生产环境中（如 GitHub、Shopify、Stripe）会显得效率低下，因为代码会在多个服务器上重复编译。ZJIT 的设计目标是通过保存和重用编译后的代码来解决这个问题，并进一步提升性能。该评论者还指出，他们自己尚未在小型项目中遇到这些问题，但对 ZJIT 的潜在改进感到兴趣。 • [pjmlp] 对 ZJIT 的演变表示好奇，并从编译器技术爱好者的角度看待这个问题。他们赞赏 ZJIT 将所有代码生成标志包含在标准实现中，而不像 V8 需要调试版本，或大多数 JVM 需要额外的插件。这表明该评论者对 ZJIT 在实现细节和开发者体验方面的改进持积极态度。 补充讨论： • 讨论的焦点之一是 JIT 编译器在不同规模应用中的效率问题。大型生产环境中的重复编译问题被认为是 YJIT 的局限性，而 ZJIT 的设计旨在解决这一问题。 • 另一个值得注意的点是不同 JIT 编译器之间的比较，尤其是 ZJIT 与 V8 和 JVM 在实现细节和开发者友好性方面的差异。 • 最后，还隐含了一个争议点：ZJIT 的出现是否会对 Crystal 等其他语言或技术产生竞争压力，这可能会影响开发者的选择和技术生态。

Beyond the Wrist: Debugging RSI

文章摘要

这篇文章是一位计算机科学研究生自述经历慢性手腕疼痛（RSI）的个人故事。起初，他因长时间编码感到手腕和前臂疼痛，医生和理疗师都认为是肌腱炎或重复性劳损，建议他休息和进行手腕锻炼。然而，这些方法没有效果，他的情况逐渐恶化。在自行研究慢性疼痛的文献后，他意识到疼痛并非简单的“硬件”损伤，而是一个复杂的“软件”问题，涉及大脑对疼痛的预测和处理。最终，通过一系列与手腕看似无关的锻炼，他的疼痛得到了显著缓解，几个月后恢复了正常生活。文章还讨论了传统疼痛模型的问题，提出疼痛是多层次的神经系统反应，而不仅仅是组织损伤的直接结果。
