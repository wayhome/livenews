Why Wisconsin's county highways are lettered, not numbered (2019)

作者: kaladin-jasnah | 评分: 37 | 评论数: 9 | 发布时间: 2025-08-05 18:50
文章摘要

在威斯康星州，县级公路使用字母而非数字命名，以区别于州级公路，避免维护和修理工作的重复。这一系统自1917年开始实施，由各县自行命名，由于字母只有26个，常出现重复，单字母用完后会使用双字母或多字母组合。威斯康星州是全美首个区分州县公路的州，并率先举办道路学校，分享最佳实践和创新，保持在交通领域的领先地位。该系统由威斯康星县级公路协会管理，该协会对此历史感到自豪。

评论摘要
主要讨论点：对各州和县道路命名系统的不同观点及其实际影响 不同观点： • [ehaskins] 认为Google Maps应该学会正确发音县道路的名称，而不是简单地将其读作"County Road North"。这相比人工智能（AGI）的实现应该更容易。 • [bombcar] 指出Siri会错误地将县道路称为高速公路，并提到自己正在寻找County Road PP，打算亲自开车去验证，并让孩子嘲笑Siri的错误。 • [abecode] 分享个人经验，提到County Road AF是一个他喜欢的地方，靠近Fall Creek和Augusta。 • [jethkl] 引用Conway's Law来解释州和县道路系统的分离是为了避免维护和修理队伍重复工作，并提供了一个维基百科链接以支持其论点。 • [brettgriffin] 对使用字母来区分县道路的必要性提出质疑，认为即使在没有计算机和互联网的时代，也应该有可能设计出一个跨72个县不冲突的数字系统。 • [aarestad] 作为威斯康星州本地人，抱怨字母系统容易导致押韵问题，例如Dane县的PB和PD道路，需要特别注意发音，并幽默地称其为“可用性问题”。 • [jonstewart] 对比爱荷华州和威斯康星州的道路系统，赞扬爱荷华州的道路系统合理且易于导航，批评威斯康星州的道路系统混乱且难以理解，特别是在方向和命名上。 • [skywhopper] 提到密苏里州也使用字母来命名县道路，并指出威斯康星州的一些道路使用其目的地缩写，例如通往Whitefish Dunes州立公园的道路为“WD”。 • [PaulDavisThe1st] 简单地指出，威斯康星州并不是唯一一个拥有州和县道路组合的州，暗示其他州也有类似问题。 补充讨论： • 争议焦点在于县道路命名系统的合理性和实用性，特别是字母系统的使用是否必要和有效。 • 讨论中涉及到技术系统（如Google Maps和Siri）在处理这些命名系统时的表现和不足。 • 不同州的道路系统对比，特别是爱荷华州和威斯康星州之间的差异，成为讨论中的一个重要话题。 这些观点展示了用户对道路命名系统的多样化看法，从技术实现到实际使用体验，再到历史和组织结构的讨论。

Claude Code IDE integration for Emacs

作者: kgwgk | 评分: 772 | 评论数: 42 | 发布时间: 2025-08-06 13:17
文章摘要

**Claude Code IDE for Emacs** 是一个将 Claude Code CLI 深度集成到 Emacs 的工具，通过模型上下文协议（MCP）实现双向通信。它使 Claude 能够利用 Emacs 的强大功能，如 LSP、项目管理、自定义 Elisp 函数等，成为真正的 Emacs 感知 AI 助手。主要功能包括自动项目检测、终端集成、工具支持、诊断集成、高级 diff 视图、标签栏支持、选择和缓冲区跟踪等。Claude 可以直接访问 Emacs 的各种功能，如代码导航、语法树分析、项目操作等，提供更智能、更具上下文感知能力的帮助。安装需要 Emacs 28.1 及以上版本和 Claude Code CLI，并可通过 `use-package` 进行配置。

评论摘要
主要讨论点：Emacs和Vim等老牌编辑器如何整合现代AI编码工具（如Claude Code和Aider），以及这些工具对编辑器竞争力和用户体验的影响。 不同观点： • **支持整合AI工具的观点**： - 像Emacs和Vim这样的编辑器通过与Claude Code或Aider等AI工具整合，可以更轻松地获得高级IDE功能，而无需自己实现。这使得这些编辑器更具竞争力，因为它们本身已经高度可定制且易于与新工具整合 ([blahgeek])。 - Emacs由于其高度可定制性（如通过elisp改变编辑器行为）可能特别适合AI代理，具有巨大的优势 ([yoyohello13])。 - 有人已经开始使用Claude Code整合工具，并创建了高效的工作流，如使用`claude-code.el`和`eca-emacs`，虽然新工具的采用需要谨慎 ([vemv], [pjm331])。 - Emacs的历史与MIT AI Lab密切相关，拒绝AI工具的整合似乎与其历史不符 ([cml123])。 • **对整合持保留或质疑态度的观点**： - 一些用户发现Emacs配置越来越复杂，尤其是与LSP和tree-sitter的整合，可能导致配置问题。虽然Claude Code在某些情况下易于配置，但其他工具（如gopls）仍然存在问题 ([Karrot_Kream])。 - 有人质疑Emacs用户与“采用AI代理编码”的开发者之间是否存在显著重叠，认为这两类人群可能并不重合 ([efitz])。 • **对AI工具的实际应用和本地化需求**： - 用户希望AI工具能与Emacs的org模式或其他笔记功能整合，以便构建知识库，而不是像GitHub Copilot那样删除对话 ([wwarner])。 - 有用户关心是否能以较低成本在本地运行AI工具，并希望能够切换模型提供商以节省成本和提高效率 ([megaloblasto], [eulers_secret])。 • **对敏感数据安全的担忧**： - 一些用户担心在Emacs或Vim中使用AI工具可能导致敏感数据（如SSH密钥）被上传到LLM。有人提出使用bubblewrap等解决方案来隔离实例 ([qalmakka])。 • **对Neovim的关注**： - 一些用户询问Neovim中是否有类似AI工具的整合方案，并希望这些工具也能在Vim中实现 ([cristea], [brotherjerky])。 补充讨论： - 有多个Emacs/Claude Code整合包可供选择，但有些包未被广泛讨论，可能具备所有需要的功能 ([wyuenho])。 - 有开发者专注于开发适用于Emacs的AI配对编程工具，如`eca-emacs`，并希望进一步改进这些工具 ([ericdallo])。 争议焦点： - Emacs和Vim等老牌编辑器是否应整合现代AI工具，特别是考虑到配置复杂性和敏感数据安全问题。

Efrit: A native elisp coding agent running in Emacs

作者: simonpure | 评分: 131 | 评论数: 8 | 发布时间: 2025-08-08 19:20
文章摘要
