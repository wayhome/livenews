Parcom: CL Parser Combinators

作者: todsacerdoti | 评分: 10 | 评论数: 0 | 发布时间: 2025-04-22 17:53
文章摘要

`parcom` 是一个用于 Common Lisp 的简洁解析组合器库，类似于 Haskell 的 `parsec` 和 Rust 的 `nom`。它严格操作字符串，不处理流式字节数据，且为“零复制”，即不会重新分配原始输入的子字符串。`parcom` 无外部依赖，提供多种基本和组合解析器，包括字符、字符串、数字、空白字符等解析功能。 ### 主要功能： - **字符与字符串**：如 `char`, `string` 等。 - **数字**：如 `unsigned`, `integer`, `float`。 - **空白字符**：如 `space`, `newline` 等。 - **组合器**：如 `*>`, `<*>`, `alt`, `many` 等。 - **工具函数**：如 `empty?`, `fmap`, `const`。 解析器返回 `parser` 结构，包含解析结果和剩余输入。失败时返回 `failure` 结构。`parse` 函数运行解析器并忽略未消耗的输入，失败时会触发条件。 支持的 Lisp 编译器包括 SBCL、ECL、ABCL、CCL、Clisp 和 Allegro。

Detecting if an expression is constant in C

作者: ingve | 评分: 58 | 评论数: 16 | 发布时间: 2025-04-22 09:27
文章摘要

本文讨论了如何在C语言中实现一个宏，验证表达式是否为常量表达式，并在编译时中止非 constant 表达式的编译。以下是几种解决方案： 1. **静态复合字面量（C23）**： - 利用C23的`static`复合字面量确保表达式为常量。 - 缺点：C23尚未广泛支持。 2. **__builtin_constant_p（GNU扩展）**： - 使用GNU扩展`__builtin_constant_p`检测常量表达式。 - 若非常量，调用标记为`error`的函数导致编译错误。 - 缺点：依赖GNU扩展。 3. **static_assert（C11）**： - 使用C11的`static_assert`确保常量性。 - 通过`sizeof`和匿名结构体实现，可能改变表达式类型。 - 缺点：可能改变类型，GNU编译器对浮点数有警告。 4. **sizeof + 复合字面量（C99）**： - 利用复合字面量和数组大小验证常量性。 - 支持C99，但可能改变表达式类型，不支持浮点数。 5. **sizeof + enum常量**： - 使用enum常量验证，但enum会“泄漏”。 - 通过在函数参数中声明enum解决多次使用问题，但编译器会有警告。 每种方法各有优缺点，选择取决于C标准版本和编译器支持情况。

评论摘要
主要讨论点：如何保持代码无警告以及处理C语言中与编译器相关的复杂问题 不同观点： • **hermitdev**：倾向于保持库无警告，而不是让用户关闭警告。同时表达了对Google及protobuf库在C++中处理有符号和无符号比较问题的不满。 • **listeria**：指出static_assert技巧在GCC中不起作用，并提出了一种使用sizeof和复合字面量的替代方案，但该方案不支持浮点表达式。 • **dandersch**：建议使用GCC的诊断推送和弹出功能来忽略特定警告，而不是完全关闭警告，以保持代码的警告自由。 • **fuhsnn**：认为程序员追求可移植性是值得赞扬的，但过于依赖C语言的技巧可能在一些编译器上产生问题，尤其是那些对标准支持有限的编译器。并以chibicc为例，说明为处理这些技巧而添加额外逻辑的经历。 • **variadix**：提出可以使用__builtin_choose_expr来避免类型转换规则，从而避免使用typeof cast。 • **pjmlp**：指出在C++中可以使用if consteval来解决问题，特别是在使用较新标准时。 • **o11c**：讨论了一种将整数常量表达式转换为静态分配字符数组的方法，并提到可以在交叉编译时使用。 • **rurban**：建议宏的名称应更具描述性，例如IS_CONST()，而不是C()。 • **gitroom**：表达了对为了保持可移植性而使用各种编译器技巧的无奈，但赞赏追求无警告代码的努力。 • **re**：质疑这种宏的实际用途，询问是否仅是为了 puzzle 本身。 • **Y_Y**：建议如果使用C23标准，可以直接使用constexpr来解决问题。 • **uecker**：指出可以在宏内部使用_Pragma来控制警告。 • **jesse__**：提到有一种方法可以在clang和MSVC上通过编程方式控制警告，以解决宏调用时产生的警告问题。 • **_sbrk**：通过实验证明GCC不允许定义负大小的数组，即使在多种警告和优化选项下也是如此。 补充讨论： • 讨论中涉及了多种编译器（GCC、clang、MSVC）和标准（C11、C23、C++），反映了在不同环境下的兼容性和可移植性问题。 • 争议焦点在于如何在保持代码无警告的同时，确保代码的可移植性和可读性，特别是在面对编译器特性和标准支持不一致的情况下。
