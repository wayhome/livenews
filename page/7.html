Jira Is Turing-Complete

作者: vinhnx | 评分: 202 | 评论数: 26 | 发布时间: 2026-05-25 03:54
文章摘要

这篇文章证明了Atlassian的项目管理工具Jira具有图灵完备性。作者通过在Jira中构建Minsky寄存器机来实现这一证明：使用Epic的状态作为程序计数器，关联的Bug和Task数量作为寄存器，自动化规则作为指令分派表。文章展示了两个实例：一个实现加法运算（2+3=5），另一个计算斐波那契数列。通过Issue的创建、删除和类型转换操作，配合条件分支规则，成功模拟了INC和DEC指令。这证明了Jira的自动化功能在理论上可以执行任意计算，因此复杂的Jira自动化本质上就是程序。

评论摘要
主要讨论点：Jira作为项目管理工具的优劣及使用体验 不同观点： • **积极利用派**：Buttons840认为可以通过API和脚本自动化Jira操作，甚至用AI处理繁琐任务，将其变成保护自己的工具（"用数百条Jira更新记录来证明自己已充分沟通"）。0xbadcafebee赞同自动化功能，通过设置自动规则（如自动计算故事点、整理待办事项）快速优化团队看板。 • **批评体验派**：多数评论者抱怨Jira的糟糕体验——unconscionable提到速度慢且配置混乱造成创伤；jdthedisciple指出加载时间长和布局抖动导致频繁误操作（如误分配任务）；taspeotis对比旧版本，认为新版有"千刀万剐"般的小问题（如双击文本意外进入编辑模式）。 • **技术讽刺派**：lmm和rectang用图灵完备性讽刺Jira的复杂性（"无法判断操作是否会停止""比Brainfuck还恶心"）；fercircularbuf吐槽自动化工具难用"像汇编编程"。 • **替代方案派**：kvgr认为60%使用Jira的公司用Trello就够了；noja寻求本地部署的低成本替代品。 补充讨论：pjmlp指出所有工作流引擎本质上都是图灵完备的；hyperhello用"完全糟糕因此能承载任何形式的糟糕"总结Jira特性；还有人开玩笑要在Jira上运行DOOM游戏。

Defeating Git Rigour Fatigue with Jujutsu

作者: ikesau | 评分: 93 | 评论数: 22 | 发布时间: 2026-05-24 18:39
文章摘要

这篇文章介绍了使用 Jujutsu 版本控制系统解决"Git 严谨疲劳"的技巧。 **核心问题：** 开发大功能时，很难保持提交历史整洁。实际开发中常产生混乱的提交序列，后续提交会覆盖早期工作。 **解决方案：** 先创建理想的空提交结构（按功能模块划分），然后将所有实际改动合并到一个"大杂烩"提交中，最后用 `jj squash -i` 交互式地将相关改动分拣到对应的空提交里。 **优势：** 比开发过程中维持严格提交规范更轻松，避免了 `jj absorb` 的误判和 `jj split` 的反复操作，最终状态保证无冲突。 **缺点：** 无法保证每个提交都能编译通过。

评论摘要
主要讨论点：Jujutsu (jj) 与 Git 的工作流对比，特别是关于提交历史管理和分支处理的不同方式 不同观点： • **反对 jj 的立场**：y1n0 认为 jj 的分支管理极其繁琐，在多人协作场景下需要手动维护分支指向正确的提交，这对于同时维护多个分支的工作流来说不可行。Git 的命名分支机制简单易用。 • **支持 jj 的立场**：nozzlegear 和 xyzsparetimexyz 等用户完全转向 jj，认为其工作流更符合人体工程学。特别是 `jj new` 创建新变更的方式更符合心智模型，`jj split` 等交互式工具比 `git add -p` 体验更好。 • **实用主义观点**：drdrey 表示已接受 squash PR 的做法，认为追求"完美提交"是浪费时间；jadar 使用 `git reset --soft` 在推送前重写历史；codemog 建议让 AI 代理处理 Git 操作。 • **工具辅助派**：singiamtel 指出 lazygit 已经很好地解决了 Git 的痛点，但 jj 的类似工具 lazyjj 还不够成熟；mcookly 提到 Magit 可能也能高效完成类似操作。 补充讨论：everybodyknows 强调每个提交都应该能编译通过，这是结构性标准；nextaccountic 希望 VCS 能同时保存真实历史和清理后的历史；关于 `jj absorb` 的智能程度存在技术细节讨论。

Migrating from Go to Rust

作者: jabits | 评分: 133 | 评论数: 21 | 发布时间: 2026-05-24 18:31
文章摘要

这篇文章是关于从 Go 迁移到 Rust 的指南，作者 Matthias Endler 主要面向后端开发场景。文章指出 Go 到 Rust 的迁移讨论重点不在性能或类型系统，而是**正确性保证、运行时权衡和开发体验**。 作者坦承自己不喜欢 Go 的设计（如 nil 到处存在、错误处理方式），但承认 Go 很成功。文章对比了两种语言的工具链：Go 和 Rust 都有"开箱即用"的工具链，`cargo` 甚至比 `go` 提供更多内置功能。两者都采用了统一的代码格式化工具（gofmt/rustfmt），消除了代码风格争论。 文章承诺会讲解：Go 和 Rust 的异同、模式映射、借用检查器的优势、何时该保留 Go 或迁移到 Rust，以及如何增量迁移服务。作者披露自己经营 Rust 咨询公司，建议读者同时参考相反观点的文章以获得平衡视角。

评论摘要
主要讨论点：Go与Rust在Web后端开发中的选择权衡 不同观点： • **Go更适合Web服务派**：Go的goroutines并发模型优秀，标准库成熟且经过Google大规模验证，依赖树简洁（多数功能由标准库覆盖）。Rust的异步编程（tokio）复杂，包管理导致依赖爆炸（一个简单项目可能有400+依赖），不如Go务实。 • **Rust技术优势派**：Rust在编译时捕获数据竞争，无GC停顿，性能优20-50%，内存安全保证更强。适合关键业务系统、需要确定性行为的场景（如确定性模拟测试）。`match`等语法特性优于Go。 • **务实中立派**：选择取决于是否需要托管运行时。已有系统用原语言重写即可，不必为语言争论。Python/Node才是真正的对手，Rust vs Go是"小圈子内战"。绿地项目可选Rust，棕地项目保持现状更经济。 • **AI时代经济性考量**：Go增量编译快，在AI辅助开发场景下成本更低。Rust编译慢消耗更多token，对普通CRUD应用性价比不高。LLM生成Go代码质量明显优于Rust。 补充讨论：Rust运维体验差（日志冗长无用、错误缺乏上下文、内存泄漏）；Go 1.28将改进错误处理冗长问题；build.rs存在安全风险；技术选型常受炒作驱动而非实际需求。

Childhood Computing

作者: blenderob | 评分: 232 | 评论数: 50 | 发布时间: 2026-05-24 12:07
文章摘要

作者回忆了自己90年代在小镇学校机房接触电脑的童年经历：用软盘启动老式IBM兼容机，在极少的上机时间里学习Logo、靠纸笔写程序并与同学“模拟开源”式分享代码，也接触了《Space Invaders》《Digger》《Grand Prix Circuit》等游戏。这些有限却深刻的体验，点燃了他对计算与编程持续数十年的热爱。

评论摘要
主要讨论点：早期个人电脑与编程启蒙经历，及其与当代儿童接触计算机方式的差异 不同观点： • 早期设备的“可探索性”最能激发兴趣：多人提到 C64、Tandy、DOS、老式网页源码、RPG Maker、Turbo Pascal 等，因能直接改代码、看即时反馈、甚至调磁带头/内存/IRQ，促成从“玩机器”到“学编程”。 • 基础原理越早理解越重要：有人强调一旦理解变量、BASIC、HTML 等基本概念，后续进步会很快，也更容易理解计算世界如何运作。 • 旧环境比现代平台更适合入门：支持者认为早期系统简单、抽象少、一步步可见；相比之下，现代 Python/JS、GNOME、图形库和当代软件栈“选项太多、封装太厚、限制太强”，削弱了掌控感与乐趣。 • 当代环境也有现实阻碍：有人把问题归因于商业和平台限制，如微软当年授权昂贵，导致孩子只能用 QBASIC、网页和 JS 曲线入门，而难以做 Windows 程序。 • 关于孩子是否应接触屏幕存在分歧：一派担心短视频社交媒体，但希望孩子接触 Apple II、树莓派模拟器、老游戏等“低干扰”计算环境；另一派则对“反屏幕”风潮感到矛盾。 补充讨论：争议焦点在于“今天的计算机是否比过去更不利于培养创造性探索”。怀旧不仅是情感，也包含具体论据：即时反馈、低门槛修改、对系统细节的可见性，更容易让人从消费者转为创造者。
