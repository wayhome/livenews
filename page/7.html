Browser extensions turn nearly 1M browsers into website-scraping bots

作者: chha | 评分: 22 | 评论数: 6 | 发布时间: 2025-07-10 11:12
文章摘要

近100万台设备的浏览器扩展被发现绕过关键安全保护，将浏览器变成替付费服务抓取网站数据的工具。这些扩展共有245个，适用于Chrome、Firefox和Edge，累计下载量近909,000次。它们包含MellowTel-js库，该库允许开发者通过扩展获利。这些扩展被用于网页抓取，服务于广告商等客户。MellowTel库激活一个websocket连接到AWS服务器，收集用户位置和带宽等信息，并注入隐藏的iframe访问指定网站，绕过常见安全保护如Content-Security-Policy和X-Frame-Options。这使浏览器更容易受到跨站脚本攻击，且用户不知情。此前也曾有类似扩展收集用户所有浏览活动并共享给第三方。

评论摘要
主要讨论点：浏览器扩展的分发及其潜在的安全和隐私问题 不同观点： • [riedel] 认为浏览器扩展的分发缺乏类似于F-Droid那样的集中管理和审查机制。尽管很多扩展是开源的，但它们通常以zip文件的形式分发，内容不透明。浏览器厂商也未严格履行审查责任，扩展的manifest文件更多是为了保护广告收入而非用户安全。 • [paulryanrogers] 指出，扩展和VPN多年来一直使用类似技术，尤其在数据抓取和“隐形”浏览方面。他提到其曾工作过的公司通过代理/抓取公司获取 residential IPs，而这些公司使用的技术与这些扩展类似。尽管Chrome web store多年前改变了政策，但执行力度不够。 • [xnx] 支持开放的互惠爬虫网络，用于非个人/私密页面，认为这可以对抗封闭的生态系统。但强烈反对秘密和欺骗性的行为，尤其是涉及个人内容（如邮件、聊天记录等）。 • [nerdjon] 提出一个更为激进的观点，认为浏览器可能会在未来原生支持此类功能，绕过AI拦截器并获取通常爬虫无法获取的信息。他设想了一种“AI浏览器”，将所有浏览数据发送到云端处理，尽管可能会附带一些模糊的“隐私”承诺。 补充讨论： • 浏览器扩展的分发和审查问题：讨论了当前zip文件分发方式的不透明性，以及浏览器厂商在审查方面的不足。 • 扩展和VPN在数据抓取中的应用：指出了这些技术在商业环境中的使用情况，以及政策执行不力的现状。 • 开放互惠爬虫网络的可行性和伦理问题：支持对抗封闭生态系统，但强调行为透明和不涉及个人数据的重要性。 • 未来浏览器可能原生支持类似功能，引发对隐私保护的新担忧：设想了浏览器可能的发展方向及其潜在隐私风险。 争议焦点：浏览器扩展的分发透明度、审查机制的有效性以及使用这些技术进行数据抓取的伦理和法律问题。

Ruby 3.4 frozen string literals: What Rails developers need to know

作者: thomas_witt | 评分: 182 | 评论数: 21 | 发布时间: 2025-07-06 09:58
文章摘要

Ruby 3.4开始逐步引入冻结字符串字面量，默认情况下现有代码不受影响，但可以通过启用弃用警告来提前准备未来的变化。变化分为三个阶段：3.4版本引入可选警告，3.7版本默认启用警告，4.0版本默认冻结字符串字面量。冻结字符串可以带来性能提升，如减少垃圾回收和内存使用。开发者需要关注依赖的gem可能出现的警告。要查找问题，可以在开发环境中启用警告，并使用测试套件进行检查。常见需要修改的模式包括字符串构建和就地修改等。对于新代码，建议直接编写适应冻结字符串的代码，而对于现有应用则无需急于移除魔法注释。

评论摘要
主要讨论点：Ruby 引入默认冻结字符串字面量的变化及其影响 不同观点： • maximegarcia 认为此举主要是为了优化垃圾回收（GC），避免每次声明字符串时都进行分配。虽然这会使字符串操作更复杂，但社区已经通过工具（如 Rubocop）来推行这种做法，因此不应感到意外。 • ttoinou 提出疑问，动态类型语言是否最终都会走向类似编译型语言的复杂优化路径，以及这种变化是否会影响 Ruby 初期的简单性及其成功。 • teddyh 指出 Ruby 的可变字符串特性，并与其他语言（如 Python）的不可变字符串进行比较。 • temporallobe 分享了在 Rails 项目中引入该特性时发现了一些隐藏的 bug，但现代工具（如 Rubocop）能有效缓解这些问题。 • _flux 提到 OCaml 也曾进行过类似的转变，虽然初期有些波折，但最终顺利过渡，静态类型检查在此过程中起到了帮助作用。 • meisel 对 Ruby 如何在底层实现该特性提出了技术细节上的疑问，尤其是如何进行字符串去重及引用计数管理。 • lcnPilGDnU4H9OF 讨论了冻结字符串字面量对具体代码模式的影响，并提出了在不同情况下更优的代码模式。 • flufluflufluffy 对“冻结字符串字面量”这一术语感到困惑，认为字符串字面量本身应是静态不变的，不应被称为“冻结”。 • jbverschoor 指出线程中对可变字符串的误解较多。 • phendrenad2 质疑冻结字符串字面量带来的性能改进是否显著，并担心这种微优化可能会降低代码可读性。 • bitbckt 提到 Twitter 在约 15 年前就进行了类似的优化。 • skywhopper 对 Ruby 团队有条不紊的过渡计划表示赞赏。 • ksec 假设 Shopify 和 GitHub 已经对此进行了充分测试，表明 Rails 生态系统已经为该变化做好了准备。 补充讨论： - 争议焦点在于优化带来的复杂性与性能提升之间的权衡。 - 讨论中多次提及社区工具（如 Rubocop）在推行新特性中的作用。 - 部分开发者对该变化的技术实现细节和实际性能影响表示关注。 - 一些评论提到了其他语言的类似转变经验，提供了跨语言的视角。

Most RESTful APIs aren't really RESTful

作者: BerislavLopac | 评分: 335 | 评论数: 84 | 发布时间: 2025-07-09 07:04
文章摘要

Roy T. Fielding的论文《架构风格与基于网络的软件架构设计》介绍了REST（表现层状态转移）架构风格，旨在分析不同架构风格的优缺点，强调REST在可扩展性、简洁性和适应性方面的优势。REST为设计分布式系统提供了原则和约束，特别是通过使用无状态接口和基于资源的交互。Fielding批评了许多自称“RESTful”的API，因为它们未能实现REST的核心约束，尤其是缺乏超媒体作为应用状态引擎（HATEOAS）。HATEOAS要求客户端通过服务器响应中的超媒体链接动态发现可执行操作，从而减少客户端与服务器之间的耦合。关于“资源”，Fielding指出，任何可命名的信息都可以是资源，其关键在于资源标识符的分配和表示的关联，而非服务器上的具体实体。因此，实现HATEOAS比争论API中是否允许使用动词更符合REST原则。

评论摘要
