Microsoft is open sourcing Windows 11's UI framework

作者: bundie | 评分: 195 | 评论数: 39 | 发布时间: 2025-08-02 07:52
文章摘要

Microsoft计划逐步开放Windows 11用户界面框架WinUI的源代码，但因其复杂性及与操作系统专有层的关联，无法一蹴而就。微软将分阶段开放WinUI的GitHub仓库：第一阶段增加内部提交的镜像频率，提升透明度；第二阶段允许外部开发者本地构建代码；第三阶段开放贡献和测试功能；最终阶段将GitHub作为主要开发和社区互动平台。整个过程需要时间，微软正在积极推进，但目前无法确定具体完成时间。开发者在此期间可通过反馈和问题报告参与贡献。

评论摘要
主要讨论点：Windows原生UI技术的未来及开发者体验 不同观点： • paavohtl认为微软在Windows 11中用webview包装的应用程序替代原生应用程序，导致性能下降和视觉不一致，这与传统上微软自己使用并推广高性能、一致性的原生应用的做法背道而驰。 • arunc对微软的资源分配和开放框架的策略持批评态度，认为微软只是将框架丢给社区，依赖社区贡献，而自己并未真正投入资源解决问题。 • pjmlp表示Windows开发社区对WinUI不感兴趣，认为微软通过WinRT/UWP造成的“技术债务”让开发者陷入困境，且微软不愿修复这些问题，期望社区自行解决。 • muhehe指出Windows中UI框架繁多且混乱，质疑微软开放源代码的实际效益，并怀疑其开放性是否只是表面文章。 • tekdude支持继续开发WPF，认为WPF有一些需要改进的地方，比如数据绑定系统可以利用.NET的编译时代码生成来提升性能和开发体验。 • daemin认为WinUI3的开发体验很差，调试需要安装应用，且示例程序不稳定，因此仍选择使用Win32和WTL。 • chiph怀念过去微软为开发者提供一致视觉风格的支持，认为引入web技术后，Windows的视觉体验变得碎片化。 • Springtime希望Windows 11引入原生垂直任务栏功能，指出这一功能自Windows 98以来就存在，但目前依赖第三方工具实现。 • dehrmann质疑微软对Windows的长期承诺，认为Windows在公司内部的占比下降，用户向其他设备迁移，可能导致微软减少对Windows的投入。 • bobajeff建议微软直接承认Electron/TypeScript为其主要UI框架，因为微软已经拥有GitHub和VSCode，且这些工具广泛使用Electron。 • bob1029支持使用Win32/GDI/DirectDraw等低级API，认为这些API稳定性高，不易被微软改变或废弃。 • elygre对讨论中的负面情绪感到惊讶，认为开放框架没有明显的坏处。 • eska分享了一个学习OS和winapi开发高效原生UI的示例，认为开发者可以通过学习底层技术实现高效UI。 • Woodi对微软可能开发更好的UI抱有希望，但同时担心微软可能推出更差的UI，期待有其他合理的操作系统和UI项目出现。 • vachina批评微软将混乱的框架开放源代码并期望他人贡献，认为微软有足够财力自行解决问题。 补充讨论： • 微软对Windows UI技术的资源分配和长期承诺是争议焦点，部分开发者认为微软未尽到责任。 • 不同开发者对各种UI框架的优劣有不同看法，有些人支持继续改进WPF，有些人则倾向于使用更底层的Win32 API。 • 对微软开放源代码策略的实际效果存在质疑，部分开发者认为微软只是将问题转嫁给社区。 • 对Windows原生UI功能（如垂直任务栏）的需求和期望也是讨论的重要内容。

The /o in Ruby regex stands for "oh the humanity "

作者: todsacerdoti | 评分: 156 | 评论数: 14 | 发布时间: 2025-08-02 14:37
文章摘要

这篇文章讨论了Ruby中正则表达式使用`/o`修饰符引发的一个隐蔽问题。作者在代码审查中发现一个`Matcher`类，其`matches_any?`方法使用正则表达式匹配输入字符串。最初测试通过，但后来发现无论输入什么值，结果都始终一致。经过排查，发现问题源于`/o`修饰符，它会导致正则表达式在首次插值后被缓存，后续不再重新插值。作者通过查阅文档和分析VM字节码，最终解决了问题并理解了其内部机制。这个修饰符本意是优化，但在此场景中引发了难以察觉的错误。

评论摘要
主要讨论点：Perl 和 Ruby 中正则表达式插值模式（/o）的用法、文档清晰度以及其潜在问题 不同观点： • fanf2 认为 Ruby 的文档，尤其是“插值模式”部分，具有误导性，相比之下 Perl 的文档更加清晰。他引用了 Perl 文档中的解释，指出 /o 修饰符在现代 Perl 中几乎不需要使用，并给出了 Perl 4 的相关说明。 • tialaramex 将 /o 修饰符视作一种“footgun”（容易被误用导致问题的功能），认为编程语言应尽量避免这种设计。他强调这种功能会导致神秘且难以发现的错误，而非仅仅性能问题。 • jononor 用幽默的方式将 /o 修饰符的符号比作表情符号，没有深入技术讨论。 • cbsmith 作为一个有经验的 Perl 程序员，表示自己立即理解了 /o 的作用，暗示对老手来说这并不是问题。 • kazinator 提供了对 /o 修饰符的正面解释，并用 C++ 中的静态变量和 POSIX 的 pthread_once 函数进行类比，说明这种“一次性初始化”的行为在其他编程环境中也存在。 • alfiedotwtf 提到如果不喜欢 /o，那么可能会更不喜欢 Perl 的 /e 修饰符，暗示 /e 的问题可能更大。 • jwlake 认为这个功能类似于 JavaScript 中正则表达式的 g 修饰符，试图寻找不同语言中相似功能的关系。 • IshKebab 表示这种情况在 Ruby 中很常见，似乎暗示 Ruby 的设计本身就容易导致混淆。 • lupire 将此问题与闭包中按名或按值捕获参数的困惑相比较，指出用户容易混淆插值的行为。 • phoronixrly 对 /o 功能持积极态度，认为这是一个有趣的特性。 • zer00eyz 引用经典的正则表达式调侃，暗示正则表达式本身就容易带来问题，无论是否有插值模式。 • Joker_vD 表示无法理解 /o 修饰符的存在意义，认为如果插值值会变化，那么每次都重新插值是显然的，而如果值不变，那直接编译一次保存结果即可，因此觉得整个设计不合理。 补充讨论： • 争议焦点在于 /o 修饰符是否容易导致误用和神秘错误。tialaramex 和 Joker_vD 等人认为这是一个危险的功能，而 kazinator 等人则试图为其行为提供合理的解释和类比。 • 文档清晰度也是一个讨论重点，fanf2 和 Joker_vD 都对 Ruby 文档的描述感到困惑，而认为 Perl 的文档相对清晰。 • 不同语言背景的开发者对类似功能的比较和联想，例如 jwlake 提到 JavaScript 的类似功能，riffraff 提到 `END {}` 继承自 awk 等，提供了更广泛的背景讨论。

Mezzano, an operating system written in Common Lisp

作者: dargscisyhp | 评分: 79 | 评论数: 4 | 发布时间: 2025-07-30 14:09
文章摘要
