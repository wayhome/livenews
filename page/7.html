Fast Factorial Algorithms

作者: nill0 | 评分: 42 | 评论数: 8 | 发布时间: 2026-05-20 03:55
文章摘要

文章介绍了5种计算阶乘 n! 的算法：SplitRecursive（简单且不依赖质因数分解时最快）、PrimeSwing（目前渐近最快，基于“摆动数”和质因数分解）、Moessner（仅用加法但很慢）、Poor Man’s（无需大整数库，适合实现）、ParallelPrimeSwing（适合多核并行）。文中还给出递归实现示例，并强调不要使用朴素递归阶乘。

z386: An Open-Source 80386 Built Around Original Microcode

作者: wicket | 评分: 125 | 评论数: 8 | 发布时间: 2026-05-23 14:25
文章摘要

这篇文章介绍了z386项目——一个基于Intel原始微码在FPGA上重建的386级CPU。z386能运行DOS 6/7和保护模式程序如Doom游戏，性能相当于70MHz的386或低端486。项目使用8K行代码，保留了386的核心架构特征（如32项TLB、微码ROM），同时采用FPGA友好的优化（DSP乘法器、16KB四路组相联缓存）。文章详细说明了CPU的八大功能单元：预取、解码、微码序列器、ALU/移位器、分段、保护、分页和总线接口，展示了如何从z8086项目演进到更复杂的z386实现。

评论摘要
主要讨论点：关于386处理器FPGA实现项目的技术评价和应用场景 不同观点： • **技术局限性观点**（spankibalt）：认为缺少FPU浮点运算单元的FPGA实现限制了生产力和研究用途，只适合游戏等基础应用，类比Ao486也只实现了486SX • **应用可行性观点**（cbdevival）：指出可以运行Linux 3.7内核，提到Gray386linux项目仍在维护，展示了实际应用潜力 • **技术效率观点**（UncleOxidant）：对仅需18K LUTs感到惊讶，认为这在现代FPGA中是相当小的规模，暗示实现效率很高 • **安全研究角度**（mmastrac）：关注微码反汇编是否发现了无需开盖就能读取微码的后门 • **怀旧与实用性讨论**（KellyCriterion）：询问是否还有386在实际生产环境运行，分享了90年代末见过用软盘传输数据的工业设备案例 补充讨论：多条评论提到了相关的"80386微码反汇编"讨论帖，显示社区对386底层技术的持续关注。整体氛围在技术评估、实用性探讨和怀旧情怀之间。

Aube – Node.js package manager in Rust

The day my ping took countermeasures

作者: moonleay | 评分: 18 | 评论数: 3 | 发布时间: 2026-05-24 02:02
文章摘要

这篇文章讲述了作者在假期后启动电脑时，运行ping命令遇到"taking countermeasures"（采取对策）警告的调查过程。原因是ping在系统NTP同步时间前启动，时钟被回拨导致RTT测量值为负。作者深入研究了ping的源码（可追溯到1983年），发现它有两种时间测量模式：旧模式使用墙上时钟（gettimeofday），新模式使用更精确的网络时间戳（SO_TIMESTAMP）。当检测到负RTT时，ping会将其重置为0ms。文章还探讨了如何追踪gettimeofday调用，因为现代Linux使用vdso机制使某些系统调用在用户空间执行，常规strace无法捕获，作者尝试了多种技术方案来绕过这一限制。

评论摘要
主要讨论点：关于Unix网络工具ping的历史和文化联想 不同观点： • powerbroker提到了一个幽默的文学联想，引用了1933年的儿童读物《The Story About Ping》，巧妙地将其与Unix的ping命令联系起来，指出这本书比操作系统和网络基础设施早了几十年，形成有趣的时间悖论式玩笑 • defrost提供了技术历史信息，指出ping命令由Mike Muuss于1983年在美国陆军弹道研究实验室编写，并分享了个人的时代记忆 • hntiz则联想到了《猎杀红色十月》电影，认为标题让他想起了该电影中的声呐ping场景 补充讨论：这些评论展现了技术社区的文化特点——将严肃的技术工具与流行文化、文学作品联系起来。没有明显的争议，更多是不同角度的补充：一个是文学幽默，一个是技术历史，一个是电影联想。整体氛围轻松友好，体现了技术人员的人文情怀。

Rubish: A Unix shell written in pure Ruby

作者: winebarrel | 评分: 143 | 评论数: 22 | 发布时间: 2026-05-23 06:32
文章摘要

Rubish 是一个用纯 Ruby 编写的 UNIX Shell：将 Shell 语法解析并编译为 Ruby，再由 Ruby VM 执行。它目标是完全兼容 Bash，可直接运行现有 bash 脚本；同时深度整合 Ruby，支持在脚本中混用命令与 Ruby 表达式、方法链、迭代器、lambda、Ruby 风格函数和自定义提示符等，适合既想保留 Shell 体验又想利用 Ruby 能力的用户。

评论摘要
主要讨论点：关于 Rubish（Ruby shell）项目的评价和对未来开源开发模式的思考 不同观点： • **实用性担忧派**：freedomben 认为虽然项目有趣，但最大障碍是远程环境部署问题——Rubish 不够轻量，需要安装，导致必须在两个世界间切换，这通常不可持续 • **AI 辅助编码质疑派**：ciconia 对"vibe-coded"（AI 辅助生成）的代码表示担忧，指出代码缺乏清晰的接口边界、存在 200 行的长方法，使得非 AI 用户难以理解和贡献。质疑这是否意味着未来贡献者也必须使用 AI 才能参与开源项目 • **学习工具支持派**：saysjonathan 希望看到更多解释型语言提供原生 shell，认为像 rush 和 scsh 这样的工具能帮助开发者沉浸式学习语言，虽然最终因人机工程学问题回归传统 shell，但作为学习机制很有价值 • **性能讨论派**：faangguyindia 和 1vuio0pswjnm7 关注性能，指出 Ruby 比 Go 慢但比 Python 快，质疑 Rubish 可能比 bash 更慢 • **命名赞赏派**：多位评论者（keyle、searls、terminalbraid 等）高度赞扬项目命名的巧妙（Rubish = Ruby + sh，也谐音 rubbish） 补充讨论：ifh-hn 表达了对传统管道操作的偏好，不喜欢方法链式调用的风格
