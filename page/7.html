Warm up your MacBook (2019)

作者: kristianp | 评分: 132 | 评论数: 33 | 发布时间: 2026-05-27 20:42
文章摘要

这篇文章介绍了在寒冷天气下快速加热MacBook的方法。作者提出通过让CPU满负荷运行来产生热量,推荐了两种方案: 1. 使用内置命令 `yes > /dev/null` 让CPU达到100%使用率 2. 安装 `stress` 工具并运行 `stress -c 6 -m 2 -t 300`,启动6个CPU线程和2个内存线程,设置5分钟超时防止过热 文章还建议将命令设为bash别名以便快速使用。这是一个实用的技巧,适合在冬季使用冰冷的金属键盘前快速预热笔记本电脑。

评论摘要
主要讨论点：MacBook 的散热问题及如何快速让电脑升温 不同观点： • **旧款 Intel MacBook 过热问题**：2019 年 Intel MacBook Pro 散热极差，日常编译或视频会议就会导致风扇狂转和热节流，系统用 kernel_task 占用核心来限制性能，用户不得不把电脑放在冰袋上使用 • **新款 MacBook 散热优异**：现代 MacBook（Apple Silicon）散热太好，用户从未听到风扇声音，即使 CPU/GPU 跑到 90 度也不启动风扇，需要手动工具确认风扫是否工作 • **实用主义方案**：有用户发现 7 年不清灰是最好的"保温"方法；清理灰尘后温度明显下降 • **幽默调侃**：多位用户开玩笑称只需打开 Microsoft Teams、编译 monorepo 或运行 Cinebench 就能快速升温 补充讨论： 有用户关注冷启动的硬件风险（低温下开机是否影响可靠性）和冷热交替的冷凝风险（湿度和露点问题）。评论区还提供了多种 CPU 压力测试命令（yes、xargs 等）作为升温方法。整体氛围轻松幽默，反映出 Intel 时代和 Apple Silicon 时代 MacBook 散热性能的巨大反差。

Announcing Rust 1.96

文章摘要

Rust 1.96.0 发布，主要更新包括： 1. **新的 Range 类型**：引入 `core::range` 模块下的新范围类型，支持 `Copy` trait，解决了旧版 `Range` 因实现 `Iterator` 而无法 `Copy` 的问题。 2. **断言匹配宏**：新增 `assert_matches!` 和 `debug_assert_matches!` 宏，用于检查值是否匹配指定模式。 3. **WebAssembly 变更**：链接器不再默认传递 `--allow-undefined` 参数，未定义符号现在会导致链接错误。 4. **安全修复**：修复了两个针对第三方注册表用户的漏洞（CVE-2026-5223 和 CVE-2026-5222），crates.io 用户不受影响。

评论摘要
主要讨论点：Rust标准库中ranges的重新设计和版本管理策略 不同观点： • **反对原地替换方案**（j1elo）：认为将现有std::range替换为新版本，并把旧版本移到std::range::legacy是短视的设计。担心未来如果再次迭代会导致命名混乱（如legacy::legacier）。建议借鉴Go的做法，采用版本化命名（如std::range/v2或std::range::v2），保持旧版本不变。 • **支持标准库扩展**（j1elo延伸观点）：指出Rust标准库因"一旦加入就永久保留"的顾虑而过于保守，导致缺少官方认证的常用功能。认为解决版本迭代问题有助于标准库更积极地添加实用API，满足大多数开发者需求。 • **积极看待改进**（Tuna-Fish）：对ranges问题能得到修复感到意外和欣慰，此前认为这会成为永久性缺陷。关注过渡过程的平滑程度。 • **关注新特性**（PoignardAzur）：对assert_matches!宏的加入表示兴奋。 补充讨论：核心争议在于API演进策略——是原地替换+legacy命名，还是版本化命名。这反映了Rust社区在标准库稳定性与可演进性之间的权衡困境。

评论摘要

文章介绍作者因 Typst 与 Pandoc 升级导致旧模板失效，于是重建了一套新工作流：改用 Pandoc 默认 Typst 输出模板，并通过 `-V template=article.typ` 调用真正的 Typst 模板。新模板能读取 Markdown 元数据，提供页眉页脚、字体排印、引文、代码块、图片标题、脚注、标题层级、epigraph 与参考文献等样式，结构更清晰，也更利于长期维护。

评论摘要
主要讨论点：关于使用 Pandoc 将 Markdown 转换为 Typst 再生成 PDF 的工作流程 不同观点： • **支持 Markdown+Pandoc 工作流**：多位用户认为这种方式很实用，特别是需要同时输出多种格式（PDF、Word）时，便于与习惯 Word 的合作者协作；有人已成功应用于设计文档和咨询工作，可实现交叉引用、图表、目录等功能 • **质疑 Markdown 必要性**：认为 Typst 语法本身已经足够简单（不比 Markdown 难），直接用 Typst 编写更合理，无需引入 Pandoc 这个中间环节；一位开发者创建了直接在 Typst 中导入 Markdown 的库，认为单一构建步骤、无中间文件更有优势 • **Typst 体验极佳**：多位用户从 LaTeX 转向 Typst 后体验显著提升，编译时间从 10 秒降至 10 毫秒，生产力大幅提高；从零构建模板的时间从数天缩短到不到一天 补充讨论： • 版本兼容性问题：作者提到模板在 Typst 和 Pandoc 多次升级后失效，这是该工作流的潜在风险 • 文章展示不足：有读者希望看到具体的 Markdown 格式示例和输出 PDF 效果 • 对工作流理解困惑：有人不理解为何需要 Typst 参与 Markdown 到 PDF 的转换
