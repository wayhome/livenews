Programmers aren’t so humble anymore, maybe because nobody codes in Perl

作者: Timothee | 评分: 178 | 评论数: 37 | 发布时间: 2025-07-29 17:51
文章摘要

Perl曾经是广泛使用的脚本语言，尤其在2000年前后，许多网站和企业（如Amazon、Google、Yahoo等）都依赖它处理文本数据和生物信息学任务。尽管Perl流行，但其语法混乱、结构复杂，常被称为“互联网的 duct tape（胶带）”和“只写语言”。Perl允许用多种方式实现同一功能，这种多样性源自其创始人Larry Wall对语言演化和多样性的哲学理念：语言应具有包容性和非规范性。然而，这种“混乱”可能导致用户偏好更简洁、结构化的语言，如Python。尽管Perl不再如昔日流行，但它提醒我们，在复杂的世界中，谦逊和多样化的方法至关重要。编程语言不仅为机器服务，更为人类理解和使用。

评论摘要
主要讨论点：Perl语言的优缺点、其衰落的原因以及与其他语言的比较 不同观点： • noisy_boy 认为Perl让从bash转过来的他感觉像成为了高手，特别是在重写bash脚本时感受到了Perl的高效和强大功能。然而，在参与大型Perl项目后，他感到Perl代码难以维护，最终转向Java让他松了一口气。 • KaiserPro 强调了通过代码审查和团队文化可以保持Perl代码的可读性和可维护性，并指出Perl文档在过去比Python文档更实用。 • CaliforniaKarl 赞赏Perl的taint模式在安全性方面的优势，认为这是其他语言值得借鉴的地方。 • alexpotato 对比了Perl和Python，指出Perl容易写出“只写代码”，但同时也认为Perl的正则表达式和向后兼容性是其优点，而Python的强制缩进和对象模型更好。 • jbullock35 认为Perl的衰落与社区在Perl 5到Perl 6过渡中的不成功尝试有关，并提到Perl书籍作者未及时推出适用于Web开发的书籍可能给了PHP机会。 • ben7799 指出在1990年代Perl在学术界已经不被看好，认为其不适合长期维护和团队开发。 • lapsed_lisper 通过自身经历说明Perl代码难以理解，许多Perl程序员依赖试错和文档查询来理解代码，认为这降低了生产力。 • altacc 认为Perl没有试图让编程变得更直观，而其他语言则通过更清晰的语法和框架来降低复杂性。 • inoffensivename 和 gortok 分享了他们年轻时学习Perl的积极经历，认为Perl带来了很多乐趣和学习机会。 • cozzyd 指出Perl代码可以多年不维护仍正常运行，而Python代码则容易“腐烂”。 • finaard 则表示同时享受Perl和Lisp，认为Perl在文本处理方面有独特的优势。 补充讨论： • kqr 对Perl的衰落原因持怀疑态度，认为尽管Perl 6（现Raku）没有取得巨大成功，但Perl在互联网基础设施中的重要地位保证了其不会迅速消失。 • throwanem 用幽默的方式比喻Perl像是20年前的“管道胶带”，暗示其过时和不再适用。 争议焦点： • Perl代码的可读性和可维护性是讨论的核心争议点，一些人认为通过良好的代码审查和团队文化可以保持Perl代码的可读性，而另一些人则认为Perl天生容易写出难以维护的代码。 • Perl衰落的原因也被广泛讨论，有人认为是技术社区的过渡失败，有人则认为是其他语言如Python的崛起导致了Perl的边缘化。

Qwen3 Coder 480B is Live on Cerebras

作者: retreatguru | 评分: 22 | 评论数: 5 | 发布时间: 2025-08-01 17:50
文章摘要

Alibaba的Qwen3 Coder 480B Instruct模型已在Cerebras平台上推出。该模型是全球顶级编码模型之一，性能可与Claude 4 Sonnet和Gemini 2.5媲美，并在Cerebras Wafer Scale Engine上实现了每秒2,000个 token 的速度。相比其他模型，如Sonnet4需要20秒处理的编码问题，Qwen3 Coder只需1秒。为增加可访问性，推出了两种月度订阅计划：Cerebras Code Pro（50美元/月）和Cerebras Code Max（200美元/月），提供更高的速率限制。发布仅两周，Qwen3 Coder 480B的采用率迅速上升，在OpenRouter的编码模型排行榜上跃居第二，超越了多个竞争对手。Cerebras平台还与Cline集成，方便开发者在VS Code中使用，并按输入或输出token计费（2美元/百万token）。

评论摘要

When Flatpak's Sandbox Cracks

作者: dxs | 评分: 23 | 评论数: 5 | 发布时间: 2025-08-01 20:01
文章摘要

本文讨论了Flatpak在Linux系统中作为沙箱技术的安全问题。尽管Flatpak通过使用bubblewrap命名空间、系统调用过滤和门户接口来隔离应用程序，理论上提供了一个安全的运行环境，但实际使用中存在漏洞。许多Flatpak应用声明了广泛的权限，如`filesystem=home`或`device=all`，这削弱了沙箱的效果。文章具体介绍了两个安全漏洞：CVE-2024-32462，涉及通过门户接口执行任意主机命令；CVE-2024-42472，涉及利用符号链接获取对敏感文件的访问。此外，Flatpak应用的权限配置复杂，且更新滞后，可能包含过时且有漏洞的库。为增强安全性，文章建议保持Flatpak核心和门户的更新、最小化应用权限、使用工具审核权限、推广安全默认设置并加强教育。未来可以通过自动化沙箱生成工具和持续的运行时扫描来改进安全性。

评论摘要
主要讨论点：Flatpak的安全性、实用性及其在Linux系统中的角色 不同观点： • ChocolateGod认为，Flatpak应用常附带filesystem=home权限，可能导致安全隐患，例如通过覆盖sudo配置文件或.desktop文件间接获取root权限。虽然非Flatpak应用也可能有类似问题，但Flatpak给人一种虚假的安全感，可能促使人们下载原本不会考虑的应用。此外，Linux应用开发者缺乏像Android/iOS那样的更新动力，导致安全隐患持续存在。ChocolateGod强调，Flatpak主要是一个应用分发工具，而非安全项目。 • BrenBarn表示，他希望有一个类似Flatpak但不强调安全性的工具。他的主要需求是能够独立于操作系统级别的包管理器更新程序。他对Flatpak的安全性没有特别关注，更看重其在软件更新方面的优势。 • WesolyKubeczek指出，Flatpak的沙盒功能大多是表面功夫，隐私保护有限。他建议一个理想的系统应该允许用户对应用权限进行更细致的控制，例如伪造摄像头、麦克风输入或文件访问路径，而不让应用感知到拒绝或伪造的信息。他认为实现这些功能的组件已经存在，但实际操作较为复杂。 • Fake-name完全反对使用Flatpak、Snap、AppImage等打包项目，认为这些工具只是为了开发者方便，却牺牲了用户体验。他找不到任何理由让用户选择使用这些打包形式的应用。 补充讨论： • Flatpak的安全性与开发者更新动力之间的矛盾。 • 用户对应用权限控制的细化需求与现有技术实现之间的差距。 • 不同用户对Flatpak的实用性与安全性的认知差异。 • 对Flatpak等打包工具在开发者与用户体验之间的权衡与取舍。
