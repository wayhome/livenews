We can still stop California's 3D printer surveillance scheme

作者: hn_acker | 评分: 405 | 评论数: 24 | 发布时间: 2026-06-26 21:13
文章摘要

加州众议院通过了AB 2047法案，要求3D打印机内置监控和审查软件，以阻止无证制造枪支。电子前哨基金会（EFF）对此强烈反对。 法案的主要修订包括：取消了对个人转售旧设备的犯罪化处罚；为开源工具设置了豁免，但仍要求其包含合规的审查软件；将性能标准从"有效阻止"降低为"大幅减少规避可能性"；并为娱乐业商业用户设立豁免，但小型创作者未获保护。 EFF认为该法案存在三大核心问题：技术上根本无法实现预期效果，只会干扰守法用户；强制监控所有打印文件，严重威胁隐私；对开源开发者设置模糊且不切实际的标准，压制创新。此外，商业豁免条款还可能让制造商借机推出更贵的商业版打印机，加剧市场垄断。 EFF呼吁民众联系加州参议员，要求否决这一无效且侵权的法案。

评论摘要
主要讨论点：加州提议的3D打印机监管法案引发争议，核心是关于技术自由与公共安全的平衡问题 不同观点： • **反对派（主流）**：认为法案过度监管且无效。论据包括：类比其他工具（车床、剪刀、汽车）若如此监管将荒谬；执法难以实施；无法真正阻止犯罪（可自制打印机）；criminalizes开源软件使用者；要求专有切片软件违背技术开放原则 • **技术自由视角**：将此法案视为更大的技术压制趋势的一部分，与加密战争、AI监管、年龄验证、维修权限制等并列，担心政府对技术的全面控制正在加剧 • **讽刺批评者**：指出加州有更紧迫问题（如无家可归危机）未解决，却优先立法监管3D打印机，质疑政府优先级 • **行动倡议者**：呼吁选民联系州参议员反对法案，强调硅谷不应使用受限工具 补充讨论：有人分享幼儿园儿童因打印玩具人偶被误报为枪支的荒诞案例；也有人担心加州轮廓本身可能触发算法误报；部分评论上升到宪法层面，指责这是"叛国"行为；有人惊讶科技YouTube博主未对此发声；欧洲用户担心被效仿。

Fusion Programming Language

作者: efrecon | 评分: 92 | 评论数: 21 | 发布时间: 2026-06-24 11:27
文章摘要

Fusion 是一种编程语言，旨在从单一代码库为 C、C++、C#、D、Java、JavaScript、Python、Swift、TypeScript 和 OpenCL C 等多种语言实现可重用组件（库）。它能将一份代码翻译成所有这些目标语言，生成的代码轻量级（无虚拟机、模拟或依赖），人类可读，并且符合目标语言的命名规范和文档注释风格。通过一个简单的命令即可完成多语言转换。

评论摘要
主要讨论点：Fusion编程语言作为跨语言库开发工具的可行性和实用性 不同观点： • **技术对比派**：多人提及与Haxe的相似性，要求性能、生成代码质量、标准库完善度的对比。gr4vityWall特别关注异常处理在无异常语言（如C）中的转换，以及跨平台行为一致性问题 • **怀疑派**：Panzerschrek和xiaoyu2006质疑多语言统一的必要性，认为生成的代码会次优且不符合目标语言习惯，要么取无用的语言交集，要么做出怪异的抽象 • **实用问题派**：teo_zero、anonzzzies、hyperhello集中关注调试困难——需要在目标语言中调试后再反向修改源码，缺乏解释器和调试器支持 • **代码质量关注**：poppadom1982指出C代码示例存在具体问题（缺少边界检查、数组大小返回、头文件引用等） • **文档不足**：eoanermine批评文档只有示例，缺乏类型和语句到特定语言转换的详细说明 补充讨论：knhung指出通用语言难以为特定语言优化的根本矛盾；FattiMei质疑OpenCL这种不同编程模型的支持；zabzonk认为过度使用类是技术倒退

这篇文章探讨AI对软件行业的深远影响： **大规模裁员**：Block、Atlassian、Salesforce等公司因AI裁员数千人，捷克保险公司也裁员三分之一。 **四大变革**： 1. **降低门槛**：AI让人人可编程，软件从高门槛的数学领域变成人人可评判的营销领域，导致尊重度和薪资下降 2. **选择过剩**：就像约会软件改变恋爱市场，AI让软件产品激增，用户不再满足于"够用"的方案 3. **中产消失**：SaaS市场将呈现幂律分布，只有头部产品和定制化方案存活，"还行"的产品将消失 4. **服务转型**：软件公司需从卖产品转向卖服务 核心观点：软件将像水一样普及但不再是差异化优势，只有顶尖专家和专业化能力才能获得溢价。

评论摘要
主要讨论点：AI编码（vibe-coding）是否会降低软件工程师的地位，以及是否会改变SaaS商业模式 不同观点： • **怀疑论者**：认为vibe-coding不会根本改变现状。理由包括：非技术人员不会为技术结果负责(mgh95)；实现仍然困难，消费体验易评判但实现难(wxw)；AI只是放大器，不能让零基础者成功(gherkinnn)；软件需要持续维护，成本和复杂度被低估(npodbielski) • **谨慎乐观者**：承认AI降低门槛但强调局限。Michelangelo11指出软件护城河已失效，高复杂度场景除外；xlii认为入门容易但学习曲线陡峭，无经验者难以应对工程决策；wavemode系统反驳四个推论，强调企业更看重降低风险而非成本 • **批评原文论据**：_fw作为营销人员强烈反对，认为作者对营销工作的理解肤浅（将营销简化为选颜色），且"卖服务不卖软件"的建议在营销上没有实质区别；runningmike质疑"长尾理论"和"入门门槛降低"的老生常谈 • **部分认同者**：ingvay7认为观点对中小企业SaaS有方向性意义；KolibriFly认为仅适用于产品化的可见层 补充讨论：争议焦点在于AI是否真正降低了软件开发的实质门槛，还是只是降低了原型制作门槛。多数评论者认为软件维护、架构决策、需求分析等核心难题未被AI解决。

Show HN: DBOSify – Drop-in Temporal replacement built on Postgres

作者: KraftyOne | 评分: 68 | 评论数: 4 | 发布时间: 2026-06-24 17:20
文章摘要

DBOSify 是 Temporal Python 的替代品,使用 Postgres 数据库(通过 DBOS Transact)替代 Temporal 服务器。它让你无需额外基础设施即可运行持久化工作流、活动、信号、更新、重试和恢复功能。 核心机制:将 Temporal 工作流作为 Postgres 支持的 DBOS 工作流运行,使用确定性解释器在虚拟事件循环上执行,所有非确定性操作都在 Postgres 中设置检查点。活动和计时器成为 DBOS 步骤,信号和更新通过 Postgres 的 LISTEN/NOTIFY 传递,支持故障恢复和精确一次执行。 注意:这不是协议兼容的替代品,不支持其他语言的 Temporal SDK,也不支持 Temporal Web UI 或 CLI。

评论摘要
主要讨论点：DBOSify与Temporal的关系及其实现方式 不同观点： • **兼容性质疑（antman）**：询问DBOSify是否能通过Temporal Python SDK的测试套件，以及是否有未实现的功能，暗示对其"替代品"声称的验证需求 • **定位混淆（unsnap_biceps）**：指出项目描述存在矛盾——既说是Temporal的替代品，又说是Python客户端SDK的替代品；同时质疑"只需Postgres"的说法，因为架构图显示仍需worker节点作为额外基础设施 • **创建者回应（KraftyOne/Peter）**：项目创建者出现但尚未提供实质性解答 补充讨论：核心争议聚焦在DBOSify的准确定位和基础设施需求上。unsnap_biceps的质疑揭示了营销说法与技术实现之间可能存在的gap——声称"无需基础设施"但实际仍需worker节点。这是典型的"简化vs准确"的沟通问题。

Why Carbon Capture Can't Conceivably Solve Climate Change

文章摘要

这篇ProPublica和Drilled的调查报道揭露了碳捕获与封存(CCS)技术的局限性。40多年来,石油公司资助大学研究这项技术,但实际部署远未达到预期目标。要在2050年实现每年60亿吨CO2封存,需要建设6.8万英里管道(超过美国州际公路系统总长)、开辟2000多个地质储存库(相当于未来25年每4天新建一个)、占用76.8万平方英里土地种植吸碳植物。即使实现,每年成本也将达5000亿美元。目前全球实际封存量还不及一座大型电厂的年排放量。报道质疑这项技术能否真正解决气候危机。
