Using JWT to establish a trusted context for Row Level Security

作者: JeanSebTr | 评分: 26 | 评论数: 5 | 发布时间: 2025-08-29 13:32
文章摘要

本文探讨了PostgreSQL中行级安全(RLS)功能的实现挑战，并提出使用JWT(JSON Web Tokens)建立可信上下文的解决方案。作者指出传统RLS依赖数据库角色存在诸多不足，如管理复杂、与连接池不兼容等问题。文章提出通过数字签名技术(JWT)构建加密可信上下文，使数据库能验证上下文来源的真实性和完整性，从而安全地用于RLS策略。作者介绍了对称(HMAC)和非对称(RSA/ECDSA)加密方案的优缺点，并发布了一个实验性扩展jwt_context来实现这一构想。最后，作者邀请社区就这种使用JWT的方式提供反馈意见。

评论摘要
主要讨论点：[使用JWT实现数据库行级安全(RLS)的不同方法和潜在问题] 不同观点： • MattPalmer1086分享了一种20年前的非JWT方案，通过会话令牌和角色缓存实现RLS，虽然性能消耗大但稳定运行7年 - 优点：实际验证过长期可用性 - 缺点：30%性能开销，维护复杂导致最终被替换 • conradludgate介绍了Neon的JWT实现方案 - 采用严格的双层验证：连接池签发临时JWK，每次请求新签JWT - 安全措施：单调递增token ID防止伪造，DISCARD ALL清除上下文 - 设计理念：信任连接池而非客户端 • some_furry强烈反对使用JWT - 指出JWT存在经典安全漏洞（提供多个CVE链接） - 推荐替代方案：PASETO（更安全的令牌标准） • Apaec和themafia提供现有实践参考 - PostgREST长期使用JWT实现认证 - 建议兼容OAuth标准流程，在现有令牌中扩展属性 补充讨论： [争议焦点] • JWT的安全性问题是否可规避 vs 是否应该直接采用更安全的替代方案 • 复杂定制方案（如Matt的方案）的长期可维护性问题 [技术细节对比] • 上下文管理方式：临时令牌 vs 缓存方案 • 性能考量：连接池开销 vs 缓存构建开销

Zfsbackrest: Pgbackrest style encrypted backups for ZFS filesystems

作者: sphericalkat | 评分: 52 | 评论数: 2 | 发布时间: 2025-09-01 13:35
文章摘要

该项目是一个实验性的ZFS文件系统备份工具，模仿pgbackrest风格，提供加密备份功能。主要特点包括： 1. 支持全量、差异和增量备份，依赖关系明确 2. 强制使用age加密，不提供非加密选项 3. 支持S3存储后端 4. 提供备份清理功能，可自动删除过期和孤立的备份 5. 基于ZFS快照实现，不影响原始数据集 项目处于早期开发阶段，警告用户不要将其作为唯一备份方案。提供安装、配置、备份、恢复等基本操作说明，使用Go语言编写，采用MIT许可证。

评论摘要
主要讨论点：[是否适合使用ZFS send流作为备份格式] 不同观点： • **反对使用ZFS send流作为备份格式** - 论据：ZFS send流（无论是全量还是增量）缺乏数据恢复的弹性，一旦流损坏就无法使用。 - 论据：增量流依赖于其基础数据，没有基础数据则完全无用。 - 论据：缺乏选择性恢复和易于访问的索引，长期使用会带来问题。 - 来源：引用了一篇博客文章，详细列举了ZFS send流的局限性。 • **支持使用ZFS send流作为备份格式** - 论据：对于大型PostgreSQL数据库，基于文件的备份方式（即使是增量备份）扩展性较差。 - 论据：ZFS send流作为一种工具，可以解决特定场景下的备份需求。 - 例子：用户表示长期寻找此类解决方案，认为其在实际应用中非常有用。 补充讨论： - 争议焦点在于ZFS send流的可靠性和适用场景。反对者强调其技术缺陷，而支持者则从实际需求出发，认为其解决了特定问题。 - 讨论中还隐含了对备份格式选择的权衡：是选择技术上的完美性，还是选择实际应用中的便利性。
