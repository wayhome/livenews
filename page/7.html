Microsoft Office Lens getting the axe

作者: zanmat0 | 评分: 9 | 评论数: 1 | 发布时间: 2025-08-09 22:45
文章摘要

Microsoft Lens, a popular mobile document scanning app, will be discontinued starting September 15, 2025. The app, which converts documents, receipts, and business cards into digital files, will be removed from app stores by November 15, 2025. Existing users can continue scanning until December 15, 2025, after which scanning functionality will cease, though previous scans will remain accessible. Users are being directed to Microsoft's Copilot AI app, which lacks several key features of Lens, such as direct saving to OneNote, Word, or PowerPoint, and accessibility functions like read-out-loud. Despite its popularity, with over 92 million downloads since 2017, Microsoft has not provided a reason for the shutdown.

Gateway pattern for external service calls

作者: linhns | 评分: 5 | 评论数: 1 | 发布时间: 2025-08-06 12:30
文章摘要

本文讨论了在编写服务时，如何将外部依赖与业务逻辑分离，特别是在Go语言中。通常会创建一个名为`external`或`http`的包，将与外部服务通信的逻辑放在其中，而业务逻辑依赖该包来调用RPC。这种做法比在业务函数中直接进行RPC调用更好，因为直接调用会使业务逻辑与外部服务紧密耦合，难以单独测试。 这种模式被称为**Gateway模式**。根据**依赖倒置原则**，高层次模块（业务逻辑）不应依赖低层次模块（外部服务），两者应依赖于抽象。具体实现中，业务逻辑通过接口与外部包交互，接口由业务逻辑定义，而不是由外部包实现。 示例项目结构如下： ``` yourapp/ ├── cmd/ ├── order/ ├── external/ └── go.mod ``` 在`external/stripe/gateway.go`中，实现与Stripe API的通信细节，但不由此导出接口。接口由`order`包根据其需求定义，以确保只依赖所需的方法，并在测试中进行模拟。这种设计符合**接口隔离原则**，避免依赖不必要的方法。

评论摘要
主要讨论点：Uncle Bob的评论是否指的是服务依赖注入，以及其解释是否清晰易懂。 不同观点： • 观点一：Uncle Bob的评论可能指的是服务依赖注入（dependency injection of services）。这种观点认为Uncle Bob在讨论一种编程实践，即通过依赖注入来管理服务，但表达方式让人感到困惑。 • 观点二：Uncle Bob的解释令人困惑，特别是在其成为标准实践之前。这种观点指出，Uncle Bob的解释可能是在依赖注入成为普遍做法之前给出的，因此对于不熟悉这一概念的人来说，理解起来有难度。 补充讨论： • 争议焦点在于Uncle Bob的解释是否清晰。有人认为他的解释可能会让初学者感到困惑，因为当时依赖注入尚未成为广泛接受的标准实践。 • 例子：评论中提到，Uncle Bob的解释让人觉得混乱，暗示可能有其他更清晰的方式来解释这一概念。 • 讨论关系：两种观点都承认Uncle Bob在讨论依赖注入，但在其解释的清晰度和时机上存在分歧。一方认为时机导致了理解困难，另一方则关注解释本身的问题。

Claude Code IDE integration for Emacs

**Claude Code IDE for Emacs** 是一个将 Claude Code CLI 深度集成到 Emacs 的工具，通过模型上下文协议（MCP）实现双向通信。它使 Claude 能够利用 Emacs 的强大功能，如 LSP、项目管理、自定义 Elisp 函数等，成为真正的 Emacs 感知 AI 助手。主要功能包括自动项目检测、终端集成、工具支持、诊断集成、高级 diff 视图、标签栏支持、选择和缓冲区跟踪等。Claude 可以直接访问 Emacs 的各种功能，如代码导航、语法树分析、项目操作等，提供更智能、更具上下文感知能力的帮助。安装需要 Emacs 28.1 及以上版本和 Claude Code CLI，并可通过 `use-package` 进行配置。

评论摘要
主要讨论点：Emacs和Vim等老牌编辑器如何整合现代AI编码工具（如Claude Code和Aider），以及这些工具对编辑器竞争力和用户体验的影响。 不同观点： • **支持整合AI工具的观点**： - 像Emacs和Vim这样的编辑器通过与Claude Code或Aider等AI工具整合，可以更轻松地获得高级IDE功能，而无需自己实现。这使得这些编辑器更具竞争力，因为它们本身已经高度可定制且易于与新工具整合 ([blahgeek])。 - Emacs由于其高度可定制性（如通过elisp改变编辑器行为）可能特别适合AI代理，具有巨大的优势 ([yoyohello13])。 - 有人已经开始使用Claude Code整合工具，并创建了高效的工作流，如使用`claude-code.el`和`eca-emacs`，虽然新工具的采用需要谨慎 ([vemv], [pjm331])。 - Emacs的历史与MIT AI Lab密切相关，拒绝AI工具的整合似乎与其历史不符 ([cml123])。 • **对整合持保留或质疑态度的观点**： - 一些用户发现Emacs配置越来越复杂，尤其是与LSP和tree-sitter的整合，可能导致配置问题。虽然Claude Code在某些情况下易于配置，但其他工具（如gopls）仍然存在问题 ([Karrot_Kream])。 - 有人质疑Emacs用户与“采用AI代理编码”的开发者之间是否存在显著重叠，认为这两类人群可能并不重合 ([efitz])。 • **对AI工具的实际应用和本地化需求**： - 用户希望AI工具能与Emacs的org模式或其他笔记功能整合，以便构建知识库，而不是像GitHub Copilot那样删除对话 ([wwarner])。 - 有用户关心是否能以较低成本在本地运行AI工具，并希望能够切换模型提供商以节省成本和提高效率 ([megaloblasto], [eulers_secret])。 • **对敏感数据安全的担忧**： - 一些用户担心在Emacs或Vim中使用AI工具可能导致敏感数据（如SSH密钥）被上传到LLM。有人提出使用bubblewrap等解决方案来隔离实例 ([qalmakka])。 • **对Neovim的关注**： - 一些用户询问Neovim中是否有类似AI工具的整合方案，并希望这些工具也能在Vim中实现 ([cristea], [brotherjerky])。 补充讨论： - 有多个Emacs/Claude Code整合包可供选择，但有些包未被广泛讨论，可能具备所有需要的功能 ([wyuenho])。 - 有开发者专注于开发适用于Emacs的AI配对编程工具，如`eca-emacs`，并希望进一步改进这些工具 ([ericdallo])。 争议焦点： - Emacs和Vim等老牌编辑器是否应整合现代AI工具，特别是考虑到配置复杂性和敏感数据安全问题。
