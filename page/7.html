Fluid Simulation for Dummies (2006)

作者: sebg | 评分: 61 | 评论数: 7 | 发布时间: 2026-05-30 16:46
文章摘要

这篇文章是Mike Ash关于流体模拟的入门教程。作者在2005年完成了3D流体模拟的硕士论文后,发现现有资料过于理论化,因此写了这篇面向程序员的实用指南。 文章基于Jos Stam的实时流体动力学论文,通过将流体看作相互作用的网格单元来简化Navier-Stokes方程。重点讲解不可压缩流体(如水)的模拟,通过添加染料来可视化流动。 代码实现使用3D数组存储流体属性(密度、速度),定义了FluidCube结构体,包含网格大小、时间步长、扩散系数、粘度等参数,以及密度和三维速度的数组。文章强调实际编程实现,适合希望快速上手流体模拟的开发者。

评论摘要
主要讨论点：关于流体模拟技术的不同层次理解和应用场景 不同观点： • **实用图形派（luismedel）**：强调早期demo场景中的水效果实现，展示了通过简化物理模型（当a²Δt²/h²=½时）可以用极少运算（仅4次加减和1次位移）实现视觉效果，代表"够用就好"的工程思路 • **物理准确派（cherryteastain）**：批评文章物理概念不严谨，指出多处错误——可压缩性应看马赫数而非流体类型、不可压缩不等于压力恒定。强调真实CFD求解器需要处理压力梯度项和泊松方程，这是最昂贵的计算步骤，与文章展示的简化方法完全不同 • **教学资源派（otterdude）**：认为文章缺乏科学性和洞察力，作者承认不理解部分代码。推荐Lorena Barba的CFD教程作为更系统的学习路径 • **应用需求派（jlhawn）**：关注可压缩流体的实现，想要构建大气模型但因复杂度受阻，寻找近20年的新资源 补充讨论：有评论提到这是2006年的旧文章，也有人单纯表达对作者其他技术博客（如Friday Q&A）的欣赏。核心争议在于**图形渲染的视觉近似与科学计算的物理准确性之间的取舍**。

When does fragmentation occur in the CUDA caching allocator?

作者: matt_d | 评分: 10 | 评论数: 1 | 发布时间: 2026-06-01 18:43
文章摘要

这篇文章主要讨论 PyTorch CUDA 缓存分配器中的内存碎片问题。 **核心问题**：尽管有足够的空闲内存，分配器仍可能无法满足请求。 **原因**：分配器将 GPU 内存组织为段(segments)和块(blocks)两层结构。分配时会分割块，释放时会合并相邻的空闲块。关键限制是**不同段中的块无法合并**。 **典型场景**：在 LLM 服务等需要最大化内存利用的应用中，分配顺序会导致碎片。例如先分配小块再分配大块时，可能创建多个无法合并的段，导致浪费。 **解决方案**：文章介绍了"可扩展段"(expandable segments)特性如何通过允许段动态增长来缓解碎片问题，特别是在 CUDA 图录制等场景中。

评论摘要
这条评论只有一个作者的观点，没有多方讨论。以下是分析： **主要讨论点：** LLM服务中的内存分配策略，特别是如何处理长期存在的权重/图缓冲区与短期KV缓存的碎片化问题 **核心观点：** • 作者认为长期块与短期块交错导致的碎片化是LLM服务的常态而非边缘情况——模型权重和图缓冲区永久驻留，而每个请求的KV缓存频繁创建和销毁 • 可扩展段(expandable segments)无法跨越合并这种混合场景，因此标准缓存分配器不适用 • 解决方案是放弃依赖缓存分配器管理KV缓存，改为在上层自行管理：vLLM在启动时预留大内存区域，用固定大小的块进行分页管理，让底层分配器完全看不到KV的频繁分配释放 • 这种方法将碎片化问题提升一层解决——虽然碎片化依然存在，但通过应用层的显式内存管理避免了分配器层面的问题 **技术背景：** 这是针对GPU内存管理的专业讨论，涉及PyTorch缓存分配器的局限性和vLLM等推理框架的优化策略。

文章摘要

这篇文章揭露了一个VSCode/GitHub的安全漏洞。攻击者可通过点击链接窃取GitHub token，该token能读写用户的所有仓库（包括私有仓库）。 漏洞原理：GitHub的github.dev功能在浏览器中运行VSCode，使用OAuth token进行操作。VSCode使用webview（iframe）隔离不受信任内容，通过postMessage API实现跨域通信。但由于VSCode需要支持键盘快捷键等基础功能，存在安全边界被突破的风险。 文章详细分析了VSCode的webview安全模型、跨域隔离机制，以及攻击者如何利用这一机制中的缺陷来窃取敏感token。

评论摘要
主要讨论点：关于 VSCode/GitHub 网页版编辑器存在 1-Click 窃取 GitHub Token 漏洞的安全事件及其披露处理 不同观点： • **架构设计问题**：网页版 VSCode 与 GitHub 账户深度集成是原罪，应该采用单仓库临时权限模型，避免完整 Web 会话权限（zbentley） • **微软响应评价分歧**： - 正面：修复速度快，是见过最快的厂商响应之一（ammar2） - 负面：MSRC 长期表现糟糕，经常静默修复不给研究者反馈，已失去研究者信任（NagatoYuzuru, parable） • **披露方式争议**： - 支持全面公开：感谢作者公开披露提升安全意识，迫使 MSRC 改进（Noumenon72, parable） - 质疑披露流程：应该披露后等待一周再发布，避免负面影响，证明真正关心安全而非寻求认可（lionkor） • **扩展生态风险**：VSCode 扩展与编辑器同权限运行，开发者安装数十个扩展却不审查权限，应使用隔离配置文件（AgentReinAi） • **工具选择反思**：质疑为何不用 Neovim 等轻量工具，复杂的扩展、同步、token 系统难以掌控访问权限（meszmate） 补充讨论：多位开发者分享被窃取 token 的亲身经历，强调零信任原则和损害隔离的重要性；技术细节讨论集中在本地扩展绕过 CSP、快捷键绑定等攻击链条的实现机制。
