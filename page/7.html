Carmack on Operating Systems (1997)

作者: bigyabai | 评分: 71 | 评论数: 8 | 发布时间: 2025-10-25 00:59
文章摘要

约翰·卡马克在1997年3月18日的.plan文件中主要讨论了《雷神之锤2》的扩展机制和技术平台选择。主要内容包括： 1. 扩展机制：首选DLL接口，考虑过Java但实现成本过高，QC语言等其他方案可能性很低。将发布《雷神之锤1》的QC接口和解释器代码。 2. 平台选择：明确Win32是首要平台，NT优先开发；不再支持DOS；Linux因黑客社区支持成为第二重要平台；对其他平台（MacOS、OS/2、Unix等）持不同保留态度。 3. 开发偏好：个人最喜爱NeXTSTEP环境，认为其综合优势最强。 全文反映了卡马克务实的技术决策思路，在商业考量与技术创新间寻求平衡，同时表达了对不同操作系统的技术评价。

/dev/null is an ACID compliant database

文章摘要

这篇文章以幽默的方式将Linux系统中的/dev/null设备比作一个完美的ACID合规数据库。作者从数据库的四个关键特性（原子性、一致性、隔离性和持久性）逐一论证：写入/dev/null的数据要么全部消失（原子性），始终保持空状态（一致性），并发写入互不干扰（隔离性），且"丢失"的数据在系统崩溃后也不会恢复（持久性）。最后作者调侃说这个"数据库"唯一的问题是存储空间为零，需要联系企业销售（其实就是作者本人）扩容。文章用技术术语玩了一个巧妙的文字游戏，展现了程序员式的幽默。

评论摘要
主要讨论点：对/dev/null作为数据库或存储解决方案的幽默讨论，以及对其是否符合ACID特性的争议。 不同观点： • **支持/dev/null作为理想数据库的观点** - 认为/dev/null具备高可用性、一致性和分区容忍性（CAP），可以无限扩展（cluckindan）。 - 指出其符合部分ACID特性，如原子性（A）、一致性（C）和隔离性（I），但缺乏持久性（D）（brunoborges）。 - 类比为数学中的“平凡解”，强调其简单性（magicalhippo）。 • **质疑/dev/null的实用性** - 指出/dev/null不符合严格的可序列化（serializable）或持久性（Durability）要求（mjb、brunoborges）。 - 认为其状态单一，无法实现真正的状态转换（jefftk）。 • **幽默类比与延伸讨论** - 提到类似的笑话概念，如“写仅内存”（WOM）（torcete、phendrenad2）。 - 引用其他幽默项目，如MangoDB（xandrius）和S4存储服务（tech234a）。 补充讨论： - **争议焦点**：主要围绕/dev/null是否符合ACID中的持久性（D）以及是否具备真正的数据库功能。 - **实际应用场景**：有人提到/dev/null在开发中作为临时输出目标的实用性（pyuser583）。 - **安全性问题**：讨论了/dev/null是否可能被滥用或数据是否可被其他进程访问（dd_xplore）。

How memory maps (mmap) deliver faster file access in Go

作者: ingve | 评分: 129 | 评论数: 18 | 发布时间: 2025-10-23 21:56
文章摘要

本文介绍了内存映射（mmap）技术在Go语言中的应用及其性能优势。内存映射通过将文件直接映射到虚拟内存，避免了昂贵的系统调用，使文件访问速度大幅提升。测试数据显示，mmap的随机查找和迭代操作比传统ReaderAt方法快25倍以上。然而，mmap在写入操作中存在性能问题，特别是当页面未映射到物理内存时。文章还分享了作者在实际项目中使用mmap优化HTTP文件系统的经验，实现了显著的性能提升。

评论摘要
主要讨论点：[mmap的性能优势与适用场景] 不同观点： • **支持mmap的观点**： - [Ingon]提到在klevdb中使用mmap后性能显著提升，尤其是随机读取速度。 - [lzaf]通过基准测试显示mmap在读/写大文件时性能优于传统文件IO（如`os.File`）。 - [liuliu]认为mmap是快速实现预加载和跨进程缓存管理的“足够好”方案，尤其在缺乏高级异步IO（如io_uring）时。 • **反对或质疑mmap的观点**： - [buybackoff]指出基准测试不公，认为mmap未实际读取数据，仅返回数据地址，而传统文件IO涉及缓存复制。 - [nteon]提到Go运行时对mmap的页错误处理不佳，可能导致线程阻塞和利用率下降。 - [philippta]引用Casey Muratori的观点，认为mmap在顺序读取时性能更差，因CPU预取效率低。 - [charlietap]批评mmap适用场景狭窄，多数程序只需顺序读取缓冲区，而非随机小规模读取。 • **中立或技术限制观点**： - [gustavpaul]强调mmap的SIGBUS风险和数据访问延迟不可预测性问题。 - [karel-3d]指出mmap在内存不足时表现糟糕，且Go的pprof工具难以调试mmap内存占用。 - [habibur]质疑现代系统中mmap是否仍比`fread`快，因文件可能已被缓存到内存。 补充讨论： - **争议焦点**： 1. **基准测试的合理性**：是否公平比较了数据实际访问（如[buybackoff]与[gustavpaul]争论）。 2. **适用场景**：mmap是否仅适合随机读取（如[charlietap]与[Ingon]的分歧）。 3. **现代系统优化**：文件缓存是否削弱了mmap的优势（[habibur]的疑问）。 - **其他讨论**： - [benjiro]认为HTTP请求的瓶颈可能掩盖mmap的优化效果。 - [Animats]对Linux mmap的写时复制行为表示意外。 - [commandersaki]质疑文章与Varnish Cache的关系。
