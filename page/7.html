How to make things slower so they go faster

作者: neehao | 评分: 119 | 评论数: 11 | 发布时间: 2025-08-24 05:10
文章摘要

本文主要讨论了同步需求现象及其对系统的影响。同步需求指大量客户端几乎同时发起请求的情况，可能导致系统过载、队列积压和级联故障。文章分析了同步需求的自然来源（如定时任务、缓存过期）和人为因素（如系统重启、DDoS攻击），并指出系统资源瓶颈可能导致性能急剧下降。 为缓解这一问题，作者提出通过分散请求负载来降低峰值压力，并推导出最优延迟分配方案。关键解决方法是：确定系统可用容量后，合理设置时间窗口W来均匀分布请求，同时考虑延迟和公平性。文章给出了量化公式，指导如何计算最小W值以避免过载，并建议采用统一抖动机制来优化请求调度。 最后，作者强调需要权衡峰值降低与延迟增加的关系，并根据系统约束条件选择最佳策略，必要时可通过增加容量或放宽要求来解决问题。

这篇文章探讨了"危险建议"的价值，作者认为像SSH或SQL控制台这样的强大工具一样，某些职业建议虽然风险高但效果显著。作者列举了自己常给出的危险建议，如鼓励读者自主决定工作重点、偶尔打破公司规则等。文章指出优秀工程师渴望这种真实建议，而管理者通常不会提供这类建议以避免责任。作者认为危险建议虽然高风险高回报，但对有能力的工程师特别有价值，并强调不适合的人不应盲目跟随。

评论摘要
主要讨论点：[在组织中何时以及如何打破规则，以及规则在组织中的作用和影响] 不同观点： • **功能性组织 vs. 功能性失调组织** - 在功能性组织中，可以策略性地打破规则，但需在获得上级信任后进行。 - 在功能性失调的组织中，打破规则可能被用来诋毁你，因此应优先保护自己。 • **规则遵守者与规则打破者的平衡** - 组织需要既有遵守规则的人（“水手”）也有打破规则的人（“海盗”）才能有效运作。 - 引用Dimitri Glazkov的“水手与海盗”框架支持这一观点。 • **规则制定者的视角** - 规则制定者通常基于不完美的信息，且未必是规则的执行者，容易制定不切实际的规则。 - 管理者应亲身体验开发过程，避免制定过于低级的规则。 • **规则打破的“正确性”** - 打破规则的前提是必须“正确”，即你的想法和技能足够支撑你的行为。 - 引用Tom Cruise的“不要小心，要胜任”来强调能力的重要性。 • **激励与道德** - 在功能性失调的组织中，员工可能为了个人利益而损害公司利益，导致组织进一步恶化。 - 建议寻找更好的公司或创业，而非牺牲道德和工艺精神。 • **危险建议的适用范围** - 对于缺乏经验的人来说，“危险建议”可能带来实际风险，尤其是遗留项目中已存在的技术债务。 - 只有对过度谨慎的人才需要鼓励他们突破限制。 补充讨论： - **规则的目的**：规则旨在约束判断力差的工程师，而非束缚有良好判断力的人。 - **争议焦点**：是否所有工程师都有能力判断何时打破规则？部分评论认为只有顶尖工程师（如前5%）才有这种自由。 - **实践中的复杂性**：不同组织和文化背景下，规则的适用性和打破规则的后果差异巨大，需根据具体情境调整策略。

An illustrated guide to OAuth

文章摘要

这篇文章通过YNAB连接Chase银行的例子，简明介绍了OAuth授权协议的运行机制。OAuth诞生于2007年，旨在解决第三方应用安全访问用户数据的问题，避免了直接分享密码的风险。核心流程分两部分：1)用户授权流程：用户被重定向到银行登录，选择授权范围后生成授权码；2)令牌交换流程：应用通过安全后端请求用授权码换取访问令牌。关键创新点在于使用授权码间接获取访问令牌，避免了令牌直接暴露在URL中的安全隐患，确保了数据传输的安全性。整个过程实现了第三方应用无需知道用户密码就能获得特定权限的访问令牌。

评论摘要
主要讨论点：[OAuth/OIDC 的实现难点、文档质量、安全性问题及不同授权流程的比较] 不同观点： • **实现困难与文档不足** - [gethly] 和 [osdev] 认为 OAuth 的概念虽然简单，但实际实现时缺乏具体、可操作的代码示例，导致难以落地。建议增加如 Curl 请求等实用示例。 - [losvedir] 提到 OAuth2 框架包含多种授权流程（如 Client Credentials、JWT Bearer），但当前讨论多集中于“3-legged redirect”流程，其他流程的上下文较少。 • **安全性争议** - [homakov] 批评 OAuth2 设计存在结构性缺陷，如账户劫持、Referrer 泄露、CSRF 令牌（state）的忽视等，并附上解决方案链接。 - [TofuLover] 和 [tbarbugli] 反驳关于 URL 明文传输的观点，指出 HTTPS 下查询参数是加密的，但 [homakov] 提到的漏洞（如 redirect hijack）仍需关注。 - [fcpguru] 补充历史案例，提及 OAuth 1.0a 因会话固定（session fixation）攻击而紧急推出的背景。 • **解释方式与工具建议** - [languagehacker] 和 [chrisgd] 赞赏当前文章的类比（如啤酒园）和插图，认为有助于理解。 - [Pet_Ant] 建议增加动画或幻灯片以增强解释效果。 - [politelemon] 和 [losvedir] 呼吁补充 PKCE（Proof Key for Code Exchange）相关内容，强调其流完整性作用，而非“安全性较低”。 • **技术细节讨论** - [losvedir] 提出多租户系统中 OAuth2 的挑战（如 self-hosted 应用的 `redirect_uri` 管理、Client Credentials 流程的适配），并寻求实践经验分享。 - [tiffanyh] 类比 OAuth 与 Open Banking，质疑两者为何被视作不同事物，引发对协议定位的思考。 补充讨论： - 争议焦点：OAuth2 的安全性（如漏洞是否被夸大）及实现优先级（如 PKCE 的实际作用）。 - 工具推荐：[gethly] 提到借助 AI（如 Grok）解析晦涩的规范文档。 - 历史背景：[fcpguru] 提及 OAuth 1.0a 的紧急修复事件，侧面反映协议演化中的实践教训。
