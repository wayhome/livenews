Closing the Chapter on OpenH264

作者: todsacerdoti | 评分: 62 | 评论数: 9 | 发布时间: 2025-03-25 09:59
文章摘要

本文讨论了在Freedesktop SDK中移除OpenH264的决策过程和历史背景。Freedesktop SDK最初是为了提供独立于主机的“运行时”环境，现已发展成一个社区维护的项目，提供最小Linux运行时，包括Flatpak运行时和扩展。由于H.264编解码器受专利保护，无法直接包含在基础运行时中，因此在2019年通过Tom Coldrick引入的html5-codecs扩展绕过这一问题。随后，Robert McQueen提议使用Cisco的OpenH264，但由于法律限制，只能通过额外数据支持方式在用户端下载和安装。为解决兼容性问题，Endless提出了一个名为noopenh264的库作为临时方案。然而，由于Freedesktop运行时的每年主要版本都是全新ABI，维护OpenH264扩展变得繁琐，最终导致决定将其移除。

评论摘要
主要讨论点：视频编解码器的未来发展及其专利问题，尤其是AV1和H.264/H.265的比较和应用场景 不同观点： • [ray023] 认为AV1有光明的未来，但目前场景组仍主要使用H.265。随着硬件支持的提升，希望未来能够广泛采用AV1，摆脱专利问题的困扰。 • [xfp] 指出H.264是目前唯一在聊天/消息客户端、浏览器、智能电视/手机、平板电脑和流媒体设备上具有一致支持的编解码器。由于大量设备和软件仍在使用H.264，如果不想提供多种编码，H.264是唯一可行的选择。 • [jsiepkes] 提到在欧洲算法不能被专利，因此像MP3在欧洲是免专利费的，并询问H.264是否也已经在欧洲免专利。 • [ksec] 补充说，除了美国，H.264的高配置文件将在今年八月后免专利。 • [hcfman] 担心如果不使用H.264或H.265，是否还能在所有浏览器版本上实现类似WebRTC的功能，因为H.264的兼容性最好。 • [userbinator] 提出通过下载源代码并在用户机器上编译来规避二进制文件的分发限制，从而避免专利问题。 • [mastax] 认为开源项目通常选择忽视专利问题，并质疑Canonical为什么没有因为分发FFmpeg而被起诉。 • [robert_foss] 强烈批评H.264和H.265的专利问题，认为应尽量避免使用它们，并希望AV1的继任者尽快出现。 补充讨论： • 专利问题在不同地区的差异，尤其是在欧洲和美国的法律差异，影响了编解码器的采用。 • 关于如何规避专利限制的技术方法，如通过源代码编译或使用特定容器格式。 • 争议焦点在于是否应继续使用受专利保护的H.264/H.265，还是推动免专利但支持较少的AV1。

Mruby/C and picoruby: high level langs in low-level devices?

作者: rahil627 | 评分: 62 | 评论数: 10 | 发布时间: 2025-03-23 09:20
文章摘要

PicoRuby 是一个专为单片微控制器设计的微型 Ruby 实现，具有小尺寸和可移植性特点。它在 32 位架构下仅需 256 KB ROM 和 128 KB 或更少的 RAM。PicoRuby 依赖标准 C 库，如 glibc 或 Newlib，并支持 Raspberry Pi Pico 等微控制器板。它提供了 API 文档和演示视频，并依赖于 mruby/c 实现的虚拟机。PicoRuby 可用于构建 PRK Firmware 键盘固件和 PicoRuby WASI WebAssembly 运行时。构建过程需要 C 工具链、git 和 Ruby 3.0 以上版本。项目仍在开发中，遵循 MIT 许可协议，并获得了 Ruby Association Grant Program 的支持。

评论摘要
主要讨论点：微控制器上不同编程语言和工具的适用性及优缺点 不同观点： • **支持MicroPython**：[throwaway81523] 认为MicroPython非常流行，适合在能支持它的设备上使用，尤其是像Adafruit Trinket这样具有256KB闪存和32KB RAM的设备。虽然MicroPython在只有16KB RAM的BBC micro:bit上运行比较困难，但在多数小型设备上表现良好。另外，提到Lua和Hedgehog Lisp作为更小的选择，以及Javacard和J2ME在特定设备上的使用。对于极小设备，建议放弃垃圾回收机制，使用Forth或交叉编译语言。 • **MicroPython与C的结合**：[jononor] 喜欢MicroPython，并指出它易于与C语言结合使用，这对于在微控制器设备上获得最佳性能非常必要。 • **支持picoruby**：[aidog] 推荐picoruby，认为它非常有趣，是mruby/c的更小版本。他还分享了HASUMI Hitoshi的演示视频，展示了picoruby在Raspberry Pi Pico及其他微控制器上的应用。 • **支持高层次语言在微控制器上运行**：[calebh] 介绍了Juniper，一种用于Arduino的功能反应式编程语言，证明了高层次代码（如闭包）也可以在小型设备上运行。 • **提供picoruby的资源**：[xutopia] 提供了picoruby的文档链接，供感兴趣的人查阅。 • **再次推荐MicroPython**：[TkTech] 提到MicroPython在这个领域占据主导地位，并提供了GitHub链接供进一步了解。 • **对C语言的争议**：[rahil627] 提到有些人不喜欢使用C语言，而有些人则喜欢并拥抱它。同时提出疑问，Ruby这样的复杂语言在微控制器（如传感器）上是否有意义，并表示对pico上Ruby实现的维护感到欣赏。 • **提到Shedskin Python到C++编译器**：[actionfromafar] 提到了Shedskin，一个Python到C++编译器，作为另一种选择。 • **对设备存储的看法**：[bsder] 认为256KB闪存和128KB RAM已经不算小，比1990年之前的平均计算机还大，并指出RAM和闪存的大小对微控制器的价格有很大影响。 补充讨论： • 讨论中涉及多种语言和工具，如MicroPython、picoruby、Lua、Hedgehog Lisp、Forth、Juniper、Javacard和J2ME，反映了在微控制器上运行不同类型语言的可行性和实用性。 • 争议焦点在于是否在微控制器上使用复杂语言如Ruby，以及C语言是否真的不适合这些场景。 • 不同语言和工具的支持者提供了各自的资源和演示，展示了它们在微控制器开发中的实际应用和优势。
