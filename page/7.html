Tokenization for language modeling: BPE vs. Unigram Language Modeling (2020)

作者: phewlink | 评分: 65 | 评论数: 7 | 发布时间: 2025-05-30 08:59
文章摘要

本文讨论了常见语言模型（如BERT和GPT-2）在词 tokenization 过程中出现的问题，即这些模型经常错误地分割单词，导致对词义的误解。例如，模型可能将 "destabilizing" 错误地解析为 "dest-abilizing"，从而无法识别 "de-" 作为否定前缀的作用。这种分割问题源于使用字节对编码（BPE）进行词汇构建，其主要目标是压缩数据集，而非保留词素的形态结构。尽管如此，BERT和GPT-2仍能取得出色结果，但本文提出，更好的 tokenization 方法可能有助于提升模型性能，减少训练数据需求。近期研究表明，使用单gram语言模型（unigram language modeling）替代BPE，可以在下游任务中提升模型表现，表明改进 tokenization 可能带来益处。

评论摘要
主要讨论点：围绕AI模型的分词算法、可解释性、以及在实际应用中的优缺点和改进方向的讨论。 不同观点： • [janalsncm] 提到Meta的最新研究，使用神经网络进行分词，与传统基于预定义列表的分词方法相反。这种方法虽然新颖，但会增加调试难度，降低可解释性。 • [mrkramer] 认为LLM（大型语言模型）的“幻觉”问题在严肃工作中是个缺点，但在某些创意领域（如诗歌、歌词创作或商业创意生成）中，这种“幻觉”可能是有益的，因为越疯狂的想法有时越有价值。 • [macawfish] 表示当前追求更大模型的趋势忽略了语义信息的利用，认为这是一个低成本高回报的改进方向。 • [wejick] 感叹近年来AI讨论的氛围变化迅速，反映出技术发展的迅猛步伐。 • [anonymoushn] 关注SentencePiece的初始词汇选择过程，询问如何确定最终具有理想特性的词汇。 • [pbronez] 希望看到更新的资料，了解当代分词器在算法上的改进。 补充讨论： • [Lerc] 详细描述了自己在实验中对分词的处理方法，包括避免语义问题，使用BPE（字节对编码）处理标点和空格，以及自定义的分词和编码策略。他还提到未来可能改进的方向，如对多语言的统一编码和处理同音词的策略。 • 争议焦点：不同分词方法在可解释性和调试难度之间的权衡。神经网络分词方法虽然灵活，但增加了调试和解释的难度，而传统方法虽然直观，但可能无法充分利用语义信息。 总结：讨论涉及AI分词算法的设计、优缺点以及在不同应用场景中的价值。参与者们对如何改进现有分词器提出了不同看法，包括对多语言处理、同音词处理以及语义信息的更好利用等。

The radix 2^51 trick (2017)

作者: blobcode | 评分: 384 | 评论数: 16 | 发布时间: 2025-05-30 03:55
文章摘要

本文讨论了在现代CPU上加速大整数加减运算的方法。传统的手算加法从最低位开始，逐位相加并处理进位，这种方法类似于我们通常的编程实现。然而，由于进位依赖于前一位的计算结果，这种方法难以并行化，导致在现代CPU上的效率较低。 现代CPU可以通过并行执行多个简单的加法指令（如`add`）来提高性能，但处理进位的`adc`指令更为复杂且依赖前一个指令的结果，导致无法并行执行，性能下降。 文章进一步探讨了通过避免进位来提升性能的可能性，提出了类似于“无进位加法”的方法，这种方法在理论上可以通过预处理数字来减少对进位的依赖，从而提升并行计算的效率。 最终，通过重新设计算法以减少或消除进位依赖，可以在现代CPU上显著加速大整数的加减运算。

评论摘要
主要讨论点：关于使用AVX和相关技术优化加法运算以及处理进位的不同方法和观点 不同观点： • [ashdnazg] 认为使用AVX512和AVX2可以高效实现256位加法，并且能够将更多数字装入寄存器。他提供了一段代码示例，展示了如何通过掩码操作处理进位，并指出这种方法在512位加法中效果更显著。 • [addaon] 质疑为何不将最高位设置为64位而是52位，并建议通过分配更多位数给高位，可以积累更多加法操作，从而优化性能。他还提到这样做可以利用指令集的某些特性进行对齐和分割。 • [e4m2] 提出使用ADX指令可以在某些现代x86 CPU上获得更快的速度，尤其是在处理传统上使用2^51表示法有优势的情况下，例如Curve25519。 • [nine_k] 强调更多的独立操作可能会更快，因为它们可以并行执行，而较少的操作如果因为数据依赖性必须串行执行可能会更慢。这个观点具有更广泛的适用性。 • [smcin] 批评文章标题具有点击诱饵性质，认为标题应该更准确地反映内容，比如应突出该技巧仅适用于某些x86架构，并且是为了解决进位问题以避免流水线减速。 补充讨论： • [dang] 提供了一些相关的讨论链接，包括2022年11月和2020年5月的讨论，提供了更多背景信息。 • [hdjrudni] 分享了自己在处理缓冲区编码和解码时的经验，通过留出一些未使用的位来处理进位，从而在计算上节省了资源。 • [brucehoult] 指出在x86_64上工作的人证明了RISC-V省略进位标志是正确的。 • [eru] 提到“基数技巧”也适用于数据结构，并引用了Okasaki的书《Purely Functional Data Structures》中的例子。 • [Dwedit] 误以为2^51是关于将整数存储到双精度浮点数中，但后来澄清在此情境下应为2^53-1。 • [t0010q] 提到无进位二进制加法是异或操作，而带有进位的子集和问题是NP完全的，这揭示了进位对并行化的影响。 • [foota] 询问C/C++编译器是否可以合法地实现这种优化。 • [russdill] 对adc指令在现代CPU上是否必然比add指令慢表示怀疑，但承认文章的重点是数据依赖性。 • [alwahi] 询问如何将这种方法应用于大数乘法。 争议焦点： • 关于如何分配最高位的位数以优化性能存在不同看法，[addaon] 建议64位而[ashdnazg] 使用了52位。 • 点击诱饵标题引发了[smcin] 的不满，他认为标题应该更准确地反映内容。 总结：讨论主要围绕使用AVX指令优化加法运算、处理进位的不同方法以及这些技巧在不同架构和情境下的适用性展开。同时，也涉及到了编译器优化和标题准确性的问题。

On eval in dynamic languages generally and in Racket specifically (2011)

文章摘要

文章讨论了动态语言中的`eval`函数，它看似强大，但有经验的程序员通常避免使用，因其不当使用会引发问题。作者通过一个比喻解释了`eval`的本质：一种是直接给出明确指令（如将画布涂成红色），另一种是让其他人执行包含指令的句子。前者可被编译和优化，而后者类似于`eval`，无法很好地编译且执行结果依赖于环境。`eval`在某些情况下是必要且有用的，例如当指令来自外部（如施工经理），但多数情况下应避免，因其使程序更难理解和优化。关键在于区分何时真正需要动态执行代码。

评论摘要
主要讨论点：不同编程语言中 `eval` 函数的差异及其使用场景，特别是 Lisp 语言中的 `eval` 特性及其相关讨论。 不同观点： • **taeric 的观点**：Lisp 中的 `eval` 与大多数其他语言的 `eval` 不同，它接受的不是字符串，而是代码即数据（code is data）的理念。这使得 Lisp 的 `eval` 可以带来一些显著的差异，尤其是在元编程（metaprogramming）方面。他通过个人探索展示了这一特性。 • **neilv 的观点**：反对新手在未充分理解的情况下滥用 `eval`。他指出，许多新手在阅读学术教材后会立即尝试使用 `eval`，而往往这是不合适的。他还提到，在 Racket 社区中，他曾尝试 discourage 误用 `eval`。他认为 `eval` 应作为最后的、危险的工具来使用，且在教学中应尽量延后介绍。 • **kazinator 的观点**：认为 `eval` 不应被阉割，主张保留完整的语言功能。他提出可以通过多种方式对 `eval` 进行沙盒化，包括验证代码和在限制环境中执行代码。他还强调，不应让 `eval` 的功能因为安全问题而被削弱。 • **programLyrique 的观点**：通过引用学术文章，展示了 `eval` 在其他语言（如 JavaScript 和 R）中的使用情况，提供了一些背景信息和实例，但没有深入展开讨论。 • **behnamoh 的观点**：提出了 Lisp 的强大宏系统是否源于能够用 Lisp 自身实现 `eval` 函数的问题。他认为 Lisp 通过少量原语和特殊形式构建了 `eval` 函数，并通过此机制扩展出新的语法规则，这与 Lisp 宏系统有相似的核心思想。 • **TOGoS 的观点**：总结了 `eval` 函数在不同层次上的语义定义。他认为，`eval` 的语义定义越复杂，其行为就越不明确。他将 JavaScript 的 `eval` 视为不明确的一端，Lisp 宏则处于中间，而经过解析和编译的 lambda 表达式则处于定义明确的另一端。 补充讨论： • 争议的焦点之一是 `eval` 的使用场景及其潜在的危险性。neilv 强调新手容易误用 `eval`，而 kazinator 则认为应通过沙盒化等手段来安全地使用 `eval`，而不是简单地避免使用。 • 另一个讨论点是 Lisp 的 `eval` 与宏系统的关系，behnamoh 和 TOGoS 提供了对 Lisp 元编程能力的深入理解，并探讨了 `eval` 在其中扮演的关键角色。 • 不同语言中 `eval` 的实现和使用差异也被提及，如 JavaScript 和 R 中的 `eval`，提供了跨语言的比较视角。 通过这些观点，可以看出 `eval` 函数在不同语言和场景中的复杂性和潜在问题，以及 Lisp 在元编程方面的独特优势。
