Software development with AI is starting to feel like cooking steak

作者: yusyd | 评分: 398 | 评论数: 85 | 发布时间: 2026-08-06 15:30
文章摘要

这篇文章用"煮牛排"比喻AI辅助软件开发。作者指出，虽然AI让我们构建软件的速度大幅提升，但就像煮牛排一样，做出"能吃的"容易，做出"完美的"很难。 核心观点是：AI不是专业大厨，而是"牛排机器"——它能按配方执行，但无法理解你真正想要什么。许多开发者寄希望于付费AI产品或工具来解决问题，却发现结果仍然不理想，因为"每家餐厅都雇了同一个AI厨师"。 作者强调，要用AI构建好软件，开发者必须真正理解软件开发本身——知道如何提出正确需求、判断输出质量、识别错误。AI只能提高效率，无法替代判断力。唯一的解决方案是：持续学习、实践和失败，直到真正掌握技能，而不是依赖运气。

评论摘要
**主要讨论点：**一篇用"煮牛排"类比AI编程的文章引发的多角度讨论 **不同观点：** • **类比批评派**：多位评论者认为煮牛排实际上很简单（用肉温计+逆向烹饪法即可），是个糟糕的类比，不能说明AI编程的复杂性 • **质量标准派**：严肃批评软件行业对"bugs"的轻松态度，认为应该像航空业一样经历质量觉醒，反对用"我们"来为低标准辩护 • **AI乐观派**：相信LLM能帮助构建更高质量软件（如更好的原生UI、快速原型对比），未来只需"有品味的用户"提需求，不再需要工程师监督 • **AI局限派**：指出AI缺乏感知反馈能力（看不到、尝不到），只能随机调整等待用户反馈，本质上是盲目试错 • **实用主义派**：认为少折腾反而效果更好；AI对明确需求场景有效，但艺术性工作仍需人类；关键在于用AI"扩展思考"而非"替代思考" • **内容疲劳派**：抱怨到处都是AI相关内容，难以分辨AI生成文本，期待看到其他主题 **补充讨论：** 有评论指出现实中软件工程追求的是"大规模生产"而非"完美代码"（成本和时间权衡）；最后一条元评论幽默地指出，作者可能没想到会引发关于"煮牛排难度"的技术性争论。

Software is about people, not code (2020)

作者: venamresm__ | 评分: 41 | 评论数: 20 | 发布时间: 2026-08-07 14:55
文章摘要

这篇文章是作者写给新开发者的一封信。作者回顾了自己的职业历程:刚入行时,他认为软件开发的核心是代码,因此投入大量精力学习编程技术、代码规范、设计模式等。 然而,经过多年实践后,他意识到**人比代码更重要**。原因在于: - 软件是为满足人的需求而创建的 - 用户只关心问题能否被解决,并不在意代码本身 - 即使代码写得再完美,如果解决的是错误的问题,或缺乏市场需求,项目仍会失败 作者最终得出结论:代码只是通用工具,必须解决真实世界中真实人群的实际问题。这个认知转变帮助他理解了软件开发的本质。

评论摘要
主要讨论点：围绕"软件应关注人而非代码"这一观点，评论者从职业发展、商业价值、技术质量等多角度展开讨论，观点分歧明显。 不同观点： • **平衡务实派**：代码质量仍有其价值，不应走向"代码无用"的极端。应根据项目实际需求，在适当场景下追求代码质量，服务于更大目标（randusername, agentultra） • **商业导向派**：软件最终是为了赚钱，客户和销售比代码更关键。开发者从技术视角转向商业视角后，会意识到市场和客户才是核心（JSR_FDED, lenerdenator） • **自然成长派**：这是职业发展的正常过程，初级开发者专注代码，随经验增长逐渐关注更广泛的人际和业务层面，并非什么"重大发现"（WCSTombs） • **质疑讽刺派**：担心过度强调"人"会导致忽视代码质量和技术标准，用反讽语气表达对这种观点的不满（negativi, 38127） • **哲学/政治派**：从更抽象层面讨论，认为这涉及软件自主权、用户控制权等政治问题，或指出任何人类讨论的事物本质上都"关于人"（Kinrany, livingsoft） 补充讨论：争议焦点在于是否应该弱化代码本身的重要性。支持者认为这反映成熟认知，反对者担心成为忽视技术质量的借口。部分评论者认为这是老生常谈。

The web server deployment model breaks at hobby scale

作者: meetpateltech | 评分: 52 | 评论数: 21 | 发布时间: 2026-08-07 13:15
文章摘要

这篇文章讨论了个人规模 Web 应用部署面临的困境。核心问题是：当你开发供他人自行托管的 Web 应用时，无法依赖特定的基础设施配置，导致许多效率优化无法实现。 文章列举了两个典型场景： **静态文件服务**：理想情况下应由反向代理处理以提高效率，但容器化环境会增加配置复杂度，而某些云原生代理根本不支持，最终只能让应用自己处理，牺牲效率。 **未认证缓存**：无法依赖专业缓存方案（如 Varnish），只能使用基础的 Cache-Control 头，但不同管理员的配置五花八门，导致缓存失效、内存浪费等问题。 文章对比指出：在专业规模部署中，这些问题不存在，因为团队可以完全控制部署环境和基础设施。

评论摘要
主要讨论点：自托管网络应用的部署复杂度与配置策略 不同观点： • **简化最小化派**：应该只提供基础HTTP服务和容器镜像，让用户自行配置反向代理、TLS等。理由是每个管理员都有自己的偏好设置，预配置反而增加复杂度。业余规模流量低，简单可用即可（smashed, turtlebits） • **容器编排派**：认为K8s/K3s等容器方案已经解决了文章提到的大部分问题。虽然前期学习成本略高,但能消除配置难题。市场正朝这个方向发展，如Synology已提供简易容器界面（horsawlarway, KronisLV） • **AI辅助乐观派**：认为现代AI工具（如Claude、Codex）能在几分钟内解决配置问题，即使是非技术用户也能通过AI完成复杂的homelab设置。技术门槛已大幅降低（ComputerPerson, glaslong） • **实践困难派**：分享实际遇到的问题——高流量导致缓存OOM、企业版功能限制、HTTPS强制要求等。这些问题确实存在且影响用户体验（SlavikCA, sam_lowry_） • **质疑夸大派**：认为文章把问题复杂化了，业余规模不应该如此复杂，或质疑文章的场景定位不清（bradly, andai, JodieBenitez, wainstead） 补充讨论：技术细节争议——有评论指出原文对nginx的if功能理解有误，该功能实际很有用。这反映出技术讨论中对工具理解深度的差异。另外有人提到无JavaScript访问者比盲人访客还少，暗示某些可访问性考虑可能过度。

作者因不满Android系统的诸多限制（Google服务追踪、阻碍定制ROM开发、强制AI功能、限制应用安装等），决定将手机系统切换到Linux。 经过对比Ubuntu Touch、postmarketOS和SailfishOS等移动Linux系统后，作者在Fairphone 4上选择了SailfishOS。该系统具有手势导航、优秀的应用框架和可SSH远程管理等优点，但也存在软件版本过旧、Waydroid和GPS功能不可用等问题。 由于部分银行、政府服务和Uber等必需应用无法在SailfishOS上运行，作者暂时保留了一台Android备用机(Galaxy A17)应急使用。作者计划继续测试并分享使用体验。

评论摘要
主要讨论点：移动操作系统的开放性与用户自主权，以及Linux手机等替代方案的可行性 不同观点： • **Android系统可取但服务层有问题**：有用户认为Android内核设计优秀，真正的问题是Google Play Services过度集成，获得过多权限，且Play Integrity阻碍替代方案发展。理想状态应该是模块化的核心服务，用户可自由选择实现方式。 • **平台锁定趋势悲观论**：担心银行和服务商以"安全"为名将服务锁定在iOS和Android两个平台，Web也可能通过安全启动栈被Chrome垄断。批评Android采用"先开源吸引用户，后逐步锁定"的策略。 • **Linux手机体验差距论**：认为移动Linux在相机软件、键盘输入体验、GPS和银行应用支持等方面落后多年，难以追赶iOS/Android，涉及大量专有技术和优化。 • **实用主义替代方案**：部分用户分享Sailfish OS等实际使用经验，通过双手机策略（一部用于日常，一部专门用于银行）、逆向工程银行应用等方式解决兼容性问题。也有人提议使用可解锁bootloader的设备配合安全性高的第二手机。 • **硬件制约论**：Pinephone等设备硬件过时（如缺少5G），用户希望能在现有高性能硬件（如iPhone）上安装真正的Linux系统。 补充讨论：评论中提到VoLTE支持、NFC支付、汽车数字钥匙、蓝牙编解码器等具体功能缺失是Linux手机的实际障碍；也有人怀念Windows Phone的跨平台开发潜力。
