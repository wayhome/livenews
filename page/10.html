PR spam today looks like email spam in the early 2000s

作者: dakshgupta | 评分: 207 | 评论数: 20 | 发布时间: 2026-06-24 14:32
文章摘要

这篇文章分析了 OpenClaw 项目 PR 激增现象。主要发现： 1. **PR 数量暴增但质量下降**：从每周2个增至3400个，合并率从48%降至9.3%。大量低质量 PR 由 AI 编程助手生成，有人一天提交106个 PR。 2. **需要贡献者信誉系统**：类似早期邮件垃圾问题，需要通过信誉过滤。数据显示老贡献者合并率（18.6%）高于新手（8.2%）。 3. **AI 导致思维趋同**：多人用相同 AI 工具提交重复 PR，削弱开源多样性优势。 4. **深度理解更重要**：需要深入理解代码库的重构类 PR 合并率（35%）远高于功能类（9%）。AI 时代，思考比编码更关键。

评论摘要
主要讨论点：开源项目遭遇AI生成的垃圾PR问题及应对方案 不同观点： • **邮件反垃圾机制不适用论**（andix）：邮件反垃圾依赖服务器IP和域名声誉，由组织管理用户行为。但PR/issue是个人行为，无法套用同样机制 • **技术限制派**（guidoiaquinti, giancarlostoro）：GitHub已推出可配置的PR限制功能；建议通过仓库规则集锁定PR权限来防止垃圾提交 • **人工审核派**（j2kun）：要求新贡献者首次PR前必须与维护者进行非文字形式会面，适合小型项目 • **声誉系统倡导**（haneul）：建议建立类似邮件的声誉基础设施，并提供类似uBlock Origin的退订列表 • **讽刺质疑**（janalsncm）：指出文章抱怨AI垃圾PR却发生在OpenClaw（AI工具）自己的仓库，认为维护者应更新工具防止其提交PR到自己项目 • **经济激励方案**（Retr0id）：建议让人们直接向开源项目捐赠代币额度，由维护者决定使用方式 补充讨论：多位评论者（DeepYogurt, fecal_henge）质疑制造垃圾PR的动机和盈利模式；benj111质疑用AI对抗AI垃圾的逻辑矛盾；elzbardico感慨营销思维破坏了互联网早期的美好交流环境。usernametaken29则批评文章本身就是AI工具广告。

Ending respiratory infections

作者: EthanFantl | 评分: 128 | 评论数: 20 | 发布时间: 2026-06-25 01:14
文章摘要

Intercept是一项5亿美元的慈善计划，旨在消除感冒和流感等呼吸道感染。文章指出，呼吸道感染每年让人们损失约5%的生命时间，造成全球约6000亿美元的经济损失，并可能引发哮喘、心脏病、痴呆等严重后果。该计划将开发两类技术：广谱预防药物(BSPs)和空气净化技术。由于单一技术无法实现群体免疫，需要两者结合才能大幅降低呼吸道病毒传播。新的平台技术、免疫学进展和蛋白质设计工具使这一目标成为可能。

评论摘要
主要讨论点：关于一项旨在消除呼吸道病毒感染的5亿美元资助计划的讨论 不同观点： • **支持者立场**：多位用户因个人经历强烈支持该计划。有人因女友死于人类偏肺病毒而希望计划成功；有人因长新冠导致自己和朋友永久残疾而期待新的预防技术；还有家长因孩子易感染而错过大量学校时间表示支持 • **资金规模质疑**：有观点认为5亿美元"太少"，对比NASA阿波罗计划的3000亿美元和Artemis超900亿美元的投入，认为预防疾病比探索火星更重要，批评依赖慈善而非政府投资 • **怀疑论者**：质疑这是否只是公关噱头、科学家为获取资金编造故事；有人认为技术可行性本身就是缺乏资金的原因；有人完全不相信"健康人每年病15-25天"的统计数据 • **市场阴谋论**：认为制药公司不愿放弃数十亿美元的感冒药市场，一次性解决方案无法创造持续收益，这是"市场力量负面作用"的证明 • **技术路线讨论**：关于空气净化技术未能在疫情后普及表示失望；质疑紫外线消毒是否会导致病原体突变；有人分享使用苹果白兰地蒸汽治疗肺部疾病的非主流方法 补充讨论：资助方包括OpenAI和Anthropic引发好奇，但有人庆幸"至少不是用AI或区块链解决问题"。关于水源控制与空气传播病毒控制难度差异的基本认知分歧也被提及。

Pull request limits are cutting down the noise

作者: ingve | 评分: 81 | 评论数: 12 | 发布时间: 2026-06-19 10:03
文章摘要

GitHub推出了pull request限制功能，解决开源项目维护者面临的主要问题：PR数量过多、低质量噪音泛滥。该功能限制无写入权限的用户在单个仓库中同时打开的PR数量，达到上限后必须先关闭或合并现有PR才能提交新的。可信贡献者可加入豁免名单。这迫使贡献者更谨慎地选择提交内容，帮助维护者更容易发现高质量工作。GitHub的PR数量从2023年1月的月均2500万增至今天的9000万，增长3.6倍。未来计划推出PR归档、issue限制、智能豁免信号和跨仓库控制等功能。

评论摘要
主要讨论点：GitHub限制单个仓库开放PR数量的新功能是否能有效解决AI生成的垃圾PR问题 不同观点： • **跨仓库限制派**（CodesInChaos）：认为单仓库限制治标不治本，真正问题是垃圾账号在多个仓库分散提交PR。建议基于账号在所有公共仓库的PR总数限制，并对未合并就关闭的PR进行惩罚性计数 • **根源问题派**（trjordan）：认为这只是创可贴方案，核心问题是GitHub假设所有代码都值得阅读。建议在PR中附加AI代理日志，让维护者快速判断提交背后是否有真人思考 • **积极支持派**（frankfrank13）：认为这是可靠举措，给了OSS维护者灵活性。可以设置0完全手动审核，或1-3允许新人尝试，比目前的无限制好太多。类比Gmail也应有类似机制 • **矛盾心态派**（Unfunkyufo）：肯定GitHub认真对待问题，但担心这会巩固其垄断地位，希望更多人迁移到其他平台打破垄断 • **规避机制派**（SaucyWrong）：指出已有人制作"循环"脚本绕过限制——自动关闭未合并PR并重新提交，噪音依然存在 补充讨论：有人建议关闭所有issue按需打开（cyanydeez），也有人推荐Mitchell Hashimoto的Vouch系统作为更智能的PR筛选方案（esafak）

这篇文章讲述了作者将Wine移植到自己的hobby操作系统Astral的过程。主要内容包括：为了运行32位Windows游戏Cogmind，作者完成了Wine移植工作，包括启用MinGW编译PE DLL、通过切换到DRI后端实现EGL支持以获得OpenGL功能、实现WoW64模式让64位系统运行32位程序（涉及LDT内核支持）。最终成功运行了Cogmind和其他多款游戏如FTL、Deltarune等。文章展示了hobby操作系统也能支持大量Windows游戏，向成为日常使用系统迈进了一步。

评论摘要
主要讨论点：业余操作系统（hobby OS）开发的价值、挑战和技术实现 不同观点： • **兼容性困境观点**（da-x）：hobby OS 最令人沮丧的是必须实现"遗留"接口（TCP、POSIX等）才能实用，无法独立创建新生态系统，最终沦为充斥兼容代码的 Linux/Win32 模仿者。提出思想实验：如果外星人从零发明计算机和OS会是什么样 • **简化实用主义观点**（vinc）：开发 hobby OS 五年的实践者认为可以移除主流OS的大量复杂性，仍能满足个人计算需求。承认是在"拙劣地重新发明DOS和Unix/Plan 9之间的东西"，但非常适合实验 • **技术成就赞赏观点**（pbohun, bionsystem, univocal）：对 hobby OS 支持 Linux 基础设施→Wine→Windows 应用的多层兼容性表示惊叹。关注技术细节如 Wine 与 XLib 的深度耦合、是否需要 X server 模拟器等 补充讨论： • spwa4 提出实际需求：希望有 Windows 老游戏的标准化"ROM格式"运行方案 • int0x29 指出关键技术盲点：GPU 驱动在 hobby OS 上的实现可能很困难，但博客未提及 核心矛盾：理想主义的"全新设计"与现实的"兼容性需求"之间的权衡
