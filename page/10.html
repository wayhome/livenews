I made a search engine worse than Elasticsearch (2024)

作者: softwaredoug | 评分: 137 | 评论数: 10 | 发布时间: 2025-06-05 18:37
文章摘要

文章描述了作者尝试将自己开发的搜索库SearchArray与Elasticsearch进行对比的过程，使用BEIR基准测试，特别是在MSMarco数据集上进行相关性和性能测试。结果显示，SearchArray在各个维度上都逊色于Elasticsearch，包括相关性指标NDCG@10和查询吞吐量。 作者解释了这种差距的原因，主要在于Elasticsearch使用了Weak-AND（WAND）算法优化查询，能有效减少不必要的计算，快速获取前K个高分文档。而SearchArray则直接计算所有文档的BM25分数并进行简单求和，导致性能较低。此外，SearchArray使用位置索引和Roaring Bitmap实现短语匹配，而非像Elasticsearch那样使用倒排索引，这也影响了其效率。 文章最后总结，SearchArray虽然功能齐全，但在性能优化上不及专业的搜索引擎。

评论摘要
主要讨论点：搜索引擎技术的选择与优化，尤其是与ElasticSearch相关的讨论。 不同观点： • **sh34r** 认为，改进网站的搜索功能往往需要很长时间，且自制的搜索引擎几乎总是比不上ElasticSearch。他强调了搜索问题在工程中的难度，以及ElasticSearch在性能上的优势。 • **nchmy** 推荐Manticoresearch，认为它比ElasticSearch更容易使用且速度更快，并指出Manticoresearch源于Sphinx search，历史更久，且在一些大型网站如Craigslist上得到应用。 • **intalentive** 提出，特定情况下可以通过优化某些特殊用例来超越标准方案，例如通过NLP技术提取关键词，从而避免某些标准化步骤，甚至可以通过竞争性网络模型获得有趣的查询结果。 • **fucalost** 表达了对Elasticsearch的喜爱，认为其功能强大且生态系统健康，尽管计算成本较高，但在很多情况下都能很好地工作。同时提到AWS的新实例类型可以为OpenSearch带来显著的成本节约。 • **0xB0UNCE00** 认为，即使自制的搜索引擎不如Elasticsearch，但通过玩和学习的过程本身就有价值。 • **amai** 列举了多个不如ElasticSearch的搜索引擎选项，如Meilisearch、Typesense和Whoosh-reloaded，暗示市场上存在多种选择。 • **Alifatisk** 表达了对Elasticsearch存在的感激之情。 • **niazangels** 表示从讨论中学到了很多。 • **neuroelectron** 夸张地表示这个讨论内容比Alphabet（谷歌母公司）还重要。 • **stuaxo** 则表示不喜欢使用Elasticsearch，认为在一些不必要的项目中使用Elasticsearch是一种负担。 补充讨论： • 争议焦点之一是自制的搜索引擎是否能与ElasticSearch相媲美。**sh34r**和**amai**认为ElasticSearch更优，而**0xB0UNCE00**和**intalentive**则认为通过特定优化或学习，自制方案也有其价值。 • **nchmy** 提出了Manticoresearch作为ElasticSearch的替代方案，并强调了其易用性和速度优势。 • **fucalost** 强调了Elasticsearch的生态系统优势和AWS上的成本节约潜力，提供了另一种支持使用ElasticSearch的论据。 • 总体来看，评论中既有对ElasticSearch的肯定（**fucalost**、**Alifatisk**、**sh34r**），也有对其不满的声音（**stuaxo**），同时还有人推荐其他替代方案（**nchmy**、**amai**）。

Sandia turns on brain-like storage-free supercomputer

作者: rbanffy | 评分: 209 | 评论数: 25 | 发布时间: 2025-06-06 15:24
文章摘要

Sandia National Labs和德国公司SpiNNcloud合作推出了SpiNNaker2超级计算机，该计算机受大脑神经网络启发，旨在用于国家核威慑任务。SpiNNaker2采用高度并行架构，无GPU和内部存储，依赖SRAM和DRAM进行高速数据处理，通过高速芯片间通信消除了对集中存储的需求。该系统每块服务器板有48个SpiNNaker2芯片，共152个内核和专用加速器，单板内存达96GB。Sandia采购的系统包含24块板，共17.5万个内核，连接至现有HPC系统，无操作系统和磁盘，通过以太网端口加载和保存数据。SpiNNaker2能够模拟1.5至1.8亿个神经元，具有高效能和事件驱动计算能力，适用于国防和安全领域的高计算需求。

评论摘要
主要讨论点：关于在技术系统或法律中采用“失败则开放”还是“失败则关闭”机制的争论，以及大科技公司与版权、权利主张之间的复杂关系。 不同观点： • mjevans主张采用“失败则开放”（fail open）的机制，认为当前默认的做法往往是限制用户的权利。他建议让有利益相关方证明公众不应该拥有某些能力，而不是默认限制用户的权利。这种观点强调保护用户的权利，防止无理由的限制。 • hello_computer则对这种讨论的真诚性表示怀疑，提到了Yasha Levine的研究，指出大科技公司与电子前哨基金会（EFF）之间的联系。他认为大科技公司在版权问题上有双重标准：对自己的版权保护非常严格，但对公众的版权则可能不太在意。这种观点质疑大科技公司在版权和用户权利讨论中的立场和动机。 补充讨论： • mjevans的观点基于一种保护用户权利的法律推定，认为在缺乏明确限制理由的情况下，用户应默认保留权利。 • hello_computer的评论引入了对大科技公司和版权主张者动机的质疑，指出潜在的利益冲突和双重标准。 • 争议的焦点在于技术系统和法律应如何平衡用户权利与利益相关方的权利主张，以及大科技公司在其中的角色和影响。 这些观点反映了关于技术系统设计、法律推定和企业动机之间的复杂关系。

文章摘要

Py-PGlite 是一个 Python 包，旨在简化使用 PostgreSQL 进行测试的过程，类似于使用 SQLite 那样便捷。它无需 Docker 或配置文件，即可快速启动真实的 PostgreSQL 数据库用于测试。支持 SQLAlchemy、Django 等框架，并提供隔离的数据库环境。主要特点包括：零配置、快速设置、支持 JSON 和数组等 PostgreSQL 高级功能，以及与多种框架的无缝集成。通过 Py-PGlite，开发者可以在 2-3 秒内启动 PostgreSQL 测试环境，大大提高测试效率。

主要讨论点：WebAssembly (WASM) 与原生方式运行 PostgreSQL 的比较及其在测试和开发中的应用 不同观点： • WhyNotHugo 认为，WASM 在 Node.js 中运行无法比经过几十年优化的原生代码更快，且 Node.js 的体积较大（63MB），相比之下 PostgreSQL 仅 32MB，因此声称“不需要安装 PostgreSQL”并不能作为卖点。 • jauco 提到 Testcontainers 作为另一种选择，并表示其在 Node.js 单元测试中表现不慢。 • samwillis 介绍了 PGlite 的实验性 WASI 构建，指出其目前缺乏错误处理，但未来可能取消 Node.js 依赖，并表示愿意提供帮助和解答相关问题。 • benpacker 分享了其在 Node/Bun 环境中的集成经验，展示了使用 WASM 支持的 Postgres 和 PGlite 进行并行单元测试的简洁代码示例。 • ptx 质疑 WASM 运行 PostgreSQL 是否真的能减少安装开销，认为原生版本可能更为高效，避免了 WASM 和 Node.js 的额外开销。 • laurencerowe 建议直接使用 Postgres 作为子进程运行，而不是 PGlite。 • veggieroll 反对在运行时安装 npm 包，建议在 README 中明确说明，并提议使用 Python WASM 解释器运行 PostgreSQL。 • perrygeo 推荐了 Zonky，一个在 JVM 上运行嵌入式原生 Postgres 的工具，作为 WASM 方案的替代。 • selimnairb 提到使用 pytest-docker-compose 来避免 NPM，并表示对 pytest 的“魔法”感到满意。 • murkt 提出是否可以将 Postgres 编译为 Python 扩展而不是 WASM，以避免 Node.js 依赖。 • wey-gu 提供了项目的 v1 路线图链接。 • ForHackernews 指出 PGtap 可以用于测试 Postgres 本身。 • lucideer 对项目自动管理 NodeJS 依赖的方式提出批评，认为这可能与现有的项目设置不兼容，并建议默认禁用此功能并提供文档说明。 • gleenn 希望类似方案能应用于 Snowflake 等难以在非生产环境中测试的数据库。 • jodiug 认可该项目在数据库测试中的价值，询问是否支持 asyncpg 以及是否在路线图中。 补充讨论： • 项目的自动依赖管理功能引起了一些争议，部分用户认为可能导致兼容性问题，并建议改进文档说明。 • 用户对 WASM 和原生运行方式的性能和实用性进行了对比，提出了不同的技术选择和替代方案。 • 对于不同编程语言和环境的工具推荐，如 Python 和 JVM 上的嵌入式数据库方案，也成为讨论的一部分。

A proposal to restrict sites from accessing a users’ local network

作者: doener | 评分: 663 | 评论数: 58 | 发布时间: 2025-06-04 18:15
文章摘要

这篇文章介绍了一项由Chrome安全网络团队提出的提案，旨在限制公共网站未经用户许可访问其本地网络。当前，公共网站可以探测用户的本地网络并发动针对本地设备的CSRF攻击，利用浏览器作为“被迷惑的代理”来攻击用户的本地设备。为解决此问题，提案建议取消公共网站直接访问私有IP地址的能力，要求用户明确授予网站访问本地网络的权限。 该提案基于Chrome此前暂停的“私有网络访问（PNA）”工作，但通过权限控制替代预检请求，以增加用户控制并简化实施。目标包括阻止通过网页利用本地 vulnerable 设备，并允许在用户明确期望和允许的情况下，公共网站与本地设备通信。提案不打算破坏依赖本地设备控制的现有工作流程，也不解决本地网络HTTPS问题。 主要用例包括：普通用户防止未经授权的访问，以及通过公共网站前端设置和控制本地设备（如物联网设备、家庭路由器等）。

评论摘要
主要讨论点：浏览器或操作系统对本地资源（如本地网络、USB、蓝牙）的访问控制 不同观点： • **支持加强本地资源访问控制**： - [mystifyingpoi] 认为网站不应默认能够访问任意本地IP，建议通过弹窗让用户选择允许或拒绝。 - [socalgal2] 希望对USB和蓝牙的访问也采取类似控制，建议应用程序只能访问预定义的设备ID。 - [skybrian] 认为目前的方案过于粗略，应该限制网站只能访问特定的本地服务器，而不是所有本地资源。 - [bmacho] 完全同意此提议，认为应阻止网站随意访问localhost，但也希望在用户许可下实现设备间的资源共享。 • **对当前情况的批评和担忧**： - [paxys] 指出浏览器默认行为存在安全隐患，任何本地网络服务都可能被网站访问，安全依赖于服务器配置。 - [sroussey] 提到此举可能阻止Meta等公司通过本地通信绕过限制，保护用户隐私。 - [rerdavies] 担心IPv6地址的识别问题，尤其是在IoT应用中，并指出目前本地网络使用自签名证书的困难。 • **技术实现和替代方案**： - [pacifika] 提到Internet Explorer曾通过分区系统解决此问题。 - [G_o_D] 解释CORS并不能完全阻止请求发送，但可以通过代理服务器绕过，建议慎重考虑完全禁止localhost访问。 - [ronsor] 指出由于NPAPI插件的移除，许多本地软件依赖localhost进行公共网站的交互，完全限制可能造成困扰。 • **对现有安全机制的质疑**： - [AshamedCaptain] 质疑为何不依赖同源策略解决此问题，认为基于IP地址范围的保护标准不妥。 补充讨论： • **简化浏览器的呼声**： - [1vuio0pswjnm7] 认为现代浏览器过于复杂，支持使用简单、无JavaScript功能的浏览器以避免安全问题。 争议焦点： • 是否应默认允许网站访问本地资源，以及如何在安全和用户便利之间取得平衡。 • IPv6地址的识别问题及其对提案可行性的影响。 • 完全禁止localhost访问可能导致的兼容性问题，如rclone的OAuth机制可能失效。 总体来看，讨论围绕如何在保障安全的前提下，不影响用户对本地资源和服务的正常使用。
