Voxel Space (2017)

作者: davikr | 评分: 297 | 评论数: 29 | 发布时间: 2026-05-30 14:25
文章摘要

这篇文章介绍了Voxel Space渲染引擎的工作原理。1992年NovaLogic发布的游戏《Comanche》采用了这项技术,在当时呈现出惊艳的地形图形效果。 Voxel Space是一种2.5D引擎,使用高度图和颜色图来表示地形。核心算法非常简单:从远到近绘制,对每个距离的扫描线进行光栅化,通过透视投影计算高度,然后绘制垂直线条。这种"画家算法"能自然实现遮挡效果。 相比当时的3D多边形引擎,Voxel Space用极少代码就能渲染出带纹理、阴影的地形,是CPU时代的巧妙解决方案。文章还展示了如何通过旋转坐标实现视角变化。

评论摘要
主要讨论点：Comanche游戏使用的体素渲染技术及其历史意义 不同观点： • **技术本质争议**：nine_k指出这并非真正的体素技术，而是高度图（heightmap）渲染，每个柱体有固定方形底面，类似Doom地图结构，与沃克素（三轴均分3D空间）有本质区别 • **技术局限性认知**：wolvoleo强调该技术有明显限制——无法实现多层结构或悬垂效果，只适合山地地形；但对当时而言效果惊人 • **历史评价一致**：多位评论者（wolvoleo, nine_k, mikeaskew4, mft_）都认为这在1992年是"令人震撼"的技术突破 • **实践应用启发**：superjan从游戏首个任务"油罐假日"（无敌人的简单任务）中获得测试理念——先写最小化测试验证代码基本功能，称为"油罐假日测试" 补充讨论： 评论中分享了多个相关项目和历史背景：C++复刻版本、AGS引擎移植、4k demo实现MARS.EXE、Magic Carpet可能使用类似技术。mthoms分享了青少年时期自学复现该算法的经历，通过查找表和位移优化克服286 CPU性能限制。esafak揭示该技术源于程序员在医疗行业（CT/MRI扫描）的经验。tdeck注意到颜色贴图内置阴影实现3D斜面效果的巧妙设计。

Is that song AI-generated? UChicago scientists create tool to check

文章摘要

芝加哥大学科学家开发了名为Quicksilver的浏览器扩展工具，用于检测歌曲是否由AI生成。2024年流媒体平台上近半数新上传曲目为AI生成，但平台通常不披露这一信息。Quicksilver在用户设备本地运行，通过分析音频中人耳无法察觉的AI"痕迹"来识别AI音乐，特别针对Suno和Udio等平台生成的作品。该项目由芝加哥大学SAND实验室与非营利组织ETCH共同开发，旨在提升透明度、保护人类创作者权益，并确保技术服务于社会利益而非仅追求利润。

文章摘要

这篇Zig开发日志主要介绍了两项重要更新： **ELF链接器改进**（5月30日）：新ELF链接器现已支持构建完整的Zig编译器（包含LLVM和LLD库），并实现了快速增量编译功能。在x86_64 Linux上，重新构建仅需30-300毫秒。目前缺少DWARF调试信息支持，但已可用于实际项目。 **构建系统重构**（5月26日）：将构建过程分离为两个独立进程——配置器（configurer）和制造器（maker）。配置器以调试模式编译build.zig文件并生成配置文件；制造器以发布模式编译并执行构建图。制造器可全局缓存复用，显著提升构建性能。 这些改进将在即将发布的Zig 0.17.0版本中提供。

评论摘要
主要讨论点：Zig 近期在增量编译/链接上的进展，是否会推动它从“利基语言”走向更广泛替代 C，以及这对生态、采用和实际发布的意义。 不同观点： • 看好派认为 Zig 正在兑现“高性能 + 高迭代速度”的承诺。`bpavuk` 认为若其他目标上的链接器和增量编译落地，Zig 可能成为“C 的替代品”，还能让 DAW 这类对性能和 UX 都苛刻的软件更易实现；`teabee89` 也表示这是 Zig 早期承诺的实现。 • 生态/技术实践派更关注 Zig 作为“目标平台”的价值。`onlyrealcuzzo` 认为 Zig 的构建系统设计和转译目标属性优于 Rust，并举自己做“转译到 Zig 的内存安全语言”为例；`librasteve` 则提到把 Raku 的 MOARVM 从 C 迁到 Zig，期待借助更多哈希方案和重构获得性能提升。 • 怀疑派认为 Zig/Rust 难以真正替代 C。`up2isomorphism` 的核心论点是：能替代 C 的语言必须像 C 一样简单，而 Zig 和 Rust 都不够简单。这与“Zig 将成 C replacement”的判断直接对立，争议焦点在“性能工具链进步”是否足以克服语言复杂度。 • 务实派关注落地条件而非愿景。`androiddrew` 认为企业采用还需要 1.0；`quikoa` 关心改进是否覆盖 Windows；`derefr` 追问增量链接是否与 LTO 冲突、是否只适合开发构建；`setheron` 则要求解释其增量链接设计，因为这一直是其他链接器难点。 补充讨论：还有人从行业热度角度观察，如 `c0rruptbytes` 询问 Zig 是否正在取代 Rust 的风头，`bcardarella` 猜测这波推进是否受 Bun 相关争议刺激。整体上，讨论既有技术期待，也有对复杂度、发布成熟度和适用场景的保留。
