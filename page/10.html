Models.dev: open-source database of AI model specs, pricing, and capabilities

作者: maxloh | 评分: 139 | 评论数: 19 | 发布时间: 2026-05-22 20:26
文章摘要

Models.dev 是一个开源的 AI 模型规格数据库，提供模型定价、能力等信息。项目通过 API 提供数据访问，支持查询模型规格和获取提供商 logo。数据以 TOML 文件存储在 GitHub 仓库中，按提供商和模型组织。 贡献方式： 1. 在 providers/ 目录创建提供商文件夹，添加 provider.toml 配置文件 2. 可选添加 logo.svg（使用 currentColor） 3. 在 models/ 目录创建模型定义文件，包含名称、功能支持、定价、token 限制、支持的模态等信息 4. 对于镜像提供商，可使用 extends 字段复用现有模型定义 项目鼓励社区贡献以保持数据更新。

评论摘要
主要讨论点：这个AI模型数据库/价格表是否真正有价值，以及它要想长期有用还缺哪些关键功能与数据。 不同观点： • 支持其基础价值：有人认为统一的模型列表/API很实用，已用于开源项目；也有人称表格性能很好，是“宝藏”。核心理由是集中整理价格和模型信息，方便查询比较。 • 质疑其独特性与可持续性：有人指出类似项目已“几十个”，担心又会成为被弃坑的“综合AI模型数据库”之一。争议焦点是：该项目能否持续更新，并与现有方案形成差异化。 • 强烈要求增强筛选/交互：多条评论集中批评缺少过滤功能，只能排序不够，建议按“current”、是否闭源/非LLM、工具调用、多模态等筛选；还有人指出横向滚动不直观。此处形成较强共识。 • 认为价格信息还不够：有人希望追踪价格变动、延迟基准；也有人进一步指出“token单价没意义”，因为模型可能中途“变笨”、被路由到更便宜的变体，实际成本更高。建议持续跑任务评测质量，但也有人隐含担心提供方会“特调”结果。 • 希望加入更贴近实战的比较：有人建议不仅列模型，还应加入“harness + models”组合，并举例称 Pi Dev + DeepSeek Pro 可完成与 Claude Code + Opus 4.7 类似工作，且经Claude复核代码可用。 • 个别讨论转向具体模型/平台：有人询问 AIHubMix 上免费模型是否有隐藏限制，以及相比 opencode-zen 之类工具的实际收益，属于围绕接入与使用场景的延伸讨论。 补充讨论：整体上，大家普遍认可“统一信息入口”方向，但认为要成功，关键在于长期维护、强筛选能力，以及补充质量/延迟/路由等动态数据。

OpenAI的一个模型解决了离散几何中的一个核心猜想——平面单位距离问题。这个由数学家Erdős在1946年提出的问题，近80年来一直困扰着数学界：在平面上放置n个点，最多能有多少对点之间的距离恰好为1？ 长期以来，数学家们认为"方格网格"构造是最优解。但OpenAI的模型推翻了这一猜想，找到了一个多项式级别的改进方案，并运用了代数数论的高级工具。 这是AI首次自主解决数学子领域的重要开放问题，标志着AI推理能力的重大突破。菲尔兹奖得主Tim Gowers称其为"AI数学的里程碑"，数学家们认为这证明了AI不仅是辅助工具，更能产生原创性的天才想法并将其实现。

评论摘要
主要讨论点：OpenAI模型解决数学难题（Erdős猜想）的意义及其对科学研究的影响 不同观点： • **乐观派**：认为这是重大突破，LLM能帮助科学家突破日益增长的复杂性障碍和过度专业化问题，使数学家能够跨领域调用工具和灵感，扩展研究雄心（trostaft, cpard） • **技术质疑派**：指出这次是通过反例证伪而非正面证明，本质上是高级搜索和连接现有想法，而非创造新数学理论；真正的理论创新还需要更长时间跨度的工作能力（mooreat） • **透明度怀疑派**：质疑训练数据的来源和过程透明度，担心OpenAI可能使用了专家生成的原创训练数据甚至已有解法，无法确定模型是否真正"独立"解决问题；同时质疑解题过程中的人工干预程度和尝试次数（recitedropper, lesostep） • **成本效益关注者**：关心解题消耗的总token数和计算成本，认为这影响对成果的评价——是相当于1人1年还是1000人1年的工作量（Quentak） 补充讨论： - 模型输出缺乏引用归属，这在数学界很重要（trostaft） - 有人认为"重组现有材料"不应被贬低，否则许多菲尔兹奖得主也该被质疑（m-hodges） - OpenAI在学术领域似乎领先于Anthropic和Google（aurareturn）

Multi-Stream LLMs: new paper on parallelizing/separating prompts, thinking, I/O

作者: atomicthumbs | 评分: 151 | 评论数: 12 | 发布时间: 2026-05-21 19:37
文章摘要

这篇论文提出了多流语言模型（Multi-Stream LLMs），突破了传统语言模型单一顺序处理的限制。现有AI代理基于消息交换格式，只能串行处理——无法在阅读时输出、在写作时接收新信息、在思考时行动。该研究通过将指令微调从顺序消息格式转变为多个并行计算流，将不同角色分离到独立流中，使模型在每次前向传播时能同时从多个输入流读取并在多个输出流生成token。这种方法提升了模型的可用性、效率、安全性和可监控性。

评论摘要
主要讨论点：关于AI模型并行流（parallel streams）架构的可行性、效果和实现方式 不同观点： • **支持并行化提升性能**（killcoder, jhack, foota）：认为并行处理是提升性能的有效途径，工具调用和代码生成任务天然具有并行性，可通过异步流模式和任务分解实现。强调定期打断模型重新迭代能显著改善输出质量，单一文本流的限制应被打破。 • **质疑并行效果**（bob1029）：实践中禁用并行工具调用后，结果质量反而显著提升。虽然速度变慢，但正确率更高、更可预测。认为"慢即是快"，稳定的串行方式优于追求速度。 • **技术实现的担忧**（NitpickLawyer, Eextra953, coalteddy）：关注数据准备过程可能存在污染问题（用80B模型转换数据），希望看到强化学习验证；担心并行流会分割上下文导致单流上下文变短；质疑不同流产生矛盾token时如何处理。 补充讨论： NitpickLawyer指出该架构提供了大量可调节参数（流间注意力权重、独立评分等），类似OpenAI的harmony模板但采用并行而非顺序方式。论文作者承认模型规模较小、训练数据有限，需要更大规模验证。部分开发者开始思考如何调整现有上下文管理策略以适应新架构。

GitHub confirms breach of 3,800 repos via malicious VSCode extension

作者: Timofeibu | 评分: 1037 | 评论数: 87 | 发布时间: 2026-05-20 13:43
文章摘要

GitHub确认发生数据泄露事件，约3,800个内部代码仓库被攻击者窃取。事件起因是一名员工安装了恶意的VS Code扩展程序（后确认为被篡改的Nx Console扩展）。GitHub已从市场移除该恶意扩展并隔离受感染设备。黑客组织TeamPCP声称掌握这些数据并索要至少5万美元。GitHub表示目前仅内部仓库受影响，客户数据未受波及。此事件与TanStack npm供应链攻击有关，凸显了开发工具扩展的安全风险。

评论摘要
主要讨论点：VSCode扩展安全漏洞导致GitHub内部仓库被入侵，引发开发者对IDE扩展安全模型的广泛担忧 不同观点： • **批评VSCode安全缺失派**：认为VSCode扩展安全模型几乎不存在，微软多年来忽视2018年就提出的沙箱功能请求，将精力放在Copilot而非安全上。扩展可随意访问文件和网络，这是明显的攻击向量 • **谨慎使用派**：只安装官方公司扩展，但即便如此也难以确认真伪。VSCode经常弹窗推荐扩展，其中混杂着公司和个人开发者的扩展，有些虽有数百万安装量但难辨真假 • **转向替代方案派**：因安全问题放弃VSCode，转用Zed编辑器（采用WASM扩展和dev-container隔离语言服务器）或将Code Server放在Docker容器中运行，尽管后者体验欠佳 • **系统层面反思派**：认为问题根源在操作系统安全模型——应用默认可访问所有文件和网络是不合理的。同时指出Linux沙箱化极其困难，Electron的SUID沙箱助手难以在沙箱中运行 补充讨论：有开发者怀疑此次攻击与nx console扩展被入侵有关（时间吻合）。也有人对GitHub拥有3800个内部仓库感到意外，还有调侃GitHub运行时间窗口的评论。社区普遍呼吁微软和其他IDE厂商建立显式权限系统。
