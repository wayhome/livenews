Help I accidentally a wigglegram

作者: gregsadetsky | 评分: 554 | 评论数: 51 | 发布时间: 2026-06-20 01:55
文章摘要

作者发现自己拍照时习惯从多个角度拍摄同一场景，手机里积累了大量类似照片。这些照片恰好可以制作成"wigglegram"（摇摆动图）——一种通过循环播放不同角度的照片来产生立体效果的动图。作者编写了一个脚本，使用感知哈希技术自动识别照片库中的相似图片序列，成功提取出数百个意外拍摄的wigglegram素材，包括风景、动物、设计作品和雕塑等。脚本已在Github开源，支持Mac的iCloud照片库或本地目录。

评论摘要
主要讨论点：wigglegram（摇摆动图）的制作方法、技术演进及观赏体验 不同观点： • **制作方法派**：aleyan详细介绍两种主流方法——多镜头同时拍摄（如80年代Nimslo相机）和单张照片合成深度图。认为iPhone的多重曝光和LiDAR深度传感功能使现代设备进入wigglegram黄金时代，但这种形式已过时 • **技术实践者**：scottshambaugh开发了matplotlib可视化库、GL26分享定制树莓派四摄像头方案、ksymph利用任天堂3DS双摄制作web应用。强调后期对齐处理的重要性（strickinato指出锁定焦点对视差效果至关重要） • **体验负面者**：nkrisc和jakzurr表示"意外"wigglegram引发眩晕和偏头痛症状，认为循环速度过快。rendaw觉得额外运动反而削弱了深度错觉，看起来像不连贯的动画 • **设计欣赏派**：computerfriend称赞网站设计和图像抖动效果，vova_hn2发现原图比像素化版本更好看 补充讨论：y04nn提到Pixel/iPhone的短视频元数据功能可保存静态图像丢失的运动信息；jannyfer赞赏手写代码的真实感；olwmc认出作者是优秀的前同事

VibeThinker: 3B param model that beats Opus 4.5 on reasoning with novel SFT+GRPO

作者: timhigins | 评分: 226 | 评论数: 23 | 发布时间: 2026-06-23 02:01
文章摘要

VibeThinker-3B是一个仅有30亿参数的小型语言模型,研究其在可验证推理任务上的极限表现。通过课程式监督微调、多领域强化学习和离线自蒸馏等优化技术,该模型在AIME26数学竞赛(94.3分)、LiveCodeBench编程(80.2分)和LeetCode竞赛(96.1%通过率)等严格可验证任务上达到顶级水平,性能匹敌甚至超越DeepSeek V3.2、GLM-5等参数量大得多的旗舰模型。研究提出"参数压缩-覆盖假说":可验证推理能力可压缩到紧凑推理核心中,而开放领域知识需要广泛参数覆盖,表明小模型在特定能力上可达到前沿性能。

评论摘要
主要讨论点：关于小型推理模型（vibe thinker等3B参数模型）在实际开发场景中的表现和应用潜力 不同观点： • **乐观派**：认为小模型通过专注推理训练可以媲美大模型，类似"聪明但知识有限的人配合工具"的模式。支持领域专精的小模型发展，可部署在边缘设备（如ASIC芯片）实现高速推理 • **谨慎派**：质疑基准测试是否真实反映开发者工作流，强调模型需要足够的基础知识储备才能有效工作（类比"10岁孩子无法开车"），小模型在某些任务上表现不佳 • **实用主义者**：提出双模型架构——用小型工具调用模型处理主流程，调用推理模型处理复杂逻辑；或让Agent承担更多职责，模型只做特定任务 补充讨论： 实测反馈差异大：在Python代码和安全审查场景有一定效果，但存在明显局限——仅擅长Python、结构化输出较弱、SVG生成失败、安全漏洞检测零发现。社区关注点包括本地部署方法、与其他小模型（Qwen 3.6、Gemma 4）的对比，以及如何与代码生成模型组合使用。核心争议在于推理能力与知识储备的权衡。

评论摘要
主要讨论点：关于AI模型Fable性能的评价，以及与其他模型（Opus、GPT、DeepSeek等）的比较 不同观点： • **Fable显著优于前代模型**：多位用户认为Fable在实际使用中表现出色，能一次性完成大型功能，发现其他模型遗漏的bug（如Qt C++数据损坏bug），在空间推理方面尤为突出。有用户形容它像"旧版Opus的回归"但更智能 • **统计数据存在误导**：JumpCrisscross指出排行榜排序有问题，GPT 5.5 Pro只完成4个测试案例中的2个却排名第一，经Wilson评分区间调整后，DeepSeek-v4因速度快（91秒）和成本低应是真正赢家 • **Mythos只是解除安全限制的普通模型**：po1nt认为Mythos的特殊之处仅在于关闭了安全功能，如果现有模型不抵触搜索漏洞，可能表现同样出色 • **Opus系列模型退步明显**：airstrike指出Opus 4.6曾经优秀，但后续版本被"阉割"，4.7和4.8写出大量废话且不可用，Fable让人重拾旧版Opus的体验 补充讨论： 有用户质疑Anthropic的营销手段可能夸大其词以提升估值；Agent功能未必总能提升效果反而增加成本；威胁在于零专业知识的人也能利用Mythos找到零日漏洞；需要更科学的评测方法（如ROC曲线、置信区间）而非简单的排行榜。

8086 Segmented Memory was a good idea

作者: billpg | 评分: 57 | 评论数: 21 | 发布时间: 2026-06-21 14:07
文章摘要

这篇文章为Intel 8086的分段内存架构辩护。作者指出，8086用两个16位寄存器（段寄存器和偏移量）组合生成20位地址，以实现1MB内存访问。Intel的初衷是将内存划分为多个64KB段，让8080代码无需重写即可运行，并且理论上可扩展至4GB。 然而软件开发者破坏了这个设计——他们利用段之间仅相隔16字节的特性，将分段内存当作连续的平坦地址空间使用（归一化指针）。这种做法固化后，80286无法改变段间隔，导致架构受限。作者认为，如果开发者遵循Intel的设计意图，将段作为不透明的选择器而非可计算的地址，这个架构本可以持续数十年。问题的根源在于开发者，而非设计本身。

评论摘要
主要讨论点：8086分段内存模型的优劣评价 不同观点： • **支持者观点**：st_goliath认为分段是简单优雅的设计，本质是64K滑动窗口，通过CS/DS/SS/ES四个段寄存器实现代码数据分离，类似哈佛架构。b800h和justincormack也认为分段直观好用，后者指出WebAssembly的多线性内存就是分段模型，是优秀的安全模型。 • **批评者观点**：wewewedxfgdf和deepsummer强烈反对，认为平坦内存模式明显更优，8086分段是历史包袱。从68k转来的开发者觉得x86是噩梦。RagnarD用实例说明在80年代处理256MB图像缓冲区时分段"绝对可怕"。 • **技术局限批评**：AKSF_Ackermann指出致命缺陷——无法处理超过64KB的对象，导致段溢出、指针比较失效、地址表示复杂化。pif质疑这与数组索引操作的兼容性。tliltocatl认为段寄存器太少且加载缓慢，导致软件放弃使用。 • **设计改进建议**：M95D提出16位段选择器方案，可平滑扩展到286的16MB和386的4GB。peterfirefly建议增加ADSC指令处理段进位。trollbridge认为真正悲剧是选择20位而非24位地址空间。 补充讨论：hexmiles将其类比游戏机的banking模型；senfiaj认为在当时软件简单的环境下尚可，但现代需求催生了分页内存；trollbridge指出Intel原本为128K内存设计，但内存价格骤降使精巧设计失去意义。

An Introduction to YOLO26

作者: teleforce | 评分: 79 | 评论数: 16 | 发布时间: 2026-06-23 01:52
文章摘要

YOLO26是2026年1月发布的端到端多任务计算机视觉模型系列，支持目标检测、实例分割、姿态估计、定向目标检测和图像分类。提供从Nano到Extra Large五种尺寸变体。主要改进包括：移除非极大值抑制（NMS）降低延迟、去除Distribution Focal Loss模块以提升边缘设备兼容性、CPU推理速度提升43%、引入MuSGD优化器改善训练稳定性、增强小目标识别能力。模型针对边缘部署优化，支持多种导出格式，在COCO数据集上表现优异，mAP从40.9（Nano）到57.5（XL）不等。

评论摘要
主要讨论点：YOLO26发布后，社区对其性能、许可证和替代方案的评价 不同观点： • **许可证争议方**：Ultralytics采用AGPL协议过于激进，存在"钓鱼式"收费风险。Frigate项目因此拒绝集成YOLO模型。建议选择Apache 2.0的RF-DETR或LibreYOLO等真正开源的替代方案 • **性能质疑方**：长期用户反馈YOLO26在足球视频任务中表现不如v9和v11，质疑为何Roboflow和Ultralytics大力推广此版本 • **实用局限方**：YOLO26仅支持80个COCO类别，未标注物体无法识别。对比SAM2虽慢但可识别任意物体，更适合通用场景。示例图中三只熊被误识别为两只大象 • **正面评价方**：易于训练自定义数据集，部署简单（支持Rust+AVX2），可实现近实时推理。在老版本YOLO上训练2D游戏检测效果良好 补充讨论：CLIPSeg被推荐为无需训练的替代方案；有用户寻找浏览器端实时演示；RF-DETR被多次提及为速度更快、精度更高的开源替代品

Deno Desktop

作者: GeneralMaximus | 评分: 1074 | 评论数: 68 | 发布时间: 2026-06-22 05:38
文章摘要

`deno desktop` 是 Deno 2.9 版本推出的新功能，可将 Deno 项目（从单个 TypeScript 文件到 Next.js 应用）打包成独立的桌面应用程序。主要特点包括：默认使用系统 WebView 保持体积小巧，完全兼容 Node 生态系统；自动检测并支持主流前端框架（Next.js、Astro、Remix 等）；使用进程内绑定而非 IPC 通信；支持从单台机器交叉编译到 macOS、Windows 和 Linux；内置二进制差分自动更新功能。开发者只需一行命令即可将 Web 应用转换为桌面应用，无需修改代码。

评论摘要
主要讨论点：Deno Desktop 作为跨平台桌面应用开发工具的优劣势，以及与 Tauri、Electron 等竞品的对比 不同观点： • **对 Deno Desktop 持积极态度**：认为 Deno 生态成熟，TypeScript 原生支持是优势，虽然包体积比 Tauri 大（40MB vs 5MB），但 150MB 的下载时间可接受，且渲染引擎更可靠 • **Tauri 仍有独特优势**：支持 sidecar 嵌入现有应用、可与 Elixir/BEAM 集成打包单一二进制文件，Livebook Desktop 等成功案例证明其成熟度；WebView 虽有局限但正在通过 CEF 改进 • **对 Web 技术作为 UI 工具的质疑**：批评 Electron 类应用无法遵循操作系统原生 UI 模式，Web 技术本质上不是真正的 UI 工具包，即使是未样式化的按钮也无法原生适配各操作系统 • **技术细节的讨论**：关于共享 CEF 运行时的版本管理问题、多进程模式下是否真的是共享内存还是 IPC、权限系统如何在编译时向用户展示等实现细节的疑问 补充讨论：有人指出文档将 electrobun 错误标注为仅支持 macOS（实际支持多平台）；有开发者更偏好原生 UI；还有人提到替代方案如 WASM 方案（Jumpjet）可不依赖浏览器引擎；Deno Desktop 的 canary 版本可通过压缩将应用体积降至 15MB
