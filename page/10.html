Behind the 6-digit code: Building HOTP and TOTP from scratch

作者: dogacel | 评分: 230 | 评论数: 24 | 发布时间: 2025-04-11 13:06
文章摘要

这篇文章主要介绍了基于一次性密码（OTP）的认证机制，特别是HOTP和TOTP的工作原理。OTP是一种用于动态生成密码的技术，有效防止重放攻击。与传统密码不同，OTP每次使用后即失效，或在限定时间内有效。 文章首先解释了OTP的基本概念，然后详细介绍了HOTP（基于计数器的一次性密码）和TOTP（基于时间的一次性密码）。HOTP通过一个递增的计数器生成密码，而TOTP则使用当前时间作为计数器，通常以30秒为间隔更新密码。 文章进一步说明了TOTP的生成公式，强调了密码生成依赖于共享的密钥，且该算法必须是可预测且同步的，以确保客户端和服务器生成相同的密码。TOTP的优势在于利用时间同步，避免了计数器同步问题，并减少了恶意用户收集密码的可能性。 文章最后提到，HOTP和TOTP已被标准化，并广泛用于双因素认证（2FA）系统中。

JEP 506: Scoped Values final for Java 25

作者: ludovicianul | 评分: 33 | 评论数: 4 | 发布时间: 2025-04-15 11:17
文章摘要

JEP 506 提出引入 "scoped values" 机制，允许方法在线程内及其子线程中共享不可变数据。相比线程局部变量（ThreadLocal），scoped values 更易于理解和推理，具有更低的空间和时间成本，尤其在与虚拟线程（JEP 444）和结构化并发（JEP 505）结合使用时。该机制经历了多个预览和改进阶段（JEP 429, JEP 446, JEP 464, JEP 481, JEP 487），并计划在 JDK 25 中正式引入。其目标包括易用性、可理解性、健壮性和高效性，但不旨在改变 Java 语言或废弃 ThreadLocal API。Scoped values 解决了在方法间传递共享数据时的繁琐问题，尤其在大型程序中不同组件间传递上下文时非常实用。

评论摘要
主要讨论点：Java中通过隐式参数传递上下文的机制及其与现有机制的比较 不同观点： • [bhawks] 认为隐式参数传递（如参数走私）过于“魔法化”，不如Golang中的context.Context那样明确和广泛接受。虽然他承认在Java生态中引入类似Golang的机制可能不现实，但从实际角度看，这种隐式传递可能是传播上下文的唯一可靠方法。 • [Pet_Ant] 认为ScopedValue机制类似于一种DSL，用于替代ThreadLocal，并且能更好地表示变量的生命周期，而不是像ThreadLocal那样作为全局变量。他提到虚拟线程的引入会大幅增加线程数量，传统的ThreadLocal机制难以应对。虽然他承认这种机制在处理大量数据时可能有好处，但对于大多数企业级CRUD应用来说，可能并不适用。他还猜测这种机制可能与函数式编程中的Monad概念有关，但表示自己不是函数式编程的专家。 • [skerit] 对ScopedValue提案表示感兴趣，认为自己在某些情况下可能会使用这种机制。 • [djenndhxhd] 提到 tramp parameters（传递参数）是常见现象，若不谨慎处理会带来问题。他认可ScopedValue提案的价值。 补充讨论： • 争议的焦点在于隐式参数传递是否过于“魔法化”以及其在Java生态中的适用性。 • ScopedValue相对于ThreadLocal的优势和适用场景，特别是在处理大量虚拟线程时的表现。 • 对ScopedValue机制是否属于Monad的猜测，反映了参与者对函数式编程概念的不同理解。 • 对ScopedValue提案的实际应用价值存在一定共识，多数参与者认为在特定场景下可能有帮助。

New Vulnerability in GitHub Copilot, Cursor: Hackers Can Weaponize Code Agents

文章摘要

What I don't like in JavaScript

文章摘要

本文讨论了作者对JavaScript的喜爱与不满。尽管JavaScript有一些设计缺陷和不一致之处，但作者认为它依然是一个强大且灵活的语言。JavaScript的优点包括简单易学、变量模型统一、支持闭包、异步编程便捷、语法人性化、灵活性高以及性能较好。然而，作者也指出了几个问题： 1. **`typeof`和`instanceof`操作符**：这两个操作符容易混淆，导致错误。特别是`typeof null`返回"object"而不是"null"。 2. **`NaN`比较**：`NaN`不等于自身，需用特殊方法比较。 3. **`Array.prototype.sort()`默认比较器**：默认按字典顺序排序，需自定义回调函数以正确排序数字。 4. **对换行的敏感性**：JavaScript自动插入分号机制可能导致意外行为，如函数返回`undefined`。 5. **意外声明全局变量**：忘记使用`let`、`const`或`var`可能导致声明全局变量。 尽管有这些问题，作者仍认为JavaScript是一个优秀的编程语言。

评论摘要
主要讨论点：JavaScript中NaN的行为及其依据的IEEE 754标准 不同观点： • **NaN行为符合IEEE 754标准**：mubou指出，NaN的比较行为是依据IEEE 754标准定义的。根据该标准，任何两个值的比较可能小于、等于、大于或无序。对于NaN，任何比较都会被认为是无序的。这意味着像 ">" 这样的操作符在比较NaN时总是返回false，例如"5 > NaN" 和 "NaN > 5" 都返回false。 • **NaN比较的无序性导致的结果**：由于NaN比较无序，正向比较（如 == 和 >）总是返回false。然而，反向比较（如 !=）总是返回true，因为根据定义，A != B 等价于 !(A == B)。由于NaN永远不会等于任何值，因此任何值与NaN的比较都会返回true。 补充讨论： • **是否应对NaN进行特殊处理**：mubou提到了一种可能的观点，即是否应对NaN在==操作符上进行特殊处理，使其表现不同于标准定义。然而，当前规范并没有这样做，因此NaN与任何值的相等比较都返回false。 争议焦点： • 争议的焦点在于NaN的处理是否应该在==操作符上进行特殊处理。当前标准选择不特殊处理NaN，导致了一些反直觉的结果，比如NaN != NaN 返回true，这可能会让不熟悉IEEE 754标准的开发者感到困惑。
