MCP doesn't need tools, it needs code

作者: the_mitsuhiko | 评分: 216 | 评论数: 26 | 发布时间: 2025-08-18 09:53
文章摘要

本文探讨了MCP（模型上下文协议）与命令行工具在AI代理编程中的优劣比较。作者指出命令行工具存在平台依赖性、版本兼容性和文档缺失等问题，且代理在管理状态会话时容易出错。虽然命令行工具具有组合灵活性（如通过bash脚本），但MCP在状态保持方面表现更好。作者建议采用折中方案：将MCP服务器设计为支持单一工具（如Python解释器），通过eval()执行代码并保持状态，既保留了编程灵活性又解决了状态管理问题。最后以pexpect-mcp项目为例，展示了这种混合方法的可行性。

评论摘要
主要讨论点：[MCP（Model Context Protocol）的优缺点及其替代方案的讨论] 不同观点： • **支持MCP的观点** - MCP通过提供工具集，可以作为LLM的防护栏/沙盒，适用于特定任务（如专业工作流）。 - 示例：MCP服务器（如scosman的YAML工具描述）能提高效率，减少错误命令，并支持并行执行。 • **反对MCP的观点** - MCP限制了LLM的能力，使其输出受限，不适合作为无界伴侶（如编程助手）。 - 争议焦点：MCP是否真正“连接模型与世界”，还是仅仅是一种限制性协议。 - 示例：jumploops认为MCP是“防护栏”，而非“超能力”；BLanen批评MCP缺乏正式行为规则。 • **替代方案提议** - 直接调用原生API（如HTTP/CLI/WebSocket），避免专用包装服务器（juanviera23的UTCP协议）。 - 代码注入与沙盒化：通过安全运行时（如CharlieDigital的Jint、preek的Guix/Bubblewrap）允许LLM生成并执行代码。 - 对象能力（object capabilities）作为沙盒化方案（ryukafalz）。 补充讨论： - **安全性争议**： - 部分用户担忧代码注入风险（xavierx），而其他人主张沙盒化（pploug、preek）或容器化（scosman）作为解决方案。 - **工具与代码的权衡**： - larve认为赋予LLM代码执行能力（如eval()）比工具定义更灵活，能减少token消耗并支持临时应用开发。 - **协议成熟度**： - philipp-gayret指出MCP工具尚未成熟，输出污染上下文，更倾向于直接使用Python沙盒。

这篇文章讲述了作者通过IRC（互联网中继聊天）结识朋友并学习编程的经历，以及一个由朋友玩笑引发的"割草机IRC服务器"计划。作者回忆了90年代在Undernet网络上的成长经历，IRC帮助他接触不同文化和编程爱好者，最终成为软件工程师。2020年，朋友提议将他的割草机改装成IRC服务器的玩笑持续发酵，尽管最初是个恶作剧，但朋友们坚持追问进展，展现了IRC社区特有的幽默和持久友谊。

评论摘要
主要讨论点：[关于将树莓派（Pi）连接到割草机并运行IRC服务器的有趣项目及其引发的讨论] 不同观点： • **[支持创意和技术乐趣]** - [wolrah] 和 [mrweasel] 赞赏项目的趣味性和互联网的创意精神，认为这是互联网应有的内容。 - [bombcar] 进一步提出现代电动割草机可能具备运行更复杂程序（如DooM）的能力，并认为直接在其上运行IRC服务器会很有趣。 • **对IRC的怀旧与讨论** - [neilv] 回忆早期互联网通过IRC结识全球朋友的经历，强调其文化价值。 - [herodoturtle] 称赞项目中IRC讨论的文化魅力，认为它完美捕捉了IRC的社区精神。 - [poemxo] 质疑IRC在2021年是否仍然相关，引发对IRC现代意义的讨论。 • **技术实现的扩展与建议** - [jeremysalwen] 和 [DonHopkins] 提到其他类似项目（如OpenMower），建议将割草机完全通过IRC控制。 - [calgoo] 讨论了IRC在隐私和审查方面的技术问题，提出关于SSL加密和服务器管辖权的疑问。 补充讨论： • **争议点**：IRC的现代实用性（[poemxo]的质疑与其他用户的怀旧形成对比）。 • **幽默与无厘头**：[BobbyTables2] 的“鳟鱼”评论为讨论增添了轻松氛围。 • **技术可行性**：[bombcar] 提到廉价中国品牌割草机的可黑客性，引发对硬件潜力的探讨。
