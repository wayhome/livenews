Bypassing the Branch Predictor

作者: signa11 | 评分: 67 | 评论数: 14 | 发布时间: 2025-11-16 06:51
文章摘要

这篇文章探讨了当分支预测器对程序性能产生负面影响时的解决方案。作者以金融交易系统为例，说明在大多数交易被放弃的情况下，分支预测器会倾向于预测"放弃"路径，导致少数需要发送的交易因预测错误而付出性能代价。文章分析了x86和ARM架构对分支预测的控制能力，指出现代x86处理器已不再支持通过指令前缀强制预测方向。虽然C++20引入了[[likely]]和[[unlikely]]属性，但它们主要影响代码布局而非实际预测行为。最后，作者提出了一个实用解决方案：通过注入大量模拟交易来"训练"分支预测器，使其倾向于预测"发送"路径。这种方法虽然不够完美，但在现代x86架构上提供了一种可行的优化途径。

评论摘要
主要讨论点：[如何优化分支预测以减少交易处理中的性能损耗] 不同观点： • **使用条件移动指令** - 通过条件移动避免分支预测错误，但可能阻止CPU正确推测路径 - 极端情况下可使用低级技巧（如触发异常）强制CPU不推测失败路径 • **利用ARM/x86的预测指令差异** - 有人误以为ARM支持分支预测指令（BEQP/BEQNP），实际x86才有相关机制 - 引发关于不同架构支持预测指令的讨论 • **滥用返回地址预测器** - 通过修改返回地址将冷路径（abandon）伪装成正常返回，欺骗预测器 - 需处理控制流完整性和栈状态问题 • **完全避免分支** - 通过布尔逻辑或标记无效交易（如伪造校验和）无条件执行，下游丢弃无效请求 - 示例：网络适配器直接丢弃标记的包 • **内存预取优化** - 认为5微秒远超分支预测开销，建议预取热路径内存以减少实际影响 • **C++属性标签的争议** - `[[likely]]`/`[[unlikely]]`实际效果有限，且语义易混淆（需标记“希望加速的冷路径”） - 质疑其被纳入标准的合理性 补充讨论： - **性能争议焦点**：是否分支预测是主要瓶颈（5微秒可能包含其他因素） - **架构差异**：x86与ARM的分支预测机制差异及开发者误解 - **极端方案风险**：异常触发或返回地址篡改可能破坏可维护性 - **缓存一致性**：即使预测正确，冷路径代码可能不在缓存中

I made a better DOM morphing algorithm

作者: joeldrapper | 评分: 93 | 评论数: 16 | 发布时间: 2025-11-07 12:02
文章摘要

文章介绍了DOM Morphing技术及其挑战，重点讨论了节点识别问题。现有解决方案如依赖id属性或子节点id集合，但存在局限性，尤其在无id时会导致不必要的大量节点变更。作者提出新库Morphlex 1.0，通过匹配算法优化处理插入、删除和排序操作，减少不必要的节点变化，提升性能。

评论摘要
主要讨论点：[DOM morphing/diffing 技术的适用性和优缺点] 不同观点： • **支持 DOM morphing/diffing** - 优点：提升性能（如 Turbo 8 的 View Morphing 带来明显的速度提升），减少不必要的 DOM 操作（如 Morphlex 比 diffHTML 快 8→69 倍）。 - 用例：适用于 SSR（服务端渲染）场景，如解决 htmx 在 DOM 交换时的状态丢失问题（igor47 的讨论）。 - 创新点：Morphlex 和 Idiomorph 在解决 DOM 重排序等问题上有新思路（originofstorms 的评论）。 • **反对 DOM morphing/diffing** - 缺点：性能优化有限（spankalee 认为 99% 的情况下是坏主意），不如直接比较模板 ID 并完全重新渲染。 - 争议点：HTML 作为数据传输格式效率低（解析慢、体积大），不如 JSON + 客户端渲染（CSR）。 - 替代方案：使用模板标记和客户端渲染（spankalee 提出），或直接采用 SPA 架构（incrudible 的评论）。 补充讨论： - **技术细节争议**：是否应该使用内存中的节点 ID（Nathanba 的疑问）或 immutable DOM 表示（conartist6 的提案）。 - **工具链需求**：是否有支持 JSX 的 DOM diffing 库（geon 的提问）。 - **术语争议**：是否应称为“DOM Merging”而非“DOM morphing”（jdthedisciple 的建议）。 - **实际案例**：Turbo 8 使用 Idiomorph 实现 View Morphing（dmix 的体验）。
