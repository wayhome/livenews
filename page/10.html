I Got Claude to Write Code I Could Ship

作者: gen220 | 评分: 8 | 评论数: 1 | 发布时间: 2025-07-28 14:26
文章摘要

本文介绍了作者如何使用Anthropic的Claude Code工具来编写可交付的代码。尽管Claude Code能自动化处理许多任务，如修复bug和重构代码，但它生成的代码往往过于庞大且难以理解，导致审查困难。为解决这一问题，作者引入了"stacked PRs"（堆叠式拉取请求）的方法，将大块代码拆分为一系列小而可独立审查的PRs。通过在提示中加入规划和分步执行的指导，Claude Code学会了按计划生成堆叠的PRs，从而提高了代码的可审查性和质量。最终，Claude Code成为作者处理工程任务的得力工具，尤其在处理遗留代码和长期搁置的重构任务方面表现出色。作者还开发了GT MCP工具，以推广这种工作流并应用于其他AI代理。

评论摘要
主要讨论点：代码提交的结构和流程优化 不同观点： • frankfrank13指出，当前堆栈中最大的Pull Request（PR）包含268行代码，但大部分是HTML。这表明该PR的主要内容为HTML结构和样式，可能相对简单。该用户关注代码的组成以及每部分的贡献。 • frankfrank13建议在编写任何代码之前，应向用户展示计划提交的堆栈结构，并请求确认。这强调了在开发过程中透明度和用户确认的重要性，以确保开发方向符合预期。 • 该用户还强调了每个PR的代码必须是原子的（即单一职责，不包含不相关更改），并且必须通过持续集成（CI）。这指出了代码质量和开发流程中的关键要求，以确保每个PR的独立性和稳定性。 补充讨论： • 强调了在PR提交之前，确认代码结构和通过CI的重要性，以避免不必要的错误和回滚。 • 提出了对代码提交流程的改进建议，特别是在多层审核和确认机制方面，以提高团队协作的效率和代码质量。 争议焦点： • 当前堆栈中PR的大小和内容构成是否合理。有人可能认为268行的HTML代码是可以接受的，而其他人可能觉得应该进一步拆分以提高可读性和审核效率。 • 如何在代码提交前有效地进行结构展示和确认，以平衡开发速度和代码质量。这可能涉及工具支持和团队流程的调整。

GPT might be an information virus (2023)

作者: 3willows | 评分: 87 | 评论数: 26 | 发布时间: 2025-07-27 20:23
文章摘要

文章讨论了生成式模型（如ChatGPT）在未来2-5年内对网络和信息经济的潜在影响。作者认为，自动生成与人类内容无异的大量内容将严重破坏现有的网络生态。当前，许多小企业利用ChatGPT进行SEO优化，生成网站内容、社交媒体帖子和评论，这加速了内容农场的低质内容泛滥。随着AI生成内容的增加，真实有价值的信息将更难获取，而人类创作的动力也可能减弱。作者将此现象比作“信息病毒”，认为经济利益驱动下，AI生成内容将充斥网络，导致人类无法有效利用网络获取信息。谷歌等搜索引擎面临严重威胁，因为它们无法检测和过滤这些错误内容，最终可能失去用户和广告商的信任。文章最后提到，即使谷歌推出更先进的AI工具，这一趋势仍无法逆转。

Fast and cheap bulk storage: using LVM to cache HDDs on SSDs

作者: todsacerdoti | 评分: 215 | 评论数: 19 | 发布时间: 2025-07-27 03:38
文章摘要

本文介绍了如何利用Linux的逻辑卷管理器（LVM）构建一个缓存的RAID阵列，结合SSD和HDD以实现高性价比的存储方案。SSD用于加速频繁访问数据的读取，而大容量的HDD用于存储不常访问的数据。作者选择LVM缓存而不是ZFS或其他工具，因为LVM配置简单且兼容性好。HDD部分采用RAID 1以提高数据可靠性，防止磁盘故障导致数据丢失。文章详细介绍了硬件设置、RAID 1配置、缓存分区创建及逻辑卷管理的具体步骤，并讨论了该方案的优势和注意事项。通过这种方式，用户可以在享受SSD高速性能的同时，利用HDD的大容量存储。

评论摘要
主要讨论点：LVM及其相关技术（RAID、缓存、精简配置等）的使用经验和优缺点 不同观点： • **支持LVM的灵活性与功能**： - dale_glass认为LVM非常灵活，具备RAID、迁移、完整性检查、缓存、快照、精简配置等多种功能，推荐将所有设备放入同一个卷组（VG）以充分利用LVM的灵活性。 - iam-TJ也支持LVM的RAID功能，指出LVM可以按逻辑卷（LV）进行定制，包括缓存、镜像等，且支持实时扩展，非常灵活。 • **对精简配置（thin provisioning）的警告**： - dale_glass警告不要轻易使用精简配置，因为其性能影响显著，且在数据故障时可能会导致问题。 • **对缓存功能的讨论**： - gopalv指出缓存的性能提升取决于访问模式，并分享了使用ext4外部日志和将SSD用于缓存的成功经验，但也提到SSD故障可能导致数据丢失的风险。 - jpecar对LVM缓存持负面态度，认为其早期版本像一个黑盒，无法根据工作负载调整，最终选择了全闪存方案。 • **RAID和数据损坏问题**： - Szpadel提醒RAID1仅在磁盘完全损坏时提供保护，但在数据损坏时可能会导致双磁盘数据损坏，而像ZFS或Btrfs这样的文件系统具备校验功能，能更好地处理这种问题。 • **对LVM和MDADM的批评**： - KaiserPro对LVM和MDADM持负面态度，认为早期文档不足，且LVM快照曾经不实用，推荐ZFS或GPFS。 • **对其他技术的提及**： - riedel询问QNAP NAS的分层技术，认为灵活的分层比缓存更适合普通用户。 - rsync提到ZFS的元数据缓存设备可以大幅提升IOPS，但警告如果丢失元数据设备会导致数据池丢失。 • **其他实现细节和建议**： - oakwhiz分享了设置LVM RAID5的经验，指出设置过程复杂，但运行良好。 - Padriac强调RAID需要监控和告警，以避免潜在问题。 - whazor建议使用写回缓存以提高写入速度。 - hinkley提到将数据库的WAL文件放在最快存储上以加速数据库。 - bjt12345怀念Optane驱动器。 - thebeardisred指出需要定量测试方法（如fio、rsync）来评估性能改进。 补充讨论： - LVM的设置和使用涉及复杂的配置和调优，早期文档不足导致一些用户（如KaiserPro）对其持负面态度。 - 不同用户根据自己的需求和经验对缓存、精简配置、RAID等功能有不同的看法，特别是对数据损坏和缓存故障的担忧。 - 对ZFS和Btrfs等其他技术的提及表明，用户在选择文件系统和存储技术时会根据性能、可靠性和功能进行权衡。

Shallow water is dangerous too

Tinyio: A tiny (~200 line) event loop for Python

作者: tehnub | 评分: 111 | 评论数: 7 | 发布时间: 2025-07-22 22:02
文章摘要

**tinyio** 是一个简化版的 Python 事件循环库，仅约200行代码，旨在解决 **asyncio** 的一些复杂性和错误处理问题。它适用于简单场景，当任何协程出错时，整个事件循环会崩溃，所有协程都会取消。与 **asyncio** 不同，它使用 **yield** 而不是 **await** 来暂停和恢复协程。 ### 主要特点： 1. **简单性**：没有 **futures** 或 **tasks**，API 非常少，包括 **Loop**、**run_in_thread**、**sleep** 和 **CancelledError**。 2. **错误处理**：一个协程出错会取消所有协程，错误会传播到整个事件循环和线程中运行的同步操作。 3. **嵌套支持**：允许嵌套事件循环。 4. **线程支持**：通过 **run_in_thread** 可以在线程中运行同步函数，并返回可被 **yield** 的协程。 5. **语法**：使用 **yield** 来暂停协程，支持等待单个或多个协程。 ### 示例： ```python import tinyio def slow_add_one(x: int): yield tinyio.sleep(1) return x + 1 def foo(): four, five = yield [slow_add_one(3), slow_add_one(4)] return four, five loop = tinyio.Loop() out = loop.run(foo()) assert out == (4, 5) ``` ### 安装： ```bash pip install tinyio ``` ### 为什么用 **yield** 而不是 **await**： 因为 **await** 语法需要额外定义如 **tinyio.Task** 这样的类，而 **yield** 更简单直接。
