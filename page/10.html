Kelp – simple replacement for homebrew on macOS

作者: amai | 评分: 74 | 评论数: 15 | 发布时间: 2025-05-19 14:55
文章摘要

Kelp 是一个用 Go 编写的简单工具，作为 Homebrew 的替代品，用于在 MacOS 上安装二进制包。它解决了 Homebrew 公式等待和多电脑同步更新问题，支持同时安装多个包（即将支持）。用户可以通过 releases 页面下载安装，配置文件位于 `~/.kelp/kelp.json`，默认安装路径为 `~/.kelp/bin`。Kelp 支持指定版本安装、手动升级、检查更新等功能。若包不在 GitHub releases 中，用户可直接提供 HTTP(S) 链接进行添加。当前 Kelp 主要为 MacOS 设计，Linux 支持尚未实现。如遇 GitHub API 限流，可设置 GitHub 令牌环境变量解决。项目以满足个人工作流为主，功能请求一般不被接受。

评论摘要
主要讨论点：Homebrew及其替代品的优缺点和使用体验 不同观点： • felipellrocha认为Homebrew在未提示的情况下自动升级所有依赖项，导致其设备出现问题，支持该领域引入竞争。 • disintegrator推荐Mise作为Homebrew和asdf的替代品，特别是对于需要多版本工具的项目，Mise表现出色。 • lambdaba支持使用Nix和nix-darwin来管理非GUI应用程序，并认为Homebrew在处理GUI应用程序方面有优势。 • righthand作为一个macports用户，质疑Homebrew的优势，特别是编译速度方面。 • droelf介绍pixi和pixi global作为Homebrew的替代品，基于Conda包，并具有硬链接去重功能。 • e12e讨论如何处理不在GitHub releases上的软件包，提供通过kelp直接添加二进制链接的解决方案。 • natemcintosh提到sps作为另一个可能的替代品，功能接近Homebrew。 • chin7an推荐bin来管理通过GitHub发布的二进制文件，并提到kelp试图整合这些工具的功能。 • mx-bojangles担心新管理器安装包的可信度。 • pomdtr推荐eget作为另一种选择。 • drcongo分享使用Jetify's Devbox和Mise的体验，认为Mise表现出色，并提到Ubi作为Mise后端的可能性。 • oulipo建议使用mise-en-place作为一种兼容多种包管理系统的元包提供者。 • JadeNB回顾包管理器的历史，质疑包管理器能否保持简单，并提到Fink和Homebrew的演变。 • internet2000幽默地建议包管理器的命名方案。 补充讨论： • 争议焦点：Homebrew的自动升级机制是否合理以及其整体优势。 • 多种替代工具的推荐和比较，如Mise、Nix、pixi、sps、bin、eget和Ubi。 • 对新工具的可信度和实用性的关注。 • 对包管理器命名和历史演变的轻松讨论。

Hyper Typing

作者: azhenley | 评分: 100 | 评论数: 27 | 发布时间: 2025-05-18 20:41
文章摘要

本文讨论了TypeScript类型系统中的一个固有矛盾：更严格的类型更安全，但往往更复杂。作者提出一种称为“过度类型化”（hyper-typing）的现象，即一些库为了追求完美的类型安全，导致类型过于复杂，难以理解，产生难以理解的错误信息，甚至引发不安全的变通方法。作者认为，更简单的类型，甚至是类型生成，通常能带来更实用和愉快的开发体验，尽管它们不那么“完美”。 作者通过一个打印对象属性的函数示例，展示了从宽松类型到严格类型的转变，并指出严格类型提供了编译时的安全保证，但代价是类型定义更加复杂。作者担心“过度类型化”正成为TypeScript生态系统中的趋势，并以TanStack Form库为例，说明这种复杂性如何导致类型文件难以理解、错误信息难以解读，最终迫使开发者使用不安全的变通方法，如将类型强制转换为`any`。

评论摘要
主要讨论点：复杂类型系统在编程中的应用及其优缺点 不同观点： • jasonthorsness认为，类型完备的库是非常有用的，问题往往源于API设计不合理，而不是类型系统本身。一个设计糟糕的API，无论是否有类型，都会很难用。 • nine_k指出，复杂的类型通常反映了缺乏抽象，而不是过度抽象。类型参数过多或嵌套过深，通常意味着需要更好的抽象设计。 • freeqaz寻求在处理复杂静态类型方面更优雅的替代方案，比如Elm或Typed Racket，但也承认不同语言各有其痛点。 • chris_armstrong将问题归因于TypeScript和JavaScript的灵活性，认为这种灵活性导致了复杂类型定义的泛滥，建议使用更简单的TypeScript子集和代码生成工具。 • skrebbel支持使用"Hyper Typing"这个术语来描述过度工程化的类型安全问题。 • CapsAdmin认为，复杂的类型往往反映了底层代码的复杂性，特别是在与JavaScript的动态特性交互时。 • sberens希望IDE能提供更多类型相关的工具功能，比如逐级展开类型定义。 • jasonlantz分享了自己通过构建Rust项目Typesynth来解决类似问题的经验。 • Waterluvian喜欢使用模板类型和点标记路径，但希望TypeScript能更直观地表达数值范围。 • codr7以亲身经历说明在Haskell和C++中过度使用类型可能带来的问题。 • jelder支持手动定义新类型，而不是在泛型中迷失，认为渐进类型系统趋势可能是一个错误。 • codethief对Astro框架生成的类型持批评态度，认为这些类型带来了很多痛苦和bug。 • arcfour认为简单的JSDoc类型注解比TypeScript更适合自己，因为TypeScript带来了额外的问题和时间成本。 补充讨论： • 争议的焦点在于复杂类型系统带来的类型安全和代码可读性、可维护性之间的平衡。 • 不同语言在处理复杂静态类型方面的优劣被多次提及，开发者对替代方案的探索和实践经验分享。 • IDE工具功能改进的建议反映了开发者在实际工作中对类型系统可用性的需求。 • 个人背景和项目类型对类型系统偏好的影响，如系统编程与Web开发的对比。
