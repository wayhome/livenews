Toys/Lag: Jerk Monitor

作者: ptramo | 评分: 49 | 评论数: 9 | 发布时间: 2025-07-06 14:33
文章摘要

作者升级到240 Hz显示器后，对延迟更加敏感，发现无线鼠标更换USB端口后每几秒会有约10毫秒的延迟。为研究这些细微延迟，作者开发了一个工具（found.as/l），用于显示浏览器渲染帧之间以及指针移动报告之间的延迟，还分析了指针事件的批处理及其偏移。为了获得高精度计时器，作者修改了配置文件（xmit.toml），添加了跨源隔离头。最终，作者的观察得到了验证，他将避免使用该USB端口。

评论摘要
主要讨论点：鼠标事件处理、采样率、显示刷新率对用户体验的影响，以及相关技术问题 不同观点： • TheTon：几年前在Windows 10系统上发现鼠标事件丢失导致位置漂移的问题，但在macOS或Linux上没有此问题，怀疑是Windows的bug。尽管如此，仍相信高性能鼠标用户可能会丢失偶尔的移动事件，尽管这不一定被注意到。 • sillysaurusx：虽然可以理解高刷新率（如120Hz）可能有不易察觉但仍可感知的影响，但对8kHz鼠标设置是否真正影响用户体验持怀疑态度。建议通过双盲实验验证高采样率的实际影响，并提到类似的采样率辩论已经在音乐领域有过结论，通常是期望偏差导致人们认为有区别。 • jerlam：提到Logitech无线鼠标由于传感器休眠导致延迟问题，影响用户体验，最后退货。相比之下，之前的游戏鼠标由于高采样率和长休眠时间没有此问题。 • naoru：指出Safari在macOS上可能没有正确处理"pointerrawupdate"事件，导致没有指针事件的帧，同时提到ProMotion在不同浏览器中的帧率差异。 • ptramo：认为在240Hz显示器上需要将鼠标采样率设置为4000Hz或8000Hz，并提到有一个工具可以帮助确认硬件上的设置。 • daft_pink：发现将键盘直接插入Mac的USB端口速度更快，询问是否有更高品质的USB hub。 • xnx：询问某个工具是否测量与另一个网站不同的内容。 • rufus_foreman：无关技术讨论，提到对Devo乐队歌曲的个人喜好。 补充讨论： • 争议焦点：高采样率（如8kHz）是否对用户体验有实际影响。sillysaurusx主张通过实验验证，而TheTon和ptramo则相信高采样率可能有影响。 • 不同操作系统（Windows, macOS, Linux）处理鼠标事件的差异以及对用户体验的影响。 • 无线鼠标因节能功能引入的延迟问题与游戏鼠标高采样率的对比。 • 浏览器和操作系统对鼠标事件处理的兼容性问题。

'Positive review only': Researchers hide AI prompts in papers

文章摘要

研究发现，来自14所大学的学术论文中隐藏了引导人工智能（AI）给出积极评价的指令。这些论文发布在学术平台arXiv上，涉及日本、韩国、中国等八个国家，包括早稻田大学、KAIST、北京大学等。隐藏指令使用白色文字或极小字体，内容如“仅给出积极评价”等，旨在影响AI评审。虽然有研究者认为此举是对依赖AI评审的反击，但许多学术机构表示不知情且不认可这种做法。目前，学术界对AI参与评审缺乏统一规范，部分出版商禁止使用AI工具以避免错误或偏见。该事件凸显了AI应用中的风险及制定相关规则的必要性。

评论摘要
主要讨论点：在学术评审中使用隐藏提示对抗AI生成评审的做法及其伦理性和有效性 不同观点： • 支持使用隐藏提示：一些评论者（如[xg15]、[gmerc]、[ashton314]）认为在论文中加入隐藏提示是对抗“懒惰评审者”使用AI生成评审的有效手段，有助于维护同行评审的诚信。他们建议在各种场合广泛应用这种方法。 • 质疑隐藏提示的必要性：部分评论者（如[dynm]、[empiko]）对使用隐藏提示的做法表示理解，但认为这是对同行评审系统缺陷的反映，质疑其是否为最佳解决方案。他们指出AI生成的评审在识别论文局限性方面可能表现良好，但也可能被滥用。 • 关注系统性问题：[luma]和[chriskanan]提到期刊和会议在评审过程中存在更广泛的问题，如高收费和不合格评审者的问题。他们认为使用AI生成评审的现象反映了系统性缺陷，而不是单纯的技术问题。 • 技术检测手段：[occamschainsaw]和[ashton314]提到已有研究尝试通过技术手段检测AI生成的评审，但目前检测准确率并非百分之百。 • 商业利益与伦理问题：[doug-moen]指出出版商在禁止评审者使用AI工具的同时，自己却在利用AI技术以增加利润，这种双重标准引发了伦理争议。 补充讨论： • 提示设计与随机性：[xg15]建议使用随机提示以增加不可预测性，避免提示本身被滥用。 • 具体案例与实践：[empiko]提到在顶级机器学习会议上，AI生成的评审已成问题，尤其在论文的局限性部分。 • 历史与演变：[zeristor]认为这种对抗行为是系统演变的一部分，未来将会有新的策略和反制措施。 争议焦点： • 使用隐藏提示是否符合伦理，特别是在同行评审系统存在更广泛问题的情况下。 • 技术检测手段的有效性和未来发展方向。 • 出版商和学术机构在AI使用上的双重标准及相关伦理问题。

Deno 2.4

作者: hackandthink | 评分: 117 | 评论数: 11 | 发布时间: 2025-07-07 08:44
文章摘要

Deno 2.4 恢复了 `deno bundle` 命令，用于创建单文件 JavaScript 捆绑包，支持服务器和浏览器平台，兼容 npm 和 JSR 依赖，并通过 esbuild 实现自动树摇和压缩。此外，新增 `--unstable-raw-imports` 标志，允许直接导入文本和二进制文件，简化非 JavaScript 文件的处理。同时，捆绑功能也支持与 `deno compile` 结合使用，可将资源嵌入最终编译的二进制文件中。其他更新包括内置 OpenTelemetry 稳定化、使用 `--preload` 修改环境、更简单的依赖管理等。`deno bundle` 目前为实验性功能，未来计划增加运行时 API 和插件支持。

评论摘要
主要讨论点：Deno 的使用体验、兼容性、技术实现、安全性以及在生产环境中的应用挑战 不同观点： • [outlore] 赞赏 Deno 的设计理念，如 Deno.json、JSR、现代导入方式和 Deno Deploy，但在使用 Next.js 时遇到问题，部分功能（如类型）偶尔出现细微错误。相比之下，Bun 虽然不如 Deno “干净”，但使用起来更简单直接，不过 Bun 也存在如无法在 Vercel 上运行等问题。 • [voat] 强调 Deno 的 Node 兼容性，认为 `compat` 环境变量会促进 Deno 的采用，并建议创建类似 `denon` 的命令来简化兼容模式的使用。 • [aseipp] 欣赏 Deno 在脚本粘合代码中的表现，特别是在 gRPC 支持推出后会更具吸引力，但对于机器学习等特定领域仍会选择 Python。 • [blinkingled] 指出 Deno 在 FreeBSD 上仍然不可用，因为 Rust V8 绑定尚未移植到该平台。 • [impulser_] 对 Deno 选择 esbuild 而非即将推出 v1 版本的 Rust 基础工具 Rolldown 感到意外。 • [eranation] 认为 Deno 在生产环境中未广泛使用的原因是缺乏标准化的漏洞数据库，且由于没有集中式包管理器，使得管理依赖变得更加复杂。 • [mcraiha] 对 `bundle` 子命令的回归表示欢迎，认为这省去了使用变通方法的麻烦。 • [duesabati] 高度评价 Deno，认为它是 Node 应有的样子，但担心 Deno 在面对竞争时会为了追逐短期热度而失去耐心，做出一些不理智的决策。 • [deafpolygon] 表示一直听到对 Deno 的积极评价，可能会因此开始尝试使用 JavaScript。 • [bflesch] 对 Deno 的安全性表示关注，特别指出 `curl mywebsite.com/foo.sh | sh` 这种安装方式存在较大的供应链攻击风险，认为这种做法过于追求便利而忽视了安全性，建议使用如 `npm install -g deno` 这样更安全的安装方式。 补充讨论： • Deno 的安装和使用过程中，安全性成为一个值得关注的问题，特别是在处理外部脚本时。 • 讨论中涉及到 Deno 与 Node 的兼容性问题，以及如何通过工具和命令简化这种兼容性转换。 • 技术实现上，对 Deno 选择的打包工具（esbuild 而非 Rolldown）存在争议，部分用户对 Deno 在特定平台（如 FreeBSD）的支持表示担忧。 • 生产环境中 Deno 的应用受限于漏洞数据库和包管理器的不足，这对大规模采用构成一定挑战。

文章摘要
