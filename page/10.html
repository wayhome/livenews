From XML to JSON to CBOR

作者: GarethX | 评分: 85 | 评论数: 23 | 发布时间: 2025-07-30 10:31
文章摘要

文章简要回顾了数据交换格式的发展，重点介绍了三种格式：XML、JSON和CBOR。XML源于20世纪60-70年代IBM的GML，后来演变为SGML，并于1996年通过W3C简化为XML，旨在为互联网提供结构化的数据交换格式。XML具有良好的可扩展性和兼容性，但较为冗长。JSON则是为Web应用设计的轻量级格式，语法简单，更注重性能和易用性。CBOR是针对物联网等资源受限环境设计的二进制格式，强调高效和紧凑。每种格式都在特定历史背景下解决了不同的技术需求，反映了数据交换格式不断演变的趋势。

评论摘要
主要讨论点：CBOR数据格式及其与其他数据格式（如JSON、XML、MessagePack等）的比较 不同观点： • **CBOR的定位和重要性**： - **mrbluecoat**：认为将CBOR称为“关键数据格式”言过其实，与其他格式如Protobuf、Parquet、Avro和Cap'n Proto相比，CBOR并非那么重要。 - **nabla9**：认为CBOR在需要非常小的代码体积时具有优势，但在可以使用压缩的情况下，CBOR相对于JSON没有显著的数据体积优势。 • **CBOR与JSON的对比**： - **_the_inflator**：赞赏JSON的简洁和易用性，尽管需要为datetime、BLOBs等写类型转换器，但这些转换器正是JSON实用性的原因。此外，JSON的灵活性使其在简单和复杂需求之间取得平衡。 - **brookst**：指出文章中缺少CBOR的具体示例，使其难以理解CBOR的具体表现形式。 • **CBOR与其他二进制格式的对比**： - **makapuf**：认为ASN.1在简洁性和通用性上优于CBOR等格式。 - **camgunz**：认为CBOR和MessagePack在本质上是相同的，但CBOR的标签注册机制和标准化的扩展类型并不实用，且增加了解码负担。 • **CBOR的实际应用**： - **JoelJacobson**：提到CBOR在WebAuthn（Passkey）协议中的实际应用，并分享了一个纯SQL/PLpgSQL CBOR解析器的实现。 - **gethly**：希望浏览器能原生支持CBOR，以便在提高速度的同时减少数据体积，而不需要担心解码问题。 • **CBOR的细节和技术问题**： - **aidenn0**：对CBOR浮点数表示的准确性提出疑问，并指出文档中的潜在错误。 - **fjfaase**：提到文档的下一部分将CBOR与其他二进制存储格式（如protobuf）进行比较。 • **CBOR的历史和社区讨论**： - **dang**：提供了一些与CBOR相关的历史讨论链接，显示出社区对CBOR和MessagePack的长期争论。 - **JimDabell**：提到之前关于CBOR和MessagePack选择的讨论。 • **ASN.1的实际应用**： - **johnisgood**：分享了Erlang/Elixir对ASN.1的良好支持，并对比了Java/Kotlin在ASN.1支持上的不足。 补充讨论： • **压缩与格式比较**： - **glenjamin**：指出文档中对压缩的提及不足，并建议比较压缩后的JSON和CBOR，以获得更全面的理解。 • **对CBOR的幽默批评**： - **naggumsghost**：以幽默的方式批评CBOR，并引用了一个对XML的激烈批评，暗示需要为CBOR想出一个类似的“激烈批评”。 争议焦点： • CBOR是否真的如宣传所言是“关键数据格式”，以及其相对于其他格式（如JSON、MessagePack、ASN.1等）的实际优势和应用场景。

Fixing Ctrl+C in Rust terminal apps: Child process management

作者: Callicles | 评分: 100 | 评论数: 12 | 发布时间: 2025-07-29 22:05
文章摘要

本文讨论了在Rust终端应用程序中处理Ctrl+C中断时遇到的终端损坏和子进程管理问题，并提供了相应的解决方案。主要问题包括终端状态损坏、子进程输出干扰、挂起的后台进程以及竞争条件。文章提出了以下解决方法： 1. **进程输出代理**：将子进程输出重定向到日志系统，避免直接输出到终端。 2. **终端状态管理**：确保应用程序退出时恢复终端到原始状态，使用`crossterm`库实现跨平台终端操作。 3. **优雅的进程终止**：先尝试使用`SIGTERM`优雅关闭进程，必要时再用`SIGKILL`强制终止，并设置超时。 4. **线程安全的状态指示器管理**：协调交互元素与子进程输出，防止同时写入终端导致字符格式错误。 此外，文章还提供了测试策略和常见陷阱的避免方法，强调从一开始就实现这些模式以避免终端问题。

评论摘要
主要讨论点：Rust CLI 程序中的信号处理问题及其复杂性，尤其是 SIGINT 和 SIGPIPE 的处理，以及与操作系统相关的子进程管理问题。 不同观点： • mprovost：认为 Rust CLI 程序在处理 SIGPIPE 时存在问题，因为编译器在调用 main() 前会忽略 SIGPIPE，导致程序无法像其他程序一样在管道关闭时被信号杀死，而是返回写错误。虽然可以通过手动检查错误类型和退出状态码来模拟，但无法完全重现被信号杀死的情况。 • duped：认为优雅地关闭进程固然重要，但并不是所有子进程都适合被管道输出。对于某些进程（如需要 stdin 的 shell），应该为子进程分配新的 pty。此外，提出可以通过操作系统特性（如 PR_SET_PDEATHSIG 和 PID namespaces）管理子进程，而不是维护一个子进程注册表，并指出在 raw mode 下无法接收 ctrl+C 信号的问题。 • anp：同意 mprovost 提出的问题在 Rust 程序中存在，但认为这些问题并不是 Rust 特有的，其他语言的终端应用程序也会遇到类似问题。 • vlovich123：支持 anp 的观点，进一步指出这些问题在任何语言的终端应用程序中都会出现，不限于 Rust。 • silon42：质疑应用程序是否应该负责清理工作，认为这应该是 shell 或终端的责任，并提出如果使用 "kill -9" 发送 SIGKILL 信号，应用程序无法处理。 • mook：指出 Windows 系统上的情况更复杂，因为 Windows 不使用 Unix 信号，通常只有类似 SIGKILL 的信号，但可以选择加入类似 SIGINT 的信号。 • koakuma-chan：询问主进程退出后，子进程是否还能继续运行并写入 stdout/stderr。 • rendaw：抱怨代码可读性问题，认为代码对比度不够，影响阅读体验。 • windowshopping：提到标题容易引起误解，但最终避免了歧义。 • npalli：质疑 Rust 的并发处理能力，认为在生命周期管理、线程协作和整体人体工学方面，现代 C++ 可能更具优势。 补充讨论： • 争议的焦点在于应用程序是否应该负责处理子进程和信号的清理工作，还是应由操作系统（如 shell 或终端）处理。 • 讨论还涉及不同操作系统（Linux、MacOS、Windows）在信号处理和子进程管理上的差异，尤其是 Windows 系统的特殊性。 • 有人关注代码的可读性问题，建议改进代码高亮和排版以提升阅读体验。

Critical vulnerability in AI coding platform Base44 allowing unauthorized access

作者: waldopat | 评分: 112 | 评论数: 17 | 发布时间: 2025-07-30 16:12
文章摘要

文章主要介绍了在大语言模型（LLM）革命背景下，代码生成领域发生的重大转变，尤其是“氛围编码”（vibe coding）的兴起。这种新方式让没有技术背景的用户也能通过自然语言提示生成全功能应用。平台如Loveable、Bolt和Base44引领了这一潮流，使用户能创建从个人工具到企业内部聊天机器人等各种应用。 Wiz Research在研究中发现，Base44平台存在一个严重漏洞，攻击者利用该漏洞可以通过提供简单的“app_id”值绕过认证，获取对私有企业应用及其敏感数据的完全访问权限。该漏洞在24小时内被修复，且未发现被滥用的证据。 文章强调，氛围编码平台的共享基础设施模式带来了安全风险，一个平台漏洞可能危及所有在其上构建的应用。研究旨在提醒业界关注此类AI开发平台的安全隐患，确保技术的安全演进。
