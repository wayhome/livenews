The time bomb in the tax code that's fueling mass tech layoffs

作者: booleanbetrayal | 评分: 1547 | 评论数: 88 | 发布时间: 2025-06-04 13:30
文章摘要

文章讨论了美国税法中一项鲜为人知的变更如何导致大规模科技行业裁员。具体而言，2017年特朗普税改法案对 Section 174 的修改使得企业不能再立即全额抵扣研发费用，而是需要在5年或15年内逐步摊销。这项变更在2022年开始产生影响，导致科技公司削减研发投入和裁员，因为他们的税务负担增加，尤其在软件和产品开发领域。尽管该变更旨在使税改法案在预算评分上显得“赤字中性”，但它无意中成为了科技行业裁员的加速剂。自2023年初以来，已有超过50万科技员工被裁，而这一隐藏的税法“定时炸弹”是部分原因。目前，国会正试图通过两党合作废除这项修改。

评论摘要
主要讨论点：Section 174 税法修正案对软件研发支出 amortization（摊销）要求的影响，尤其是对初创企业、小型公司以及整个软件行业的影响。 不同观点： • **demosthanos**：引用法律文本，明确表示所有软件开发支出必须按照Section 174的要求在5年内摊销，不能立即扣除。这尤其对尚未在市场站稳脚跟的公司（如初创企业）不利。 • **sampton**：认为软件开发本身具有高风险，要求摊销是不合理的政策，因为并非所有软件项目都能在5年内产生稳定收入，尤其对初创公司来说，这可能导致其无法存活到摊销期结束。 • **potamic**：通过类比，指出如果对其他行业（如餐饮业的原材料成本）实施类似的政策，会引发巨大反对，因此不理解为何员工薪资支出要被区别对待。 • **mccolin**：指出修正Section 174表面上是针对大公司，但实际上对小公司、新公司以及个体经营者影响更大，并提到一个约20人的公司因此受到重创。 • **wdaher**：提到众议院通过的法案将从2025年开始暂停国内研发支出摊销的要求，并允许国内软件开发费用立即扣除，但尚需参议院通过。 • **layer8**：作为非美国人，质疑常规软件开发成本为何能享受扣除或摊销，认为这可能是对某一行业的补贴。 • **Huxley1**：分享个人经历，表示如果其以前所在的初创公司需要摊销工程师薪资，公司可能无法存活，并指出单一税收政策可能对招聘产生重大影响。 • **anymouse123456**：指出该政策可能导致公司缴纳的税款远高于其实际收入，但多数公司目前选择忽视，希望政策能在执行前得到修正。 • **pzo**：反对将所有软件开发视为研发，尤其对非创新性、维护性质的软件开发，认为这与酒店业将清洁工、保安等职位视为研发一样荒谬。 • **sumanthvepa**：提出一种避税策略，建议在印度等允许100%研发扣除的地区进行研发，并在美国购买SaaS服务，以规避Section 174的影响。 • **inadequatespace**：怀疑Section 174是否是导致大规模科技行业裁员的主要原因，认为其他因素（如利率上升）也可能有贡献。 • **hollerith**：认为该政策对美国程序员是利好消息，因为他们的薪资只需摊销5年，而非美国程序员的薪资需摊销15年，同时认为该政策解释了程序员需求减弱的原因。 • **svara**：询问在不盈利的公司情况下，哪些税款会导致痛苦的高额税单，尤其是在风险投资资金枯竭和利率上升的情况下。 补充讨论： • **争议焦点**：Section 174修正案对软件开发支出的摊销要求是否合理，特别是对小型企业和初创公司的影响。支持者认为该政策对所有公司一视同仁，而反对者则认为这对高风险的软件行业尤其不公平。 • **政策变动预期**：提到众议院通过的法案可能在2025年暂停该摊销要求，但尚需参议院通过，政策前景不明朗。 • **国际影响**：有评论提到该政策对非美国程序员和国际公司的影响，并建议通过国际税务策略规避该政策的影响。

Binfmtc – binfmt_misc C scripting interface

作者: todsacerdoti | 评分: 86 | 评论数: 11 | 发布时间: 2025-06-08 12:38
文章摘要

**binfmtc** 是一个让 C 语言用于脚本编写的工具，解决了因编译步骤繁琐而选择解释型语言的问题。通过在 C 脚本中添加特定注释标记 `/*BINFMTC: ...*/` 并赋予执行权限，每次调用脚本时，系统会自动编译并执行程序。该工具利用 Linux 的 **binfmt_misc** 机制，在调用 C 脚本时自动调用编译器（如 gcc）生成临时二进制文件并运行。此外，还提供了一个类似 C shell 的 "real csh" 示例，用于日常系统管理任务。安装可通过添加特定源并使用 `apt-get` 完成，未来计划包括支持更多语言如 gcj、g77、mono 等。

评论摘要
主要讨论点：通过不同方法实现C脚本或类似功能 不同观点： • [rwmj] 提出了一种不使用 binfmt 的方式，通过条件编译和 shell 脚本结合，直接编译和运行 C 文件。他提到虽然可以用临时文件实现，但给出了一个无需 binfmt 的简单示例。 • [zx2c4] 提到了自己过去的一个类似项目，提供了一个链接，展示如何通过外部工具实现脚本化的 C 编译和执行。 • [monocasa] 提出了另一种方法，使用 tcc（tiny C compiler），其具有 shebang 兼容性，可以直接用于脚本。 • [radiospiel] 也分享了一个类似的方法，通过指向 C 编译器和运行器的 shebang 行实现。他质疑了通过 binfmt_misc 注册扩展的必要性。 • [kazinator] 强调这种方法完全可以在没有 Linux 特定的 binfmt-misc 黑科技的情况下实现，并提供了一个 Rosetta Code 上的多行 shebang 示例。 • [codr7] 分享了自己为书籍编写的一个简单黑科技，通过 C 程序内部实现类似的功能，并提供了 GitHub 链接。 • [rurban] 仅提到了一个年份 (2006)，可能暗示这种方法或类似想法早已存在。 • [elitepleb] 提到了一个类似的旧网页，展示了一种早期的实现方式。 • [enriquto] 惊讶地发现通过简单的包安装（binfmtc）就能在 Linux Mint 上实现类似的功能。 • [JSR_FDED] 表达了对 C 语言的喜爱，强调了 C 语言的简洁和直接，以及编程中的责任感。 • [Surac] 简短地表达了对这种方法的喜爱。 补充讨论： • 争议焦点之一是是否需要使用 binfmt_misc 注册扩展。部分评论者质疑其必要性，认为有其他更简单和跨平台的方法。 • 各种方法的优劣被间接讨论，包括条件编译、外部工具、shebang 兼容性等不同实现方式。 • 一些评论者分享了个人项目或发现，提供了具体的示例和资源链接，丰富了讨论。 总体来看，讨论围绕着多种实现 C 脚本化编译和执行的方法展开，涉及到具体技术细节和个人偏好。

本文介绍了一种利用mRNA-脂质纳米颗粒（LNP）技术逆转HIV潜伏期的方法。研究人员开发了一种新型LNP配方（LNP X），能够在不引起细胞毒性或激活的情况下，将mRNA高效递送到难以转染的静息CD4+ T细胞中。通过封装编码HIV Tat蛋白的mRNA，LNP X增强了来自HIV感染者的CD4+ T细胞中HIV的转录。此外，LNP X还可以递送CRISPR激活机制，调节病毒和宿主基因的转录。这种方法为开发基于核酸的T细胞疗法提供了潜力，可能有助于清除HIV潜伏病毒库。

评论摘要
主要讨论点：MRNA技术在治疗潜伏病毒（如疱疹、水痘/带状疱疹）方面的潜在应用及公众教育的重要性 不同观点： • [sroussey] 认为MRNA技术有可能用于治疗其他嵌入细胞的潜伏病毒，如疱疹和带状疱疹。这个评论提出了将MRNA技术扩展至其他病毒性疾病的设想，并关注其在医疗领域的广泛应用潜力。 • [Zigurd] 强调MRNA疗法的巨大潜力，但指出公众由于缺乏相关知识，容易被不科学的言论误导，甚至可能受到敌对国家势力的影响。Zigurd认为，加强公众教育和宣传是防止人们被误导的关键，并强调了这一问题的紧迫性和重要性。 补充讨论： • [Zigurd] 进一步提出，公众因误导而受到的伤害不仅是个人层面的问题，还可能成为国家安全层面的问题，因为敌对国家可能会利用公众对MRNA技术的不了解来进行干预。这一论点将问题提升到了更广泛的社会和国际政治层面。 • 争议的焦点可能在于如何有效开展MRNA技术的公众教育，以及如何防止虚假信息和敌对势力的干预。这涉及科学传播、公共政策和国际关系等多方面的复杂问题。

Focus and Context and LLMs

作者: tarasglek | 评分: 87 | 评论数: 12 | 发布时间: 2025-06-08 09:09
文章摘要

本文讨论了大语言模型（LLM）在软件工程任务中的应用，特别是完成高难度任务的能力，同时批评了过度炒作的“代理编码”概念。作者基于自己自2020年采用GPT-3以来的经验，指出LLM确实能显著提高某些任务的效率，如生成SQL语句。然而，文章强调，要让LLM成功完成复杂软件项目，需要提供精确的上下文和严格的算法监督，而不是依赖于当前被热炒的“代理工具”调用。作者以HTTP/2服务器项目为例，说明在精心管理下，LLM可以完成连高级工程师都可能失败的任务，但这一过程耗时长且复杂。文章最后指出，LLM的输出质量取决于输入的上下文，目前只有 exceptional 的工程师能在使用LLM时取得令人印象深刻的结果。

评论摘要
主要讨论点：LLM（大型语言模型）在代码生成和软件开发中的实际应用效果及潜力 不同观点： • **tptacek的观点**：LLM目前无法独立完成复杂的端到端开发任务，特别是在不需要人工干预的情况下。然而，LLM在辅助开发中仍然能够加速开发过程，特别是在代码生成和初步调试阶段，而不需要开发者特别精进与LLM的沟通技巧。 • **summarity的观点**：个人经验表明，LLM（如o3）在处理大代码库的调试和特定代码任务（如DSP代码、图形程序优化等）方面表现出色，但在使用某些IDE的代理模式时，性能下降。这表明当前的代理模型可能过度拟合于工具调用，而非复杂的代码生成任务。此外，提供过多工具会使模型更加困惑。 • **artembugara的观点**：关注如何“为LLM提供正确的上下文”是一个重要问题，并询问有哪些创业公司正在解决这一问题。 • **jmward01的观点**：当前LLM的局限性主要在于上下文限制，解决这一问题需要新的LLM结构，能够提供无限的上下文。 • **jumploops的观点**：Claude Code是目前为止最有用的“代理”工具，优于其他工具如Aider或Cursor，但难以具体解释原因。 • **briian的观点**：调侃“vibe coding”现象，认为需要找到更好的方法让代理模型选择合适的上下文，且这一问题应该不难解决。 • **quantum_state的观点**：强调上下文是LLM应用中最重要的因素。 • **emorning3的观点**：文章的核心观点是“上下文就是一切”，并且人类助理的参与也是必要的。 • **mathgeek的观点**：批评某些人在讨论中表现出的自大，认为最好的教师应保持谦逊。 • **__mharrison__的观点**：通过一个YouTube视频示例，证明LLM可以在无需编码和极少提示的情况下构建复杂软件，如在一小时内构建一个绘图应用。 • **Workaccount2的观点**：指出软件工程师不应仅仅因为LLM在专业开发中表现不如预期就贬低其价值。LLM在帮助非专业人士实现基本编程需求方面非常有效。 补充讨论： - LLM在代码生成中的实际效用和局限性，尤其是在处理复杂项目和不同工具集成时的表现。 - 上下文在LLM应用中的关键作用以及如何有效提供和选择合适的上下文。 - LLM对不同用户群体的价值，包括非专业人士和专业开发人员。 - 对当前LLM工具和代理模型的具体体验和比较。
