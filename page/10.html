Automating AI Away

作者: gritzko | 评分: 122 | 评论数: 18 | 发布时间: 2026-07-07 15:11
文章摘要

本文探讨了LLM（如Claude）在软件开发中的局限性：虽然聪明但容易犯低级错误，且这种不精确和非确定性是其本质特征。 作者提出的解决方案是将LLM"夹在"确定性工具和正式流程之间——底层用可靠的确定性工具（如Ragel解析器）处理精确任务，顶层建立正式工作流程，让LLM专注于其擅长的高层决策。 关键思路是让工具和流程可编程：当LLM重复某些操作时就将其自动化，当它频繁失败时就自动化验证步骤。本质上是让LLM"自动化掉自己"，转化为简单可靠的确定性工具。 Beagle SCM实现了这一理念：LLM可用JavaScript编写自己的例程，核心功能用C实现，工具层和工作流层用JavaScript动态加载，类似增强版的git hooks系统。

评论摘要
主要讨论点：如何在自动化系统中合理使用LLM，以及LLM与确定性代码的关系 不同观点： • **确定性优先派**：认为应该将人工流程逐步转化为确定性代码，而不是用LLM替代。代码是确定性的、可重复运行且成本低，LLM只应加速代码创建和维护过程，而不是成为生产系统的核心（alexpotato, stego-tech强调将概率系统交给确定性过程是本末倒置） • **工具化中间层派**：主张让LLM生成工具或通过精心设计的工具集工作，而非直接操作。例如让LLM编写Roslyn API代码来转换代码，或为每个视图提供定制的工具列表，将图灵完备问题简化为二元决策（contextfree, bob1029, iamflimflam1将流程分为数据收集和处理阶段） • **实用主义分层派**：提出"确定性软件>LLM>人工"的优先级体系，将LLM视为"新CPU"嵌入确定性工作流，在合适场景使用LLM但尽快用确定性方法替换（mchusma, sebastianconcpt） • **技术本质派**：指出问题核心不在非确定性，而在自然语言的非正式性和模型认知局限。认为需要自我验证循环来改善准确性，而不是简单追求确定性输出（orbital-decay） 补充讨论：Animats提出LLM可用于形式化验证的证明推导；多位评论者呼吁需要更多实践案例和深度产品评测来指导工具选择。

AI Meets Cryptography 1: What AI Found in Cloudflare's Circl

作者: duha | 评分: 55 | 评论数: 3 | 发布时间: 2026-07-07 18:36
文章摘要

zkSecurity公司使用其开发的AI审计工具zkao扫描了Cloudflare的CIRCL实验性加密库，发现并确认了7个真实漏洞，所有漏洞已在上游修复。 这7个漏洞包括： 1. TSS/RSA多项式计算中的float64精度丢失（关键） 2. qndleq通过prover控制的SecParam伪造 3. BLS聚合缺少消息唯一性检查 4. DLEQ可靠性通过FillBytes符号碰撞破坏 5. HPKE PSK验证通过位运算OR开关绕过 6. TSS/RSA拉格朗日系数使用int64 7. CP-ABE访问控制通过AND共享漏洞破坏（严重） 实验使用了两种配置：纯LLM和带专家技能的LLM。值得注意的是，AI评估的漏洞严重性与Cloudflare确认的严重性存在差异。这是zkSecurity关于AI在开源加密项目中发现漏洞的系列文章首篇，展示了AI辅助安全审计的能力和局限性。

评论摘要
主要讨论点：对一篇AI辅助安全审计文章的技术性评论，涉及审计方法论和加密实现细节 不同观点： • **审计流程质疑**（dboreham）：关注AI辅助审计的效率问题，询问LLM生成的候选报告与最终确认漏洞的比例，试图了解"人工审核"环节的工作量和价值 • **测试覆盖度质疑**（dboreham）：针对CP-ABE访问控制漏洞，质疑为何缺少高层级的功能测试（如"没有所需属性时无法解密"），认为这类似于忘记测试"错误密码无法登录"的基础场景 • **工具定义困惑**（dboreham）：对zkao工具的实际功能表示不清楚，不确定它是持续审计系统还是某种特殊的LLM • **加密实现惊讶**（ur-whale）：对在加密算法中使用浮点数表达强烈意外，认为这不符合常规做法，仅知道djb曾用浮点单元做过非常规的整数运算优化 补充讨论：两条评论没有直接交互，一个聚焦方法论和工具，一个聚焦实现细节，体现了技术审查中不同关注维度

Herdr: One terminal to rule them all

作者: handfuloflight | 评分: 144 | 评论数: 20 | 发布时间: 2026-07-02 04:28
文章摘要

Herdr 是一个终端复用器，专为管理多个编码代理（coding agents）设计。核心特性包括： **功能亮点**： - 在单个终端中运行所有代理，每个代理运行在独立的真实终端中 - 支持远程 SSH 使用，服务器保持会话持久化 - 可视化显示代理状态（工作中/阻塞/完成） - 支持从任何设备重新连接 **技术特点**： - 纯二进制程序，无 Electron、无账户注册、无遥测 - 支持 Linux/macOS（稳定版）和 Windows（预览版） - 提供脚本、Homebrew、Nix 等多种安装方式 **定位**：类似 tmux 的现代化替代品，专注于代理编排和多任务管理，被 Google、AWS、NVIDIA 等公司的工程师使用。

评论摘要
主要讨论点：Herdr（一个新的终端复用器）与 tmux 的对比，特别是在 AI agent 管理场景下的优劣 不同观点： • **支持 Herdr 的观点**：运行多个 AI agent 时，Herdr 提供更好的可见性和状态管理。一位用户管理 10+ 个 agent，发现 tmux 难以追踪哪些 agent 在等待批准或已空闲数日。Herdr 的侧边栏和状态显示（idle/working）解决了这个痛点。 • **质疑 Herdr 价值的观点**：部分用户认为除了 agent 状态通知外，看不出相比 tmux 有何实质性优势。有用户满意于 tmux 的功能（如可在手机上使用），不认为需要切换。 • **功能特性讨论**：Herdr 的优势包括鼠标友好、display-popup UI、自动剪贴板复制、更好的嵌套会话支持、跨会话重连能力。但也存在问题：输入延迟、键盘复制粘贴在某些终端（wezterm）中不好用、缺少键位重绑定功能。 • **工作流集成需求**：开发者关注 git worktree 支持，希望在多个 worktree 中并行运行 agents。现有工具（Emdash、Nimbalyst）管理状态的方式不够灵活。 • **商业模式争议**：有评论质疑 Herdr 是否在向新手收费，而这些功能用 tmux 等免费工具也能实现。另有人指出其营销材料中使用公司 logo 可能存在法律风险。 补充讨论：TUI 工具的兴起被认为反映了现有 GUI 的不足；多位用户推荐了替代工具（belfry、terminai.app、Superset、Conductor）；Herdr 的目标用户似乎是需要同时管理大量 AI agents 的重度用户。

文章摘要

Davit 是一款轻量级的 macOS 原生容器管理工具。它直接通过 XPC 与 Apple 的开源容器守护进程通信,无需 Electron 或后台代理,应用体积仅约 17MB。 **主要功能:** - 容器管理:启动、停止、删除,实时显示 CPU、内存和 IP - 一键终端访问,直接集成 Terminal 或 iTerm - 编辑并重建容器配置(端口、环境变量、挂载等) - 镜像、卷和网络管理,支持所有 OCI 标准仓库 - 可自动安装容器平台(无需管理员权限) **技术特点:** 完全使用 SwiftUI 构建的原生应用,利用 Apple Virtualization 框架,每个容器运行在独立轻量级 VM 中,启动速度极快,针对 Apple Silicon 优化。与 Docker Desktop 相比,架构更简洁,直接使用系统原生能力。

评论摘要
主要讨论点：Davit作为Docker Desktop轻量级替代方案的可行性，以及AI辅助开发的应用质量 不同观点： • **积极评价派**：认为应用小巧高效（17MB）、运行流畅，特别指出Claude深度参与的项目通常质量较高（原生体验、非Electron），愿意尝试替代现有方案 • **功能需求派**：希望增加Dockerfile直接构建、容器内文件浏览、菜单栏集成等功能，部分用户因缺少特定功能（如Caddy集成）暂时无法迁移 • **性能关注派**：主要关心内存占用，因Docker Desktop资源消耗大而寻找替代品，OrbStack虽好但收费模式让部分用户犹豫 • **技术细节派**：讨论压缩比异常（17MB压缩vs 56MB二进制）、macOS UI设计趋势、容器兼容性等技术问题 补充讨论： 有人列举了其他类似的AI辅助项目（contained-app、berth），形成竞品对比。入门体验被认为需要改进（nginx:latest不是好的演示案例）。整体氛围偏正面，但用户更关注实际可用性而非概念验证。
