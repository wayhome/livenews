Illusions of understanding in the sciences

文章摘要

文章指出，科学家常误以为自己已深刻理解现象成因，但实际理解多为不完整的“理解幻觉”。数学模型和计算模拟因预测精确，更易强化因果错觉。作者以线性回归为例说明深层理解之难，并探讨这种幻觉如何影响实验设计、理论检验、推理、交流与教学。

评论摘要
主要讨论点：科学理解的本质——预测能力是否等同于真正的理解，以及科学家是否存在"理解的错觉" 不同观点： • **支持论文核心观点**：科学本质上是简化的心智模型，预测准确不等于理解因果结构。真正的理解应承认完美预测不可能，关键是定义可接受的"信息损失"（jdw64） • **批评论文质量**：论文缺乏原创性贡献，像是综述而非研究；核心论述缺少引用支撑，分类观点未提供证据来源；作者未充分研究科学哲学文献，重新发明轮子，应参考Duhem-Quine命题等经典理论（smarm52, raincom, ian_j_butler） • **实用主义立场**：过度思考了。归纳和演绎虽有逻辑缺陷但确实产生新知识；经验科学虽不完美但长期有效，现代医学和工程证明这套系统可行（usernametaken29） • **预测即理解**：预测能力本身就编码了理解，从信息论角度看，预测力提升永远是好目标，与人类能否"感知"这种理解无关（chermi） • **AI时代的新困境**：这种错觉在AI时代更严重——人们以为能用AI得到正确答案就是理解，但获得正确输出不等于理解（Ozzie-D） 补充讨论：多位评论者提到个人经验——以为彻底理解某事后发现还有更深层次，产生失望、敬畏和兴奋的复杂感受。论文本身存在可读性问题（过长、重复、网站交互故障）。

Moving away from Tailwind, and learning to structure my CSS

作者: mpweiher | 评分: 683 | 评论数: 74 | 发布时间: 2026-05-16 09:14
文章摘要

作者分享了从 Tailwind CSS 迁移到语义化 HTML + 原生 CSS 的经验。8年前她因不懂 CSS 结构而选择 Tailwind，现在发现 Tailwind 其实教会了她很多组织 CSS 的方法。她的新方案包括：1) 复制 Tailwind 的 reset 样式；2) 按组件组织 CSS，每个组件独立文件和类名；3) 用 CSS 变量统一管理颜色；4) 借鉴 Tailwind 的字体大小系统；5) 保留少量通用工具类。核心思路是保留 Tailwind 的优秀系统设计，但用更语义化的方式实现，让代码更易维护。

评论摘要
主要讨论点：Tailwind CSS 的利弊及其对 Web 开发实践的影响 不同观点： • **反对 Tailwind 阵营**：认为 Tailwind 颠倒了 HTML/CSS 的思考顺序，应该先写语义化 HTML 再用 CSS 样式化，而 Tailwind 推动 CSS 优先的方法，导致 div 汤泛滥，降低可访问性和代码质量。新手开发者因此养成坏习惯，LLM 也会输出大量无意义的 div 结构。 • **支持 Tailwind 阵营**：强调实用性优势——样式与组件代码紧密结合，无需在文件间切换；避免类名膨胀和命名困扰；生产环境自动优化 CSS 体积；对于 AI 生成代码特别友好，因为样式信息就在 JSX 中。经过适应期后，认为 Tailwind 更高效、可维护。 • **折中方案支持者**：提出使用 CSS Modules 解决级联问题但保持可读性；或结合 Tailwind 与 scoped styles（如 Svelte/Vue）减少模板污染；或使用 Open Props 等 CSS 变量库，既保持 CSS 优先又提供设计系统。 补充讨论：多位开发者指出全局 CSS 在多人协作中难以维护，会陷入"修复 A 破坏 B"的循环；也有人怀念 SMACSS（2011）等被忽视的 CSS 架构方法；部分开发者因现代框架的 scoped styles 功能已不再需要 Tailwind。

Project Gutenberg – keeps getting better

文章摘要

古腾堡计划是一个拥有超过75,000本免费电子书的数字图书馆，成立于1971年。该项目专注于美国版权已过期的经典文学作品，由数百名志愿者数字化和校对。用户可以免费下载或在线阅读epub和Kindle格式的电子书，无需注册或付费。网站提供多种分类和搜索选项，还与LibriVox等机构合作提供有声书服务。项目完全依靠志愿者运营和捐赠支持。

评论摘要
主要讨论点：Project Gutenberg（古腾堡计划）的价值、使用体验和技术改进 不同观点： • **积极评价派**：多位用户分享感人故事（如为父亲购买Kindle使用PG）和个人贡献经历，认为PG是人类文化宝藏，体现"作品属于全人类"的理念 • **技术改进需求派**：批评PG倾向纯文本格式，缺乏排版和格式化；建议电子书阅读器应内置PG商店功能，降低使用门槛；指出需要通过Calibre等工具才能便捷使用 • **替代方案推荐派**：推荐Standard Ebooks（排版一致性更好）、IMSLP音乐库、Archive.org书籍扫描、以及加拿大FadedPage和瑞典Runeberg等类似项目 补充讨论： • **地理封锁问题**：意大利用户遇到司法查封页面，德国曾长期被地理封锁，涉及版权管辖权争议 • **异常下载数据**：技术类书籍《混凝土施工》下载量超越经典名著，疑似机器人行为 • **实用资源**：ZIM离线包（英文60GB）、RSS订阅源、ePub格式改进等技术细节获得关注 • **历史价值**：PG始于1971年ARPANET时代，创始人Hart的远见获得致敬

Mercurial, 20 years and counting: how are we still alive and kicking? [video]

作者: ibobev | 评分: 162 | 评论数: 28 | 发布时间: 2026-05-15 11:39
文章摘要

这是一场 FOSDEM 2026 主会场演讲，题为“Mercurial，20年仍在前行”。演讲回顾分布式版本控制系统 Mercurial 自2005年以来的发展，探讨其虽在流行度上输给 Git、却仍保持活跃和竞争力的原因。内容涵盖项目历史、技术与社区演变、大公司参与影响、Mercurial 对现代工具的贡献，以及版本控制和社区开源的未来。

评论摘要
主要讨论点：围绕 Mercurial（hg）与 Git 的技术体验、生态胜负及替代工具展开，核心是“技术上更好用”与“生态上输给 Git/GitHub”的落差。 不同观点： • Mercurial 技术体验更好：多人认为 hg 更安全、更清晰、命令面更小、对普通团队足够，TortoiseHg、Windows Explorer 集成等让使用更顺手；相比 Git，遇到复杂问题时更怀念 hg。 • Git 胜在生态而非纯技术：原帖和 reddit 旧员工都认为当年选择 hg 技术上合理，但 Git 因成为主流、GitHub/开源贡献流程普及而胜出。reddit 开源时即使偏好 hg，也为获得贡献和“显得严肃”改用 Git。 • 托管平台影响关键：Bitbucket 停止支持 Mercurial 被多位评论者视为促使放弃 hg 的转折点；缺少 GitHub 式平台、Heptapod 使用不顺，也削弱了 hg 的生存空间。 • Mercurial 仍有现实用途：有人继续自托管或在家用 Raspberry Pi 部署 hg，认为如今家庭光纤让自托管更可行。 • 新工具可能取代 hg：有人认为 Jujutsu（jj）出现后，Mercurial 复兴希望更小；也有人期待 jj 获得更多认可。 • 争议焦点：Git 的“更强大”是否真是大多数团队所需；Mercurial 是否因生态失败而非技术失败被淘汰。 补充讨论：有人怀念 Mercurial 作者 Matt Mackall 的工程文化；也顺带表达了对 Perforce 的反感、对 Hginit 回归的关注。
