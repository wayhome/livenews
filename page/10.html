NSA tries to weaken mlkem standardisation?

文章摘要

这篇文章揭露NSA正推动一项被认为会削弱加密安全的标准"ietf-tls-mlkem"(相比更安全的"ietf-tls-ecdhe-mlkem")。NSA在IETF TLS工作组最近的投票中失败后,于2026年6月24日发起新投票,并通过让从未参与过的人员(如Mike Jenkins)投票来"塞人"。 文章呼吁公众行动:任何人都可以加入IETF TLS邮件列表,在7月7日前发送反对该文档的声明(需使用真实姓名)。截至7月1日已有超过30份反对声明。文章提供了多个反对声明范例供参考。 核心议题是NSA试图通过标准化流程削弱加密标准的安全性。

评论摘要
**主要讨论点：** IETF TLS 工作组是否应发布纯 ML-KEM（后量子密码）标准，而非仅混合方案（ECC+PQ） **不同观点：** • **警告派（DJB 等）：** 认为 NSA/GCHQ 试图削弱安全标准，将混合方案（ECC+ML-KEM）降级为纯 ML-KEM，不应信任情报机构参与标准制定，强调历史上有被破坏先例 • **技术务实派：** 指出这是信息性 RFC（非强制标准），不影响已有的混合规范推荐；多个主流加密库已实现 ML-KEM 支持；电信等行业因合规要求需要 RFC 文档；纯 ML-KEM 有助于对抗"现在收集，未来解密"攻击 • **程序质疑派：** 批评 DJB 行为不专业，已被邮件列表多次警告；认为其发起社交媒体动员违反 RFC 7282 关于工作组讨论的规范；指责这是诉诸权威和制造功能障碍的策略 • **中立观察派：** 质疑 NSA 参与的具体证据（未见 nsa.gov 邮箱）；疑问为何可选标准会构成威胁；注意到双方论述都有夸大成分 **补充讨论：** 争议核心在技术安全与实际部署之间的平衡——DJB 被社区广泛尊重但也被认为有偏执倾向；多数密码学界认为 ML-KEM 安全可靠；这场争论已持续一年以上且高度政治化。

这篇文章探讨AI代码生成与编程语言设计的关系。作者认为，虽然AI能生成各种语言的代码，但在局部代码质量高的同时，往往难以把握全局理解，导致过多防御性检查和状态复杂度指数增长。作者以Rust多线程编程为例，说明编程语言设计如何通过局部推理实现全局属性保证，认为这可能为解决AI代码生成的全局理解问题提供启示。

评论摘要
主要讨论点：如何通过类型系统、静态分析和编译器特性来提高代码的可验证性和正确性 不同观点： • **局部验证优先派**（budro）：主张编写在最小上下文窗口中可验证的软件，通过断言和静态分析缩小状态空间。认为Rust在并发安全方面具有其他语言无法比拟的优势，特别推荐嵌式领域的RTIC框架。 • **防御性编程派**（mike_hock）：支持在代码中加入防御性检查，相信编译器会优化掉不必要的检查。建议用注释标注"不可能发生"的情况，为未来的代码维护者提供上下文。 • **类型缩窄技术派**（cadamsdotcom）：详细阐述类型缩窄（如List→NonEmptyList、状态枚举缩窄）如何在类型层面表达"某些情况不会发生"。指出TypeScript可自动进行类型缩窄。认为手动缩窄虽增加代码量，但提升了清晰度。强调将期望属性编码为可机器验证的机制具有巨大价值。 补充讨论：twoWhlsGud提到Rust生态的Verus项目，这是一个形式化验证工具，正在实现文章讨论的验证理念。整体讨论氛围是协作性的，各方从不同角度补充如何利用编程语言特性提升代码质量，没有明显的观点冲突。

crustc: entirety of `rustc`, translated to C

作者: Philpax | 评分: 385 | 评论数: 30 | 发布时间: 2026-07-02 22:57
文章摘要

crustc 是一个将 Rust 编译器（rustc 1.98.0）转换成 4600 万行 C 代码的项目，可用 GCC 和 make 构建成功能完整的 Rust 编译器。 其背后是 cilly 工具链——一个创新的 Rust 到 C 编译器。核心特点是能适配各种 C 编译器，通过"见证程序"自动检测编译器支持的特性，不假设超出 ANSI C 的任何功能。 主要目标是让 Rust 支持没有 LLVM/GCC 的老旧或冷门硬件平台。特性包括：网络透明编译（通过 TCP 与远程 C 编译器通信）、生成 makefile 以便用 C 编译器构建 Rust 代码、与普通 rustc 基本 ABI 兼容。 这为 Rust 进入更多平台提供了可能性。

评论摘要
**主要讨论点：** crustc（Rust 到 C 的编译器）项目的价值、技术路线和应用场景 **不同观点：** • **支持派**：认为项目有独特价值。转译到 C 比 LLVM IR 更简单，且能让 GCC 进行优化；对于 bootstrappable 项目有重大意义，可大幅简化 Rust 编译器的可引导性；作者的执着精神值得尊重 • **质疑派**：认为应该直接为 LLVM/GCC 添加旧硬件支持，而非构建语言转译器。从工程角度看，扩展现有项目比创建新转译器更合理 • **技术探讨**：讨论 bootstrapping 问题（需要 Rust 编译器来编译 Rust）；提出用 DDC（双重编译）验证官方编译器安全性；指出 LLVM 曾有 C backend 但已废弃 • **应用场景**：关注具体用途如 Plan 9、PPC Mac OS X、iPadOS 等平台；强调跨网络/设备编译的实用性 **补充讨论：** 社区出现多条反讽式评论（"用 C 重写 Rust"、"等 rustcrustc"、"移植到 Rust"），反映了对"用 Rust 重写"风潮的调侃。核心技术争议在于：**直接改进现有编译器基础设施 vs. 创建新的转译层**，前者看似更直接，但后者提供了更灵活的跨平台方案和 bootstrapping 价值。

Save Claude Code Tokens with Smart Routing

文章摘要

Brick是一个AI模型路由网关，能根据每个查询的能力需求和复杂度自动选择最合适的LLM模型。它的核心优势是：无需级联调用，每个查询仅做一次路由决策，在保持最强模型质量的同时大幅降低成本。 **主要应用场景**： - 管理多模型池，让简单查询使用便宜模型，复杂查询使用强大模型 - 降低Claude Code/Codex等编码助手的成本 - 通过单一端点统一调用OpenAI、DeepSeek、Qwen等不同模型 **技术特点**：支持6个维度的能力感知、复杂度评估、多模态输入，提供OpenAI兼容接口。通过CLI工具可快速集成到Claude Code中，只需设置`model: "brick"`即可使用。

评论摘要
主要讨论点：关于AI系统中模型切换和功能设计的技术讨论 不同观点： • **成本效率角度（nithiink）**：指出模型切换存在缓存失效问题。单模型对话通过缓存命中可节省成本，但切换模型会导致新模型需要以完整输入价格重新处理所有历史对话上下文，造成额外开销。这是对系统架构中成本优化的技术性担忧。 • **功能必要性角度（patch_dev）**：质疑新功能的存在价值，认为现有的subagents（子代理）系统可能已经能够满足需求。这是对功能冗余和系统复杂度的考量，暗示新功能可能与现有机制重复。 补充讨论：两条评论分别从不同维度审视同一系统设计——一个关注运营成本和技术实现，一个关注架构设计和功能边界。这反映了技术决策中常见的权衡：既要考虑经济性，也要避免功能膨胀。两者都在挑战设计方案的合理性，但切入点完全不同。
