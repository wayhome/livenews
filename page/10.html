Proportional-Integral-Derivative (PID) controllers

作者: dhorthy | 评分: 119 | 评论数: 15 | 发布时间: 2026-06-19 16:28
文章摘要

PID控制器是一种基于反馈的自动控制机制，通过比较目标值（设定值SP）与实际值（过程变量PV）的误差来调节系统。它包含三个控制项：比例项（P）根据当前误差大小进行即时修正；积分项（I）累积历史误差以消除稳态偏差；微分项（D）预测误差变化趋势以减少超调和提高稳定性。PID控制器广泛应用于工业过程控制、温度调节、电机速度控制等需要精确自动控制的场景，例如汽车巡航系统。其理论基础可追溯到1920年代的船舶自动转向系统。

评论摘要
主要讨论点：PID控制器在实际应用中的效果、局限性及替代方案 不同观点： • **PID效果良好派**：多位用户分享成功案例，如GPU风扇温控、消息队列自动扩展、电机转速控制等。认为PID概念简单实用，三个部分（比例、积分、微分）各司其职，能有效控制系统 • **PID局限性派**：指出PID难以调参，在非线性复杂系统中表现不佳，无法适应环境变化（如温湿度波动）。有用户分享调参失败导致系统振荡的痛苦经历，强调需要深入理解物理现象才能调好 • **替代方案派**：提出ADRC（主动抗扰控制）在机器人速度控制中表现优于PID，能更好应对真实环境变化。预测未来将用小型神经网络替代PID，因其更易适应条件变化 • **学习价值派**：认为应学习更广泛的反馈控制理论（增益、稳定性、噪声过滤等），这些概念适用于各类长期运行系统，比单纯的PID控制器更有价值 补充讨论：有程序员对控制理论的兴趣引发跨学科讨论；现代调参已改用粒子群优化等自动化技术；部分用户吐槽教材缺乏实用性导向，直接跳入数学推导令人困惑

评论摘要
主要讨论点：Go语言中nil检查的必要性和最佳实践，以及类型系统的局限性 不同观点： • **支持减少nil检查派**：认为过度防御性检查会污染代码库，nil检查应该只在系统边界进行，内部代码应假设接收到有效值。错误应在初始化失败时立即处理，而不是传递nil指针让深层代码重新发现问题 • **支持防御性编程派**：主张在公共方法（如构造函数）中检查参数是标准实践，有助于局部推理和快速检测未来代码重构时的回归问题。特别是在LLM辅助编程时代，不应依赖对所有代码路径的完整了解 • **类型系统批评派**：认为这根本不是开发者责任问题，而是Go类型系统的缺陷。Go将可选性（语义概念）与指针/引用（机器概念）混为一谈，缺少非空指针类型。Rust的`&T`与`Option<&T>`、Java的null注解等已解决此问题 • **实践改进派**：建议不使用指针，总是在栈上分配结构体并按值传递；不检查接口的nil，使用空对象模式；或引入简单的Optional泛型类型 补充讨论：指针在Go中承载了可选性、可变性、内存优化三重意图但未在代码中显式区分；接口的nil检查问题尤为复杂；nilaway等静态分析工具可部分缓解但不如显式的null注解

Granularity comes at a cost

作者: sidhantbansal | 评分: 46 | 评论数: 7 | 发布时间: 2026-06-19 19:16
文章摘要

这篇文章探讨了系统颗粒度的反直觉现象：更细的选择并非总是更好。 **金融市场例子**：股票报价的最小变动单位(tick size)若过小，交易者可以轻易插队抢单，导致流动性提供者不愿积极报价，反而使价差变宽。 **运动场地预订例子**：允许半小时错位预订(如10:30-11:30)会让用户钻空子——在9-10和12-1已被预订时，预订中间时段可"免费"占用前后各30分钟的空隙，因为系统不允许预订这些碎片时段。 **核心观点**：在策略性系统中，过度的颗粒度会创造博弈空间，降低诚实参与的激励，需要找到最优平衡点。

评论摘要
主要讨论点：系统颗粒度（granularity）设计对资源分配效率和用户行为的影响 不同观点： • **支持低颗粒度**（martin_drapeau）：网球俱乐部实际案例显示，30分钟起始时间虽允灵活预订（1小时、1.5小时、2小时），但会产生无法填补的30分钟空档，导致永远无法满负荷运营。即使限制某些时段预订也无法根本解决问题。 • **质疑市场论证**（lesam）：低颗粒度补贴了做市商而损害小订单，价格竞争比以纳秒计的排队位置游戏更有经济价值，低颗粒度并非纯粹的好处。 • **增加颗粒度可解决问题**（jpatten）：体育场地案例的问题恰恰可以通过提高颗粒度（允许用户更精细地选择时段长度）来解决，这样文中提到的不良策略就会失效。 • **理论支持**（emil-lp）：纳什均衡对模型高度敏感，看似无害的修改可能导致更差结果，引用了Braess悖论等经典案例支持这一观点。 补充讨论：dtgriscom对"granular"术语的相对使用提出质疑，认为该词在比较语境中容易造成混淆（更granular究竟是指更大还是更小的单位）。

Show HN: Selector Forge – browser extension for AI-generated resilient selectors

作者: ahmadilaiwi | 评分: 34 | 评论数: 3 | 发布时间: 2026-06-22 14:21
文章摘要

这篇文章介绍了 Selector Forge——一个浏览器扩展工具（支持Chrome和Firefox）。它帮助用户在网页上直接选取元素，自动生成可靠的CSS或XPath选择器。 **核心工作原理：** 1. 用户在页面上选择目标元素 2. 扩展捕获DOM快照并发送到后端 3. AI后端生成候选选择器 4. 扩展在真实DOM中重新验证每个候选项 5. 只返回经过验证的选择器 **主要特点：** - 支持单元素选择和列表选择两种模式 - 浏览器DOM是真实性验证的最终裁判，AI只负责提议和排序 - 适用于编写端到端测试、构建爬虫和页面自动化 该项目使用TypeScript开发，包含完整的单元测试、浏览器测试和端到端测试体系。

评论摘要
LLMs struggle with generating good selectors by default for several reasons: **Lack of runtime context** - LLMs don't see the actual rendered DOM structure, dynamic IDs, or how elements appear after JavaScript execution. They work from static code or descriptions, missing crucial runtime details. **Fragility bias** - Without seeing the full HTML structure, LLMs tend to generate overly specific selectors (like long CSS paths or brittle XPath expressions) that break easily when the page structure changes slightly. **No visual understanding** - They can't determine which elements are actually visible, interactive, or semantically important on the page. A selector might technically match, but target a hidden duplicate element. **Trade-off uncertainty** - Good selectors balance specificity and resilience. LLMs lack the feedback loop to know whether a selector is too broad (matches multiple elements) or too narrow (breaks on minor changes). **Framework-specific patterns** - Modern web apps use dynamic attributes, shadow DOM, and framework-specific conventions (like React's data attributes or Angular's directives). LLMs may not recognize these patterns without explicit context. **Best practice: Provide the actual HTML snippet or DOM structure when asking for selectors, and specify requirements like "must be resilient to layout changes" or "should work across similar pages."**
