JavaScript decided my day starts at 9am

作者: SenHeng | 评分: 32 | 评论数: 16 | 发布时间: 2025-07-26 06:57
文章摘要

文章主要讨论了JavaScript中使用`new Date('YYYY-MM-DD')`创建日期对象时，默认时间为UTC凌晨，而非本地时间。例如在日本（UTC+9），`new Date('2000-01-01')`实际为`2000-01-01T09:00:00+09:00`。这导致作者的管理仪表板在日期过滤时，遗漏了早上9点前的数据。 **问题原因**：`new Date()`将日期字符串解释为UTC时间。 **解决方案**：明确设置时间为本地时区的午夜，并设定最大日期范围到当天最后一毫秒： ```javascript const minDate = new Date(`${minInputDate}T00:00:00`); const maxDate = new Date(`${maxInputDate}T23:59:59.999`); ``` **经验教训**：处理跨时区数据时，需注意日期字符串的解释方式，建议显式设置时间或使用本地时间构造日期。

评论摘要
主要讨论点：处理日期和时间时，尤其是跨时区场景下的最佳实践和常见问题 不同观点： • **日本程序员的时区处理习惯**：koito17指出，由于日本只有一个时区，许多日本程序员在处理日期时缺乏时区相关逻辑，经常使用OffsetDateTime而不是UTC，导致一些细微的错误。例如，后端返回UTC+9的时间戳，而前端根据用户本地时间格式化，从而产生不一致。他提到，很多日本服务不考虑海外用户，因此这些问题不会被修复。 • **时区作为时间参考系的问题**：sgentle认为，时间问题源于没有明确的时间参考系。如果日期和时间没有明确其相对的时区，传递给不同时区的用户时会导致混乱。因此，设计时需要明确时间的参考系，避免隐式时区引发的复杂性。 • **使用UTC作为内部表示**：AdieuToLogic和hatthew建议，所有日期计算应使用UTC作为内部表示，只在展示给用户时转换为本地时间，以避免歧义。 • **JavaScript的Date类问题**：多个评论（如gnabgib, svachalek, tobyhinloopen）提到JavaScript内置的Date类处理日期和时间时存在很多问题，建议使用第三方库如Joda或新的Temporal API来简化处理。 • **具体实现建议**： ◦ sangeeth96提供了从HTML输入元素获取日期并设置时间为午夜的代码示例，并指出没有"date-local"输入类型可能导致的陷阱。 ◦ xyzzy9563建议将日期存储为Unix秒，并在浏览器端根据本地时间显示，以避免歧义。 补充讨论： • **全球化产品的日期处理焦虑**：CuriousRose提到在开发全球化SaaS产品时，对如何正确存储和展示日期感到焦虑，目前使用Postgres的timestampz和Luxon库，但希望找到更多最佳实践来确保正确性。 • **幽默与历史背景**： ◦ kayodelycaon引用MDN文档说明JavaScript日期处理的特性，并幽默地提到JavaScript的历史问题。 ◦ jedimastert通过Tom Scott的视频幽默地表达了处理时间问题的复杂性。 争议焦点： • 主要争议在于是否应使用UTC统一处理日期和时间，以及如何在设计中明确时间参考系，避免隐式时区问题。日本程序员的习惯做法在国际化场景中暴露出问题，而全球化产品则需要更严谨的时区处理策略。 总结：讨论围绕日期和时间处理的最佳实践展开，重点是如何在跨时区场景中避免错误和混乱，提出了使用UTC、第三方库、明确时间参考系等多种策略。
