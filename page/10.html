Nondeterminism's Not the Problem

作者: isaacvando | 评分: 9 | 评论数: 2 | 发布时间: 2026-05-29 15:43
文章摘要

这篇文章反驳了"非确定性是LLM问题根源"的观点。作者指出： 1. **确定性定义**：确定性函数的输出仅依赖输入。编译器是确定性的，LLM因引入随机性而非确定性。 2. **可互换性**：编译器可以通过随机选择寄存器变成非确定性，但仍然有用；LLM可以通过设置temperature=0或固定seed变成确定性。 3. **核心论点**：非确定性本身不是问题。编译器即使非确定性仍可靠，LLM即使确定性也不能等同于编译器。真正的差异不在于确定性，而在于其他根本性质。 作者用Python代码演示了如何让LLM产生确定性输出，证明非确定性是个"替罪羊"。

评论摘要
主要讨论点：prompt 与代码的本质关系，以及开发者对确定性和规范一致性的态度差异 不同观点： • peterlk 的核心观点：充分明确的 prompt 本质上等同于代码，两者在功能上无法区分 • Krssst 的延伸讨论：开发者过度关注"确定性"而忽视"规范一致性"。指出编译器可以是非确定性的但仍然正确，这比不正确但确定性要好 • 对开发者行为的观察：多数开发者可能不重视语言规范，而是依赖直觉判断代码行为；使用库时常不读 API 文档，仅凭函数名猜测功能（忽略前置条件） 补充讨论：Krssst 提出一个悖论——对于不读文档的开发者，非确定性的可观察行为比不符合规范更成问题，因为他们本就不依赖规范作为参考标准。这揭示了理论正确性与实践可用性之间的张力。

What is to be done about MGLRU?

文章摘要

这篇文章讨论了Linux内核内存回收机制面临的问题。目前内核同时维护两套完全独立的回收算法——传统LRU和多代LRU（MGLRU），导致代码重复、维护困难。在2026年Linux峰会上，开发者提出统一方案：将两套实现分离到独立文件、定义性能评估工作负载、识别共同特性、对比实现差异。主要挑战包括MGLRU原作者失联导致理解困难、两者使用不同术语描述相似功能、以及如何在不阻碍现有改进工作的前提下推进代码重构。目标是通过模块化和共享代码来统一这两套系统。
