Civil War in 3D: Stereographs from the New-York Historical Society (2015)

作者: LorenDB | 评分: 53 | 评论数: 8 | 发布时间: 2025-05-29 15:43
文章摘要

这篇文章介绍了纽约历史协会将超过700张美国内战立体照片数字化并公开展示的项目。立体照片通过结合两张略有偏差的图片，使用立体镜设备实现三维效果。立体镜技术由查尔斯·惠特斯通于1838年发明，奥利弗·温德尔·霍尔姆斯在1859年对其进行了改进。内战期间，马修·布雷迪的公司通过派遣摄影师和便携式暗房记录战争，布雷迪本人可能并未亲自拍摄。亚历山大·加德纳是另一位著名摄影师，曾为多位将军和重要战役拍摄。这些照片提供了珍贵的历史影像，其中一些还包括了亚伯拉罕·林肯的肖像。

评论摘要
主要讨论点：立体图的观看方式及其效果 不同观点： • [kazinator] 认为，对于裸眼观看，交叉眼睛（cross-your-eyes）方式比注视远方（stare-into-distance）方式更合适。他指出，大多数人无法让眼睛发散，因此注视远方方式的图像尺寸受限。而在交叉眼睛方式下，可以使用更大的图像。此外，使用立体镜的放大功能可以缓解眼睛聚焦的问题，因为放大的虚拟图像看起来更远。 • [ge96] 提供了一个具体例子，展示了一个有效的立体图，但提到观看后感到不适，类似于之前使用VR头戴设备时的体验。 • [saddat] 建议使用特定工具（https://huggingface.co/spaces/cavargas10/TRELLIS-Multiple3D）将图像转换为立体图。 • [JeremyHerrman] 质疑一些例子是否真的是立体图像对，表示通过交叉眼睛观看时，有些图像（如"McLean’s House"和"Lincoln visits General McClellan at Antietam"）没有明显的深度变化。 • [bredren] 希望将这些图像转换为适用于Vision Pro的空间照片，以增强观看体验。 • [ramesh31] 指出，通过交叉眼睛并聚焦在出现的第三个中心图像上，可以直接看到这些立体效果，类似于3D视觉错觉书籍。 补充讨论： • 观看立体图的不同方法及其适用性，如交叉眼睛方式和注视远方方式。 • 使用工具和设备（如立体镜、VR头戴设备、Vision Pro）对观看体验的影响。 • 一些图像是否真正展示了预期的深度效果，存在争议。 • 观看立体图可能导致的不适感及其原因。 争议焦点： • 一些立体图像对是否真的展示了深度变化（[JeremyHerrman]的观点）。 • 哪种观看方式（交叉眼睛 vs. 注视远方）更适合裸眼观看立体图（[kazinator]的观点）。

RSyncUI – A SwiftUI based macOS GUI for rsync

作者: mickelsen | 评分: 113 | 评论数: 13 | 发布时间: 2025-05-29 05:05
文章摘要

RsyncUI 是一个基于 SwiftUI 的 macOS 应用程序，为命令行工具 rsync 提供图形用户界面（GUI），适用于 macOS Sonoma 及更高版本。它帮助用户组织同步任务和设置 rsync 参数，简化了 rsync 的使用。虽然 GUI 用于任务管理，但实际的同步任务是由 rsync 命令行工具执行的外部任务，RsyncUI 会监控其进度和终止状态，用户可以随时中止任务。RsyncUI 可通过 Homebrew 安装，并且已获得 Apple 的签名和公证。项目文档基于 Hugo 主题 Docsy，并使用 MIT 许可证发布。

评论摘要
主要讨论点：围绕 macOS 上的 rsync 工具及其图形界面（GUI）替代方案的讨论 不同观点： • **支持 Carbon Copy Cloner (CCC)**：watersb 提到 Mike Bombich 的 Carbon Copy Cloner (CCC)，它是一个商业软件，但其对 rsync 的补丁是开源的，能够处理 Mac 特有的扩展属性。这提供了对 Mac 用户有用的功能，尤其是在处理历史遗留特性时。 • **推荐 Unison 工具**：mhw 认为 Unison 是一个不错的选择，它允许用户交互式地调整同步算法，并且能够存储文件的前一次运行状态，从而提高同步效率。Unison 提供了 GUI 和 TUI，适合在多台设备之间同步目录。 • **使用旧工具的经验**：lproven 提到了自己使用过的多个 rsync GUI 工具，包括 RSyncOSX 和 ARsync。这些工具各有优缺点，其中 ARsync 已经不再维护，而 RSyncOSX 也在不断更新。 • **偏好命令行工具**：dmarinus 偏好使用命令行工具，并开发了一个简单的 cli 前端 rzn，用于 rsync 和 rclone，类似于 git 的 pull/push 操作。 • **对安全性的关注**：w10-1 关注应用的安全性问题，尤其是 XPC 代码和应用的沙盒化问题，建议开发者总结如何识别和解决这些风险。 • **希望增加更多功能**：Bender 和 joshstrange 希望该工具能够支持更多的功能或前端集成，例如 LFTP 和 Rclone，从而扩展工具的应用场景。 • **跨平台需求**：MortyWaves 询问是否有好的 Windows 平台上的 rsync GUI，显示出对跨平台工具的需求。 • **UI 设计的批评**：nesarkvechnep 对 SwiftUI 应用的 UI 设计提出批评，认为表格和侧边栏的填充有问题，建议改进侧边栏的导航结构。 补充讨论： • 一些用户（如 AnonC）提到在使用 rsync 时需要反复查阅手册或进行试错，以确定正确的参数，因此认为这些工具能提供更好的用户体验。 • 关于工具安装的讨论中，AnonC 建议在文档中加入通过 Macports 安装 rsync 的选项，而不仅仅通过 Homebrew。 • ctippett 提到了 Transmit 这一工具的同步功能，认为它也是一个不错的选择，尤其是在 SFTP/远程文件浏览场景下。 争议焦点： • 主要集中在工具的安全性（w10-1 的评论）和 UI 设计（nesarkvechnep 的评论）上，部分用户对应用的实现细节和界面设计提出了质疑和改进建议。

文章摘要

本文讨论了AI辅助开发工具在代码生成中的局限性，通过一个具体的Rust代码示例说明这些工具可能带来的问题。文章分析了Cursor编辑器展示的AI建议代码，指出其中的长度验证是多余且无用的，因为`u16`类型的最大值本身就是65535，导致验证条件永远为假。此外，代码中的清理操作虽能实现基本功能，但存在不必要的内存分配，且代码风格不佳。作者认为，AI工具生成的代码不仅无用，还可能产生编译器警告和不良代码风格，强调需要更智能的工具来帮助开发者做出正确的编码决策。
