Show HN: Epiq – Distributed Git based issue tracker TUI

作者: jolaflow | 评分: 83 | 评论数: 20 | 发布时间: 2026-05-16 00:18
文章摘要

文章介绍了 Epiq：一个面向 Git 仓库的本地优先、事件溯源式项目管理工具。它提供终端 ASCII 看板、键盘/类 Vim 操作、可按需同步、冲突友好协作，并支持 MCP，方便 AI 代理参与工作流。

评论摘要
主要讨论点：基于 Git 的分布式 issue tracker 的设计可行性、目标用户、协作冲突处理，以及安装/集成方式。 不同观点： • 支持者认为方案很“优雅”，把 Git 当数据库很酷，适合保持 issue 本地化、随仓库分发，尤其适合开发者和个人任务管理，也能减少切换到网页工具的成本。 • 质疑者担心面向更广团队时，TUI 不够用；若产品经理、设计师也要参与，终端界面在组织层面不现实，建议加本地 Web UI。 • 有人追问数据层是否独立于 Git、以及“后提交覆盖前提交”的冲突模型：如果多人同时补充同一 issue，是否会丢失一方内容，之后如何恢复/合并。 • 也有人建议默认提供中心化 issue 仓库，或支持跨仓库关联，因为 issue 往往和代码演化速度不同，未必适合和本地 WIP 代码一起提交。 • 集成方式上，有人更偏好单一二进制/CLI skill，而不是 MCP；也有人建议参考 git-bug 的前人经验。 补充讨论： • 争议焦点主要是“开发者工具”还是“团队协作工具”，以及 npm 安装链路是否会劝退用户。

评论摘要
主要讨论点：Waymo因部分Robotaxi可能驶入积水而“召回”并OTA修复，引发对自动驾驶感知积水、软件更新、安全边界和监管措辞的讨论。 不同观点： • 技术难点派：区分湿路面与深水本就困难，人类也常误判；建议加装水传感器，车辆可低速试探，但可能对浅水坑过度保守。 • 软件迭代乐观派：自动驾驶的优势在于发现问题后可统一修复，所有同型号/相关车型都能受益，长期会比人类司机更安全；新司机则无法“批量打补丁”。 • 推理与数据派：不一定要专门传感器，可结合视觉、车辆减速、转向修正判断涉水；还可利用Google地图/手机加速度数据上报积水危险位置。 • 现实环境担忧派：异常天气、暴雨、暴雪等训练数据外场景很危险，需要仿真验证；新奥尔良等积水和隐藏坑洞多的城市尤其考验“本地道路知识”。 • 道路基础设施派：问题也暴露道路排水差，若自动驾驶促使改善道路，是好事。 • 监管措辞质疑派：“召回”现在常只是OTA更新，容易制造恐慌标题；建议NHTSA区分进店停驶式召回与软件更新。 补充讨论：有人询问特斯拉摄像头方案如何处理此类情况；也有评论用“Waymo潜艇”等玩笑调侃。

Solar-based sleep patterns compared to modern norms

文章摘要

文章认为，连续八小时睡眠是现代9-5制度和人工照明的产物。传统地中海农耕社会顺应日照与季节：夏有午睡、冬有“二段睡”。作者赞赏希腊仍保留午休与分段工作，认为这更符合自然节律。

评论摘要
主要讨论点：午睡/分段睡眠（siesta、polyphasic sleep）与现代9-5工作制、商店营业时间是否冲突，以及这种作息到底是“自然”还是被浪漫化。 不同观点： • 质疑派：西班牙用户认为午睡被过度美化，虽有健康益处，但会压缩白天可用时间；8小时工作制下很难安排，学校和工作制度也因此混乱。 • 支持派：有人认为地中海作息更灵活，下午下班后商店、牙医、餐馆仍开着，方便办事；也有人觉得炎热季节“晚睡+午休”更合理。 • 历史/科学争论：有人说分段睡眠是现代工业社会前就存在的普遍模式；反对者指出缺乏确证，工业化并非处处同步。也有人补充现代平均睡眠比百年前少，睡眠时长本身就受现代生活影响。 • 现实批评：有人认为9-5和过早开工、过少服务时间在“惩罚”上班族，连办事、取包裹都困难。 • 折中观点：睡眠应因人因地而异，受纬度、光照、孩子、疲劳程度影响；与其坚持某种“标准”，不如多实验找适合自己的节奏。

Erlang/OTP 29.0

文章摘要

Erlang/OTP 29.0 是重大版本更新，新增 unsafe 标记、原生 record、范围整数守卫、多值推导等；编译器/JIT优化并增加多项默认警告。SSH/SFTP 默认更安全，SSL/SSH 优先后量子混合算法；新增 io_ansi、ct_doctest、rand:shuffle，并调整代码路径与Windows支持。

评论摘要
主要讨论点：围绕 Erlang/OTP 新版本改进、安全性、生态使用现状及与 Elixir/Rails/Go 的对比展开。 不同观点： • 版本改进积极派：认为默认关闭 SSH daemon 和 SFTP 是重要安全改进；io_ansi 有助于构建复杂 CLI；跨节点 fwrite 体现 Erlang 优势；Native Records 被视为对旧 records 的实质改进，可能影响 Elixir 中 records/tuples/maps 的使用方式。 • 安全升级派：提醒生产环境应尽快升级到该版本或最新补丁版，因为旧版本被安全扫描发现多个 2026 年的严重和高危 CVE。 • 生态关注派：有人关心 Native Records 会如何在生态中落地，也有人询问 WhatsApp 是否仍基于 Erlang，反映对 Erlang 实际应用规模的兴趣。 • Erlang 现状质疑派：有人问是否还有人用“纯 Erlang”做新项目，以及相比 Elixir 的选择理由。 • Web 开发反对派：质疑 Erlang/Phoenix 的生产力，认为 Rails 对独立开发者更高效，LLM 写 Rails 更好；实验用 Rails，稳定后再用 Go 重写，并用 Hotwire/HTMX 替代前端框架。 • 背景解释派：有人补充 OTP 是一套用于构建高可靠、容错应用的库和设计原则，源自电信领域。 补充讨论：还有人调侃新增 `-unsafe` 属性“正好赶上 Rust 重写”，属于对安全语义的玩笑式评论。
