Batteries and Buildings

作者: sonderotis | 评分: 4 | 评论数: 1 | 发布时间: 2025-07-01 20:49
文章摘要

本文讨论了软件开发中的"含电池"（battery-included）和"无电池"（no-batteries）框架的分类。含电池框架如Express，开箱即用，提供高度抽象，便于快速开发，但可能缺乏细节控制，不利于问题排查。无电池框架如Flask，需要开发者自行添加包和配置，虽然灵活，但可能导致架构臃肿和开发繁琐。文章还以Vim的懒人vim（lazyvim）为例，说明过度含电池的工具可能包含不必要的插件，导致新手最终放弃使用。作者认为理想的框架应具备可插拔性，既能简化开发，又能根据需要精简或扩展功能。

评论摘要
主要讨论点：对“电池”在文章中含义的不同理解 不同观点： • detourdog认为评论最初让他以为文章是关于建筑物的备用电源（back-up power for buildings）。他原本期待文章讨论实体的电力系统或设备，例如在停电时提供电力的电池或发电机。 • detourdog随后推测，作者实际上是用电池作为一种隐喻，用来形容软件部署的准备状态（batteries as a metaphor for software deployment readiness）。他认为“电池”并非指实际的物理设备，而是象征一种准备就绪的状态，可能涉及软件系统在应对问题或突发情况时的应急能力。 补充讨论： • 评论中提到对文章主题的预期与实际内容之间的差异，表明读者在阅读前可能带有不同的背景知识或期望。 • 隐喻的使用在技术文档或讨论中较为常见，detourdog的理解表明作者可能借用了“电池”这一概念来传达软件系统中“准备”和“应急”的相关理念。

Experiment: Colocating agent instructions with eng docs

作者: dannyrosen | 评分: 9 | 评论数: 2 | 发布时间: 2025-06-30 13:44
文章摘要

本文探讨了将AI代理指令嵌入工程师文档中的实验。作者最初对单独维护代理文档持怀疑态度，因为这可能导致信息重复和不同步。为此，作者尝试将代理指令嵌入现有的工程师文档（如`examples.rst`）的注释中，而非创建单独的文档（如`GEMINI.md`）。实验中，作者使用Gemini CLI根据文档中的指令迁移代码示例，结果显示代理严格遵循了嵌入的指令，甚至捕捉到了文档中的一个错误。尽管实验成功，但作者指出，若仓库中完全没有单独的代理文档，结果可能会有所不同。实验表明，将代理指令嵌入现有工程师文档可能是一种有效的解决方案。

评论摘要
主要讨论点：如何在工程项目中有效记录和利用LLM（大型语言模型）和AI助手的使用日志及指令 不同观点： • **jauntywundrkind** 认为，默认将aider日志添加到`.gitignore`并不理想。他主张保留这些日志，以便人类和AI都能从中反思和学习。他建议将AI指令与工程文档一起保存，并提出可以利用像Backstage这样的工具来集成和管理这些知识库。他还提到了MCP服务器用于反思聊天历史的可能性，并对Kenton Varda和Cloudflare在该领域的实践表示赞赏。 • **8note** 对jauntywundrkind的观点表示支持和兴奋，特别强调了让LLM在不同工程师之间保持可重复性的重要性。他赞同保留日志和指令的想法，认为这有助于提高团队协作和知识共享的效率。 补充讨论： • **争议焦点**：是否应该默认忽略aider日志。jauntywundrkind认为忽略日志对人类和AI都不利，而默认设置是忽略这些日志。 • **技术工具的建议**：jauntywundrkind提到了Backstage和MCP服务器的潜在应用，特别是如何通过这些工具来更好地组织和管理AI助手和LLM的使用记录。 • **实际案例**：Kenton Varda和Cloudflare的项目被当作一个好的实践例子，用于展示如何记录和推广AI指令作为参考材料。 通过这些讨论，可以看出社区对于如何在工程中有效利用和记录LLM及AI助手的使用持有不同但积极的看法，并提出了具体的工具和方法建议。

WASM Agents: AI agents running in the browser

作者: selvan | 评分: 142 | 评论数: 17 | 发布时间: 2025-07-04 05:19
文章摘要

本文介绍了一个名为 **Wasm agents blueprint** 的实验性项目，旨在通过将代理编写为 HTML 文件，使其能够在浏览器中直接运行，而无需额外安装工具或框架。该项目利用 **WebAssembly** 和 **Pyodide** 技术，将 Python 代码在浏览器中运行，实现了一种轻量、跨平台的 AI 代理。项目中的每个代理都是独立的 HTML 文件，包含用户界面和运行代码，使用 **openai-agents-python** 库与 LLM（如 GPT-4）进行交互，也可以接入自托管模型（如通过 Ollama 或 HuggingFace 提供的模型）。项目提供了多个示例，包括简单对话代理、多代理系统和带有工具的代理等，展示了 Wasm 代理的潜力。用户可以通过 GitHub 获取代码并按照说明运行这些代理。

主要讨论点：在浏览器中运行AI代理和相关技术的可行性及其实现方法 不同观点： • simonw：认为文中的"agent"定义来源于OpenAI的Python库，该库将工具作为可选项，而不是必选项，这与许多其他代理定义不同。他还指出"hello world"演示仅运行单个提示。 • thepoet：提到他们在评估Pyodide和WASM时发现多步骤任务需要本地运行LLM生成的代码，并选择了Apple Containers上的CodeRunner，但认为在处理任意提示方面仍需改进。 • meander_water：认为直接在浏览器中运行模型更有趣，可以通过transformers.js和onnx runtime实现，且无需GPU。 • om8：展示了在浏览器中运行llama3模型的demo，并建议未来可以完全本地化。 • TekMol：质疑为何需要WASM，因为当前仅运行与服务器LLM通信的代码。 • ipsum2：分享了通过修改JS绕过网站反自动化点击检测的经验，并认为Firefox由于其可扩展性可能成为代理的未来。 • _pdp_：认为用Python编写客户端代码并没有简化代理创建，反而更复杂。他还指出代理连接工具并嵌入工作流仅是工作的一小部分，更多的工作在于可观察性、后台任务、队列系统等。 • asim：认为代理应是长期运行的外部浏览器进程，WASM的想法聪明但浏览器环境需要进化。 • sandGorgon：介绍了他们在移动浏览器中创建AI代理的经验，并提到通过扩展框架实现这些代理，且在Android上实现更困难。 • benatkin：认为文章试图用"agent"这个词来显得酷，但并未说明为何这不仅仅是基础AI工作，指出openai-agents-python库可用于编写非代理代码。 • raybb：询问是否可以通过浏览器扩展绕过CORS问题。 • zoobab：指出未提及WebGPU。 • dncornholio：认为在HTML文件中将Python代码放入字符串是过时的做法。 • _joel：理解为何需要禁用CORS限制，但仍觉得这不太理想。 补充讨论： • 关于是否需要WASM的争议（simonw, TekMol）。 • 在浏览器中直接运行模型的可行性和工具选择（meander_water, om8, meander_water）。 • 对代理定义及其实际应用的讨论（simonw, _pdp_, benatkin）。 • 绕过技术限制（如CORS）的实际操作经验（ipsum2, raybb）。 • 对不同技术栈（如Python、WebGPU）在浏览器中应用的看法（zoobab, dncornholio）。

Armin Ronacher在这篇文章中讨论了他对模型上下文协议（MCP）的看法，认为MCP目前存在两大问题：缺乏真正的可组合性和对上下文的过度需求。他通过实验比较了使用GitHub MCP和gh CLI工具完成任务的效率，发现后者更高效。虽然有人认为MCP在特定领域应用中可能有价值，但Ronacher认为，由于依赖推理，MCP在当前形式下始终不如编写代码便捷。 他强调，自动化任务应关注可重复性和可靠性，代码生成是更优选择，因为它允许验证和审查过程。例如，让LLM生成Python代码进行计算，比直接让LLM计算更可靠，因为代码可以被检查和验证。Ronacher总结，在实现自动化时，应优先考虑使用代码，以确保任务能正确且高效地执行。
