I'm Getting into Mesh Networks (Meshtastic, MeshCore, and Reticulum)

作者: Panda_ | 评分: 365 | 评论数: 29 | 发布时间: 2026-05-27 19:52
文章摘要

文章批评当今互联网虽号称去中心化，实际仍受少数服务商和地址资源体系控制。作者主张用基于 LoRa 的网状网络提升抗审查、韧性与个人网络主权，尤其适合消息和信息共享；同时认为 Meshtastic 虽易用且流行，但难支撑大规模公共网络。

评论摘要
主要讨论点：围绕 MeshCore、Meshtastic、Reticulum 等去中心化网状通信方案的现实价值，讨论其在应急通信、独立性、覆盖范围、可扩展性和普及前景上的优劣。 不同观点： • 强调“独立自主”与应急价值：`smlacy`认为若依赖互联网等外部传输，就失去“谁都无法控制”的自由通信意义；MeshCore断电后仍可运行，配合太阳能节点，对灾害恢复尤其关键。`m4rtink`也赞赏设备间可直接通信，不依赖基站或运营商。 • 认可其实用性，但更偏“低速替代互联网”或本地实验：`raffael_de`喜欢“只适合文本”的 para-internet，认为天然抑制垃圾信息；`robotswantdata`、`sschueller`给出太阳能节点、跨城活跃度等正面例子，说明局部网络已能运转。 • 认为现阶段更像玩具/技术演示：`rcarmo`、`Groxx`都觉得这类网络有趣但缺乏结构、标准和大众基础，像早期 wardriving 或 CB，无力扩展成严肃基础设施。 • 质疑覆盖、性能与规模化：`rta5`、`LelouBil`、`transcriptase`反映网络稀疏、距离不稳定、速率低；`lormayna`指出好天线可显著改善距离，但 Meshtastic 的泛洪机制长期不可扩展，需更复杂路由协议。 • 指出成本与生态问题：`moontear`嫌 LoRa 硬件贵；`ChrisMarshallNY`认为开放标准不成熟，可能因缺少商业驱动，反而专有方案如 GoTenna 更成功。 补充讨论：争议焦点主要在“它是严肃的独立应急基础设施，还是小众爱好者玩具”；另一个焦点是“应优先保证彻底去中心化，还是接受现实中的外部依赖与渐进发展”。

Gemini, Gophers, and Fingers. Oh My Alternative Internets Beyond HTTPS

作者: ChrisArchitect | 评分: 134 | 评论数: 15 | 发布时间: 2026-05-27 17:24
文章摘要

文章介绍了互联网中除 HTTPS 外的另一种可能：URI 协议生态。作者批评 Chrome/Chromium 主导造成网络“单一栽培”，主张通过去中心化的 Finger、Gopher、Gemini 等协议重建更简洁、自主的网络体验。它们多为纯文本、无需 GUI 和 JavaScript，可在终端运行，拥有独立社区与美学，也体现了 IndieWeb 对抗平台垄断的理想。

评论摘要
主要讨论点:关于简化互联网协议(Finger、Gopher、Gemini)与现代Web的对比,以及是否需要回归简单化的网络体验。 不同观点: • **怀旧派**:认为早期协议(Finger、Gopher)简洁高效,没有广告、追踪等干扰,John Carmack通过Finger分享开发日志就很有吸引力,不需要点赞转发等社交机制(sedatk, cortesoft) • **实用主义者**:质疑简化协议的实际价值,认为去除所有现代功能(如实时交互、内联图片、cookies认证)过于极端,使用场景太受限(AuthAuth, unethical_ban) • **协议中立派**:指出问题不在HTTP/HTTPS协议本身,而在生态系统。简单HTML同样可行,不必完全抛弃现有协议。Google/Chrome并不控制HTTP协议(progbits) • **折中方案支持者**:建议通过"Simple Web"规范、浏览器插件、屏蔽列表等方式在现有Web上实现简化,而非完全替换协议(angiolillo, unethical_ban) • **实践者**:有人持续使用文本浏览器、开发Gopher版本网站服务低带宽地区用户,证明简化协议仍有实用价值(1vuio0pswjnm7, ktallett) 补充讨论: 争议焦点在于"格式限制能否解决Web问题"——支持者认为技术限制可遏制广告追踪,反对者认为即使纯文本也会被垃圾信息淹没,需要配合审核机制。另有讨论指出加密(HTTPS)本身也服务于数据收集公司利益。

Private equity bought America's essential services

作者: NoRagrets | 评分: 527 | 评论数: 59 | 发布时间: 2026-05-27 12:00
文章摘要

这篇文章揭露了私募股权如何通过收购美国关键公共服务行业来牟利。以消防车行业为例：私募基金通过杠杆收购整合市场，将20多家独立制造商缩减至3家巨头控制80%市场。REV Group（由私募基金持有）系统性收购竞争对手后，消防车价格十年翻倍，交付周期延长至4年，利润率从5%飙升至13%。2025年芝加哥一起火灾中，故障的消防云梯导致4人死亡，暴露了这种"买入-剥离-转手"商业模式的致命后果：私募基金通过债务融资收购企业，削减成本追求短期利润，将基础设施变成利润提取机器，最终由公众承担代价。

评论摘要
主要讨论点：私募股权(PE)公司通过杠杆收购、削减成本、转售获利的商业模式及其社会影响 不同观点： • **养老金驱动论**：PE存在是因为养老基金需要7%回报率维持偿付能力。PE通过剥夺消费者和员工利益来实现高回报，本质是将当代人生活质量转移给退休老人。要解决PE问题需先解决养老金制度（spyckie2） • **道德缺失论**：公司只需跑赢通胀即可，不必追求每季度数十亿利润。问题核心是经营者缺乏基本人性，消费者和员工应拒绝与这类公司交易。养老金违约是公司贪婪导致，非员工过错（BirAdam） • **制度漏洞论**：杠杆收购(LBO)本身不应被允许——用被收购公司的钱支付收购款。PE向投资者和被收购公司双向收费，即使公司倒闭PE仍获利，存在严重利益错配（sega_sai, WarmWash） • **市场失灵论**：某些服务不应以营利为目的运营，无论所有者是谁（danielmarkbruce） 补充讨论： - PE正在吞并各行业小企业（公寓、餐饮、教育科技），通过垄断涨价剥削固定需求市场 - 有评论将PE比作古罗马Crassus的消防队勒索模式 - PE最近游说允许普通人退休金投资PE，被警告为寻找"新韭菜" - 债务转嫁机制引发质疑：收购方贷款如何变成被收购公司负债

Announcing Rust 1.96

作者: adamch | 评分: 139 | 评论数: 4 | 发布时间: 2026-05-28 19:20
文章摘要

Rust 1.96.0 发布，主要更新包括： 1. **新的 Range 类型**：引入 `core::range` 模块下的新范围类型，支持 `Copy` trait，解决了旧版 `Range` 因实现 `Iterator` 而无法 `Copy` 的问题。 2. **断言匹配宏**：新增 `assert_matches!` 和 `debug_assert_matches!` 宏，用于检查值是否匹配指定模式。 3. **WebAssembly 变更**：链接器不再默认传递 `--allow-undefined` 参数，未定义符号现在会导致链接错误。 4. **安全修复**：修复了两个针对第三方注册表用户的漏洞（CVE-2026-5223 和 CVE-2026-5222），crates.io 用户不受影响。

评论摘要
主要讨论点：Rust 标准库中 `std::range` 的重构方式，以及标准库 API 版本演进策略是否应更明确、可维护。 不同观点： • 反对“新实现直接替换旧 `std::range`、旧版移到 `std::range::legacy`”。`j1elo` 认为这会制造命名混乱，也不利于未来继续迭代；若以后再改进，层层 `legacy` 会很尴尬。其主张保留现有 `std::range`，把新方案作为 `v2` 等版本化接口引入，并以 Go 标准库为正面例子。 • 借题发挥到 Rust 标准库哲学。`j1elo` 认为 Rust 因“标准库 API 一旦加入就难以更改”的顾虑，长期不愿提供更“官方、成套”的方案；若能解决 API 演进与迭代方式，或能减少对扩充标准库的抗拒。 • 谨慎乐观但关注迁移成本。`Tuna-Fish` 表示原以为 ranges 的问题会一直成为“历史包袱”，现在能修正是意外之喜，但核心担忧是过渡是否足够平滑，和前者形成“支持修正、担心落地”的关系。 • 纯正向反馈但未展开论证。`PoignardAzur` 对 `assert_matches!` 回归表示兴奋，说明讨论中除 `range` 外，也有人关注其他新增内容。 • 离题讽刺。`7e` 提到“接受 AI 贡献的 Rust 分叉”，更像调侃，对主讨论没有实质论证。 补充讨论：主要争议焦点是“如何处理标准库破坏性改进”：应直接替换并把旧版标为 `legacy`，还是采用显式版本化（如 `v2`）以保持清晰和可持续演进。

What Apple and Google are doing to push notifications

作者: iamacyborg | 评分: 409 | 评论数: 65 | 发布时间: 2026-05-27 19:24
文章摘要

这篇文章讨论了推送通知从简单传输层演变为平台主动干预的过程。苹果和谷歌控制着所有推送通道，最初为解决电池问题而建立的中介架构，在过去15年里逐步加强了平台控制：从2017年Android引入通知频道分类，到2021年iOS的Focus和中断级别分类，再到2022年Android 13将推送改为需明确授权。每一步都削弱了发送方的控制权，部分转移给用户（这是合理的），但更多转移给了平台。平台通过不透明的算法模型来决定通知的优先级、摘要和展示方式，本质上是将用户注意力视为需要保护的稀缺资源——既为用户利益，也为平台自身的留存率考虑。

评论摘要
主要讨论点：关于手机推送通知的控制权、隐私问题以及平台（Apple/Google）的干预政策 不同观点： • **极简主义派**：主张严格限制通知权限，仅保留紧急联系类应用（电话、短信、即时通讯），认为大多数通知都是为了抢夺注意力而非传递重要信息。支持24/7勿扰模式，主动检查而非被动接收。 • **平台干预支持者**：认为Apple和Google对通知的控制和过滤是必要的，可以防止垃圾信息泛滥。推送应仅用于交易性通知，反对营销类推送。 • **隐私担忧者**：指出集中式推送架构（APNs/FCM）存在监控风险，美国政府已被曝光秘密获取推送通知元数据。批评这种架构本质上是大规模元数据收集系统，开发者无法阻止。 • **用户体验批评者**：不满应用滥用通知权限发送营销内容，希望平台提供更精细的通知分类控制（如单独关闭营销通知）和更好的摘要格式。 • **服务商视角**：作者站在推送发送方立场，认为平台的干预损害了合法的营销、教育和发现类通知，批评平台将用户注意力视为需要保护的稀缺资源。 补充讨论：部分用户提到Uber、Airbnb等服务混合核心功能通知和营销信息的问题；也有技术用户探讨自托管推送服务的可能性（如Home Assistant）以绕过集中式架构。
