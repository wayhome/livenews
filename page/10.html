crustc: entirety of `rustc`, translated to C

作者: Philpax | 评分: 292 | 评论数: 24 | 发布时间: 2026-07-02 22:57
文章摘要

crustc 是一个将 Rust 编译器（rustc 1.98.0-nightly）转换成 4600 万行 C 代码的项目，可用 GCC 和 make 构建出功能完整的 Rust 编译器。这是作者新开发的 Rust 到 C 编译器工具链 cilly 的演示。 cilly 的核心创新是能自适应不同的 C 编译器，通过生成"检测程序"来查询编译器支持的特性、类型布局、字符编码等，尽量只依赖 ANSI C 标准。主要目标是支持缺乏 LLVM/GCC 但有 C 编译器的老旧或冷门硬件平台。 cilly 还具有网络透明性，可通过 TCP 与远程 C 编译器通信，解决交叉编译问题。它能生成 makefile，让用户用标准 C 工具链构建 Rust 代码，并保持与原生 rustc 的 ABI 兼容性。

评论摘要
**主要讨论点：** Rust到C编译器（crustc）项目的价值和应用场景 **不同观点：** • **支持派（多数）**：赞赏作者14次尝试的坚持，认为转译到C比LLVM IR更可行，让GCC处理优化是聪明的方案。前C++编译器开发者明确表示支持 • **质疑派**：认为直接为LLVM/GCC添加老硬件支持比构建语言转译器更合理，质疑项目目标的技术路线选择 • **实用主义者**：关注具体应用场景 - Plan 9系统支持、PPC Mac OS X移植可能性、性能表现对比、以及在bootstrappable项目中大幅简化Rust编译器引导过程的潜力 **补充讨论：** • 有人提出用Diverse Double-Compiling方法验证官方编译器是否存在后门的安全性测试思路 • 多人发现LLVM曾有C后端但已废弃，现在可能重新出现 • 出现多条幽默评论，调侃"用C重写Rust"反转了"用Rust重写一切"的梗，以及"Rust终于内存安全到可以变成C"的讽刺

评论摘要
**主要讨论点：** IETF TLS 工作组是否应发布纯 ML-KEM（后量子密码）标准，而非仅混合方案（ECC+PQ） **不同观点：** • **警告派（DJB 等）：** 认为 NSA/GCHQ 试图削弱安全标准，将混合方案（ECC+ML-KEM）降级为纯 ML-KEM，不应信任情报机构参与标准制定，强调历史上有被破坏先例 • **技术务实派：** 指出这是信息性 RFC（非强制标准），不影响已有的混合规范推荐；多个主流加密库已实现 ML-KEM 支持；电信等行业因合规要求需要 RFC 文档；纯 ML-KEM 有助于对抗"现在收集，未来解密"攻击 • **程序质疑派：** 批评 DJB 行为不专业，已被邮件列表多次警告；认为其发起社交媒体动员违反 RFC 7282 关于工作组讨论的规范；指责这是诉诸权威和制造功能障碍的策略 • **中立观察派：** 质疑 NSA 参与的具体证据（未见 nsa.gov 邮箱）；疑问为何可选标准会构成威胁；注意到双方论述都有夸大成分 **补充讨论：** 争议核心在技术安全与实际部署之间的平衡——DJB 被社区广泛尊重但也被认为有偏执倾向；多数密码学界认为 ML-KEM 安全可靠；这场争论已持续一年以上且高度政治化。

Memorizing session transcripts isn't useful

文章摘要

这篇文章论证了让AI代理访问历史会话记录对软件工程任务并无帮助。 作者团队发现，尽管直觉上会话记录似乎包含有价值的上下文信息（如用户意图、废弃的方案等），但实际测试表明这种"记忆"功能不仅无益，甚至可能降低代理性能。 核心原因在于：优秀的代理应该已经将有价值信息提炼成代码注释、文档、PR描述等工件。会话记录中剩余的多是被有意丢弃的"草稿"内容。更关键的是，代理无法有效清理记忆——它们会将所有输入视为"意图"，导致垃圾信息累积，浪费token并降低质量。 作者建议：会话记录可用于团队观察，但不应自动用于增强代理能力。如需从历史中学习，必须有人工审核环节。

评论摘要
**主要讨论点：** AI助手的记忆功能是否有用，以及如何避免上下文污染和错误假设的问题 **不同观点：** • **反对派：** 记忆功能弊大于利，会导致上下文污染（estetlinus称其在不相关项目间传播信息）、产生错误假设（zackify提到AI会基于假设性问题做出误判，如假设用户拥有数据中心），且过时记忆会严重误导AI当前任务。多人表示这是第一个会关闭的功能 • **条件支持派：** 记忆功能在特定场景有价值。tracyhenry认为在"项目模式"中记忆有用（围绕同一主题的问题），但通用模式下应保持无状态。linsomniac举例说明记忆能提供有价值的上下文（如考虑团队规模提供建议），尽管偶尔出错 • **日志记录派：** shepherdjerred强烈支持会话日志系统，通过AGENTS.md配置让Claude生成结构化日志，用于追踪工作状态和历史决策。trjordan补充日志在验证阶段特别有用，可展示AI的手动验证过程 • **系统性解决方案：** 有人指出这是硬件限制问题（1M tokens不足），建议通过微调模型或更好的文档系统替代；scosman通过配置文件明确指导AI不要过度记忆一次性评论 **补充讨论：** 争议焦点在于记忆粒度控制——低价值记忆会形成恶性循环，且模型难以区分"当前发生"和"过去发生"的事件，导致推理混乱
