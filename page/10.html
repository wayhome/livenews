JEP 506: Scoped Values final for Java 25

作者: ludovicianul | 评分: 28 | 评论数: 3 | 发布时间: 2025-04-15 11:17
文章摘要

JEP 506 提出引入 "scoped values" 机制，允许方法在线程内及其子线程中共享不可变数据。相比线程局部变量（ThreadLocal），scoped values 更易于理解和推理，具有更低的空间和时间成本，尤其在与虚拟线程（JEP 444）和结构化并发（JEP 505）结合使用时。该机制经历了多个预览和改进阶段（JEP 429, JEP 446, JEP 464, JEP 481, JEP 487），并计划在 JDK 25 中正式引入。其目标包括易用性、可理解性、健壮性和高效性，但不旨在改变 Java 语言或废弃 ThreadLocal API。Scoped values 解决了在方法间传递共享数据时的繁琐问题，尤其在大型程序中不同组件间传递上下文时非常实用。

评论摘要
主要讨论点：Java中引入ScopedValue作为ThreadLocal的替代方案的适用性和潜在优势 不同观点： • Pet_Ant认为ScopedValue提供了一种了解变量生命周期的方法，适合处理大量数据，但对于大多数企业级CRUD应用而言可能并不适用。他提到ScopedValue的语法并不吸引人，并猜测这可能是一种"monad"（虽然他自称不是函数式编程专家）。 • skerit对该提案表示感兴趣，认为自己在某些场景下可能会使用ScopedValue。 • djenndhxhd指出，如果不小心处理， tramp参数（方法中为了传递数据而增加的额外参数）会很常见，并表示认同该提案的价值。 补充讨论： • Pet_Ant提到虚拟线程的引入预期会大幅增加运行线程的数量，传统的ThreadLocal在这种情况下可能不适用，因此引入了ScopedValue。 • 争议的焦点可能在于ScopedValue的适用范围及其在不同类型应用中的实际价值，特别是对于企业级CRUD应用的适用性存在分歧。 • 对ScopedValue是否属于monad的讨论表明，部分开发者对新特性在函数式编程中的定位存在疑问。 总体而言，讨论围绕ScopedValue的实际应用价值及其在不同开发场景中的潜在优势和局限性展开。

本文介绍了在FPGA中实现W65C832（W65C816的32位扩展版）的过程。W65C832由Western Design Center（WDC）设计，具有32位指令集，可访问16MB内存。作者更新了naken_asm汇编器以支持W65C832的.l修改器，并通过Verilog在FPGA中实现了该处理器核心。该FPGA包含少量块RAM，用作4k RAM、4k ROM和Winbond W25Q128J闪存芯片的页面。作者提供了Verilog源码，并支持使用开源工具进行构建，如yosys和nextpnr-ice40。此外，还实现了通过UART上传程序的XMODEM引导加载程序，并使用Winbond W25Q128闪存芯片扩展ROM区域。

评论摘要
主要讨论点：围绕6502及其后续版本（如65C816、65C832）的性能、架构设计及其在现代的应用潜力展开讨论。 不同观点： • **JPLeRouzic**：认为65C816（10MHz）不如100MHz的6502有趣，暗示对65C816的性能和速度不满意。 • **thristian**：提出6502的32位后代可以参考ARM架构，指出ARM在初期技术上与6502的联系，并引用了Bill Mensch的言论支持这一观点。 • **homarp**：说明W65C816是6502的16位版本，而32位的W65C832仅以数据表和FPGA版本存在，且可以使用开源FPGA工具进行构建。 • **gblargg**：讨论了65C816的寄存器模式（8位或16位）在实际编码中带来的挑战，分享了在PANCAKE-ROM项目中的经验，并比较了65816与其他常见CPU（如80x86和68000）的寄存器处理方式。 • **mrandish**：表达了对复古核心的喜爱，特别是Apollo FPGA核心如何扩展68000系列并加入现代CPU特性，认为这种扩展能够延续过去的技术并引入现代功能。 • **cmrdporcupine**：认为65C816的24位地址总线和16位寄存器限制了其设计优雅性，提出一个更好的32位65xx架构应该将所有寄存器扩展到32位，并放弃二进制兼容性。 补充讨论： • **kevin1024**：询问是否可以将相关工作移植到IIGS MiSTer核心上，表现出对该技术在其他平台上应用的兴趣。 • **ted_dunning**：关注FPGA版本的时钟频率，显示出对该FPGA实现具体性能参数的关注。 争议焦点： • 65C816的寄存器和地址总线设计是否限制了其性能和优雅性，以及是否需要放弃二进制兼容性来实现更好的32位架构。

文章摘要

Meilisearch 是一个快速、可定制的搜索引擎API，支持AI驱动的混合搜索，适用于各种应用和网站。它提供即开即用的功能，如混合搜索、输入即搜、错别字容忍、过滤与分面搜索、排序、同义词支持、地理搜索、多语言支持、安全管理、多租户支持等。Meilisearch 易于安装和维护，并提供RESTful API和多种SDK以实现无缝集成。此外，Meilisearch Cloud 提供无服务器部署和全球分析监控服务。用户数据会被匿名收集以改进产品，但可以随时停用和请求删除。更多信息和使用指南可在其文档中查看。

评论摘要
主要讨论点：Meilisearch及其他搜索工具在生产环境中的使用体验、功能特性、性能问题以及AI和混合搜索的集成。 不同观点： • **Meilisearch的积极评价**： - [adrianvincent] 认为Meilisearch相较其他替代品非常容易设置，从alpha版本开始就一直在使用。 - [justAnotherHero] 表示Meilisearch与Firebase结合使用多年，效果很好，但指出Firebase扩展未更新导致兼容性问题。 - [Hawxy] 分享了使用Meilisearch的良好体验，但希望有更靠近的地理实例（如澳大利亚）。 • **Meilisearch的生产环境适应性**： - [be_erik] 质疑Meilisearch是否适合生产环境工作负载，尤其是高可用性（HA）需要手动管理多个实例同步。 - [saintfiends] 指出Meilisearch在处理频繁更新的文档时性能较差，任务可能滞后数小时，推荐使用传统RDBMS作为替代方案。 • **混合搜索的挑战**： - [adeptima] 偏好使用Tantivy和Quickwit等工具进行全文搜索，并寻找有效的混合搜索（结合全文与嵌入向量）解决方案。 - [softwaredoug] 强调了混合搜索解决方案中向量索引的过滤操作的重要性，指出该领域缺乏标准化。 - [esafak] 询问了Meilisearch的混合搜索重排序和流式摄取的支持情况。 • **AI与搜索功能的争议**： - [subpixel] 提到在启用AI功能后，搜索结果质量下降，不如传统搜索。 • **其他替代方案的推荐**： - [mentalgear] 推荐了Orama作为一种轻量级、支持全文、向量和混合搜索的替代方案。 - [amazingamazing] 希望搜索工具能支持可插拔后端，以避免频繁同步导致的数据滞后问题。 • **资源消耗问题**： - [k4rli] 提到Meilisearch内存占用较高，类似Elasticsearch，运行时内存消耗较大。 补充讨论： - [bsnnkv] 分享了使用Microsoft Search（MS）在生产中的长期经验，但对新的AI功能缺乏信心，认为旧版本表现良好。 - 讨论中多次提到对混合搜索和AI集成的关注，反映出用户对这些新兴功能的需求和担忧。 - 性能和可扩展性是用户关注的重点，尤其是处理大量数据时的表现（如7百万文档的实时更新）。
