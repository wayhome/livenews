Bringing 3D shoppable products online with generative AI

作者: bookofjoe | 评分: 23 | 评论数: 8 | 发布时间: 2025-05-13 15:58
文章摘要

谷歌实验室的最新AI技术利用生成式AI将2D产品图像转化为沉浸式3D体验。传统在线购物难以复制实体店中的直观感受，而现有的3D可视化工具对企业来说成本高且耗时。为此，谷歌开发了新的生成式AI技术，仅需三张产品图片即可生成高质量的3D产品视图。 初期技术（2022年）使用神经辐射场（NeRF）从五张以上的图片生成360°旋转视图，但存在噪声和视角稀疏的问题。2023年，谷歌引入第二代技术，采用视图条件扩散模型（view-conditioned diffusion model），通过分数蒸馏采样（SDS）优化3D模型，成功解决了视角有限的问题，并实现了鞋类产品的广泛应用。 最新技术（第三代）基于谷歌先进的视频生成模型Veo，能够生成复杂的灯光、材质和几何交互视频，进一步提升了3D视图的质量和真实感，已在谷歌购物中应用于多种产品类别。

评论摘要
主要讨论点：GenAI在电子商务中生成3D模型技术的潜力和问题 不同观点： • [mintplant] 认为该技术有风险，因为生成的3D视图不一定能准确代表实际产品，可能导致问题。 • [dagmx] 批评将此技术应用于电子商务领域的做法，指出大多数产品已有CAD模型，使用传统工具（如mesher和decimation）可以获得更好且无“幻觉”问题的结果。此外，对虚假广告和责任问题表示担忧，认为这是市场营销对研发的误用。 • [Huxley1] 支持该技术，认为它能为没有专业摄影资源的卖家提供帮助，尤其是处理反射和半透明物体方面，可能会是一个重大突破。对小卖家来说可能是一个竞争优势。 • [allears] 以讽刺的语气评论，暗示顶尖人才正在将精力浪费在提升购物体验这样的领域上。 • [ivanjermakov] 质疑是否真的需要用AI来解决3D模型描述格式的问题，认为现有的通用格式已经足够。 • [dm8] 认为该技术是从摄影测量到NeRFs的重大进步，尤其在购物场景中，真实感至关重要，包括光影、纹理和不同环境下的表现。同时对从现有图像/视频中快速创建3D模型的效率表示关注。 • [iamtoomas] 对该技术表示兴趣，但找不到可以试用的链接，表现出对实际应用的渴望。 补充讨论： - 争议焦点在于该技术是否能在电子商务中提供实际帮助，尤其是在生成3D模型的准确性和效率方面。 - 一些评论者（如[dagmx]和[dm8]）关注技术可能带来的问题，如幻觉、责任和真实性。 - 其他评论者（如[Huxley1]）则看好该技术在特定场景（如小卖家）中的应用潜力。 - [ivanjermakov] 和 [allears] 对该技术是否必要和价值提出质疑，尤其是与现有解决方案的对比。

I don't like NumPy

作者: MinimalAction | 评分: 459 | 评论数: 70 | 发布时间: 2025-05-15 16:05
文章摘要

这篇文章讨论了作者对NumPy的一些不满和其使用中的复杂性。虽然NumPy在处理简单数组运算时表现得直观且高效，但当涉及更复杂的多维数组操作时，其语法和操作变得不直观且容易出错。作者指出，NumPy缺乏一种理论来清晰地表达对不同维度数组的操作，导致用户需要使用复杂的维度对齐技巧或难以理解的函数（如`np.tensordot`）。文章还提到，尽管NumPy可以通过一些特殊函数（如JAX或CuPy）调用GPU加速，但正确调用这些函数的语法往往不明确，用户通常需要通过试错来找到可行的解决方案。作者认为这种状况使得编写和阅读NumPy代码变得困难且容易出错。

评论摘要
主要讨论点：NumPy的优缺点及其在多维数组操作中的局限性 不同观点： • WCSTombs认为，NumPy在处理多维数据（尤其是三维及以上）时存在局限，推荐使用Xarray。Xarray通过添加维度命名，简化了广播和数组对齐操作，尽管在某些方面（如线性代数）功能略显单薄，但可以轻松回退到NumPy。 • ChrisRackauckas对比了NumPy和Julia，认为NumPy的API和数据模型在处理多维数据时不够直观，且在性能优化上需要花费过多时间。相比之下，Julia允许更灵活的向量化和循环操作，代码可读性更强。 • brosco指出NumPy在函数参数和操作一致性上的问题，比如有些函数使用轴参数，有些则不，且需要频繁查阅文档，相比Matlab和Julia，NumPy的向量化操作不够直观和一致。 • vector_spaces提到NumPy的类型和返回值存在不一致性，比如`np.poly1d`在不同操作下的行为不同，容易导致调试困难。 • SirHumphrey认为Python数据科学生态系统缺乏标准化，不同库之间需要频繁转换数据格式，而Julia在这方面表现更好。 • blululu认为NumPy在处理高维张量时确实存在问题，但其他专用库（如Torch）可能更好，尽管它们也有自己的困难。 • aborsy认为NumPy的语法相对冗长，不如Matlab或Julia易读。 • dima55推荐使用numpysane等工具来改善NumPy的使用体验。 • a_t48提到NumPy和CuPy在操作时容易产生大量内存分配，需要手动使用就地操作来优化性能。 • wedesoft和hodder则分别从JIT编译和Matlab背景的角度讨论了NumPy的局限性和可能的解决方案。 • munchler从强类型语言背景出发，认为NumPy和PyTorch的API设计过于灵活，难以掌握。 • cycomanic部分同意作者对高维数组操作困难的看法，但认为这可能是因为人类对高维数据的直观理解有限，同时指出NumPy在参数命名一致性上的问题。 补充讨论： • 争议焦点在于NumPy在处理多维数组时的局限性以及与其他语言（如Julia、Matlab）的对比。 • 不同用户对NumPy的语法、一致性、性能优化和类型系统存在不同程度的抱怨和建议。 • 一些用户推荐使用Xarray、numpysane等工具来改善NumPy的不足。 • 对于高级线性代数操作和自定义内核，NumPy被认为不如Julia等语言灵活。

Git: Move files from one repo to another with history (2021)

作者: transpute | 评分: 9 | 评论数: 1 | 发布时间: 2025-05-16 07:23
文章摘要

本文介绍了如何使用Git命令行和`filter-repo`命令将文件及其历史记录从一个代码仓库迁移到另一个。传统方法如`filter-branch`和patching存在复杂性和问题，而`filter-repo`更为高效。首先，需要单独安装`filter-repo`。然后，通过以下步骤完成迁移： 1. **清理源仓库**：使用`filter-repo`命令包含或排除文件和文件夹及其历史。 2. **添加源仓库为目标仓库的远程源**：在目标仓库目录中添加源仓库路径。 3. **获取并合并更改和历史**：从远程源获取更改并合并到目标分支。 4. **清理**：删除远程源和临时分支。 示例命令包括： - 包含文件和文件夹：`git filter-repo --path --path ` - 排除文件和文件夹：`git filter-repo --path --path --invert-paths` - 添加远程源：`git remote add ` - 获取并合并：`git fetch ; git merge --allow-unrelated-histories` - 清理：`git remote rm ; git branch -d ` 这样可以成功将文件及其历史记录迁移到新仓库。

评论摘要
主要讨论点：通过命令行在Git仓库之间传输和应用补丁的不同方法 不同观点： • 第一种观点（precompute提出）：提出了一种相对简单但“不那么干净”的方法，即使用`git format-patch`和`git am`命令。具体步骤是先在源仓库生成补丁文件，然后将该补丁文件应用到目标仓库。这种方法的优点是操作简单，直接将指定数量的提交“堆叠”到目标仓库的HEAD之上。 • 第二种观点（未明确提出，但可能存在的反对意见）：这种“不干净”的方法可能存在风险，特别是在处理复杂项目或涉及多人协作时。直接在HEAD之上堆叠补丁可能导致冲突或历史记录混乱，尤其是在目标仓库有其他未提交的更改或后续提交时。此外，未详细解释的操作步骤可能对新手不够友好，容易引发错误。 补充讨论： - 使用`git format-patch`和`git am`命令的灵活性：这些命令允许用户在不同仓库间传输特定的提交，而不需要通过完整的合并或变基流程。这种方法在处理特定文件或文件夹的变更时尤其有用。 - 命令中涉及的具体参数说明：`-C {source_repo}`用于指定源仓库，`format-patch`用于生成补丁，`-{number of commits}`指定要处理的提交数量，`--stdout`将输出重定向到标准输出，最终通过重定向操作存储在临时文件中。然后，在目标仓库使用`git am`命令应用该补丁。 - 潜在的争议焦点：这种方法的“不干净”之处可能在于其对Git提交历史的直接修改，可能引发冲突或导致历史记录难以追踪。因此，在需要保持提交历史清晰和可追溯的项目中，这种方法可能不是最佳选择。 - 其他方法的提及：讨论中没有明确提及其他方法，但可以推测，如通过`git cherry-pick`或完整的合并/变基流程，可能提供更安全和可控的解决方案，特别是在复杂项目中。

Show HN: Muscle-Mem, a behavior cache for AI agents

作者: edunteman | 评分: 210 | 评论数: 23 | 发布时间: 2025-05-14 19:38
文章摘要

**Muscle Memory (muscle-mem)** 是一个用于 AI 代理的行为缓存工具。它记录代理在执行任务时的工具调用模式，并在遇到相同任务时重放这些轨迹，从而避免重复调用大语言模型（LLM），提高速度、减少变异性并节省成本。Muscle Memory 不是一个新的代理框架，而是可以与任何自定义代理集成。它通过缓存命中（cache-hit）和缓存未命中（cache-miss）机制工作，并使用 "Check" 进行缓存验证，确保工具调用的安全性。开发者可以通过 `@engine.tool` 装饰器记录工具调用，并定义捕获和比较回调函数来验证缓存有效性。项目已开源，并提供了安装和使用指南。
