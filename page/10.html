My Favorite Bugs: Invalid Surrogate Pairs

作者: meysamazad | 评分: 87 | 评论数: 15 | 发布时间: 2026-05-16 12:49
文章摘要

文章讲述作者最喜欢的一个协同编辑器 Bug：在 TipTap/ProseMirror + Yjs 中，插入相邻的特定 emoji 会导致内容停止同步且无报错。原因是某些 emoji 位于 U+FFFF 以上，在 JavaScript UTF-16 中需用代理对表示；底层 CRDT 在错误位置 splice，切断代理对，产生无效字符。文章借此解释 code units、code points、grapheme clusters 的区别，以及 JS 的 `slice()` 如何可能破坏 emoji。

评论摘要
主要讨论点：围绕 Unicode 字符串处理，尤其是 CRDT/编辑器按 code unit、code point 还是 grapheme cluster 切分文本的风险与实践。 不同观点： • 反对按 code unit 操作：认为 CRDT 库在代码单元层处理文本必然出错，可能产生孤立 surrogate、无效 Unicode，JavaScript/Dart 的 substring/slice 都有类似“切半 emoji”问题。 • 对 grapheme cluster 持谨慎态度：有人认为编辑器应按 grapheme 边界切分，避免拆开 emoji；但也有人指出 extended grapheme cluster 随 Unicode 规则变化，并非长期稳定，类比 PostgreSQL 因 collation 变化导致索引损坏。 • code point/scalar 更“技术安全”但不充分：按 Unicode scalar 可避免无效 Unicode，但仍可能产生语义上奇怪的文本；emoji 往往由多个 code point 组成。 • 工具与语言支持差异：有人推荐 Intl.Segmenter、toWellFormed、Swift 的 String、属性测试；也有人提到 Windows 文件名可含无匹配 surrogate、Linux 文件名可含非法 UTF-8，因此出现 WTF-8 保留往返能力。 • 编码假设也会引发 bug：例子包括服务器 LANG 环境变量因 SSH 改变导致 Unicode 输出时好时坏，以及从 Python 移植到 Rust 时改用二进制 regex 反而简化逻辑、避免未知编码问题。 • 有人感叹 Unicode 复杂度过高，甚至提出若字符固定 64 位会更简单；也有人解释历史原因：UCS-2/UTF-16 导致 code unit 与 code point 分裂。 补充讨论：争议焦点在于“字符串 API 是否应默认按 grapheme cluster 操作”。支持者重视用户感知字符完整性，反对者强调稳定性、规范演进和底层语义复杂性。

The sigmoids won't save you

作者: Tomte | 评分: 282 | 评论数: 55 | 发布时间: 2026-05-15 10:51
文章摘要

文章指出，“所有指数增长最终都会变成S曲线”虽正确，但不能据此断言增长会很快放缓。作者用出生率、太阳能和AI能力预测的误判说明：趋势可能在很长时间内仍保持指数型。若不理解机制，应更多依赖林迪法则：已持续越久的过程，往往还会持续更久。

评论摘要
主要讨论点：AI能力/产业增长究竟会持续指数上升，还是进入S型放缓；以及用Lindy法则、sigmoid、趋势线等模型预测AI未来是否可靠。 不同观点： • 不确定性派：认为无论数据或模型多精致，都难以确定AI何时繁荣或崩盘；若能准确预测早已获利巨大。数学模型“有效直到失效”，更应关注逻辑论证、监管、政策和现实后果，而非用sigmoid或Lindy当结论。 • Lindy支持派：主张在不了解趋势极限时，可默认趋势还会持续约已持续时间；可给出粗略置信区间。有人将其用于判断高速成长公司或AI趋势还能持续多久。 • Lindy/趋势线质疑派：指出作者可能因预测AGI很快到来而有立场偏向；趋势不是静态对象，不能简单套Lindy。也有人建议应做贝叶斯拟合并给出置信区间，因为不确定性极高。 • S型/约束派：认为所有指数增长最终都会因限制因素变成sigmoid。例子包括Nvidia数据中心收入三年增15倍但不可能再持续三年；芯片产能、晶圆厂建设、电力、能源和制造链都不是无限可扩张。 • 多重sigmoid派：飞机速度看似长期增长，其实是螺旋桨、喷气、冲压等多代技术接力；AI也类似，GPT-2架构本身已不够，靠多次架构和算法突破叠加。未来是否继续取决于是否出现下一条技术曲线。 • 硬件乐观派：虽然摩尔定律放缓，但当前AI硬件仍低效；模拟矩阵乘、memristor、存算融合等突破可能抬高AI上限。 • 能力衡量怀疑派：认为AI在便利指标上进步，不等于接近真正智能或意识；神经网络只是更好拟合定义好的函数。Wharton图表等“能力Y轴”含义不清，难说新模型真有数倍智能。 • LLM上限派：认为LLM主要是在训练数据内插，需要大量人工数据生产；所谓指数增长或许只是软件复用和库知识释放，未必能超出训练分布。 补充讨论：争议焦点集中在“AI增长曲线的正确模型”“现有基准是否代表真实智能”“供应链/能源是否会成为硬上限”，以及是否会出现新的算法或硬件突破延续增长。

评论摘要
主要讨论点：独立创业者/小团队是否值得、以及能否负担 SOC2/ISO27001 这类安全合规认证。 不同观点： • 反对派认为不该“预期性”去做 SOC2：它更像企业销售里的“门槛”，只有在客户明确以此作为采购条件、且收入足以覆盖成本时才值得做；否则只是耗时耗钱，拿不到也不影响真正会买的人。 • 可行性怀疑派指出，ISO27001/SOC2 依赖职责分离、内审、审批等角色，小团队甚至 solo 很难满足；很多问卷会因“没有员工/流程”直接判 NO，且还会被客户二次审查。 • 实操可行派认为不是绝对不行：只要有真实客户需求、用合规工具/外部审计支持、缩小范围并把流程文档化，个人或小团队也能通过，且可能带来大客户。 • 客户导向派强调，关键不是证书本身，而是“可验证的安全姿态”：很多企业更看重问卷、风险例外、公共安全页、单租户/自托管方案等替代证明。 补充讨论：争议焦点在于“认证是否真能提升销售”以及“小团队能否通过并值得投入”。
