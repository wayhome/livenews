Run TypeScript code without worrying about configuration

作者: nailer | 评分: 92 | 评论数: 21 | 发布时间: 2025-07-17 17:29
文章摘要

**tsx**（TypeScript Execute）是一个Node.js增强工具，用于直接运行TypeScript文件，类似于使用`node`命令运行JavaScript文件。用户可以通过`tsx file.ts`命令执行TypeScript代码，无需配置，且支持Node.js CLI参数和JavaScript文件。它解决了CJS和ESM模块之间导入的问题，并提供监视模式（Watch mode），在文件保存时自动重新运行代码，提高开发效率。 **tsx**简化了TypeScript的执行过程，支持`tsconfig.json`中的路径配置，并整合了esbuild以提升性能。目前项目依赖用户捐赠维持发展，呼吁企业赞助以支持长期维护和改进。

评论摘要
主要讨论点：TypeScript 在 Node.js 环境中的运行方式及其相关工具（如 tsx、Bun）的使用和争议。 不同观点： • jauco 指出，较新的 Node.js 版本可以直接运行 TypeScript，尤其是剥离类型后的版本被认为是稳定的，但不能使用 Node.js 不理解的语法（如 enums）。同时提到正在开发让需要转译的功能也能运行。 • chmod775 对 "tsx" 这一命名表示不满，认为在 TypeScript 生态系统中，"tsx" 代表了两种不同的事物，造成混淆。 • low_tech_punk 补充说，目前实际上有第三种名为 "TSX" 的东西正在兴起，并提供了相关链接。 • kylecordes 提到 TSX 及其他类似工具不支持 TypeScript decorator metadata。对于旧项目，这可能是一个障碍，但对于新项目，使用 TSX 或 Bun 是更好的选择，可以避免使用不兼容的库。 • stevage 表示自己使用 Bun，因其无需处理各种 TS 和 ESM 配置选项，直接运行 TypeScript，且运行良好。 • low_tech_punk 回应 stevage，认为说 Bun 无需配置并不准确，当需要调整配置时，默认设置可能会成为摩擦点，且在打包代码时可能会出现错误。他希望有一个在运行时可用的 tsx，从而无需担心转译器。 • dimgl 高度赞扬 tsx，称其节省了大量时间，并替代了 ESBuild 的变通方案。 • dzonga 对后端使用 TypeScript 的合理性提出质疑，认为 C#、Java、Kotlin、Golang 等语言在后端开发中具有更好的生态和工具支持。 • hu3 研究了 tsx 的工作原理，指出它实际上是 esbuild 的一个包装器，并引用了相关文档支持这一观点。 • __alexs 表示他们长期使用 ts-node 配合 swc，效果很好，不理解为何 tsx 存在。 • postalrat 开玩笑地说 JavaScript 版本可以称为 jsx。 • lacoolj 认为两个帖子的 timing 是故意的。 • fjcero 和 molszanski 简单地表示支持使用 Bun 和 tsx。 • spankalee 询问 tsx 是否只是传递了 --experimental-strip-types 标志给 Node.js。 补充讨论： • 关于 "tsx" 命名的争议，以及不同工具（如 tsx、Bun、ts-node、swc）在运行 TypeScript 时的优劣比较。 • 关于 TypeScript 在后端开发中的合理性及其替代方案的讨论。 • 关于工具默认配置和自定义配置的优缺点，尤其是在打包和运行时可能出现的问题。

Fcrand (Go language): drop-in replacement for crypto/rand, up to 10x faster

作者: sdrapkin | 评分: 10 | 评论数: 3 | 发布时间: 2025-07-18 22:14
文章摘要

fcrand 是一个高性能的 Go 语言库，用于替代标准库中的 "crypto/rand"，能够在保证相同加密安全性的前提下，提供最高可达 10 倍的速度提升。它与 crypto/rand 完全 API 兼容，支持多线程，且无需额外配置。根据基准测试，fcrand 在处理小于 512 字节的数据请求时表现出显著的性能提升，尤其在并发场景下，性能提升更为明显。安装和使用 fcrand 非常简单，只需通过 `go get` 安装并替换导入路径即可。适用于 Go 1.24 及以上版本，并支持 FIPS-140 标准。
