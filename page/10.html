The Frontend Treadmill

作者: Kerrick | 评分: 722 | 评论数: 104 | 发布时间: 2025-03-20 12:25
文章摘要

这篇文章讨论了前端团队频繁重写代码和追逐新框架的问题。作者认为，选择前端框架并不是最重要的技术决策，因为无论选择哪个框架，五年后都会过时。频繁更换工具只会浪费精力，建议团队深入了解当前工具，避免陷入追求新工具的陷阱。对于求职的工程师，作者建议根据自己偏好的框架选择工作，而不是试图让现有团队更换框架，因为这非常耗时且昂贵。 作者进一步指出，前端生态系统目前存在问题，新开发者学习难度大，公司招聘困难。很多学习新技术的开发者忽视了网络基础，导致未来适应变化的能力不足。作者主张回归网络基础技术，认为这不仅能提高工程师的市场价值，也有助于公司降低技术过时的成本。文章最后表达了作者对网络平台的长期信心，认为其具备独特的软件交付能力。

评论摘要
主要讨论点：前端开发中的快速变化和相关问题 不同观点： • **前端开发的快速变化让人沮丧**：[mplanchard] 提到前端开发中工具和技术的快速过时与大量废弃的API，导致开发者需要频繁重写代码。他认为后端开发的变化相对较少，而前端开发则不断拥抱破坏性变化和废弃，这让他感到困扰。 • **核心技术与市场价值**：[localghost3000] 认为，深入理解核心 web 技术会使工程师更具市场价值，但对求职来说，精通 React 仍然是基础。他指出，招聘时往往会模式化地重视某些流行框架（如 React），即使理解核心技术很重要，但缺乏这些流行框架的经验可能会限制工作机会。 • **框架选择的长期有效性**：[jchw] 认为前端框架的变化并没有那么快，React 和 Angular 等框架已经存在并主导市场很长时间。虽然新框架（如 Svelte）正在兴起，但这种变化并不像人们说得那么频繁和剧烈。 • **生态系统的快速变化是普遍问题**：[Illniyar] 指出，前端开发中的快速变化不仅仅是前端特有的问题，而是整个技术生态系统中新技术和工具不断涌现的结果。他提到后端开发中也有类似的现象，例如语言的更替（如从 VB 6 到 Rust）。 • **放弃前端框架的建议**：[antirez] 认为，完全放弃前端框架，采用服务器端渲染和只在必要时使用 JavaScript，可以避免前端框架快速变化带来的问题。这种方法消除了前后端分离的复杂性。 • **新手应关注基础而非框架**：[conorbergin] 建议新手开发者应专注于基础技术（如 MDN 文档），而不是被各种框架的优劣讨论分散注意力。 • **React 的长期有效性**：[ng12] 反驳了关于框架会在5年内过时的观点，指出 React 已经存在了超过十年，并且仍然广泛使用。 • **避免现代前端复杂性**：[grishka] 选择避免现代前端开发的复杂性，仍然使用类似2007年的方法构建网站，尽量减少对第三方依赖的使用。 • **服务器端渲染与现代框架的平衡**：[H1Supreme] 认为，现代前端生态的复杂性确实存在，但通过使用服务器端渲染和只在必要时使用 JavaScript，可以有效减少复杂性。他还提到，管理复杂的 UI 状态在服务器端更为简单。 • **自建框架的挑战**：[AlexMoffat] 指出，不使用流行框架而自己构建解决方案可能导致文档不足、维护困难等问题，而现有的框架已经解决了常见的开发问题。 • **坚持传统技术栈**：[rambambram] 提到自己仍然使用 CHAMP 技术栈（CSS, HTML, Apache, MySQL, PHP），并且对这种选择感到满意，认为避免了现代前端框架的复杂性。 • **对整个 JavaScript 生态的批判**：[zwnow] 认为，当前的 web 开发过度依赖 JavaScript，整个生态系统需要真正的变革，而不是仅仅通过新框架来修补现有问题。 • **转向非 JavaScript 技术栈的解放**：[krainboltgreene] 分享了自己从 JavaScript 生态转向 Elixir 和 Phoenix LiveView 的经历，认为这种转变使他摆脱了前端开发的复杂性，并感到非常满意。 • **JavaScript 依赖的脆弱性**：[pier25] 强调了 JavaScript 生态系统中依赖关系的脆弱性，指出许多依赖项可能随时被放弃，并且每个依赖项都由其维护者自行决定其发展方向。 • **前端代码质量问题**：[only-one1701] 认为，前端生态系统假设每个人都写出了完美的代码，但实际上很多代码质量较差，当框架或库发生重大变化时，这些问题会被放大，导致更多糟糕的代码来修补旧的问题。 补充讨论： - 前端开发中的快速变化和复杂性不仅仅是一个技术问题，还涉及到市场需求、招聘模式、代码质量等多个方面。 - 部分开发者选择坚持传统技术栈或转向非 JavaScript 技术栈，以避免现代前端开发的复杂性。 - 对新手开发者的建议普遍倾向于关注基础技术，而不是被各种流行框架分散注意力。 - JavaScript 生态系统的依赖性和脆弱性是另一个值得注意的问题，影响着整个开发体验。

There's no emotion we ought to think harder about than anger

作者: privong | 评分: 46 | 评论数: 10 | 发布时间: 2025-03-22 20:31
文章摘要

本文探讨了愤怒的本质及其问题，指出愤怒既普遍存在又具有破坏性。作者引用亚里士多德的定义，愤怒是对关心事物遭受不公损害的回应，并包含对报复的期望。然而，报复并不能真正弥补损失，虽然人们常认为惩罚能带来公正，但这种想法并不合理。文章提出，愤怒的人面临三种选择：一是关注自身地位，通过报复提升自己，但这过于自我中心；二是关注原初的伤害，期望通过报复改善情况，但这逻辑上不成立；三是理性地选择第三条路，即放弃报复。文章认为，报复仅在涉及个人地位时有意义，但对真正的伤害问题无济于事。

评论摘要
主要讨论点： anger的本质、功能及其处理方式 不同观点： • jordwest认为，愤怒是人类设置个人界限的生物学本能，长期压抑愤怒是反效果的。通过允许自己表达愤怒并设定界限，能减少对世界的愤怒和有害的爆发。他认为社会教导人们压抑这种本能是不健康的。 • tibbar指出，愤怒并不一定与报复欲望相关，愤怒可以只是一种情绪，甚至可以对自己感到愤怒。同时，过度压抑愤怒也不好，因为这样会让问题重复发生，而无法给出反馈。 • voidhorse认为，愤怒是可以通过环境和经验学习的。在一个接受愤怒的家庭中长大的人可能会形成不正当的愤怒反应模式，因此照顾他人时要注意自己的行为可能对他人产生长期影响。 • 0xbadcafebee认为，愤怒是心灵感知到错误或不如意时的自然反应，本身不是坏事，但关键在于如何处理这种情绪，避免让情绪直接驱动行为。 • conartist6质疑报复作为愤怒表达方式的有效性，并引用“以牙还牙”的博弈论策略来解释愤怒的合理性。 • jkmcf简单提到参加了有关愤怒的哲学和心理学研讨会，未深入发表个人观点。 • wewewedxfgdf认为，愤怒的进化目的是为了操控或控制他人的行为。 • amriksohata引用宗教经典，认为愤怒会导致迷失和智力丧失，最终导致堕落。 • mhertenberger对文章中引用曼德拉作为例子表示反对，认为曼德拉曾是恐怖分子，并对其政治行为提出批评，认为文章对曼德拉的美化是不负责任的。 补充讨论： • 争议焦点之一是愤怒是否与报复相关，以及如何处理愤怒。jordwest和tibbar更倾向于接受愤怒作为一种自然情绪，而conartist6和mhertenberger则对愤怒引发的行为（尤其是报复和暴力）持批判态度。 • 另一个值得注意的点是对愤怒的来源和影响的讨论，voidhorse和wewewedxfgdf强调了环境和学习对愤怒的影响，而amriksohata则从宗教角度警告愤怒的危害。 • mhertenberger的评论引入了对曼德拉历史角色的争议，虽然与主要讨论点不完全相关，但增加了讨论的政治维度。

The Case for Centralizing Authorization

作者: mooreds | 评分: 28 | 评论数: 9 | 发布时间: 2025-03-18 13:20
文章摘要

文章《The Case for Centralizing Authorization》由Omri Gazitt于2025年1月9日发表，讨论了集中授权系统的好处。作者指出，授权是业务应用的关键组成部分，必须高可用、低延迟，并正确评估每个决策以防止权限提升或信息泄露。尽管身份和访问管理（IAM）通常由专门团队集中管理，但授权往往是应用特定的，许多组织选择将授权去中心化。 文章主张集中授权，认为其优势包括标准化能力、降低成本、统一治理与合规。历史表明，从共享数据中心到云平台，集中化趋势逐渐上升。在身份管理方面，组织已通过LDAP、Active Directory、Okta等实现集中IAM。 集中授权允许将授权逻辑从应用代码中分离，使用统一的语言和策略（如“策略即代码”），从而实现统一管理、审计及日志记录。对于企业而言，授权是共享责任，需平衡应用开发者与中心服务团队的需求。 总结：集中授权能提升效率、降低成本并增强安全性，是企业IT发展的合理方向。

评论摘要
主要讨论点：中央认证授权系统（如AAA、SSO、Kerberos）的实施及其优缺点 不同观点： • [neuroelectron] 认为AAA系统在Amazon的实施过程中，虽然增强了安全性，但某些服务无法整合，导致不得不允许其绕过系统。尽管如此，目前为止没有出现问题，暗示这种“忽略”策略在某些场景下是可行的。 • [mixxit] 提到因为使用Google进行身份验证，如果因广告屏蔽被禁，可能会失去所有数字内容，强调了过度依赖单一认证系统（如Google）的风险。 • [Animats] 指出Kerberos协议作为一种已存在数十年的中央授权方案，早已在Windows等系统中内置，质疑为何讨论中未提及Kerberos，暗示现有技术已经能很好地解决中央授权问题。 • [stego-tech] 支持中央授权系统，尤其是对Active Directory、AAD、Entra、IAM、Okta等工具的熟悉，强调了其核心优势如精简、高度可用、紧密集成等，并计划进一步研究。 • [gramx] 认为单点登录（SSO）是安全中的单一故障点，违反了深度防御原则，是给攻击者的一份“礼物”，强调了SSO在安全性上的潜在风险。 • [CaffeineLD50] 描述了在“零信任”环境中的工作体验，指出这种环境带来的延迟和每次连接都需要认证（如使用安全钥匙）的不便，暗示了高度安全环境可能带来的用户体验下降。 补充讨论： • 争议焦点之一是中央授权系统的实际效果和副作用。一些人认为其增强了安全性，而另一些人则担心其带来的单一故障点和操作不便。 • 不同技术（如AAA、Kerberos、SSO）在不同场景下的适用性和局限性也是讨论的要点。 • 实际操作中的体验（如延迟、用户不便）与理论上的安全性之间的平衡是另一个值得注意的讨论点。

Meta, while disagreeing with O'Carroll's claims, has complied with her request.
