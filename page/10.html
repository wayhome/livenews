文章摘要

本文讨论了使用CGI技术处理大量请求的性能测试，特别关注不同编程语言在CGI环境下的表现。作者首先澄清了关于CGI不安全或过时的误解，指出CGI协议本身简单且有效，编写安全的CGI程序与其他HTTP处理代码一样可行。测试在一台60核/240GB内存的虚拟机上进行，使用Vegeta工具和GoHTTP服务器进行负载测试。 测试结果显示，Bash脚本的性能极差，仅达到40请求/秒。Perl表现较好，达到500请求/秒。JavaScript（Node.js）表现超出预期，达到600请求/秒。Python表现最佳，达到700请求/秒。每种语言的CGI程序在测试中均保持100%的成功率。作者强调，基准测试需结合实际环境，测试结果仅供参考。

评论摘要
主要讨论点：CGI（通用网关接口）在现代开发中的使用及其优缺点 不同观点： • neilv 认为，CGI 在遗留系统和简单系统中仍然有价值。遗留系统可能由高效开发者构建，且运行良好，而简单系统（如家庭路由器上的 Web UI）不需要现代 Web 开发中复杂的工具链。他还提到，现代前端框架（如 Svelte）的复杂性和运行时效率可能不如直接使用 CGI/SCGI。 • pkal 分享了自己用 Go 编写 CGI 脚本的经验，认为在访问量很小的情况下，效率不是问题，重要的是使用标准库中的工具（如 HTML 模板）来编写安全代码。他提供了自己的 CGI 示例并邀请他人测试。 • kragen 引用了之前关于 CGI 性能的讨论，提供了不同语言实现 CGI 的性能数据，指出 Rust 和 C 的性能最好，而 Go 的性能相对较低。他还质疑了所使用的 web 服务器是否是性能瓶颈。 • simonw 对 CGI 示例代码表示赞赏，认为这些代码展示了如何用多种语言实现 SQLite 支持的留言板。 • antoineleclair 分享了在 Disco 项目中使用 CGI 支持扩展的经验，认为 CGI 的简单性和灵活性使其适用于让开发者使用任意语言，但不推荐用于大型生产站点。 • 0xbadcafebee 认为，Bash 脚本在嵌入式设备上非常适合用作 CGI，因其体积小且可以调用其他程序处理复杂任务，但需要注意安全性（如使用基本认证）。 • shrubble 提到在企业环境中常见过度配置的 VM 用于低请求量的内部站点，并指出复杂应用服务器和 web 服务器的集成可能导致不必要的开销。 • jchw 不理解为何有人希望回归 CGI，认为尽管 CGI 能达到很高的请求处理量，但现代的 FastCGI 和其他模型更为优越，特别是在安全性和性能方面。他还指出，在现代环境中设置单独的应用服务器比使用 CGI 更合适。 • hedgehog 认为，CGI 在处理低频请求的多个应用时仍然有意义，因为无需在服务器上保留常驻内存的应用进程，且静态文件可以通过 web 服务器直接提供。 • carodgers 提到 Python 3 已移除 CGI 支持，并询问现代的替代方案。 • rokob 对 Rust 和 C 在尾部延迟方面的表现相似表示好奇。 • dengolius 建议使用更快的 Go 第三方库（如 fasthttp）替代 gohttpd。 • exabrial 抱怨现代 JavaScript 前端在低带宽环境下的表现不佳，并表示欢迎 FastCGI 和服务器端渲染，认为大部分任务不需要复杂的 JavaScript。 • oxcabe 建议将 CGI 与 WASI 和 WebAssembly 进行性能对比，以探索新的设计方式。 补充讨论： • CGI 的安全性和性能是讨论的焦点，特别是与 FastCGI 和其他现代技术的比较。 • 不同语言在 CGI 实现中的性能表现引起了关注，特别是 Rust 和 C 的高性能表现。 • 对现代开发中过度复杂的工具链和前端框架的批评，以及对简单解决方案的回归呼吁。 • 实际应用场景中，CGI 仍然在遗留系统和简单系统中具有实用价值，但在大型生产环境中的适用性受到质疑。

Running a Certificate Transparency log

作者: Metalnem | 评分: 153 | 评论数: 21 | 发布时间: 2025-07-07 20:36
文章摘要

文章呼吁拥有多余存储和带宽的组织或工程师考虑运行一个**证书透明度日志（Certificate Transparency Log）**，这对网络安全至关重要。证书透明度机制通过让证书颁发机构（CA）提交证书至第三方日志，确保网站所有者能得知未经授权的证书颁发，提升了网络安全。 运行CT日志过去昂贵且复杂，但通过新的**静态CT API**和**Sunlight**工具，现在变得更简单和便宜。Geomys公司以每年1万美元的成本运行一个受信任的CT日志。 **运行CT日志的要求**包括：一台服务器、ECC内存、2 Gbps出站带宽、3-5 TB存储（SSD或对象存储），以及谷歌要求的两名代表联系人。日志的持久性至关重要，数据一旦写入不能丢失。 运行CT日志需要遵守谷歌和苹果的政策，定期更新，并每年轮换时间分片。社区欢迎新的日志运营者加入，可通过Slack等渠道获取支持。 总之，运行CT日志对网络安全有重大贡献，且现在更易实现。

评论摘要
主要讨论点：证书透明性（Certificate Transparency, CT）日志系统的改进和相关技术方案的讨论。 不同观点： • **agwa** 认为，Sunlight和static-ct-api为CT日志领域带来了新气象。传统的CT日志基于数据库构建，过于复杂且成本高昂（每年花费高达10万美元），导致日志运营困难且鲜有组织愿意运行。Sunlight和static-ct-api正在改变这一现状，令人兴奋。 • **baobun** 提到Mozilla在CRLite上的进展，认为这是一个未被充分关注的改进，提供了对CT系统下游改进的示例。 • **torbid** 质疑为何CT日志服务器要负责存储，建议由日志提交者自己存储数据，服务器仅负责其密钥和增量签名，以简化服务器职责并避免高昂的存储成本。 • **tonymet** 关注证书系统的审计问题，指出消费者和发布者常对证书掉以轻心，导致错误使用。SSL/TLS在防窃听方面表现良好，但在建立信任和身份方面不足，建议进行业余或专业审计。 • **gslin** 对CT日志所需的带宽提出疑问，不确定是否真的需要2-3 Gbps的出站带宽，并提供了存档链接供参考。 • **ncrmro** 建议使用Arweave这样的区块链存储方案，认为这可能是一种有用的存储方式，费用可用于支持存储成本的增长。 • **udev4096** 反对支持中心化的CA，认为DANE（DNS-based Authentication of Named Entities）才是未来，不需要依赖这些CA。 • **cypherpunks01** 询问CT系统如何实现仅追加条目和公开透明的时间记录，并提出是否可以使用区块链技术，或者这是否会导致数据量过大。 补充讨论： • 评论中涉及的技术方案包括Sunlight和static-ct-api的创新、CRLite的进展、区块链存储的建议以及DANE的未来展望。 • 争议的焦点在于CT日志服务器是否应负责存储，以及区块链技术是否适用于CT系统。 • 带宽需求和审计问题也被提出作为需要进一步澄清和探讨的要点。 总体来看，讨论围绕CT日志系统的技术改进、存储和审计问题展开，并涉及未来技术和去中心化方案的潜在应用。

文章摘要

本文讨论了艺术作品中色彩持久性的重要性，即“耐光性”，以及如何选择耐光材料以防止褪色。作者Sarah Renae Clark在过去六个月中对50多个彩铅品牌进行了耐光性测试，将色卡暴露在阳光下并记录变化。文中解释了什么是耐光性、其重要性、测量方法（如蓝羊毛尺度、ASTM D6901标准等），以及作者的测试结果和见解。耐光性对想要作品长久保存的艺术家尤其重要，无论是展示、赠送还是出售。然而，对于仅注重创作过程或数字使用的作品，耐光性则不那么关键。文章旨在帮助艺术家选择合适的材料，以确保作品的持久鲜艳。
