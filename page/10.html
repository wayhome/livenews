We made our filesystem 47× faster by deleting it

作者: appcypher | 评分: 50 | 评论数: 10 | 发布时间: 2026-05-19 18:01
文章摘要

这篇文章讲述了 microsandbox 团队如何将文件系统性能提升 47 倍的过程。 **问题**：用户反馈沙箱内列出 Python 标准库文件需要 5.3 秒，而 Docker 只需毫秒级。原因是每次文件操作都要通过 FUSE 在 VM 和宿主机之间往返，开销巨大。 **解决方案**：放弃用户态文件系统，改用 Linux 磁盘镜像让 VM 直接挂载。采用 EROFS（只读文件系统）构建镜像，用 Rust 自行实现镜像写入器，避免依赖平台特定工具。文件操作现在完全在 VM 内核中完成，无需跨越 VM 边界。 **结果**：几何平均速度提升 47 倍，最差情况提升超 1000 倍，代码减少 5300 行。

评论摘要
主要讨论点：关于 OCI 文件系统性能优化的技术讨论，围绕 FUSE、用户态文件系统和实现方案的选择展开 不同观点： • **FUSE 性能批评派**：认为 FUSE 虽然是好想法但性能很慢，通过 FUSE 在 VM 中进行文件操作必然导致性能问题，如果能避免使用 FUSE 就应该避免（moralestapia, nasretdinov） • **用户态文件系统质疑派**：认为用户态文件系统天然就慢，尤其处理小文件时，这篇文章反而降低了对 microsandbox 项目的信心（andix） • **技术方案改进派**：指出 tar 处理是 OCI 层操作的性能瓶颈，提出将层拆分为元数据+块的更高效格式方案（a_t48） • **实现方式批评派**：认为自己重新实现文件系统（NIH - Not Invented Here）反而让性能变慢了 47 倍（PunchyHamster） 补充讨论： • 标题争议：有人指出标题违反 HN 规范，属于 linkbait，应使用原标题而非编辑化标题（gnabgib） • 实用性询问：有用户询问该软件的实际使用场景和集成方式（cassianoleal） • 可读性问题：网站配色导致阅读困难（jmclnx）

Bun support is now limited and deprecated

文章摘要

yt-dlp 项目宣布限制并弃用对 Bun 运行时的支持。主要原因： 1. **版本限制**：仅支持 Bun 1.2.11 至 1.3.14 版本。低于 1.2.11 存在安全隐患（忽略 ejs 锁文件），高于 1.3.14 的版本使用 Rust 重写且采用 AI 辅助开发，可靠性存疑。 2. **弃用声明**：虽然暂时保留支持，但保留随时完全移除 Bun 支持的权利，若维护成本过高将停止支持。 3. **背景**：Bun 最近用 Claude AI 重写为 Rust 版本，开发方式转向"vibe-coded"（凭感觉编码），团队认为这带来未来维护风险。

评论摘要
主要讨论点：yt-dlp 拒绝接受 Bun 的 Rust 重写版本（通过 AI 辅助完成），引发关于 AI 辅助编程（"vibe coding"）的争议 不同观点： • **支持拒绝方**：100万行代码无法充分审查，维护者需要理解代码库；大量 unsafe 代码存在兼容性和安全隐患；测试套件不足以替代代码审查 • **质疑拒绝方**：这是基于情绪而非工程数据的政治决定；应该根据实际表现（bug、安全漏洞）而非开发方式来评判；类比"因为不喜欢开发者用的编辑器就拒绝软件" • **中立/观望派**：LLM 擅长语言转换，但逐文件转换导致过多 unsafe；应等 Rust 版本发布后根据实际质量决定是否恢复支持；Bun 的做法可能是为了营销炒作 补充讨论： • 术语混乱："vibe coding"被泛化为 LLM 使用的贬义词，但实际上很多开发者用 LLM 提升效率 • Bun 被 Anthropic 收购后的发展方向引发担忧 • 有人认为 Bun 因此"注定失败"，也有人认为如果 Rust 版本表现良好应该重新接纳 争议焦点：是否应该因为使用 AI 辅助开发就拒绝一个项目，还是应该以最终代码质量为准

A blueprint for formal verification of Apple corecrypto

作者: hasheddan | 评分: 116 | 评论数: 5 | 发布时间: 2026-05-22 18:52
文章摘要

苹果安全团队发布了corecrypto库的量子安全加密算法实现及其形式化验证方法。为应对未来量子计算机威胁，他们在iMessage等应用中部署了ML-KEM和ML-DSA算法，并开发了严格的数学证明来确保实现的正确性。corecrypto为25亿台设备提供加密服务，因此苹果对新算法采用极其谨慎的评估标准，包括安全性、性能和正确性。他们公开了算法实现、数学证明以及形式化验证工具，供专家独立评估，以推动关键软件保障技术的发展。

评论摘要
主要讨论点：形式化验证工具在密码学实现中的应用，以及高保障软件开发的挑战 不同观点： • **工具易用性观点**：SAW/Cryptol等形式化验证工具相比其他方法更易用，但C++在高保障领域仍然流行，其安全性和工具支持却不如C语言 • **形式化验证价值观点**：ML-DSA早期的missing-step bug是SAW的完美应用场景——这类罕见输入导致的bug在代码审查中容易被忽略（缺失的代码行看起来像是正确的下一行），常规测试也难以捕获 • **后量子密码进展观点**：Apple在2024年就已部署后量子密码（ML-KEM和ML-DSA），值得肯定。同时赞赏"crypto"一词回归密码学本义，而非加密货币 • **安全优先级批评观点**：虽然验证密码学很重要，但Apple对解析器安全重视不足，选择提供锁定模式而非从根本上修复问题 补充讨论：讨论涉及高保障软件开发的多个层面——从底层语言选择、形式化验证工具应用，到具体密码学实现bug案例，再到厂商安全策略的取舍。争议焦点在于Apple的安全策略是否足够全面。

z386: An Open-Source 80386 Built Around Original Microcode

文章摘要

这篇文章介绍了z386项目——一个基于Intel原始微码在FPGA上重建的386级CPU。z386能运行DOS 6/7和保护模式程序如Doom游戏，性能相当于70MHz的386或低端486。项目使用8K行代码，保留了386的核心架构特征（如32项TLB、微码ROM），同时采用FPGA友好的优化（DSP乘法器、16KB四路组相联缓存）。文章详细说明了CPU的八大功能单元：预取、解码、微码序列器、ALU/移位器、分段、保护、分页和总线接口，展示了如何从z8086项目演进到更复杂的z386实现。

评论摘要
主要讨论点：关于386处理器FPGA实现项目的技术评价和应用场景 不同观点： • **技术局限性观点**（spankibalt）：认为缺少FPU浮点运算单元的FPGA实现限制了生产力和研究用途，只适合游戏等基础应用，类比Ao486也只实现了486SX • **应用可行性观点**（cbdevival）：指出可以运行Linux 3.7内核，提到Gray386linux项目仍在维护，展示了实际应用潜力 • **技术效率观点**（UncleOxidant）：对仅需18K LUTs感到惊讶，认为这在现代FPGA中是相当小的规模，暗示实现效率很高 • **安全研究角度**（mmastrac）：关注微码反汇编是否发现了无需开盖就能读取微码的后门 • **怀旧与实用性讨论**（KellyCriterion）：询问是否还有386在实际生产环境运行，分享了90年代末见过用软盘传输数据的工业设备案例 补充讨论：多条评论提到了相关的"80386微码反汇编"讨论帖，显示社区对386底层技术的持续关注。整体氛围在技术评估、实用性探讨和怀旧情怀之间。

评论摘要
