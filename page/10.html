Rsync replaced with openrsync on macOS Sequoia

作者: zdw | 评分: 558 | 评论数: 47 | 发布时间: 2025-04-06 21:14
文章摘要

在macOS Sequoia中，Apple将长期使用的rsync工具替换为openrsync。这是因为rsync 2.x版本使用GPLv2许可证，而rsync 3.x使用GPLv3许可证，Apple无法完全遵守GPLv3的条款。为避免许可证问题，Apple选择了不受GPL限制的openrsync，其采用更宽松的ISC许可证。这一变化使得Apple可以自由更新openrsync，但需注意openrsync仅支持rsync命令行参数的一个子集，可能影响旧版macOS上某些rsync功能的使用。用户可通过运行`/usr/bin/rsync –version`查看openrsync版本信息。

评论摘要
主要讨论点：围绕 `openrsync` 及其相关工具的可用性、兼容性、许可证问题以及在不同操作系统中的表现展开的讨论。 不同观点： • **adrian_b** 认为 `openrsync` 的文档不完善，无法保证完美复制文件和元数据，因此认为它目前是不可用的。相比之下，`rsync` 能够在不同操作系统和文件系统之间完美复制文件，包括保留扩展文件属性、访问控制列表和高精度时间戳。`adrian_b` 还提到 `scp` 和一些归档工具在默认情况下无法完美复制文件。 • **thrdbndndn** 作为新手 Linux 用户，指出系统工具的不同版本导致的使用混乱问题，例如 `unzip` 在不同发行版中对 AES-256 加密的支持不一致。他质疑是否应该替换系统自带的工具，因为这可能会带来安全隐患。 • **duskwuff** 认为尽管 `openrsync` 缺乏 `rsync` 的一些功能，但多个独立实现有助于将 `rsync` 作为协议而非单一软件来发展，这是一种积极的趋势。 • **watersb** 提到 `rsync` 对扩展属性的支持，特别是对 macOS 元数据的支持，并引用了相关工具和项目，例如 Carbon Copy Cloner 和 Backup Bouncer，强调了对备份保真度的高要求。 • **jeroenhd** 对苹果公司对 GPLv3 许可证的回避态度提出疑问，认为如果静态编译可执行文件，应该可以避免许可证问题。 • **secure** 指出在实现自己的 `rsync` 版本时参考了 `openrsync`，并提到苹果开始转向 `openrsync` 导致其测试环境出现问题。 • **Symbiote** 对一些组织资助 `openrsync` 开发的原因表示疑问，并提供了相关项目的链接。 • **0x0** 描述了在使用 `xcodebuild` 时遇到的问题，因为 `homebrew rsync` 不支持 `openrsync` 的特定命令行参数，导致构建失败。 • **emmelaich** 提到在 Sequoia 15.3 和 15.4 版本之间 `rsync` 实现的变化，并指出 `openrsync` 在支持 `--relative` 参数时存在的问题。 • **abotsis** 对苹果增强和保留 macOS 的 POSIX 特性表示赞赏，认为这是对操作系统的一种积极维护。 • **fmajid** 认为苹果用 zsh 替代 bash 也是出于对 GPL3 的回避，大多数大科技公司都不喜欢 GPL3。 • **tiffanyh** 确认 `openrsync` 是由 OpenBSD 维护的项目，并提供了相关链接。 • **toutiao6** 认为从许可证角度看，使用 `openrsync` 是合理的，但在功能上是一种倒退，可能会导致许多脚本无声地失败，这是苹果为了避免 GPL 而做出的妥协。 • **steeeeeve** 对 macOS 上 `openrsync` 导致的不一致行为表示困惑，认为这会影响用户体验。 补充讨论： • 讨论中涉及的争议焦点包括 `openrsync` 的功能不足、不同系统工具的版本不一致问题、苹果对 GPL3 的回避策略，以及这种策略对用户和开发者的影响。 • 另一个值得注意的讨论点是不同工具在处理文件复制和归档时的保真度问题，尤其是在跨操作系统和文件系统时的表现。 • 一些用户提供了相关工具和资源的链接，如 Backup Bouncer 和 RsyncOSX，这些工具可以帮助验证备份的完整性。 • 讨论中也提到了对系统工具版本管理和替换的担忧，特别是对于新手用户来说，版本不一致和工具替换可能带来安全隐患。

Variable duty cycle square waves with the Web Audio API

作者: iamdan | 评分: 55 | 评论数: 13 | 发布时间: 2025-04-07 16:23
文章摘要

本文介绍了如何使用Web Audio API创建不同占空比的方波，以模拟Gameboy的音效。标准OscillatorNode仅支持50%占空比的方波，而Gameboy有12.5%、25%、50%和75%的选项。为突破这一限制，文章提供了两个方法： 1. **傅里叶级数法**：通过数学计算生成一系列傅里叶系数，利用这些系数创建自定义周期波形，从而实现不同占空比的方波。 2. **WaveShaper节点法**：使用锯齿波，通过WaveShaperNode创建一个阶跃函数，根据占空比将波形转变为方波。 这两种方法都能有效生成可变占空比的方波，满足复古芯片音乐的需求。

评论摘要
主要讨论点：方波合成中的频率生成、占空比选择、混叠效应及其在不同平台（如Gameboy、WebAudio API）中的实现方式 不同观点： • **meindnoch** 认为简单地在 -1 和 1 之间切换会产生严重的混叠效应，并且由于只能在整数采样点切换，无法精确生成与采样率不整除的频率。他还提到正确的做法是通过傅里叶级数或BLIT合成来减少混叠。 • **recursive** 质疑Gameboy硬件为何提供25%和75%占空比，因为这两种占空比在人耳听来是相同的，都是具有相同泛音内容的波形，只是极性相反。 • **SonOfLilit** 强调完美的方波在低采样率下会产生明显的混叠音效，因此推荐使用带限音频合成算法（如blargg的blip_buf）来减少这种问题。 • **dlbucci** 分享了自己在web音频项目中的经验，通过手动创建wav缓冲区来模拟低采样率和低音高分辨率，并解决了WebAudio API调度问题。 • **gmueckl** 建议使用AudioWorkletProcessor来实现自定义方波生成器，认为这是更直接的方法。 • **nayuki** 提供了傅里叶方法合成方波的示例，并展示了带限方波的实现。 补充讨论： • **sapiogenesis** 表达了对Web Audio API的赞赏，认为它为浏览器内实现音频处理提供了基础构件，并期待看到相关项目的成果。 • **chaosprint** 也推荐使用AudioWorklet，并介绍了Glicol项目，提供了结合Rust和Web技术的音频处理示例。 • **jcims** 提供了不同样本在时域和频域的对比图，展示了不同实现方式下的效果。 • **Blackthorn** 担心waveshaper版本会有严重的混叠问题，并询问原版Gameboy声音是否也有这种混叠。 • **geraldog** 提到Waveshaper 50%占空比和傅里叶25%占空比听起来非常相似，质疑这是否是正常现象或代码中的错误。 • **Dave_Rosenthal** 指出音频示例存在问题，选择相同占空比会产生不同的声音，导致无法验证占空比对声音的影响。 • **timewizard** 认为占空比变化类似于PWM（脉宽调制），并建议通过组合不同相位的方波来实现超过50%占空比的效果。 争议焦点： • 主要争议在于方波的占空比选择是否会显著影响声音，特别是在Gameboy硬件和WebAudio实现中，以及如何有效减少混叠效应。

Deleting multiplayer from the Unreal engine can save memory

作者: mariuz | 评分: 147 | 评论数: 11 | 发布时间: 2025-04-06 10:23
文章摘要

这篇文章讨论了在Unreal引擎中移除多人游戏相关功能以节省内存的可行性。尽管Unreal引擎的多人游戏功能集成良好，便于开发，但对于单人游戏项目，这些功能会占用不必要的内存。文章详细分析了即使在单人游戏中，某些变量（如与网络复制相关的数据）仍会占用内存空间，如"bReplicates"变量和一些自定义结构体，分别占用了120和216字节。通过手动移除这些变量，作者成功将每个actor的内存占用减少了328字节。不过，这种优化不易实现，因为Unreal的头文件工具（UHT）不支持通过预处理宏动态排除这些变量。最终，作者通过手动注释相关代码完成了优化，但建议在生产环境中谨慎操作。

评论摘要
主要讨论点：Unreal Engine中的内存和性能优化，特别是关于多玩家模式的取舍以及数据结构的精简对性能的影响。 不同观点： • [mwkaufma] 认为移除多玩家模式以及其他冗余部分（如内置重叠事件）不仅节省了内存，还减少了幽灵读写问题。他们提到精简Aactor和UPrimitiveComponent是ABZÛ项目中做出的有效优化。 • [jofla_net] 支持mwkaufma的观点，并回顾了20多年前Unreal引擎的早期版本，指出当时代码较为混乱，包含许多与多玩家模式相关的额外处理，但认为那段经历是美好的。 • [dleslie] 指出从Unreal Engine首次发布以来，这种优化模式就存在，并提到这种方法帮助他们将游戏压缩到PS2和Xbox上运行。 • [bengarney] 强调在100k actor的情况下，减少3-4个纹理可以更有效地节省内存，暗示纹理优化可能比actor精简更有效。 • [joegibbs] 建议避免拥有过多的actor，因为它们会消耗大量资源。推荐使用实例化或创建处理UObjects的actor来管理大量对象。 • [out-of-ideas] 提到了一个与主讨论无关的技术问题，涉及页面加载时无休止地加载请求，通过阻止特定URL提高了页面加载速度。 • [thenthenthen] 提出了一个无关的技术问题，询问如何在Stalker 2中实现A-life。 • [spockz] 关心除了内存节省外的性能提升，特别是更多actor能否适应缓存行，从而提升缓存一致性和性能。 • [shadowgovt] 赞同优化数据结构对缓存一致性的好处，但警告如果后期决定添加多玩家模式会非常困难，因为多玩家模式引入了复杂的同步和预测机制，建议从一开始就考虑多玩家模式的设计，但同时承认并非所有游戏都需要多玩家模式。 • [keyle] 质疑这种优化是否会对生产构建产生影响。 • [Fokamul] 批评大公司不重视这种优化，认为他们会依赖玩家购买新硬件，而不愿意雇佣核心引擎开发人员进行优化。 补充讨论： • 争议的焦点在于是否应该从一开始就考虑多玩家模式的设计，以及内存和性能优化的实际效果和必要性。 • 讨论中还涉及了具体的优化策略，如纹理减少和actor实例化，以及这些策略对性能的影响。 • 部分评论提到了历史背景和个人经验，增加了对优化过程的理解和反思。

The Mathematics of Crochet

作者: edward | 评分: 120 | 评论数: 7 | 发布时间: 2025-04-04 17:47
文章摘要
