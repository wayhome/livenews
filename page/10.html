Coding Neon Kernels for the Cortex-A53

文章摘要

本文介绍了作者在FOSDEM会议上展示的用于高性能软件定义无线电（SDR）运行时环境qsdr的工作进展，特别是针对Kria KV260板上ARM Cortex-A53处理器的NEON汇编内核实现。作者解释了如何手写汇编实现一个计算核\(y[n] = ax[n] + b\)，并详细讨论了优化该内核的技巧。由于Cortex-A53的指令时序文档不公开，作者通过微基准测试 reverse-engineer 其指令时序。Cortex-A53是一个按序执行且部分双发射的CPU，这意味着优化代码的手动调整可能带来显著性能提升。作者还讨论了NEON寄存器和指令的并行执行特性，如128位NEON操作会占用两个NEON单元，而64位操作可以并行执行。此外，作者指出CPU与L1缓存之间的加载和存储路径宽度不同，加载为64位，存储为128位。这些细节对优化汇编代码至关重要。

作者: prng2021 | 评分: 7 | 评论数: 1 | 发布时间: 2025-04-22 03:23
文章摘要

Microsoft is reintroducing the Recall feature to Windows 11, initially limited to Copilot+ PCs, which constitute a small fraction of Windows 11 systems. Recall had previously faced controversy due to privacy and security concerns, as it created an extensive database of text and screenshots recording user activity. The original version was criticized for being enabled by default, having significant security flaws, and lacking protection for sensitive data. In response, Microsoft has revamped Recall's security architecture. It is now turned off by default, requires Windows Hello reauthentication, and encrypts data at rest. Sensitive information is automatically filtered, and users must explicitly opt in twice to enable the feature. Additionally, Recall will not function if Windows Hello or drive encryption is not enabled. The feature captures screenshots and uses OCR to create a searchable text database, but only from the active window and display. Despite these changes, Recall remains limited to newer PCs with specific NPUs, meaning most current Windows users won't be affected.

"training-hot-swap" 是一个用于 PyTorch 训练代码热替换的工具，允许开发者修改代码而无需将大型语言模型（LLM）从显存（VRAM）中卸载。对于大模型，加载过程可能耗时超过30秒，频繁重载会影响开发效率。该工具通过创建一个后台进程，在脚本退出后保持模型在显存中，并在需要时后台重载模型，确保下次运行时模型立即可用。利用 Python 的 eval() 函数执行代码，还支持通过 VPN 远程执行代码，兼容 IntelliJ 调试器。此外，工具提供了与 DearImgui 绑定的图形界面示例，用于监控训练进度和损失。使用时需注意安全，避免直接暴露服务器以防任意代码执行风险。

Better Error Handling

作者: zdgeier | 评分: 64 | 评论数: 20 | 发布时间: 2025-04-20 20:13
文章摘要

文章讨论了错误处理不当所带来的严重后果，如经济损失、空难、人员伤亡等，强调了错误处理在软件安全和可靠性方面的重要性。特别是在TypeScript和JavaScript中，传统的try/catch错误处理方法在简单场景下有效，但在复杂应用中面临挑战，如无法对错误进行类型检查、难以处理限流错误和聚合多个API调用错误等。文章还提到JavaScript允许抛出任何类型的错误，导致类型安全问题。最后，文章指出良好的堆栈跟踪能在一定程度上缓解错误跟踪问题，但传统方法仍存在局限性，需寻找更优的错误处理方案。

评论摘要
主要讨论点：错误处理的最佳实践和不同编程语言中的错误处理机制 不同观点： • jackjeff：认为在每行代码后检查错误（如Go语言）是一种糟糕的做法，容易导致开发者忽视错误检查，从而产生难以调试的问题。相比之下，异常机制更为直观，虽然Monad等模式有其优势，但在JavaScript中使用会带来不必要的复杂性。同时，对重试机制持谨慎态度，认为重试可能引发其他问题。 • geocar：反驳认为即使在Rust等静态类型语言中也无法检查和处理所有错误，例如磁盘满错误是无法预见的。主张在多任务环境下通过用户干预解决此类问题，而不是完全依赖代码处理。 • zeroq：通过实际经验说明在已有代码库中引入错误处理和日志记录可能导致代码复杂化，即使从整洁的实现开始，最终也可能变得混乱。 • ivanjermakov：认为将错误作为值处理的方法有其局限性，尤其在函数签名需要更改时，会导致调用链上的每个调用者都需要更新。适合在程序需求明确且正确性优先于原型速度的情况下使用。 • medhir：质疑为何不直接使用.then().catch()处理异步调用中的错误，认为这比引入新模式更符合Go语言的做法。 • RadiozRadioz：指出JavaScript的错误处理本身较差，认为原生支持的类型检查和检查异常能解决许多问题。 • whatsakandr：希望C++默认是`nothrow`，并通过经验说明对不太可能失败的操作使用异常，对更可能失败的操作使用optional。 • kikimora：介绍Common Lisp中的重试机制，并希望现代语言也能引入类似功能。 • pmontra：介绍Erlang/Elixir的错误处理方法，包括返回包含ok或fail值的元组和模式匹配，并指出这些方法在其他语言中可能不适用。 • Animats：强调错误需要有用的分类，以便在捕获错误后知道如何处理，并批评Rust在这方面不够完善。 • eximius：希望语言在错误处理上更加标准化，包括堆栈跟踪、错误包装和多错误组合。 • Lord_Zero：指出“结果模式”在C#中早已存在，并非新概念。 • ChrisMarshallNY：认为最好的错误处理是尽量避免错误发生，通过良好的用户体验设计减少错误率，并在错误发生时以简明和同理的方式报告。 • havkom：主张在合适的代码层次处理特定类型的错误，避免在不合适的层次处理错误以减少代码复杂性和数据不一致问题。 补充讨论： • 对重试机制的争议：jackjeff和pmontra对重试机制持谨慎态度，认为可能导致其他问题，而kikimora则希望引入类似Common Lisp的重试机制。 • 对JavaScript错误处理的普遍批评：多位评论者（如RadiozRadioz和jackjeff）指出JavaScript在错误处理方面的不足。 • 对错误分类和处理方法的讨论：Animats和geocar强调了错误分类和处理策略的重要性，并提供了实际例子。 通过这些观点，可以看到不同语言和开发者在错误处理上的偏好和实践各有不同，主要争议点在于是否应在每行代码后检查错误、如何有效地处理和分类错误以及如何在语言层面支持这些机制。
