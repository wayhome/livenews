Use your Nvidia GPU's VRAM as swap space on Linux

作者: tanelpoder | 评分: 459 | 评论数: 42 | 发布时间: 2026-06-02 22:55
文章摘要

**nbd-vram 项目概要：** 这是一个让 NVIDIA GPU 显存作为 Linux 交换空间的工具，专为混合显卡笔记本设计。在集成显卡负责显示、独显闲置时，将其显存用作高优先级 swap。 **工作原理：** 守护进程通过 CUDA API 分配显存，用 NBD 协议将其作为块设备暴露给内核，再挂载为 swap 分区。数据通过 PCIe 在内存和显存间传输。 **优势：** 无需编写内核模块，不依赖 NVIDIA 内核符号，兼容所有 CUDA GPU（包括消费级显卡）。绕过了 P2P API 的 Quadro 限制。 **实测效果：** 8GB 显存分配 7GB 作 swap，配合 zram 和 SSD，总可用内存从 16GB 扩展至 46GB。

评论摘要
主要讨论点：将GPU显存(VRAM)用作系统交换空间的可行性和实际效果 不同观点： • **支持者观点**：适合笔记本等无法升级内存的场景，能让闲置的显存发挥作用。特别是对于拥有大显存但日常开发不跑AI模型的用户(如32GB VRAM大部分时间闲置)，这是个不错的想法 • **性能质疑者**：实测性能令人失望。RTX 3070的1.3 GB/s顺序读写速度远低于理论值(PCIe 4.0 x16应有64GB/s，GDDR6本身448GB/s)，甚至不如直接用NVMe SSD做交换空间快两倍。实际使用体验"完全就像传统的交换分区"，并非"90%性能损失换更多内存"的理想方案 • **技术实现讨论**：已有多个类似实现(MTD/phram驱动、OpenCL方案、Windows的GpuRamDrive等)。有人质疑当前实现层次过多导致性能低下，建议使用自定义块设备驱动 • **稳定性担忧**：Wayland环境下显存分配更动态，显存不足可能导致整个桌面崩溃。需要考虑显存分配的反压机制 补充讨论：有人提出应将此功能内置到内核中作为资源管理的一部分；另有观点认为现代系统很少使用交换空间(除了休眠功能)；GPU数据库应用场景的探讨

Stop Ruining It

作者: herbertl | 评分: 304 | 评论数: 28 | 发布时间: 2026-06-02 09:52
文章摘要

这篇文章探讨了"不破坏"的理念。作者引用音响制造商Paul McGowan的观点：音乐性不是添加到放大器的功能，而是不破坏它后剩下的东西。文章将此理念扩展到多个领域：客户满意度不是项目添加的特性，而是不破坏后的结果；好奇心不是教育的产物，而是教育系统未破坏时保留的天性；工作满足感不是老板创造的，而是老板未破坏时存在的状态；品牌信任不是广告建立的，而是营销者未破坏时自然形成的。核心观点是：许多美好品质本就存在，关键是避免破坏它们。

评论摘要

Open Repair Data Standard

文章摘要

开放维修数据标准(ORDS)旨在规范小型电器和电子产品维修数据的收集与共享方式,便于汇总来自全球各地社区维修活动的数据,识别设备故障和维修的趋势模式。 该标准聚焦三大信息模块:产品相关(类别、品牌、制造年份)、维修相关(问题、维修状态、维修障碍)和活动相关(标识、组织、日期)。目前最新版本为v0.3(2021年12月发布)。 数据采用知识共享许可开放共享,开放维修联盟每六个月发布一次汇总数据集。标准持续演进中,未来将探讨故障类型定义和产品分类体系等议题。

评论摘要
主要讨论点：对一个维修/产品数据标准的实用性、信息完整度以及项目维护状态的讨论。 不同观点： • 质疑实用性：`[1970-01-01]`认为现有数据对普通用户和维修人员都“几乎没用”，因为真正需要的是服务手册、零件及规格、完整拆装/维修流程、所需工具清单；还举例说，甚至从 YouTube 维修视频评论里挖信息都可能更有价值。 • 补充信息来源：`[cassepipe]`没有直接反驳批评，但回应说正式规格其实在 Open Repair 标准页面上，说明部分信息可能不在当前帖子里，而在外部文档中。 • 认为字段不完整：`[memco]`关注的是数据结构层面，觉得产品相关信息过于单薄，连“model（型号）”这样的基础字段都缺失，说明标准或展示内容不够完善。 • 质疑项目活跃度：`[kensai]`把焦点转向维护情况，认为自 2024 年后几乎没有重大更新，因此怀疑项目是否已停滞或被放弃。 补充讨论：争议焦点主要有两点，一是这个标准/数据到底能否真正支持维修实践，二是即便有规范链接，当前呈现出的产品信息是否过少、项目是否仍在持续维护。

微软发布编程模型 MAI-Code-1-Flash，主打在 GitHub Copilot 和 VS Code 中提供更快、更省 token 的日常开发辅助。该模型基于微软自建合规数据训练，强调真实开发环境、指令跟随和代理式编码能力；在多项编程基准上整体优于 Claude Haiku 4.5，并已向 Copilot 个人用户逐步推出。

评论摘要
主要讨论点：微软 `MAI-Code-1-Flash` 的实际编码能力、对标方式、定价与产品落地是否匹配其宣传。 不同观点： • 质疑模型实力与宣传不符：`camelmel`、`capten`、`eterevsky`认为137B总参数却只比更小模型略强，SWE-bench Pro成绩偏低，却被包装得很“革命性”；尤其只对标较弱且过时的 Claude Haiku，而不对比 Sonnet、Opus 或同价位模型，说明基准选择有避重就轻之嫌。 • 关注价格与性价比：`bel8`、`Hfuffzehn`、`deckar01`把讨论延伸到 Copilot 和 API 计费，认为即便价格表面接近 Haiku，也缺少与同价位如 GPT-5.4 mini 的对比；Copilot 新配额机制和自动选模型还会“悄悄烧光额度”。 • 认为小模型有竞争价值但适用性存疑：`bel8`欢迎竞争，但认为小云模型不适合严肃编码；`hmokiguess`进一步追问，小模型是否只适合把大模型做完规划后的结构化任务分发。 • 讨论产品定位偏差：`capten`、`mentos`认为若编码能力有限，不如明确卖点为数学代理或系统设计；他们质疑“写代码”可能已接近解决，真正缺的是高质量系统设计能力。 • 批评产品发布与工程质量：`motoboi`指出微软自家模型发布后竟不能立刻在 Foundry/API 使用；`efields`、`cwillu`则批评官网滚动效果和 Safari 兼容性差，影响观感。 补充讨论：`AntiRush`补充了官方博客、模型卡和“5B active”来源；`tosh`注意到模型似乎并非 open weight；`OsrsNeedsf2P`则质疑是否在 SWE-bench Pro eval 集上训练，触及评测可信度这一争议焦点。
