Denial of service and source code exposure in React Server Components

作者: sangeeth96 | 评分: 335 | 评论数: 39 | 发布时间: 2025-12-11 20:46
文章摘要

React团队披露了React Server Components组件中两个新漏洞：可导致服务器瘫痪的高危拒绝服务漏洞（CVE-2025-55184和CVE-2025-67779，CVSS 7.5分）和可能泄露源代码的中危漏洞（CVE-2025-55183，CVSS 5.3分）。受影响的版本包括19.0.0至19.2.2，建议立即升级至19.0.3、19.1.4或19.2.3修复版本。即使已安装上周的补丁仍需更新，因为之前的修复不完整。该漏洞影响Next.js等多个框架，但纯客户端应用不受影响。团队建议开发者不要依赖主机商的临时缓解措施，而应立即更新。

评论摘要
主要讨论点：React Server Components（RSC）的安全性、复杂性和实用性 不同观点： • **RSC过于复杂且存在安全隐患** - Simonw：RSC模糊了客户端和服务器端代码的界限，需要深序列化RPC机制，容易引入安全漏洞。 - WatchDog：RSC和Next.js的复杂性高，文档不足，且依赖项管理混乱，安全风险可能持续增加。 - Tagraves：对CVE的披露方式表示担忧，认为应先明确漏洞范围和缓解措施。 - Dzonga：RSC增加了不必要的复杂性，大多数应用无需SPA，传统服务端渲染更安全。 • **RSC是错误的设计方向** - Chuckadams：SPA的初衷是减少与服务器的复杂交互，只需获取原始数据。 - Delifue：RSC是前端“吞噬”后端的尝试，而HTMX是后端“吞噬”前端，但后者更安全。 - _Heimdall：RSC解决了本不该存在的问题，希望其热度消退。 - Kpozin：框架模糊客户端和服务器代码界限会导致混淆，Next.js中常见此问题。 • **历史与替代方案** - Hbbio：回顾Opa的经验，认为自动代码分割（类似RSC）可能过早，静态分析和明确分离更优。 - Hollowturtle：建议React保持轻量，将复杂功能交给框架，回归MVC中的“视图”角色。 - Nathants：主张前后端分离，通过JSON交换数据，结合现代工具（如Claude）减少摩擦。 • **个人争议与行业反应** - Dizlexic：提及与Dan Abramov的争论，认为RSC是“自掘坟墓”。 - Sangeeth96：指出Next.js团队已发布安全更新，影响多个版本。 - Bflesch：调侃新漏洞可能导致Cloudflare服务中断。 补充讨论： - **争议焦点**：RSC是否值得为性能优化牺牲安全性和简洁性。 - **替代方案**：HTMX、传统服务端渲染或明确分离前后端（如JSON API）被多次提及。 - **行业趋势**：部分开发者认为LLM和现代工具可能改变全栈开发模式，减少对RSC类技术的依赖。

The Cost of a Closure in C

作者: ingve | 评分: 199 | 评论数: 20 | 发布时间: 2025-12-11 07:21
文章摘要

本文主要讨论了C和C++中闭包（closures）的性能问题及其设计缺陷，以及如何解决这些问题。闭包是一种编程语言构造，它包含了与输入参数和返回值无关的数据和指令。文章首先解释了闭包的概念，并指出几乎所有现代编程语言都支持闭包，但C和C++由于其“底层”特性，闭包的设计并不理想。 文章通过一个具体的例子（使用`qsort`函数时如何传递额外数据）展示了闭包在C语言中的常见问题，如静态变量的共享和线程安全问题。针对这些问题，文章列举了四种主要的解决方案： 1. 重新实现函数以接受用户数据指针（如`qsort_r`或`qsort_s`）。 2. 使用GNU嵌套函数直接引用所需数据。 3. 使用Apple Blocks直接引用所需数据。 4. 使用C++ Lambda表达式和一些额外代码来引用所需数据。 每种解决方案都有其优缺点，文章简要介绍了它们的实现方式，并指出了设计上的局限性。

评论摘要
主要讨论点：[GCC嵌套函数、Lambda性能、可执行堆栈与安全性、C与C++中函数指针和闭包实现的差异] 不同观点： • **GCC嵌套函数与可执行堆栈** - [kazinator]认为GCC的`-ftrampoline-impl=heap`可能更多是为了移除可执行堆栈的需求而非性能优化，因为现代Linux发行版默认禁用可执行堆栈以提升安全性。堆分配蹦床（trampoline）需解决释放问题。 - [zzo38computer]提出通过`static`和`register`关键字实现无需蹦床的嵌套函数，但承认其局限性。 • **Lambda与性能** - [Rochus]指出C++ Lambda通过编译时静态链接优化性能，而GCC的性能问题部分源于OS/CPU管理可执行堆栈的开销。`std::function`因值拷贝语义导致递归性能问题，`std::function_ref`则避免了这一点。 - [mgaunard]质疑测试方法，认为所有Lambda选项（除分配外）性能应等价，关键在于内联和去虚拟化。 • **C与C++的闭包实现** - [sirwhinesalot]支持类似C++引用捕获的本地函数，认为其直接调用和类型擦除的“胖指针”版本最适合C。 - [dfawcus]展示了一种纯C实现的嵌套函数方案，避免堆栈蹦床，但未验证性能。 - [uecker]批评Lambda设计不适合C，并引用其文档说明。 补充讨论： • **争议焦点** - [unwind]对文中关于`static`变量持久性的描述提出质疑，认为全局作用域的`static`与持久性无关。 - [Progge]对代码中复杂的参数解析提出疑问，认为简化写法更合理。 • **其他方案** - [RossBencina]提出“stateful”函数概念，类似`static`但支持多实例状态。 - [groundzeros2015]建议使用线程局部存储解决回调上下文问题。 - [hyperbolablabla]和[nesarkvechnep]讨论C++中自定义函数抽象和Lambda的实用性。 • **实践偏好** - [ddtaylor]表示喜欢GNU的蹦床函数扩展，并在实际中使用。
