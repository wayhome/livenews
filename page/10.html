Client-side load balancing at a million requests per second

作者: cjbooms | 评分: 47 | 评论数: 4 | 发布时间: 2026-07-01 11:35
文章摘要

Zalando的高流量产品API最初通过共享的Skipper负载均衡器处理所有流量。问题在于批处理请求会扇出100个并发调用，每个都经过Skipper，导致延迟累积且无法准确定位问题根源。 团队的解决方案是为内部高扇出流量实现客户端负载均衡（CSLB），让路由决策在调用进程内部完成。核心挑战是必须复制Skipper的一致性哈希环算法（xxHash64 + 虚拟节点），确保两者对相同产品ID的路由决策完全一致，避免缓存分裂和数据库负载翻倍。 边缘流量继续使用Skipper，只有内部扇出流量迁移到客户端负载均衡。通过单元测试和生产验证确保哈希一致性，迁移过程中缓存命中率保持稳定。这让团队获得了路由决策的完全控制权和详细日志。

评论摘要
主要讨论点：在构建客户端负载均衡方案时的架构选择和发布策略设计 不同观点： • **复用现有组件 vs 独立开发**：有评论者质疑为何将内部开发的Skipper视为第三方依赖，建议尝试为Skipper贡献改进并复用其服务发现机制，而不是完全独立开发新的负载均衡模块。虽然承认大公司跨团队协作困难，但认为值得尝试。 • **渐进式发布策略的设计**：针对文章提到的市场组发布顺序（test -> eu-0 -> eu-1 -> eu-2），有评论者质疑这些分组的划分依据——是地理位置、随机分配还是基于用户价值。担心固定分组会导致某些用户持续遭遇更多问题，建议采用每次变化的随机子集策略。 补充讨论：作者介绍了文章涵盖的高级分布式计算主题，包括在JVM客户端复制相同哈希环、渐进式Pod启动以预热缓存、以及通过可用区感知路由降低AWS跨区传输费用等技术实现细节。

JEP 539: Strict Field Initialization in the JVM moved to preview

作者: za3faran | 评分: 55 | 评论数: 5 | 发布时间: 2026-07-02 18:56
文章摘要

JEP 539 在 JVM 中引入严格初始化字段（预览功能）。这些字段必须在读取前完成初始化，避免观察到默认值（如 0 或 null）。对于 final 的严格初始化字段，保证始终读取到相同的值。 该提案旨在解决当前字段初始化机制的问题：默认值可能被误读为合法数据（导致 NullPointerException），以及 final 字段在初始化期间可能被读取到不一致的值。文章通过一个循环依赖的实例展示了这类 bug 的危害。 这为 JVM 语言设计者提供了更强的完整性保证选项，但不改变 Java 语言本身或 javac 编译策略。

评论摘要
主要讨论点：Java某项涉及final字段的新特性变更及其影响 不同观点： • **积极支持派**：认为这是急需的改变，短期阵痛可以接受，长远来看是正确的方向 • **谨慎乐观派**：肯定变更的价值，但担心实际影响——许多序列化/编组库依赖修改final字段的技巧，会导致大规模的库版本升级需求。有开发者承认自己也在代码中使用过类似技巧来弥补库的不足 • **功能关联派**：指出这项变更是为未来的null-restricted类型功能做铺垫，是更大技术路线的一部分 • **质疑派**：对Oracle的意图提出疑问——如果某个特性明确标注"不能从Java使用"，是否意味着Oracle在规划新的JVM语言？这种设计在历史上罕见 补充讨论：核心争议在于技术债务的处理方式——是否应该打破现有的"hack"做法来实现更清晰的语义，即使这会带来生态系统的短期混乱。

文章摘要

macvdmtool 是 AsahiLinux 项目开发的工具，用于简化 Apple Silicon 或带 T2 芯片的 Mac（2018年后）进入 DFU 模式的操作，无需复杂的键盘组合。 **使用条件**：需要两台 Mac，主机必须是 Apple Silicon。 **主要步骤**： 1. 在主机上安装 Xcode 命令行工具和 Apple Configurator 2 2. 克隆并编译 macvdmtool，复制到系统路径 3. 用支持数据传输的 USB-C/TB 线连接两台 Mac 的 DFU 端口（Apple Silicon 在左侧靠近屏幕处，Intel 在左侧靠近触控板处） 4. 执行 `sudo macvdmtool dfu` 命令让目标 Mac 进入 DFU 模式 5. 使用 cfgutil 或 Apple Configurator 2 配合 IPSW 固件恢复系统 这大大简化了 Mac 的 DFU 恢复流程。

评论摘要
主要讨论点：关于Apple设备DFU工具的使用体验和技术细节 不同观点： • **DFU端口位置争议**：有人指出Apple Silicon机器的DFU端口并非总是在左侧靠近屏幕的位置，并提供Apple官方支持文档作为证据，说明实际情况因机型而异 • **工具易用性肯定**：用户认为这个工具极大改善了用户体验，相比传统需要按特定时序组合按键的方式（形容为"召唤Apple精灵"），新工具更直观易用 • **网站界面问题**：有用户反馈bkurtz.io网站在light模式下存在可读性问题——背景模糊不够、白色字体在浅色背景上难以辨认、字体过小过细 • **平台兼容性限制**：Intel Mac不支持此工具，技术原因在于Intel Mac采用接近标准PC的UEFI架构，而Apple Silicon本质上是iPhone/iPad架构，两者底层技术不同 补充讨论：评论整体呈现三个层面：技术准确性纠正、用户体验改进认可、以及架构差异导致的功能限制。其中Intel与Apple Silicon的架构差异是功能支持的根本原因。

文章摘要

FBI联合业界合作伙伴查封了以色列上市公司Alarum Technologies旗下住宅代理服务NetNut的数百个域名。多家安全公司发现NetNut与Popa僵尸网络关联,该僵尸网络感染了至少200万台智能电视和流媒体盒子等家用设备,将其转变为代理节点,用于中继恶意流量、内容抓取、广告欺诈和账户接管攻击。 Google威胁情报组在一周内观察到316个不同的威胁组织使用NetNut出口节点,包括网络犯罪和间谍组织。Google已禁用NetNut用于恶意软件控制的账户和服务。 专家认为此次行动将对网络犯罪社区产生重大影响,因为NetNut在其竞争对手IPIDEA被打击后获得了大量市场份额,并可能减少大规模DDoS僵尸网络的威胁。

评论摘要
主要讨论点：FBI查封以色列公司NetNut住宅代理服务的执法行动及其影响 不同观点： • **设备被劫持问题**：大量智能电视和流媒体盒子预装代理软件，LG webOS平台42%的应用、Samsung Tizen平台超过25%的应用包含住宅代理SDK组件，用户设备在不知情下成为代理节点 • **执法有效性质疑**：FBI查封了错误域名（netnut.com而非实际运营的netnut.io），后端基础设施可能仍在运行，执法行动效果存疑 • **合法性争议**：有评论质疑住宅代理本身是否违法，以及为何FBI介入看似民事性质的行动 • **地缘政治考量**：有观点认为干扰以色列上市公司会引发外交问题，暗示此举可能影响情报合作，FBI"没收到备忘录" • **互联网隐私担忧**：从更宏观角度担心此类行动会减少匿名访问选项，配合Google等公司对网络爬虫的限制，整体上损害互联网隐私和自由 补充讨论：评论间存在明显分歧——技术派关注实施细节和有效性，而另一派则从情报合作和网络自由角度提出更深层担忧。
