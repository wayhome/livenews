Developing with GitHub Copilot Agent Mode and MCP

文章摘要

本文介绍了作者如何通过GitHub Copilot的Agent Mode与Model Context Protocol (MCP) 协议结合，极大提升了开发效率。作者详细描述了如何在VS Code中自定义Copilot，包括设置自定义指令、提示和聊天模式，从而为不同开发阶段创建专属的AI助手。作者还分享了其VS Code的详细设置，启用了多个实验性功能以减少手动干预。通过MCP，作者让Copilot可以访问外部工具和数据源，如Sequential Thinking、SearXNG和Playwright，进一步增强了AI助手的功能。这些设置使代码生成、测试创建和问题解决更加自动化和高效。

Nano-engineered thermoelectrics enable scalable, compressor-free cooling

作者: mcswell | 评分: 119 | 评论数: 15 | 发布时间: 2025-06-30 14:51
文章摘要

研究人员在约翰霍普金斯应用物理实验室（APL）开发了一种基于纳米工程材料的新型固态热电制冷技术，其效率是商用块体热电材料设备的两倍。这种名为CHESS（控制分层超晶格结构）的技术为更高效、紧凑和环保的制冷解决方案提供了可扩展的替代方案。CHESS材料通过金属有机化学气相沉积（MOCVD）方法制造，具有良好的可扩展性和成本效益。在实验中，CHESS材料在室温下实现了近100%的效率提升，并在集成制冷系统中实现了70%的效率提升。该技术由APL经过10年研发，最初用于国家安全领域，并已获得2023年R&D 100奖。这项突破为下一代无压缩机、无化学制冷剂的制冷技术奠定了基础。

How often is the query plan optimal?

作者: eatonphil | 评分: 26 | 评论数: 5 | 发布时间: 2025-06-30 15:19
文章摘要

本文讨论了PostgreSQL查询优化器选择“最优”查询计划的有效性。尽管优化器承诺选择最优计划，但实际上依赖于成本估算，这可能导致错误选择。作者通过实验展示了在不同选择率下（如1-5%），优化器有时会选择性能较差的索引扫描而非更快的顺序扫描或位图扫描。实验还表明，位图扫描在多数情况下表现更好，尤其在低选择率时，而索引扫描缺乏预取能力，导致性能不佳。 数据分布也会影响计划选择，均匀分布和线性分布的结果不同。在冷缓存情况下差异更明显，而热缓存时差异减小。总体而言，优化器基于统计和成本模型选择计划，但不总是最优。用户很难察觉有更好计划，手动干预也非易事。调整成本参数或有帮助，但适应所有数据分布的完美配置可能不存在。

评论摘要
主要讨论点：SQL查询优化与执行计划的选择和优化 不同观点： • **mike_hearn**：认为基于统计的查询计划对临时查询非常有用，尤其是对于人工编写的SQL查询。但对于机器生成的查询，可预测性更为重要，应该考虑硬编码计划或锁定执行计划以避免生产环境中的意外变化。他还提出可以设计一种数据库模式，提前构建索引和计划，避免性能突然下降。 • **bob1029**：同意可以通过自适应查询处理技术改进查询计划，使数据库引擎在查询执行过程中调整策略，提升性能。他提供了多个高性能RDBMS中自适应查询处理的参考链接。 • **to11mtm**：指出最佳查询计划往往依赖于具体数据库，且存在一些反模式，例如不当使用ORM导致性能问题。他还提到在处理特定数据库流量时，可以利用ORM将某些内容视为字面量而非参数化查询，以提升性能。 • **remus**：不同意查询优化器总是选择“最佳”执行计划的观点，认为优化器在有限的时间和资源内工作，实际上是选择一个“足够好”的计划，并且需要快速和高效地完成。 • **alexisread**：认为Linq风格的查询比SQL风格更具确定性，尤其在云环境和复杂表结构（如Iceberg表）中。Linq可以在查询生成时明确过滤和连接顺序，避免依赖查询计划的优化选择。 补充讨论： • **争议焦点**：查询优化器的实际作用和性能表现。mike_hearn和remus对优化器的期望不同，前者关注可预测性和硬编码，后者强调优化器在有限资源下的效率和速度。 • **技术实现**：bob1029提出的自适应查询处理技术和to11mtm对ORM使用中的反模式及具体数据库性能优化的讨论，提供了不同的技术实现视角。 • **工具选择**：alexisread提出的Linq风格查询与传统SQL的对比，突显了在现代数据处理场景中，不同查询语言对性能和确定性的影响。 通过这些讨论，可以看出在SQL查询优化领域，存在多种技术路径和方法，选择合适的查询计划和优化策略需要根据具体应用场景和需求进行权衡。

Stalking the Statistically Improbable Restaurant with Data

作者: nkurz | 评分: 70 | 评论数: 8 | 发布时间: 2025-07-03 17:15
文章摘要

Pennybase 是一个简化版的后端即服务（BaaS），类似于 Firebase、Supabase 和 Pocketbase。它使用不到 1000 行 Go 代码实现核心后端功能，不依赖外部库，仅使用标准库。主要功能包括：基于 CSV 文件的存储（支持版本控制）、REST API（返回 JSON 响应）、基于会话 Cookie 和基本认证的用户认证、基于角色和所有权的权限控制（RBAC）、实时更新（通过 SSE）、模式验证（支持数字、文本、列表）以及模板渲染。 数据以人类可读的 CSV 格式存储，每次更新都会创建新版本，读取时使用最新版本。系统通过内存索引加快查找和更新速度。用户权限和数据模式分别定义在 `_users.csv` 和 `_schemas.csv` 文件中，权限控制基于角色或资源所有者。REST API 提供对资源的增删查改和实时事件流功能，并支持基本认证。
