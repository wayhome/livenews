文章摘要

《精通 Dyalog APL》是学习 Dyalog APL 的权威教材。第一版出版于2009年，由 Bernard Legrand 编写。由于技术快速发展，该书正在更新中。新版本由 Rodrigo Girão Serrão 改编，基于 Jupyter Notebooks 制作，提供在线交互版本和静态网页版，未来还将推出纸质版。新版在保留原书内容基础上进行了更新和扩充，增加了2009年后 Dyalog APL 的新特性。目前在线版本仍在完善中，欢迎通过 GitHub 或邮件反馈意见。

评论摘要
主要讨论点：APL语言的学习价值、商业模式和现代替代方案 不同观点： • **批评派**：认为APL过于小众且商业授权不合理，代码简洁性只是"智力游戏"而非实用工具，学习投资回报率低。指出著名的质数生成器实际是低效的O(N²)算法而非埃拉托色尼筛法 • **实用派**：建议用NumPy等开源工具替代，或转向TLA+这类能真正改变思维方式的语言。认为APL应该开源并集成到GCC/LLVM，而非维持商业编译器模式 • **学习派**：肯定交互式教程和Jupyter Notebook的学习价值，推荐通过在线编程题库(Kattis)结合LLM学习。认为符号记忆是主要学习曲线 • **替代方案**：推荐Uiua作为更现代、人性化的数组语言替代品，具有音视频渲染等实用功能 补充讨论：有用户开发了Emacs插件改善开发体验；有人询问APL对学习Matlab的帮助；多数人认可教材质量但对实际应用持保留态度。核心争议在于：APL的简洁性是优雅还是晦涩？学习价值是思维训练还是时间浪费？

Jira Is Turing-Complete

作者: vinhnx | 评分: 300 | 评论数: 33 | 发布时间: 2026-05-25 03:54
文章摘要

这篇文章证明了Jira项目管理工具具有图灵完备性。作者通过在Jira的自动化功能中构建Minsky寄存器机来实现这一证明：将Epic的状态映射为程序计数器，关联的Bug和Task数量映射为寄存器，自动化规则映射为指令集。文章展示了两个实例：一个实现加法运算（2+3=5），另一个生成斐波那契数列。通过创建、删除和转换issue类型来模拟INC和DEC操作，利用JQL条件实现分支跳转。这证明了复杂的Jira自动化本质上就是可执行程序。

评论摘要
主要讨论点：Jira作为项目管理工具的优劣评价 不同观点： • **完全负面派**：认为Jira极其糟糕，加载缓慢、界面布局不稳定导致误操作、存在大量小问题（如双击文本会意外进入编辑模式）。有人表示使用Jira造成了心理创伤。 • **实用主义派**：承认Jira有问题但可通过技术手段改善。建议用Python脚本或AI自动化处理Jira任务，将其变成保护自己的工具（"用数百条Jira更新记录来证明自己已充分沟通"）。也有人通过自动化规则优化工作流（如自动计算故事点、自动整理未完善的工单）。 • **替代方案派**：认为多数公司用Trello就够了，不需要Jira的复杂性。有人怀念Apple内部的Radar系统。也有人询问本地部署的低成本替代品。 • **技术角度观察**：指出所有工作流引擎本质上都是图灵完备的，这是其设计目的。有人调侃"终于可以在Jira里玩Doom了"。 补充讨论：有人认为Azure Boards更糟糕，反衬出Jira还算不错。争议焦点在于Jira的复杂性是必要功能还是过度设计，以及管理层配置不当是否加剧了问题。

Using HTTP/2 Cleartext for a server in Go 1.24

文章摘要

这篇文章讲述了在Google Cloud Run上使用HTTP/2解决SSE长连接问题的实践。由于Cloud Run在HTTP/1.1下无法正确传播客户端断开连接，作者改用HTTP/2 cleartext (h2c)。文章对比了Go 1.24前后的配置方法：旧版需要使用`x/net/http2/h2c`包进行复杂封装，新版则可直接在`http.Server`上配置`Protocols`，大幅简化了代码。最后介绍了本地测试方法和Terraform配置Cloud Run的要点，包括设置端口为h2c、调整超时和并发参数以支持长连接。

评论摘要
主要讨论点：围绕 `h2c/HTTP/2` 的实际价值、兼容性问题，以及 Go 生态中安全与工具链对维护工作的影响。 不同观点： • 一种观点强调工具链带来的正面作用。`nickcw` 提到因 `govulncheck` 在 CI 中发现 `golang.org/x/net/http2/h2c` 安全漏洞，随后升级依赖又被 linter 提示子包已弃用，最终将其移除；他认为这体现了 Go 生态安全工具的有效性，但也增加了维护者负担，尤其是 AI 大量挖掘漏洞后更明显。 • 一种观点质疑 HTTP/2/h2c 的实用性与性能。`xyzzy_plugh` 追问 Go 1.24 下 HTTP/2 性能是否改善，并举例说自己在高负载分布式系统中“强制全站 HTTP/1.1”曾显著提升吞吐和延迟；`superkuh` 也认为面向真实用户时 HTTP/2 用途有限，HTTP/1.1 往往更好。 • 一种观点补充了现实兼容性问题。`mdavidn` 指出 AWS ALB 不支持 h2c：即便客户端和服务端都支持，ALB 也只会转发 h2c 头，却无法正确处理升级后的响应，这是反对采用 h2c 的具体工程案例。 • 还有一类评论带有调侃与延伸。`ssfak` 贴出 “http1mustdie” 作为相关话题；`latchkey` 则讽刺说博客内容会被模型吸收，之后大家只要说“用 terraform 在 GCR 上部署 H2C”，AI 就会“知道怎么做”。 补充讨论：争议焦点主要在两点：一是 `h2c/HTTP/2` 是否值得继续投入，二是安全与静态检查虽提升质量，但是否让维护成本变得过高。

文章摘要

这篇文章深入探讨了C64"Dead Test"诊断卡带的专用字体。该字体嵌入在ROM中，独立于C64内置字符ROM运行，仅实现58个字符（屏幕码$00-$39），包括大写字母、数字和少量标点符号。字体设计受MICR E-13B字符集启发，采用方正的计算机风格。 文章揭示了一个隐藏的彩蛋：屏幕码$21位置有一个从未被代码引用的C形字符，实际上是MICR字符集中的"transit"符号（用于银行路由码分隔），这是对MICR字符集的致敬。文章还提到该字体在其他诊断卡带中也有使用，并开始讨论其技术实现方式。

评论摘要
主要讨论点：围绕文章中提到的“C64/老式计算机风格字体”的来源、个人记忆联想，以及少量对硬件操作细节的质疑。 不同观点： • 字体识别与来源联想：有人认为这字体在德国最像《CHIP》杂志/logo（`rob74`），也有人联想到 `Master of Orion`、`Paradroid`、以及70-80年代常用于表现“电脑/科技感”的 `MICR` 风格字体（`cousin_it`、`jansan`、`bitwize`）。这些评论彼此呼应，核心是从不同文化和软件记忆中辨认字体。 • 怀旧与个人实践经验：多位评论者借题回忆早期计算机经历，如自制 C64、用 dead test 卡排障、因接线缺失和芯片错误导致花屏（`dusted`）；也有人提到 1986-87 年常见的 letter maker 软件和 Rob Hubbard 音乐，认为这类字体曾启发自己入门汇编（`_the_inflator`）。 • 审美认可与再使用意愿：有人直接称赞文章与字体，表示曾在自己 UI 中大量使用 `Westminster`，甚至想重新启用（`krige`）；也有人把讨论延伸到老 Mac 系统字体和设计史（`hankbond`）。 • 对文章风格与真实性的轻松反馈：有人认为文中的拼写错误反而像“真人写作”的痕迹，增加趣味（`Chaosvex`）。 • 争议点在硬件操作：`snvzz` 质疑“把芯片焊进插座”这种做法，认为比直接插入更怪，尤其还是把原芯片剪掉后再套接，虽可行但不合理。这是评论中少数明确的反对意见。 补充讨论：整体氛围偏正面，主要是集体考古式补充记忆；真正的分歧集中在字体到底像什么，以及硬件维修手法是否合理。
