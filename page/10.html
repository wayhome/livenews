XLIDE: VBA without excel

作者: sts153 | 评分: 63 | 评论数: 6 | 发布时间: 2026-05-27 12:08
文章摘要

XLIDE 是一个 VS Code 扩展，允许用户直接在 VS Code 中编辑 Excel VBA 代码。主要特性包括：在侧边栏树形视图中浏览模块、语法高亮、符号导航（跳转定义、查找引用、重命名）、通过 Ctrl+S 保存更改回 .xlsm 文件，并通过语言模型 API 向 GitHub Copilot 公开所有操作。 技术架构采用虚拟文件系统（xlide-vba://）、Python 后端（pyOpenVBA + openpyxl）处理 VBA 读写、JSON-RPC 2.0 通信协议。无需 COM 自动化或 Office 安装，支持跨平台（Windows/macOS/Linux）。提供完整的 TextMate 语法定义和 Copilot 集成工具。

评论摘要
主要讨论点：关于一个VBA相关项目的评价和VBA技术本身的讨论 不同观点： • **质疑项目质量**：stymaar认为这个项目理论上很酷，但实际上只是一个周末"vibe-coded"的项目，代码量达到50klocs（包括依赖pyOpenVBA），暗示项目可能缺乏深度和可靠性 • **关注VBA安全性**：leshenka提出两个问题——VBA在当今Excel中的使用程度如何？为什么VBA宏不在沙箱中运行，限制其破坏性操作仅限于表格数据？质疑现有安全机制的合理性 • **质疑技术选择**：bigfishrunning不理解为什么要用VBA，认为应该使用VB.net或其他更现代的工具 • **负面评价**：nickstinemates用"downside without the upside"（只有缺点没有优点）简短表达了对该项目的否定态度 • **积极态度**：_boffin_表示会尝试使用这个项目，持开放和乐观的态度 补充讨论：评论整体偏负面，主要争议集中在项目的实用价值和VBA技术本身的现代性上。stymaar的"vibe-coded"暗示代码质量可能不够严谨。

C array types are weird

作者: signa11 | 评分: 120 | 评论数: 16 | 发布时间: 2026-05-25 05:05
文章摘要

这篇文章讨论了C语言数组类型的奇怪之处。主要问题包括： 1. **自动转换**：数组类型`T[n]`会自动转换为指针`T*`，指向首元素，但`sizeof`是例外。 2. **函数参数**：函数参数中的数组会被解释为指针，长度信息丢失，导致`sizeof`行为不一致。 3. **混淆性**：这种设计让初学者困惑——修改函数内的数组会影响外部，但结构体不会。 作者建议：数组应该像结构体一样按值传递，保留长度信息。如需指针行为，应显式写`&arr[0]`。这样能使语言更清晰易懂，避免隐式转换带来的困惑。 文章还对比了函数类型的类似行为，指出函数指针的处理方式虽相似但更一致。

评论摘要
主要讨论点：C语言中“数组与指针”的设计、历史成因、实际价值，以及它在多维数组、安全性和现代语言互操作中的问题。 不同观点： • **主张C缺少更安全的“切片”抽象**：Animats认为若C有slice，就能覆盖大多数“指向数组中间”的需求，且语义更合理；他还提到自己曾尝试给C补上slice，但受政治/生态阻力失败。the__alchemist也赞成把“集合抽象”和“裸指针/MMIO”分开，提到Rust FFI常把C指针API包装成`&[]`。 • **认为C的数组/指针设计虽怪，但有现实价值**：danborn26指出“数组衰变为指针”虽易坑新手，却让传参非常轻量。uecker补充说，`[static n]`和“指向数组的指针”写法虽难读，但能带来编译器警告和边界检查。 • **批评其在多维数组上尤其不直观**：alexey-salmin认为二维数组暴露出严重不对称性，`a[i][j]`既可能是连续内存，也可能是`char**`指向分散内存，内存布局和汇编表现完全不同，说明“数组≈首元素指针”在多维情形下失效。moktonar也强调`int x[n]`和`int *x`在内存布局上本质不同，尤其影响结构体定义。 • **从历史解释这种设计**：kazinator追溯到B语言，称“数组产生指针”原本在更早语言里是实际存在的隐藏指针机制，C是沿袭/简化了旧设计。fooker则认为C所处年代不能“没有数组”，因为当时Fortran主导，语言设计必须回应这种预期。 补充讨论： • 争议焦点在于：这是“简单高效的低层设计”还是“不合适且历史包袱重的抽象”。 • 其他评论多在调侃其怪异性，如`3[x] == x[3]`、`register`数组取地址的UB，以及“C很简单”的反讽。

Theseus: Translating Win32 to WASM

作者: ingve | 评分: 48 | 评论数: 13 | 发布时间: 2026-05-25 07:26
文章摘要

文章介绍 Theseus 已可将 Win32/.exe 翻译为 WebAssembly，在网页中运行。核心改动包括：复用原有 x86 翻译输出、抽象 Host API 以适配 SDL 和 Web。最大难点是“是否允许阻塞”：原先异步方案利于浏览器运行，但调试复杂、性能较差；新版改用同步阻塞和真实线程。为解决 Web 主线程不能阻塞的问题，作者让模拟器在线程 worker 中运行，并用共享内存与 Atomics 实现阻塞式调用。

评论摘要
主要讨论点：围绕该项目将 Win32/x86 程序搬到浏览器/WASM 的可行性、实现路线、线程与渲染限制，以及其实用价值展开讨论。 不同观点： • 技术上可进一步简化实现：kettlecorn认为若主二进制由Rust实现，可利用Rust分配器在启用原子支持后“忙等”而非等待主线程，从而有机会让主线程二进制被多个线程共享，不必采用博文中较复杂的方案；这是对原文“malloc可能阻塞”的直接回应。 • 浏览器/WASM生态正在改善：hardwaresofton提到WASM Component Model及其线程支持正在推进，LLVM也已有相关进展；modeless则建议使用OffscreenCanvas，把图形渲染放到后台worker，减少对浏览器主线程依赖。Aurornis与valorzard补充说，浏览器线程和WASM调试目前仍是明显痛点，多线程Rust WASM体验“不稳定”。 • 该方向很有潜力，甚至可扩展到更多程序：astlouis44认为若补上WebGPU，或可用于把原生Windows游戏转到WASM；univrsaltrans更乐观，认为未来可能出现“通用二进制翻译器”。theanonymousone也表达了强烈兴趣并询问如何贡献。 • 也有人强调这是学习型项目，离实用尚远：gigel82明确认为项目“有趣但不可实际使用”，并拿Boxedwine作对比，称其也主要只能跑较老的软件。lukax举Retrotick为另一条路线，说明模拟x86+JS实现Windows API已能跑部分旧程序，但API覆盖仍不足。 • 对项目本身的肯定多集中在“轻量”和“有趣”：mickael-kerjean称赞示例仅约1MB，相比一些体积巨大的WASM项目（如压缩后50MB的LibreOffice）很清爽；也有人单纯觉得扫雷在浏览器中运行很酷。 • 还有命名与认知层面的讨论：Findecanor最初误以为是Theseus OS；arka2147483647则吐槽项目名不如“win2wasm”直观，反映品牌化命名不易记忆。 补充讨论：争议焦点主要在“技术前景是否足以支撑实际可用性”——一方认为线程、组件模型、渲染能力正在快速补齐，另一方则指出当前多线程、调试、API兼容和现代软件支持仍是现实障碍。
