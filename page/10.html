PgDog is funded and coming to a database near you

作者: levkk | 评分: 528 | 评论数: 60 | 发布时间: 2026-06-10 14:02
文章摘要

PgDog是一个开源的Postgres水平扩展代理解决方案。团队认为Postgres是唯一需要的数据库，其他NoSQL数据库存在只是因为Postgres的扩展性问题。PgDog通过在Postgres前加代理层实现水平扩展，支持100TB+表和每秒百万级查询。目前已在生产环境处理超200万QPS，分片超20TB数据，Docker拉取量达140万次。这是一个三人初创团队，创始人曾在Instacart大规模运维Postgres。产品可部署在任何环境，完全开源，每周四发布新版本，已获550万美元融资。

评论摘要
主要讨论点：PgDog（Postgres代理和分片工具）获得融资的消息引发的技术讨论 不同观点： • **分片策略担忧**：ahachete指出PgDog使用模运算(hash % num_shards)分片存在重大缺陷，当需要替换分片时必须重新分片整个数据集。更好的方案是像Citus那样使用线性范围+虚拟分片，支持平滑迁移 • **高可用性更关键**：eikenberry认为Postgres最大问题不是扩展性而是高可用性。单集群可轻松处理10万/分钟事务，但故障转移需要人工干预，自动化方案不可靠 • **正面使用体验**：多位用户(directionless, mijoharas, ParadisoShlee)分享了从PgBouncer迁移到PgDog的顺利经验，特别称赞其对每连接设置的透明处理 • **配置管理问题**：kjuulh在Kubernetes多租户环境中使用PgDog遇到配置管理困难和认证缓存问题，认为PgDog更适合需要大规模扩展的少量数据库场景 补充讨论： chrisvenum询问4TB数据库的分片可行性；yabones关注版本升级停机时间问题；aejm质疑企业版与开源版的功能差异；Ozzie_osman对"20TB分片"数据表示疑惑。整体氛围积极但对技术细节有理性质疑。

Sequoyah’s syllabary created a written language for the Cherokee

作者: grahambargeron | 评分: 144 | 评论数: 9 | 发布时间: 2026-06-10 22:07
文章摘要

切罗基族银匠Sequoyah于1821年发明了切罗基文字系统，使用85个音节符号让族人能够书写自己的语言。这项创造最初被视为巫术，但很快让四分之一的切罗基人在六个月内实现读写，识字率超过当时美国非原住民人口。该文字系统促成了切罗基宪法的制定和首份原住民报纸《切罗基凤凰报》的出版。尽管遭遇"血泪之路"的强制迁徙，这套文字系统被带到俄克拉何马州并可能传播到西非。如今，它仍是保护切罗基语言和文化的重要工具。

评论摘要
主要讨论点：关于切罗基文字系统的创造及其效率性的讨论 不同观点： • **标题误导论**（rayiner）：文章标题有误导性。切罗基人认为这是"魔法"并非因为文字系统高效，而是因为他们不熟悉"书写"这个概念本身。创造者甚至因此被指控巫术并受审。 • **内容批评**（steve-atx-7600）：文章质量差，连切罗基文字符号的示例都没有提供，认为史密森尼学会也沦为像福布斯一样的点击诱饵来源。 • **语音准确性讨论**（torben-friis）：文章称切罗基音节文字因语音准确性和简洁性而比英语更易掌握，但这是必然的——为当前语言定制的文字系统本就更准确。英语因语音与拼写不符而臭名昭著。 • **扩展兴趣**：有人分享了切罗基音节文字的维基百科链接（CPLX）和英语音节文字的人造系统（philipswood），还有人提出关于"理论上最紧凑高效语言"的哲学问题（HoldOnAMinute）。 补充讨论：讨论从对文章的批评延伸到文字系统设计原理，以及语言效率的理论探讨。核心争议在于：文字系统的"高效"是技术优势还是文化背景差异的结果。

Claude Desktop spins up a VM without no way of stopping it

作者: tonyrice | 评分: 189 | 评论数: 33 | 发布时间: 2026-06-10 17:11
文章摘要

这是一个关于 Claude Desktop Windows 版的内存占用问题报告： **核心问题**：Claude Desktop 每次启动都会自动创建一个占用 1.8 GB 内存的 Hyper-V 虚拟机（Vmmem 进程），即使用户只需要聊天功能而不使用 Cowork 或代理模式。在 16 GB 内存的笔记本上，这占用了超过 11% 的总内存。 **根本原因**：应用发现了 2,689 个未清理的历史 Cowork 会话文件，且 VM 基础设施在每次启动时无条件初始化，而非按需启动。 **影响**：导致系统空闲时内存使用从 50% 跃升至 62%，正常使用时达 70-75%，造成系统卡顿。 **临时解决方案**：禁用 VirtualMachinePlatform 功能或手动终止 VM 进程（但会失去 Cowork 功能）。 **期望行为**：仅在实际使用 Cowork 时才启动 VM，并自动清理旧会话文件。

评论摘要
主要讨论点：Claude桌面应用的Cowork功能自动安装约10GB虚拟机且无法禁用或删除的问题 不同观点： • **产品设计缺陷派**：认为Cowork应该设计为可选功能（opt-in），而非强制安装。批评Anthropic缺乏工艺精神，产品匆忙上线，存在broken links指向macOS设置等明显bug • **行业竞争视角**：认为这反映了AI模型公司与操作系统公司在本地AI集成方面的竞赛，质疑Google同时拥有Gemini和Android却未能解决类似问题 • **用户控制权流失派**：将此问题放在更大背景下讨论——从过去强调个性化定制，到现在用户失去对设备的控制权（无法删除"系统"应用、复杂的隐私设置等） • **性能问题抱怨**：部分用户因应用启动缓慢、交互卡顿而放弃使用Claude桌面版，认为与Anthropic的AI rhetoric不符 • **讽刺/调侃派**：用"vibecoded with AGI"、"LLM coded nonsense"等表达对AI公司产品质量的讽刺 补充讨论：有用户发现该功能导致存储空间不足问题，删除后不敢再打开Cowork标签。标题语法错误（"without no way"双重否定）也引发讨论。

评论摘要

评论摘要

主要讨论点：GitHub 认证系统故障导致多个服务和工具无法正常使用 不同观点： • **频繁故障抱怨派**：用户讽刺 GitHub 故障频繁（"如果每次故障给我5美分，我都能买DDR5内存了"），认为服务可靠性有问题 • **误判为安全问题派**：多位用户最初以为自己账号被黑或出现安全问题，浪费时间排查才发现是 GitHub 的问题 • **技术影响派**：大量用户报告具体受影响的工具和服务（VS Code 扩展、Chrome 扩展、gh CLI、Heroku 集成、CodeQL Actions 等） • **自建服务转移派**：有用户因此转向自托管方案如 Forgejo，表示运行良好 • **状态页面批评派**：指出 GitHub 状态页面分类不清晰，将认证问题归类在 API 下，导致实际影响范围被低估，正常运行时间数据被美化 补充讨论： 核心争议在于错误码选择（返回 401 认证错误而非 500 服务器错误）误导用户，以及 GitHub 的透明度和可靠性问题。多数用户对故障频率和处理方式表示不满。
