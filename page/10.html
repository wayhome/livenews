Writing Portable ARM64 Assembly (2023)

作者: luu | 评分: 58 | 评论数: 7 | 发布时间: 2026-05-31 17:59
文章摘要

本文介绍如何编写可移植的 ARM64 汇编代码。主要问题是开发者为 Apple ARM 设备编写汇编时忽略了其他平台。关键差异包括： 1. **ABI 差异**：Darwin 使用 Mach-O 格式，所有符号需加下划线前缀；Linux 等使用 ELF 格式，支持符号类型定义 2. **平台差异**：Darwin ABI 保留 x18 寄存器 3. **语法差异**：避免使用 Apple 特有的 NEON 简化语法（如 `eor.16b`），应使用 ARM 官方语法（如 `eor v2.16b, v2.16b, v0.16b`） 解决方案是使用宏来抽象平台差异，处理符号命名和类型定义，从而实现跨平台兼容。

评论摘要
主要讨论点：ARM/AArch64 汇编在不同平台上的可移植性，以及 Darwin、Linux、Android、Windows 等 ABI/目标文件格式差异会带来哪些实际问题。 不同观点： • 一种观点认为，跨平台并非完全不可行，但必须了解 ABI 细节差异。例子是 Darwin/Android 会保留 `x18`，而 GNU/Linux/Alpine 通常不保留；还要注意 Mach-O 与 ELF 的区别，以及避免 Apple 特有语法。 • 另一种观点强调 Apple 平台适配成本高。有人提到自己代码里有很多 `#ifdef __APPLE__`，在缺少 Apple Silicon 真机时，只靠 GitHub Actions 和源码资料，修复汇编/编译器问题更困难。 • 有人补充，讨论不能只盯着 macOS 和 ELF/Linux，还应考虑 Windows on ARM、PE 格式、对齐规则、shadow stack 等，否则“可移植”讨论不完整。 • 也有质疑具体代码可移植性的观点：如果代码把 `clang` 默认等同于 macOS，这种假设本身就不通用。 • 更悲观的观点认为“汇编本来就不便携”，并举 6502 在 Apple、Gameboy、C64 之间不能直接通用作类比，强调平台差异是常态。 补充讨论：争议焦点在于“汇编是否能称得上可移植”。一方认为可通过处理 ABI/格式差异实现有限移植；另一方认为这些差异过多，尤其加上 Apple 和 Windows 特例后，可移植性本就很弱。另有一条 `ORPort...` 评论与主线讨论关联较弱。

评论摘要
主要讨论点：Gmail及其他软件强推AI写作/摘要功能，引发用户对产品体验、实用性、隐私与邮件可靠性的集中不满。 不同观点： • 迁移派：多名评论者推荐转向Fastmail等替代品，认为其速度快、迁移顺畅、搜索可靠、界面少打扰；也有人主张进一步“去Google化”，理由是隐私和整体体验更好。 • 反AI写作派：多数人认为邮件代写、长篇建议回复和自动改写既空洞又浪费时间；举例包括Gmail建议回复“听起来正确但没信息”、摘要经常失真、YouTrack把文字改得不像本人。 • 反强推派：争议焦点之一不是AI是否绝对无用，而是为何要靠弹窗、提示、通知反复推销；有人提到Gmail、Google Docs、Chrome、Windows都在不断打扰，且关闭成本高。 • 保留有限AI派：少数意见接受“这时间可以”这类一键短回复，认为轻量辅助有用，但反对生成整封或逐点回复。 补充讨论： • 有人建议关闭Google“smart features”作为缓解方案，但也有人认为根本解决还是换服务。 • 还出现对Gmail可靠性的批评，如邮件消失、垃圾邮件误判、DKIM策略变更不透明，说明不满不只针对AI，也涉及邮件基础能力。
