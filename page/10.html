Parse, Don’t Validate – Some C Safety Tips

作者: lelanthran | 评分: 118 | 评论数: 16 | 发布时间: 2025-07-09 08:07
文章摘要

这篇文章讨论了“解析而非验证”技术在C语言中的应用，以减少可被利用的错误风险。作者指出，常见的验证方法会导致系统深处的代码重复验证输入，增加错误机会。通过在输入边界处直接解析输入数据为特定类型（如`email_t`），可以避免系统内部重复验证的问题。文章建议使用不透明类型来替代`char *`，确保数据类型安全，防止恶意输入。这种方法不仅提高了安全性，还能借助编译器类型检查进一步减少攻击面。最终，只有边界处的函数处理原始`char *`输入，内部函数只接受已验证的类型。

评论摘要
主要讨论点：通过解析输入并利用类型系统进行验证的编程实践 不同观点： • [myaccountonhn] 认为在"边缘"将输入解析为适合问题域的数据结构是好的做法，可以提高代码的可维护性。然而，过度使用 newtype 包装会增加不必要的仪式性和样板代码。如果数据可以合理地表示为原始类型，则应直接使用原始类型。此外，与大量使用 newtype 的库交互可能会导致问题，尤其是当库没有提供访问内部数据的途径时。 • [OptionOfT] 支持充分利用类型系统来防止错误。通过使用特定类型（如 ValidatedEmail、PriviligedUser）可以让编译器提供保护，减少代码中的条件检查，提高代码的安全性和可读性。 • [o11c] 指出不应在自定义类型中使用 "_t" 后缀，因为这是为未来标准类型保留的。同时，认为防止双重释放的声明是无效的，C 语言在对象所有权方面表现不佳。 • [hackrmn] 强调通过解析输入和利用类型系统来提高代码的健壮性，但指出在实践中往往难以说服同事采用这种方法。许多开发者仍然依赖于分散的验证函数，而没有充分利用类型系统。 • [hansvm] 提到 "Parse, Don't Validate" 方法在实际代码库中可能导致类型的组合爆炸。如果需要同时满足多个条件，可能导致中间类型和解析代码的指数增长。提出了一种使用编译时标记来解决此问题的方案。 • [pianoben] 认为虽然概念上同意这种方法，但在实际操作中处理解析结果非常困难，尤其是当需要将自定义类型转换回基本类型时。 • [rorylaitila] 分享了自己在 web 应用中使用这种方法的经验，通过自动生成值对象和访问器类来解决大量字段的验证问题，但指出这种方法可能在性能上有所影响。 • [anon-3988] 强调在 C 语言中实现安全性需要使用 newtype 模式，将信息封装在结构体中，并建议在创建和消费时以外部库处理指针。 • [charcircuit] 简单表示不信任 C 开发者处理字符串的能力。 • [belter] 认为 "Parse, Don't Validate" 模式只是防御的一部分，还需要结合资源限制和其他保护措施。 补充讨论： • 关于使用 "_t" 后缀的争议，多个评论指出这是保留给标准类型的，自定义类型不应使用。 • 讨论中多次提到性能问题，特别是在 web 应用中处理大量数据时的性能影响。 • 对于 C 语言中的安全性和内存管理问题，有评论指出需要更好的所有权管理和防止双重释放的措施。 • 关于说服其他开发者采用这种方法的困难，强调了实际应用中的文化和沟通挑战。 争议的焦点： • 使用 newtype 模式的必要性和其带来的仪式性代码的权衡。 • 在实际项目中应用 "Parse, Don't Validate" 模式的可行性和复杂性。 • 在 C 语言中处理字符串和内存管理的固有困难和风险。

这篇文章介绍了2023年7月12至14日在瑞典举办的一场活动，活动通过Twitch直播。三天日程包括多位演讲者的技术分享，涵盖编程历史、物理引擎并行化、调试器可视化架构、游戏开发中的车辆编程、音频对齐、可伸缩字形渲染、深度学习与计算机视觉等主题。物理出席为邀请制，不公开发售门票。活动将直播并录制，免费公开。地点在一个迷人的小镇。组织者为Sam、Sander和Charlie。更多信息可通过订阅新闻通讯或在Twitter上提问获取。

评论摘要
主要讨论点：对软件质量会议及相关议题的看法与争议 不同观点： • **对会议承诺的怀疑**：burnt-resistor对会议和书籍所承诺的“这次会有所不同”表示怀疑，认为这些只是卖点，而实际过程和工具并没有显著变化。他们质疑AI在编码中的作用，认为依赖AI可能导致经验不足的人重复犯错。 • **有效的质量控制经验**：supportengineer分享了自己30年职业生涯中唯一见到有效质量控制的公司的经验。该公司通过分离质量工程师和开发工程师的组织结构，不同的激励机制，严格的文档和发布节奏，以及质量工程师的绝对权威来实现质量控制。 • **会议与特定群体的关联**：kragen认为该会议与Handmade Hero和Jon Blow的Jai群体有关，关注点更偏向用户体验和效率，而非正确性。 • **网站质量与会议宗旨的矛盾**：imwally和jofzar指出，一个倡导高质量软件的会议应该有一个更好的网站。jofzar特别提到网站在移动设备上的用户体验问题，以及缺乏对演讲者社交链接的介绍。 • **对演讲标题和组织者透明度的批评**：alabhyajindal和kilpikaarna对某些演讲标题表示不满，认为其形式具有侮辱性。kilpikaarna还对会议的组织方式和匿名组织者表示质疑，认为其可能在刻意保持某种排他性。 • **对AI工具与质量平衡的关注**：reactordev对如何平衡快速业务需求与AI工具带来的质量问题表示关注，并分享了个人经验。 • **对会议实质内容的信息不足**：rkagerer指出很难找到关于会议实质的信息，仅从Twitch标签中了解到“软件质量正在变差，我们来改善”。 • **对网站设计元素的关注**：wavemode注意到网站使用的编程语言可能是Odin，而grob则对网站使用的字体Berkeley Mono表示赞赏。 • **对知名演讲者的期待**：ravenstine希望Jonathan Blow能成为演讲者。 • **对 dysfunctional code 框架的讽刺**：mediumsmart讽刺地建议创建一个 dysfunctional code 框架以加快项目进度。 • **对HR和企业实践的重视**：ChrisMarshallNY认为，除非会议倡导有利于留住人才的HR实践和激励质量的企业实践，否则很难带来实质性改变。他提到Watts Humphrey等人的经典质量实践书籍，并指出不良的管理和短视的高层是质量问题的根本原因。 补充讨论： • **对具体演讲内容的正面反馈**：elcapitan对Casey Muratori的演讲表示赞赏，认为其对OOP历史方面的见解很有启发性。 争议焦点： • 会议和网站的实际质量与所宣扬的质量宗旨之间的矛盾。 • AI工具在编码中的应用及其对软件质量的影响。 • 会议的组织方式及其可能的排他性。
