Stop Using JWTs

作者: dzonga | 评分: 176 | 评论数: 33 | 发布时间: 2026-06-16 16:49
文章摘要

这篇文章主张停止使用JWT进行用户登录管理。核心观点包括： 1. **JWT不适合会话管理**：JWT设计用于5分钟以下的短期token，而会话需要更长生命周期。 2. **无状态认证不安全**：真正的无状态认证不可行，必须维护某种状态来保证安全，既然需要数据存储，不如直接使用传统会话。 3. **JWT规范本身存在安全问题**：安全专家不信任JWT规范，原始规范甚至允许伪造token。 4. **传统cookie会话更优**：更安全、更高效、更灵活。谷歌等大公司的浏览器用户会话也使用传统cookie，JWT仅用于单点登录的服务器间传输。 文章推荐使用PASETO作为短期token的替代方案，并建议避免在localStorage存储认证凭据。

评论摘要
主要讨论点：JWT在Web认证中的适用性及其安全性争议 不同观点： • **JWT适用但需正确使用**（littlecranky67, tracker1, himata4113, miiiiiike）：JWT撤销列表比session列表更小、成本更低；使用短生命周期（5-15分钟）配合刷新机制；适合服务间通信和作为认证缓存；采用RSA签名而非共享密钥；可通过minimum_issued_at实现"全设备登出" • **JWT存在根本性问题**（文章作者，rdegges支持）：无法撤销单个token是致命缺陷；既然需要撤销列表就失去了无状态优势，不如直接用session；规范本身不被安全专家信任；建议用PASETO替代 • **JWT完全可行且优越**（bijowo1676, Grollicus）：比cookies更优秀；在特定场景（如RabbitMQ权限控制）设置简单高效 • **争议被夸大**（solatic, ApolloFortyNine, Aeolun, bastawhiz, blixt）：反对文章引用的安全问题实际是实现bug而非标准缺陷；AWS STS等大规模系统成功使用JWT证明其可靠；"5分钟生命周期限制"缺乏RFC依据；标题过于耸人听闻 补充讨论：BlackFly总结核心矛盾——若需状态化撤销列表，JWT的无状态优势即消失；himata4113强调子服务隔离的安全价值；多人提到使用场景区分（浏览器session vs 服务间通信）是关键

A 24-byte TAR-like file system for microcontrollers

作者: drewcg | 评分: 6 | 评论数: 0 | 发布时间: 2026-06-17 14:25
文章摘要

UTFS是一个为嵌入式系统设计的轻量级文件存储系统，类似TAR格式。它可以在EEPROM或flash等顺序存储介质中保存命名数据块（"文件"），仅需两个源文件（utfs.c/utfs.h），无需动态内存分配，每个文件仅24字节头部开销。 核心特点：零堆分配、C99标准、通过实现sys_read/sys_write两个函数即可移植到任何存储介质、减少擦写次数、格式开放且向前兼容、MIT许可。 使用流程简单：注册文件（指向RAM中的结构体）→ 加载 → 使用 → 保存。适合资源受限的单片机，如ATMega328仅1KB EEPROM即可存储多个独立命名的数据结构。

Wolfram Language和Mathematica第15版于2026年6月16日发布。这是自1988年首次推出以来的第38年更新。主要特性包括：内置AI助手、时间序列和分类数据处理增强、新的ModelFit超函数、符号音乐功能、笔记本界面改进（侧边栏、视觉主题、暗黑模式）、增量数据结构、异常处理优化、GPU加速、WebSocket实时连接、偏微分方程求解改进、强化学习控制系统等。该版本继续扩展计算语言的应用范围，使其不仅服务于人类用户，也能被AI系统调用。

评论摘要
主要讨论点：Wolfram Mathematica 15的价值与局限性 不同观点： • **产品优秀但过于封闭**：Mathematica功能强大、直观易用（创建分形、动画等），但作为封闭生态系统，企业级应用成本过高。如果开源可能释放更大价值（Lucasoato, lutusp） • **AI助手表现不佳**：Wolfram自带AI助手远不如Claude等通用模型，经常幻觉生成不存在的函数名和参数。原因是公开的Wolfram代码训练数据远少于Python（mlpicker, stblack） • **语言设计的权衡**：有人将Wolfram Language比作拉丁语（优雅纯粹但实用性低），Python比作英语（混杂但无处不在）。规则严谨但生态受限（steve1977） • **实际应用有限**：企业环境中几乎不使用，学术界转行者也不会怀念它。同类商业软件（SPSS、SAS等）面临相似处境（SilverElfin, Vaslo） 补充讨论：有评论质疑Stephen Wolfram本人的学术可信度；也有用户提到开源替代品Hissab的存在；个别用户仍认可其solve等特定功能的价值。核心争议在于闭源高价策略是否阻碍了技术传播。

评论摘要
主要讨论点：Iroh v1.0发布，一个应用层的P2P连接协议，类似"应用层的Tailscale" 不同观点： • **支持者观点**：多位生产环境用户（分布式ML训练、商业应用）高度评价，认为比libp2p更好用，团队响应迅速，hole punching功能优秀，能实现去中心化网络愿景 • **质疑实用性**：认为现有IP/DNS/IPv6/QUIC已足够，不理解要解决什么问题，需要主流厂商和软件支持才有前景 • **对比Tailscale的困惑**：多人询问与Tailscale的区别，建议urgent添加对比页面说明与tailscale/netbird/zerotier等方案的差异 • **协议设计疑问**：质疑为何协议层面需要"定价"页面；询问与Reticulum的区别；文档不够清晰（未说明密钥类型、relay机制等） 补充讨论： 开发者回应支持自定义传输层（Tor/BLE/LoRa等可作为独立crate实现），避免代码臃肿。技术问题涉及密钥轮换、peer发现/DHT、人类可读命名、离线通信、匿名性等深层设计考量。整体氛围积极，但需更清晰的定位说明和与现有方案的对比。
