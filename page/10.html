Azure Linux 4.0 is Microsoft's first general-purpose Linux

作者: haydenbarnes | 评分: 211 | 评论数: 32 | 发布时间: 2026-06-05 03:14
文章摘要

微软在 Build 2026 发布了 Azure Linux 4.0 公开预览版，这是首次允许用户在任意 Azure 虚拟机上运行该系统，标志着它从专用设备发行版转变为通用 Linux 发行版。 4.0 版本基于 Fedora 43 构建（而非此前的从零构建），采用 6.18 LTS 内核，用 dnf5 替换了此前的 tdnf 包管理器，包含 glibc 2.42、systemd 258、Python 3.14 等现代组件栈，支持 FIPS 140-3 认证和 SELinux 安全加固。 该系统现可部署在虚拟机、容器、AKS、WSL 等多种环境，Databricks 和 LinkedIn 已迁移大量基础设施。其特点是供应链可审计：所有相对 Fedora 的改动都有文档记录并开源在 GitHub。

评论摘要
主要讨论点：微软发布Azure Linux作为"通用云操作系统"的定位是否准确，以及微软在Linux领域的战略意图 不同观点： • **支持者观点**（rswail）：Azure Linux具有重要价值——它是通用的应用交付平台，支持容器/虚拟机/裸机部署；拥有完整的SBOM（软件物料清单）可追溯到Fedora源头，满足安全审计要求；采用只读OS设计。虽不支持任意硬件，但能在多种环境中运行通用应用 • **质疑"通用"定位**（codycharris, froh, bananaquant）：这只是为Azure优化的系统，不会在其计算环境外运行；真正的通用OS应能在任意硬件上运行并获得厂商支持；基于前沿发行版Fedora却声称"通用"是不负责任的，这正是Fedora/RHEL分离的原因——前者不适合所有生产环境 • **怀疑微软动机**（nullpoint420, egorfine, ramon156）：这是"拥抱、扩展、消灭"(EEE)策略的体现；微软在稀释"通用"一词的含义以占领新空间；微软过度依赖Red Hat的工作成果；质疑微软近期多个模仿行为 补充讨论：有用户指出微软从Xenix时代就支持Unix系统；从tdnf迁移到dnf5显示平台变得更标准化而非更定制化；部分用户对AI和大公司产品普遍持批评态度

Programmers Aren't People

作者: elliotbnvl | 评分: 26 | 评论数: 7 | 发布时间: 2026-06-06 21:38
文章摘要

这篇文章追溯了"computer"一词从指代人到指代机器的演变历史。最初三百年间，computer指从事计算工作的人，如19世纪法国的理发师、哈佛天文台的女性天文学家、NASA的女性计算员等。1945年ENIAC问世后，这个词迅速转移到机器身上。作者指出"programmer"面临同样命运——这些词本质上都是"动词+er"结构，描述的是功能而非人。当AI能完成编程工作时，"programmer"这个词也会像"computer"一样被机器占据，程序员需要像当年Dorothy Vaughan那样爬向更高的梯级。

评论摘要
主要讨论点：AI/LLM对程序员职业的影响及"程序员"定义的演变 不同观点： • **怀疑AI影响论**：认为文章是NVIDIA员工的广告或危机营销。虽然AI能快速生成代码，但代码产出不等于实际价值——已有数十亿行免费代码存在，关键在于理解和责任。若真有100倍生产力提升，AAA游戏应6天完成，但现实并未出现这种变化，99%程序员也未被裁员。 • **职业演变论**：程序员职业正经历类似"印刷工→平面设计师"的转型。当工具改变时，多学科技能融合诞生新领域（如数据科学=统计+计算+数据管理）。AI时代下，"程序员"可能演变为真正的"软件工程师"，强调工程化思维而非纯编码。 • **本质不变论**：编程的本质从未改变——从图灵机、打孔带到纺织品都能实现编程，只是载体不同。LLM只是又一层抽象（如同COBOL试图用自然语言编程），仍需要人来制定规格、验证正确性和修复问题。 补充讨论：两条极简观点引发思考——"程序员不一定是人"和编程可通过多种介质实现，暗示编程作为逻辑过程与执行主体的分离。

文章摘要

Ladybird浏览器项目宣布不再接受公开pull request，今后只有项目维护者能提交代码。这一改变是为了迎接首个alpha版本发布，建立更严格的开发流程和安全模型。AI工具的普及改变了代码贡献的信任机制——过去大量补丁意味着付出和善意，现在AI可以快速生成看似高质量的代码，但难以判断提交者意图。对于需要运行不受信任输入的浏览器来说，安全风险太高。项目仍保持开源，欢迎bug报告、测试反馈等非代码形式的贡献，但代码责任必须由核心维护者承担。

评论摘要
主要讨论点：Ladybird浏览器项目因AI生成代码泛滥而关闭外部PR提交，引发开源社区关于项目开放性、AI对开源贡献影响的激烈讨论 不同观点： • **支持关闭PR派**：AI降低了代码提交门槛但不代表质量，大量AI生成PR让维护者不堪重负。"大量代码"不再等同于"实质性努力"，这一信号失效使得审查成本激增。维护者同样能使用AI，外部AI代码无额外价值 • **反对关闭PR派**：这背离了开源精神，切断了发现和培养新维护者的渠道。贡献者发现bug并修复后却不能提交方案，要求维护者重做工作极不合理。代码审查应关注正确性而非提交者背景，关闭PR等于放弃了低成本获得修复的机会 • **中立/理解派**：理解资金有限团队的困境，但感到矛盾。这让Chromium/Firefox等大公司支持的项目反而显得更"开放"。认为整个软件工程游戏规则已改变，但对未来方向感到困惑和担忧 补充讨论：多人指出类似趋势正在蔓延（Godot、Linux基金会项目都面临相同问题）；有人质疑Ladybird作者本人常提交大量未审查代码的做法；SQLite和Blender等成功项目早已采用类似封闭模式；社区担忧失去的不仅是代码，还有想法交流、代码审阅等无形贡献
