Don’t use “click here” as link text (2001)

作者: theandrewbailey | 评分: 486 | 评论数: 78 | 发布时间: 2025-07-02 11:39
文章摘要

这篇文章为网站管理员提供了关于链接文本的建议。强调不要使用“点击这里”作为链接文本，而应使用简短且有意义的文本，这些文本应在脱离上下文时仍具有信息性，解释链接内容，避免提及技术细节，且不应为动词短语。例如，避免使用“点击这里下载Amaya”，而应直接写“获取Amaya！”。文章还引用了W3C的网页内容无障碍指南和其他参考资料，强调链接文本应易读且不涉及操作细节。这些建议旨在提高网页的可访问性和用户体验。文章最后说明这些提示由W3C质量保证兴趣小组提供，仅为信息性内容，不具规范性。

评论摘要
主要讨论点：链接文本的最佳实践及其对可访问性的影响 不同观点： • **支持“点击这里”的观点**（crazygringo）：认为“点击这里”能清楚表达链接的操作性质，尤其在下载或了解更多信息的情况下，明确表示这是一个动作链接，而不是参考链接。这种用法在网络上非常普遍且有效。 • **反对“点击这里”的观点**（robin_reala, scary-size, eightnoneone, latexr）：认为“点击这里”对屏幕阅读器用户不友好，尤其是当所有链接都使用相同文本时，会剥夺这些用户通过非线性方式访问内容的便利。UK政府的数字服务指南也建议避免这种做法。 • **偏好名词链接的观点**（guhcampos, retsibsi）：倾向于使用名词或名词短语作为链接文本，认为这样更清晰地指示链接指向的内容，避免使用动词和命令语气。 • **混合观点**（zzo38computer, seanwilson）：认为在某些情况下，动词或动词短语是合适的，尤其是直接下载链接，但应确保链接文本在上下文中是有意义的。同时，可以通过技术手段为屏幕阅读器提供额外文本，以增强可访问性。 补充讨论： • **对可访问性的进一步探讨**（jfax, smallerize）：提到一些用户难以区分页面上的不同元素，强调了网页设计中标准化和文本指示的重要性。还引用了Dragan Espenschied关于链接文本演变的文章，指出从动作指示到用户状态重配置的转变。 • **技术实现与SEO优化**（seanwilson）：强调可以通过技术手段如aria-label或CSS类来为屏幕阅读器提供额外文本，同时提高SEO效果。 • **实用性与规则的冲突**（scosman）：提到Lighthouse等工具对通用链接文本的警告，但有时这些警告会被忽略，因为一些通用文本在实际应用中仍被广泛接受。 • **对“点击这里”的技术性批评**（1970-01-01）：指出“点击这里”在触摸屏设备上的准确性问题，以及文本动态变化对用户体验的影响。 总体来看，争议焦点在于链接文本应如何平衡清晰性、可访问性和用户体验。不同用户和开发者对链接文本的最佳实践有不同的偏好和见解。

What's the difference between named functions and arrow functions in JavaScript?

作者: jrsinclair | 评分: 39 | 评论数: 5 | 发布时间: 2025-06-30 09:10
文章摘要

本文讨论了JavaScript中普通函数和箭头函数的区别。普通函数有三种创建方式：函数声明、函数表达式（可以是匿名或命名函数表达式）和箭头函数。 1. **函数声明**：如`function isVowel(chr) {}`，会被JavaScript引擎提升（hoisted），在整个作用域内可用。 2. **函数表达式**：如`const takeWhile = function ...`，可以是匿名或命名函数，但命名函数的名称不会绑定到作用域，仅在错误追踪时有用。 3. **箭头函数**：如`const dropWhile = (predicate, arr) => {...}`，总是匿名且为表达式，不能直接命名，但可以被引擎推断名称。 箭头函数简洁，但与普通函数不同，没有自己的`this`、`arguments`对象，也不能用作构造函数。选择哪种函数语法取决于具体需求和上下文。

The Evolution of Caching Libraries in Go

作者: maypok86 | 评分: 125 | 评论数: 10 | 发布时间: 2025-06-29 17:07
文章摘要

本文讨论了Go语言中缓存库的演变，特别是on-heap和off-heap缓存的区别与发展。Off-heap缓存避免了GC暂停并减少内存开销，但存在淘汰策略不佳、需要手动转换数据类型等问题，适合不频繁淘汰数据的情况。On-heap缓存则解决了上述问题，但有GC开销。早期Go缺乏高级并发缓存，常用方法是使用锁保护的LRU/LFU地图，并通过分片来解决扩展问题，但这种方法在实际负载中效果有限。 Dgraph Labs在2019年开发的Ristretto库成为Go中领先的on-heap缓存库，借鉴了Java的Caffeine设计，采用了BP-Wrapper、TinyLFU和Doorkeeper等技术提升性能。Ristretto提供了较高的吞吐量和不错的命中率，并引入了MaxCost和per-entry cost来更灵活地管理缓存容量。然而，Ristretto的一个重大变更——自动计算元数据大小——导致了使用 entry count 设置缓存容量的客户端出现问题，这一变化令人困惑且影响了兼容性。

评论摘要
主要讨论点：各类缓存库（如Theine、Ristretto、Otter、Caffeine等）的实现、性能比较及应用场景 不同观点： • [Yiling-J] 作为 Theine 的作者，介绍了 Theine 的开发历程，包括从 Python 版本到 Go 版本的演进。他们提到了参考 Ristretto 实现，并通过采用 Caffeine 的自适应算法来提升命中率。作者认为 Python 社区正在向自由线程方向发展，未来对高性能缓存库的需求将增加，因此考虑重新聚焦 Python 版本的开发。 • [jzelinskie] 对 Yiling-J 在 Otter 上的工作表示感谢，并提到他们一直在使用 Ristretto，但尚未优先考虑尝试 Theine。不过，Otter v2 的新特性可能促使他们进行评估。此外，提到 on-heap 缓存的可移植性，特别是编译到 WebAssembly 的能力，对他们来说很重要。 • [regecks] 寻求一个分布式的 Go 缓存解决方案，希望在多实例运行的情况下实现共享缓存层，以提高效率，并避免理想的网络请求往返。 • [jasonthorsness] 认为缓存的复杂性源于需要适应各种工作负载。如果工作负载是已知的，简单的专用缓存有时能比复杂的库表现更好。 • [coxley] 分享了使用 Otter 两年来的积极体验，并表示计划升级到 Otter v2，特别是为了实现异步刷新功能。 • [wejick] 提到 ccache 是他们常用的缓存库，尤其是在高流量端点场景下使用 LRU 策略。他们询问 Theine 与 ccache 的比较。 • [z0r] 表示希望有一个像 Guava/Caffeine 这样的库让 Go 更像一个“真正的语言”，并对过去几年的发展感到兴趣，计划推荐给团队。 • [nchmy] 询问是否有对 Otter 等库与本地 Redis（通过 localhost/Unix socket）的基准测试比较。 补充讨论： • [yumenoandy] 提到在讨论 S3-FIFO 问题时，可以考虑 TinyUFO（Cloudflare/pingora 项目的一部分）。 争议焦点： • 不同缓存库在各种应用场景下的性能比较，特别是 Theine、Ristretto、Otter 和 Caffeine 之间的选择。 • 关于分布式缓存的需求和实现方式，特别是如何在多实例环境下实现高效的共享缓存层。 总结：讨论围绕多个缓存库的性能、特性及应用场景展开，参与者分享了各自的经验和需求，并对不同缓存库的优劣进行了对比和评价。

本文探讨了贵格会（Quakerism）与禅宗（Zen Buddhism）的共通之处，以及作者在这两种精神实践中的个人体验。作者出生于贵格会家庭，从小参加贵格会的静默礼拜，但一直觉得静坐困难。后来在27岁时接触到佛教，通过禅修技巧学会了如何更好地静坐，并从中获得内心的平静。禅宗强调通过冥想觉悟真实本性，而贵格会则通过集体的静默礼拜寻求和平与共识决策。两者都旨在通过释放自我、减轻痛苦来实现精神转化。作者认为，这两种传统都提供了减轻痛苦、追求和平的途径，尽管方法不同，但最终目标相似。

That XOR Trick (2020)

作者: hundredwatt | 评分: 306 | 评论数: 34 | 发布时间: 2025-06-30 17:32
文章摘要

这篇文章主要介绍如何利用XOR运算符解决一些常见的面试问题，尤其是那些看似需要复杂算法但可以通过XOR简化的问题。XOR是一种位运算，具有以下几个关键性质： 1. **与0的运算**：`x ^ 0 = x`，即任何数与0进行XOR运算结果仍为该数。 2. **相同数的运算**：`x ^ x = 0`，即相同数进行XOR运算结果为0。 3. **交换律**：`x ^ y = y ^ x`，即XOR运算具有交换性。 基于这些性质，文章提出一个核心技巧：在一系列XOR运算中，成对的重复值会相互抵消。利用这个技巧可以解决诸如“在一个包含n-1个1到n之间整数的数组中，找出缺失的数字”的问题。具体方法是对所有数组元素和1到n的所有数进行XOR运算，最终结果即为缺失的数。 文章还介绍了XOR的另一个应用：在不使用额外变量的情况下交换两个数。通过三次XOR运算即可实现两个数的交换。 总的来说，XOR运算因其独特的性质，在解决某些问题时显得非常巧妙和高效。

评论摘要
