文章摘要

微软宣布将大幅优化 WinUI 3 性能，重点改进应用启动时间，并以文件资源管理器和记事本为主要基准。目前文件资源管理器启动中 WinUI 部分已实现：内存分配减少41%、临时分配减少63%、函数调用减少45%、WinUI代码耗时减少25%。改进将陆续进入 winui3/main，并尽可能纳入 WinAppSDK 2.x。部分优化可能涉及破坏性变更，需应用主动选择启用，未来版本或默认开启。

评论摘要
主要讨论点：围绕 WinUI 3/Windows 应用性能优化，评论者讨论了现代 UI 框架变慢、微软质量取向、开发体验与跨平台需求。 不同观点： • 性能批评派：认为 WinUI 3 比 WPF、UWP 慢，连计算器、文件管理器、图片查看器等基础应用都启动慢或卡顿；老技术在资源受限时代反而更高效，现代 UI 像是在“重复发明轮子”且更耗资源。 • 质疑微软方向：有人认为微软在 Windows 11 上“迷失方向”，技术质量只有符合 VP 目标时才被重视；也有人讽刺优化后只是“广告加载更快”。 • 技术原因讨论：有评论指出 WinUI 从客户端代码到屏幕像素经历大量抽象、间接层和通用化流程，怀疑这天然带来成本；也有人认为优化单个组件可能对整体体验帮助有限。 • 支持但期待改进：有人希望微软统一 Windows 应用开发到 WinUI，并大力投入性能和质量；也期待支持 macOS、提供 C 接口便于多语言绑定。 • 开发者体验不满：实际开发者抱怨 WinUI 3 文档差、需要大量 hack、控件实现复杂，甚至要读系统级源码；对用 XML 重写文本框等基础控件感到担忧。 • 跨平台立场：部分人更倾向 Avalonia、EGUI 等跨平台方案，认为 OS 专属软件是兼容性错误；也有人因缺少 F# 支持而继续支持 Avalonia。 • 类比 Apple：有 macOS 用户指出 Finder 在 Apple Silicon 上仍显得慢，认为苹果也应像微软一样关注基础应用性能。 补充讨论：争议焦点在于 WinUI 优化是否能真正改善 Windows 日常体验，以及微软是否会持续重视底层性能而非只做局部优化。

Linux gaming is faster because Windows APIs are becoming Linux kernel features

作者: haunter | 评分: 952 | 评论数: 79 | 发布时间: 2026-05-10 20:54
文章摘要

文章称，Linux 游戏用户在 Steam 占比首次突破5%，受 Windows 10 停止支持和 Steam Deck 推动。Linux 游戏性能提升正从 Wine/Proton 扩展到内核层，NTSYNC 驱动为 Windows 游戏提供原生同步机制，减少开销，显著提升兼容性与速度。

评论摘要
主要讨论点：Linux 游戏生态在 Proton/Wine、NTSync、Steam Deck/Bazzite 等推动下快速成熟，但性能证据、反作弊、驱动与兼容边界仍是争议焦点。 不同观点： • 乐观派认为“Windows 才能玩游戏”的时代正在过去。多位用户表示旧游戏、新游戏和 Mod 环境在 Proton 下已能“点运行即可”，如 ESO 的 Windows 插件客户端、Returnal、Stellar Blade 都运行良好，睡眠恢复等体验也接近主机化。 • 经济与产业角度支持 Linux：云游戏厂商不愿为 Windows 授权付费，因此有动力用 Linux+Proton+Vulkan+AMD 机器串流游戏；Steam Deck 也降低了普通玩家接触 Linux 的门槛。 • 兼容性派强调 Wine/Proton 的价值：Linux 反而成为优秀的 WinAPI 平台，能跑 30 年前 Windows 游戏，甚至 16 位程序；相比之下，原生 Linux 老程序常因依赖库被废弃而无法编译或运行。 • 技术进展派提到 NTSync/Wine 锁机制改进，尤其实现 Win32 事件、信号量、互斥量和 WaitForMultipleObjects，可改善多线程同步性能；也有人预测未来可能发展成类似“Linux Subsystem for Windows”的低开销 NT 内核兼容层。 • 谨慎/怀疑派要求更多数据：不仅要 FPS，还要帧时间、延迟等端到端对比；此前一些测试显示 Linux 仍落后 Windows 5%-30%，且 Nvidia 支持仍有顾虑。 • 最大争议集中在反作弊：BattlEye、Vanguard、Battlefield、Warzone、League 等竞技游戏若不支持 Linux，将阻碍主流玩家迁移，也可能决定市场临界点是否到来。 • 另有用户从历史类比谈兼容层价值：早年 CTOS 通过实现少量 trap 就能跑 DOS 命令行程序，说明接口兼容可带来巨大生态收益。 补充讨论：有人讨论 NTSync 为何不用 epoll/eventfd 形式实现；也有人从情感上表示，转向免费开源后反而更愿意感谢和回馈开源开发者。

评论摘要
主要讨论点：围绕午睡/地中海作息、现代9-5制度与“自然睡眠节律”是否更健康、更灵活展开。 不同观点： • 支持午休/弹性作息：有人认为午后犯困是普遍生理节律，强行保持效率很残酷，导致依赖咖啡；短暂趴睡15分钟会更人性化。也有人希望更多人尝试不同睡眠安排，找到适合自己的节奏。 • 反思“午睡浪漫化”：西班牙用户指出午睡虽有健康益处，但现实中会造成商店关闭、业余活动时间被挤压；若仍工作8小时，午睡会导致早起或晚下班，学校和家庭安排也变得混乱。核心问题是“8小时工作制+午睡”难兼容。 • 赞成地中海式营业时间的便利性：有人喜欢下班后商店、牙医、餐馆仍开放，比美国需要请假理发更灵活；但也承认这对服务业员工不友好。 • 质疑“古代普遍多相睡眠”说法：部分评论认为证据不足，若多相睡眠是前工业社会常态，应能在非工业化社会观察到。另有人引用BBC文章支持几百年前仍有双相睡眠。 • 更综合的睡眠观：有评论指出不同地区和时代睡眠模式并不统一；猎人采集者多为6-7小时连续睡眠，偶尔午睡，但人类睡眠本来就很灵活。现代光污染、设备娱乐可能降低睡眠质量，因此预留更长睡眠窗口仍有意义。 • 批评现代公共服务时间：多人抱怨9-5社会反而不方便工作者，邮局、银行、医疗、商店营业时间与上班冲突，像是在“惩罚”有工作的人。 补充讨论：纬度差异被指出是文章忽略点，北欧与南欧日照节律不同；地中海夏季高温让午睡更合理，但清晨和晚间营业不足仍是障碍。
