RethinkDNS Resolver That Deploys to CF Workers, Deno Deploy, Fastly, Fly.io

作者: indigodaddy | 评分: 102 | 评论数: 4 | 发布时间: 2025-05-03 18:04
文章摘要

**Serverless-DNS** 是一个类似 Pi-Hole 的内容拦截、无服务器 DNS 解析器，支持 DNS-over-HTTPS (DoH) 和 DNS-over-TLS (DoT)。它可以部署在 Cloudflare Workers、Deno Deploy、Fastly Compute@Edge 和 Fly.io 等平台，免费层级足以支持 10 到 20 台设备的 DNS 流量。RethinkDNS 已在多个平台上运行，延迟在 10ms 到 30ms 之间。Cloudflare Workers 是最易于设置的平台，其他平台如 Deno 和 Fastly 也提供了不同的部署选项。设置包括配置拦截列表、环境变量及各平台的开发工具安装。项目代码遵循 Google JavaScript 风格指南，并包含预提交钩子以确保代码质量。支持通过 bearer token 进行 DoH 和 DoT 认证。详细部署指南和代码见项目 GitHub 页面。

评论摘要
主要讨论点：Rethink DNS的实现方式及其性能表现，以及其他替代方案的讨论 不同观点： • [对Rethink DNS性能的质疑] maxloh 对Rethink DNS服务器使用JavaScript实现表示怀疑，认为JavaScript作为性能关键的DNS服务器语言不够理想。他通过基准测试发现Rethink DNS的响应时间在400-500ms，而Cloudflare只需要5-10ms，因此选择了AdAway作为替代方案。 • [对Rethink DNS的兴趣与支持] chrisweekly 对Rethink DNS表示了一定的兴趣，特别是将其与Pi-hole进行类比，并提到Bunny.net作为另一个CDN和云服务提供商，具有可编程DNS的功能。 • [提出dnsdist作为替代方案] karel-3d 提供了dnsdist作为另一种选择，指出它是一个高效的DNS负载均衡器，同时也可以作为stub resolver，支持DoH/DoT，并且资源消耗低。他认为dnsdist的这种用途没有被广泛讨论。 • [对Rethink DNS项目活力的担忧] Onavo 对Rethink DNS移动应用多年未发布新版本表示担忧，并在GitHub上询问项目是否仍然活跃。 补充讨论： • maxloh 提供了具体的基准测试数据来支持其对Rethink DNS性能的质疑，特别是与Cloudflare的对比，显示出显著的性能差异。 • chrisweekly 提到了Bunny.net作为一个新的CDN和服务提供商，扩展了讨论范围，增加了对其他类似服务的兴趣。 • karel-3d 提供了技术细节，强调dnsdist的优点，并指出其作为stub resolver的潜力，尽管其这种用途未被广泛讨论。 • Onavo 提出了对Rethink DNS项目持续发展的关注，质疑其是否仍然在积极维护和开发。 争议焦点：Rethink DNS使用JavaScript实现的性能是否足够好，以及其项目是否仍然活跃。

Creating the Commodore 64: The Engineers' Story

作者: amichail | 评分: 90 | 评论数: 5 | 发布时间: 2025-04-30 01:04
文章摘要

《Commodore 64的诞生：工程师的故事》讲述了这款历史上最畅销电脑的研发过程。1981年1月，MOS Technology的工程师们开始设计图形和声音芯片，最初目标是用于高级电子游戏。然而，在1982年1月拉斯维加斯的消费电子展上，这些芯片被集成到了一台全新的家用电脑——Commodore 64中，售价仅595美元，远低于市场预期。这台电脑拥有64KB内存，超越了当时16KB或32KB的标准配置。工程师们在极短时间内完成了原型设计和生产，并在展会上获得热烈反响。尽管面临质量控制和缓慢磁盘驱动器的批评，Commodore 64凭借其高性价比和强大的图形、声音性能，成功占据市场主导地位，迫使许多竞争对手退出。

主要讨论点：Commodore电脑历史及其相关资源 不同观点： • [crb] 推荐了Commodore International Historical Society网站，认为它是了解Commodore历史的好资源，并提供了一个Amiga面板讨论的YouTube链接（VCF East活动）。 • [sohkamyung] 提到了正在阅读的一本书《Too Much Fun: The Five Lives of the Commodore 64 Computer》，作者是Jesper Juul，并提供了一个该书的链接和一个配套网站，认为这本书对理解C64在游戏、Demoscene及其作为复古电脑的影响很有帮助。 • [jandrese] 对比了旧技术与现代技术，特别指出过去5微米技术芯片在8 MHz时钟频率下耗电1.5瓦，与现代500瓦显卡形成对比，突显了技术进步。 • [hggh] 提供了原始文章的存档链接，指向1985年3月关于Commodore 64的文章，为讨论提供了历史背景资料。 • [rasz] 提到在VCF East 2025有一个Ensoniq扬声器面板，并指出该视频应会被上传至YouTube的某个频道。 补充讨论： • 讨论中涉及多个历史资源链接，包括历史学会、书籍、视频和文章存档，显示出参与者对历史资料的重视。 • 对比旧技术和现代技术的功耗，突显了技术发展的快速和深远影响。 • 提到的活动和视频资源表明，讨论者对实际活动和多媒体内容也有一定关注。 • 尽管观点多样，但讨论者都对Commodore电脑的历史表现出兴趣，并通过不同资源和角度进行探讨。

A PostgreSQL planner semi-join gotcha with CTE, LIMIT, and RETURNING

作者: namanyayg | 评分: 55 | 评论数: 10 | 发布时间: 2025-05-04 01:24
文章摘要

文章描述了在PostgreSQL中使用CTE（Common Table Expression）结合`DELETE ... RETURNING`和`LIMIT`处理队列表时遇到的意外行为。作者原本希望通过CTE查询找到并删除一行任务，并返回相关`item_id`，但由于查询规划器的优化，导致返回了多行。 具体问题在于，PostgreSQL查询规划器将查询转换为一个嵌套循环半连接（Nested Loop Semi Join），导致子查询中的`LIMIT 1`被执行了多次（每次针对外层查询找到的每个候选行）。这与预期的全局`LIMIT 1`不同，造成删除了多行。 该问题具有间歇性，因为规划器的选择取决于统计信息和数据分布。为解决此问题，作者建议避免在`DELETE`条件中使用CTE，而是直接在`WHERE`子句中使用子查询： ```sql DELETE FROM task_queue WHERE id = ( SELECT id FROM task_queue WHERE queue_group_id = 15 LIMIT 1 ) FOR UPDATE; ``` 这样可以确保`LIMIT`在`DELETE`之前全局应用。

评论摘要
主要讨论点：Postgres查询中子查询和CTE的使用及其潜在问题 不同观点： • i_have_to_speak：认为问题与CTE无关，而是由于Postgres对无关联子查询的多次运行导致的。主张不应依赖查询计划的正确性，而应确保查询逻辑正确，比如通过物化CTE或临时表来确保子查询只运行一次。 • impulsivepuppet：对查询中使用`deleted_tasks`命名表示困惑，认为查询逻辑混乱，特别是`FOR UPDATE SKIP LOCKED`部分。质疑如果不使用`SKIP LOCKED`是否能避免问题。 • eknkc：认为这是一个查询规划器的bug，而非小问题。 • swid：对查询是否应删除多行表示不确定，认为查询计划可能导致歧义，期望Postgres只使用单一解释。 • wordofx：质疑作者为何使用CTE而不是直接返回结果。 • clhodapp：认为子查询在每行上重新运行是性能和正确性问题，个人偏好使用CTE而非子查询。 • simonw：对`RETURNING item_id`中的`item_id`来源表示困惑，猜测是未提及的列。 • abhisek：关注如何防止查询优化导致意外结果，建议使用linter或CI工具在生产前检测这些问题。 • Horffupolde：不推荐使用`IN`，建议使用`= ANY`。 • tucnak：认为在`SKIP LOCKED`场景下使用`DELETE`容易出问题，建议仅在`UPDATE`中使用`SKIP LOCKED`。 补充讨论： • 争议焦点在于Postgres查询规划器对子查询的处理是否正确，特别是当子查询被多次运行时可能导致的逻辑错误。 • 不同开发者对如何正确使用CTE、子查询和`SKIP LOCKED`等特性存在不同见解，部分开发者偏好使用特定SQL结构以避免潜在问题。 • 对查询命名和结构的解读存在分歧，部分开发者认为查询结构不清晰或不符合常规用法。 • 提出如何通过工具和实践在开发过程中检测和防止此类问题，以提高代码的健壮性和可维护性。
